# 세션 노트 양식 — `para/resources/session/S-NNN-<slug>.md`

컨퍼런스·밋업 발표 하나를 **다시 발표를 보지 않아도 사례와 경험을 이해할 수 있는 노트 한
장**으로 만든다. 슬라이드 순서 요약이 아니라, 발표가 다룬 문제와 해결 경험을 사례 단위로
재구성하는 문서다.

작성 전에 다음을 읽는다.

1. `para/resources/resource.md`의 `session/` 규약 — 경로·원본·불변성의 SoT
2. `para/resources/session/assets/S-NNN/reconstruction.md` — 이 노트가 사용할 발표 근거
3. 기존 concept를 연결하거나 후보를 판단할 때만 `para/areas/area.md`의 concept 규약과 맵

`reconstruction.md`가 없으면 최종 세션 노트부터 만들지 않는다. 먼저 녹취·음성·사진을
교차 검증해 발표를 복원한다.

## 이 문서의 역할

- 발표 전체를 **문제 → 만든 개념 → 적용과 아키텍처 → 결과와 한계**로 읽히게 만든다.
- 발표에서 다른 업무에도 옮겨갈 경험을 추상화하고, concept로 올릴 후보와 조건을 남긴다.
- 발표가 출발점이 된 단위 개념을 더 조사할 공식 자료로 연결한다.

다음은 하지 않는다.

- 슬라이드마다 내용을 다시 옮기지 않는다 — 시간순 근거는 `reconstruction.md`가 갖는다.
- 발표 사진을 본문에 나열하지 않는다 — 구조는 표와 Mermaid로 다시 그린다.
- 발표에 없는 성과·수치·내부 구조를 일반론이나 웹 자료로 채우지 않는다.
- 제품 기능 목록을 핵심 개념이나 참고 자료 목록으로 만들지 않는다.
- frontmatter를 넣지 않는다. 제목과 출처 줄이 문서의 머리다.

---

## 머리

```markdown
# <발표의 경험을 드러내는 제목> — <회사·조직>

> 출처: <행사명> · YYYY-MM-DD · HH:MM:SS 또는 MM:SS
```

- 원래 발표 제목을 그대로 복사하기보다 무엇을 해결한 발표인지 드러낸다.
- 행사·날짜·발표 길이는 `reconstruction.md`와 일치시킨다.
- 발표자·소속은 출처 줄에 중복하지 않고 `1.1 발표 정보`에 둔다.
- 모르는 값은 추정하지 말고 `미확인`으로 적는다.

---

## 1. 개요

### 1.1 발표 정보

```markdown
## 1. 개요

### 1.1 발표 정보

| 항목 | 내용 |
| --- | --- |
| 어떤 발표였나 | <문제·접근·적용 대상을 한 문장으로> |
| 어디서 들었나 | <행사명> |
| 언제 들었나 | YYYY-MM-DD |
| 발표자 | <이름 또는 미확인> |
| 소속 | <회사와 팀·조직. 발표 사례의 신뢰 범위를 판단할 수 있게> |
| 발표 길이 | <N분 N초> |
```

`어떤 발표였나`는 기술 이름을 나열하지 않는다. 누가 어떤 업무 문제를 어떤 구조로 풀었는지
한 문장으로 쓴다. 사례 발표는 발표자의 **회사와 소속 조직을 반드시** 남긴다.

### 1.2 핵심 흐름

발표의 목차가 아니라 **문제가 해결되는 논리 흐름**을 Mermaid로 그린다.

````markdown
### 1.2 핵심 흐름

```mermaid
flowchart LR
    P["문제<br/>업무에서 막힌 지점"]
    C["만든 개념<br/>공통 기준이나 해결 원리"]
    A["적용<br/>데이터 · 시스템 · 역할 구성"]
    R["결과<br/>구현·운영된 변화"]
    P --> C --> A --> R
```
````

- 기본 방향은 `LR`이다.
- 한 줄은 5개 안팎의 노드로 제한한다. 8~10개를 한 줄에 넣어 글자를 읽을 수 없게 만들지
  않는다.
- 사례가 여러 개면 사례별 `flowchart LR`를 따로 만들거나 논리 단계별로 두 줄로 나눈다.
- 노드에는 한 개념만 넣고, 설명은 두 줄을 넘기지 않는다.
- 발표에서 확인되지 않은 연결은 그리지 않는다.

### 1.3 핵심 개념

발표를 이해하는 데 꼭 필요한 개념만 고른다. `키워드 : 설명`처럼 짧게 읽혀야 하며, 긴 일반론
교안이 되어서는 안 된다.

```markdown
### 1.3 핵심 개념

#### <핵심 개념명>

<이 발표에서 이 개념이 무엇을 뜻했고 어떤 문제를 푸는 데 쓰였는지 1~2문단>
```

- 제품 기능보다 발표가 세운 **업무 기준·판단 구조·역할 경계**를 우선한다.
- 이미 concept 문서가 있으면 `[[concept-stem]]`으로 연결하고, 여기에는 이 발표에서 맡은 역할만
  적는다. concept의 일반 정의를 다시 길게 쓰지 않는다.
- 새 후보라면 발표자가 사용한 의미까지만 설명한다. 외부 일반론을 발표자의 정의처럼 섞지
  않는다.
- 개념 사이의 대조나 역할 분담이 중요하면 짧은 표를 사용한다.

## 2. 사례 상세

사례마다 문제·개념·적용·결과를 한 묶음으로 쓴다. 독자가 `문제 1`을 읽고 다른 절을 오가며
해결 방법을 찾아야 하는 구조로 만들지 않는다.

````markdown
## 2. 사례 상세

### 2.1 <문제와 해결 방향이 드러나는 사례 제목>

#### 2.1.1 문제

<어떤 조직·업무에서 무엇이 막혔는가. 기존 방식과 그로 인한 비용·오류·판단 불일치>

#### 2.1.2 해결 접근

<문제를 어떤 관점으로 다시 정의했고 어떤 개념·기준을 만들었는가>

#### 2.1.3 적용과 아키텍처

<데이터·도구·Agent·Program·사람·사용자 접점의 역할과 연결>

| 구성 또는 계층 | 구성요소 | 역할 |
| --- | --- | --- |
| <이 발표의 실제 구분> | <확인된 구성요소> | <무엇을 책임지는가> |

```mermaid
flowchart LR
    INPUT["입력"] --> CORE["핵심 처리·판단"] --> OUTPUT["업무 결과"]
```

#### 2.1.4 결과와 한계

<실제로 구현·공개·사용·측정된 결과>

<비공개 수치, 데모 범위, 발표자의 주장에 그친 효과, 확인할 수 없는 지점>

### 2.2 <다음 사례 제목>

<같은 네 절을 필요한 사례 수만큼 반복>
````

### 문제 작성법

- 기술 기능이 없었다는 말보다 **실제 업무가 어디서 느려지고 달라지고 끊겼는지** 쓴다.
- 기존 흐름, 참여자, handoff, 수작업, 판단 불일치를 구체적으로 적는다.
- 회사·업무 규모의 수치는 발표에 나온 것만 사용한다.

### 해결 접근 작성법

- 어떤 제품을 도입했다는 사실보다 문제를 풀기 위해 **어떤 기준과 책임을 새로 만들었는지**
  설명한다.
- 발표 개념이 기존 용어와 다른 의미로 쓰였다면 발표 안에서의 정의를 먼저 둔다.
- 해결 접근과 실제 구현을 섞지 않는다. 여기서는 선택한 원리와 판단을 설명한다.

### 적용과 아키텍처 작성법

- 표는 구성요소의 **역할 대조**, Mermaid는 **흐름과 관계**를 보여줄 때 쓴다. 같은 내용을
  표와 Mermaid에 중복하지 않는다.
- 구성요소 나열로 끝내지 말고 데이터, 판단, 실행, 검증 책임이 어디로 이동하는지 설명한다.
- Mermaid는 가로 흐름을 우선하되, 노드가 많으면 입력·처리·검토·개선처럼 논리 묶음으로
  나눈다.
- 사진 속 복잡한 구조를 단순화할 때 핵심 연결을 지우거나 새 연결을 만들지 않는다.

### 결과와 한계 작성법

결과는 다음 수준을 구분한다.

| 표현 | 쓸 수 있는 근거 |
| --- | --- |
| 구현했다 | 발표 자료에서 화면·구조·동작이 확인됨 |
| 공개·운영했다 | 발표자가 실제 공개나 운영을 명시함 |
| 사용됐다 | 사용자·사용 범위·현업 반응이 구체적으로 제시됨 |
| 개선됐다 | 전후 수치와 측정 조건이 제시됨 |

발표자가 효과를 설명했지만 측정 조건이 없으면 `발표자는 ...라고 설명했다`로 귀속한다. 정확도,
사용률, 비용 절감액이 공개되지 않았으면 그 사실도 결과와 같은 문단에 남긴다. 슬라이드와 발화의
수치가 충돌하면 어느 쪽도 임의로 선택하지 않는다.

## 3. 적용할 경험

이 절은 발표 내용을 다시 요약하는 곳이 아니다. 발표의 구체적인 구현을 다른 업무에도 적용할
수 있는 개념 후보로 바꾸는 **추출 대기열**이다.

```markdown
## 3. 적용할 경험

| 발표에서 나온 개념 | 추상화·일반화 | 적용 조건·제약 | 추출할 concept 이름 |
| --- | --- | --- | --- |
| <발표의 구체적 접근> | <다른 도메인에도 남는 원리> | <성립 조건·실패 조건·운영 비용> | `<concept-slug>` — 신규 후보 |
| <기존 concept를 넓히는 경험> | <추가되는 일반 원리> | <적용 한계> | `<concept-slug>` — 기존 concept 보강 후보 |
```

각 행은 다음 변환을 보여줘야 한다.

```text
발표의 구체적 구현 → 맥락을 걷어낸 일반 원리 → 적용 조건과 제약 → concept 후보
```

- 추상화하면서 회사명·제품명만 지우지 않는다. 다른 업무에도 성립하는 **판단 기준**을 뽑는다.
- 적용 조건·제약을 반드시 적는다. 조건을 지운 교훈은 어느 상황에도 맞는 상투어가 된다.
- concept 이름은 영문 kebab-case stem 후보로 쓴다.
- 실제 concept 맵을 확인해 `신규 후보`와 `기존 concept 보강 후보`를 구분한다.
- 이 절에서는 concept 파일을 만들지 않는다. 승격은 별도 작업이다.

---

## 4. 참고 자료

3절 후보 중 더 알아야 하는 **단위 개념**만 고른다. 발표에 나온 제품 기능 사용법은 제외한다.

```markdown
## 4. 참고 자료

| 단위 concept | 이 발표에서 시작된 질문 | 더 조사할 범위 | 추천 자료 |
| --- | --- | --- | --- |
| `<concept-slug>` | <발표만으로 답하지 못한 핵심 질문> | <정의·구성·경계·검증 범위> | [기관·문서명](직접 URL) |
```

- 추천 자료는 공식 문서, 표준, 원 논문, 공공기관 가이드처럼 1차 자료를 우선한다.
- 검색 결과나 블로그 목록이 아니라 해당 내용을 직접 설명하는 페이지로 연결한다.
- 한 concept에 링크를 많이 모으지 않는다. 정의와 적용 경계를 가장 잘 설명하는 1~2개면 된다.
- 제품 문서는 그 제품의 기능이 아니라 일반 개념의 정식 정의를 제공할 때만 사용한다.
- 발표 사례와 외부 자료를 섞지 않는다. 외부 자료는 일반 개념의 후속 조사 경로일 뿐, 회사가
  실제로 그렇게 구현했다는 근거가 아니다.
- 신뢰할 1차 자료를 찾지 못하면 링크를 지어내지 말고 `조사 필요`로 남긴다.

## 문장과 검증

- 핵심부터 말하고 문단은 2~4문장으로 끊는다. 긴 줄글보다 표·짧은 소제목을 사용한다.
- `혁신적`, `강력한`, `획기적` 같은 평가어를 쓰지 않는다. 무엇이 어떻게 달라졌는지 적는다.
- 발표자의 표현, 문서 작성자의 일반화, 외부 자료의 정의를 서로 구분한다.
- 같은 개념 설명을 1.3, 사례 상세, 적용할 경험에서 반복하지 않는다.
  - `1.3`: 발표를 이해하기 위한 짧은 의미
  - `2`: 실제 사례에서 어떻게 쓰였는지
  - `3`: 다른 업무로 옮길 일반 원리와 조건
- 완성 후 `reconstruction.md`와 이름·숫자·기간·구성요소·결과를 다시 대조한다.
- 모든 사례가 `문제 → 해결 접근 → 적용과 아키텍처 → 결과와 한계`를 갖는지 확인한다.
- `para/resources/resource.md`의 맵 등록은 이 문서 작성이 끝난 뒤 별도 작업으로 한다.
