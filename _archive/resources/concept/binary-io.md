# 바이너리 입출력 (Binary I/O)

**값을 사람이 읽는 문자로 바꾸지 않고, 타입마다 정해진 비트 표현 그대로 주고받는 것.** 같은 통로([[io-stream]])를 쓰지만 통로에 흘려보내는 것이 「`20` 이라는 두 글자」가 아니라 「정수 20 의 4바이트」다.

## 정의

Day38 이 「타입별로 인코딩하는 방식이 다르다」로 적은 표가 이 방식의 내용 전부다 — **타입마다 규칙이 따로 있고, 그 규칙은 새로 만든 것이 아니라 그 값이 메모리에서 이미 쓰고 있는 표기다.**

| 값 | 바이트로 바뀌는 규칙 |
|---|---|
| `"abc"` | UTF-8 문자코드 바이트 → [[character-encoding]] |
| `20` | 2의 보수 → [[twos-complement]] |
| `3.14` | IEEE-754 → [[floating-point]] |
| `true` | (필기는 2의 보수라 적었다 — 아래 「경계와 오해」) |

그래서 이 방식의 특징 셋도 필기가 적은 그대로다 — 「메모리를 적게 사용하고 속도가 빠르다」, 「설정 방법이 복잡하다」, 그리고 결과물이 「PDF, PPT, DOC, GIF, JPEG, MP3, AVI」 같은 것이 된다.

## 사용 예시

Day38 이 `int` 하나를 파일에 내보내는 코드가 이 방식의 최소 단위다.

```java
    ByteArrayOutputStream out = new ByteArrayOutputStream()
    out.write(no >> 24);
    out.write(no >> 16);
    out.write(no >> 8);
    out.write(no);
```

**네 줄이 나가고 파일에는 정확히 4바이트가 남는다.** 회원 번호가 `1` 이든 `2000000000` 이든 4바이트다 → [[bit-shift]]

같은 값을 텍스트로 내보내면 이렇게 된다.

```java
    out.write(String.valueOf(no).getBytes());   // "1" → 1바이트, "2000000000" → 10바이트
```

**둘의 차이가 이 개념의 두 얼굴이다.** 바이너리 쪽은 크기가 값에 상관없이 일정해서 읽는 쪽이 「4바이트를 떼면 된다」로 끝나고, 텍스트 쪽은 어디까지가 한 숫자인지 표시할 것이 따로 필요하다. 반대로 바이너리 쪽은 `1` 을 저장하는 데도 4바이트를 쓴다 → [[length-prefix-framing]]

문자열은 규칙이 하나 더 붙는다 — **어떤 인코딩으로 바이트를 만들지 코드가 정해 준다.**

```java
      byte[] bytes = name.getBytes(StandardCharsets.UTF_8);
```

Day22 에서 `new String(bytes, "utf-8")` 로 **읽는** 쪽을 정했던 것의 반대 방향이고, 이번에는 문자열 리터럴이 아니라 `StandardCharsets` 상수로 넘긴다 → [[character-encoding]]

### 하루 뒤 — 「타입별로 인코딩하는 방식이 다르다」를 클래스가 대신 안다

Day39 는 위의 네 줄을 지우고 한 줄로 바꾼다.

```java
        out.writeInt(user.getNo());
        out.writeUTF(user.getName());
```

Day38 의 표(「`"abc"`→UTF-8, `20`→2의 보수, `3.14`→IEEE-754」)가 **메서드 이름 목록으로 나타난 것**이 `DataOutputStream` 이다 — `writeInt`·`writeUTF`·`writeDouble`·`writeBoolean` 이 그 표의 칸마다 하나씩 있다. Day39 가 「Int,UTF,IEE-754를 읽어온다」로 세 타입을 나열한 것이 그 표를 다시 부른 것이고, **바이너리 입출력에서 「형식을 정한다」가 「어느 메서드를 부를지 정한다」로 바뀐다** → [[data-io-stream]]

그리고 Day38 이 코드 순서에만 두고 있던 **바이트 순서가 여기서 규격이 된다** — `DataOutputStream` 은 상위 바이트를 먼저 쓰는 것(big-endian)을 문서로 못 박는다. 「네 줄의 순서를 뒤집으면 little-endian 이 된다」던 선택의 여지가 없어지는 대신, **두 프로그램이 같은 기준을 갖는다.**

## 왜 중요한가

**프로그램이 끝나도 데이터가 남는 첫 경로다.** Day19 에 만든 회원 번호는 「번호가 안정적인 범위는 한 번의 실행 안」이었다 — 끄면 목록과 카운터가 함께 사라지고 다시 1번부터였다. 파일에 바이트를 적기 시작하면서 그 한계가 풀리고, 대신 **저장한 형식을 지켜야 하는 새 책임**이 생긴다 → [[surrogate-key]] · [[serialization]]

**구분자를 고민하지 않아도 된다.** 텍스트로 저장하면 「어디까지가 이름인가」를 표시해야 하고, 그 표시(콤마·탭·줄바꿈)가 데이터에 들어갈 수 있으므로 이스케이프 규칙이 따라온다. 바이너리에서는 길이를 먼저 적어 두면 **내용이 어떤 바이트든 상관없다** → [[length-prefix-framing]]

**변환 비용이 없어진다.** 텍스트로 쓰려면 `int` → 10진 문자열 → 바이트로 두 번 바꾸고, 읽을 때 `Integer.parseInt` 로 되돌려야 한다. 바이너리는 이미 그 모양인 비트를 옮긴다. 「빠르다」의 실체가 크기가 아니라 **이 변환이 사라지는 것**이다 → [[number-parsing]]

## 경계와 오해

- **`true` 는 2의 보수로 저장되지 않는다** — 2의 보수는 **음수를 표현하는 방법**이고 `boolean` 에는 음수가 없다. `DataOutputStream.writeBoolean` 은 `1` 또는 `0` 을 1바이트로 쓴다. 표의 나머지 셋은 각각 맞는 규칙인데 이 한 줄만 앞 줄(`20`)에서 따라왔다 → [[twos-complement]]
- **`20` 을 「2의 보수」라 적는 것은 반만 맞다** — `int` 가 **2의 보수 체계의 타입**인 것은 맞지만, 양수 20 의 비트는 그냥 이진수 `10100` 이고 보수를 취하는 일이 일어나지 않는다. 2의 보수가 실제로 하는 일은 `-20` 을 적을 때 나타난다. 「타입별 인코딩」 표에서 정수 칸에 적을 이름은 「2의 보수(부호 있는 고정 길이 정수)」이지 「2의 보수를 구한다」가 아니다.
- **바이너리 입출력 ≠ 항상 작다** — 값에 따라 뒤집힌다. 회원 번호 `1` 은 텍스트로 1바이트, 바이너리로 4바이트다. Day38 의 실습이 정확히 그 구간에 있다 — 회원이 몇 명뿐이라 `no` 는 늘 한 자리이고, **4바이트를 쓰는 것이 손해인 상태로 저장하고 있다.** 이득이 나는 것은 자릿수가 타입 크기를 넘어설 때이고, 문자열(`"abc"`)은 어느 방식이든 같은 바이트다.
- **바이너리 파일 ≠ 바이너리 입출력** — 「PDF, JPEG, MP3」는 **이 방식으로 만들어진 파일 형식**이지 방식 자체가 아니다. 같은 `FileOutputStream` 으로 텍스트 파일도 쓸 수 있고, JPEG 을 Base64 로 바꿔 텍스트 파일에 담을 수도 있다. 가르는 축은 「무슨 확장자인가」가 아니라 **「사람이 읽는 문자로 바꿨는가」**다.
- **바이트 순서를 아무도 정해 주지 않는다** — `no >> 24` 를 **먼저** 쓰는 것이 상위 바이트부터 나간다는 뜻(big-endian)이고, 네 줄의 순서를 뒤집으면 little-endian 이 된다. **둘 다 컴파일되고 둘 다 「바이너리」다.** 맞고 틀림은 읽는 쪽이 같은 순서로 조립하는지가 정하는데, 그 약속은 `getBytes()` 와 `valueOf()` 두 메서드에 흩어져 있고 코드 어디에도 적혀 있지 않다. 필기의 「타입별로 인코딩하는 방식이 다르다」에는 이 축이 없다 — **타입만 알면 바이트가 정해지는 것이 아니다** → [[serialization]]
- **바이너리라고 플랫폼 독립인 것은 아니다** — 위의 바이트 순서와 타입 크기가 기계마다 다를 수 있다. Java 는 `int` 를 4바이트로 못 박고 표준 `DataOutputStream` 이 big-endian 을 고정해 이 문제를 언어가 막아 주지만, **C 로 쓴 파일을 읽을 때는 다시 나타난다.** 텍스트 파일이 인코딩에서 같은 문제를 겪는 것과 짝이다 → [[platform-dependency]]
- **사람이 못 읽는 것이 이 방식의 대가다** — 텍스트 파일은 열어서 눈으로 확인하고 손으로 고칠 수 있는데 `user.data` 는 열어도 알 수 없다. 규칙을 한 곳 어긋나게 짜면 **틀린 결과만 보이고 어디가 틀렸는지 안 보인다.** 그래서 Day38 이 §4 「데이터 구조」와 §5·§6 에 그림을 남긴 것이 취향이 아니라 **필수 문서**다 — 바이너리 형식에서 그 그림이 유일한 사양서다.
- **「설정 방법이 복잡하다」는 이 방식의 성질이 아니라 도구 선택의 결과였다** — Day38 이 세 줄로 정리한 특징 중 앞의 둘(작다·빠르다)은 방식의 성질이지만, **셋째는 하루 뒤에 사라진다.** `writeInt`·`writeUTF` 를 쓰면 설정할 것이 없고 코드는 텍스트로 쓰는 것보다 짧다. 「복잡하다」의 실체는 **「타입별 규칙을 손으로 짜면 복잡하다」**였고, 그 규칙을 갖고 있는 층(`DataOutputStream`)이 표준에 이미 있었다 → [[data-io-stream]]
- **표준 도구로 바꿔도 「사람이 못 읽는다」는 그대로다 — 그래서 다음 절이 텍스트로 간다** — `writeUTF` 로 쓴 `user.data` 도 열어서 확인할 수 없다. Day39 가 §2 에서 Object I/O 까지 간 뒤 §3 에서 CSV 로 내려가는 것이 그 대가를 지불하지 않기로 한 선택이고, **형식을 고르는 축이 「크기·속도」만이 아니라 「고장났을 때 눈으로 볼 수 있는가」**라는 것이 두 절을 나란히 놓으면 드러난다 → [[csv]] · [[character-stream]]
- **「설정 방법이 복잡하다」의 실체는 코드 양이 아니라 대칭이다** — 복잡한 것은 `write` 를 네 번 부르는 일이 아니라, **읽는 쪽에 정확히 거울인 코드가 하나 더 있어야** 한다는 것이다. 텍스트라면 형식을 조금 어겨도 사람이 보고 고칠 수 있는데 여기서는 한쪽만 고치면 조용히 어긋난다 → [[serialization]]
