# 멱등성 (Idempotency)

**같은 요청을 몇 번 보내도 결과가 한 번 보낸 것과 같은 성질.** 두 번 오지 않게 막는 것이 불가능한 자리에서, **두 번 와도 같게** 만드는 쪽으로 문제를 뒤집는 것이다.

## 정의

```
[멱등하지 않다]  결제 요청 ×2 → 두 번 청구된다
[멱등하다]       결제 요청 ×2 → 첫 번째만 반영, 두 번째는 같은 결과를 돌려준다
```

**요청에 「그 사건을 가리키는 이름」을 붙이는 것**이 실제 구현이다. 새로 만드는 값이 아니라 **같은 사건이면 같은 값이 나오는** 것이어야 한다.

| 무엇을 키로 쓰나 | 어디서 |
|---|---|
| `drive_file_id` | 외부 시스템이 준 식별자 |
| `transaction_id` | 결제 사업자가 준 거래 번호 |
| `email` | 시드 데이터의 자연키 |

그리고 그 키에 **유일 제약**을 건다 → [[unique-key]]

## 왜 중요한가

**재시도가 필연인 자리가 있다.** 네트워크는 끊기고 webhook 은 중복 발송하며 웹소켓은 재연결한다. **「정확히 한 번」은 대개 만들 수 없어서**, 실무의 답은 「여러 번 와도 한 번처럼」이다 → [[transport-layer]]

**그래서 경로를 이중화할 수 있다.** 같은 결과를 여러 경로로 받아도 안전하다는 것이 보장돼야, 「client 가 직접 확인 + webhook」처럼 **둘 다 받는 설계**가 가능해진다.

## 경계와 오해

- **읽기는 원래 멱등이다** — 문제는 쓰기, 그리고 쓰기에 딸린 **부작용**(발송·결제·알림)이다. 상태만 같아지고 메일이 두 번 나가면 멱등이 아니다
- **upsert 가 멱등의 전부는 아니다** — 「덮어쓴다」와 「같은 결과를 낸다」는 다르다. 두 번째 요청이 **더 오래된 값**을 들고 오면 upsert 는 상태를 되돌린다. 순서를 함께 봐야 한다 → [[optimistic-lock]]
- **애플리케이션 검사만으로는 뚫린다** — 「있으면 건너뛴다」를 코드에서 해도 **동시에 두 개가 들어오면** 둘 다 통과한다. 최종 방어선은 DB 의 유일 제약이다 → [[unique-key]] · [[transaction]]
- **키를 요청마다 새로 만들면 의미가 없다** — UUID 를 매번 새로 뽑으면 재시도가 새 사건이 된다. **같은 사건이면 같은 키**여야 한다
- **재시도 자체가 부하를 늘린다** — 멱등하다고 무한정 다시 보내면 상대를 더 밀어붙인다. 물러설 줄 아는 재시도와 함께 가야 한다 → [[async-io]]
