# 영속성 컨텍스트 (Persistence Context)

**엔티티를 DB 에 보내기 전까지 들고 있는 메모리 공간.** `EntityManager` 가 관리하며, 여기에 담긴 객체는 **DB 의 그 행과 이어져 있다.**

## 정의

성질이 넷이고 서로 맞물린다.

| 성질 | 무엇 |
|---|---|
| **1차 캐시** | 같은 트랜잭션에서 같은 것을 또 조회하면 **DB 에 안 간다** → [[caching]] |
| **변경 감지**(더티체킹) | 담긴 엔티티의 값이 바뀌면 **커밋할 때 자동으로 `UPDATE`** 가 나간다 |
| **지연 로딩** | 연관된 것을 **쓸 때까지** 안 읽는다 |
| **동일성 보장** | 같은 트랜잭션에서 같은 행을 조회하면 **같은 인스턴스**가 온다 → [[object-equality]] |

**저장 메서드를 부르지 않아도 수정이 반영된다**는 것이 가장 낯선 지점이다.

```java
@Transactional
public Post modify(Long id) {
    Post post = postRepository.findById(id).orElseThrow();
    post.setUsername(post.getUsername() + "!");   // save() 를 안 부른다
    return post;                                   // 커밋 시점에 UPDATE 가 나간다
}
```

**트랜잭션이 곧 이 공간의 수명**이다 — 시작할 때 열리고 끝날 때 비워지며, 그때 쌓인 변경이 한 번에 나간다 → [[transaction]] · [[declarative-transaction]]

## 왜 중요한가

**「객체를 고치면 DB 가 바뀐다」가 성립하려면 중간에 이것이 있어야 한다.** SQL 을 직접 쓰던 방식에서는 `UPDATE` 를 부르는 것이 곧 반영이었는데, 여기서는 **바뀐 것을 누군가 알아채야** 한다 → [[persistence-framework]] · [[dao-pattern]]

**그리고 같은 것을 여러 번 읽어도 한 번만 나간다.** 한 요청 안에서 같은 엔티티를 여기저기서 조회하는 코드가 **질의를 늘리지 않는다** — 계층을 나눈 대가를 이 캐시가 상쇄한다 → [[service-layer]]

## 경계와 오해

- **이 공간의 경계가 트랜잭션이라는 것이 모든 함정의 뿌리다** — 트랜잭션 밖에서 꺼낸 엔티티는 **더 이상 연결돼 있지 않다.** 값을 바꿔도 저장되지 않고, 아직 안 읽은 연관을 만지면 예외가 난다 → [[osiv]]
- **1차 캐시는 트랜잭션 하나짜리다** — 요청이 끝나면 사라지므로 **서버 전체의 캐시가 아니다.** 「JPA 를 쓰면 캐시가 된다」로 읽으면 틀린다 → [[caching]]
- **변경 감지는 편한 만큼 위험하다** — 조회해 온 엔티티의 값을 무심코 바꾸면 **의도 없이 `UPDATE` 가 나간다.** 조회 전용 메서드에 `@Transactional(readOnly = true)` 를 붙이는 이유가 그것이다 — 감지 자체를 끈다
- **동일성 보장은 트랜잭션 안에서만이다** — 다른 트랜잭션에서 읽은 것과는 다른 인스턴스이므로, `==` 로 비교하면 안 된다 → [[object-equality]]
- **지연 로딩이 N+1 의 씨앗이다** — 나중에 읽는다는 것은 **목록을 돌면서 하나씩 읽는다**는 뜻이 될 수 있다 → [[n-plus-one]]
- **쌓아 두었다가 한 번에 보낸다는 것도 알아야 한다** — 예외가 나는 시점이 **값을 바꾼 줄이 아니라 커밋 시점**일 수 있다. 원인과 증상이 떨어진다 → [[exception-handling]]
