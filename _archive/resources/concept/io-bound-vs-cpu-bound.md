# I/O 바운드와 CPU 바운드

**기다리느라 느린 것과 계산하느라 느린 것은 처방이 다르다.** 어느 쪽인지 모르고 손대면 아무것도 안 바뀐다.

## 정의

| | I/O 바운드 | CPU 바운드 |
|---|---|---|
| 시간이 어디로 가나 | **응답을 기다리는 데** | **연산하는 데** |
| 그동안 CPU 는 | **논다** | **꽉 찬다** |
| 예 | DB 질의 · 외부 API · 파일 읽기 · 네트워크 | 수학 계산 · 이미지/영상 처리 · 암복호화 |
| 처방 | **비동기 · 동시 실행** | **코어를 더 쓰기 · 알고리즘 바꾸기** |

**비동기가 듣는 것은 왼쪽뿐이다.** 기다리는 시간이 있어야 그 틈에 다른 일을 시킬 수 있고, 계산 중에는 내줄 틈이 없다 → [[async-io]]

```python
# 3. 백테스트 실행 (CPU 집약적 작업은 동기로)
backtest_results = self._run_backtest_calculation(...)
```

필기가 **비동기 코드 한가운데에 동기 함수를 일부러 둔** 자리다 — 「전부 비동기로」가 아니라 **성격에 맞게 가른다**는 것이 요점이다.

## 왜 중요한가

**같은 「느리다」에 정반대 처방이 붙는다.** I/O 바운드에 코어를 늘리면 노는 CPU 만 늘고, CPU 바운드에 `async` 를 붙이면 **이벤트 루프가 통째로 멈춘다** — 오히려 남의 요청까지 막는다.

**그리고 어느 쪽인지는 재면 안다.** 처리량이 안 오르는데 CPU 사용률이 낮으면 왼쪽이고, CPU 가 이미 100% 면 오른쪽이다 → [[monitoring]] · [[performance-testing]]

## 경계와 오해

- **「간단한 CRUD 는 비동기가 불필요」는 성격이 아니라 정도의 문제다** — 필기가 그렇게 분류했지만 **DB 조회도 캐시 조회도 엄연히 I/O 바운드**다. 짧아서 효과가 작을 뿐 성격이 다른 것이 아니고, 동시 접속이 많아지면 **그 짧은 대기가 쌓여** 워커가 마른다 → [[async-io]]
- **CPU 바운드를 비동기로 감싸면 더 나빠진다** — 이벤트 루프를 쥔 채 계산하면 그 프로세스의 **모든 요청이 함께 멈춘다.** 별도 프로세스나 워커로 빼는 것이 답이다 → [[process]]
- **동시성과 병렬성은 다른 말이다** — 기다리는 것을 겹쳐 진행하는 것(동시성)은 코어 하나로도 되고, 계산을 진짜로 나눠 도는 것(병렬성)은 **코어가 있어야** 된다 → [[thread]]
- **한 요청 안에 둘이 섞여 있는 것이 보통이다** — API 를 부르고(I/O) 결과를 가공한다(CPU). **긴 쪽이 무엇인가**로 판단하고, 둘 다 길면 나눠서 다뤄야 한다
- **메모리·디스크 대역폭이 범인인 경우도 있다** — CPU 도 안 차고 네트워크도 안 기다리는데 느리면 이 둘을 본다. 두 갈래로만 나누는 분류가 놓치는 자리다
