# JVM 스택과 스택 프레임 (JVM Stack)

메서드를 호출하면 [[jvm]] 이 스택 메모리에 **프레임 하나**를 쌓고, 그 메서드가 끝나면 프레임을 버린다. 매개변수와 지역 변수가 사는 자리가 이 프레임이고, **메서드가 끝날 때 그 변수들이 사라지는 이유**가 이것이다.

## 정의

프레임의 생성·소멸 시점은 두 낱말로 고정되어 있다.

```text
매서드가 호출 되면 JVM stack 메모리 영역에 메서드 Frame이 생성
LIFO 구조로 순차적으로 호출 및 종료 된다.
JVM stack 영역에 메서드가 call이 있으면 생성을 하고 return이 있으면 삭제를 한다.
```

| 시점 | 스택에서 일어나는 일 |
|---|---|
| `call` | 프레임 생성 — 매개변수와 지역 변수의 자리가 여기 잡힌다 |
| `return` (또는 블록 종료) | 프레임 삭제 — 그 자리의 변수는 함께 사라진다 |

**LIFO** 인 것은 규칙이 아니라 결과다. 나중에 부른 메서드가 먼저 끝나야 부른 쪽으로 돌아갈 수 있으므로, 가장 위 프레임만 제거 대상이 된다.

## 사용 예시

이 필기의 배열 전달 예제를 프레임으로 보면 **스택에 있는 것과 힙에 있는 것**이 갈린다.

```java
public class Test09 {
  public static void main(String[] args) {
    int[] values = new int[] {100, 110, 120};
    m1(values);                          // main 프레임 위에 m1 프레임이 쌓인다
    System.out.println(values[0]);       // m1 프레임은 이미 사라졌다 — 그런데 200 이 찍힌다
  }

  static void m1(int[] value) {
    value[0] = 200;
  }
}
```

```text
[ m1 프레임   ] value  ─┐        (call 때 생기고 return 때 사라진다)
[ main 프레임 ] values ─┼──▶ 힙: { 200, 110, 120 }
                        └─ 두 프레임의 변수가 같은 인스턴스를 가리킨다
```

`m1` 의 `value` 는 프레임과 함께 없어지지만 **힙의 배열 인스턴스는 남는다.** `main` 이 아직 그것을 가리키고 있기 때문이다 → [[instance]] · [[call-by-value]]

## 왜 중요한가

**"지역 변수의 수명"이라는 말이 이 그림 없이는 외울 것이 된다.** 프레임이 곧 수명의 경계다. 그래서 다른 메서드의 지역 변수를 볼 수 없고, 메서드가 끝난 뒤 그 값을 쓰려면 `return` 으로 내보내야 한다. 매개변수도 지역 변수라는 사실이 여기서 따라 나온다 → [[parameter-and-argument]]

두 번째는 **스택이 유한하다**는 것이다. 프레임이 쌓이는 깊이에 한계가 있어서, 호출이 너무 깊어지면 `StackOverflowError` 로 죽는다. 이것이 [[recursion]] 의 실질적인 한계선이다.

세 번째는 **예외의 스택 트레이스가 무엇인지**가 설명된다는 것이다. 트레이스에 줄줄이 찍히는 것은 예외가 난 순간 쌓여 있던 프레임 목록이고, 위에서 아래로 읽으면 "누가 누구를 불렀는지"가 그대로 나온다 → [[exception-handling]]

## 경계와 오해

- **JVM 스택 ≠ `java.util.Stack`** — 이름이 같아서 자료구조 클래스 이야기로 읽히지만, JVM 스택은 **실행 엔진이 쓰는 메모리 영역**이고 내 코드가 `push`/`pop` 할 대상이 아니다. 같은 LIFO 성질을 쓴다는 것만 겹친다.
- **스택 ≠ 힙** — 프레임은 `return` 과 동시에 확정적으로 사라지지만, 힙의 인스턴스는 아무도 가리키지 않게 된 뒤 JVM 이 정한 시점에 회수된다 → [[garbage-collection]]. **정리 방식이 다르기 때문에** 지역 변수는 신경 쓸 것이 없고 인스턴스는 참조를 끊는 것이 관심사가 된다.
- **프레임이 사라지는 것 ≠ 인스턴스가 사라지는 것** — 이 필기는 "로컬변수로 ... 메서드가 종료 될때 JVM stack에서 제거된다"고 적었는데, 제거되는 것은 **주소를 담고 있던 변수**다. 그 주소가 가리키던 인스턴스는 힙에 그대로 있고, 위 예제의 `values[0]` 이 200 으로 남아 있는 것이 그 증거다 → [[object-reference]]
- **`StackOverflowError` ≠ `OutOfMemoryError`** — 앞은 **스택 깊이**가 넘친 것이고 뒤는 **힙**이 부족한 것이다. 원인 영역이 다르므로 "메모리가 부족하다"로 뭉쳐 읽으면 엉뚱한 곳을 고치게 된다.
- **`StackOverflowError` 는 예외가 아니라 `Error` 다** — 문법적으로 `catch` 할 수는 있지만 잡아서 흐름을 이어 갈 대상이 아니다. 입력이 이상한 것이 아니라 **호출 구조가 이상하다**는 신호이므로 고칠 곳은 `try` 블록이 아니라 호출 자체다 → [[exception-handling]]
- **스택 크기는 코드가 정하지 않는다** — 실행 옵션(`-Xss`)과 환경이 정한다. 그래서 같은 재귀 코드가 어떤 환경에서는 돌고 어떤 환경에서는 죽는다.
- **스택은 스레드마다 하나씩이다** — 힙은 공유하지만 스택은 그렇지 않다. 지역 변수가 스레드 안전하고 인스턴스 필드가 그렇지 않은 이유의 뿌리가 여기다.
