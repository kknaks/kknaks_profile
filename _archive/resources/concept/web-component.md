# 웹 컴포넌트 (Web Component)

**서블릿 규격이 「컨테이너가 만들어서 부르는 부품」으로 인정하는 서버 측 클래스들의 묶음 이름.** Day64 의 정의는 「웹 애플리케이션 개발에 사용되는 특정 서버 측 기술들을 말한다」이고, 종류를 셋 든다 — **리스너 · 필터 · 서블릿** → [[servlet]] · [[servlet-filter]] · [[servlet-listener]]

## 정의

Day64 가 셋을 나란히 적었다. **셋의 공통점은 「무엇을 하나」가 아니라 「내가 `new` 하지 않는다」다.**

| 종류 | Day64 의 설명 | 컨테이너가 언제 부르나 |
|---|---|---|
| **리스너** | 「특정 이벤트가 발생할 때 자동으로 실행되는 객체」 | 앱·세션·요청이 **생기고 없어질 때** → [[servlet-listener]] |
| **필터** | 「요청이 서블릿에 도달하기 전이나 응답이 클라이언트에 전달되기 전에 특정 작업을 수행」 | 요청마다, **서블릿 앞뒤로** → [[servlet-filter]] |
| **서블릿** | 「서버 측에서 동작하는 자바 코드 … HTTP 요청을 처리하고 동적인 웹 콘텐츠를 생성」 | 요청마다, **그 URL 로 왔을 때** → [[servlet]] |

**등록도 셋이 같은 모양이다** — `@WebListener` · `@WebFilter` · `@WebServlet` 어노테이션이거나 `web.xml` 이고, 어느 쪽이든 **내 코드가 아니라 컨테이너가 클래스를 찾는다.** Day64 의 리스너 구동원리가 그것을 한 줄로 적었다 — 「서블릿 컨테이너는 `web.xml`이나 `@WebListener` 어노테이션을 통해 등록된 리스너들을 탐색한다」 → [[annotation]] · [[servlet-container]] · [[reflective-instantiation]]

### 「컴포넌트」는 클래스가 아니라 규칙을 지킨 부품이라는 뜻이다

Day63 의 JavaEE 표가 EJB 를 「분산 컴포넌트」로 부르는 것과 같은 용법이다. 규칙(구현할 인터페이스 · 붙일 어노테이션 · 놓일 자리)을 지키면 **내가 만들지 않은 서버에도 얹힌다**는 것이 이 낱말이 약속하는 것이고, 그래서 이 셋의 값은 톰캣이 아니라 명세에서 온다 → [[java-ee]] · [[interface]] · [[web-application-deployment]]

## 왜 중요한가

**「어디에 코드를 둘 것인가」의 선택지가 셋으로 정해진다.** Day61 까지의 서버는 코드를 어디에 둘지가 자유였다 — 접속 루프 안이든 명령 객체 안이든 내가 정했다. 웹에서는 **하려는 일의 성질이 자리를 정한다**: 앱이 뜰 때 한 번이면 리스너, 모든 요청에 공통이면 필터, 이 URL 에만 해당하면 서블릿. 이 셋 중 어디에도 안 맞는 코드는 대개 자리를 잘못 잡은 것이다 → [[cohesion]] · [[main-method]]

**그리고 Day64 의 실습이 정확히 그 배치를 한다.** MyBatis 설정을 읽고 DAO 를 만드는 일은 요청마다 할 일이 아니므로 **리스너**로 갔고, 회원 목록을 그리는 일은 `/user/list` 에만 해당하므로 **서블릿**으로 갔다. 남은 하나(필터)에 갈 일이 이 회차에 이미 있는데 아직 안 옮겼다 — 서블릿 안에 손으로 적은 `res.setContentType("text/html;charset=UTF-8")` 이다 → [[servlet-filter]] · [[character-encoding]]

## 경계와 오해

- **Day64 의 정의문은 셋 중 서블릿에만 맞는다** — 「클라이언트의 요청을 받아 이를 처리하고 동적인 콘텐츠를 생성하여 응답을 돌려준다」인데, **리스너는 요청을 받지 않고**(앱이 뜨고 지는 것, 세션이 생기고 지는 것이 그 입력이다) **필터는 콘텐츠를 만들지 않는다**(지나가는 것을 만지고 넘긴다). 정의를 그대로 외우면 다음 두 절의 리스너·필터가 왜 같은 목록에 있는지 설명되지 않는다. 셋을 묶는 실제 기준은 **컨테이너가 생명 주기를 갖는다**는 것 하나다 → [[servlet-container]]
- **한 목록에 축이 둘 섞여 있다** — 필터와 서블릿은 **요청 하나가 지나가는 순서**(필터 → 서블릿 → 필터) 위에 있고, 리스너는 그 순서 위에 없다. 리스너는 **생명 주기 축**(앱이 뜬다 / 세션이 생긴다)에 붙는다. 「종류가 셋」으로 평평하게 두면 리스너를 요청 처리 흐름 안에서 찾게 되고, 실제로는 요청이 오기 **전에** 이미 다 끝난 일이다. Day64 의 실습이 그 순서를 그대로 보여 준다 — 리스너가 DAO 를 만들어 두어야 서블릿의 `init()` 이 그것을 꺼낼 수 있다 → [[servlet-context]]
- **웹 컴포넌트(Java EE) ≠ Web Components(브라우저 표준)** — 같은 이름의 완전히 다른 것이 있다. 브라우저 쪽의 Web Components 는 Custom Elements·Shadow DOM·HTML Template 으로 **클라이언트에서 재사용 가능한 태그를 만드는** W3C 표준이다. Day64 의 것은 **서버 측 클래스**이고 브라우저는 그 존재를 모른다. 검색하면 대개 뒤쪽이 나오므로, 이 낱말은 **어느 층의 이야기인지 붙여서 말해야** 뜻이 고정된다 → [[static-and-dynamic-content]]
- **셋이 전부가 아니다 — JSP 가 빠져 있다** — 같은 필기의 다른 절이 「서블릿, JSP, 필터, 리스너 같은 웹 애플리케이션 구성 요소들」·「서블릿, JSP, 필터 등의 웹 컴포넌트」로 **넷**을 적는다. 즉 종류 절의 셋과 컨테이너 절의 넷이 어긋나고, JSP 는 이 필기에서 이름으로만 지나간다. 규격 쪽에서 웹 컴포넌트로 세는 것도 서블릿과 JSP 이며(JSP 는 결국 서블릿으로 번역된다), 「셋」은 이 회차가 실습한 범위다 → [[java-ee]]
- **웹 컴포넌트 ≠ 내가 실행하는 프로그램** — 셋 다 `main` 이 없고 내가 `new` 하지 않는다. 이 사실을 놓치면 값비싼 실수가 나온다 — Day64 의 서블릿에 인수를 받는 생성자가 남아 있어서, **컨테이너가 그 클래스를 아예 만들 수 없다**(→ [[servlet-lifecycle]]). 「컴포넌트」라는 낱말이 그 제약을 이미 담고 있는데 그것이 코드로 옮겨지지 않은 자리다 → [[constructor]] · [[dependency-injection]]
- **「특정 서버 측 기술들」이라는 정의는 기술 목록이 아니라 규격 목록이다** — DAO·Command·`SqlSessionFactoryProxy` 도 서버에서 도는 자바 코드이지만 웹 컴포넌트가 아니다. 갈리는 것은 **컨테이너가 그 클래스를 찾아서 부르는가**이고, Day64 의 부팅 코드에서 그 경계가 눈에 보인다 — `ContextLoaderListener` 만 `@WebListener` 가 붙어 있고 그것이 만드는 `DaoFactory`·DAO 는 **평범한 객체**다 → [[dao-pattern]] · [[proxy-pattern]]
