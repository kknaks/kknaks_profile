# DB 모델링 (Data Modeling)

**시스템을 분석해 「무엇을 저장할 것인가」를 표와 관계로 그려 내는 일.** 목표는 **데이터가 중복되지 않도록 테이블로 구조화하는 것**이다.

## 정의

같은 것을 부르는 이름이 여럿이다 — 이론(관계형 모델)·구현(파일)·프로그래밍(객체)의 어휘가 겹쳐 있기 때문이다.

| 우리가 부르는 것 | 다른 이름들 |
|---|---|
| table | relation · entity · file |
| row | tuple · record |
| column | attribute · field |
| **intension** | schema · header — **데이터 구조 설계도** → [[database-schema]] |
| **extension** | instance · data — **그 안에 담긴 데이터** |

**intension 과 extension 의 구별이 이 절의 핵심**이다 — 「테이블」이라는 말이 설계도를 가리킬 때와 담긴 값을 가리킬 때가 있다.

그림으로 그릴 때는 **IE 표기법**처럼 약속된 기호를 쓴다.

### 절차

1. **엔티티 식별** — 저장해야 하는 데이터의 유형을 고른다
2. **속성 식별** — 그 엔티티를 이루는 항목(컬럼)을 고른다
3. **키 식별** — 행을 구분할 수 있는 컬럼 조합(슈퍼키)을 찾는다
4. **후보키 선정** — 그중 더 뺄 수 없는 최소 조합으로 줄인다
5. **기본키 선정** — 후보키 중 하나를 고른다. 나머지는 대안키 → [[primary-key]]
6. **정규화** — 중복을 찾아 별도 테이블로 분리하고 부모-자식 관계를 맺는다 → [[db-normalization]]

## 왜 중요한가

**테이블 구조가 나중에 쓸 수 있는 질의를 정한다.** 한 컬럼에 값을 여러 개 몰아넣으면 그 안을 뒤지는 것이 문자열 처리가 되고, 나눠 두면 조인 하나다 → [[sql-join]]

**그리고 중복은 언젠가 어긋난다.** 같은 사실이 두 곳에 적혀 있으면 한쪽만 고치는 날이 오고, 그때 **어느 쪽이 맞는지 알 방법이 없다.** 정규화가 푸는 것이 성능이 아니라 이 문제다 → [[db-normalization]]

**모델링은 코드보다 먼저이고 바꾸기 어렵다.** 테이블 구조를 바꾸면 이미 쌓인 데이터를 옮겨야 하고, 그 위에 얹힌 모든 질의와 DAO 가 함께 움직인다 → [[dao-pattern]]

## 경계와 오해

- **엔티티 ≠ 테이블** — 모델링 단계에서는 「저장할 것의 유형」이고, 테이블은 그것을 DB 에 실제로 만든 결과다. 하나의 엔티티가 여러 테이블이 되기도 하고 그 반대도 있다
- **「데이터가 중복되지 않도록」이 모든 중복을 없앤다는 뜻은 아니다** — 외래키로 저장되는 부모 키 값은 **의도된 중복**이고, 조회 성능을 위해 값을 복사해 두는 선택(반정규화)도 있다. 없애는 것은 **같은 사실이 두 곳에서 갱신될 수 있는 상태**다
- **용어가 세 갈래인 것을 알아 둬야 남의 글을 읽는다** — 논문은 relation·tuple·attribute 를, 실무는 table·row·column 을, 객체 쪽은 entity·instance·property 를 쓴다. **같은 것을 말하고 있다는 것만 알면 된다**
- **그림이 모델이 아니다** — IE 표기법은 표기일 뿐이고, 결정된 것은 엔티티·키·관계다. 도구를 바꿔도 그 결정은 남는다
- **키를 먼저 정하고 정규화한다는 순서가 절대적이지는 않다** — 실제로는 오가며 다듬는다. 필기의 여섯 걸음은 **한 번 훑는 길**이지 되돌아오지 않는 절차가 아니다
