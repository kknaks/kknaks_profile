# SQL 조인 (cross · natural · using · inner · outer)

**여러 테이블의 행을 짝지어 한 행으로 만들어 조회하는 것.** [[sql-set-operation]] 이 결과 두 개를 **세로로 쌓는** 층이었다면 조인은 **가로로 잇는** 층이다 — 컬럼 개수가 늘어난다. Day55 가 이것을 다섯 갈래로 세워 적었고, 그 다섯은 [[db-normalization]] 으로 갈라 둔 테이블을 다시 붙이는 유일한 문법이다.

## 정의

Day55 는 다섯을 `1)`~`5)` 로 나란히 세웠지만 **한 축이 아니다.** 두 축이 겹쳐 있다 — **짝을 정하는 조건을 어디서 얻는가**와 **짝이 없는 행을 어떻게 하는가**다.

| Day55 의 번호 | 문법 | 조건을 어디서 얻나 | 짝 없는 행 |
|---|---|---|---|
| 1) cross join | `from a cross join b` · `from a, b` | **없다** — 모든 조합 | (해당 없음) |
| 2) natural join | `from a natural join b` | **같은 이름의 컬럼 전부** (암묵) | 버린다 |
| 3) join ~ using | `from a join b using (컬럼)` | 같은 이름 컬럼 중 **내가 고른 것** | 버린다 |
| 4) inner join | `from a join b on 식` | **임의의 식** (명시) | 버린다 |
| 5) outer join | `from a left join b on 식` | 임의의 식 (명시) | **한쪽을 남긴다** |

**1)~4) 는 같은 축에서 조건이 점점 명시적으로 되는 순서**이고(아예 없음 → 이름이 같으면 → 고른 이름 → 임의의 식), **5) 는 다른 축**이다. 두 축이 직교한다는 증거가 `natural left join` 이 성립한다는 것이다 — 조건을 이름에서 얻으면서 짝 없는 행을 남길 수 있다.

그리고 **1) 은 나머지의 출발점**이다. 조인은 원리상 「모든 조합을 만든 뒤 조건으로 거른다」이므로, `inner join ... on 식` 은 `cross join` 뒤에 `where 식` 을 붙인 것과 결과가 같다.

### 1) cross join — Day55 가 소제목만 남긴 자리

필기에는 **`1) cross join` 이라는 줄만 있고 본문이 없다.** 그 자리에 들어갈 것은 짧다: **조건 없이 왼쪽의 모든 행과 오른쪽의 모든 행을 조합한다.** 행 수가 `m × n` 이 되고, 이것을 카티전 곱(cartesian product)이라 부른다.

```sql
select * from a cross join b;
select * from a, b;            -- 옛 표기. 같은 뜻이다
```

**이것을 일부러 쓰는 일은 드물고, 대개 실수로 만든다** — `from a, b` 로 두 테이블을 적고 `where` 에 연결 조건을 빠뜨리면 그 순간 결과가 곱이 된다. 10만 행 × 10만 행이 100억 행이므로 오류가 아니라 **응답이 돌아오지 않는 쿼리**로 나타난다. MySQL 에서 `cross join`·`join`·`inner join` 은 문법상 동의어이고, 갈리는 것은 **`on` 을 붙였는지**뿐이다.

### 2) natural join — 조건을 스키마가 정한다

```sql
select 컬럼명
from 테이블명
    natural join 테이블명2
```

**같은 이름을 가진 컬럼 전부**가 조건이 된다(`a.x = b.x and a.y = b.y ...`). 그리고 그 컬럼은 결과에서 **하나로 합쳐진다** — `select *` 에 `user_id` 가 두 번 나오지 않는다.

Day55 가 적은 문제점 세 줄이 이 문법의 위험을 정확히 짚는데, **첫 줄의 결말은 필기가 쓴 것과 반대**다(아래 「경계와 오해」).

### 3) join ~ using — 이름을 내가 고른다

```sql
select 컬럼명
from 테이블명
join 테이블명2
using (동일한 이름의 컬럼명)
```

같은 이름의 컬럼이 여러 개일 때 **그중 어느 것을 조건으로 쓸지 고르는 것**이다. `natural join` 과 마찬가지로 지정한 컬럼은 결과에서 하나로 합쳐지고, 그래서 `select user_id` 가 모호해지지 않는다.

### 4) inner join — 조건을 식으로 적는다

```sql
select 컬럼명
from 테이블명
inner join 테이블명2
on (테이블명.컬럼명 = 테이블명2.컬럼명2)

-- inner를 생략 할 수 있다.
select 컬럼명
from 테이블명
join 테이블명2
on (테이블명.컬럼명 = 테이블명2.컬럼명2)
```

**컬럼 이름이 달라도 되고, `=` 가 아니어도 되고, 조건이 여러 개여도 된다.** `on` 은 `where` 와 같은 자리의 식을 받으므로 조인의 일반형이 이것이고, 2)·3) 은 「이름이 같을 때만 쓸 수 있는 축약」이다.

### 5) outer join — 짝이 없어도 남긴다

```sql
select 컬럼명
from 테이블명
[left|right] outer join 테이블명2
on 조건
```

`left` 면 **왼쪽 테이블의 모든 행이 남고** 짝이 없는 자리의 오른쪽 컬럼이 `NULL` 로 채워진다. 「첨부가 없는 게시글도 목록에 나와야 한다」가 이 문법이 필요한 자리다 → [[sql-null]]

## 사용 예시

Day55 의 실습 코드에 **조인이 실제로 쓰인 자리가 하나** 있다 — 중간 테이블에서 프로젝트의 팀원을 읽어 오는 DAO 메서드다.

```sql
select pm.user_id, u.name
  from myapp_project_members pm
  join myapp_users u
    on pm.user_id = u.user_id
 where pm.project_id = ?
```

**이 한 문장이 그날 지운 자바 코드를 대신한다.** 고치기 전의 `findBy` 는 이랬다.

```java
String members = rs.getString("members");
String[] memberNoList = members.split(",");
for (String memberNo : memberNoList) {
  User user = userDao.findBy(Integer.parseInt(memberNo));   // 팀원 수만큼 질의
  if (user != null) {
    project.getMembers().add(user);
  }
}
```

팀원이 다섯이면 **질의가 여섯 번**(프로젝트 1 + 회원 5)이고, 조인으로 바꾸면 두 번(프로젝트 1 + 팀원 1)이다. 목록 화면에서 프로젝트 스무 개를 그리면 전자는 100번을 넘긴다 — 나중에 **N+1 문제**라 불리는 것의 원형이 그 루프이고, Day55 가 그것을 지우면서 조인으로 옮긴 것이다 → [[jdbc]] · [[db-normalization]]

**그리고 이 쿼리는 세 갈래 문법이 다 통하는 자리다.** `pm.user_id` 와 `u.user_id` 는 **이름이 같으므로** `using (user_id)` 도 `natural join` 도 성립한다. 그런데도 `on` 을 고른 것이 결과적으로 맞다 — 두 테이블에 같은 이름 컬럼이 또 생기면 `natural join` 은 조건이 조용히 늘어나는데 `on` 은 그대로다.

`select pm.user_id` 에 붙은 접두사도 선택이 아니다. 두 테이블에 `user_id` 가 있으므로 `select user_id` 는 `Column 'user_id' in field list is ambiguous` 로 거절된다 — **필기의 문법 예제가 전부 `select 컬럼명` 으로 접두사 없이 적혀 있어서**, 그대로 따라 쓰면 처음 만나는 오류가 이것이다.

## 왜 중요한가

**나눈 것을 되붙이는 방법이 이것 하나뿐이다.** Day54 가 정규화로 테이블을 갈랐고, 그 대가로 「게시글과 첨부를 함께 보여 주기」가 한 테이블 조회로는 불가능해졌다. 조인이 없으면 방법은 **애플리케이션에서 두 번 조회해 자바 코드로 맞추는 것**이고, Day55 의 지워진 루프가 정확히 그 형태다. 조인을 알고 나서야 정규화가 **비용을 감당할 수 있는 설계**가 된다 → [[db-normalization]] · [[foreign-key]]

**질의 횟수가 행 개수에 비례하는 코드가 사라진다.** 위의 루프는 팀원 수만큼 DB 를 왕복하고, 왕복 하나하나가 네트워크와 인증을 거친 연결 위에서 일어난다. 조인은 그 일을 **서버 안에서** 하므로 오가는 것이 결과 한 덩어리다. 이것이 「SQL 을 잘 쓰면 자바 코드가 줄어든다」의 가장 실감되는 형태다 → [[jdbc]] · [[tcp]]

**대신 결과의 행 수가 내 통제에서 벗어난다.** 지금까지 조회 결과의 행 수는 언제나 「그 테이블 행의 부분집합」이었다. 조인 뒤로는 **조건 하나를 빠뜨리면 결과가 곱으로 불어나고**, 1:N 을 조인하면 왼쪽 행이 N 번 반복된다. `select` 를 읽을 때 「몇 행이 나올 것인가」를 따로 생각해야 하는 것이 이 층에서 처음 생기는 부담이다 → [[aggregate-function]]

## 경계와 오해

- **`natural join` 은 같은 컬럼명이 없으면 「연결되지 못한다」가 아니라 `cross join` 이 된다** — Day55 가 적은 첫 문제점의 결말이 뒤집혀 있다. 공통 컬럼이 하나도 없으면 조건이 **빈 조건**이 되므로 표준·MySQL 모두 이것을 **모든 조합**으로 계산한다. 즉 「아무것도 안 나온다」가 아니라 **`m × n` 행이 나온다.** 오류도 경고도 없고, 결과가 적으면 그냥 이상하지 않아 보인다 — 「연결되지 못한다」로 외워 두면 결과가 0행일 줄 알고 기다리다가 폭발한 행 수를 만난다. **같은 문장(「같은 컬럼명이 없을 경우」)을 필기가 3) `using` 의 문제점에도 그대로 적었는데 그쪽은 정말로 실패한다** — `using (없는컬럼)` 은 `Unknown column` 오류다. **한 줄로 같아 보이는 두 위험이 한쪽은 조용한 폭발, 한쪽은 즉시 오류**로 갈리고, 이 비대칭이 `natural join` 을 실무에서 금지하는 첫 번째 이유다.
- **`natural join` 의 조건은 내가 쓴 것이 아니라 스키마가 정한다** — Day55 의 두 번째·세 번째 문제점이 그것인데, 더 걸리는 것은 **쿼리를 고치지 않아도 뜻이 바뀐다**는 점이다. 누가 `alter table ... add column` 으로 양쪽에 같은 이름의 컬럼(`created_at` 같은 것)을 더하면, 그날부터 그 컬럼까지 조건에 들어가 **결과가 조용히 줄어든다.** 쿼리는 한 글자도 안 바뀌었고 오류도 없다. **`on` 을 쓴 쿼리는 스키마가 변해도 조건이 그대로**이며, 이것이 축약을 포기하고 매번 조건을 적는 값이다 → [[ddl]]
- **`[left|right] outer join` — 대괄호가 반대쪽에 걸렸다** — 필기 표기는 `left`/`right` 가 생략 가능한 것처럼 보이지만, MySQL 문법은 `LEFT|RIGHT [OUTER] JOIN` 이다. **생략할 수 있는 것은 `outer` 이고 방향은 필수**다. `from a outer join b on ...` 은 문법 오류(1064)이고, 반대로 `left join` 은 `left outer join` 과 완전히 같다. 「outer join 이라는 종류가 있고 옵션으로 방향을 준다」로 읽으면 실행되지 않는 문장을 쓰게 된다 — 실제로 있는 것은 **왼쪽을 남기는 조인과 오른쪽을 남기는 조인 둘**이다.
- **`full outer join` 은 MySQL 에 없다** — 「양쪽 다 남기기」는 표준에 있지만 MySQL 8.x 에도 구현이 없어서, `left join` 과 `right join` 을 [[sql-set-operation]] 의 `union` 으로 합쳐 흉내 내야 한다. Day55 의 표기 `[left|right]` 에 셋째 선택지가 없는 것이 그래서 맞다.
- **`inner join` 의 「문제점: 데이터가 누락될 위험이 있다」는 결함이 아니라 정의다** — Day55 는 다섯 갈래마다 「문제점」을 달았는데, 4) 의 세 줄은 **inner join 이 하기로 되어 있는 일**을 적은 것이다(짝이 없으면 그 행은 결과에 없다). 이것을 결함으로 읽으면 「안전한 쪽」을 고르려고 **어디에나 `left join` 을 쓰게 되고**, 그러면 짝이 없는 행이 `NULL` 로 섞여 들어와 뒤의 집계와 조건이 어긋난다. 「누락」인지 「필터」인지는 문법이 아니라 **내가 무엇을 세려는지**가 정한다 → [[aggregate-function]]
- **`left join` 뒤에 `where` 로 오른쪽 컬럼을 조건에 걸면 `inner join` 이 된다** — 가장 흔한 실제 버그다. `from a left join b on a.id = b.aid where b.status = 'Y'` 는 짝이 없어 `NULL` 로 채워진 행을 `where` 가 전부 떨어뜨리므로, 애써 남긴 왼쪽 행이 사라진다. 조건을 `on` 쪽으로 옮기면(`on a.id = b.aid and b.status = 'Y'`) 의도대로 남는다 — **`on` 은 짝짓기 규칙이고 `where` 는 만들어진 행의 필터**여서, inner join 에서는 둘이 같은 결과를 주지만 outer join 에서는 갈린다. 「조건은 `where` 에 모아 쓴다」는 습관이 그대로 오면 outer join 이 조용히 무력화된다 → [[dql]] · [[sql-null]]
- **조인은 행을 늘릴 수 있다 — 그리고 그 위의 집계가 조용히 틀린다** — 1:N 을 조인하면 왼쪽(1 쪽) 행이 오른쪽 개수만큼 반복된다. 그 결과에 `sum(왼쪽.금액)` 을 씌우면 같은 금액이 여러 번 더해지고, 오류 없이 숫자만 커진다. [[sql-set-operation]] 의 `union all` 이 같은 값을 두 번 세는 것과 **원인이 다르고 증상이 같다**(그쪽은 세로로 쌓아서, 이쪽은 짝이 여럿이라서) → [[aggregate-function]]
- **`distinct` 로 조인 결과를 정리하는 것은 대개 잘못된 짝짓기를 덮는 것이다** — 행이 불어난 결과에 `distinct` 를 붙이면 화면은 맞아 보이지만 원인은 그대로다. [[sql-set-operation]] 에 적어 둔 같은 함정이고, 조인에서 특히 자주 나온다 — 「조인했더니 중복이 생겨서」가 아니라 **「조건이 부족해서 짝이 여럿이 된 것」**을 먼저 봐야 한다 → [[dql]]
- **SQL 조인 ≠ `String.join` ≠ `Thread.join`** — 같은 낱말이 이 필기 안에서 셋으로 쓰인다. 이 노트의 조인은 **행을 짝지어 컬럼을 늘리는 것**, `Collectors.joining(",")`(Day55 가 지운 코드)은 **문자열을 이어 붙이는 것**, [[thread-join]] 은 **끝나기를 기다리는 것**이다. 그래서 이 노트의 stem 이 `join` 이 아니라 `sql-join` 이고, `[[join]]` 이라고 쓰면 무엇을 가리키는지 알 수 없다. 공통점은 「합친다」는 어감뿐이며 대상도 결과도 다르다 → [[string-builder]]
- **조인은 외래키를 요구하지 않고, 외래키가 조인을 만들지도 않는다** — 아무 컬럼끼리나 `on` 으로 이을 수 있고(타입만 비교되면 된다), 반대로 외래키를 걸어 두어도 조회할 때 조건은 매번 적어야 한다. [[foreign-key]] 는 **쓸 때의 검사**이고 조인은 **읽을 때의 짝짓기**다. 「외래키를 걸었으니 두 테이블이 이어졌다」로 읽으면 조인 조건을 빠뜨린 `from a, b` 가 나온다.
- **조인 조건 컬럼에 인덱스가 없으면 오른쪽 테이블을 왼쪽 행마다 다시 훑는다** — MySQL 의 기본 실행 방식이 중첩 루프 조인이므로, 인덱스가 없으면 비교 횟수가 `m × n` 이 된다(결과 행 수와는 별개다). Day55 의 중간 테이블은 복합키 덕분에 `(user_id, project_id)` 인덱스를 갖고 있어 이 벽이 드러나지 않고, MySQL 은 외래키를 걸 때 그 컬럼에 인덱스를 자동으로 만들어 주기까지 한다 — **인덱스를 신경 쓰지 않아도 되는 이유가 그날의 설계에 우연히 들어 있었다** → [[database-index]] · [[linear-search]]
- **`on` 의 괄호는 문법이 아니다** — 필기의 4) 예제가 `on (테이블명.컬럼명 = 테이블명2.컬럼명2)` 로 괄호를 씌웠는데, `on` 은 `where` 처럼 식을 받으므로 괄호는 그냥 식을 감싼 것이다. `using` 의 괄호는 반대로 **필수**다(컬럼 목록이라서). 두 줄이 나란히 있어 같은 규칙으로 보이는 자리다.
- **조인의 대상은 테이블 이름만이 아니다** — 같은 테이블을 두 번 조인하거나(자기 참조 — 「상사와 부하」) 서브쿼리의 결과를 조인할 수도 있다. 그래서 별칭(`pm`·`u`)이 편의가 아니라 **필요**가 되는 자리가 생긴다 — 같은 테이블을 두 번 쓰면 이름으로는 둘을 구별할 수 없다. Day55 에는 자기 조인이 없고, 별칭은 DAO 코드에만 나온다 → [[dql]]
