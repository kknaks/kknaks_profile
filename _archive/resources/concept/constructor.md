# 생성자 (Constructor)

`new` 로 인스턴스가 만들어질 때 실행되어 **초기 상태를 갖춰 주는 것**. 이름이 클래스명과 같고 반환 타입이 없다. 여러 개 둘 수 있고, 그러면 「만드는 방법」이 여러 개가 된다.

## 정의

```java
public class Score {
  private String name;
  private int kor;

  public Score() {}                                    // 기본생성자

  public Score(String name, int kor, int eng, int math) {   // 생성자 오버로딩
    this.name = name;
    this.kor = kor;
    ...
    this.compute();                                    // 파생값까지 맞춰 둔다
  }
}
```

- 이름은 **클래스명과 같고** 반환 타입을 쓰지 않는다
- 매개변수 목록이 다르면 여러 개 둘 수 있다(오버로딩). `new` 할 때 넘긴 인수로 하나가 골라진다
- 생성자를 **하나도 선언하지 않으면** 컴파일러가 매개변수 없는 기본 생성자를 넣어 준다

`new` 와 생성자는 하는 일이 갈린다.

| 순서 | 누가 | 하는 일 |
|---|---|---|
| 1 | `new` | 메모리를 확보하고 타입별 기본값으로 채운다 → [[instance]] · [[default-initialization]] |
| 2 | 생성자 | 그 자리에 쓸 값을 넣는다 |
| 3 | `new` 식의 값 | 확보한 메모리의 주소 → [[object-reference]] |

## 사용 예시

생성자 이전에는 인스턴스를 만든 다음 밖에서 여섯 줄을 채웠다.

```java
Score s1 = new Score();
s1.name = "홍길동";
s1.kor = 100;
s1.eng = 90;
s1.math = 85;
compute(s1);              // 이것을 잊으면 sum·aver 가 0 이다
```

생성자를 오버로딩한 뒤에는 한 줄이다.

```java
Score s1 = new Score("홍길동", 100, 90, 85);
Score s2 = new Score("임꺽정", 90, 80, 75);
Score s3 = new Score("유관순", 80, 70, 65);
```

**줄이 줄어든 것이 값의 전부가 아니다.** 「무엇을 어떤 순서로 채워야 완전한 `Score` 인가」를 아는 곳이 **호출부에서 클래스 안으로 옮겨졌다.** 생성자가 `this.compute()` 를 부르므로 만들어진 순간 `sum`·`aver` 가 이미 맞다 → [[this-reference]]

## 왜 중요한가

**「만들었지만 아직 안 채워진 객체」가 존재하는 구간이 사라진다.** 앞 코드에서 `new Score()` 와 마지막 대입 사이의 `s1` 은 `name` 이 `null` 이고 점수가 전부 `0` 인 상태다. 그 사이에 `printScore(s1)` 를 부르면 예외도 나지 않고 `null: 0, 0, 0, 0, 0.0` 이 출력된다. 생성자는 그 창을 닫는다 — **불완전한 상태를 밖에서 볼 수 없게** 만드는 것이 생성자의 일이다.

**필드를 닫을 수 있게 되는 것도 생성자 덕이다.** 값을 넣는 정식 경로가 생겼기 때문에 필드를 `private` 으로 만들 수 있다. 생성자 없이 `private` 부터 붙이면 값을 넣을 방법이 없어 setter 를 전부 열어야 하고, 그러면 닫은 의미가 줄어든다 → [[encapsulation]]

**오버로딩은 「만드는 방법」의 목록이다.** 인수 없이 만들 수도, 넷을 주고 만들 수도 있다는 것이 그 클래스가 허용하는 사용법이 된다.

## 경계와 오해

- **생성자 ≠ 메서드** — 반환 타입이 없다는 것이 문법적 차이다. `public void Score() {}` 라고 쓰면 그것은 생성자가 아니라 **이름이 클래스명과 같은 메서드**이고, 컴파일은 되지만 `new` 할 때 불리지 않는다. 증상이 "생성자가 실행되지 않는다"로 나타나서 원인을 찾기 어렵다 → [[method]]
- **생성자의 이름은 클래스 이름이다 — 클래스 이름을 바꾸면 함께 바꿔야 한다** — 위 항목의 짝이고 실수는 반대 방향에서 온다. Day35 가 커맨드를 기능 단위로 쪼개면서 `UserCommand` 를 복사해 `UserAddCommand` 를 만들었는데 **생성자 이름을 안 바꿨다.**

  ```java
  public class UserAddCommand implements Command {
    private List<User> userList;

    public UserCommand(List<User> list) {     // ← 클래스 이름과 다르다
      this.userList = list;
    }
  ```

  이름이 클래스명과 다르므로 이것은 생성자가 아니라 **반환 타입이 없는 메서드 선언**이고 「invalid method declaration; return type required」로 걸린다. `public void UserCommand(...)` 로 고쳐 통과시키면 이번엔 **그 클래스에 선언된 생성자가 하나도 없는 상태**가 되어 기본 생성자만 생기고 `new UserAddCommand(userList)` 가 다시 컴파일 오류다. 어느 길로 가도 `userList` 가 채워지지 않으므로 **동작으로 밀어붙이면 `userList.add(user)` 에서 `NullPointerException`** 이 목적지다. 「생성자 이름이 안 맞으면 안 불린다」로 기억하면 위 항목과 구별되지 않는데, **위 항목은 컴파일되고 이쪽은 안 된다** — 클래스명과 같은 이름은 반환 타입이 없어도 되지만 다른 이름은 반환 타입을 요구하기 때문이다. 필기가 「동일 한 방법으로 클래스를 나눈다」로 열다섯 개를 같은 손놀림으로 만들 참이었으므로 **한 번의 실수가 열다섯 번 복사될 자리**였다 → [[default-initialization]] · [[command-pattern]] · [[refactoring]]
- **기본 생성자가 언제나 있는 것은 아니다** — 필기는 "객체를 인스턴스하면 자동적으로 생성자가 생성된다"고 적었지만, 컴파일러가 넣어 주는 것은 **생성자를 하나도 선언하지 않았을 때뿐**이고 그 일이 일어나는 시점은 인스턴스 생성이 아니라 **컴파일**이다. 이 필기가 `public Score() {}` 를 손으로 적어 둔 것이 바로 그 증거다 — 인수 넷을 받는 생성자를 더한 순간 `new Score()` 가 막히므로 빈 생성자를 다시 써 줘야 했다.
- **"다른 타입의 생성자를 여러개 호출 할 수 있다" 는 한 번에 하나다** — `new` 한 번에 실행되는 생성자는 하나뿐이다. 여러 개를 **준비해 두고 그중 하나가 골라지는 것**이고, 고르는 시점은 실행이 아니라 컴파일이다(넘긴 인수의 타입으로 정해진다).
- **「객체 오버로딩」이라는 것은 없다** — 필기의 표기다. 오버로딩되는 것은 생성자·메서드이고, 구별 기준은 **이름 + 매개변수 타입 목록**이다. 매개변수가 같은 생성자를 두 개 둘 수는 없다 → [[method]]
- **오버로딩 ≠ 오버라이딩** — 같은 클래스에서 매개변수를 달리해 여러 개 두는 것과, 상속에서 부모의 메서드를 다시 정의하는 것은 다른 일이다. 앞은 어느 것을 부를지가 컴파일 시점에 정해지고 뒤는 실행 시점에 정해진다 → [[method-overriding]] · [[polymorphism]]
- **생성자는 값을 돌려주지 않는다** — `Score s1 = new Score(...)` 에서 주소를 주는 것은 `new` 다. 생성자에 반환 타입을 쓰지 않는 것은 「인스턴스를 리턴하기 때문」이 아니라 **돌려주는 것이 아예 없기 때문**이다 → [[object-reference]]
- **생성자에서 파생값을 계산해도 그 뒤에 필드가 바뀌면 다시 어긋난다** — 생성자는 만드는 순간만 보장한다. 그래서 이 필기는 3.6 에서 setter 마다 `compute()` 를 부른다 → [[encapsulation]]
- **생성자의 접근 지정자는 「누가 만들 수 있나」를 정한다** — Day16 은 `public Score() {}` 로 열어 두는 것만 봤지만, 보름 뒤 싱글톤은 `private` 으로 닫는다. 생성자를 닫으면 **밖에서 `new` 가 컴파일되지 않고** 그 클래스가 자기 인스턴스의 개수를 스스로 정하게 된다. 「생성자는 만드는 방법의 목록」이라는 데서 한 발 더 가면 **목록을 밖에 보여 줄지도 결정 사항**이다 → [[access-modifier]] · [[singleton-pattern]]
- **`private Car();` 는 생성자 선언이 아니다** — 몸통 없이 세미콜론으로 끝나는 것은 **추상 메서드의 문법**이고, 생성자는 `abstract` 가 될 수 없으므로 컴파일 에러다. 「접근만 막는 것이 목적이라 안에 쓸 것이 없다」와 「선언만 해 둔다」가 다른 이야기인데, 몸통이 빌 뿐 `{}` 는 있어야 한다 → [[abstract-class]]
- **생성자를 닫으면 상속이 같이 막힌다** — 자식의 생성자는 반드시 `super()` 를 부르므로, `private` 생성자만 있는 클래스는 `extends` 자체가 성립하지 않는다. 접근 지정자를 「보이는 범위」로만 읽으면 생성자에서는 그것이 **확장 가능성**까지 정한다는 것이 안 보인다 → [[inheritance]]
- **필드에 값을 정할 자리가 셋이다** — 선언 자리(`int result = 0`), 생성자, setter. 같은 필드를 두 곳에서 정하면 어느 것이 이겼는지 읽기 어려워지고, 선언 자리의 초기화는 생성자보다 먼저 실행된다 → [[default-initialization]]

## 출처

- [[2024-06-17-Day16]] — 객체를 만들면 생성자가 불린다는 것, 기본 생성자와 매개변수 넷을 받는 생성자를 오버로딩해 `new Score("홍길동", 100, 90, 85)` 한 줄로 초기화하고 생성자 안에서 `compute()` 까지 부르는 것을 실습으로 배웠다. 이것을 「객체 오버로딩」이라 적은 것은 이 필기의 표기다
- [[2024-07-03-Day28]] — 싱글톤 패턴에서 생성자를 **`private` 으로 닫는** 첫 코드를 봤다. 「클래스의 생성자의 접근을 제한하며 static 메서드를 통해 하나의 인스턴스만 생성」이 그것이고, Day16 이 생성자를 열어 두는 쪽만 봤던 것과 갈린다. 필기의 `private Car();` 는 몸통이 없어 컴파일되지 않는다
- [[2024-07-15-Day35]] — 생성자가 **협력자를 받는 자리**로 쓰이는 회차다. 메뉴 트리의 `AbstractMenu(String title)` 가 `super(title)` 로 제목을 위로 넘기고, `MenuItem(String title, Command command)` 가 실행할 것을 받고, 쪼갠 커맨드마다 `UserAddCommand(List<User> list)` 처럼 **그 기능이 필요한 것만** 받는다 — 생성자 목록을 읽으면 의존이 보인다(→ [[dependency-injection]]). 그리고 클래스를 복사해 쪼개다 `UserAddCommand` 안에 `public UserCommand(List<User> list)` 를 남겨 **생성자 이름이 클래스 이름과 어긋난 실제 사례**가 나온다 — 이름이 다르면 생성자가 아니라 반환 타입 없는 메서드이므로 그 파일은 컴파일되지 않는다. `MenuItem` 은 `command` 없이 제목만 받는 생성자도 두었는데 `App` 이 그것을 쓰지 않아 **오버로딩해 둔 쪽이 죽어 있다**
