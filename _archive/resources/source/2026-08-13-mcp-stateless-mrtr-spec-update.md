# MCP 신규 스펙 해설: 세션에서 스테이트리스로 전환

## 개요

2026년 7월 28일 공개된 MCP(Model Context Protocol) 신규 스펙과 공식 파이썬 SDK v2 업데이트를 해설하는 유튜브 영상이다. FastMCP에서 MCPServer로의 클래스명 변경 이면에 있는 프로토콜 구조 변화 — 세션 기반에서 스테이트리스 구조로의 전환, 서버에서 클라이언트로의 요청 방식 변화(MRTR 도입) — 를 약 4분 분량으로 요약한다.

스펙 원문이 아니라 이를 요약하고 해설하는 2차 콘텐츠이며, "저는 이게 가장 중요한 변화라고 생각합니다"처럼 화자의 해석과 평가가 명시적으로 섞여 있다. 제품이나 서비스 판매를 유도하는 홍보성 문구는 없다.

## 출처와 맥락

유튜브 채널(영상 메타데이터상 "Bloom AI", 화자는 영상 말미에 스스로를 "블루 AJ"로 소개)이 2026-08-09 업로드한 약 4분(238초) 영상이다. 2026-07-28 공개된 MCP 신규 스펙 발표라는 1차 사건을 소재로 삼아 요약하고 해설한 2차 콘텐츠이며, 스펙 원문이나 공식 changelog는 영상 내 "고정 댓글"로만 안내되고 이 자료 자체에는 포함되지 않았다.

## 핵심 주장

- 기존 MCP는 initialize 이후 세션을 유지하며 요청을 처리하는 세션 중심 프로토콜이었으나, 신규 스펙은 각 요청이 필요한 정보를 스스로 담아 독립적으로 처리되는 스테이트리스 구조로 바뀌었다.
- 이 변화는 MCP가 로컬 환경을 넘어 여러 서버를 로드밸런싱하는 원격·클라우드 환경에서 쓰이기 시작했기 때문이며, 세션 유지가 서버 확장을 어렵게 만드는 문제를 해결하기 위함이다.
- 기존에는 서버가 실행 중 클라이언트를 역으로 호출해 추가 입력을 요청할 수 있었으나, 신규 스펙은 서버가 "정보가 더 필요하다"는 응답으로 요청을 끝내고 클라이언트가 필요한 정보를 얻어 다시 요청하는 MRTR(Multi-Round Trip Request) 구조를 도입했다.
- MRTR 도입 이유는 웹에서 흔히 쓰이는 HTTP request-response 구조와 더 잘 맞기 때문이다.
- (화자 의견으로 명시) 이번 업데이트에서 가장 중요한 변화는 이름 변경이 아니라, MCP가 stateful 프로토콜에서 request-response 기반 stateless 프로토콜로 — 즉 단순 툴 연결 규격에서 에이전트 인프라를 위한 웹 프로토콜로 — 성숙해가는 과정이라는 점이다.

## 주요 개념

<!-- 아직 concept 노트가 없어 후보만 기록한다 -->

- MCP 스테이트리스 전환 (개념 후보) — 세션 유지 없이 요청마다 필요한 컨텍스트를 자체 포함시켜 독립 처리하는 구조 변화
- MRTR: Multi-Round Trip Request (개념 후보) — 서버가 클라이언트를 역호출하지 않고, "정보 부족" 응답 후 클라이언트가 재요청하는 상호작용 패턴

## 근거와 사례

자료는 정량적 벤치마크나 수치를 제시하지 않는다. 유일한 예시는 화자가 든 개념적 시나리오다 — MCP 서버 여러 대를 로드밸런서로 분산 운영할 때, 서버가 특정 사용자의 세션을 계속 들고 있어야 하면 첫 요청과 후속 요청을 처리하는 서버가 달라지는 순간 문제가 생기지만, 요청을 독립적으로 처리할 수 있으면 서버 확장이 쉬워진다는 설명이다. 이 시나리오는 화자의 해설이며 스펙 문서나 실측 부하 테스트에서 인용된 것이 아니다.

## 적용 가능성

> 아래는 원문 요약이 아니라 적용을 위한 해석이다.

- [해석] 이 레포의 open-kknaks-mcp는 stdio transport로 동작하는 로컬 단일 프로세스 documentation-only 서버다 — 세션이 클라이언트 프로세스 하나에 묶여 있어 이 자료가 지적하는 "여러 서버 로드밸런싱" 문제 자체가 지금은 발생하지 않는다. 따라서 스테이트리스 전환과 MRTR 도입은 현재 시점에 바로 적용할 결정 사항은 아니다.
- [해석] 다만 open-kknaks-mcp를 로컬 stdio가 아니라 원격·다중 인스턴스로 배포하는 방향을 검토하게 되면, 세션 상태를 서버 프로세스에 두지 않는 설계가 이 자료가 설명하는 것과 같은 이유로 유리할 수 있다는 점은 참고할 만하다.
- [해석] MCP 클라이언트와 서버 간 추가 입력이 필요한 흐름(예: 사용자 확인)을 새로 설계할 일이 있다면, 서버가 클라이언트를 역호출하는 구조 대신 "정보 부족 응답 후 클라이언트 재요청" 형태로 설계하는 편이 신규 스펙 방향과 맞는다.

## 한계와 검증이 필요한 부분

- 스펙 원문(공식 changelog, SDK v2 릴리스 노트)을 직접 확인하지 않았다. 이 노트는 2차 해설 영상만을 근거로 한다.
- 채널명 표기가 자료 내에서 일관되지 않는다 — 영상 메타데이터는 "Bloom AI", 화자는 영상 말미에 스스로를 "블루 AJ"로 소개한다. 정확한 채널명은 원 링크 재확인이 필요하다.
- "여러 서버 로드밸런싱" 예시는 화자가 든 가상의 설명이며, 실제 MCP 배포 사례나 수치로 뒷받침되지 않는다.
- MRTR 구조의 구체적인 메시지 포맷, 에러 처리, 하위 호환성 여부는 다루지 않는다 — 스펙 원문 확인이 필요하다.
