## 무슨 일 하는지

피부과 전용 CRM과 MSO(Multi-Site Operation) 백엔드를 맡고 있으며, 레거시 의사결정 흐름을 Action Runtime의 정식 도메인으로 이식하는 워크플로 엔진(스테이지·엣지·Action·권한·알림 축)과 그 워크플로가 노출하는 MCP tool 표면(조회/쓰기 tool 인벤토리와 인증 정책)의 스펙·구현을 함께 주도하고 있다. 조직 데이터 모델에서 사람 참조를 `users`에서 `organization_member`로 전환하는 cutover를 도메인별로 확장하는 작업과, 업무 관리 축에서 task를 업무의 정본으로 두고 WBS 업무 행을 간트·조직축 정렬만 얹는 선택적 projection으로 재정의하는 작업도 함께 이끌고 있다.

## 담당 영역

backend 중심으로 도메인 모델과 API를 설계하고, 제품 스펙(SPEC)과 작업계획(WP) 문서로 워크플로·MCP tool 계약을 먼저 정의한 뒤 별도 구현 레포의 실제 구현과 짝을 맞추는 방식으로 일한다. 그 과정에서 알림·권한·태스크 라이프사이클뿐 아니라, 어떤 tool을 세션에 노출할지(노출 축)와 그 tool 호출에 사람 인증을 요구할지(인증 축) 같은 크로스커팅 관심사를 스펙 레벨에서 조율하고, 사람 참조 축·업무 정본 축처럼 여러 도메인에 걸친 데이터 모델 전환과 그에 따른 RBAC 규칙 조정도 함께 설계한다.

## 챌린지

- 스펙을 구현 전에 완벽하게 쓰기보다, 구현·실측 중 드러난 괴리(배정 알림 종수, round_no 축 오류, DnD 삽입선 좌표계 불일치, MCP 토큰 만료·스트림 유실 위험 지점, 도메인 스펙과 공용 카드 골격 간 필드명 불일치로 인한 값 누락, 회의록 근거 축의 wire 키 표기 오류(ts_start/ts_end로 적었으나 실제는 ts), 초안 승인 전 수정 지시 대상 부재, Task 칸반보드 스펙이 데이터·행동 계약만 담고 시각 규칙(반복 태그 제거·공통값 생략·밀도)은 암묵으로 남겨 실기동 2회 반려된 것 등)를 "소정합"이라는 이름으로 스펙에 계속 환류하는 방식으로 운영한다.
- 레거시 데이터와 신규 workflow 데이터를 한 대시보드에 합류시키는 문제나 미종결 건 이관처럼, 스코프를 유보했다가 원칙만 먼저 합의하고 실행 시점은 배포 시점으로 유보해 리스크를 관리하는 판단을 반복하며, 레거시 의사결정 원장은 결국 tool 표면에서 완전히 은퇴시키고 신규 workflow로 이관을 마무리했다.
- 세션에 노출할 tool을 설계할 때 "후보에 넣을지"·"호출에 인증을 요구할지"·"승인 카드를 요구할지"를 서로 다른 층의 통제로 나눈다 — 민감한 write 경로는 후보 목록에서 아예 빼고, 승인 카드 필요 여부는 검수할 AI 산출물이 있는지로 가른다(사실을 그대로 전달하는 즉시형 조작은 처음부터 해당 없음). 범용 "승인 요청 tool 1개"로 여러 도메인을 묶는 안은 tool 1개=권한 선언 1개 원칙이 깨져 기각한다.
- 설계상 있어야 할 흐름(발화→승인 게이트)이 실제 코드엔 그 게이트를 열 tool이 없는 경우, 신규 기능이 아니라 "계약됐지만 구현이 빠진 조각"으로 규정하고 전제조건으로 못박아 우선순위를 분명히 한다.
- 사람 참조 축 전환처럼 도메인을 확장할 때는 배정 자리만이 아니라 감사·결재선 자리까지 전수조사해, 부분 전환으로 인한 도메인 내부 불일치를 미리 차단한다.
- 업무 관리 모델에서는 task를 정본으로 못박고 WBS 업무 행 같은 파생 뷰의 존재 여부는 정본과의 연결로만 판정되게 하며, 권한 규칙도 신규 업무는 담당자를 필수로 강화하되 레거시 호환 예외는 좁게 남겨 절충한다.
- SPEC-031에서는 최종본 트랜스크립트가 전량 교체 저장 방식이라 재삽입 시 벽시계 시각이 덮어씌워지는 문제를 되살리는 설계(녹음 시작 앵커 컬럼, finalize 재계산 등)까지 검토했으나, "필요한 건 정확한 시각이 아니라 해당 구간으로의 점프"라는 이유로 복원 설계 자체를 하지 않기로 확정하는 비용 대비 효용 판단을 내렸다.

## 배운 점

- 승인 같은 행위 자체가 추적 가능한 태스크로 남아야 한다는 설계(부트스트랩 태스크)가 여러 워크플로에서 재사용 가능한 패턴임을 확인했다.
- 설계 초안의 가정(축 오류·좌표계·위험 지점·시각 규칙 누락)은 스펙 선행만으로는 안 잡히고 구현·실측과의 짧은 피드백 루프에서 뒤집히며 드러난다 — 데이터·행동 계약과 시각 규칙 계약은 서로 다른 층이라 따로 명시해야 하고, 답만 채우지 않고 질문과 계약 자체를 다시 쓴다.
- tool 노출 여부(노출 축)와 사람 인증 요구 여부(인증 축)를 분리해서 설계하면, 같은 통제 패턴을 다른 세션·에이전트 표면에도 그대로 재사용할 수 있다.
- 정본 엔티티를 하나로 못박고 파생 뷰의 존재 여부를 정본과의 연결로만 판정하게 하면, 업무 관리처럼 다른 도메인의 데이터 모델에도 재사용 가능한 패턴임을 확인했다.
- 승인 카드 정보는 최종 값(facts) → 변경분(diff) → 결과 미리보기(preview) 순으로 배치해야 한다 — 변경분을 먼저 보이면 사용자가 아직 모르는 값의 증감부터 읽게 되는 문제를 e2e 검증에서 발견했다.
- 근거 축은 "정확한 값"이 아니라 "재탐색 진입점"을 주면 된다 — 회의 국면(중간본=벽시계, 최종본=녹음경과)마다 시간축이 달라져도 별도 표시 필드 없이 같은 응답 안의 국면 플래그로 판별하게 하면 축이 섞이지 않는다.
