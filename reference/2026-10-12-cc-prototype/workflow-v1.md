## 원칙

- **자동은 없다.** 고객 이동 · 시술 추가 · 배정은 KOS 에서도 사람이 손으로 한다. 관제도 같다
- **배정 = 데스크.** 시작 · 종료 = 그 직원 본인 탭 · 폰(의사 · 상담사 · 피부관리사)
- **KOS 필드 그대로.** 없는 정보를 다른 필드로 짐작해 채우지 않는다
- **동선은 관제가 주관한다**(사용자 2026-10-13). 순서 · 방 · 담당 · 시작/종료 시각은 관제 DB 가 정본. 단 각 단계에 KOS 작업 `sequence` · `ticketId` 를 같이 저장한다(KOS 가 작업을 순번으로 가리킴 — HAR)
- **KOS 는 읽기 + 결과만 쓰기.** 읽기: 예약 · 고객 · 결제 · 시술권 · 직원 / 쓰기(나중, 공개 API 있는 것만): 진료 단계 `changeFlowStep` · 상담 메모 `updateScheduleConsultationInfo` · 예약 메모 `changeReservationMemo`
- 공개 API 에 없는 결과 — **시술권 사용 처리(AVAILABLE → USED)** 가 1순위. 연동 때 KOS 에 요청
- **PoC 에서는 KOS update API 를 절대 호출하지 않는다**(운영 데이터). 어느 API 를 쓸지 **기록만** 하고, 코드에는 그 조작 자리에 아래 주석만 넣는다(호출 코드 없음):

```text
## ============kos api 연동 필요 ========================
## <api 명>
## ======================================================
```

## 큰 흐름 (사용자 원문 기준)

```text
예약 → 내원 · 접수 → 상담(상담실장) → 결제 → 데스크가 결제된 시술 중 오늘 할 것 선택 → 배정 → 시술(본인 시작 · 종료)
```

## KOS 진료 단계(`flowStep`) — 흐름의 뼈대

KOS update API `changeFlowStep`(스냅샷 스펙 `protos.open.OpenChangeFlowStepCommand.step`)에 정의된 단계. 관제의 각 조작이 나중에 이 단계 변경으로 KOS 에 간다.

| `flowStep` | 의미 |
|---|---|
| `RESERVED` | 예약됨 |
| `RECEPTION` | 접수 |
| `CONSULTATION_WAITING` | 상담 대기 |
| `CONSULTATION` | 상담 |
| `PROCEDURE_WAITING` | 시술 대기 |
| `PROCEDURE` | 시술 |
| `PROCEDURE_DONE` | 귀가 대기 |
| `COMPLETED` | 귀가 |

캡처(하루 끝 상태)에는 `COMPLETED` 151 · `RESERVED` 26 만 남아 있다(중간 단계 이력 없음).

## PoC 범위(사용자 2026-10-13)

- **데이터 = 목데이터(실데이터 바탕)**: 시드 = 「아침에 KOS 에서 받아 온 것」(예약 · 고객 · 보유 시술권 · 이전 상담 기록 · 직원) / 이벤트 = 「진행하다 KOS 에서 들어오는 것」 — 상담 완료 때 상담 기록 · 오더 메모 · 상담사가 넣은 시술(수납필요) · 결제 금액, [결제 완료] 때 시술권. 목업 고객마다 10-09 실제 방문 하나를 대본으로(이름만 가짜), 시드에 없는 장면(재내원 · 남은 시술권 · 지난 상담)은 같은 양식으로 만든다. 모양은 KOS 응답 그대로

- **KOS 호출 없음 — 주석만.** 공식 · 비공식(내부) API 로 될 가능성은 확인했으니 연결은 하지 않는다. 데이터 = 10-09 캡처

## 동선이 메인 데이터(사용자 2026-10-13)

- **동선(단계: 시술 · 순서 · 담당 · 상태 · 시각)이 메인 데이터.** 메모(오더 · 상담 · 예약 · 담당자)는 **참고용 임시 데이터** — 동선을 만들 때 보는 입력이고, 화면의 기준은 동선이다
- 오더 메모의 번호 줄 = 시술 순서의 근거 → 데스크가 보고 동선을 맞춘다. 이후 바뀌는 것(의사가 순서 변경 · 빼기 · 추가)은 **메모를 고치지 않고 동선을 고친다**(순서 바꾸기 · 진행 안 함 · 시술 추가). 결제가 바뀌는 변경은 KOS 에서
- KOS 에 결과로 보내는 것도 동선(단계 · 시술 완료/취소 · 담당)
- **오늘 오더 = 동선.** 데스크(또는 간호사)가 오더 메모를 보고 시술을 순서대로 넣으면 **그 동선이 곧 오늘 오더**다. 오더 메모 텍스트는 그 뒤로 아무도 고치지 않는 임시 글 → **화면의 「오늘 오더」 는 동선(시술 · 순서 · 담당 · 상태)으로 보여 준다.** 시술 추가 · 순서는 **현황판에서**(데스크 · 간호사 공용) 오더 메모 원문은 [시술 추가] 할 때만 옆에 참고로, 특이사항은 ⚠ 로(사용자 2026-10-13)

## 메모 원칙(사용자 2026-10-13)

**메모는 「언제 쓰였나」에 따라 보인다 — 화면에는 그 시점에 이미 존재하는 메모만.**

| 메모 | 생기는 시점 | 보이는 시점 |
|---|---|---|
| 과거 방문의 메모 전부(상담 · 오더 · 예약 · 담당자) · 시술 이력 · 보유 시술권 | 지난 방문 때 | **언제나**(예약 상세 · 방 패널 오른쪽 히스토리 · 직원 환자 상세) — 접수 전에도 있다 |
| 고객 메모 | 고객 등록 · 수정 때 | 언제나 |
| 오늘 예약 메모 | 예약할 때 | 예약 때부터 |
| 오늘 상담 메모 · 오늘 오더 | 오늘 상담 중 · 후 | **오늘 상담 종료 뒤** |
| 오늘 담당자 메모 | 그 시술 끝난 뒤 | 그 시술 종료 뒤 |

- ⚠ 주의 · 요청(지정)도 같은 원칙 — 그 메모가 보일 때 같이 보인다
- **메모 양식에 기대지 않는다**(사용자 2026-10-13): 지점마다 쓰는 양식이 다르다(명동점 `------` · `[특이사항]` · `OUT TIME` · `날짜/유입처/…` 는 명동점 습관). **메모는 원문 그대로 보여 주고, 잘라 읽지 않는다.** 구조화된 값은 KOS 구조 필드에서만
- 「오늘」과 「과거」를 섞지 않는다: 화면에서 오늘 칸과 히스토리 칸을 나눈다(방 패널 왼쪽 오늘 · 오른쪽 히스토리)

## 2. 내원 · 접수

- **재내원 고객**: 접수 때 동선 = **기존 시술 리스트(보유 시술권) + 상담 · 원장 진료를 데스크가 추가**

- 고객이 오면 **데스크가 [접수]** → KOS `RESERVED` → `RECEPTION`, 접수 시각 `receptionDateTimeUtc`
- 고객 위치 = **접수대기실** — 시안의 「라운지」와 같은 곳. **화면 이름을 「접수대기실」로 바꾼다**
- 접수대기실 = **접수 전 · 후 고객이 머무르는 같은 공간.** KOS 에 「도착」 단계가 없어 접수 전 고객은 시스템에 안 나온다 → 관제의 접수대기실에는 **[접수]한 고객만** 보인다. 도착 표시 기능은 만들지 않는다
- KOS API(기록만): [접수] → `changeFlowStep` (step `RECEPTION`)

## 3. 시술실 배정 · 안내

- 고객이 접수대기실에서 기다리면 **코디가 시술실(관리실) 하나에 배정하고 안내**한다
- 관제: 지금 현황판처럼 **방을 클릭해서 고객을 집어넣는다**(시안 「대기 고객 · 선택 후 관리실 배정」)

## 5. 결제

- 상담 뒤 고객은 **상담사와 데스크로 가서 결제**하거나, **시술실에서 바로 결제**한다
- **결제는 KOS 에서 한다**(관제가 하지 않는다) → 결제되면 **시술권이 생긴다**
- 데이터로 확인한 것: 시술권 묶음(`getTicketBundlesQuery`)에 `purchaseId` · `purchaseItemId` 가 붙어 있다 — 결제(상품 옵션 `PRODUCT_OPTION`) 하나 = 시술권 묶음 하나(`ticketSets[]` = 시술, `tickets[]` = 회차 한 장). 이벤트 상품도 같다
- 관제가 결제 · 시술권을 받는 길(기록만): 결제 후 KOS 조회 — 시술권 `getTicketBundlesQuery`, 결제 품목 `getPurchaseItemStatistics` 등(조회 API — 연동 때)
- 결제하러 데스크로 가도 **방은 그대로 점유**한다 — 관제는 단순 이동을 기록하지 않는다
- 「결제 중」 표시 **없음**
- **상담 종료 뒤 방 패널에 상담 결과 · 상담사가 넣은 시술(수납필요) · 미결제 금액(합계)이 보인다.** 금액 옆 **[결제 완료]** 를 누르면 수납필요가 풀리고 미결제 0 → 시술권 연결(사용자 2026-10-13). 실제 연동 땐 이 버튼 = KOS 결제 조회

## 6. 원장 상담 · 시술 추가 · 준비

- 결제 뒤 **원장 상담**이 있다
- **데스크가 원장을 배정**한다(현황판: 방 클릭 → 직원 배정)
- 그사이 **데스크가 오더 메모(시술 특이사항 · 순서)를 보고 결제 시술 후보에서 순서대로 동선에 넣는다**(시술 1장 = 동선 단계 하나) — 시술 추가는 데스크
- **원장**: 탭 · 폰으로 배정을 보고 그 시술실로 이동하면서 **환자 차트 · 상담 내용을 파악**한다 → **상담사가 남긴 것이 원장 화면에 보여야 한다**. 상담사가 KOS 에 남기는 것(사실, `orchestration/work/sts-prototype/research-counselor-trace-report.md`):
  - 상담 기록 `consultations[].content.text` 한 글 — 위 `[상담내용]`(고민 · 이력 · 추천) + `------` 아래 **오더지 사본**(`실장 :` · OUT TIME · 번호 시술 · `[특이사항]` · `[임플란트 여부]`). 결제 뒤에도 고친다(126/138)
  - 구매 담당 `getPurchaseSummaries.assignees` = 상담사(160/168) · 거래 담당 `transactions[].assignee`(157/173)
  - 구조로 남기는 상담 시술 `consultationProcedures` 는 145건 전부 비어 있음 — 권한 시술은 메모 글로만
  - `orderMemo` 작성자 칸 없음(상담 메모 오더지와 87/137 같음 · 37% 어긋남). 원장 상담 [시작] · [종료]는 원장 본인 화면
- **간호사**: **업데이트된 시술을 보고** 그에 맞는 **시술 준비**를 한다 → 간호사 화면(순회형)에 환자별 오늘 시술(데스크가 추가한 것)이 보여야 한다
- 데이터상 순서: 결제 승인 → 시술권 생성(약 1초) → 시술 작업 ready(중앙값 0.2분). 사용자 판단: **시술권이 생기면 직원이 작업을 생성하는 것**(현장 확인)
- **시술 순서가 중요하다**(순서에 따라 시너지가 다름). **가정: 데스크가 오더 순서대로 잘 넣는다**(오더 메모의 번호 줄 순서 · KOS 작업 `sequence`). 관제는 넣은 순서 = 동선 순서
- **시술 순서 바꾸기**: 시술 리스트에서 고른 순서 ≠ 오더 순서일 수 있다 → **방을 선택했을 때(방 패널) 그 방 고객의 시술 순서를 바꿀 수 있게** 한다. 방이 대기 상태일 때 **간호사나 데스크가** 바꾼다 — 어차피 원장 배정할 때 같이(사용자 2026-10-13)
- KOS 작업에 순번이 있다: `tasks[].sequence`(스펙 「태스크 순번」, `order` 와 같은 값) — 일정 146건 중복 0, 시술 2개 이상 126건 중 122건이 순번 = ready 시각 순서. 관제는 **자기 쪽에서 순서를 관리**한다(동선 정본 = 관제). 단 **각 단계에 KOS 작업 `sequence` 를 같이 저장**한다 — KOS 가 작업을 순번으로 가리킨다(HAR `cancel-flow-tasks`)
- KOS 작업 목록 모양(데이터): 1번 = `방 점유/원장 상담`(ETCETERA, 144/146 — 기타 작업은 이것 한 종류) → 2번~ = 시술(PROCEDURE, 시술권 1장씩). 작업 2개 이상 139건 중 116건이 전부 같은 방(덮어쓰기 가능성 있음). 상담사 상담 · 접수 · 귀가는 작업이 아님 → **관제는 KOS 작업 목록을 「원장 상담 1 + 결제한 시술들」 참고 자료로만 쓴다**(사용자 2026-10-13)
- **관제 흐름: 결제 완료(KOS) → KOS 불러오기(시술권 조회) → 데스크(혹은 다른 직원)가 관제에서 시술 생성(동선 작업) → KOS 업데이트**(PoC 는 기록 · 주석만)
- KOS(기록만): 원장 = 작업 `doctors` · `doctorCallDateTime`(원장 호출) · 상담 기록 `consultationDoctors` / 시술 추가 = 일정 작업(`tasks[]`)에 시술권(`ticketId`) · `sequence` 로 작업 추가 — **작업 추가 쓰기 API 없음.** 2026-10-13 현재 공개 스펙(`https://developers.kos-solution.com/openapi.yaml`, 75개)으로 다시 확인: 9월 스냅샷 대비 추가는 `changeReservationMemo` · `getAccounts` 둘뿐. 일정 쓰기 작업 = 예약 · 예약 변경/취소 · `changeFlowStep` · `changeReservationMemo` · `updateScheduleConsultationInfo` · `createOccupiedTime`. 시술 추가 · 방 배정 · 담당 배정을 보내는 API 는 공개 스펙에 없다 → 연동 때 KOS 에 요청하거나 그 부분은 KOS 화면에서

참고(데이터로 확인한 것): KOS 동선 = 일정의 `tasks[]`. 시술 작업 574/574 에 `procedureConfiguration.ticketConfiguration.ticketId` · `round` — 시술권 한 장을 동선에 넣으면 작업 하나

## 7. 시술

- 원칙적으로 **원장 상담이 끝나면 원장이 바로 시술을 시작**하고, **간호사가 세팅**한다
- **PoC: 원장 상담 [종료] 뒤 방 상태 = 「원장 대기 · 세팅 준비」** → 원장이 본인 화면에서 시술 [시작] · [종료]
- **원장 배정은 시술 단위**(사용자 2026-10-13). 원장마다 할 수 있는 시술이 다르다(예: 제모는 누구나, 보톡스는 전문의) — 규칙화하지 않고 **데스크가 시술마다 배정**한다
  ```text
  환자 동선: 1. 시술1 → 2. 시술2 → 3. 시술3
  데스크: 시술1 에 원장(예: 권태윤) 배정 → 원장 [시술 시작] · [시술 종료] → 방 상태 「다음 시술 대기」
  데스크: 시술2 에 원장 배정 → … 반복
  ```
- **피부관리사 시술도 원장 시술과 똑같다** — 시술마다 데스크(또는 코디)가 피부관리사를 배정 → 피부관리사가 본인 화면에서 [시술 시작] · [시술 종료] → 「다음 시술 대기」(사용자 2026-10-13)
- 데이터와 맞음: KOS 시술 작업마다 `doctors` 칸이 따로 있다(작업 단위 의사)
- **이 구조라야 다음 사람이 움직인다**(사용자 2026-10-13):
  - 원장이 [시술 종료] → **코디 · 간호사가 「시술 끝났군」을 보고 들어와** 다음 동선 배정이나 다음 원장 배정을 한다 → 순회형 화면(코디 · 간호사)에 시술 종료 · 「다음 시술 대기」가 보여야 한다
  - 또는 **다음 원장이 자기 화면에서 「다음 스케줄 대기」를 보고** 그 방으로 간다 → 배정형 화면(원장)의 「다음」에 보여야 한다
  - 배정은 현황판이 원칙이지만 코디 · 간호사가 폰에서 하는 경우도 있다(3단계와 같음 — PoC 범위는 정할 때)
- **현황판에서 방을 누르면 시술 정보가 뜬다 — 방 패널은 고객 중심**: 그 방 고객의 동선 단계를 한 줄씩(상담 · 원장 상담 · 시술1 · 시술2 …, 시술은 한 개 = 한 줄), **단계마다 [배정]** → 그 단계에 맞는 직원 목록에서 고른다. 단계별 배정 직원 · 상태 표시
- **수면실 이동**: 수면 시술은 수면실로 옮긴다. 이때 **기존 방도 계속 점유**한 채 수면실로 이동한다(사용자 2026-10-13). 시안 현황판에 이미 있는 동작 — 「수면실로 이동」(원래 방 기억 · 그 방은 다른 고객 못 넣음) → 수면 시술 끝나면 원래 방으로 돌아옴. 화면 이름도 도면대로 **「수면시술실」**(01–03)로 한다(시안의 「수면실」 → 「수면시술실」)
  - 데이터: KOS 시술 작업 `anesthesiaType` 은 `CREAM` 128 · 미지정 446 뿐 — **수면 마취를 가리키는 값이 캡처에 없다.** 어느 시술이 수면인지는 데스크가 정한다(데이터로 규칙화 불가)
- 원장 화면의 버튼은 그 환자의 지금 단계에 따라 **두 가지** — 원장 상담이면 [상담 시작] · [상담 종료], 시술이면 [시술 시작] · [시술 종료]
- KOS(기록만): `PROCEDURE_WAITING`(시술 대기) → `PROCEDURE`(시술) = `changeFlowStep`

## 8. 귀가

- 동선의 모든 단계가 끝나면 **간호사나 코디가 고객을 모시고 데스크로** 온다 → 데스크가 안내 → 귀가
- **어느 단계에서든 귀가할 수 있다** — 상담만, 원장 진료까지만 하고 갈 수도 있다(남은 단계는 하지 않음)
- KOS(기록만): `PROCEDURE_DONE`(귀가 대기) → `COMPLETED`(귀가) = `changeFlowStep`
- **귀가는 데스크가 한다** — 데스크에서 그 고객을 눌러 **[귀가] 처리**
- 귀가는 잠깐 자리 비움(결제)과 다르다 → **귀가 처리 때 방을 비운다**
- 중간 귀가면 남은 단계는 **「진행 안 함」으로 로그를 남긴다** — 나중에 그 시술권이 **차감되지 않게**
- KOS 화면에서 시술권이 처리되는 방식(데이터 — 시술권과 이어진 작업 11개, 표본 작음): **작업 DONE → 시술권 USED(4) · 작업 CANCELED → 시술권 AVAILABLE 그대로(7)**, 일정은 모두 귀가. 시술 완료 시각이 귀가 직전(1분 · 10분 차) → **귀가 때 데스크가 시술마다 완료/취소를 정리 → 완료분만 차감 → 귀가**로 보인다. `changeFlowStep` 의 「COMPLETED 로 바꿀 때 완료되지 않은 시술」 오류와 맞음. 시술권엔 사용 시각 칸 없음(`id` · `status` · `price` · `createdDateTimeUtc`)
- 관제의 「진행 안 함」 = KOS 작업 **CANCELED**(시술권 차감 안 됨)
- **KOS 반영은 시술 [종료] 때마다**(사용자 2026-10-13): 원장 · 피부관리사 [시술 종료] → KOS 그 시술 작업 DONE(시술권 차감). 매칭 = `ticketId`(관제 단계 1개 = 시술권 1장 = KOS 작업 1개). 귀가 때는 **남은 단계만** 「진행 안 함」→ CANCELED, 그리고 `changeFlowStep(COMPLETED)`
- KOS 에 요청할 API(구체): **「시술 작업 상태 변경」** — 일정 id + 작업(또는 `ticketId`) → DONE / CANCELED, 시술권 차감 연동
- 그날 KOS 에 넣는 것 전체(PoC 는 기록 · 주석만):
  | 무엇 | KOS 쪽 | 공개 API |
  |---|---|---|
  | 진료 단계 → 귀가 | `flowStep` `COMPLETED` | `changeFlowStep` 있음 |
  | 완료한 시술 → 시술권 사용 처리 / 「진행 안 함」 → 차감 안 함 | 작업 DONE/CANCELED → 시술권 USED/유지 | **없음(작업 완료/취소 쓰기) — KOS 에 요청 1순위.** 2026-10-13 현재 공개 스펙 75개 재확인: 시술권 API 는 조회 `get-ticket-bundles` 하나, 쓰기 25개 중 시술권 · 시술 작업 · 결제 쓰기 없음. `changeFlowStep` 에 「COMPLETED 로 바꿀 때 완료되지 않은 시술이 남아 있음」 오류가 있다 → KOS 안에서 시술 완료를 관리하지만 공개 API 로는 못 한다(파트너용 API 유무는 KOS 에 문의) |
  | 시술별 담당 원장 · 피부관리사 · 방 · 시각 | 작업 `doctors` · `assignees` · `room` · 시각 | **없음** |
  | 상담 기록(차티) | 상담 메모 | `updateScheduleConsultationInfo` 있음(메모만) |
  | 예약 메모 덧붙임 | 예약 메모 | `changeReservationMemo` 있음 |

## KOS 반영 표 — 단계가 끝날 때마다 최대한 바로(사용자 2026-10-13)

PoC 는 호출하지 않는다. 각 조작 자리에 `kos api 연동 필요` 주석(✅ = API 이름 · ❌ = 「공개 API 없음 — KOS 요청」). 근거: 2026-10-13 현재 공개 스펙 75개.

| 관제 조작 | KOS 에 반영 | 공개 API |
|---|---|---|
| 데스크 [접수] | 단계 `RECEPTION` | ✅ `changeFlowStep` |
| 시술실 배정 | 단계 `CONSULTATION_WAITING` | ✅ `changeFlowStep` |
| ↳ 방 | 작업의 방 | ❌ |
| 상담사 [상담 시작] | 단계 `CONSULTATION` | ✅ `changeFlowStep` |
| ↳ 상담사 | 상담 기록 상담사 | ❌ |
| 상담사 [상담 종료] | 상담 메모(차티 기록) | ✅ `updateScheduleConsultationInfo` |
| 결제 | KOS 에서 직접 | (관제는 조회) |
| 데스크 시술 추가 | 시술 작업 생성(시술권) | ❌ |
| 원장 · 피부관리사 배정 | 작업 담당 | ❌ |
| 원장 상담 종료 → 시술 대기 | 단계 `PROCEDURE_WAITING` | ✅ `changeFlowStep` |
| [시술 시작] | 단계 `PROCEDURE` | ✅ `changeFlowStep` |
| [시술 종료] | 그 작업 DONE → 시술권 차감 | ❌ 요청 1순위 |
| 마지막 시술 종료 | 단계 `PROCEDURE_DONE` | ✅ `changeFlowStep` |
| 데스크 [귀가] | 남은 작업 CANCELED · 단계 `COMPLETED` | ❌ · ✅ `changeFlowStep` |
| 예약 메모 덧붙임 | 예약 메모 | ✅ `changeReservationMemo` |

⚠ `changeFlowStep` 은 **단계 표시만 바꾸고 시술권을 차감하지 않는다.** 문서(`/docs/openapi/change-flow-step.md`, 2026-10-13)에 정의된 거절 조건:
- `CONSULTATION` — 상담 담당자가 지정돼 있지 않으면 거절
- `PROCEDURE_WAITING` · `PROCEDURE` — 시술 목록이 없으면 거절
- `COMPLETED` — 완료되지 않은 시술이 남아 있으면 거절

→ 상담사 지정 · 시술 작업 추가 · 시술 완료를 API 로 못 하므로 위 ✅ 중 `CONSULTATION` 이후 단계는 **KOS 화면에서 먼저 해 둬야 통과**한다. 공개 API 만으로 확실히 되는 것: `RECEPTION` · `CONSULTATION_WAITING` · 메모 2종

**KOS 화면에는 기능이 다 있다**(사용자 캡처 2026-10-13, `app.kos-solution.com` 내원 현황): 시술 카드 동작 바 = 시술메모 · 마취 · 우선순위 · 담당자 · 방 · 집도의 · 간호관리차트 · 의사차트 · **시술 완료하기 · 시술 취소하기**. 「귀가 대기」로 바꿀 때 미완료 시술은 「일괄 취소 후 단계 변경」. → KOS 서버엔 API 가 있고 **공개 OpenAPI 에만 안 열려 있다**

KOS 에 요청할 것 = **KOS 웹앱 동작 바를 OpenAPI 로 열어 달라**:
| 관제 조작 | KOS 화면 동작 |
|---|---|
| 시술별 원장 · 피부관리사 배정 | 집도의 · 담당자 |
| 방 배정 · 이동 | 방 |
| 시술 순서 | 우선순위 |
| [시술 종료] → 시술권 차감 | 시술 완료하기 |
| 「진행 안 함」 | 시술 취소하기 |
| 귀가 | 단계 변경(미완료 일괄 취소 포함) |
| 상담사 지정 · 시술 추가 | (화면 위치 확인) |

코드 주석에 KOS 화면 동작 이름을 같이 적는다(예: `## 시술 완료하기 — 공개 API 없음, KOS 요청`)

**KOS 웹앱 내부 API 확인(DEMO HAR, 2026-10-13 — `orchestration/work/sts-prototype/research-kos-har-report.md`)**
- 내부 호스트 `api.kos-solution.com/tenants/{tenantId}/…` (공개 `open-api.kos-solution.com` 과 다름)
- 단계 변경 = `…/schedule/v1/commands/change-flow-step` `{id, step}` — 공개 `changeFlowStep` 과 같음
- **「귀가 대기 + 미완료 일괄 취소」 = 요청 2개**: ① `…/schedule/v1/commands/cancel-flow-tasks` `{scheduleId, sequences:[1,2,3,4], reason:"CANCEL"}` → ② `change-flow-step` `PROCEDURE_DONE`. ①은 **공개 없음**
- ⇒ **KOS 는 시술 작업을 `sequence`(작업 순번)로 가리킨다.** 관제는 동선을 주관하더라도 **각 단계에 KOS 작업 `sequence` 를 같이 들고 있어야** 취소 · 완료를 KOS 에 보낼 수 있다(앞의 「`sequence` 는 참고」 정정)
- 공개에 없는 조회: `get-rooms`(방 목록 28개 — 방 마스터) · `get-roles`(역할 15개) · `get-accounts-last-update`
- **2차 HAR(`research-kos-har2-report.md`)** — 내부 API(전부 `POST api.kos-solution.com/tenants/{tenantId}/…`, 공개 없음):
  | 화면 동작 | 내부 경로 | 본문 |
  |---|---|---|
  | 상담사 지정(상담 기록 생성) | `consultation/v1/commands/create-consultation` | `{consultationId, visitorId, consultationStartedDateTimeUtc, scheduleId, content:{text}, counselorIds[]}` |
  | 상담 의사 지정 | `consultation/v1/commands/change-consultation-doctors` | `{consultationId, doctorIds[]}` |
  | 담당자 | `schedule/flow/v1/commands/change-tasks-assignees` | `{scheduleId, sequences[], assigneeIds[]}` |
  | 집도의 | `schedule/flow/v1/commands/change-tasks-doctors` | `{scheduleId, sequences[], doctorIds[]}` |
  | **시술 완료하기** | `schedule/flow/v1/commands/change-tasks-complete` | `{scheduleId, sequences[], complete:true}` → 작업 DONE |
  | 미완료 일괄 취소 | `schedule/v1/commands/cancel-flow-tasks` | `{scheduleId, sequences[], reason:"CANCEL"}` |
  - 작업 쓰기는 전부 **`scheduleId` + `sequences[]`** 로 가리킨다(task id · `ticketId` 안 씀)
  - `consultationStartedDateTimeUtc` = 상담사 지정 순간의 브라우저 시각(상담 기록 「생성 순간」 53건의 정체)
  - 시술권 차감 여부는 미확인 — DEMO 작업에 시술권이 없었다(결제 없음)
- 아직 모름: 방 · 우선순위 · 시술 추가 · 단건 취소(같은 `cancel-flow-tasks` 에 순번 1개로 추정)

## 현장 확인할 것

- KOS 화면에서 시술에 「수납필요」 표시(작업 `paymentRequired`) — **결제 전에 시술이 동선에 들어가 있을 수 있다.** 「결제 → 시술권 → 시술 추가」 순서와 다른지

- 수면 시술을 어떻게 구분하나(KOS 마취 칸에 수면 값 없음) · 수면실 이동은 누가(데스크 · 코디 · 간호사)

- 원장 배정을 시술 단위로 하는 게 맞나 · 원장별 가능 시술(전문의 시술) 목록이 있나

- 시술 순서를 누가 어떻게 정하나(가정: 데스크가 오더 순서대로 넣음) · 관제에서 순서 바꾸기가 필요한가

- 원장 상담과 시술을 현장에서 **따로 누르나, 「상담+시술」 하나로 묶나**

- 원장 상담 뒤 시술 세팅 동안 원장이 **나갔다 다시 들어오나, 방에서 같이 대기하나**

- 시술권 → 시술 작업 생성을 현장에서 누가 하나(사용자 추정: 직원이 생성) · 관제에서 시술 생성 담당이 데스크인지 다른 직원인지

- 간호사가 담당으로 붙은 시술 단계는 누가 시작 · 종료하나 — 임시: 그 단계 원장
- 시술별 기본 방이 있나(캡처: 보톡스는 방 무관, 필러 5건 중 4건 시술실1)
