## 0. 왜 하나

상담 앱 구조(10-30 결정 「목표 · 아키텍처」)는 `Jev → 허브 도구 → Claude` 다. 아래 두 질문의 근거가 아직 없다.

1. **골드가 답의 품질 · 속도를 올리나** — 원장을 그대로 Claude 에 주는 것과 비교
2. **Jev 를 쓰는 의미가 있나** — 결정표에 남은 Jev 의 이유는 「빠름」(10-30) 하나 · 잰 기록 없음.
   DEC-001 D-08 기준 Jev 의 역할 = 발화 → 슬롯(허브 노드 id 목록 안에서 · TypeSafe) · 신뢰도 낮은 슬롯은 Claude 가 되묻기에 씀

부수로 「허브 도구를 누가 부르나(앱 서버 / LLM 도구 호출)」(미정)에 대한 근거도 이 비교에서 나온다.

### case1 — 원장 + Claude (기준선)
- 데이터: 브론즈 원장 json 21개 — 로컬 `/Users/kknaks/orca/workspaces/PROCEDURE-HUB/phub-stg-2026-10-26/`(1.2MB · 10-26 「stg 공개 GET 21개를 브론즈로」)
- 허브 · Jev 없음. 원장을 Sonnet 에 주고 답하게 한다
- **구현 전 정할 것**: 원장을 넣는 방식(§7 O-1)

### case2 — 골드 + Claude
- Sonnet 이 허브 도구(MCP)를 **직접 호출**한다 — 말 해석 · 어떤 도구를 부를지 · 탐색 경로를 Sonnet 이 정함
- 도구를 부를 때마다 Sonnet 왕복이 한 번씩 생긴다
- 허브 도구 목록은 골드 설계에서 정해진다(지금 미정 — `gold-research` 진행 중)

### case3 — 골드 + Jev + Claude (설계안 그대로)
- Jev: 질문 → 의도 + 슬롯(허브 노드 id) — 선택지는 허브가 노드 목록 · 스키마로 제공(10-26)
- 앱 서버: 슬롯으로 의도별 탐색 경로를 **한 번** 호출
- Sonnet: 탐색 결과를 받아 답 문장만 씀(1번)

### 비교가 답하는 것

| 비교 | 답하는 질문 |
|---|---|
| case1 ↔ case2 | 골드가 품질 · 속도에 도움이 되나 |
| case2 ↔ case3 | Jev 가 의미 있나 — ① 빠름(시간) ② 정해진 꼴 출력(case2 Sonnet 이 고른 노드 vs case3 Jev 슬롯, 어느 쪽이 정확한가) |

case2 와 case3 의 차이:

| | case2 | case3 |
|---|---|---|
| 말 해석 | Sonnet | Jev |
| 허브 호출 | Sonnet 도구 호출 | 앱 서버가 Jev 슬롯으로 |
| LLM 왕복 | 도구 호출 수만큼 | Jev 1 + Sonnet 1 |
| 탐색 경로 | Sonnet 이 그때그때 | 의도별 고정 |

## 4. 품질 평가 — 두 층

```
답변 ─┬─▶ ① 단어 검사 (결정론 · 원장 대조)
      │     이름 뽑기 → 정규화 → 원장에 있나?  → 「없는 이름 N개」
      │
      └─▶ ② Opus 채점 (판단)
            관계 · 숫자 · 안전 빠뜨림 · 후보 처리 · 불확실 표시 · 질문에 답함
```

### ① 단어 검사 (결정론)

목적: **지어낸 이름**을 숫자로 센다. 원장 기준이라 세 케이스에 똑같이 공정하다.

1. **이름 뽑기** — 답에서 시술 · 제품 · 장비 · 부위 이름처럼 보이는 것을 전부 뽑는다
   - ⚠ 시맨틱 사전(표현 1962)으로 답을 훑는 것만으로는 안 된다 — 사전에 있는 말만 찾으므로 **지어낸 이름은 애초에 안 걸린다**
   - 그래서 뽑기는 별도(LLM 추출 등 — §7 O-4). 뽑기만 하고 **판정은 원장 대조**라 Opus 채점보다 흔들림이 작다
2. **정규화** — 시맨틱 사전 정규화와 같은 규칙: 공백 제거 · 영문으로 시작하면 소문자 · 라틴 악센트 제거(`semantic.md` §4)
3. **대조** — 원장 21개 문자열 전체(정규화 뒤)에 있나 · 시맨틱 사전의 표현 · 변형으로도 확인(표기 차이 거짓 경보 줄이기)
4. **출력** — 이름마다 `{name, norm, found: true|false, where[] (원장 파일 · 경로)}` · 열마다 「없는 이름 N개」

못 잡는 것(→ ② 의 몫):

| 경우 | 예 |
|---|---|
| 단어는 맞고 관계가 틀림 | 「팔자엔 보톡스」 — 둘 다 원장에 있음 |
| 숫자 틀림 | 「사우나 1주」(원천 2주) |
| 빠뜨림 | 금기 · 주의를 아예 안 말함 |
| 원장에 있지만 쓰면 안 됨 | 허가 취소 제품 — 원장엔 이름이 있음(추천 제외는 실버 표시) |

### ② Opus 채점 (판단)

항목별 **통과 / 실패 / 해당 없음** — 100점 하나로 매기지 않는다(흔들림).

| 항목 | 묻는 것 | 근거 결정 |
|---|---|---|
| 정확성(관계 · 숫자) | 시술 ↔ 부위 ↔ 고민 관계 · 간격 · 용량 숫자가 원천과 맞나 | — |
| 안전 정보 | 추천한 시술의 금기 · 주의를 같이 말했나 | 10-26 「안전 엣지는 시술 노드와 항상 같이」 |
| 후보 처리 | 뜻이 갈리는 말(「보톡스」 = 계열 · 제품)을 단정하지 않고 고르거나 되물었나 | 10-27 「후보 전부 → 외부 LLM 이 고르거나 되묻기」 |
| 불확실 표시 | 근거 약 · 정보 없음을 「안전함」 · 「확실함」처럼 말하지 않았나 | 시맨틱 표시 gap 「없음 = 안전 아님」 |
| 질문에 답함 | 물은 것에 답했나 · 새지 않았나 | — |

(「지어낸 말 없음」은 ① 이 맡는다 — ② 에서는 「원장에 있는 말로 틀린 주장」만 본다)

공정 장치:
- **가리기** — 세 답의 순서를 섞고 case 이름을 지운 채 채점
- **감점 근거 인용 필수** — 실패마다 「원장 어느 파일 · 어느 내용과 다르다」를 적게 함. 근거 없는 실패는 무효
- **기준 자료** — §7 O-3(구현 전 정할 것)
- **사람 확인** — 처음 몇 건은 사용자가 Opus 채점을 보고 맞다/틀리다 표시(채점관 검수)
