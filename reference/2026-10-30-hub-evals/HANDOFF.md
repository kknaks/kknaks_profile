**제품 목표**: 상담 앱에서 사용자 질문에 빠르고 정확하게 답한다. **case3(골드 + Jev + Claude)을 제품 구조로 쓴다.** case1 · case2는 비교 기준이다.

## 4. 알게 된 것

1. **Claude는 받은 건 쓴다.** 실패의 대부분은 「골드에 있는데 못 가져옴」이었다. v8a 기준 안전 실패 13 중 12, 정확성 실패 20 중 16이다. 「받았는데 안 씀」은 거의 0이었다.
2. **Jev에게 「얼마나 가져올지」를 맡기면 적게 가져온다.** 4걸음 동안 섹션을 합계 3개만 펼쳤다. → **Jev = 의도 · 시작 노드 · 어느 이웃으로 갈지**로 줄이고, **섹션 양은 규칙**(의도 묶음 + 남은 예산 채우기)으로 정했다(v8a).
3. **응답이 크면 놓친다.** 「줬는데 놓침」이 10KB 이하에서는 0%, 80KB 이상에서는 10%였다. 짧은 fact 꼴(섹션 하나 약 2KB)과 예산 20KB로 막는다.
4. **case2는 처음에 실험 장치 탓에 손해를 봤다.** Claude CLI가 MCP 결과를 약 2KB로 잘랐다. 허브 도구 meta `anthropic/maxResultSizeChars=200000`로 해결했다.
5. **안전 실패의 주원인은 확인 조건 노드의 내용**(켈로이드 · 복용약 · 심박조율기 등)이 안전 예산 8KB에서 잘리는 것이다. fullrun-v2 case3 안전 실패 28 중 25가 여기 해당한다. 후보 조건이 시술마다 12~16개이고 필요한 것이 7~8번째에 있다.
6. **노드 상당수가 빈 껍데기다**(골드 567677ed 기준).

   | 종류 | 노드 수 | 사실이 0개인 노드 |

## 8. 함정

- **구독 한도**: 239 × 3 + Opus 채점은 5시간 한도에 여러 번 걸린다(fullrun-v2는 2회 대기 · 약 7시간 반). 배치는 한도가 열리면 이어서 돈다. 한도에 걸린 순간의 채점은 비니 끝나고 다시 채점한다(`rejudge`).
- **계정을 바꾸면 떠 있는 워커 claude 프로세스는 옛 계정에 묶여 있다.** 워커마다 `/exit` → `claude --dangerously-skip-permissions` 재실행 → 발주서 경로 + taskId + dispatchId를 다시 넣는다.
- **orca 발주는 Run 바인딩이 필요하다**(`orca orchestration run-create` · 지금 run = `run_fe7f55b0e98e`). 새 터미널은 claude를 먼저 띄워야 `--inject`가 된다. 터미널이 `exited`면 새로 만든다.
- **허브를 재시작하면 측정이 섞인다.** 재실행 도중에는 18005를 재시작하지 않는다. 빌드 발행(DB 포인터)은 재시작 전까지 서버에 반영되지 않는다.
- **공개 레포**(profile · clinic_chat): 키 · 원장 · 실버 · 골드 · runs · 환자 정보 · 사용자 홈 경로 커밋 금지. `runs/` · `build-out/`은 gitignore.
- 사용자 포트(3700 · 3800 · 8700 · 8800 · 54329)와 `procedure-*` 컨테이너는 건드리지 않는다.
