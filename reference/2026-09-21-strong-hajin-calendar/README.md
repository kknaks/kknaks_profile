## 1. 코디 핸들이 조용히 죽는다 — **제일 위험하다**

**무슨 일이 있었나.** `$ORCA_TERMINAL_HANDLE` 은 그대로인데 **실제 터미널이 바뀌어 있었다.**
워커들이 그 죽은 핸들로 완료 보고를 보내고 있었다. 발주가 `terminal_handle_stale` 로 튕겨서야 알았다.

**왜 무서운가.** 보고가 **조용히 유실된다.** 워커는 보냈다고 믿고 끝내고, 코디는 안 왔으니 기다린다.
「워커가 조용하다」로 보이는데 원인이 겉으로 안 드러난다.

**런북에 경고가 이미 있었다.** 그런데도 당했다 — `new-work.sh` 가 **발주 시점에 한 번** 검사하고,
**세션 도중에 바뀌는 것**은 아무도 안 본다.

### 다음에 할 것

- **워커를 새로 띄울 때마다** `orca terminal list --json` 으로 내 핸들이 살아 있는지 본다.
  `env` 를 믿지 않는다.
- 핸들을 찾는 법: `terminal list` 에서 **이 세션의 제목**으로 고른다(예: `◑ 스트롱 하진 새 작업`).
  워크트리 경로만으로는 **남의 세션을 집는다** — `new-work.sh` 가 자동 추측을 안 하는 이유다.
- 바뀌었으면 **브리프 전부와 `_RESUME.md` 를 한 번에 갱신**하고 **살아 있는 워커에게 정정을 보낸다.**

## 2. 워커 터미널이 자주 죽는다 — **여섯 번 죽었다**

**무슨 일이 있었나.** writer·reviewer·backend·frontend 가 번갈아 나갔다(`status: exited`).
새 워커는 앞 판의 맥락이 **하나도 없다.**

### 다음에 할 것 — **지시서를 자립형으로 쓴다**

이것이 이번 작업의 제일 큰 운영 교훈이다.

- **모든 지시서 머리에** 「앞 판 워커는 죽었다 — 너는 맥락이 없다」와 **읽을 것 목록**을 둔다:
  역할 문서 · 코드 레포 `AGENTS.md` · **앞 판이 남긴 리포트**.
- **리포트를 `work/<slug>/` 에 쌓는다.** 워커 보고를 인박스에만 두면 워커가 죽을 때 같이 죽는다.
  워커가 scratchpad 에 리포트를 쓰면 **`work/` 로 옮긴다.**
- **맥락을 사람(터미널)이 아니라 파일에 둔다.** 그러면 워커가 죽어도 이어진다 —
  이번에 여섯 번 그렇게 이어받았다.

## 3. 긴 발주 메시지가 잘린다 — **두 번 당했다**

**무슨 일이 있었나.** 2742 bytes · 3126 bytes 메시지가 **앞부분 없이** 워커에게 들어갔다.
한 번은 리뷰어가 지시서 파일로 축을 복원해서 살았고, **그 파일이 없었으면 엉뚱한 것을 검수했다.**

### 다음에 할 것

- **지시는 파일로, 메시지는 포인터 + 세 줄 요약.** 예:
  ```
  [코디 — Phase X 검수] 지시서: work/<slug>/review-x-instructions.md 를 읽어라.
  요지: <한 줄>. 코디 확인: <수치>. 리포트는 새 파일 review-x-report.md.
  ```
- **1000 bytes 를 넘기지 않는다**는 감각으로 쓴다. 넘으면 파일로 뺀다.
- 워커가 「앞부분이 잘려 들어왔다」고 신고하면 **그 판정을 믿고** 다시 보낸다.

## 4. 자동 검증이 못 보는 층이 있다 — **이번 작업의 발견**

**무슨 일이 있었나.** 1루프가 **검수를 전부 통과**했다(SPEC 4판 PASS · 코드 4판 PASS ·
테스트 전부 초록). 사용자가 화면을 열자 **다섯이 나왔다** — 같은 업무가 두 번 뜨고, 겹치는 블록이
밑에 깔려 안 보이고, 겹쳐도 안 막히고….

**계약이 맞는지는 테스트가 본다. 쓸 만한지는 못 본다.**

### 다음에 할 것

- **「1루프 → 사용자 E2E → 2루프」를 처음부터 계획에 넣는다.** 1루프에서 픽셀·문구를 완벽히
  맞추려 시간 쓰지 않는다 — 어차피 눈으로 볼 때 다시 잡힌다.
- **마지막 검수에 「사용자가 실물에서 만날 자리」를 모으게 한다.** 이번에 U-1~U-9 가 그렇게 나왔다.
  리뷰어는 코드를 읽으므로 「막히진 않는데 사람 눈에 이상해 보일 자리」를 짚을 수 있다.
- 시안이 있으면 **옆에 띄워 대조**한다: `cd "<시안 경로>" && python3 -m http.server 8000`

## 5. E2E 스택이 기계를 누른다 — **두 번 죽었다**

**무슨 일이 있었나.** `make local-stack` 이 프로세스 18개(API + 워커 4개 + 프론트)를 물고,
워커 터미널 다섯이 각각 Claude 를 물고 있었다. `load average 19.39` 를 봤고, 스택이
**메모리 부족으로 두 번 죽었다.** 그 부하가 **테스트 flaky 도 악화시켰다**(별건 문서 참조).

### 다음에 할 것

- **구현 중에는 스택을 안 띄운다.** 사용자가 볼 때만 띄우고, 끝나면 내린다.
- **포트 충돌을 먼저 본다** — 워크트리마다 compose 프로젝트명이 달라 **같은 포트로 새 컨테이너**를
  띄우려 한다. 앞 작업 컨테이너가 살아 있으면:
  ```bash
  COMPOSE_PROJECT_NAME=<앞 작업 프로젝트명> make local-stack
  ```
  이번엔 `strong-hajin-work` 를 재사용했다(`54329`). **다른 프로젝트가 쓰는 포트(5432)는 안 건드린다.**
- 테스트 수치를 비교할 거면 **스택을 내린 뒤** 잰다.

**무슨 일이 있었나.** 워커 보고(`1135p/3f`)를 그대로 받고 **직렬 재실행 근거를 안 남겼다.**
BE-3 검수가 **「분리 없이는 이번 계약이 초록이라는 증명이 안 닫힌다」**고 지적했다. 맞는 말이었다.

### 다음에 할 것

- **기존 flaky 는 한 번 판정하고 파일로 남긴다** (`work/<slug>/flaky-baseline-evidence.md`).
  이후 워커·검수가 그 판정을 인용한다.
- 코디는 **워커 수치를 그대로 쓰지 않는다** — 최소한 관문이 되는 명령 하나는 직접 돌린다.

## 7. 결정을 워커 작업 **뒤에** 내리면 그 판이 FAIL 난다

**무슨 일이 있었나.** 두 번 있었다 — K18(레일 범위)과 K24(업무 탭 축). 둘 다 워커가 물어서 생긴
결정인데 **답이 코드·문서가 쓰인 뒤에 내려왔다.** 검수가 「반영 안 됨」으로 FAIL 을 줬다.
**워커 잘못이 아니다.**

### 다음에 할 것

- 워커가 `[질문]` 을 보내면 **그 판이 끝나기 전에** 답한다. 늦으면 다음 판에 반영 비용이 붙는다.
- 답이 늦었으면 **검수 발주에 「이건 내가 뒤에 정했다, 워커 잘못 아니다」를 적는다** —
  판정은 FAIL 이어도 책임 소재가 기록에 남는다.
