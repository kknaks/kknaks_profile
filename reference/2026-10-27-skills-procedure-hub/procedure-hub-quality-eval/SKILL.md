# Procedure Hub 허브 품질 측정 · 판 비교

허브 품질 측정(2026-10-30 · 1차 → 2차 → 3차)에서 실제로 한 방법을 옮긴 것이다. 새로 지어낸 절차가 아니다.
실버 정리가 끝나고(`procedure-hub-semantic-check` 다음) 골드를 짓기 전에, **실버 · 시맨틱이 상담 질문에 맞는 답을 내는지 원천 근거 정답으로 잰다.** 계기는 사용자가 연결 구조 페이지에서 「이중턱 → 겨드랑이 마이크로웨이브」 같은 오연결을 직접 찾은 것이다 — 「허브 데이터 유효한지 품질 측정 테스트가 먼저」(사용자 10-30). 사람이 그림을 하나씩 보지 않게 측정이 먼저 잡는다.

- 측정 스크립트(정본): `orchestration/work/phub-recommend/quality-eval.py` — 결정론 · LLM 없음 · 읽기만(실버 · 시맨틱 · 브론즈 수정 없음) · 시드 고정. `--inputs <폴더>` 로 다른 판 실버를, `--out <폴더>` 로 다른 곳에 쓴다
- 산출: `quality-eval-set.json`(문항 111 · 정답 · 근거) · `quality-report.json`(정본) · `quality-report.md`(맨 위 = 목표 판정 1차 → 지금 · 원인별 고침 · 남은 것)
- 보관 판: `quality-v1/`(1차 — 문항 · 스크립트 · 리포트 · 입력 실버 전부) · `quality-v2/inputs/`(2차 리포트 · 스크립트 · 입력) · `quality-v3/inputs/`(3차 리포트 · 문항 · 입력) · `quality-v1/v1-data-v2-eval.json`(1차 실버를 2차 측정으로 잰 대조값)
- 이 스킬의 점검: `scripts/check_quality.py` — quality-eval.py 를 **감싸기만** 한다(측정 로직을 다시 짜지 않음). 기준 `references/baseline.json`
- 결정 정본: `orchestration/work/phub-recommend/_RESUME.md` §2 2026-10-30 「KOS 연결 = 기록만 · 다음 우선 = 허브 데이터 유효성」 · 「허브 품질 측정 1차 발주」 · 「품질 목표(사용자 승인)」 · 「품질 수정 중 판단(코디)」(R28 CC 슬롯) · 「품질 2차 결과」 · 「남은 8문항 처리」 · 「골드 규칙 판단」 ①. 규칙이 바뀌면 거기가 이긴다
- 과정 기록: `para/projects/company/procedure-hub/log/2026-10-30-quality-eval.md`(왜 · 설계 · 1차 원인 14 · 고침 · 2차 · 3차 · 전후 예 · 틀린 것)
- 측정 상세: `references/measures.md` · 칸 `references/record-schema.md` · 틀렸던 것 `references/mistakes.md`

**측정 · 문항 · 정답 · 채점 식은 목표를 맞추려고 고치지 않는다.** 정답이 원천 근거와 다르다고 판단되면 고치지 말고 보고한다(quality-fix 브리프 · 사용자 10-30). 지표는 데이터(실버 · 시맨틱)를 고쳐서 움직인다.

## 1. 언제

| 경우 | 시작점 |
|---|---|
| ① **실버 · 시맨틱이 바뀜**(어느 단계든 apply 재실행 · semantic-build 재생성 뒤) | 그 단계 스킬 errors 0 → `check_quality.py` — 「정본 낡음」이 나면 §4 로 측정을 다시 돌려 정본을 갱신하고 목표 · 판 비교를 본다 |
| ② **골드 빌드 · 골드 E2E 전 · 후** | `check_quality.py` 한 번 — CC 슬롯 6/6 이어야 골드로. 골드가 생기면 골드 도구 응답을 같은 문항 · 정답으로 재는 것이 골드 E2E 의 정확성 몫(SPEC-005) |
| ③ **이 문항이 왜 틀렸나** | `quality-report.json` `m1[]`(문항별 got · wrong_units · why) · `causes[]`(원인 묶음 · 고칠 단계) — §2-5 |
| ④ **문항 · 정답 · 채점을 바꾸자는 요청** | 최종 판단(사용자). 바꾸면 그 판부터 1차와 직접 비교가 깨진다 — 바꾸기 전 판을 보관하고 `--write-baseline` 으로 기준을 새로 쓴 이유를 남긴다 |
| ⑤ 정기 점검 | `check_quality.py --selftest` |

점검(읽기만 · 표준 라이브러리 · quality-eval.py 를 임시 폴더 둘에 두 번 돌림 · 작업 폴더에 아무것도 안 씀):

```bash
python3 <스킬>/scripts/check_quality.py \
  --work orchestration/work/phub-recommend \
  --out <scratchpad>/quality-check.json --selftest     # --require cc(기본) · nocc · v1 쉼표로
```

`errors[]` = quality-eval.py 종료 코드 ≠ 0 · **결정론 아님(두 번 실행 바이트 다름)** · **정본 낡음(작업 폴더 산출 ≠ 재실행)** · **문항 수 · id 다름** · **문항 바뀜(문장 · 슬롯 · 의도 · 출처 · 근거 · 정답 상태)** · **정답 바뀜(원천 근거 칸 — 규칙 칸 밖)** · 정답 있음 ↔ 미정 · **채점 식 바뀜(채점 함수 · 상수 지문)** · 목표 제외 문항 바뀜 · **목표 미달(필수 경로)**.
`warnings[]` = 측정 경로 함수가 기준과 다름(사람이 diff 확인).
`rule_field_changes[]` = 규칙으로 계산되는 정답 칸이 1차와 달라진 문항 · 칸 · 더함/뺌(오류 아님 — 보고).
`goals{cc · nocc · v1}` = 목표 6 묶음별 통과 · `versions[]` = 판별 지표 · `version_changes[]` = 판 사이 상태가 바뀐 문항.
`selftest[]` = 틀린 값 13가지를 넣어 각각 잡히는지(규칙 칸 바꿈은 오류가 아니라 바뀜 목록에 나와야 통과).

### 2-3. 경로 셋 — CC 슬롯 · CC 없음 · 1차

I-01(고민 → 추천)만 경로가 갈린다. 리포트는 셋을 나란히 낸다.

| 경로 | 무엇 | 쓰는 곳 |
|---|---|---|
| `cc` CC 슬롯(R28 + R32) | 질의가 원천 CC(구체 고민 — 예 「여드름 · 아그네스」의 「아그네스」)를 말하면 같은 원천 문제 안에서 그 CC 엣지만 · 부위 층 + 「상위」 층 표시 | **골드 도구 입력 `cc?`**(골드 판단 ① · 사용자 10-30 「응 추천으로 가자」) — **필수 6/6** |
| `nocc` CC 없음(R32) | 고민 노드 엣지 전부 + 층 표시 | CC 를 못 받는 질의의 바닥값 — 보고만(10-30 3차 4/6 · I-01 정밀도 낮음) |
| `v1` 1차 경로 | 부위 층만 · CC 없음 | 1차와 같은 경로로 지금 데이터를 잰 대조 — 보고만 |

CC 「없음」이 낮은 것은 데이터 오류가 아니라 질의가 덜 구체적인 것이다 — 「여드름」만 물으면 원천의 여드름 CC 전부(압출 · 아그네스 · 필링 …)의 시술이 다 맞는 후보다. 정답(그 CC 의 추천 시술)보다 넓게 나오므로 정밀도가 떨어진다.

## 3. 규칙 체크리스트

틀렸던 예는 `references/mistakes.md`.

- [ ] **정답은 원천 근거로만** — 워커가 원천 칸에서 초안 · 틀린 것만 의료진. 근거 없으면 「정답 미정」(가상 문장 · 지어낸 정답 없음)
- [ ] **문항 · 정답 · 채점 식을 고쳐 목표를 맞추지 않는다** — `check_quality.py` 가 지문 · 문항 대조로 막는다
- [ ] **규칙으로 계산되는 정답 칸이 바뀌면 숨기지 않고 보고**(10-30 3차: 다파장 KTP 로 7문항 정답 하위에 KTP — 문항 · 슬롯 · 다른 칸 · 채점 식은 같음)
- [ ] **측정 경로를 바꾸면 「1차 실버 × 이 판 측정」 대조** — 측정 변경만으로 지표가 움직이지 않았는지
- [ ] **측정기도 틀린다** — 1차 측정기 스스로의 오류(4자 미만 원문 「간독성」을 있어도 없음으로 셈 · 부위 무관 「점제거 → 병변 레이저」를 거름 · by_direction 을 안 읽음)는 데이터 원인과 따로 적는다
- [ ] **두 경로(CC 슬롯 · CC 없음)를 나란히** — 하나만 보고하면 「CC 를 못 받을 때」 품질이 가려진다
- [ ] **충돌 판을 밝힌다** — 8단계 충돌 해소 칸(resolved)이 있으면 해소 판 기준 · raw 판과 달라진 문항(`m1_raw_diff`)을 같이
- [ ] **원인 → 고침 순서: 원인 먼저 · 숫자 확인 뒤 다른 빈틈**(10-30 — 원인 14 수정 · 재측정 · 목표 확인 · 사용자 보고 → 그다음 골드 빈틈 2. 한 번에 묶었다가 바로잡음)
- [ ] **판을 보관하고 비교** — 고치기 전 판(문항 · 스크립트 · 리포트 · 입력 실버)을 `quality-vN/` 으로 남긴다. 고친 판만 남으면 「얼마나 나아졌나」를 다시 셀 수 없다
- [ ] 실명 · 키 금지 · 수치는 파일에서 다시 셈

### 끝 조건

- [ ] `check_quality.py` **errors 0** — 결정론 · 정본 낡음 0 · 문항 · 정답 · 채점 식 고정 · 목표 제외 고정
- [ ] **CC 슬롯 경로 목표 6/6**(`--require cc`) · CC 없음 · 1차 경로 값은 보고
- [ ] `--selftest` **전부 잡힘**
- [ ] 남은 틀린 문항은 원인 · 넘길 곳 · 「데이터 아님(골드 판단)」으로 적었다

## 4. 갱신 방법

1. **실버 · 시맨틱이 바뀌었으면** 그 단계 스킬 · semantic-check 가 먼저(errors 0). 측정은 실버를 읽기만 한다
2. **보관** — 지금 판을 남긴다(다음 번호 `quality-vN/inputs/` 에 리포트 · 문항 · 바뀔 실버 · 스크립트). 그리고 `references/baseline.json` `versions[]` 에 한 줄(label · report · note)
3. **재측정** — 프로필 레포 루트에서

```bash
W=orchestration/work/phub-recommend
(cd $W && python3 quality-eval.py)                                          # 정본 갱신(실버가 승인돼 바뀐 뒤에만)
(cd $W && python3 quality-eval.py --out <scratchpad>/q2 && cmp quality-report.json <scratchpad>/q2/quality-report.json)   # 결정론
python3 <스킬>/scripts/check_quality.py --work $W --out <scratchpad>/quality-check.json --selftest
```

4. **측정 경로를 바꿨으면**(사용자 · 코디 결정이 측정 쪽에 닿을 때만 — 예 R28 CC 슬롯 · 8단계 by_direction 읽기 · 계열 옮김 표를 결정 파일에서) 대조 `python3 quality-eval.py --inputs quality-v1/inputs --out <폴더>` → 리포트 「1차 실버 × 이 판 측정」 열. 그다음 `check_quality.py --write-baseline` 으로 경로 지문을 새로 쓰고 그 이유를 `baseline.json` note 에. **채점 지문(scoring)을 바꾸는 것은 사용자 결정이 있을 때만**
5. **검수** — 목표 판정 · 원인 묶음 · 남은 문항을 원천 근거와 대조(읽기 전용 검수자). 정답이 원천과 다르게 보이면 고치지 않고 보고

## 5. 출력 형식 — 측정 보고
