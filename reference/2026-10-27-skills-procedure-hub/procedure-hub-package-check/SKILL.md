# Procedure Hub 패키지 판정 · 실버 패키지 원장 갱신

실버 6단계(패키지 노드 · 패키지 → 구성 단위 시술 엣지, 2026-10-29)에서 실제로 한 방법을 옮긴 것이다. 새로 지어낸 절차가 아니다.
5단계(단위 시술 — `procedure-hub-unit-check`) 다음 단계다. 5단계가 행선지 「6단계 패키지」로 넘긴 원장 · 시장가 행을 **이름 있는 단위 시술 묶음**으로 세우고, 구성은 원천에 적힌 만큼만 잇는다.

- 정본 원장: `orchestration/work/phub-recommend/step6-packages.json` · `.md` — 현재 값(패키지 · kind · 구성 엣지 · 슬롯 · 원천 질문 · open) = `scripts/check_packages.py` 출력. 숫자를 여기 박지 않는다(결정이 바뀌면 낡는다 — 6단계 검수 W3 이 바로 스킬 문서의 5단계 고정 숫자였다)
- 결정(사람이 고치는 곳): `step6-decisions.json` — 패키지 `packages[]`(구성 `components[]`) · 묶음 이름 `non_packages[]` · 넘겨받은 것 `handoffs[]` · 원천 질문 `origin_questions[]` · 원천 수정 후보 `source_fix[]` · 5단계로 돌린 행 `backport_step5[]` · kind 값 `kinds[]` · 규칙 `rules`(R1~R11)
- 결정론 반영: `step6-apply.py`(입력 = 결정 · 원천 taxonomy · market-pricing · synergy · `step5-units.json` → 출력 `step6-packages.json` · `.md` · `step6-origin-questions.md` · `step6-source-fix.md`) · 가드 시험 `step6-fixture-test.py` + `step6-fixtures/cases.json`(「결정 한 줄 빼면 open」만)
- 결정 정본: `orchestration/work/phub-recommend/_RESUME.md` §2 2026-10-29 6단계 행 — 「6단계 패키지 이해」 · 「실버 6단계 시작 — 계획 승인」 · 「6단계 패키지 조사 반영」(R1~R11 · U1~U4) · 「데이터 끝」. 규칙이 바뀌면 거기가 이긴다
- 과정 기록: `para/projects/company/procedure-hub/log/2026-10-29-silver-step6-package.md`(§3 규칙 · §5 틀린 것) · 조사 `step6-research.*` · 검수 `review-step6-report.md`
- 원천: `step6-decisions.json` `source.path` — 경로는 프로필 레포 기준

**원장 · 결정 파일은 승인 없이 고치지 않는다.** 판정 → 결정 목록(사람) → 결정 한 줄(승인된 것만) → 반영(스크립트) → 점검 · 검수 고리를 그대로 돈다.

## 1. 언제

| 경우 | 시작점 |
|---|---|
| ① **5단계가 새 행을 6단계로 넘김**(원장 행선지 · 시장가 kind 「6단계 패키지」가 늘거나 이름이 바뀜) | `step6-apply.py --out <scratchpad>` 의 open 「결정 없는 패키지 원천 행」 · 「패키지 원장 이름 바뀜」 → 행마다 §2 |
| ② **새 묶음 메뉴 · 회차 패키지 · 콤보 시장가 행이 원천에 생김** | 5단계가 먼저 행선지를 정한다(`procedure-hub-unit-check` §2-1 — 「A + B」 · 프로그램 · 회차 = 6단계 패키지). 그 뒤 ① |
| ③ **시장가 패키지 가격이 바뀜** | 가격은 원천을 그대로 읽는다 — `step6-apply.py` 재실행만(결정 고칠 것 없음). 원장 `price_raw` 가 원천 detail 에서 사라지면 open |
| ④ **원천 질문 답이 옴**(병원 — 구성 · 부위 · 투여 방식 · 정체 · 소속) | `step6-origin-questions.md` 그 행 — 그 패키지 구성(슬롯 · 엣지)만 §2-3 ~ 2-4 다시 |
| ⑤ **5단계에 새 키가 생김**(슬롯 `missing_unit` 이 풀림) | 그 슬롯을 엣지로 — 한 줄 |
| ⑥ 정기 점검 · 결정을 고친 뒤 | `scripts/check_packages.py` 한 번 — errors 0 · open 0 |

점검(읽기만 · 표준 라이브러리):

```bash
python3 <스킬>/scripts/check_packages.py \
  --work orchestration/work/phub-recommend \
  --out <scratchpad>/package-check.json     # 새 스냅샷은 --source <폴더>
```

`open[]` = 결정 없는 패키지 원천 행 · 이름 바뀜 · 구성 키도 질문도 없음 · 근거 약 구성인데 질문 없음 · **구성도 질문도 없는 패키지** ·
`stale_decisions[]` = 결정은 있는데 원천 행이 아님(지우지 말고 결정 목록에) ·
`errors[]` = **원천에 없는 구성** · **적응증에서 온 구성** · 키 없음 · 원천 질문 id 없음 · **시그니처 추천 노출** · kind 값 밖 · 메뉴 묶음 어긋남 · 가격 원문 없음 · 회차 어긋남 · 원천 행 겹침 · 5단계 정본 ↔ 결정 어긋남 · 원장 낡음 · summary 불일치 · 원장 open.
`step6-apply.py` 의 open 은 이와 겹치고 synergy 링크 번호 · 묶음 이름 행선지 번호 대조가 더 있다 — `references/record-schema.md` §3.

## 2. 판정 순서

원천 행(5단계가 넘긴 원장 · 시장가 행) 하나마다 위에서부터. **앞에서 끝나면 뒤로 가지 않는다.** 상세 `references/package-rules.md`.

### 2-0. 「패키지」 두 뜻 — 먼저 맞춘다

| | 사이트 「추천 패키지」 | 6단계 「패키지」 |
|---|---|---|
| 원천 | `problem-combos` — 고민별 시술 조합 · 가격대 · 세일즈 문구(화면 「추천」 · `AppShell.tsx` · `recommend/page.tsx`) | 원장 · 시장가에 **이름이 붙은** 묶음(「꿀광토닝」 · 「MTS + PRP (전체얼굴)」 · 「스컬트라 (3회 패키지)」) |
| 말하는 것 | 이 고민에 이 조합을 권한다(추천) | 이 이름으로 이 시술들을 묶어 판다(판매 단위) |
| 단계 | **7단계** 추천 조합(「추천 패키지」는 그 동의어) | **6단계** 패키지 노드 → 구성 단위 시술 |

요청에 「패키지」가 나오면 어느 쪽인지 먼저 확인한다. 화면에 같은 낱말이 있으면 화면 쪽 뜻부터 본다(`references/mistakes.md` #1).

### 2-1. 패키지인가 — 다섯 갈래

1. **이름 있는 단위 시술 묶음** — 이름이 구성을 말하거나(꿀광토닝 = 레이저토닝 + 스킨부스터) detail 이 「A+B」로 서로 다른 단위 시술을 적는다 → **일반 패키지**
2. **같은 단위 시술 × N회** 를 한 가격으로 판다(시장가 「3회 패키지」 · `sessions`) → **회차 묶음**. 1회 가격과 한 칸에 두지 않는다(U4)
3. 원천 라벨이 「시그니처」 · **고정 가격 · 고정 용량** → **병원 시그니처** — 추천 노출 기본 제외(U3). 「특정 병원 상품」은 판정이라 근거가 있어야 — 이름이 낯설다는 것은 근거 아님, 「일반 근거 없음」 + 원천 질문으로 적는다
4. **묶음 이름(분류)** — taxonomy 하위 라벨(「색소/토닝」 · 「시그니처 프로그램」)은 묶어 파는 상품이 아니다 → **패키지 아님** `non_packages[]`: 메뉴 분류 = 7단계 목적 원문 · 시그니처 묶음 = 패키지 속성 `menu_group`
5. **단위 시술** — 한 장비의 여러 모드 · 같은 키 두 제제 · 한 회 · 한 이름 · 한 가격 → **패키지 아님, 5단계로 돌린다**(`backport_step5[]` + `procedure-hub-unit-check` 로 그 키 동의어). 예: 포토나4D(한 장비 다중 모드 — 제네오X · 올타이트와 같은 꼴) · 리쥬하이(리쥬란 + HA 가 같은 스킨부스터 키)

이름 없는 묶음(synergy 「보톡스+필러+리프팅 3종 풀 패키지」)은 패키지가 아니다 — 8단계 근거.

### 2-2. 구성 — 원천에 적힌 시술 낱말만

- 원천 칸 = 원장 **이름 · detail · extracted overview · mechanism** / 시장가 **행 이름**. **적응증(indications)은 구성이 아니다**(7단계 근거) — 적응증에 부위가 나와도 구성으로 쓰지 않고, 쓸 거면 슬롯 후보 + 원천 질문
- 엣지 셈 단위 = 「패키지 × 원문 낱말 한 개」. 같은 단위 시술이 두 패키지에 들면 두 줄
- 수량(600 · 200 · 2병 · 24cc · N회)은 엣지 속성 `quantity_raw` 원문 · 회차는 `sessions`
- 시장가 두 행이 구성이 같으면 한 패키지 · 가격은 두 행 따로(R6)

### 2-3. 구성마다 단위 시술 키

- 낱말 → 5단계 키. 대응표는 결정 `rules.R2`(레이저토닝 · 피코토닝 → 토닝 키 · 매질 없는 「토닝」 → 매질 미지정 토닝 키 · 물광 · 리투오 → 스킨부스터 키 …) — 새 낱말은 5단계 키의 동의어(`step5-units.json` `synonyms`)에서 찾는다
- 부위 = 원천 부위 → 없으면 J2(얼굴 계열 = 얼굴 전체 기본값). **M1 · M2 · 몸 계열은 기본값 없음** → 슬롯
- **5단계에 키가 없으면 여기서 만들지 않는다** — `procedure-hub-unit-check` 로 키부터(새 원장 항목 · 시장가 · 메뉴가 그 키를 부를 때만). 그 사이는 슬롯 + `missing_unit`
- 정체 · 투여 방식이 원천으로 안 닫히는 구성(튠 · 줄기세포 · 엑소좀)은 키를 넣고 `evidence_level: 약` + 원천 질문(R5)

### 2-4. 못 푼 구성 = 슬롯 + 원천 질문

「구성 없음」으로 두지 않는다. 슬롯 = `unit` 없음 · 원문 · `candidates` · `origin_question` · (`missing_unit`). 엣지가 0 인 패키지도 슬롯 + 질문이 있으면 끝 조건을 지킨다 — **구성도 질문도 없는 패키지만 open**.

### 2-5. 가격 · 같은 날 — 원문

- 가격 = 원장 detail(`price_raw` — detail 안 글자 그대로) · 시장가 행 low · mid · high · unit. **단위 시술 1회 가격 합으로 만들지 않는다**(R7)
- 같은 날 = `same_day_raw` 에 원천 문구 그대로. 「동시」만 같은 날로 읽는다. 「결합」 · 「복합」 · 「순차」는 원문 그대로 · 효과 문장 속 「동시에」(꿀광토닝 overview)는 같은 날이 아니다(R8)

### 2-6. 넘기는 것 — 6단계가 세우지 않는다

- **시너지 · 간격 · 순서 = 8단계**(원천 synergy 그대로). 패키지는 「함께 판매 사례」 근거로만. 구성 쌍을 synergy 와 대 본 결과는 `step8_notes[]` 메모만(같음 · 다름 · 링크 없음) — 다르면 둘 다 남기고 충돌 표시 후보(D-13b), 안전 충돌(줄기세포 + MTS 「개방 채널에 사용하지 않음」)은 따로 표시
- 고민 · 목적 = 7단계(메뉴 분류 이름 · 사이트 추천 패키지)
- 7단계 판정(고민 대응표 · 고민 · 목적 → 단위 시술 엣지 · 사이트 「추천 패키지」 등 추천 조합)은 `procedure-hub-concern-check` — 6단계 `non_packages` 중 「7단계」로 넘긴 메뉴 분류가 거기서 목적 원문 · 대응표 행이 된다

판정마다 「원천 id · 원문 · kind · 구성(원문 · 키 / 슬롯 · 근거 칸) · 가격 원문 · 같은 날 원문 · 원천 질문」을 남긴다. 형식은 `references/record-schema.md`.

## 4. 갱신 방법

1. **결정 목록 먼저** — 변경분만, 사용자 앞에는 **표 하나**. 셋으로 나눈다
   - **승인**: 규칙으로 답이 닫힌 것 — 기존 키로 풀리는 구성 · 시장가 회차 묶음 · 묶음 이름 · 가격 원문
   - **원천 질문**: 구성 · 부위 · 투여 방식 · 정체 · 수량 단위 · 소속 미상 — 지금 값(슬롯 · 근거 약 키)은 넣어 두고 질문
   - **최종 판단**: 패키지 ↔ 단위 시술 경계(한 장비 다중 모드 류) · 새 kind · 시그니처 노출 규칙 · 6 ↔ 7 ↔ 8 경계 — 추천 + 기본값을 깔고 결정만 받는다
   - 숫자에는 **단위(패키지 / 엣지 / 슬롯 / 행)와 판**을 붙인다
2. **반영 = 결정만 고치고 `step6-apply.py` 재실행** — 원장 json · md 를 손으로 고치지 않는다
   - 재실행 **전에** 지금 정본을 판 사본으로 남긴다(`step6-packages.v1.json` 식)
   - **새 패키지 = `packages[]` 한 줄**(다음 `P6-NN`) — `id` · `name`(원천 그대로) · `kind` · `shape` · `source`(ledger + `ledger_id` / market + `market_names`) · `menu_group` · `same_day_raw` · `recommendable` · `components[]` · (`price_raw`) · `notes` · `step8_notes` · `decided_by`. 형식 `references/record-schema.md` §1
   - **구성 = `components[]` 한 줄** — `text`(원문) · `basis`(원천 칸 · 문구) · `unit` 또는 `candidates` + `origin_question` · (`evidence_level` · `quantity_raw` · `sessions` · `missing_unit`)
   - **새 원천 질문 = `origin_questions[]` 한 줄** · **새 묶음 이름 = `non_packages[]`** · **5단계 새 넘김 = `handoffs[]`** · **단위 시술로 돌림 = `backport_step5[]` + 5단계 결정 한 줄**(5단계 먼저)
   - 원천 질문 답 → 그 슬롯을 엣지로(또는 엣지의 `evidence_level` · `origin_question` 을 지움) — 구성에서도 안 쓰이고 `packages` · `target` 도 없는 질문은 stale 로 잡힌다
3. **점검** — 프로필 레포 루트에서

python3 $W/step6-fixture-test.py          # 결정 한 줄 빼면 open 이 나오나

   - 5단계 정본을 고친 뒤면 5단계 먼저(open 0) — 6단계는 `step5-units.json` 을 읽는다
