## 원칙

v2 의 원칙(KOS 동기화 · 데이터 원천 = KOS 데모 지점 · KOS 필드 그대로 · ccc DB 가 KOS 를 품는 구조 D-12 ~ D-15)은 **그대로 이어진다** — 다시 쓰지 않는다. 예약 구간에서 더해지거나 달라진 것만 적는다.

- **KOS 와 ccc 는 항상 같은 데이터를 쓴다**(사용자 지시). ccc DB 는 KOS **사본**을 갖고(D-12 · 모든 행 ccc id + `kos_id`), KOS 에 칸이 있는 값은 **KOS 가 기준** — 조회 때 사본을 덮어쓰고(D-09), ccc 조작은 KOS 에 써서 다음 조회로 사본에 돌아온다. ccc 만의 것(아래 「ccc DB 에만 있는 것」)은 ccc 가 기준. 예약 구간도 시술 구간과 같은 구조
- **KOS 에 없으면 안 쓴다 · KOS 에 있으면 칸을 만든다**(사용자 지시 — 예약 등록 모달에서 정함). 시안에 있어도 KOS 에 없는 칸은 뺀다(통역 · 예산 칸). 시안에 없어도 KOS 에 있으면 칸을 만든다(~~수면마취~~ · 귀가 희망 시각 · 예약 담당자 · ~~당일 지정 의사~~ · 희망 상담사 등 — 수면마취 · 당일 지정 의사는 (2026-10-27 바뀜) 예약 등록 모달에서 뺀다 · 사용자 「필요 없어」). **예외: KOS 「희망 시술」(`requestedProcedures` — 상품 옵션 · 시술권 선택)은 칸을 만들지 않는다** — 현장이 안 쓴다. 희망 시술은 예약 메모에만
- **시안이 정본, 단 시안과 KOS 가 다르면 KOS 칸에 맞춰 시안을 고친다** — 문진(시안 질문 → KOS 문진 양식 그대로) · 예약 등록 모달(KOS 예약 칸 그대로) · 스케줄 표(KOS 「예약 현황」 그대로) · 상태(KOS 두 축 그대로)
- **상태 = 2계층(주 상태 + 부상태)**. KOS 값 하나 = 칸 하나, 지어낸 상태 없음(아래 1)
- **웹이 정본 · 앱은 나중에 웹에 맞춘다**(사용자 지시) — 웹/앱 규칙 차이는 「열린 질문」이 아니라 앱 후속 작업
- **v2 「현장은 KOS 를 직접 조작하지 않는다」(D-10)와 범위가 다르다** — v2 의 그 원칙은 **시술 구간**(간호 스테이션 · 시술실)이다. 예약 구간에서는 **상담사(실장)가 KOS 에서 직접** 한다: [상담 시작] · 상담 기록 · 수납(추가 포함) · 시술 추가 · 오더 메모 · **시술 대기 전환**(사용자 지시). ccc 에는 상담 · 수납 · 시술 추가 화면이 없고, 그 결과를 사본으로 읽어 보여 준다(시술 목록 · `paymentRequired` · `orderMemo` — 시술 현황과 같은 원천). 데스크(코디)가 하는 예약 · 접수 · 방 배정 · 고객 정보 · [실장 호출] · 귀가 완료는 ccc 가 조작 화면이다
- **데모 지점에만 쓴다** — 데모 지점 KOS 쓰기 시험 허가(사용자 지시 · 2026-10-26). 운영 명동점 쓰기는 금지 그대로

## 1. 예약 현황 — 스케줄 표 · 상태

- **스케줄 표 = KOS 「예약 현황」 그대로**(사용자 지시 — KOS 화면 캡처)
  - **칸 = KOS 예약 그룹 전부**(order 순). 시안의 국가별 5칸(국내 · 중화권 · 영미권 · 일본 · 기타)으로 줄이지 않는다(Q-4 닫힘). 데모 그룹 13개 = 그 5개 + 시술 그룹 8개(R§3.3)
  - 카드의 칸 = 일정이 차지한 예약 그룹(R§3.1 3행)
  - **국기 = `visitor.nationality`(ISO 3166-1 alpha-2) → ccc 가 국기 그림으로 바꿔 그린다** — 코드 변환이지 추정이 아니다(Q-8 닫힘)
- **시간축 = 기본 30분 + 예약 그룹의 시간**(사용자 지시). 세부(코디 기본값 — 코디 제안 · 이의 없음 전제 · Q-5 · Q-123 · Q-125 · Q-126 닫힘):
  - ~~**세로축 = 그룹 운영 시간**(지금 데모 13개 그룹 모두 10:00–20:00 · 쉬는 시간 · 휴무 0 — TA§0 · §2 · §3). KOS 화면처럼 08:00 부터 그리지 않는다(KOS 는 전역 08:00 부터 줄을 긋는다, TA§4)~~ (2026-10-27 바뀜)
  - **세로축 = 06:00 ~ 22:00 고정**(사용자 지시 · E2E — 「시간은 06시부터 22시까지 표시하고 운영시간 표시해 주고 화면이 렌더링될 때 현재 시간으로 가야 함」). 운영 시간은 칸마다 회색으로 보인다(아래). **첫 렌더 때 지금 시각 줄로 자동 스크롤**. 데모 그룹 운영 시간은 그대로 10:00–20:00(TA§0)
  - **시각 라벨 = 30분**
  - **칸마다 자기 간격으로 줄을 긋는다**(그룹 `intervalMinutes` — 30분 9개 · 60분 리프팅 · 스킨부스터 · 15분 보톡스 · 제모, TA§0). **1시간 높이는 모든 칸이 같다** — 60분 칸의 한 줄은 30분 칸 두 줄 높이, 15분 칸은 반 줄(KOS 화면과 같은 꼴, TA§4)
  - **운영 시간 밖 = 회색**(칸마다 그룹 운영 시간표 · 쉬는 시간 · 휴무로 — TA§4 · §5). 시안의 「지난 시각 회색」과는 다른 표시다
  - **칸 머리 = 「{정원}명 / {간격}분」**(그룹 `intervalCapacities` · `intervalMinutes` — KOS 와 같은 문구, TA§4)
- **카드 이름 = KOS `visitor.name` 그대로 + 한글 발음(`phoneticName`)**(사용자 지시 · Q-6 닫힘). 현장은 이름 칸에 영문을 넣는다(국가 접두 「(TW)」 등 포함) — **ccc 는 잘라 읽지 않는다**. 시안의 영문 여권 이름 「SURNAME, GIVEN」(`passport*`)을 따로 쓰지 않는다
- 그 밖 카드 값(성별 · 국적 · 초진/재진 `visitor.isNew` · 차트번호 · 시각)은 모두 일정 응답에 있다(R§0 · §3.1)
- **「총 예약 N건」 · 칸 머리 N 은 취소 · 부도를 뺀다**(사용자 지시 · Q-3 닫힘 · Q-90 건수 부분 닫힘)
- **공지 = 그 날짜의 KOS 공지** — 스케줄 표 날짜 이동과 같이 움직인다. 공지만 따로 날짜를 고르는 조회는 없다(사용자 지시 · Q-17 일부 닫힘). KOS 공지는 공개 API 가 없어 내부 `get-notices`(게시 시각 범위로 조회, R§1 15행 · §3.5)

**상태 = 2계층**(사용자 지시 · Q-1 · Q-2 닫힘) — KOS 두 축을 그대로:
① 예약 상태 `reservation.status` 가 취소 · 부도(`CANCELED` · `NO_SHOW`)면 그것이 먼저 ② 아니면 내원 단계 `flowStep`.

| KOS | 주 상태 | 부상태 |
|---|---|---|
| `reservation.status = CANCELED` | 취소 | — |
| `reservation.status = NO_SHOW` | 부도 | — |
| `RESERVED` | 예약 | — |
| `RECEPTION` | 접수 | — |
| `CONSULTATION_WAITING` | 상담 | 대기 |
| `CONSULTATION` | 상담 | 진행 |
| `PROCEDURE_WAITING` | 시술 | 대기 |
| `PROCEDURE` | 시술 | 진행 |
| `PROCEDURE_DONE` | 귀가 | 대기 |
| `COMPLETED` | 귀가 | 완료 |

- 「시술 완료」라는 상태는 따로 없다 — `PROCEDURE_DONE` = 귀가 대기. 「상담 완료」도 없다(아래 6)
- 취소 · 부도 일정은 `flowStep` 이 `RESERVED` 그대로이고 예약 상태만 바뀐다(R§3.2 · MC§3) — 그래서 ① 이 먼저
- **예약 현황 표시 = 카드 색 · 범례 = 주 상태 7개(예약 · 접수 · 상담 · 시술 · 귀가 · 취소 · 부도) · 부상태 = 카드 뱃지**. 시안 범례(예약 · 접수 · 상담 중 · 시술 중 · 귀가 대기 · 귀가 · 취소, D§3.2)를 이것으로 고친다
- 시술 현황판도 같은 2계층(같은 주 상태 · 부상태 이름 · 색)으로 맞춘다(사용자 · `_RESUME` §1 메모) — 범위 · 시점은 예약 현황 spec 때(아래 「보류 · 다음 버전」)

## 3. 예약 이동 · 취소 · 부도

- **이동**: KOS 는 드래그를 지원하지 않는다 — 별도 **[이동] 버튼**(`update-reservation`). **드래그 이동은 ccc 가 지원**(시안) — KOS 호출은 같은 이동 API(사용자 지시)
  - 이동은 **부분 수정**이다 — 일정 묶음(`occupiedResources`)만 보내고 메모 · 유입 · 담당 · 상담은 그대로(MC§0 · §2.1 · 데모 확인)
  - 접수된(`RECEPTION`) 일정도 이동된다(MC§0)
  - **드래그 거절**(코디 기본값 · Q-83 · Q-84 닫힘): 거절은 데이터 불일치가 아니라 **KOS 예약 규칙**(정원 · 같은 고객 겹침 · 변경 정책) 때문이다(MC§2.2). 사본의 정원으로 꽉 찬 칸은 **미리 막고**, 그래도 KOS 가 거절하면(동시 조작) **카드 원위치 + 오류 토스트**. 드래그는 **예약 길이를 유지**한다
- **[예약 취소] = 사유 고르기**(사용자 지시 · Q-85 닫힘): 예약 취소 `CANCELED` / 예약 부도 `NO_SHOW` — KOS 와 같다. 둘 다 `cancel-reservation` 하나에 `reason` 으로 갈린다(MC§3)
  - 시안 [예약 취소]는 접수 전만 보인다(D§3.4)
- **취소 되돌리기 = 이번엔 ccc 조작 로그만 쌓는다**(사용자 지시 · Q-88 닫힘) — 시술 현황과 같은 순서: 로그 먼저 → 나중에 토스트 + [되돌리기] 버튼(내부 `revoke-canceled-reservation`, 데모 확인 MC§4). 버튼은 「보류 · 다음 버전」
- 취소 · 부도 카드는 주 상태 「취소」 · 「부도」로 판에 남는다(1의 범례)

## 4. 접수 — 고객 정보 · 특이사항 · 이전 방문

### 4.1 고객 정보 = 신분증 스캔 + 문진

**고객 데이터는 두 갈래로 완성한다**(사용자 지시).

① **신분증 스캔** — 국적 · 여권번호 · 신분증은 **데스크가 앱으로 스캐너를 열어 스캔한 값**이다(문진 질문 아님)
- **기존 고객 수정 = 내부 `update-visitor-personal-information`**(Q-39 닫힘 — 공개 API 에는 기존 고객을 고치는 작업이 없다, U§0). 스캔 값 전부가 들어갈 칸이 있다(U§6)
- 흐름(사용자 지시 · Q-40 닫힘): 기존 고객이면 **KOS 값을 먼저 채워 보여 주고 → 데스크가 고침(스캔 값 반영) → 읽은 묶음 전체를 고쳐 보낸다** — 빠진 필드가 지워질 위험을 피한다(U§2.2)
- 신규 고객은 예약 등록 때 만든 고객(2)을 같은 길로 고친다
- **신분 확인 상태(확인 완료 / 미확인 · 스캔 기기 · 시각) = ccc DB** — KOS 에 칸이 없다(사용자 지시 · Q-35 · Q-44 닫힘)
- **신분증 이미지 = KOS 에 올린다**(사용자 지시 · Q-45 닫힘) — 지금도 현장이 여권 사진을 KOS 에 올린다. 공개 `generateUploadingImageUrl` → PUT → `registerVisitorImages`(U§6 S16 · Q§5 M16)

② **문진** — **방문할 때마다 항상**(초진 · 재진 모두 — KOS 양식에 방문 유형 질문이 있다, 사용자 지시)
- **방향 = ccc 가 자체 질문지를 갖고, 그 답을 KOS 사전 질문(문진)에 제출**(사용자 구상)
- **시안 질문을 KOS 문진 양식 그대로로 고친다** — KOS 에 없는 시안 질문은 목업이라 뺀다(Q-26 닫힘). 시안 「건강 정보」 7개는 KOS 양식 「건강 정보」 질문 7개와 이름이 같다(R§3.1 18행)
- **건강 「확인 필요」 = 답이 「없음 / 아니오」가 아닌 것**(사용자 지시 · Q-12 · Q-36 닫힘) — KOS 에는 이 기준이 없어 ccc 가 문진 답으로 판정한다
- 문진 제출이 KOS 에 남기는 곳: 설문 응답 자체(`getQuestionnaireSubmit`) + **고객 정보 일부**(성별 · 휴대폰 · 주소가 제출 값으로 바뀐다, Q§0 · §4)
- **KOS 문진은 고객당 1건**(매 방문 덮어씀)이다 → 최신본은 사본으로 두고, **방문마다 제출한 답은 ccc 만의 데이터로 쌓는다**(사용자 지시 · Q-27 · Q-36 일부 닫힘)
- **고객 입력 QR 보내기 = 우리 앱으로**(사용자 구상) — 받는 기기 ① 데스크 태블릿(코디 계정 로그인) ② 코디 본인 폰(코디 계정 로그인). 고객이 그 기기에서 질문지를 채운다(시안 「태블릿에 띄우기」 · 기기 스캔 자리). KOS 설문 링크(내부 `issue-questionnaire-link` · 30일, Q§2)는 쓰지 않는다(Q-25 — ccc 자체 질문지). 세부는 spec 때

- AS-IS(KOS 현장): 직원이 KOS 예약 화면에서 설문 **링크를 발급**하고, 고객이 그 링크로 제출한다. KOS 는 URL 만 돌려준다 — 메신저 · 문자로 보내는 기능은 없다(Q§0 · §2)

### 4.2 특이사항(주의사항)

- **시안 「주의사항」 = KOS 고객 「특이사항」**(사용자 지시 · Q-13 · Q-37 · Q-46 닫힘)
  - 읽기: 일정 응답의 `visitor.memo`(공개). **공개 `getVisitor` 에는 `memo` 가 없다** — 공개로는 일정의 `visitor.memo` 로만 읽힌다(MT§0 · Q-80 닫힘)
  - 쓰기: 내부 `update-visitor-management-information` — **읽고 고쳐 전체 보낸다**(관리 묶음 = 유입 · 추천인 · 고객 유형 · 분류 · 담당 · 동의 · 커스텀 속성 + `memo`). 읽은 그대로 + memo 만 바꾸면 memo 와 수정 시각 말고는 안 바뀐다(MT§0 · §4, 데모 확인)
  - **「특이사항 = visitor.memo」 사용자 눈 확인 끝**(KOS 웹 「특이사항」에 시험 문구 보임 · Q-82 닫힘)
- 시안 자리 글자 「고객 공통 메모 (모든 방문에 표시)」와 같은 뜻 — 고객 단위 메모

## 5. 접수 완료 = 방 배정

- **AS-IS(KOS 현장 우회)**(사용자 설명 · RM§0): 코디 목표는 「고객이 오면 방 배정」이다. 그런데 KOS 의 방 지정 화면(시술 진행판)은 **시술 대기만** 보여서, KOS 에서는 화면 세 곳을 오가며 쓰기 5번을 한다

  ```text
  ① 접수(recept)                     — 고객 상세 · 예약 탭
  ② 「방 배정」 기타 작업 추가          — 고객 상세 · 수납 탭
  ③ 시술 대기로 올림                    — 고객 상세 · 상담 탭
  ④ 방 지정(change-tasks-room)         — 시술 진행판
  ⑤ 상담 대기로 되돌림                  — 고객 상세 · 시술 탭
  ```

## 6. 상담 — [실장 호출]

- **흐름 = 상담 대기 → 상담 진행 → (상담 끝) 수납 → 시술 대기**(사용자 지시)
- **[실장 호출] = 상담사 지정(KOS `update-reservation{counselor}`) + 그 상담사 앱 알림까지**(사용자 지시)
  - 상담사 지정 = 예약의 「희망 상담사」(`reservation.counselor`)를 정하는 것 — KOS 상담 HAR 이 쓴 길이다(CS§2.3). 공개 짝은 없다
  - **KOS 에 상담사 「호출」은 없다** — [실장 호출]의 알림은 **ccc 만의 알림**(Q-97 닫힘 · CS§6)
  - 알림 = 상담사 앱 푸시. 의사 호출 푸시(SPEC-004 A-14 · APNs)와 같은 구조 — 받으려면 **상담사(실장) 계정 · 역할**과 ccc 계정 ↔ 직원 사본 연결이 필요하다(`_RESUME` §1 메모 · 아래 「계정 · 역할」). 범위 · 시점은 spec 때
- **상담사 목록 = ccc 직원 사본**(사용자 지시) — KOS `getAccounts` 1시간 동기화 · 상담사 역할 태그(`COUNSELOR`)로 거름. 시술 현황과 같은 사본
- **상담사 「지금 상태」(비어있음 / {방} 상담 중) = ccc 가 계산해서 넣는다**(사용자 지시 · Q-14 상담사 부분 · Q-98 닫힘) — KOS 에 필드가 없다. 그날 `CONSULTATION`(상담 진행) 일정의 상담사(`counselor`) + 방으로 계산
- 실장이 고객과 방으로 가서 **KOS 에서 [상담 시작]** — 상담 기록 · 상담 진행은 KOS 가 만든다(사용자 지시). ccc 는 상담 진행으로 바꾸지 않는다
- **상담 중 KOS 작업은 상담사가 KOS 에서 직접** — 수납 추가 · 시술 추가 · 오더 메모까지(사용자 지시). ccc 는 결과를 사본으로 읽기만(시술 목록 · `paymentRequired` · `orderMemo`). **ccc 에 수납 · 시술 추가 화면 없음**
- **「상담 완료」는 만들지 않는다**(코디 기본값 · Q-92 닫힘) — KOS 에 「상담 완료」 단계 · 필드가 없다(CS§3). 다음 단계로 넘어가면 완료로 본다. 예약 상세 상담 카드의 「완료」 = 다음 단계로 넘어간 것
- AS-IS(KOS 현장 · CS§0): 접수 → 상담 대기 → 상담사 지정(`update-reservation`) → 상담 기록(`create-consultation`) → 상담 진행(`change-flow-step`) — 모두 고객 상세 화면

## 7. 수납 · 시술 대기 — KOS

- **수납은 상담사가 KOS 에서**(6). KOS 수납 = 쓰기 5번: 수납 생성 → 상품 옵션 추가 → 일정 ↔ 수납 연결(일정 `purchaseIds`) → 결제 → 수납 확정(PD§0)
  - 이 수납으로 일정에 작업이 자동으로 생기지는 않았다(PD§0 — 이 경우). 시술 작업은 상담사가 동선에 넣는다
- **수납 뒤 시술 대기 전환도 상담사가 KOS 에서** — ccc 는 사본으로 읽어 카드를 띄운다(사용자 지시)
- **시술 구간 넘김**: KOS 일정이 시술 대기(`PROCEDURE_WAITING`) + 방 있음이 되면 시술 현황 카드가 생긴다 — 그 뒤는 **workflow-v2**(마취 · 의사 호출 · [시작] · [종료] · [귀가 대기])
- **후납 = 결제를 마치고 시술에 들어간 뒤 추가 시술을 하는 경우** — KOS 에 「수납 필요」로 뜬다(사용자 설명)
  - 원천 = 작업 `tasks[].paymentRequired` — 시술권 없이 상품 옵션으로 넣은 작업은 `true`(PP§0). 수납 `status` 로는 알 수 없다
  - **수납 확정(`accept-purchase`) 직후 KOS 가 그 작업에 시술권을 붙이고 `false` 로 바꾼다**(PC§0 · §2 — 확인)
  - 시술 현황 카드의 「수납 필요」와 같은 원천 · 같은 모양이다(PP§5)

## 8. 귀가 대기 정산 · 귀가 완료

- 시술 현황의 [귀가 대기](v2 6 — `PROCEDURE_DONE`) 뒤, 예약 상세가 「귀가 · 대기」 단계의 **정산 상자**를 보인다(D§3.4)
- **[수납하기 ›] = KOS 수납 화면을 연다(딥링크)**(사용자 지시) — ccc 는 수납을 하지 않는다
  - 주소 꼴(PD§2): `https://app.kos-solution.com/{tenantId}/reservation/schedule/?visitorId={visitorId}&scheduleId={scheduleId}&tab=purchase` — 어느 탭에서 결제 창이 뜨는지 · KOS 로그인 세션은 정할 것(Q-102 · Q-103)
- **수납 정보는 KOS 에서 받아 온다**(사용자 지시) — 공개 `getScheduleDetail.purchaseIds` → 공개 `getPurchaseSummaries`(PD§4 · 데모 확인)
  - 「전체 금액」 · 「결제 금액」은 KOS 값으로 **계산**한다(항목 합 · 승인 거래 합 — PD§4). **「후납 금액」이라는 KOS 값은 없다**(PD§0 · PP§0) — 무엇을 보일지는 정할 것(Q-105 · Q-111 · Q-112)
  - 「수납 필요 N건」은 KOS 값(`tasks[].paymentRequired` 개수)만으로 판정할 수 있다(PC§4)
- **[처방전 출력] = KOS 에서 출력한다**(사용자 지시 — `_RESUME` 10-26 「[처방전 출력]」 줄) — ccc 는 **KOS 일정 상세 딥링크**를 연다
  - 주소 꼴(RXD§0 · §1): `https://app.kos-solution.com/{tenantId}/reservation/schedule/?visitorId={visitorId}&scheduleId={scheduleId}&tab=etceteraWork` — 그 일정의 처방전 목록이 있는 탭(「기타 업무」)까지 열린다(Q-129 · Q-130 · Q-135 닫힘)
  - **처방전 창 열기 · 인쇄는 데스크가 KOS 에서 한 번 누른다** — 처방전 id 로 여는 주소가 없고(쿼리 · 해시 없음, RXD§0) 처방전 조회 · 출력 공개 API 도 없다(RX§0). KOS [처방전 출력] = 내부 `print-prescription`(출력 기록) + 브라우저 인쇄 창(RX§0)
  - 필요한 값(`visitorId` · `scheduleId`)은 ccc 사본에 있다. 일정 `prescriptionIds`(공개)는 「처방전 있음」 판단에만 쓴다(RXD§0)
- **여정 리포트는 뺀다**(사용자 지시 — 정산 상자에서 뺌)
- **[귀가 완료] = 데스크가 ccc 에서**(사용자 지시) → KOS 귀가(`COMPLETED`)
  - **「수납 필요」가 남으면 [귀가 완료]를 못 한다** — KOS 도 막는다(사용자 지시 · Q-121 닫힘 · Q-116 꺼짐 조건 부분 닫힘)
  - KOS 귀가 HAR = 내부 `change-flow-step{id, step:COMPLETED}` 한 번 · 예약 상태도 `COMPLETED` 로 바뀐다(PD§5). 공개 후보 = `changeFlowStep(COMPLETED)`(사용자 지시의 「후보」) — 데모 귀가 대기 일정이 없어 시험 못 함(Q-110)
  - 참고: 리포트는 공개 스펙의 `changeFlowStep` 거절 조건에서 「수납 필요」를 찾지 못했다(끝나지 않은 시술뿐, PC§6). ccc 는 사용자 지시대로 「수납 필요」가 남으면 막는다 — 시안 「후납이 남으면 꺼짐」과 같다
  - 귀가하면 시술 현황 카드가 사라진다(v2 6 — E2E-9)

## 인증 · 계정

v2 「인증 · 계정」(공개 API 데모 키 · 내부 시스템 계정 · 토큰 보관)은 그대로. 바뀐 것만 적는다.

| 무엇 | 방식 |
|---|---|
| 데모 쓰기 | **데모 지점 KOS 쓰기 시험 허가**(사용자 · 2026-10-26). 운영 명동점 금지 그대로. 리포트의 쓰기 시험은 모두 데모 키 · 데모 테넌트 확인 뒤(RT · MT · MC 머리말) |
| KOS 쓰기 주체 | 내부 쓰기는 **시스템 계정** 이름으로 남는다 — 누가 했는지는 ccc 조작 로그에만(U§7) |
| KOS 웹 세션 | [수납하기 ›] 딥링크는 데스크 PC 브라우저의 KOS 웹 로그인 세션이 있어야 한다(PD§2 · Q-102) |
| ccc 계정 · 역할 | 지금 = 관리자 · 의사 · 간호사(SPEC-004 §3). **코디 역할을 추가한다**(사용자 「코디 추가해야지」). **코디 권한은 제한하지 않는다 — 직무별 제한은 마지막에 한 번에**(사용자 지시) |
| 상담사(실장) 계정 | [실장 호출] 알림을 받으려면 **상담사(실장) 계정 · 역할**이 필요하고 ccc 계정 ↔ 직원 사본 연결(의사의 `staffId` 처럼)이 필요하다(`_RESUME` §1 메모 · 구상 — 범위 · 시점은 spec 때) |
| 동시 로그인 | **한 계정이 기기 · 웹 · 앱에 동시 로그인**(구상). 토큰이 HMAC 무상태라 지금 구조에서 막히지 않는다 · 기기마다 푸시 토큰 등록. 세부는 spec 때 |

- **public 레포** — 키 · 비밀번호 · 토큰 · KOS id · 실명 · 금액 값은 여기 적지 않는다. 경로의 id 는 `{tenantId}` 꼴

## 보류 · 다음 버전

- **본사 예약 요청**(오른쪽 패널 「예약 요청」 · 가안 카드 · 승인/반려 모달) — **자리만**(사용자 지시). 예약 폼은 나중. KOS 에 해당 객체가 없다(R§3.1 30 · 31행 · Q-18 · 디자인 Q-17)
- **취소 되돌리기 버튼** — 이번엔 로그만. 나중에 토스트 + [되돌리기](내부 `revoke-canceled-reservation`) — 시술 현황 되돌리기와 같은 순서(`_RESUME` 10-26)
- **KOS 소켓 실시간**(PC§3) — 일정 전체가 즉시 온다. 원천으로 쓸지 · 놓친 이벤트 따라잡기는 열린 질문(Q-119 · Q-120). 그 전엔 조회
- **시술 현황판 상태 2계층 맞추기** — 지금 시술 현황은 `flowStep`(시술 대기 · 진행 · 귀가 대기)와 작업 status 를 따로 다룬다 → 같은 주 상태 · 부상태 이름 · 색으로(사용자 · `_RESUME` §1). 범위 · 시점은 예약 현황 spec 때(되돌리기 판에는 넣지 않음)
- **상담사 알림 앱** — 상담사 계정 · 역할 · 푸시(`_RESUME` §1). 범위 · 시점은 spec 때
- **앱을 웹에 맞추기** — 웹/앱 규칙 차이는 앱 후속 작업(`_RESUME` 10-26 「웹이 정본」)
- **자체 CRM 차트번호** — 지금 정본은 KOS. 자체 CRM 을 만들 때 ccc 가 부여(`_RESUME` 10-26)
- **직무별 권한 제한** — 코디 · 상담사 등 역할별 제한은 마지막에 한 번에(사용자 지시). 그 전엔 코디 권한 제한 없음
- **여정 리포트** — 뺀다(사용자 지시). 정산 상자에 두지 않는다
- 원내 현황(평면도 · 시안 하위 화면 C) — 이 문서 밖
