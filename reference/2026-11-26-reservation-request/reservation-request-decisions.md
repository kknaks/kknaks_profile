## A. 범위 · 큰 틀

| # | 결정 |
|---|---|
| RQ1 | 이번 작업 = 예약 현황판 오른쪽 「예약 요청」 칸(`section.day-res-req` · SPEC-006 R3 · R32 에서 미룬 것) + 그것을 채우는 ext API |
| RQ2 | **범위 = 고객 → 링키 → 병원 요청 흐름만.** 예약이 생긴 뒤 예약 생애(내원 · 노쇼 · 당일 미방문 취소 · 병원 쪽 변경)는 기존 예약 현황에서 평소대로 — 스레드가 따라가지 않고 감지 · 글 · 알림 없음. 병원이 먼저 KOS · DAY 에서 수정 · 취소하는 흐름은 없다 |
| RQ3 | 스레드 하나 = 예약 하나. 예약은 고객에 종속(고객 밑에 스레드 여러 개 가능) |
| RQ4 | 근무 데이터(원장 근무 · 코디 언어 · 출근)는 이번에 제외 → 근무 일정 칸 없음 |
| RQ5 | 현황판 예약 카드 → 스레드 입구 **없음**. 스레드는 오른쪽 「예약 요청」 목록 · 웹 알림에서만 연다 |

## C. 요청 본문 · 버전

초안(칸 이름 · 예시): `orchestration/work/day-reservation3/ext-request-body-draft.md` — 이름은 제안, 결정은 아래.

| # | 결정 |
|---|---|
| RQ11 | 새 스레드 = `POST /reservation-requests`(v1 · 늘 신규 요청) · 같은 스레드 새 버전 = `POST /reservation-requests/{requestId}/versions`(`kind` = 수정 `change` · 취소 `cancel`) · `Idempotency-Key` 헤더 |
| RQ12 | 버전 종류 = 신규 요청 · 수정 요청 · 취소 요청. **버전은 늘 링키가 올린다.** 확정 뒤 새 버전이 오면 같은 스레드가 다시 열린다 |
| RQ13 | **버전 번호는 서버가 매긴다**(스레드 안 1, 2, 3 …) — 링키는 응답으로 받는다. `baseVersion` 충돌 검사 없음 |
| RQ14 | 요청 본문 = 예약 등록(SPEC-007) 값 **완성본** — 병원 직원이 생성 때 채우는 칸 없음(담당자만 예외 RQ15). 수정 버전도 완성본 전체 · 취소 버전 = `reason` 선택 칸만 |
| RQ15 | **담당자 = 「예약 생성」을 누른 로그인 직원**(요청 본문에 담당자 없음 · 예약 생성은 병원 최종 권한) |
| RQ16 | 고객 칸: **이름 · 생년월일 필수**(KOS 고객 등록 조건) · 발음 이름 · 성별 · 국적 · 휴대폰(국가번호 + 번호) · SNS(종류 · 계정) · **이메일(선택 · 새 고객이면 KOS 고객 이메일로)** · 재진이면 `customerId`(DAY 고객 id — ext `/customers/lookup` 응답 값) |
| RQ17 | 시작 시각 필수 · 끝 = 예약 그룹 간격(웹 예약 등록과 같음) |
| RQ18 | **예약 그룹 = 링키가 보냄(필수)** |
| RQ19 | 지정 원장 · 지정 상담사 = 선택(없으면 비움) |
| RQ20 | 희망 시술 = **텍스트**(메뉴 id 아님) |
| RQ21 | 통역 = 한 칸(언어 코드 · null = 필요 없음) |
| RQ22 | **유입 = 보내는 쪽이 유입 채널 목록에서 골라 보냄 · 필수.** 「링키」 고정 아님. KOS 「상세 유입 채널」(자유 글)은 이번에 뺌 |
| RQ23 | 예약 메모 = 링키가 보냄 · 병원이 고칠 수 있음(1열 입력칸 · 따로 저장 버튼 없음 — 생성 · 수정 때 같이 나감). 「원장 1:1 상담」 같은 내용은 **메모 글의 일부**(따로 칸 아님 · KOS 체크 「상담 필요」와 연결 안 함) |

## D. 초진 · 재진 (같은 고객)

| # | 결정 |
|---|---|
| RQ24 | `customerId` 가 오면 그 고객(재진). 없으면 DAY 가 **이름(대소문자 · 띄어쓰기 무시) + 생년월일 정확히 같음**으로 찾는다: 1명 = 재진 · 0명 = 초진(생성 때 새 고객) · **2명 이상 = 생성 막고 「고객 확인 필요」 댓글 → 링키가 `customerId` 넣은 새 버전** |
| RQ25 | 잘못 잡힌 경우 = 직원이 댓글 → 링키 새 버전. **후보 고르는 화면 없음**(시안 v15 그대로). 기획안 정책 15(네 값 · 후보 고르기)와 다름 → 「기획안과 다른 곳」에 적는다 |

## E. 저장 · KOS 쓰기

| # | 결정 |
|---|---|
| RQ26 | **DAY DB 는 칸별로 나눠 저장**(희망 시술 · 통역 · 예약 메모 …). 요청 버전 = 링키가 보낸 값 고정 기록. 생성 뒤 예약 메모는 KOS 동기화 그대로(어긋나도 됨) |
| RQ27 | KOS 쓰기 = 기존 쓰기(새 고객 · 예약 만들기 · 예약 변경 · 예약 취소 — SPEC-007 W2 · W3 · W4 · W5). **KOS 에 칸이 있는 값은 그 칸으로**: 예약 그룹 · 시간 · 지정 원장(`reservationGroup.doctors`) · **지정 상담사(KOS 새 예약 화면 「당일 지정 상담사」 — DAY 가 지금 안 보냄 · 본문 키는 실물 확인)** · 담당자 · 유입 |
| RQ28 | **KOS 에 칸이 없는 값만 KOS 예약 메모에 합친다**: 형식 = `필드: 내용` 한 줄씩(줄바꿈) · 순서 희망 시술 → 통역 → 예약 메모 · 빈 칸 줄은 뺌 · 통역은 한국어 언어 이름(예 「중국어」) · 합친 글이 KOS 한도(1000자)를 넘으면 요청을 400 으로 받지 않는다. KOS 「희망 시술」 목록 칸은 비움 |

## F. 상태 · 버튼 · 댓글

| # | 결정 |
|---|---|
| RQ29 | 상태 두 층: 스레드(예약 카드) = 요청됨 · 확정 · 취소됨 · 닫힘 / 댓글 = 종류가 있고, 답이 필요한 댓글만 상태 |
| RQ30 | 병원 거절 버튼(「처리 불가」) 없음. 버튼 = [예약 생성](신규) · [예약 수정](수정 요청) · [예약 취소](취소 요청) — 답할 버전의 종류에 따라 하나. 위치 = 1열 예약 메모 입력칸 아래 오른쪽(v15) |
| RQ31 | 생성 안 된 스레드 닫힘 = 링키 철회 또는 희망 일시가 지나면 자동 |
| RQ32 | 댓글 종류 3개(값): **`message`**(일반 글 · 병원 · 링키 양쪽) · **`change_request`**(변경 요청 · 병원만) · **`reservation_applied`**(예약 반영됨 · 시스템 자동) |
| RQ33 | `change_request` = 병원이 **일시만** 여러 개 제안(2열 예약 현황 표의 시간 머리를 골라 칩 · 예약 그룹은 안 넣음 · 다른 날도 고를 수 있음) + 글. 링키는 수락 버튼이 없고 **새 버전으로 답한다** |
| RQ34 | 새 버전이 오면 답 없는 `change_request` 는 「대체됨」 · 새 버전에 버튼 다시 |
| RQ35 | `change_request` 를 보낸 버전은 **버튼 숨김**(「링키 답 기다림」 · 버튼 줄 높이 유지) · 병원이 그 변경 요청을 철회하면 버튼 돌아옴 |
| RQ36 | `reservation_applied` = **링키 요청을 처리했다는 글만** — 스레드 버튼(생성 · 수정 · 취소)이 KOS 에 반영될 때 자동(생성 · 수정 · 취소 중 무엇인지 · 반영 일시). 링키는 이걸 조회해 고객에게 확정 알림 |
| RQ37 | 댓글 입력 = 요청됨 · 확정 스레드는 쓸 수 있음 · 취소됨 · 닫힘은 읽기만(새 버전이 오면 다시 열림) |
| RQ38 | 고르기 위주로 가볍게 · 글은 필요할 때만 |
