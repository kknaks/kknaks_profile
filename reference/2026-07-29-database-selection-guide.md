# 개발 시 데이터베이스 선택 가이드

## 개요

새로운 서비스를 개발하거나 취업 준비 중인 개발자를 대상으로 주요 데이터베이스 유형 6가지(키밸류, 관계형, 그래프, 도큐먼트, 컬럼 패밀리, 검색 인덱스)를 분류하고 각각의 적합한 사용 시나리오를 설명한다.

의견글에 가깝다. 수치·출처·벤치마크 없이 강사의 직관적 설명과 단순화된 권고를 중심으로 구성된 입문용 영상이다.

## 출처와 맥락

코딩애플(한국 개발 튜토리얼 유튜브 채널, 개인 운영)의 입문용 영상(2022.11.09). 공식 문서나 1차 자료가 아닌 강사 개인의 요약과 권고다. 대상 시청자는 데이터베이스를 처음 선택해야 하는 입문 개발자다.

## 핵심 주장

- Redis는 데이터를 RAM에 저장하기 때문에 하드디스크 기반 DB보다 빠르며, 메인 DB의 자주 쓰이는 데이터를 캐싱하는 보조 용도(캐싱, pub/sub)로 주로 활용한다.
- 관계형 DB는 정규화(중복 제거)와 트랜잭션으로 데이터 정확도를 보장하므로 금융 거래처럼 정확도가 중요한 경우에 적합하다.
- 도큐먼트 DB(MongoDB, CouchDB, Firestore)는 스키마 정의 없이 JSON 형태로 자유롭게 저장하고 분산 처리가 쉬워 대량 입출력에 유리하다.
- 그래프 DB(Neo4j)는 노드 간 관계와 방향을 직접 저장하므로 SNS 친구 관계·추천 서비스·감염 경로 추적 등 관계 중심 데이터에 적합하다.
- 컬럼 패밀리 DB(Cassandra, BigTable)는 표 형식이지만 정규화 없이 칼럼을 자유롭게 구성하고 분산 처리가 뛰어나 대량 입출력에 활용한다.
- 검색 인덱스 DB(Elasticsearch, Amazon CloudSearch)는 일반 DB보다 인덱스 보관 전용으로 쓰며, 빠른 검색·자동완성·오타 교정 기능 구현에 활용한다.
- 일반적인 선택지는 관계형 DB(정확도 우선)와 도큐먼트 DB(처리량 우선) 둘 중 하나다.

## 주요 개념

- 정규화(Normalization) — 관계형 DB에서 데이터 중복을 제거하기 위해 테이블을 분리하는 설계 원칙
- 캐싱(Caching) — 자주 조회되는 데이터를 빠른 저장소(RAM 등)에 복사해 두는 성능 최적화 패턴
- 분산 처리(Distributed Processing) — 데이터를 여러 노드에 나눠 저장·처리하는 방식
- 검색 인덱스(Search Index) — 빠른 검색을 위해 별도 저장하는 색인 구조

## 근거와 사례

- Redis 속도 우위: RAM이 하드디스크보다 "수십~수백 배 빠르다"고 언급한다. 구체적인 수치나 측정 조건은 제시하지 않는다.
- 분산 처리 트레이드오프: 도큐먼트 DB와 컬럼 패밀리 DB 모두 분산 시 "DB 간 정확도가 떨어질 수 있다"고 언급한다. 어떤 조건(읽기·쓰기 부하, 네트워크 파티션 등)에서 그런지는 다루지 않는다.
- 그래프 DB 사례: SNS 친구 관계, 비행기 노선, 코로나 감염 경로 추적, 대기업 추천 서비스.
- 관계형 DB 사례: 금융 거래(정확도·트랜잭션 요구).

## 한계와 검증이 필요한 부분

- 수치·출처·벤치마크 없이 강사의 직관적 설명에만 의존한다. "RAM이 수십~수백 배 빠르다"는 조건 없는 주장이다.
- "관계형 또는 도큐먼트 중 하나"라는 단순화된 권고는 CAP 이론, 스케일 수준, 데이터 구조, 운영 복잡도 등을 반영하지 않는다.
- 컬럼 패밀리 DB와 도큐먼트 DB의 실질적 차이가 명확히 설명되지 않는다.
- 운영 비용, 생태계 성숙도, 학습 곡선은 다루지 않는다.
- 입문용 영상으로, 기술 선택의 1차 자료(공식 문서, 벤치마크)로 쓰기에는 한계가 있다.
