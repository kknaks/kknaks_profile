# 1. 회의 시작

## 1-1. 화면에서 무슨 일이 일어나나

```
회의록 목록
  └ 회의를 고른다 → 우측 미리보기
      └ [회의 입장]                      ← MF-5
          └ 시작 전 화면
              안건을 미리 적어둘 수 있다
              상태 바 「기록 대기 00:00:00」
              └ [회의 시작]
                  → 회의 중 화면으로 바뀐다 (페이지 이동이 아니라 상태 변화)
```

**✅ MF-5 — CTA 를 상태별로 가른다**

```
scheduled    「회의 입장」   → 시작 전 화면. 거기서 「회의 시작」을 누른다
recording    「회의 입장」   → 회의 중 화면. 돌고 있는 회의에 다시 들어간다
generating   「상세보기」    → 「회의록 생성중」
ended        「상세보기」    → 최종 회의록

전     가는 곳은 상태별로 다른데 라벨이 「상세보기」 하나였다
왜     아직 안 한 회의를 「상세보기」로 들어가는 건 말이 안 된다 —
      거기서 하는 일은 **회의를 시작하는 것**이다
```

**✅ MF-7 — 상세에서 목록으로 돌아갈 길** (**전 화면 공통**)

```
┌─ 상세 화면 헤더 (회의록 · 업무 · 설정 전부) ────────────────┐
│                                                            │
│  ←  홈 ›  회의록 ›  테스트                                 │
│  ‾    ‾‾    ‾‾‾‾‾‾    ‾‾‾‾‾                                │
│  │    링크   링크      지금 여기(링크 아님 · 색만 진하게)   │
│  └ 한 단계 뒤로 — 회의록 목록으로                          │
└────────────────────────────────────────────────────────────┘

「←」          **한 단계 뒤로.** 상세 화면에만 붙는다
              회의록 상세 → /meetings/   ·   업무 상세 → /tasks/
breadcrumb    **아무 단계로나 점프.** 앞 단계가 링크다
              마지막(지금 여기)만 링크가 아니다
              호버·포커스 표시를 준다 — 키보드로도 닿아야 한다

지금   AppShell 의 Breadcrumb 이 trail 을 전부 <span> 으로 그린다. 링크가 아니다
      → 상세에서 목록으로 돌아갈 어포던스가 화면에 **없다**
      업무 상세도 같다(`뒤로`·`ArrowLeft`·`router.back` grep 0건)

⚠ **회의록만 고치면 업무·설정에 같은 게 남는다.** 공용 부품에서 한 번에 고친다
```

**✅ MF-8 — 상세 헤더는 업무 상세를 따른다** (**업무 헤더가 정본이다**)

```
지금 — 둘이 다르다

┌─ 업무 상세 ────────────────────────────────────────────────┐
│  홈 › 내 업무 › 같은 프로젝트                              │
│  [ 미팅·회의 ]  [ ● 후보 검증 프로젝트 ]  ← 배지 줄이 제목 위│
│  같은 프로젝트                            ← 제목 28/700    │
└────────────────────────────────────────────────────────────┘

┌─ 회의록 상세 ──────────────────────────────────────────────┐
│  홈 › 회의록 › 테스트                                      │
│  테스트                                   ← 제목이 먼저    │
│  09월 07일 09:30–10:30 · 60분 · 미팅·회의 ˅ · 프로젝트 ˅   │
│                        ↑ 메타 한 줄에 인라인 셀렉터가 섞임 │
│                              [ 삭제 ] [ ● 종료된 회의 ]    │
└────────────────────────────────────────────────────────────┘

바꾼 뒤

┌─ 회의록 상세 ──────────────────────────────────────────────┐
│                                                            │
│  ←  홈 › 회의록 › 테스트                    ← MF-7         │
│                                                            │
│  [ 미팅·회의 ˅ ]  [ ● 프로젝트 ˅ ]   [ 삭제 ] [ ● 종료 ]   │
│   ↑ 업무와 같은 배지 줄                ↑ 우측 액션이       │
│     클릭하면 셀렉터 (인라인 편집 유지)   같은 높이에        │
│                                                            │
│  테스트                                     ← 제목 28/700  │
│                                                            │
│  09월 07일 (월) 09:30 – 10:30 · 60분        ← 회의 고유    │
│                                                            │
└────────────────────────────────────────────────────────────┘

유형·프로젝트   메타 줄에서 빠져 **제목 위 배지 줄**로 올라간다
우측 액션      삭제 · 상태 칩이 배지 줄과 **같은 높이**에 붙는다
일시·소요      회의에만 있는 것이라 **제목 아래 한 줄**로 남는다
인라인 편집     배지를 눌러 유형·프로젝트를 바꾸는 동작은 **그대로**

같이 맞추는 것   **시작 전 화면 헤더**도 지금 「제목 → 부제」 순서다
업무 쪽은 안 바꾼다 — 업무가 정본이고 회의록이 따라간다
```

## 1-2. 서버에서 무슨 일이 일어나나

```
POST /api/meetings/{id}/start

  ① 상태 전이   scheduled → recording
                recording_started_at = now()          ← 경과 시간·근거 칩의 기준점
                **한 UPDATE**

  ② 웜스타트를 **큐에 넣는다**

  ③ **즉시 응답**                                      ← 기다리지 않는다

  ④ (나중에) 워커가 끝나면 ai_session_id 를 UPDATE
```

**✅ MF-1 — 기다리지 않는다** (2026-09-07 · `decisions-pending.md` ① 닫힘)

```
전    /start 가 codex 응답까지 기다렸다 → 실측 13초 스피너
      매 회의마다 걸린다(회의당 세션 하나). 컨텍스트가 클수록 길어진다

후    큐에 넣고 끝

근거  웜스타트에서 받는 것은 **session_id 하나**다. 결과 본문은 버린다
      (meeting_batch_service.py:640 · DEC-003 §STT 「결과 무시」)
      그 id 는 **첫 배치 때까지만** 있으면 된다 —
      첫 배치는 확정 발화 600자가 쌓여야 도니 최소 몇 분 뒤다

함께 닫힘
  D-2/DG-9  워커가 죽어 있어도 **회의는 시작된다.** 배치만 안 돈다
            → 회의가 recording 에 갇히는 일이 없어진다
  W-1       service 가 commit() 할 이유가 없어진다
            (전이만 하고 끝이니 요청 하나 = 트랜잭션 하나)
```

## 1-3. 프론트가 하는 일

```
/start 응답을 받으면
  └ WS 를 연다        ws://…/api/meetings/{id}/stream
      첫 프레임으로 access 토큰 + 오디오 포맷 선언
      → 서버가 ready 를 준다

  └ 마이크를 잡는다    getUserMedia({audio:true})   내 마이크만
      **「재개」를 눌렀을 때만** 부른다 — 권한 프롬프트가 사용자 동작에 붙어야 한다
      실패하면 일시정지 + 사유 배너. 자동 재연결하지 않는다

  └ 오디오를 보낸다    250ms 단위. 서버가 ① 녹음 파일 append → ② Soniox 순으로 흘린다
```

**실물 확인에서 밟은 것 (2026-09-07)**

```
macOS   Info.plist 에 NSMicrophoneUsageDescription 이 없어 권한을 안 물었다
        → 넣었다. tauri dev 실행파일에도 박힌다(tauri-codegen)
CSP     connect-src 에 ws://localhost:8000 이 없어 WS 가 막혔다
        → 넣었다. 3000(Next HMR)만 있었다
Windows WebView2 는 PermissionRequested 를 처리해야 getUserMedia 가 산다
        → 코드는 넣었으나 **실물 확인 못 했다**
```

## 1-4. 웜스타트가 AI 에게 주는 것

**MCP 가 붙으면 컨텍스트를 싣지 않는다.** 역할·규칙·용어·도구만 준다.
프롬프트 초안은 `ai-prompt-draft.md` §A.

```
역할        「회의에 참가하는 두 명 중 하나」 — 사람과 AI 가 각자 쓰고 종료 후 합친다

```

      첫 배치가 안건을 잘못 만들면 **회의 내내 그대로 남는다**

후    배치마다 **AI 트랙 전체를 다시 낸다.** 서버가 AI 트랙을 갈아끼운다
      → 앞 배치가 잘못 가른 안건을 다음 배치가 합친다

왜 비싸지 않나  회의당 세션이 하나다. **앞 발화는 이미 그 세션 안에 있다**
              그래서 넘기는 것은 이번 구간뿐이고, 「전체를 다시 정리해라」만 요청한다
              (지금 코드의 최종 배치는 발화 전체를 다시 싣는다 — 세션을 쓰는 의미가 없다)

        ② 매 배치마다 AI 줄 id 가 새로 생긴다

      → 합칠 재료를 만드느라 두 번 불렀다

후    재전사 스크립트 + 사람이 적은 줄 + AI 줄을 주고 **정리본 한 벌**을 받는다
      → 잔여 발화도 여기서 같이 처리된다. 전체를 다시 보니까

호출   전  회의 중 N회 + 최종 배치 1 + 통합 1
      후  회의 중 N회 + **1회**
```

**✅ MF-57 — 최종 회의록은 AI 가 쓴다**

```

어차피 사람이 그 위에서 고친다. 정리 단계가 그것이다
```

**✅ MF-54 — STT 용어 보정은 여기서 한다**

```
회의 중에는 안 만든다. **전체를 놓고 최종에서 한 번** 정정한다

두 겹이다

① STT 단계 — Soniox `context` 로 미리 준다 (상한 8000 토큰)
   context.general   회의 제목 · 프로젝트 · 참석자 · **화자 수**
   context.terms     사내 고유명사 · 제품명 — 「소니옥스」로 안 들리게
   context.text      직전 회의 요약
   → 애초에 덜 틀리게 만든다

② 최종 단계 — AI 가 **매핑표를 만든다**

   | STT 표기       | 정확 표기    | 등급      |
   |---------------|-------------|----------|
   | 소니옥스        | Soniox      | 자동 치환 |
   | 시술 프린세프   | 시술 프리셋  | 자동 치환 |

   등급 둘
     자동 치환   문맥이 확실한 제품명·시스템명 → **본문을 바꾸고** 표에 남긴다
     추정       인명 · 숫자 · 금액 · 일정, 1회 등장 → **본문은 안 건드리고** 표에만

   화자 라벨은 어떤 경우에도 안 바꾼다
   표가 곧 백업이다 — 표에 없는 치환은 하지 않는다. 그래야 되돌릴 수 있다
   회의 1건 단위다. 다음 회의로 안 넘어간다
```

**✅ MF-58 — 재전사 실패에 fallback 을 두지 않는다**

**✅ MF-59 — 최종 회의록에 업무 페이로드를 담는다**

```
「넣기」를 누르면 **입력 없이 바로 DB 에 들어간다**

액션 → 새 업무
  제목     줄 본문
  유형     AI 가 고른다 (list_work_types 조회 · 못 고르면 기본값)
  프로젝트  회의의 프로젝트
  일정     시작일 ~ 기한 — 말에 나왔으면 담고 없으면 비운다
  설명     detail
  **할일**  체크리스트 — 「A 하고 B 하고」가 말에 나왔으면 항목으로 쪼갠다
  상태     시작전 고정

업무 → 기존 업무 갱신
  taskId  조회로 확인한 것만
  변경분   기한 · 상태(done 제외) · 진행 메모 · 할일 추가

⛔ done 은 안 보낸다 — 완료 게이트에 회의록 뒷문을 만들지 않는다

**✅ MF-52 — 출력 스키마는 한 벌. 페이로드만 nullable**

```
파일 하나에 payload 를 nullable 로 둔다 — taskId 가 이미 그런 식이다(항상 있고 값이 null)

증분 배치   payload = null      회의 중에는 업무를 안 만든다
최종       payload 를 채운다    액션은 생성분 · 업무는 변경분

증분에서 payload 가 실려 오면 **서버가 버린다.** 프롬프트에도 「null 로 둬라」를 적는다
```

## 3-4. 사람이 「넣기」를 누를 때 뜨는 것

**✅ MF-67 — payload 드로어는 회의록 것이다** (2026-09-07 저녁 · MF-13 · 14 정정)

```
전    업무 탭의 새 업무 드로어 · 업무 상세 드로어에 슬롯 · 프리필 · 푸터 prop 을 얹어 재사용한다
후    **회의록 payload 드로어를 따로 만든다.** 업무 드로어는 손대지 않는다

왜    성격이 다르다
      업무 드로어    업무를 만들고 고친다 — 자동 저장 · 상태 전이 · 첨부 · 연관 · 로그
      payload 드로어  줄에 붙일 값을 적는다 — 자동 저장 없음 · 푸터 버튼 하나 · 필드는 payload 키만
      prop 넷으로 갈라 놓은 게 사실상 다른 드로어였다

F-2(시작일이 비던 문제)는   payload 에 일정을 시작 ~ 기한 둘로 두므로 다시 안 생긴다
```

**✅ MF-13 — 업무 생성 = 액션 payload 드로어** (정정)

```
필드     안건(그 줄로 고정) · 제목 · 유형 · 프로젝트 · 계획 시작 ~ 종료 · 설명 · 할일
         = payload 키 그대로. 상태 필드 없음(시작전 고정)
프리필    **MF-59 페이로드가 채운다.** 없으면 제목 = 줄 본문 · 프로젝트 = 회의 프로젝트 (MF-61)
푸터     편집 「취소 · 저장」 / 보기 「취소 · 넣기」 (MF-66)
넣기     업무 생성과 줄 갱신은 한 요청 · 한 트랜잭션. 업무 자체는 POST /api/tasks 규칙 그대로
```

**✅ MF-14 — 업무 갱신 = 업무 payload 드로어** (정정)

```
헤더     업무 셀렉터 — 누르면 업무 화면의 후보 고르기(RelationPopover) 단일 선택
         기준 프로젝트에 업무가 0건이면 기본이 「전체」로 내려간다
         (실측에서 이것 때문에 연결할 업무가 하나도 안 나왔다)
필드     기한 · 상태(todo | in_progress) · 진행 메모 · 할일 추가 · 연관 업무 · 프로젝트 · 완료 결과
         = 변경분 일곱(MF-59). 제목 · 유형 · 설명 · 시작일은 회의록에서 못 바꾼다
프리필    **MF-59 페이로드의 변경분.** 업무를 안 골랐으면 본문 비활성
푸터     편집 「취소 · 저장」 / 보기 「취소 · 넣기」 (MF-66)
넣기     한 요청 — 서버가 순서대로 반영하고 하나라도 거부되면 전부 롤백
```

## 3-5. 사람이 최종 회의록을 고칠 때

**✅ MF-60 — 줄 종류는 못 바꾼다**

```
논의 · 결정 · 액션 · 업무 를 서로 바꾸는 것을 **막는다.** 파급이 너무 크다

바꿀 수 있게 두면 딸려오는 것
  액션 → 논의    이미 넣은 업무를 지우나, 남기고 줄만 끊나
  논의 → 업무    taskId 가 없는데 업무 줄이 된다 (kind=task ↔ taskId 불변식이 깨진다)
  논의 → 액션    페이로드가 없는데 「넣기」를 눌러야 한다
  → 갈래가 계속 늘어난다

종류가 틀렸으면   그 줄을 **지운다.** 필요하면 새로 적는다

**✅ 사람이 편집 화면에서 할 수 있는 것 — 넷**

줄 수정        본문을 고친다
업무 넣기      액션·업무 줄의 페이로드를 확인하고 「넣기」 (MF-13 · MF-14)

못 하는 것     **줄 종류 바꾸기** (MF-60) · **안건 삭제** (MF-62)

**✅ MF-21 — 유형에 설명을 붙인다**

**✅ MF-25 — 카운트는 최종 회의록 기준이다**

      merged 11 · ai 9 · human 3 — 세는 대상과 그리는 대상이 달랐다

후    **화면에 그리는 그것을 센다.** 최종 회의록 한 벌이 기준이다

**✅ MF-65 — 드로어는 하나다**

```
액션 줄   → **액션 payload 드로어** 하나 (MF-13 · MF-67)
업무 줄   → **업무 payload 드로어** 하나 (MF-14 · MF-67 — 헤더에 업무 셀렉터)

AI 가 만든 줄     payload 가 차 있다 → 값이 채워진 채로 뜬다
사람이 만든 줄     payload 가 비어 있다 → 사람이 채운다 → 그 값이 payload 가 된다

**차이는 payload 있고 없고 하나뿐이다.**
필드 같고 · 저장 경로 같고 · 둘 다 「넣기」

⛔ AI 것과 사람 것으로 드로어를 나누지 않는다
⛔ 「AI 줄은 넣기 모드 · 사람 줄은 자동 저장」으로 가르지 않는다

액션·업무 드로어 둘 다 같다
⛔ 한 푸터에 셋을 두지 않는다. 모드마다 하나씩이다

**✅ MF-64 — 칩은 둘로 갈린다** (2026-09-07 저녁 정정 — 「칩 넷이 같다」 폐기)

  「액션만 적어두기」는 그대로 된다 — 「저장」이 줄을 만들고 업무는 안 만드니까 (MF-66)

서버   POST …/lines 가 액션·업무 줄에 한해 payload(업무 줄은 taskId 도)를 받는다

**✅ MF-61 — 사람이 적은 액션·업무 줄은 빈 드로어로 연다**

```
AI 가 만든 줄     페이로드가 있다 → 드로어가 **값이 다 찬 채로** 뜬다. 확인하고 넣기
사람이 적은 줄     페이로드가 없다 → 드로어가 **거의 빈 채로** 뜬다
                제목 = 줄 본문 · 프로젝트 = 회의의 프로젝트
                유형 · 일정 · 설명 · 할일은 사람이 채운다

그 줄 하나만 AI 에게 다시 물어보지 않는다 — 호출을 늘리지 않는다
```

## 3-3. 남는 것

```
track 셋은 그대로다
  human    사람이 회의 중에 적은 줄     원본
  ai       AI 가 회의 중에 뽑은 줄      원본
  merged   **최종 회의록 — 정본.** 사람이 회의 끝나고 보는 것

→ 최종이 끝나면 **AI 정리본 = 회의록**이 성립한다
```
