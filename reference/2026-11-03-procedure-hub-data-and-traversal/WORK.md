# Procedure Hub 데이터 정비와 골드·Jev 탐색 작업계획

작성일: 2026-11-03

상태: **방향 합의 · 설계 검토 단계. 데이터 이관·골드 반영·새 탐색 구현은 미완료.**

이 문서는 원장부터 데이터를 정비한 뒤 골드·Jev 탐색으로 연결하기로 한 사용자 합의와 작업 순서를 기록한다. 현재 코드의 동작 설명이나 구현 완료 보고가 아니다. 기존 SPEC/WP를 대체하는 별도 API 정본도 아니다. 후속 구현 전에 검토한 설계를 기존 정본에 반영한다.

## 1. 목표와 현재 판단

원문의 의미와 적용 범위를 보존한 실버를 만들고, 골드가 이를 손실 없이 제공하도록 한다. Jev는 질문에 필요한 탐색 대상을 선택하고 앱은 공개 근거·범위·완료 조건을 검증한다. 최종 답변 모델에는 검증된 답변 자료를 전달한다.

현재 데이터 맵이 자연스럽다는 것만으로 행별 데이터가 정확하다고 판단하지 않는다. 이미 원장→실버에서 안전정보 덮어쓰기와 고민 오연결이 확인됐다. 따라서 앱의 예외 처리나 탐색량 증가로 원천 문제를 우회하지 않고 **데이터 설계와 검수를 먼저 진행한다.**

## 3. 데이터 설계 원칙

### 3.1 실버에서 구분할 것

| 구분 | 역할 |
|---|---|
| 원문 snapshot·record | 어느 파일판의 어떤 원문 행·필드인지 고정 |
| 엔터티 | 제품·계열·단위시술·부위·기법·고민 등 대상의 identity |
| 주장 | 원천별 효과·위험·조건·설명·관계 주장과 원문 |
| 적용 범위 | 제품·계열·부위·용법·환자 조건·조합·방향·시점·한정 |
| 매핑 | 원천 표현과 엔터티 사이의 후보/확정 대상 및 근거 |
| 판정 이력 | 규칙판·검토자·사유·승인/미정·변경 이력 |
| resolution | 여러 원천 주장을 정책으로 접은 결과와 대안 |
| attachment | 검색·노출을 위해 노드에 자료를 붙인 경로와 근거 |

논리 구분이며 모두 별도 그래프 노드나 DB 테이블로 만들겠다는 결정은 아니다. 기존 엔터티 ID와 정상 구조는 유지할 근거를 확인하고, 불필요한 전면 재발급은 하지 않는다.

### 3.2 ID·메타데이터

- 이름은 표시·검색용이며 원문 행의 유일키로 사용하지 않는다.
- snapshot, 원문 occurrence, entity, claim, mapping/decision의 ID 역할을 구분한다.
- 원문 occurrence는 특정 snapshot의 file+정확한 pointer를 참조한다. 행 재정렬로 새 snapshot이 되면 다른 판의 연속성은 검증된 대응으로 연결한다.
- 출처 파일·버전/hash·정확한 원문 경로, 원문값과 정규화값, 대상·조건·확정 상태·판정 근거를 보존한다.
- missing/null/빈 배열/false의 의미를 필드별로 정한다. 정보 미기재를 무조건 적용 또는 제한 없음으로 해석하지 않는다.
- 원장에 없는 사실은 메타데이터를 추가한다는 이유로 생성하지 않는다. 확인할 질문과 미정 사유를 남긴다.
- 후보 매핑을 확정 적용으로 승격하지 않는다. attachment는 적용 승인과 다르다.
- 원문 claim과 보수적으로 계산한 resolution은 분리한다. 상충·대안·조건을 숨기지 않는다.

## 4. 골드와 Jev의 역할

```text
원장 snapshot
  → 실버: 정리·출처·주장·범위·매핑·판정 검증
  → 골드: 검증된 노드·엣지와 근거 조회
  → 질문에 맞는 시작 노드 후보
  → Jev의 다음 탐색 대상 선택
  → 앱의 골드 API 조회·근거/범위 검증
  → 필요한 답변 자료 확정
  → Claude 답변 생성·검증·전달
```

런타임 탐색의 기준은 골드다. Jev가 DB를 직접 조회하는 것이 아니라 질문·후보 정보를 판단하고, 앱이 골드 API를 호출한다. 원장은 조사·검수와 역추적의 기준이며, 실버 오류를 숨기기 위한 런타임 임의 대체 조회는 이 계획에 포함하지 않는다.

골드는 필요한 관계의 종류·방향·조건·후보/확정·원천/파생 구분, 근거 claim 및 원문 참조를 유지해야 한다. 엣지 종류·카디널리티·저장/파생 방식은 HTML 설계 검토로 확정한다. 실버의 미정이 골드에서 확정 추천으로 바뀌어서는 안 된다.

## 5. 탐색 깊이와 종료 방향

### 5.1 깊이

전체 깊이를 고정 N홉으로 정하기보다 **한 번에 1홉 후보를 열고 질문에 필요한 갈래를 이어간다.** 여기서 1홉은 노드 전이 단위다. 페이지·원문·적용 범위 메타데이터 조회는 해당 노드 근거를 완성하는 작업이며 모두 새 그래프 홉으로 세지 않는다.

Jev는 다음 후보의 질문 관련성과 추가 탐색 필요성을 판단한다. 앱은 유효한 후보·방문 장부·적용 범위·필수 자료·완료 조건을 검증한다. Jev의 종료 판단만으로 필수 안전·조건·반대 근거 미확인을 완료 처리하지 않는다. 확률 임계값과 실제 질문 계약은 구현 전 별도 검증하며 이 문서에서 수치를 정하지 않는다.

예시:

```text
팔자주름 → 시술 후보
         → Jev가 필요한 갈래 선택
         → 선택한 시술의 역할·위험·조건 확인
         → 필요한 근거와 범위가 충족되면 종료
```

시술→부작용을 조회했다는 이유로 부작용→다른 시술→다른 고민까지 자동 확장하지 않는다. 새 전이는 원래 질문의 미충족 항목에 어떤 정보를 추가하는지 설명 가능한 후보여야 한다. 정해진 깊이에 도달했다는 이유만으로 ‘정보 없음’을 출력하지 않는다.

### 5.2 종료 상태

| 상태 | 의미 |
|---|---|
| 근거 충족 | 해당 답 범위의 필수 자료·적용 범위·관련 조건/상충을 검증하여 답변 가능 |
| 관련 후보 소진 | 필요한 정보를 추가할 유효한 미방문 후보가 없음. 답변 가능 여부는 충족 장부로 별도 판단 |
| 원천·범위 미확정 | 필요한 사실/적용 범위를 끝내 확인할 수 없어 해당 주장·갈래를 보류 |
| 실행 중단 | deadline·API 오류·build 불일치 등으로 완료하지 못함. 정보 부재와 구분 |

원문 부재, 미조회, 적용 미정, 실행 오류를 같은 ‘정보 없음’으로 묶지 않는다. 부분 답변은 지원된 범위만 검증하여 제공하고 미지원 범위를 명시하는 계약으로 별도 확인한다.

### 5.3 반복·완료 검증

- 조회 장부는 build·node·section/page·fact ID·projection mode·관계 요청·답 범위를 구분한다.
- 같은 범위의 중복 조회·재방문은 막되, 새로운 명시 대상이나 제품 선택으로 scope가 바뀌면 필요한 검증을 다시 연다.
- 추천 근거 한 개 발견, slim 목록 완료, 원문 수신, 적용 검증, 최종 답 범위 완료는 각각 별도로 기록한다.
- 같은 범위의 필수 경고·조건·반대 근거는 낮은 relevance나 인용 미선택만으로 제외하지 않는다.
- 다른 제품·조합·범위의 자료는 원천/관계 증거로 구분한다. 모든 첨부 자료를 현재 답의 필수 사실로 취급하지 않는다.
- 필요한 범위가 원천상 미확정이면 이유를 기록하고 종료한다. 무관한 그래프를 계속 넓혀 해결한 것으로 만들지 않는다.

## 6. 작업 순서와 완료 기준

| 단계 | 할 일 | 완료 기준 | 현재 |
|---|---|---|---|
| 1. 조사 | 원장↔실버 fidelity·미정·ID·조건·관계 오류와 분모 확인 | 원문/실버 locator·변환 규칙·문제 분류·미확인 범위 보존 | 조사 보고 작성 완료, 전수 임상 재판정 아님 |
| 2. 설계 검토 | 엔터티별 필드·ID·scope·노드·엣지·빈값 의미 확정 | 현재→제안 대응과 미정·출처가 설명되고 필수 계약 합의 | HTML 권고안 작성, 세부 검토 중 |
| 3. 실물 설계 검증 | 실제 오류·조건·후보 사례를 새 구조로 표현 | 원문 손실0, 원문 역추적, 조건·후보·상충 보존, 참조 정합 | 지정 pilot의 ID·refs·scope·rule 독립검수 PASS. 25타입247필드 전체승인은 아님 |
| 4. 실버 수정·이관 | 확정 설계에 맞춰 생성·매핑·메타데이터 정비 | 별도 원장 대조와 구조 검수 통과, 기존/신규 대응 및 이력 보존 | 첫 candidate P0~P4 완료. P5 검증기 두 결함 보완·독립 폐쇄 검수 PASS. 원문 문맥·복수 연결 등은 HTML v2에서 별도 검토(62행152field를26주제로 묶음). 원문 의미 전수승인·정본전환 미실행 |
| 5. 골드 반영 | 실버 의미를 보존하는 노드·엣지·조회 응답 구성 | 확정/후보·범위·근거·source loss 없는 변환 및 공개 응답 검증 | 새 설계 반영 미착수 |
| 6. 탐색 연결 | Jev 노드 선택·앱 근거 수집/종료를 골드 계약에 연결 | 중복/순환/무관 확장 방지, 필수 자료 검증, 종료 상태 구분 | 새 설계 기준 미착수 |
| 7. 실제 답 검증 | 실제 자료 수신부터 생성·의미 검증·최종 전달 확인 | 질문에 유용한 답, 원문 근거/범위/조건 보존, 명확한 미확정 표시 | 새 설계 기준 미착수 |

설계 검증에는 안전 alias 충돌, 같은 이름의 다른 고민 행, singleton/n-ary, same_site 순서 조건, 다계열 제품 override, 조합 후보, 원장 scope 충돌, 언어별 한정 차이, 보수 resolution을 포함한다. Q002 하나에 맞춘 하드코딩으로 구조를 확정하지 않는다.

11-03 사용자가 계획대로 진행을 지시하여 [실물 설계 검증 브리프](../../orchestration/work/phub-recommend/silver-design-pilot-brief.md)로 3단계를 발주했다. 산출물은 `orchestration/work/phub-recommend/silver-design-pilot/`에 별도로 작성한다. **이는 검증용 데이터 작성이며 실버 정본 이관·골드 반영·서비스 활성화는 아니다.** 결과 검증 후 다음 단계로 진행하고 앱 수정으로 먼저 돌아가지 않는다.
