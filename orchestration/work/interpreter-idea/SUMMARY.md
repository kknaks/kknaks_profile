
# 작업 요약 — interpreter-idea (interpret-pwa)

기간: `2026-11-12` ~ `2026-11-16`
결과: 머지 · 배포까지 — 기록 보관 env(D-42 · 배포 12) · 통역 품질 개선(D-43 ~ D-66 · code #12 `6d57ba3` · infra #55 · 배포 13). 요금제 설계는 문서로 남김

## 1. 무엇을 했나

통키(통역 PWA) 베타에서 실장 · 중국 코디가 「토닝 번역 어색 · 울쎄라 · 써마지가 영어로 · 시술이 수술처럼 들림 · ChatGPT 가 더 자연스러움」을 전했다. 운영 통역 기록 4일치를 발화마다 평가해 원인을 갈랐다(사전 값 · 역할 모르는 번역 · 잘게 끊김 · 원문 없는 번역 · STT 인식). STT 를 v6 로 올리고, 직원 → 손님 역할 문안 · 빈 원문 막기 · 7개 언어 현지 클리닉 조사로 사전을 다시 세우고(그 나라 글자 우선), 엔진이 사전을 무시할 때를 위한 「번역 뒤 시술명 바로잡기」를 넣었다. 같은 음성 파일로 고치기 전 · 후 · 나라별(7개 언어 × 직원 · 손님 196행)을 돌려 사람 판정까지 매기고 배포했다. 앞 단계로 요금제(토큰제) 설계 문서와 통역 기록 무기한 보관(D-42)을 했다.

## 2. 적용한 기술·개념

- **번역 뒤 시술명 바로잡기** — 엔진이 사전 짝을 무시한 번역을 내보내기 직전에 사전 이름으로 갈아 끼움 → [[transcript-term-correction]]
  - 왜 이걸 골랐나: 10-27 판은 「통역은 사후 정정이 맞지 않는다 — 엔진 입력에 용어를 싣는다」로 정했다. 그런데 사전 값이 context 에 정확히 들어갔는데도 울쎄라 · 써마지 · 스컬트라 · 보툴렉스 zh 가 영문 음역 · 일상 낱말로 나왔다 — `translation_terms` 는 모델에 주는 참고(문서: 「Tell the model how…」)일 뿐 보장이 아니다. 엔진 입력 + 출력 바로잡기 두 겹으로 바꿨다. LLM 다듬기는 속도 때문에 버렸다(사용자 — 속도 우선)
  - 무엇이 어려웠나: 바꿔 끼우기가 멀쩡한 글을 망가뜨리는 길이 검수마다 새로 나왔다 — en · vi 의 일상 낱말(later → Laser), 한자 언어끼리의 같은 한자(ja 「色素」), 한글 「보톡을 → 보톡스」(조사 먹음) · 「마지막 → 써마지막」 · 「지방이 → 지방이식」. 범위를 좁히는 규칙(③ 은 비라틴 언어만 · 한자 언어 사이 제외 · 한글은 첫 음절 같음 · 남는 것이 조사일 때만 · 음절 빠짐 해석 안 함 · 멈춤 목록)을 네 번 더했다. 「일상 낱말은 틀린 꼴 목록에 넣지 않는다」가 기준이 됐다
  - 근거: `back/app/service/interpret/correct.py` · DEC D-58 · D-63 ~ D-66 · `review-wp26-code-report.md` · `review-predeploy-code-report.md` · `-2.md` · code PR #12
- **사전을 나라별 현지 클리닉으로 다시 세우기 — 그 나라 글자 우선** → [[translation-glossary-normalization]]
  - 왜 이걸 골랐나: 앞 조사는 「현지 클리닉도 영문을 쓴다」면 영문 name 을 두어, 비라틴 5개 언어에 영문 name 이 220칸이었다. 사용자 원칙(그 나라 글자 · 없을 때만 영어)대로 플랫폼(新氧 등)까지 근거로 넓혀 73칸을 현지 글자로. 근거 없는 별칭(대만 77 · zh 19 · th 17)은 뺐다
  - 무엇이 어려웠나: 별칭 하나하나 근거를 따로 조사해야 했고(r3), 「~針」 시장 이름 · 상자 색 · 여러 기기를 가리키는 말처럼 이름인지 별명인지 갈리는 칸이 처분 거리였다. 처분으로 정한 값(보툴렉스 = 레티보 = 乐提葆)을 코디가 「겹침 오류」로 잘못 읽은 적도 있다
  - 근거: `quality-r1-zh-report.md` · `quality-r2-en-ja-th-vi-report.md` · `quality-r3-tw-alias-report.md` · `r4a-zh-report.md` · `r4b-th-ja-report.md` · `quality-research-dispositions.md` §1 ~ §16 · DEC D-46 · D-53 · D-61
- **context 는 사전의 한 열을 짝으로 바꿔 보낸다 — 받아쓰기 힌트와 번역 짝은 다르다** → [[context-catalog-injection]]
  - 왜 이걸 골랐나: 역할 서술(`text`)을 줄이지 않는 칸으로 두고, 사전은 짝으로 · 한도는 실측으로 맞췄다
  - 무엇이 어려웠나: 중국어 손님 쪽이 계속 약했는데 원인은 `terms`(받아쓰기 힌트)에 **한국어 이름만** 들어 있어서였다 — 손님이 「美版超声刀」를 말하면 STT 가 소리 같은 「每晚」로 적는다. 번역 짝은 맞게 들어가 있어도 원문이 틀어지면 못 건다(다음 판 후보)
  - 근거: `back/app/service/glossary.py` `build_context` · 7차 결과 `test7c-result.json` · SPEC §4.5 · §4.6
- **같은 음성 파일 · 고정 규칙으로 전후 비교 시험** → [[golden-set-regression]]
  - 왜 이걸 골랐나: 고치기 전(v5 · 사전 `.6`)은 v5 제거일(12-15) 전에만 돌릴 수 있어서 먼저 고정했다. TTS 로 만든 음성 · 규칙 파일(글자 그대로 · 정규식 · 발화 수 · 사람)을 돌린 뒤엔 안 바꿈
  - 무엇이 어려웠나: 기계 판정이 사람 판정과 자주 갈렸다(새 음역 `Ulsera` 를 놓침 · 맞는 문장에 정규식이 걸림). 기계는 「사전 이름이 있나」만 보고 뜻은 사람이 매기는 두 숫자로 갔다. 합성 음성이 영문 상표를 이상하게 읽어 손님 쪽 「인식」 실패가 부풀었다 — 실기기 확인이 남음. 시험 목록이 기록에서 뽑혀 zh · en · ja 뿐이었던 것을 사용자가 짚어 7개 언어 × 직원 · 손님으로 넓혔다
  - 근거: `back/scripts/quality_check.py` · `test7.py` · `wp22-be-report.md` · `wp24-be-report.md` · `wp27-be-report.md` · `wp22-human.json` · `wp24-human.json`
- **context 한도를 모델마다 다시 재기** → [[empirical-limit-probing]]

## 3. 막혔던 것 / 사고

- 처음 세운 시험 목록이 통역 기록에서 뽑혀 3개 언어뿐이었다 → 사용자가 「각 나라별로 테스트 하라고」 지적 → 7개 언어 × 직원 · 손님 · 같은 시술 9개로 다시 짬. 사전을 7개 언어로 고쳤으면 시험도 7개 언어여야 한다
- 이 세션이 원래 코디가 아니었는데 같은 워크트리에 원 코디 세션이 살아 있었다 → 발주 직전 `terminal list` 로 발견 → 사용자 확인 뒤 이 세션이 넘겨받고 `_RESUME` · Run 을 갱신
- 워커 터미널이 여러 번 죽었다(planner · reviewer · researcher) — `stable_pane_required` · `no recognized agent` 로 dispatch 거절 → 새 터미널 + 같은 브리프로 다시 발주. 브리프 · 리포트를 파일로 둔 덕에 끊김 없음
- 코디가 근거 요약만 보고 결정해 틀렸다 — 「대만은 세대별 이름뿐」 요약으로 써마지 zh-Hant 를 영문으로(D-51) → 사용자가 짚어 원 리포트에 대만 2곳 근거 확인(D-60). 「레티보 · 보툴렉스 겹침 오류」도 처분 문서를 안 읽고 말했다가 정정
- 공개 레포에 통역 기록 문장 조각을 BASE · DEC 에 적었다 → 문서 검수가 짚음 → 서술로 바꿈
- 바로잡기 위험이 검수마다 새로 나왔다(§2) — 테스트는 초록인데 계약이 깨진 자리를 리뷰어가 직접 함수에 넣어 찾았다
