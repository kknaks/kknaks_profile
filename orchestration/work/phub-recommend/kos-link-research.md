## 1. KOS 카탈로그 구조

### 1-1. 수집 방법(읽기만 · 값 기록 안 함)

- **auth**: API Key(.env KOS_API_KEY · 구 이름 KOS_API_tenent 도 지원)를 POST /open/authorization/commands/exchange-token 으로 교환 → 받은 토큰을 Authorization 헤더에. 토큰 직접 입력(KOS_AUTH_TOKEN)도 됨. 키 · 토큰은 저장 · 출력 안 함(수집기 규칙)
- **base**: 운영 open-api.kos-solution.com · 개발 open-api.kos-solution.dev
- **calls**: 조회 전용(POST …/queries/…) · 허용 경로는 kos_query_catalog.py(공식 스펙 2026-09-18 SHA 고정)만 · 쓰기 API 차단
- **reference_group**: getCategories · getProducts(옵션 포함) · getTargetCountries · getMachines · getMedicalServices · getMedicines · getProcedures · getReservationGroups · getReservationRuleSummaries · getZones — 요청 본문 {} · 현재 설정 1회 조회
- **raw_rule**: 응답 바이트 그대로 저장(파일 600 · 폴더 700 · manifest.json 에 해시) · Git 제외

### 1-2. 엔드포인트 · 칸 · id 관계

```text
getCategories (16)  id · name · opened · order · translsMap(ko/en/ja/zh)
   ▲ categories[] (상품 1개 = 카테고리 1개, 129 중 128)
getProducts (129 = 이벤트 59 + 일반 70)  id · title · description · caution(s) · isEvent · displayPeriod · offeringPeriod · medicineAndMachines[]
   └ options[] (454 = SINGLE 417 · GROUP 37)
        id · title · type · count(회차: 1=337 · 3=19 · 5=59 · 10=2 · GROUP 은 없음) · displayChannels[] · price{amount · additional[visitorType 「이벤트가」] · VAT}
        ├ SINGLE → procedure{id,name}            ── getProcedures 의 id
        └ GROUP  → compositions[] (2~11개)       ── 한 줄 = medicalService 1 + procedure + unit{type,value} + count + price
                                                   (refSingleOptionId 104 중 0 채움 — SINGLE 옵션으로 되돌아가는 링크 없음)
getMedicalServices (316 · 모두 PUBLISHED · 모두 비급여)  id · title · description · configuration{
        code · procedure{id,name} (꼭 1) · medicines[] (0~1) · machines[] (0~1) · unit{type,value} · taxation }
   ▲ 시술 하나에 진료 항목 1~17개(예: 같은 시술 × 톡신 4종 · 샷 수 · 용량)
getProcedures (1626) · getMedicines (354) · getMachines (307)   id · name 뿐 (부위 · 계열 · 제품 칸 없음)
```

- 진료 항목 단위 칸(`unit.type`): CC 71 · None 137 · UNIT 48 · VIAL 1 · PULSE 5 · SHOT 21 · KJ 21 · QUANTITY 9 · SYRINGE 1 · MINUTE 2 — 용량 · 샷 · 에너지 · 개수가 허브엔 없는 「판매 단위」 축.
- 진료 항목 약제 · 장비 꼴: 약제1·장비0 193 · 약제0·장비1 104 · 약제0·장비0 18 · 약제1·장비1 1.
- 노출 채널: GANGNAMUNNI+HOMEPAGE+KOS_CONNECT 135 · HOMEPAGE+KOS_CONNECT 2 · HOMEPAGE 317 · 이벤트가(추가 가격) 있는 옵션 58.
- SINGLE 옵션은 진료 항목 id 를 안 가진다(procedure 만) → SINGLE 옵션의 제품 · 용량은 「같은 procedure 의 진료 항목」으로만 짐작 가능(옵션 제목에만 있음). GROUP 구성 줄은 진료 항목을 직접 가진다.

## 2. 연결 분류(전수)

### 2-1. 분류 기준(결정론 · 추정 금지)

| 분류 | 뜻 | 판정 규칙 |
|---|---|---|
| 1:1 | KOS 하나 = 단위 시술(제품) 하나 · 이름도 허브 노드 이름 조합 | 단위 시술 1 · 제품 없음 · 남은 낱말 없음 · 동의어 안 거침 |
| 이름만 다름 | 같은 것인데 허브 동의어(시술 · 부위)로만 닿음 | 단위 시술 1 · 동의어 경유 |
| 가늚 | KOS 가 단위 시술보다 좁음 — **제품 고정**(허브 단위 시술은 제품 무관) 또는 허브 사전 밖 낱말(좁은 부위 · 규격) | 단위 시술 1 + 제품 1 이상, 또는 남은 낱말 |
| 굵음 | KOS 하나 = 단위 시술 여럿(상위 부위 · 「주름」 · 장비 하나가 여러 부위) | 단위 시술 2+ · 남은 낱말 없음 |
| KOS만 | 허브에 없음 — (a) 계열 · 제품은 있으나 그 부위 · 그 제품의 단위 시술 없음 (b) 허브 사전에 아무것도 안 걸림 | 단위 시술 0 |
| 판단 불가 | 후보가 갈리는데 고를 근거가 이름에 없음 · 사전 밖 낱말이 범위를 좁힐 수 있음 · 사전 충돌 | — |

매칭 방식: 결정론 — ① 이름 정규화(공백 제거 · 소문자) 후 시맨틱 사전 정확 일치 ② 실패하면 최장 일치 분절: 부위(3단계 노드 이름 · 동의어) · 계열 · 제품 · 단위 시술 표현 — 한 글자 부위는 사전 밖 글자와 붙으면 안 씀 · 고민/목적/기법만 가리키는 표현은 연결에 안 씀 ③ 단위 시술 = 사전 직접 대상 ∪ 제품의 5단계 연결(stored_units · 없으면 상속 후보) → 부위로 거름, 없으면 계열 × 부위로 5단계 키 조합 ④ 시술 이름으로 못 맞추면 진료 항목(제목 · 약제 · 장비)이 단위 시술 하나를 직접 가리킬 때만 그걸 씀 ⑤ 남은 글자(허브 사전 밖 낱말)는 leftover 칸에 그대로 — 추정으로 채우지 않음

## 3. 연결 층 모델 추천(병원 무관)

> 허브(병원 무관 지식) ↔ 병원 상품(병원마다)을 연결 층 하나로만 잇는다. 허브는 병원 데이터로 바뀌지 않는다(사용자 10-30).

```text
[병원 원천]  KOS · 다른 병원 시스템 · 엑셀
     │  L2 어댑터(원천마다 1개 · 필드 매핑만 · 병원 고유 이름 규칙 없음)
     ▼
[L1 병원 상품 표준 꼴]  clinic → offer(상품) → offer_option(옵션: 회차 · 가격 · 이벤트가 · 채널) → offer_item(구성 한 줄: 시술 · 약제 · 장비 · 양)
     │  결정론 매칭(허브 사전 버전 고정)
     ▼
[L3 clinic_link]  (clinic_id, source_kind, source_id) → hub 정본 id 0..N · relation · match_method · leftover · confirmed_by
     │  읽기만
     ▼
[허브]  semantic.json 사전 · ids.map · 실버(단위 시술 · 제품 · 패키지) — 병원 데이터로 안 바뀜
```

### L1 병원 상품 표준 꼴(병원 무관) — 위치: 앱(상담 앱 백엔드)

- `clinic`: clinic_id · source(kos|excel|…) · snapshot_at
- `offer(상품)`: clinic_id · offer_id(원천 id) · title · categories[] · is_event · display_period · channels[]
- `offer_option(옵션)`: offer_id · option_id · kind(single|bundle) · title · sessions(회차) · price · event_price[] · channels[]
- `offer_item(옵션 구성 = 판매 단위 한 줄)`: option_id · service_id(원천 진료 항목 id) · procedure_ref{source_id,name} · medicines[]{source_id,name} · machines[]{source_id,name} · amount{value,unit(cc|unit|shot|kj|pulse|vial|quantity|minute)} · count
- **basis**: KOS 꼴: getProducts(상품) → options(SINGLE: procedure 1 · GROUP: compositions[] = 진료 항목 + procedure + 약제/장비 + unit + 가격) · getMedicalServices(진료 항목 = 시술 1 + 약제/장비 0~1 + 단위) · getProcedures · getMedicines · getMachines(id · name 만)

### L2 소스별 어댑터 — 위치: 앱

- **rule**: 원천 하나당 어댑터 하나 — KOS 어댑터가 첫 번째. 다른 병원 시스템 · 엑셀도 L1 꼴로만 내보낸다. 어댑터에 병원 고유 이름 규칙 없음(필드 매핑만)
- KOS → `offer`: getProducts[]
- KOS → `offer_option`: getProducts[].options[] (type SINGLE→single · GROUP→bundle · count→sessions · price.additional[visitorType]→event_price · displayChannels→channels)
- KOS → `offer_item`: SINGLE: option.procedure (+ 같은 procedure 의 getMedicalServices 행들) · GROUP: compositions[] (medicalService · unit · count)

### L3 연결(링크) 테이블 — 위치: 앱 — 허브 밖. 허브 id 는 읽기만(semantic.json ids.map 정본 id)

- `clinic_link`: clinic_id · source_kind(procedure|medicine|machine|service) · source_id · source_name · hub_kind(unit_procedure|product|family|package|none) · hub_id · relation(1:1|이름만 다름|가늚|굵음|KOS만|판단 불가) · match_method(사전 정확|사전 조합|진료 항목 경유|사람 확인) · dictionary_version(semantic.json version) · confirmed_by(null|사람) · leftover(사전 밖 낱말)
- **cardinality**: 원천 1 → 허브 0..N (굵음 = N행 · 가늚 = 1행 + qualifier(제품 · 규격 · 좁은 부위) · KOS만 = hub_kind none). 허브 1 → 원천 0..N(병원마다 · 한 병원 안에서도 제품별로 여럿)
- **direction**: 조회는 양방향: ① 허브 → 병원(추천 단위 시술 → 이 병원이 파는 상품 · 옵션 · 가격) ② 병원 → 허브(상품 → 설명 · 안전 정보). 저장은 원천 → 허브 한 방향(원천 행이 키)
- **refresh**: 병원 카탈로그 새 스냅샷 → 어댑터 → L1 → 결정론 매칭 재실행(같은 사전 버전이면 같은 결과). 사람이 확인한 행(confirmed_by)은 원천 id 가 그대로면 유지, 원천 이름이 바뀌면 재확인으로 내림. 사전 버전이 바뀌면 전체 재매칭 + 차이만 보고

- **왜 허브 밖인가**: 허브에 두면 병원 수만큼 허브가 커지고 병원 상품 변경이 허브 버전을 흔든다 — 「허브는 병원 데이터로 안 바뀐다」와 충돌. 허브는 사전 · id 만 제공(이미 있는 MCP/REST 조회 + semantic 사전), 연결 층은 앱 소유
- **명동점은 첫 시험 대상**: 위 셈 · 매칭률은 명동점 것이지만 매칭 규칙엔 명동점 이름이 없다(정규화 · 허브 사전 · 5단계 제품 연결만). 다른 병원은 L2 어댑터만 새로 쓰면 같은 매칭이 돈다.

## 6. 한계

- 매칭은 이름 문자열만 — KOS 에 부위 · 제품 칸이 따로 없어(시술은 id · name 뿐) 이름에 없는 정보는 못 맞춤
- 허브 사전에 없는 낱말은 leftover 로 남김(추정 안 함)
- 「가늚 — 제품 고정」은 허브 쪽 단위 시술이 제품 무관이라 생기는 구조 차이(허브 결정 그대로)
- 상속 후보(5단계 inherited_candidates)는 허브가 계산해 둔 값을 그대로 씀 — 제품 → 단위 시술이 여럿이면 굵음
- 명동점 고유 이름 규칙 없음 — 같은 스크립트를 다른 병원 L1 에 그대로 돌릴 수 있음(규칙은 허브 사전 · 정규화뿐)
