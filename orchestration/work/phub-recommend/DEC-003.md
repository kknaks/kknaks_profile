# 제조사 · 제품/장비 · 규격 원장 + 식약처 원천

**정한 것.** 실버에 원장 셋을 더한다. **제조사**, **제품·장비**, **규격**이다. DEC-002 의 단위 시술(무엇을 × 어디에 × 어떻게)은 그대로 둔다.
**시술 1회 = 단위 시술 + 제품 + 규격·양**으로 정의하고, 가격은 이 조합에 붙인다.
제품·장비의 공식 정보는 **식약처 공개 허가 정보**에서 가져온다. 의약품은 의약품 제품 허가정보, 의료기기는 의료기기 품목허가 정보를 쓴다. 매칭 결과는 출처를 달아 승인 게이트를 거친다.
식약처 데이터는 두 길로 받는다. Hub 적재 스크립트는 API 응답을 브론즈에 그대로 저장한다(LLM 없음). 작업용 조회 MCP 는 프로필 `reference/` 에 직접 만든다.
부위가 없는 시술은 이렇게 채운다. 수액·정맥은 「전신」 + 「정맥 주사」, 그 밖에 원천에 부위가 없는 필링 등은 「얼굴 전체」가 기본값이다.
분류표 1차 검수의 반려 296건은 다섯 유형으로 나눠, 유형마다 처리 경로를 하나씩 정했다.

> 결정의 정본은 `_RESUME.md` §2 의 2026-10-27 행 가운데 다음 넷이다: 「실버에 제조사 · 제품/장비 · 규격 원장 추가」, 「식약처 공개 허가 정보로 확인 · 부위 없는 시술 · 반려 ③」, 「식약처 조회 MCP 작업용 reference」, 「분류표 1차 검수」. 이 문서는 그 넷을 풀어 쓴 것이다.
> **스키마 · 테이블 · API 필드 설계는 하지 않는다.** 아래 필드 표의 「원천」 칸은 *원천에서 기대하는 값*이다. API 응답 필드는 다음 단계 1~2(실호출 → 응답 필드 확인)에서 확정하고, 저장 모양은 SPEC 이 정한다.
> 원천 근거는 stg 저장본 `phub-stg-2026-10-26/`(2026-10-26 수집)만 읽었다. stg 와 식약처 API 는 부르지 않았다.

## Context

- 관련 입력
  - DEC-002: 단위 시술 정의(D-02), 축별 자리(D-03: 제품·용량은 속성, 제품 노드는 「쓰는 제품」 엣지), 이름 원칙(D-04), 부위 트리(D-05)
  - `taxonomy-classify.json` · `.md`: 521 항목 가운데 제품 183 · 장비 157(합 340). §10 미결 9건
  - 분류표 1차 검수 답(사용자, 2026-10-27): 승인 225 · 반려 296
  - 원천 `phub-stg-2026-10-26/`
    - `products.json` v1.2: 제품 59건. 필드는 name · name_en · manufacturer · country · mfds(True 35 · False 6 · 없음 18). 「유통사 아닌 제조사 기준」 매핑이고 제조사 이름은 39가지다
    - `taxonomy.json`: 제품 정보가 따로 된 필드로 있지 않다. 제조사는 `detail` 문자열에만 적혀 있다(예: M2 「이브아르」 → 「LG화학」). 그 밖의 필드는 6건에만 있는 표시(`is_marketing_name` · `naming_caveat` 등)와 1건의 `verification_needed`(톡스온 「식약처 허가 정보 미검증」)뿐이다
    - `market-pricing.json`: 17개 시술군에 122 항목. 항목마다 name · unit · low/mid/high 가 있다
  - `reference/2026-10-27-mfds-mcp/NOTES.md`: 오늘 남은 **부분 실호출 기록**. 의료기기 품목허가와 의료기기 수입·제조허가 상세는 「사용 가능」, 의약품 제품 허가정보는 「키 미등록」으로 적혀 있다. 이 DEC 는 이 기록으로 필드를 확정하지 않는다. 기대값 칸에 참고로만 인용한다
- 문제
  - 분류표 반려 가운데 가장 큰 유형은 「제품·장비 정체 확인 불가」다(137 · 아래 D-06). taxonomy 와 products.json 만으로는 공식 품목명 · 제조사 · 성분 · 허가 여부를 확정할 수 없다
  - 제조사 표기가 원천마다 다르다. taxonomy detail 은 「엘러간」, products.json 은 「앨러간/애브비」다. 제품 이름도 다르다. taxonomy 는 「리즈톡신」, 반려 사유에 적힌 공식 품목명은 「리즈톡스」다
  - 가격은 단위 시술 하나에 붙지 않는다. 시장가 항목은 「팔자주름 (HA 1cc)」, 「써마지 FLX (눈가 450샷)」처럼 부위 · 제품 · 양이 한 줄에 함께 들어 있다
  - 부위가 없는 단위 시술 후보(수액 · 필링)가 반려됐다(47건)
- 결정이 필요한 이유: 분류표 재판정과 SPEC-001 개정(DEC-002 D-08)에 앞서, 제품·장비를 무엇으로 확인하는지와 반려를 어떻게 처리하는지를 정해 둔다

## Options

| Option | Description | 판단 |
|---|---|---|
| A | 제품 정보는 원천(taxonomy detail · products.json)에서만 가져온다 | **기각** — 반려 ①의 원인이다. 원천 자체가 「식약처 허가 정보 미검증」이라고 적어 둔 항목도 있다(톡스온 `verification_needed`) |
| B | 식약처 공개 허가 정보를 공식 원천으로 쓰고, 매칭 결과를 승인 게이트에 올린다 | **채택** — `_RESUME` §2 10-27 「식약처 공개 허가 정보로 확인(출처 기록 · 승인 게이트)」 |
| C | 웹 검색이나 LLM 으로 제품 정체를 채운다 | **기각** — Hub 에는 LLM 이 없다(DEC-001 D-12). 이름 매칭에도 모델을 쓰지 않는다 |

## Decision

| ID | 결정 | 근거 |
|---|---|---|
| D-01 | **원장 셋을 실버에 더한다** — 제조사 · 제품/장비 · 규격. 필드는 아래 「원장 필드」 표(제조사 5 · 제품/장비 10 · 규격 3). 필드 표에는 「뜻 · 원천 · 필수 여부」만 적는다. 테이블과 컬럼 설계는 SPEC 이 맡는다 | `_RESUME` §2 10-27 「실버에 제조사(…) · 제품/장비(…) · 규격(…) 원장 추가」 |
| D-02 | **시술 1회 = 단위 시술 + 제품 + 규격·양.** 가격(시장가 low/mid/high)은 단위 시술이 아니라 이 조합에 붙는다. 이 조합이 DEC-002 D-03 의 「제품 · 용량은 속성」 자리를 채운다. 예는 아래 「D-02 예시」 | 같은 행 「시술 1회 = 단위 시술 + 제품 + 규격·양, 가격은 그 조합에」 · `market-pricing.json` 항목 모양 |
| D-03 | **공식 정보 원천 = 식약처 허가 정보.** 의약품(톡신 · 수액 성분 · 약)은 **의약품 제품 허가정보**(data.go.kr 15095677)로 확인한다. 의료기기(필러 · 스킨부스터 · 실 · PLLA · 장비)는 **의료기기 품목허가 정보**(15057456)로 확인하고, 업체 정보는 **의료기기 수입 및 제조허가 상세**(15073895)를 보조로 쓴다. 매칭 결과는 원장 행마다 **출처**(API · 조회 조건 · 응답 식별값)를 달아 **승인 게이트**에 올린다. 게이트 규칙은 분류표와 같다: 승인된 것만 다음 단계로 가고, 반려는 사유를 붙여 재작업한다 | `_RESUME` §2 10-27 「제품·장비 공식 정보는 식약처 공개 허가 정보로 확인(출처 기록 · 승인 게이트)」 · 같은 날 「승인 게이트」 행 |
| D-04 | **식약처 데이터는 두 갈래로 받는다.** ① **Hub**: 적재 스크립트가 API 를 직접 부르고 응답을 **가공 없이 브론즈에 저장**한다. 실버 원장(D-01)은 이 브론즈에서 결정론으로 만든다. LLM 은 쓰지 않는다(DEC-001 D-12). ② **작업용 MCP**: 프로필 `reference/2026-10-27-mfds-mcp/` 에 직접 만든다. 원장 초안 작성과 재판정 때 코디와 워커가 조회하는 용도다. 키는 env(`.env` 의 `MFDS_API_KEY`)로만 넣고, 응답 캐시는 gitignore 한다. 이 레포는 public 이다. 상담 에이전트 단계에서는 **DUR**(병용 · 임부 · 연령 금기, 15059486)도 이 MCP 로 조회한다 | `_RESUME` §2 10-27 「식약처 조회 MCP 를 작업용으로 직접 만든다 — 위치 프로필 reference/(…) tool 후보: 의약품 허가 · 의료기기 품목허가 · 의료기기 업체 · DUR」 · `reference/2026-10-27-mfds-mcp/.gitignore`(`.env` · `cache/` 확인) |
| D-05 | **부위 없는 시술** — 수액 · 정맥 시술은 부위 **「전신」** + 기법 **「정맥 주사」**로 둔다. 원천에 부위가 없는 필링 등은 부위 기본값 **「얼굴 전체」**로 둔다. 「전신」은 DEC-002 부위 트리의 바디 하위 노드를, 「얼굴 전체」는 얼굴 하위 노드를 그대로 쓴다. 다만 기존 「전신」 노드는 원천 근거에 레이저 제모처럼 몸 표면 전체를 가리키는 뜻도 함께 들고 있다. 이 차이는 OQ-306 으로 남긴다 | `_RESUME` §2 10-27 「부위 없는 시술: 수액·정맥 = 부위 「전신」 + 기법 「정맥 주사」, 원천에 부위 없는 필링 등 = 기본 「얼굴 전체」」 · DEC-002 부위 트리 |
| D-06 | **1차 검수 반려는 유형별로 처리한다.** ① 정체 확인 불가 → 식약처 원장(D-01 · D-03)을 만든 뒤 재판정 ② 부위 없음 → D-05 로 재판정 ③ 판정 틀림(사유에 고칠 값이 적혀 있음) → 적힌 대로 고쳐 재승인 ④ 분류 경계 → OQ 로 모아 사용자가 결정 ⑤ 참고 자료(링크 · 허가 정보 붙임) → 해당 원장 행의 근거로 쓴다. 건수는 아래 「반려 유형별 건수」 | `_RESUME` §2 10-27 「분류표 1차 검수」 · 「반려 ③(고칠 값 명시)은 적힌 대로 고쳐 재승인」 |

## 원장 필드

> 「원천」 칸은 *기대값*이다. 브론즈 파일 이름은 이번에 읽은 stg 저장본 기준이다. API 항목명은 다음 단계 2(응답 필드 확인)에서 확정한다.
> NOTES.md 에 이미 보이는 이름은 괄호 안에 「NOTES」로 표시했다. 그것도 아직 확정이 아니다.
> 「필수」는 원장 행이 승인 게이트에 오르기 위한 조건이다. 값이 없으면 빈칸으로 두고 그 행은 미결로 남긴다. 추정해서 채우지 않는다.

## Rationale

- 판단 기준: 공식 정보는 한 곳에서, 결정론으로, 출처를 달아 가져온다. 원천 셋(taxonomy · products.json · 시장가)은 표기가 서로 다르고, 스스로 「미검증」이라고 적은 항목도 있다. 그래서 어느 원천도 공식값이 될 수 없다(Option A 기각)
- 식약처를 고른 이유: 국내 허가가 제품 정체(품목명 · 업체 · 성분 · 허가번호)를 하나로 묶어 주는 공개 원천이다. 허가 구분(의약품 / 의료기기)이 곧 어느 API 를 볼지를 정한다(D-03)
- 두 갈래(D-04)로 나눈 이유: Hub 는 응답 원본을 브론즈에 보존해 다시 만들 수 있어야 한다(메달리온). 반면 원장 초안 작성과 재판정은 사람과 워커가 그때그때 조회하는 일이라, Hub 에 넣지 않고 작업용 도구로 둔다
- 가격을 조합에 붙이는 이유(D-02): 시장가 항목 한 줄이 이미 부위 · 제품(또는 등급) · 양을 함께 담고 있다. 단위 시술에 붙이면 「1cc 와 2cc」, 「수입과 국산」의 가격 차이를 담을 자리가 없다
- 리스크
  - NOTES 에 따르면 의료기기 품목허가의 품목명은 일반명칭이고, 브랜드는 모델명에 있을 때만 잡힌다. 그래서 브랜드 이름만으로는 매칭이 안 될 수 있다. 의약품 API 는 아직 키 승인 전이다. 매칭 방법이 정해지기 전에는 원장 초안의 규모를 짐작할 수 없다
  - ① 137건 가운데 식약처에 없는 이름(병원 마케팅명 · 화장품 계열)이 얼마나 되는지 모른다. 원장 초안이 나와야 알 수 있다
