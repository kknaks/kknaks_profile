## ⛔ 2. OQ 규칙 — 막지 않는다. 근거를 요구한다

**OQ 를 0 으로 맞추려고 구멍을 덮지 마라.** 진짜 구멍은 반드시 올려라. 대신 **가짜 OQ 를 쓰지 마라.**

| 종류 | 무엇 | 처리 |
|---|---|---|
| **가짜** | ① 기획·정책·다른 DEC·기존 SPEC 에 답이 있는데 못 찾음 ② **SPEC 이 정하면 되는 것** — API 경로·요청/응답 필드·에러코드·검증 규칙·수치·화면 조립 | **쓰지 마라. SPEC 이 채운다** |

**업무 상세 드로어(SPEC-003 U-3)와 이 회의록 상세 페이지를 합쳐 U-n 으로 신설해라.** 새 시안이 필요 없다.

**정책이 이미 닫아 놓은 것 — OQ 로 올리지 마라**
- **종료 파이프라인**(§4 L101): 종료 → 「회의록 생성중」 스피너 → ① 마지막 배치(AI 탭 **전체 재정리** = 로그성 기록) → ② **통합본 생성(회의록 탭 = 정본)**. 통합본 줄은 **AI 줄의 타임스탬프를 물려받아 근거 칩을 갖는다**
- **통합 규칙**(§4 L102): **사람 줄 우선.** 같은 내용이면 **사람 문장 그대로 쓰고 AI 줄에서 근거 타임스탬프만 가져온다.** AI 트랙에만 있는 내용은 **추가로 붙인다.** **AI 가 사람 문장을 다듬거나 바꾸지 않는다**
- **중복 판정은 유사도 임계값이 아니라 구조로**(DEC-003 OQ-7 L180): `sourceHumanLineId` 계승 + **본문 글자 일치 검증** + **한 사람 줄의 이중 계승 금지**
- **통합본 재생성 없음.** 정상 생성분은 편집으로만 고친다. **「다시 생성」은 실패 상태에서만** 노출(§4 L103)
- **줄 종류 4종**(논의·결정·**업무**·액션). 디자인 시스템 [09] L668~672 에 규격: 업무 줄 = 라벨 `#5F6470` + 유형 배지 + **「업무 갱신」 버튼**, 액션 줄 = `#4B52A8` + **「업무 생성」 버튼**(DEC-003 §1 L49~54)
- **업무 갱신 허용 필드**(§4 L99): **기한** = `due_date` · **상태** = 상태 전이(**완료로 가면 완료 게이트 통과 필요**) · **note** = 업무 **메모에 새 항목 추가**
- **업무 상태 변경은 `PATCH /api/tasks/{id}/status` 하나만 지난다.** 일반 PATCH 에 `status` 를 실으면 **422**. **회의록 쪽에 판정 코드를 두지 마라**(DEC-003 §1 L50 · SPEC-004)
- **같은 상태로의 전이는 409** — 이미 완료인 업무를 완료로 보내면 사용자에게 에러가 보인다(SPEC-004 L478). 화면이 그 요청을 내지 않게 설계해라
- **삭제**: 소프트 딜리트 + 모달. **녹음 원본은 지우지 않는다**(§4 L104 · §6 L124)
- **종료된 회의록 조회**: **회의록 탭 = 통합본, AI 탭 = 마지막 배치 결과**(§5 L113)
- **연관 업무 검색**은 내 업무가 제공(BASE-003 인바운드 L84)

**DEC-003 §7 이 열거한 실패만 처리한다**
```
마지막 배치 실패     → AI 탭은 회의 중 증분 상태 그대로 유지(버리지 않음)
통합본 생성 실패     → 자동 재시도 2회 → 실패 시 스피너 걷고
                       회의록 탭에 **사람 원본 노출** + 「통합 정리 실패 · 다시 생성」 배너
스피너 타임아웃      → 무한 대기 금지. 시간 초과도 실패로 처리
```
**재시도 2회·타임아웃 값은 SPEC 이 정한다**(§7 L141). 묻지 마라.
「생성중」 화면은 **스피너 + 단계 문구 + 사람 원본 노출 + 편집 잠금**, 실패 배너·「다시 생성」은 **`ended` + 실패 표시 조합에서만**(DEC-003 OQ-2 L175).

**SPEC-006·007 이 정한 계약을 물려받는다.** **그 파일들을 고치지 마라.** 어긋나면 §7 에 적어라(코디가 맞춘다).

## 6. 산출물 구조

SPEC-003·004 와 같게 —
```
1. Context (Meta · Business Requirement · Scope)
2. UX Contract (Placement + U-1..U-n)
3. Scenarios
4. Data Contract (API 표 · Request/Response · Validation · Case Matrix)
5. Flow (mermaid)
6. Acceptance
7. Open Questions   ← §2 규칙. 그리고 「시안에 있으나 기획에 없어 제외」 목록을 여기에
8. 근거 표
```

**§2 규칙**
- 화면 하나 = U-n 하나. **값마다 시안 줄 번호**를 단다
- **상태 · 문구 · CTA · 기대 결과** 넷을 반드시 쓴다
- 시안에 있어도 기획·정책에 없으면 U-n 에 담지 않는다

**§4 규칙**
- **화면에 나오는 모든 값의 출처를 정의한다.** 컬럼이 없으면 「ERD 변경 필요」로 명시한다(OQ 아님)
- **에러코드는 SPEC 이 정한다.** 다만 Case Matrix 의 행마다 **기획·정책의 어느 실패인지** 근거를 단다.
  DEC-003 §7 이 열거한 실패 밖의 것을 만들지 마라 — **「설계한 것 이외의 에러는 그대로 터뜨린다」(BASE-003 L43)**
- **fallback 을 만들지 마라**
