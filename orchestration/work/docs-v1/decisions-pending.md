## ~~① 웜스타트를 언제 하나~~ — 위에서 닫힘 (원문 보존)

### 지금 무슨 일이 벌어지나

`POST /api/meetings/{id}/start` 가 이렇게 돈다(`meeting_service.py:464`).

```
① scheduled → recording 전이를 쓴다
② service 안에서 session.commit()          ← 여기가 문제
③ open-kknaks 에 웜스타트를 제출한다(수 초~수 분)
④ 새 세션에서 ai_session_id 를 UPDATE 한다
```

**②가 아키텍처 규약 두 줄과 동시에 부딪힌다.**

```
BE §2 표   service — commit() 금지
BE §7 표   외부 호출 — 읽기 → (커밋) → 외부 호출 → 새 세션에서 쓰기
           수 분짜리 외부 대기가 커넥션과 락을 잡고 있으면 안 된다
```

**§7 이 「커밋하라」고 하는데 §2 는 「service 는 commit 하지 않는다」고 한다. 누가 커밋하는지가 안 적혀 있다.**

### 그리고 실패했을 때가 안 정해져 있다 (D-2)

③이 터지면 회의는 이미 `recording` 인데 `ai_session_id` 가 없다.
**DEC-003 §7 실패 목록에 이 상황이 없다.** BASE-003 L43 대로 전파하면 사용자는 500 을 보는데 회의는 시작돼 있다.

> 지금은 compose 에 Redis·worker 가 없어서 **항상** 이렇게 된다(D-8). 그건 이번 수정에서 닫는다.

### 갈림길

**A. 웜스타트를 백그라운드로 민다**

```
/start 는 전이만 하고 바로 응답한다
웜스타트는 배치처럼 백그라운드 태스크로 나간다

- DEC-003 §STT 가 「웜스타트(결과 무시)」라고 이미 적었다 — 응답을 기다릴 이유가 없다
- service 가 commit 할 일이 없어진다 → W-1 이 같이 닫힌다
- 실패하면 첫 배치가 세션을 새로 만들면 된다 → D-2 도 닫힌다
- BE §7 「백그라운드 job — 단계마다 세션을 새로 열고 그 단계 끝에 commit」 규약을 그대로 탄다
```

**B. 지금 구조를 두고 규약에 예외를 명시한다**

```
BE §2 에 「외부 호출 앞의 커밋은 예외」를 적는다
D-2 는 별도로 정한다 — 웜스타트 실패 시 recording 을 되돌릴지, 두고 갈지
```

**코디 의견: A.** 정책이 이미 「결과 무시」라고 적었고, A 는 W-1·D-2 를 함께 닫는다.
다만 **아키텍처 규약을 바꾸는 일이라 사용자 확인이 필요하다.**

## ④ 종료 후 **async 재전사**로 통합본을 만든다 — 사용자 제안 (2026-09-07)

### 제안

통합본을 만들 때 **마지막 녹음 파일로 Soniox async API 를 호출**해 전사·화자 분리를 다시 받고,
그 결과로 통합본을 만든다. 지금은 실시간 스트림 결과를 그대로 정본으로 쓴다.

### 왜 맞는가

```
① 통합본이 정본이다
   BASE-003 L39 「회의록 탭 = 통합 정리본(사람은 회의 끝나고 이것만 볼 거라고 확신해)」
   그 정본을 실시간 정확도로 만드는 것은 아깝다

② 재료가 이미 있다
   녹음 원본을 영구 보관한다(DEC-003 §6). 실측: /data/recordings/1.bin

③ async 가 확실히 낫다
   soniox-study §1 「실시간 화자 분리는 async 대비 정확도가 낮다.
   저지연 제약 때문에 화자 오귀속·일시적 화자 전환이 생긴다.
   최고 정확도는 async(전체 오디오 컨텍스트)」
   §5 「비슷한 목소리는 정확도 저하」
   → 실측에서 실제로 화자가 제대로 안 갈렸다(2026-09-07 사용자 확인)

④ 조사 문서가 이미 열어둔 갈래다 — 아직 안 정한 것
   soniox-study L32 「2-pass 여부(정책 결정 필요) —
   회의 종료 후 async 재전사로 화자·전사 정정할지, 실시간 결과를 정본으로 둘지」
```

### 시간축은 살아남는다

`at_ms` 는 **녹음 시작 기준 오프셋**이다(ERD M-1-a · M-11). 같은 파일을 다시 전사해도 **시각은 같다.**
근거 타임칩을 **블록 id 가 아니라 시각(ms)으로** 매칭하면 재전사해도 안 깨진다.

### 확인이 필요한 것 — **착수 전에 반드시**

```
✅ 녹음 파일은 온전하다 — 2026-09-07 실측
   /data/recordings/1.bin (21MB) · ffprobe:
     format_name = matroska,webm
     codec_name  = opus
     sample_rate = 48000 · channels = 1 (모노 — 「내 마이크만」 정책대로)
     duration    = N/A     ← 실시간으로 흘려 써서 총 길이가 헤더에 없다. 디코딩은 된다
   → 청크를 날로 이어붙인 것이 아니라 **EBML 헤더가 붙은 정상 WebM** 이다.
     적재 방식을 먼저 고칠 필요가 없다. 파일 그대로 재전사에 쓸 수 있다.
   ⚠ 확장자만 `.bin` 이다 — async 업로드에서 포맷 판별에 걸리면 `.webm` 으로 바꾸는 것을 함께 본다

남은 확인
  Soniox async API 의 실제 엔드포인트·요청 형태·비용·소요 시간
  조사 문서에 async 가 낫다는 언급만 있고 계약은 조사되지 않았다.
  duration 이 비어 있는 파일을 받아주는지도 함께 확인한다.
```
