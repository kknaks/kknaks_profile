## ① 웜스타트를 언제 하나 — W-1 · D-2 가 같은 뿌리다

### 지금 무슨 일이 벌어지나

`POST /api/meetings/{id}/start` 가 이렇게 돈다(`meeting_service.py:464`).

```
① scheduled → recording 전이를 쓴다
② service 안에서 session.commit()          ← 여기가 문제
③ open-kknaks 에 웜스타트를 제출한다(수 초~수 분)
④ 새 세션에서 ai_session_id 를 UPDATE 한다
```

**②가 아키텍처 규약 두 줄과 동시에 부딪힌다.**

```
BE §2 표   service — commit() 금지
BE §7 표   외부 호출 — 읽기 → (커밋) → 외부 호출 → 새 세션에서 쓰기
           수 분짜리 외부 대기가 커넥션과 락을 잡고 있으면 안 된다
```

**§7 이 「커밋하라」고 하는데 §2 는 「service 는 commit 하지 않는다」고 한다. 누가 커밋하는지가 안 적혀 있다.**

### 그리고 실패했을 때가 안 정해져 있다 (D-2)

③이 터지면 회의는 이미 `recording` 인데 `ai_session_id` 가 없다.
**DEC-003 §7 실패 목록에 이 상황이 없다.** BASE-003 L43 대로 전파하면 사용자는 500 을 보는데 회의는 시작돼 있다.

> 지금은 compose 에 Redis·worker 가 없어서 **항상** 이렇게 된다(D-8). 그건 이번 수정에서 닫는다.

### 갈림길

**A. 웜스타트를 백그라운드로 민다**

```
/start 는 전이만 하고 바로 응답한다
웜스타트는 배치처럼 백그라운드 태스크로 나간다

- DEC-003 §STT 가 「웜스타트(결과 무시)」라고 이미 적었다 — 응답을 기다릴 이유가 없다
- service 가 commit 할 일이 없어진다 → W-1 이 같이 닫힌다
- 실패하면 첫 배치가 세션을 새로 만들면 된다 → D-2 도 닫힌다
- BE §7 「백그라운드 job — 단계마다 세션을 새로 열고 그 단계 끝에 commit」 규약을 그대로 탄다
```

**B. 지금 구조를 두고 규약에 예외를 명시한다**

```
BE §2 에 「외부 호출 앞의 커밋은 예외」를 적는다
D-2 는 별도로 정한다 — 웜스타트 실패 시 recording 을 되돌릴지, 두고 갈지
```

**코디 의견: A.** 정책이 이미 「결과 무시」라고 적었고, A 는 W-1·D-2 를 함께 닫는다.
다만 **아키텍처 규약을 바꾸는 일이라 사용자 확인이 필요하다.**
