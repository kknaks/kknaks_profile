AGENTS.md, orchestration/work/phub-ledger-redesign/ledger-first-pass/SKILL.md, batch-01-review.md, _RESUME.md, batch-01-dispatches.json. 모든 작업 경로는 orchestration/work/phub-ledger-redesign/ 기준이다.

## 2. 배경

독립 검토는 batch-01 5개 모두 1차 종료 가능(PASS3/WARN2)·추출 오류0이라고 했다. 사용자는 1차 수집 뒤 다음 원장으로 넘어가며 최종 의미 해석·모든 형태소 정답을 위해 반복하지 말라고 합의했다. 이번 작업은 이미 확인한 기록·분류만 반영한다. 원장 재조사·의미 모델 설계·후속 판단 확정은 하지 않는다.

## 3. 계약

검토 리포트 §5의 보완을 원문 근거와 대조해 반영한다. 원문·추출 데이터와 이미 기록된 관찰은 지우지 않는다. 원문 부족을 닫거나 잠정 해석을 확정하지 않는다.

- products issues B5는 외부 사실 확인, B6 일부는 해석 과제임을 병기한다. 번호는 유지하고 단순히 미결 수를 줄이지 않는다.
- procedure-comparison review 및 validation 맨 위에 1차 수집 범위 종료(코디 확인 전)/원장 전체 미완료를 표시한다. 생성 원고가 있으면 같이 맞춘다.
- complications: 카테고리별 id/name에 정확한 개별 Pointer를 붙이는 표를 보완한다. 값은 원문에서 확인한다. build.py가 재생성해도 유지되도록 원고 또는 생성부를 최소 수정하되 원본 값·JSON을 바꾸지 않는다. 알려진 오분절 2출현(시술·전층), '삽입 깊이' 구절 후보 한계, keyword 동일 구간 57쌍의 중복 기준을 issues에 정확한 위치·영향과 함께 기록한다. 57쌍을 무조건 의도됐다고 확정하지 말고 검토 보고의 관찰과 구분한다. 후보 보충이나 새 JSON 생성은 하지 않는다.
- treatment-sequence issues B1은 하한0 잠정 해석+숫자 단독 사용 위험을 병기한다. C1·C3·C5·C6의 사용자 결정 후보 문구를 후속 의미/원장 간 비교 과제로 정리한다. 원문 불일치 관찰은 유지한다. 실제 원본 수정 제안이 필요해질 때만 사용자에게 묻는다고 적는다.
- synergy: U1은 F1 관계 방향 후속 검토, U2는 실버 변환 규칙 후속 검토 후보로 옮긴다. 현재 사용자 선택 대기는0, 원본은 사용자 지시대로 보존. 기존 U번호·원문·영향을 남겨 재분류를 추적할 수 있게 한다. 삭제/수정 승인 또는 방향 확정으로 쓰지 않는다. issues/review/생성 원고/validation의 관련 집계를 일치시킨다. /links/55/reason [35,37) 전층 오분절을 알려진 한계로 기록한다.

## 4. 실제 변경 범위

5개 first-pass/<원장명>/ 안 **Markdown과 생성 원고**, complications/build.py의 카테고리 Pointer 행 생성부만 필요하면 최소 수정 가능. 그 밖의 코드·JSON·원본·스킬·기존 검토 리포트는 수정/삭제 금지. _RESUME의 현재 상태·산출물·이력과 '발주' 종료 보고 상태는 갱신 가능(코디 확인 전으로 둔다). batch 발주 기록은 읽기 전용. 신규 batch-01-final-note.md에 변경·검증·남은 한계를 기록한다.

## 5. 재조사하지 말 것

리포트에서 지적한 위치·문서만 확인한다. 새로운 의미 조사·전체 품사 재판정·후속 ERD·다음 원장 발주는 하지 않는다. 알려진 오류 위치 기록은 수정된 토큰으로 오해되지 않게 한다. 원장 전체 완료라고 말하지 않는다.

## 9. 완료 보고 — **문구 변경 금지**

> **⚠ 핸들은 dispatch preamble 의 값을 믿어라.** 아래 명령에 박힌 코디handle 은 **브리프 작성 시점** 값이라 오래됐을 수 있다 — 세션이 재연결되면 핸들이 바뀐다(2026-07-28·29 두 번 겪음). preamble 의 코디네이터 핸들과 아래 값이 다르면 **preamble 이 맞다.** 두 곳에 다 보내지 말고 preamble 쪽으로만 보내라.


- **커밋·push·PR 하지 마라.** 워크트리에 변경만 남긴다. 검증·PR 은 코디네이터가 한다.
- 끝나면 **아래 두 명령을 모두** 실행한다. 하나만 하면 안 된다.

```bash
# (1) 인박스 적재 — 태스크 완료 처리·영구 기록. 코디네이터를 깨우지 않는다.
orca orchestration send \
  --to term_9817d7e4-b067-40b3-9235-c8dcddad8f26 --from term_8c2999f2-0bca-4945-9d09-c5212852bdaa \
  --type worker_done \
  --task-id <이 태스크의 taskId — dispatch 로 받은 context 에 들어 있다> \
  --dispatch-id <이 태스크의 dispatchId — dispatch 로 받은 context 에 들어 있다> \
  --subject "researcher 완료: <한 줄>" \
  --body "변경 파일 목록 / 구현 요약 / 검증 결과(수치) / 계약 준수 / 미결·주의점"

# (2) 직접 주입 — 코디네이터 세션에 유저 메시지로 꽂혀 자동으로 깨운다.
orca terminal send --terminal term_9817d7e4-b067-40b3-9235-c8dcddad8f26 \
  --text "[worker_done] researcher 완료 — <한 줄 요약>. 상세는 인박스." --enter
```

- 막히면 30분 이상 혼자 헤매지 말고 같은 (2) 방식으로 물어라:
  `orca terminal send --terminal term_9817d7e4-b067-40b3-9235-c8dcddad8f26 --text "[질문] researcher: <질문>" --enter`
  (`orca orchestration ask` 는 채널이 닫혀 답이 안 닿는 경우가 많다.)
