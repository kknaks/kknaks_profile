## 2. 이번 수정의 성격 — 구조가 아니라 경계

v0.2.0 이 세운 「네이티브가 점유 수명을 소유한다」를 그대로 두고, **그 구조가 열어 둔 네 빈틈**만
닫았다. 넷 중 셋(R2-F2·F3·F4)은 같은 뿌리였다 — **「점유는 녹음이 끝날 때만 풀린다」를 적었지만
그 반대편(끝나지 않았는데 풀리는 길 · 끝났는데 남는 길)을 전부 세지 않았다.**

| 축 | v0.2.0 | v0.2.1 |
|---|---|---|
| 커맨드 수 | 4 | **4 (그대로)** |
| TTL · 주기적 갱신 · 참조계수 | 없음 | **없음 (되살리지 않았다)** |
| 해제 계기 | 「창 닫기·문서 교체」 (시점 미정) | **«완료» 사건만.** 취소된 요청으로는 안 풀린다 |
| `degraded` 탈출 | **없었다** | **사건 기반 재요청(재무장).** 푸는 방향이 아니라 **거는 방향** |
| 늦은 `acquire` | 계약 없음 | **최종 잔존 0** 요구 (수단은 구현 몫) |
| 커맨드 호출 실패 | 계약 없음 | `E-14` 로 분리. **`release` 실패를 「녹음 계속」으로 뭉개지 않는다** |
| 웹의 주기적 의무 | 없음 | **없음 (그대로).** 더해진 것은 **사건 1회 재확인**뿐 |

> **「재요청」이 「갱신」이 아닌 이유 — 재검수가 마지막에 볼 자리로 지목한 구분.**
> 갱신은 **안 오면 푸는** 신호다. 재요청은 **와야 거는** 신호다. v0.2.1 은 같은 문장을
> §4·§5 두 곳에 박았다 — **「셸은 재요청이 오지 않는다고 해서 절대 풀지 않는다.」**
> 신호 부재로 푸는 길은 **여전히 문서 어디에도 없다.**

| # | 시나리오 | 계약이 답하는가 | 걸리는 조항 |
|---|---|---|---|
| 1 | **정상** — 마이크 열림 → 녹음 → 종료 | `acquire(s1)`→`on` … `release(s1)`→`off` | L-01 · L-02 · AC-T01 · AC-T04 |
| 2 | **취소된 닫기** — 녹음 중 닫기 → `계속 녹음` | 되묻기 **하나**만 뜨고, **완료가 아니므로 해제 없음** → 점유 `on` 유지 | L-06 · `E-12` · AC-T36 · AC-T38 |
| 3 | **막힌 이동** — 허용 목록 밖 주소 시도 | 셸이 취소 → **문서가 안 바뀌었으므로 트리거 아님** → 점유 유지 | L-11 · `E-05` · AC-T37 |

| 5 | **호출 실패** — IPC 예외 | `acquire` 면 degraded 와 동일 / **`release` 면 녹음을 다시 켜지 않고 잔존을 드러냄** | `E-14a` · `E-14b` · AC-T43 |

| 10 | **수동 절전 복귀** | 재확인 → 녹음 중이면 재무장 / 끝났으면 해제. **자동 재연결은 없다** | L-14 · S-11 · AC-T19 |

**빈틈을 하나 더 찾아 같이 막았다** — `E-14b` 가 만드는 **새 사용자 문구**가 §2 에 정의돼 있지
않았다(Case Matrix 만 갖고 있었다). U-3 에 그 문구와 사라지는 조건을 명시했다.
**U-3 의 원래 문구를 그대로 쓰면 「녹음 중에는」이 거짓이 된다** — 녹음은 이미 끝났기 때문이다.

## 7. 남는 것 — 실측 / 사용자 결정 / 문서 오류를 가른다

### 7-1. 문서 오류 — **이번에 전부 닫혔다**

R2-F1~F4 · R2-W1~W7 은 전부 **문서만으로 틀렸거나 못 박히지 않은 것**이었고, 11건 모두
이번 수정에서 닫았다. **미반영 0건.**

### 7-2. 실측 — **14건** (M-1 ~ M-14, M-2b 포함하면 15)

이번에 **2건 신설**(M-13 취소된 사건 · M-14 늦은 완료·정리 실패)하고 **2건 확장**(M-1 의 AC
목록 · M-12 의 재무장 여부). **개발 fixture 로 뗄 수 있다는 판정은 그대로**이고,
운영 주소가 막는 것은 여전히 M-1·M-5 의 «최종» 확인과 인수조건 최종 통과뿐이다.

가장 무거운 둘은 바뀌지 않았다 — **M-1**(원격 문서에서 커맨드 호출이 성립하는가)과
**M-2**(대상 OS·웹뷰 판에서 녹음 포맷이 열리는가). W7 정정으로 **M-2 의 대상 범위가 넓어졌다** —
macOS Sonoma·Ventura 까지 본다.

### 7-3. 사용자 결정 — **11건, 늘지 않았다**

OQ-T01 ~ OQ-T11 그대로다. **이번 수정으로 새 OQ 를 만들지 않았다.**
R2-W5 의 관찰 시간(`max(3T, 30분)`)은 **코디 기본값으로 확정**했고 사용자에게 올리지 않았다.

**성격이 바뀐 것 하나** — **OQ-T01(지원 OS)의 무게가 늘었다.** W7 정정으로 대상 macOS 판이
Sequoia 하나가 아니라 Sonoma·Ventura 까지 걸리고, 그것이 OQ-T07(녹음 포맷)의 답을 좌우한다.

### 7-4. 이 SPEC 이 여전히 **보장하지 않는** 것 — 과장하지 않았다

| 무엇 | 왜 |
|---|---|
| 웹이 **살아 있는 채로 멈춘** 경우의 정리 | 네이티브가 탐지할 수 없다 (L-12 · OQ-T08). **이번에도 「자동 정리된다」고 쓰지 않았다** |
| OS 절전 방지가 풀리는 **순간**을 아는 것 | 상시 감시하지 않는다. **확인 가능한 사건과 재요청 결과로만** 갱신된다(§4·§5·U-3 세 곳에 명시) |
| 재무장이 **반드시 성공**하는 것 | 재요청해도 실패하면 `degraded` 가 남고 **녹음은 계속된다**(AC-T39 후단) |
| 수동 절전 **복귀 직후**의 OS 상태 | 플랫폼에 달렸다. 계약은 「**깨어나면 다시 확인하고, 풀려 있으면 다시 건다**」까지 (S-11 5 · M-12) |
| 되묻기를 **어느 층이** 내는가 | 외부 계약은 「**하나만 뜬다**」까지. 층은 M-6 실측과 WP 가 정한다 (`E-12` · AC-T38) |
| 늦은 획득을 **어떤 수단으로** 막는가 | 결과(**최종 잔존 0**)만 요구한다. 취소·직렬화·보상 해제는 구현 몫이고 **영구 기록을 강제하지 않는다** |

## 8. 재검수 때 볼 자리

R2 검수가 마지막에 지목한 기준 그대로다 — **「푸는 방향」이 다시 열렸는가.**

1. **재요청은 거는 방향뿐인가.** `E-09` · L-14 · §5 · Flow 어디에도 **「신호가 없으면 푼다」가 없다.**
   같은 취지의 문장을 §4·§5 두 곳에 박아 두었다
2. **해제가 전부 «완료» 사건인가.** L-06 · L-09 · L-13 셋과 웹 쪽 넷(L-02 · L-05 · L-08 · L-10) —
   **전부 녹음이나 창이 실제로 끝나는 자리**다. 취소 경로 둘은 L-11 이 흡수했다
3. **`E-14b` 가 「녹음 계속」으로 새지 않는가.** `release` 실패는 **정리 실패**이지 녹음 실패가 아니다
4. **커맨드가 넷인가.** §4 표 · AC-T23 그대로

**DEC-005 D-01 ~ D-06 을 건드리는 수정은 이번에도 하나도 없다.**
