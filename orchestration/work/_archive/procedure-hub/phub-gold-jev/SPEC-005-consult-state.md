## 1. 목적 · 범위

### 1-1. 목적

0.1 은 「한 턴 = 고민 → 시술 리스트 + 얼굴 점 + 짧은 답」 과 이어 묻기의 뼈대다(SPEC-004 §0). 턴 사이에 앱이 드는 것은 **앞 턴 대상**(SPEC-004 §5-2 CR1)과 실은 재료의 줄 번호뿐이라, 「이 손님의 고민이 무엇이고 무엇에 관심이 있으며 무엇을 아직 모르는가」 를 앱이 알지 못한다.

0.2 는 그것을 **상담 객체**로 든다. 목적은 손님이 「나는 이런 시술들이 필요하구나」 를 알게 하는 것이다 — 고민 · 효과 · 시술 정보 · 시너지 · 같이 받으면 좋은 시술(`_RESUME` §2 11-17 「상담 초반부 흐름(사용자 · 0.2 재료)」).

### 1-2. 정해진 것(다시 묻지 않는다)

지시서 「정해진 것」 을 옮긴다.

## 2. 상담 객체

### 2-1. 원칙

| # | 규칙 | 상태 |
|---|---|---|
| SL1 | 객체는 대화(`conv_id`)마다 하나다. **항목의 값은 (표, 코드) 하나**이고 이름은 허브가 낸 값을 함께 적는다(표시용). 글자만 있는 항목은 없다 — 코드가 없으면 객체에 못 들어간다 | 결정(D5-9) |
| SL2 | 객체는 **앱의 것**이다. LLM 은 객체를 읽기만 하고(턴 메시지의 「앱 판정」 안) 쓰지 못한다 — 쓰는 길은 §3 의 갱신 규칙뿐이다 | 제안(§4 의 (가)) |
| SL3 | 객체의 칸은 **gold 가 답할 수 있는 것**만 둔다(§2-3 의 셈). gold 에 칸이 없는 바람(통증 · 가격 · 시술 시간 · 횟수)은 칸을 만들지 않는다 | 결정(D5-10) |
| SL4 | 항목은 지우지 않는다. 거둔 항목은 `state` = `withdrawn` 으로 남는다(§5) | 제안 |
| SL5 | 객체는 **순위 · 점수를 갖지 않는다.** Jev 값은 출처(`source.noul`)로만 남고, 객체가 시술을 고르거나 줄 세우지 않는다 | 결정(D5-8) · SPEC-004 PL4 |
| SL6 | `procedures[]` 는 **시술 코드(PRC)** 로만 남긴다 — 다음 단계(상품 매핑 · 최저가)의 입력 자리다. 이 판에서 이 칸을 읽는 화면 동작(담기)은 없다 | 결정(D5-11) |

### 2-2. 칸

항목 공통 꼴 = `{table, code, name, state, source}`(§2-4). 「채우는 것」 = 그 칸에 값을 넣는 길 전부다.

| 칸 | 값(표 · 코드) | 뜻 | 채우는 것 |
|---|---|---|---|
| `concerns[]` | `concern` · `CON-…` | 손님의 고민. 여럿이 함께 있을 수 있다(§5) | ① 이번 글의 고민 입구(`resolve` → Jev 대상 Noul) ② 걸린 선택지에서 Jev 가 고른 것(UP4) |
| `focus` | `concerns[]` 가운데 하나의 코드 또는 `null` | 지금 대화가 놓인 고민(리스트 · 점 · 빈 칸의 기준) | 가장 최근에 말하거나 고른 고민(RV5) |
| `sites[]` | `site` · `SITE-…` | 손님이 **말한** 부위 | 이번 글의 부위 입구(`resolve` → Jev) |
| `concern_sites[]`(파생) | `site` · `SITE-…` + `concern_code` · `csi_id` | 고민이 놓이는 부위(얼굴 점의 재료 — SPEC-004 §6-2) | 허브 `concern_candidates` 응답 머리의 고민 부위 목록(SPEC-001 0.7 · SPEC-004 §6-3 HN1 ~ HN4) |
| `subjects[]` | `modality` · `procedure` · `procedure_case` · `product`(코드 = 계열 `M…` · `PRC-…` · `CAS-…` · `PRD-…`) | 손님이 이름 대거나 물어본 **대상**(언급 · 관심). 제품 칸 = 이 가운데 `table` = `product` 인 항목 | ① 이번 글의 대상 입구(`resolve` → Jev) ② 걸린 선택지 |
| `procedures[]`(파생) | `procedure` · `PRC-…` + `via{subject, scope_gid}` | `subjects[]` 가 닿는 **시술** — 다음 단계의 입력(SL6) | 허브 `scope`: 시술 = 자기 · 케이스 · 제품 = `g_scope` 「물려받음」 의 시술 holder. **계열 대상은 시술을 정하지 않으므로 넣지 않는다**(semantic-map §5 「계열 층만」) |
| `wishes[]` | (가) 값: `effect` · `EFF-…` / `method` · `MET-…` / `material` · `MAT-…` (나) 정보 종류: `kind` ∈ SPEC-001 §5-8 의 14 | 손님의 바람 — 「이런 효과였으면」 · 「주사 말고」 · 「회복이 궁금」 | (가) 이번 글의 값 · 속성 입구(`resolve` → Jev) (나) Jev 정보 종류 Noul 이 yes 인 종류(SPEC-002 §3-1 KD1) |
| `shown` | `lists[]` · `info[]` · `synergy[]` | 이미 보여 준 것 — 다시 읽지 않고 다시 말하지 않기 위한 기록 | 앱이 턴 끝에 적는다(§3-4) |
| `asked[]` | `{slot, turn, options[], answered}` | 물어 보라고 LLM 에 준 빈 칸과 그때의 선택지(코드) | 앱이 턴 끝에 적는다(NQ3) |
| `blanks[]`(파생) | `{slot, about, options_n}` | 지금 빈 칸 목록(§6-1) | 턴마다 객체에서 다시 센다 — 저장하는 상태가 아니다(장부에는 그 턴의 값을 남긴다) |

- 부위가 두 칸인 까닭: 손님이 말한 부위(`sites[]`)는 거르개가 될 수 있고(`concern_candidates.site` — SPEC-001 §4-5), 고민에 딸린 부위(`concern_sites[]`)는 점의 재료일 뿐이다(SPEC-004 SI7 「점 기준은 고민 부위 하나」). 섞으면 「팔자주름」 의 부위 SITE-046 이 손님이 고른 거르개처럼 쓰인다.
- 「담은 시술」 칸은 없다(D5-11). `procedures[]` 는 「관심 대상이 닿는 시술」 이지 손님이 고른 목록이 아니다.

### 2-4. 항목의 꼴 · 출처 · 확실함

```
{ "table": "concern", "code": "CON-009", "name": "<허브가 낸 이름>",
  "state": "said",
  "source": { "turn": 1, "how": "text", "matched": "<맞은 조각>", "covered_by": null,
              "noul": 0.93, "decision": "target", "from_ask": null },
  "history": [ { "turn": 1, "state": "said" } ] }
```

| `state` | 뜻 | 들어오는 길 |
|---|---|---|
| `said` | 손님이 말했다 | 이번 글에 이름이 덮이지 않고 통째로 들었고 Jev 대상 Noul 이 yes 문턱 이상 · 또는 걸린 선택지에서 yes 로 골라짐 |
| `guess` | 앱의 추정이다 | 이름이 글에 들었으나 Noul 이 yes 가 아님(사이 값 · 낮음) — 걷기는 읽지만(SPEC-002 TG2 · TG3) 객체는 추정으로 둔다 |
| `confirmed` | 확인됐다 | `guess` 항목을 손님이 다시 말하거나 확인 질문(BK5)에 답했다 · `said` 항목이 뒤 턴에 다시 나왔다 |
| `withdrawn` | 거뒀다 | §5 RV2 · RV3 |

| `source.how` | 뜻 |
|---|---|
| `text` | 이번 글의 입구 이름(`resolve` 맞춤) |
| `option` | 앱이 물어 둔 빈 칸의 선택지에서 Jev 가 골랐다(이번 글에 그 이름이 글자로 없을 수 있다 — UP4) |
| `derived` | 허브 응답에서 끌어냈다(`concern_sites[]` · `procedures[]`) — `state` 는 근거가 된 항목의 것을 따른다 |

- `source.noul` · `decision` 은 걷기 trace 의 값 그대로다(`front.targets[]` — SPEC-004 LG3 `trace`). 객체가 새 점수를 만들지 않는다.
- 덮인 조각(`covered_by` ≠ `null`)은 Jev 가 yes 일 때만 객체에 든다 — 걷기 규칙 그대로다(`_RESUME` §2 11-17 「덮인 조각 규칙」).

## 3. 한 턴 루프

### 3-1. 흐름

```
말
 L1 받기                — SPEC-004 TF1 그대로
 L2 후보 모으기          — 이번 글의 입구(resolve) + 든 후보(앞 턴 대상 · CR1) + 걸린 선택지(asked[] 의 마지막 것)
 L3 걷기                — SPEC-004 TF2 그대로(같은 walk) · 후보에 L2 가 더해질 뿐
 L4 객체 갱신            — 걷기 trace → 갱신 규칙(§3-2) → diff
 L5 객체 기준 조회        — 걷기가 이번 턴에 읽지 않은 것 가운데 객체가 시키는 조회(§3-3)
 L6 화면                — list · sites(객체 기준으로 다시 지음 — §3-5) → 첫 delta 보다 먼저
 L7 빈 칸 고르기         — blanks[] 에서 하나(§6) → ask
 L8 LLM                — 새 재료 + 앱 판정(객체 요약 · ask · 시너지 표지) → 답 + 질문 하나
 L9 맺기                — 장부 한 줄(consult.diff · consult.after · blanks · ask) · shown · asked 갱신
```

- **Jev 는 L3 안에서만 돈다**(걷기의 맨 앞 판단 · 깊이). L4 ~ L7 은 결정론이다. 「거둠」 판단(§5 RV2)만 Jev 요청 하나를 더 쓴다 — L3 과 **함께** 띄운다(걷기를 기다리게 하지 않는다).
- **LLM 은 L8 한 번**이다. 객체를 채우는 데 LLM 을 쓰지 않는다(§4 추천 (가)).

### 3-2. 객체 갱신 규칙

| # | 규칙 | 상태 |
|---|---|---|
| UP1 | 객체에 드는 값은 **걷기가 대상 · 값으로 확정한 개념**(`front.targets[]`)과 **허브 응답에서 끌어낸 것**뿐이다. 앱이 글에서 따로 낱말을 뽑지 않는다 | 결정(D5-9) |
| UP2 | 확정된 개념의 표가 칸을 정한다: `concern` → `concerns[]` · `site` → `sites[]` · `modality` · `procedure` · `procedure_case` · `product` → `subjects[]` · `effect` · `method` · `material` → `wishes[]`. 그 밖의 표(`adverse` · `condition` · `anatomy` · `offer` · `package`)는 **객체에 넣지 않는다** — 그 턴의 조회에만 쓰인다(안전 · 상품은 객체가 끌고 다니지 않는다 — D5-7 · D5-10) | 제안 |
| UP3 | `state`: 덮이지 않은 이름 + Noul yes → `said` · 덮이지 않은 이름 + Noul 이 yes 아님(걷기 `decision` = `named` · `uncertain_kept`) → `guess` · 덮인 조각은 yes 일 때만 `said`(아니면 안 넣는다) · 든 후보 · 걸린 선택지는 yes 일 때만 `said`(SPEC-004 CR4 와 같은 꼴) | 제안 |
| UP4 | **걸린 선택지를 다음 턴 후보로** — 앞 턴에 `ask` 로 준 빈 칸의 `options[]`(코드)를 이번 턴 Jev 대상 후보에 「든 후보」 와 같은 꼴로 붙인다(`matched` = `null` · `origin` = `option`). 이번 글에 이름이 글자로 없어도 손님의 답이 선택지 가운데 하나를 가리키면 Jev 가 고른다. yes 만 객체에 든다. **입구 고르기(SPEC-002 TG4 — 후보 0 일 때의 전체 fan-out)는 걸린 선택지도 0 일 때만 돈다** | 제안(§8-1 턴 2 가 이 길이다) |
| UP5 | 걸린 선택지는 **한 턴만** 산다 — 다음 턴에 안 골라졌으면 후보에서 뺀다(`asked[].answered` = `false`). 같은 빈 칸은 NQ4 대로 다시 물을 수 있다 | 제안 |
| UP6 | 같은 (표, 코드)가 이미 객체에 있으면 새 항목을 만들지 않고 `history[]` 에 턴을 더한다. `guess` → 다시 나옴 = `confirmed` · `withdrawn` → 다시 말함 = `said` | 제안 |
| UP7 | 고민이 3단의 윗고민이고(대분류 · 중분류) 뒤 턴에 그 하위 고민이 들어오면 **둘 다 둔다** — 윗고민을 지우지 않고 `focus` 만 하위로 옮긴다(허브 응답이 다르다 — 윗고민은 하위를 펼친 행 · 하위는 자기 행) | 제안 |
| UP8 | `procedures[]` · `concern_sites[]` 는 근거 항목이 `withdrawn` 이 되면 함께 빠진다(파생 — 다시 센다) | 제안 |
| UP9 | diff = 이번 턴에 객체가 바뀐 것의 목록: `{op, slot, table, code, from, to, why}` · `op` ∈ `add` · `state` · `withdraw` · `focus` · `shown` · `asked`. 바뀐 것이 없으면 빈 목록이다(턴마다 한 줄은 그대로 쓴다) | 제안 |

### 3-3. 객체 기준 조회 — 무엇을 언제

걷기는 **이번 글이 물은 것**을 읽는다(대상 × 정보 종류 — SPEC-002 §3-1). 객체 기준 조회는 **이번 글이 묻지 않았지만 객체가 바뀌어 필요해진 것**만 더 읽는다. 걷기가 이번 턴에 이미 읽은 조회(같은 도구 · 같은 입력)는 다시 부르지 않는다.

| # | 언제(객체의 변화) | 허브 조회 | 무엇에 쓰나 |
|---|---|---|---|
| QY1 | `concerns[]` 에 `said` · `confirmed` 고민이 새로 듦 · `focus` 가 바뀜 | `concern_candidates(concern_code, site = sites[] 가 있으면 그것)` — 쪽 넘김 끝까지 | 시술 리스트(SPEC-004 §6-1) · 고민 부위(→ `concern_sites[]`) · 하위 고민 목록(BK3 의 선택지 = 행의 `concern_code`) |
| QY2 | `subjects[]` 에 대상이 새로 듦 | `scope(node)` — 「자기」 · 「물려받음」 | `procedures[]`(시술 holder) · 층(계열 · 시술 · 케이스) |
| QY3 | `subjects[]` 에 대상이 새로 들었고 **`concerns[]` 가 비어 있음** | `facets(node, facet = indication)` 대상 쪽 — 기본 role(자기 · 물려받음) | 「고민」 빈 칸의 선택지 = 그 행들의 서로 다른 `concern_code`(BK2). 층(`layer.role`)을 함께 든다 |
| QY4 | 시너지 조건이 참(§7 SY1)이고 그 대상의 시너지를 아직 안 읽음 | `pair(a = 대상, classes = [보완])` — `b` 없음 · 쪽 넘김 끝까지 | 시너지 묶음(§7) |
| QY5 | `sites[]` 에 부위가 새로 들었고 `focus` 고민이 있음 | QY1 을 그 부위 거르개로 다시 | 리스트를 그 부위로 좁힘(0 이면 0 그대로 + `counts.unfiltered_rows` — SPEC-001 §4-5) |
| QY6 | — | **객체가 안전 종류를 시키는 일은 없다** — `adverse` · `contraindication` · `avoid` 는 걷기가 「손님이 물었다」 고 확정한 턴에만 읽힌다(SPEC-002 KD7). `recovery` 는 손님이 바람으로 말한 턴에만(§2-3) | D5-7 |

- 조회 수의 위(재셈 — 예시 셋): 한 턴에 객체가 더하는 조회는 0 ~ 3 이다(QY1 · QY2 · QY3 또는 QY4). 걷기와 겹치면 0 이다(예: 고민으로 들어온 턴의 QY1 은 걷기가 이미 읽었다).
- **허브에 새로 필요한 것은 없다.** 대상 → 고민(QY3)은 `facets` indication 대상 쪽 · 고민 → 하위 고민은 `concern_candidates` 행의 `concern_code` · 대상 → 시술은 `scope` 로 지금 계약에 있다. 고민 → 부위만 SPEC-001 0.7 이다(SPEC-004 §6-3 그대로).
- 읽은 행은 0.1 의 재료 규칙을 그대로 탄다(SPEC-004 §5-3 — 새로 읽은 줄만 · 줄 번호 이어감 · 요약 줄). QY3 · QY4 의 행은 **요약 줄**로 싣는다(§6-2 · §7 SY4).

**추천 = (가).** 값의 출처가 한 길(허브 코드)이고, 0.1 의 걷기 · trace · 장부를 그대로 쓴다. (나)가 메우는 곳(글자로 안 잡히는 말)의 큰 몫은 「앱이 방금 물은 것의 답」 인데, 그것은 UP4 가 선택지를 후보로 주어 결정론 안에서 받는다. 그래도 남는 것(첫 턴의 구어)은 (가)의 E5-2 값을 본 뒤 (나)를 다시 본다 — **사용자 결정 U5-1**.

| RV7 | 거둔 것이 `focus` 였음 | `focus` = 남은 고민 가운데 가장 최근 것 · 없으면 `null`(리스트 ② 는 빈 조각 · 점도 빈 조각 — SPEC-004 SI5 와 같은 까닭) | 제안 |

## 6. 「자연스러운 질문」

### 6-1. 빈 칸

| # | 빈 칸(`slot`) | 언제 빈 칸인가 | 선택지(`options[]`) — 전부 gold 에서 |
|---|---|---|---|
| BK1 | `interest` — 궁금한 시술 | `focus` 고민이 있고 `subjects[]` 가 비었고 리스트를 보여 줬다 | 없다(리스트가 화면에 있다 — 선택지를 따로 주지 않는다) |
| BK2 | `concern` — 왜 받고 싶은가 | `subjects[]` 가 있고 `concerns[]` 에 `said` · `confirmed` 가 없다 | QY3 의 서로 다른 고민 — 층이 가까운 것부터(자기 → 케이스 → 시술 → 계열) · 층 안에서는 허브 순서 |
| BK3 | `concern_narrow` — 그 가운데 어떤 고민 | `focus` 고민이 윗고민이고 QY1 응답 행에 하위 고민(`concern_match` = 「하위 고민」)이 있다 | 그 응답 행의 서로 다른 `concern_code`(물은 고민 자신 빼고) |
| BK4 | `site` — 어디가 | `focus` 고민 아래 하위 고민들의 `concern_sites[]` 가 **둘 이상의 부위**로 갈린다(BK3 과 같은 응답에서) · `sites[]` 가 비었다 | 그 부위들(SITE 코드 · 허브가 낸 이름) |
| BK5 | `confirm` — 이걸 말한 게 맞나 | `guess` 항목이 있다 | 그 항목 하나 |

- 빈 칸은 **객체에서 세는 것**이지 단계가 아니다. 같은 턴에 여럿이 빈 칸일 수 있고 §6-2 가 하나를 고른다.
- 「정보를 아직 안 봤다」(예: 관심 시술의 효과를 아직 안 실음)는 빈 칸으로 **두지 않는다** — 그것은 걷기의 「더 볼 수 있는 정보」(`offered` — SPEC-002 KD3)가 이미 LLM 에 주는 되묻기 재료다. 둘을 섞으면 묻지 않은 정보를 앱이 밀게 된다.

### 6-2. 하나 고르기 · 묻지 않는 경우

| # | 규칙 | 상태 |
|---|---|---|
| NQ1 | 앱이 `blanks[]` 에서 **하나**를 골라 「앱 판정」 의 `ask{slot, about, options[]}` 로 준다. LLM 은 그것을 답 끝의 **질문 하나**로 잇는다. `ask` 가 `null` 이면 LLM 은 객체에 대해 묻지 않는다 | 결정(D5-2) · 꼴은 제안 |
| NQ2 | 고르는 순서는 **칸의 고정 순서가 아니라 대화에 가까운 순**이다: ① 이번 턴에 객체에 새로 든 항목에 딸린 빈 칸(이번에 시술을 말했으면 BK2 · 이번에 윗고민을 말했으면 BK3 · BK4) ② 이번 턴에 새로 생긴 `guess` 의 BK5 ③ 앞 턴부터 남은 빈 칸 가운데 `focus` 고민 · 가장 최근 대상에 딸린 것 ④ 그 밖의 남은 것. 같은 급이면 가장 최근 턴의 것 | 제안 |
| NQ3 | 준 `ask` 는 `asked[]` 에 `{slot, about, turn, options[]}` 로 적는다. 그 `options[]` 가 다음 턴의 걸린 선택지다(UP4) | 제안 |
| NQ4 | 같은 빈 칸(`slot` + `about`)은 **두 번까지만** 준다. 두 번 주고도 안 채워졌으면 그 대화에서 다시 주지 않는다 | 제안 · 값은 임시 |
| NQ5 | **잇달아 묻지 않는다** — 앞 턴에 `ask` 를 줬는데 이번 글이 그것에 답하지 않고(걸린 선택지 가운데 yes 0 · 객체에 새 항목 0) 다른 것을 물었으면 이번 턴은 `ask` = `null` 이다. 손님이 정보만 원할 때 질문이 쌓이지 않는다 | 제안 |
| NQ6 | 이번 턴이 **안전 종류를 물은 턴**(걷기가 `adverse` · `contraindication` · `avoid` 를 읽음)이면 `ask` = `null` — 안전 답 끝에 유도 질문을 붙이지 않는다 | 제안 |
| NQ7 | 종료 상태가 「범위 밖」 · 「입구 없음」 · 「실행 중단」 이면 `ask` = `null`(그 상태의 답은 0.1 프롬프트의 종료 상태별 줄이 정한다) | 제안 |
| NQ8 | 선택지는 **이름과 층만** LLM 에 준다(코드는 장부). LLM 은 선택지에 없는 고민 · 부위 이름을 예로 들지 않고, 선택지를 전부 읊지 않으며(몇 개만 예로), 어느 것이 낫다고 하지 않는다 | 결정(D5-4 · D5-8) · 「몇 개만」 은 제안 |
| NQ9 | 선택지가 0 인 빈 칸(BK2 인데 그 대상의 적응 행이 0)은 `ask` 로 주지 않는다 — 앱이 선택지를 지어 채우지 않는다 | 결정(D5-4) |

- 고르기는 결정론이라 같은 장부로 다시 돌리면 같은 `ask` 가 나온다(시험 S5-T9).
- 앱이 둘을 주고 LLM 이 하나를 고르게 하는 길은 두지 않았다 — 어느 것을 물었는지 앱이 알 수 없어 `asked[]` 가 흐려진다(O5-4).

### 6-3. 프롬프트 JSON 에 들어갈 절(초안 — 문구는 사용자)

`prompts/consult.json`(WORK-011 §3-1)에 **키를 더한다.** 0.1 의 키(`system` 의 다섯 절 · `jev_front` · `turn_headers` · `tail_marker`)의 뜻은 바꾸지 않는다. 아래 「낱말」 은 절이 담아야 할 뜻이지 확정 문장이 아니다 — 구현은 초안으로 하고 `version` 을 `-draft` 로 둔다(WORK-011 §3 과 같은 길).

| 키 | 꼴 | 담을 뜻(초안 낱말) |
|---|---|---|
| `system[]` 에 절 `consult` | `{id: "consult", lines[]}` — `screen` 과 `material` 사이 | 「앱 판정」 의 `consult` 는 지금까지 앱이 알아낸 손님의 상태다 · 거기 없는 고민 · 시술을 손님이 말한 것처럼 쓰지 않는다 · `guess` 는 확정처럼 말하지 않는다 |
| `system[]` 에 절 `ask` | `{id: "ask", lines[]}` — `consult` 뒤 | `ask` 가 있으면 답 끝에 그 하나만 자연스럽게 묻는다 · 예는 `options` 안에서만 · 전부 읊지 않는다 · `ask` 가 없으면 객체에 대해 묻지 않는다 · 한 답에 질문은 하나 · 캐묻지 않는다 |
| `system[]` 에 절 `synergy` | `{id: "synergy", lines[]}` — `ask` 뒤 | 시너지 줄이 있으면 묻지 않았어도 짧게 짚는다 · 「같이 받으면 좋다」 는 「같은 날 받아도 된다」 가 아니다(같은 날 값이 줄에 있을 때만 그 값을 말한다) · 상대를 전부 읊지 않는다(화면에 있다) · 우열을 말하지 않는다 |
| `system[]` 절 `rules` 의 한 줄 | 0.1 의 「묻지 않은 것 안 붙임」 줄 | 「시너지 줄은 예외」 한 구절을 더한다(D5-6). 안전 정보는 그대로 물을 때만 |
| `jev_front.target_option` | 문자열(영어 — D10) | 걸린 선택지를 읽는 법: 이 후보는 앞 턴에 앱이 물은 것의 선택지다 · 이번 말이 그 물음의 답으로 이것을 가리키는가 |
| `jev_state.retract` | 문자열(영어) | 거둠 Noul(RV2): 이번 말이 `items[j]` 를 더는 원하지 않거나 아니라고 하는가 |
| `turn_headers.consult` | 문자열 | 턴 메시지 안 객체 요약 블록의 머리(사람에게 보일 문장이 아니다 — SPEC-004 §7-2 끝 줄과 같은 자리) |

- 절을 더하면 `system` 글이 바뀐다 → 프롬프트 sha 가 바뀌고 **새 대화부터** 쓰인다(WORK-011 §3-1 「대화는 시작할 때 읽은 프롬프트로 끝까지」).
- 「앱 판정」 JSON 에 더하는 칸: `consult{concerns[{name, state, focus}], subjects[{name, table, state}], sites[{name}], wishes[{name | kind}]}` · `ask`(NQ1) · `synergy_lines[n…]`(§7 SY4 의 줄 번호). 코드 · id 는 싣지 않는다(공통 지시 2 번 — 답에 코드를 넣지 않는다).
