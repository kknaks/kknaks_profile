# 조사 4 — 「이름으로 KOS 검색 → 이메일로 거르기」가 되는가

> researcher · 2026-11-11 · 데모 테넌트만 · 조회만(`/queries/`).
> 내부 API 토큰 발급(`sign-in`, 데모 테넌트 계정)은 코디 허용을 받아 1회만 불렀다. 그 밖의 `/commands/` 호출은 0회다.
> public 레포라 이름 · 이메일 · 연락처 · id · 토큰 · 계정값은 적지 않았다. 아래에는 모양 · 건수 · 비율만 있다.
> 예시 값은 자리표시다(`<이름>` · `a@example.com`).

## 0. 한 줄 답 · 판정

**판정: 그대로 가능하다(상세 호출 없이).** 내부 `get-visitors` 목록이 고객마다 `email` 을 같이 준다. 그래서 「이름 검색 1회 → 우리 쪽 이메일 대조 → 시술권 1회」, 모두 2호출이면 된다(데모 실측 107~235ms).
**단, 데이터가 거의 비어 있다.** 데모 고객 494명 중 email 이 채워진 사람은 5명(1.0%)이다. 그 5명은 모두 한국 국적에 한글 이름이고, 그중 1개는 `@` 가 없는 값이다. 그대로 쓰면 대부분의 고객이 「찾을 수 없음」이 된다. 운영 지점의 비율은 이번 범위(데모만)에서 보지 않았다.
**공개 API 로는 할 수 없다.** 공개 쪽 고객 응답(`getVisitor` · `searchVisitors` · `findVisitor`)에는 email 칸이 없다. 공개 이름 검색도 전화번호 없이는 0건이다.

| # | 질문 | 답 |
|---|---|---|
| 1 | 검색 응답에 email 이 오나 | **내부 `get-visitors` 목록: 온다**(값이 있을 때만 키가 생긴다). 목록의 값은 내부 상세 `visitor/v2/get-visitor` 와 13/13 같았다. 따라서 상세 호출은 필요 없다. **공개 `getVisitor` · `searchVisitors` · `findVisitor`: 스펙과 실응답 모두 email 칸이 없다** |
| 2 | 이름 검색의 성질 | **부분 일치(포함)**이고 대소문자는 구분하지 않는다. **공백은 그대로 비교한다.** 앞뒤 공백 · 공백 제거 · 공백 두 칸 · 단어 순서 바꿈은 모두 0건이었다. 발음명(`phoneticName`)도 검색 대상이고, 여권 성·이름은 대상이 아니다. 한 페이지 크기 `countInPage` 는 5000까지 받았다(데모 전체 494명이 한 번에 왔다). 데모에서 자기 이름으로 검색하면 494명 중 348명은 1건, 119명은 2~5건, 23명은 6~20건, 4명은 21건 이상(최대 37건)이 나온다 |
| 3 | email 채워진 비율 | 494명 중 **5명(1.0%)**. 키가 있는 사람은 103명인데 그중 98명은 빈 문자열이고, 나머지 391명은 키가 없다. **같은 email 을 가진 고객은 0쌍**이다 |
| 4 | 이메일 대조 규칙 | 채워진 5개 중 대문자가 섞인 값 0개, 앞뒤 공백 0개, 가운데 공백 0개, **`@` 없는 값 1개**였다. 「정확 일치」로 놓치는 사례는 데모에서 보이지 않았다(표본 5개라 근거가 약하다) |
| 5 | 호출 비용 | 이름 검색(내부) 1회 + 시술권(공개 `getTicketBundlesQuery`) 1회 = **2호출**이다. 상세 호출은 0회다. 실측 총 107~235ms(검색 64~168ms, 시술권 42~64ms). 내부 토큰은 약 14시간 유지되므로, 토큰이 없거나 만료됐을 때만 `sign-in` 이 1회 더 붙는다 |
| 6 | 동명이인 + 같은 email | **데모에는 없다**(같은 email 0쌍). 동명이인 자체는 흔하다. 완전히 같은 이름을 가진 고객이 53묶음 138명이고 가장 큰 묶음은 11명이다. email 보유자 5명 중 3명이 동명이인 묶음에 속하지만, 이메일로 모두 1명씩 갈렸다 |

## 1. 1건 조회 호출 순서

```text
(입력) 이름 + 이메일  예: 「<이름>」 + 「a@example.com」
   │
   ├─ [토큰 없거나 만료 시만] 내부 sign-in(시스템 계정) ── 1회 · 약 14시간 유지
   │
   ▼
① 내부 POST /tenants/{데모}/visitor/v2/queries/get-visitors
     {indexOfPage:0, countInPage:N, visitorName:"<이름>", phoneNumber:"", chartNumber:"", sort{…}}
     → {data[{id, name, phoneticName, email?, …35키}], count}
     · 부분 일치 · 대소문자 무시 · 공백은 그대로 · 발음명 포함
     · count > N 이면 다음 페이지가 있다(데모 최대 37건 · countInPage 5000까지 받음)
   │
   ▼
② 우리 쪽: data[].email 과 입력 이메일 대조   ── 호출 없음
     · 키 없음 / 빈 문자열 = 이메일 없는 고객 → 후보에서 빠짐
     · 결과 0명 / 1명 / 2명 이상 으로 갈림
   │  (상세 호출 불필요 — 목록 값 = 상세 값 13/13)
   ▼
③ 공개 POST /ticket/open/v1/queries/get-ticket-bundles {visitorId}
     → {data[…]} 또는 {} (사용 가능한 묶음이 없을 때 · 조사 2)
```

실측(데모 email 보유자 5명 전원, 각 1회):

| 이름 검색 결과 수 | 이메일 일치 | 묶음 수 | 검색 ms | 시술권 ms | 합계 ms |
|---|---|---|---|---|---|
| 20(첫 페이지가 꽉 참 · 실제 count 37) | 1 | 0 | 168 | 64 | 235 |
| 1 | 1 | 4 | 161 | 52 | 215 |
| 1 | 1 | 1 | 64 | 42 | 107 |
| 2 | 1 | 0 | 124 | 44 | 169 |
| 3 | 1 | 0 | 145 | 45 | 191 |

첫 줄은 `countInPage:20`(우리 `search()` 의 값)으로 불렀을 때다. 검색 결과는 37건이었고, 대상은 첫 페이지 2번째에 있어서 우연히 잡혔다. 대상이 21번째 이후에 있으면 첫 페이지만으로는 놓친다.

## 2. 근거 상세

### 2.1 내부 `get-visitors` (우리가 쓰는 것)

- 우리 코드: `reservations.py:78` `PATH_VISITORS = "visitor/v2/queries/get-visitors"`, `search()`(437~469줄). 요청 몸통은 `indexOfPage` · `countInPage:20` · `visitorName` · `phoneNumber` · `chartNumber` · `sort{by:lastVisitedDateTimeUtc, order:DESC}` 이다. 이름은 우리 쪽에서 앞뒤 공백을 지운 뒤 보낸다(`strip()`).
- 약 167줄 `v.get("email")` 은 `personal_of()` 안에 있다. 그 `v` 는 **내부 상세 `visitor/v2/queries/get-visitor`** 응답이다(`_detail_reads()` 592줄 `client.internal(PATH_VISITOR, …)` → 542줄 `personal_of(visitor)`). 목록(`search()`)은 지금 email 을 읽지 않는다. `items` 에 email 칸이 없다.
- 응답: `{data[], count}`. 각 항목의 키는 상세와 같은 35개이고, `email` 이 있으면 36개다. `deleted:true` 인 항목은 0건이었다.
- `count` 는 전체 맞은 수다. `countInPage` 를 100 · 500 · 1000 · 5000 으로 보내 봤고, 모두 200 이었다(500 이상이면 494명 전원). 상한은 보지 못했다(데모 인원이 494명뿐이다).
- 이름 검색 시험: 이름 모양 6종(한글 3자 동명이인 · 한글 3자 단독 · 라틴 대소문자 섞임+공백 · 라틴 대문자+공백 · 한자/가나 · 한글+라틴 섞임)에 대해 변형을 넣어 봤다. 대상이 잡혔는지(Y/N)는 다음과 같다.

| 변형 | 결과 |
|---|---|
| 그대로 | 6/6 Y |
| 앞 절반 | 6/6 Y(맞은 수는 늘어난다. 예: 1 → 16) |
| 가운데 부분 | 6/6 Y |
| 소문자 · 대문자 | 해당 4종 모두 Y |
| 공백 제거 · 공백 두 칸 | 해당 3종 모두 **N(0건)** |
| 앞 · 뒤 공백 추가 | 6/6 **N(0건)** |
| 단어 순서 바꿈 | 해당 3종 모두 **N** |
| 발음명(`phoneticName`) | 해당 4종 모두 Y. 라틴 이름 고객을 한글 발음명으로 찾는 경우도 Y(1건) |
| 여권 성+이름 | N |

- 이름 모양 분포(데모 공개 `getVisitor` 493명 기준): 한글만 227, 라틴만 106, 한자/가나 107, 한글+라틴 53. 공백이 든 이름은 215명, 앞뒤 공백은 0명이다. 발음명은 494명 중 11명만 채워져 있다.

### 2.3 공개 API (데모 키)

| 작업 | email 칸 | 이름 검색 |
|---|---|---|
| `getVisitor` | 없음. 응답 키는 `id · chartNumber · name · phoneNumber · dateOfBirth · gender · nationality · passportSurname · passportGivenNames` 이다. 스펙(`additionalPhoneNumber` 포함)과 같다. 493명 전수 확인 | — |
| `searchVisitors` | 응답에 없음. 요청의 `email` 은 **추가 조건**이라 단독으로 보내면 400 | `partOfVisitorName`(부분 일치)도 추가 조건이라 단독으로 보내면 400. `phone` · `chartNumber` · `dateOfBirth` 중 하나가 있어야 한다(스펙 설명과 실호출이 일치) |
| `findVisitor`(deprecated) | 응답에 없음(`id · chartNumber · name · phoneNumber`) | 이름만 보내면 **실제 이름이어도 0건**이었다(6종 모두). 200 에 빈 값 `{data{id:"", …}}` 이 온다. 이름+전화번호를 보내면 8명 중 6명이 잡혔다. 앞 2글자+전화번호는 0건이므로 정확 일치로 보인다 |

## 3. 정할 것 (결정하지 않고 모은다)

1. **email 이 비어 있는 고객**(데모 99%)을 어떻게 다룰지: 「찾을 수 없음」으로 끝낼지, 다른 식별값(전화 · 생년월일)을 더 받을지. 운영 지점의 채움 비율을 먼저 볼지도 정해야 한다.
2. **이름 검색의 페이지 크기**: 우리 `search()` 의 `countInPage:20` 을 그대로 쓰면 결과가 21건 이상일 때 대상을 놓칠 수 있다(데모 4명). 한 번에 크게 받을지(5000까지 받았다), `count` 를 보고 다음 페이지를 넘길지 정해야 한다.
3. **이름 정규화**: KOS 는 공백을 그대로 비교한다. 공백 차이(외국인 이름 띄어쓰기 · 성·이름 순서)로 0건이 나는 경우를 어떻게 할지. 우리 쪽에서 앞뒤 공백만 지울지(지금 코드), 공백을 바꿔 다시 검색할지, 발음명이나 여권 이름까지 범위를 넓힐지(여권 이름은 KOS 검색 대상이 아니다) 정해야 한다.
4. **이메일 대조 규칙**: 정확 일치로 할지, 대소문자와 앞뒤 공백을 무시할지. 데모에서는 차이가 없었지만 표본이 5개다. `@` 없는 저장값(1건)도 비교 대상에 넣을지 정해야 한다.
5. **이메일 대조 뒤 2명 이상**(동명이인 + 같은 email)일 때 무엇으로 가를지. 데모에서는 생기지 않았다(0쌍).
6. **부분 일치의 부작용**: 짧은 이름은 다른 사람의 이름에 포함되어 함께 걸린다(3자 이름 1개가 37건). 이메일로 거르면 결과는 1명이 되지만, 검색 결과가 커지는 것을 그대로 둘지 정해야 한다.
7. **내부 API 의존**: 이 경로는 공개 API 로 대신할 수 없다(email 칸 없음). 시스템 계정 토큰(약 14시간)과 브라우저 UA 조건까지 내부 API 에 묶인다. 이를 받아들일지 정해야 한다.
8. **시술권 조회 범위**: 공개 `getTicketBundlesQuery` 는 사용 가능한 묶음만 준다. 결과가 없으면 `{}` 다(조사 2). 「남은 시술권 없음」과 「고객을 못 찾음」을 응답에서 어떻게 구분해 보일지 정해야 한다.
