## 고객이 실물에서 만날 자리

- 링키 · 차티: 이메일이 비어 있는 기존 고객(데모 99%)은 모두 `404` 다. 처음 예약하면 KOS 에 같은 사람이 하나 더 생긴다(D-22 로 받아들인 것). 협업자 공유 문서에 이 점을 **첫 줄로** 적어야 「API 가 고장 났다」는 문의가 줄어든다(SPEC §8 앱 설명 절 목록에 이 항목이 없다).
- 짧은 이름 · 흔한 이름의 조회는 느려질 수 있다(W2). 데모 실측 107 ~ 235ms 는 이름 검색 결과가 1 ~ 37건일 때 값이다.
- `totalCount` · 가격이 산 때보다 작게 나오는 묶음이 있다(SPEC §4.3 이 이미 적음 — 좋다). 연동처 화면에 「구매 금액」으로 그대로 띄우면 고객에게 틀린 값을 보여 준다(Q-C).
- 외부 예약은 구역 · 담당자를 고를 수 없다. 데스크가 KOS 화면에서 바꾸게 된다(D-33 · 의도).

## WORK-012 점검 (§2 의 5)

- **WP 순서**: BE1(메뉴) → BE2(인증 · 기록 · 제한) → BE3(메뉴 API) → BE4(조회) → BE5(예약 — BE4 의 조회 함수를 씀) → BE6(Swagger · 전체 시험) → REVIEW → INFRA → E2E-LOCAL → DEPLOY → E2E-PROD. 의존 순서가 맞다. INFRA 는 env 이름이 고정돼 있어 병렬이 가능하다는 서술도 맞다.
- **완료 조건**: WP 마다 SPEC §9 의 T 번호 범위와 데모 실물 확인(BE1 행 수 · BE4 조회 · `lastVisitedDateTimeUtc` 유무)이 있다. 조사 1 §4 의 행 수(상품 101 · 옵션 323 · 구성 32 · 시술 804 · 진료항목 226 · 기기 302 · 약물 349 · 카테고리 15 · 국가 4)와 같다.
- **실물 확인**: E2E-LOCAL 에 조회(맞음 200 · 틀림 404)와 예약(기존 · 새 고객 각 1번)이 있고, 끝난 뒤 취소하는 것까지 있다. E2E-PROD 는 운영 호스트에서 키로 확인한다. 「실물 e2e 없이 done 금지」를 지킨다.
- **검증 범위**: WP 마다 그 WP 의 시험 + 이웃 회귀 1 ~ 2개만 돌리고, 전체는 BE6 끝에 한 번 돈다. 명령에 적힌 기존 시험 파일(`test_kos_sync.py` · `test_auth_roles.py` · `test_resv_detail.py` · `test_resv_write.py` · `test_openapi_docs.py`)은 `c9f30ac` 에 모두 있다.
- 걸리는 것: W9(actor 넘기는 법) · W13(그룹 id 자리). BE2 완료 조건의 「시험용 임시 경로 하나로 단언」은 그 경로를 지우는지가 안 적혀 있다(참고 3).
