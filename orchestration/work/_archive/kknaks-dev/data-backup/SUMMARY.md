# 작업 요약 — data-backup (kknaks-dev)

기간: `2026-09-20` ~ `2026-09-21`
결과: 아키텍처 초안·인프라 조사 리포트를 main 에 머지 (PR #50). 실측 4건이 미결로 남음

## 1. 무엇을 했나

메디솔브 사내 8개 서비스의 운영 DB를 맥스튜디오 백업 서버로 모으는 방식을 정하는 작업.
시니어는 덤프를 제안했고, 전송 시간이 문제라는 판단에서 대안을 설계했다.
논의 끝에 **베이스 백업 1회 + 바이너리 로그 상시 스트리밍**으로 방향을 잡고,
수집 방식을 엔진 단위 단일(`pg_receivewal` / `mysqlbinlog`)로 확정했다.
배포 대상인 맥스튜디오 k8s 인프라는 surveyor 워커를 발주해 조사했고,
그 결과로 통신 구간·배치 제약을 문서에 반영했다. 시니어 제안용 문서로 main 에 머지됐다.

## 2. 적용한 기술·개념

- **WAL 아카이빙 / binlog 시핑** — 덤프를 대체하는 수집 방식
  - 왜 이걸 골랐나: 8서비스 × 약 120GB(총 약 960GB)에서 전체 덤프는 전송량·복원 시간·소스 부하가 모두 감당 안 됨. 변경분만 보내면 전송량이 데이터 크기가 아니라 변경량에 비례
  - CDC(Debezium+Kafka)도 같은 로그를 읽지만 **디코딩해서 이벤트 스트림을 만드는** 기술이라 목적이 다름. 원본을 그대로 보관하는 쪽이 필요했고, 운영 인력이 1명이라 Kafka 운영을 붙일 수 없었다
  - 무엇이 어려웠나: 「덤프 vs CDC」로 시작했는데 실제 축은 **베이스를 물리로 뜰 수 있는가**였다. WAL은 블록 단위 물리 로그라 논리 덤프 위에 못 얹는다(`pg_control` 불일치로 기동 거부). MySQL binlog는 ROW 이벤트(논리)라 `mysqldump --source-data` 베이스 위에 얹힌다 — 이 비대칭이 엔진별 베이스 방식을 갈랐다
  - 근거: `reference/2026-09-19-data-backup/architecture.md` §3.2·§3.2.1

- **복제 프로토콜 스트리밍 (`pg_receivewal`)** — 수집 방식을 환경 무관 단일로 만든 열쇠
  - 왜 이걸 골랐나: 처음엔 `archive_command` 를 전제해서 「관리형 RDB는 셸을 못 써 → 논리 복제로 분기」라는 결론을 냈고, 호스팅 3형태별로 경로를 쪼갰다. `pg_receivewal` 은 파일시스템이 아니라 **네트워크로 붙는 클라이언트**라 관리형에서도 되고, 이걸 수집 방식으로 잡으면 환경 차이가 사라진다
  - 무엇이 어려웠나: 폴링이 아니라 **연결 유지 스트리밍**이라는 점. 주기 실행이면 실행 간격 사이에 소스가 로그를 회전시켜 체인에 구멍이 나고, slot으로 막으면 이번엔 소스 디스크가 찬다. `max_slot_wal_keep_size` 로 상한을 걸어 서비스를 보호하는 게 짝
  - 근거: `architecture.md` §2.2·§3.2 「스트리밍 동작 구조」

- **상시 재생 = 검증 내재화** — 복원 드릴을 별도 작업으로 두지 않는 구조
  - 왜: 백업은 조용히 썩고, 복원을 시도하는 시점은 이미 장애 상황이다. 재생 인스턴스가 매일 로그를 적용하며 살아 있으면 그 자체가 매일 도는 복원 검증
  - 근거: `architecture.md` §3.1 단계별 설명

- **GitOps 배포 제약 파악 (ArgoCD app-of-apps)** — 조사로 확정한 배포 경로
  - 앱 레포 GH Actions(arm64) → GHCR `<sha>-arm64` → `charts/*/values.yaml` image.tag write-back → root-app 자동 sync. `kubectl apply` 직접 금지
  - 근거: `reference/2026-09-19-data-backup/survey-k8s-infra-mac.md` §6

## 3. 막혔던 것 / 사고

- **스코프를 반복해서 넘었다** — 「§3.1까지 써라」에 §3.4·§4까지 썼고, 논의에 없던 「재해대비」를 목적에 넣었고, 확정된 안을 난이도 비교 때 다시 꺼냈다 → 사용자가 §3 전체 삭제·문서 전면 재작성을 지시 → 이후 「시킨 절까지만 · 논의된 내용만」으로 교정. 같은 지적이 한 세션에 네 번 나왔다
- **크기를 추측으로 낙관했다** — 실측 없이 「대부분 압축 덤프로 감당된다」고 말했다가 8×120GB를 듣고 뒤집었다. §2.5의 실측 항목을 먼저 닫았어야 했다
- **제약을 과장했다** — 「x86_64 베이스는 arm64에서 재생 불가」로 단정했으나, 양쪽 모두 64bit 리틀엔디안·`MAXALIGN 8`·`BLCKSZ 8192` 라 `pg_control` 검사를 통과할 여지가 있다. 「미지원·검증 필요」가 맞는 서술. 확실한 제약은 **메이저 버전 불일치**뿐
- **PR 머지 후 archive 검사가 막혔다** — 스쿼시 머지라 원본 커밋(`a6d4881`)이 main 히스토리에 없어 「미머지 의심」으로 중단. 내용 동일성(`git diff` 공집합)을 확인하고 `git reset --hard origin/main` 으로 정렬해 통과

## 7. 잔여

- **회사망 아웃바운드 5432/3306 개방 여부** — 조사 리포트 §8-11 「없음이 아니라 기록 없음」. `nc -zv <host> 5432` 로 확인
- **소스별 PG 메이저 버전** — 재생 인스턴스 버전을 결정. 섞여 있으면 버전별로 재생 인스턴스가 나뉨
- **크로스 아키텍처 재생 가부** — x86_64 베이스를 arm64 클러스터에서 재생. `pg_basebackup` 1회 + 기동으로 실측 (2차 조사 예정)
- **일 WAL·binlog 생성량 실측** — 시니어 설득의 핵심 수치. 아직 추정치뿐
- **아카이브 용량** — `pgdata` 100GiB(여유 93G) vs 필요 3TB 수준. 외장 스토리지 증설이 전제
- **§3.5 테스트 절차 미작성** — 로컬 compose 검증 / 배포 검증 순서를 논의만 하고 문서에 안 넣음
- 서비스별 엔진 배정(PG 몇 개 / MySQL 몇 개) 미확인
