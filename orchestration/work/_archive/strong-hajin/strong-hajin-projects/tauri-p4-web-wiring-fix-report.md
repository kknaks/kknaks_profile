## 3. W-1 — 브라우저 회차 키

**문제**: `captureId` 는 `useState(() => crypto.randomUUID())` 라 **마운트당 하나**다.
`start()` 가 `startBrowserRecording` 에서 던지면 `onChange` 가 불리지 않아 `item.status` 가
`waiting` 으로 남고 **같은 창에서 다시 시작**할 수 있다 → 2회차가 **같은 키**로 acquire 한다.
1회차의 늦은 해제가 2회차를 푸는 `E-08` 보호가 그만큼 얇아진다.

**고친 방식 — 키를 «분리»했다.** 브리프가 준 두 선택지(제거 / 별도 회차 키) 중 **별도 키**다.

- `captureId` 는 **서버가 녹음 회차를 짚는 값**이다(`startBrowserRecording` ·
  `stopBrowserRecording` 인자). 이걸 회차마다 갈면 **기존 브라우저 동작과 API 계약이 바뀐다** —
  금지 사항이다. 그래서 **그대로 두었다**
- 점유 키는 `wakeSession.current = newWakeSession()` 으로 **마이크가 열릴 때마다 새로** 뽑는다.
  회의 경로(`stream.ts`)와 같은 규칙이 됐다

→ 재시작하면 **다른 점유 키**가 쓰이므로 1회차의 늦은 해제가 2회차를 풀 수 없다.

## 4. W-3 — 언마운트 정리 실패를 «화면 밖»에 남긴다

**문제**: `stream.ts` 의 `releaseWake()` 는 `if (!stopped …) setState(...)` 인데, L-10 언마운트
정리에서는 `stopped = true` 가 **먼저** 서므로 **가장 흔한 해제 경로에서 `E-14b` 가 절대 안 보였다.**

**고친 방식 — 사실을 React state 밖에 적는다**(브리프: 「state 업데이트 없이도 사실을 남길 수 있는 방식」).

`shell.ts` 의 `releaseWakeGuard` 가 실패하면 **호출 지점과 무관하게** 기록한다:

- 모듈 기록 `cleanupFailures`(세션 키 집합) — 진단·시험이 읽는다(`wakeGuardCleanupFailures()`)
- `console.warn` 한 줄 — 화면이 이미 사라진 뒤에도 남는 **관측 가능한 사실**
- **같은 세션은 한 번만** 적는다(중복 경고 없음)

화면이 **아직 살아 있을 때만** 추가로 U-3 자리에 한 줄을 띄운다(`onClosed` 경로).

- **녹음을 다시 켜지 않는다.** 점유를 되살리지도 않는다 — 기록일 뿐이다
- 창을 닫으면 네이티브가 정리하므로(L-06) 문구도 「남을 수 있다」까지만 적는다

## 5. W-4 — 늦은 호출 가드

**문제**: `stream.ts` 는 `stopped` 와 `wakeSession !== session` 을 둘 다 보는데,
`BrowserRecordingPage` 의 `holdWake`/`dropWake` 에는 **언마운트·회차 가드가 없었다.**

**고친 방식 — 회의 경로와 규칙을 맞췄다.**

- `mounted` ref 를 두고 언마운트에서 내린다
- `holdWake`: 응답이 온 뒤 **`mounted` 와 «내 회차 키가 아직 최신인가»를 함께** 본다.
  둘 중 하나라도 어긋나면 상태를 건드리지 않는다
- `dropWake`: **키를 먼저 비우고** 해제한다 → 두 번 도는 정리에서도 같은 키를 두 번 풀지 않는다(멱등)
- 해제 실패 표시도 `mounted` 일 때만 — 사실 자체는 §4 가 이미 남긴다

## 6. 동시 호출 안전성 보강 — 시험 환경에서 관측한 경합

브리프가 요구한 **직렬화 단위 시험**을 쓰다가, 두 키를 **동시에** 발행하면 두 번째가
`{kind:"degraded"}` 로 떨어지고 **`invoke` 가 한 번만 불린다**는 것을 관측했다.

```text
INVOKE wake_guard_acquire {"session":"a", …}
RA= {"kind":"on"}   RB= {"kind":"degraded"}   calls= 1
```

**관측 환경**: `vi.mock` + `vi.resetModules()` 를 쓰는 **jsdom/vitest 모듈 러너**다.
그 환경에서 `call()` 이 **호출마다** `await import("@tauri-apps/api/core")` 하자 두 번째 동적
import 가 실패했고, `acquireWakeGuard` 의 `catch` 가 그것을 `E-14a` 로 받아 획득을
`degraded` 로 보고했다.

⚠ **이것을 «제품 결함»으로 단정하지 않는다.** 실제 번들러·브라우저에서 같은 specifier 의
동시 `import()` 는 **같은 약속을 돌려주고 두 번째가 실패하지 않는다.** 따라서 「사용자에게
이유 없는 U-3 이 보인다」는 것은 **확인되지 않은 추정**이고, 앞선 판에서 그렇게 쓴 것을
여기서 내린다(검수 R-2).

**그래도 보강은 유지한다**: 호출마다 동적 import 를 되풀이할 이유가 없고, 약속을 하나로
모으는 편이 **어느 환경에서도 옳다.** 즉 이것은 **결함 수정이 아니라 동시 호출 안전성 보강**이다.

**바꾼 방식**: 모듈 약속을 **한 번만** 만들어 공유한다(`corePromise`). 실패하면 캐시를 비워
**다음 시도가 다시 해 볼 수 있게** 둔다 — 한 번의 실패로 셸 기능이 영구히 죽지 않는다.

> 이 경합은 검수 WARN 목록에 없었고, 발주가 테스트 파일 1개를 열어 준 덕분에 드러났다.
> **다만 「시험이 없었으면 못 찾았을 제품 버그」로 기록하지 않는다** — 관측은 시험 환경의
> 모듈 러너에서 나왔고, 제품 환경에서 같은 실패가 난다는 증거는 없다(검수 R-2).

## 7. `open_external` / U-4 (W-5 · W-6)

**유지했다** — 브리프가 「Phase 3 의 실제 네이티브 커맨드 넷 계약에 포함된 기능이므로 유지」로
정리했고, Phase 3 셸이 실제로 그 커맨드를 연다. **임의 권한·운영 URL 을 더하지 않았다.**

**W-6(조용한 실패)은 고쳤다.**

| 상황 | 이전 | 지금 |
|---|---|---|
| 셸 없음 | `false` | `"absent"` → App 이 **기존 `window.open` 그대로** |
| 성공 | `true` | `"opened"` |
| **실패(`E-14c`)** | `true` → App 이 폴백도 안 해 **링크가 조용히 아무 일도 안 함** | `"failed"` + `console.warn` 기록 |

**실패에 웹 폴백을 «붙이지 않은» 이유**: 셸 안에서 `window.open` 은 **앱 창 안에 두 번째
웹뷰가 앉는** 길이고, U-4 가 막으려는 사고가 바로 그것이다. `E-14c` 의 「다시 시도하지 않는다」도
같은 방향이다. 그래서 **폴백 대신 «기록»으로** 조용한 실패를 없앴다.
