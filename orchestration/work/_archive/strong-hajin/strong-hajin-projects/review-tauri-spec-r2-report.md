  올바른데도. 두 문장이 **같은 사건**에 반대 결론을 준다.
- **원인**: 「**셸이 그 사건만으로 풀지 않는다**」와 「**웹이 녹음을 끝내며 푼다**」가 한 문장에 섞였다.
- **권장 수정 (AC-T17 을 셸 동작으로 다시 쓴다)**

  > 않는다** — 그 사건만으로 점유를 풀지 않는다. (녹음이 실제로 끝나 **웹이** 푸는 것은 별개이고

### R2-F2. **`degraded` 에서 빠져나올 길이 없다** — 「OS assertion 복구」가 계약상 불가능하다

- **상태 기계에 전이가 없다.** `spec-006:507-517` 의 전이 전부:
  `off→on` · `off→degraded` · `on→on`(같은 세션 재요청) · `on→off` · `degraded→off` ·
  `on→[*]` · `degraded→[*]` · `off→[*]`.
  **`degraded→on` 도 `on→degraded` 도 없다.** v0.1.0 에는 있었다(`renew` 가 재시도를 날랐다).
- **재요청이 재무장을 금지당했다.** `E-09`(`:457`)는 같은 세션 재요청에 「**성공으로 답하고 점유를
  늘리지 않는다**」이고, `:418-419` 도 `state` 를 acquire 시점의 값으로만 정의한다.
  **「OS 에 다시 걸어 본다」를 허용하는 문장이 한 줄도 없다.**
- **그 결과 두 곳이 실행 불가능해진다**
  1. **L-14 · AC-T19**(`:543`·`:704`) — 수동 절전 복귀 후 「녹음이 이어지고 있으면 **그대로
     유효하다** … 같은 세션 키로 한 번 더 걸어도 안전하다(멱등)」. 잠든 사이 OS 절전 방지가
     사라졌다면, 멱등 재요청은 **아무것도 하지 않는다.** 「다시 자동으로 잠들지 않고」라는
     AC-T19 의 합격 조건을 만족시킬 수단이 계약에 없다.
  2. **U-3 · `E-03`**(`:451`) — OS 호출 실패는 **acquire 시점에만** 보고된다. 두 시간짜리 회의의
     0분에 일시적으로 실패하면 **두 시간 내내 무방비**이고, 재시도도 재보고도 없다.
     v0.1.0 은 「다음 `renew` 에서 다시 시도한다」로 이 자리를 덮고 있었는데 **그 보상 없이 제거됐다.**
- **왜 FAIL 인가**: v0.2.0 의 약속은 「녹음 중에는 절전 방지가 유지된다」인데, **OS 쪽에서 풀린
  경우를 회복할 길도 알릴 길도 없다.** 막으려던 사고가 다른 문으로 들어온다.
- **권장 수정 (TTL 을 되살리지 않는다 — 더하는 방향뿐이다)**
  1. `E-09` 를 한 문장 고친다 — 「같은 세션 키의 재요청은 **점유를 늘리지 않는다.** 다만 그 시점에
     OS 절전 방지가 걸려 있지 않으면 **다시 건다**, 그리고 응답 `state` 는 **그때의 실제 상태**다」.
  2. 상태 기계에 `degraded → on`(재요청으로 재무장 성공)과 `on → degraded`(OS 쪽에서 풀림)를 넣는다.
  3. 웹이 재요청해도 되는 자리를 **사건으로만** 적는다 — 「문서가 다시 보이게 될 때 · 수동 절전에서
     깨어난 뒤」. **주기적 갱신이 아니고, 셸은 신호가 없다고 해서 절대 풀지 않는다** — 이 문장을
     같은 자리에 남겨 v0.1.0 구조로 되돌아간 것이 아님을 못박는다.
  4. U-3 은 「acquire 응답이 `degraded` 일 때」가 아니라 「**점유 상태가 `degraded` 인 동안**」 보이게 한다.

### R2-F4. **늦은 `acquire`** — 세션 키가 막지 못하는 누수. 실제 코드 형태에서 도달 가능하다

- 세션 키는 **늦은 `release`** 를 막는다(`E-08` · AC-T13). **반대 방향은 아무 문장도 없다.**
- **코드 형태**: L-01(`:525`)은 「**마이크가 실제로 열린 순간**」 획득이라고 못박았고, 그 자리는
  비동기다 — `frontend/src/features/meetings/stream.ts:251-255`
  ```
  void startMicrophone(...).then((handle) => { if (stopped) handle.stop(); else microphone = handle; })
  ```
  `stopped` 분기가 **있다는 사실 자체가** 「정리가 먼저 끝나고 마이크가 나중에 열리는」 순서를
  제품이 이미 겪는다는 뜻이다. 브라우저 인터랙션 경로도 같다 —
  `features/browser/BrowserRecordingPage.tsx:51-55` 는 `await` 둘을 지나서야 세션을 세운다.
- **실패 시나리오**: 사용자가 회의 화면에 들어갔다 바로 나간다 → 정리가 `release` 를 부른다 →
  뒤늦게 마이크가 열려 `.then()` 이 `acquire` 를 부른다 → **녹음은 없는데 점유가 선다.**
  그 세션을 풀 주체가 이제 아무도 없다(화면은 사라졌다). **창을 닫을 때까지 기기가 안 잠든다.**

  예측 가능한 경로다.
- **권장 수정**: §4 `wake_guard_acquire` 에 한 줄 — 「**그 녹음의 정리가 이미 끝난 뒤에 도착한
  획득은 걸지 않는다.** 웹은 늦게 열린 마이크를 닫는 같은 자리에서 획득도 취소한다」.
  (셸 쪽에 「이미 해제된 세션 키는 다시 살아나지 않는다」를 두는 것도 같은 문제를 닫는다 —
  둘 중 하나면 충분하고, 어느 쪽을 고를지는 구현의 몫이다.)

### R2-W1. `session` 키의 **유일성·재사용 금지**가 Validation 에 없다 — AC-T13 의 전제가 빠졌다

`spec-006:437` Validation 의 `session` 규칙은 「1~128 자 · **한 녹음 안에서 불변** · PII 금지」뿐이다.
**「녹음마다 달라야 한다」가 없다.** §4 본문(`:414-416`)에는 「회의 라이브는 마이크를 여는 회차마다
새로 만든다」가 있지만 **규칙 표에는 없다.** 구현이 회의 id 를 키로 쓰면 같은 회의를 다시 열 때
키가 겹치고, **AC-T13(지난 녹음의 늦은 해제가 지금 녹음을 풀지 않는다)의 보호가 그대로 사라진다.**
F-4 와 합쳐 키를 참조계수 대신 쓰는 선택 전체가 이 한 줄에 매여 있다.
**권장**: Validation 에 「**녹음 1회마다 새로 만든 값**. 지난 녹음의 키를 재사용하지 않는다」.

## 모호점 — 판단은 코디네이터 (FAIL·WARN 아님)

1. **`E-11`(미인증이 관측되어 스트림이 실제로 닫힌다)이 언제 발화하나.** 코드상 4401 은
   **핸드셰이크에서만** 나고 이 제품에는 자동 재연결이 없으므로, 열린 스트림이 인증 때문에 닫히는
   일은 실질적으로 **사용자가 화면을 다시 들어와 새로 붙을 때**뿐이다. S-8 3 이 「새로 붙으려 하면」으로
   정확히 적었으므로 모순은 아니지만, `E-11` 만 읽으면 더 자주 도는 것처럼 보인다.
2. **L-12(웹이 멈춤)와 AC-T19(수동 절전 복귀)는 충돌하지 않는다.** AC-T19 는 웹이 살아난 경우를
   전제하고, 살아나지 못하면 그것이 L-12 다. **L-14 가 녹음 생존을 판정하는 방법을 발명하지도
   않았다** — 「스트림·마이크가 살아 있나」는 제품이 이미 들고 있는 상태이고, 끊긴 녹음의 자동
   재연결을 만들지 않겠다고 Scope Out 에 못박았다(`:105-106`). **이 부분은 통과**다.
   다만 복귀 후 OS 절전 방지가 살아 있는지는 **R2-F2 가 닫혀야 답할 수단이 생긴다.**
3. **Windows 의 절전 방지가 스레드에 매인다**는 사실(조사 §4-2)은 SPEC 에 없다. 플랫폼 구현
   상세를 SPEC 이 요구할 일은 아니라고 본다 — 다만 R2-F2 의 수정에서 **「점유가 살아 있는 동안
   OS 절전 방지가 계속 유효해야 한다」**를 관찰 가능한 문장으로 한 줄 넣으면 이 자리도 함께 덮인다.
