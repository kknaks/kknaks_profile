### 2-1. 무엇이 바뀌었나

### 2-2. 채택 근거 — 검수 권고를 따르지 않은 이유

검수 F-1 의 권고는 「갱신을 타이머가 아니라 **녹음 청크**에 태우고, TTL 을 **최악 스로틀(분당 1회)의
3배 이상**으로 두라」였다. **계약 공백이 있다는 지적은 수용했다. 수단은 바꿨다.**

1. **청크 콜백이 스로틀되지 않는다는 보장이 없다.** MDN 의 `dataavailable` 문서는 이 이벤트가
   타임슬라이스마다 발생한다고 **설명**할 뿐 지연 없는 전달을 **보증하지 않는다**
   (<https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event>, 확인 2026-09-22).
2. **「분당 1회」는 Chromium 계열의 규칙이다.** 대상 웹뷰는 **WebKit(macOS)·WebView2(Windows)** 다.
   한 엔진의 수치를 다른 엔진에 적용해 「3배면 안전」이라고 **쓸 근거가 없다.**
3. 따라서 어떤 배수를 골라도 **「정상 녹음 중인데 신호가 늦었다」와 「웹이 죽었다」를 가르지 못한다.**
   가르지 못하는 판정으로 **OS 절전 방지를 푸는** 것은 — 이 SPEC 이 막으려는 바로 그 사고다.

**그래서 판정 자체를 계약에서 없앴다.** F-1 이 지적한 실패 시나리오(화면이 꺼지면 갱신이 늦어
점유가 만료 → 기기가 잠든다 → 녹음이 끊긴다)가 **구조적으로 발생할 수 없게 된다** — 만료가 없기 때문이다.
**검수와 다른 수단으로 같은 문제를 닫았고, 더 강하게 닫았다.**

### 2-3. 남는 한계 — 과장하지 않고 적었다

| 사건 | 누가 정리 | 근거 |
|---|---|---|
| 창 닫기 · 앱 종료 | **네이티브** (L-06) | `WindowEvent::CloseRequested`/`Destroyed` · `RunEvent::ExitRequested`/`Exit` |
| 문서 교체 · 재로드 | **네이티브** (L-09) | `PageLoadEvent::Started` · `on_navigation` |
| 프로세스 소멸 | **OS** (L-13) | 절전 방지가 프로세스·스레드에 매인 자원이다 |
| 앱 내 화면 전환 | **웹만** (L-10) | 문서가 그대로라 네비게이션 사건이 아니다 |
| 같은 문서 주소 변경 | **아무도 — 트리거 아님** (L-11) | 이것을 해제 트리거로 보면 녹음 중에 풀린다 |
| **웹이 살아 있는 채로 멈춤** | **아무도. 탐지 불가** (L-12) | 아래 |

**웹 콘텐츠 프로세스 소멸을 Tauri 공개 API 에서 받는 경로를 문서로 확인하지 못했다.**
`RunEvent::WebviewEvent` 가 있으나 문서에서 해당 통지를 찾지 못했다(조사 §10-3). 플랫폼 층에는
그런 델리게이트가 있지만 **확인 못 한 것을 「된다」고 쓰지 않았다.**

그래서 **v0.1.0 의 「셸이 마지막 방어선이라 점유가 영구히 남는 경로를 두지 않는다」는 과장을
철회했다.** L-12 가 그 경로다. 결과는 「사용자가 창을 닫을 때까지 기기가 자동으로 잠들지 않는다」 —
**녹음이 끊기는 것보다 덜 나쁜 쪽**이고, 그 선택을 SPEC 에 적었다.
