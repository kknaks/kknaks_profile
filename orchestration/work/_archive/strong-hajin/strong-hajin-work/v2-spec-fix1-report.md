## F-1 — `POST /api/tasks` 의 타인 지정

**코디 판단대로 「호환 방식」이 가능했고, 그것이 사실이기도 했다.**

읽어서 확인한 것 — `POST /api/tasks` 는 한 명령이지만 `decide_task_creation()` 이 경로를 가른다.
담당이 없거나 본인이면 `self`, **다른 사람이면 `horizontal`(수평 요청)** 이고 `WORK_REQUEST_CREATE`
역량을 물은 뒤 `WorkRequestApplication.create()` 를 부른다. `create_assigned_task()` 를 **지나지 않는다.**
관리자 배정(`managed`)은 이 입구로 들어오지 않는다(`POST /api/tasks/assign` 전용).
→ BASE-002 **O-26** 으로 실었다.

그래서 **입구를 없애거나 타인 지정을 거부할 필요가 없다.** 그 입력은 W1 에서도 요청이었고,
v2 가 바꾸는 것은 그 요청의 **응답 단계**뿐이다. 같은 행위 → 같은 결과(K-10).

- SPEC §4 API 표의 `POST /api/tasks` 행을 「담당이 없거나 본인이면 본인 업무, 다른 사람이면 **요청 발송**」으로.
- SPEC §4 Request/Response 에 **「생성 (한 명령, 두 갈래)」** 문단 신설 — 타인 갈래의 응답이
  `POST /api/work-requests` 와 **같다**는 것, REST·MCP·AX 가 같다는 것.
- **무단 자동 전환이 아님을 명시** — 「서버가 배정을 요청으로 바꾸는 것이 아니다. 이 갈래는 원래부터
  요청이다」 + E-2(권한 밖 배정의 자동 요청 전환 금지)는 그대로 살아 있다.
- SPEC-001 상단 안내에 그 갈래를 **입구 유지 · 응답 단계만 대체**로 적었다.
- DEC-002 **D-3** 에 근거 문단 추가.
- §6 인수조건 2줄 추가(두 입구 동일 결과 · 타인 갈래의 필드 거절).

**곁가지로 U-3 이 닫혔다** — 그 갈래는 `parent_task_id`·`start_date`·`project_id` 를
`_refuse_unsupported_horizontal_fields` 로 **명시 거절**한다. BASE-002 **O-27** 로 싣고
U-3 행과 「과거 관측과의 차이」 행을 **닫힘**으로 갱신했다.
→ 하위 요청에 상위를 붙이려면 `POST /api/work-requests`(거기서 `parent_task_id` 가 신규로 열린다)다.
**이 차이는 v2 가 만든 것이 아니다.**

## F-2 — 배정 관측과 OQ-204

- BASE-002 **O-28** 추가: `assign()` → `create_assigned_task()` 가 `status="active"`,
  `accepted_at=now`. 주석이 「관리자 배정도 수락을 기다리지 않는다」라고 적는다.
  수락이 붙는 배정은 `hand_to()`(첫 지정, O-14)와 `reassign()`(교체, O-12) 둘뿐이다.
- **「규칙이 셋이라 재승인이 필요하다」로 만들지 않았다.** DEC-002 에 **§ 범위 기록**을 새로 두고
  세 줄로 갈랐다 — ① 신규 관리자 배정 **현행 유지** · ② 무담당 첫 지정 **현행 유지** ·
  ③ 담당 교체 **v2 적용**(V-18 이 직접 확정한 자리).
- OQ-204 를 **사용자 결정 표에서 내리고** 범위 기록 + 기본값 통보로 옮겼다.
  초판의 틀린 문장(「배정은 지금처럼 지정 → 상대 수락」)은 **정정 각주**로 남겼다.
- SPEC §1 Scope Out 에 「회귀로 지킬 현행이 한 모양이 아니다」 세 줄을 넣었다.

## F-3 — 수락 후 취소

- SPEC §4 API `cancel` 행: **수락된 요청 Task 에서는 거부**. `proposals(kind=cancellation)` 로만.
  수락 전 요청 Task · 본인 업무 · 배정 업무는 **현행 그대로 (기존 동작 보존)**.
- **수락 전 철회를 다른 권한자에게 확장하지 않았다** — v2 가 연 것은 요청자의 `withdraw` 이고,
  타인의 취소 권한을 넓히지도 좁히지도 않는다(침묵은 폐기가 아니다).
- Case Matrix 에 `WORK_CANCEL_REQUIRES_AGREEMENT`(409) 추가 — 요청자·담당자·관리자 **모두** 같다.
- §4 State 다이어그램에 단서, §5 권한표에 행위별 두 줄, §3 S-11 에 3·7 항 추가,
  §6 인수조건 2줄 추가(거부 1 · 수락 전 현행 회귀 1).

## F-4 — 회의 후속 승격

**「시스템 발신」으로 임의 변경하지 않았다.** 코드가 이미 둘을 가르고 있다 —
요청자 자리에는 `system:meeting` 이 서고 **누른 사람은 `promoted_by_member_id` 로 남는다**
(`requester_kind` 가 둘을 가른다). BASE-002 **O-30** 으로 실었다.

- §4 Validation 의 「본인 지정은 요청이 아니다」를 **`POST /api/tasks` 의 경로 판정**으로 좁혔다.
  요청 표면 전체의 금지가 아니다.
- 승격의 **본인 지정 허용을 보존**했다(`allow_self_assignment`). 전수 grep 결과 그 값을 켜는
  호출부는 **회의 승격 둘뿐**이고 일반 요청 표면은 꺼져 있다 — 그것도 기존 동작으로 적었다.
- 승격 요청도 v2 에서 **수락 대기로 선다. 자동 수락을 신설하지 않았다**(L-15 · M-7).
  「내가 나에게 보낸 요청을 내가 **명시적으로 수락**한다」로 처분을 적었다.
- §5 표면 일치에 출처/actor 보존 문단(K-6)을 넣었다.

## F-5 — OQ-203 (완료 보고 제출)

**「제출 차단 확정」으로 승격하지 않았다.** 원문이 직접 열어 둔 자리임을 확인했다 —
생명주기 v2 §5.4 마지막 줄 「상위의 **최종 완료**를 막는 규칙은 **확정**이며, 그 전에 결과를
제출할 수 있는지는 **별도로 정한다**」. 작업계획서 A7 도 「**최종 완료** 시도」다.

세 의미를 갈라 적었다 — 본인·배정 업무의 `complete`(=최종 완료) / 요청 Task 담당자의
`complete`(=완료 보고 제출, `state=done`+`awaiting_review`) / 요청자의 승인(=최종 완료).

- §4 `complete` 에 **선행 검사가 어디에 걸리는지** 3행 표. **별도 endpoint 를 신설하지 않는다**고 명시.
- §5 상위 완료 차단에서 「기본값은 막지 않는다」를 **(기존 동작 보존 — O-19)** 로 근거화.
  기본값에서 생기는 `done`+`awaiting_review` 구간이 **상위로 새지 않는 이유**(완결 판정은 승인까지)를 적었다.
- §3 S-7 을 두 갈래로 다시 썼다. §6 인수조건·A7 추적 행·10단계 6행도 같이 맞췄다.
- OQ-203 을 두 안(A 제출도 막는다 / B 기본값)과 **각 안의 영향**으로 다시 썼다.
  **모순은 제거됐다** — 이제 어느 쪽을 골라도 문서가 맞고, 뒤집히면 §6 인수조건 한 줄만 바뀐다.

## 사용자에게 올릴 진짜 정책 질문 — 셋

**정정 전에는 올릴 수 없었던 OQ-203 이 이제 올라갈 수 있다.** 나머지 둘은 이번 정정에서 드러났다.

### OQ-203 — 상위의 완료 「보고 제출」도 막나

- **원문**: 생명주기 v2 §5.4 — 「상위의 **최종 완료**를 막는 규칙은 **확정**이며, 그 전에 결과를
  제출할 수 있는지는 **별도로 정한다**」. 작업계획서 A7 도 「최종 완료 시도」다.
- **안 A (제출도 막는다)**: 담당자가 하위를 먼저 닫아야 보고할 수 있다. 「하위는 남았지만 내 몫은
  끝났다」를 알릴 자리가 없어진다.
- **안 B (기본값 — 제출은 열고 승인에서 막는다)**: **기존 동작 보존**(O-19). `done`+`awaiting_review`
  인데 하위가 남은 구간이 보이지만, 그 Task 는 **완결이 아니므로**(승인까지여야 완결) 상위로 새지 않는다.
- **둘 다 새 명령·새 endpoint 를 만들지 않는다.** 본인·배정 업무는 제출과 최종이 갈리지 않아
  **어느 안이든 결과가 같다.** 뒤집히면 §6 인수조건 **한 줄**만 바뀐다.

### OQ-205 (신규) — cutover 이전 행에서 상위 완료가 새로 막힐 때

- **원문**: 없다. P-8(일괄 전환 금지)과 V-15(미완결 하위면 최종 완료 차단)가 만나는 자리이고
  **원문이 이 충돌을 다루지 않았다.**
- **안 ① 그대로 막는다** — 규칙이 한 벌이라 설명이 쉽다. 이미 `done` 이되 승인 이력이 없는 기존
  요청 하위 때문에 **상위 완료가 실무에서 멈추는 행**이 생긴다.
- **안 ② cutover 이전에 생긴 하위는 완결 판정에서 기존 기준(`state=done`)으로 읽는다** — 실무가
  멈추지 않는다. 대신 한동안 **두 기준이 공존**하고 그 경계를 오류 문구가 설명해야 한다.
- **어느 안도 승인 사실을 만들어내지 않는다.** 판정 기준을 고르는 선택이다.
  막히는 행의 **개수**는 읽기 전용 점검(`30-work/`)이 센다 — 지금 세지 않았다.

### OQ-206 (신규) — 요청자 자리가 시스템인 요청

- **원문**: 정의 v2 §2.5·§2.9 는 「**요청자**가 확인한다」까지다. 회의 후속 승격의 요청자는
  `system:meeting` 이고(O-30) 확인자는 요청 행의 `requester_id` 에서 나온다(O-29).
  **원문이 이 조합을 답하지 않았다.**
- **안 A (기본값 — 기존 동작 보존)**: 지금 값을 그대로 쓴다. 확인이 **사람에게 닿지 않는 자리**가 남는다.
- **안 B (누른 사람 `promoted_by_member_id` 를 확인자로)**: 확인이 사람에게 닿는다. 대신
  「확인자 = 요청자」에 **예외가 하나** 생긴다.
- **출처(회의)와 실제 actor(누른 사람) 기록은 어느 안에서도 바뀌지 않는다**(K-6).

**셋 다 착수를 전면 차단하지 않는다.** OQ-203 은 인수조건 한 줄, OQ-206 은 승격 경로 한 자리,
OQ-205 는 **cutover 시점에** 답하면 되는 질문이다 — 요청·본인 업무 축의 A1~C2 는 전부 그대로 선다.
