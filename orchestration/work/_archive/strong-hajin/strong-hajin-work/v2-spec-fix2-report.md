## RF-1 — 승격 요청의 「기존 동작 보존」이 두 갈래다

**읽어서 확인했다(읽기 전용).** 리뷰의 지적이 사실이고, **두 자리를 갈라 관측으로 실었다.**

- **O-31** — 요청자 전용 조작(**수정·재상신·철회**)의 판정은 `requester_id` **또는**
  `promoted_by_member_id` 다(`requests.py:739-748` · `request_lifecycle.py:127-129`·`:185-187`).
  docstring 이 이유를 직접 적는다. **완료 확인자를 뽑는 `_requester_of()` 에는 그 대행이 없다**
  (`application.py:649-653`).
- **O-32** — 완료 확인 명령은 `reviewer_id == principal.id` 인 사람에게만 열린다
  (`policy.py:55-70` · `action_center.py:1320-1323`). **둘 다 직접 읽어 확인했다.**

**정정 내용**

1. **OQ-206 을 완료 확인 한 조각으로 좁혔다.** 수정·재상신·철회는 **기존 동작 보존**으로 내렸다
   (SPEC §5 표면 일치 · §5 권한표 · DEC M-19 · OQ 표 각주).
2. **안 A 를 기본값에서 뺐다.** 지금 값을 그대로 쓰면 「확인이 닿지 않는다」가 아니라
   **「승인 명령을 부를 수 있는 사람이 0명」**이고, 그 Task 를 하위로 둔 상위도 완료할 수 없다.
   **사람이 승인할 수 없는 상태를 기본값으로 확정하지 않는다** — 답이 오기 전까지
   **승격 경로의 완료 승인은 구현 대상이 아니다**로 적었다.
3. **새 취소·조건 변경 제안에 「기존 구현이 있다」고 주장하지 않았다.** 그 명령은 v2 신규다.
   정할 것은 **「요청자」 판정을 어느 모양으로 쓰는가**이고 **기술 계약**임을 명시했다 —
   요청자 전용 조작의 기존 판정과 **같은 모양을 쓴다 (제안)**. 완료 확인과 달리 여기에는
   **부르는 사람이 반드시 있다.**

## RF-2 — OQ-205 의 전제 정정

**전수로 확인했다** — `DONE` 을 대입하는 자리는 `backend/src` 전체에서 **한 곳**
(`application.py:562`, `accept_delivery` 안)이고, 요청 Task 의 `DONE` 전이는 그 앞에서 거부된다
(`lifecycle.py:81-83`). `accept_delivery` 는 **반드시 판단 행을 남긴다**(`:559-560`). → **O-33**.

**정정 내용**

1. **정상 기존 `done` 요청 하위는 승인 사실의 매핑으로 읽는다** — 없던 승인을 만들지 않으므로
   P-8 을 어기지 않는다. **기술 호환 매핑**임을 SPEC §5 cutover 와 DEC 에 적었다.
2. **「DB 에 0건」을 단정하지 않았다.** 코드 경로의 사실과 실행 DB 를 가르고, 예외 행(유산 행 등)은
   **Phase 0 읽기 전용 SELECT** 로 센다 — **BASE-002 U-6** 신규. **0건이 아니면 그때 사용자에게 올린다.**
3. **OQ-205 를 사용자 결정 표에서 내렸다**(SPEC §7 · DEC § 착수 전 점검). **RW-6 이 함께 닫혔다** —
   그 표의 「사용자」 담당 표기가 사라졌다.

## RW-1 · RW-2 — 두 입구

- **RW-1**: 인수조건의 자기모순을 없앴다. 「응답·오류·권한이 같다」를 **「결과 상태와 권한이 같다」**로
  좁히고, **입력 계약이 다르다는 줄과 모순되지 않는다**고 한 줄 더 적었다.
- **RW-2**: **응답 본문 모양을 바꾸지 않는다.** `POST /api/tasks` 의 201 은 **Task 투영 하나**
  그대로이고(SPEC-001 계승), v2 가 바꾸는 것은 **그 Task 의 값**이다. 임의 breaking 확장을 하지 않고
  §1 대체표에 그 행을 명시했다. SPEC-001 상단 안내에도 같은 문장을 넣었다.

## RW-3 — 줄 번호

**절과 인용 문구로 지목**했고 SPEC-001 상단 안내도 같이 고쳤다. **코드 관측의 경로·줄은 BASE-002 에

## RW-4 — 제출/승인의 실물 반영 (가장 큰 정정)

**실물은 이렇다** — 제출은 **별도 입구** `POST /api/tasks/{id}/completion-report` →
`submit_completion()` 이고 **하위 검사가 없다.** 승인 `accept_delivery()` 에는
**`_require_children_finished` 가 이미 있다.** → **O-34**. 그리고 **O-19 를 다시 썼다** —
그 건너뛰는 가지는 요청 Task 에서 **도달하지 않는다**.

**정정 내용**

1. **SPEC §4 API 표에 `completion-report` 행을 세우고**, `complete` 행은
   **「최종 완료 — 본인·배정의 자리. 요청 Task 에서는 거부」**로 고쳤다(기존 동작).
2. **「`complete` 하나로 통합」처럼 읽히던 문단을 「명령이 둘이고 이 SPEC 이 합치지 않는다」로 다시 썼다.**
   **불필요한 API 통합을 피하고 기존 입구를 호환**하면서 v2 의미(제출 ≠ 최종 완료)를 보장한다.
   표면 값은 SPEC-001 계약대로 `done` + `derived.approval=awaiting_review` 다 **(제안)**.
3. **DEC D-5 를 정정**했다 — 「승인 쪽 차단은 **이미 있고**, 새로 닫는 것은 **완결 판정(O-20)** 하나」.
   M-8 의 근거도 O-19 → O-34 로 바꿨다. Rationale 의 리스크 문단도 같이 고쳤다.
4. **OQ-203 의 두 안은 그대로 유효하다** — 고른 것은 「제출 명령에 검사를 더할 것인가」 하나다.
   §3 S-6·S-7, §6 인수조건, §5 상위 완료 차단, Case Matrix 비고를 같은 말로 맞췄다.

## 프론트 범위 반영 — 이번에 스펙까지만

**최신 승인**(「아니 이제 프론트까지 같이 작업 할 수 잇는거 같아서」)을 반영하되 **과거 이력을 보존**했다.

- **BASE-002 입력 2** — 초판 세 줄을 그대로 두고 **갱신 승인**을 아래에 덧붙였다.
  **E2E 사용자 담당은 갱신되지 않았다**고 명시. **입력 5**(확정 시안 + 분석 3종)를 신설하고,
  **분석 3종은 시안을 읽은 보고서이며 `03` 은 14:29 스냅샷 대조라 최신 SPEC 대조가 아니다**를 적었다.
- **DEC-002** — 머리말·D-2·Scope 를 갱신하고 **초판 문장을 각주로 보존**했다.
  **§ 시안 반영**을 신설해 보고서의 물음을 **세 갈래**로 갈랐다.
- **SPEC-003 §2 UX Contract** — 「해당 없음」을 걷어내고 **확정 시안 기준 UX 계약**으로 다시 썼다
  (2.1~2.12). 기존 SPEC-001/002 본문과 SPEC-003 §3~§7 의 계약은 **그대로 보존**했다.

**§2 가 연결한 것** — 탭(소유·종결 축 ↔ 생성 행위 축) · 상태와 파생 표시의 **매핑표** · 표 세 벌 ·
**상하위 두 단계** · 행 액션 ↔ 명령 · 필터 칩(파생 조건) · 생성 모달(세 행위가 갈리는 자리) ·
수신함(자동 수락 없음) · 캘린더 · 내비 · **부품·데이터 책임 3갈래 표** · 원문 화면 요구 F-1~F-8.

**가른 방식 (브리프 §4 그대로)**

- **상태 vs 배지** → **상태 넷 + 파생 표시**로 이미 닫혀 있다. 시안의 배지는 그 표현이다.
- **탭 ↔ 세 행위** → **축이 다르다.** 대응표를 만들지 않았다.
- **dev `StateSwitch`** → **시안 원문에 답이 있다**(「remove when implementing」) — 제품 제외.
- **별표·미읽음·출처·근무 시간·회의 일정** → **부재의 종류를 갈랐다** — 출처는 개념은 있으나
  봉투 계약이 없다 / 아바타·수신 시각은 파생 가능해 보이나 **확인되지 않았다**(U-7) /
  **미읽음은 정의 자체가 없다** / 근무 시간·회의 일정은 **새 계약**이다.
- **승인 없는 새 서비스** → **자동으로 추가하지 않았다.** 메일·메신저 통합 전체와 시안 내비의
  새 페이지 전량을 **Out** 으로 적고, **무엇이 설계되지 않았는지만** M-20~M-24 로 좁게 기록했다.
- **시안에 상세가 없는 것을 정책 부정으로 읽지 않았다** — 상하위·취소/재개·담당 변경 대기는
  **미설계**로 표시하고 계약은 그대로 세웠다.

**인수조건** — §6 에 **UX 계약 U-1~U-15** 를 더했고, 각 줄에 **에이전트 자동 검증 / 사용자 브라우저
E2E** 를 나눠 적었다. **계약이 없는 요구(M-21~M-24)는 인수조건으로 세우지 않았다.**

**WORK-002 는 쓰지 않았다** — 다음 단계다.
