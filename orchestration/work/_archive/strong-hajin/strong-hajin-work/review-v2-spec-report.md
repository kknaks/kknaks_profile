## 위반 (FAIL 사유)

### F-1. `POST /api/tasks` 의 타인 지정 경로가 계약에서 사라졌다 — 수락 대기를 우회한다

- `20-spec/spec-003-task-lifecycle-v2.md:307` — `POST /api/tasks` 를 **「본인 업무 생성」**으로만 적는다.
- 그런데 **W1 계약에서 이 경로는 타인 지정 경로다**:
  - `20-spec/spec-001-work-management.md:412` 「업무 생성 — **본인 또는 수신자 지정**」
  - `20-spec/spec-001-work-management.md:458` 「`assignee_id` … 다른 사람이면 그 사람에게 **즉시 배정**」
  - `20-spec/spec-001-work-management.md:466` 「`assignee_id` 가 남이어도 `state` 는 `open` 이고
    **「수락 대기」에 해당하는 값이 없다**」
  - `20-spec/spec-001-work-management.md:606` 담당의 출처에 **`수평 요청`** 이 들어 있다
- 실물 코드도 같다 — `backend/src/ax_workspace/entrypoints/http.py:1261-1284`,
  docstring 이 **"업무 생성 — 본인 또는 수신자 지정. 담당이 남이어도 **수락 없이** 그 사람의 업무가 된다."**
  이 경로는 `parent_task_id` 도 이미 받는다(`http.py:1282`).
- **SPEC-003 은 이 경로를 어떻게 할지 한 줄도 적지 않는다.** §1 대체 관계는 「일반 요청의 즉시 배정」만
  가리키고(`:67`), §4 Validation(`:433`)은 `work-requests` 쪽 `assignee_id` 만 다루며,
  Case Matrix(`:445-462`)에 해당 오류 코드가 없다.
- 근거(원문): 작업계획서 §4.3 「**HTTP·MCP·AI 생성·회의 후속 업무 등 일반 요청을 만드는 모든 경로에
  같은 규칙을 적용한다**」 · 정의 §2.4(V-9).

**무엇이 깨지나**: 구현자가 SPEC-003 만 읽으면 `POST /api/tasks` 의 타인 지정이 그대로 살아남는다.
같은 제품 안에서 한 문으로는 수락 대기가 서고 다른 문으로는 수락 없이 담당이 선다 — A2 의 인수조건
(「발송 직후 활성 담당이 없다」)이 **다른 입구에서 무너진다.**

**최소 정정**: §4 API 표의 `POST /api/tasks` 행에 「`assignee_id` 는 **본인만** 받는다. 타인 지정은
`POST /api/work-requests` 로 보낸다」를 적고, Case Matrix 에 오류 한 행(코드값은 (제안))을 더한다.

### F-2. DEC-002 OQ-204 의 사실 진술이 실물 코드와 다르다 — 사용자가 틀린 그림으로 판단하게 된다

- `10-decision/decision-002-task-lifecycle-v2.md:326` OQ-204 Next —
  「이대로 두면 배정은 지금처럼 **「지정 → 상대 수락」**으로 남는다」
- **신규 배정은 수락을 기다리지 않는다.** `POST /api/tasks/assign`
  (`entrypoints/http.py:1384`) → `modules/work/assignments.py:86 assign()`
  → `platform/work_tasks.py:1713 create_assigned_task()` 가
  `status="active", accepted_at=now` 로 담당을 세운다(`work_tasks.py:1760-1762`).
  바로 위 주석이 **「관리자 배정도 수락을 기다리지 않는다 — 명령이 성공하면 상대의 업무 목록에 바로 선다
  (WORK-001 Phase 4)」**(`work_tasks.py:1758-1759`).
- `20-spec/spec-001-work-management.md:413` 도 「관리자 직접 배정. **즉시 활성 담당으로 선다**」다.
- 수락이 붙는 배정은 **둘뿐**이다 — 담당 없는 업무의 첫 지정 `hand_to()`(`work_tasks.py:1616-1645`,
  `status="pending"` + 수락 판단 항목)와 담당 교체 `reassign()`(`work_tasks.py:1825-1861`).
- **BASE-002 § 현재 관측 — 담당 관계와 변경(O-11~O-16)에 `assign()`/`create_assigned_task()` 경로가
  아예 없다.** O-14 는 `hand_to()` 만 보고 있고, DEC-002 는 그 한 줄로 배정 전체를 일반화했다.

**무엇이 깨지나**: OQ-204 는 「현행 유지」를 고르라고 사용자에게 올라간다. 사용자가 보는 「현행」이
사실과 다르다. 실제로는 **배정 안에 두 규칙이 섞여 있고**(신규=즉시 active, 첫 지정·교체=수락 대기),
요청만 수락 대기로 되돌리면 제품에 **세 번째 규칙**이 생긴다. 이것이 사용자 판단 거리다.

**최소 정정**:
1. BASE-002 § 현재 관측에 `O-26` 추가 — 「`assign()`/`create_assigned_task()` 는 `status="active"`,
   `accepted_at=now`. 관리자 배정은 수락을 기다리지 않는다 (`platform/work_tasks.py:1755-1762`)」.
2. DEC-002 OQ-204 Next 를 「현행 배정은 **두 갈래**다 — 신규 배정은 즉시 `active`, 첫 지정·교체는
   수락 대기. 요청만 바꾸면 규칙이 셋이 된다」로 정정.
3. SPEC-003 §1 Out of scope(`:116-117`)에 그 사실을 한 줄로 붙인다(회귀로 지킬 「현행」이 무엇인지가
   지금은 문서 어디에도 없다).

### F-3. 「수락 후 취소는 제안–동의로만」과 직접 취소 명령이 같은 문서 안에서 부딪힌다

- `spec-003:312` — `POST /api/tasks/{id}/cancel` 「직접 취소 — 사유 필수 | **담당자 · 요청자 · 관리자**」
  (SPEC-001:418·688 을 그대로 계승)
- `spec-003:759` 인수조건 — 「**수락 후 취소는 제안 → 담당자 동의로만 반영되고**, 응답 전에는
  아무것도 바뀌지 않는다」
- `spec-003:505·508` 상태도도 `직접 취소` 를 `cancelled` 로 가는 전이로 그대로 둔다.
- 원문: 정의 v2 §2.8 「수락 후 취소 — 요청자가 취소를 **제안**하고 담당자가 **동의**하면 취소.
  응답 전에는 기존 상태 유지」(V-19) · 생명주기 §6.1 같은 표.

**무엇이 깨지나**: 수락된 요청 Task 에서 요청자가 `cancel` 을 직접 부르면 담당자 동의 없이 끝난다.
담당자도 단독으로 끝낼 수 있다. **제안–동의 경로가 선택지로 전락**하고 B6 인수조건이 다른 문으로 깨진다.

**최소 정정**: `POST /api/tasks/{id}/cancel` 행을 「**요청 Task 는 수락 전까지만**(요청자 철회와 같은 뜻).
수락 후에는 `proposals(kind=cancellation)` 로만 취소된다. 본인·배정 업무는 현행 그대로」로 좁히고
Case Matrix 에 오류 한 행을 더한다. 상태도의 `직접 취소` 에도 같은 단서를 단다.

### F-4. §4 Validation 의 「본인 지정은 요청이 아니다」가 현행 회의 후속 승격 계약을 깬다 — 문서 내부에서도 어긋난다

- `spec-003:433` — 「`assignee_id`(요청) … **본인 지정은 요청이 아니라 본인 업무 생성**」
- 그러나 **회의 후속 승격은 본인 지정도 요청으로 보낸다**:
  - `bootstrap/application.py:1857-1858` 주석 — **「담당이 자기 자신이어도 요청으로 간다 —
    Task 를 바로 세우는 갈래가 없다 (SPEC-004 §9-5)」**, `allow_self_assignment=True`
  - `bootstrap/application.py:3573` (MCP 경로)도 같다
  - `modules/work/request_lifecycle.py:98` 가 그 조합을 `assignee_validation="none"` 으로 받는다
- 같은 SPEC 이 `spec-003:682` 에서 「**회의 후속 승격은 위 발송 계약을 그대로 쓴다. 우회 adapter 를
  두지 않는다**」고 적는다 → **§4 가 금지한 입력을 §5 가 요구한다.**

**무엇이 깨지나**: 승격 경로가 계약상 불법 입력이 되거나, 아니면 우회 adapter 가 생긴다. 둘 다

(자동 수락은 L-15·M-7 로 막혀 있다).

**최소 정정**: 그 줄을 「**사람이 직접 보내는 요청**에 한한다. 회의 승격 등 시스템 발신 요청의
본인 지정은 **기존 동작 보존**」으로 좁히고, 본인 지정 요청이 수락 대기로 서는지 한 줄로 적는다
(자동 수락은 M-7 이므로 「수락 대기로 선다」가 기본값이 되어야 앞뒤가 맞다).

### F-5. OQ-203 의 기본값이 이 SPEC 자신의 계약과 모순된다

- `spec-003:615` — 상위 완료 차단은 「**완료·승인 명령의 선행 검사**」다.
- `spec-003:619` — 「완료 **「보고 제출」**을 막을지는 (미정) — OQ-203. **기본값은 막지 않는다**」
- `spec-003:391` — `POST /tasks/{id}/complete` 에 「추가된 선행 검사 … 하나라도 있으면 **거부**」
- `spec-003:207`(S-7 = A7) — 「디자이너가 디자인을 **완료하려 하면 거부된다**」
- `spec-003:197`(S-6 1) — 담당자의 **완료 = 완료 보고**다(`state=done` + `approval=awaiting_review`).
  별도의 「보고 제출」 명령이 §4 에 **없다.**

즉 이 계약에는 「제출」과 「최종 완료」를 가르는 명령이 없으므로 **이미 제출 단계에서 막고 있다.**
「막지 않는다」는 기본값은 구현될 자리가 없다. 원문(생명주기 §5.4 · example §6.4)이 연 미정은
**명령이 둘일 때** 의미가 있는 질문이다.

**최소 정정**: §5 에 「요청 Task 의 `complete` 가 곧 완료 보고이므로 **제출 단계에서 막힌다**」를
확정으로 적고, OQ-203 은 **닫거나** 「보고 제출을 완료와 분리한 별도 명령을 신설할 것인가」로 다시 쓴다.
**정정 전에는 사용자에게 올리지 마라** — 지금 형태로는 어느 쪽을 골라도 문서가 맞지 않는다.

### F-6. SPEC-002 대체 안내가 **틀린 종류**를 지목하고, 실제로 바뀌는 절을 빠뜨렸다

  신규 경로로 돌아온다」
- SPEC-002 의 어휘에서 「배정 수락」과 「업무 요청 수락」은 **다른 종류**다
  (`spec-002:124-125` §2.2 종류 표가 둘을 각각 행으로 둔다).
  v2 가 되돌린 것은 **업무 요청 수락**이다(V-9~V-12).
- 「배정 수락이 돌아온다」로 읽으면 **원문 L-8**(「배정에 같은 수락·거절 정책을 적용하지 않는다」),
  **P-13**, 그리고 **SPEC-003 자신의 Scope Out**(`:116-117` 배정의 수락·거절 절차는 M-1 미정)과
  정면으로 어긋난다.
- 그리고 **실제로 v2 가 무효화하는 두 자리가 대체 목록에 없다**:
  - `spec-002:124` §2.2 종류 표 「업무 요청 수락 | **신규 생성이 만들지 않는다** | —(생성되지 않는다)」
  - `spec-002:186` §2.7 빈 상태 「**「동료의 요청, 관리자의 배정」이라는 문구는 쓰지 않는다 —
    그 두 종류가 사라진다**」
  둘 다 v2 하에서 거짓이 된다. 종류 원장은 화면이 아니라 **판단 항목 계약**이므로 이번 범위다.

**최소 정정**: 대체 행을 「SPEC-002 **§2.2 종류 표의 「업무 요청 수락」 행** · **§2.7 빈 상태 문구** ·
§4 Data 「사라지는 값」 중 **요청 판단의 수락·조정·거절·재상신·철회**」로 바꾼다.
**「배정 수락」은 사라진 채로 둔다** — 배정은 이번 범위 밖이다. SPEC-002 상단 안내도 같이 고친다.
