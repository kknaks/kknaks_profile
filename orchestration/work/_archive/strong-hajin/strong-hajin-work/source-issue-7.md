## 목표 계약

### W1. 직접 생성과 타인 요청/배정

1. 내 업무는 사용자가 생성 내용을 확인하고 생성 명령을 실행할 때 생성한다. 별도의 수락 절차를 새로 만들지 않는다.
2. 권한 있는 사용자가 다른 사람에게 업무를 요청/배정하면 상대방의 수락·거절·조건 협의를 기다리지 않고 Task와 활성 담당 관계가 성립한다. 상대방 내 업무에는 즉시 `시작 전`으로 나타난다.
3. 신규 요청/배정에 수락용 ActionItem·pending assignment·재상신 round를 만들지 않는다. 요청자·담당자·출처·행위자·시각과 변경 이력은 보존한다.
4. 책임 담당자는 한 명이다. 내 업무 만들기는 본인 담당으로 생성한다. 타인 요청 경로에서는 일반 구성원도 수신자를 지정해 한 번의 명시적 생성 명령으로 해당 수신자에게 바로 배정한다. 이를 위해 내 업무를 먼저 만들고 관리자 권한으로 재배정하는 우회를 요구하지 않는다. 새 요청과 이미 존재하는 업무의 담당자 변경은 별도 명령·권한으로 구분한다. 기획의 본인 생성→상세에서 넘기기 단일 경로는 이 사용자 결정에 맞춰 동기화한다.
5. **사용자 확정(2026-09-11): 일반 구성원도 타인에게 업무를 요청·생성하면 상대방에게 즉시 배정된다. 관리자만 가능한 기능으로 제한하지 않는다.** 기존 일반 구성원의 수평 요청 허용 범위를 유지하며 수행자의 수락 없이 Task와 활성 담당 관계를 만든다. 수평 요청에 관리자 전용 `task.assign`을 요구하지 않는다. 별도 관리자 직접 배정은 기존 조직 scope를 지키며, 이 변경으로 타인 업무 수정·재배정·열람 권한을 일괄 확대하지 않는다.
6. AI 제안은 사용자 실행 확인을 거친다. **수행자 수락 제거는 AX action preview/confirmation, 완료 승인, 다른 종류의 사람 판단 제거가 아니다.**

### W2. 수행·완료·개인별 목록

**기존 구조 재사용:** 현행 요청 업무도 TaskDelivery 제출 → 결과 확인 ActionItem → 요청자의 승인/보완 요청으로 처리한다. 승인 기능을 새로 만드는 작업이 아니다. 제거 대상은 업무 생성 시 수행자 수락용 ActionItem이며, 완료 결과 확인용 ActionItem은 유지·활용한다. 기존 `completion_submitted → 승인 → done` 경로는 `완료 제출 시 Task done + 완료 승인 ActionItem 생성`으로 정렬한다. 업무 완료와 승인 판단은 별도 상태로 관리한다. 새로운 승인 원장을 중복 도입하지 않는다. (사용자 확인 2026-09-11)

1. 사용자에게 보이는 기본 수행 상태는 시작 전·진행 중·완료·취소다. 내 업무·보낸 업무·완료 업무는 현재 사용자에게 필요한 행동을 기준으로 투영한다.
2. 승인자는 0..1명이며 완료 시 다시 확인한다. 요청자와 승인자를 동일인으로 고정하지 않는다.
3. **사용자 확정(2026-09-11): 완료 명령이 성공하면 승인자 유무와 관계없이 Task 자체를 완료(`done`) 처리한다.** 승인자가 있으면 같은 완료 제출 처리에서 기존 TaskDelivery/완료 승인 ActionItem 경로를 활용한다. **목표 Task 상태 모델에서 `completion_submitted`를 제거한다.** 신규 command/API/UI/도메인 전이는 이를 생성하거나 요구하지 않는다. 기존 저장 데이터의 해당 값에 대한 전환·호환 처리는 이번 범위에서 제외한다(D4).
4. 완료 업무에 연결된 **현재 유효한 완료 승인 ActionItem이 미결일 때만** `승인 대기`를 파생 표시한다. 임의의 ActionItem이 존재하거나 과거 승인 이력이 남아 있다는 이유로 대기 표시를 하지 않는다. 수행자의 완료 업무에는 `완료 · 승인 대기`, 승인자의 응답 목록에는 해당 ActionItem을 표시한다.
5. 승인하면 Task는 완료 상태를 유지하고 대기 표시만 해소한다. 보완 요청이면 Task를 진행 중으로 돌리고 수행자의 내 업무에 다시 나타내며 이전 판단·제출 근거를 보존한다. 재완료하면 Task는 다시 완료되고 같은 결과 확인 흐름의 새 제출 회차가 미결인 동안 승인 대기를 표시한다. 승인자가 없으면 ActionItem 없이 완료로 끝난다.
6. 일반 담당자의 `[완료 해제]`를 두지 않는다. 승인/보완/판정 변경 권한은 기획 X-178~180과 대조해 명시하고 종전 self Task reopen 동작을 무조건 유지하지 않는다.
7. 담당자 변경·취소·실제 기한 변경은 허용된 행위자가 사유를 남기는 직접 명령이다. 별도 변경 요청 승인 gate를 두지 않는다. 계획 기한과 실제 기한을 구분한다.
8. 문의·결정 요청을 보내면 회신 대기가 자동으로 붙고 답변하면 해소된다. 제품 밖 대기는 상태 메모로 표현한다. 여러 미응답 문의가 있을 때 해소 판정은 D2에서 정한다.
9. 답하면 끝나는 목록의 종류 칩은 문의 요청·승인 요청 둘이다. 진행 기록은 시간순 append-only이며 자료는 하나의 구획으로 표시한다. 자료 접근 시 재인가와 binding별 연결 해제는 유지한다.

### M1. 회의와 회의록

1. 회의 상태는 예정·진행 중·종료·실패·취소다. 후처리 중은 회의록 영역의 처리 표시이며 별도 회의 상태가 아니다.
2. 회의 진행 중 안건별 AI 정리와 메모를 제공한다. 종료 후 회의록이 자동으로 채워지고 별도 `요약 채택` 단계 없이 편집할 수 있다. 처리 지연/실패를 완성된 결과로 표시하지 않는다.
3. 사용자 회의록은 한 벌이며 화면에는 최신 저장본만 표시한다. 회의 생성자만 편집하고 회의 열람권자는 읽는다. 본문 항목마다 발화 시각과 원문 이동 근거를 유지한다.
4. **사용자 확정(2026-09-11): 회의록은 현재 저장 방식(immutable versions·evidence·감사 이력)을 유지하고, 사용자 화면에는 최신본만 보여준다.** 저장 시 기존 버전을 덮어쓰거나 삭제하지 않으며 동시 수정 보호와 과거 근거 연결을 유지한다. 사용자용 버전 선택·판 관리·확정 UI는 노출하지 않는다. 이 결정 때문에 저장 모델을 재설계하거나 기존 이력을 이관하지 않는다. AI 요약의 자동 반영 여부는 M1.2의 별도 계약이며 이 저장 결정과 혼동하지 않는다.
5. 후속업무는 후보일 뿐 자동 생성하지 않는다. 사용자가 생성하면 W1과 동일한 명령·권한·멱등성 경로를 사용한다. 기존 WorkRequest 수락 경로를 우회 adapter로 남기지 않는다.
6. 공유는 종료 후에만 열고 비참석 공유자는 읽기만 허용한다. 예정 회의만 삭제하며 연결된 회의실 예약 취소 여부를 구분한다.
7. 회의 반복은 1차 제외. 지난 회의의 정보·미결 안건 불러오기, 내보내기, 자료 미리보기는 별도 검증 가능한 slice로 구현한다.

### X1. 수신함·외부 연동·권한·범위

- 메일·그룹웨어가 1차 수신/회신 채널이다. 수신함은 업무·참고로 분류하고 원문 열기·답장·내 업무 만들기를 구분한다. 업무 생성 시 정형 수신 회신을 보낸다. 제품 안 단순 알림은 참고, 행동이 필요한 항목은 업무 목록으로 간다.
- 회의 생성과 the Connect 회의실 예약은 별도 행위다. 예약 실패가 회의 생성 성공으로 위장되거나 업무/회의가 중복 생성되지 않도록 결과를 구분한다.
- 자동 회신·예약 같은 외부 effect는 transactional outbox 또는 동등한 durable intent, 멱등성, 재시도, receipt/reconciliation을 갖춘 뒤 붙인다. 제품별 API 계약과 실제 권한은 sandbox/공식 자료로 확인한다.
- 제품 권한 어휘는 관리자·구성원이고 조직 단위/하위 범위를 따른다. 내부 capability·grant 엔진 교체를 전제하지 않으며 직급·직책만으로 권한을 넓히지 않는다.
- 업무 내 체크리스트는 2차 재검토, 여러 팀 프로젝트 묶음은 후속 판단이다. 현재 Checklist/Subtask/Project가 있다는 이유로 1차 UI에 강제하지 않는다. 기존 데이터·API를 즉시 삭제하는 작업은 포함하지 않는다.

## 기획과 합의할 사항 — 요구사항 누락·상세 계약·원문 동기화

아래는 기획과 대조·합의할 검토 목록이다. **기획 원문에 이미 명시된 요구의 존재를 다시 승인받는 목록이 아니다.** 원문 요구는 유지하고, 이슈에 빠진 인수조건·소유 문서·적용 차수·예외 동작을 정리한다. 구현 증거 없이 완료로 표시하지 않는다. 새 범위 결정이나 원문 변경이 필요한 항목만 기획 판단으로 남긴다.

## 인수조건과 검증

- [ ] 본인이 명시적으로 만든 업무는 한 건만 생성되며 별도 수락 카드는 없다.
- [ ] 관리자 배정 권한이 없는 일반 구성원이 허용된 동료를 수신자로 요청을 생성하면 상대 내 업무에 한 건이 즉시 나타나고 시작할 수 있다. 본인 업무 선생성·관리자 재배정·상대 수락을 요구하지 않으며 신규 수락용 판단은 생기지 않는다.
- [ ] 일반 구성원의 신규 요청 권한으로 타인 기존 업무를 임의로 수정·재배정할 수 없다. 관리자 직접 배정은 기존 scope 검사를 유지한다.
- [ ] 권한 밖 요청/배정은 거부하며 같은 명령 재시도·동시 실행은 중복 업무/활성 담당을 만들지 않는다.
- [ ] UI·REST·MCP·AX가 동일한 application 계약을 사용한다. AX 실행 확인은 남아 있으며 읽기만으로 업무가 생기지 않는다.
- [ ] 승인자 없음/있음/요청자와 다른 승인자 모두 완료 명령 직후 Task가 done임을 검증한다. 승인자 없음은 승인 ActionItem을 만들지 않는다.
- [ ] 현재 완료 승인 ActionItem 미결 시에만 완료 업무에 승인 대기를 표시한다. 과거 처리된 ActionItem이나 다른 종류의 ActionItem만 있는 경우 대기 표시를 하지 않는다.
- [ ] 승인 시 done 유지·대기 표시 해소, 보완 요청 시 in_progress 복귀, 재완료 시 done·새 제출 회차 승인 대기를 검증한다. 수행자와 승인자의 목록이 각 원장의 현재 상태와 일치한다.
- [ ] 완료 제출과 필요한 승인 ActionItem 생성은 원자적으로 반영되고, 중복 완료·중복 승인·오래된 회차의 명령은 중복 판단이나 잘못된 상태 전이를 만들지 않는다.
- [ ] 문의 발송/답변/복수 문의/취소의 회신 대기 규칙과 기한·담당 변경 권한을 검증한다.
- [ ] 회의 종료 결과가 별도 채택 없이 현재 회의록에 표시되며 생성자만 편집한다.
- [ ] 회의록을 여러 번 저장해도 화면에는 최신본만 표시하고 버전 선택 UI는 노출하지 않는다. 기존 immutable versions·감사 이력·과거 원문 근거가 보존되며 오래된 버전을 기준으로 한 동시 수정은 기존 계약대로 거부한다.
- [ ] live summary 지연/실패/후처리 완료 상태를 구분하고 항목의 원문 locator를 검증한다.
- [ ] 후속업무 반복 생성 명령은 한 건만 만들고 원본 회의로 돌아갈 수 있다.

## 비범위와 종료

- 기존 데이터 migration·backfill·구 상태 호환 adapter는 이번 범위에서 제외한다. 검증은 새 모델의 seed·fixture로 수행하며 기존 데이터 삭제나 실제 DB reset을 이 이슈로 실행하지 않는다.

- 이 이슈로 production deploy, 실제 외부 메시지 전송/예약, 운영 DB migration, 기존 데이터 삭제를 실행하지 않는다.
- 모든 ActionItem/Submission 체계를 제거하거나 사용자의 AI 실행 확인을 없애지 않는다.
- 체크리스트·Project의 저장 모델을 기획 범위 축소만을 이유로 삭제하지 않는다.
- mediness-app과 runtime/DB 의존성을 만들지 않는다.
- 코드 PR merge만으로 닫지 않는다. 미충족 인수조건은 연결된 하위 이슈로 명시적으로 이관하거나 해결하고, 검증된 계약의 SPEC 동기화까지 확인한다.
