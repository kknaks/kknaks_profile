
# 작업 요약 — meeting-room-workflow (mediness)

기간: `2026-08-31` ~ `2026-08-31`
결과: spec PR #665 · code PR #137 머지, mediness-dev 배포·alembic 0135 실측 완료. main 릴리스(#667·#138)는 대기

## 1. 무엇을 했나

채팅(AX 비서) 발 회의실 예약이 승인·실행되면 THE CONNECT 에 방만 잡히고 회의관리(`meeting_v2`)에는 아무것도 안 생겨 회의록·참석자·이력이 끊겼다. 조사(FE→BFF→router→service→repo→DB 전 경로 실측) → SPEC-151 §7.9 계약 신설 → WP-125 → 코드 착지(체인 어댑터·보상 원자성·수정취소 파급·부분 유니크 인덱스 migration 0135) 순으로 직렬 파이프라인을 돌았다. 당초 요구였던 「시간대별 회의실 점유 스케줄 화면」은 조사 결과(원장이 외부 THE CONNECT)를 근거로 사용자 결정으로 제외했다.

## 2. 적용한 기술·개념

- **보상(compensation) 기반 원자성** — 외부 API(THE CONNECT) 예약 + 로컬 회의 저장을 all-or-nothing 으로 묶는 데 씀
  - 왜 이걸 골랐나: 외부 write 는 DB 트랜잭션에 못 들어온다. 재시도 루프는 사용자가 명시적으로 거부("재시도는 없고 하나의 트랜잭션으로") → 실패 시 방금 만든 그 예약 하나를 external_id 로 취소. 조건 재조회 삭제는 남의 예약을 지울 수 있어 기각
  - 무엇이 어려웠나: 보상까지 실패한 조합(D 행)의 원장 표현 — 실행 축을 «실패» 로 적으면 외부에 실재하는 예약을 원장이 부정한다. «성공 유지 + 회의 미등록 별도 표기» 로 착지 (§5.3.2 조합표가 실증으로 잡았던 결함과 같은 축)
  - 근거: SPEC-151 §7.9.4 조합표 · `meeting_chain.py` · PR #137
- **실행 축 기록을 체인 뒤로 미루기** — 외부 예약 성공 «시점» 에 «성공» 을 적으면 회의 실패 시 표에 없는 «성공→실패» 전이가 된다. 완료 기록(`complete_execution`)을 체인 종료 후로 이동
  - 근거: WP-125 P2 · 코드 리뷰 W-계열 테스트 11건
- **파생 매핑에서 «없는 축을 추론하지 않기»** — payload 에 없는 visibility(→private 확정)·product_tags(→빈 배열)를 모델·서버가 추론해 채우지 않는다. 30분 슬롯도 입력 스키마 규칙이지 도메인 불변식이 아니라 비적용(반올림하면 사람이 승인한 시간과 갈라진다)
- **파급 가드 2겹(연결 + source)** — 모달 발 회의도 `link_reservation` 으로 예약 참조를 가져서 「연결 유무」만으론 못 거른다. 리뷰가 잡기 전까지 나(코디)와 planner 둘 다 놓쳤던 지점 — 모달 발 예약 취소가 모달 발 회의를 soft delete 하는 실버그였다
  - 근거: review-wp-report.md V-3 · §7.9.5 「자동 등록된 회의 한정」
- **부분 유니크 인덱스로 멱등 보증** — 「예약 건당 회의 최대 1」을 생성 직전 조회가 아니라 인덱스(0135)로. 동시 재진입은 조회로 못 막는다 (P0 실사에서 결정)

## 3. 막혔던 것 / 사고

- **스펙 검수 FAIL 2건** — §7.9 신설이 SPEC-031 의 기존 문장(30분 슬롯 422 소유 · 「예정 시간 변경 기능 없음」)과 같은 문서 안 모순을 만들었다 → 리뷰어가 절 번호로 지목 → 경로 단서·처분 신설·예외 단서로 정합. 교훈: 새 절 신설은 인접 기존 문장 개정을 동반해야 한다
- **머신 종료로 워커 사망** — backend 수정 라운드 중 재부팅. 미커밋 변경은 디스크에 살아 있어 재개 브리프(전임 상태 판정 → 이어받기)로 복구. 코디 핸들이 세션마다 바뀌는 것도 이때 3번째 확인 — 브리프의 핸들은 늙는다는 전제(preamble 정본)가 실제로 일을 했다
- **P0-② 스펙-코드 불일치** — §7.2 문면(display_name/work_email)과 코드(users.name/email)가 갈렸다 → 워커가 코드에서 정하지 않고 보고 → §7.2 환류 커밋으로 스펙을 코드에 맞춤. 「코드가 SoT」 규율이 워커 행동으로 이어진 사례
- **스쿼시 머지 후 아카이브 검사 걸림** — 원 커밋이 브랜치에 남아 「미머지 의심」. 트리 대조(diff HEAD 머지커밋 = empty)로 완전 머지 확인 후 base 로 reset — 런북 §STEP 7 경고의 실사례
