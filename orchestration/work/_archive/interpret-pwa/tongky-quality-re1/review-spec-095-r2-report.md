## WARN

### WARN-1 `playback_stopped` 를 받은 back 이 보내던 발화의 `audio_end` 를 보내는지 — 정해져 있지 않다

- 자리: `spec:1659`(「F 의 재생 멈춤 절차를 한다 — ①(`audio_stop`)만 빼고」) ↔ `spec:1629` ①(「… 먼저 보낸다 … 그 뒤 **다음 `audio_start` 전까지 PCM · `audio_end` 를 보내지 않는다**」 — 이 문장이 ① 안에 들어 있다) · `spec:1802`(「`playback_stopped` 를 받으면 그 차례의 **남은 번역**을 보내지 않는다」 — 보내던 발화는 말하지 않는다) · 시험 `spec:1908` ⑯(PCM · `audio_end` 를 보지 않는다).
- 무엇: 「① 만 빼고」 가 `audio_stop` 메시지만 뺀다는 뜻인지 · ① 에 딸린 「PCM · `audio_end` 를 보내지 않는다」 도 같이 빠지는지 문서가 고르지 않았다. 보통 때는 어느 쪽이든 같다 — front 가 버림 표시를 세워 조각과 `audio_end` 를 무시한다(`spec:1802`).
- 갈리는 곳: **감수한 좁은 창**(`spec:1660`). front 가 `playback_stopped{u3}` 를 보낸 뒤 back 이 이미 보낸 `audio_start{u4}` 를 받으면 front 는 버림 표시를 풀고 u4 를 재생한다 — 출력 구간이 다시 열린다. back 이 그 뒤 u4 의 PCM 을 끊고 `audio_end{u4}` 도 보내지 않으면, front 의 출력 구간은 **`audio_end` 를 받아야 닫히므로**(지금 코드 `front/lib/outputWindow.ts` `audioOpen` · HEAD 의 `halfDuplex.ts` 도 같음 — 「`audio_end` 를 받았고 재생 조각이 다 끝나면 400 ms 뒤」) 닫히지 않는다. 화면은 소리 없이 #4 「출력 중」 에 붙고(`spec:1766` — #4 가 멈춤 · 듣는 중보다 위), 다음 통키 차례의 `audio_start` → `audio_end` 가 오거나 사용자가 다시 멈출 때까지 그대로다. 마이크 송신은 막히지 않는다(0.9.5).
- 왜 WARN: D-70 ④ 가 감수한 것은 「다음 발화가 재생될 수 있다」 까지다(`dec:126`) — 「출력 중」 표시가 붙는 것은 적혀 있지 않고, back · front 워커가 병렬로 각자 메우는 자리다(rules.md 「워커가 추측으로 메워야 하는 빈칸」). 창이 좁아 FAIL 로 올리지 않았다.
- 닫는 길(결정은 코디): 「`playback_stopped` 로 멈출 때 back 은 `audio_start` 를 보냈고 `audio_end` 를 아직 안 보낸 발화가 있으면 PCM 은 끊되 **`audio_end{id}` 는 보낸다**」 한 줄(front 는 고칠 것 없음 — 버리는 중이면 무시 · 아니면 구간이 닫힌다) + ⑯ 에 한 줄. 또는 감수 범위에 「출력 중 표시가 다음 차례까지 남을 수 있다」 를 적고 §9.6 ⑥ 에서 같이 본다.

### WARN-2 `playback_stopped` 의 `id` — 같은 차례의 앞 발화 id 를 맞는 것으로 보는지가 두 자리에서 다르게 읽힌다

- 자리: `spec:1168`(§5.3 「`id` = 마지막으로 받은 `audio_start` 의 `id` … 통키 차례가 아니거나 **`id` 가 다르면** back 은 무시한다」) ↔ `spec:1659`(「`id` 가 **지금 통키 차례에서 `audio_start` 를 보낸 발화의 id** 면」) · `work:119` ②(「맞는 `id` 면」) · 시험 `spec:1908` ⑯(「통키 차례에 맞는 `id`」 · 「`id` 가 다르면 아무 일 없음」).
- 무엇: WARN-1 과 같은 창에서 front 가 보낸 `id` 는 u3 인데 back 은 이미 u4 의 `audio_start` 를 보냈다. §5.13 H 를 「이 차례에 보낸 발화 가운데 하나」 로 읽으면 멈춘다. §5.3 의 「`id` 가 다르면」 을 「마지막으로 보낸 id 와 다르면」 으로 읽으면 무시한다 — 그러면 back 은 읽을 큐를 끝까지 읽고, front 는 새 `audio_start` 마다 버림 표시를 풀어 **멈춘 뒤에도 남은 번역이 줄줄이 나온다**(멈춤 중에도 — `spec:1766`). 감수한 「다음 발화 하나」 보다 넓다.
- 닫는 길: §5.3 한 줄을 §5.13 H 낱말로 맞추고(「이 통키 차례에서 `audio_start` 를 보낸 발화의 id 가운데 하나」) ⑯ 에 「같은 차례의 앞 발화 id → 멈춘다 · 지난 차례의 id → 아무 일 없음」.

### WARN-3 멈춤 절차 ③ 의 기다림(3초까지)이 ④ ~ ⑥ · `resume` · 마이크 조각을 막는지 — 「끝」 을 재는 때가 두 가지로 읽힌다

- 자리: `spec:1629`(「순서대로 … ③ `terminated` 를 `TTS_CANCEL_WAIT_SEC` = 3초까지 기다리며 읽어 버린다 … ④ agent text 를 끝낸다 ⑤ 열린 재생 구간을 닫는다(끝 = **지금** `sent_ms`) ⑥ 상태 → 듣는 중」) ↔ `spec:1617`(「끝 = 재생이 끝난(또는 F · H 로 **멈춘**) 틱의 `sent_ms`」) · `spec:1659`(H 는 같은 절차) · `spec:1668`(재생 중 누름 → `playback_stopped` → `resume`).
- 무엇: ③ 이 걸리는 것은 TTS 스트림이 아직 진행 중일 때 — 통키 차례의 앞머리다(스트림은 실시간보다 빨리 끝난다 · `spec:1629` 끝). 그때 ④ ⑤ ⑥ 이 ③ 을 기다리는지가 없다.
  - 기다리고 · 그동안 front 메시지는 계속 읽는 쪽으로 만들면: 누르고 말하기로 재생 중에 눌렀을 때 `resume` 과 마이크 조각이 ③ 사이에 처리되어 `sent_ms` 가 흐르고, ⑤ 의 「지금 `sent_ms`」 가 누른 뒤의 값이 된다. 구간은 멈춤 중에 닫히지 않았으므로 여유 500 도 붙는다 → **직원 대답(재생 쪽 언어)의 첫머리가 `[시작, 끝 + 500)` 에 들어 버려진다.** FAIL-1 이 막으려던 증상이고, ㉑ ㉒ 는 이 경우를 보지 않는다(㉑ 은 재생이 끝난 뒤 · ㉒ 는 `pause` 쪽).
  - 기다리는 동안 front 메시지 읽기도 멈추는 쪽으로 만들면: 위 증상은 없지만 `terminated` 가 늦는 동안 마이크 조각 · `pause` 처리가 최대 3초 밀린다.
  - ④(`end_of_segment`)도 같이 밀린다 — 공식 「When the user interrupts」 는 멈춘 때에 보내라고 한다.
- 근거: D-70 ④ 「마이크가 닫힌(멈춤 중) 동안 끝난 재생 구간은 여유 없이 끝 = 시작」 · 「(한도 있는 기다림)」(`dec:126`) — 기다림이 다른 단계를 막는지는 DEC 도 SPEC 도 말하지 않는다. `spec:1617` 의 「멈춘 틱」 과 `spec:1629` ⑤ 의 「지금」 은 ③ 이 0 이 아닐 때 다른 값이다.
- 닫는 길: 「③ 의 기다림은 ④ ~ ⑦ 과 front 메시지 처리를 막지 않는다 — ④ ⑤ ⑥ 은 `cancel` 을 보낸 직후에 한다(끝 = 절차를 시작한 때의 `sent_ms`)」 한 줄 + 시험 한 줄(「스트림 진행 중 · 멈춤 중 재생에서 `playback_stopped` → `resume` · 가짜 TTS 가 `terminated` 를 늦게 줌 → 재생 쪽 언어 첫 토큰이 남는다」).

## 고객이 실물에서 만날 자리

- **멈춘 뒤 「출력 중」 이 소리 없이 남는다** — WARN-1(여러 문장 차례가 막 시작됐을 때 원을 누른 경우).
- **멈췄는데 남은 번역이 계속 나온다** — WARN-2 가 무시 쪽으로 만들어졌을 때.
- **통역 음성이 막 나오기 시작할 때 누르고 한 대답의 첫머리** — WARN-3.
- 앞 리포트의 자리는 그대로다(문서가 감수로 적어 둠): 끼어든 뒤 멈추기까지 1.3 ~ 1.9초 + 전달(`spec:1628`) · 말 끝 → 음성 약 2초 + TTS(`spec:1597`) · 통역 음성과 같은 언어로 끼어든 말은 사라짐(`spec:1619`) · 재생 직후 0.5초 안 같은 언어 대답 첫머리(`spec:1617` — 자동 듣기 · 마이크가 열려 있을 때만) · 누른 채 통역 음성이 나오는 중에 떼면 음성이 끊김(`spec:1668`) · 새 front + 옛 back 이면 오류 화면(`spec:1181` · `spec:2455`) · 재생 소리가 목소리보다 크면 진짜 말이 묻힘(OQ-035 · `spec:2496`).
- FAIL-1 의 자리(누르고 말하기 기본 흐름의 대답 첫머리)는 닫혔다 — `spec:1621` · ㉑.

## 참고(기존 부채 · 낮음)

- **G 「언제」 식에서 「보낸 오디오를 넘지 않는다」 가 빠졌다** — `spec:1643` 은 `그 발화의 재생 시작 + 글자 시작 시각 ≤ 지금 + 0.7` 로 적고, 한도는 `spec:1607` 「재생 위치」 정의에만 있다(공식 `min(elapsed, audio_sent_s)`). 글자 시각은 오디오와 같이 오므로(공식 `tts/rt/timestamps` 「never exceed the duration of audio generated so far」) 실제로 앞질러 나갈 일은 거의 없다 — 계약은 맞고 표기만 두 곳이다.
- **재생 쪽이 바뀌는 발화 경계에서 `end_of_segment` 를 보내는 때** — `spec:1643`(다음 발화 글자를 앞 발화가 끝나기 전에 · 「한 메시지로」) + `spec:1644`(재생 쪽이 바뀌면 끊고 새로)를 겹치면 「앞 언어 마지막 글 + `end_of_segment`」 와 「다음 언어 첫 글」 이 같은 틱에 두 메시지로 나간다. 순서는 따라 읽으면 하나로 정해진다(앞 발화 글자가 먼저 다 나간다) — ⑫ 의 「발화 경계」 는 같은 쪽 둘만 본다. back 안의 일이고 실물 ㉘-3 으로 오류 여부가 보인다.
- **「옛 front + 새 back 은 돈다」**(`spec:2455`) — 돌기는 하지만 옛 front 는 `playback_stopped` 를 보내지 않으므로, 여러 문장 차례 중에 원을 눌러 멈추면 back 이 남은 번역을 계속 보내 다시 재생된다(`spec:1668` 이 적은 바로 그 경우). 배포 사이의 잠깐 · 홈 화면 앱이 옛 껍데기를 들고 있을 때만 — 실기기 확인을 「새 front 를 받은 뒤」 로 적어 둔 것(`spec:2455`)으로 충분하다.
- 표기: `spec:1675` 「`TTS_CANCEL_WAIT_SEC` … 숫자는 이 문서의 기본값」 — 이제 `dec:126` 이 3초를 직접 적었다 · `30-work/README.md` 의 WORK-001 행은 「D-68 · D-69」 까지만 적혀 있다(D-70 없음 · 본문 `work:55` 가 정본이라 무해).
- 무관 · 기존: `spec:1766` #4 「멈춤 중이면 `resume` → 8」 표기(앞 리포트 참고 그대로).
