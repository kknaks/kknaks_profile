## F-1. 줄에 붙은 시각을 없앤다 — 안건에만 남긴다

**화면** — 회의 중 / 종료 후 상세, 안건 > 줄 트리 (`AgendaLineTree` · `LineRow`)

**지금**

```
안건 1  캐스티 안건  [논의 중]                          10:03
  액션   이번 주에 틱톡 검색 기능을 추가하고 …          10:03  ▾
  논의   계정 점수를 보여주고 SNS 공유를 유도하는 …     10:03
  액션   캐스티로 사용자 유입을 유도할 방안을 설계한다.  10:05
  액션   DM·이메일 컨택 기능은 이번 주에 상세 설계를 …   10:05
  논의   캐스티 관련 비용은 부가세 포함 383,900원과 …   10:05
```

**바꿀 것**

```
안건 1  캐스티 안건  [논의 중]                          10:03   ← 남긴다
  액션   이번 주에 틱톡 검색 기능을 추가하고 …                  ▾  ← 시각 없앤다
    지난주 결제 심사 요청은 완료했다.
    근거  ⏱ 10:02 – 10:03   ← 구간은 여기서 본다
```

**왜** — 줄마다 붙은 시각이 **근거 타임칩과 겹친다.** 펼치면 `10:02 – 10:03` 구간이 나오는데
접힌 상태의 `10:03` 은 그 구간의 시작 시각일 뿐이라 정보가 중복되고 눈만 어지럽다.
**안건 단위 시각 하나면 시간 흐름이 읽힌다.**

**바꿀 문서**

```
SPEC-007 §2 U-2 · U-4   줄 행 규격에서 우측 시각 제거
SPEC-008 §2 U-3         종료 후 상세도 같다
                        — 근거 칩(§7 U-5 · SPEC-007 U-6)은 그대로
시안                     시안에 줄 시각이 그려져 있으면 「기획·정책 판단으로 제외」로
                        §7 제외 목록에 넣는다(시안이 아니라 우리가 정한다)
코드                     features/meetings/components/LineRow.tsx
```

**주의** — 안건 헤더의 시각은 **남긴다.** AI 탭 안내 바의 「배치 n회 반영 · HH:MM」,
프롬프트 바 우측 현재 시각, 「자동 저장 · HH:MM」은 **다른 것**이니 건드리지 않는다.

## F-2. 회의록의 「업무 생성」이 「새 업무」와 다른 드로어다 — **하나로 합친다**

**화면** — 회의록 상세 → 액션 줄 「업무 생성」 / 안건 「+ 액션 아이템」

**지금 — 두 드로어가 다르다**

```
SPEC-003 U-1  새 업무          제목 · 유형/프로젝트/**일정** · 설명 · 할일
                              · 참고자료/연관업무 · 결과자료/완료결과 · 로그   (7블록)
SPEC-008 U-10 회의록 업무 생성  안건 · 제목 · 유형/프로젝트 · **기한** · 메모   (5필드)
```

**사용자 판단(2026-09-07)** — 「상식적으로 새 업무랑 업무 생성이랑 다른 드로어를 보여줄 이유가 있어?」
**같은 「업무를 만든다」인데 만드는 자리에 따라 폼이 다를 이유가 없다.**

**실제로 어긋난 것**

```
업무 드로어    「일정」 = 기간(start_date ~ due_date)   ← DEC-002 2026-09-06 5필드 결정
회의록 드로어   「기한」 하나만
→ 회의에서 만든 업무는 시작일이 비어 있다. 나중에 다시 열어 채워야 한다
→ SPEC-003 U-1 이 바뀌어도 회의록 쪽이 안 따라온다는 증거다
```

**바꿀 것 — SPEC-003 U-1 드로어를 그대로 쓴다**

```
본문       SPEC-003 U-1 의 블록을 그대로. 별개 컴포넌트를 두지 않는다
           (MeetingDetailBody 를 전체 페이지·드로어가 공유하는 것과 같은 방식)
더할 것     「안건」 셀렉터 하나 — 회의록에서 열었을 때만 맨 위에 붙는다
프리필      제목 = 액션 줄 본문 · 프로젝트 = 회의의 프로젝트
그대로 유지  「시작 상태」 없음(항상 시작전) · 「연관 업무로 바꾸기」 토글 없음
           업무 생성과 줄 갱신은 한 요청 · 한 트랜잭션
```

**바꿀 문서**

```
SPEC-008 §2 U-10   「필드 5개」를 「SPEC-003 U-1 드로어 + 안건 셀렉터」로
SPEC-008 §4        POST …/lines/{id}/task 요청이 SPEC-003 생성 계약을 그대로 받는다
                   (지금은 기한 하나만 받는다 — 일정 기간이 못 들어간다)
SPEC-003 U-1       회의록에서 열릴 때의 변형(안건 슬롯 · 프리필)을 여기에 적는다
시안 L2600~2882    축소형으로 그려져 있다 → 「기획·정책 판단으로 SPEC-003 U-1 을 쓴다」로
                   §7 에 근거를 남긴다
코드               CreateTaskFromLineDrawer 를 TaskCreateDrawer 재사용으로
```

**화면** — 회의록 목록(`/meetings`)

회의를 고르면       우측 패널이 화면 오른쪽으로 넘어가 잘린다

**규격** — SPEC-006 U-6 반응형: 목록은 **좌 400/500 고정 + 우 유동**.

## F-4. 「연관 업무 연결」도 업무 쪽 후보 고르기와 다른 UI 다 — **하나로 합친다** (F-2 와 같은 뿌리)

**지금 — 서버 표면은 하나인데 UI 가 둘이다**

               우측 카운트 「n건 중 m」 · 칩 ↔ §4 `scope` 파라미터 1:1
               **「기준 프로젝트가 없으면 「이 프로젝트」 비활성 + 기본 「전체」」**
SPEC-008 U-9   프로젝트 셀렉터 · 검색 입력 · 결과 목록      ← 칩 없음. scope 를 못 쓴다

**실제로 막혔다(2026-09-07 실측)**

SPEC-003 U-8 은 **칩으로 「전체」까지 넓히는 길**이 있어서 이 함정을 안 밟는다.
SPEC-008 U-9 은 「회의가 무소속이면 전체」만 있고 **프로젝트에 업무가 0건인 경우**를 안 다뤘다.

**바꿀 것 — SPEC-003 U-8 의 후보 고르기를 그대로 쓴다**

**바꿀 문서**

## F-5. breadcrumb 이 링크가 아니다 — **상세에서 목록으로 돌아갈 길이 없다** (전 화면 공통)

**화면** — 회의록 상세 전체 페이지(`/meetings/detail?id=`). **업무 상세·설정도 같다.**

**실측**

```

   사이드바 「회의록」을 다시 누르는 것이 유일한데, 그건 「돌아가기」가 아니라 새로 들어가는 것이다

**둘은 하는 일이 다르다**

**바꿀 문서**

### ⛔ 완료는 회의록에서 하지 않는다 — 게이트 뒷문을 만들지 않기 위해

결정      회의록에서는 **`done` 으로 보내지 않는다.**
         대신 **완료 결과(`completion_result`)만 채운다**
         → 나중에 업무 화면에서 「완료」를 누르면 **게이트가 이미 열려 있다**

**남은 확인 2건**

## F-23. 유형을 AI 가 고르게 한다 — 유형 목록·설명을 컨텍스트로 준다

**사용자 제안(2026-09-07)** — 「업무 유형을 DB 에서 찾아서 안 던져?」 「업무 설정에 설명을 추가하면 AI 가 생성해줄 수 있지 않아?」

**실측 — 지금은 안 준다**

```
있는 것   meeting_batch_service.py:668  "workType": task.work_type_name
         → **화이트리스트 업무마다** 그 업무의 유형 **이름**은 준다
없는 것   **유형 목록 자체**를 안 준다
         → AI 가 「새 업무를 만들 때 어떤 유형을 골라야 하나」를 모른다
출력      ai_schemas/meeting_batch.json 에 `taskId` 만 있고 **`workType` 을 낼 자리가 없다**
결과      그래서 「액션 → 업무 자동 생성」의 유형 기본값을 코디가 정해야 했다(F-7 남은 항목)
```

**유형에 설명이 없다**

```
지금 work_type   이름 · 종류(meeting|task) · 색 · is_default
                「개인 업무」·「문서·보고」 — **이름만으로는 경계가 모호하다**

설명을 더하면
  개인 업무   「혼자 처리하는 실무. 개발·수정·확인 등」
  문서·보고   「산출물이 문서인 것. 기획서·보고서·회의록 정리」
  → AI 가 액션 내용을 보고 어느 쪽인지 판단할 근거가 생긴다
  → 사용자가 유형을 새로 만들 때도 「이 유형은 뭘 담나」를 적게 된다
```

**할 일 셋**

```
① work_type 에 description 컬럼 추가
   설정 화면(업무 유형)에 입력칸. 기본 3종에도 시드 문구를 넣는다
   ⚠ 기본 유형은 「이름·종류 고정, 색만 편집」(DEC-001 §3)이다 —
     **설명은 편집 가능하게 할지** 정해야 한다

② 배치·웜스타트 컨텍스트에 **유형 목록**(이름·종류·설명)을 싣는다
   DEC-003 §8 L149 웜스타트 = 프로젝트 + 업무 + 안건 → **+ 유형 목록**

③ 출력 스키마에 workType 을 낸다
   AI 가 액션마다 유형을 고른다. 못 고르면 `null` → **그때만 기본값**을 쓴다
   화이트리스트와 같은 방식으로 **목록 밖 유형은 거부**한다(DEC-003 §7 「없는 업무 참조」와 같은 결)
```

**바꿀 문서**

```
DEC-001 §3        유형에 설명 추가 · 기본 유형의 설명 편집 가능 여부
DEC-003 §8 L149   웜스타트 컨텍스트에 유형 목록
DEC-003 §7        「없는 유형 참조」를 실패 목록에 더한다(강등이 아니라 기본값 대체)
SPEC-002          업무 설정 화면에 설명 입력칸
SPEC-007 §4       배치 입력·출력 계약
ERD               work_type.description
ai_schemas/meeting_batch.json   출력에 workType
```

## F-24. 회의록 액션이 업무로 저장되지 않는다 — **실측 확인**

```
회의 1 실측(2026-09-07)

  track   kind        줄수   task 연결
  merged  action       14        0
  merged  decision      5        0
  merged  discussion   10        0
          kind=task     0        —
  실제 업무 62개는 전부 회의록 밖에서 만든 것

→ **액션 14개 중 업무가 된 것이 하나도 없다**
```

**지금 설계대로다** — DEC-003 §5 L116 「줄을 적는 것만으로는 업무가 생기지 않는다 — 버튼을 눌러야 요청」.
버튼을 안 누른 액션은 그냥 글자로 남는다.

**F-7 이 이것을 뒤집는다.** 「액션 = 이제 해야 할 태스크」면 만들어지는 순간 업무가 생겨야 한다.

```
바뀐 뒤
  AI 배치가 액션 줄을 만들면   → 그 순간 업무가 생긴다(taskId 가 붙는다)
  사람이 「/ 액션」으로 적어도  → 마찬가지
  유형은 F-23 대로 AI 가 고른다. 못 고르면 기본값

⚠ 그러면 **회의 하나에 업무가 14개 생긴다.** 이게 의도인지 확인이 필요하다 —
  원래 정책의 취지가 「회의 중에 업무가 우수수 생기면 안 된다」였다.
  AI 가 만든 액션까지 전부 업무가 되는 것인지, **사람이 확인한 것만**인지 정해야 한다
```

## F-25. 프롬프트 바에 **슬래시 명령어**를 지원한다 — 팝오버와 같은 결과

**사용자 요청(2026-09-07)** — 「팝오버도 슬래시 명령어도 지원」 「`/결정` 치고 띄어쓰기 하면 팝오버 선택처럼 `[결정]` 이 떠야 하는 거 아니야?」

**지금** — 팝오버에서 **골라야만** 한다. 타이핑으로 못 넣는다. 회의 중에 손이 멈춘다.

**바꿀 것 — 두 경로가 같은 자리로 모인다**

```
┌──────────────────────────────────────────────────────────┐
│  [안건 2 ▾]  /결정                                        │  ← 치는 중
└──────────────────────────────────────────────────────────┘
                    ↓  띄어쓰기
┌──────────────────────────────────────────────────────────┐
│  [안건 2 ▾]  [결정]  B안으로 간다                          │  ← 칩으로 바뀐다
└──────────────────────────────────────────────────────────┘
                          팝오버로 고른 것과 **완전히 같은 상태**
```

```
"/" 만 치면          팝오버가 뜬다 (지금 동작 그대로)
"/결" 까지 치면       팝오버가 그 항목으로 좁혀진다(자동완성)
"/결정" + 띄어쓰기    "/결정" 이 사라지고 [결정] 칩이 붙는다. 뒤는 본문
백스페이스           칩 앞에서 지우면 "/결정" 으로 되돌아간다
```

**명령어 — 다섯 개다** (2026-09-07 사용자 확정)

```
/논의   /결정   /업무   /액션      줄 종류 4종  (lineKinds.ts:13-16)
/새안건                          새 안건
```

**「다른 안건으로 이동」은 슬래시로 안 한다** — 안건이 여러 개라 명령어만으로 못 끝난다.
이동은 **팝오버에서만** 한다(지금 동작 그대로 · `LineKindPopover.tsx:139`).

**팝오버를 없애지 않는다** — 뭘 칠 수 있는지 모르는 사람에게 필요하다.
마우스로 가는 길과 키보드로 가는 길 **둘 다** 둔다.

**정할 것**

```
① 못 알아들으면   "/ㅁㄴㅇㄹ 어쩌고" → 논의로 넣나, 아무것도 안 하고 팝오버를 띄우나
② 이스케이프     "/" 로 시작하는 본문을 쓰고 싶으면 — "//" 로? 아니면 안 되는 걸로?
③ IME           한글 조합 중 확정 판정 — isEnterSubmit 과 같은 자리(lib/keyboard.ts)
```

**바꿀 문서**

```

SPEC-008 §2 U-7    편집 모드의 줄 추가도 같은 입력을 쓴다면 함께
