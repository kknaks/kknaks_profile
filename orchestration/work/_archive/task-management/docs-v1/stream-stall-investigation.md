**결론: 스트림 코드는 정상이다. 마이크가 잡는 소리가 회의 11 보다 20~30 dB 낮다 — 전사가 멈춘 게 아니라 알아들을 소리가 없다.**

## 3. 블록 두 개가 언제·어디서 나왔나 (헷갈리기 쉬운 자리)

- 블록 309 는 `at_ms 90987` = 세션 #2 의 `base_ms`(88.0초 — 연결 시점의 벽시계 오프셋) + 토큰 2.99초. **#2 가 낸 것**이다.

- 세션 #1 은 88초 동안 블록 0, 세션 #3 은 지금까지 12분 넘게 블록 0.

## 4. 원인 — 녹음된 소리가 20~30 dB 낮다

같은 파이프라인으로 **정상 전사된 회의 11**(블록 57개)과 회의 12 를 같은 방법으로 디코드해 잰 값이다(10초 창 · RMS/피크 dBFS).

```
회의 11 (정상)   -27.8/-8.2  -27.7/-5.3  -27.9/-8.2  -25.6/-4.3  -27.4/-6.0  …   ← 사람 말소리 수준
회의 12 스트림①  -60.4/-37.6 -56.1/-36.4 -52.4/-32.9 -51.7/-34.0 -57.1/-36.1 …   ← 25~30 dB 낮다
회의 12 스트림②  -43.2/-24.2 -51.1/-31.7 -51.9/-32.8 -57.5/-37.1 …  -39.1/-18.1  ← 15~25 dB 낮다
회의 12 스트림③  -51.2/…     -56.5/…     -53.6/…     …            -46.3/…       ← 지금도 같다
```

**Soniox 자신에게 물어도 같은 답**이다 — 녹음 원본을 `stt-async-v5` 로 다시 돌렸다(스트림 단위 · 실비 몇 센트).

| 대상 | 디코드된 길이 | 토큰 |
|---|---|---|
| 스트림 ①(WS #1) | 79.9초 | **6개** — 「안녕하세요.」(end_ms 79470) |
| 스트림 ②(WS #2) | 153.7초 | **0개** |
| 스트림 ③(WS #3 앞 4 MB) | 147.4초 | **0개** |

즉 **파일에 담긴 소리 자체에 알아들을 말이 거의 없다.** 실시간 세션이 낸 블록 두 개는 스트림 ② 앞부분의
**가장 큰 소리 구간**(피크 −24 dB)에서 겨우 건진 것이고, 그 뒤로는 실시간·비동기 모두 아무것도 못 냈다.

- 녹음 파일이 계속 커지는 것과 모순되지 않는다 — Opus 는 **조용해도 일정 비트레이트로 바이트를 만든다**(3초에 84 KB).
  그래서 화면에는 「녹음 중」으로 보이고 전사만 비어 있다.
- 회의 12 는 **처음부터** 조용했다(스트림 ① 이 가장 조용하다). 사용자가 「일시정지·재개」를 한 것은
  **전사가 안 나와서 다시 붙여 본 것**이고, 재연결이 원인을 만든 게 아니다. 재연결 뒤 두 줄이 나온 것은 그 구간이 잠깐 컸기 때문이다.
- 내용(「고객사 대리님 연결됐습니다」)으로 보아 **다른 앱이 마이크를 잡고 있는 통화 중**일 가능성이 크다 —
  입력 장치가 통화 앱 쪽으로 가 있거나, 시스템 입력 볼륨이 낮거나, 먼 거리의 다른 마이크가 잡히는 상태다.

## 5. 지금 할 수 있는 것 (사용자)

1. **입력 장치와 입력 볼륨을 확인한다** — macOS 시스템 설정 › 사운드 › 입력에서 말할 때 레벨 막대가 크게 흔들리는 장치를 고른다.
2. 통화 앱이 마이크를 독점하고 있으면 그 앱의 입력 장치를 바꾸거나, 우리 앱이 쓸 장치를 따로 지정한다.
3. 바꾼 뒤 **재개**를 누르면 새 recorder·새 STT 세션이 열리고 그 시점부터 전사가 붙는다(앞 구간은 소리 자체가 없어 복구 불가).

## 6. 코드에 남는 문제 — 「조용함」이 어디에도 안 드러난다

원인이 환경이라도 **제품이 그것을 못 말해 준 것**은 우리 문제다. 지금 계약상 서버는 실패가 아니면 아무 말도 하지 않는다
(SPEC-007 §4 의 설계된 실패는 `upstream` · `write_failed` 둘뿐이고, 이번 건은 그 둘 다 아니다).

### ② 에서 넣을 것 (제안 · 코디 결정 필요)

| # | 무엇 | 어디 | 계약 |
|---|---|---|---|
| 1 | **입력 레벨 로그** — 세션당 30초마다 `meeting_id · elapsed_s · rms_dbfs · chunk_bytes` 를 INFO 로 한 줄. Opus 를 디코드하지 않고 **바이트/초** 와 **무토큰 경과 시간**만 찍는 가벼운 판(디코드는 서버가 할 일이 아니다) | `service/meeting_stream_service.py` `StreamSession` | 계약 변경 없음 — 로그만 |

**백엔드만으로 닫으려면 1 · 2 만 하면 된다**(로그). 3 · 4 는 사용자에게 보이는 계약이라 SPEC 결정이 먼저다.

## 7. 곁가지로 확인된 것 두 개 (이번 버그와 별개 · 보고만)

1. **재연결 공백만큼 파일 시간축이 앞당겨진다.** 재연결 사이 공백(#1→#2 약 8초 · #2→#3 약 4초)은 파일에 **기록되지 않는다**.
   실시간 `at_ms` 는 벽시계 기준(`base_ms`)이라 정확하지만, 종료 후 **재전사는 파일 시간축**을 쓴다 — 이 회의는 재전사 결과가
   실시간 블록보다 **약 12초 앞당겨진다**(M-11 · M-9-a 의 근거 칩 매칭이 그만큼 어긋난다). 재연결이 잦을수록 커진다.
2. **이어 붙인 다중 헤더 webm 은 디코드된다** — ffmpeg 로 3스트림(0~10.3 MB)을 돌리면 **381.0초**로 셋의 합과 정확히 같다.
   즉 재전사 입력으로서 파일 자체는 온전하다(Soniox async 는 스트림 단위로만 확인했다 — 다중 헤더 파일 통짜는 미검증).

## 8. 조사 방법 (재현용)

- api 로그 — `docker compose logs api -t | grep -E "WebSocket|connection (open|closed)"`
- 살아 있는 연결 — api 컨테이너의 `/proc/net/tcp` 파싱(브라우저 WS 1개 · Soniox 443 1개 · 송신 큐 0)
- 파일 구조 — `12.bin` 에서 EBML 매직(`1A 45 DF A3`) 위치 · Matroska 클러스터 타임코드 단조성
- 소리 크기 — 스트림별로 잘라 `ffmpeg → wav` 뒤 10초 창 RMS/피크(회의 11 을 대조군으로)
- STT 재현 — 스트림별 `stt-async-v5` 업로드·전사(회의 8 실물 e2e 와 같은 방법)

**쓴 것은 이 문서 하나다** — `app/back` · `app/front` · compose · `.env` · DB 어디에도 쓰지 않았고 컨테이너도 재시작하지 않았다.
