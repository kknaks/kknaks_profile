# SYS-OQ-5 실물 확인 — 헤더 없는 webm 을 `stt-async-v5` 가 받는가

**답: 받는다.** 컨테이너를 바꿀 필요가 없다.

## 무엇을 올렸나

우리 스택이 실제로 흘려 쓴 녹음 원본이다 — compose `api` 컨테이너의 `/data/recordings/3.bin`(1,784,919 바이트 · 약 62초).

```
$ head -c 64 /data/recordings/3.bin | od -c
0000000 032   E 337 243 237   B 206 201 001   B 367 201 001   B 362 201
0000020 004   B 363 201  \b   B 202 204   w   e   b   m   B 207 201 004
0000040   B 205 201 002 030   S 200   g 001 377 377 377 377 377 377 377
```

- `1A 45 DF A3` = EBML(Matroska/WebM) 매직 · DocType `webm` — **컨테이너 헤더 자체는 있다**(첫 청크에 실려 있었다)
- `18 53 80 67 01 FF FF FF FF FF FF FF` = Segment 크기 **unknown**(`0x01FF…FF`) — 스트림 append 라 **길이가 비어 있다**.
  SYS-OQ-5 가 걱정한 것이 이 자리다

## 결과 — 받는다

실제 `SONIOX_API_KEY` 로 `POST /v1/files` → `POST /v1/transcriptions`(`model: stt-async-v5` ·
`language_hints:["ko"]` · `enable_speaker_diarization:true` · `context.general` 셋) → 5초 폴링 → `GET …/transcript`.

```
ACCEPTED — 토큰 307개 · 9.1초
  '응'   speaker=1  750~810
  '.'    speaker=1  930~990
  ' 이'  speaker=1  990~1050
  ...
화자: ['1', '2', '3'] · 마지막 endMs: 62190
```

- **거절 없음** — 4xx 도 error 상태도 없다. 62초 파일이 **9.1초**에 끝났다(상한 1200초에 여유가 크다)
- 화자 분리가 **셋**을 냈다(실시간 스트림은 같은 녹음에서 화자를 더 거칠게 갈랐다 — MF-37 이 재전사를 넣은 이유)
- 토큰이 **sub-word** 단위다(`'이'` · `'제'`) — 블록으로 묶어야 한다는 전제가 실물로 확인됐다

## 블록 묶기 — 실시간과 같은 함수를 지난다

같은 토큰을 `service/meeting_transcript_blocks.build_blocks()` 에 넣었다(실시간 중계가 쓰는 그 함수).

**2회차(전량 기록)** — 같은 파일을 다시 올려 블록 전부를 적었다. 토큰 307개 · 9.2초 · 화자 셋으로 1회차와 같다.

```
블록 5개
  1. 화자1   750~8670   응. 이제 회의하면 여기서 이제 스크립트가 이제 뜨는 구조고, 여기서는 이제.
  2. 화자2   8910~12330 어, 속도가 좀 느려.
  3. 화자1  12390~18810 여기 이렇게 회의에 계속 내가 뭔가를 계속 결정, 논의를, 사람들이 계속 실시간으로 쓸 수 있는 구조?
  4. 화자3  22770~23610 느려, 느려.
  5. 화자1  23910~62190 제, 그건 제 타자가 느리. 타자가 느리. 그래서 지금 뭐 여기서 뭐 안건 1에 대해서, 안건 1에서
                        얘기해서 뭐가 결정됐다 그러면은 이제 AI가 놓칠 수도 있고, 뭐 타이핑을 하는 사람도 있더라고요,
                        회의 때. … 그다음에 종료하게 되면은.
```

화자 변경에서 끊겼고 `at_ms` 가 파일 시작(=`recording_started_at`) 기준이다 — 근거 칩 기준이 실시간과 같다(M-9-a).

### ⚠ 블록 수는 **실행마다 다를 수 있다** — 1회차는 6개였다

1회차 같은 파일에서 앞부분이 이렇게 갈렸다.

```
  화자1   750~6570  응. 이제 회의하면 여기서 이제 스크립트가 이제 뜨는 구조고, 여기서는 이제
  화자1  8610~8670  .
  화자2  8910~12330 어, 속도가 좀 느려.
```

문장부호 하나(`.`)가 **따로 블록이 됐다** — 앞 토큰과 2초 넘게 벌어져서다(6570 → 8610). 2회차에서는 같은 자리가
한 블록으로 붙었다(750~8670). **Soniox 출력이 실행마다 완전히 같지 않고**(토큰 시각·화자 배정이 조금 흔들린다)
블록 경계가 그 위에서 결정되므로 개수가 5가 되기도 6이 되기도 한다.

- **계약은 어긋나지 않는다** — 경계 규칙(화자 변경 · 300자 · 2초)은 그대로 적용됐고, 두 결과 모두 그 규칙의 결과다.
- 다만 **「재전사 결과가 결정적이다」를 전제로 하는 테스트를 쓰면 안 된다.** 이 발주의 테스트는 대역 토큰을 쓰므로 영향이 없다.
- 「.」 하나짜리 블록이 나올 수 있다는 사실은 남는다 — 실시간도 같은 규칙이라 새로 생긴 문제가 아니고, 다듬을지는 문서가 정할 일이다.

## 남는 것

- **300분짜리 실물은 아직 안 올려 봤다** — 이번 파일은 62초다. 상한 1200초는 그 규모에서 다시 볼 값이다.
- 비용은 두 번 합쳐도 브리프의 $0.10 안이다(62초 × 2 · 시간당 $0.10 요금).
