## ⛔ 1. 정본 — 축을 나눈다

| 무엇 | 정본 |
|---|---|
| **기능** — 어떤 화면·필드·상태·흐름·문구·API 가 있나 | **기획 BASE-003 + 정책 DEC-003** |

**판정은 기획·정책 한 축뿐이다. 시안은 판정에 들어오지 않는다.**

| 기획·정책 | 판정 |
|---|---|
| **있다** | **만든다.** 시안에 화면이 있으면 그 배치를 따르고, **없으면 디자인 시스템 컴포넌트로 조립한다** |

  §7 에 **「시안 L### 에 있으나 기획·정책에 없어 제외」**로 줄 번호와 함께 적는다
- **기획·정책에 있고 시안에 없다** → **만든다.** 「시안 없음」은 막힐 이유가 아니다.
  정책이 「무엇과 같은 구조」라고 지정했으면 그 화면을 쓰고, 아니면 디자인 시스템으로 조립한다.
  **이걸로 OQ 를 만들지 마라**

## ⛔ 2. OQ 규칙 — 막지 않는다. 근거를 요구한다

**OQ 를 0 으로 맞추려고 구멍을 덮지 마라.** 진짜 구멍은 반드시 올려라. 대신 **가짜 OQ 를 쓰지 마라.**

| 종류 | 무엇 | 처리 |
|---|---|---|
| **가짜** | ① 기획·정책·다른 DEC·기존 SPEC 에 답이 있는데 못 찾음 ② **SPEC 이 정하면 되는 것** — API 경로·요청/응답 필드·에러코드·검증 규칙·수치·화면 조립 | **쓰지 마라. SPEC 이 채운다** |
| **진짜** | 기획·정책에 정말 없다 / 기획과 정책이 **서로 충돌**한다 | **§7 에 올린다** |

**OQ 를 하나라도 쓸 거면 그 항목에 반드시 함께 적어라.**
```
- 어디를 찾았나 — 파일·섹션·grep 한 문자열과 결과 건수
- 왜 SPEC 이 못 정하나
```
**이게 없는 OQ 는 반려한다.** 안 찾고 올린 것으로 본다.

## 6. 산출물 구조

SPEC-003·004 와 같게 —
```
1. Context (Meta · Business Requirement · Scope)
2. UX Contract (Placement + U-1..U-n)
3. Scenarios
4. Data Contract (API 표 · Request/Response · Validation · Case Matrix)
5. Flow (mermaid)
6. Acceptance
7. Open Questions   ← §2 규칙. 그리고 「시안에 있으나 기획에 없어 제외」 목록을 여기에
8. 근거 표
```

**§2 규칙**
- 화면 하나 = U-n 하나. **값마다 시안 줄 번호**를 단다
- **상태 · 문구 · CTA · 기대 결과** 넷을 반드시 쓴다
- 시안에 있어도 기획·정책에 없으면 U-n 에 담지 않는다

**§4 규칙**
- **화면에 나오는 모든 값의 출처를 정의한다.** 컬럼이 없으면 「ERD 변경 필요」로 명시한다(OQ 아님)
- **에러코드는 SPEC 이 정한다.** 다만 Case Matrix 의 행마다 **기획·정책의 어느 실패인지** 근거를 단다.
  DEC-003 §7 이 열거한 실패 밖의 것을 만들지 마라 — **「설계한 것 이외의 에러는 그대로 터뜨린다」(BASE-003 L43)**
- **fallback 을 만들지 마라**
