## 2. 무엇을 보나

### 2.1 아홉 갈래가 실제로 닫혔나

`§11.4` 일곱 + `can_edit_agendas` 벌별 + 저장 시 줄 id. **각각 코드에서 확인하고 파일:줄을 대라.**
보고서가 「했다」고 적은 것을 믿지 마라 — 네가 본 줄을 인용하라.

### 2.2 조용히 통과하는 자리 — 여기가 핵심이다

- **벌 이름은 `memo`·`ai`·`final` 이다** (사용자 결정 — 스펙 §4.0-2 의 `human` 을 뒤집었다).
  개명이 «일어나지 않았는지» 확인하라. `human` 이 코드에 새로 들어왔으면 되돌려야 한다.
  **안건 벌과 줄 track 이 같은 이름을 쓰는지**가 확인할 것이다 — 한 벌을 두 이름으로 부르면 안 된다
- **`source` 의 `ai` 값 은퇴**: enum·검증·기본값·프롬프트·테스트 픽스처에 남아 있지 않은지
- **`platform/meetings.py` 의 「메모 줄이 매달린 AI 안건은 남긴다」 예외**: 분기가 **통째로** 사라졌나,
  아니면 조건만 뒤집혔나. 남아 있으면 AI 벌 전량 교체가 진짜 전량이 아니다
- **`application.py:778` 응답 필터**: `[l for l in lines if l["track"]=="final"] or lines` 가
  세 벌을 다 내도록 바뀌었나. **`or lines` 폴백이 남아 있으면** 최종 벌이 빈 회의에서 원본이 최종인 척한다
- **`clear_track`**: 재시도가 최종 벌의 **줄만** 비우고 **안건은 남기던** 것에 안건 삭제가 더해졌나 (§8-5)

### 2.3 계보가 저장 한 번에 죽지 않나 — 가장 위험한 자리

`§8-9` 는 네 갈래를 정했다. **코드가 네 갈래를 다 갖는지 확인하라.**

| 들어온 것 | 계약이 요구하는 것 |
|---|---|
| id 가 왔고 본문이 그대로 | 그 줄을 이어 쓰고 `from_lines` **그대로** |
| id 가 왔고 본문이 달라짐 | **그 줄의** `from_lines` 만 지운다 |
| id 없이 옴 | 새 줄, `from_lines` 빈 목록 |
| 모르는 id | **그 줄만** 거절, 저장 전체는 산다 |

「안건의 줄을 지우고 새로 만든다」로 짜여 있으면 **첫 갈래가 거짓이 되고 계보가 전멸한다.**
이것이 문서 검수의 F-3 이었다. **직접 시나리오를 짜서 확인하라** — 계보 든 줄 셋 중 하나만 고쳐 저장하고,
나머지 둘의 `from_lines` 가 살아 있는지.

### 2.4 게이트가 새지 않나

`can_edit_agendas` 가 `{human, ai, final}` 이고 **`ai` 가 언제나 거짓**인지.
「종료」·「실패」에서 **사람 벌 안건이 편집 불가**인지 — 여기가 새면 D-4(원본이 대조의 근거)가 무너진다.
**응답이 내는 값만 보지 말고 서버가 실제로 거절하는지** 보라. 게이트가 화면 힌트로만 있고
API 가 받아 주면 계약이 아니다.

### 2.5 범위가 안 샜나

- **충돌 판정이 들어오지 않았나** (`OQ-308` · D-3). `merge_conflicts` 류 필드·API·판정 로직 전수 grep
- **`OQ-320`(기존 데이터 이관)을 워커가 임의로 정하지 않았나** — 이관 코드가 있으면 위반이다
- **프론트를 고치지 않았나** — `git diff --stat` 에 `frontend/` 가 있으면 위반
- **커밋에 프론트 워커의 미커밋 산출물이 섞이지 않았나** — 이 워크트리에 30여 파일이 쌓여 있었다.
  `git show --stat` 으로 커밋마다 확인하라
