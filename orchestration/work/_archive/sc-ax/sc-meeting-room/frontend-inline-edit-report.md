# 프론트 — 안건 제목 제자리 편집

2026-09-15 · `sc-ax-fe` · 워크트리 `ax-workspace/sc-meeting-room` · 브랜치 `kknaksss/sc-meeting-room` · **미커밋**

> ⚠ **브리프 상단이 잘려 들어왔다.** 받은 것은 「그린다. 실패하면 원래 글자로 되돌리고…」 아래뿐이다.
> 디스크·인박스에도 이 발주의 브리프 파일이 없었다. 범위는 **보이는 제약 + 내가 직전 보고서에 올린

## 한 줄

안건 제목이 **그 자리에서** 칸이 된다. 사람 벌만, 서버 게이트가 연 동안만.
글자·상자·활자가 그대로라 누르는 순간 줄이 흔들리지 않는다.

## 1. 구현 방식과 고른 이유

### `ds/InlineText.tsx` — DS 부품으로 만들었다

**왜 화면 안에 인라인으로 짜지 않았나.** 「글자가 안 움직인다」는 마크업이 아니라 **CSS 계약**이다 —
닫힌 쪽과 열린 쪽이 같은 상자·같은 활자여야 성립한다. 그 계약을 한 파일에 가두지 않으면
다음에 같은 자리를 만들 때 반드시 어긋난다. `DS-gaps` 규칙(「없으면 새 DS 어휘로 만든다」)도 같은 쪽이다.

**어떻게 안 움직이나.** 닫힌 쪽은 `<button>`, 열린 쪽은 `<input>` 인데 둘 다:

```css
display:block; width:100%; margin:0; padding:0; border:0;
background:none; font:inherit; letter-spacing:inherit; color:inherit; text-align:left;
```

활자를 **자기가 정하지 않고 부모에서 물려받는다.** 그래서 어느 글자 위에 얹어도 그 글자로 보인다.
`.scax-textfield` 를 쓰지 않은 이유가 이것이다 — 그 껍데기는 48px 최소 높이 + 1px 테두리 +
좌우 안여백을 한꺼번에 들고 와서 줄을 통째로 민다.

**번호는 칸 밖에 남는다.** 머리는 「안건 1. 제목」인데 사람이 고치는 것은 **제목뿐**이라
`안건 1.` 은 글자로 두고 제목만 칸이 된다 (`agendaHeadNo` 라벨 신설).

**여러 줄을 받지 않는다** — `<input>` 이라 줄바꿈이 **구조적으로** 불가능하다.
`textarea` + `Enter` 가로채기가 아니다: 붙여넣기로도 줄이 안 들어간다.

### 상태를 들고 있지 않다 — 낙관 렌더가 없다

`value` 는 늘 서버가 말한 값이다. 저장을 보내면 **보낸 값**을 잠깐 보여 주고(옛 글자가 한 번
깜빡이지 않게), 요청이 끝나면 그것을 비운다. 성공이면 그 사이 `value` 가 새 제목으로 바뀌어 있고,
**실패면 `value` 가 원래 글자 그대로라 저절로 돌아온다.** 되돌리는 코드가 따로 없다 —
되돌릴 낙관 렌더를 안 만들었기 때문이다.

### `titleEdit` 를 안 주면 마크업이 한 글자도 안 달라진다

고칠 수 없는 자리(AI 벌 · 게이트가 닫힌 회의 · 최종 벌)에는 `<button>` 도 `<span>` 도 서지 않고
**예전 그대로 글자만** 선다. 「고칠 수 있다」는 구조를 못 고치는 자리에 남기지 않는다.
기존 테스트 144건이 한 건도 안 깨진 것이 그 증거다.

### 여는 조건은 **하나**다

```ts
const agendaAlways = canEditAgendas && shownTrack === "memo";   // 이미 있던 값
```

## 3. 저장·취소 규칙

| 입력 | 무엇이 일어나나 |
|---|---|
| 글자를 누름 | 그 자리가 칸이 되고 지금 글자가 들어 있다 (초점도 들어간다) |
| `Enter` | 저장. **줄바꿈이 아니다** (`preventDefault`) |
| `Esc` | 되돌린다. 친 글자를 버리고 **요청이 안 나간다**. 뒤따르는 `blur` 저장도 건너뛴다 |
| 초점이 빠짐(`blur`) | **저장한다** (`Enter` 와 같다) |
| 빈 값 / 공백만 | **저장하지 않는다.** 이름을 지우는 것은 이 자리의 일이 아니다 — 지우기는 안건 `×` 다 |
| 값이 그대로 | **요청이 안 나간다.** 헛 `PATCH` 를 내지 않는다 |
| 저장 실패 | 기존 `run()` 규칙대로 오류가 뜨고, 글자는 **원래대로 돌아온다** |

### 내가 정한 것 둘 (브리프에 없어서)

1. **`blur` 는 저장이다.** 브리프는 `Enter`=저장 · `Esc`=취소만 정했다. 초점이 빠질 때 조용히
   버리면 **사람이 친 글자가 말없이 사라진다** — 그쪽이 더 나쁘다고 봤다. 버리는 길은 `Esc` 로 남아 있다.
2. **`expected_last_saved_at` 을 싣지 않았다.** 실으면 409 가 날 수 있고, 그것을 «판정할» 자리가
   필요한데 **충돌 판정 UI 는 금지**다 (OQ-308). 사람 벌은 임시 재료라 마지막에 고친 사람의 제목이
   그 제목이다. **줄 편집(최종 벌)은 그대로 읽은 시각을 실어 보낸다** — 거기는 회의록이다.

## 4. DS-gaps 추가분

`design/DS-gaps.md` 는 **이 워크트리에 없다.** 실물은 아카이브이고 살아 있는 문서는
`orchestration/work/sc-meeting-room/ds-gaps-status.md` 라 **거기에 적었다.** 새 파일을 만들지
않았다 — 같은 주제의 문서가 둘이 되는 것이 더 나쁘다. 다른 자리를 원했으면 말해 달라.

- **G-47 제자리 편집** — DS 에 없다. `.scax-textfield` 는 껍데기라 글자 위에 못 얹는다
- **판단 요청: 누를 수 있다는 것을 무엇으로 말하나.** 지금은 `cursor:text` 가 전부라
  **마우스를 올리기 전에는 알 방법이 없다.** 후보 셋(연한 hover 바탕 · 점선 밑줄 · 지금 그대로)을
  적어 두고 **만들지 않았다.** 정해지면 `.scax-inline-text:hover` 한 줄이다
- **키보드 초점 테두리(`:focus-visible`)는 남겼다** — hover 꾸밈이 아니라 키보드로 이 자리에
  닿았다는 유일한 표시다. 마우스로는 안 뜬다. 이견 있으면 게이트로 올려 달라

## 5. 게이트로 올린 것 — **메모 «줄» 수정 표면이 서버에 없다**

브리프가 「없으면 만들지 말고 게이트로 올려라」 했다. 확인했고 **없다.** 코디에 올렸다.

| | 있나 |
|---|---|
| 안건 **제목** 고치기 | **있다.** `PATCH …/agendas/{id}` 의 `title`. 벌별 게이트를 타고, 사람 벌은 예정·진행 중·취소에서 참 (`policy.py:45`) → **이번에 붙인 것이 이것이다** |
| 메모 **줄** 더하기 | 있다. `POST …/agendas/{id}/lines` |
| 메모 **줄** 고치기 | **없다.** `PATCH` 의 `lines` 는 `application.py:1086` 이 `track != final` 이면 **409** 를 낸다 |
| 메모 **줄** 지우기 | **없다.** `DELETE` 는 안건 단위뿐이다 |

**판단이 필요한 것:** 사용자 결정 「사람이 고치고 지울 수 있다」가 «안건» 까지인지 «줄» 까지인지.
줄까지라면 서버 표면이 하나 필요하다. 안건까지라면 지금으로 닫힌다 — 줄은 안건을 지우면 함께 사라진다(§4.1-10).

> 곁가지: `application.py:1037` 의 docstring 이 아직 「사람 벌은 예정·취소에서만」이라 낡았다.
> 동작은 `policy` 를 타서 맞다. **백엔드 몫이라 안 건드렸다.**

| 빈 값(공백만)은 저장되지 않는다 | 빈 값이 저장되지 않는다 |
| 값이 그대로면 요청이 안 나간다 | 값이 그대로면 요청이 안 나간다 |
| AI 벌은 눌러도 안 열린다 — 칸도 단추도 없고 제목은 글자로 선다 | AI 벌 안건은 눌러도 안 열린다 |
| `can_edit_agendas.memo` 가 거짓이면 사람 벌도 안 열린다 | 게이트가 거짓이면 안 열린다 |
| **저장 실패면 원래 글자로 돌아온다** | (「실패하면 원래 글자로 되돌린다」) |
| **테두리·바탕을 주는 클래스가 안 붙는다** | (「글자가 안 움직인다」의 대체) |

### 적색을 먼저 봤다 — 양쪽으로

- 배선을 끊으니 **9개 중 7개 적색** (게이트 부정 둘은 그대로 통과 — 맞는 동작이다)
- 게이트를 무시하고 언제나 열게 하니 **정확히 그 둘만 적색**

### 못 건 것 — 정직하게 적는다

- **「글자가 한 픽셀도 안 움직인다」는 못 걸었다.** jsdom 은 배치를 계산하지 않아
  `getBoundingClientRect()` 가 전부 0 이다. 크기·위치로는 아무것도 증명할 수 없다.
  대신 **그 움직임을 만드는 원인**을 걸었다 — DS 입력 껍데기 클래스(`scax-textfield`·`scax-field`·
  `meeting-line-edit`)가 붙지 않고 `scax-inline-text__input` 하나만 붙는다는 것.
  껍데기가 붙으면 48px 높이·1px 테두리·좌우 안여백이 한꺼번에 따라 들어와 줄이 밀린다.
- **`font:inherit` 이 실제로 상속되는지**도 못 걸었다 — jsdom 은 CSS 파일을 적용하지 않는다.
  CSS 는 테스트가 아니라 **눈으로 볼 자리**다.
- **hover 가 없다는 것**도 못 걸었다 (같은 이유). CSS 에 `:hover` 규칙을 아예 안 썼다는 것이 담보다.
- **`cursor:text`** 도 같다.

→ **이 넷은 사용자의 육안 검증이 필요하다.** 브라우저로 직접 보지 않았다(사용자가 직접 한다).

## 1. 인라인 편집이 계약을 어겼다 — 다시 짰다

### 무엇이 잘못됐나 — 둘이 겹쳐 있었다

| # | 원인 | 무엇이 보였나 |
|---|---|---|
| ① | **`<input>` 으로 갈아 끼웠다** | 다른 노드라 기준선·기본 크기·안여백이 달라 글자가 밀린다 |
| ② | **`:focus-visible` 에 `--scax-focus-ring` 을 내가 붙였다** | 3px 보라색 박스. 「테두리가 그려진 입력칸」의 실체가 이것이다 |

브리프가 「`input`/`textarea` 로 갈아끼운 것으로 보인다」고 짚은 것이 맞다. ②는 §2 가 함께 지운다.

### 다시 고른 방식 — **노드를 바꾸지 않는다**

글자를 이고 있던 바로 그 `<span>` 이 **`contenteditable` 로 바뀐다.** 갈아 끼울 것이 없으니
활자·여백·자리가 달라질 여지 자체가 없다 — 「1px 도 안 움직인다」를 CSS 로 쫓는 대신
**움직일 대상을 없앴다.**

```
닫힘: <span role="button"  contenteditable="false" class="scax-inline-text">사람이 적은 안건</span>
열림: <span role="textbox" contenteditable="true"  class="scax-inline-text">사람이 적은 안건</span>
                 ↑ 같은 노드 · 같은 클래스 · 같은 활자. 캐럿만 생긴다
```

- **클래스가 상태에 따라 달라지지 않는다** — 모양을 바꿀 고리가 애초에 없다
- 테두리·바탕·그림자·**둥근 모서리**를 어느 상태에도 주지 않는다 (`border-radius` 도 걷었다)
- `:focus` 규칙을 **두지 않는다**
- 캐럿은 **글자 끝**에 둔다 — 전체 선택을 하면 파란 칠이 생겨 계약을 깬다
- `Enter` 는 `preventDefault` 로 저장이고, **붙여넣기로 들어온 줄바꿈은 저장할 때 걷는다**
  (`contenteditable` 은 `<input>` 과 달리 줄바꿈이 구조적으로 막히지 않으므로 우리가 지킨다)
- React 가 편집 중 자식을 건드리지 않게 한다 — 안 그러면 치는 동안 캐럿이 맨 앞으로 튄다

### 테스트 — **「같은 노드」 자체를 걸었다**

```ts
const before = slot();
fireEvent.click(before);
expect(slot()).toBe(before);                 // ← 갈아 끼웠다면 깨진다
expect(before.getAttribute("contenteditable")).toBe("true");
expect(body.querySelector("input")).toBeNull();
expect(body.querySelector("textarea")).toBeNull();
expect(element.className).toBe("scax-inline-text");   // 열려도 그대로
```

전 11건 통과. 여전히 **못 거는 것**은 같다 — jsdom 은 CSS 도 배치도 안 돌린다:

## 3. 회의 중 메모 줄 수정·삭제 — 서버 계약대로 붙였다

`lib/api.ts` 에 둘을 더했다 (백엔드 보고 §4 그대로):

```
PATCH  /api/meetings/{m}/agendas/{a}/lines/{l}   { text }  → 그 줄 하나
DELETE /api/meetings/{m}/agendas/{a}/lines/{l}             → 204
```

### 화면

- 메모 줄의 글자가 **같은 `InlineText`** 로 제자리 편집이 된다 (안건 제목과 같은 부품·같은 규칙)
- 줄 오른쪽에 `×` — **확인을 묻지 않는다** (자기가 적은 임시 재료다)
- **빈 줄로 지우려 하지 않는다.** 빈 값은 `InlineText` 가 애초에 요청을 안 내고, 지우는 것은 `DELETE` 다

### 게이트 — 안건 [수정]·[삭제]와 **같은 값**

`agendaAlways` (= `can_edit_agendas[보는 벌]` × 사람 벌) 하나다. `can_write_memo` 를 쓰지 않는다 —
그쪽은 「새 메모를 쓸 수 있는가」(만든 사람 × 진행 중)이고 고치기·지우기는 **예정·취소에서도 열린다.**

### 실패 코드 — §4 표 그대로, **셋을 갈라 다룬다**

| 코드 | 화면이 하는 일 |
|---|---|
| **422** | 한 줄로 알리기만 한다. **다시 읽지 않는다** — 서버는 그대로다 |
| **409** | **다시 읽어** 화면을 서버에 맞춘다(편집 자리가 걷힌다) + 한 줄 알림 |
| **404** | 역시 **다시 읽는다.** 이 모듈은 권한 밖도 「없는 것처럼」 답하므로 **403 을 기다리지 않는다** |

### 곁에서 고친 것

`memosOf` 가 글자만 내던 것을 **줄 전체**로 바꿨다(`line_id` 가 있어야 고치고 지운다). 그 김에
**기록과 세션에 같은 줄이 겹쳐 두 번 서던 것**을 `line_id` 로 걷었다 — 새로고침 뒤에 나던 자리다.

### 알고 있는 한계 (백엔드 §3-②)

수정·삭제에는 **스트림 프레임이 없다.** 회의 중에 내가 메모를 고치면 **같은 방의 다른 참석자
화면은 옛 줄을 그대로 들고 있다** (다시 열거나 다시 읽을 때 맞는다). 쓴 사람 화면은 응답으로 바로 맞는다.
프레임을 낼지는 §5.3 개정의 일이라 **손대지 않았다.**

### 테스트 8건 — 전부 적색 먼저

제자리 수정이 `PATCH …/lines/{lineId}` 로 간다 · **빈 값은 요청 자체가 안 나간다** ·
지우기는 `DELETE` 이고 확인을 안 묻는다 · **409/404 는 다시 읽는다** · **422 는 다시 읽지 않는다** ·
AI 벌 줄에는 안 단다 · 게이트가 거짓이면 안 열린다.
(자리를 닫으니 6건 적색 / 409·404 분기를 죽이니 정확히 그 2건만 적색)

## 2. 누를 수 있는 범위를 넓혔다

### ★ 한 줄 — 어느 노드에 무엇을 줬나 (되돌리려는 다음 사람에게)

> **`ds/InlineText` 의 그 `<span>` 하나에 `.scax-inline-text--fill`(= `display:block;width:100%`)을
> 더했다. 메모 줄에서만(`fill` prop), 안건 제목에는 안 줬다. 레이아웃은 건드리지 않았다 —
> 부모 `.scax-note-line__text` 는 **원래부터** `flex:1 1 auto` 였고 바뀐 것은 그 안의 글자가
> 인라인에서 블록이 된 것뿐이다. 되돌리려면 CSS 한 줄과 `fill` prop 을 걷으면 된다.**

### 왜 그 자리였나

`.scax-note-line__text` 는 이미 늘어나 있었다. 좁았던 것은 **그 안의 글자**다 —
`display:inline` 이라 과녁이 글자 폭에 묶여 있었고, 짧은 줄일수록 오른쪽 빈 자리를 눌러도
`__text` 만 맞고 편집이 안 열렸다.

블록으로 바꿔도 **글자는 안 움직인다**: 같은 줄 상자, 같은 왼쪽 시작점, 같은 활자·줄높이다.
세로 여백을 주지 않았고 `padding` 도 0 그대로다. 넓어진 것은 **과녁뿐**이다.

### 안건 제목에는 **안 줬다** — 판단과 근거

안건 머리는 「안건 1. 제목」이 **한 줄로 흐르는 인라인**이다. 거기서 제목을 블록으로 만들면
줄이 갈라지고, 대신 flex 로 가르면 「안건 1.」과 제목 사이 간격이 **글자 사이 공백에서 `gap` 으로
바뀐다** — 그 둘은 같은 값이 아니라 글자가 움직인다. 「1px 도 안 움직인다」와 정면으로 부딪힌다.

그래서 **넓히지 않고 남겼다.** 넓히려면 그 간격이 바뀌는 것을 받아들여야 한다 — 판단이 필요하면 말해 달라.

|---|---|
| 줄의 **빈 자리를 눌러도** 편집이 열린다 | 그 글자가 `--fill` 을 달았고, 딛는 칸이 늘어나는 칸(`__text`)이다 |

### 어떻게 나눴나

```ts
const [running, setRunning] = useState<ReadonlySet<string>>(() => new Set());
const runningRef = useRef<Set<string>>(new Set());     // 잠금은 ref 가 든다

const LIFECYCLE = ["start", "end", "retry"];
const conflicting = (key, active) =>
  active.has(key) || (LIFECYCLE.includes(key) && LIFECYCLE.some((one) => active.has(one)));

const isBusy = (key) => conflicting(key, running);     // 단추의 진행 표시
function claim(key) { if (conflicting(key, runningRef.current)) return false; … }
```

- **진행 중 표시는 그 일을 시킨 자리에만** 선다. 키가 대상마다 다르므로 줄 A 를 지우는 동안
  줄 B 는 그대로 눌린다
- **잠금은 `ref` 가 든다.** `state` 는 렌더를 기다려서 같은 tick 의 연타와 StrictMode 의 두 번째
  진입이 «아직 안 잠긴» 값을 본다 — 빠른 시작에서 회의가 둘 생겼던 자리와 같은 함정이다
- **`disabled` 를 떼지 않았다.** 그대로 두되 **무엇을 보고 끄는지**만 바꿨다

### 무엇과 무엇을 여전히 막았나 — 근거

**① 같은 조작을 두 번** — 모든 키. 같은 키가 돌면 두 번째는 요청 자체를 안 낸다.

**② 생애주기 셋끼리** (`start` · `end` · `retry`) — 이 셋만 서로 막는다. 근거:

- 셋 다 `meeting.status` 를 옮긴다. 둘이 동시에 도는 것은 **뜻 자체가 모순**이다 —
  「끝내는 중에 시작하기」·「끝내는 중에 또 끝내기」·「다시 거는 중에 또 걸기」
- 서버가 상태 기계를 들고 있어 나중 것은 **409** 로 떨어진다. 그 실패는 사람이 한 일이 아니라
  **화면이 두 번 보낸 탓**이라 사람에게 알릴 말이 없다

**그 밖은 안 막았다** — 근거:

- **회의록을 고치는 것과 회의를 끝내는 것은 상관이 없다.** 이것이 이번 버그 자체다
- **내용을 고치는 일끼리도 안 막았다.** 저마다 끝에서 상세를 **다시 읽으므로**, 겹쳐 돌아도
  마지막 읽기가 «서버가 말한 하나»로 화면을 맞춘다. **화면이 스스로 지어낸 값이 없어서**
  (낙관 렌더 0) 어긋날 것이 없다 — 이 결정은 그 성질에 기대고 있다
- 안건을 지우는 것과 그 안건의 줄을 고치는 것이 겹치면 줄 쪽이 **404** 를 받는데,
  §3 에서 이미 **404 는 다시 읽어 맞추도록** 해 두었다. 막을 필요 없이 이미 답이 있다

### 테스트 셋 (브리프가 이름 댄 것 그대로)

| 테스트 | 적색 확인 |
|---|---|
| 메모를 저장하는 **동안** [회의 종료]가 계속 눌릴 수 있다 | `isBusy` 를 옛 전역 깃발로 되돌리니 적색 |
| 같은 조작을 **세 번** 눌러도 요청이 한 번만 나간다 | `claim` 의 가드를 죽이니 적색 |
| **부딪히는 조합은 여전히 막힌다** — 끝내는 중에 또 끝낼 수 없다 | (두 되돌림 어느 쪽도 이것을 깨지 않는다 — `disabled` 가 DOM 에서 두 번째 클릭을 막는다. **이중 방어라 그렇다**: 표시와 잠금 둘 다 살아 있어야 통과한다) |

저장을 «끝나지 않게 붙들어» 두고 **도는 동안의 화면**을 본다 — 그 순간이 깜박임이 나던 자리다.

**새 것과 고친 것을 한 손잡이로 합쳤다.** 받는 쪽이 하는 일이 「id 로 upsert」 하나로 같기 때문이다 —
둘로 가르면 같은 코드가 두 벌이 되고 그때부터 한쪽만 고치는 실수가 난다.

**기존 둘(`memo.line`·`agenda.added`)은 이름도 본문도 안 건드렸다.**
「모르는 타입은 조용히 지나간다」도 테스트로 잠갔다.

## upsert · delete 를 어디에 뒀나

**두 층이다.** 위층이 진짜 규칙이고, 아래층은 원래부터 있던 두 번째 방어다.

### ① 스트림 상태 (`stream.ts`) — **여기가 규칙이다**

```ts
onMemo:  findIndex(line_id) < 0 ? push : 그 자리를 갈아 끼운다
onAgenda: findIndex(agenda_id) < 0 ? push : 그 자리를 갈아 끼운다
onMemoRemoved:   memos 에서 빼고 removedLines 에 id
onAgendaRemoved: agendas 에서 빼고 그 안건의 memos 도 빼고 removedAgendas 에 id
```

예전 `onMemo`·`onAgenda` 는 **붙이기(`push`)** 였다. 에코가 되돌아올 때마다 목록이 자랐고,
화면이 두 번 안 그린 것은 아래 ②가 뒤에서 걸러 준 덕이었다. 이제 **자라지 않는다.**

### ② 그리는 자리 (`MeetingDetailPage`) — 합치는 규칙

- `agendas` — `record.agendas` 와 `stream.agendas` 를 `agenda_id` Map 으로 합치되
  **스트림이 나중이라 이긴다**(= `agenda.updated` 가 옛 제목을 덮는다). 그다음
  `stream.removedAgendas` 를 **걸러낸다** → 본문 목록과 **메모 대상 드롭다운이 함께** 따라간다
  (드롭다운은 `byTrack.memo` 에서 나오므로 자동이다 — 「사라진 안건을 골라 404」가 막힌다)
- `memoLinesOf(agenda)` **(신규)** — 상세의 줄과 스트림의 줄을 `line_id` 로 합치되
  **스트림이 이긴다.** 그다음 `stream.removedLines` 를 걸러낸다

> ⚠ **여기서 하나 고쳤다.** 예전 합치기는 «상세가 이기고 스트림의 같은 id 는 버리는» 모양이었다.
> 그 상태로 `memo.line.updated` 를 받으면 **남이 고친 글자가 조용히 무시된다.** 뒤집었다.

**프레임을 받고 다시 읽지 않는다.** 테스트가 매번 `readMeeting` 이 안 불렸음을 함께 건다.
낙관 렌더도 새로 넣지 않았다 — 그리는 값은 전부 프레임이 실어 온 서버의 것이다.

## 멱등을 어떻게 걸었나

**전부 「id 로 제자리를 짚는다」 하나로 건다.** 순서도, 횟수도, 누가 보냈는지도 안 본다
(`actor` 필드가 없는 이유이기도 하다 — 사람 벌을 손대는 사람은 언제나 회의를 만든 사람이다).

- 같은 프레임이 **두 번** 와도 같은 자리를 다시 쓸 뿐이다
- **자기가 보낸 것이 되돌아와도** 마찬가지다 — `PATCH` 응답으로 이미 그린 그 자리다
- 지우기는 **id 를 남겨 두는 방식**이라 두 번 와도 결과가 같다(`includes` 로 중복도 안 쌓는다).
  상세가 실어 온 줄은 스트림 목록에 없으므로 «지웠다는 사실»을 따로 들어야 걸러진다

## 테스트 일곱 — 브리프가 이름 댄 것 전부 + 둘

| 테스트 | 적색 확인 |
|---|---|
| 남이 고친 메모 줄이 내 화면에서 바뀐다 | **상세가 이기게 되돌리니 적색** |
| 남이 지운 줄이 사라진다 | `removedLines` 필터를 빼니 적색 |
| 안건 제목이 바뀌면 **본문과 드롭다운이 같이** 바뀐다 | (합치기 방향과 같은 자리) |
| 안건이 사라지면 **드롭다운에서도 빠진다** | `removedAgendas` 필터를 빼니 적색 |
| **같은 프레임을 두 번 받아도** 한 번 그린 것과 같다 (줄 고침·새 줄·안건 셋 다) | 상세가 이기게 되돌리니 적색 |
| **내가 보낸 것이 되돌아와도** 두 번 안 그린다 | — (에코 잠금) |
| **모르는 타입은 조용히 지나간다** | — (계약 잠금) |

모든 테스트가 **`readMeeting` 이 안 불렸음**을 함께 건다 — 재조회로 때우는 회귀를 막는다.

### ⚠ 정직하게 — 적색이 안 난 되돌림 하나

스트림의 memo **upsert 를 붙이기로 되돌려도 테스트가 안 깨졌다.** 아래층 ②의 `Map` 이
같은 `line_id` 를 이미 접기 때문이다. 즉 **화면에 보이는 결과로는 두 층 중 하나만 있어도 같다.**

그래도 ①을 둔 이유는 그것이 **보이지 않는 쪽**을 고치기 때문이다: 붙이기면 에코가 올 때마다
`stream.memos` 가 **끝없이 자란다**(긴 회의에서 메모 한 줄을 여러 번 고치면 그만큼 쌓인다).
DOM 으로는 잴 수 없는 성질이라 테스트로 못 걸었다 — **감추지 않고 적는다.**
