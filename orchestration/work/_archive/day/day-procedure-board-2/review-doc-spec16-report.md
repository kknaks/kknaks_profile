## FAIL

### F1. 점유 중에 다시 「점유 이동」하면 규칙 28 과 U-15 가 반대로 말한다
- `spec-002:335` U-15 「점유 이동 뒤 다시 다른 방으로 옮길 수 있다 — **「방 배정」은 그대로 원래 방에 남는다**」.
- `spec-002:823` 규칙 28 ① 「남길 「방 배정」 = 그 방문의 살아 있는 「방 배정」 작업 중 **지금 방에 있는 것** … **없으면** KOS 에 기타 작업 「방 배정」을 만들어 **지금 방에 둔다**. **그 밖의 작업은 … 전부 새 방으로**」.
- 원래 방 A 에서 F 로 점유 이동한 상태(「방 배정」은 A · 카드는 F)에서 G 로 다시 점유 이동하는 경우를 보자.
  - 규칙 28 대로면 F 에는 「방 배정」이 없으니 F 에 새로 만든다.
  - A 의 「방 배정」은 「그 밖의 작업」이라 G 로 간다.
  - 결과: 점유는 A 에서 F 로 바뀌고, 「방 배정」이 둘이 된다.
  - U-15 는 「A 그대로」라 했으므로 서로 반대다. 원래 방(규칙 33 「여럿이면 `sort_order` 첫 행」)과 점유 판정(규칙 28)도 어느 「방 배정」을 볼지 갈린다.
- 정본 :66 「① 점유 이동 = **기존 방**에 「방 배정」 작업 하나 남기고」는 처음 이동만 말한다. 「기존 방」이 원래 방(A)인지 지금 방(F)인지는 점유 중 재이동에서 갈리고, 정본으로는 정해지지 않는다 → **사용자 확인 필요 ①**.
- 고칠 것(사용자 답 뒤):
  - ⓐ A 유지라면 규칙 28 ① 을 「살아 있는 「방 배정」이 있으면 그대로 두고(어느 방이든) 나머지만 옮김 · 없을 때만 지금 방에 만듦」으로 고친다.
  - ⓑ F 로 넘긴다면 U-15 :335 를 고치고 A 의 「방 배정」을 어떻게 할지(취소?) 적는다.

## WARN

### W1. 점유 판정에 「살아 있는(취소 안 된) 「방 배정」」이 빠졌다 — 복귀 뒤 전체 이동하면 점유로 잘못 보일 수 있음
- `spec-002:823` 규칙 28 「점유 = 「방 배정」 작업의 방 ≠ 카드 지금 방」 · 용어 「점유」 행 · `spec-002:420` 「원래 방 = 「방 배정」 작업의 방(**취소된 행 포함**)」 · 규칙 29 「취소된 「방 배정」 행은 원래 방 판정에 남는다」.
- 복귀하면 「방 배정」(A)이 KOS 에서 취소되고(규칙 29), 그 행은 남는다. 그 뒤 전체 이동(G)을 하면 규칙 28 ② 는 「KOS 취소 작업 뺌」이라 취소된 「방 배정」은 A 에 남는다. 점유 판정이 취소 행까지 보면 「A ≠ G」 → 다시 점유로 보이고 띠 · [복귀하기]가 뜬다.
- 원래 방(묶음 기준)은 취소 행을 포함하는 것이 맞다(규칙 33). 점유 판정은 「살아 있는 「방 배정」」으로 좁혀야 한다 — 용어 · 규칙 28 · 스냅샷 `holdRoom` 주석 한 줄씩.

### W2. 의사차트에서 **호출 중** 시술의 집도의를 고르면 KOS 가 그 작업을 수락(READY)으로 볼 수 있다 — OQ-42 기본값 「제한 없음」의 위험이 OQ 에 빠짐
- `spec-002:826` 규칙 31 ② · ③ — 의사 담당자를 바꾸면 `change-tasks-doctors`. `spec-002:911` OQ-42 는 「준비중 · 호출 중 시술의 집도의 → 호출 없이 [시작]」만 말한다.
- DAY 의 [수락] 쓰기는 같은 `change-tasks-doctors` 이고 확인 조건이 「`doctors` 에 그 원장 · **`status = READY`**」이다(SPEC-002 KOS 쓰기 표 [수락] 행 :740 · 코드 `backend/day/emr/kos/writes.py:124`). 그래서 호출 중(KOS WAITING) 작업에 차트에서 집도의를 넣으면, KOS 는 수락된 것처럼 바뀌는데 DAY 호출은 「수락 대기」로 남는다. 다음 조회가 KOS READY 를 어떻게 읽는지(SPEC-002 :466 「KOS `READY` 를 「수락」으로 읽지 않는다」)에 따라 두 화면이 갈린다.
- 앞 결정 4-1(:47 「[시작] = 지금 DAY 조건(수락 → 시작 명시적 · 원장 없이 시작 없음)」)과 바로 부딪치지는 않는다. 준비중 + 담당의 있음 → 호출 없이 [시작]은 지금 규칙 10(U1)이다. 그러나 「원장 변경과 같음」(정본 :64)을 「같은 제한(수락 · 진행중만)」으로 읽을 수도 있다 → **사용자 확인 필요 ②**. OQ-42 에 「호출 중이면 KOS 가 수락으로 바뀔 수 있음」을 더할 것.

### W3. 의사차트로 집도의를 바꿀 때 규칙 27 의 나머지(수락 행 · `task.doctor_change` · 「수락 뒤 미시작」 다시 셈)도 하는지 불분명
- `spec-002:826` 규칙 31 ② 「`visit_task_staff` doctor 덮어쓰기 — 규칙 27 과 같은 쓰기」.
- 규칙 27(원장 변경)은 집도의만이 아니라 수락 행 원장 · `event_log task.doctor_change` · 수락 뒤 미시작 다시 셈 · 원장 상태까지 바꾼다(#236 구현도 그렇다). 차트에서 수락 · 진행중 시술의 집도의를 바꾸면 이것도 하는지 「같은 쓰기」만으로는 갈린다. 「= 규칙 27 전부(수락 · 진행중이면) · 그 밖 상태는 집도의만」처럼 한 줄 적을 것(W2 답과 같이).

### W4. 차트 저장 「담당자 없음」만 HTTP 422 — 이 문서 · 구현의 오류 관례(형식 = 400 · 규칙 = 409)와 다르다
- `spec-002:634` `422 chart_staff_required`(제안). 같은 매트릭스 :618 형식 오류 = 400 `invalid_request`, 나머지 규칙 거절은 409다. 구현 쪽 API 라우터도 「형식 오류는 422 가 아니라 400」(CENTURION_DAY `routers/api/board.py` 머리 주석)이다. 409(규칙 · 필수) 또는 400(형식) 가운데 하나로 맞출 것.

### W5. 옛 차트 JSON 이 「읽기 전용 · 규칙 23」 꼬리표를 단 채 남았다
- `spec-002:523` 「차트 JSON 본문(**개정 ⑯ 전 모양 — 아래 차트 JSON 이 바꿈**): `{… tasks: [{id, title, assigneeNote, doctorNote}]}`(**읽기 전용 · 규칙 23**)」. 규칙 23 은 이제 「쓰기는 31 · 32」라, 앞뒤가 다른 모양 두 개가 한 절에 있다. 취소선(~~ ~~)으로 바꾸거나 지우기를 권한다(U11 반대 문장의 마지막 흔적).

### W6. 간호관리차트 담당자 처음 값에 「저장된 담당자가 있으면 그 사람」을 더했다 — 정본은 「로그인한 사람」뿐
- `spec-002:315` 「처음 값 = **로그인한 사람**(그 줄에 저장된 담당자가 있으면 그 사람)」. 정본 :64 「간호관리차트 담당자 = 처음 값 로그인한 사람 · 다른 사람 고를 수 있음」.
- 괄호 부분은 planner 가 정한 것이다. 이미 다른 간호사가 담당자로 저장한 줄을 내가 열어 글만 고치면, 처음 값을 「로그인한 사람」으로 하면 담당자가 나로 바뀌고, 「저장된 사람」으로 하면 그대로다. 어느 쪽이든 그럴듯해 지어낸 정책이라고 보지는 않는다. 다만 정본에 없으므로 **사용자 확인 필요 ③**.

### W7. 「최근 저장 : HH:MM」은 「이 창에서 저장이 아직 없으면 보이지 않는다」 — 정본은 시점을 말하지 않음
- `spec-002:320`. 정본 :65 「저장 상태 = 모달 오른쪽 회색 글씨 「최근 저장 : {날짜}」 — 시각만」. 창을 열었을 때 그 차트의 마지막 저장(이력 마지막 행) 시각을 보일지, 이 창에서 저장한 뒤에만 보일지가 갈린다. 낮음 — **사용자 확인 필요 ④**(OQ-41 에 묶어도 됨).

### W8. 점유 이동 KOS 쓰기는 새 「방 배정」의 `sequence` 를 모르면 2단계를 보낼 수 없다 — OQ-38 에 있으나 규칙 28 이 「만든다」로 단정
- `spec-002:749` KOS 쓰기 표 · `spec-002:823` 규칙 28 ①. `add-flow-tasks` 응답은 `{}`다(`고객예약접수시술.har` #18 — 이번 리뷰에서 확인). 그래서 새 작업의 `sequence` 는 다음 조회 전엔 모른다. 2단계(`change-tasks-room` 새 「방 배정」 → 기존 방)를 같은 조작 안에서 바로 쌓을 수 없다. 시드 스크립트는 「sequence 1」로 가정했다(`scripts/seed_demo_board.py:13`). 표는 이것을 「확인 안 됨(OQ-38)」으로 정직하게 적었다(PASS). 다만 규칙 28 은 그대로 「만든다」라 구현이 막힐 수 있다. 「`sequence` 를 알 때까지 2단계 op 은 기다림(조회 뒤 쌓음)」 같은 기본값이나 「데모 실물 전엔 점유 이동 = 「방 배정」이 있을 때만」 같은 범위 한 줄이 필요하다 → **사용자 확인 필요 ⑤**.
