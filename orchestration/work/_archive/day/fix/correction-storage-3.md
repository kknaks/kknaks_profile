# 정정 3 — 저장소: 환경은 컨테이너로 나눈다 · 환경 폴더 없음 (2026-11-11 · 사용자)

사용자(2026-11-11): 「daydev / dayprod 이렇게 컨테이너 만들고」 · 「일단 그렇게 했다고 가정하고 코드 짜면 안 돼? 그럼 환경 설정값만 내가 주면 되는 거 아니야?」

→ **컨테이너가 환경별로 있다고 가정하고 짓는다.** `correction-storage-2.md` 결정 2 의 「맨 위 환경 폴더는 그대로 둔다」를 **뒤집는다.**

## 결정

1. **환경 분리 = 컨테이너.** dev 서버는 dev 컨테이너, prod 서버는 prod 컨테이너를 본다. 컨테이너 이름은 환경별 설정값 `DAY_BLOB_CONTAINER`(사용자가 정한 이름: dev = `daydev` · prod = `dayprod`). 값은 사용자가 준다 — 코드 · 시험은 특정 이름을 가정하지 않는다.
2. **경로에 환경 폴더를 두지 않는다.** 키 = `{용도}/{병원 id}/{임의 이름}.{확장자}` → 채팅 = `chat/{병원 id}/{32 hex}.{jpg|mp4}` — **지금 코드의 `new_key` 그대로다**(7판이 더한 `{APP_ENV}/` 접두와 「키의 환경 = 자기 환경」 `check_key` 규칙을 걷어 낸다).
3. 용도 폴더 셋(`chat` · `identity` · `before-after` — 사용자 확정)은 그대로. 컨테이너 안 맨 위가 용도 폴더다.
4. **지금 실제 상태**: 저장소에는 컨테이너가 하나(`files`)뿐이고 `daydev` · `dayprod` 는 **아직 없다** — 사용자가 인프라 담당에게 요청한다(생성 + VM 관리 ID · 본인 계정에 파일 권한). 설정한 컨테이너가 없으면 스펙의 기존 실패 동작(`ContainerNotFound` = 503 · 채팅 글은 정상)으로 간다 — 새로 정할 것 없음.
5. `deploy/config/dev.env`: 계정 주소는 안내문에서(앞 지시 그대로) · `DAY_BLOB_CONTAINER=daydev` · 채팅 첨부 스위치 `blob`. `prod.env` 는 값을 넣지 않는다(칸 · 주석만 — prod 배포 때 사용자).
6. 옛 키(로컬 `disk` 의 `chat/…`)와 새 키 모양이 같아진다 → 7판의 「옛 키 읽지 않음」 문제는 없어진다.

## 누가 무엇을

- **backend(WP-BE-4)**: 2 · 5 를 반영(환경 접두 · 환경 `check_key` 제거 · dev.env 컨테이너 값). 시험에서 환경 폴더 단언을 걷어 내고 「컨테이너 이름은 설정에서만 온다」를 단언. 배포 뒤 실물 확인 명령의 경로도 `chat/{병원 id}/…` 로.
- **planner**: `deployment.md` 「파일 저장소」 절 · env 표 · 용도 폴더 표 · 미결 / SPEC-004 「키」 · C-A26 · C-A27 / SPEC-000 `file_key` / `system.md` / `wp-plan.md` WP-BE-4 를 위 결정으로 고친다. 「맨 위 = 환경(`dev`/`prod`) 폴더」(7판 사용자 확정)는 **사용자가 컨테이너 분리로 바꿨다**고 개정 머리말에 적는다.
