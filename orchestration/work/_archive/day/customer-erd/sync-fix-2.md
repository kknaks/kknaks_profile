## backend (코드 워크트리 `customer-erd`)

1. **FAIL-1 — 무한 재조회를 막는다.**
   - 고객의 시술권을 받은 뒤에도 DAY 에 없는(출처 구매 항목 없음) 티켓 id 를 **병원별 Redis 집합**에 넣는다.
   - TTL 은 그 병원 기준 하루 끝(또는 24시간 · 관례대로) 이다.
   - `ticket_changed_customers` 는 이 집합에 있는 티켓 때문에는 고객을 다시 큐에 넣지 않는다.
   - KOS `ticketId` 가 바뀌거나 구매가 바뀌면 지금처럼 다시 큐에 넣는다.
   - 테스트: 못 푸는 티켓 → 두 번째 회차는 구매 호출만 하고 시술권 · 카드 호출 0 이다.
2. **WARN-1 — 오늘 구매 회차를 별도 태스크로 뗀다.**
   - 일정 태스크 안에서 await 하지 않는다. 일정 회차가 끝난 뒤 `.kiq` 등 기존 taskiq 관례로 발행한다.
   - 같은 일정 응답을 재사용하는 이점은 유지한다: 필요한 입력(구매 id 목록 · 작업 티켓)을 메시지로 넘기거나 Redis 에 둔다. KOS 호출을 늘리지 않는다.
   - 일정 태스크의 실행 시간 · DB 풀 사용이 새 동기화 전과 같아야 한다.
3. **WARN-2 — 예외 범위를 넓힌다.** `fetch_schedules` 안의 `schedule_sale` 은 `except Exception`(+ `noqa: BLE001` · `_isolated` 와 같은 이유 주석)으로 감싼다. 실패하면 판 동기화는 계속하고, sale 쪽만 건너뛰고 센다.
   - 테스트: `schedule_sale` 이 아무 예외나 내도 `fetch_schedules` 결과(판 입력)가 같다.
4. **WARN-3 — 5분 회차에서 카드 이벤트 통계의 카드 id 로 ④(이벤트 · 공유 고객)를 직접 부른다.** ㉔ ⑥ 문구대로다. 상한은 그대로 둔다.
5. **WARN-4 — 5분 회차가 장 수 상한에 걸리면 표시를 「받은 마지막 행 시각」까지 옮긴다.** 같은 시각 행이 겹쳐도 upsert 라 안전한지 확인한다.
   - 테스트: 상한에 걸린 다음 회차는 앞으로 나아간다.
6. **WARN-5** — 위 테스트들로 덮는다. 격리 테스트는 「판 입력 결과 같음」을 직접 본다.
7. 전체 테스트를 돌리고 DEMO 실물로 한 번 더 확인한다. 같은 방식(테스트 계정 · DEMO 테넌트만 · 세션 해제)이고, 오늘 회차 두 번째에 다시 받은 고객이 0 이어야 한다.
