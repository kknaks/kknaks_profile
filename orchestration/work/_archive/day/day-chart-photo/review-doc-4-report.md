## 4. 지적 (파일:줄)

### W1 — OQ-92 행 표가 깨졌고, 옛 기본값이 C23 과 어긋난다 · `spec-002:1359`

- **표 깨짐.** fix-5 가 행 끝 `|` 뒤에 보충 「· (C22 · 2026-11-24) 목록 · 그림은 이제 DAY 에서 읽어 …」을 붙였다. 이 보충이 네 번째 칸이 되었는데 표 머리는 3칸이라 GFM 에서 이 글이 보이지 않는다. 앞 판(`a896cda0`)은 행이 `|` 로 끝났다.
- **옛 기본값이 남아 있다.** 「토큰이 없으면 사진 보기도 세션 만료(위 매트릭스)」가 취소선 없이 살아 있다. 그러나 지금 사진 목록(규칙 39 ①)과 파일 열기는 토큰을 검사하지 않는다. 매트릭스 401 행 :823 도 올리기 · 삭제 · 다시 시도만 적었다.
- **보충 글도 C23 과 어긋난다.** 보충은 「직원 토큰은 올리기 · 삭제 · 다시 시도에만」이라고 적었다. 그런데 C23 가져오기 작업(⑪ ⓓ)은 직원 토큰으로 KOS 를 **읽는다**(`get-visitor-images` · 서명 주소).
- 고칠 방향: 보충을 기본값 칸 안으로 옮긴다. 「사진 보기도 세션 만료」는 취소선으로 남긴다. 토큰을 쓰는 곳에 「가져오기 작업 읽기(⑪ ⓓ)」를 더한다.

### W2 — 지운 「KOS 미반영」 행의 KOS 사진을 가져오기가 어떻게 다루는지 정해지지 않았다 · `spec-002:1212`(③ · ⑤ · ⑪ ⓑ)

일이 벌어지는 순서:
1. 올리기 ⓓ 에서 `register-visitor-images` 는 성공한다. 그 뒤 `get-visitor-images` 로 id 를 찾다가 실패한다. 행 = 「KOS 미반영」.
2. 사용자가 그 사진을 지운다. ⑤ 는 「살아 있는 `external_ref` 가 있으면」만 KOS 를 지우므로 KOS 사진은 남는다.
3. ③ 은 「둘 다 아니면 아무것도 안 함」이라 이 행을 다시 시도할 길도 없다.

그다음 가져오기 ⑪ ⓑ 의 「`fileName` uuid 자리가 이 방문 DAY 행 id」가 지운 행도 셈하는지 적혀 있지 않다. 그래서 갈래가 둘로 나뉜다.
- **살아 있는 행만 센다면:** 새 `source = kos` 행으로 들어온다. 사용자가 지운 사진이 다시 보인다.
- **지운 행도 센다면:** 지운 행에 `external_ref` 를 단다. 그러면 「KOS 삭제 안 됨」이 되고 ③ 으로 지울 수 있다.

코드 워커가 이 둘 중 하나를 고르려면 되물어야 한다. 기본값 한 줄이 필요하다. 제안: 지운 행도 세어 `external_ref` 를 단다. 그러면 KOS 삭제 다시 시도 대상이 되고, 사용자가 지운 사진이 되살아나지 않는다.

### W3 — 같은 KOS 사진을 찾는 방법이 ③ 과 ⑪ ⓑ 에서 다르다 · `spec-002:1212`

- ③(다시 시도)은 그 행의 **`fileName` 전체**로 KOS 사진을 찾는다.
- ⑪ ⓑ(가져오기)는 **uuid 자리 = DAY 행 id** 로 찾는다.

`fileName` 앞쪽에는 `{고객 이름}_{올린 날}` 이 든다(④ · `customer.name`). 첫 시도와 다시 시도 사이에 고객 이름이 동기화로 바뀌면, ③ 은 등록돼 있는 사진을 못 찾는다. 그러면 새로 등록해 KOS 에 같은 사진이 두 장이 된다. 둘 다 uuid 자리로 찾게 맞추는 편이 ④ 의 「같은 이름이 된다」 의도와도 맞는다.

### W4 — 파일 형식 · 확장자가 정해지지 않아 저장소 키 규칙을 만들 수 없다

- 자리: `spec-002:815` · `:1353` OQ-86 · `:1212`(키 `{확장자}` · ⑪ ⓒ 「`content_type` = 받은 형식」) · `spec-000:1202`
- 지금 키 규칙 코드(`contracts.py:19` `KEY_PATTERN …\.(jpg|mp4)$`)는 확장자 목록이 있어야 「키 모양이 맞을 때만 연다」를 만들 수 있다.
- OQ-86 ⓑ(형식)는 「정해지지 않음」이고 기본값이 없다. 매트릭스 :815 의 오류 코드도 「정해지지 않음」이다.
- 가져오기(⑪ ⓒ)는 KOS 가 주는 어떤 형식이든 저장한다고 읽힌다. HAR 에서 KOS 웹이 올린 것은 png 였다.
- C22 로 DAY 가 파일을 저장하게 되면서, 앞 판에는 열어 둘 수 있던 이 OQ 가 막는 자리가 되었다.
- 필요한 것: 기본값 한 줄 — 받는 형식 · 확장자 목록(예: jpg · png), 머리 확인을 할지, 가져오기에서 목록 밖 형식을 만나면 어떻게 할지.

### W5 — 가져온 행의 `created_at` 이 데이터 규칙과 다르고 이유가 없다 · `spec-000:1207` ↔ `spec-000:158`

§2 「생성 · 수정 · 삭제 시각」은 「연동 기간에 외부에서 받은 행은 `created_at` = 외부 생성 시각」이다. `visit_photo` 는 `source = kos` 행도 `created_at` = 「DAY 에 들어온 시각」으로 적었다.

이 규칙과 다르게 가려면 이유를 적는다(예: 「찍은 시각은 `shot_at` · KOS 목록 응답에 생성 시각이 확인 안 됨」). 아니면 규칙을 따른다. DAY-SPEC-000 데이터 규칙의 SoT 가 §2 라, 이대로 두면 코드 워커가 둘 중 무엇을 따를지 되묻는다.

### W6 — 삭제 · 다시 시도의 KOS 401 과, 저장소가 꺼졌을 때의 다시 시도가 매트릭스에 없다

자리: `spec-002:824` · `:825` · `:820` ↔ `:1212` ⑦.

- ⑦ 은 「KOS 가 401 이면 … 그 세션을 끝낸 뒤 401」이라고 모든 사진 동작에 걸리게 적었다. 그런데 매트릭스 401 행 :824 는 **올리기**만 다룬다. 삭제 KOS 실패 행 :825 는 「200 · `kos_unavailable`」이다. 그래서 삭제 · 다시 시도에서 KOS 가 401 을 주면 세션을 끝내는지, 200 토스트인지 갈린다.
- 저장소 꺼짐 행 :820 은 올리기 · 파일 열기 · 목록만 적었다. 저장소에서 파일을 읽어야 하는 [다시 시도](③)는 적지 않았다.
- 매트릭스에 줄 하나씩 더하면 닫힌다. 그러면 코드 워커가 401 갈래를 묻지 않아도 된다.

### W7 — 「KOS 사진 — 직접 호출」 첫머리가 가져오기 작업을 덮지 않는다 · `spec-002:1109`

첫머리 문장은 「탭이 **그 요청 안에서** 부르는 KOS」, 「`Authorization: Bearer <그 요청 세션 직원의 KOS 토큰>`」이다. 그런데 같은 표의 가져오기 행(:1115)과 목록 ↳ 행은 **worker 작업**이 부르는 호출이다. 토큰도 작업 인자 `staff_id` 의 `external_session` 이다(⑪ ⓓ). 첫머리에 「(C23) 가져오기는 중앙 작업 · 탭을 연 직원 토큰 — 규칙 39 ⑪ ⓓ」 한 줄이 필요하다.

### W8 — DAY-SPEC-004 에 `before-after` 가 살아 있다 · `spec-004-internal-chat.md:425`

채팅 키 행에 「전후 사진(`before-after`) 폴더와 섞지 않음」이 남아 있다. 정본 `deployment.md:206` 은 `beforeAfter` 로 바뀌었다. planner 는 범위 밖이라며 코디 판단으로 넘겼다(fix-6 보고 「미결」). 같은 `products/day/` 안에서 이름이 둘이라, 코드 상수를 맞출 때 헷갈린다. 고친다면 취소선 + `beforeAfter` 한 단어면 된다.

### W9 — DB 절 문단이 굵은 「migration 없음」으로 시작한다 · `spec-002:1320`

같은 문단 뒤쪽은 「시술전후사진 = 새 테이블 — migration 필요」다. 첫머리만 읽으면 개정 ㉘ 전체에 migration 이 없다고 읽힌다. 첫머리를 「(개정 ㉘ 차트 탭 저장) migration 없음」처럼 범위를 붙이면 닫힌다. 뜻은 이미 맞으니 글만 고치면 된다.
