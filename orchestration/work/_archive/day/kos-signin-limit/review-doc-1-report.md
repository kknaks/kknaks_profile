- 제안: §3 「직원 — 기기 선택 단계」 2 에 「값에 종류(`kind`)를 담거나 키 접두사를 따로 둔다. 다른 종류의 토큰은 그 단계에서 `session_expired` 로 본다(되돌리지 않음)」 한 줄.

### W-2. 「병원 고르기와 같은 처리」라고 쓴 두 곳이 코드 사실과 다름
- spec-001 :405 · :445: 「고른 id 가 목록 밖이면 400 `invalid_request`. **병원 고르기의 후보 밖 병원과 같은 처리**」. 코드에서 후보 밖 병원은 **403 `no_connected_hospital`** 이다(`services/auth.py:238-239`). 같은 것은 「남은 시간만큼 되돌림」(:225-228) 하나뿐이다.
- spec-001 :182 · OQ-K8 ②: 웹 「`/login?reason=session_expired` — 병원 고르기의 잘못된 병원 값과 같은 처리」. 코드에서 redirect 가 되는 것은 **UUID 로 안 읽히는 값**뿐이다(`routers/login.py:142-145`). 형식은 맞지만 후보 밖인 병원은 오류 카드다(`_failed` :151-152 → `no_connected_hospital` 문구).
- 영향: `invalid_request` 를 그대로 `_failed` 에 넘기면 웹에 「이메일과 비밀번호를 모두 입력해 주세요」가 뜬다(`routers/login.py:43`). 스펙이 redirect 를 따로 정했으니 결과는 맞다. 다만 근거 문장이 틀려서 구현자가 잘못 따라 할 수 있다.
- 제안: 괄호를 「임시 토큰을 남은 시간만큼 되돌리는 것만 병원 고르기와 같다 · 코드는 새로 `invalid_request`」로 고친다.
- 덧붙임(낮음): 웹은 redirect 로 떠나는데 서비스가 토큰을 되돌리면(:405), 비밀번호 암호문이 아무도 못 쓰는 채로 Redis 에 남은 시간만큼 남는다. 웹 경로에서는 되돌리지 않는 쪽도 OQ-K3 에 같이 적어 둘 만하다.

### W-3. 시스템 계정 자동 해제의 남는 왕복 위험이 스펙에 적혀 있지 않음(OQ-K1 근거 부정확)
- 위치: spec-001 :394 · OQ-K1 :598(「같은 환경의 **api · worker** · 병원별 연결이 … 왕복」)
- 코드 사실: 시스템 계정 클라이언트(`KosClient`)는 `emr/factory.py:59-71` `adapter_for` 가 **worker 프로세스 안에서 병원마다** 캐시한다. api 는 들지 않는다. `outbox_kick.py` 는 태스크 이름만 발행한다(:4-8). 그러니 왕복의 주체는 「api · worker」가 아니다. **같은 시스템 계정을 쓰는 병원 연결 수 × worker 프로세스 수**다. 토큰은 만료 10분 전에 새로 받는다(`client.py:37` · :208-212). 401 이면 한 번 더 받는다(:253-271). 그때마다 KOS 로그인이 하나 남는다.
- 기본값 「가장 오래된 하나」의 판단은 맞다. 낡은(stale) 로그인이 대개 가장 오래됐기 때문이다. 하지만 **같은 UA 로그인이 전부 살아 있는 클라이언트의 것**이면(같은 계정을 쓰는 연결 수 ≥ 남은 자리) 이렇게 돈다. A 가 B 를 끊음 → B 의 다음 호출 401 → B 가 다시 sign-in · 막힘 → A 를 끊음 … 호출 하나마다 한 번으로 묶여 있어서 「무한 재시도」는 아니다. 그래도 **호출마다 서로 끊는 지속 왕복**이 된다. 로컬 개발자 둘이 같은 `local` 표시로 같은 시스템 계정을 쓸 때도 마찬가지다.
- 제안: §3 「시스템 계정」에 남는 위험 한 줄. 「같은 표시 로그인이 전부 살아 있으면 서로 끊을 수 있다. 호출당 한 번으로 묶여 무한 반복은 없다. 로그(규칙 5 「n개 해제」)로 본다」. OQ-K1 근거의 「api · worker」는 「worker 의 병원별 연결 · 프로세스」로 고친다. 뿌리(OQ-K16)는 범위 밖이 맞다.

### W-4. 시스템 계정의 해제가 KOS 에서 거절될 때(4xx)가 비어 있음
- 위치: spec-001 :394-396. 직원 쪽은 OQ-K8 ① 로 정했고(:406 · :605), 시스템 계정 쪽은 말이 없다.
- 실제로 생기는 자리: 같은 계정을 쓰는 두 worker 연결이 동시에 막히면 둘 다 「가장 오래된 하나」를 고른다. 같은 id 를 해제하므로 두 번째가 4xx 를 받는다. `_token_lock` 은 클라이언트마다 따로라서(`client.py:207`) 이 경합을 막지 못한다.
- 제안: OQ-K8 ① 기본(「그래도 sign-in 한 번 다시 · 결과대로」)을 시스템 계정에도 쓴다고 한 줄. 쓰면 재시도 1회 상한은 그대로다.

### W-5. 「처음으로」(OQ-K10) 기본값이 같은 문서의 「글자 짓지 않음」과 어긋남
- spec-001 :153 「KOS 웹 화면 글자 그대로 … **이 밖의 글자를 짓지 않는다**」 · :164 · OQ-K10 :613 「기본 = 둔다」.
- K-3 의 화면 글자는 KOS 화면 문구뿐이다. 브리프 §6-1 도 「결정 표에 있는 것만」이라고 했다. 「처음으로」는 이미 승인된 DAY 글자라 새로 지은 것은 아니다. 하지만 기기 선택 화면에 두는 것은 결정 표 밖이다. 스펙이 OQ 로 열어 둔 것은 맞다. 다만 기본값이 「둔다」라서, fe 가 기본값으로 착수하면 결정 표를 넘는 글자가 화면에 들어간다.
- 판정: 넘침(경미). 제안: 기본값을 **「두지 않음」**(KOS 화면 그대로)으로 바꾸고 사용자 확인 뒤 더한다. 둘 경우에는 :153 문장과 맞춘다. 돌아갈 길은 `/login` 새로 열기로도 있다.

### W-6. SPEC-003 ⑱ 「깔린 앱 = `unexpected_response`」에 앞선 조건이 빠짐
- spec-003 :72 ② · :234 · :748 은 `session_controller.dart:203` 만 근거로 든다. 그런데 앱은 그보다 앞서 `:186` `_targetFrom(body, …)` 를 먼저 탄다. 정식 빌드(`requireEnvironment`)는 `environment` · `api_base_url` 이 없거나 허용 origin 밖이면 `environment_unavailable` 로 끝난다(:269-288).
- 그래서 `unexpected_response` 가 되는 것은 **서버가 `choose_device` 에 그 두 칸을 실을 때만**이다. spec-001 :289 가 「앱이면 `environment` · `api_base_url` 도」라고 정해 두어서 계약끼리는 맞는다. 다만 서버 구현이 그 칸을 빠뜨리면 깔린 앱에는 다른 코드가 보인다. 이 조건을 SPEC-003 에 한 마디 적어 두면 be 검수 때 대조할 수 있다.

## 직원이 실물에서 만날 자리

- **앱(깔린 빌드)**: KOS 5개가 꽉 찬 직원이 앱으로 로그인하면 빨간 칸에 `unexpected_response` 만 보인다. 우회 방법(DAY 웹 기기 선택이나 KOS 웹에서 하나 해제)은 앱 안 어디에도 안내가 없다. 현장 공지가 필요하다(spec-003 ⑱ ④).
- **데모 계정(심사관)**: dev 의 데모 계정 로그인이 쌓여 5개가 차면 심사관 앱 로그인이 막힌다. OQ-K7 대로 넘겨도 깔린 앱은 처리하지 못한다. 심사 기간에는 데모 계정 KOS 로그인을 미리 비워 두는 운영 확인이 필요하다.
- **웹 기기 선택**: 「n분 전」만 쓰므로 며칠 된 로그인은 「4320분 전」처럼 보인다(OQ-K5 기본).
- **「계속하기」 뒤 다시 막힘**: 그 사이 다른 기기가 들어오면 같은 화면이 다시 나온다. 다시 나온다는 안내 글자는 없다(K-3 글자만).
- **해제된 기기**: 고른 기기의 DAY 세션은 KOS 가 그 토큰을 거절할 때 끝난다(OQ-K11 미확인). 당장 끊기지 않을 수도 있다.
