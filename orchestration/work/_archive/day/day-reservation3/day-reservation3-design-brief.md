## 2. 배경 / 무엇을 바꾸나

지금 시안의 「예약 요청」은 **본사 요청을 한 번 받아 한 번 답하는** 모양이다 — 상세 창(`approveHtml`)에서 [처리 완료] 또는 [처리 불가](사유 고르기 → 보내기)로 끝난다.

이번에 **슬랙 스레드 같은 구조**로 바꾼다.

```text
스레드 하나 = 예약 하나 (고객 하나 밑에 스레드 여러 개 가능)
 ├ [신규 요청 v1]  ← 링키가 보냄 (예약 등록에 필요한 값이 다 채워진 완성본)
 ├ 우리 · 댓글      "13시 중화권 꽉 찼어요 14시 가능할까요?"
 ├ 링키 · 댓글      "고객 확인해 볼게요"
 ├ [신규 요청 v2]  ← 링키가 값 고쳐 다시 보냄 (14:00)  ← 최신
 └ 우리 [예약 생성] → 예약 확정 (현황판에 카드)
   ...
 ├ [수정 요청 v3]  ← 확정 뒤 링키가 보냄 → 스레드 다시 열림 → 우리 [예약 수정]
 └ [취소 요청 v4]  ← 확정 뒤 링키가 보냄 → 스레드 다시 열림 → 우리 [예약 취소]
```

- 버전은 **늘 링키가** 올린다. 우리는 댓글과 버튼으로만 답한다.
- 병원이 거절하는 버튼은 **없다**([처리 불가] · 사유 창 삭제).
- 예약 카드(스레드) 상태 = **요청됨 · 확정 · 취소됨 · 닫힘** 넷.
- 근무 데이터(원장 근무 · 코디 언어 · 출근)는 **이번에 뺀다** → 근무 일정 칸 삭제 · 판정 경고는 정원 초과만.

## 3. 계약 — 화면 · 상태 목록 (전부 시안에 있어야 한다)

### 3-1. 상세 창(예약 요청 모달) 배치 — 기획자 피드백 그대로

```text
┌─ 예약 요청 ──────────────────────────────────────────── ✕ ┐
│ 1열                │ 2열                │ 3열               │
│ 판정 카드(머리)    │ 예약 현황 요약      │ 스레드             │
│  = 지금 vd2 를 옮김 │  = 지금 rd-sum 을   │  버전 카드 · 댓글  │
│ 고객 · 초진/재진   │    옮김(표/그래프 ·  │  시간 순           │
│ 요청 값(최신 버전) │    ‹ 날짜 › 그대로)  │                    │
│ 상담 · 시술 이력   │                    │  ── 입력부 ──      │
│ 예약 메모          │                    │                    │
├────────────────────────────────────────────────────────────┤
│                              [예약 생성 | 수정 | 취소 버튼]  │
└────────────────────────────────────────────────────────────┘
```

- **1열 머리** = 판정 카드(`slotVerdict` · `.vd2`)를 1열 맨 위로. 값은 **최신 버전** 기준. 경고는 정원 초과만(지정 원장 휴무 · 코디 없음 줄 삭제).
- **2열** = 예약 현황 요약(`daySum` · `.rd-sum`)을 그대로 옮긴다. 원장 · 직원 근무 일정(`dayStaff`)은 **삭제**.
- **3열** = 스레드(새로 그림 — §3-2).
- **아래 버튼** = 맨 위 버전 종류에 따라 하나: 신규 → 「예약 생성」 · 수정 → 수정 버튼 · 취소 → 취소 버튼. 확정 · 취소됨 · 닫힘 상태(답할 버전 없음)면 버튼 없음. [처리 불가] · `rejectHtml` 창 · `REJECT` 사유 목록 · 「쓰던 메모를 버릴까요?」 창은 **삭제**.
- 같은 고객 후보 창(`dupPop` — [이 고객으로 예약] / [새 고객으로 등록])은 **그대로** 둔다(예약 생성 때).
- 창 크기는 지금(1080 × 700)에서 3열이 들어가게 조정해도 된다 — 바꿨으면 리포트에 값.

### 3-2. 3열 스레드

- **버전 카드**: 종류(신규 요청 · 수정 요청 · 취소 요청) + 번호(v1 · v2 …) + 받은 시각 + 요청 값 요약(일시 · 그룹(열) · 시술/메모 첫 줄). **최신 버전** 표시. 앞 버전 대비 바뀐 값은 「13:00 → 14:00」처럼 보인다.
- **댓글**: 글쓴이(우리 = 직원 이름 · 링키 = 링키 상담사 이름) + 시각 + 글. 우리 / 링키를 한눈에 구분.
- **시스템 줄**: 「예약 생성됨」 · 「예약 수정됨」 · 「예약 취소됨」 같은 처리 기록(누가 · 언제).
- **입력부**(3열 맨 아래): 글 입력 + 보내기. 그리고 **「변경 제안」 검토용 변형 하나** — 타입을 고르면 일시만 고르는 칸(2열 예약 현황 표의 시간 칸을 누르면 채워짐) + 선택 글. 제안 댓글은 상태 배지(답변 대기 · 수락 · 거절 · 대체됨) 를 갖는다. ⚠ 변경 제안은 **아직 미정**(_RESUME §1 P1 ~ P7) — 시안에서 「검토용」 으로 따로 보이게 두고, 기본 입력부는 글 + 보내기.

### 3-3. 오른쪽 패널 「예약 요청」 목록(인박스 카드)

- 제목 「예약 요청 n」 · 카드 = 이름 · 희망 일시 · 국적 · 통역(지금 그대로) **+** 맨 위 버전 종류 배지(신규 · 수정 · 취소) **+** 새 글 점(링키 쪽 새 버전 · 새 댓글이 있으면).
- 새 버전 · 링키 댓글이 오면 카드가 목록 맨 위로.
- 처리할 게 있는 스레드(상태 「요청됨」)만 목록에. 확정 뒤 수정 · 취소 요청이 오면 다시 목록에 올라온다.
- 알림: 새 요청 · 새 버전 · 링키 댓글이 오면 현황판에 토스트(기존 토스트 부품이 있으면 그것). 시연 버튼(가짜 「링키 새 글 도착」)으로 재현할 수 있게.

## 9. 완료 보고 — **문구 변경 금지**

> **⚠ 핸들은 dispatch preamble 의 값을 믿어라.** 아래 명령에 박힌 코디handle 은 **브리프 작성 시점** 값이라 오래됐을 수 있다 — 세션이 재연결되면 핸들이 바뀐다(2026-07-28·29 두 번 겪음). preamble 의 코디네이터 핸들과 아래 값이 다르면 **preamble 이 맞다.** 두 곳에 다 보내지 말고 preamble 쪽으로만 보내라.


- **커밋·push·PR 하지 마라.** 워크트리에 변경만 남긴다. 검증·PR 은 코디네이터가 한다.
- 끝나면 **아래 두 명령을 모두** 실행한다. 하나만 하면 안 된다.

```bash
# (1) 인박스 적재 — 태스크 완료 처리·영구 기록. 코디네이터를 깨우지 않는다.
orca orchestration send \
  --to term_5c196973-a9ec-4982-81c2-655361f18aec --from term_7e47fe77-2f67-4fd1-99ef-28fd8de41111 \
  --type worker_done \
  --task-id <이 태스크의 taskId — dispatch 로 받은 context 에 들어 있다> \
  --dispatch-id <이 태스크의 dispatchId — dispatch 로 받은 context 에 들어 있다> \
  --subject "designer 완료: <한 줄>" \
  --body "변경 파일 목록 / 구현 요약 / 검증 결과(수치) / 계약 준수 / 미결·주의점"

# (2) 직접 주입 — 코디네이터 세션에 유저 메시지로 꽂혀 자동으로 깨운다.
orca terminal send --terminal term_5c196973-a9ec-4982-81c2-655361f18aec \
  --text "[worker_done] designer 완료 — <한 줄 요약>. 상세는 인박스." --enter
```

- 막히면 30분 이상 혼자 헤매지 말고 같은 (2) 방식으로 물어라:
  `orca terminal send --terminal term_5c196973-a9ec-4982-81c2-655361f18aec --text "[질문] designer: <질문>" --enter`
  (`orca orchestration ask` 는 채널이 닫혀 답이 안 닿는 경우가 많다.)
