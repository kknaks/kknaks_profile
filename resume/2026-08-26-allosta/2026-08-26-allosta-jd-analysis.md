### 3.2 요구사항 분석 — 왜 이걸 요구했나

항목마다 **요구 사유**(§2 회사 정보에 근거한 읽기)와 **필요 개념**(구분: 기술 · 경험 · 인적 역량 · 도메인).

#### 3.2.1 풀스택 개발 경력 2년 이상 `필수`

**요구 사유** — 시니어 층이 얇은 초기 팀이 사수 붙일 여유 없이 한 사람에게 제품 한 축을 맡기는 구조다(업무 4행이 FE+BE+인프라+아키텍처 전부인 것이 방증). 2년은 연차 심사가 아니라 「혼자 배포하고 장애를 겪어 본 최소선」— 공고 스스로 "하한선"이라 부른다.

| 필요 개념 | 구분 |
|---|---|
| 실서비스 배포·운영을 끝까지 겪은 이력 | 경험 |
| 장애 대응 — 원인 추적·복구·재발 방지 | 경험 |
| 사수 없이 스스로 학습·판단하는 습관 | 인적 역량 |

**나의 강점**
- 개념/보유 — 개발 13개월(퀀터스 6 + 메디솔브 7) + 도화 4년(다부서 조율) 직장 경력
- 적용 — 사수 없는 환경에서 배포·운영을 직접 완주: 개인 제품 기획→출시→운영, 회사에선 입사 직후부터 제품 백엔드 전담
- 결과 — 입사 4개월 만에 AX 리더(4인 팀 기술 총괄) · App Store 심사 통과 · PyPI 배포 · 홈서버 라이브 운영 중

**나의 약점** — **풀스택 경력 2년 미달** — 개발 경력 약 13개월(퀀터스 2025.08–2026.02 + 메디솔브 2026.02–현재). 15개 항목 중 유일하게 수치로 반박 불가능한 미달. 「하한선」 선언에 기대어 역량 축으로 상쇄해야 한다.

#### 3.2.2 다양한 FE·BE 프레임워크 활용 `필수`

**요구 사유** — 제품이 3표면(검사·커머스·앱)에 어드민까지, 표면 수가 사람 수보다 많다. 특정 스택 전문가보다 낯선 표면에 빨리 진입하는 제너럴리스트가 필요하다.

| 필요 개념 | 구분 |
|---|---|
| 프레임워크를 관통하는 공통 원리 — 라우팅·상태·렌더링 / 계층·ORM·미들웨어 | 기술 |
| 둘 이상의 FE·BE 스택을 실물에서 오간 이력 | 경험 |
| 새 스택 진입 속도 — 전이 학습 | 인적 역량 |

**나의 강점**
- 개념 — 언어를 바꿔도 남는 원리를 `cs` 169건으로 분리, 프레임워크 내부는 `back` 137건(servlet→spring-boot 계보를 원리 단위로)
- 적용 — 같은 원리를 스택 넘어 재사용: FastAPI(회사·개인) ↔ Java/Spring(학습 계보) ↔ Next.js · RN/Expo · Swift/SwiftUI
- 결과 — 한 사람이 kknaks.dev 웹(Next.js), RN 앱 3종(wine-log·study-timelapse·language-diary), Swift 앱 1종(DeskDeck)을 만들어 운영 중

**나의 약점** — NestJS 실물 없음. 그리고 지식 체계화가 백엔드 편중 — concept `front` 는 2건뿐이라, FE 는 실물은 있는데 원리 기록이 얇다.

#### 3.2.3 Docker·Kubernetes 클라우드 인프라 구축·운영 `필수`

**요구 사유** — 인프라 전담이 없다. 만든 사람이 배포·운영까지 든다("구축 및 운영"이 업무 문장마다 반복). 커머스 프로모션·챌린지 오픈 같은 트래픽 스파이크에 오토스케일로 대응하고, 흑자 기조라 클라우드 비용 효율도 직접 챙겨야 한다.

| 필요 개념 | 구분 |
|---|---|
| 컨테이너 · 이미지 빌드 · 레지스트리 | 기술 |
| 오케스트레이션 — 워크로드 · 스케일링 · 셀프힐링 | 기술 |
| CI/CD · 무중단 배포 | 기술 |
| IaC · 모니터링/알림 | 기술 |
| 인프라를 직접 세우고 운영해 본 이력 (규모 무관) | 경험 |

**나의 강점**
- 개념 — `container` `kubernetes` `kubernetes-workload` `infrastructure-as-code` `ci-cd` `zero-downtime-deployment` `reverse-proxy` `monitoring`
- 적용 — 홈서버에 Docker + 리버스프록시로 kknaks.dev 전 구성(백·프론트·DB·워커) 배포, 리뉴얼 워커 컨테이너화(compose), 퀀터스에서 AWS RDS → Azure MySQL **800GB 무중단 이관**(3방안 비교 → DMS 선택, binlog CDC 복제 후 접속 전환)
- 결과 — 도메인 2개(profile.kknaks.cloud · profile-api.kknaks.cloud) 라이브 운영 중, 800GB DB 를 다운타임 없이 이관 완료(블로그 기록 공개)

**나의 약점** — **K8s 실물이 없다.** 개념·스터디 수준이고, 매니지드 클러스터(EKS 류) 운영 이력이 없다. 필수 4행 중 절반만 채우는 항목 — Docker 운영 실물로 방어하고 K8s 는 학습 중으로 정직하게 두는 쪽이 맞다.

#### 3.2.4 대용량 트래픽 처리·성능 최적화 `필수`

**요구 사유** — B2C 라 사용자 수가 곧 매출이고, 매년 2배 성장 중이라 지금 아키텍처가 2년 뒤 4배 부하를 견뎌야 한다. 검사 결과 조회·커머스 주문·AI 코칭 알림이 겹치는 피크를 소수 인원이 감당한다.

| 필요 개념 | 구분 |
|---|---|
| 캐싱 전략 | 기술 |
| DB 인덱싱 · 파티셔닝 · 쿼리 최적화 | 기술 |
| 커넥션 풀 · 로드밸런싱 | 기술 |
| 병목을 측정으로 찾는 성능 테스트 | 기술 |
| 실제 부하를 수치로 개선해 본 이력 | 경험 |

**나의 강점**
- 개념 — `caching` `database-index` `elasticsearch` `load-balancer` `connection-pool-sizing-formula` `universal-scalability-law` `little-law` `async-io` `performance-testing`
- 적용 — 퀀터스 Insight 조회 표면을 MySQL 동기 접근 → Elasticsearch 비동기 검색으로 전환: 병목을 다층 진단(인덱스 부재·중복 쿼리·메모리 페이지네이션·동기 블로킹), 원장-인덱스 분리(Logstash), 집계 쿼리로 호출 3→1회, k6 로 전후 실측
- 결과 — **고부하(300 VUs) 처리량 3.2배**(RPS 25.7→81.2) · **평균 응답 −68%**(5,173→1,637ms) · P95 −57%, worker timeout 해소, 성공률 100% 유지 — 블로그에 측정 기록 공개 (`para/archive/company/insight/showcase.md`)

**나의 약점** — 「대용량」의 절대 규모는 아니다 — 증거는 300 VUs 부하 실측까지이고, 수백만 사용자 급 트래픽 운영 경험은 없다. 다만 병목 진단 → 구조 전환 → 측정 증명의 방법론은 수치로 서 있다.

#### 3.2.5 React / React Native 프론트엔드 (모바일·웹) `업무`

**나의 강점**

- 개념/보유 — 라이브 실물 + AI 워크플로 설계 경험 (`workflow-orchestration` `human-in-the-loop`)
- 적용 — 옛 레포 이관에 워커 10대 병렬 분류(concept 366건), 커밋→AI 요약 파이프라인(잔디), 문서 우선 + AI 구현 방식의 회사 적용
- 결과 — 지금 접속 가능한 증명: kknaks.dev(홈서버) · DeskDeck(App Store) · wine-log(운영 중) · open-kknaks(PyPI)

**나의 약점** — 증명 자료가 흩어져 있다. 라이브 링크·수치·스토리가 이력서/포트폴리오 표면 하나로 정리돼 있지 않다 — 지금 이 작업이 그걸 만드는 중.

## 4. 어필 전략 — 이력서를 어떻게 쓸 것인가

§3.2 의 강점/약점을 채용담당자 관점으로 뒤집는다: **무엇을 부각하고(정면),
무엇을 다른 소스로 커버하고(우회), 무엇을 경합하고(방어), 무엇을 말하지 않나(침묵).**

### 4.1 항목 × 소스 매핑

어필 소스는 둘이다 — **프로젝트(회사 실무)** 가 기본값이고, 회사로 못 덮는 것만
**사이드**가 맡는다. 실무 증거가 사이드 증거보다 신뢰가 높기 때문.

| 요구 항목 | 수준 | 소스 | 어필 카드 | 방식 |

| 대용량 트래픽·성능 | 필수 | 프로젝트(퀀터스) | ELK 전환 — 처리량 3.2배 · 응답 −68% (k6 실측) | **정면 부각** |

### 4.2 약점 경합 — 셋만 다룬다

**① 경력 2년 미달 (13개월)** — 숨기지 못한다(경력 기간이 표면이다). 전략은
**선제 재프레임**: 공고 스스로 "기술 스택은 하한선, 진짜 보는 건 문제를 끝까지
푸는 힘"이라 선언했으니, 소개 첫 문단에서 연차 대신 **밀도**를 먼저 제시한다 —
입사 4개월 만에 AX 리더 · 6개월 무장애 · 처리량 3.2배. 도화 4년은 「직장 경력
5년+」로 사회인 근육을 보증한다. 연차를 사과하지 않는다.

**② K8s 실물 없음** — 이력서에서 K8s 를 **쓰지 않는다**(거짓 나열이 최악수).
대신 Docker 운영 실물(홈서버 전 구성 배포·워커 컨테이너화)과 800GB 무중단
이관으로 「인프라를 직접 드는 사람」을 증명한다. K8s 는 면접 질문에 정직하게 —
개념 학습 완료·실물 없음·필요하면 빠르게 세운다.

**③ 고객 관점 사용성** — B2C 지표 실물이 없다. 이력서에서는 **사용자가 있는
제품을 만들어 왔다는 사실**로 간접 증명한다 — 의료진·상담사가 매일 쓰는 화면,
App Store 심사(외부 사용성 기준) 통과. 별도 절로 주장하지 않고 bullet 안에
사용자 주어를 심는다("상담사가 ~할 수 있게").

침묵 항목: FaaS(비동기 실물로 대체), NestJS(요건이 「또는」).

### 4.3 배치 — 이력서 절 ↔ 요구 항목

| 이력서 절 | 치는 항목 |
|---|---|
| 소개 (3~4문장) | 역량 4축 선언 + 수치 예고 + ① 경합(밀도 재프레임) |
| 경력 · 퀀터스 | 성능(필수) · 비동기(업무) · 문제 정의(서술 구조) |
| 경력 · 메디솔브 | 헬스케어(우대) · FastAPI(업무) · 아키텍처(업무) · AI 방식(역량) |
| 경력 · 도화 | ① 경합 보조(직장 경력 5년+) |
| 사이드 · 여름별컴퍼니 | RN(업무) · 오너십(역량) · 증명(역량) · ② 경합 보조(Docker 운영) |
| 기술표 | 프레임워크 폭(필수) — K8s 미기재 |

**순서 논점** — JD 가 역량(문제 정의·완성)을 최상단에 둔 공고라, 경력(문제 해결
스토리)이 위, 사이드(오너십 증명)가 아래인 현재 순서가 맞다. 단 사이드를 「부록」
이 아니라 「역량 4축 중 두 축의 본 증거」로 쓴다 — 분량을 줄이지 않는다.
