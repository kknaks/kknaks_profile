## 한 일

mediness에서 진행 중이던 이니셔티브 세 갈래가 각각 한 단계 나아갔다. 랜딩 채팅(SPEC-230/WP-102)은 미확정 질문을 실측 스파이크로 해소하며 계약을 다시 썼다 — MCP 토큰 만료 위험은 턴 도중이 아니라 refresh rotation 폐기 타이밍이었고, 스트림 유실 복구는 브로커(Redis Stream) 특성에 맞춰 2단 구조로 재설계됐다. 조직도 cutover(사람 참조를 organization_member로 전환)는 ax 실행 태스크 도메인(SPEC-154)까지 확장했다 — 배정 자리뿐 아니라 감사·결재선 자리까지 전수조사해 불일치를 차단했다. 의사결정 인테이크는 Slack 게이트 run 제목이 본문을 잘라 문단이 되는 결함을 발견해 title/본문 축을 분리하고, 방치된 후보안 소비 표면 공백을 SPEC-154 소유로 명시했다.

kknaks_profile은 자동 발행 파이프라인이 mediness 작업 요약을 career 문서(무슨 일/담당 영역/챌린지/배운 점)에 반영하고 8/4 데일리를 실었다. 별도로 알고리즘 로그에서 A-077 today 플래그를 끄고 A-078(전화번호 글자 조합)을 오늘의 문제로 올렸다.

open_kknaks는 mediness P8 실측 중 재현된 codex_adapter 버그 두 건을 고쳤다. asyncio 스트림 리더의 묵시적 64KiB 줄 길이 한계에 MCP tool 결과 JSONL이 걸려 태스크가 죽는 문제를 10MiB로 올려 해소했고, mcp_tool_call 이벤트의 실제 툴명이 tool 필드에 실린 걸 몰라 폴백 체인이 빗나가던 문제를 고쳤다.

## 막힌 것 · 판단

랜딩 채팅 스파이크에서 애초 세운 위험 가정 두 개(토큰 만료 지점, 스트림 유실 시나리오)가 실측으로 뒤집혔다 — 잘못된 위험을 방어하고 있었다. 발화에서 승인 게이트로 이어지는 흐름은 설계상 있는데 그 게이트를 열 MCP 툴이 실제 코드엔 없다는 걸 인벤토리 점검으로 뒤늦게 발견해, 계약됐지만 구현이 빠진 조각으로 규정하고 전제조건으로 못박았다. 범용 승인 요청 툴 1개로 여러 도메인을 묶는 안은 파라미터 스키마가 뭉개져 기각했다. 조직도 cutover는 배정 자리만 옮기면 사람 축이 갈라진다고 보고 4군 27자리 전수조사를 택했다. open_kknaks의 두 버그는 코드 리뷰가 아니라 실제 운영 재현(mediness P8)으로 드러났다.

## 알게 된 것

승인 행위 자체가 추적 가능한 태스크로 남는 설계(부트스트랩 태스크)가 여러 워크플로에서 재사용 가능한 패턴임을 확인했다. 설계 초안의 축 오류·좌표계 불일치는 스펙 선행만으로 안 잡히고 구현·실기동과의 짧은 피드백 루프가 있어야 드러난다. tool 노출 축과 인증 축을 분리하면 같은 통제 패턴을 다른 세션·에이전트 표면에도 재사용할 수 있다. 실측 결과가 사전 질문의 전제를 뒤집을 때는 답만 채우지 않고 질문·계약을 재작성해야 한다는 패턴이 반복 확인됐다.
