# jd-analysis — 채용 공고 분석 스킬

공고 URL 하나를 받아 **원문 박제 → 개요 → 회사 정보 → 요구사항 분해 → 강점/약점
매핑** 순서로 분석 문서를 만든다. 산출물이 이력서 작성의 입력이 된다.

> 세트 구성 — [template.md](./template.md) 분석 문서 양식 ·
> [resume-template.md](./resume-template.md) 이력서 양식 ·
> [checklist.md](./checklist.md) 진행 체크리스트 ·
> [scripts/fetch_jd.py](./scripts/fetch_jd.py) 공고 크롤러 ·
> [scripts/build_pdf.py](./scripts/build_pdf.py) resume.md → A4 PDF

## 산출물

```text
resume/YYYY-MM-DD-<회사slug>/
├── jd.md                                  원문 박제 — frontmatter 메타 + 원문 그대로
├── YYYY-MM-DD-<회사slug>-jd-analysis.md   분석 — template.md 양식 (§1~§4)
├── resume.md                              이력서 — resume-template.md 양식
└── resume.pdf                             제출본 — build_pdf.py 산출
```

## 절차

**절 단위로 사용자와 진행한다. 한 번에 끝까지 쓰지 않는다** — 각 절을 마치면
보고하고, 다음 절은 사용자 확인 후 간다. (옛 jd-analysis 스킬의 폐기 원인이
시킨 범위를 넘어 혼자 완주한 것이었다.)

1. **jd.md — 원문 박제.** `scripts/fetch_jd.py <URL>` 로 크롤링한다. 403 이면
   스크립트가 브라우저 UA 로 재시도하고, SPA(greetinghr 류)면 `__NEXT_DATA__`
   JSON 에서 본문·메타를 파싱한다. frontmatter 에 회사(법인명)·포지션·고용형태·
   근무지·게시~마감·조회일을 적고, 본문은 원문 그대로 — 수정·요약하지 않는다.
   마감일 등 메타는 페이지 데이터가 정본이다(공고 텍스트보다 정확하다).
2. **§1 개요** — jd.md frontmatter 를 표로.
3. **§2 회사 정보** — 아래 「회사 정보 수집」 방법으로 모은다. **자사 서술과
   외부 확인을 출처로 가른다.** 제품 구조에는 「기술 함의」를 달아 JD 의 기술
   요구가 제품 어디에 걸리는지 잇는다. 추정은 추정이라고 적는다.
4. **§3.1 요구사항 표** — 원문의 절(자격요건·주요 업무·우대·인재상)을 수준
   축(필수·업무·우대·역량)으로 삼아 구분·항목·수준 3열로. 원문 인용은 jd.md 가
   담당하므로 복사하지 않는다.
5. **§3.2 항목별 분석** — 항목마다 네 블록:
   - **요구 사유** — §2 에 근거해 「왜 이 회사가」를 읽는다
   - **필요 개념** 표 — 기술/경험/인적 역량/도메인 구분
   - **나의 강점** — 개념→적용→결과 세 층. 근거는 para 맵에서만:
     `para/areas/area.md` §3.4(concept 맵) · `para/projects/project.md` §4 ·
     각 showcase.md · DB(career·product·problem)
   - **나의 약점** — 미달은 미달로. 방어 전략이 있으면 한 줄
6. **빵구 처리** — 결과(수치·스토리)가 없는 강점은 「없음 — 발굴 필요」로 남긴다.
   인터뷰로 소재가 나오면 **원장부터 갱신한다**: showcase/problem 에 쓰고 →
   DB 등록하고 → 분석 문서를 갱신한다. 분석 문서에만 적고 끝내지 않는다.
7. **§4 어필 전략** — §3.2 를 채용담당자 관점으로 뒤집는다. 세 표:
   - **항목 × 소스 매핑** — 요구 항목마다 소스(프로젝트=회사 실무 기본값,
     회사로 못 덮는 것만 사이드)와 방식(정면 부각 / 커버 / 경합 / 침묵)을 정한다.
     실무 증거가 사이드 증거보다 신뢰가 높다.
   - **약점 경합** — 숨길 수 없는 미달은 선제 재프레임(사과하지 않는다),
     실물 없는 기술은 침묵(거짓 나열이 최악수), 얇은 축은 서술 방식으로 간접 증명
   - **배치** — 이력서 절 ↔ 요구 항목 대응표
8. **resume.md 작성** — §4 확정 후에만. `resume-template.md` 양식. 링크는
   DB(project.links · product.links)에서 꺼낸다 — 스토어·PyPI·repo·라이브.
9. **한글화** — `/korean-humanizer` 를 resume.md 에 적용한다. 이력서 특칙:
   - **산문 문장 안의 줄표(—)는 전부 제거** — 문장 분리나 어미 연결로 푼다
   - **제목의 `—` 구분자는 서식이라 보존** — h3(`회사 — 역할 · 기간`)와 bullet
     머리(`**카드 제목 — 결과.**`). PDF 테마의 기간 우측정렬이 여기 의존한다
   - 기간의 `–`(YYYY.MM – YYYY.MM)와 가운뎃점 나열(스택 표기)은 날짜·서식이라 보존
   - 수치·고유명사 100% 보존 확인 후 등급(A~D)을 보고한다
10. **PDF** — `scripts/build_pdf.py resume.md` → A4 PDF (playwright 가 설치된
    python 으로 실행). frontmatter(전략 메모)는 자동 제외된다. 생성 후 렌더를
    눈으로 확인한다 — 헤더 연락처 3행(이메일/깃허브/블로그) · 기간 우측정렬 ·
    링크 행 스타일 · 페이지 나눔. 이력서는 사이트 밖에서 관리한다(_RESUME.md §5)
    — 레거시 `/print` 라우트를 살리지 않는다.

## 회사 정보 수집

두 층을 따로 모으고, 표의 「출처」 컬럼에 어느 층인지 적는다.

**자사 서술** — 회사가 스스로 하는 말. 과장이 섞이므로 "자사 주장"으로 다룬다.
- 채용사이트 랜딩(공고 말고 회사 소개 페이지) — greetinghr 류 SPA 는 공고와 같은
  방식으로 `__NEXT_DATA__` JSON 안에 소개 문구·핵심가치·연혁이 통째로 들어 있다.
  `fetch_jd.py` 로 안 잡히면 curl + 브라우저 UA 로 받아 파싱한다
- 회사 공식 홈페이지 · 브랜드 SNS(랜딩 footer 에 링크가 있다)

**외부 확인** — 제3자가 확인한 사실. 자사 주장과 겹치면 「자사 + 외부 일치」로 승격.
- 투자 DB — THE VC(`thevc.kr/<법인명영문>`): 설립일 · 대표 · 투자 라운드 · 업종 분류
  (옛 분류가 회사의 원류를 드러내기도 한다)
- 언론 — 웹검색 쿼리 패턴: `<법인명> <브랜드명> 투자 설립`, `<법인명> 시리즈`,
  `<법인명> 매출`. 보도자료(뉴스와이어 류)는 회사발이므로 자사 서술에 가깝게 취급
- 브랜드명 ≠ 법인명이면 **둘 다로 검색한다** — 법인명 쪽에 투자·재무 기사가 걸린다

수집 후 §2.5 「읽히는 것」에 추론을 몰아 적는다 — 사실 절(2.1~2.4)에 추론을 섞지
않는다.

## 문장 톤

- **단정형으로 짧게.** "~로 보인다"를 남발하지 않는다 — 근거가 있으면 단정하고,
  없으면 추정 표시를 하고 §2.5 로 보낸다.
- **수치·고유명사가 문장을 끈다.** "성능을 크게 개선" 이 아니라 "처리량 3.2배
  (RPS 25.7→81.2)". 근거 없는 수치는 아예 쓰지 않는다.
- **강점의 결과 층은 증거 문장이다** — 출시·운영·측정 중 하나로 끝나야 한다.
  형용사로 끝나면 결과가 아니다.
- **AI 티를 걷어낸다** — 번역체(~을 통해 · ~에 대한), hype 어휘(혁신적·강력한),
  결산 상투구(결론적으로 · 주목할 만하다) 금지. showcase 템플릿의 톤 규칙과 같다.
- **요구 사유는 회사의 사정으로 쓴다** — "이 기술이 중요해서"가 아니라 "이 회사의
  제품 구조·팀 규모·성장 단계 때문에"로. §2 에 근거가 있어야 한 문장이 성립한다.

## 규칙

- **옛 이력서·옛 분석의 주장을 근거 없이 끌어오지 않는다.** 원장(블로그·showcase·
  DB)에 근거가 있는 수치만 쓴다.
- **강점을 지어내지 않는다.** concept slug 는 실제 파일명으로, 실물은 실제
  제품명으로.
- **약점은 정직하게.** 수치로 반박 불가능한 미달(연차 등)은 그대로 적고 상쇄
  전략을 따로 적는다.
- 크롤링은 공개 페이지만. 페이월·봇 차단은 우회하지 않는다.
