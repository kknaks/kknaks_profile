# Reconstruction 형식

## 1. 문서 머리

```markdown
# 발표 재구성 — <회사·발표 식별자> (<행사, YYYY-MM-DD>)

발표자: <이름 또는 미확인> (<소속>) · <음성 또는 녹취 길이>
원료: 같은 폴더의 `transcript.txt`(STT <블록 수>) + 음성 원본 + 슬라이드 사진 <N>장

슬라이드 순서대로 복원했다. 각 대목은 **사진 → 슬라이드가 보여준 것 → 발표자가 말한 것**
순이다. 사진이 없는 구간은 녹취만으로 적고 그렇다고 밝혔다.
```

음성 원본이 없거나 사용하지 못했다면 원료 줄에서 빼고 이유를 적는다. 발표자, 소속, 행사,
날짜를 확인하지 못했으면 추정하지 말고 `미확인`으로 둔다.

녹취 잘림이나 사진 누락처럼 문서 전체의 해석에 영향을 주는 문제는 머리말 다음에 인용문으로
먼저 경고한다.

```markdown
> **녹취 앞부분이 잘려 있다.** 첫 블록이 발표 중간 문장으로 시작해 발표자 이름을 확인할 수
> 없다.
```

## 2. 시간순 복원

발표의 큰 부가 실제로 나뉘어 있으면 H1, 개별 슬라이드와 사진 없는 발화 구간은 H2로 쓴다.
번호는 사진 번호와 맞춘다.

```markdown
# 1부 — <발표의 실제 부 제목>

## 03 · <슬라이드 제목 또는 내용을 드러내는 제목>

![무엇이 보이는지 설명하는 대체 텍스트](03-semantic-name.webp)

**슬라이드**

<화면에 실제로 보이는 문구·표·단계·관계의 재구성>

**발표자**

> 「<해당 슬라이드를 설명한 실제 발화>」
```

사진이 없는 구간은 번호를 만들지 않는다.

```markdown
## 서비스 소개와 현업 반응 (00:02:52 ~ 00:03:38) — 사진 없음

<해당 구간의 설명과 인용>
```

한 슬라이드가 애니메이션이나 단계적 공개로 여러 장 찍혔다면 각각 무엇이 추가됐는지 설명한다.
같은 내용을 중복해서 전부 옮기지 않는다. 한 개념을 보여주는 연속 사진은 `21–22`처럼 묶을 수
있지만 두 사진의 차이를 본문에 남긴다.

### 슬라이드 재표현

- 문장과 짧은 목록: Markdown 본문 또는 목록
- 행·열 비교와 분류: Markdown 표
- 화면 속 텍스트 배치가 의미를 가질 때: `text` 코드 블록
- 노드와 연결 관계가 핵심일 때: Mermaid
- 제품 화면: 화면에서 확인되는 조작·출력만 설명하고 보이지 않는 내부 동작은 추정하지 않음

슬라이드의 모든 장식 문구를 옮기는 것이 목표가 아니다. 발표의 주장과 구조를 이해하는 데 필요한
텍스트·숫자·관계를 빠짐없이 복원하는 것이 목표다.

### 발표자 발화

핵심 설명은 직접 인용으로 남기고, 반복·군더더기는 인용 밖에서 짧게 연결한다. 여러 문장을
이어 붙일 때 원래 순서를 바꾸지 않는다. 숫자나 고유명사를 수정했다면 음성으로 확인한 경우에만
본문에 반영하고 transcript 원문은 그대로 둔다.

## 3. 재구성하면서 남긴 것

시간순 복원 뒤에 근거의 한계를 적는다.

```markdown
## 재구성하면서 남긴 것

- **사진이 없는 구간** — <범위와 복원 근거>
- **녹취 누락** — <앞·뒤 잘림 또는 무음>
- **슬라이드와 발화의 충돌** — <각 근거가 무엇을 말하는지>
- **비식별·가림** — <확인할 수 없는 데이터·기능·성과>
- **미식별 사진** — <파일명과 제외 이유>
```

해당 사항이 없는 항목을 억지로 만들지 않는다.

## 4. 최종 정리

최종 정리는 발표 순서를 반복 요약하는 절이 아니다. 발표가 다룬 실제 사례 단위로 경험을
재구성한다.

```markdown
# 최종 정리 — <발표 전체를 관통하는 한 문장>

<왜 이 발표를 사례 단위로 묶었는지 짧은 도입>

## 사례 1 — <문제와 해결 방향이 드러나는 제목>

### 문제 — <업무에서 막힌 지점>

### 만든 개념 — <발표자가 정의하거나 사용한 개념>

### 적용과 아키텍처

<개념을 데이터·시스템·Agent·사용자 흐름에 어떻게 배치했는지>

### 결과

<확인된 구현·운영 결과와 공개되지 않은 한계>

## 사례 2 — <필요한 만큼 반복>

...

## 두 사례에서 가져갈 경험

1. **<일반화한 원칙>.** <적용 의미와 조건>
2. ...
```

발표에서 사례가 하나뿐이면 제목을 `이 사례에서 가져갈 경험`으로 쓴다. 사례 수를 미리 정하지
않는다.

### 최종 정리의 판정 기준

- `문제`는 기술 기능 부족이 아니라 실제 업무에서 어떤 판단·전달·검증이 막혔는지 설명한다.
- `만든 개념`은 제품 기능 목록이 아니라 문제를 풀기 위해 발표가 세운 기준이나 구조다.
- `적용과 아키텍처`는 구성요소 나열보다 데이터와 책임이 이동하는 흐름을 보여준다.
- `결과`는 구현됨, 공개됨, 사용됨, 측정됨을 구분한다. 발표자가 효과를 말했지만 측정 조건이
  없으면 그 한계를 함께 쓴다.
- `가져갈 경험`은 다른 조직에도 옮길 수 있는 원칙으로 일반화하되 적용 조건과 제약을 지우지
  않는다.
