# Areas

**지속되는 것이 사는 자리다.** 프로젝트는 시작하고 끝나지만 영역은 남는다.

`projects/` 가 「무엇을 했나」라면 여기는 「나는 어떤 사람이고 무엇을 알고 있나」다.
그래서 이 레포에서 축이 되는 층이다 — 프로젝트는 영역을 두껍게 만들려고 하는 것이다.

## 하위

| 디렉토리 | 역할 |
|---|---|
| `personal/` | **내가 어떤 사람인가** — 정체성, 하는 일, 지향 |
| `concept/` | **어떤 개념들을 가지고 왔나** — 내가 정리한 지식 |

## 경계

- **`resources/` 와의 경계는 「누가 썼나」다.** 내 머리에서 나온 정리는 여기, 밖에서
  들어온 자료(영상·글·문서)는 `resources/`.
- **`projects/` 와의 경계는 「다른 데서도 쓰나」다.** 그 프로젝트에서만 의미 있는 판단은
  프로젝트가 갖고, 어디서나 다시 쓰이는 것은 여기로 올린다.
- 소속(회사·여름별컴퍼니)은 영역이 아니다. `projects/` 의 필드다.

## 개념과 영역은 같은 축이다

영역은 굵은 개념이고 개념은 잔 개념이다. 별도 층으로 나누지 않는다.
개념이 두꺼워지면 하위 영역으로 갈라진다.

한 개념이 두 영역에 걸리면 **주 영역 하나에 두고 다른 쪽에서 링크한다.** 사본을 만들지 않는다.

## `personal/` 의 하위

| 디렉토리 | 담는 것 |
|---|---|
| `company/` | 회사에서의 나 — 조직·팀·내 역할과 그 변천 |
| `summer-star/` | 여름별컴퍼니에서의 나 — 사업체 운영·방향 |

**이력서·포트폴리오는 여기 두지 않는다.** 그건 원천이 아니라 `company/`·`summer-star/`·
`concept/`·`projects/` 에서 뽑아낸 **발행물**이다. 발행물을 `para/` 안에 둘지 DB 로 뺄지는
아직 안 정했다 — 정해질 때 그 자리로 간다.

## `concept/` 의 영역

| 영역 | 담는 것 |
|---|---|
| `cs/` | 스택 무관한 기초 — 자료구조·알고리즘·네트워크·OS, 그리고 **소프트웨어 설계**(응집·결합·계층·디자인 패턴) |
| `back/` | 서버 — 언어·런타임·프레임워크·API, 그리고 **코드가 DB 를 다루는 것**(ORM·커넥션풀) |
| `db/` | **데이터베이스 자체** — 쿼리·트랜잭션·MVCC·락·인덱스·실행계획·정규화·복제 |
| `front/` | 화면 — 브라우저·UI 구현·클라이언트 |
| `ai/` | 모델·에이전트·프롬프트·평가 |
| `infra/` | 배포·운영 — 컨테이너·오케스트레이션·CI/CD·모니터링 |
| `design/` | **UI/UX 디자인** — 화면 설계·인터랙션·디자인 시스템·접근성 |
| `pm/` | 제품·기획 — 요구 정의·우선순위·지표 |
| `qa/` | 품질 — 테스트 전략·검증·회귀 |

`design/` 과 `front/` 가 헷갈릴 때: **무엇을 어떻게 보이게 할지**는 `design/`,
**그걸 코드로 어떻게 만드나**는 `front/`.

**⚠ 「디자인 패턴」은 `design/` 이 아니라 `cs/` 다.** 싱글턴·팩토리·옵저버 같은 GoF 패턴은
소프트웨어 설계지 UI/UX 가 아니다. 이름이 겹쳐서 매번 걸리는 자리라 여기 박아 둔다.

### `cs/` ↔ `back/` — 원리냐 구현이냐

물량이 제일 많이 갈리는 경계다. **언어를 바꿔도 그대로면 `cs/`, 스택 이름이 붙으면 `back/`.**

| 개념 | 어디 | 왜 |
|---|---|---|
| 싱글턴 패턴 | `cs/` | 설계 원리 |
| Bean scope singleton | `back/` | Spring 이 그걸 어떻게 구현하나 |
| 프로세스·스레드 | `cs/` | OS |
| JVM 메모리 구조 · GC | `back/` | 특정 런타임 |
| 트랜잭션 격리수준 · MVCC · 락 | `db/` | DB 안에서 일어나는 일 |
| `@Transactional` 전파 옵션 | `back/` | 코드가 그걸 부르는 방식 |
| B-tree 인덱스 · 실행계획 | `db/` | 엔진이 어떻게 도나 |
| JPA N+1 · 커넥션풀 | `back/` | ORM 이 만드는 문제 |

`db/` 와 `back/` 의 기준: **DB 를 안 바꾸고 프레임워크만 바꿔도 그대로면 `db/`.**
MVCC 는 JPA 를 안 써도 그대로고, N+1 은 ORM 이 없으면 생기지 않는다.

## 아직 정하지 않은 것

- `personal/` 이 갖는 문서의 종류
- 영역 안에서 더 쪼갤지 (예: `back/` 이 두꺼워지면 언어·프레임워크로)
