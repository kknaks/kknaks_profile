# 모니터링과 관측 (Monitoring · Observability)

**돌아가는 것을 밖에서 볼 수 있게 만드는 일.** 배포로 끝나지 않고, **지금 어떤 상태인가**를 계속 답할 수 있어야 운영이 된다.

## 정의

```
[수집]  각 대상이 메트릭을 내놓는다 (exporter · SDK)
   ↓
[저장]  시계열로 쌓는다 (Prometheus)
   ↓
[시각화] 대시보드로 본다 (Grafana)
   ↓
[알림]  임계값을 넘으면 사람을 부른다
```

무엇을 볼지는 **층으로 나뉜다** — 시스템 자원, 애플리케이션, 그리고 그 위의 도메인 → [[metric-type]]

### 쓰는 방향 네 가지

필기가 「메트릭의 역할과 활용」에 적어 둔 것이 그대로 목적의 분류다.

| 목적 | 하는 일 |
|---|---|
| **성능 모니터링** | 응답시간·처리량·에러율로 서비스 품질을 잰다 |
| **장애 감지** | 임계값 알림으로 먼저 안다 |
| **용량 계획** | 사용 패턴으로 **언제 늘릴지** 정한다 |
| **비즈니스 인사이트** | 사용자 행동·서비스별 비교 |

**앞의 둘은 지금을 보고, 뒤의 둘은 다음을 정한다.**

### 층이 바뀌어도 모양은 같다

LLM 에이전트를 보는 것도 같은 구조다 — 대상만 바뀐다.

| 서버 모니터링 | 에이전트 관측 |
|---|---|
| 요청/응답 | **입력·출력 · 시스템 프롬프트 · 모델에 실제로 보낸 메시지** |
| 응답시간·에러율 | 단계별 소요·실패 지점 |
| 자원 비용 | **호출 비용** |
| 호출 흐름 추적 | 워크플로우 타임라인 |

**「무엇이 오갔는지 나중에 볼 수 있는가」**가 공통점이다. 비결정적으로 움직이는 [[ai-agent]] 에서는 이것이 선택이 아니라 전제에 가깝다 — 같은 입력이 같은 출력을 보장하지 않으므로 **기록이 없으면 재현도 없다** → [[workflow-orchestration]]

## 왜 중요한가

**모르는 것은 고칠 수 없다.** 「느리다」는 신고가 들어와도 어디가 느린지 재고 있지 않으면 **추측으로 고치게 된다** → [[performance-testing]]

**그리고 언제 늘릴지를 감이 아니라 추세로 정하게 한다.** 자원을 미리 키우면 비용이고 늦으면 장애다 — 그 사이를 정하는 것이 축적된 수치다 → [[kubernetes-workload]] · [[universal-scalability-law]]

## 경계와 오해

- **필기의 「Pull 방식의 장점」 항목은 pull 의 장점이 아니다** — 아래에 적힌 세 줄(실시간 수집 · 중앙 집중식 관리 · Grafana 시각화)은 **메트릭 수집 일반의 장점**이지, 밀어 넣는(push) 방식과 갈리는 지점이 아니다. **pull 이 실제로 다른 점**은 수집 서버가 대상 목록을 쥐고 있다는 것(대상이 살아 있는지 자체가 신호가 된다)과, 대상 쪽에 전송 설정이 필요 없다는 것이다
- **그래서 짧게 살고 죽는 작업은 pull 로 못 잡는다** — 배치 잡은 긁으러 갔을 때 이미 없다. 이런 것은 **중간에 밀어 두는 곳**(push gateway)이 따로 필요하다 → [[data-pipeline]]
- **재는 것과 보는 것은 다르다** — 메트릭만 쌓아 두고 대시보드도 알림도 없으면 **장애 후 사후 확인용**에 그친다
- **알림이 많으면 아무도 안 본다** — 임계값을 촘촘히 걸수록 거짓 알림이 늘고, 그러면 진짜 알림도 무시된다. **깨울 만한 것만 깨우는 것**이 설계다
- **메트릭은 원인을 모른다** — 「무엇이 언제」까지가 메트릭이고, 「왜」는 로그와 추적이 답한다. 셋을 합쳐 부르는 말이 관측(observability)이다
- **관측 자체가 비용이다** — 수집 주기가 짧고 레이블이 많을수록 저장·질의 비용이 커진다. LLM 관측은 여기에 **프롬프트 전문을 남기는가**라는 문제가 하나 더 붙는다 → [[metric-type]]

## 출처

- [[2025-07-21-Prometheus]] — 메트릭을 **「타입 → 인프라 → 애플리케이션 → 활용」** 순으로 세워 둔 필기다. 활용을 **성능·장애·용량·비즈니스** 넷으로 가른 것이 이 노트의 뼈대가 됐다. 다만 마지막 「주요 포인트」의 **「Pull 방식의 장점」 표제 아래에 pull 과 무관한 세 줄**이 붙어 있어, 그때 pull/push 의 구별까지는 가지 않았음이 드러난다
- [[C-026-voltagent-demo-first-agent-workflow]] — VoltOps 관측 플랫폼 부분. 「에이전트별 **입력·출력·시스템 프롬프트·LLM 전송 메시지**를 실시간으로 확인」과 「과거 실행 기록에서 입력·출력·**비용**을 조회」가, 서버에서 하던 일이 **LLM 층에 그대로 옮겨 온** 모습을 보인다. 프로덕션 모드의 라이브 트레이스도 같은 계열이다. 다만 **프레임워크 벤더의 공식 데모**라 장점 위주로 기술돼 있다
