# 무중단 배포 (포트 전환 방식)

**새 버전을 옆에 띄워 두고, 준비가 끝나면 들어오는 트래픽만 그쪽으로 돌린다.** 끄고 켜는 사이의 빈 시간이 없다.

## 정의

같은 애플리케이션을 **두 자리**에 번갈아 띄운다.

```
                    ┌── blog_1 : 8082  (현재)
클라이언트 ─▶ 8081 ─┤
              socat └── blog_2 : 8083  (새 버전)
```

- **8081** — 밖에서 보는 고정 포트. `socat` 이 여기서 받아 안쪽으로 넘긴다
- **8082 / 8083** — 실제 컨테이너가 도는 자리. 번갈아 쓴다

배포가 여섯 걸음이다.

```python
def update_service(self) -> None:
    self._find_current_service()      # 1. 지금 도는 것은 어느 쪽인가
    self._find_next_service()         # 2. 그럼 반대쪽에 띄운다
    self._remove_container(...)       # 3. 그 자리를 비우고
    self._run_container(...)          # 4. 새 버전을 띄운다
    #  5. 상태 확인 → 6. 포트 전환 → 이전 것 제거
```

포트 전환은 **프록시를 죽였다 다시 띄우는 것**이다.

```python
# 기존 socat 프로세스를 찾아 종료
ps aux | grep 'socat -t0 TCP-LISTEN:8081' | grep -v grep | awk '{print $2}'
kill -9 ...

# 새 대상으로 다시 연결
socat -t0 TCP-LISTEN:8081,fork,reuseaddr TCP:localhost:8083 &
```

`socat` 은 **TCP 연결을 그대로 전달하는 도구**다 — 8081 로 들어온 것을 안쪽 포트로 흘려보낸다 → [[socket]] · [[port-number]]

## 왜 중요한가

**「배포 중입니다」 화면이 없어진다.** 컨테이너를 멈추고 새로 띄우면 그 사이 요청이 전부 실패하는데, **두 자리를 번갈아 쓰면 언제나 하나는 살아 있다.**

**그리고 상태 확인이 전환의 조건이 된다.** 새 컨테이너가 뜨자마자 넘기면 아직 준비 안 된 곳으로 트래픽이 간다 — 그래서 **띄우기와 넘기기 사이에 확인 단계**가 있다 → [[ci-cd]]

**되돌리기도 쉬워진다.** 이전 버전이 아직 다른 포트에 살아 있으므로, 문제가 보이면 **프록시만 되돌리면** 된다.

## 경계와 오해

- **`kill -9` 로 프록시를 끊으면 그 순간의 연결은 끊긴다** — 진행 중이던 요청은 살려 주지 않는다. **엄밀히는 「짧은 중단」**이고, 완전한 무중단은 새 연결만 새 쪽으로 보내고 기존 것은 끝날 때까지 두는 방식이 필요하다
- **두 버전이 같은 DB 를 본다** — 새 버전이 스키마를 바꾸면 **잠시 두 버전이 동시에 도는 그 시간**에 옛 버전이 깨진다. 그래서 스키마 변경은 **양쪽이 다 견디는 모양**으로 나눠 배포한다 → [[db-normalization]] · [[transaction]]
- **포트가 둘이면 자원도 둘이다** — 전환하는 동안 컨테이너 둘이 함께 떠 있으므로 **메모리·커넥션이 잠시 두 배**다 → [[connection-pool-sizing-formula]]
- **상태 확인이 「떴다」로 끝나면 안 된다** — 프로세스가 살아 있는 것과 요청을 처리할 준비가 된 것은 다르다. **실제로 한 번 호출해 보는 것**까지가 확인이다
- **프록시가 단일 실패 지점이다** — `socat` 프로세스가 죽으면 두 컨테이너가 멀쩡해도 서비스가 멈춘다. 앞단에 리버스 프록시가 따로 있는 구성이 더 흔한 이유다 → [[reverse-proxy]]
- **이 방식은 한 대 안에서의 블루그린이다** — 서버가 여러 대면 로드밸런서 쪽에서 같은 일을 한다. **개념은 같고 도구가 다르다** → [[distributed-processing]]

- [[2025-01-15-Day12]] — 이틀 뒤. **손으로 쓴 스크립트가 기능으로 들어와 있다.** 쿠버네티스 Deployment 의 `strategy: RollingUpdate` 와 `maxSurge`·`maxUnavailable` 두 값이 「한 번에 몇 개씩 갈아 끼울지」를 정하고, 새 ReplicaSet 을 만들어 파드를 하나씩 교체한 뒤 **이전 ReplicaSet 을 남겨 롤백까지 준비**한다. 포트 두 개를 번갈아 쓰던 방식이 **복제본 N 개를 굴려 가며 바꾸는 방식**으로 일반화된 자리다 → [[kubernetes-workload]]
- [[2025-01-13-Day10]] — 「무중단 배포 스크립트 작성」 절이 **파이썬 스크립트로 절차 전체를 구현**했다. `ServiceManager` 가 `socat_port: 8081`, `services: {blog_1: 8082, blog_2: 8083}` 를 들고, `update_service()` 가 **현재 확인 → 다음 선정 → 컨테이너 교체 → 상태 확인 → 포트 전환 → 이전 제거** 여섯 걸음으로 돈다. 전환 코드가 특히 구체적이다 — `ps aux | grep socat` 으로 기존 프로세스를 찾아 `kill -9` 하고 5초 기다린 뒤 `nohup socat -t0 TCP-LISTEN:8081,fork,reuseaddr TCP:localhost:8083 &` 로 다시 띄운다. **socat 을 「로컬에서 원격 서버로 TCP 연결을 전달하는 도구」**로 정의해 둔 것도 이 방식의 원리를 짚는다. 다만 전환 순간 진행 중이던 연결이 끊긴다는 것, 두 버전이 같은 DB 를 공유할 때의 문제는 다루지 않았다
