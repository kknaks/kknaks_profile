# 분산 락 (Distributed Lock)

여러 프로세스나 서버가 공유 자원에 동시에 들어가지 못하도록 외부의 공통 저장소에서 처리 권한을 조정하는 락이다. 한 프로세스 안에서만 보이는 언어 수준의 락과 달리, 모든 참여자가 같은 락 저장소와 규약을 사용해야 한다.

## 정의

분산 락은 자원을 식별하는 락 키, 락 소유자를 구분하는 고유 토큰, 락의 만료 시간으로 구성된다.

1. 작업을 시작하려는 서버가 공유 저장소에서 락 키를 원자적으로 선점한다.
2. 선점에 성공한 서버만 보호 대상 작업을 실행한다.
3. 작업을 마친 뒤 결과를 먼저 확정하고 락을 해제한다.
4. 선점에 실패한 서버는 즉시 실패하거나, 제한된 시간 동안 기다린 뒤 결과 또는 락 상태를 다시 확인한다.

Redis에서는 흔히 만료 시간을 포함한 `SET key token NX PX ttl` 명령으로 선점한다. 해제할 때는 키의 현재 값이 자신이 발급한 토큰과 같은 경우에만 삭제해야 한다. 값 확인과 삭제도 Lua 스크립트처럼 하나의 원자적 연산으로 수행한다.

## 사용 예시

```redis
SET lock:payment:ORDER-42 7d52f7c0 NX PX 30000
```

```lua
-- KEYS[1]: 락 키, ARGV[1]: 소유자 토큰
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
return 0
```

결제 API의 여러 서버가 같은 멱등성 키를 동시에 받았을 때 키별 락을 획득한 서버만 결제를 수행하고 응답을 저장한다. 나머지 서버는 처리 완료 기록을 조회해 같은 응답을 반환한다 → [[idempotency]]

## 왜 중요한가

로드 밸런서 뒤의 서버 A와 서버 B는 각자의 메모리와 프로세스 락을 공유하지 않는다. 첫 요청과 재시도가 서로 다른 서버에 도착하거나 같은 요청 두 개가 동시에 배분되면, 로컬 락만으로는 둘 다 비즈니스 로직을 실행하는 것을 막지 못한다.

공유 저장소의 원자적 선점 연산을 사용하면 어느 서버로 요청이 가더라도 하나만 임계 구역에 들어가게 할 수 있다. 결제·주문 생성, 스케줄러의 단일 실행, 공유 파일 갱신처럼 동시 실행 비용이 큰 작업에서 사용된다.

## 경계와 오해

- **분산 락 ≠ 데이터 무결성의 최종 방어선** — 락 저장소 장애, TTL 만료, 구현 오류가 있을 수 있다. 핵심 데이터에는 [[unique-key]]나 트랜잭션 같은 저장소 수준의 불변 조건도 둔다.
- **락 획득 ≠ 정확히 한 번 실행** — 작업은 성공했지만 결과 기록 전에 프로세스가 죽을 수 있다. 상태 조회, 멱등 처리, 복구 가능한 상태 머신이 함께 필요하다.
- **TTL이 없으면 죽은 소유자가 락을 영구 점유한다** — 반대로 TTL이 작업 시간보다 짧으면 이전 소유자가 아직 실행 중인데 새 소유자가 들어올 수 있다. 작업 시간의 상한, 갱신 규칙과 실패 정책을 함께 정한다.
- **토큰 없이 삭제하면 다른 소유자의 락을 지울 수 있다** — 자신의 락이 만료된 뒤 다른 서버가 같은 키를 획득했을 수 있으므로 소유자 검증과 삭제를 원자적으로 수행한다.
- **결과 저장 전에 락을 풀면 임계 구역이 열린다** — 다른 서버가 완료 기록을 보기 전에 같은 작업을 시작할 수 있다.
- **모든 동시성 문제에 분산 락이 필요한 것은 아니다** — 데이터베이스의 조건부 갱신, 유일 제약, 낙관적 락처럼 더 단순하고 강한 저장소 연산으로 해결할 수 있으면 그것을 우선한다.
