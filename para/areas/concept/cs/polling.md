# 폴링 (Polling)

**클라이언트가 「새 것 있나요」를 주기적으로 물어보는 방식.** HTTP 가 **요청이 있어야 응답한다**는 제약을 가진 채로 실시간처럼 보이게 만드는 가장 단순한 답이다.

## 정의

```
클라이언트 ──요청──▶ 서버      (3초마다)
          ◀─응답──         새 것 없음
클라이언트 ──요청──▶ 서버
          ◀─응답──         새 메시지 2건
```

**간격이 곧 지연이자 부하**다.

- 간격을 **짧게** 하면 → 실시간에 가까워지지만 **서버 부하가 커진다**
- 간격을 **길게** 하면 → 부하는 줄지만 **늦게 안다**

중간을 취한 것이 **롱폴링**이다 — 요청을 보내면 서버가 **새 것이 생길 때까지 응답을 붙들고 있다가** 돌려준다. 빈 응답이 줄고 지연도 짧아지지만, **연결이 오래 열려 있다.**

### 무엇을 물어볼 것인가

전부 다시 받으면 낭비이므로 **「어디까지 봤는지」를 함께 보낸다.**

```
GET /chat/messages                 전체 조회
GET /chat/messages?fromUuid=D      메시지 D 이후로 발생한 것만
GET /chat/messages?fromUuid=F      메시지 F 이후로 발생한 것만
```

**마지막으로 받은 것의 식별자를 커서로 쓰는 것**이고, 페이지 번호로 끊는 방식과 다른 계열이다 → [[pagination]]

## 왜 중요한가

**HTTP 의 성질이 설계를 정하는 자리다.** 서버가 먼저 말을 걸 수 없으므로, 실시간이 필요하면 **누가 언제 물어볼지**를 정해야 한다 — 이 결정 하나가 서버 부하·지연·구현 난이도를 전부 좌우한다 → [[client-server-model]] · [[http-message]]

**그리고 가장 단순하다는 것이 실제 장점이다.** 특별한 프로토콜도, 연결 관리도, 재접속 처리도 없다. **평범한 GET 요청** 이므로 캐시·로드밸런서·프록시가 전부 그대로 동작한다 → [[http-method]]

## 경계와 오해

- **요청 대부분이 헛걸음이다** — 새 메시지가 없어도 요청·응답 한 벌이 오간다. 사용자 1000명이 3초마다 물으면 **초당 300여 건**이 새 것 없이 오가고, 그 대부분이 HTTP 헤더 비용이다
- **간격을 줄이는 것이 실시간의 답이 아니다** — 부하는 간격에 반비례해 커지는데 체감 지연은 그만큼 좋아지지 않는다. 어느 선을 넘으면 **다른 방식으로 갈아타는 것이 맞다** → [[server-sent-events]]
- **커서(`fromUuid`)가 없으면 매번 전체를 받는다** — 「이후로 발생한 것만」이 폴링을 쓸 만하게 만드는 조건이다. 그 커서가 **정렬 가능한 값**이어야 「이후」가 정의된다 → [[primary-key]] · [[date-time]]
- **롱폴링은 연결을 붙든다** — 대기 중인 요청 하나가 서버의 처리 자원을 점유하므로, 동시 사용자만큼 **열린 요청**이 쌓인다. 쓰레드당 요청 모델에서는 이것이 바로 한계가 된다 → [[thread]] · [[little-law]]
- **폴링은 「실시간」이 아니다** — 최선의 경우에도 **평균 간격의 절반만큼 늦다.** 채팅처럼 몇 초를 견딜 수 있는 곳에서만 성립한다

## 출처

- [[2024-12-30-Day01]] — 「HTTP를 활용한 통신방식」이 **「HTTP 는 클라이언트의 요청이 있을 때만 응답을 하기 때문에 실시간 통신을 구현하기 어렵다」**로 문제를 세우고, 그 우회로 폴링·롱폴링·SSE 셋을 나열한다. 「폴링 방식」 절이 **간격을 짧게 하면 서버에 부하가 걸린다**는 절충을 명시했다. 이어지는 「폴링방식을 활용한 채팅기능 구현」이 실제 설계를 보인다 — 조회는 `/chat/messages?fromUuid=D` 처럼 **마지막으로 받은 메시지 이후만** 요청하고, 작성은 엔터마다 서버로 보낸다. **커서로 끊어 받는다는 것**이 이 구현의 요점인데 필기는 그 이름을 붙이지 않았다. 롱폴링은 이름만 나오고(본문 표기는 「롤폴링」) 동작은 설명되지 않았다
