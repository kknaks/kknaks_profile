# 길이 접두사 (Length-Prefix Framing)

**가변 길이 데이터를 바이트 한 줄에 담을 때, 내용 앞에 그 길이를 고정 크기로 먼저 적는 것.** 읽는 쪽은 길이를 먼저 읽고 정확히 그만큼 떼어 내므로 **내용을 들여다보지 않고 경계를 안다.**

## 정의

Day38 은 이것을 「데이터의 구조에 따라 바이트의 할당규칙을 정해야 load과정에서 해당규칙을 통해 값을 읽을 수 있다」 한 줄로 적었다. **규칙이 있어야 읽을 수 있다는 것이 이 기법의 전부**이고, 그 규칙은 필드마다 둘 중 하나다.

| 필드 | 규칙 | 왜 |
|---|---|---|
| `no` | **고정 4바이트** — 접두사 없음 | `int` 는 항상 4바이트라 길이를 말할 필요가 없다 |
| `name`·`email`·`password`·`tel` | **길이 2바이트 + 내용 N바이트** | UTF-8 바이트 수가 값마다 다르다 |
| 레코드 하나 | **길이 2바이트 + 내용 N바이트** | 필드 수와 각 길이에 따라 달라진다 |
| 회원 수 | **고정 2바이트** (맨 앞) | 몇 번 반복할지 읽는 쪽이 알아야 한다 |

**고정 길이에는 접두사가 없고 가변 길이에만 붙는다** — 그것이 이 기법이 답하는 질문의 범위다.

```text
파일 전체:  [회원수 2] [len 2][레코드] [len 2][레코드] ...
레코드 하나: [no 4] [len 2][name] [len 2][email] [len 2][password] [len 2][tel]
```

## 사용 예시

쓰는 쪽은 「길이 → 내용」 두 단계다.

```java
      //이름 넣기
      byte[] bytes = name.getBytes(StandardCharsets.UTF_8);
      out.write(bytes.length >> 8);
      out.write(bytes.length);
      out.write(bytes);
```

읽는 쪽이 정확히 거울이다.

```java
      int len = in.read() << 8 | in.read();
      in.read(buffer, 0, len);
      user.setName(new String(buffer, 0, len, StandardCharsets.UTF_8));
```

**`len` 이 세 곳에 쓰인다** — 몇 바이트를 읽을지, 어디까지를 문자열로 볼지, 그리고 (레코드 층에서는) 배열을 얼마로 만들지. 길이 하나가 뒤의 모든 결정을 정하므로 **이 값이 틀리면 그 뒤가 전부 밀린다** → [[serialization]]

목록 층도 같은 모양이고, 여기서는 길이가 **배열 크기**가 된다.

```java
      int userLength = in.read() << 8 | in.read();
      for (int i = 0; i < userLength; i++) {
        int len = (in.read() << 8) | in.read();
        byte[] bytes = new byte[len];
        in.read(bytes);

        User user = User.valueOf(bytes);
        userList.add(user);
      }
```

**`new byte[len]` 이 이 기법의 실용적인 값을 보여 준다** — 정확한 크기의 그릇을 한 번에 만들 수 있고, 늘려 가며 담거나 끝을 찾아 훑을 필요가 없다 → [[byte-array-stream]]

### 하루 뒤 — 표준이 같은 규칙을 이미 갖고 있었다

Day39 는 이 코드를 지우고 `writeUTF`/`readUTF` 로 바꾼다. **그 메서드가 하는 일이 정확히 「길이 2바이트 + 내용」이다.**

```java
        out.writeUTF(user.getName());     // 안에서: 바이트 길이 2바이트 → UTF-8 바이트
```

```java
        user.setName(in.readUTF());       // 안에서: 길이 2바이트 읽고 → 그만큼 떼어 문자열로
```

**Day38 의 세 줄과 네 줄이 각각 한 줄로 접혔고 형식은 같다.** 손으로 짠 것이 표준이 쓰는 것과 같은 규칙이었다는 것이 여기서 확인되는데, **접두사 크기까지 같은 2바이트**다 → [[data-io-stream]]

바뀐 것은 두 가지다.

| | Day38 (손으로) | Day39 (`DataOutputStream`) |
|---|---|---|
| 회원 수 접두사 | 2바이트 (65535 한계) | `writeInt` — **4바이트** |
| 레코드 길이 접두사 | 있다 (2바이트) | **없다** — 필드 길이만으로 읽는다 |
| 길이를 넘겼을 때 | 상위 비트를 버리고 **조용히** 저장 | `UTFDataFormatException` |

레코드 길이가 사라진 것은 손해가 아니다 — Day38 도 그 값을 실제로 쓰지 않았다(아래 「경계와 오해」의 「길이가 두 층에 중복으로 적혀 있고」). **쓰지 않던 중복이 도구를 바꾸자 자연히 없어진 것**이다.

## 왜 중요한가

**구분자 방식의 이스케이프 문제가 사라진다.** 이름·이메일을 콤마로 갈라 저장하면 이름에 콤마를 쓴 회원 하나가 파일 전체를 부순다. 그래서 구분자 방식은 「내용에 구분자가 있으면 어떻게 적을지」라는 규칙을 반드시 하나 더 만들어야 하고, 그것이 CSV 가 생각보다 복잡한 이유다. 길이 접두사는 **내용을 검사하지 않는다** — 어떤 바이트가 와도, 길이 접두사와 똑같은 바이트가 내용에 있어도 상관없다 → [[binary-io]]

**읽는 일이 탐색에서 계산으로 바뀐다.** 끝 표시를 쓰면 한 바이트씩 읽으며 「이게 그 표시인가」를 물어야 하는데, 길이를 알면 그만큼 건너뛰면 된다. 관심 없는 레코드를 **내용을 읽지 않고 지나칠 수 있다**는 것도 같은 성질에서 온다.

**네트워크 프로토콜의 기본 모양이 이것이다.** TCP 는 바이트 스트림만 주고 「메시지 하나」의 경계를 알려 주지 않으므로, 받는 쪽이 어디까지가 한 메시지인지 아는 방법이 필요하다. 길이 접두사(또는 그 확장인 TLV — 타입·길이·값)가 그 답이고, Day38 이 파일에 손으로 만든 형식이 그것의 축소판이다 → [[io-stream]]

## 경계와 오해

- **길이의 단위는 문자가 아니라 바이트다** — 코드는 `name.getBytes(UTF_8).length` 이고 `name.length()` 가 아니다. 「이건학」은 문자 3개, UTF-8 바이트 9개다. `length()` 를 적었다면 3바이트만 읽어 「이」 하나로 복원되고 **남은 6바이트가 다음 필드의 길이 자리로 밀려 들어가** 그 뒤 전부가 무너진다. **UTF-8 이 가변 길이인 것이 길이 접두사가 필요한 이유이면서 동시에 그 길이를 잘못 셀 수 있는 이유다** → [[character-encoding]]
- **접두사의 크기가 담을 수 있는 최대 길이를 정한다 — 그리고 그 한계가 코드에 숫자로 없다** — 2바이트면 65535 다. 이름·이메일에는 넉넉하지만 **회원 수도 2바이트**이므로 65536명째부터 어긋난다. `write(int)` 가 하위 8비트만 쓰고 나머지를 말없이 버리므로 `userLength >> 8` 과 `userLength` 두 바이트에 65536 이 `0` 으로 남고, **예외 없이 「회원 0명」인 파일이 저장된다.** 한계는 「2바이트」라는 값으로 적혀 있지 않고 `>> 8` 이라는 시프트 횟수에 숨어 있다 → [[bit-shift]] · [[overflow]]
- **길이 접두사 ≠ 구분자** — 둘 다 「어디까지가 한 덩어리인가」에 답하지만 방향이 반대다. 구분자는 **끝을 표시**하므로 쓸 때 길이를 몰라도 되고 읽을 때 찾아야 하며, 내용에 나타나면 안 된다. 접두사는 **크기를 미리 말해** 주므로 읽기가 쉽고 내용에 아무 값이 와도 되지만, **다 만든 뒤에야 알 수 있는 값을 먼저 써야 한다.** 그 모순을 푸는 것이 메모리 버퍼이고, Day38 이 `getBytes()` 를 따로 둔 이유가 거기 있다 → [[byte-array-stream]]
- **길이가 두 층에 중복으로 적혀 있고, 안쪽만으로 충분하다** — 레코드 길이(2바이트)를 읽어 `new byte[len]` 을 만들지만, `valueOf` 는 그 안의 필드 길이들만으로 끝까지 읽는다. 즉 **레코드 길이는 없어도 복원된다.** 그것을 두는 값은 「형식을 모르는 레코드를 내용을 안 읽고 건너뛸 수 있다」인데, 이 코드는 건너뛰지 않으므로 그 값을 쓰지 않는다. **중복이 손해라는 뜻은 아니다** — 앞으로 형식이 늘어날 자리를 만들어 둔 것이고, 다만 그 의도가 코드에 적혀 있지 않다.
- **길이가 거짓이면 읽는 쪽이 무엇이든 한다 — 그리고 그것을 검증하는 코드가 없다** — 파일이 중간에서 잘리면 `in.read()` 가 `-1` 을 주고 `-1 << 8 | -1` 이 **`-1`** 이 된다. `new byte[-1]` 은 `NegativeArraySizeException`, `in.read(buffer, 0, -1)` 은 `IndexOutOfBoundsException` 이며 **둘 다 `IOException` 이 아니라 `catch` 를 통과해 프로그램을 죽인다.** 그리고 값이 음수가 아니라 큰 수로 어긋나면 그 크기의 배열을 할당하려 든다 — **신뢰할 수 없는 입력에서 길이 접두사를 그대로 믿으면 길이 두 바이트로 메모리를 고갈시킬 수 있다.** 「길이를 적으면 경계를 안다」는 참이지만 **「적힌 길이가 맞다」는 별개의 가정**이고, 이 형식에는 그것을 확인할 수단이 없다 → [[exception-handling]] · [[serialization]]
- **개수를 앞에 적는 것과 끝까지 읽는 것은 다른 선택이다** — 회원 수를 맨 앞에 적었으므로 읽는 쪽이 `for` 를 돌 수 있고 「몇 명인지」를 미리 안다. 대가는 **개수를 나중에 고칠 수 없다**는 것이다 — 회원 한 명이 늘 때 파일 끝에 이어 붙이면 맨 앞의 개수가 틀리므로, `saveUser` 는 매번 파일 전체를 다시 쓴다. 개수를 적지 않고 「더 읽을 것이 있으면 계속」으로 만들었다면 이어 붙이기가 가능했다. **형식이 정하는 것은 읽는 방법만이 아니라 갱신하는 방법이다.**
- **접두사 크기의 한계는 표준 도구를 써도 그대로다 — 다만 넘겼을 때가 다르다** — `writeUTF` 도 접두사가 2바이트이므로 **한계가 똑같이 65535바이트**다. 갈리는 것은 넘겼을 때의 행동이다. Day38 의 `out.write(len >> 8)` 은 상위 비트를 말없이 버려 **저장은 되고 못 읽는 파일**을 남기고, `writeUTF` 는 `UTFDataFormatException` 을 던져 저장을 멈춘다. **같은 형식·같은 한계인데 한쪽은 조용하고 한쪽은 알려 준다** — 표준 도구를 쓰는 값의 절반이 여기 있다 → [[data-io-stream]] · [[overflow]]
- **끝을 값으로 알리는 것과 예외로 알리는 것이 형식의 안전성을 바꾼다** — Day38 의 `in.read()` 는 파일 끝에서 `-1` 을 주므로 그것이 **길이 계산에 섞여 들어가** `len = -1` 이 되고 `new byte[-1]` 로 죽었다. `readInt`·`readUTF` 는 **바이트가 부족하면 `EOFException`** 을 던지므로 「거짓 길이」가 만들어지는 경로 자체가 없어진다. 다만 그것이 안전을 뜻하지는 않는다 — 예외가 `IOException` 계열이라 기존 `catch` 에 걸려 **잘린 파일이 조용히 「일부만 읽힌 목록」이 되고, 다음 저장이 그것을 확정한다** → [[data-io-stream]] · [[exception-handling]]
- **길이 접두사를 쓸 수 있는 것은 바이트를 세는 층에서만이다** — 같은 노트의 CSV 절은 문자 스트림을 쓰므로 바이트 개수를 다루지 않고, 그래서 **경계를 구분자로 잡을 수밖에 없다.** 「길이냐 구분자냐」가 취향이 아니라 **어느 층에서 형식을 만드는지에 따라 결정되는** 자리다 → [[csv]] · [[character-stream]]
- **`no` 가 접두사 없이 4바이트인 것은 「고정」이지 「최적」이 아니다** — 이 실습의 회원 번호는 늘 한 자리인데 4바이트를 쓴다. 가변 길이 정수 인코딩(작은 수는 1바이트)을 쓰면 줄지만, 그러면 정수 필드에도 길이 정보가 필요해진다. **고정 길이는 「길이를 적는 비용」과 「쓰지 않는 자리의 비용」을 교환한 것**이고, 값의 분포를 알아야 어느 쪽이 나은지 정할 수 있다 → [[binary-io]]
