# 인터프리터 방식 (Interpreter)

소스를 한 줄씩 기계어로 변환해 그때그때 실행하는 방식. 미리 실행파일을 만들어 두지 않는다. Python·JavaScript 가 이 방식이다.

## 정의

[[compilation]] 과 실행 시점이 갈린다.

| | 컴파일 방식 | 인터프리터 방식 |
|---|---|---|
| 변환 시점 | 실행 전에 전부 | 실행하면서 한 줄씩 |
| 산출물 | 실행파일 | 없음 — 실행할 때마다 소스가 필요 |
| 오류를 아는 시점 | 변환할 때 (실행파일이 안 생긴다) | **그 줄에 도달할 때** |
| 대표 언어 | C, C++ | Python, JavaScript |

한 줄씩 처리하므로 **오류가 있는 줄 앞까지는 정상적으로 실행된다.** 그 지점에 닿기 전에는 오류가 있는지 알 수 없다.

## 왜 중요한가

이 방식의 성질 셋이 그대로 대가로 돌아온다.

- **오류를 사전에 알 수 없다** — 실행해 봐야 알고, 실행 경로가 닿지 않는 줄의 오류는 끝까지 드러나지 않는다. 테스트를 더 촘촘히 써야 하는 이유가 여기서 나온다.
- **소스를 공개해야 한다** — 실행할 때마다 소스가 필요하니 배포에 소스가 따라간다.
- **실행이 느리다** — 실행 중에 문법 검사와 변환을 계속 하기 때문이다.

이 세 가지를 컴파일 방식의 단점(환경별로 따로 컴파일해야 한다)과 맞바꾼 것이 [[bytecode]] 를 쓰는 하이브리드 방식이다.

## 경계와 오해

- **인터프리터 ≠ 변환을 안 한다** — 기계어로 바꾸는 일은 똑같이 한다. 다른 것은 **언제** 하는가다.
- **느리다는 것이 언어의 한계는 아니다** — 지금은 실행 중에 자주 쓰이는 부분만 미리 컴파일해 두는 방식(JIT)으로 상당히 메운다. 옛 필기의 "실행 속도가 느리다"는 순수 인터프리터를 전제한 비교다.
