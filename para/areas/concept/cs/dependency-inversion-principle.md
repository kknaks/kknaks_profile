# 의존 역전 원칙 (DIP)

**고수준 모듈이 저수준 모듈을 직접 알지 않고, 둘이 같은 추상에 기대게 만드는 것.** 필기의 두 줄이 정의 전부다 — 「고수준 모듈은 저수준 모듈에 의존해서는 안 된다. 둘 다 추상화에 의존해야 한다 / 구체적인 구현이 아니라 추상화된 인터페이스나 상위 클래스에 의존해야 한다」.

## 정의

「역전」이 무엇의 역전인지가 이 원칙에서 가장 자주 흐려지는 자리다. **화살표의 방향이 뒤집힌다.**

```text
적용 전:  Switch ──────────────▶ FluoLamp        (고수준이 저수준을 가리킨다)

적용 후:  Switch ──▶ Switchable ◀────── FluoLamp  (저수준이 위를 가리킨다)
```

적용 전에 `Switch` 는 `FluoLamp` 를 향한다. 적용 후에도 `Switch` 는 여전히 무언가를 향하지만 **그 무언가를 `Switch` 쪽이 소유한다** — 인터페이스는 「스위치가 필요한 것」의 목록이고, 램프가 그것에 맞추러 온다. 뒤집힌 것은 **누가 누구에게 맞추는가**다.

그래서 두 개가 같이 성립해야 한다.

| 조건 | 없으면 |
|---|---|
| 고수준이 **추상 타입으로 받는다** | 구현 클래스 이름이 고수준 코드에 남는다 |
| 고수준이 **그 구현을 만들지 않는다** | `new` 한 줄에 구현 클래스 이름이 다시 들어온다 |

두 번째가 필기의 마지막 두 줄이다 — 「인터페이스를 직접적으로 생성하지 않는다( = 의존객체를 만들지 않는다.) / 외부에서 객체를 생성해서 대입을 받는다」 → [[dependency-injection]]

## 사용 예시

램프/스위치 예제가 다섯 단계를 지나는데, **1단계와 4단계가 둘 다 DIP 위반이고 위반의 종류가 다르다.**

1단계 — 「기존 Switch클래스는 FluoLamp클래스만 객체로 사용 가능하다 / 고수준 모듈이 저수준 모듈에 의존적이다」. 타입이 구체 클래스다.

4단계 — 인터페이스로 받는 데까지 갔는데 「새로운 제품군이 들어오면 Switch클래스 내부에서 코드 수정이 필요하다 / Dependency Inversion Principle을 충족시키지 못한다」. **타입은 추상인데 생성이 안쪽에 남아 있다.**

5단계가 그 `new` 를 밖으로 뺀다. 즉 **DIP 는 「인터페이스를 쓰자」가 아니라 두 걸음이고, 4단계는 첫 걸음만 밟은 상태다.**

실습 프로젝트 쪽에서는 같은 이동이 `App` 에 일어난다. 하루 앞 회차의 `App` 은 이랬다.

```java
UserCommand userCommand = new UserCommand("회원");
ProjectCommand projectCommand = new ProjectCommand("프로젝트", userCommand.getUserList());

void processMenu(String menuTitle) {
  switch (menuTitle) {
    case "회원": userCommand.execute(); break;
    case "프로젝트": projectCommand.execute(); break;
    ...
  }
}
```

**`App` 이 구현 클래스 넷의 이름을 타입으로 들고 있고, 메뉴 이름도 코드에 박혀 있다.** 이 회차가 그것을 이렇게 바꾼다.

```java
Map<String, Command> commandMap = new HashMap<>();

void processMenu(String menuTitle) {
  Command command = commandMap.get(menuTitle);
  if (command == null) {
    System.out.printf("%s 메뉴의 명령을 처리할 수 없습니다.\n", menuTitle);
    return;
  }
  command.execute();
}
```

**`processMenu` 에서 구현 클래스 이름이 전부 사라졌다.** 남은 것은 `Command` 라는 약속 하나이고, 그래서 명령이 하나 늘어도 이 메서드는 그대로다 → [[interface]] · [[polymorphism]] · [[dispatch-table]]

다만 `new UserCommand(...)` 는 `App` 의 생성자로 옮겨졌을 뿐 사라지지 않았다 — 램프 예제의 4단계에 해당하는 상태다(아래).

## 왜 중요한가

**고수준 코드가 저수준의 교체를 견딘다.** 필기의 예가 「데이터베이스 접근 로직을 직접 클래스에 구현하는 대신, 인터페이스를 통해 접근하여 다른 데이터베이스로 쉽게 교체할 수 있도록 한다」다. 교체할 계획이 없어도 값이 있다 — **저수준이 바뀔 때 고수준을 다시 읽고 이해해야 하는 일이 없어진다.**

**그리고 「무엇이 중요한 코드인가」가 방향으로 드러난다.** 적용 전에는 램프가 바뀌면 스위치가 따라 바뀌므로 램프가 상전이다. 적용 후에는 스위치가 필요한 것을 램프가 맞추므로, **정책이 세부에 명령하는 방향**이 된다. 이 회차가 「고수준/저수준」이라는 낱말을 처음 쓴 것이 그 축을 세운다.

**테스트가 가능해지는 것도 같은 성질이다.** `Switch` 가 안에서 `new FluoLamp()` 를 하면 스위치만 떼어 시험할 방법이 없다. 밖에서 대입받으면 아무것도 아닌 가짜 램프를 넣어 볼 수 있다 — 이 실습에는 테스트가 없지만, **DIP 를 지킨 코드와 지키지 않은 코드의 차이가 가장 먼저 드러나는 자리가 그쪽**이다.

## 경계와 오해

- **DIP ≠ 의존성 주입(DI)** — 필기가 실습 절 첫 줄을 「DIP를 적용하여 외부에서 값을 대입하면 의존성을 탈피 할 수 있다」로 적어 둘을 한 문장에 뭉갰다. DIP 는 **어떤 타입에 기대는가**(추상 대 구체)이고 DI 는 **그 인스턴스를 누가 넣어 주는가**(자기 대 외부)다. 갈리는 것은 두 조합이 다 존재한다는 데서 드러난다 — 구체 타입을 생성자로 받으면 DI 는 하고 DIP 는 안 한 것이고, 인터페이스 타입 필드를 안에서 `new` 하면 DIP 만 반쪽으로 한 것이다 → [[dependency-injection]]
- **의존이 사라지는 것이 아니라 옮겨 간다** — 「의존성을 탈피」라는 말이 의존이 없어지는 것으로 읽히는데, `Switch` 는 여전히 인터페이스에 의존하고 **누군가는 구현 클래스를 알아야 한다.** 이 실습에서 그 누군가는 `App` 의 생성자다. DIP 가 하는 일은 의존을 없애는 것이 아니라 **구체 클래스를 아는 자리를 한 곳으로 모으는 것**이고, 그 자리는 프레임워크에서 설정 파일이나 컨테이너가 된다 → [[coupling]]
- **인터페이스를 만든 것만으로는 역전되지 않는다** — 램프 예제 4단계가 그 상태다. `Switch` 가 인터페이스로 받으면서도 그 안에서 구현체를 만들면, **컴파일 의존은 그대로 남아** 새 제품군마다 `Switch` 를 고친다. 하루 앞 회차가 `Command` 와 `List` 인터페이스를 만들고도 어느 것도 타입으로 쓰지 않은 것은 그보다 한 걸음 더 앞이다 → [[interface]]
- **이 회차의 `App` 도 4단계에서 멈춘다** — `processMenu` 에서는 구현 클래스가 사라졌지만 `App` 의 생성자에는 `new UserCommand("회원")` 이 그대로 있다. 그래서 명령을 하나 더하려면 **여전히 `App` 을 고쳐야 하고**, 필기가 램프 예제에서 「Switch클래스 내부에서 코드 수정이 필요하다」로 지목했던 바로 그 상태다. **한 절에서 문제로 적은 것을 다음 절 실습에서 그대로 남긴 것**이고, 5단계까지 가려면 명령 목록을 `App` 밖에서 만들어 넘겨야 한다 → [[open-closed-principle]]
- **「고수준/저수준」은 호출 방향이 아니다** — 스위치가 램프를 부르므로 부르는 쪽이 고수준으로 보이는데, 기준은 **정책에 가까운가 세부에 가까운가**다. 그래서 저수준이 고수준을 부르는 구조에서도 DIP 는 성립한다 — 하루 앞 회차의 `AbstractCommand.execute()` 가 자식의 `processMenu()` 를 부르는 형태가 그것이고, 거기서도 부모(정책)는 자식 클래스 이름을 모른다 → [[template-method-pattern]]
- **상위 클래스도 추상화의 자리가 된다** — 필기가 「추상화된 인터페이스나 상위 클래스」로 둘을 나란히 적었고, 램프 예제 2단계가 실제로 상속으로 한다(「Lamp의 공통적 속성을 활용하여 부모클래스를 생성한다」). 다만 `extends` 는 하나뿐이라 나중에 다른 축의 추상이 필요해지면 막히고, 그래서 4단계에서 인터페이스로 갈아탄다 → [[abstract-class]] · [[multiple-inheritance]]
- **DIP 를 지켜도 `null` 이 새 실패 경로로 들어온다** — `switch` 의 `default:` 가 사라진 대신 `commandMap.get()` 이 `null` 을 돌려줄 수 있고, 그것을 검사하는 책임이 `processMenu` 로 왔다. 원본이 그 검사를 넣어 두었지만, **분기를 데이터로 바꾸면 「없는 키」가 컴파일 시점에서 실행 시점으로 내려온다** — `case "회원":` 의 오타는 그 자리에서 눈에 띄고 `put("회웜", ...)` 의 오타는 눌러 봐야 안다 → [[dispatch-table]] · [[switch-statement]]
