# 실행 중 프로세스 메모리에서 비밀 회수

**오프라인으로 재현할 수 없는 비밀(키·토큰)을, 그 비밀을 이미 계산해 들고 도는 프로세스의 메모리를 읽어 그대로 꺼내 오는 것.** 파생식을 못 뚫을 때 「어차피 저쪽은 평문으로 갖고 있다」를 이용하는 우회다.

## 정의

암호화 키가 **런타임에 파생**되는 경우가 있다 — 하드웨어 식별자·OS 보관소(Windows DPAPI, macOS keychain)·사용자 비밀을 엮어 실행 중에 만든다. 이걸 밖에서 똑같이 재현하려면(오프라인 파생) 파생식을 알아야 하는데, 종종 막힌다:

- **anti-debug** — 디버거를 붙이면 자폭하거나 다른 경로로 샌다.
- **OS 보관소 종속** — DPAPI 복호는 그 사용자·그 기기 컨텍스트를 요구한다.
- **난독화·패킹** — 정적 분석으로 파생식을 못 읽는다.

**그러나 프로세스가 살아 있는 동안엔 파생이 이미 끝나 키가 힙 어딘가에 평문으로 있다.** OS 가 허가한 크로스 프로세스 읽기(Windows `ReadProcessMemory`+`VM_READ`, 리눅스 `process_vm_readv`/`/proc/pid/mem`)로 그 영역을 스캔해 키를 회수한다. 같은 사용자 권한이면 대개 별도 상승 없이 읽힌다 — [[process]] 의 메모리 격리는 **다른 사용자·다른 권한**을 막는 것이지, 같은 사용자의 관찰까지 막지는 않는다.

**passive read 로 끝낸다** — 대상 프로세스에 코드를 주입하거나 상태를 바꾸지 않고 바이트만 읽는다. 반복 스캔 비용은 회수한 키를 세션 동안 캐싱해 줄인다.

## 왜 중요한가

두 방향으로 값이 있다.

- **문제 해결 관점** — kakao-task 에서 카톡 SQLCipher raw key 의 오프라인 파생을 4차 시도(anti-debug + DPAPI 벽)까지 못 뚫자, **실행 중 카톡 메모리를 passive VM_READ 로 스캔해 raw key 를 회수**하고 chatLogs 를 실복호했다. 파생식은 셸빙하고 속도는 세션 키캐시로 메웠다.
- **방어 관점** — 「메모리에 있는 비밀은 같은 사용자 권한 앞에서 안전하지 않다」가 왜 성립하는지를 설명한다. 그래서 키를 짧게 들고 즉시 지우기·메모리 잠금(mlock)·비밀 최소 상주가 방어 규율이 된다.

## 경계와 오해

- **키 비상주 ≠ 이 공격 무력화** — 우리 쪽 코드가 키를 안 들고 있어도, **원래 그 비밀을 만든 다른 프로세스**가 들고 있으면 그쪽을 읽으면 된다.
- **격리를 뚫는 게 아니다** — OS 가 정식으로 제공하는 API 로 읽는다. 취약점 익스플로잇이 아니라 권한 안에서의 관찰이다. 그래서 **권한 경계**(다른 사용자·보호 프로세스·SIP)를 넘으려면 별도 상승이 필요하다.
- **오프라인 파생과 트레이드오프** — 메모리 회수는 대상이 **실행 중이어야** 하고 메모리 레이아웃 변화에 취약하다. 오프라인 파생은 언제든 되지만 파생식을 뚫어야 한다.
