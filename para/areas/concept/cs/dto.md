# DTO (Data Transfer Object)

**계층 경계를 넘어갈 때 값을 담아 나르는 객체.** 안에서 쓰는 엔티티를 그대로 내보내지 않고, **주고받을 모양을 따로 정의한다.**

## 정의

방향에 따라 둘로 갈린다.

| | 무엇 | 어디서 |
|---|---|---|
| **RequestDTO** | 클라이언트가 보낸 JSON 을 받을 그릇 | `@RequestBody` 로 채워진다 |
| **ResponseDTO** | 클라이언트에게 내보낼 모양 | 서비스가 돌려준 **엔티티를 변환**한다 |

```
클라이언트 ──JSON──▶ RequestDTO ──▶ 서비스 ──▶ Entity
                                              │
클라이언트 ◀──JSON── ResponseDTO ◀── 변환 ◀────┘
```

**엔티티는 계층 안쪽에만 머문다** → [[service-layer]] · [[persistence-framework]]

## 왜 중요한가

**엔티티를 그대로 내보내면 두 가지가 새어 나간다.**

- **내부 구조** — 컬럼 이름·연관관계가 그대로 API 의 계약이 된다. 테이블을 고치면 **클라이언트가 깨진다**
- **보여선 안 되는 값** — 비밀번호 해시·내부 상태가 응답에 딸려 나간다

반대 방향도 같다 — 요청을 엔티티로 바로 받으면 **클라이언트가 보내면 안 되는 필드까지 채워진다** → [[handler-method-argument]] · [[encapsulation]]

**그리고 화면이 원하는 모양과 저장하는 모양이 원래 다르다.** 목록에는 제목만, 상세에는 본문까지 — 같은 엔티티에서 **다른 DTO 를 여럿 만드는 것이 정상**이다.

## 경계와 오해

- **DTO 는 로직을 갖지 않는다** — 값을 나르는 것이 일이다. 판단이 들어가기 시작하면 그것은 서비스나 도메인의 몫이다 → [[service-layer]]
- **기본 생성자가 없으면 JSON 을 못 받는다** — 필기가 부딪힌 자리다: 「`ArticleDTO` 의 기본 생성자가 없어 final 필드의 값을 입력할 수 없어 에러가 발생」. 변환기가 **객체를 만든 뒤 값을 채우는 방식**이라 `final` + 전 인자 생성자만 있으면 실패한다 → [[constructor]] · [[reflective-instantiation]] · [[json]]
- **`record` 로 만들면 그 문제가 다시 온다** — 불변이라 좋아 보이지만 라이브러리 지원과 설정이 따라야 한다. **불변성과 역직렬화가 부딪히는 자리**다 → [[immutability]]
- **변환 코드가 지겹다는 것이 실제 비용이다** — 엔티티 ↔ DTO 를 손으로 옮기는 코드가 필드 수만큼 늘어난다. 그것이 싫어 엔티티를 그대로 쓰는 유혹이 생기는데, **지겨움과 결합은 다른 문제**다 → [[lombok]]
- **DTO 를 계층마다 또 만들 필요는 없다** — 컨트롤러↔서비스까지 따로 두면 클래스가 배로 는다. **경계는 밖으로 나가는 자리 하나면 충분한 경우가 많다** → [[coupling]]
