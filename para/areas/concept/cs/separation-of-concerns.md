# 관심사 분리 (Separation of Concerns)

**서로 다른 종류의 일을 별도 영역에 배치해 각 코드가 한 가지 관심사를 책임하게 하는 설계 원칙.** 요청 형식, 업무 정책, 저장 방식처럼 서로 다른 이유로 변하는 코드를 분리해 변경의 파급 범위를 줄인다.

## 정의

관심사는 코드가 해결하는 일의 종류이자 코드가 변경되는 이유다. 웹 애플리케이션에서는 다음과 같이 나눌 수 있다.

| 관심사 | 맡는 일 | 대표적인 변경 이유 |
|---|---|---|
| 표현 | 요청 해석, 입력 형식 검증, 응답 변환 | HTTP·JSON·화면 형식 변경 |
| 비즈니스 | 정책 판단, 도메인 규칙, 유스케이스 조율 | 할인·승인·주문 정책 변경 |
| 영속성 | 데이터 저장과 조회 | DB·ORM·쿼리 변경 |

한 코드 조각에 여러 관심사가 섞여 있으면 그 코드에는 변경 이유도 여러 개 생긴다. 분리할 때는 클래스나 폴더의 이름보다 **무엇 때문에 함께 바뀌는가**를 기준으로 책임을 묶는다.

관심사 분리는 특정 아키텍처가 아니다. [[layered-architecture]]는 이 원칙을 표현·비즈니스·영속성 계층으로 구현하는 한 가지 방식이다.

## 왜 중요한가

요청 파싱, 할인 계산, SQL 실행이 한 메서드에 있으면 할인 정책만 바꿀 때도 웹과 DB 코드를 함께 열어야 한다. 핵심 규칙만 시험하려 해도 HTTP 요청과 데이터베이스를 준비해야 하며, 같은 규칙을 배치나 메시지 소비자에서 재사용하기 어렵다.

관심사를 분리하면 정책 변경은 도메인과 서비스에, 외부 형식 변경은 컨트롤러와 DTO에, 저장 기술 변경은 데이터 접근 구현에 국소화된다. 각 부분을 독립적으로 테스트하거나 교체할 수 있고, 코드가 쓰는 어휘도 해당 책임에 가까워진다.

## 경계와 오해

- **관심사 분리 ≠ 파일 수 늘리기** — 클래스를 여러 개 만들어도 모든 클래스가 HTTP·정책·SQL을 함께 알면 관심사는 분리되지 않았다. 책임과 의존 관계가 실제로 갈라져야 한다.
- **관심사 분리 ≠ 한 메서드는 한 줄이어야 한다** — 코드 길이가 아니라 변경 이유의 개수가 기준이다. 하나의 책임을 완결하는 긴 알고리즘은 여러 관심사를 섞은 짧은 메서드보다 응집적일 수 있다.
- **관심사 분리 ≠ 모든 경계에 DTO 만들기** — 외부 API, 애플리케이션, 영속성처럼 변화 주기가 다른 경계에서는 변환이 유용하지만, 모든 내부 호출에 별도 객체를 만들면 변환 비용만 늘 수 있다 → [[dto]].
- **분리는 공짜가 아니다** — 파일, 인터페이스, 매핑 코드와 간접 호출이 늘어난다. 변경과 독립 테스트의 이득이 작은 단순 CRUD에는 더 작은 구조가 적합할 수 있다.
- **한 가지 관심사 ≠ 한 가지 기능** — 주문 생성이라는 기능도 표현, 업무 규칙, 저장이라는 서로 다른 관심사를 포함할 수 있다.
