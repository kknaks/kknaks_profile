# 심층 방어 (Defense in Depth)

**통제를 한 층에만 두지 않고 독립된 여러 층에 겹쳐 걸어, 한 층이 뚫려도 다음 층이 막게 하는 설계.** 핵심 따름정리: **보이는 것을 거르는 층은 접근제어가 아니다** — 표시·선언층 필터는 발견 가능성만 줄일 뿐이고, 실행 지점의 재판정만이 통제다.

## 정의

1. 각 층은 **독립적으로** 판정한다 — 앞 층이 걸렀을 것이라고 가정하지 않는다.
2. 층의 역할이 다르다: 바깥 층(목록 필터·UI 숨김·선언)은 노출을 줄이고, 안쪽 층(서버 재판정)은 실행을 막는다.
3. 안쪽 층 없이 바깥 층만 있으면, 바깥 층을 우회한 직접 호출이 그대로 실행된다.

## 사용 예시

mediness MCP 도서관 발행(WP-123): 발행 툴을 system_admin capability 전용으로 열 때 두 층에 걸었다 —

- **선언층**: tools/list 필터가 권한 없는 에이전트에게 툴 자체를 안 보여준다.
- **실행층**: back 이 `baseline.publish.agent` leaf 를 요청마다 재판정한다.

선언층만 있으면 tools/list 를 거치지 않는 직접 `tools/call` 이 뚫린다 — 목록에 없는 툴도 이름만 알면 호출할 수 있기 때문이다.

## 왜 중요한가

이걸 모르면 「UI 에서 버튼을 숨겼으니 됐다」「목록 필터에 걸었으니 됐다」로 통제가 끝났다고 믿게 된다. 실제로는 바깥 층은 정상 경로만 거르고, 공격·오작동·우회 호출은 전부 안쪽 층으로 직행한다. 통제가 한 층뿐이면 그 층의 버그 하나가 전체 통제의 구멍이다.

## 경계와 오해

- **심층 방어 ≠ 같은 검사의 중복** — 같은 코드를 두 번 부르는 것은 층이 하나다. 층은 서로 다른 지점(노출/실행)에서 독립 판정할 때만 센다.
- **선언층 필터 ≠ 권한 체계** — LLM 에이전트의 툴 목록 필터는 UX·토큰 절약 장치다. 권한은 실행층의 몫이다.
