# 비동기 I/O 와 워커 블로킹

**요청을 처리하는 일꾼이 「기다리는 동안」에도 붙들려 있는가.** 붙들려 있으면 일꾼 수가 곧 동시 처리 수의 상한이 된다.

## 정의

서버는 요청을 **워커**(쓰레드나 프로세스)가 처리한다. 그 안에서 DB 나 외부 API 를 부르면 응답이 올 때까지 **아무것도 안 하면서 기다린다**.

```
[동기·블로킹]
워커1  ──질의──▶ ····· 기다림 ····· ◀──응답── 처리 → 끝     이 동안 다른 요청 못 받음
워커2  ──질의──▶ ····· 기다림 ·····
...
워커가 다 차면 → 새 요청은 대기 → 시간이 지나면 worker timeout

[비동기·논블로킹]
워커1  ──질의──▶ (다른 요청 처리) ◀──응답── 이어서 처리
       기다리는 동안 일꾼이 놓여난다
```

**바쁜 것이 아니라 기다리느라 못 받는 것**이라는 게 이 문제의 성격이다 — CPU 는 놀고 있는데 처리량이 안 오른다.

```python
self.client = AsyncElasticsearch(
    hosts=[settings.ELASTICSEARCH_URL],
    timeout=30,               # 무한정 기다리지 않는다
    max_retries=3,
    retry_on_timeout=True,
)
```

**타임아웃과 재시도가 함께 있는 것**도 중요하다 — 비동기로 바꿔도 **끝나지 않는 요청**이 있으면 결국 자원이 묶인다.

## 사용 예시

세 API 를 부르는 같은 일을 두 방식으로 적으면 차이가 시간으로 드러난다.

```python
# 동기 — 하나씩 기다린다 (2초 + 3초 + 1초 = 6초)
response1 = requests.get(".../users/1")
response2 = requests.get(".../portfolio/1")
response3 = requests.get(".../interviews/1")

# 비동기 — 함께 보내고 함께 기다린다 (가장 긴 3초)
user, portfolio, interview = await asyncio.gather(
    fetch_user_info(session),
    fetch_portfolio_info(session),
    fetch_interview_info(session),
)
```

**총 시간이 「합」에서 「최댓값」으로 바뀐다** — 이것이 비동기가 주는 것의 전부다.

### 자주 틀리는 두 가지

```python
# ❌ async 로 감싸기만 함 — 여전히 블로킹
async def wrong_async():
    time.sleep(2)

# ✅ 기다리는 동안 놓아 주는 함수를 쓴다
async def correct_async():
    await asyncio.sleep(2)

# ❌ 순차 await — 병렬이 아니다 (2초 + 3초 = 5초)
result1 = await api_call_1()
result2 = await api_call_2()

# ✅ 먼저 다 띄우고 나중에 기다린다 (3초)
result1, result2 = await asyncio.gather(api_call_1(), api_call_2())
```

**`async` 는 「기다릴 수 있는 함수」라는 표시일 뿐, 그 안이 블로킹이면 아무것도 안 바뀐다.** `await` 를 붙이는 자리도 마찬가지다 — **부르는 순간이 아니라 기다리는 순간**을 늦춰야 겹쳐서 돈다.

## 왜 중요한가

**worker timeout 은 대개 「느린 코드」가 아니라 「기다리는 구조」의 증상이다.** 질의 하나를 빠르게 만드는 것과 **기다리는 동안 일꾼을 놓아 주는 것**은 다른 처방이고, 후자가 고부하에서 훨씬 크게 듣는다 → [[performance-testing]] · [[little-law]]

**그래서 부하가 클수록 차이가 벌어진다.** 한산할 때는 워커가 남으니 티가 안 나고, 몰릴 때 **워커가 먼저 마른다** — 이 회차의 측정이 그것을 그대로 보인다(Load Test 90% ↔ Stress Test 215% 향상) → [[universal-scalability-law]]

**커넥션 풀이 마르는 것과 같은 모양이다.** 자원의 이름만 다르고 「기다리는 동안 붙들고 있다」는 구조가 같다 → [[connection-pool-sizing-formula]] · [[osiv]]

## 경계와 오해

- **비동기가 「빠르게」 만들지 않는다** — 질의 하나의 시간은 그대로다. 바뀌는 것은 **같은 시간에 몇 개를 겹쳐 처리하느냐**다. 응답시간이 줄어든 것도 대기열이 짧아진 결과이지 질의가 빨라진 것이 아니다
- **한 곳만 비동기로 바꾸면 소용없다** — 경로 어딘가에 블로킹 호출이 하나 남아 있으면 **거기서 다시 막힌다.** 「비동기로 바꿨는데 왜 그대로냐」의 대부분이 이것이다
- **CPU 를 쓰는 일에는 안 듣는다** — 기다리는 것이 아니라 계산하는 것이면 일꾼을 놓아 줄 시간이 없다. **I/O 대기에만 효과가 있다** → [[io-bound-vs-cpu-bound]] · [[thread]]
- **`async` 를 붙인다고 비동기가 아니다** — 안에서 `time.sleep` 이나 동기 HTTP 클라이언트를 부르면 **이벤트 루프를 쥔 채 멈춘다.** 이때는 그 프로세스의 다른 요청까지 함께 막히므로 **동기 코드보다 나쁠 수도** 있다
- **`await` 를 줄줄이 쓰면 순차 실행이다** — 하나씩 기다리면 시간이 그대로 더해진다. 겹쳐 돌리려면 **먼저 전부 띄우고 나중에 모아 기다려야** 한다(`gather`·`create_task`)
- **전부 동시에 보내는 것이 늘 옳지도 않다** — 상대가 못 견디거나 막는다. **동시 개수에 상한**을 다시 두는 것이 짝이다 → [[semaphore]]
- **타임아웃이 없으면 비동기도 마른다** — 응답 없는 요청이 쌓이면 결국 자원이 다 묶인다. 필기의 `timeout=30`·`max_retries=3` 이 그 방어다
- **재시도는 부하를 늘릴 수도 있다** — 상대가 이미 힘든데 세 번씩 다시 보내면 **더 밀어붙이는 셈**이다. 물러설 줄 아는 재시도가 필요하다 → [[transport-layer]] 의 혼잡제어와 같은 발상이다
- **비동기 코드는 읽기 어렵다** — 흐름이 이어지지 않으므로 디버깅과 예외 처리가 까다로워진다. **얻는 것이 분명할 때 치를 대가**다 → [[exception-handling]]

## 출처

- [[2025-10-01-insight]] — 문제 원인 여섯 가지 중 다섯 번째가 **「Worker timeout — DB 병목으로 인한 worker timeout 발생 / 동기식 접근으로 인한 블로킹 발생」**이고, 개선의 첫 항목이 **`AsyncElasticsearch` 클라이언트**다. 「비동기 검색으로 블로킹 없이 여러 요청 동시 처리」라는 한 줄이 이 개념의 요약이고, `timeout=30`·`max_retries=3`·`retry_on_timeout=True` 설정이 함께 적혀 있어 **비동기만으로는 부족하다**는 것도 코드에 남았다. 무엇보다 이 개선의 효과가 **부하에 따라 다르게 나타난 것**이 기록됐다 — 50 VUs 에서 RPS 90% 향상, 300 VUs 에서 215% 향상. 「고부하 환경일수록 성능 우위가 더 크게 나타남」이라는 관찰이 블로킹 구조의 성격을 정확히 짚는다. 여섯 번째 원인(「앱·웹·AI(SSE) 모든 라우팅 간 자원 공유로 인한 병목」)도 같은 구조의 다른 얼굴이다 → [[server-sent-events]]
- [[2025-07-21-Sync_Async]] — 같은 이야기를 **실무에 쓰기 전에 정리해 둔** 쪽이다. 세 API 호출을 동기(6초)와 비동기(3초)로 나란히 적고 **실행 결과의 타임라인까지 주석으로 남긴 것**이 「합 → 최댓값」의 변화를 눈으로 보인다. FastAPI 예제에서 「총 5초 소요, **이 시간 동안 서버는 다른 요청을 처리할 수 없음!**」이라 적은 자리가 이 개념의 요점이고, 「꼭 알아야 할 3가지」로 **async/await · `asyncio.gather` · `Semaphore`** 를 꼽아 **겹쳐 보내는 것과 상한을 두는 것을 한 벌**로 묶었다 → [[semaphore]]. 「❌ 동기 함수를 async 로 감싸기만 함 / ❌ 순차적 await」 두 반례가 특히 값지다. 다만 4장의 **「성능 향상: 약 16.7배」**는 10명이 동시에 요청할 때 50초 → 3초를 단순히 나눈 수치라, **워커·커넥션 한도를 무시한 이상적인 계산**이다 — 실제 개선폭은 이 배수를 그대로 따라가지 않는다
