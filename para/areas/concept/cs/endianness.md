# 바이트 순서 (Endianness)

**한 값이 여러 바이트를 차지할 때, 그 바이트를 어느 쪽부터 늘어놓는지의 규칙.** 값도 같고 바이트 집합도 같은데 **순서만 다른** 두 표기가 있고, 어느 쪽인지 모르면 되읽을 수 없다.

## 정의

`가` 의 유니코드 번호는 `U+AC00` 이다. 두 바이트를 늘어놓는 방법이 둘이다.

| | 이름 | `가`(AC00) | 큰 자리가 오는 곳 |
|---|---|---|---|
| **big-endian** (BE) | 빅엔디안 | `AC 00` | **앞** |
| **little-endian** (LE) | 리틀엔디안 | `00 AC` | 뒤 |

Day41 이 같은 문자열을 두 규칙으로 내보내 이것을 나란히 놓는다.

```java
    String str = new String("AB가각");
    byte[] bytes_UTF_16BE= str.getBytes("UTF-16BE");  //00 41 00 42 ac 00 ac 01 
    byte[] bytes_UTF_16LE = str.getBytes("UTF-16LE"); //41 00 42 00 00 ac 01 ac 
```

**두 배열의 길이가 같고 들어 있는 바이트도 같다** — 두 개씩 짝지어 뒤집은 것뿐이다. `A`(`0041`)가 `00 41` 과 `41 00` 으로 갈리고, `가`(`AC00`)가 `ac 00` 과 `00 ac` 로 갈린다.

이름의 유래는 「어느 쪽 끝(end)이 먼저 오는가」다 — 큰 쪽(big end)이 먼저면 BE, 작은 쪽이 먼저면 LE.

## 사용 예시

Day41 의 같은 예제에서 **UTF-8 과 MS949 는 이 문제가 없다.**

```java
    byte[] bytes_UTF_8 = str.getBytes("UTF-8");       //41 42 ea b0 80 ea b0 81 
    byte[] bytes_MS949 = str.getBytes("MS949");       //41 42 b0 a1 b0 a2 
```

**`UTF-8BE`·`UTF-8LE` 라는 것은 없다.** UTF-8 은 「한 글자를 바이트 몇 개로 어떻게 쪼갠다」를 규칙 자체에 이미 정해 두었기 때문이다 — 나눈 조각의 순서가 규격의 일부라 남은 선택지가 없다. 순서를 정해야 하는 것은 **16비트·32비트 값을 통째로 메모리에서 꺼내 늘어놓는** 방식뿐이고, 그래서 이 문제는 UTF-16·UTF-32 와 `int`·`double` 같은 **고정 폭 이진 값**에만 생긴다 → [[character-encoding]] · [[binary-io]]

## 왜 중요한가

**깨진 데이터와 순서가 틀린 데이터는 증상이 다르고, 구별하면 고칠 자리가 달라진다.** UTF-16 을 반대 순서로 읽으면 `가` 가 `U+00AC`(`¬`)가 되고 한글이 아예 다른 문자로 보인다 — **바이트는 하나도 안 잃었는데 전부 다른 글자**가 되는 형태다. 인코딩을 잘못 고른 것(→ [[character-encoding]])과 순서를 잘못 고른 것이 화면에서는 둘 다 「글자가 이상하다」로 보이지만, 후자는 **글자 수가 정확히 맞는다**는 표시가 있다.

**두 프로그램 사이의 약속이 코드에 안 적히는 대표적인 자리다.** Day38 이 `out.write(no >> 24)` 를 먼저 쓴 것이 big-endian 이라는 뜻인데, 그 사실은 **네 줄의 순서에만** 있었다. 표준 층(`DataOutputStream`)이 big-endian 을 규격으로 못 박는 것이 이 문제를 없애는 방법이고, 「형식을 문서로 갖는다」의 구체적인 내용 중 하나가 바로 바이트 순서다 → [[binary-io]] · [[data-io-stream]]

**같은 파일이 기계를 옮기면 못 읽히는 경로가 이것이다.** x86·ARM 은 little-endian 이라 C 로 `fwrite(&n, 4, 1, f)` 처럼 메모리를 그대로 쓰면 LE 로 나가고, 네트워크 프로토콜은 관례상 BE(그래서 「네트워크 바이트 순서」라 부른다)다. **Java 는 `int` 를 4바이트로, 표준 스트림을 BE 로 못 박아 언어가 이 문제를 막아 주지만, 다른 언어가 쓴 파일을 읽을 때 다시 나타난다** → [[platform-dependency]]

## 경계와 오해

- **바이트 순서 ≠ 비트 순서** — 뒤집히는 것은 바이트 단위이고 한 바이트 안의 8비트는 그대로다. `AC 00` → `00 AC` 이고 `35 00`(비트를 뒤집은 것) 같은 것이 되지는 않는다. 그래서 `>>`·`&` 같은 비트 연산은 엔디언과 무관하게 같은 결과를 준다 — **엔디언은 메모리·파일에 늘어놓을 때만 나타나고 계산에는 나타나지 않는다** → [[bit-shift]] · [[bitwise-operator]]
- **메모리 안의 `char` 에는 바이트 순서가 없다 — Day41 필기의 「UCS2(UTF16BE, 2바이트)」가 그 혼동이다** — 필기가 JVM 이 문자를 다루는 방식을 「UTF16BE」라 적었지만, `char` 는 **16비트 정수 하나**이고 프로그램이 그것을 두 바이트로 쪼개 보지 않는다. BE/LE 는 **바이트 열로 늘어놓는 순간**에만 정해지는 것이라, 값으로 들고 있는 동안에는 물을 수 없는 질문이다. `0xac00` 을 「AC 가 앞이다」로 읽는 것은 **16진수 표기를 보고 메모리 배치를 말하는** 것이고, 실제 JVM 은 그것을 어떻게 저장하든 상관없다 — 필기의 「JVM(UCS2) 00 41 ==> File(UTF-8) 41」 표가 왼쪽 칸에 바이트를 두 개 적으면서 그 두 개의 순서를 규격처럼 다룬 자리다 → [[unicode]] · [[data-type]]
- **`"UTF-16"` 은 BE·LE 중 하나가 아니라 「BOM 을 보고 판단한다」는 뜻이다** — Java 에서 `"UTF-16"` 으로 **쓰면** 맨 앞에 `FE FF` 두 바이트(BOM, byte order mark)를 붙이고 BE 로 적는다. **읽을 때는** BOM 이 있으면 그것을 따르고 없으면 BE 로 가정한다. 그래서 「UTF-16 으로 저장했는데 앞에 두 바이트가 더 붙었다」와 「BOM 이 그대로 문자(`﻿`)로 읽혔다」가 둘 다 흔한 사고다. `"UTF-16BE"`·`"UTF-16LE"` 를 명시하면 BOM 을 붙이지도 읽지도 않는다 — **Day41 이 쓴 것이 이 명시형이고, 그래서 예제 출력에 BOM 이 없다.** 반대로 앞 회차에서 `new String(bytes, "utf-16")` 으로 BOM 없는 바이트를 읽어 성공했던 것은 **「없으면 BE」라는 기본값을 밟은 것**이었다 → [[character-encoding]]
- **순서가 틀려도 예외가 나지 않는다** — UTF-16 은 두 바이트 조합의 거의 전부가 유효한 문자이므로, 반대로 읽어도 디코더가 성공하고 **엉뚱한 글자가 조용히 나온다.** UTF-8 은 규칙에 맞지 않는 바이트 조합이 있어 잘못 읽으면 `U+FFFD`(�)가 나타나 표시가 되는데, UTF-16 의 순서 오류에는 그 표시가 없다. **틀렸다는 신호가 없는 것이 이 문제의 실질적인 어려움**이다 → [[character-stream]]
- **`length()` 나 바이트 수로는 순서 오류를 못 잡는다** — BE 와 LE 는 길이가 같다. 그래서 「길이가 맞으니 잘 읽혔다」가 성립하지 않는다. 반대로 인코딩 자체를 틀리면 길이가 달라지는 경우가 많아(UTF-8 3바이트 vs UTF-16 2바이트) 그쪽은 검증에 걸린다 → [[length-prefix-framing]]
- **Java 표준 스트림은 늘 big-endian 이라 선택할 수 없다** — `DataOutputStream.writeInt` 는 상위 바이트부터 쓰고 옵션이 없다. LE 가 필요하면 `ByteBuffer.order(ByteOrder.LITTLE_ENDIAN)` 을 쓰거나 손으로 뒤집는다. **「Java 는 엔디언 문제가 없다」가 아니라 「Java 안에서만 왕복하면 문제가 없다」**가 정확한 말이다 → [[data-io-stream]] · [[serialization]]
- **텍스트 파일에서도 이 문제가 남는다 — UTF-16 으로 저장한 텍스트에 한한다** — 「바이너리는 엔디언, 텍스트는 인코딩」으로 나누면 UTF-16 텍스트 파일이 설명되지 않는다. Windows 의 메모장이 「Unicode」로 저장하면 UTF-16LE + BOM 인데, 그것을 BOM 을 무시하는 파서에 넣으면 글자 사이에 `\0` 이 끼어 보인다. **UTF-8 이 사실상 표준이 된 이유의 하나가 이 축을 아예 없앤 것**이다 → [[unicode]]
