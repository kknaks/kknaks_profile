# 개방-폐쇄 원칙 (OCP)

**기능을 더할 때 더하는 것으로 끝나고, 이미 있는 코드를 열지 않아도 되게 만드는 것.** 필기의 한 줄이 「엔티티(클래스, 모듈, 함수 등)는 확장에는 열려 있어야 하고, 수정에는 닫혀 있어야 한다」다. 확장과 수정이 **같은 파일에서 일어나느냐**가 이 원칙이 재는 전부다.

## 정의

두 낱말이 서로 반대말처럼 보이는 것이 이 원칙의 이름을 어렵게 만든다. 가리키는 대상이 다르다.

| | 무엇에 대해 | 뜻 |
|---|---|---|
| **개방**(open for extension) | 동작을 늘리는 일 | 새 클래스를 하나 더할 수 있다 |
| **폐쇄**(closed for modification) | 이미 검증된 코드 | 그 파일을 다시 열지 않는다 |

**「고칠 곳이 몇 군데인가」가 아니라 「고쳐야 할 곳이 있는가」를 묻는다.** 그래서 판정 방법이 단순하다 — 새 종류를 하나 상상해 보고, `git diff` 에 새 파일 하나만 나오면 지킨 것이고 기존 파일이 나오면 아니다.

지키는 수단은 대체로 **갈리는 부분을 타입으로 빼는 것**이다 → [[polymorphism]] · [[interface]]

## 사용 예시

### 램프 예제 — 2단계가 위반으로 지목된다

부모 클래스를 만들어 다형성으로 램프 전부를 제어하는 데까지 갔는데, 필기가 여기서 「**Switch의 새로운 기능 추가 시, Open/Closed Principle을 충족시키지 못한다**」로 멈춘다.

램프의 **종류**는 늘려도 `Switch` 를 안 고친다 — 그것은 이미 다형성이 해결했다. 걸리는 것은 반대쪽이다. 「깜빡이기」처럼 **`Switch` 가 시킬 수 있는 일의 종류**가 늘면 `Lamp` 부모에 메서드를 더해야 하고, 그러면 그 부모를 상속한 모든 램프가 영향을 받는다. **한 축(구현 교체)은 열렸고 다른 축(연산 추가)은 닫히지 않은 상태**이며, 상속으로 얻는 확장성이 대개 그렇다.

### 실습 프로젝트 — `switch` 를 지우면 절반이 닫힌다

하루 앞 회차의 `App.processMenu` 는 메뉴가 하나 늘 때마다 `case` 를 하나 더해야 했다.

```java
switch (menuTitle) {
  case "회원": userCommand.execute(); break;
  case "프로젝트": projectCommand.execute(); break;
  ...
}
```

이 회차가 그 자리를 조회로 바꾼다.

```java
void processMenu(String menuTitle) {
  Command command = commandMap.get(menuTitle);
  if (command == null) { ... return; }
  command.execute();
}
```

**`processMenu` 는 이제 어떤 메뉴가 몇 개 있어도 안 바뀐다** — 이 메서드에 대해서는 수정이 닫혔다 → [[dispatch-table]]

그런데 등록하는 자리는 열려 있다.

```java
public App() {
  commandMap.put("회원", new UserCommand("회원", userList));
  commandMap.put("게시판", new BoardCommand("게시판", boardList));
  ...
}
```

**명령을 하나 더하려면 `App` 의 생성자를 고친다.** 필기가 램프 예제 4단계에서 「새로운 제품군이 들어오면 Switch클래스 내부에서 코드 수정이 필요하다」로 지목한 상태와 같은 것이고, 그것이 5단계(외부에서 대입)로 가야 해소된다 → [[dependency-injection]]

### 보름 뒤 — 지킨 쪽의 예가 처음 나온다

Day31 은 이 원칙을 **위반 지점을 짚는 데만** 썼다. Day42 가 이 원칙을 다시 꺼내는 자리는 반대쪽이다 — 데코레이터 패턴의 근거로 「상속을 이용한 강결합은 유지보수 측면에서 OCP 원칙을 위배한다」를 적고, 그 다음에 위배하지 않는 코드를 만든다.

커피에 「모카」를 더하는 일이 **파일 하나**다.

```java
public class Mocha extends Decorator{
  public Mocha(Beverage beverage){
    this.beverage = beverage;
  }

  public double cost(){
    return beverage.cost() + 200;
  }
}
```

`Beverage`·`Espresso`·`Decorator`·이미 있는 다른 조미료 중 **아무것도 열지 않는다.** Day31 이 「새 파일 하나만 나오면 지킨 것」이라는 판정 기준을 세워 두었고, 여기가 그 기준을 통과하는 첫 코드다 → [[decorator-pattern]]

**대조군이 필기에는 없어서 「왜 상속이 위배인가」가 비어 있다.** 조미료를 상속으로 붙이려면 두 길뿐이고 둘 다 걸린다.

| 상속으로 하는 방법 | 조미료를 하나 더할 때 |
|---|---|
| 조합마다 클래스 (`EspressoWithMocha`·`EspressoWithMochaWhip`…) | 기존 조합 **전부와 곱해진** 새 클래스들 |
| 부모에 조미료 옵션을 몰아넣기 (`hasMocha`·`hasWhip` 필드 + 부모 `cost()` 가 합산) | **부모 클래스를 고친다** |

**아래쪽이 진짜 「수정」이다.** 위쪽은 형식적으로는 추가뿐이라 곱셈이 비용이고, 아래쪽은 조미료가 늘 때마다 `Beverage` 를 열고 필드와 `cost()` 를 고치게 된다 — 그리고 클래스 폭발을 피하려면 대개 아래쪽으로 간다. **「상속이 OCP 를 위배한다」의 정확한 형태는 「상속으로 조합을 표현하려다 결국 부모를 고치게 된다」**이고, 필기는 결론만 옮겨 적었다 → [[inheritance]] · [[coupling]]

## 왜 중요한가

**이미 도는 코드를 안 건드리는 것 자체가 이득이다.** 새 파일을 더해 생긴 버그는 새 기능만 망가뜨리지만, 기존 파일을 고쳐 생긴 버그는 **이미 잘 되던 것을 망가뜨린다.** 하루 앞 회차가 그 대가를 실물로 남겼다 — 리팩터링 중에 `indexOf` 의 비교가 `.equals()` 에서 `==` 로 후퇴해 조회·변경·삭제가 전부 죽었다. **손대지 않은 코드는 그렇게 죽지 않는다** → [[refactoring]] · [[object-equality]]

**그리고 「빠뜨림」이 사라진다.** `switch` 로 갈래를 내는 구조에서는 새 명령을 더할 때 `case` 를 넣는 것을 잊어도 컴파일된다 — 실행하고 그 메뉴를 눌러 봐야 안다. 등록이 한 줄이면 잊는 자리도 하나다.

**빌드 단위가 커지면 값이 커진다.** 「고치지 않는다」의 실제 이득은 파일 하나가 아니라 **그 파일을 의존하는 모든 것을 다시 컴파일하고 다시 확인하지 않아도 되는 것**이다. 이 실습은 클래스 열 몇 개라 체감되지 않지만, 라이브러리를 배포한 뒤에는 「이미 나간 인터페이스에 메서드를 더할 수 없다」가 되고 그것이 `default` 메서드가 생긴 이유다 → [[default-method]]

## 경계와 오해

- **OCP ≠ 코드를 절대 고치지 않는다** — 요구가 바뀌면 고친다. 이 원칙이 말하는 것은 **예상되는 변화의 축**에서만이고, 그 축을 고르는 것이 설계다. 축을 잘못 고르면 「확장에 열린」 방향으로는 아무도 확장하지 않고 정작 필요한 변경은 전부 수정이 된다 — 열어 둔 방향마다 클래스와 인터페이스가 늘므로 **아무 방향으로나 열어 두는 것이 공짜가 아니다.**
- **이 회차의 필기가 OCP 를 잘못 붙인 자리가 있다** — 「App()에서 List를 생성하고 매개변수로 Comman에 넘긴다.(OCP원칙)」이라 적었는데, 목록을 밖에서 만들어 넘기는 것은 **의존성 주입**이다. 그것으로 무엇이 닫히는지 세어 보면 드러난다 — `Command` 는 `List` 를 만들지 않게 되었지만 **`App` 은 오히려 목록 넷을 새로 알게 되었다.** 원칙 이름을 붙일 때는 「무엇을 고치지 않게 되었나」에 답이 있어야 하고 여기에는 없다 → [[dependency-injection]]
- **OCP 위반은 대개 다른 위반의 증상이다** — 램프 예제 4단계의 「새 제품군이 오면 `Switch` 를 고쳐야 한다」를 필기는 DIP 위반으로 적었다. 둘 다 맞다 — `Switch` 가 구현체를 스스로 만들기 때문에(DIP) 고쳐야 하는 것이므로(OCP), **원인은 DIP 고 증상이 OCP** 다. 그래서 「OCP 를 지키려면 무엇을 하나」에 직접 답이 없고, 대개 DIP·다형성·ISP 를 지키는 일로 되돌아간다 → [[dependency-inversion-principle]] · [[solid-principles]]
- **분기를 없애는 것과 분기를 옮기는 것은 다르다** — `switch` 가 사라졌지만 「어느 명령인가」를 고르는 일은 없어지지 않았다. `HashMap` 의 조회로 옮겨 갔고, 그 짝을 채우는 코드가 생성자에 있다. **`processMenu` 가 닫힌 대가로 생성자가 열려 있는 것**이고, 옮긴 곳이 한 곳이라는 것이 이득의 전부다 → [[dispatch-table]] · [[switch-statement]]
- **메뉴 목록이 여전히 두 곳에 있다** — `String[] mainMenus` 는 화면에 찍기 위해, `commandMap` 의 키는 갈래를 내기 위해 각각 메뉴 이름을 들고 있다. 메뉴를 하나 더할 때 **두 곳을 고쳐야 하고 한쪽만 고치면 조용히 어긋난다** — 배열에만 넣으면 눌렀을 때 「처리할 수 없습니다」가 나오고, 맵에만 넣으면 화면에 안 보이는 명령이 된다. 필기는 이 중복을 적지 않았고, `commandMap.keySet()` 으로 화면을 찍으면 한 곳이 된다 → [[hash-based-collection]]
- **`default` 가 `null` 검사로 바뀐 것이 안전망까지 옮긴 것은 아니다** — `switch` 의 `default:` 는 「빠진 `case`」를 실행 시점에 알려 주는 자리였고, 지금은 `commandMap.get()` 이 `null` 을 주는 것으로 같은 일을 한다. 다만 오타가 걸리는 시점은 그대로 실행 시점이다 — **분기를 데이터로 바꾼 대가는 키의 오타를 컴파일러가 못 보는 것**이고, 그것을 되찾으려면 키가 문자열이 아니라 enum 이어야 한다 → [[switch-statement]]
- **「Open-Close」가 아니라 「Open-Closed」다** — Day42 가 「OCP : Open-Close Principle으로」라 적었다. 뒤쪽은 **상태**(닫혀 있다)이지 동작(닫는다)이 아니고, 앞쪽 `open` 과 품사를 맞추면 `closed` 가 된다. 뜻을 옮긴 문장(「확장에는 열려 있어야 하지만 변경에는 닫혀있어야 한다」)은 정확하므로 이해가 아니라 표기의 문제인데, **검색하거나 남과 말할 때 걸리는 자리**라 한 번 고쳐 두면 끝난다.
- **적용 대상이 클래스만은 아니다** — Day42 는 「**클래스는** 확장에는 열려 있어야 하지만」으로 적어 대상을 하나로 좁혔다. Day31 의 「엔티티(클래스, 모듈, 함수 등)」가 원래 범위이고, 함수·모듈·라이브러리·서비스에 그대로 걸린다. 좁혀 두면 **클래스 밖의 같은 문제가 안 보인다** — 배포한 라이브러리에 메서드를 못 더하는 것도, 실행 중인 API 의 응답 필드를 못 지우는 것도 같은 원칙의 자리다 → [[default-method]]
- **상속 ≠ OCP 위배** — Day42 의 「상속을 이용한 강결합은 OCP 원칙을 위배한다」를 그대로 읽으면 상속 자체가 위반이 되는데, **Day31 의 램프 예제 2단계는 상속으로 OCP 를 지킨 자리**다. 램프의 종류가 늘어도 `Switch` 를 안 고치는 것이 다형성으로 얻은 것이었다. 갈리는 것은 **상속으로 「종류」를 표현하는가 「조합」을 표현하는가**다 — 종류는 서로 배타적이라 하나만 고르면 되고, 조합은 여러 개를 동시에 걸치므로 클래스로 표현하면 곱셈이 된다. **「강결합」이라는 낱말이 그 구분을 덮어 버린다** → [[inheritance]] · [[polymorphism]] · [[coupling]]
- **「컴파일 단계에서 결정된다」는 OCP 와 다른 축이고, 이어지는 지점이 한 군데다** — Day42 는 「상속을 사용하여 객체들을 추가하면 컴파일 단계에서 결정이 되며」를 위배의 근거로 댄다. 하지만 OCP 가 재는 것은 **기존 파일을 여는가**이고 결정 시점은 그것과 별개다 — 컴파일 시점에 다 정해져도 새 파일만 더해서 끝나면 지킨 것이다(램프 2단계가 그렇다). 두 축이 만나는 곳은 **조합의 수가 미리 셀 수 없을 때**다 — 실행 중에 조립하는 것만이 답인 상황에서는 컴파일 시점 고정이 곧 「미리 클래스로 만들어 둬야 한다」이고, 그때 기존 코드를 여는 일이 따라온다.
- **상속으로 여는 것과 조합으로 여는 것이 열어 주는 축이 다르다** — 램프 예제 2단계는 상속으로 「종류」를 열었다. 종류는 무한히 늘 수 있지만 **부모가 정한 연산 목록은 고정**이다. 반대로 명령 객체를 맵에 담는 이 회차의 구조는 「명령의 종류」에 열려 있고, `Command` 인터페이스에 메서드를 더하는 방향으로는 닫히지 않는다 — 실제로 같은 노트 뒤쪽에서 `execute()` 가 `execute(Stack)` 으로 바뀌며 **구현 넷 전부를 고쳤다** → [[interface-segregation-principle]] · [[inheritance]]

- [[2024-07-09-Day31]] — 「엔티티는 확장에는 열려 있어야 하고, 수정에는 닫혀 있어야 한다」로 원칙을 정리하고, 램프/스위치 예제 2단계에서 「Switch의 새로운 기능 추가 시, Open/Closed Principle을 충족시키지 못한다」로 위반 지점을 지목했다. 실습에서는 `App.processMenu` 의 문자열 `switch` 를 `commandMap.get(menuTitle)` 조회로 바꿔 그 메서드에 대한 수정을 닫았지만, 명령 등록이 `App` 의 생성자에 남아 명령 추가 시 여전히 `App` 을 고쳐야 한다. 필기가 목록을 생성자로 넘기는 것을 「(OCP원칙)」이라 적은 것은 의존성 주입에 붙은 잘못된 이름이며, 메뉴 이름이 `mainMenus` 배열과 `commandMap` 키 두 곳에 남은 중복은 언급되지 않았다
- [[2024-07-24-Day42]] — 이 원칙을 **위반이 아니라 근거로** 처음 쓴다. 데코레이터 패턴의 정의 절에 「OCP : Open-Close Principle으로 클래스는 확장에는 열려 있어야 하지만 변경에는 닫혀있어야 한다」·「상속을 이용한 강결합은 유지보수 측면에서 OCP 원칙을 위배한다」를 적고, 조미료 하나를 파일 하나로 더하는 코드(`Mocha extends Decorator`)를 만들어 **Day31 이 세운 「새 파일 하나만 나오면 지킨 것」 기준을 통과하는 첫 예**를 남긴다. 다만 이름을 `Open-Close` 로, 대상을 「클래스」로 좁혀 적었고, 위배의 근거를 「컴파일 단계에서 결정」에 두어 **정작 진짜 수정이 일어나는 경로(조미료 옵션을 부모 `Beverage` 에 몰아넣고 `cost()` 를 고치게 되는 쪽)는 대조군으로 두지 않았다.** 「상속을 이용한 강결합」이라는 표현은 Day31 램프 예제 2단계에서 상속이 OCP 를 지켰던 것과 나란히 읽어야 뜻이 좁혀진다
