# 쓰레드 조인 (Thread join)

**다른 쓰레드가 끝날 때까지 지금 쓰레드를 세우는 것.** `t.join()` 은 「`t` 가 TERMINATED 가 될 때까지 나는 기다린다」는 뜻이고, 그 덕분에 **끝난 쓰레드가 남긴 값을 안전하게 읽을 수 있다.** Day48 이 이 필요를 이렇게 적었다 — 「쓰레드가 독립적으로 시행 되기 때문에 다른 쓰레드의 값을 참조 할 수 없다 / 참조하기 위해서는 참조하는 값을 생성하는 쓰레드의 종료를 기다려야한다」 → [[thread]] · [[thread-state]]

## 정의

쓰레드는 결과를 **돌려주지 못한다** — `run()` 의 반환 타입이 `void` 다. 그래서 결과를 받는 경로는 언제나 셋으로 고정된다.

1. 결과를 담을 **필드**를 쓰레드 객체에 둔다
2. `run()` 이 그 필드를 채운다
3. `join()` 으로 끝난 것을 확인한 뒤 **읽는다**

```java
worker.start();
worker.join();          // 여기서 멈춘다 — worker 가 끝날 때까지
worker.getResult();     // 이제 읽어도 된다
```

`join()` 은 `InterruptedException` 을 던지므로 `try` 가 반드시 붙고, 시간을 정해 기다리는 `join(ms)` 도 있다 → [[exception-handling]]

## 사용 예시

Day48 은 1부터 100까지 더하는 일을 작업 쓰레드에게 주고 메인 쓰레드가 결과를 읽는다.

```java
public class JoinExample {
  public static void main(String[] args) {
    //메인 쓰레드 시작
    SumThread sumThread = new SumThread();
    // 작업 쓰레드 시작
    sumThread.start();
    try {
      //작업 쓰레드가 종료 될때 까지 메인 쓰레드는 기다림
      sumThread.join();
    } catch (InterruptedException e) {

    }
    // 종료된 작업쓰레드의 결과값을 메인 쓰레드가 참조
    System.out.println("1~100 합: " + sumThread.getSum());
  }
}

class SumThread extends Thread {
  private long sum;

  public long getSum() { return sum; }

  @Override
  public void run() {
    for (int i = 1; i <= 100; i++) { sum += i; }
  }
}
```

**`join()` 을 지우면 대개 `5050` 이 그대로 나온다.** 100번 더하는 일이 순식간이라 `System.out.println` 에 닿기 전에 끝나 있기 때문이다 — 그래서 이 코드는 **틀린 상태로도 시험을 통과한다.** 합을 1억까지로 늘리면 `0` 이나 중간값이 찍히기 시작한다.

**필기의 클래스 배치는 컴파일되지 않는다.** 원본은 `SumThread` 를 `main()` 안, 그것을 쓰는 줄보다 **아래에** 두었다(위 코드는 밖으로 내어 놓은 형태다) → 아래 「경계와 오해」

## 왜 중요한가

**쓰레드에게 일을 시키고 결과를 받는 첫 방법이다.** `start()` 만 배운 상태에서는 「시켜 놓고 잊는」 일밖에 못 한다. 결과가 필요한 순간 **어디까지 진행됐는지 알 방법이 없다**는 문제가 생기고, 그 답이 이 메서드다.

**그리고 「기다리는 것」보다 하나를 더 준다 — 값이 보이는 것을 보장한다.** 위 코드의 `sum` 은 `volatile` 도 아니고 잠금도 없다. 쓰레드가 쓴 값이 다른 쓰레드에게 보이는 것은 **원래 보장되지 않으며**(각자 캐시에 들고 있을 수 있다), `join()` 이 돌아왔다는 것이 「그 쓰레드가 한 모든 쓰기가 내게 보인다」를 보장해 준다. **이것이 `join()` 을 `Thread.sleep(1000)` 으로 대신할 수 없는 이유다** — 충분히 기다려도 값이 안 보일 수 있다. 「기다리기」로만 이해하면 이 차이가 안 보이고, 그래서 「어차피 끝났을 텐데」라며 `sleep` 으로 바꾼 코드가 특정 기계에서만 틀리게 나온다 → [[thread-state]]

**같은 프로세스라는 것의 값이 여기서 드러난다.** 엿새 전 Day45·Day46 은 프로그램을 두 프로세스로 갈라 값 하나를 넘기려고 소켓과 스트림을 다 썼는데, 여기서는 `getSum()` 한 줄이다. **나눈 단위가 무엇이냐가 결과를 받는 비용을 정한다** → [[process]] · [[socket]]

## 경계와 오해

- **join(쓰레드) ≠ join(SQL·문자열)** — 낱말이 같아서 검색이 섞인다. 데이터베이스의 `JOIN` 은 두 테이블을 잇는 것이고 `String.join` 은 문자열을 이어 붙이는 것이다. 여기서는 **두 실행 흐름을 다시 하나로 합치는 것**만 뜻하며, 그래서 링크는 `[[thread-join]]` 으로 건다.
- **`join()` 은 「끝내라」가 아니라 「끝날 때까지 기다린다」다** — 상대를 종료시키지 않으므로, 상대가 안 끝나면 **나도 영원히 안 돌아온다.** 무한 루프를 도는 쓰레드에 `join()` 을 걸면 그 자리에서 프로그램이 멈춘 것처럼 보이고, 그것을 막는 것이 `join(ms)` 다. 다만 **시간이 다 되어 돌아온 것과 상대가 끝나서 돌아온 것이 구별되지 않는다** — `join(1000)` 은 아무것도 돌려주지 않으므로 `isAlive()` 로 따로 물어야 하고, 확인하지 않으면 **아직 채워지지 않은 값을 읽는 경로**가 그대로 열린다.
- **하나씩 start-join 하면 병렬이 아니다** — 쓰레드 셋을 만들어 `t.start(); t.join();` 을 세 번 반복하면 언제나 하나만 돌고 있어 순차 실행과 같다. **셋을 먼저 다 `start()` 한 다음 셋을 `join()` 해야** 시간이 겹친다. Day48 은 쓰레드가 하나라 이 함정이 드러나지 않고, 「join 을 쓰면 기다린다」만 남는다.
- **서로 `join()` 하면 둘 다 안 깬다** — A 가 B 를, B 가 A 를 기다리면 교착이다. 자기 자신에게 `join()` 을 걸면 영원히 자기를 기다린다. **잠금이 없어도 교착이 생기는 자리**이고, 「동기화 안 했으니 교착은 없다」가 틀린 이유다.
- **`catch (InterruptedException e) { }` 를 비워 두면 「안 기다린 채로 읽는」 경로가 생긴다** — Day48 의 `catch` 는 비어 있다. `join()` 이 예외로 깨어나는 것은 **기다림이 끝난 것이 아니라 중단된 것**인데, 비워 두면 그대로 다음 줄인 `getSum()` 으로 내려간다. 즉 **작업 쓰레드가 아직 도는 중인데 결과를 읽는다.** Day11 이 「어떤 상태를 되돌려야 다시 시도할 수 있는가」를 물었던 자리가 여기서는 「이 예외를 받았으면 결과를 읽어서는 안 된다」이고, 빈 블록은 그것을 지운다 → [[exception-handling]]
- **Day48 의 `JoinExample` 은 컴파일되지 않는다 — `SumThread` 가 쓰이는 줄보다 아래에 선언돼 있다** — 원본은 `class SumThread extends Thread { … }` 를 `main()` **안**, 그리고 `new SumThread()`·`sumThread.getSum()` **뒤**에 두었다. 로컬 클래스의 유효 범위는 **선언 이후의 블록**이라서, 앞에서 쓴 세 줄이 모두 「symbol 을 찾을 수 없다」로 막힌다. 마지막 중괄호 둘이 그 증거다 — `main()` 이 클래스 선언을 품은 채 닫힌다. 교재가 `SumThread` 를 별도 클래스로 두었던 것을 한 파일에 붙여 적으면서 닫는 괄호 위치가 어긋난 것이고, **선언을 `main()` 밖으로 내면 그대로 돈다.** 「보이지 않는 실수」가 아니라 컴파일러가 막아 주는 쪽이라는 점은 다행이다 → [[variable-scope]] · [[nested-class]]
- **`setSum()` 은 아무도 부르지 않고, 불러서도 안 된다** — 원본은 `getSum` 과 짝으로 `setSum` 을 만들어 두었지만 쓰이는 곳이 없다. 그리고 밖에서 값을 넣을 수 있게 열어 두면 **`join()` 으로 얻은 「끝난 뒤에 읽는다」는 규율이 무의미해진다** — 쓰는 쪽이 둘이 되는 순간 그 필드는 다시 동기화가 필요한 값이 된다. 결과 필드는 **그 쓰레드만 쓰고 밖은 읽기만** 해야 한다 → [[encapsulation]] · [[immutability]]
- **「다른 쓰레드의 값을 참조 할 수 없다」는 좁은 표현이다** — 참조 자체는 언제든 된다. 같은 프로세스라 힙이 하나이고, `join()` 없이 `getSum()` 을 불러도 컴파일되고 실행되며 값도 나온다. 없는 것은 **그 값이 맞다는 보장**이다. 「참조할 수 없다」로 외우면 `join()` 을 지운 코드가 왜 대개 잘 돌아가는지, 그런데 왜 틀린 것인지 설명되지 않는다 → [[process]]
- **`join()` 은 결과를 받는 가장 낮은 층이다** — 필드에 담고 기다리고 읽는 세 단계를 손으로 하는 형태이고, 그래서 **예외를 나를 방법이 없다.** 작업 쓰레드 안에서 실패했으면 그 사실은 필드 하나를 더 두어 직접 전달해야 하고, 안 두면 「끝났지만 실패한」 것이 정상값처럼 읽힌다. `Callable` 과 `Future` 는 반환값과 예외를 함께 나르도록 이 자리를 대체한 것이다 → [[thread-state]]
