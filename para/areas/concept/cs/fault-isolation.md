# 결함 격리 (계층 소거로 발생 층 특정)

**요청이 지나는 층을 전부 나열하고, 각 층이 「낼 수 있는 에러의 어휘」를 확인해 발생 층을 소거법으로 특정하는 디버깅.** 고치기 전에 "이 증상을 낼 수 있는 층이 어디인가"를 닫는다 — 증상이 난 층과 고칠 층은 다를 수 있다.

## 정의

1. **경로를 전부 나열한다** — 클라이언트 → (프록시/게이트웨이) → BFF → 앱 서버 → 저장소처럼, 요청이 실제로 지나는 층을 빠짐없이 센다. 코드 밖의 층(인그레스·프록시·터널)이 목록에서 빠지면 소거가 성립하지 않는다 → [[layered-architecture]] · [[reverse-proxy]]
2. **층마다 어휘를 확인한다** — 각 층이 그 증상을 **낼 수 있는지**를 본다. 제한값이 얼마인지, 초과하면 어떤 코드·메시지로 말하는지. "이 층은 이 코드를 모른다"가 확인되면 그 층은 소거된다.
3. **남는 층이 범인이다** — 앱의 모든 층이 소거되면 원인은 코드 밖이다. 반대로 코드 밖이 소거되면 앱이다.

## 사용 예시

mediness prod 에서 1.4MB 첨부가 413. 층별 어휘 확인 — 클라이언트 가드는 25MB 초과를 화면 문구로, 앱 서버는 400 + `TASK_REFERENCE_FILE_TOO_LARGE` 로, BFF 는 50mb 까지 통과, uvicorn 은 무제한. **앱 경로 어디에도 413 을 내는 층이 없다** → 남는 것은 인그레스뿐 → nginx-ingress 어노테이션 부재(기본 1m) 특정. 추측으로 앱 제한을 올렸다면 헛수정이었다.

## 경계와 오해

- **증상 재현보다 어휘 대조가 먼저다** — 재현 환경을 만드는 비용 없이, 각 층의 제한·에러코드를 읽는 것만으로 소거가 진행된다. 코드와 설정이 곧 증거다.
- **소거는 나열이 전부일 때만 성립한다** — 층 하나를 빠뜨리면 「남는 층」이 틀린다. 계약이 닿는 표면을 전수 세는 규율과 같은 축이다 → [[contract-surface-enumeration]]
- **격리와 수정은 별개다** — 발생 층을 특정한 뒤에도 고칠 자리는 선택이다(프록시 한도를 앱 한도보다 크게 두어 거절 문구의 소유권을 앱에 남기는 판단처럼).
- **검증도 층의 성질을 쓴다** — 프록시 검사는 인증보다 앞단이므로, 무인증 요청의 응답 코드 전환(413→401)만으로 해당 층의 수정 반영을 밖에서 판별할 수 있다.
