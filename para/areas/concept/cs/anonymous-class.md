# 익명 클래스 (Anonymous Class)

**클래스를 선언하는 일과 그 인스턴스를 만드는 일을 한 식에 합친 것.** 이름을 주지 않으므로 파일도 클래스명도 생기지 않고, 그 자리에서 한 번 쓰고 끝나는 구현에 쓴다. Day32 의 표현으로 「명시적으로 클래스를 선언하지 않기 때문에 쉽게 객체를 생성 할 수 있다」이고, 하루 뒤 회차가 그것을 한 줄로 조인다 — 「**클래스를 정의(호출)하는 동시에 인스턴스를 생성**」. 괄호 안의 「호출」이 헛말이 아니다 — 선언이 곧 식이라서 **정의를 쓰는 행위 자체가 생성을 부르는 행위**다.

## 정의

```java
new 부모생성자(매개값,...){
    //필드
    //메서드
}
```

**`new` 뒤에 오는 것이 상속할 클래스이거나 구현할 인터페이스**이고, `{ }` 안이 그 클래스의 몸통이다. 인터페이스를 쓰면 채워야 하는 것은 추상 메서드 전부다 → [[interface]] · [[method-overriding]]

이름이 없는 데서 나머지 제약이 다 나온다.

| | 로컬 클래스 | 익명 클래스 |
|---|---|---|
| 이름 | 있다 | 없다 |
| 생성자 | 둘 수 있다 | **둘 수 없다** (생성자 이름을 쓸 방법이 없다) |
| 같은 자리에서 두 번 만들기 | `new` 를 두 번 | 몸통을 두 번 쓴다 |
| 부모가 여러 개 | — | 하나뿐(클래스 하나 또는 인터페이스 하나) |
| `this` | 자기 자신 | 자기 자신 — 바깥은 `바깥클래스명.this` |

바깥 인스턴스에 대한 숨은 참조는 로컬·인스턴스 멤버 클래스와 같이 갖는다 → [[nested-class]]

## 사용 예시

Day32 가 `ListIterator` 를 세 방식으로 만든 뒤 네 번째로 **이름을 지운다.**

```java
public abstract class AbstractList implements List {
  protected int size = 0;

  public int size() { return size;}

  public Iterator iterator() {
    return new Iterator(){
        private int cursor;

        @Override
        public boolean hasNext() {
        return cursor < AbstractList.this.size();
        }

        @Override
        public Object next() {
        return get(cursor++);
        }
    };
  }
}
```

**`class ListIterator implements Iterator` 라는 한 줄이 `new Iterator(){` 로 접혔다.** 그리고 `AbstractList` 안에서 `ListIterator` 라는 이름을 부르는 곳이 없어졌으므로, 반복자의 구현이 **`iterator()` 라는 메서드 하나에만 존재하게** 된다 → [[iterator-pattern]]

`return` 뒤의 식이 세미콜론으로 끝나는 것을 놓치기 쉽다 — `};` 다. 클래스 선언이 아니라 **식**이기 때문이다.

**엿새 뒤 Day36 은 익명 클래스를 목적지가 아니라 사다리의 가운데 칸으로 쓴다** — 같은 인터페이스를 로컬 클래스 → 익명 클래스 → 람다로 세 번씩 구현해 나란히 놓는다. 그리고 그 사다리에 오르는 인터페이스는 전부 **추상메서드가 하나**다(`void play()`·`void introduce(String)`·`double compute(int)`) — 즉 Day36 의 익명 클래스들은 **람다로 대체되는 쪽만 골라 놓은 것**이고, Day32 의 `Iterator`(메서드 둘 + 상태)처럼 그럴 수 없는 경우는 그 장에 없다 → [[functional-interface]] · [[lambda-expression]]

```java
// 2.익명 클래스로 구현하기 - v1
Intro anonymousIntro1 = new Intro() {
    @Override
    public void introduce(String s) {
    System.out.println(s);
    }
};
anonymousIntro1.introduce("익명클래스1입니다");

// 2.익명 클래스로 구현하기 - v2
new Intro() {
    @Override
    public void introduce(String s) {
    System.out.println(s);
    }
}.introduce("익명클래스2입니다");
```

**v2 가 익명 클래스만 할 수 있는 형태다.** 만들고 바로 부르고 참조를 남기지 않는다 — 같은 것을 람다로 쓰면 `(s -> System.out.println(s)).introduce("…")` 가 되는데 이것은 **컴파일되지 않는다**(아래 「경계와 오해」).

### 26일 뒤 Day48 — 골격의 나머지 절반이 채워진다

Day32 의 골격 `new 부모생성자(매개값,...){}` 이 **클래스 상속 쪽만 담고 있어 정작 그 노트의 예시(인터페이스)와 어긋난다**는 것이 아래 「경계와 오해」의 두 번째 항목인데, 쓰레드를 배우는 회차가 **그 골격이 실제로 맞는 첫 예시**를 가져온다. 그리고 인터페이스 쪽 형태와 **같은 절에 나란히** 놓인다 → [[thread]]

```java
// ① 인터페이스를 구현하는 익명 클래스 — 매개값 자리에 놓는다
new Thread(new Runnable() {
  @Override
  public void run() { /* 쓰레드가 실행할 코드 */ }
});

// ② 클래스를 상속하는 익명 클래스 — new 뒤가 Thread 다
new Thread() {
  @Override
  public void run() { /* 쓰레드가 실행할 코드 */ }
};
```

**Day32 가 「주로 필득밧, 로컬변수값, 매개변수값으로 사용한다」로 자리만 적어 둔 것 중 매개변수 자리의 실물이 ① 이다.** 그리고 Day48 은 그 형태에 처음으로 값 판단을 붙인다 — 「구현 객체를 생성할 수 있지만, 익명클래스를 활용하여 생성 할 수도 있으며, **실무에서는 이 방법이 활용도가 높다**」. `Task implements Runnable` 이라는 클래스를 만들어 두면 그 이름을 부르는 곳이 `new Task()` 한 군데뿐이라는 것이 근거다.

**② 는 이 노트에서 처음으로 「가릴 구현이 있는」 익명 클래스다.** 지금까지의 익명 클래스는 비어 있는 추상 메서드를 채웠는데, `Thread.run()` 은 **몸통이 있다**(넘겨받은 `Runnable` 이 있으면 그것을 실행하고, 없으면 아무 일도 하지 않는다). 그래서 ② 는 채우는 것이 아니라 **덮는 것**이고, 아래 「경계와 오해」의 `@Override` 항목이 여기서 실물을 얻는다 → [[method-overriding]]

## 왜 중요한가

**한 곳에서만 쓰이는 구현에 파일과 이름을 만들지 않게 된다.** 반복자는 `iterator()` 가 돌려주는 순간에만 존재하고 밖에서는 `Iterator` 타입으로만 다뤄지므로, `ListIterator` 라는 이름을 아는 코드가 애초에 없었다. **이름은 부를 사람이 있을 때 필요하다** — 부를 사람이 없는 이름을 없앤 것이 이 형태다 → [[nested-class]]

**구현을 「값처럼」 넘길 수 있게 된다.** 익명 클래스는 식이므로 `return` 뒤에도, 매개변수 자리에도, 필드 초기값에도 놓인다. Day32 가 「주로 필득밧, 로컬변수값, 매개변수값으로 사용한다」로 적은 세 자리가 그것이다. 인터페이스 하나를 받는 메서드에 그 자리에서 만든 구현을 바로 넘기는 것이 정렬 비교자·이벤트 처리기의 기본 형태가 된다 → [[polymorphism]] · [[parameter-and-argument]]

**그래서 「전략을 넘긴다」가 클래스를 늘리지 않고 된다.** 이레 전 회차의 `Sorter` 는 정렬 방법마다 클래스를 하나씩 만들었다(`BubbleSort`·`QuickSort`·`MergeSort`). 한 번만 쓰는 정렬이라면 익명 클래스로 그 자리에서 만들 수 있고, **구현이 늘 때 파일이 늘지 않는다** → [[interface]] · [[dispatch-table]]

## 경계와 오해

- **「이름이 없어 new 명령으로 인스턴스를 생성 할 수 없다」는 정반대다 — 익명 클래스는 `new` 로만 만들어진다** — 하루 뒤 회차가 익명 클래스를 두 줄로 요약했는데 첫 줄이 뒤집혀 있다. `new Iterator(){ ... }` 라는 식 자체가 `new` 이고, 그것이 **이 문법의 전부**다. 뜻이 통하게 고치면 「이름이 없어 **나중에 다시** `new` 할 수 없다」다 — 만들 수 없는 것은 인스턴스가 아니라 **두 번째 인스턴스**이고, 정확히 말하면 그 자리에서는 매번 새로 생기지만(`iterator()` 를 부를 때마다 하나) **다른 자리에서 그 클래스를 이름으로 불러 `new` 할 수 없다.** 바로 다음 줄(「클래스를 정의(호출)하는 동시에 인스턴스를 생성」)이 맞는 이해를 담고 있어서, 첫 줄은 「이름으로 생성할 수 없다」를 줄여 쓰다 「`new` 로 생성할 수 없다」가 된 것으로 보인다 → [[instance]]
- **「부모생성자」라는 표기는 클래스를 상속할 때만 맞다** — Day32 의 골격이 `new 부모생성자(매개값,...){}` 인데, **정작 그 노트 자신의 예시는 인터페이스**(`new Iterator(){...}`)다. 인터페이스에는 생성자가 없으므로 그 형태에서 괄호는 언제나 비어 있고, `new Iterator()` 는 생성자 호출이 아니라 **「이 약속을 지키는 이름 없는 클래스를 하나 만들고 그것의 인스턴스를 낸다」**는 뜻이다. 클래스를 상속하는 익명 클래스에서는 그 괄호가 실제로 부모 생성자의 인수 자리이므로 골격은 **둘 중 한쪽만** 적힌 것이다. 「익명 구현 객체」라는 그 노트의 절 제목이 오히려 정확하다 → [[constructor]] · [[interface]]
- **익명 클래스에 생성자를 둘 수 없다 — 그래서 정적 중첩 버전은 익명으로 옮길 수 없다** — 같은 노트의 정적 멤버 클래스 버전은 `public ListIterator(List list)` 로 컬렉션을 받았는데, 익명 클래스에는 그 생성자를 쓸 자리가 없다. 익명 버전이 `AbstractList.this` 로 바깥을 물어보는 쪽을 택한 것이 **선택이 아니라 유일한 길**이었던 것이고, Day32 는 네 방식을 나란히 놓으면서 이 의존 관계를 적지 않았다. 밖에서 값을 받아야 하면 초기화 블록(`{ ... }`)이나 지역변수 포획으로 우회하게 된다 → [[nested-class]] · [[constructor]]
- **익명 클래스 ≠ 람다 — 엿새 뒤 Day36 이 그 조건을 코드로 채운다** — 람다는 **추상메서드가 하나뿐인 인터페이스**에만 쓸 수 있고, 필드를 가질 수 없고, `this` 가 바깥을 가리킨다. Day32 의 `Iterator` 는 `hasNext()` 와 `next()` **둘**이고 `cursor` 라는 상태를 갖는다 — **이 반복자는 람다로 바꿀 수 없다.** Day36 이 로컬 클래스 → 익명 클래스 → 람다를 세 번 나란히 놓으면서 그 사다리에 올린 인터페이스는 전부 추상메서드가 하나인 것들이고, 그래서 **셋이 서로 바꿔 써지는 것처럼 보이는 예제만 남았다.** 「익명 클래스는 람다로 대체된 옛 문법」으로 읽으면 이 반복자가 설명되지 않는다 → [[lambda-expression]] · [[functional-interface]]
- **익명 클래스는 만든 자리에서 바로 부를 수 있고 람다는 못 한다** — `new Intro(){…}.introduce("익명클래스2입니다")` 는 되지만 `(s -> System.out.println(s)).introduce("…")` 는 컴파일 오류다. 익명 클래스는 `new` 뒤에 타입이 적혀 있어 **그 식만으로 타입이 정해지는데**, 람다는 받는 쪽 타입이 있어야 무엇인지 정해진다(`((Intro)(s -> …)).introduce("…")` 로 캐스팅하면 통과한다). Day36 이 v2 형태를 두 번 쓰면서 람다 쪽에서는 그 형태를 만들지 않은 것이 우연이 아니다 — **「참조를 남기지 않고 한 번 쓴다」는 익명 클래스가 더 짧은 유일한 자리**다 → [[lambda-expression]] · [[type-casting]]
- **만든 자리에서 바로 부르는 형태는 「대입」과 같이 쓸 수 없다 — Day48 이 그것을 세 번 어긴다** — `Thread thread = new Thread(new Runnable(){…}).start();` 는 컴파일되지 않는다. `new Thread(…){…}` 까지는 `Thread` 타입인 식이지만 **`.start()` 를 붙이면 식의 타입이 그 메서드의 반환 타입(`void`)이 되기 때문**이다. Day36 의 v2(`new Intro(){…}.introduce("…")`)가 바로 이 형태이고, 거기서는 결과를 **아무 데도 담지 않았기 때문에** 성립했다 — 즉 v2 는 「참조를 남기지 않는」 형태이지 「참조를 만드는 짧은 방법」이 아니다. Day48 은 앞 절에서 `Thread thread = new Thread(task);` 를 맞게 쓴 다음 그 줄 끝에 `.start()` 를 이어 붙였고, 익명 `Runnable` 판·익명 `Thread` 판·상속 판 셋이 모두 같은 모양이 되었다. **그리고 쓰레드에서는 참조를 버리는 대가가 따라온다** — 나중에 `join()`·`interrupt()` 를 부를 상대가 없어진다 → [[thread]] · [[thread-join]] · [[method]]
- **Day48 의 첫 익명 `Runnable` 예시는 `);` 가 빠져 있다** — `Thread task = new Thread(new Runnable(){ … }` 로 끝나 **생성자 괄호가 닫히지 않는다.** 익명 클래스가 식이라는 것을 놓치면 정확히 이렇게 된다 — 몸통의 `}` 로 문장이 끝난 것처럼 보이기 때문이다. Day32 의 「`return` 뒤의 식이 `};` 로 끝나는 것을 놓치기 쉽다」와 같은 실수가 **매개값 자리에서는 `});` 로 나타나는 것**이고, 괄호가 하나 더 있어 더 잘 빠진다. 같은 노트의 뒤쪽 예제들은 `}).start();` 로 맞게 닫아 두었다 → [[thread]]
- **Day36 의 익명 클래스 예제(`Player`)는 컴파일되지 않는다 — 앞 절 두 줄이 따라 들어왔다** — `Player player = new Player(){…};` 로 익명 객체를 대입한 뒤 「//실행하기」 아래에 `Player player = new MyPlayer(); player.play();` 두 줄이 그대로 남아 있는데, 이것은 **바로 위 「1. 일반 클래스로 구현하기」의 마지막 두 줄**이다. 오류가 둘 겹친다 — `player` 가 **같은 블록에서 두 번 선언**되고(`variable player is already defined`), `MyPlayer` 는 앞 예제의 `main` 안에 있던 로컬 클래스라 **이 `main` 에는 존재하지 않는다.** 컴파일 단위 전체가 막히므로 아래 v2 의 `new Player(){…}.play()` 까지 함께 죽어 **「익명클래스1」도 「익명클래스2」도 찍히지 않는다.** 앞 절의 코드를 복사해 인터페이스 선언과 `main` 껍데기만 남기고 고치던 중 실행 두 줄을 지우지 못한 자리이고, 같은 사다리를 세 장에서 반복하므로 **같은 손놀림이 아홉 번 지나간 자리** 중 하나다 → [[variable-scope]] · [[nested-class]]
- **`this` 가 바깥을 가리키지 않는다** — `hasNext()` 안의 `this` 는 익명 인스턴스 자신이다. 그래서 바깥의 `size()` 를 부르려면 `AbstractList.this.size()` 라고 써야 하고, Day32 의 코드가 그렇게 되어 있다. 람다라면 `this` 가 곧 바깥이므로 **같은 코드를 옮길 때 `this` 의 뜻이 조용히 바뀐다** → [[this-reference]]
- **이름이 없는 것과 하나만 있는 것은 다르다** — `iterator()` 를 부를 때마다 새 인스턴스가 생긴다. 클래스는 하나(`AbstractList$1.class`)이고 인스턴스는 호출 횟수만큼이다. 그리고 그것이 맞다 — 반복자는 순회마다 새 커서가 필요하다 → [[instance]] · [[class-file-format]]
- **재사용할 수 없다** — 두 번째 자리에서 같은 구현이 필요해지면 몸통을 복사하는 수밖에 없고, 그때가 이름을 줄 시점이다. **「쉽게 생성한다」의 대가가 「두 번째에 복사한다」**이므로, 쓸 자리가 하나임을 확인한 뒤 고르는 형태다 → [[refactoring]]
- **디버깅과 스택 트레이스에 이름이 없다** — 예외가 나면 `AbstractList$1.next()` 로 찍힌다. 반복자가 셋이 되면 `$1`·`$2`·`$3` 이 되고 어느 것인지 소스를 세어 봐야 한다. **읽는 사람에게 이름을 안 준 대가**를 오류가 났을 때 치른다 → [[exception-handling]]
- **익명 클래스가 「추가)」에서 중첩 클래스의 넷째 종류로 승격한다** — Day32 는 로컬 클래스 뒤에 「추가) 익명구현객체」로 덧붙였고, 하루 뒤 회차는 「4.익명 클래스(anonymous class)」로 **다른 셋과 같은 층의 장**으로 올렸다. 분류가 바뀐 것이 아니라 같은 것을 대등하게 본 것이지만, **그 장에서 코드는 나오지 않는다** — 두 줄만 적힌 채 노트가 잘려 있다. 그래서 이 개념의 예시는 여전히 Day32 의 `new Iterator(){ ... }` 하나뿐이다 → [[nested-class]]
- **Day32 의 「필득밧」은 「필드값」이다** — 오타이고, 가리키는 것은 필드 초기값 자리에 익명 객체를 두는 형태다(`Iterator it = new Iterator(){ ... };`).
- **`@Override` 는 익명 클래스에서도 유효하고, 오히려 여기서 더 필요하다** — 이름이 없어서 「이 몸통이 무엇을 채우는 것인가」가 선언 줄에만 있기 때문이다. 메서드 이름을 잘못 쓰면 추상 메서드가 안 채워져 컴파일 오류가 나므로 인터페이스 쪽은 안전하지만, **클래스를 상속하는 익명 클래스에서는 오타가 「메서드를 하나 더 만든 것」으로 통과한다.** Day48 의 `new Thread(){ public void run(){…} }` 가 그 위험의 실물이다 — 여기서 `run` 을 `ran` 으로 잘못 쓰면 `Thread` 의 원래 `run()` 이 실행되고, 넘겨받은 `Runnable` 이 없으므로 **쓰레드는 정상적으로 뜨고 아무 일도 하지 않고 끝난다.** 오류도 예외도 없다 → [[annotation]] · [[method-overriding]] · [[thread]]
- **익명 클래스 안에서만 `public` 을 빠뜨리기 쉽다 — Day48 의 `void run()`** — 같은 회차가 이름 있는 클래스에서는 `public void run()` 으로 세 번 맞게 썼는데 익명 클래스 판에서만 `void run()` 이 되었다. `Thread.run()` 이 `public` 이므로 **접근을 좁히는 재정의라 컴파일 에러**다. 중괄호 안쪽이 「그 자리에서만 쓰는 지역」처럼 보여서 접근 지정자를 생략해도 될 것 같지만, **재정의 규칙은 익명 클래스에서도 똑같이 걸린다** → [[method-overriding]] · [[access-modifier]]
- **한 번에 하나만 붙일 수 있다** — 익명 클래스는 클래스 하나를 상속하거나 인터페이스 하나를 구현한다. 둘 이상이 필요하면 이름 있는 클래스로 나가야 한다 → [[multiple-inheritance]]
