# 멱등성 (Idempotency)

**같은 요청을 몇 번 보내도 결과가 한 번 보낸 것과 같은 성질.** 두 번 오지 않게 막는 것이 불가능한 자리에서, **두 번 와도 같게** 만드는 쪽으로 문제를 뒤집는 것이다.

## 정의

```text
[멱등하지 않다]  결제 요청 ×2 → 두 번 청구된다
[멱등하다]       결제 요청 ×2 → 첫 번째만 반영, 두 번째는 같은 결과를 돌려준다
```

멱등성에서 같아야 하는 것은 매번의 HTTP 상태 코드나 응답 본문이 아니라 **의도된 최종 상태와 부작용**이다. 첫 번째 `DELETE`가 성공하고 두 번째가 404를 반환하더라도 리소스가 없다는 상태는 같으므로 멱등할 수 있다.

**요청에 「그 사건을 가리키는 이름」을 붙이는 것**이 실제 구현이다. 새로 만드는 값이 아니라 **같은 사건이면 같은 값이 나오는** 것이어야 한다.

| 무엇을 키로 쓰나 | 어디서 |
|---|---|
| `drive_file_id` | 외부 시스템이 준 식별자 |
| `transaction_id` | 결제 사업자가 준 거래 번호 |
| `email` | 시드 데이터의 자연키 |
| UUID | 클라이언트가 논리적 요청마다 생성하는 멱등성 키 |
| 주문 ID + 사용자 ID | 의미와 범위가 드러나는 비즈니스 키 |
| 정규화한 요청의 해시 | 요청 내용 자체로 동일성을 판정할 때 |

결제·주문 API에서는 보통 클라이언트가 이 값을 `Idempotency-Key` 헤더로 전달한다. 같은 작업을 재시도할 때는 같은 키를 유지하고, 새로운 작업을 시작할 때만 새 키를 만든다. 서버는 키와 함께 요청 해시를 보관하여 **같은 키가 다른 요청 본문에 재사용되면 충돌로 거부**한다.

그리고 그 키에 **유일 제약**을 건다 → [[unique-key]]

### 처리 상태와 응답 재생

서버는 멱등성 키마다 `PROCESSING`, `SUCCEEDED`, 필요하면 `FAILED` 같은 처리 상태와 HTTP 상태 코드, 응답 본문, 생성·만료 시각을 저장한다.

1. 완료된 키면 비즈니스 로직을 실행하지 않고 저장된 응답을 반환한다.
2. 처리 중인 키면 처리 중임을 알리거나 제한된 시간 동안 기다린 뒤 다시 조회한다.
3. 새 키면 유일 제약이나 원자적 선점 연산으로 처리 권한을 얻은 요청만 비즈니스 로직을 실행한다.
4. 비즈니스 처리와 응답 저장을 확정한 뒤 처리 권한을 해제한다.

서버가 여러 대면 로컬 메모리가 아니라 Redis나 데이터베이스 같은 공유 저장소가 필요하다. 동시 요청은 [[distributed-lock]]이나 저장소의 원자적 연산으로 제어하고, 저장 레코드의 TTL은 클라이언트의 최대 재시도 기간보다 길게 둔다.

## 사용 예시

```http
POST /payments HTTP/1.1
Content-Type: application/json
Idempotency-Key: 6f5484e8-3dc7-4cb6-8987-e95d65b48767

{"orderId":"ORDER-42","amount":10000}
```

서버가 결제를 저장한 뒤 응답 전송에 실패해도 클라이언트는 같은 키와 본문으로 요청을 다시 보낸다. 서버는 저장해 둔 최초 결제의 상태 코드와 응답을 재생하므로 결제 행과 실제 청구가 다시 생성되지 않는다.

동시 요청을 애플리케이션의 선행 조회만으로 막을 수는 없다. 멱등성 키나 주문 ID에 유일 제약을 두어 쓰는 순간 원자적으로 중복을 거절하고, 패배한 요청은 기존 레코드의 처리 결과를 조회한다.

## 왜 중요한가

**재시도가 필연인 자리가 있다.** 네트워크는 끊기고 webhook은 중복 발송하며 웹소켓은 재연결한다. 서버가 처리를 마친 뒤 응답만 유실되면 클라이언트는 성공 여부를 알 수 없다. **「정확히 한 번」은 대개 만들 수 없어서**, 실무의 답은 「여러 번 와도 한 번처럼」이다 → [[transport-layer]]

**그래서 경로를 이중화할 수 있다.** 같은 결과를 여러 경로로 받아도 안전하다는 것이 보장돼야, 「client가 직접 확인 + webhook」처럼 **둘 다 받는 설계**가 가능해진다.

## 경계와 오해

- **HTTP 메서드의 멱등성 ≠ 구현 전체의 멱등성** — `GET`·`PUT`·`DELETE`는 의미상 멱등하지만 알림·메일·결제 같은 부수 효과가 반복되면 실제 구현은 멱등하지 않다. `POST`·`PATCH`도 서버가 별도 장치를 두면 멱등하게 만들 수 있다 → [[http-method]]
- **읽기는 원래 멱등이다** — 문제는 쓰기, 그리고 쓰기에 딸린 **부작용**(발송·결제·알림)이다. 상태만 같아지고 메일이 두 번 나가면 멱등이 아니다.
- **upsert가 멱등의 전부는 아니다** — 「덮어쓴다」와 「같은 결과를 낸다」는 다르다. 두 번째 요청이 **더 오래된 값**을 들고 오면 upsert는 상태를 되돌린다. 순서를 함께 봐야 한다 → [[optimistic-lock]]
- **애플리케이션 검사만으로는 뚫린다** — 「있으면 건너뛴다」를 코드에서 해도 **동시에 두 개가 들어오면** 둘 다 통과한다. 최종 방어선은 DB의 유일 제약이다 → [[unique-key]] · [[transaction]]
  - 제약을 걸 컬럼이 **nullable**(연결이 없는 행이 대부분)이면 일반 유일 제약이 아니라 **부분(조건부) 유니크 인덱스** — `WHERE 컬럼 IS NOT NULL` — 로 값 있는 행만 잡는다
- **키를 요청마다 새로 만들면 의미가 없다** — UUID를 매번 새로 뽑으면 재시도가 새 사건이 된다. **같은 사건이면 같은 키**여야 한다.
- **같은 키가 같은 요청을 뜻한다고 가정하면 안 된다** — 키와 요청 해시를 함께 저장하고, 다른 본문에 재사용된 키는 충돌로 거부해야 한다.
- **TTL은 단순한 저장 공간 설정이 아니다** — 재시도 창보다 짧으면 늦게 도착한 중복 요청이 새 작업이 된다. 반대로 영구적인 중복 방지가 필요하면 TTL 레코드와 별도로 비즈니스 키의 유일성을 유지해야 한다.
- **락만으로 결과의 원자성이 생기지는 않는다** — 결제와 멱등성 응답 저장이 서로 다른 시스템에 있으면 하나만 성공할 수 있다. 가능한 작업은 같은 트랜잭션으로 묶고, 외부 호출은 상태 조회·아웃박스·상태 머신으로 복구 가능하게 만든다.
- **재시도 자체가 부하를 늘린다** — 멱등하다고 무한정 다시 보내면 상대를 더 밀어붙인다. 제한된 횟수와 [[exponential-backoff]]를 함께 사용한다.
