# 원격 호출 (RPC · Stub/Skeleton)

**다른 컴퓨터의 객체에게 일을 시키는 것을, 내 안의 객체에게 메서드를 부르는 것처럼 보이게 만드는 구조.** 양쪽에 대리인을 하나씩 세우고 그 둘이 소켓과 프로토콜을 맡는다 — Day45 가 그 대리인을 「브로커」라 부른다.

## 정의

Day45 가 네 역할에 이름을 붙였다.

| 역할 | 어디 있나 | 하는 일 (필기의 표현) |
|---|---|---|
| ORB (Object Request Broker) | 양쪽 | 「서버/클라이언트의 결과를 송수신」 |
| Stub | 클라이언트 | 「클라이언트 측 브로커」 |
| Skeleton | 서버 | 「서버 측 브로커」 |
| Remote Object | 서버 | 「실제 데이터를 처리하는 업무를 수행하고 결과를 브로커에 전달」 |

**Stub 이 핵심이고, 그것이 성립하는 조건은 하나다 — Stub 이 Remote Object 와 같은 인터페이스를 구현한다.** 그래야 부르는 코드가 둘을 구별하지 못한다. 호출 한 줄이 실제로 지나는 길은 이렇게 늘어난다.

```text
클라이언트 코드 → Stub → (인자를 바이트로) → 소켓 → Skeleton → (바이트를 인자로) → Remote Object
                                                                              ↓
클라이언트 코드 ← Stub ← (바이트를 결과로) ← 소켓 ← Skeleton ← (결과를 바이트로) ←
```

**여섯 칸 중 다섯 칸이 대리인의 몫이고, 부르는 쪽에 남는 것은 첫 칸 하나다.** Day44 의 옵저버에서 「바깥에서 부르는 것은 첫 줄 하나」였던 것과 같은 모양인데, 여기서 감춰지는 것은 호출의 순서가 아니라 **호출이 기계를 건너간다는 사실**이다.

Stub 이 하는 일에는 이미 배운 이름이 붙어 있다. **같은 인터페이스를 구현하고 안쪽 하나에게 위임하는 것** — Day42 가 「데코레이터 ≠ 프록시」로 갈라 놓으면서 「원격 호출」을 프록시의 용도로 적었던 그 프록시가 이것이다. 데코레이터가 **동작을 더하려고** 낀다면 Stub 은 **거리를 감추려고** 낀다 → [[decorator-pattern]] · [[interface]] · [[polymorphism]]

인자와 결과를 바이트로 바꾸는 칸은 Day39 에 배운 것이 그대로 쓰인다 → [[serialization]]

## 왜 중요한가

**소켓 코드가 한 곳에 모인다.** 이 구조가 없으면 서버에 일을 시키는 모든 자리마다 스트림을 꺼내고 형식을 맞추고 응답을 파싱하는 코드가 붙는다. 대리인을 세우면 그 코드가 Stub 안에 한 번만 있고, 나머지는 메서드 호출로 보인다 — **명령 클래스 스무 개를 고치는 일과 클래스 하나를 만드는 일의 차이**다 → [[socket]] · [[cohesion]]

**프로토콜이 다시 컴파일러의 검사 안으로 들어온다.** 양쪽이 **같은 인터페이스 파일**을 공유하면 메서드 이름과 인자 타입이 컴파일 시점에 맞춰진다. 소켓에 문자열을 직접 실어 보낼 때 잃어버렸던 것을 되찾는 것이고, 그것이 이 구조가 사는 가장 큰 이유다. 다만 **되찾는 범위는 인터페이스가 같은 파일일 때까지**이고, 한쪽만 다시 배포하면 다시 어긋난다 → [[network-protocol]] · [[interface]]

**클라이언트 코드가 서버의 위치를 모르게 된다.** IP·포트가 Stub 안에 있으므로 서버를 옮기는 일이 업무 코드와 무관해진다 → [[ip-address]] · [[coupling]]

## 경계와 오해

- **Stub(원격 대리인) ≠ Stub(테스트 대역)** — 같은 낱말이 두 뜻으로 쓰이는데 **방향이 반대다.** 여기서의 Stub 은 호출을 **진짜 객체에게 실어 보내는** 것이고, 테스트에서 말하는 stub 은 진짜를 부르지 않고 **정해진 값을 돌려주는** 가짜다. 둘 다 「같은 인터페이스를 구현한 대역」이라 모양이 겹쳐서 구별이 안 되는데, 기준은 **안쪽에 진짜가 있는가**다. 검색할 때 섞여 나오는 대표적인 자리다.
- **ORB·Skeleton 은 지금 자바에서 쓰지 않는 낱말이다 — 2024년 기준으로 다시 쓰면** ORB 는 CORBA 의 용어이고 자바의 대응물은 RMI(Remote Method Invocation)다. 그리고 **Skeleton 은 JDK 1.2 에서 없어졌다** — 그 뒤로는 서버 쪽이 리플렉션으로 호출을 넘겨 주므로 클래스마다 Skeleton 을 만들지 않는다(CORBA 자체도 Java 11 에서 표준 라이브러리에서 빠졌다). 그러므로 **필기의 네 칸 그림은 개념의 지도이지 지금 쓰는 API 의 목록이 아니다.** 「클라이언트 쪽 대리인 / 서버 쪽 받는 자리」로 읽으면 gRPC·REST 클라이언트에도 그대로 대응되므로 낱말이 사라져도 구조는 남는다.
- **Stub·Skeleton 은 손으로 쓰는 클래스가 아니다** — 인터페이스를 보고 **생성되는** 코드다(RMI 의 `rmic`, gRPC 의 코드 생성기). 그래서 「클래스 넷을 만든다」로 읽으면 실제 작업량을 잘못 잡는다 — 사람이 쓰는 것은 **인터페이스와 Remote Object 둘**이다.
- **원격 호출 ≠ 지역 호출 — 그리고 문법에서 이미 갈린다** — 「메서드 호출처럼 보인다」가 이 구조의 목적이지만 완전히 같아지지는 않는다. RMI 의 원격 인터페이스는 모든 메서드가 `RemoteException` 을 던지도록 선언해야 하고, 그것이 **checked 예외**라 부르는 쪽이 `try`/`catch` 를 쓰게 된다. **「투명하다」던 것이 시그니처에서 티가 나는 셈**이고, 이것은 결함이 아니라 **지역 호출에는 없던 실패가 실제로 존재한다**는 사실을 문법이 강제로 드러낸 것이다 → [[exception-handling]]
- **실패의 종류가 하나 늘어난다 — 「됐는지 안 됐는지 모르는」 실패다** — 지역 호출은 성공하거나 예외를 던진다. 원격 호출은 **요청은 도착했는데 응답이 오는 길에 끊기는** 경우가 있어서, 예외를 받은 쪽이 서버가 그 일을 했는지 알 수 없다. 그래서 「실패했으니 다시 보내자」가 **같은 등록을 두 번 하는** 일이 될 수 있고, 재시도가 안전한 연산인지를 따로 따져야 한다 → [[crud]]
- **객체를 넘기면 참조가 아니라 복사가 간다** — 지역 호출에서 인자로 넘긴 객체는 양쪽이 **같은 인스턴스**를 만진다. 원격에서는 직렬화된 복사본이 가므로 **받은 쪽이 그 안을 고쳐도 내 것은 그대로다.** Day44 의 옵저버가 밀어 넣은 `Weather` 하나를 화면 셋이 공유했던 구조는 **원격으로 옮기면 성립하지 않는다** — 같은 코드가 한 프로세스에서는 공유이고 두 프로세스에서는 복사다. 「호출처럼 보이게」의 대가 중 가장 조용한 것이 이것이고, [[defensive-copy]] 가 걱정하던 문제가 여기서는 공짜로 해결되면서 대신 **공유를 전제한 코드가 조용히 망가진다** → [[object-reference]] · [[serialization]] · [[call-by-value]]
- **호출 한 줄의 값이 몇 천 배 다르다** — 지역 메서드 호출은 나노초 단위이고 원격 호출은 밀리초 단위다. 그래서 **반복문 안에 원격 호출을 넣는 코드**가 이 구조에서 가장 흔한 성능 사고가 된다(회원 100명을 하나씩 조회하는 형태). 지역 호출과 구별되지 않게 만든 것이 목적인데 **그 성공이 이 사고의 원인**이라, 「목록을 한 번에 받아 오는 메서드」를 인터페이스에 따로 두는 설계가 필요해진다 → [[interface-segregation-principle]]
- **「결과를 송수신」은 절반이다** — 필기의 ORB 설명이 결과 쪽만 적었는데, 브로커는 **요청도 나른다**(어느 객체의 어느 메서드를 어떤 인자로 부르라는 것). 결과만 나르는 것으로 읽으면 「어느 메서드인지」를 무엇이 실어 보내는지가 설명되지 않고, 그 부분이 바로 프로토콜에서 정할 항목이다 → [[network-protocol]]
- **Day45 는 이 구조를 그림으로만 보고 쓰지 않는다** — 같은 노트의 myApp 변경은 ORB 없이 소켓을 직접 쓰는 방향이다. **개념을 배운 회차와 그 개념을 쓰는 회차가 다르다**는 것이고, 그래서 앞의 「소켓 코드가 한 곳에 모인다」는 이 회차의 코드에서 아직 얻어지지 않은 이득이다 → [[client-server-model]]

## 출처

- [[2024-07-30-Day45]] — 「APP에서의 통신과정은 통신 객체를 만들어서 통신을 한다」에 이어 ORB·Stub·Skeleton·Remote Object 네 역할을 그림과 함께 정리했다. 「Stub : 클라이언트 측 브로커 / Skeleton : 서버 측 브로커」로 **양쪽에 대리인을 하나씩 세운다**는 뼈대를 정확히 잡았고, Remote Object 를 「실제 업무를 수행하고 결과를 브로커에 전달」로 적어 업무 코드가 통신을 모른다는 것까지 담았다. 다만 ORB 를 「결과를 송수신」으로만 적어 **요청을 나르는 쪽이 빠졌고**, Stub 이 Remote Object 와 같은 인터페이스를 구현한다는 성립 조건은 적히지 않았다. 낱말은 CORBA 세대의 것이라 2024년 자바 기준으로는 RMI 가 대응물이고 **Skeleton 은 JDK 1.2 에서 이미 없어진 역할**이다. 이 절은 그림으로 끝나고, 같은 노트의 myApp 변경은 이 구조 없이 소켓을 직접 쓰는 쪽으로 간다
