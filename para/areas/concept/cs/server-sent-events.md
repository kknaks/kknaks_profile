# SSE (Server-Sent Events)

**연결을 한 번 열어 두고 서버가 클라이언트에게 계속 밀어 보내는 단방향 통신.** 클라이언트가 물어보는 것이 아니라 **서버가 생길 때마다 보낸다.**

## 정의

```
클라이언트 ──요청 한 번──▶ 서버
          ◀──── 이벤트 ────      (새 것이 생길 때)
          ◀──── 이벤트 ────
          ◀──── 이벤트 ────      연결은 계속 열려 있다
```

**방향이 하나뿐**이다 — 서버 → 클라이언트. 클라이언트가 무언가를 보내려면 **평범한 HTTP 요청을 따로** 해야 한다.

[[polling]] 과 갈리는 축이 「누가 시작하는가」다.

| | 누가 말을 거나 | 연결 | 방향 |
|---|---|---|---|
| 폴링 | 클라이언트가 주기적으로 | 요청마다 새로 | 요청↔응답 |
| SSE | **서버가 생길 때** | **하나를 계속** | 서버 → 클라이언트 |

## 왜 중요한가

**헛걸음이 사라진다.** 폴링은 새 것이 없어도 요청이 오가지만, SSE 는 **보낼 것이 있을 때만** 데이터가 흐른다. 지연도 「다음 요청까지」가 아니라 **생기는 즉시**다 → [[polling]]

**그리고 여전히 HTTP 다.** 별도의 프로토콜이 아니라 응답을 끊지 않고 이어 보내는 방식이라, 기존 서버·인증·방화벽을 그대로 쓴다 — 이것이 양방향 연결과 갈리는 실질적 이점이다 → [[http-message]] · [[socket]]

## 재연결의 실제 동작 — `EventSource` 가 해 주지 않는 것

브라우저 `EventSource` 의 자동 재연결은 **네트워크가 끊긴 경우**에만 돈다. 다시 붙는 길을 화면이 직접 쥐어야 하는 자리가 넷 있다.

1. **비-200 이면 영구히 닫힌다** — 응답이 401·502 같은 비-200 이거나 `Content-Type` 이 `text/event-stream` 이 아니면 `readyState = CLOSED` 로 끝나고 다시 시도하지 않는다. `onerror` 에는 **상태 코드가 없다** — 「로그인이 풀렸다」 와 「서버가 재시작 중이다」 를 이벤트만으로는 못 가른다
2. **그래서 가르는 것은 다른 요청이다** — `onerror` 뒤에 세션 확인(`/api/auth/me` 같은 가벼운 인증 요청)을 한 번 부른다. 401 이면 로그인 화면으로, 200 이면 서버 쪽 문제이니 **화면이 직접 백오프로 새 `EventSource` 를 연다** → [[exponential-backoff]]
3. **새 인스턴스에는 `Last-Event-ID` 가 없다** — 그 헤더는 같은 인스턴스가 자동 재연결할 때만 붙는다. 화면이 새로 열면 서버는 어디서부터인지 모른다 → 마지막으로 받은 id 를 **쿼리로**(`?last_event_id=`) 넘긴다
4. **멈춤 조건은 「인증 200 + 스트림 실패」만 센다** — 「N회 실패하면 멈춤」 을 단순히 세면 서버 장애 동안에도 횟수가 차서 **앱이 조용히 실시간을 놓는다.** 세션은 살아 있는데 스트림만 실패하는 경우만 세야 한다

다시 붙은 뒤 놓친 것을 채우는 쪽에도 두 장치가 필요하다(사건을 보내는 경우 — 스냅샷이면 아래 절).

- **「둘째 이후 ready = 다시 읽기」** — 스트림이 열릴 때마다 서버가 `ready` 를 보내고, 화면은 **첫 번째가 아닌 ready 를 받으면 목록을 다시 읽는다.** 이어받을 id 가 없거나 서버가 보관 범위를 넘었을 때의 바닥이다. 이게 빠지면 커서 없이 「붙으면 끝」 이던 WS 보다 **오히려 후퇴한다**
- **겹침 창** — 사건 id 가 순번(시퀀스)이면 **발급 순서와 커밋 순서가 다를 수 있다** — 먼저 받은 번호의 트랜잭션이 늦게 커밋되면, 「마지막 id 이후」 로 이어받을 때 그 행이 빠진다. 이어받기를 「마지막 id 이후」 가 아니라 **마지막 받은 시각에서 일정 창(예: 60초)을 겹쳐** 다시 보내고, 화면이 이미 가진 id 를 거른다

## 사건 대신 전체 스냅샷을 보낼 때

보낼 것을 **바뀐 것(사건)** 이 아니라 **지금 화면 전체(스냅샷)** 로 잡으면 위의 이어받기 장치가 통째로 사라진다. 명동 PoC v2 시술 현황판은 현황판 · 의국 화면 · 앱이 같은 `board` 이벤트 하나를 받는다.

- **고르는 조건 = 스냅샷이 작다** — 한 지점 · 한 구역 · 오늘 일정(하루 HAR 15건 ≈ 32KB). 바뀐 것만 보내면 합치기 · 순서 · 빠진 사건 복구가 front 와 앱 **양쪽에** 생긴다. 스냅샷이면 받는 쪽은 통째로 바꾸기만 하고, 규칙 계산(`canStart` 등)이 back 한 곳에 남는다
- **첫 접속 = 첫 화면** — 연결되면 바로 스냅샷 1개. 따로 목록 GET 을 안 부르니 첫 로딩과 갱신이 같은 길이다. 재연결도 첫 접속과 같아 `Last-Event-ID` 가 필요 없다
- **`version` 하나로 순서** — 보낼 때마다 1 씩 느는 정수, 받는 쪽은 가진 것 이하를 버린다. 다만 **새 연결의 첫 스냅샷은 무조건 받는다** — 서버 재시작이면 0 부터 다시 센다
- **값이 시간으로 바뀌면 주기 발행** — 「확인이 필요(20분)」 처럼 사건 없이 시간 경과로 바뀌는 표시가 있으면, 변화가 없어도 10초마다 보낸다. 사건이 있을 때만 보내면 그 표시가 안 바뀐다
- **조작 응답은 `{ok}` 만** — 화면은 뒤따르는 스냅샷으로 바뀐다. 갱신 길이 하나다

`EventSource` 밖에서 받는 쪽과 배포에서 막힌 자리:

- **토큰이 쿼리로 간다** — `EventSource` 는 헤더를 못 싣는다 → `?token=`. 그러면 **접근 로그에 토큰이 남는다**(리뷰에서 잡힘) → 서버 접근 로그에서 쿼리를 지우는 필터, ingress 로그도 같은 기준
- **Flutter 에는 `EventSource` 가 없다** — HTTP 스트림 요청 + 직접 만든 파서(빈 줄 = 이벤트 끝 · `data:` 여러 줄 잇기 · `:` 주석 무시). 서버 ping 15초에 맞춰 **45초 동안 한 바이트도 안 오면 끊긴 것으로 보고** 다시 연결한다 — TCP 가 조용히 죽는 것을 스트림 요청은 알려 주지 않는다. 앱이 백그라운드로 가면 닫고 돌아오면 다시 연다
- **ingress 가 모으면 실시간이 아니다** — 프록시 버퍼링을 끄고 읽기 timeout 을 길게(3600s). 아래 「프록시가 응답을 모아 버리면」 의 실제 설정

## 스트림이 「기기」 를 실어 나를 때 — 붙는 때는 로그인이 아니라 앱 시작 · 복귀

스트림이 사용자만이 아니라 **기기**(푸시 토큰으로 등록한 행 id)를 쿼리로 싣고, 서버가 그 연결로 「이 기기가 지금 붙어 있다」 를 판정하면 연결 순서가 결과를 바꾼다. 전체현황판 앱의 웹 → 폰 「띄우기」 는 서버가 `online(deviceId)` 면 SSE 로, 아니면 푸시로 보낸다.

- **저장된 id 로 먼저 붙으면 「기기 없는 연결」 이 된다** — 앱 업데이트 뒤 저장된 로그인으로 켜면, 앱이 등록 전에 옛 `deviceId` 로 스트림을 연다. 서버가 그 id 를 이 계정 기기로 못 알아보면 연결은 **기기 없이** 붙고, 앱에는 아무 신호가 없다(스트림은 열려 있으니 끊김 감시도 안 걸린다)
- **「id 가 안 바뀌었으니 그대로」 가 구멍이다** — 이어서 등록이 같은 id 를 돌려주면 「바뀜 없음」 으로 보고 다시 안 열었다 → 그 세션 내내 기기 앞 이벤트를 못 받는다. 다시 로그인하면 됐던 것이 단서였다(로그인 경로만 등록 → 연결 순서가 맞았다)
- **고침 = 시작 · 앞으로 올 때마다 다시 등록 → 등록 응답 id 로 한 번 다시 연다(같은 id 여도)** — 등록과 연결을 「로그인 이벤트」 에 걸지 않고 **앱 시작 · 복귀(생명주기)** 에 건다. 등록이 겹치면 늦게 온 옛 응답이 id 를 되돌리므로 등록은 한 번에 하나씩
- **서버가 정상이면 서버 로그로는 안 보인다** — 「보냄 1 · 실패 0」 이었다. 연결이 기기로 붙었는지는 연결 때만 갱신되는 `last_seen_at` 이 안 바뀐 것으로 알았다. 연결이 `deviceId` 를 받았는데 기기를 못 찾은 경우를 로그 한 줄로 남기는 것이 다음 판의 몫
- **앞에서 받은 푸시는 앱이 받는다** — iOS 는 앱이 앞일 때 원격 푸시를 `willPresent` 로 앱에 넘기고, 앱이 배너만 띄우면 **눌러야** 열린다. 스트림이 빠진 자리를 푸시가 메우려면 앞 푸시도 누른 것과 같은 길로 넘긴다
- **SSE 를 골랐는데 끊겨 있으면 둘 다 놓친다** — 서버는 끊긴 연결을 다음 쓰기(ping)에서야 안다. 폰이 잠긴 사이 `online` 이 참으로 남아 푸시를 건너뛸 수 있다 → 「SSE + 푸시 둘 다」 는 열린 질문으로 남았다

## 경계와 오해

- **단방향이라는 것이 제약이자 단순함이다** — 채팅처럼 **양쪽이 보내야 하는** 것에는 반쪽만 맞는다. 필기가 「클라이언트가 서버에게 요청을 보내는 방식이 아니」라고 적은 그 성질 때문에, 보내기는 따로 만들어야 한다
- **필기의 「요청 간격을 조절할 수 없다」는 단점이 아니다** — 조절할 간격이 **애초에 없는 것**이다. 폴링의 어휘로 SSE 를 설명하려다 생긴 문장이고, 실제 제약은 「클라이언트가 보낼 수 없다」쪽이다
- **연결이 사용자 수만큼 열린다** — 각 클라이언트가 연결 하나를 계속 붙들므로, 동시 접속자가 곧 열린 연결 수다. 쓰레드당 요청 모델에서는 이것이 한계가 된다 → [[thread]] · [[connection-pool-sizing-formula]]
- **끊기면 다시 붙어야 한다** — 브라우저가 자동 재연결을 하지만, **끊긴 동안 놓친 것**은 따로 챙겨야 한다. 마지막으로 받은 이벤트 id 를 보내 이어받는 장치가 그래서 있다 → [[polling]] 의 커서와 같은 문제다. 다만 **「자동 재연결」 은 생각보다 좁다** — 아래 절
- **프록시가 응답을 모아 버리면 안 나간다** — 중간의 서버가 응답을 버퍼링하면 이벤트가 뭉쳐서 도착한다. 「코드는 맞는데 실시간이 아닌」 흔한 원인이다
- **새 연결 대신 기존 허브에 이벤트 추가**(cc-prototype 내부 채팅) — 메신저라고 WebSocket 을 새로 열지 않고 계정 단위 SSE 허브(`send_to_account`)에 `chat_*` 이벤트 6종을 얹었다. 웹은 `board` 만 들어 깨지지 않는다. 앱은 백그라운드에서 SSE 를 닫으므로 앞으로 올 때 REST `since` 로 메워야 한다 · [[2026-10-30-internal-chat]]
