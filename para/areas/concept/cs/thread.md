# 쓰레드 (Thread)

**한 프로그램 안에서 따로 흐르는 실행 흐름 하나.** Day48 의 정의가 「쓰레드 : 하나의 코드 실행흐름을 말한다」이고, 그것이 둘 이상이면 「멀티쓰레드 : 두가지 이상의 코드 실행 흐름」이다. 지금까지 배운 모든 프로그램에는 흐름이 하나뿐이었고 — `main()` 부터 `return` 까지 — **이 개념이 그 「하나」를 늘릴 수 있는 것으로 바꾼다.**

## 정의

Day48 은 세 낱말을 나란히 놓는다. **셋이 같은 층이 아니다.**

| 낱말 | Day48 의 정의 | 무엇인가 |
|---|---|---|
| 멀티태스킹 | 두가지 이상의 작업을 동시에 처리하는 것 | **목적** |
| 멀티프로세스 | 운영체제가 프로세스를 여럿 생성해 처리하는 것 | 수단 ① → [[process]] |
| 멀티쓰레드 | 두가지 이상의 코드 실행 흐름 | 수단 ② — 프로세스 **안**에서 |

`main()` 을 실행하면 이미 쓰레드 하나가 돌고 있다(**메인 쓰레드**). 그 안에서 흐름을 더 만드는 것이 이 문법이고, Day48 은 두 형태를 적는다 → [[main-method]]

```java
// ① 할 일을 Runnable 로 만들어 넘긴다
class Task implements Runnable {
  @Override
  public void run() { /* 쓰레드가 실행할 코드 */ }
}
Runnable task = new Task();
Thread thread = new Thread(task);

// ② Thread 를 상속해 run() 을 덮는다
class WorkerThread extends Thread {
  @Override
  public void run() { /* 쓰레드가 실행할 코드 */ }
}
Thread workerThread = new WorkerThread();
```

**어느 쪽이든 시작은 `start()` 하나다.**

```java
thread.start();
```

`Runnable` 은 추상메서드가 `void run()` 하나뿐인 인터페이스여서 익명 클래스로도 람다로도 그 자리에서 만들 수 있고, Day48 은 익명 클래스 쪽을 「실무에서는 이 방법이 활용도가 높다」로 적는다 → [[anonymous-class]] · [[functional-interface]]

**두 형태의 차이는 「무엇을 물려받나」다.** ① 은 할 일만 넘기므로 `Task` 가 다른 클래스를 상속할 수 있고, ② 는 `Thread` 자리를 써 버려 상속 칸이 남지 않는다. 그래서 실무의 기본형은 ① 이다 → [[inheritance]]

### 소제목만 남은 넷 — 양보 · 동기화 · 안전종료 · 데몬

Day48 은 뒤쪽 네 절을 **제목과 메서드 이름만 적고 비워 두었다.** 무엇이 들어갈 자리인지만 여기 적어 둔다.

| 비어 있는 절 | 무엇을 하는 것인가 | 왜 필요해지나 |
|---|---|---|
| 양보 — `yield` | 「지금 CPU 를 내가 안 쓰겠다」고 스케줄러에 **제안**한다 | 강제가 아니다. 곧바로 다시 자기가 받아도 규칙 위반이 아니라서 실무에서 거의 안 쓴다 |
| 동기화 — `synchronized`·`wait()`·`notify()` | 공유 자원을 **한 번에 한 쓰레드만** 만지게 잠근다. `wait()` 는 그 잠금을 놓고 기다리다 `notify()` 로 깨어난다 | 아래 「왜 중요한가」의 세 번째 — 흐름이 둘이 되면 값 하나를 두 흐름이 동시에 고친다 |
| 안전종료 — 조건 · `interrupt()` | **바깥에서 죽이지 않고** 「끝내라」고 표시만 하고 쓰레드가 스스로 나가게 한다 | 남이 강제로 죽이면(`Thread.stop()`) 잠금을 든 채 죽어 남은 값이 반쪽이 된다. 그래서 그 메서드는 폐기되었다 |
| 데몬쓰레드 | `setDaemon(true)` 로 표시한 쓰레드. **JVM 이 그 끝을 기다려 주지 않는다** | 아래 「경계와 오해」의 「메인쓰레드는 종료되지 않는다」 항목이 이것의 반대쪽이다 |

**`interrupt()` 는 이 노트 안에서 이미 망가져 있다.** 안전종료가 쓸 도구는 「자고 있는 쓰레드를 예외로 깨우는 것」인데, Day48 의 모든 `catch` 가 비어 있어 그 신호를 삼킨다 → [[exception-handling]] · [[thread-state]]

## 사용 예시

Day48 은 같은 프로그램을 **쓰레드 없이 한 번, 쓰레드로 한 번** 짠다. 비프음 5회와 「띵」 5회를 각각 0.5초 간격으로 낸다.

```java
public class BeepPrintExample {
  public static void main(String[] args) {
    Toolkit toolkit = Toolkit.getDefaultToolkit();
    for(int i=0; i<5; i++) {
      toolkit.beep();
      try { Thread.sleep(500); } catch(Exception e) {}
    }
    for(int i=0; i<5; i++) {
      System.out.println("띵");
      try { Thread.sleep(500); } catch(Exception e) {}
    }
  }
}
```

**두 루프가 순서대로 돈다 — 비프음이 다 끝난 뒤에 「띵」이 시작한다.** 필기의 표현이 「메인쓰레드만 사용하면, 다음 작업은 순차적으로 실행된다」다. 걸리는 시간은 2.5초 + 2.5초다.

앞 루프를 쓰레드에게 넘기면 둘이 겹친다.

```java
Thread thread = new Thread(new Runnable() {
  @Override
  public void run() {
    Toolkit toolkit = new Toolkit();
    for(int i=0; i<5; i++) {
      toolkit.beep();
      try { Thread.sleep(500); } catch(Exception e) {}
    }
  }
}).start();

for(int i=0; i<5; i++) {
  System.out.println("띵");
  try { Thread.sleep(500); } catch(Exception e) {}
}
```

**`start()` 가 돌아온 다음 줄이 곧바로 실행되는 것이 이 문법의 전부다.** 부른 쪽은 `run()` 이 끝나기를 기다리지 않는다 — 그래서 아래 `for` 문이 비프음과 같이 돈다. 걸리는 시간이 5초에서 2.5초가 된다.

같은 것을 상속 형태로 바꾼 것도 나란히 있다(`new Thread(){ ... }.start()`). **다만 이 세 코드는 그대로는 컴파일되지 않는다** — `.start()` 를 대입하고 `new Toolkit()` 으로 추상 클래스를 만들고 있다(아래 「경계와 오해」).

쓰레드에는 이름이 붙어 있고 바꿀 수 있다. 기본값은 `Thread-0`·`Thread-1` 처럼 붙는다.

```java
Thread thread = new Thread();
thread.setName("작업쓰레드");
System.out.println(thread.getName());
```

### 17일 뒤 Day61 — 이 문법이 처음 일을 한다

Day48 의 예제는 비프음과 「띵」이었다. Day61 이 같은 문법을 서버에 붙인다.

```java
private void service(Socket socket) {
    new Thread(() -> {
      try {
        Prompt prompt = new Prompt(socket, appCtx);
        // 이 접속과의 대화 전부
      } catch (Exception e) {
        System.out.println("실행 오류!");
        e.printStackTrace();
      }
    }).start();
  }
```

**Day48 이 세 번 틀렸던 그 한 줄이 여기서는 맞다.** `Thread t = new Thread(…).start();` 로 `void` 를 대입하던 것이 `new Thread(…).start();` 가 됐고, 익명 클래스 대신 람다다 — 그 사이 회차에서 `Runnable` 이 함수형 인터페이스라는 것이 손에 익은 결과다 → [[lambda-expression]] · [[functional-interface]]

**그리고 참조를 버린 대가가 이번에는 실제로 온다.** Day48 노트가 「참조를 버리면 나중에 `join()`·`interrupt()` 를 부를 상대가 없어진다」고 적어 둔 그 자리다 — 서버는 접속 쓰레드를 하나도 손에 들고 있지 않으므로 **특정 접속을 끊거나 종료를 기다릴 방법이 없다.** 같은 노트의 종료 리스너 블록이 도달할 수 없는 코드로 남은 것과 한 짝이다 → [[thread-join]] · [[socket]]

**쓰레드가 얼마나 생기는지는 정해져 있지 않다.** 접속마다 하나이므로 100명이 붙으면 100개다. Day48 이 「병렬 작업의 갯수를 고려하여 쓰레드를 생성하여야 한다」로 적어 둔 것이 **여기서 지켜지지 않는데**, 그것을 지키는 도구(쓰레드 풀)는 이 회차에 없다 → [[universal-scalability-law]] · [[queue]]

## 왜 중요한가

**기다리는 시간을 겹칠 수 있다.** 위 예제가 5초에서 2.5초가 되는 것은 계산이 빨라져서가 아니라 **두 `sleep()` 이 같은 2.5초를 쓰기 때문**이다. 파일을 읽는 동안, 응답을 기다리는 동안, 사용자가 입력하는 동안 — 프로그램이 아무것도 안 하고 서 있던 시간이 전부 이 자리다 → [[io-stream]]

**엿새 전에 막혔던 서버가 여기서 풀린다 — 그리고 17일 뒤에 실제로 쓰인다.** Day45·Day46 의 서버는 `accept()` 한 번 → 통신 → 끝이었고, `while(true)` 로 감싸도 **한 클라이언트와 대화하는 동안 다음 접속을 받지 못한다**는 문제가 그대로 남았다. 답이 「접속마다 쓰레드를 하나 준다」이고, 그 문법이 Day48 에 온다 — 소켓 회차에서 「다음 문제」로 적어 둔 것이 6일 뒤 도구를 얻은 것이다. **도구를 쓴 것은 Day61 이다**(위 절) — `while (true) { service(serverSocket.accept()); }` 와 `service()` 안의 `new Thread` 가 그것이고, **문제를 만난 날·도구를 얻은 날·실제로 붙인 날이 셋 다 다르다** → [[socket]] · [[client-server-model]] · [[queue]]

**대신 「값 하나」가 위험해진다.** 흐름이 하나였을 때는 어떤 필드도 내가 보는 사이에 바뀌지 않았다. 흐름이 둘이 되면 **`count++` 한 줄조차 안전하지 않다** — 읽고·더하고·쓰는 세 단계라 둘이 같은 값을 읽어 하나가 사라진다. Day48 이 「쓰레드 동기화」를 제목만 남긴 자리가 정확히 이 문제이고, 지금까지 배운 코드 중 실제로 위험해지는 것이 이미 있다(일련번호를 붙이는 `++seqNo`) → [[increment-operator]] · [[jvm-stack]]

**그리고 그 빈 절에 들어갈 답이 둘인데, 18일 뒤 Day62 가 고르는 것은 뒤쪽이다.** 하나는 **순서를 정하는 것**(`synchronized` — 하나의 값을 여럿이 차례로 쓴다), 다른 하나는 **나눠 갖는 것**(값을 쓰레드마다 따로 둔다). Day62 는 `SqlSession` 을 쓰레드마다 갖게 해서 문제를 없애는데, 그 선택이 성능 때문이 아니다 — **세션을 잠그면 대기만 생기고 커밋 경계는 여전히 하나**여서 남의 트랜잭션이 섞이는 문제가 그대로 남는다. **「공유 값이 위험하다」의 답이 언제나 잠금은 아니라는 것**이 이 필기에서 처음 나오는 자리다 → [[thread-local]] · [[transaction]] · [[sql-session]]

**그리고 「몇 개를 만들 것인가」가 결정 사항이 된다.** 필기가 「병렬 작업의 갯수를 고려하여 쓰레드를 생성하여야 한다」로 적고 이유는 적지 않았는데, 쓰레드마다 스택이 따로 할당되고(기본 1MB 안팎) 수가 늘면 CPU 가 갈아타는 비용과 잠금 경쟁이 함께 늘어난다. **늘려도 처리량이 안 늘고 어느 지점부터 줄어드는** 축이 여기서 시작한다 → [[universal-scalability-law]] · [[little-law]]

## 경계와 오해

- **Day61 의 서버는 접속마다 쓰레드를 붙이면서 `SqlSession` 을 한 벌만 쓴다 — 「필드는 안전하지 않다」의 실물이 여기 있다 (Day61 기준. 하루 뒤에 고쳐진다)** — `appCtx.getAttribute("userDao")` 는 **모든 접속이 같은 DAO 프록시**를 받는다는 뜻이고, 그 프록시의 핸들러(`DaoFactory`)가 `sqlSession` 을 필드로 들고 있다. [[mybatis]] 노트가 정리한 세 객체의 수명이 「`SqlSessionFactory` 는 앱에 하나, `SqlSession` 은 **작업마다 하나** — 커밋 경계와 같다」인데, 여기서는 **접속 수십 개가 세션 하나를 함께 쓴다.** 결과가 둘이다: ① `SqlSession` 은 쓰레드 안전하지 않아 두 접속이 동시에 문장을 보내면 결과가 섞이거나 예외가 나고, ② `commit()`·`rollback()` 이 **남의 작업까지 확정한다** — A 가 등록 중인데 B 가 커밋하면 A 의 미완성 변경이 함께 저장된다. **이 노트의 「지역 변수는 안전하고 필드는 안전하지 않다」가 딱 맞는 자리**이고, `Prompt prompt = new Prompt(socket, appCtx)` 는 `run()` 안의 지역 변수라 안전한 것과 나란히 놓여 있다. 그리고 **Day61 의 필기는 두 주제를 같은 날 다루면서 이 충돌을 짚지 않는다** — 앞부분(프록시 DAO)과 뒷부분(멀티쓰레드 서버)이 서로의 전제를 깨는데 절이 나뉘어 있어 안 보인다. **하루 뒤 Day62 의 첫 절이 정확히 이 충돌을 적는다** — 「하나의 SqlSession을 생성하여 하나의 캐시를 공유한다」·「하나의 클라이언트에서 커밋을 하면 전체 캐시가 데이터베이스에 업데이트된다」가 위 ①② 이고, 답은 세션을 쓰레드마다 갖게 하는 것이다. 즉 **이 항목은 하루짜리 상태를 적은 것**이고, 그 하루 사이에 「필드는 안전하지 않다」를 실제로 고치는 방법이 손에 들어온다 → [[transaction]] · [[sql-session]] · [[dynamic-proxy]] · [[thread-local]] · [[connection-lifetime-mismatch]]
- **하루 뒤 Day62 는 쓰레드가 죽는 것에 기대어 맞고 있다 — 쓰레드 풀을 넣는 순간 뒤집힌다** — 고친 방법이 「쓰레드마다 세션을 하나 갖게 하는 것」인데, 그 값을 **작업이 끝날 때 지우는 코드가 없다.** 이 회차의 서버는 접속마다 `new Thread` 를 만들고 대화가 끝나면 그 쓰레드가 죽으므로 값도 함께 사라져서 문제가 안 보인다. 그런데 이 노트가 「쓰레드는 재사용되지 않는다 — 그 비용을 피하려고 쓰레드를 살려 두고 작업만 바꿔 넣는 것이 쓰레드 풀이다」로 적어 둔 그 도구를 넣으면, **재사용된 쓰레드가 먼저 다녀간 클라이언트의 세션을 물려받는다**(그 사람의 미확정 트랜잭션과 캐시까지). Day48 이 「병렬 작업의 갯수를 고려하여 쓰레드를 생성하여야 한다」고 적은 것을 지키려 할 때 **먼저 지워야 하는 코드가 생긴 것**이고, 「쓰레드가 곧 죽는다」가 설계의 전제가 되어 있는데 어디에도 적혀 있지 않다 → [[thread-local]] · [[thread-state]] · [[garbage-collection]]
- **「하나의 쓰레드에서 예외를 발생시키면 프로세스가 종료된다」가 틀렸다는 것이 Day61 에서 확인된다** — 아래 항목이 Day48 기준으로 지적한 것인데, Day61 의 `service()` 는 그 위에 **의존해서** 만들어져 있다. `run()` 안의 `catch (Exception e)` 가 「실행 오류!」와 스택트레이스를 찍고 그 접속만 끝나며 **서버와 다른 접속은 계속 돈다.** 만약 필기의 Day48 문장이 맞았다면 클라이언트 하나가 잘못된 입력을 넣는 것으로 서버 전체가 죽었을 것이다 — **잘못 배운 문장 위에 맞는 코드가 세워진 자리**이고, 접속마다 `try`/`catch` 로 감싸는 것이 이 구조의 필수 조건인 이유가 그것이다 → [[exception-handling]]
- **`start()` ≠ `run()`** — 이 개념에서 가장 비싼 한 줄이다. `thread.run()` 이라고 부르면 컴파일도 되고 실행도 되는데 **새 흐름이 생기지 않는다** — 그냥 지금 쓰레드에서 메서드 하나를 부른 것이라 `run()` 이 끝날 때까지 다음 줄로 가지 않는다. 즉 **쓰레드를 쓴 코드가 조용히 순차 코드로 돌아간다.** 결과가 같아 보여서(비프음과 「띵」이 다 나온다) 오류로 드러나지 않고, 순서만 보면 「쓰레드가 안 겹치네」로 보인다. Day48 은 「thread의 시작은 start()를 호출하여 실행한다」로 맞게 적었지만 **`run()` 을 직접 부르면 무엇이 달라지는지는 적지 않았다** — 새 흐름을 만드는 것은 `start()` 이고 `run()` 은 그 흐름이 실행할 내용일 뿐이다 → [[method-overriding]]
- **`Thread thread = new Thread(…).start();` 는 컴파일되지 않는다 — Day48 에 세 번 나온다** — `start()` 의 반환 타입은 `void` 라서 대입할 값이 없다(`incompatible types: void cannot be converted to Thread`). 익명 `Runnable` 판·익명 `Thread` 판·상속 판 셋이 모두 같은 모양이고, **앞 절에서 `Thread thread = new Thread(task);` 를 맞게 쓴 다음 그 줄 끝에 `.start()` 를 붙인 형태**다. 두 줄로 쪼개거나 참조를 버리고 `new Thread(…).start();` 로 쓰면 된다. **다만 참조를 버리면 나중에 `join()`·`interrupt()` 를 부를 상대가 없어진다** — 익명 클래스를 대입 없이 쓰는 형태가 여기서는 대가를 갖는다 → [[anonymous-class]] · [[thread-join]]
- **`Toolkit toolkit = new Toolkit();` 도 컴파일되지 않는다 — 그리고 같은 노트가 맞는 형태를 이미 갖고 있다** — `java.awt.Toolkit` 은 추상 클래스이므로 `new` 로 만들 수 없고 `Toolkit.getDefaultToolkit()` 으로 받아야 한다. **쓰레드를 안 쓴 첫 예제는 그렇게 맞게 썼고, 그 코드를 `run()` 안으로 옮겨 적으면서 `new` 로 바뀌었다** — 옮기는 손이 팩토리 호출을 생성자로 착각한 자리다 → [[abstract-class]] · [[platform-dependency]]
- **익명 `Thread` 판의 `void run()` 은 접근을 좁힌 것이라 막힌다** — `Thread.run()` 이 `public` 이므로 재정의에서 `public` 을 빼면 컴파일 에러다. 같은 회차의 다른 세 곳은 `public void run()` 으로 맞게 썼는데 익명 클래스 안에서만 빠졌다 → [[method-overriding]] · [[access-modifier]]
- **멀티쓰레드 ≠ 더 빠름** — 코어가 하나면 두 흐름이 **번갈아** 도는 것이라 CPU 를 쓰는 일의 총 시간은 줄지 않고, 갈아타는 비용만큼 늘어난다. Day48 의 예제가 실제로 빨라지는 이유는 **두 흐름이 대부분 `sleep()` 으로 놀고 있어서** 기다리는 시간이 겹치기 때문이다. 「쓰레드를 쓰면 빨라진다」로 외우면 계산만 하는 코드에 쓰레드를 넣고 왜 안 빨라지는지 묻게 된다 → [[process]]
- **실행 순서는 보장되지 않는다** — 위 예제의 출력이 「띵」과 비프음이 정확히 번갈아 나오는 것으로 보이지만, 실행마다 갈리고 두 「띵」이 붙어 나올 수도 있다. `start()` 가 「지금 시작한다」는 뜻이 아니라 **「실행 가능한 상태로 만든다」**는 뜻이기 때문이다 → [[thread-state]]
- **같은 쓰레드를 두 번 `start()` 할 수 없다** — 끝난 쓰레드도 마찬가지로 `IllegalThreadStateException` 이다. **쓰레드는 재사용되지 않는다** — 「같은 일을 또 시킨다」는 새 `Thread` 객체를 만드는 일이고, 그 비용을 피하려고 쓰레드를 살려 두고 **작업만 바꿔 넣는** 것이 쓰레드 풀이다 → [[thread-state]]
- **「멀티쓰레드에서는 작업중인 쓰레드가 있으면, 메인쓰레드는 종료되지 않는다」는 주체가 틀렸다** — `main()` 이 `return` 하면 **메인 쓰레드는 그 자리에서 끝난다.** 남아 있는 것은 프로세스(JVM)이고, 그것이 안 죽는 이유는 **끝나지 않은 일반 쓰레드가 하나라도 있으면 JVM 이 기다려 주기 때문**이다. 둘을 겹쳐 읽으면 비어 있는 「데몬쓰레드」 절이 설명되지 않는다 — 데몬으로 표시한 쓰레드는 **아무리 일하는 중이어도** JVM 이 기다리지 않고 프로세스를 끝낸다 → [[process]] · [[main-method]]
- **쓰레드에서 난 예외는 그 쓰레드만 끝낸다** — Day48 의 「하나의 쓰레드에서 예외를 발생시키면, 프로세스가 종료된다」는 지금까지 모든 프로그램이 단일 흐름이어서 「예외 = 프로그램 종료」로 겹쳐 있던 것을 그대로 옮긴 문장이다. 실제로는 스택 트레이스만 찍히고 **나머지 흐름은 계속 돈다** → [[process]] · [[exception-handling]]
- **`Runnable` 을 넘기는 것과 `run()` 을 덮는 것을 섞으면 조용히 아무 일도 안 한다** — `new Thread(task){ public void run(){ /* 다른 일 */ } }` 처럼 둘을 겹치면 `task` 는 실행되지 않는다. `Thread.run()` 의 원래 구현이 「넘겨받은 `Runnable` 이 있으면 그것을 실행」인데, 덮으면 그 코드가 사라지기 때문이다. 반대로 `new Thread()` 로 만들고 `run()` 을 재정의하지 않으면 **쓰레드는 정상적으로 뜨고 즉시 끝난다** → [[method-overriding]]
- **쓰레드는 반환값을 주지 않는다** — `run()` 이 `void` 라서 결과를 받으려면 필드에 담아 두고 끝난 뒤에 읽어야 한다. 그 「끝난 뒤」를 만드는 것이 `join()` 이다 → [[thread-join]]
- **지역 변수는 안전하고 필드는 안전하지 않다** — 쓰레드마다 스택이 따로 있어서 `run()` 안에 선언한 변수는 다른 쓰레드가 볼 수 없다. 위험한 것은 힙에 있는 것(필드·배열·컬렉션)이고, **그 구분이 「쓰레드 안전」이라는 말의 실제 내용**이다 → [[jvm-stack]] · [[object-reference]]
- **그 구분에 세 번째 칸이 있다 (Day62 기준) — 필드인데 쓰레드마다 다른 값** — `ThreadLocal` 필드는 힙에 있고 모든 쓰레드가 같은 객체를 보는데도 안전하다. 값이 그 필드에 담기지 않고 **각 `Thread` 객체가 든 맵**에 담기기 때문이다. 그래서 위 두 문장을 정확히 세우면 **「값이 어디 사는가」가 기준**이고 「어느 문법으로 선언했나」가 아니다 — 스택에 있으면 안전하고, 힙에 있으면서 쓰레드를 키로 나뉘어 있으면 안전하고, 힙에 있으면서 하나면 위험하다. Day62 가 고친 것이 정확히 세 번째 칸을 두 번째 칸으로 옮긴 일이다 → [[thread-local]] · [[static-member]]
