# 람다식 (Lambda Expression)

**매개변수와 처리 내용만 남긴 식.** 자바 8부터 들어왔고, 생김새는 이름 없는 함수지만 실제로 만들어지는 것은 **함수형 인터페이스의 인스턴스**다. Day36 이 그것을 한 줄로 적었다 — 「람다식은 익명구현 객체로 변환한다」. 그래서 람다를 쓸 수 있는 조건도 함수 쪽이 아니라 **받는 타입 쪽**에 있다 → [[functional-interface]]

## 정의

```java
람다식 : (매개변수,...) -> {처리내용}
```

지울 수 있는 것이 네 자리이고, Day36 의 세 장이 그 자리를 하나씩 짚는다.

| 자리 | 규칙 | Day36 의 예 |
|---|---|---|
| 매개변수 타입 | 생략 가능 — 추상메서드 선언에서 추론된다 | `(String s) -> …` → `s -> …` |
| 매개변수 괄호 | **하나일 때만** 생략. 없으면 `()` 를 그대로 쓴다 | `s -> …` / `() -> …` |
| 몸통 중괄호 | 문장이 하나면 생략 | `() -> System.out.println("…")` |
| `return` | 중괄호를 지울 때 **함께** 지운다 | `money -> money * (1 + rate)` |

지울 수 있는 것이 다섯 번째로 하나 더 있는데 그것은 하루 뒤 회차의 몫이다 — **몸통이 딱 한 번의 호출이면 몸통 자체를 지울 수 있다**(`(x, y) -> My.plus(x,y)` → `My::plus`) → [[method-reference]]

필기가 마지막 두 줄을 정확히 적었다 — 「{}의 명령어가 하나인 경우 람다식의 바깥부분 {};을 생략할 수 있다」·「중괄호를 생략 하려면 "{return"과 "};"을 같이 생략해야한다」. **둘 중 하나만 지울 수는 없다** — `return` 은 문장이고 문장은 중괄호 안에만 살 수 있는데, 중괄호가 없는 몸통은 문장이 아니라 **식**이라서 그 값이 곧 반환값이 된다.

세 장의 골격을 나란히 놓으면 이렇다.

```java
()->{ /*오버라이딩*/ }                        // 매개변수 없음
(매개변수...)->{ /*오버라이딩*/ }              // 매개변수 있음
(매개변수...)->{ /*오버라이딩*/ return 반환 값;};  // 반환값 있음
```

## 사용 예시

**Day36 은 같은 인터페이스를 세 번 구현하는 사다리를 세 번 반복한다** — 로컬 클래스 → 익명 클래스 → 람다. 줄어드는 것을 보면 람다가 무엇을 지운 문법인지가 드러난다.

```java
@FunctionalInterface
interface Player{
    void play();
}
```

```java
// 1. 일반클래스로 구현하기
class MyPlayer implements Player{
    @Override
    public void play(){
        System.out.println("일반클래스로 재생합니다.");
    }
}
Player player = new MyPlayer();
player.play();
```

```java
// 2. 익명 클래스로 구현하기
Player player = new Player(){
    @Override
    public void play(){
        System.out.println("익명클래스1로 재생합니다.");
    }
};
```

```java
// 3. 람다식으로 구현하기
Player player = ()->{
    System.out.println("람다식1로 재생합니다.");
};

Player player2 = ()->System.out.println("람다식2로 재생합니다.");
```

**클래스 이름 · `implements` · `@Override` · 메서드 이름 · 반환 타입이 차례로 없어지고 `()` 와 몸통만 남는다.** 익명 클래스가 지운 것은 이름 하나였는데(→ [[anonymous-class]]) 람다는 **어느 메서드를 채우는지까지** 지운다. 그것을 아는 것은 코드가 아니라 왼쪽의 `Player` 타입이다.

**Day37 이 그 사다리에 한 칸을 더 붙여 람다가 아직 남겨 둔 것을 드러낸다.**

```java
Cal c3 = (x, y) -> My.plus(x,y);   // Day36 의 마지막 칸
Cal c4 = My::plus;                 // Day37 이 붙인 칸
```

`c3` 의 `(x, y)` 는 **받아서 그대로 넘기기만 하는 이름 두 개**이고, 호출문 `My.plus(x,y)` 도 이미 있는 메서드를 부르는 껍데기다. 람다는 「어느 메서드를 채우는가」를 지웠지만 **「무엇을 실행하는가」는 여전히 손으로 쓰게 한다** — 그것까지 이름 하나로 대신하는 것이 다음 칸이다. 다만 그 칸에는 조건이 붙는다(아래 「경계와 오해」) → [[method-reference]]

**반환값이 있는 쪽이 이 문법의 값을 가장 잘 보여 준다.** `Factory` 는 이율을 받아 「이자를 계산하는 방법」을 만들어 돌려준다.

```java
interface InterestCalculator {
  double compute(int money);
}

public class Factory {
  // 3.람다식 1
  static InterestCalculator create5(double rate) {
    return (int money) -> {
      return money * (1 + rate);
    };
  }

  // 4.람다식 2
  static InterestCalculator create6(double rate) {
    return money -> money * (1 + rate);
  }
}
```

`create6` 은 **한 줄로 객체를 만들어 반환한다.** 같은 일을 하는 로컬 클래스 판(필드 · 생성자 · 대입문 · `@Override` 로 여덟 줄)과 익명 클래스 판(다섯 줄)이 바로 위에 나란히 있어서 대비가 그대로 읽힌다 → [[nested-class]]

그리고 `rate` 는 **메서드가 끝난 뒤에도 살아 있다.** `create6(0.025)` 가 반환된 다음에 `compute(10000000)` 이 불리는데 그때 `rate` 는 이미 사라진 지역변수다 — 람다가 그 값을 붙잡아 두기 때문에 동작한다.

### 한 주 뒤 — 내가 만들지 않은 인터페이스에 처음 넣는다

Day36·Day37 의 인터페이스는 전부 필기가 직접 선언한 것이었다(`Player`·`Cal`·`InterestCalculator`). **Day41 은 표준 라이브러리 메서드의 인자 자리에 람다를 넣는다.**

```java
    File dir = new File(".");
    //
    //    class JavaFilter implements FilenameFilter{
    //      public boolean accet(File file){
    //        return file.getName().endsWith(".java") && file.isfile();
    //      }
    //    }
    //현재 디렉토리 정보 전체 출력
    File[] files = dir.listFiles(file -> file.getName().endWith(".java") && file.isFile());
```

**주석으로 남은 클래스가 사다리의 아래 칸이고, 살아 있는 한 줄이 위 칸이다.** 지운 것이 Day36 과 같다 — 클래스 이름 · `implements` · 메서드 이름 · 반환 타입. 그런데 여기서는 **하나가 더 지워졌다** — `FilenameFilter` 라는 **타입 이름 자체**가 코드에서 사라진다. 람다는 왼쪽 타입에서 자기가 무엇인지 알아내므로, 넘기는 쪽은 그 인터페이스의 이름도 메서드 이름도 모른 채 조건만 쓴다 → [[functional-interface]] · [[file-class]]

**그것이 이 문법이 실제로 값을 내는 자리다.** 인터페이스가 남의 것이면 「추상메서드 이름이 `accept` 인지 `test` 인지」를 찾아보는 일이 사라지고, 표준 API 의 콜백 자리가 전부 같은 모양으로 쓰인다. 동시에 **모른 채로 쓰는 것의 대가**도 여기서 처음 나온다(아래 「경계와 오해」의 두 항목).

## 왜 중요한가

**「동작 하나」를 넘기는 데 드는 코드가 클래스 한 개에서 한 줄로 내려간다.** 하루 전 회차가 커맨드를 기능 단위로 쪼개면서 클래스가 다섯에서 열일곱 개로 늘었는데, `Command` 는 `execute(String)` **하나뿐인 인터페이스**다 — 즉 그 열다섯 개는 문법상 람다로 쓸 수 있었던 것들이다. **패턴을 바꾸지 않고 그것을 표현하는 코드 양만 바뀌는 자리**가 여기서 열린다 → [[command-pattern]] · [[functional-interface]]

**만드는 일과 부르는 일이 갈라진다.** `Player player2 = ()->System.out.println(...)` 는 아무것도 찍지 않는다. 람다식은 코드를 실행하지 않고 **실행할 것을 담은 객체를 만드는 식**이고, 실행은 `player2.play()` 가 한다. 그래서 「나중에 실행할 것」·「받는 쪽이 실행할 것」을 값으로 다룰 수 있게 된다 → [[functional-programming]]

**지역변수의 수명보다 오래 사는 코드를 쓸 수 있게 된다.** `create6` 이 반환한 람다는 `rate` 를 들고 나간다. 이것이 없으면 팩토리는 필드와 생성자를 가진 클래스를 만들어야 하고, 실제로 Day36 의 「일반 클래스1」이 그 형태다(`private double rate` + `GeneralClass(double rate)`). **람다는 그 세 줄을 문법으로 대신한다** → [[variable-scope]] · [[nested-class]]

## 경계와 오해

- **람다식 ≠ 익명 클래스의 짧은 표기** — 엿새 전 회차의 노트가 「나중에 배우는 람다」로 미뤄 둔 구분이 Day36 에서 코드로 확인된다. 조건이 셋 다르다. ① **추상메서드가 하나뿐인 인터페이스**에만 쓸 수 있다(익명 클래스는 추상 클래스도 되고 메서드가 몇 개든 된다), ② **필드를 가질 수 없다**(`cursor` 같은 상태를 둘 자리가 없다), ③ `this` 가 자기 자신이 아니라 **바깥 인스턴스**를 가리킨다. 엿새 전의 `Iterator`(`hasNext`·`next` 둘 + `cursor` 상태)는 그래서 **람다로 옮길 수 없다.** 「익명 클래스는 람다로 대체된 옛 문법」으로 읽으면 그 반복자가 설명되지 않는다 → [[anonymous-class]] · [[this-reference]]
- **람다식은 혼자서는 타입이 없다 — 그래서 만든 자리에서 바로 부를 수 없다** — 익명 클래스는 `new Player(){…}.play()` 처럼 식 하나로 만들고 바로 부를 수 있고 Day36 이 그 형태를 두 번 쓴다(`new Intro(){…}.introduce("익명클래스2입니다")`). 람다에는 그 길이 없다 — `(()->{…}).play()` 는 컴파일 오류이고, `((Player)()->{…}).play()` 처럼 **타입을 알려 줘야** 통과한다. 같은 이유로 `var p = () -> {};` 도 오류다. **어느 메서드를 채우는지가 코드에 없기 때문에 왼쪽에 받을 타입이 반드시 있어야 한다** — 람다가 「짧아진 익명 클래스」가 아니라는 것이 이 자리에서 문법으로 드러난다 → [[type-casting]] · [[variable]]
- **「람다식의 반환값은 객체가 생성되어 반환되는 인스턴스 값이다」는 두 개의 반환을 겹쳐 놓았다** — 반환이 둘 있다. ① **람다식 자체를 평가한 값** = 함수형 인터페이스의 인스턴스(`Player player = ()->{…}` 의 오른쪽), ② **몸통의 `return`** = 그 인스턴스의 메서드를 불렀을 때 나오는 값(`money -> money*(1+rate)`). 필기의 문장은 ①을 말한 것으로 읽히는데, 세 장 뒤의 제목이 「**반환값**이 있는 람다식」이고 그것은 ②다. **같은 낱말이 두 장에서 다른 것을 가리키므로 §2 의 정리를 §4 에 그대로 들고 가면 어긋난다.**
- **람다를 평가할 때 새 객체가 생긴다는 보장은 없다** — 위 ①에 딸린 함정이다. 익명 클래스는 `new` 를 만날 때마다 새 객체가 생기는 것이 보장이지만, 람다는 **바깥 값을 붙잡지 않으면**(`()->System.out.println("…")`) 같은 인스턴스를 계속 돌려줄 수 있다 — 자바 명세가 새로 만들지 말지를 정해 두지 않았다. 그래서 람다를 `==` 로 비교하거나 인스턴스마다 상태를 기대하면 안 된다. 「객체가 생성되어」로 외우면 이 차이가 안 보인다 → [[instance]] · [[object-equality]]
- **`/*오버라이딩*/` 이라 적힌 자리에 `@Override` 를 붙일 수 없다** — 람다 몸통은 **메서드 선언이 아니다.** 이름도 반환 타입도 없으니 붙일 문법 자리가 없고, 애노테이션이 검사해 주던 「정말 그 메서드를 채우는가」를 여기서는 컴파일러가 **대입되는 타입**으로 확인한다. 매개변수 개수나 반환형이 어긋나면 오타가 아니라 **타입 불일치**로 걸린다 → [[annotation]] · [[method-overriding]]
- **매개변수 타입은 전부 쓰거나 전부 안 쓰거나다** — Day36 의 §3 정리가 「(타입 매개변수) 또는 (매개변수)를 사용 할 수 있다」로 「또는」이라 적은 것이 정확히 그 규칙이다. 둘이 섞인 `(String a, b) -> …` 는 컴파일 오류다. 그리고 **타입을 쓰면 하나여도 괄호를 지울 수 없다** — `(String s) -> …` 는 괄호가 필수이고 `s -> …` 만 지울 수 있다. §2 의 정리(「매개변수가 없는 경우 추상메서드의 ()을 그대로 사용한다」)와 §3 의 정리(「매개변수가 하나인 경우 ()을 생략할 수 있다」)는 **따로 외울 규칙이 아니라 「하나일 때만」이라는 한 규칙의 양쪽**이다.
- **람다식 ≠ 메서드 레퍼런스로 줄일 수 있는 것** — Day37 이 붙인 네 번째 칸은 **몸통이 딱 한 번의 호출이고 인수를 순서 그대로 넘길 때만** 열린다. `(x, y) -> My.plus(x,y) + 1` 도, 순서를 바꾸는 `(x, y) -> My.plus(y,x)` 도, 인수 하나를 상수로 고정하는 `x -> My.plus(x, 10)` 도 `::` 로 쓸 수 없다. Day37 의 예제가 전부 그대로 넘기기만 하므로 **네 번째 칸이 언제나 도달 가능한 것처럼** 읽히는데, 앞의 세 칸과 달리 이 칸은 조건부다 — **람다가 상위 집합이고 메서드 레퍼런스가 그 안의 특수한 경우**다 → [[method-reference]]
- **`()->{}` 는 「매개변수가 없다」이지 「인자를 무시한다」가 아니다** — 추상메서드가 인자를 받으면 람다도 반드시 그 개수만큼 받아야 한다. 하루 전 회차에서 `execute(String menuName)` 의 인자를 아무도 안 읽게 되었어도, 그것을 람다로 옮기면 `menuName -> {…}` 로 **여전히 받아 두고 안 쓰는** 모양이 된다 → [[parameter-and-argument]] · [[interface-segregation-principle]]
- **람다가 붙잡는 지역변수는 바꿀 수 없다** — `create6` 의 `rate` 를 몸통에서든 메서드에서든 다시 대입하면 컴파일 오류다. 람다는 값을 **복사해** 들고 나가므로 원본이 바뀌면 둘이 갈리고, 그것을 막으려고 변경을 금지한다. 로컬 클래스가 받는 것과 같은 제약이고 Day36 이 두 문법을 나란히 놓았으므로 같은 제약인 것이 보인다 — 다만 **필기는 이 제약을 적지 않았다** → [[nested-class]] · [[call-by-value]]
- **§3·§4 의 「기본구조」 설명이 §2 것을 그대로 복사해 왔다** — 세 장 모두 「매개변수가 없는 람다식의 구조는 아래와 같다」로 시작하는데 §3 은 매개변수가 있는 장이고 §4 는 반환값이 있는 장이다. **바로 아래의 골격 코드는 각각 맞다** — 설명 문장만 앞 장에서 따라온 것이다.
- **「함수」라고 불러도 자바에 함수는 없다** — 람다는 함수형 인터페이스를 구현한 객체이고, 그래서 변수에 담기고 반환되고 인자로 넘어간다. 함수 자체가 값인 언어와 결과는 비슷해 보이지만, **타입이 인터페이스 이름으로 적힌다**는 것이 계속 남는 차이다(`InterestCalculator c6 = …`) → [[functional-interface]] · [[object-reference]]
- **오버로드된 메서드에서는 매개변수 개수가 어느 인터페이스인지를 고른다 — Day41 의 주석과 코드가 서로 다른 인터페이스를 가리킨다** — `File.listFiles` 는 세 벌이 있다 — 인자 없는 것, `FileFilter`(`boolean accept(File)`), `FilenameFilter`(`boolean accept(File dir, String name)`). 인자 자리에 람다를 넣으면 **매개변수 개수가 어느 벌을 부르는지 정한다.** Day41 의 `file -> …` 는 하나라서 **`FileFilter` 로 풀리는데, 주석으로 남은 클래스는 `implements FilenameFilter` 다.** 즉 사다리의 두 칸이 **같은 인터페이스의 두 표기가 아니고**, 주석 쪽은 애초에 컴파일되지 않는다(`FilenameFilter.accept` 는 인자가 둘인데 한 개짜리 메서드를 썼고 이름도 `accet` 로 틀렸다). **람다가 타입 이름을 지워 준 대가가 여기서 나온다** — 무엇을 구현하고 있는지 코드에 안 적혀 있으니 **잘못 알고 있어도 컴파일이 통과한다.** 두 벌 중 어느 것을 원했는지 확실히 하려면 `(FilenameFilter) (dir, name) -> …` 처럼 개수를 맞추거나 타입을 명시한다 → [[functional-interface]] · [[method]] · [[file-class]]
- **주석의 클래스는 익명 클래스가 아니라 로컬 클래스다 — 사다리의 한 칸이 비어 있다** — Day36 은 로컬 클래스 → 익명 클래스 → 람다 세 칸을 매번 나란히 놓았는데, Day41 의 비교는 **메서드 안에 선언한 이름 있는 클래스**와 람다뿐이다. 가운데 칸(`new FileFilter(){ … }`)이 없다. 그 칸이 실제 코드에서 가장 흔한 형태였기 때문에 **자바 8 이전의 표준 라이브러리 사용례를 읽을 때 다시 만나게 되는 자리**다 → [[nested-class]] · [[anonymous-class]]
- **람다는 조건을 값으로 넘기는 것이고, 그 조건이 어디서 평가되는지는 부르는 쪽이 정하지 않는다** — `listFiles(filter)` 는 목록을 훑으며 파일마다 람다를 부른다. 즉 **람다가 몇 번 실행되는지·어떤 순서로 실행되는지가 넘겨받은 쪽의 구현에 달려 있다.** 반환된 배열의 순서가 정해져 있지 않은 것도 같은 이유다. 자기가 부르던 `player.play()` 와 달리 **호출 시점의 통제권을 넘긴 것**이고, 그래서 람다 안에 부수 효과를 두면 예측이 어려워진다 → [[functional-programming]] · [[file-class]]
