# MVC 아키텍처 (MVC1 / MVC2)

화면·데이터·흐름 제어를 **셋으로 갈라 두는** 배치. 갈라진 정도에 따라 MVC1 과 MVC2 로 부른다.

## 정의

세 역할이 맡는 것.

| 역할 | 하는 일 |
|---|---|
| **모델 (Model)** | 데이터와 업무 로직. DB·외부 서비스와 이야기하고 검증한다 → [[dao-pattern]] |
| **뷰 (View)** | 받은 데이터를 사람에게 보인다. **로직 없이 표시에만 집중한다** → [[jsp]] |
| **컨트롤러 (Controller)** | 요청을 받아 모델을 부르고, 결과를 뷰에 넘긴다. **어떤 뷰를 보일지 정한다** → [[servlet]] |

MVC1 과 MVC2 가 갈리는 것은 **요청을 누가 먼저 받는가**다.

| | 요청을 받는 곳 | 결과 |
|---|---|---|
| **MVC1** | 뷰(JSP)가 직접 받는다 | 화면 파일 안에 업무 로직이 섞인다 |
| **MVC2** | **컨트롤러가 전부 받는다** | 컨트롤러가 모델과 뷰를 잇는다 |

**MVC2 의 핵심은 「모든 요청이 컨트롤러를 통과한다」**는 것이다. 뷰는 직접 불리지 않는다.

## 사용 예시

이 회차의 실습이 MVC2 다. 서블릿이 받고, 담고, JSP 를 부른다.

```java
@WebServlet("/board/list")                     // ← 컨트롤러가 URL 을 갖는다
public class BoardListServlet extends GenericServlet {
  public void service(ServletRequest req, ServletResponse res) ... {
    List<Board> list = boardDao.list();        // 모델에게 묻는다
    req.setAttribute("list", list);            // 뷰에 넘길 자리에 담는다
    res.setContentType("text/html;charset=UTF-8");
    req.getRequestDispatcher("/board/list.jsp").include(req, res);   // 뷰를 고른다
  }
}
```

**JSP 는 URL 을 갖지 않는다.** `/board/list.jsp` 를 브라우저가 직접 부르는 것이 아니라 서블릿이 안에서 끼운다 → [[request-dispatcher]]

값을 넘기는 통로가 **요청 속성**이다 — 컨트롤러가 `setAttribute`, 뷰가 `getAttribute`. 문자열 이름으로 이어진 계약이다.

## 왜 중요한가

**고칠 곳이 역할별로 갈린다.** 화면 모양을 바꾸면 `.jsp` 만, 조회 조건을 바꾸면 서블릿만, 쿼리를 바꾸면 DAO 만 만진다. Day63~66 의 서블릿은 그 셋이 한 메서드 안에 있어서 어느 것을 고쳐도 같은 파일을 열었다 → [[cohesion]]

그리고 **화면이 여럿일 때 재사용이 생긴다.** 같은 데이터를 다른 모양으로 보이려면 뷰만 하나 더 만들면 되고, 컨트롤러가 어떤 뷰를 고를지만 바꾼다.

## 경계와 오해

- **이 필기가 「Servlet과 JSP(MVC1 아키텍쳐)」로 제목을 달았지만 실제로 만든 것은 MVC2 다** — 그 절이 비교하는 것은 「서블릿만 쓰기」와 「JSP만 쓰기」인데, 둘 다 한 파일이 다 하는 형태이므로 MVC1 쪽이다. 그런데 **뒤의 실습은 서블릿이 받고 JSP 가 그리는 MVC2** 다. 제목과 코드가 어긋나 있어서, 그 절만 읽으면 「Servlet + JSP = MVC1」로 외우게 된다 — **가르는 기준은 「둘을 같이 쓰는가」가 아니라 「요청을 누가 받는가」다.**
- **MVC 는 웹만의 것이 아니다** — 데스크톱 GUI 에서 나온 패턴이고, 원래 MVC 에서는 모델이 뷰에게 변경을 알린다([[observer-pattern]]). 웹의 MVC2 는 요청-응답이 끊기므로 그 통지가 없고, **컨트롤러가 매번 새로 조립한다.** 같은 이름이지만 흐름이 다르다.
- **「뷰는 로직 없이」가 지켜지지 않는다** — 필기의 `view.jsp` 가 `<%! isMember() %>` 로 메서드를 선언하고 `<% for %>` 로 돌린다. **반복과 조건은 뷰의 일이지만 「팀원인지 판정」은 모델의 일**이고, 그것이 뷰 파일에 들어와 있다. MVC2 로 배치해도 **무엇이 뷰의 로직인지는 매번 정해야 한다** → [[jsp]]
- **컨트롤러가 뷰를 고르는 것과 뷰가 자기를 고르는 것은 다르다** — 이 실습은 URL 하나에 JSP 하나가 고정이라 「고른다」의 값이 아직 드러나지 않는다. 오류 때 `error.jsp` 로 보내는 자리가 유일하게 갈라지는 지점이다 → [[exception-handling]]
- **MVC2 의 단점을 「복잡성」으로만 적으면 절반이다** — 파일이 셋으로 늘고 이름 계약(`"list"`)이 생기는 것이 실제 비용이다. **컴파일러가 그 계약을 검사하지 않으므로** 오타가 `null` 로 조용히 나타난다.
- **프레임워크 목록의 Ruby on Rails 는 MVC2 라는 말을 쓰지 않는다** — MVC1/MVC2 라는 구분 자체가 Java 웹 쪽 용어다. Rails 는 그냥 MVC 라 부르고, 구조는 MVC2 에 해당한다.
- **「컨트롤러」가 한 덩어리라는 보장은 없다** — MVC2 는 「요청을 컨트롤러가 받는다」까지만 정하고, 그 컨트롤러가 **하나인지 요청마다 하나씩인지**는 정하지 않는다. Day63~74 의 배치는 URL 마다 서블릿이 하나였고, Day75 가 그것을 하나의 진입점으로 모은다 → [[front-controller]]
- **모델을 「DAO」로 읽으면 좁다** — 위 표가 모델에 「데이터와 업무 로직」을 함께 적었는데, 실습에서는 그 둘이 DAO 하나에 뭉쳐 있거나 서블릿에 흩어져 있다. Day75 가 **업무 로직과 트랜잭션 제어를 따로 세우면서** 모델 쪽이 두 층으로 갈린다 → [[service-layer]] · [[transaction]]

- [[2024-08-30-Day67]] — 「MVC 아키텍쳐」 절이 MVC1 과 MVC2 를 「역할이 명확히 구분되지 않았던 초기 방식」과 「모든 요청이 컨트롤러를 통해 처리되며, 컨트롤러가 모델과 뷰를 연결한다」로 갈랐고, 세 역할의 책임을 각각 네 줄씩 정리했다. 장점 넷(유지보수·확장성·협업·테스트)과 단점 둘(복잡성·초기 설정 비용), 대표 프레임워크 셋(Spring MVC·Struts·Ruby on Rails)까지 붙어 있다. 그리고 **실습 전체가 이 배치로 다시 만들어진다** — 서블릿이 `setAttribute` 로 담고 `include` 로 JSP 를 부르는 형태다. 다만 앞 절 제목이 「Servlet과 JSP(MVC1 아키텍쳐)」인데 그 뒤 실습은 MVC2 라 제목과 코드가 어긋나고, 「뷰는 로직 없이」라고 적어 둔 것과 달리 `view.jsp` 가 판정 메서드를 선언해 쓴다
