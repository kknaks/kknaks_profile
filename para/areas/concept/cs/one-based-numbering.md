# 1부터 세는 번호와 0부터 세는 인덱스

사용자에게 보여 주는 번호는 1부터고 배열 인덱스는 0부터다. 그래서 그 사이에 **`-1` 변환**과 **범위 검사**가 늘 짝으로 따라온다.

## 정의

```java
if (userNo < 1 || userNo > userLength) {    // 유효한 번호는 1 ~ userLength
  System.out.println("없는 회원입니다.");
  return;
}
User user = users[userNo - 1];               // 번호 → 인덱스
```

| | 범위 | 조건으로 쓰면 |
|---|---|---|
| 화면 번호 | 1 ~ 개수 | `no >= 1 && no <= size` |
| 배열 인덱스 | 0 ~ 개수 − 1 | `i >= 0 && i < size` |
| 변환 | | `i = no - 1` |

**`<=` 를 쓰는 쪽이 번호이고 `<` 를 쓰는 쪽이 인덱스다.** 둘의 모양이 닮아서 부등호 하나를 옮겨 쓰기 쉬운데, 그 한 글자가 마지막 하나를 넣거나 뺀다.

**검사와 변환은 같은 자리에 있어야 한다.** 인덱스로 바꾼 뒤에 검사하면 이미 잘못된 인덱스를 만든 다음이다.

목록을 출력할 때는 방향이 반대다 — 인덱스로 돌면서 `i + 1` 을 보여 준다.

```java
for (int i = 0; i < userLength; i++) {
  User user = users[i];
  System.out.printf("%d %s %s\n", i + 1, user.getName(), user.getEmail());
}
```

## 사용 예시

같은 프로젝트 안에 **맞는 검사와 틀린 검사가 나란히 있다.**

```java
// UserCommand.viewUser — 맞다
if (userNo < 1 || userNo > userLength) { ... return; }

// ProjectCommand.viewProject — 같은 자리인데 부등호가 다르다
if (projectNo < 1 || projectNo >= projectLength) { ... return; }
```

`>=` 는 `projectNo == projectLength` 를 걸러 낸다. 프로젝트가 세 개면 3번이 「없는 프로젝트번호」가 되어 **마지막 프로젝트를 조회·변경·삭제할 수 없다.** 등록은 되고 목록에도 나오는데 손댈 수 없는 상태다.

그리고 이 검사는 `viewProject`·`updateProject`·`deleteProject` **세 곳에 복사돼 있어서 세 곳이 같이 틀렸다.** 회원 쪽 코드를 보고 만든 것인데 부등호 하나가 달라졌고, 맞는 코드가 같은 파일 위쪽에 있어도 눈으로 잡히지 않았다 → [[crud]]

### 다음 날 같은 자리에서 다시 틀리고, 이번에는 잡힌다

게시판 CRUD 를 만들 때 이 실수가 한 번 더 나온다. 그런데 **세 곳이 아니라 한 곳**이고, **같은 노트 안에서 고쳐진다.**

| 메서드 | 「글 … 메서드 만들기」 절 | 「완성된 코드」 절 |
|---|---|---|
| `viewBoard` | `boardNo >= boardLength` | `boardNo > boardLength` |
| `updateBoard` | `boardNo > boardLength` | `boardNo > boardLength` |
| `deleteBoard` | `boardNo > boardLength` | `boardNo > boardLength` |

하나씩 만들 때는 첫 메서드에서 틀렸고 뒤의 둘은 맞았다. 그리고 마지막에 전체를 다시 옮겨 적는 과정에서 `viewBoard` 도 `>` 가 되었다. **전날 세 곳이 같이 틀렸던 것과 갈리는 지점은 「복사했는가」다** — 프로젝트 쪽은 틀린 조회를 복사해 변경·삭제로 퍼뜨렸고, 게시판 쪽은 각각 쓰다가 다시 정리했다.

삭제는 루프 시작값에 번호를 그대로 쓴다.

```java
for (int i = boardNo; i < boardLength; i++) {
  boards[i - 1] = boards[i];          // boardNo 번은 boardNo-1 인덱스, 그 다음 칸부터 당긴다
}
boards[--boardLength] = null;
```

`boardNo` 로 시작하는 것이 「지울 칸의 다음 칸」이다 — 번호를 인덱스로 바꾸는 `-1` 이 여기서는 **루프 안의 대입식**에 들어가 있다 → [[array-element-removal]]

### 번호를 받는 메서드와 인덱스를 받는 메서드가 섞인다

이 필기는 두 규약이 함께 사는 코드를 만들었다.

```java
public static User findByNo(int userNo) { ...; return users[userNo - 1]; }   // 번호를 받는다
public User getMember(int index)        { return users[index]; }             // 인덱스를 받는다
public void deleteMember(int index)     { ... }                             // 인덱스를 받는다
```

`viewProject` 는 팀원을 찍을 때 `getMember(i)` 로 인덱스를 넘기고, `addMembers` 는 `findByNo(userNo)` 로 번호를 넘긴다. **이름의 `No` 와 `index` 가 그 규약을 알려 주는 유일한 단서**이므로, 이름을 잘못 읽으면 `-1` 이 두 번 되거나 한 번도 안 된다 → [[cohesion]]

번호 체계에 **배열에 없는 값**을 얹기도 한다. 팀원 추가 루프의 종료 값 `0` 이 그것이다 — 유효 번호가 1부터라서 `0` 이 비어 있는 것을 이용한 것이다.

```java
int userNo = Prompt.inputInt("추가할 팀원 번호?(종료:0)");
if (userNo == 0) break;
```

### 셋째 회차에 번호가 인덱스에서 떨어져 나간다

`-1` 변환이 성립하려면 **번호가 곧 위치**여야 한다. 그 전제가 다음 회차에서 깨진다 — 번호를 데이터가 필드로 들고 가면서 `-1` 로 이어지던 다리가 없어진다 → [[surrogate-key]]

세 자리가 전부 바뀐다.

| | 앞의 두 회차 | 이 회차 |
|---|---|---|
| 목록 출력 | `printf("%d ...", i + 1, ...)` | `printf("%d ...", user.getNo(), ...)` |
| 조회 | `if (no < 1 \|\| no > size)` → `users[no - 1]` | `findByNo(no)` → `if (user == null)` |
| 삭제 루프 시작 | `for (int i = userNo; ...)` | `int index = indexOf(user); for (int i = index + 1; ...)` |

**`-1` 이 사라진 것이 아니라 자리를 옮겼다.** 목록에서는 아예 없어졌고(번호를 계산하지 않으니까), 삭제에서는 `indexOf` 가 **인덱스를 되찾아 온 뒤** `+ 1` 로 다음 칸을 가리키는 형태로 남았다 → [[array-element-removal]]

가장 크게 달라진 것은 **검사할 것이 「범위」에서 「존재」로 바뀐 것**이다.

```java
// 앞의 회차 — 번호가 위치이므로 범위가 곧 유효성이다
if (userNo < 1 || userNo > userLength) { ... return; }
User user = users[userNo - 1];

// 이 회차 — 위치를 모르니 있는지 없는지만 물을 수 있다
User user = findByNo(userNo);
if (user == null) { ... return; }
```

전날까지 이 자리에서 `>` 와 `>=` 가 갈려 마지막 하나에 손댈 수 없었던 종류의 실수는, **이 형태에서는 쓸 자리가 없다.** 경계 조건이 코드에서 사라졌기 때문이다 — 고쳐서 없어진 것이 아니라 **묻는 질문이 바뀌어서** 없어졌다.

그리고 대가가 있다. 번호가 위치와 무관해지면 **번호 하나를 찾는 데 배열을 훑어야** 한다. 한 글자 부등호 실수를 없애고 O(n) 탐색을 얻은 것이다 → [[linear-search]]

목록에서 인덱스가 완전히 없어지는 것도 이 회차다.

```java
for (User user : UserList.toArray()) {
  System.out.printf("%d %s %s\n", user.getNo(), user.getName(), user.getEmail());
}
```

**`i` 를 안 쓰니 `for-each` 로 갈 수 있다.** 앞선 회차에서 「for-each 로 바꾸면 번호가 사라진다」가 걸림돌이었는데, 번호가 데이터 안에 있으면 그 대가가 없다 → [[for-loop]] · [[defensive-copy]]

## 왜 중요한가

**0부터 세는 것은 기계의 사정이고 1부터 세는 것은 사람의 사정이라, 둘을 잇는 자리가 반드시 생긴다.** 어디서 변환할지 정해 두지 않으면 한 프로그램 안에 두 규약이 섞이고, 그때부터는 메서드마다 「이건 번호인가 인덱스인가」를 확인해야 한다. 규칙은 **경계에서 한 번 바꾸고 안에서는 인덱스로만 다루기**다.

**경계값 하나가 기능을 조용히 삭제한다.** `>=` 와 `>` 의 차이는 마지막 하나에서만 드러나므로, 프로젝트를 둘 등록해 1번을 조회하는 확인은 통과한다. 게다가 증상이 예외나 오류가 아니라 **「없는 프로젝트번호 입니다」라는 정상 안내로 위장**해서 나온다 — 사용자는 자기가 번호를 잘못 넣은 줄 안다 → [[if-statement]]

**복사한 코드에서 이 실수가 가장 잘 살아남는다.** 구조가 같아서 복사하는데, 검사 조건은 한 글자라 눈에 걸리지 않는다. 「구조를 복사할 때 같이 봐야 하는 것은 경계 조건」이라는 것이 이 자리의 교훈이다.

## 경계와 오해

- **`projectNo >= projectLength` 는 이 필기의 오류다** — 유효한 번호가 1 ~ `projectLength` 이므로 `projectNo > projectLength` 여야 한다. 같은 파일의 회원 코드는 `>` 로 맞다. 인덱스 범위(`i < size`)와 번호 범위(`no <= size`)를 같은 모양으로 쓴 것이 원인으로 보인다.
- **번호 ≠ 인덱스 ≠ 식별자** — 세 번째가 빠지기 쉽다. Day17·Day18 의 번호는 **지금 목록에서 몇 번째인가**일 뿐이어서 삭제하면 다른 것을 가리킨다. 「3번 회원」을 고정된 이름으로 읽으면 어긋나고, Day19 에서 그 세 번째가 실제로 만들어진다 → [[array-element-removal]] · [[surrogate-key]]
- **셋의 값이 처음에는 다 같다** — 등록만 하고 아무것도 지우지 않으면 인덱스 `2` · 목록 번호 `3` · 식별 번호 `3` 이고, 화면에 보이는 숫자는 같다. **삭제를 한 번 하는 순간에만 갈리므로**, 지우기 전 확인만으로는 어느 체계를 쓰고 있는지 드러나지 않는다.
- **범위 검사를 없애는 것과 유효성 검사를 없애는 것은 다르다** — Day19 는 `if (no < 1 || no > size)` 를 지웠지만 검사를 지운 것이 아니다. `findByNo` 의 `null` 검사가 그 자리를 받았고, **양쪽 끝을 재는 일이 「있는지 보는 일」로 대체**된 것이다. 「검사가 사라졌다」로 읽으면 `null` 을 안 보고 쓰는 코드가 나온다 → [[linear-search]]
- **`0` 이 종료 값으로 남는 이유가 달라졌다** — 앞의 회차에서는 유효 번호가 1부터라서 `0` 이 비어 있었다. 식별 번호 체계에서도 `0` 은 비어 있는데, 그 이유는 **카운터가 `++seqNo` 로 1부터 발급하기 때문**이다. 결과는 같지만 근거가 다르고, 발급을 `seqNo++` 로 바꾸면 첫 회원이 `0` 번이 되어 그 신호 자리가 무너진다 → [[increment-operator]]
- **식별 번호도 여전히 1부터다** — 인덱스와의 연결이 끊겼는데도 `++seqNo` 로 1부터 세는 것을 골랐다. 이제는 기계의 사정이 아니라 **사람이 읽을 번호라는 이유만** 남아 있고, `0` 을 「번호 없음」으로 쓸 수 있다는 이점이 따라온다 → [[default-initialization]]
- **검사 없이 `- 1` 하면 두 방향으로 터진다** — `0` 을 넣으면 `-1` 인덱스, 개수보다 큰 수를 넣으면 범위 초과다. 둘 다 `ArrayIndexOutOfBoundsException` 이지만 **`0` 은 「엔터에 가까운 값」이라 훨씬 자주 들어온다** → [[array]]
- **`i + 1` 은 번호를 만드는 것이 아니다** — 배열 위치를 사람이 읽는 순번으로 **보여 주는** 것이다. 그 값을 저장하거나 나중에 다시 쓰면 삭제 뒤에 틀린다.
- **개수와 마지막 인덱스는 다르다** — `userLength` 는 개수이고 마지막 인덱스는 `userLength - 1` 이다. `deleteMembers` 가 `getMemberSize() - 1` 에서 시작하는 것이 그 값이다.
- **화면의 번호가 배열에 없을 수도 있다** — 서브메뉴의 `9. 이전` 이나 팀원 추가의 종료 값 `0` 처럼, 목록에 없는 번호를 화면 번호 체계에 얹는다. 그러면 **번호 검사만으로는 그 값을 처리할 수 없고 앞에서 따로 걸러야** 한다 → [[command-loop]]
- **1부터 세는 것이 사용자를 위한 것만은 아니다** — `0` 을 「없음·종료」로 비워 둘 수 있다는 이점이 딸려 온다. 인덱스를 그대로 노출하면 `0` 이 유효한 값이 되어 그 신호 자리가 사라진다.
- **한 노트 안에서 초안과 최종이 다를 수 있다** — Day18 의 `viewBoard` 는 「글 조회 메서드 만들기」 절에서 `>=` 이고 「완성된 코드」 절에서 `>` 다. 「이 필기가 이렇게 썼다」로 한쪽만 인용하면 나머지 절과 어긋나므로, **어느 절의 코드인지까지 같이 적어야** 한다.
- **경계 조건이 맞는지는 이 실수를 한 번 겪은 뒤에야 확인 항목이 된다** — 게시판 쪽에서 셋 중 둘이 처음부터 맞았고 나머지 하나도 정리되었다. 고쳐진 이유가 「검사기가 잡았다」가 아니라 **전체를 다시 옮겨 적었기 때문**이라는 것이 이 자리의 한계다. 다음에 같은 실수를 막아 주는 장치는 아직 없다.
