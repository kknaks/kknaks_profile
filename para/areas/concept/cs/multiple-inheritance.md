# 다중 상속 (Multiple Inheritance)

**한 타입이 둘 이상의 상위 타입을 동시에 갖는 것.** 자바는 클래스에는 이것을 금지하고 인터페이스에는 허용한다. 갈리는 이유는 개수가 아니라 **물려받는 것에 상태와 구현이 있는가**다.

## 정의

문법이 셋으로 갈린다. 「상속」이라는 한 단어가 세 자리에서 다르게 쓰이므로 키워드로 구별하는 것이 안전하다.

| 받는 쪽 | 주는 쪽 | 키워드 | 개수 |
|---|---|---|---|
| 클래스 | 클래스 | `extends` | **하나** |
| 클래스 | 인터페이스 | `implements` | 여럿 |
| 인터페이스 | 인터페이스 | **`extends`** | 여럿 |

```java
interface A { void m1(); }
interface B { void m2(); }

interface C extends A, B { }              // 인터페이스가 인터페이스 여럿을 받는다
class My implements A, B { ... }          // 클래스가 인터페이스 여럿을 받는다
class My2 extends P1, P2 { ... }          // 컴파일 오류 — 클래스는 하나만
```

인터페이스끼리는 `implements` 가 아니라 `extends` 다. 필기 3.2 는 이것을 「여러개의 인터페이스를 상속 받아 인터페이스를 만들수 있다」로 말로만 적었다.

### 겹쳐도 괜찮은 이유

두 상위 인터페이스에 **같은 이름 같은 매개변수**의 메서드가 있어도 받을 수 있다. 필기가 그 근거를 정확히 짚었다 — 「리턴타입이 같은 메소드명을 받을 수 있는 이유는 상속받는 메소드가 추상메서드 이기 때문에 가능하다」.

몸통이 없으므로 **고를 것이 없다.** 두 선언은 같은 약속이 두 번 적힌 것이고, 구현 클래스가 메서드 하나를 채우면 양쪽이 동시에 만족된다.

```java
interface A { void m(); }
interface B { void m(); }

class My implements A, B {
  @Override public void m() { }           // 하나로 둘 다 채워진다
}
```

리턴 타입이 서로 맞지 않으면 이것이 깨진다 — 채워야 할 몸통이 하나인데 돌려줄 타입이 둘이 되기 때문이다.

```java
interface A { int m(); }
interface B { String m(); }

interface C extends A, B { }              // 컴파일 오류
```

### 3.1 의 표가 묻는 것

필기 3.1 은 표 하나만 남기고 답을 적지 않았다. 같은 인스턴스 `new My()` 를 `My`·`B`·`A` 세 타입으로 받아 놓고 `m1()`·`m2()`·`X()` 를 부르는 세 case 다.

답은 하나의 규칙에서 나온다 — **부를 수 있는 목록은 실제 타입이 아니라 선언 타입이 정한다.** 셋 다 같은 객체를 가리키고 실행되는 몸통도 같지만, **컴파일이 되는지는 왼쪽에 적은 타입에 그 메서드가 선언되어 있는지**로 갈린다.

| 선언 타입 | 부를 수 있는 것 |
|---|---|
| `My` | `My` 와 그 상위 인터페이스들이 가진 것 전부 |
| `B` | `B` 와 `B` 의 상위에 선언된 것만 |
| `A` | `A` 에 선언된 것만 |

그림이 남지 않아 `A`·`B` 가 각각 무엇을 선언했는지는 확인할 수 없지만, **표가 세 case 에 똑같이 세 줄을 적어 둔 것이 그대로 참일 수 있는 경우는 하나뿐이다** — 최상위인 `A` 가 `m1`·`m2`·`X` 를 다 선언하고 있어야 한다. `X()` 가 `My` 에만 있는 메서드라면 case 2 와 case 3 은 **컴파일 오류**이고, `X` 를 부르려면 `((My) obj).X()` 로 되돌려야 한다 → [[type-casting]] · [[polymorphism]]

## 사용 예시

아흐레 앞선 회차의 실습이 이 조합을 이미 만들어 두었다. 한 클래스가 `extends` 와 `implements` 를 동시에 쓰는 형태다.

```java
public abstract class AbstractList implements List {   // 약속을 받는다
  protected int size;                                  // 상태를 갖는다
}

public class ArrayList extends AbstractList { ... }    // 상태와 구현을 물려받는다
public class LinkedList extends AbstractList { ... }
```

**두 축이 한 클래스에서 만난다.** 물려받을 것이 있는 쪽(`extends`)은 하나뿐이고, 지킬 약속(`implements`)은 여러 개 붙을 수 있다. 그래서 「무엇이다」는 하나로 유지되면서 「무엇을 할 수 있다」는 얼마든지 늘어난다 → [[abstract-class]] · [[interface]]

## 왜 중요한가

**클래스 단일 상속의 대가를 인터페이스가 갚는다.** 부모를 하나만 고를 수 있으므로, 이미 `AbstractList` 를 상속한 클래스는 다른 클래스의 코드를 더 물려받을 방법이 없다. 그런데 **역할은 여러 개일 수 있다** — 「목록이다」와 「복제할 수 있다」와 「비교할 수 있다」는 서로 배타적이지 않다. 인터페이스가 여럿 붙는 덕분에 **역할의 개수가 상속 계층의 모양에 갇히지 않는다** → [[object-cloning]]

**그리고 「무엇을 물려받는가」를 두 종류로 갈라 놓는다.** 상태와 구현은 한 곳에서만 오고(그래서 충돌이 없고), 약속은 여러 곳에서 온다(겹쳐도 합쳐진다). 자바가 다중 상속을 금지한 것이 아니라 **물려받을 수 있는 것을 나눈 것**이라고 읽어야 이 설계가 보인다.

## 경계와 오해

- **다중 상속 금지 ≠ 다중 구현 금지** — 「자바는 다중 상속을 지원하지 않는다」로 외우면 `implements A, B` 를 보고 멈춘다. 금지된 것은 **클래스를 여럿 `extends` 하는 것**뿐이고, 인터페이스는 클래스가 여럿 받는 것도 인터페이스가 여럿 받는 것도 된다.
- **인터페이스의 `extends` ≠ 클래스의 `extends`** — 인터페이스가 인터페이스를 받을 때는 `implements` 가 아니라 `extends` 이고, 이때는 **여러 개를 나열할 수 있다.** 같은 키워드가 클래스에서는 하나로 제한되므로 「`extends` 는 하나, `implements` 는 여럿」으로 외우면 `interface C extends A, B` 에서 어긋난다.
- **「리턴 타입이 다르면 컴파일러가 두 메소드를 구분 할 수 없다」는 이유가 뒤집혀 있다** — 필기의 설명은 컴파일러가 **구분하려다 실패하는** 것처럼 읽히는데, 애초에 자바는 리턴 타입으로 메서드를 구분하지 않는다. 메서드 시그니처는 **이름과 매개변수**뿐이므로 두 선언은 처음부터 **같은 메서드 하나**이고, 문제는 「구분이 안 된다」가 아니라 **하나뿐인 그 메서드가 돌려줄 타입이 둘로 지정되었다**는 것이다 → [[method]]
- **「리턴 타입이 다르면 불가능하다」도 반쪽이다** — 한쪽이 다른 쪽의 하위 타입이면 받을 수 있고, 그때는 **더 좁은 쪽이 이긴다.** `Object m()` 과 `String m()` 을 함께 받으면 `String m()` 을 구현하면 되고, 오버라이딩이 반환 타입을 좁히는 것을 허용하는 것과 같은 규칙이다. 「같아야 한다」가 아니라 **「한쪽이 다른 쪽으로 대입될 수 있어야 한다」**가 정확한 형태다 → [[method-overriding]]
- **클래스 다중 상속이 막힌 이유는 이름 충돌이 아니다** — 이름이 겹치는 것 자체는 추상메서드에서도 일어나는데 그쪽은 허용된다. 갈리는 것은 **몸통과 필드**다. 두 부모가 같은 이름의 필드를 갖고 있으면 자식의 인스턴스에 그 값이 두 벌 생기고, 같은 메서드에 몸통이 둘이면 실행할 것을 골라야 한다. **「고를 것이 있는가」가 기준**이고, 그래서 상태 없는 인터페이스에는 같은 금지가 필요하지 않았다 → [[inheritance]] · [[instance]]
- **디폴트 메서드가 생기면서 그 충돌이 인터페이스로 돌아왔다** — 몸통이 있는 메서드가 두 인터페이스에서 같은 시그니처로 오면 **컴파일이 막힌다.** 자바의 답은 컴파일러가 고르는 것이 아니라 **구현 클래스가 재정의해서 `A.super.m()` 으로 직접 고르게** 하는 것이다. 「인터페이스는 다중 상속해도 안전하다」는 Java 8 이전에만 무조건 참이다 → [[default-method]]
- **상수 필드가 겹치면 이름만으로는 못 부른다** — 두 인터페이스에 같은 이름의 상수가 있으면 그 이름을 그냥 쓰는 코드가 모호해져 컴파일 에러이고, `A.MAX` 처럼 인터페이스 이름을 붙여야 한다. 메서드는 하나로 합쳐지는데 **필드는 합쳐지지 않는다** — 인터페이스에 상수를 두는 것이 공짜가 아닌 이유다 → [[static-member]] · [[interface]]
- **다중 구현은 코드 재사용이 아니다** — `implements A, B` 로 얻는 것은 **채워야 할 목록**이고, 물려받는 코드는 (디폴트 메서드를 빼면) 한 줄도 없다. 인터페이스를 열 개 붙이면 할 일이 열 배가 되는 것이지 기능이 열 배가 되는 것이 아니다 → [[interface]]
- **뿌리가 여럿이 되지는 않는다** — 인터페이스를 몇 개 붙이든 클래스의 조상 계층은 `Object` 하나로 모인다. 인터페이스는 **타입 목록에 이름을 더하는 것**이고 상속 계층을 갈라 놓는 것이 아니다 → [[object-class]]
