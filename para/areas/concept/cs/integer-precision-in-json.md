# JSON 정수 정밀도 손실 (2^53 경계)

**큰 정수를 JSON number 로 실어 보내면 받는 쪽(특히 자바스크립트)에서 값이 조용히 바뀐다.** JSON 스펙에는 정수·실수 구분이 없고, JS 의 `number` 는 IEEE 754 double 이라 안전하게 표현되는 정수 상한이 `2^53 - 1`(`Number.MAX_SAFE_INTEGER`) 이기 때문이다.

## 정의

- 서버의 `int64`(BIGINT·스노우플레이크 ID·타임스탬프ns 등)는 최대 `2^63 - 1` 까지 간다.
- JSON 으로 `{"id": 3078219087654321}` 처럼 **숫자 리터럴**로 내보내면, JS `JSON.parse` 는 이를 double 로 파싱한다.
- `2^53` 을 넘는 부분은 표현 비트가 없어 **가장 가까운 표현 가능한 값으로 반올림**된다 → 뒷자리가 달라진 다른 ID 가 된다. 에러도 안 난다.

```js
JSON.parse('{"id": 3078219087654321123}').id  // 3078219087654321000  ← 뒷자리 소실
```

**해결은 문자열 직렬화다.** `{"id": "3078219087654321123"}` 로 내보내면 double 을 거치지 않아 원값이 보존된다. 받는 쪽은 문자열로 다루거나 `BigInt` 로 파싱한다.

## 왜 중요한가

**같은 값을 주고받았는데 양쪽 값이 다르다** — 계약이 조용히 깨지는 부류라 로그에서 잡기 어렵다. kakao-task 에서 카톡 `chatId`(큰 정수)를 JSON number 로 내보내자 프런트에서 2^53 위 자리가 뭉개져 방을 못 찾았다 → chatId 를 **문자열로 직렬화**해 해결.

## 경계와 오해

- **작은 정수는 안전하다** — 2^53 이하면 double 로도 정확하다. 경계를 넘는 식별자·카운터에서만 터진다.
- **서버 언어의 문제가 아니다** — 서버가 int64 를 정확히 들고 있어도, JSON number 로 나가는 순간 수신측 파서의 표현력에 종속된다. 계약(직렬화 형식)의 문제다.
- **부동소수점 오차와 뿌리는 같다** — 둘 다 유효 비트가 유한한 double 이 원인이다([[floating-point]]).
