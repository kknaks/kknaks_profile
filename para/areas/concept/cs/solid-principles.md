# SOLID 원칙 (SOLID Principles)

**객체지향 설계에서 「이 구조가 나중에 고치기 쉬운가」를 재는 다섯 개의 기준.** 다섯 머리글자를 모아 부르는 이름이지 하나의 규칙이 아니고, **다섯 개가 서로를 조건으로 쓴다** — 이 필기의 예제가 한 단계에 한 원칙씩 충족시키며 다섯 그림을 지나가는 것이 그 관계를 그대로 보여 준다.

## 정의

| 머리글자 | 이름 | 원칙 | 상세 |
|---|---|---|---|
| S | Single Responsibility | 하나의 클래스는 하나의 책임 | 아래 |
| O | Open/Closed | 확장에는 열려 있고 수정에는 닫혀 있어야 한다 | [[open-closed-principle]] |
| L | Liskov Substitution | 서브타입은 언제나 자신의 기반 타입으로 교체할 수 있어야 한다 | 아래 |
| I | Interface Segregation | 특정 클라이언트를 위한 인터페이스 여러 개가 범용 인터페이스 하나보다 낫다 | [[interface-segregation-principle]] |
| D | Dependency Inversion | 고수준 모듈은 저수준 모듈에 의존해서는 안 된다. 둘 다 추상화에 의존해야 한다 | [[dependency-inversion-principle]] |

### SRP — 하나의 책임

필기의 예가 「사용자 정보를 처리하는 클래스는 사용자 데이터베이스 접근과 같은 역할만 한다」다. **재는 것은 메서드 개수가 아니라 「이 클래스를 고치게 만드는 이유가 몇 가지인가」**다. 화면 형식이 바뀌어도 고쳐야 하고 저장 방식이 바뀌어도 고쳐야 하는 클래스는 책임이 둘이다.

19일 앞선 회차가 이 원칙을 이름 없이 이미 수행했다 — `ProjectCommand` 를 「UI처리」와 「데이터보관처리」로 갈라 `ProjectList` 를 떼어낸 것이 그것이고, 거기서 쓴 이름은 GRASP 의 High Cohesion 이었다 → [[cohesion]] · [[grasp]]

### LSP — 교체 가능성

필기의 예가 「Rectangle 클래스를 상속받은 Square 클래스는 Rectangle 클래스로 교체해도 문제 없이 작동해야 한다」다. **이 예는 교과서에서 성립하지 않는 쪽으로 유명한 것**이라 그대로 외우면 반대로 기억한다 — `Rectangle` 에 `setWidth`·`setHeight` 가 있으면 정사각형은 한쪽을 바꿀 때 다른 쪽도 바뀌어야 하므로, 「너비를 3으로 바꾸고 높이를 4로 바꾼 뒤 면적은 12」라는 부모의 규칙이 깨진다. **정사각형은 직사각형이지만 「변경 가능한 직사각형」의 서브타입은 아니다.**

그래서 LSP 가 요구하는 것은 `extends` 가 컴파일되는 것이 아니다. **부모 타입으로 코드를 쓴 사람이 믿고 있던 것을 자식이 지키는가**이고, 그 「믿고 있던 것」은 대개 코드에 적혀 있지 않다 → [[inheritance]] · [[polymorphism]]

## 사용 예시

이 회차의 램프/스위치 예제는 **다섯 그림에 다섯 원칙을 하나씩 붙인 하나의 시퀀스**다. 각 단계가 앞 단계의 남은 문제를 이름으로 지목한다.

| 단계 | 무엇을 했나 | 필기가 지목한 남은 문제 |
|---|---|---|
| 1 | `Switch` 가 `FluoLamp` 만 쓴다 | 「고수준 모듈이 저수준 모듈에 의존적이다」 |
| 2 | `Lamp` 부모를 만들어 다형성으로 제어 | 「Switch의 새로운 기능 추가 시 OCP를 충족시키지 못한다」 |
| 3 | 더 높은 상위 클래스로 올려 전부 제어 | 「Switch로 제어안해도 되는 코드도 강제로 사용해야한다 → ISP 충족 못함」 |
| 4 | `Switch` 가 쓸 인터페이스만 따로 만든다 | 「새로운 제품군이 들어오면 Switch클래스 내부에서 코드 수정이 필요하다 → DIP 충족 못함」 |
| 5 | 의존 객체를 만들지 않고 외부에서 대입받는다 | (끝) |

**한 단계가 한 원칙을 충족시키고 다음 원칙을 위반한 채로 남는다.** 이것이 이 예제의 형태이고, 그래서 다섯 원칙은 체크리스트가 아니라 **순서가 있는 하나의 리팩터링 경로**로 배워진다 → [[refactoring]]

## 왜 중요한가

**「좋은 설계」를 취향이 아니라 이름으로 반박할 수 있게 된다.** 하루 앞선 회차는 리팩터링 절의 제목에 기준의 이름(High Cohesion · Generalization)을 박았고, 이 회차는 그림마다 위반된 원칙의 이름을 적었다. 이름이 있으면 되돌리려는 사람도 같은 축에서 말해야 한다 → [[refactoring]] · [[grasp]]

**그리고 「어디까지 갈지」를 고를 수 있게 된다.** 다섯 단계 중 어디서 멈춰도 프로그램은 돌고, 각 단계는 클래스와 인터페이스를 하나씩 늘린다. 원칙이 이름으로 나뉘어 있으면 **「지금은 2단계까지만」이 판단으로 남고**, 뭉쳐 있으면 「SOLID 를 지켰다/안 지켰다」의 두 값만 남는다.

## 경계와 오해

- **SOLID ≠ 패턴** — 이 필기의 제목이 「SOLID Pattern」인데 패턴이 아니라 **원칙**이다. 패턴은 「이런 상황에 이런 구조를 쓴다」는 해법의 이름(→ [[template-method-pattern]] · [[singleton-pattern]])이고, SOLID 는 만든 구조를 재는 기준이다. 방향이 반대다 — 패턴은 처방이고 원칙은 검사다. 그래서 「SOLID 를 적용한다」는 말은 정확히는 「원칙에 걸리는 자리를 찾아 고친다」다.
- **SOLID ≠ GRASP** — 둘 다 객체지향 설계 지침 묶음이고 이 필기는 하루 사이에 둘을 배웠지만 답하는 질문이 다르다. GRASP 는 **「이 일을 누가 해야 하나」**(책임 배치)이고 SOLID 는 **「이 구조가 변경에 견디나」**(변경 비용)다. 겹치는 자리가 있어서 헷갈린다 — SRP 는 GRASP 의 High Cohesion 과 같은 방향이고 DIP 는 Protected Variations 와 같은 방향이다. **다른 이름으로 같은 것을 두 번 배운 것**이며, 하루 앞 회차가 「Generalization」을 GRASP 열 번째 지침처럼 적은 것도 이 뒤섞임의 결과다 → [[grasp]] · [[generalization]]
- **다섯 개가 독립이 아니다** — 4단계의 「새로운 제품군이 들어오면 `Switch` 내부를 고쳐야 한다」는 표현 그대로는 **OCP 위반**인데 필기는 DIP 로 적었다. 어긋난 것이 아니다 — `Switch` 가 구현체를 스스로 만들기 때문에(DIP 위반) 새 제품군에서 그 줄을 고쳐야 하는 것(OCP 위반)이므로, **DIP 위반이 원인이고 OCP 위반이 증상**이다. 원칙 하나를 지키면 다른 원칙이 따라 지켜지는 자리가 많아, 「몇 번 위반인가」를 세는 것보다 **원인 쪽 이름을 잡는 것**이 실용적이다 → [[open-closed-principle]] · [[dependency-inversion-principle]]
- **머리글자 순서(S-O-L-I-D)는 배우는 순서도 적용 순서도 아니다** — 이 필기의 예제는 D → O → I → D 순으로 지나간다. 다섯 글자가 예쁘게 모이도록 골라 배열한 이름이고, **L 은 이 회차의 예제에 등장하지 않는다.**
- **원칙이 지켜졌는지는 코드를 보는 것으로 판정되지 않는다** — LSP 는 「부모 타입으로 쓴 코드가 계속 맞나」이므로 **자식만 봐서는 알 수 없고**, OCP 는 「무엇이 변할 것인가」를 가정해야 판정된다. 그래서 이 다섯 개는 컴파일러도 정적 분석기도 대신 봐 줄 수 없고, 하루 앞 회차의 `indexOf` 회귀처럼 **원칙과 무관한 한 줄이 프로그램을 죽이는 일**은 별개로 일어난다 → [[object-equality]]
- **SRP 의 「하나」는 기능 하나가 아니다** — 「각 클래스는 하나의 기능만 가져야 한다」로 읽으면 메서드가 여러 개인 클래스가 전부 위반이 된다. 실제 기준은 **변경 이유가 하나인가**이고, 그래서 `UserCommand` 가 등록·조회·변경·삭제 다섯 개를 갖는 것은 위반이 아니다 — 다섯이 같은 이유로 같이 바뀌기 때문이다 → [[cohesion]] · [[crud]]
- **「하나의 책임」과 「높은 응집도」를 같은 말로 쓰면 반대 방향의 실수를 못 본다** — 응집도는 「같이 바뀔 것이 같이 있나」를 양쪽으로 재므로 **너무 잘게 쪼갠 것도 잡아 내는데**, SRP 는 「둘이 섞여 있나」만 본다. 하루 앞 회차가 응집도를 올린 결과 Command 넷에 같은 코드가 생겨 다시 일반화가 필요해진 것이 그 자리다 → [[cohesion]] · [[generalization]]
