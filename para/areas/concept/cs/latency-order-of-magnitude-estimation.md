# 레이턴시 차수 추정

레이턴시 차수 추정은 CPU 캐시·메모리·저장장치·네트워크 연산의 지연을 나노초·마이크로초·밀리초 수준으로 분류하고, 그 상대적 격차로 아직 만들지 않은 시스템의 비용과 병목을 근사하는 방법이다.

## 정의

정확한 하드웨어 수치를 예측하는 것이 아니라 다음 순서로 요청 경로의 규모를 계산한다.

1. 요청 경로를 함수 호출, 메모리 접근, 저장장치 I/O, 서비스 간 통신 같은 단계로 분해한다.
2. 각 단계의 비용을 정확한 값보다 `ns`·`μs`·`ms` 중 어느 차수인지로 분류한다.
3. 직렬 단계는 합산하고, 동일한 작업이 반복되면 비용에 횟수를 곱한다.
4. 병렬 단계는 가장 느린 분기와 병렬 실행을 조정하는 비용을 중심으로 계산한다.
5. 전체에서 큰 비중을 차지하는 항을 병목 후보로 삼아 캐시, 배치, 호출 제거, 데이터 배치 변경 같은 대안을 비교한다.
6. 후보를 좁힌 뒤 실제 워크로드의 벤치마크로 근삿값을 교체한다.

대표적인 비용 계층은 다음과 같다.

| 계층 | 대표 연산 | 시간 규모 |
|---|---|---:|
| CPU | 단순 명령, L1 캐시 접근 | 수 ns 이하~수 ns |
| 메모리 | 주 메모리 접근 | 약 100ns 규모 |
| 로컬 계산·통신 | 작은 블록 압축, 데이터센터 네트워크 | 수 μs~수백 μs |
| SSD | 랜덤 읽기, 큰 블록 순차 읽기 | μs~ms |
| HDD | 탐색을 수반하는 읽기 | 수~수십 ms |
| 원거리 네트워크 | 대륙 간 왕복 | 약 100ms 이상 |

개별 값은 장비와 연도에 따라 달라지지만, CPU 캐시 → 메모리 → SSD → 디스크·원거리 네트워크로 비용이 커지는 상대적 서열은 초기 설계의 기준점으로 쓸 수 있다.

## 사용 예시

캐시 적중 시 0.5ms, 캐시 실패 후 데이터베이스 조회 시 10ms가 걸리고 적중률이 90%라면 평균 지연을 다음과 같이 근사할 수 있다.

```text
예상 지연 = 적중률 × 적중 비용 + 실패율 × 실패 비용
          = 0.9 × 0.5ms + 0.1 × 10ms
          = 1.45ms
```

이 계산으로 캐시가 없는 10ms 경로와 후보 구조를 비교할 수 있다. 다만 실제 캐시 실패 경로가 캐시 확인 비용과 데이터베이스 비용을 모두 지불한다면 그 합을 실패 비용으로 넣어야 한다. 연결 풀 대기, 직렬화, 재시도 같은 단계도 요청 경로에 존재하면 별도 항으로 더한다.

압축 여부도 같은 방식으로 판단한다. 압축하지 않은 전송이 10μs이고, 압축에 3μs가 들지만 데이터 크기가 절반이 되어 전송이 5μs로 줄어든다면 압축 경로는 `3 + 5 = 8μs`다. 이 조건에서는 압축이 약 2μs 이득이지만 데이터 크기·압축률·네트워크 속도가 바뀌면 결론도 달라진다.

## 왜 중요한가

“캐시가 더 빠르다”나 “원격 호출은 느리다”는 말만으로는 설계 대안을 비교할 수 없다. 시간 단위와 호출 횟수를 붙이면 어떤 비용이 전체를 지배하는지, 최적화가 최대 어느 정도 효과를 낼 수 있는지, 어느 가정을 실제로 검증해야 하는지가 드러난다.

특히 프로세스 내부 호출을 서비스 간 호출로 바꾸면 네트워크 RTT 외에도 직렬화·역직렬화, 암호화, 프록시, 큐 대기와 장애 처리 비용이 생긴다. 이 차수를 알고 있으면 [[microservice-architecture]]의 독립 배포·확장성이라는 이점과 원격 경계의 성능 비용을 같은 의사 결정 안에서 비교할 수 있다.

## 경계와 오해

- **차수 추정 ≠ 벤치마크** — 고전적인 레이턴시 표는 병목 후보를 찾는 출발점이다. 실제 장비, 데이터 크기, 부하와 네트워크 토폴로지를 반영한 측정을 대신하지 않는다.
- **단일 연산 시간의 역수 ≠ 서버 처리량** — `1 ÷ 레이턴시`는 단순한 이론적 상한일 뿐이다. 코어 수, 동시성, 대역폭, 잠금, 큐 대기와 응답 크기를 포함하지 않는다. 레이턴시와 처리량의 관계는 [[little-law]]와 함께 봐야 한다.
- **평균 레이턴시 ≠ 사용자 경험 전체** — 평균은 느린 소수의 요청을 감춘다. p95·p99 같은 꼬리 지연은 [[performance-testing]]으로 따로 측정해야 한다.
- **레이턴시 ≠ 아키텍처의 유일한 기준** — 처리량, 비용, 일관성, 장애 복구, 독립 배포와 운영 복잡성도 함께 비교해야 한다.
- **캐시 접근 ≠ 항상 로컬 메모리 접근** — 원격 Redis 같은 캐시는 네트워크 왕복을 포함한다. 적중률, 무효화와 장애 시 원본 저장소 부하까지 포함해야 한다 → [[caching]].
- **시간 단위는 서로 바꿔 쓸 수 없다** — `1μs = 1,000ns`, `1ms = 1,000μs`, `1s = 1,000ms`이므로 단위를 섞으면 1,000배 또는 100만 배의 계산 오류가 난다.
