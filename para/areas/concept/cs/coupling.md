# 결합도 (Coupling)

**한 코드가 다른 코드에 대해 알아야 하는 것의 양과 종류.** 부르는 쪽이 부르는 대상의 클래스 이름·메서드 이름·매개변수 개수를 알고 있으면 그것이 결합이고, 그 대상이 바뀔 때 부르는 쪽도 같이 바뀐다.

## 정의

결합은 **누가 누구를 아는가**의 관계이므로 방향이 있다. 이 회차의 필기가 그 두 자리에 이름을 붙였다.

| 자리 | 필기의 표현 | 하는 일 |
|---|---|---|
| 호출자 | 「클라이언트로 구현체를 호출 하는 클래스」 | 일을 시킨다 |
| 피호출자 | 「구현체로 인터페이스의 규칙을 적용받아 메소드를 생성」 | 일을 한다 |

결합도가 높다는 것은 **호출자가 피호출자의 사정을 많이 안다**는 뜻이다. 세 노동자 클래스에게 일을 시키는 코드가 그 극단이다.

```java
BlueWorker w1 = new BlueWorker();
WhiteWorker w2 = new WhiteWorker();
JubuWorker w3 = new JubuWorker();

w1.doFight();
w2.doZingZing();
w3.doSsingSsing();
```

호출자가 아는 것이 여섯 개다 — 클래스 이름 셋과 메서드 이름 셋. 필기의 진단이 그것이다 — 「각 노동자에게 일을 시키는 방법이 다르다. 왜? => 메서드 호출 방법이 다르기 때문에」 → [[method]]

낮추는 방법은 **아는 대상을 구현에서 약속으로 바꾸는 것**이다. 셋이 같은 [[interface]] 를 지키게 하면 호출자가 아는 메서드 이름이 하나로 줄고, 변수 타입도 하나가 된다.

```java
Worker w1 = new BlueWorker();
Worker w2 = new WhiteWorker();
Worker w3 = new JubuWorker();

w1.execute();
w2.execute();
w3.execute();
```

**결합이 사라진 것이 아니라 향하는 곳이 바뀌었다.** 호출자도 피호출자도 이제 `Worker` 를 안다. 호출자는 `execute()` 라는 이름을, 구현 클래스는 `implements Worker` 를 통해 같은 약속을 안다 — **양쪽이 서로를 보지 않고 가운데를 본다.**

## 사용 예시

`new BlueWorker()` 가 그대로 남아 있는 것이 이 회차 코드의 정확한 상태다. 남은 결합과 없어진 결합을 갈라 세면 이렇다.

| 호출자가 아는 것 | 인터페이스 적용 전 | 적용 후 |
|---|---|---|
| 변수 타입 | `BlueWorker`·`WhiteWorker`·`JubuWorker` 셋 | `Worker` 하나 |
| 부를 메서드 이름 | `doFight`·`doZingZing`·`doSsingSsing` 셋 | `execute` 하나 |
| 만들 클래스 이름 | 셋 | **셋 그대로** |

**「어떻게 부를까」는 없어졌고 「무엇을 만들까」는 남았다.** 그래서 노동자가 하나 늘 때 고칠 자리가 「그 객체를 쓰는 코드 전부」에서 「그 객체를 만드는 한 줄」로 줄어든다. 부르는 코드가 여러 곳에 흩어져 있고 만드는 곳이 한 곳이면 그 차이가 클수록 이득이 커진다 → [[instance]]

그리고 이 형태가 되어야 **여럿을 한 통에 담아 돌릴 수** 있다. 타입이 하나여야 배열에 들어가고 반복문 하나로 일을 시킬 수 있다 → [[array]] · [[polymorphism]]

### 사흘 뒤 실습에서 한 축은 좋아지고 한 축은 그대로다

리팩터링 회차에서 **회원 목록에 닿는 방법이 바뀐다.** 프로젝트 팀원을 고르려면 회원 목록이 필요한데, 그것을 얻는 경로가 회차마다 이렇게 움직였다.

| 회차 | `ProjectCommand` 가 회원 목록에 닿는 방법 | 아는 것 |
|---|---|---|
| Day17 | `UserCommand.findByNo(userNo)` | `UserCommand` 라는 클래스 이름 |
| Day19 | `UserList.findByNo(userNo)` | `UserList` 라는 클래스 이름 |
| Day30 | 생성자로 받은 `userList` | **어디서 왔는지 모른다** |

```java
ProjectCommand projectCommand = new ProjectCommand("프로젝트", userCommand.getUserList());
```

```java
public ProjectCommand(String menuTitle, LinkedList userList) {
  super(menuTitle);
  this.userList = userList;                  // 누가 가진 목록인지 묻지 않는다
}
```

**`ProjectCommand` 안에 `UserCommand` 라는 글자가 없어졌다.** 「필요한 것을 스스로 찾아가는」 코드가 「받아서 쓰는」 코드가 된 것이고, 이것이 이 노트에서 결합이 실제로 줄어든 유일한 자리다. 무엇을 넘길지 아는 곳은 `App` 한 군데로 모였다 → [[constructor]] · [[static-member]]

**반대로 명령을 부르는 쪽은 그대로다.** `App` 은 `Command` 인터페이스를 만들어 두고도 구현 클래스 넷을 각각 필드로 들고 문자열 `switch` 로 `execute()` 를 부른다. Day29 의 `new BlueWorker()` 는 **만드는 자리**만 남은 상태였는데, 여기는 **부르는 자리까지** 구현 타입이다 → [[interface]] · [[polymorphism]]

### 열엿새 뒤 — 가장 강한 결합이 상속이라는 말이 나온다

Day42 가 데코레이터 패턴의 근거로 적은 한 줄이 「**상속을 이용한 강결합**은 유지보수 측면에서 OCP 원칙을 위배한다」다. 그때까지 이 노트가 센 결합은 **부르는 쪽이 아는 이름**이었는데, 상속은 아는 것의 종류가 다르다.

| 세는 항목 | 상속 (`extends Beverage`) | 조합 (`Beverage beverage` 필드로 품기) |
|---|---|---|
| 언제 정해지나 | **컴파일 시점** | 실행 시점 — `new Mocha(espresso)` |
| 몇 개와 이어질 수 있나 | 부모 하나 (Java 단일 상속) | 겹을 원하는 만큼 |
| 아는 범위 | `protected` 멤버·부모의 내부 구현 | 그 타입의 **공개 약속만** |
| 부모가 바뀌면 | 자식이 조용히 깨질 수 있다 | 약속이 그대로면 무사 |

**세 번째 줄이 상속을 「강결합」이라 부르는 이유의 핵심이다.** 자식은 부모의 메서드 이름만 아는 것이 아니라 `protected` 필드에 직접 손을 대고, 부모가 자기 메서드를 어떤 순서로 부르는지에도 기댄다 — 그것은 문법으로 드러나지 않아 아래 「순서를 아는 것이 더 강한 결합이다」와 같은 종류다. 그래서 부모의 구현이 바뀌면 자식이 깨지고, **깨진 자리가 자식 코드라 부모를 고친 사람에게는 안 보인다** → [[inheritance]] · [[access-modifier]]

Day42 가 그렇게 적고도 `Decorator extends Beverage` 를 쓴 것은 모순이 아니다 — **타입을 얻으려고 상속하고, 확장은 필드로 한다.** 상속으로 물려받는 것이 「구현」이면 위 표의 오른쪽 두 줄이 전부 걸리고, 「타입」뿐이면 걸리지 않는다 → [[decorator-pattern]] · [[interface]]

### 이틀 뒤 — 결합에 방향이 있다는 것이 코드로 갈라진다

Day44 의 옵저버 패턴은 이 노트가 지금까지 센 축을 **한 쌍**으로 만든다. 같은 두 클래스 사이에 결합이 양쪽으로 있고, 한쪽만 풀렸다.

| 방향 | Day44 의 코드 | 아는 것 |
|---|---|---|
| Subject → 옵저버 | `private List<Observer> obsevers;` | **약속뿐** — 화면 클래스 이름이 어디에도 없다 |
| 옵저버 → Subject | `private WeatherData weatherData;` | **구체 클래스 이름** |

```java
public class CurrentConditionsDisplay implements Observer, DisplyElement {
  private WeatherData weatherData;                    // Subject 가 아니다

  public CurrentConditionsDisplay(WeatherData weatherData) {
    this.weatherData = weatherData;
    weatherData.registerObserver(this);
  }
```

**Day29 의 「인터페이스를 썼다 ≠ 결합이 낮아졌다」가 방향만 뒤집혀 되살아난 자리다.** Day29 에서 남은 것은 「무엇을 만들까」(`new BlueWorker()`)였고 여기서 남은 것은 「무엇에 붙을까」다. `Subject weatherData` 로 받으면 아무 주제에나 붙는 화면이 되는데, 지금은 기상 데이터 전용이다 — 그리고 같은 노트가 그 인터페이스를 **직접 만들어 놓고** 타입으로 쓰지 않았으므로 Day30 의 상태와도 겹친다 → [[observer-pattern]] · [[interface]] · [[dependency-inversion-principle]]

**그리고 이 패턴은 결합의 방향과 의존의 방향이 어긋난 것을 이용한다.** 화면이 기상 데이터를 필요로 하지만(의존: 다 → 1), 부르는 것은 기상 데이터가 화면을 부른다(호출: 1 → 다). Day29~31 의 코드는 둘이 같은 방향이었다 — 필요한 쪽이 가서 물었다. **「필요한 쪽이 묻지 않고 아는 쪽이 알린다」로 바꾸면 필요한 쪽의 개수를 아는 코드가 없어진다** — 그것이 `List<Observer>` 한 줄이 사는 이유다.

### 나흘 뒤 — 결합이 사라지지 않고 컴파일러의 시야 밖으로 나간다

Day45 는 실습 프로젝트를 **두 프로그램**으로 가른다. 메뉴와 입력은 클라이언트가, 파일 입출력과 리스트 관리는 서버가 맡는다. 이 노트가 지금까지 센 축으로 보면 **가장 크게 결합이 낮아진 것처럼 보인다** — 소켓으로 가르면 클라이언트 코드에 서버 클래스의 이름을 쓸 자리가 아예 없다.

| 세는 항목 | 한 프로세스 안 | 소켓으로 가른 뒤 |
|---|---|---|
| 아는 이름 | 클래스·메서드 이름 | **없다** (IP 와 포트 두 숫자) |
| 틀렸을 때 언제 아나 | 컴파일 | **상대를 실행해 봐야** |
| 함께 배포해야 하나 | 한 덩어리라 자동 | 따로 배포되고 **어긋난 채로 돌 수 있다** |

**두 번째 줄이 이 회차가 이 노트에 더하는 것 전부다.** 이름을 모르게 된 것은 결합이 낮아진 것이 맞지만, 클라이언트는 여전히 「서버가 무엇을 받고 무엇을 돌려주는지」를 안다 — 그 앎이 **문법에 적히는 자리를 잃었을 뿐**이다. Day29 의 위반은 컴파일 에러였고, 여기서 같은 종류의 위반은 **쓰레기 값이나 멈춤**으로 나타난다 → [[network-protocol]] · [[socket]]

그래서 위의 「이름을 아는 것보다 순서를 아는 것이 더 강한 결합이다」가 **가장 큰 규모로 되살아난다.** 「먼저 `init()` 을 부르고 그 다음 `execute()`」가 인터페이스에 적히지 않던 것처럼, 「누가 먼저 말하고 어디까지가 한 메시지인가」는 어느 코드에도 선언되지 않는다. 양쪽이 다 「상대 말을 먼저 듣는다」로 만들면 **예외도 로그도 없이 둘 다 멈춘다.**

Day30 의 준비가 여기서 값을 한다 — `ProjectCommand` 가 목록을 **생성자로 받게** 되어 있었으므로 그 목록이 「서버에 묻는 것」으로 바뀌어도 명령 클래스는 어디서 왔는지 묻지 않는다. **주입이 결합을 낮춘 것의 진짜 값이 이 이사에서 드러난다** → [[client-server-model]] · [[dependency-injection]]

## 왜 중요한가

**고칠 때 따라 고쳐야 하는 범위가 결합도로 정해진다.** 피호출자의 메서드 이름을 바꾸면 그 이름을 아는 코드를 전부 찾아야 하고, 하나를 빠뜨리면 컴파일이 막힌다(운이 좋은 경우다). 결합도는 「깔끔한 설계」의 취향 문제가 아니라 **수정 비용의 단위**다.

**새 종류를 더할 때 기존 코드를 열지 않아도 되는지가 갈린다.** 노동자를 하나 더 만들 때, 결합이 높은 쪽은 호출부에 변수와 호출 한 줄이 늘고, 낮은 쪽은 호출부가 한 글자도 안 바뀐다. **기존 코드를 안 고치고 기능을 더할 수 있는가**가 결합도가 실제로 답하는 질문이다.

**그리고 응집도를 올릴 때 치르는 대가가 이 축에서 측정된다.** 보름 앞선 회차는 한 클래스를 데이터 쪽과 UI 쪽으로 갈라 [[cohesion]] 을 올렸고, 그 대가로 `UserCommand` 가 `UserList` 라는 클래스 이름과 메서드 다섯 개를 알게 되었다. [[grasp]] 목록에 이름만 적혀 있던 Low Coupling 이 그때 반대 방향으로 움직인 것인데, **이 회차가 그 대가를 줄이는 방법을 준다** — 아는 대상을 클래스 이름에서 인터페이스 이름으로 바꾸는 것이다.

## 경계와 오해

- **결합도 ≠ 응집도** — 둘 다 「잘 나뉘었나」를 보는 말이라 섞이는데 **세는 대상이 다르다.** 응집도는 **한 클래스 안**을 보고(이 메서드들이 한 주제인가), 결합도는 **클래스 사이**를 본다(이 클래스가 몇 개를 아는가). 그래서 한쪽을 올리면 다른 쪽이 나빠지는 거래가 성립한다 — 클래스를 쪼개면 안은 모여도 사이는 늘어난다 → [[cohesion]] · [[grasp]]
- **결합도 0 이 목표가 아니다** — 아무것도 모르면 아무 일도 시킬 수 없다. 인터페이스를 넣은 뒤에도 호출자는 `Worker` 와 `execute()` 를 안다. 줄이는 것은 **의존의 개수가 아니라 「변할 것에 대한 의존」**이고, 그래서 인터페이스가 답이 되는 이유는 **약속이 구현보다 덜 변하기 때문**이다.
- **호출명을 통일하는 것 ≠ 결합도를 낮추는 것** — 필기는 인터페이스의 효과를 「동일한 호출명으로 메서드를 호출 할 수 있다」로 적었는데, 세 클래스의 메서드 이름을 손으로 전부 `execute` 로 바꾸기만 해도 호출 세 줄은 똑같아진다. 그렇게 해도 **변수 타입이 셋이라 한 배열에 담을 수도, 매개변수 하나로 받을 수도 없다.** 인터페이스가 더하는 것은 이름 통일이 아니라 **공통 타입**이고, 그 타입이 있어야 「무엇이 올지 모르는 채로 받는 코드」를 쓸 수 있다 → [[polymorphism]] · [[type-casting]]
- **인터페이스를 썼다 ≠ 결합이 낮아졌다** — 이 회차의 코드에 `new BlueWorker()` 가 그대로 있다. **객체를 만드는 자리는 구현 클래스 이름을 알아야 하고**, 그 한 줄이 호출부 안에 있으면 결합은 옮겨진 것이지 없어진 것이 아니다. 「인터페이스로 받았으니 갈아 끼울 수 있다」는 **만드는 자리를 밖으로 빼낸 다음**에 참이 된다 → [[instance]] · [[singleton-pattern]]
- **결합은 부르는 쪽에만 있는 것이 아니다** — 구현 클래스도 `implements Worker` 로 인터페이스를 알고, 인터페이스에 메서드가 하나 늘면 모든 구현 클래스가 컴파일 에러가 난다. 「낮은 결합」이 「의존이 없다」가 아니라 **「의존이 한 점으로 모였다」**인 이유가 이것이고, 그 한 점을 고치는 비용은 오히려 올라간다 → [[interface]] · [[default-method]]
- **약속을 아는 것과 약속의 내용을 아는 것은 다르다** — 인터페이스에 메서드를 열 개 선언해 두고 호출자가 열 개를 다 부르면, 타입은 하나여도 아는 것은 열 개다. **인터페이스의 크기가 곧 결합의 크기**이므로, 「인터페이스를 뒀다」보다 「무엇을 약속에 넣었나」가 결합도를 정한다 → [[cohesion]]
- **이름을 아는 것보다 순서를 아는 것이 더 강한 결합이다** — 「먼저 `init()` 을 부르고 그 다음 `execute()` 를 불러야 한다」는 규칙은 인터페이스에 적을 수 없고 컴파일러가 검사하지도 않는다. 결합에는 **문법으로 드러나는 것과 안 드러나는 것**이 있고, 뒤쪽은 인터페이스를 도입해도 그대로 남는다 → [[read-side-effect]]
- **그 「안 드러나는 결합」의 실물이 사흘 뒤 회차에 있다** — `App` 의 필드 초기화 네 줄이 이렇다.

  ```java
  UserCommand userCommand = new UserCommand("회원");
  ...
  ProjectCommand projectCommand = new ProjectCommand("프로젝트", userCommand.getUserList());
  ```

  필드 초기자는 **선언 순서대로** 실행되므로 이 코드는 `userCommand` 가 위에 있어야만 돌아간다. 두 줄의 순서를 바꾸면 `userCommand` 가 `null` 이라 `NullPointerException` 이고, **컴파일러는 아무 말도 하지 않는다.** 주입으로 클래스 이름 하나를 없앤 대가로 **줄 순서에 대한 의존**이 생긴 것이고, 이런 결합은 UML 에도 그려지지 않는다 → [[constructor]] · [[default-initialization]]
- **주입받는 것과 약속으로 받는 것은 다르다** — `ProjectCommand` 는 목록을 **받지만** 그 타입이 `LinkedList` 다. 회원 목록을 배열 기반으로 바꾸려면 `ProjectCommand` 의 필드 타입과 생성자 선언을 같이 고쳐야 하므로, **`List` 로 받았을 때 얻는 것을 못 얻었다.** 같은 노트가 `List` 인터페이스를 만들어 놓고도 그렇다 — 「누가 주는지 모른다」와 「무엇을 받는지 모른다」는 따로 얻어야 하는 두 가지다 → [[interface]]
- **「강결합」은 결합의 종류가 아니라 정도인데, 상속에서는 종류까지 달라진다** — Day42 의 「상속을 이용한 강결합」을 「의존이 많다」로 읽으면 절반만 잡힌다. 아는 **개수**가 아니라 **깊이**가 문제다 — 인터페이스로 아는 것은 공개된 약속뿐이고, 상속으로 아는 것은 `protected` 필드와 부모가 자기 안에서 하는 호출까지다. 그래서 인터페이스 결합은 부모를 고칠 때 **컴파일 에러**로 드러나고, 상속 결합은 **동작이 조용히 바뀌는** 방식으로 드러난다. 「고치면 컴파일이 막힌다(운이 좋은 경우다)」의 반대쪽이 여기다 → [[inheritance]] · [[method-overriding]]
- **결합을 줄이는 수단이 결합을 늘리는 수단과 같은 문법일 수 있다** — 이 노트가 결합을 낮추려고 쓴 것이 인터페이스와 생성자 주입이었고, Day42 는 같은 목적으로 **필드로 품기**를 쓴다. 그런데 그 필드의 타입이 구체 클래스면(예: `Espresso beverage`) 조합인데도 결합은 상속만큼 굳는다 — 위의 「주입받는 것과 약속으로 받는 것은 다르다」와 같은 자리다. **「상속이냐 조합이냐」보다 「무엇을 아는 타입으로 적었냐」가 먼저 재는 것**이다 → [[interface]]
- **결합을 풀면 「언제 끊을까」를 아는 코드도 함께 없어진다** — Day44 의 `WeatherData` 는 화면의 클래스 이름을 모르게 되었고, 그 대가로 **어느 화면을 언제 목록에서 빼야 하는지 아는 코드도 없다.** `removeObserver` 는 약속에 있는데 부르는 곳이 없고, `List<Observer>` 가 강한 참조를 들고 있으므로 화면은 Subject 가 사는 동안 알림을 계속 받고 회수되지도 않는다. 이 노트가 지금까지 센 결합은 **컴파일 시점의 「이름을 아는가」**였는데, 여기서 처음 **실행 시점의 「수명을 아는가」**가 나온다 — 그리고 뒤쪽은 인터페이스로 낮출 수 없다. 위의 「결합도 0 이 목표가 아니다」의 다른 얼굴이고, 연결을 만드는 자리(옵저버의 생성자)와 끊는 자리가 갈려 있으면 대개 끊는 쪽이 비어 있다 → [[observer-pattern]] · [[garbage-collection]]
- **내부를 그대로 내주면 결합이 아니라 공유가 된다** — 목록을 넘기는 방법이 `userCommand.getUserList()` 다. `UserCommand` 의 필드 그 자체가 넘어가므로 두 명령이 **같은 인스턴스**를 만지고, `ProjectCommand` 가 그 목록에 `add` 를 하면 회원 목록이 바뀐다. 지금 코드는 읽기만 하지만 **막는 것은 아무것도 없다** — 「받아서 쓴다」가 「같은 것을 만진다」로 미끄러지는 지점이다 → [[encapsulation]] · [[object-reference]] · [[defensive-copy]]

## 함께 보는 개념

- [[interface]] — 결합 대상을 구현에서 약속으로 바꾸는 장치
- [[cohesion]] — 반대편 축. 올리면 이쪽이 나빠지는 거래가 된다
- [[grasp]] — Low Coupling 이라는 이름이 목록에 있던 자리
- [[polymorphism]] — 결합을 낮춘 결과로 얻는 성질
- [[method]] — 호출자가 아는 것의 최소 단위
- [[instance]] — `new` 가 남기는 결합
- [[type-casting]] — 공통 타입으로 받는 문법
- [[default-method]] — 약속을 나중에 고칠 때의 비용을 줄이는 쪽
- [[encapsulation]] — 무엇을 알게 할지 정하는 같은 방향의 결정
- [[constructor]] — 의존을 밖에서 넣어 주는 통로
- [[refactoring]] — 이 축을 움직이는 작업의 단위
- [[generalization]] — 결합을 부모 한 점으로 모으는 쪽
- [[inheritance]] — 아는 깊이가 가장 깊어지는 연결 방법
- [[decorator-pattern]] — 상속 대신 필드로 이어 결합을 실행 시점으로 옮기는 쪽
- [[observer-pattern]] — 결합의 방향이 한쪽만 풀린 예
- [[garbage-collection]] — 「수명을 아는가」로서의 결합이 드러나는 자리
- [[access-modifier]] — `protected` 가 상속 결합의 범위를 정하는 자리
- [[network-protocol]] — 결합이 컴파일러의 검사 밖으로 나간 형태
- [[client-server-model]] — 프로세스를 나눠도 앎이 남는 구조
