# Java EE / Jakarta EE (기술 명세)

**기업용 애플리케이션에 필요한 기술들을 「이런 인터페이스로 이렇게 동작해야 한다」로 적어 둔 문서 묶음.** Day63 의 정의는 「기업용 App 제작을 위해 다양한 기술을 모은 버전이다」·「다양한 애플리케이션 서버 환경에서 작동하며, 대규모, 확장 가능한, 신뢰성 있는 애플리케이션을 쉽게 구축할 수 있도록 여러 기술 명세를 제공한다」다. **「다양한 서버 환경에서 작동한다」가 이 문서가 존재하는 이유 전부**이고, 그 대가가 버전 대응표다 → [[servlet]] · [[web-application-server]]

## 정의

Day63 이 대표 기술을 넷 적었다.

| 대표 기술 | Day63 의 설명 | 이 필기에서 실제로 배우는 것 |
|---|---|---|
| **Servlet / JSP** | 「WebApplication 제작기술」 | 서블릿은 다음 회차부터 → [[servlet]] |
| EJB | 「분산 컴포넌트 제작기술」 | 이름만 — Day45 의 ORB·Stub 자리다 → [[distributed-processing]] · [[remote-procedure-call]] |
| Web Service | 「웹 기반 분산컴포넌트 제작기술」 | 이름만 |
| Authentication & Deployment | 「관리 및 보안 기술」 | 기술 이름이 아니라 **범주**다 |

### 항목 기술과 구현 서버가 따로 움직인다

명세가 판이고 서버가 그 판을 구현하므로, 표가 **둘** 필요하다. Day63 이 그 둘을 나란히 실었다.

| Java EE | Servlet | JSP | EL | EJB |
|---|---|---|---|---|
| 5 | 2.5 | 2.1 | – | 3.0 |
| 6 | 3.0 | 2.2 | 2.2 | 3.1 |
| 7 | 3.1 | 2.3 | 3.0 | 3.2 |
| 8 | 4.0 | 2.3 | 3.0 | 3.2 |

| Java EE | WebLogic | WebSphere | JEUS | Tomcat |
|---|---|---|---|---|
| 5 | 10.3 | 6.1, 7.0 | 6.0 | 6.0 |
| 6 | 11g, 12c | 7.0, 8.0 | 7.0 | 7.0 |
| 7 | 12c, 12.2 | 8.5, 9.0 | 8.0 | 8.0 |
| 8 | 12.2.1, 14.1 | 9.0.x | 8.1, 8.2 | 8.5, 9.x |

**두 표를 겹쳐 읽는 것이 이 절의 요점이다** — 「Servlet 4.0 을 쓰고 싶다」는 「Java EE 8 이 필요하다」이고 그것은 「톰캣 8.5 이상이어야 한다」다. 그리고 EJB 열은 톰캣 쪽에서 **채워지지 않는다** — 같은 서버 이름이 두 표에서 다른 크기로 읽히는 이유다 → [[web-application-server]] · [[tomcat]]

### 필기가 문장 하나를 여기서 끊었다

Day63 의 이 절은 「**이처럼 버전 별로 다르기 때문에**」에서 끝난다. 뒤가 없으므로 그 뒤에 올 것을 여기 적어 둔다.

| 버전이 다르면 | 어떻게 나타나나 |
|---|---|
| 내가 컴파일에 쓴 API 버전 > 서버가 구현한 버전 | **컴파일은 되고 배포에서 깨진다** — 없는 메서드·없는 클래스 → [[classpath]] |
| 서버를 올려서 명세 버전이 바뀐다 | 같은 배포물이 다른 서버에서 다르게 동작한다 → [[web-application-deployment]] |
| 프레임워크가 특정 명세 버전을 요구한다 | 스프링 부트 버전이 톰캣 버전을 정한다 |

**그리고 필기의 표가 멈춘 자리(Java EE 8)가 정확히 가장 큰 경계 앞이다.** 다음 판(Jakarta EE 9)에서 **패키지 이름이 `javax.*` 에서 `jakarta.*` 로 전부 바뀌었다.** 즉 이름만 바뀐 것이 아니라 **`import` 한 줄이 안 맞아 컴파일되지 않는** 변경이고, 그래서 톰캣 9 와 톰캣 10 사이에서는 **같은 war 가 돌지 않는다** — 서블릿 클래스가 발견되지 않아 예외가 아니라 **404** 로 나타난다. 스프링 부트 2 와 3 이 갈리는 것도 이 선이다 → [[tomcat]] · [[package]]

### 이름이 바뀐 이유

Day63 이 적었다 — 「과거에는 Oracle이 관리했으나, 2017년에 Eclipse Foundation으로 이관되면서 Jakarta EE로 이름이 변경되었다」. **「Java」라는 상표를 Oracle 이 계속 갖고 있어서 새 이름이 필요했던 것**이고, 그것이 위의 패키지 rename 으로 이어진다 — 조직이 바뀐 일이 코드의 `import` 줄까지 내려온 드문 사례다.

## 왜 중요한가

**서버를 바꿔도 내 코드가 그대로일 수 있다.** [[interface]] 가 한 프로그램 안에서 하는 일을 이 문서가 **회사와 제품 사이에서** 한다 — WebLogic 에 올리던 것을 JEUS 에 올릴 수 있는 근거가 명세이고, 그것이 없으면 서버를 고르는 일이 곧 코드를 묶는 일이 된다 → [[interface]] · [[coupling]]

**그래서 「무엇을 배우는가」가 제품이 아니라 규격이 된다.** 톰캣을 배우는 것과 서블릿을 배우는 것이 다른 일이고, 뒤쪽이 옮겨 다닌다. [[network-protocol]] 노트가 「프로토콜은 내가 정한다」로 남겨 둔 자리가 웹에서는 **이미 정해져 있다**는 것과 같은 축이다 — 표준을 쓰면 정할 일이 없어지는 대신 **표준을 읽어야** 한다.

**대신 「내 코드가 무엇에 기대고 있는지」가 두 곳으로 갈린다.** 컴파일할 때 보는 API 와 실행할 때 쓰는 구현이 다른 물건이므로, 빌드 파일에 적힌 버전과 서버에 깔린 버전이 **둘 다** 맞아야 한다. 라이브러리를 의존성에 넣으면 끝이던 [[gradle]] 의 감각이 여기서 한 번 깨진다 → [[build]] · [[classpath]]

## 경계와 오해

- **명세 ≠ 구현** — 명세는 인터페이스와 규칙이고 실제로 돌아가는 클래스는 서버가 갖고 있다. 그래서 서블릿 API 는 **컴파일할 때만** 내 빌드에 필요하고 배포물(war)에 넣으면 오히려 충돌한다 — 서버의 것과 두 벌이 되어 「같은 이름의 클래스가 두 개」인 상태가 된다. [[classpath]] 가 「JVM 은 클래스를 스스로 찾지 못하니 위치를 알려 줘야 한다」로 적은 자리에서, **어느 쪽이 쓰일지를 내가 정하지 않게 되는 것**이 이 층에서 처음 문제가 된다 → [[classpath]] · [[class-loading]] · [[build]]
- **Java EE 8 ≠ Java 8** — 이름에 숫자가 붙어 있어 [[jdk]] 버전과 같은 축으로 읽히는데, **다른 축**이다. Java SE 는 언어와 표준 라이브러리이고 Java EE 는 그 위에 얹는 서버용 규격 묶음이다. Day63 의 표가 「Java EE 5/6/7/8」이라 적혀 있어 이 혼동을 부추긴다 — 실제로 Java EE 8 은 Java SE 8 위에서 쓰지만 그것은 **우연히 숫자가 겹치는 것**에 가깝다 → [[jdk]] · [[jvm]]
- **Jakarta EE 는 이름만 바뀐 것이 아니다** — Day63 의 문장(「이름이 변경되었다」)만 읽으면 표기 문제로 보이는데, **패키지 이름이 바뀌어 호환성이 끊겼다.** 「이름이 바뀐 것뿐이니 아무거나 써도 된다」로 읽으면 `javax.servlet` 로 짠 코드를 톰캣 10 에 올리고 원인을 못 찾는다 — 컴파일도 되고 서버도 뜨고 **요청만 404** 다 → [[tomcat]] · [[package]]
- **「JavaEE 버전에 따라 SpringBoot(Tomcat)버전이 다르다」는 방향을 거꾸로 읽기 쉽다** — 문장 자체는 맞지만, 실제로 고르는 순서는 대개 반대다. 먼저 프레임워크 버전을 고르고, 그것이 요구하는 명세 버전이 정해지고, 그것을 구현한 서버 버전으로 좁혀진다. **명세는 판단의 출발점이 아니라 두 선택 사이의 제약**이다 → [[web-application-deployment]]
- **표에 있는 것과 이 필기가 다루는 것이 다르다** — 대표 기술 넷 중 실제로 배우는 것은 Servlet 하나이고, EJB·Web Service 는 **이름만** 나온다. 「Java EE 를 배웠다」가 아니라 「Java EE 안의 웹 층을 배운다」로 읽어야 하고, 그래서 톰캣만으로 실습이 끝나는 것이 자연스럽다 → [[distributed-processing]]
- **「Authentication & Deployment」는 기술 이름이 아니다** — 나머지 셋(Servlet/JSP·EJB·Web Service)은 규격 이름인데 이 칸만 **범주 이름**이다. 표의 한 열이 같은 종류로 채워져 있지 않다는 뜻이고, 그래서 이 칸을 규격 이름으로 검색하면 아무것도 안 나온다.
- **명세를 따른다고 배포까지 같아지지는 않는다** — 같은 war 가 어느 서버에나 올라간다는 것이 이 문서의 약속인데, 서버별 설정 파일·데이터소스 등록 방법·클래스 로더 정책은 명세 밖이다. **「코드는 옮겨지고 설정은 안 옮겨진다」**가 실무에서 남는 부분이고, Day63 의 구현 서버 표가 네 열로 갈려 있는 이유이기도 하다 → [[xml]] · [[web-application-deployment]]
