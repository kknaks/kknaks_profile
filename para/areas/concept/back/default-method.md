# 디폴트 메서드 (Default Method)

**인터페이스가 미리 구현해 두는 인스턴스 메서드.** `default` 를 붙이면 몸통을 가질 수 있고, 구현 클래스는 그것을 재정의하지 않아도 그대로 물려받는다. 필기의 한 줄이 정확하다 — 「인터페이스에서 미리 구현하는 메서드」.

## 정의

```java
interface MyInterface4 {

  void m1();                    // 추상메서드 — 구현 클래스가 반드시 채운다

  default void m2() {           // 디폴트메서드 — 채우지 않으면 이것이 실행된다
    System.out.println("MyInterface4.m2()");
    x();
  }

  private void x() {            // 디폴트메서드들이 나눠 쓰는 공통 코드
    System.out.println("MyInterface4.x()");
  }
}
```

두 가지가 추상메서드와 갈린다.

- **재정의가 선택이다** — 필기의 표현으로 「인터페이스 받는 클래스에서 구현메서드를 재정의 하지 않아도 된다. 하지만, 클래스에서 구현을 강제할 수 없다」. 강제와 선택을 고르는 것이 `default` 한 단어다 → [[method-overriding]]
- **인스턴스 필드를 읽을 수 없다** — 인터페이스에는 상태가 없으므로 몸통이 쓸 재료가 상수와 「자기 안의 다른 메서드 호출 결과」뿐이다 → [[interface]] · [[static-member]]

`private` 메서드가 같이 나오는 이유가 그 두 번째다. 필기가 적어 둔 조건이 「해당 기능을 m2()와 m3() 처럼 여러 메서드에서 사용해야 할 경우」이고, 디폴트 메서드가 늘면 그들 사이의 중복을 둘 자리가 필요해진다. **몸통을 허용한 순간 「안에서만 쓰는 코드」가 생기고, 그것을 감출 등급도 같이 필요해진다** → [[access-modifier]] · [[encapsulation]]

### 재정의해 놓고 원본을 부르는 문법

클래스 상속에서는 가려진 부모 메서드를 `super.m2()` 로 부른다. 인터페이스에서는 그것이 통하지 않고 **인터페이스 이름을 앞에 붙인다.**

```java
MyInterface4.super.m2();
```

필기가 안 되는 두 가지를 주석으로 남겨 두었고, 둘의 이유가 다르다.

| 쓴 것 | 결과 | 이유 |
|---|---|---|
| `super.m2()` | 컴파일 오류 | 「수퍼 클래스(Object)에서 m2()를 찾아 올라간다」 — `super` 는 부모 **클래스**를 가리키고, 인터페이스는 그 경로에 없다 |
| `MyInterface4.m2()` | 컴파일 오류 | 「m2()는 인스턴스(non-static) 메서드이기 때문에」 — 인터페이스 이름으로 직접 부르는 것은 `static` 메서드의 문법이다 |
| `MyInterface4.super.m2()` | OK | 「어느 인터페이스의」와 「가려진 원본을」을 동시에 지정한다 |

**이름을 앞에 붙여야 하는 이유가 인터페이스가 여러 개일 수 있다는 데 있다.** 클래스는 부모가 하나뿐이라 `super` 만으로 대상이 정해지는데, `implements` 는 여럿이므로 「어느 쪽의 원본인가」를 말하지 않으면 정할 수 없다 → [[multiple-inheritance]] · [[inheritance]]

## 사용 예시

필기의 실행 코드는 같은 인터페이스 타입으로 세 메서드를 차례로 부른다. **어느 몸통이 실행되는지가 셋 다 다르다.**

```java
class MyInterface4Impl implements MyInterface4 {
  @Override
  public void m1() {
    MyInterface4.super.m2();                          // 가려 놓은 원본을 부른다
    System.out.println("MyInterface4Impl.m1()");
  }

  @Override
  public void m2() {                                  // 디폴트메서드를 재정의했다
    System.out.println("MyInterface4Impl.m2()");
  }
  // m3() 는 재정의하지 않았다
}
```

```java
MyInterface4 obj = new MyInterface4Impl();
obj.m1();
obj.m2();
obj.m3();
```

**필기는 실행 결과를 적어 두지 않았다.** 세 호출이 무엇을 찍는지가 이 예제의 답이다.

| 호출 | 출력 | 무엇이 실행되었나 |
|---|---|---|
| `obj.m1()` | `MyInterface4.m2()` → `MyInterface4.x()` → `MyInterface4Impl.m1()` | 구현 클래스의 `m1`, 그 안에서 **인터페이스의 원본** `m2` |
| `obj.m2()` | `MyInterface4Impl.m2()` | 구현 클래스의 재정의본. 인터페이스의 `m2` 는 가려졌다 |
| `obj.m3()` | `MyInterface4.m3()` → `MyInterface4.x()` | 재정의하지 않았으므로 **인터페이스의 몸통** |

`x()` 가 두 번 찍히는데 **둘 다 인터페이스 안에서 불린 것**이다. `obj.m2()` 에서는 재정의본이 실행되어 `x()` 가 아예 불리지 않는다 — 재정의는 그 메서드의 **몸통 전체**를 갈아 끼우므로 원본이 부르던 것까지 같이 사라진다.

그리고 같은 `m2` 가 한 프로그램 안에서 **두 번 다 실행된다.** `obj.m1()` 은 인터페이스의 것을, `obj.m2()` 는 구현 클래스의 것을 부른다 → [[method-overriding]] · [[polymorphism]]

## 왜 중요한가

**이미 배포된 인터페이스에 메서드를 더할 수 있게 된다.** 추상메서드를 하나 더하면 그 인터페이스를 구현한 **모든 클래스가 컴파일 에러**가 난다. 내가 만든 클래스가 아니어도 그렇다. 기본 구현을 같이 주면 아무도 깨지지 않으므로, `default` 는 편의 문법이 아니라 **인터페이스를 나중에 고치는 비용**에 대한 답이다 → [[interface]] · [[coupling]]

**그래서 인터페이스의 성격이 「규칙」에서 「규칙 + 최소 구현」으로 바뀐다.** 이 회차 전까지 「인터페이스에는 몸통이 없다」가 규칙이었는데, 그 규칙이 뒤집히면서 **인터페이스와 추상 클래스를 가르는 기준도 메서드에서 상태로 옮겨간다** → [[abstract-class]]

**빠뜨림을 잡아 주던 장치를 스스로 끄는 선택이기도 하다.** 추상메서드는 「안 채우면 컴파일 에러」이고 디폴트메서드는 「안 채우면 조용히 통과」다. 어느 쪽으로 선언하느냐가 **구현자의 실수가 컴파일 시점에 드러날지 실행 시점까지 숨을지**를 정한다.

## 경계와 오해

- **`default` 메서드 ≠ (default) 접근 범위** — 같은 노트 안에서 한 단어가 두 뜻으로 쓰인다. 2.1 은 `abstract void m2();` 에 「public 이 생략된 것이다. **(default) 아니다!**」라고 못을 박고, 2.2 는 `default void m2() {...}` 를 가르친다. 앞의 것은 **접근 지정자를 아무것도 안 쓴 상태의 이름**(같은 패키지에서만 보인다)이고 뒤의 것은 **인터페이스 메서드에만 쓰는 키워드**다. 디폴트 메서드는 오히려 `public` 이다 → [[access-modifier]]
- **디폴트 메서드 ≠ 추상 클래스의 일반 메서드** — 둘 다 「물려주는 구현」이지만 **읽을 수 있는 것이 다르다.** 추상 클래스의 메서드는 `protected int size` 같은 필드를 읽을 수 있고 디폴트 메서드는 읽을 필드가 없다. 그래서 「일반 메서드가 있으면 인터페이스로 못 옮긴다」는 규칙이 `default` 로 반쪽이 되고, 진짜 벽은 **상태**로 남는다 → [[abstract-class]] · [[interface]]
- **재정의를 강제할 수 없다는 것이 위험이 되는 자리가 있다** — 이틀 앞선 회차의 `Sorter.sort` 가 몸통을 가진 채로 물려주자 `MergeSort` 가 재정의를 빼먹고도 컴파일되어 **정렬 없이 성공으로 끝났다.** 디폴트 메서드는 그 상태를 인터페이스에서 다시 만들 수 있는 문법이고, 「기본 구현이 있으니 안전하다」는 **기본 구현이 옳을 때만** 참이다 → [[method-overriding]] · [[abstract-class]]
- **`{ ... };` 의 마지막 세미콜론은 오류가 아니다** — 필기의 두 디폴트 메서드가 모두 `};` 로 끝난다. 인터페이스 본문에 놓인 **빈 문장**이라 컴파일러가 그냥 넘기는데, 추상메서드가 세미콜론으로 끝나는 문법과 모양이 겹쳐서 「여기까지가 선언」으로 잘못 읽게 만든다. 이틀 전 `public void sort(int[] values) {};` 와 같은 자리다 → [[abstract-class]]
- **필기 2.2 의 코드는 그대로는 컴파일되지 않는다** — `m2()`·`m3()` 가 부르는 `x()` 가 그 블록에 없다. 2.3 에서 `private void x()` 를 더한 것이 완성본이고, 2.2 는 그것을 잘라 붙인 상태다(그 흔적으로 블록 첫 줄 주석이 「인터페이스 - private 메서드」로 남아 있다). **디폴트 메서드가 private 메서드를 부르는 예제라 둘을 갈라 놓으면 반쪽이 된다.**
- **`Object` 의 메서드는 디폴트로 재정의할 수 없다** — `default String toString()` 은 컴파일 에러다. 모든 구현 클래스가 이미 `Object` 로부터 그 메서드를 물려받고 있고, **클래스가 물려준 구현이 인터페이스의 것보다 언제나 우선**하므로 그 디폴트는 어차피 한 번도 실행되지 않는다. 「인터페이스에 몸통을 둘 수 있다」를 「무엇이든 둘 수 있다」로 읽으면 걸린다 → [[object-class]]
- **다중구현에서 같은 시그니처의 디폴트 메서드가 둘이면 컴파일이 막힌다** — 어느 몸통을 쓸지 컴파일러가 고르지 않고, **구현 클래스가 그 메서드를 재정의해서 직접 고르게** 한다. 그때 쓰는 것이 `A.super.m()` 이므로, 이 문법은 「원본을 부르고 싶을 때」의 편의가 아니라 **충돌을 해결하는 유일한 수단**이다 → [[multiple-inheritance]]
- **인터페이스에 몸통이 처음부터 허용된 것이 아니다** — `default`·`static` 은 Java 8, `private` 은 Java 9 에서 들어왔다. 필기는 추상메서드와 나란히 놓아 **처음부터 그랬던 것처럼** 보이는데, 「인터페이스에는 구현이 없다」로 배운 규칙이 나중에 뒤집힌 자리다.
