# 벤더 공개 API 와 웹앱 내부 API — 운영 연동은 공개로, 내부는 근거 · 데모 지점 실호출로

외부 SaaS 에는 두 층의 API 가 있다. 문서로 열어 준 **공개 API**(OpenAPI · 토큰 발급 · 버전 약속)와, 그 벤더의 웹앱이 화면 뒤에서 부르는 **내부 API**(문서 없음 · 사람 세션 · 언제든 바뀜). 운영 연동은 공개 API 로만 하고, 내부 API 는 「이 동작이 서버에 무엇으로 존재하나」 를 확인하는 **근거**로 쓴다. 공개 쓰기가 없는데 PoC 기간 안에 원천을 움직여야 하면, **운영과 갈린 데모 지점(테넌트)에서만** 내부 쓰기를 실호출로 하나씩 확인하며 쓴다.

## 정의

1. **공개 범위부터 센다** — 특히 **쓰기**. KOS 공개 스펙은 작업 75개 중 쓰기가 예약 · 단계 변경(`changeFlowStep` — `scheduleId` · `step` 두 칸) · 메모 2종뿐이었다. 읽기가 많아도 쓰기가 없으면 「연동」 은 조회까지다
2. **공개 쓰기의 거절 조건을 본다** — 같은 「단계 변경」 이라도 시술권 차감이 없고, 상담 담당 · 시술 목록 · 미완료 시술이 있으면 거절된다. 이름만 맞는다고 화면 동작을 대신하지 않는다
3. **내부 API 는 HAR 로 읽기만 한다** — 브라우저 DevTools 녹화(HAR)에서 화면 조작 하나가 어떤 요청 몇 개로 나가는지 본다. cc-prototype 은 시술 완료 · 담당 · 집도의 · 상담사 지정이 모두 `scheduleId + sequences[]` 를 받는 내부 명령이고, 「귀가 대기 + 일괄 취소」 는 작업 취소 → 단계 변경 **두 요청**이라는 것을 알았다. 재전송 · 토큰 사용 0, 토큰 · 쿠키 값은 기록하지 않는다
4. **쓰기 표면이 기능의 범위를 정한다** — 화면이 「원천에 저장」 을 약속하는 자리는 공개 **쓰기** 작업이 있는 것만 연다. cc-prototype 2차 접수의 「추가 요청」 메모 카테고리는 예약 메모(`changeReservationMemo`) · 상담 메모(`updateScheduleConsultationInfo`) 두 개뿐이다. 오더 · 고객 · 시술(담당자) 메모는 **읽을 수는 있어도** 쓰는 공개 작업이 없어, 카테고리에 넣으면 「KOS 에 저장」 이 거짓말이 된다. 반대로 읽기 표면이 넓으면(`searchVisitors` · `findVisitor`) 실연동 때 넓힐 자리로 적어 둔다
5. **결과는 「열어 달라」 요청서가 된다** — 내부에 있음을 확인한 동작 목록을 들고 벤더에 공개 API 로 요청한다
6. **데모 지점에서는 내부 쓰기 체인을 쓴다 — 단, 실호출로 한 줄씩 확인한 것만** — 명동 PoC v2 는 공개 쓰기 25개를 전수로 세어 담당자 · 호출 · 집도의 · 완료 쓰기가 없음을 확인하고, 「KOS 에 요청」 이 PoC 기간에 안 된다는 판단으로 HAR 의 경로 · 본문을 데모 지점에 실제로 보냈다(내부 쓰기 4종 200 · 관리자 권한 재확인 · 다른 원장 id 로 대신 수락 200). 운영 키는 쓰지 않는다. 확인하면서 드러난 것은 **HAR 에 안 보이는 전제 조건**이었다
   - **200 이 반영을 뜻하지 않는다** — 로그인(`sign-in`) 응답의 id 를 담당자로 넣으면 200 을 주고 무시한다. 진짜 시스템 계정 id 는 다른 조회(`get-user-account` 의 `data.id`)에 있었다 → 다시 읽어 확인하지 않으면 모른다 → [[external-write-queue]]
   - **같은 값으로 바꾸기는 거절된다** — 같은 단계로 단계 변경을 보내면 400. 보내기 전에 지금 값과 비교한다
   - **체인에 숨은 순서가 있다** — 방이 없는 시술 작업에 의사 호출을 보내면 400 `roomId NotFound`(방은 「방 배정」 작업에만 있다) → 호출 앞에 방 넣기를 끼워 **방 → 담당자 → 호출**
   - **화면 버튼 하나 = 요청 여럿** — [귀가 대기]를 단계 변경만 보내면 「방 배정」 작업이 준비중으로 남아 방이 안 빈다 → 남은 작업 취소 → 단계 변경(`PROCEDURE_DONE`)

## 왜 중요한가

- 내부 API 직결은 당장은 된다. 그러나 **사람의 세션 토큰**으로 돌고(만료 · 권한 · 감사 기록이 그 사람 이름), 벤더는 그 계약을 지킬 의무가 없어 **예고 없이 깨진다.** 운영 DB 에 쓰는 경로라면 깨진 것을 모른 채 잘못 쓸 수 있다
- 「공개 API 가 있다」 와 「우리가 하려는 조작이 공개 API 로 된다」 는 다르다. 범위를 세지 않으면 설계 뒤에 막힌다

## 경계와 오해

- **HAR 로 본 것 = 녹화한 조작뿐** — 녹화 안 한 동작(방 · 우선순위 · 시술 추가)은 알 수 없다. 「목록을 받는 꼴이니 단건도 같을 것」 은 추정으로 표시한다
- **읽기 가능 ≠ 쓰기 가능** — 화면에 보이는 값(읽기 응답에 있음)이라고 그 값을 고치는 기능을 만들 수 있는 것은 아니다. 기능 목록은 읽기 표면이 아니라 쓰기 표면으로 센다
- **PoC 라도 호출 0 이 맞을 수 있다** — 운영 시스템에 쓰는 PoC 는 「되는 가능성」 만 확인하고 조작 자리마다 `연동 필요` 주석을 남긴다. 시연은 목데이터로 → [[seed-data]]. 운영과 갈린 데모 지점이 있으면 거기서는 실호출로 간다 — 갈림의 기준은 「PoC 인가」 가 아니라 **「쓰는 곳이 운영 데이터인가」** 다
- **데모 지점 실연동이 내부 API 의 약점을 지우지는 않는다** — 경로 · 본문이 예고 없이 바뀌면 그대로 깨진다. 바뀌거나 막혔을 때의 처리는 열린 질문으로 남겼다(DEC-005 OQ-503). 운영 전환 때는 다시 공개 API 요청서로 돌아간다
- **[[api-documentation]] 과 혼동 말 것** — 그쪽은 우리가 명세를 만드는 법, 여기는 남의 명세가 어디까지인가
