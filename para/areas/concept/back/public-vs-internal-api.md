# 벤더 공개 API 와 웹앱 내부 API — 연동은 공개로, 내부는 근거로만

외부 SaaS 에는 두 층의 API 가 있다. 문서로 열어 준 **공개 API**(OpenAPI · 토큰 발급 · 버전 약속)와, 그 벤더의 웹앱이 화면 뒤에서 부르는 **내부 API**(문서 없음 · 사람 세션 · 언제든 바뀜). 연동은 공개 API 로만 하고, 내부 API 는 「이 동작이 서버에 무엇으로 존재하나」 를 확인하는 **근거**로만 쓴다.

## 정의

1. **공개 범위부터 센다** — 특히 **쓰기**. KOS 공개 스펙은 작업 75개 중 쓰기가 예약 · 단계 변경(`changeFlowStep` — `scheduleId` · `step` 두 칸) · 메모 2종뿐이었다. 읽기가 많아도 쓰기가 없으면 「연동」 은 조회까지다
2. **공개 쓰기의 거절 조건을 본다** — 같은 「단계 변경」 이라도 시술권 차감이 없고, 상담 담당 · 시술 목록 · 미완료 시술이 있으면 거절된다. 이름만 맞는다고 화면 동작을 대신하지 않는다
3. **내부 API 는 HAR 로 읽기만 한다** — 브라우저 DevTools 녹화(HAR)에서 화면 조작 하나가 어떤 요청 몇 개로 나가는지 본다. cc-prototype 은 시술 완료 · 담당 · 집도의 · 상담사 지정이 모두 `scheduleId + sequences[]` 를 받는 내부 명령이고, 「귀가 대기 + 일괄 취소」 는 작업 취소 → 단계 변경 **두 요청**이라는 것을 알았다. 재전송 · 토큰 사용 0, 토큰 · 쿠키 값은 기록하지 않는다
4. **쓰기 표면이 기능의 범위를 정한다** — 화면이 「원천에 저장」 을 약속하는 자리는 공개 **쓰기** 작업이 있는 것만 연다. cc-prototype 2차 접수의 「추가 요청」 메모 카테고리는 예약 메모(`changeReservationMemo`) · 상담 메모(`updateScheduleConsultationInfo`) 두 개뿐이다. 오더 · 고객 · 시술(담당자) 메모는 **읽을 수는 있어도** 쓰는 공개 작업이 없어, 카테고리에 넣으면 「KOS 에 저장」 이 거짓말이 된다. 반대로 읽기 표면이 넓으면(`searchVisitors` · `findVisitor`) 실연동 때 넓힐 자리로 적어 둔다
5. **결과는 「열어 달라」 요청서가 된다** — 내부에 있음을 확인한 동작 목록을 들고 벤더에 공개 API 로 요청한다

## 왜 중요한가

- 내부 API 직결은 당장은 된다. 그러나 **사람의 세션 토큰**으로 돌고(만료 · 권한 · 감사 기록이 그 사람 이름), 벤더는 그 계약을 지킬 의무가 없어 **예고 없이 깨진다.** 운영 DB 에 쓰는 경로라면 깨진 것을 모른 채 잘못 쓸 수 있다
- 「공개 API 가 있다」 와 「우리가 하려는 조작이 공개 API 로 된다」 는 다르다. 범위를 세지 않으면 설계 뒤에 막힌다

## 경계와 오해

- **HAR 로 본 것 = 녹화한 조작뿐** — 녹화 안 한 동작(방 · 우선순위 · 시술 추가)은 알 수 없다. 「목록을 받는 꼴이니 단건도 같을 것」 은 추정으로 표시한다
- **읽기 가능 ≠ 쓰기 가능** — 화면에 보이는 값(읽기 응답에 있음)이라고 그 값을 고치는 기능을 만들 수 있는 것은 아니다. 기능 목록은 읽기 표면이 아니라 쓰기 표면으로 센다
- **PoC 라도 호출 0 이 맞을 수 있다** — 운영 시스템에 쓰는 PoC 는 「되는 가능성」 만 확인하고 조작 자리마다 `연동 필요` 주석을 남긴다. 시연은 목데이터로 → [[seed-data]]
- **[[api-documentation]] 과 혼동 말 것** — 그쪽은 우리가 명세를 만드는 법, 여기는 남의 명세가 어디까지인가
