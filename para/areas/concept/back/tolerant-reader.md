# 관대한 읽기 (Tolerant Reader)

**응답을 읽는 쪽이 자기가 쓰는 칸만 꺼내고, 모르는 칸 · 없는 칸 · 모르는 값에 실패하지 않게 짓는 것.** 그러면 서버가 칸을 더하거나 값 하나를 빼도 이미 깔린 클라이언트(심사 중 앱 · 업데이트 안 한 앱)가 깨지지 않는다.

## 정의

- **필요한 칸만 이름으로 읽는다** — 응답 전체를 엄격한 스키마로 검증하지 않는다. 새 칸은 무시된다.
- **없는 칸은 기본값(null)** — 서버가 칸을 빼도 파싱이 실패하지 않는다.
- **모르는 열거값은 그대로 두거나 기본 분기로** — 값 목록을 검사하지 않으면 서버가 값을 빼도 · 더해도 크래시가 없다.
- 지키지 못하는 것: **칸 이름 바꾸기 · 값 이름 바꾸기 · 칸 모양(문자열 → 객체) 바꾸기.** 이건 관대해도 깨진다 — 읽는 쪽이 아는 이름으로 다른 뜻이 오거나 아예 안 오기 때문.

## 사용 예시

DAY 직원 앱(Flutter) `Need.parse` 는 `why` 를 문자열 그대로 받고 `doctorName` 은 `String` 이 아니면 null, `Limits.parse` 는 `anesMin` · `callMin` 만 읽는다. 서버가 `needs[].why = "accept"` · `doctorName` · `limits.acceptMin` 을 빼고 `cards[].counselors` 를 더해도 심사 중 앱이 깨지지 않았다. 대신 앱 화면에서도 accept 표시가 같이 사라진다 — **안 깨지는 것과 안 바뀌는 것은 다르다.**

## 왜 중요한가

모바일 앱은 서버와 같이 배포되지 않는다. 심사 · 사용자 업데이트 지연 때문에 옛 앱이 새 서버를 오래 본다. 읽는 쪽이 관대하면 서버 변경마다 「앱도 같이 내야 하나」를 묻지 않아도 되고, 그 판정은 **파서 코드를 열어 보는 것**으로 끝난다.

## 경계와 오해

- **관대한 읽기 ≠ 아무거나 받기** — 쓰는 칸의 타입이 틀리면 여전히 실패해야 맞다(조용한 실패를 만들지 않는다) → [[fail-fast]]
- **값을 빼는 것과 모양을 바꾸는 것은 다르다** — 빼기는 버틴다, 이름 · 모양 바꾸기는 못 버틴다. 그래서 앱이 쓰는 `inbox.section` 의 값 이름은 그대로 두고 웹 전용 목록만 지웠다 → [[contract-surface-enumeration]]
- **쓰는 쪽의 규칙과 짝이다** — 서버는 칸을 더하는 것은 자유, 빼거나 바꿀 때는 소비처를 세야 한다 → [[minimal-api-surface]] · [[public-vs-internal-api]]
