# 바이트코드 (Bytecode)

소스를 기계어까지 내려보내지 않고 중간 형태로만 컴파일한 결과물. 특정 CPU·OS 를 향하지 않으므로 어디서 컴파일해도 같은 바이트코드가 나오고, 실행은 환경별 가상 인터프리터([[jvm]])가 맡는다.

## 정의

컴파일 방식과 인터프리터 방식은 각각 단점이 있다.

- **[[compilation]] 의 단점** — OS 별로 따로 컴파일해야 한다 → [[platform-dependency]]
- **[[interpreter]] 의 단점** — 실행할 때마다 소스가 필요해 소스를 공개해야 하고, 문법 검사를 하며 돌아 느리다

**하이브리드 방식**은 둘을 이렇게 맞바꾼다.

1. 컴파일러가 소스를 **바이트코드**로 한 번만 컴파일한다 (소스는 배포에 들어가지 않는다)
2. 그 바이트코드를 **가상 인터프리터**가 각 OS 위에서 실행한다

바이트코드는 기계어와 형태가 가까워서, 실행 시점에 소스를 해석하는 것보다 빠르다.

## 사용 예시

`Hello.java` 를 컴파일하면 `Hello.class` 라는 바이트코드가 나온다.

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello world!!");

        int a = 100;

        if (a < 100) {
            System.out.println("hahhahaha");
        }
    }
}
```

```bash
javac Hello.java   # 소스 → Hello.class (바이트코드)
java Hello         # 바이트코드를 JVM 이 실행
```

`javac` 가 컴파일러, `java` 가 [[jvm]] 을 띄우는 명령이다. 설치를 확인할 때 `java -version` 과 `javac -version` 을 따로 보는 이유가 이 둘이 다른 도구이기 때문이다.

`.class` 파일이 **어디 생기는지도 정할 수 있다.** 소스 옆에 두지 않고 따로 모으면 관리가 쉬워지는데, 그러면 실행할 때 그 위치를 JVM 에 알려줘야 한다 — 그 짝이 [[classpath]] 다.

## 왜 중요한가

**"한 번 컴파일하고 어디서나 실행"이 성립하는 자리가 바이트코드다.** 어떤 OS 에서 컴파일하든 생성된 바이트코드가 같기 때문에, 환경 조합마다 실행파일을 따로 만들 필요가 없어진다.

그리고 소스 대신 바이트코드를 배포한다는 점에서 **소스가 보호된다.** 인터프리터 방식이 소스를 함께 넘겨야 하는 것과 갈리는 지점이다.

## 경계와 오해

- **바이트코드 ≠ 기계어** — CPU 가 직접 실행하지 못한다. 실행하려면 [[jvm]] 이 있어야 한다. "기계어와 흡사하다"는 것은 속도 비교의 말이고, 실행 주체가 같다는 뜻이 아니다.
- **바이트코드 ≠ 알 수 없는 덩어리** — `.class` 는 정해진 자리에 정해진 바이트가 들어간 파일이고 규격이 공개되어 있다 → [[class-file-format]]. 16진수로 직접 써서 만들 수도 있다.
- **바이트코드 ≠ 컴파일을 건너뛴다** — 컴파일은 그대로 한다. 다만 **어디까지** 내려가느냐가 다르다. 그래서 문법 오류는 컴파일 방식과 똑같이 실행 전에 걸린다.
- **소스 보호 ≠ 읽을 수 없음** — 바이트코드는 역컴파일이 어렵지 않다. 소스를 그대로 넘기지 않는다는 정도이고, 암호화가 아니다.
