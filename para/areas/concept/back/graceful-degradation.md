# 선택적 하위 시스템은 꺼져도 본체는 뜬다 (Graceful Degradation)

**한 서비스에 덧붙인 선택적 기능이 준비되지 않았거나 실패하면, 그 기능만 「쓸 수 없음」 으로 답하고 본체는 그대로 뜨고 그대로 답한다.** 실패를 숨기는 것이 아니라 실패의 반경을 그 기능 경계 안에 가둔다.

## 정의

1. **선택적인 것과 본체를 가른다** — 본체(기존 API · health · OpenAPI)는 계약이고, 새로 붙인 하위 시스템은 없어도 서비스가 성립하는 것이다
2. **하위 시스템의 실패 갈래를 전부 센다** — 빈 표 · 해시 불일치 · 접속 실패 · 시간 한도 초과 · 설정 누락 · 예상 못 한 예외
3. **어느 갈래든 결과는 하나** — 그 기능 경로만 정해진 상태 코드(예: 503 `unavailable`)로 답한다. 본체 health · 다른 라우터 · 공개 계약은 한 글자도 바뀌지 않는다
4. **기다림도 실패다** — 하위 시스템 준비가 기동을 붙잡지 않게 시간 한도를 둔다(백그라운드 적재 + 기동 수명주기 안의 한도)
5. **꺼진 이유는 운영자에게, 바깥에는 일반 문구로** — 응답 본문에 접속 주소 · 내부 오류를 싣지 않는다 → [[minimal-api-surface]]

## 사용 예시

phub-gold-jev stg: 허브 stg 는 `app.main` 하나만 돈다. gold 조회(REST · MCP)를 별도 컨테이너로 띄우려면 인프라 레포의 Gateway 경로 일이 생기므로 `app.main` 에 붙였다. 그대로 붙이면 새 표가 아직 빈 첫 배포에서 gold 적재 실패가 허브 전체를 죽여 CD health 가 실패한다. 그래서 gold 의 모든 실패를 「gold 경로만 503 `unavailable`」 로 받고 본체 health · OpenAPI 는 그대로 두었다. 배포 순서도 이 성질 위에 섰다 — 배포(gold 꺼진 채 기동) → 적재 → 재생성.

## 왜 중요한가

- **새 기능이 기존 서비스의 배포를 막지 않는다** — 데이터가 배포 뒤에야 들어갈 수 있는 경우(새 표는 컨테이너 시작 때 생김)에도 첫 배포가 성공한다
- **장애 반경이 기능 경계와 같아진다** — 부가 기능 하나 때문에 기존 사용자가 전부 멈추지 않는다

## 경계와 오해

- **graceful degradation ≠ 조용한 폴백** — 꺼진 기능을 다른 값(빈 목록 · 옛 데이터)으로 메워 정상처럼 답하면 은폐다. 꺼졌다는 사실이 상태 코드로 드러나야 한다 → [[no-silent-fallback]]
- **본체의 필수 의존성에는 쓰지 않는다** — 본체가 없으면 안 되는 DB 가 죽었는데 「일부만 뜨게」 하면 그것이 조용한 실패다. 필수는 [[fail-fast]]
- **실패 응답이 정보를 흘린다** — 503 본문에 DB 호스트가 실릴 뻔했다(인증 없는 Gateway 뒤 · 검수 R-1). 꺼진 이유의 상세는 로그로
- **시험이 전역 앱을 다시 만들면 다른 경계를 건드린다** — gold 를 붙인 상태 · 뗀 상태를 시험하려고 전역 앱을 다시 만들다 다른 라우터 wiring 이 바뀌어 glossary 시험 3 개가 깨졌다. 시험마다 앱을 새로 짓고 전역을 건드리지 않는다
