# 서블릿 컨테이너 (Servlet Container)

**서블릿을 만들고 부르고 정리하는 실행 환경 — 내 코드의 흐름을 대신 갖는 쪽.** Day63 의 정의가 그것이다 — 「서블릿을 관리하고 실행하는 환경을 말한다. Java EE 표준을 따르며, 서블릿의 생명 주기(생성, 초기화, 요청 처리, 종료)를 관리한다」 → [[servlet]] · [[java-ee]]

## 정의

Day63 이 하는 일을 셋 적었고, **세 번째 줄에 이 회차에서 가장 큰 것이 들어 있다.**

| Day63 의 문장 | 무엇을 대신하나 |
|---|---|
| 「서블릿의 생명 주기(생성, 초기화, 요청 처리, 종료)를 관리한다」 | 내가 `new` 하고 부르던 것 → [[servlet]] |
| 「HTTP 요청을 받아 서블릿으로 전달하고, 서블릿의 응답을 클라이언트로 돌려보낸다」 | Day61 의 `accept()` 루프와 대화 규칙 → [[socket]] · [[network-protocol]] |
| 「**멀티스레딩**, **세션 관리**, **보안** 등의 기능을 제공하여 서블릿이 효율적으로 작동할 수 있도록 지원한다」 | 접속마다 `new Thread`, `setAttribute` 로 붙여 둔 로그인 정보 → [[thread]] |

그리고 관계를 두 문장으로 못 박는다 — 「서블릿은 서블릿 컨테이너 안에서 실행됩니다」·「서블릿 컨테이너가 없다면, 서블릿은 독립적으로 동작할 수 없다」.

**「없으면 동작할 수 없다」가 이 개념의 정의보다 정확한 설명이다.** 서블릿은 부품이고 이것이 기계이며, 부품 혼자로는 아무 일도 일어나지 않는다.

### 나흘 전에 비워 둔 자리 하나가 여기서 채워진다

[[thread]] 노트가 Day61(2024-08-22)을 두고 이렇게 적어 두었다 — 「접속마다 쓰레드를 붙이면서 쓰레드 수에 상한이 없고, Day48 의 「병렬 작업의 갯수를 고려하여 쓰레드를 생성하여야 한다」가 여기서 지켜지지 않는데 그것을 지키는 도구는 이 회차에 없다」.

**나흘 뒤 Day63 에서 그 도구가 「컨테이너가 제공하는 멀티스레딩」이라는 이름으로 온다.** 컨테이너는 쓰레드를 접속마다 만들지 않고 **살려 둔 것을 돌려 쓰며 상한이 설정값**이므로, Day48 의 문장이 코드가 아니라 **설정 파일로** 지켜지는 형태다 → [[thread-state]] · [[universal-scalability-law]]

**그런데 같은 한 줄이 사흘 전(Day62)의 코드를 깨뜨린다.** [[thread-local]] 노트가 그 회차를 두고 「이 코드는 「쓰레드가 곧 죽는다」에 기대어 맞고 있고, 쓰레드 풀을 도입하는 순간 이것이 최악의 버그가 된다」고 적었는데, **컨테이너가 정확히 그 풀이다.** Day62 의 `SqlSessionFactoryProxy` 를 이 위에 그대로 올리면:

| Day61·62 의 구조 | 컨테이너 위에서 |
|---|---|
| 접속마다 `new Thread` → 대화가 끝나면 쓰레드가 죽는다 | 쓰레드가 **살아서 다음 요청을 받는다** |
| 쓰레드가 죽으므로 쓰레드에 매달린 세션도 사라진다 | **먼저 다녀간 사람의 세션이 남아 있다** |
| `remove()` 가 없는 것이 드러나지 않는다 | `get()` 이 **남의 미확정 트랜잭션과 캐시**를 돌려준다 |

**즉 「가려 주던 것」이 없어지는 회차다.** 필기는 멀티스레딩을 이득으로만 적었고, 그것이 방금 만든 코드의 전제를 무너뜨린다는 것은 적지 않았다 → [[thread-local]] · [[transaction]] · [[sql-session]]

**하루 뒤 Day64 가 그 프록시를 실제로 이 위에 올린다** — 리스너의 부팅 코드에 `new SqlSessionFactoryProxy(sqlSessionFactory)` 가 있고, 그것이 `ServletContext` 속성으로 올라가 모든 요청이 쓴다. 위 표가 예고였고 여기서 실물이 됐다 → [[servlet-listener]] · [[servlet-context]]

### 하루 뒤 Day64 — 관리 대상이 셋으로 늘고 부팅 순서가 처음 적힌다

Day63 은 컨테이너가 관리하는 것을 **서블릿**으로만 적었다. Day64 는 역할을 다섯으로 다시 세우고 **마지막 하나를 새로 더한다.**

| Day64 의 역할 | Day63 에 있었나 |
|---|---|
| 「서블릿 관리 … `init()`, `service()`, `destroy()` 와 같은 생명주기 메서드를 호출」 | 있다 (메서드 이름은 새것) → [[servlet-lifecycle]] |
| 「HTTP 요청 및 응답 처리 … 요청 정보를 파싱하고, 응답을 직렬화하여 전송」 | 있다 |
| 「애플리케이션 보안 관리」 | 있다 (한 줄뿐인 것도 같다 — 아래 「경계와 오해」) |
| 「멀티스레드 처리 … 각 요청은 개별 스레드에서 처리」 | 있다 |
| **「필터와 리스너 관리」** | **없다** — 관리 대상이 [[web-component]] 셋으로 넓어졌다 |

그리고 **부팅 순서가 처음 글로 적힌다**(리스너 구동원리 절) — `Tomcat.start()` → 서블릿 컨테이너 실행 → `web.xml`·`@WebListener` 로 등록된 것 탐색 → 인스턴스화 → `contextInitialized` 호출 → **「이후 서블릿이나 JSP가 클라이언트 요청을 처리할 준비가 완료된다」**.

**마지막 한 줄이 이 회차가 준 보장이다** — 리스너가 끝난 다음에 요청 처리가 시작되므로, 서블릿은 리스너가 놓아 둔 것을 이미 있다고 가정해도 된다. Day63 노트가 「생성자에 인수를 줄 수 없어 의존을 어디서 받나가 새 문제가 된다」고 적은 자리의 답이 **이 순서 + 앱 스코프 저장소**다 → [[servlet-listener]] · [[servlet-context]] · [[dependency-injection]]

## 왜 중요한가

**실행의 주인이 바뀐다.** 지금까지 프로그램은 `main` 에서 시작해 내가 부른 순서대로 흘렀다. 컨테이너 안에서는 **내 코드가 시작점을 갖지 않고**, 언제 불릴지·몇 번 불릴지·동시에 몇 개가 불릴지를 밖에서 정한다. 이 뒤집힘이 이후에 배울 모든 프레임워크의 공통 전제다 → [[main-method]] · [[dependency-injection]]

**그래서 생성자에 인수를 줄 수 없다.** 컨테이너가 클래스를 찾아 만들므로 내 서블릿은 **기본 생성자로 만들어진다** — Day61 의 `DaoFactory(SqlSessionFactory)` 처럼 필요한 것을 생성자로 받아 오던 방식이 그 자리에서는 성립하지 않는다. 「의존을 어디서 받나」가 새로 풀어야 하는 문제가 되고, 그것이 프레임워크가 주입을 하는 이유다 → [[dependency-injection]] · [[constructor]]

**그리고 서버를 껐다 켜는 단위가 내 프로그램이 아니게 된다.** 앱 하나가 아니라 컨테이너 하나가 떠 있고 그 안에 여러 앱이 얹히므로, 내 코드의 오류가 남의 앱과 같은 프로세스에서 난다 — 메모리도 쓰레드도 함께 쓴다 → [[process]] · [[web-application-deployment]]

## 경계와 오해

- **서블릿 컨테이너 ≠ WAS** — 컨테이너는 WAS 의 **한 부분**이다. Day63 의 Tomcat 구조 절이 그것을 정확히 보여 준다 — 「Mini Web Server」와 「Web Container(Servlet Container)」와 「Java App」이 나란히 있고, 컨테이너는 그중 하나다. 그런데 같은 노트의 대표 예 목록은 톰캣을 WebLogic·WebSphere 와 한 줄에 두므로, **「컨테이너만 있는 것」과 「Java EE 전체를 구현한 것」이 같은 이름으로 불린다** → [[web-application-server]] · [[java-ee]]
- **서블릿 컨테이너 ≠ 웹 서버** — 컨테이너는 HTTP 를 직접 듣지 않아도 된다. 소켓을 열고 요청을 파싱해서 넘겨 주는 부분(커넥터)이 따로 있고, 톰캣은 그 둘을 함께 갖고 있어서 구별이 안 보인다. 외부 웹 서버 뒤에 톰캣을 두는 구성에서 실제로 갈리는 자리가 이것이다 → [[web-server]] · [[tomcat]]
- **「멀티스레딩을 제공한다」 ≠ 내 코드가 쓰레드 안전해진다** — **이 회차에서 가장 비싸게 오해할 수 있는 한 줄이다.** 컨테이너가 주는 것은 「동시에 여러 요청을 처리한다」이고, 그 동시성이 만드는 문제를 푸는 것은 여전히 내 코드다. 서블릿 인스턴스는 하나이고 여러 쓰레드가 그 안으로 들어오므로, 필드에 값을 담는 순간 Day61 이 겪은 공유 문제가 그대로 재현된다. **편해진 것은 쓰레드를 만드는 일이고, 안전은 아무도 대신 해 주지 않는다** → [[thread]] · [[servlet]] · [[thread-local]]
- **「세션 관리를 제공한다」 ≠ 상태를 알아서 지켜 준다** — [[client-server-model]] 노트가 Day61 을 두고 「`prompt.setAttribute("loginUser", loginUser)` 로 상태를 **연결에 붙인다**」·「기억의 수명이 연결의 수명과 같아진다」고 적었는데, 컨테이너의 세션은 **연결이 끊긴 뒤에도 남는 기억**이다. 필기가 손으로 만든 그 자리에 같은 이름의 API 가 있다는 것이 이 규격에서 세션이 왜 필요한지를 그대로 설명한다 — 요청마다 연결이 끊기므로 「누구인지」를 연결에 붙일 수 없다. 다만 **관리해 준다는 것은 보관해 준다는 뜻이고**, 무엇을 담을지·언제 버릴지·서버가 두 대면 어디에 있을지는 내가 정한다 → [[caching]]
- **필기의 Tomcat 구조 표가 층을 하나 어긋내 놓았다** — 「Web Container(Servlet Container) : Servlet을 구축하는 환경이다. Application에 명령을 호출한다」·「Java App : Servlet을 수행하며 동적자원을 관리한다」인데, **서블릿을 수행하는 것은 컨테이너**이고 Java App 은 **그 서블릿 자체**다. 이렇게 읽으면 컨테이너 → 애플리케이션 → 서블릿 세 층이 되어, 같은 노트의 「서블릿은 서블릿 컨테이너 안에서 실행됩니다」와 층수가 맞지 않는다. 「구축하는 환경」이라는 표현도 절반이다 — 컨테이너는 서블릿을 **빌드하는** 것이 아니라 **실행 중에 만들어 부른다** → [[tomcat]] · [[servlet]]
- **생명 주기를 컨테이너가 갖는다는 것은 「초기화가 언제 도는지 모른다」는 뜻이다** — 첫 요청에 만들어질 수도 있고 앱이 뜰 때 만들어질 수도 있다(설정으로 정한다). 그래서 **초기화 코드를 생성자에 두는 것과 초기화 메서드에 두는 것이 다른 시점**이고, 그 차이가 「서버는 떴는데 첫 요청만 느리다」로 나타난다 → [[class-loading]] · [[constructor]]
- **Day64 의 「웹 애플리케이션이 시작되면 서블릿을 로드하고 인스턴스화한다」는 기본값이 아니다 — 기본은 첫 요청이다** — 동작 원리 1번이 그렇게 적혀 있는데, 규격의 기본 동작은 **첫 요청이 올 때 만드는 것**이고 기동 시점에 만드는 것은 `loadOnStartup` 을 준 경우다. Day63 쪽은 「첫 요청에 만들어질 수도 있고 앱이 뜰 때 만들어질 수도 있다(설정으로 정한다)」로 두 경우를 다 적었으므로, **하루 뒤 필기가 한쪽만 적어 좁아졌다.** 이 차이가 값을 갖는 자리는 오류가 드러나는 시점이다 — `init` 안의 실패가 기동 로그에 나오는지 첫 요청에 나오는지가 갈린다 → [[servlet-lifecycle]] · [[class-loading]]
- **Day64 의 「요청에 따라 `doGet()`, `doPost()` 등의 메서드가 실행된다」는 컨테이너가 하는 일이 아니다** — 컨테이너는 **`service()` 까지만** 부른다. 그 안에서 요청 방식을 보고 갈라 주는 것은 `HttpServlet.service()` 의 구현이고, 같은 노트가 `implements Servlet` 으로 만든 서블릿에는 `doGet` 이 아예 없다. 「컨테이너가 `doGet` 을 부른다」로 알고 있으면 **`doGet` 을 적어 두고 왜 안 불리는지를 컨테이너 설정에서 찾게 된다** — 실제로는 부모 클래스를 잘못 고른 것이다 → [[servlet-lifecycle]] · [[generic-servlet]] · [[method-overriding]]
- **「멀티스레드 방식으로 서블릿을 관리한다 / 각 요청은 개별 스레드에서 처리된다」가 「요청마다 쓰레드를 새로 만든다」는 뜻이 아니다** — 두 회차의 문장이 어긋나 보이는데 어긋나지 않는다. 「개별 스레드」는 **동시에 도는 것이 서로 다른 쓰레드**라는 뜻이고, 그 쓰레드가 **새것이라는 뜻은 아니다.** 컨테이너는 살려 둔 쓰레드를 돌려 쓴다(위 「나흘 전에 비워 둔 자리」). 이 구별이 값을 갖는 이유는 하나다 — 「요청이 끝나면 쓰레드가 죽는다」에 기댄 코드가 Day62 에 있고, **필기는 두 회차에 걸쳐 재사용을 한 번도 적지 않았다** → [[thread]] · [[thread-local]] · [[thread-state]]
- **「서블릿 컨테이너는 웹 애플리케이션의 보안을 관리한다」 — 두 회차 모두 이 한 줄로 끝난다** — 규격이 실제로 정하는 것은 **선언적 보안**이다: `web.xml` 의 `security-constraint` 로 「이 URL 패턴은 이 역할만」을 적고, 인증 방식(BASIC·FORM·CLIENT-CERT)을 고르고, 코드에서는 `isUserInRole`·`getUserPrincipal` 로 묻는다. **컨테이너가 해 주는 것은 「누구인지 확인하고 역할을 붙이는 일」까지**이고 무엇을 누구에게 허용할지는 내가 적는다. 이 프로젝트는 그것을 쓰지 않을 것이고 로그인 정보를 세션에 담는 방식으로 갈 텐데, **그러면 「컨테이너가 보안을 관리한다」는 이 코드에 대해 아무 일도 하지 않는 문장**이 된다 → [[servlet-filter]] · [[web-application-deployment]]
- **컨테이너가 예외를 삼켜 응답으로 바꾼다** — 내 코드에서 던진 예외가 프로세스를 죽이지 않고 **500 응답**이 된다. [[thread]] 노트가 Day61 의 `catch (Exception e)` 를 두고 「그 접속만 끝내고 서버는 계속 돈다」로 적은 성질이 여기서는 구조에 들어 있다. 편한 대신 **터진 것을 내가 안 보게 되므로**, 로그를 어디로 보낼지가 처음부터 문제가 된다 → [[exception-handling]]

## 출처

- [[2024-08-26-Day63]] — 「서블릿 컨테이너와 서블릿」 절의 「서블릿 컨테이너(Servlet Container)」·「서블릿과 서블릿 컨테이너의 관계」 두 항목이 이 개념이다. 「서블릿을 관리하고 실행하는 환경 … Java EE 표준을 따르며, 서블릿의 생명 주기(생성, 초기화, 요청 처리, 종료)를 관리한다」·「HTTP 요청을 받아 서블릿으로 전달하고, 서블릿의 응답을 클라이언트로 돌려보낸다」·「멀티스레딩, 세션 관리, 보안 등의 기능을 제공」으로 하는 일을 적고, 관계를 「서블릿은 서블릿 컨테이너 안에서 실행됩니다」·「서블릿 컨테이너가 없다면, 서블릿은 독립적으로 동작할 수 없다」로 못 박았다. **「멀티스레딩」 한 낱말이 이 회차에서 가장 큰 것**인데 필기는 이득으로만 적는다 — Day61 이 접속마다 `new Thread` 를 만들며 남긴 「상한이 없다」는 문제가 이것으로 답해지는 동시에, 사흘 전 Day62 가 `remove()` 없이 쓴 쓰레드별 세션이 **쓰레드가 재사용되는 순간 남의 세션을 물려주는** 구조가 된다는 것은 다루지 않았다(→ [[thread-local]]). 「멀티스레딩을 제공한다」가 내 코드의 쓰레드 안전을 뜻하지 않는다는 것, 서블릿 인스턴스가 하나라는 것, 생성자를 내가 부를 수 없어 의존을 받을 자리가 없어진다는 것도 없다. 같은 노트의 Tomcat 구조 표는 「Web Container … Application에 명령을 호출한다 / Java App : Servlet을 수행하며」로 적어 이 절과 층수가 어긋난다
- [[2024-08-27-Day64]] — 하루 뒤. 「서블릿 컨테이너(Servlet Container)」 절이 정의를 「자바 웹 애플리케이션을 실행하고 관리하는 **서버 측 환경**」·「웹 서버와 애플리케이션 서버의 역할을 동시에 수행할 수 있으며」로 다시 적고, 역할을 다섯으로 세운다 — 서블릿 관리(`init()`·`service()`·`destroy()` 호출) · HTTP 요청/응답 처리(파싱과 직렬화) · 애플리케이션 보안 관리 · 멀티스레드 처리 · **필터와 리스너 관리**. 마지막 하나가 새것이고, 관리 대상이 서블릿에서 [[web-component]] 셋으로 넓어진다. 동작 원리를 네 단계(서블릿 로딩 → 요청-응답 처리 → 응답 전송 → 서블릿 종료)로 적고, **리스너 구동원리 절에서 부팅 순서를 처음 글로 남긴다** — `Tomcat.start()` → 컨테이너 실행 → 리스너 탐색·인스턴스화 → `contextInitialized` → 「이후 서블릿이나 JSP가 클라이언트 요청을 처리할 준비가 완료된다」. 그 마지막 줄이 Day63 에서 답 없이 남은 「의존을 어디서 받나」의 답을 성립시킨다(리스너가 만들어 [[servlet-context]] 에 올려 두면 서블릿이 꺼낸다). 다만 「웹 애플리케이션이 시작되면 서블릿을 로드하고 인스턴스화한다」는 **기본값이 아니라 `loadOnStartup` 을 준 경우**이고(Day63 쪽이 두 경우를 다 적었으므로 하루 뒤 필기가 좁아졌다), 「요청에 따라 `doGet()`, `doPost()` 등의 메서드가 실행된다」는 컨테이너가 아니라 `HttpServlet` 이 하는 일이며 같은 노트의 코드(`implements Servlet`)에는 그 메서드가 없다. 「각 요청은 개별 스레드에서 처리되며」도 쓰레드가 **새것이라는 뜻은 아니고**, 재사용은 두 회차 어디에도 적히지 않았다. 「애플리케이션 보안 관리」는 Day63 과 똑같이 한 줄로 끝난다
