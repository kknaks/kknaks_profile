# 외부 반영 대기열 — 내 상태 먼저, 원천 반영은 확인될 때까지

외부 시스템(원천)에 써야 하는 조작을 **응답 안에서 기다리지 않는다.** 우리 DB 상태를 먼저 바꾸고, 원천에 보낼 요청은 대기열 행으로 남긴 뒤 **보냄 → 원천을 다시 읽어 맞는지 확인 → 안 맞으면 재전송 → N회면 실패**로 끌고 간다. 「보냈다(2xx)」 와 「반영됐다(다시 읽으니 그 값)」 를 다른 상태로 센다.

## 정의

1. **조작 1번 = 이벤트 1줄 + 외부 op 0 ~ N줄** — op 마다 경로 · 본문 · **확인 조건(`expect`)** 을 같이 저장한다. 확인 조건이 없으면 「반영됐다」 를 말할 수 없다
2. **상태 넷** — `pending`(대기) → `sent`(2xx) → `confirmed`(다음 조회에서 `expect` 일치) / `failed`(시도 3회). 오류면 `attempts+1` 하고 `pending` 으로 되돌린다. `sent` 인데 조회 2번 동안 안 맞아도 재전송
3. **같은 대상의 op 은 만든 순서대로** — 순서가 의미인 체인(방 → 담당자 → 호출)은 앞이 오류면 대상 전체가 멈추고, 앞이 `failed` 면 뒤 op 은 보내지 않고 같이 `failed`(사유: 앞 op 실패)
4. **확인은 「다음 주기 조회」 를 기다리지 않는다** — 2xx 면 바로 다음 op 을 보내고, 보낸 게 있으면 짧은 지연(1.5초) 뒤 조회 1회로 확인을 빨리 찍는다
5. **뒤 op 이 같은 값을 다시 바꿨으면 앞 op 은 확인된 것으로 본다(`superseded`)** — 호출(`WAITING`) 뒤 수락(`READY`)처럼 앞 op 의 확인 조건이 더는 맞을 수 없는 경우
6. **조회 덮어쓰기는 반영 대기 중인 필드만 비켜 간다** — 원천 기준 필드는 주기 조회가 덮어쓰되, 그 필드를 바꾸는 op 이 `pending`/`sent` 면 건너뛴다. `failed` 는 대기가 아니다 — **실패 뒤에는 원천 값을 따른다**
7. **화면에 반영 상태를 보인다** — 카드에 「KOS 반영 중 · 실패」. 실패 표시는 그 대상의 다음 op 이 확인될 때까지 남는다

## 사용 예시

cc-prototype 명동 PoC v2 의 `kos_op` 표와 루프(`kos/ops.py` · `kos/runtime.py`):

```text
[호출] 버튼
  event_log: call_create
  kos_op seq1  change-tasks-room      expect: 작업에 방 있음
  kos_op seq2  담당자 지정            expect: assignee 포함
  kos_op seq3  call-tasks-doctors     expect: status WAITING
→ 응답은 즉시 {ok}, 카드는 「KOS 반영 중」
→ seq1 2xx → 곧바로 seq2 → seq3 → 1.5초 뒤 일정 조회 1회 → 셋 다 confirmed
```

## 왜 중요한가

- **응답이 원천을 기다리면 화면이 굳는다** — 외부 호출 3단계를 동기로 묶으면 버튼 하나가 수 초 걸리고, 중간 실패의 복구를 화면이 떠안는다
- **「보냈다」 를 「반영됐다」 로 세면 조용히 틀린다** — 원천이 200 을 주고 무시하는 경우가 실제로 있다(담당자 id 를 엉뚱한 것으로 넣으면 200 · 무반영 → [[public-vs-internal-api]]). 다시 읽어 맞는지 봐야 안다
- **확인 대기를 순서 조건으로 쓰면 느려진다** — 처음엔 「앞 op confirmed(= 다음 10초 조회) 뒤 다음 op」 이라 3단계가 KOS 에 20 ~ 30초 늦게 떴다. 순서는 2xx 로 잇고 확인은 따로 빨리 찍는 것으로 풀었다
- **「다시 읽기」 도 원천 화면이 읽는 길로 해야 한다** — 전체현황판의 여권 사진은 KOS 에 올려 200 · 저장까지 됐고 ccc 상태도 `ok` 였는데 KOS 일정 「사진 · 펜차트」 탭에 안 보였다. 그 탭은 이미지를 `{고객, 일정}` 으로 읽는다. 등록 본문의 일정 칸(`scheduleId`)을 「안 보냄」 기본값으로 둬서 사진은 고객에만 붙었고, **고객으로만 다시 읽으면 보이니 확인은 통과했다.** KOS 웹 자체의 같은 조작을 녹화(HAR)해 보니 일정 칸 · 분류를 싣고 있었다. 확인 조건(`expect`)은 「저장됐나」 가 아니라 **사람이 보는 화면이 쓰는 조회로 걸리나**로 잡는다. 이미 「성공」 으로 남은 옛 행은 이 고침으로 바뀌지 않는다 — 다시 올려야 한다
- **원천의 읽기가 최신을 주지 않을 수도 있다** — KOS 문진은 다시 제출하면 200 을 주지만, 제출본 읽기는 공개 · 내부 둘 다 **첫 제출본**을 돌려준다. 다시 읽기로 「반영됐다」 를 판정할 수 없는 자리라, 받은 답을 우리 이력(`web_submit`)에 두고 원천 제출본보다 새로우면 그것을 그린다(원천이 더 새면 원천이 이긴다)
- **분류 같은 코드 값은 지점마다 다르다** — 「여권」 분류는 그 지점 코드 표에 있을 때만 싣고, 없으면 키를 뺀다(데모 지점엔 「시술 전 · 후」 뿐). 이름 판정은 한 곳에
- **빨라지자 재전송이 원천을 되돌렸다** — 앞 op 의 확인 조건이 뒤 op 에 덮여 영영 안 맞자, 재전송이 수락된 호출을 다시 WAITING 으로 돌렸다. `superseded` 가 그 구멍을 막는다

## 경계와 오해

- **[[idempotency]] 가 아니다** — 멱등은 「두 번 와도 한 번처럼」 을 받는 쪽이 보장하는 것이고, 여기는 보내는 쪽이 원천 상태를 읽어 재전송 여부를 정하는 것이다. 원천이 멱등을 약속하지 않으면 재전송 조건(확인 실패 · supersede)을 더 좁게 잡아야 한다
- **트랜잭셔널 아웃박스와 닮았지만 확인이 다르다** — 아웃박스는 「DB 커밋과 발송을 같이」 가 핵심이고, 이것은 **원천을 다시 읽어 맞는지**가 완료 조건이다. 메시지 브로커 없이 DB 행과 주기 조회로 닫힌다
- **낙관적 UI 의 되돌리기는 없다** — 실패해도 우리에게만 있는 기록(이벤트 · 호출 · 수락)은 지우지 않는다. 원천 기준 필드만 원천 값으로 돌아간다. 되돌리기 정책은 따로 정할 몫
- **실패를 삼키지 않는다** — `failed` 는 이벤트(`kos_failed`)와 카드 표시로 드러낸다 → [[no-silent-fallback]]
