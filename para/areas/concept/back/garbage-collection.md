# 가비지 컬렉션 (Garbage Collection)

**아무 레퍼런스도 가리키지 않게 된 인스턴스**를 가비지라 하고, 그 메모리를 [[jvm]] 이 알아서 회수하는 것을 가비지 컬렉션이라 한다.

## 정의

가비지는 인스턴스가 망가져서 생기는 것이 아니다. **가리키는 이름이 사라져서** 생긴다.

```text
새로 생성된 인스턴스를 할당 받으면 기존의 레퍼런스는 가비지가 된다.
jvm에서는 다양한 방법으로 가비지를 청소한다.
```

레퍼런스와 인스턴스는 개수가 따로 움직이므로, 이름이 0개가 되는 순간이 온다 → [[object-reference]] · [[instance]]

## 사용 예시

레퍼런스에 새 인스턴스를 대입하면 앞의 것이 즉시 가비지가 된다.

```java
int[] arr = new int[5];   // 인스턴스 A 를 가리킨다
arr = new int[3];         // 이제 B 를 가리킨다
                          // → A 를 가리키는 것이 아무것도 없다 = 가비지

arr = null;               // B 도 가비지가 된다
```

받는 레퍼런스가 없으면 만들어진 그 자리에서 가비지다.

```java
new int[10];              // 주소를 아무도 받지 않았다
```

### 자기 코드에서 그것을 찾아낸 자리

다섯 주 뒤, 실습 프로젝트를 손보면서 **이 개념이 처음 「고칠 이유」로 쓰인다.** Day38 의 필기가 문제점으로 적은 두 번째 줄이 그것이다 — 「부모의 menuGroup이 있다면 인스턴스된 Stack은 Garbage가 된다」.

```java
  public MenuGroup(String title) {
    super(title);
    this.menuPath = new Stack<>();          // ① 만든다
  }

  public void setParent(MenuGroup parent) {
    this.parent = parent;
    this.menuPath = parent.menuPath;        // ② 부모 것으로 갈아 끼운다 → ①이 가비지
  }
```

**Day11 의 `arr = new int[3]` 예시와 같은 모양**이다 — 레퍼런스에 새 값을 대입하는 순간 앞의 인스턴스를 가리키는 것이 없어진다. 다른 것은 그것이 **연습용 두 줄이 아니라 실제 코드에서 매번 일어나고 있었다**는 것이고, 그래서 이번에는 관찰이 아니라 **변경의 근거**가 된다 — 생성자에서 만드는 줄을 없애는 쪽으로 갔다 → [[stack]] · [[refactoring]]

## 왜 중요한가

**C 처럼 `free` 를 부르지 않아도 되는 이유가 이것이다.** 개발자가 하는 일은 "안 쓰는 참조를 끊는 것"까지고, 언제 회수할지는 JVM 이 정한다. 이 역할 분담에서 두 가지가 따라 나온다.

1. **메모리 누수의 모양이 바뀐다** — Java 에서 누수는 "해제를 잊은 것"이 아니라 **필요 없어진 것을 계속 가리키고 있는 것**으로 나타난다. 컬렉션에 넣고 안 지운 객체, 끝난 작업의 참조를 들고 있는 캐시 같은 것들이다. 회수를 못 하는 이유가 GC 가 아니라 **내 코드가 놓지 않았기 때문**이다.
2. **회수 시점을 코드가 정할 수 없다** — 그래서 메모리가 아닌 자원(파일 핸들, 소켓, DB 커넥션)은 GC 에 맡길 수 없고 `close()` 로 직접 돌려줘야 한다 → [[standard-input]]

**그런데 회수 직전에 끼어들 자리가 하나 있는 것처럼 보인다.** [[object-class]] 의 여섯 메서드 중 마지막이 그것이다.

```java
// 6) finalize()
//    => 가비지 컬렉터에 의해 메모리에서 해제되기 직전에 호출된다.
```

모든 클래스가 이것을 물려받으므로 재정의해서 정리 코드를 넣을 수 있게 보이고, 그러면 위의 2번이 뒤집히는 듯하다. **뒤집히지 않는다** — 아래 「경계와 오해」가 그 이유다.

## 경계와 오해

- **레퍼런스 카운팅은 JVM 이 쓰는 방식이 아니다** — 이 필기는 "가비지를 파악하기 위해 레퍼런스 카운터 테이블이 존재한다"고 배웠다. 카운팅은 CPython·Objective-C ARC 같은 곳이 쓰는 방식이고, HotSpot JVM 은 **GC 루트(스택의 지역 변수, static 필드 등)에서 도달할 수 있는지**를 추적해 판정한다. 이 차이가 실제로 갈리는 자리가 **순환 참조**다 — 서로를 가리키는 두 인스턴스는 카운트가 0 이 되지 않아 카운팅 방식에서는 영원히 남지만, 도달성 추적에서는 루트에서 닿지 않으므로 정상적으로 회수된다. "카운터가 0 이면 지운다"로 외우면 왜 Java 에서 순환 참조를 걱정하지 않는지 설명할 수 없다.
- **가비지가 된 시점 ≠ 회수된 시점** — 아무도 안 가리키게 된 순간 가비지지만, 그 메모리가 언제 비는지는 JVM 이 정한다. `System.gc()` 도 명령이 아니라 요청이고, 무시될 수 있다.
- **GC 는 메모리만 돌려준다** — 파일·소켓·커넥션은 대상이 아니다. `close()` 를 부르지 않으면 객체가 회수되어도 자원은 잡혀 있을 수 있다.
- **가비지는 버그가 아니다** — 프로그램이 도는 동안 계속 생기는 정상적인 부산물이다. 문제가 되는 것은 가비지가 **되지 못하는** 쪽이다.
- **「가비지가 된다」가 그 코드를 고칠 이유로 충분하지는 않다** — Day38 이 문제점으로 든 것은 메뉴 개수만큼의 빈 `Stack` 이고, 그것은 프로그램 시작에 한 번 생겨 즉시 회수되는 몇십 바이트다. **실제로 그 변경이 값을 낸 이유는 낭비가 아니라 옆에 있던 결함**이었다 — 부모의 스택 참조를 물려받는 방식이라 메뉴가 세 층이면 조립 순서에 따라 경로가 조상을 잃었고, 참조 물려받기가 없어지면서 그 의존도 사라졌다. **필기는 눈에 보이는 낭비를 근거로 적고 눈에 안 보이는 버그를 고쳤다.** 가비지는 세기 쉬워서 근거로 쓰기 좋지만, **회수되는 가비지의 양은 대개 고칠 이유의 크기와 상관이 없다** → [[composite-pattern]] · [[refactoring]]
- **`close()` 를 손으로 부르는 것은 자바 7 부터 문법이 대신한다** — 위 2번 항목이 「파일·소켓·커넥션은 `close()` 로 직접 돌려줘야 한다」로 끝났는데, 그 「직접」을 블록 구조로 옮긴 것이 `try (자원) { }` 다. GC 가 못 하는 일이라는 사실은 그대로이고 **잊을 수 있는 자리가 줄어든 것**이다 → [[try-with-resources]]
- **`null` 대입이 메모리를 비우는 명령은 아니다** — 참조를 끊는 것일 뿐이다. 지역 변수라면 메서드가 끝나면 어차피 끊기므로, 습관적으로 `null` 을 넣는 것은 대개 의미가 없다.
- **`finalize()` 는 소멸자가 아니다** — 「해제되기 직전에 호출된다」는 **불린다면 그 시점이라는 뜻**이고 불린다는 보장이 아니다. 회수가 일어나지 않으면 안 불리고, 프로그램이 끝날 때도 남은 객체의 `finalize()` 는 실행되지 않는다. C++ 의 소멸자처럼 「범위를 벗어나면 반드시 실행」되는 것과 정반대의 성질이라, 여기에 `close()` 를 넣으면 **파일이 영영 안 닫힌다.** 회수 시점을 코드가 정할 수 없다는 성질이 이 훅에도 그대로 적용되는 것이고, 그래서 Java 9 부터 폐기 예정으로 표시됐다 → [[object-class]]
- **「모든 클래스가 물려받았다」가 「쓰라고 준 것」은 아니다** — `finalize()` 는 `toString()` 처럼 목록에 나란히 적혀 있지만 재정의할 이유가 거의 없는 쪽이다. `protected` 라 밖에서 부를 수도 없다. 여섯 메서드를 같은 자격으로 읽으면 이 구별이 안 보인다 → [[method-overriding]] · [[access-modifier]]
