# 웹 애플리케이션 서버 (WAS)

**요청을 받아 내 코드를 실행해서 응답을 만들어 주는 서버.** Day63 의 정의는 「동적인 콘텐츠를 생성하는 서버로 … 복잡한 비즈니스 로직을 처리하고, 데이터베이스와 통신하며, 사용자의 요청에 따라 동적 페이지 및 애플리케이션 로직을 수행한다」다. **내 코드가 이 서버 안에서 돌기 시작하는 것**이 이 낱말의 실질이고, 그때부터 실행의 주인이 내가 아니다 → [[static-and-dynamic-content]] · [[servlet-container]]

## 정의

Day63 이 기능을 셋 적었고, 셋이 **Day45 이후 실습에서 손으로 만들어 온 것들**이다.

| Day63 의 기능 | 실습에서는 누가 했나 |
|---|---|
| **동적 콘텐츠 생성** — 「요청에 따라 사용자 맞춤형 동적 콘텐츠를 생성」 | Day61 의 서버가 화면 문자열을 만들어 보냈다 → [[client-server-model]] |
| **비즈니스 로직 처리** — 「복잡한 비즈니스 로직을 수행하고 … 데이터를 가공하여 클라이언트에 응답」 | Command 구현체들 → [[command-pattern]] |
| **데이터베이스 연동** — 「데이터베이스와의 상호작용을 통해 데이터의 CRUD 작업을 수행」 | DAO + MyBatis → [[dao-pattern]] · [[mybatis]] |

**세 줄 어디에도 「내 코드」라는 말이 없다는 것이 이 표기의 함정이다.** 실제로 저 셋을 하는 것은 서버가 아니라 서버 안에 올려 둔 내 클래스이고, 서버가 하는 일은 **그 클래스를 언제 어떻게 부를지 정하는 것**이다. Day63 의 구조 절이 그것을 한 칸 더 갈라 적었다 — 「WAS 내에서 비즈니스 로직은 Java Application에 의해 처리된다」 → [[servlet]]

### Day63 의 비교 표

| 항목 | 웹 서버 | WAS |
|---|---|---|
| 주요 역할 | 정적 콘텐츠 제공 | 동적 콘텐츠 처리 및 비즈니스 로직 수행 |
| 주요 기능 | HTTP 요청 처리, 정적 리소스 제공, 로드 밸런싱 | 서블릿·JSP 처리, 데이터베이스 연동, **트랜잭션 관리** |
| 주로 쓰는 콘텐츠 | HTML·CSS·JavaScript·이미지 | 서블릿·JSP·PHP·ASP.NET |
| 대표적인 예 | Apache HTTP Server, Nginx, IIS | Tomcat, JBoss, WebLogic, WebSphere |
| 연동 가능성 | 보통 WAS 와 함께 사용 | **자체적으로 웹 서버 기능도 포함** |
| 복잡성 | 단순 | 복잡 |

**「트랜잭션 관리」와 「자체적으로 웹 서버 기능도 포함」 두 칸이 뒤에서 문제가 된다** — 앞의 것은 실습이 손으로 하고 있는 일이고(아래 「왜 중요한가」), 뒤의 것은 이 노트의 대표 예 목록을 흔든다(아래 「경계와 오해」).

## 왜 중요한가

**직접 만들던 것을 그만 만들게 된다.** Day45 부터 Day62 까지 손으로 세운 것이 전부 이 서버의 기능 목록에 들어 있다 — 접속을 받는 루프, 접속마다 쓰레드 붙이기, 메시지 경계와 종료 신호, 커넥션 풀, 커밋 경계. **얻는 것은 그 코드가 없어지는 것이고, 잃는 것은 그 규칙을 내가 정하지 못하는 것**이다 → [[socket]] · [[network-protocol]] · [[thread]]

**특히 「트랜잭션 관리」가 이 표에서 가장 무거운 한 칸이다.** Day57 은 `setAutoCommit(false)` ~ `commit()` 을 손으로 감쌌고 Day62 는 그 경계를 쓰레드마다 나누려고 프록시까지 세웠다. 그 일이 서버의 기능이라는 것은 **경계를 여는 코드가 내 코드에서 사라진다**는 뜻이고, 그러면 어디서 열렸는지가 다시 보이지 않게 된다 — [[transaction]] 노트가 Day62 를 두고 「경계를 여는 줄이 세션을 얻는 일로 흡수되면 어디서 열렸는지가 코드에서 사라진다」고 적은 그 방향으로 한 걸음 더 간다 → [[thread-local]] · [[connection-pool-sizing-formula]]

**그리고 배포의 단위가 프로그램에서 「서버에 얹는 것」으로 바뀐다.** `main` 을 가진 내 프로그램이 아니라 서버가 실행 중이고 내 코드가 그 안에 들어가므로, 「실행한다」가 「배치한다」가 된다 → [[web-application-deployment]] · [[main-method]]

## 경계와 오해

- **WAS ≠ 서블릿 컨테이너 — 그리고 필기의 대표 예 목록이 그 둘을 한 줄에 섞어 놓았다** — Day63 은 「Tomcat, JBoss, WebLogic, WebSphere」를 나란히 든다. 그런데 톰캣이 구현하는 것은 **서블릿·JSP 규격까지**이고, WebLogic·WebSphere·JEUS 가 구현하는 것은 같은 노트의 표에 있는 **EJB 를 포함한 Java EE 전체**다. 즉 「WAS」라는 낱말이 **두 크기를 가리킨다** — 서블릿을 돌려 주는 것과 기업용 명세를 다 구현한 것. 같은 노트의 버전 표가 그 차이를 이미 보여 준다: 「Servlet / JSP / EL / EJB」 네 칸 중 톰캣 열이 채워지는 것은 앞의 셋뿐이다 → [[java-ee]] · [[servlet-container]]
- **같은 노트가 톰캣을 세 자리에 놓는다** — ① 비교 표의 「대표적인 예」에서는 **WAS**, ② 구조 절에서는 「`Tomcat` 같은 웹 서버가 이 역할을 수행한 후, 요청을 WAS로 넘겨 처리한다」로 **웹 서버**, ③ Tomcat 구조 절에서는 「Mini Web Server + Web Container + Java App」을 **한 프로세스에 다 가진 것**. ①과 ③은 함께 맞고 **②가 틀렸다** — 톰캣은 WAS 로 넘기는 쪽이 아니라 넘겨받는 쪽이다. 이 어긋남이 눈에 안 걸리는 이유는 톰캣이 **정말로 웹 서버 기능을 안에 갖고 있어서**(같은 표의 「자체적으로 웹 서버 기능도 포함」) 두 이름 다 부분적으로 맞기 때문이다. **「무엇을 포함하나」와 「어느 자리에 서나」를 가르지 않으면** 그림의 화살표가 방향을 잃는다 → [[tomcat]] · [[web-server]]
- **WAS 가 동적 콘텐츠 전용은 아니다** — 표의 「주로 사용하는 콘텐츠」 칸을 능력의 경계로 읽으면, 톰캣 혼자로는 이미지가 안 나온다는 결론이 된다. 실제로는 톰캣이 정적 파일도 내보내고, 실습의 `src/main/webapp` 이 정확히 그 자리다. 앞에 Nginx 를 두는 것은 **못 하기 때문이 아니라 그 일에 쓰레드를 쓰지 않으려는 것**이다 → [[static-and-dynamic-content]] · [[universal-scalability-law]]
- **웹 서버도 동적 요청을 「처리」한다 — 자기가 실행하지 않을 뿐이다** — 표의 「직접적인 응용 프로그램 처리 기능 없음」이 「동적 요청이 오면 아무것도 못 한다」로 읽히는데, 웹 서버가 하는 일은 **뒤로 넘기고 받아서 돌려주는 것**이고 그것도 처리다. PHP 를 Nginx 로 서비스하는 구성이 그 형태다 — 실행하는 프로세스가 따로 있고 웹 서버가 그것과 이야기한다. **「할 수 없다」가 아니라 「자기 안에서 하지 않는다」**다 → [[web-server]]
- **「비즈니스 로직을 처리한다」의 주어가 서버가 아니다** — 이 낱말 때문에 WAS 를 「업무 로직이 들어 있는 서버」로 읽게 되는데, 업무 로직은 **내가 배치한 클래스**에 있고 서버에는 그것을 부르는 규칙만 있다. 구별이 값을 갖는 자리는 버전 문제다 — 서버를 갈아도 내 로직은 그대로여야 하고, 그 「그대로」를 보증하는 것이 서버가 아니라 **명세**다 → [[java-ee]] · [[interface]]
- **웹 서버와 WAS 를 나누면 왕복이 하나 늘어난다** — 그림에서는 화살표가 하나 더 그려지는 것뿐이지만, 실제로는 **연결이 두 벌**이고(브라우저↔웹 서버, 웹 서버↔WAS) 한쪽이 끊기거나 느릴 때 다른 쪽이 그것을 어떻게 알릴지가 새로 정할 문제가 된다. 502·504 라는 응답이 존재하는 이유가 이 구조에 있다 — **뒤가 답하지 않았다는 것을 앞이 대신 말해 주는 것**이다 → [[network-protocol]] · [[client-server-model]]
- **「자체적으로 웹 서버 기능도 포함」이 이 표를 스스로 무너뜨린다** — 두 열을 갈라 놓고 오른쪽 열에 「왼쪽 것도 포함」이라 적으면 **배타적인 분류가 아니게 된다.** 정확한 그림은 두 상자가 아니라 **포함 관계 + 배치 선택**이다: WAS 는 웹 서버 기능을 갖고 있고, 그것을 쓸지 앞에 전용 웹 서버를 둘지가 규모에 따른 결정이다. 필기가 이 조건을 적지 않아 「반드시 둘을 함께 쓴다」로 읽힌다.

## 출처

- [[2024-08-26-Day63]] — 「웹 애플리케이션 서버(Web Application Server, WAS)」 절이 정의·기능 셋·웹 서버와의 비교 표·둘의 관계·5계층 구조를 적었다. 정의는 「동적인 콘텐츠를 생성하는 서버로 … 복잡한 비즈니스 로직을 처리하고, 데이터베이스와 통신하며 … 동적 페이지(예: JSP, PHP, ASP.NET) 및 애플리케이션 로직을 수행한다」이고 기능은 동적 콘텐츠 생성·비즈니스 로직 처리·데이터베이스 연동이며, 표에 「서블릿, JSP 처리, 데이터베이스 연동, 트랜잭션 관리」·「자체적으로 웹 서버 기능도 포함」·대표 예 「Tomcat, JBoss, WebLogic, WebSphere」가 들어 있다. 구조 절은 브라우저 → 웹 서버 → WAS → Java Application → execute → Return 흐름을 적어 **비즈니스 로직의 주인을 「Java Application」으로 한 칸 갈라 놓았다.** 다만 어긋남이 둘 있다 — ① 같은 노트가 톰캣을 대표 WAS 로 적고도 「`Tomcat` 같은 웹 서버가 이 역할을 수행한 후, 요청을 WAS로 넘겨 처리한다」로 다시 웹 서버 자리에 놓아 화살표의 방향이 뒤집히고, ② 대표 예 목록이 서블릿 컨테이너(톰캣)와 Java EE 전체를 구현한 서버(WebLogic·WebSphere)를 한 줄에 섞어 「WAS」가 두 크기를 가리키게 된다 — 그 차이는 같은 노트의 EJB 열이 이미 보여 준다. 표의 「트랜잭션 관리」 칸이 Day57~62 에서 손으로 해 온 일이라는 연결, 웹 서버와 WAS 를 나눌 때 생기는 두 번째 연결의 비용, 그리고 「자체적으로 웹 서버 기능도 포함」이 이 표를 배타적 분류가 아니게 만든다는 점은 다루지 않았다
