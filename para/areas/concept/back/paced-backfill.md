# 페이싱 백필

주기 동기화는 「지금」 만 따라 읽는다. 지난 이력은 **한 번 도는 별도 작업(백필)** 으로 채운다. 외부 원천의 속도 제한과 운영 서비스를 지키려면 세 가지가 필요하다. 호출 간격 고정(페이싱), 다시 돌려도 같은 결과(멱등), 끊기면 이어 하기.

## 정의

1. **배포와 떼어 둔다** — migration 안에서 외부를 부르면 외부가 느릴 때 배포가 멈춘다(forward-only 라 되돌리기도 어렵다). 수동 명령으로 두고, 배포가 끝난 뒤 돌린다.
2. **호출 간격을 전송 층에서 강제한다** — HTTP 클라이언트 하나에 페이서를 달아, 재시도 · 토큰 · 세션 해제까지 **모든 요청**이 간격을 지키게 한다. 함수마다 sleep 을 두면 빠지는 요청이 생긴다.
3. **운영 쓰기 함수를 그대로 쓴다** — 새 쓰기 경로를 만들지 않는다. 그래서 운영 동기화와 결과가 같고, 재실행하면 쓴 행이 0 이다 → [[idempotency]] · [[external-id-mapping-table]].
4. **운영 창과 겹치지 않게 한다** — 「오늘」 은 주기 동기화 몫이다. 백필은 어제까지만 하고, 오늘 이후 값은 거부한다.
5. **같은 외부 계정을 운영과 나눠 쓰면 표시로 가른다** — 기기 수 제한이 있는 원천에서는 백필 세션에 별도 표시를 붙인다. 자동 해제가 운영 세션을 끊지 않게 하기 위해서다. 끝나면 자기 세션만 해제한다.
6. **드라이런 → 대조 → 실행** — 드라이런은 원천을 읽기만 하고 DB 에 쓰지 않는다. 받은 건수를 원천 쪽 건수와 대조한 뒤 실행한다.

## 사용 예시

- DAY `python -m runtime.backfill --hospital … --from 2026-08 [--dry-run] [--resume]`.
  - 순서: 일정(달 단위) → 구매 묶음 → 구매 고객의 시술권 → 고객 목록 → 카드.
  - KOS 1초 1회 · 내부 API 만 · 표시 `backfill` · 진행 위치 Redis.
- 실측(DEMO · dev 같음): 1회 약 750호출 · 750초. 카드 단계(고객 목록 전부)가 590초로 대부분이었다. 처음 추정(150호출)의 5배였다 — **고객 수에 비례하는 단계가 시간을 정한다.**
- dev 결과: 방문 1,319 · 구매 408 · 시술권 번들 429 · 티켓 536 · 카드 15. 백필 전에는 출처 구매가 없어 건너뛰던 지난 시술권 21개가 풀렸다.

## 왜 중요한가

- 주기 동기화만으로는 「오늘 온 고객이 지난달에 산 시술권」 처럼 출처가 과거인 데이터가 영원히 비어 있다.
- 속도 제한을 어기면 같은 외부 원천에 기대는 운영 동기화까지 느려진다.

## 경계와 오해

- **사라짐 규칙을 같이 쓰면 잘린 응답이 지우기로 번진다** — 「창 안에서 응답에 없으면 소프트 딜리트」 를 백필에도 쓰므로, 한 달 응답이 잘려 오면 그 달 행이 지워질 수 있다. 실 병원은 드라이런 대조가 필수다.
- **동시에 두 개 돌리지 않는다** — 세션 해제와 진행 위치가 겹친다.
- **방문 없는 대상은 따로 넣어야 한다** — 고객을 방문 응답에서만 만들면, 방문 이력 없는 고객의 카드는 받을 자리가 없다(DEMO 13명). 고객 목록으로 넣을지는 별도 결정이다.
