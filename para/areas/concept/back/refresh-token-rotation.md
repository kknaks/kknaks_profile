# 리프레시 토큰 회전 (Refresh Token Rotation)

**리프레시 토큰을 한 번 쓰면 새 리프레시 토큰이 나오고, 이전 것은 그 순간 무효가 되는 방식.** 탈취된 토큰을 한 번만 쓸 수 있게 만드는 보안 장치인데, 부작용으로 **같은 토큰을 두 곳이 나눠 쓸 수 없다.**

## 정의

액세스 토큰은 짧고, 만료되면 리프레시 토큰으로 새로 받는다([[jwt]]). 회전식이면 그 갱신 응답에 **새 리프레시 토큰**이 함께 오고 서버는 옛 것을 폐기한다. 그래서 인증 상태는 「파일 하나」가 아니라 **가장 최근에 갱신한 쪽만 살아 있는 사슬**이다.

## 왜 중요한가

**인증 파일을 복사해 두 프로세스에 주면, 먼저 갱신한 쪽이 다른 쪽을 죽인다.** Strong Hajin 운영 배포에서 AI(codex) 인증을 어디서 가져올지 정할 때 이게 갈림길이었다.

- 호스트에 남은 7월 auth.json → 이미 다른 쪽이 회전시켜 **401**. 복사본은 시간이 지나면 저절로 죽는다
- mediness 운영 파드의 최신본 → 지금은 살아 있지만, 복사하면 두 앱 중 먼저 갱신한 쪽이 **회사 운영 AX 를 끊는다**
- 답: **전용 인증 홈**(`CODEX_HOME=<전용 폴더> codex login --device-auth`)으로 새 사슬을 하나 더 만든다. 그 파일도 로컬에서 쓰면 같은 문제가 난다 — 만든 곳에서는 쓰지 않는다

## 경계와 오해

- **「복사하면 백업」이 아니다** — 회전식 토큰의 복사본은 원본이 한 번 갱신되는 순간 쓰레기다. 백업이 필요하면 재로그인 절차를 문서화한다
- **401 이 버전 문제처럼 보인다** — CLI 버전 차이(0.146 vs 0.158)를 먼저 의심했지만 원인은 만료된 사슬이었다. 인증 실패는 토큰 사슬부터 본다
- **API 키와 다르다** — 정적 키는 여러 곳에서 써도 서로를 무효화하지 않는다. 회전은 사용자 로그인(OAuth/디바이스 인증) 계열의 성질이다
