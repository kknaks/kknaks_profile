# 패키지 (Package)

클래스를 분류하는 문법. 프로그램에서 하는 역할에 따라 클래스를 묶고, 그 묶음이 **폴더 구조와 그대로 대응**한다.

## 정의

패키지명의 `.` 이 폴더 구분이다.

| | 값 |
|---|---|
| 패키지명 | `study.lang` |
| 폴더 경로 | `study/lang/` |
| 클래스명 | `Test` |
| 실행할 때 쓰는 이름 | `study.lang.Test` |

**클래스의 진짜 이름은 패키지를 포함한 이름이다.** 그래서 실행할 때 `Test` 가 아니라 `study.lang.Test` 라고 써야 하고, [[classpath]] 는 그 이름을 폴더 경로로 바꿔 파일을 찾는다.

## 사용 예시

패키지에 속한 클래스를 만들고 컴파일해 실행하는 흐름이다.

```bash
$ mkdir -p study2/lang2                                    # 패키지 폴더
$ javac -d app/build/classes/java/main \
        app/src/main/java/study2/lang2/Test.java           # 컴파일
$ java -cp app/build/classes/java/main study2.lang2.Test   # 실행
```

컴파일할 때 `-d` 는 **최상위 폴더까지만** 주면 된다 — 그 아래 패키지 폴더는 `javac` 가 알아서 만든다. 반대로 실행할 때는 `-cp` 에 최상위를 주고 클래스는 패키지를 붙인 전체 이름으로 지정한다.

### 역할이 갈리면 하위 패키지로 내린다

클래스가 늘면 한 패키지 안에서도 역할이 갈린다. 이 필기는 데이터 타입 노릇만 하는 `Score` 를 `vo` 하위 패키지로 내려 실행 클래스와 갈랐다 → [[class]]

```text
study/oop/clazz/        →     study/oop/clazz/
  Test02.java                   Test02.java
  Score.java                    vo/
                                  Score.java
```

옮긴 것만으로는 `Test02` 가 컴파일되지 않는다. 클래스의 진짜 이름이 `study.oop.clazz.vo.Score` 로 바뀌었으므로 `import` 가 필요하고, 지정자가 (default) 였던 `Score` 는 다른 패키지에서 보이지 않으므로 `public` 을 붙여야 한다.

```java
package study.oop.clazz;

import study.oop.clazz.vo.Score;
```

**패키지를 가르는 순간 접근 지정자가 일을 시작한다** → [[access-modifier]]

### 클래스가 늘면 역할이 층으로 갈린다

다음 회차의 실습 프로젝트는 클래스를 세 갈래로 나눴다. 「클래스의 용도에 따라 패키지를 분리한다」가 그 기준이다.

```text
myapp
|- util    : 범용적으로 사용되는 클래스        (Prompt)
|- vo      : 사용자 정의 데이터 분류           (User, Project)
|- command : 세부 명령어를 수행하는 클래스     (UserCommand, ProjectCommand)
|- App.java : main() 메서드를 수행하는 클래스
```

셋을 가르는 질문이 각각 다르다.

| 패키지 | 그 안의 클래스가 답하는 것 | 판별 신호 |
|---|---|---|
| `util` | 이 프로그램의 도메인을 몰라도 되는가 | 다른 프로젝트로 그대로 가져갈 수 있다 |
| `vo` | 데이터 한 덩어리를 이름으로 다루는가 | 필드와 getter/setter 가 대부분이다 → [[class]] |
| `command` | 사용자의 명령 하나를 수행하는가 | 입력·출력과 흐름이 들어 있다 → [[crud]] |

`Prompt` 가 `util` 로 간 이유는 「여러 클래스에서 쓰이니까」가 아니라 **회원도 프로젝트도 모르기 때문**이다. 실제로 `Prompt` 는 `User`·`Project` 를 `import` 하지 않는다 — 그래서 혼자 떼어 낼 수 있다.

반대 방향도 드러난다. `command` 는 `util` 과 `vo` 를 둘 다 `import` 하고, `vo` 는 아무것도 `import` 하지 않는다. **`import` 문의 방향이 층의 순서**다.

```java
package bitcamp.myapp2.command;

import bitcamp.myapp2.util.Prompt;
import bitcamp.myapp2.vo.User;
```

## 왜 중요한가

**이름 충돌이 사라진다.** 클래스 이름이 겹쳐도 패키지가 다르면 다른 클래스다. 남의 라이브러리를 가져다 쓸 때 내 `Test` 와 그쪽 `Test` 가 부딪히지 않는 이유가 이것이고, 그래서 패키지 없이는 라이브러리 생태계가 성립하지 않는다.

그리고 **폴더가 곧 분류**라는 점에서 코드를 읽는 순서를 정해 준다. 파일이 수백 개가 되어도 역할별로 갈라져 있으면 어디를 볼지 정할 수 있다.

## 경계와 오해

- **패키지 ≠ 폴더** — 대응하지만 같은 것은 아니다. 패키지는 **이름의 일부**이고 폴더는 그 이름을 파일 시스템에 담은 결과다. 폴더만 옮기고 소스의 `package` 선언을 안 고치면 컴파일이 되지 않는다.
- **폴더 구조를 손으로 만들지 않아도 되는 쪽이 있다** — 컴파일 산출물 폴더는 `javac` 가 만들지만, 소스 폴더는 내가 만들어야 한다. `-d` 가 자동으로 만들어 준다는 것은 결과물 쪽 이야기다.
- **실행 인자에 슬래시를 쓰지 않는다** — `java study2/lang2/Test` 가 아니라 `study2.lang2.Test` 다. 파일을 지목하는 게 아니라 클래스 이름을 부르는 것이기 때문이다.
- **하위 패키지는 상위 패키지의 「안」이 아니다** — `study.oop.clazz.vo` 는 폴더로는 `study.oop.clazz` 아래지만 접근 관점에서는 **완전히 다른 패키지**다. 포함 관계처럼 보여서 (default) 멤버가 그대로 보일 것 같지만 안 보이고, 그래서 `Score` 에 `public` 을 붙여야 했다 → [[access-modifier]]
- **패키지를 나누는 것은 공짜가 아니다** — 한 패키지 안에서는 지정자를 안 써도 서로 다 보인다. 나누는 순간 (default) 로 붙어 있던 연결이 끊기므로 **무엇을 열지 정해야** 한다. 분류만 하는 작업이 아니라 공개 범위를 선언하는 작업이다 → [[encapsulation]]
- **`util`·`vo`·`command` 는 상하 관계가 아니라 형제다** — 폴더가 나란히 있고 접근 관점에서도 서로 남이다. 「`command` 안에 `vo` 가 있다」는 구조가 아니라 **셋 다 `myapp2` 아래의 다른 패키지**이므로, 서로 쓰려면 전부 `import` 와 `public` 이 필요하다.
- **패키지 이름은 그 안의 클래스가 따를 규약을 선언한다** — `vo` 라 이름 붙이면 그 안의 클래스는 데이터 중심이라는 약속이 생긴다. 필기가 `vo : domain, dto라고도` 로 세 이름을 붙여 둔 것은 편의지만, 세 이름의 규약이 서로 다르므로 나중에 어느 쪽으로 읽어야 하는지가 흐려진다 → [[class]]
- **패키지가 갈라지는 것과 역할이 갈라지는 것은 같이 일어나지 않는다** — Day19 는 `UserCommand` 를 데이터 보관(`UserList`)과 UI 처리로 쪼갰는데 **둘 다 `command` 패키지에 남았다.** 성격이 정반대인 두 클래스가 같은 이름표 아래 있으니 폴더를 보고는 갈라진 것을 알 수 없고, `command` 라는 이름이 「명령을 수행하는 클래스」라는 약속을 스스로 어긴다. 설계 정리가 곧 패키지 정리로 이어지지 않는 자리다 → [[cohesion]] · [[grasp]]
- **`vo` 가 클래스 멤버를 갖게 되어도 `vo` 다** — Day19 의 `User` 는 `private static int seqNo` 와 `static` 발급 메서드를 갖는다. 「필드와 getter/setter 가 대부분」이라는 판별 신호에서 벗어나기 시작하지만, **다루는 것이 자기 데이터라면** 여전히 `vo` 다. 신호를 규칙으로 굳히면 이 클래스를 어디 둘지 답이 안 나온다 → [[static-member]] · [[surrogate-key]]
- **같은 노트 안에서 패키지 이름이 갈릴 수 있다** — Day19 의 `UserList` 는 `bitcamp.myapp2.command` 이고 `UserCommand` 는 `bitcamp.myapp.command` 다. 프로젝트를 복사해 이어 만들며 `myapp2` 와 `myapp` 이 섞인 것으로, **이 상태로는 서로를 못 찾는다.** 패키지 이름이 곧 클래스 이름의 일부라는 것이 이렇게 드러난다 → [[classpath]]
- **여러 곳에서 쓰인다는 것이 `util` 의 기준은 아니다** — 기준은 **도메인을 모르는가**다. 여러 곳에서 쓰이지만 `User` 를 아는 클래스는 `util` 이 아니라 도메인 쪽에 속한다. 이 구분을 놓치면 `util` 이 무엇이든 담는 서랍이 된다 → [[cohesion]]
