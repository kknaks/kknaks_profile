# 웹훅(Webhook)

웹훅은 어떤 시스템에서 사건이 발생했을 때 미리 등록한 HTTP URL을 호출해 다른 시스템에 알리는 연동 방식이다. 수신 측이 새 상태를 계속 조회하는 대신, 사건을 아는 쪽이 발생 시점에 요청을 보낸다.

## 정의

웹훅은 보통 다음 순서로 작동한다.

1. 수신 시스템이 요청을 받을 HTTPS 엔드포인트를 준비한다.
2. 송신 시스템에 그 URL과 관심 이벤트를 등록한다.
3. 이벤트가 발생하면 송신 시스템이 이벤트 정보를 담은 HTTP 요청을 보낸다.
4. 수신 시스템은 요청의 출처와 형식을 검증하고 빠르게 성공 여부를 응답한다.
5. 오래 걸리는 실제 처리는 작업 큐로 넘기고, 필요하면 외부 API 호출이나 메시지 게시를 수행한다.

Slack Incoming Webhook은 방향이 조금 다르게 보이지만 같은 핵심을 가진다. Slack이 발급한 전용 URL을 외부 서비스가 호출하면 Slack이 지정 채널에 메시지를 게시한다. 이 방식은 알림을 보내는 데 최적화되어 있으며 Slack 사용자의 메시지나 다른 이벤트를 받는 기능은 제공하지 않는다.

## 사용 예시

다음 요청은 환경 변수에 저장한 Slack Incoming Webhook URL로 배포 완료 알림을 보낸다.

```bash
curl -X POST \
  -H 'Content-Type: application/json' \
  --data '{"text":"운영 배포가 완료되었습니다."}' \
  "$SLACK_WEBHOOK_URL"
```

CI 서버나 사내 스케줄러가 작업 완료 시 이 요청을 실행하면 별도의 Slack SDK 서버 없이 채널에 결과를 알릴 수 있다. Webhook URL은 메시지 게시 권한을 가진 비밀 값이므로 코드와 저장소에 넣지 않는다.

## 왜 중요한가

웹훅은 주기적으로 새 데이터가 있는지 묻는 [[polling]]과 달리 사건이 발생한 때에만 요청한다. 불필요한 조회와 지연을 줄이고, 서로 다른 서비스가 HTTP라는 공통 경계만으로 느슨하게 연결되게 한다.

단순 알림 요구에는 완전한 SDK나 상시 실행 서버보다 구현과 운영 비용이 작다. 특히 CI 완료, 결제 결과, 저장소 변경이나 [[slack-bot]] 채널 알림처럼 사건을 다른 시스템에 전달하는 기능을 빠르게 붙일 수 있다.

## 경계와 오해

- **웹훅 ≠ 일반 API 조회** — 일반 API에서는 필요한 쪽이 요청 시점을 정하지만, 웹훅에서는 사건이 발생한 쪽이 등록된 URL을 호출한다.
- **Incoming Webhook ≠ 양방향 봇** — Slack Incoming Webhook은 메시지 전송에는 적합하지만 사용자 이벤트 수신이나 임의의 Slack 작업 수행을 대신하지 않는다.
- **성공 응답 ≠ 업무 처리 완료** — 수신 서버는 요청 접수만 확인하고 실제 작업을 비동기로 수행할 수 있다. 응답 의미를 계약으로 명확히 해야 한다.
- **한 번 전송 ≠ 한 번 처리** — 송신 측은 응답 유실이나 장애 때문에 같은 이벤트를 재전송할 수 있으므로 수신 측은 중복을 전제로 설계한다.
- **비밀 URL ≠ 충분한 인증** — URL 노출 가능성을 고려해 HTTPS, 서명 검증, 타임스탬프와 재전송 공격 방지, 비밀 교체 절차를 갖춘다.

## 함께 보는 개념

- [[slack-bot]] — Incoming Webhook을 단방향 알림 수단으로 사용하고, 양방향 기능에는 Events API와 Web API를 결합한다.
- [[polling]] — 수신 측이 주기적으로 상태를 조회하는 대안이며 구현 단순성과 요청 비용·지연 사이의 선택 기준이 다르다.
- [[idempotency]] — 동일한 웹훅이 다시 전달돼도 업무 결과가 중복되지 않게 하는 핵심 성질이다.
- [[exponential-backoff]] — 일시적 실패 뒤 웹훅을 재전송할 때 서버 과부하를 피하는 재시도 방식이다.
