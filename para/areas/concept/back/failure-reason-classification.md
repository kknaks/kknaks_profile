# 실패 사유는 판정 근거만큼만 말한다

파이프라인이 「결과 없음」 을 여러 사유(`needs_ocr` · `empty_content` …)로 가를 때, **사유는 그것을 가른 판정이
실제로 본 것만큼만 정확하다.** 판정이 얕으면 엉뚱한 사유가 붙고, 문구가 판정보다 넓게 말하면 맞는 판정도 틀린
안내가 되고, 저장 단계에서 상태를 뭉개면 판정이 화면까지 못 간다. 사유는 **판정 → 저장 → 문구 → 표시** 네 자리를
한 줄로 맞춰야 한다.

## 정의

1. **판정이 사유를 가른다** — 문서 추출에서 텍스트가 0자면 이미지 유무로 갈린다. 이미지 있음 → `needs_ocr`(스캔 · OCR 필요),
   없음 → `empty`(정말 빈 것). 사유의 정확도는 이 이미지 판정의 범위가 정한다
2. **판정이 얕으면 사유가 바뀐다** — 최상위 리소스만 보는 판정은 Form 으로 감싼 이미지 · 인라인 이미지를 못 봐서 스캔
   문서를 「빈 파일」 로 보낸다. 판정 자체가 없는 형식(Office)은 그림만 있는 덱도 무조건 「빈 파일」 이다
3. **예외를 부정 판정으로 삼키면 그것도 사유가 된다** — `except Exception: return False` 는 「확인 못 함」 을
   「이미지 없음」 으로 바꾸고, 그대로 `empty` 사유에 합쳐진다. 확인 실패는 별도 표지(`image_probe_failed` 등)로 남긴다
4. **저장 단계가 상태를 뭉개지 않는다** — 파서가 `needs_ocr` 를 냈는데 저장이 허용 집합(`failed` · `unsupported` · `too_large`)
   밖이라며 `failed` 로 바꾸면, 화면의 전용 배지는 실데이터로 영영 안 뜬다. 상태 값 범위를 판정 · 저장 · 화면이 같은 목록으로 쓴다
5. **문구는 판정이 본 범위 안에서만 말한다** — `empty` 는 이미 「이미지도 없음」 인데 문구가 「스캔 이미지 PDF 또는 빈 파일」 이라
   하면 판정과 문구가 엇갈리고, PDF 가 아닌 형식에도 PDF 를 전제한 문장이 뜬다. 판정이 못 가르는 갈래(윤곽선 글자)는
   문구에서 「그럴 수 있다」 로 열어 두고 다음 행동(원본을 올리기 · 텍스트가 살아 있는 PDF 로 다시 저장)을 준다
6. **표시는 심각도를 맞춘다** — 파일은 멀쩡하고 내용 추출만 안 된 상태를 빨간 위험 배지 + 긴 사유 문장으로 띄우면
   사용자는 「업로드 실패」 로 읽는다. 짧은 상태(「내용을 읽지 못함」) + 사유는 hover 로

## 사용 예시

```python
# 판정 — 확인 실패를 「없음」 으로 삼키지 않는다
def page_has_images(page) -> bool | None:
    try:
        return count_images(page.resources, recurse_forms=True) + count_inline(page) > 0
    except Exception:
        return None                      # 모름 → missing_units 에 image_probe_failed

# 저장 — 파서 상태를 그대로 받는 목록과 화면이 고르는 목록이 같아야 한다
TERMINAL = {"failed", "unsupported", "too_large", "needs_ocr"}
status = outcome.status if outcome.status in TERMINAL else "failed"
```

실례 — 결과 자료 PDF 가 「내용을 읽지 못함 · 본문에 텍스트가 없습니다 (스캔 이미지 PDF 또는 빈 파일)」 를 받았다.
실측해 보니 판정은 계약대로(텍스트도 이미지도 없는 윤곽선 PDF → `empty_content`)였고 틀린 것은 **문구**였다 — 사람 눈엔
멀쩡한 문서에 「스캔 또는 빈 파일」 이라고 말했다. 조사 중 같은 경로에서 두 어긋남이 더 드러났다 — 합성 PDF 로 Form 감싼
이미지 · 인라인 이미지가 `empty_content` 로 떨어지는 것(판정이 얕음)과, `needs_ocr` 가 저장에서 `failed` 로 바뀌어 FE 의
「스캔 문서」 배지가 실데이터로 안 뜨는 것(FE 테스트는 `status: "needs_ocr"` 를 직접 주입해 못 잡음).

## 왜 중요한가

- **사유가 틀리면 사람이 엉뚱한 처방을 한다** — 「빈 파일」 이라는 말에 사용자는 다시 올리고, 개발자는 업로드를 의심한다.
  사유는 다음 행동을 고르는 근거라 정확도가 곧 기능이다
- **결정적 실패는 재시도로 안 풀린다** — 같은 입력은 같은 사유를 낸다. 재추출 수단이 없으면 틀린 사유가 영구히 남으므로
  판정을 고칠 때는 이미 저장된 행을 다시 돌릴 길(파서 버전 올림 · 재추출 명령)을 같이 둔다
- **화면 전용 상태가 실데이터에 안 오면 아무도 모른다** — 화면 테스트가 상태를 직접 주입하면 저장 단계의 뭉개짐을 통과한다.
  저장값으로 시험해야 잡힌다

## 경계와 오해

- **판정이 맞다 ≠ 안내가 맞다** — 계약대로 판정해도 문구가 판정보다 넓게 말하면 사용자에겐 틀린 답이다. 이번 처방은 판정이 아니라
  문구였다
- **사유를 늘리는 것 ≠ 정확해지는 것** — 사유 코드를 더해도(`outlined_text` 등) 판정이 그 갈래를 실제로 볼 수 있어야 의미가 있다.
  못 보는 갈래는 코드가 아니라 문구에서 연다
- **[[no-silent-fallback]] 과의 관계** — 저쪽은 실패를 더 나쁜 입력으로 이어 가지 않고 `failed` 로 드러내는 것, 여기는 드러낸 `failed`
  안에서 사유가 맞는가다. 예외를 부정 판정으로 삼키는 것은 두 노트가 겹치는 자리
- **보수적 판정의 대가** — 「텍스트 0 + 콘텐츠 있음 → `needs_ocr`」 처럼 넓게 잡으면 윤곽선도 「읽을 수 없음」 으로 잡히지만 오탐이 생긴다.
  어느 쪽 오판을 감수할지는 결정 문서의 몫
