# 버퍼 스트림 (Buffered Stream)

**한 번 나갈 때 덩어리로 나가게 만드는 껍데기.** 부르는 쪽은 여전히 1바이트씩 읽고 쓰는데, 안쪽 통로에는 수천 바이트가 한 번에 오간다. Day41 의 마지막 줄이 그 결과를 정확히 적었다 — 「그래서 1바이트 씩 읽더라도 그렇게 속도가 떨어지지 않는 것이다」.

## 정의

Day41 이 비용을 두 조각으로 나눈 것이 이 개념의 출발점이다 — 「데이터를 입출력에 걸리는 시간은 데이터를 찾는 시간과 데이터를 입력하는 시간이다」.

| 조각 | 무엇에 비례하나 | 버퍼가 하는 일 |
|---|---|---|
| **한 번 오갈 때 드는 고정 비용** | **호출 횟수** | 이것을 줄인다 |
| 실제로 옮기는 비용 | 바이트 수 | 줄일 수 없다 |

옮겨야 하는 바이트 수는 정해져 있으므로 **줄일 수 있는 것은 횟수뿐**이고, 버퍼 크기 `N` 을 키우면 호출 횟수가 `전체/N` 로 준다. 필기가 「한번 조회할때 많은 데이터를 가져오는것이 시간절약 측면에서 유리하다」로 적은 것이 이것이다.

동작은 필기의 주석이 그대로 설명한다.

```java
    // => BufferedFileInputStream의 read() 메서드는
    //    FileInputStream에서 상속 받은 메서드를 이용하여
    //    바이트 배열로 데이터를 왕창 가져온 다음
    //    그 배열에서 1바이트를 리턴한다.
    // => 그 이후에는 바이트 배열의 데이터가 떨어질 때까지
    ///   계속 바이트 배열에서 값을 꺼내 리턴해 준다.
    // => 바이트 배열의 값이 떨어지면
    //    다시 바이트 배열 단위로 데이터를 읽어 온다.
```

**읽는 쪽과 쓰는 쪽이 대칭이다.** 읽기는 미리 당겨 놓고 나눠 주고(read-ahead), 쓰기는 모아 두었다가 한 번에 내보낸다(write-behind). 쓰기 쪽에는 그래서 「아직 안 나간 것」이 남고 `flush()`·`close()` 가 그것을 밀어낸다 → [[try-with-resources]]

## 사용 예시

Day41 의 예제가 세는 것은 **호출 횟수**다.

```java
    BufferedFileInputStream in = new BufferedFileInputStream("temp/jls.pdf");
    int b;
    int callCount = 0;
    while ((b = in.read()) != -1)
      callCount++; // 파일을 끝까지 읽는다.
```

`callCount` 는 파일의 바이트 수가 되고 — 즉 `read()` 는 수백만 번 불린다 — 그런데 **파일 시스템에 나가는 요청은 `바이트 수 / 8192` 번**이다. 실제 클래스 이름은 `BufferedInputStream` 이고 통로를 감싸서 만든다.

```java
    try (InputStream in = new BufferedInputStream(new FileInputStream("temp/jls.pdf"))) {
```

**앞 세 회차가 비워 둔 자리가 이 회차에서 채워진다.** Day38 은 `FileInputStream` 을 맨몸으로 써서 회원 한 명에 `read()` 를 십수 번 불렀고, Day39 는 `DataInputStream` 을 씌웠지만 그것은 타입을 해석하는 층이라 횟수를 줄이지 않았고, Day40 이 처음 `BufferedReader` 를 끼웠지만 그것은 「줄 단위로 읽으려고」였다. **성능을 위해 겹을 하나 더 끼운다는 것이 목적으로 설명되는 것은 여기가 처음이다** → [[io-stream]] · [[data-io-stream]] · [[character-stream]]

## 왜 중요한가

**같은 코드가 수십~수백 배 빨라진다 — 그리고 고친 것은 한 줄이다.** `new FileInputStream(f)` 를 `new BufferedInputStream(new FileInputStream(f))` 로 바꾸는 것뿐이고, 읽는 코드는 손대지 않는다. 겹을 씌우는 것이 호출부에 보이지 않는 변경이라 이것이 가능하다 → [[decorator-pattern]]

**「무엇이 느린가」를 재는 축이 하나 늘어난다.** Day38 을 보고 「바이너리라서 빠르다」로 읽으면 형식만 보게 되는데, 실제로 지배하는 것은 **통로에 몇 번 접근하나**다. 바이너리 형식으로 십만 번 나가는 것보다 텍스트 형식으로 열 번 나가는 것이 빠르다. **형식의 축과 횟수의 축을 가르는 것**이 이 개념이 주는 것이다 → [[binary-io]]

**그리고 이 계산이 입출력에만 있는 것이 아니다.** DB 에 한 건씩 `INSERT` 하는 것과 배치로 넣는 것, HTTP 요청을 건마다 보내는 것과 묶어 보내는 것이 전부 같은 모양이다 — **고정 비용이 있는 호출을 줄이려고 모으는 것**이고, 그때마다 「아직 안 나간 것이 있다」는 같은 대가가 따라온다.

## 경계와 오해

- **버퍼링 ≠ 캐싱** — 둘 다 「데이터를 따로 들고 있는다」인데 목적이 반대다. [[caching]] 은 **같은 데이터를 다시 쓰려고** 들고 있고(그래서 무효화·동기화 문제가 따라온다), 버퍼는 **한 번에 옮기려고** 잠깐 모아 두는 것이라 나가면 버린다. 그래서 버퍼에는 stale data 문제가 없고, 대신 캐시에는 없는 문제(안 내보내고 끝나면 유실)가 있다.
- **「데이터를 찾는 시간은 주기억장치와 램에 접근하는 시간」은 뒤집혀 있다** — 주기억장치가 곧 램이고, 램 접근은 나노초 단위라 입출력 시간의 대부분을 차지하는 쪽이 아니다. 오래 걸리는 것은 **보조기억장치**(디스크)에 가는 일과, 그보다 먼저 **커널로 넘어가는 시스템 호출** 자체다. 필기의 결론(「많이 가져오는 것이 유리하다」)은 맞는데 **원인을 램에 둔 것이라 SSD·네트워크·소켓에도 같은 결론이 나는 이유를 설명하지 못한다.** 정확히는 「호출 하나에 고정 비용이 있고 그 비용이 옮기는 양과 거의 무관하다」이고, 회전 디스크의 탐색 시간은 그 고정 비용의 한 항목일 뿐이다. 요즘 환경에서는 OS 페이지 캐시가 있어 `read()` 한 번이 디스크 한 번이 아니지만 **시스템 호출 한 번인 것은 그대로**라 버퍼의 값은 유지된다.
- **「logN의 상관관계」가 아니라 `1/N` 이다** — 버퍼를 `N` 바이트로 잡으면 호출 횟수가 `전체/N` 이므로 **고정 비용의 총합이 `N` 에 반비례해 준다.** 8 → 8192 로 키우면 1024배 줄고, 8192 → 16384 로 키우면 절반만 더 준다. 「점점 덜 이득이 된다」는 관찰은 맞지만 로그가 아니라 반비례라서 **초반의 이득이 필기가 생각한 것보다 훨씬 크고 후반은 훨씬 빨리 평평해진다.** 그래서 「기본값을 쓰면 거의 다 얻는다」가 결론이 된다.
- **버퍼 크기는 만들 때 정해지고 자라지 않는다** — 필기의 「8kb를 한번에 가져오고, 필요하면 더 가져온다」는 절반만 맞다. **다시 채우는 것**은 맞고 **더 커지는 것**은 아니다. `BufferedInputStream` 의 배열은 생성자에서 정해진 크기(기본 8192)로 고정이고, 늘리려면 `new BufferedInputStream(in, 65536)` 처럼 만들 때 줘야 한다. 안에서 자라는 것은 [[byte-array-stream]] 쪽이고 목적이 다르다 → [[dynamic-array]]
- **8Kb 가 아니라 8KB 다** — `Kb`(킬로비트)로 적으면 1024바이트가 되어 값이 8배 어긋난다. `BufferedInputStream` 의 기본값은 **8192바이트**이고, 필기가 관찰한 최적점의 값 자체는 맞다.
- **「서버에서 1MB 조회는 과부하」의 실체는 속도가 아니라 곱셈이다** — 1MB 를 한 번 읽는 것 자체는 서버에 부담이 아니다. 문제가 되는 것은 **버퍼가 연결마다 하나씩 잡히는** 경우다 — 1MB 버퍼 × 동시 연결 1만 개면 10GB 다. **버퍼 크기를 고르는 기준이 「얼마나 빠른가」가 아니라 「몇 개가 동시에 살아 있나」**라는 것이고, 그래서 서버는 큰 버퍼를 피하는 것이 맞지만 이유가 필기에 적힌 것과 다르다 → [[connection-pool-sizing-formula]]
- **버퍼를 씌워도 큰 배열로 읽으면 버퍼를 지나친다** — `BufferedInputStream.read(byte[] b, off, len)` 은 `len` 이 버퍼 크기보다 크고 버퍼가 비어 있으면 **호출자의 배열로 직접 읽는다.** 한 번 더 복사하는 것이 낭비이기 때문이다. 그래서 **이미 큰 덩어리로 읽는 코드에는 버퍼를 씌워도 얻는 것이 거의 없고**, 버퍼가 값을 내는 것은 `read()` 나 작은 배열로 잘게 읽을 때다. 「감싸면 무조건 빨라진다」가 아니다.
- **`BufferedInputStream` 은 `FileInputStream` 을 상속하지 않는다 — Day41 필기의 오류다** — 주석이 「FileInputStream에서 상속 받은 메서드를 이용하여」로 적었지만 이것은 `FilterInputStream` 의 자식이고, 감싼 통로를 **필드로 들고 있다가 그 객체의 `read` 를 부른다.** 상속이면 무엇을 감쌌는지가 컴파일 시점에 정해져 파일 전용이 되어야 하는데, 실제로는 소켓·`System.in`·`ByteArrayInputStream` 에도 똑같이 씌워진다 — **그 유연함이 상속이 아니라 필드에서 나오는 것**이다. 같은 노트가 §4 에서 「Data I/O stream은 File I/O stream을 상속받아 사용한다」로 같은 착오를 반복한다 → [[decorator-pattern]] · [[data-io-stream]]
- **클래스 이름이 `BufferedFileInputStream` 이 아니다** — 예제 코드의 이름은 존재하지 않고 `BufferedInputStream` 이다. 이름에 `File` 이 없는 것이 위 항목의 표시다 — **이 껍데기는 안쪽이 파일인지 모른다.** 문자 쪽 짝은 `BufferedReader` 이고 그쪽에만 `readLine()` 이 있다 → [[character-stream]]
- **버퍼 스트림이 주는 것은 속도뿐이고, `BufferedReader` 는 거기에 하나를 더 준다** — `readLine()` 은 「줄」이라는 개념을 만들어 주는 **별개의 기능**이고 버퍼링과 무직접적이다. 그래서 Day40 이 `BufferedReader` 를 쓴 이유(줄 단위 읽기)와 Day41 이 버퍼를 배우는 이유(호출 횟수)가 **같은 클래스 계열에 붙어 있지만 다른 것**이다. 「`Buffered` 를 쓰면 `readLine()` 이 생긴다」로 묶어 외우면 바이트 쪽에 `readLine()` 이 없는 것이 설명되지 않는다 → [[character-stream]]
- **쓰는 쪽은 닫지 않으면 데이터가 사라진다** — 읽기 버퍼는 안 닫아도 읽은 값이 맞지만, 쓰기 버퍼에는 **아직 안 나간 것**이 남는다. `close()`(또는 `flush()`)를 부르지 않으면 예외도 없이 잘린 파일이 남고, 프로그램이 `System.exit` 로 끝나면 그대로 유실된다. **버퍼를 끼우는 순간 「닫기」가 자원 반납에서 데이터 완결로 성격이 바뀐다** — Day41 의 예제는 읽기만 하므로 이 대가가 드러나지 않는다 → [[try-with-resources]]
- **버퍼는 지연을 만든다 — 그래서 대화형·실시간 통로에는 해가 된다** — 모아 두는 것이 목적이므로 「지금 보낸 것이 지금 나가지 않는다」. 콘솔 프롬프트를 버퍼에 담아 두면 사용자는 아직 아무 질문도 못 본 채 입력을 기다리게 되고, 소켓이면 상대가 응답을 기다리며 멈춘다. `System.out`(`PrintStream`)이 `autoFlush` 를 갖는 이유가 이것이다. **처리량과 지연이 맞바꿈이라는 것**이고, 버퍼는 처리량 쪽을 산 것이다 → [[io-stream]]
- **`BufferedInputStream` 의 메서드는 동기화되어 있다** — 여러 스레드가 같은 스트림을 쓰는 경우를 위해 `synchronized` 인데, 단일 스레드에서는 쓸데없는 비용이다. 그래도 시스템 호출 한 번보다 훨씬 싸므로 남는 장사다 — **성능 층을 하나 끼우는 것이 다른 종류의 비용을 조금 들여오는** 자리다.
