# 조용한 폴백 금지

파이프라인의 한 단계(외부 API 호출 등)가 실패했을 때 **더 나쁜 입력으로 다음 단계를 계속 돌리는 폴백**은 실패를 사용자 눈에서 지운다. 결과물은 나오지만 품질이 다른데 표시가 없다. 실패는 **상태(failed)와 사람이 읽는 사유**로 드러내고, **재시도 경로**가 막힘을 푼다.

## 정의

1. 실패 갈래를 전부 열거한다(입력 없음 · 업로드 실패 · 거절 · 수신 실패 · 빈 결과 · 상한 초과).
2. 어느 갈래든 결과는 같다 — 자원 상태 `failed`, 사유는 내부 식별자·HTTP 본문·예외 이름 없이 사람 말 한 줄(「무엇이 안 됐고 다음에 무엇을 하면 되는지」).
3. 다음 단계로 넘어가지 않는다(합성 미호출).
4. [다시 시도]는 실패한 단계 **부터** 다시 돈다. 멱등한 부분(같은 id 로 결과 GET)만 자동 재시도한다.

## 사용 예시

재전사 결과 GET 이 175KB 본문 도중 `IncompleteRead` 로 끊김 → 옛 규칙은 「실시간 원문 유지」로 done 처리, 화면엔 화자가 어긋난 원문 위의 회의록이 섰고 아무 표시가 없었다. 새 규칙은 결과 GET 을 3회 백오프 재시도한 뒤 안 되면 `failed`+「다시 들은 결과를 받지 못했습니다. [다시 시도] 해 주세요」.

## 왜 중요한가

- 폴백은 「막히지 않게」 하려는 선의지만, 재시도 경로가 있으면 실패로 보내도 막히지 않는다.
- 품질이 다른 두 결과가 같은 상태(done)로 섞이면 데이터 신뢰가 무너진다(`transcript_source` 같은 표지를 두어도 화면이 안 보여 주면 소용없다).

## 경계와 오해

- 모든 폴백이 나쁜 건 아니다 — 폴백을 쓰려면 **「그 실패를 사용자가 어디서 보는가」**를 같이 적어야 한다. 그 답이 없으면 폴백이 아니라 은폐다.
- 브리프에 폴백 규칙을 쓰는 사람(코디)이 이 실수를 하기 쉽다 — 워커는 브리프대로 만든다.
