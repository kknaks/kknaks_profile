# 외부 id 대응표

외부 시스템에서 받아 온 행의 외부 id 를 **본 테이블의 칸에 두지 않는다.** 대신 `(entity_type, entity_id) ↔ (vendor, external_id)` 대응표 한 곳에만 둔다. 본 테이블끼리는 내 id(FK)로만 잇는다. 그러면 외부 시스템을 떼어 낼 때 대응표만 지우면 된다.

## 정의

1. **본 테이블에 외부 id 칸 0** — `purchase` · `ticket` · `prepaid_card` 같은 표에는 `kos_id` 가 없다. 외부 id · 외부 차트번호 · 동기화 상태(`synced_at` · `is_present_in_source` · 외부 수정 시각)는 대응표에만 둔다.
2. **동기화 = 대응표로 찾아 upsert** — 같은 외부 행이 다시 오면 대응표에서 내 행을 찾아 갱신하고, 없을 때만 만든다. 그래서 다시 돌려도 쓴 행이 0 이다 → [[idempotency]].
3. **사라짐도 대응표에 적는다** — 응답에서 빠지면 대응표에 「원천에 없음」을 표시하고, 본 테이블에는 `deleted_at` 을 채운다(소프트 딜리트).
4. **외부 id 가 행마다 유일하다는 가정을 실물로 확인한다** — KOS 는 환불 한 건의 금액 · 포인트 두 이력에 같은 `chargingId` 를 준다. 그대로 넣으면 한 행만 남아서 `chargingId:주머니` 로 합성했다. 작업처럼 외부 id 가 아예 없는 행은 `일정 id:순번` 으로 만든다.
5. **원천이 계산해 주는 값은 칸으로 두지 않는다** — 카드 총액 · 티켓별 가격처럼 내 칸으로 계산할 수 있는 값은 받지 않는다. 외부를 떼면 계산할 곳이 남아 있어야 한다.

## 사용 예시

- DAY: 새 테이블 28개에 KOS id 칸 0 · `external_ref` 2,196행(DEMO 첫 동기화 — 메뉴 2,157 + 오늘 거래 39). 두 번째 회차 쓴 행 0.
- 「KOS 없이 되는가」 표: 시술권 N장 만들기 · 카드 생성 · 잔액 · 결제 합계 · 부분 환불 금액을 테이블마다 내 칸만으로 할 수 있는지 셌다(SPEC-000 §4).

## 왜 중요한가

- 원장이 외부에서 우리로 넘어오는 제품(연동 기간 → 자체 운영)이면, 외부 id 가 칸마다 흩어져 있을 때 떼는 작업이 모든 테이블의 마이그레이션이 된다.
- upsert 키가 한 곳이라 동기화 · 백필 · 재시도가 같은 규칙으로 멱등해진다.

## 경계와 오해

- **대응표 행 수 = 받은 외부 행 수** — 「ref 가 왜 2천 건이냐」 는 정상이다. 메뉴처럼 행이 많은 원천이 대부분을 차지한다.
- **외부 id 를 지우면 「어느 외부 행이었나」 만 사라진다** — 데이터 자체는 남는다. 원장이 넘어온 뒤에는 그 정보가 필요 없다.
- **대응표가 있어도 외부 계약의 변화는 막지 못한다** — 외부가 값의 뜻을 바꾸면 매핑(KOS 값 → 내 enum)을 고쳐야 한다. 매핑은 한 곳에 둔다.
