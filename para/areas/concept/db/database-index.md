# 데이터베이스 인덱스 (Database Index)

**검색 조건으로 쓰는 컬럼을 미리 정렬해 따로 들고 있는 구조.** Day51 의 네 줄이 이 개념의 뼈대를 다 갖고 있다 — 「따로 정렬 해 두면 데이터를 빨리 찾을 수 있다」·「별도로 관리하는 것이 조회에 유리하다」·「값이 추가/변경/삭제 될 때 인덱스 정보도 갱신한다」·「입력/변경/삭제 시에는 속도가 느려지지만, 조회에서는 속도가 빠르다」. **얻는 것과 내는 것이 한 문장에 함께 적혀 있는 것**이 이 개념의 성격이다.

## 정의

인덱스가 없으면 DB 는 `where` 조건을 만족하는 행을 찾기 위해 **테이블을 처음부터 끝까지 훑는다**(full scan). 그것이 자바에서 배열을 `for` 로 돌며 비교했던 그 일이다 → [[linear-search]]

인덱스는 그 컬럼의 값을 **정렬된 상태로 유지하는 별도 구조**(대개 B-tree)를 만들어 둔다. 정렬되어 있으므로 반씩 좁혀 들어갈 수 있고, 훑는 횟수가 행 수에 비례하지 않게 된다.

| | 인덱스 없음 | 인덱스 있음 |
|---|---|---|
| 조회 | 전체를 훑는다 — 행이 100배면 100배 | 정렬 구조를 따라간다 — 행이 100배여도 몇 단계 |
| 입력·변경·삭제 | 데이터만 쓴다 | **데이터 + 인덱스**를 함께 고친다 |
| 저장 공간 | 데이터만 | 인덱스만큼 더 쓴다 |

만드는 방법은 세 가지이고, **둘은 이미 만들었다.**

| 만드는 것 | 언제 생기나 |
|---|---|
| `primary key` | 걸면 자동으로 생긴다 (InnoDB 는 데이터 자체를 이 순서로 보관한다) → [[primary-key]] |
| `unique` | 제약이 곧 인덱스다 → [[unique-key]] |
| `index` / `fulltext index` | 직접 만든다 |

## 사용 예시

Day51 은 `create table` 안에 세 가지를 한꺼번에 적는다.

```sql
create table test1(
no int ,
name varchar(20),
age int,
score int,
constraint primary key(no),
constraint test1_uk unique (name, age),
fulltext index test1_name_idx (name)
);
```

나중에 더할 때는 `alter table` 이다.

```sql
alter table 테이블명
  add fulltext index 인덱스이름(컬럼명);       //문자열만 인덱스 가능
```

**세 줄이 각각 다른 종류의 인덱스를 만든다** — 기본키 인덱스, 유니크 인덱스, 전문(fulltext) 인덱스. 다만 **세 번째는 이 테이블의 조회에 쓰이지 않는다**(아래 「경계와 오해」의 첫 항목).

## 왜 중요한가

**행이 늘어날 때 무엇이 느려지는지가 인덱스로 갈린다.** 데이터가 100건일 때는 인덱스가 있든 없든 즉시 답이 오고, 그래서 **개발 중에는 이 결정이 보이지 않는다.** 100만 건에서 드러나며, 그때는 「쿼리를 고치는 일」이 아니라 「인덱스를 만드는 일」이 답이다 → [[linear-search]]

**그리고 「전부 인덱스를 걸면 되는가」의 답이 아니오인 이유가 쓰기 쪽에 있다.** 컬럼 다섯에 인덱스를 걸면 한 행을 넣을 때 **여섯 곳**(데이터 + 인덱스 5)을 고친다. 조회가 드물고 등록이 잦은 테이블(로그·이벤트)에서는 인덱스가 순손실이고, **읽기와 쓰기의 비율이 이 결정의 입력**이다.

**정렬도 인덱스가 대신한다.** `order by name` 은 인덱스가 없으면 결과를 모아 놓고 정렬하는 별도 작업이 붙지만, `name` 인덱스가 있으면 **이미 정렬된 순서를 그대로 읽는다.** 그래서 인덱스는 「찾기」만 빠르게 하는 것이 아니라 「줄 세우기」와 「범위 훑기」(`between`·`>`)까지 함께 가져간다.

## 경계와 오해

- **`fulltext index` 로는 `where name = 'aaa'` 가 빨라지지 않는다 — Day51 의 실제 오용이다** — 전문 인덱스는 문장을 **단어로 쪼개 어느 행에 있는지 적어 두는 구조**이고, `MATCH(name) AGAINST('aaa')` 라는 **전용 문법으로만** 쓰인다. 일반 비교(`=`·`like 'a%'`·`order by`)는 이 인덱스를 아예 쓰지 못하므로, Day51 의 테이블은 **인덱스를 만들어 놓고 조회에서 한 번도 쓰지 않는다** — 즉 갱신 비용만 내고 이득은 0 이다. 이름 컬럼을 빠르게 찾으려면 `index test1_name_idx (name)`(일반 인덱스)여야 했다. 게다가 전문 인덱스는 **짧은 단어를 아예 담지 않는다**(InnoDB 기본 최소 토큰 3글자) — `'aaa'` 는 걸리지만 `'ab'` 는 색인조차 되지 않는다. **「인덱스를 걸었으니 빨라졌다」가 성립하지 않는 대표적인 경로**다 → [[search-index]]
- **그 예제의 `insert` 는 실행되지 않는다 — 없는 컬럼을 쓴다** — 테이블은 `(no, name, age, score)` 인데 이어지는 네 `insert` 는 `(no,name,age,kor,eng,math)` 다. `Unknown column 'kor' in 'field list'` 로 전부 거절된다. **바로 앞 [[unique-key]] 절의 테이블에서 `insert` 만 복사해 오고 컬럼 이름을 `score` 로 바꾼 것을 반영하지 않은 것**이며, 그래서 이 절의 결과 화면은 저 문장들로 만든 것이 아니다.
- **인덱스 ≠ 별도의 테이블** — Day51 의 「별도의 테이블로 관리한다」는 **비유로는 통하지만 실물은 다르다.** 인덱스는 `show tables` 에 나오지 않고 `select` 로 조회할 수 없으며, 테이블처럼 행을 담는 것이 아니라 **정렬된 키와 행 위치의 쌍**을 담는 트리다. 「테이블」로 이해하면 「그럼 그 테이블에도 인덱스를 걸어야 하나」 같은 질문에 답할 수 없다.
- **DB 인덱스 ≠ [[search-index]] (검색엔진 인덱스)** — 이 레포에서 `[[인덱스]]`·`[[index]]` 라고 쓰면 검색엔진 쪽 노트로 풀리므로 구분해서 링크해야 한다. 둘의 차이는 **어디에 사는가**다 — DB 인덱스는 같은 테이블 옆에 있어 갱신이 같은 트랜잭션 안에서 일어나고, 검색엔진 인덱스는 별도 제품(Elasticsearch)에 있어 **원본과 시차가 생긴다.** MySQL 의 `fulltext` 는 그 경계에 걸친 것이다 — 역인덱스이면서 DB 안에 있다.
- **인덱스가 있어도 안 쓰이는 경우가 많다** — 컬럼을 함수로 감싸면(`where year(reg_date) = 2024`), 앞이 아니라 뒤를 찾으면(`like '%aaa'`), 타입이 달라 변환이 끼면 인덱스는 무시되고 전체를 훑는다. **인덱스는 「컬럼에 붙는 것」이 아니라 「조건이 그 정렬을 이용할 수 있을 때만 쓰이는 것」**이라, 있는데도 느린 쿼리가 나오는 자리가 여기다.
- **복합 인덱스는 앞에서부터만 쓸 수 있다** — `(name, age)` 인덱스는 `name` 만으로도 쓰이지만 `age` 만으로는 쓰이지 않는다. 전화번호부가 성-이름 순으로 정렬돼 있을 때 이름만으로는 찾을 수 없는 것과 같다 → [[unique-key]]
- **「문자열만 인덱스 가능」은 전문 인덱스에만 맞다** — Day51 이 `add fulltext index` 옆에 적은 주석이다. `fulltext` 는 문자 타입(`char`·`varchar`·`text`)에만 걸리지만, **일반 인덱스는 숫자·날짜에도 걸린다** — 오히려 정수 컬럼이 인덱스로 가장 이득이 크다. 이 주석을 인덱스 일반의 성질로 읽으면 `where age = 20` 을 빠르게 만들 방법이 없어진다 → [[sql-data-type]]
- **인덱스는 캐시가 아니다** — 둘 다 「빠르게 하는 파생물」이라 겹쳐 보이는데, 캐시는 **답을 보관**하고 인덱스는 **찾는 길을 보관**한다. 캐시는 원본과 어긋날 수 있고(무효화 문제) 인덱스는 같은 트랜잭션에서 함께 갱신되어 어긋나지 않는다 → [[caching]]
- **자동 증가 기본키는 인덱스에 가장 친절한 형태다** — InnoDB 는 데이터를 기본키 순서로 보관하므로, 번호가 계속 커지면 **새 행이 언제나 끝에 붙는다.** 임의의 값(UUID·주민번호)을 기본키로 쓰면 중간에 끼워 넣게 되어 페이지가 쪼개진다. Day51 의 「자동 증가」 절과 이 절이 붙어 있는 것이 우연이 아니다 → [[surrogate-key]] · [[primary-key]]
