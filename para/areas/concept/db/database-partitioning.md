# 데이터베이스 파티셔닝 (Database Partitioning)

하나의 큰 테이블을 같은 데이터베이스 인스턴스 안의 여러 저장 단위로 나누되, 애플리케이션에는 하나의 테이블로 보이게 하는 기법이다. 데이터 접근 범위를 줄이고 기간 단위의 데이터 관리를 단순화하는 DB 내부 최적화 전략이다.

## 정의

파티셔닝은 **파티션 키**의 값에 따라 각 행을 어느 파티션에 저장할지 결정한다. 애플리케이션은 보통 원래 테이블을 그대로 질의하고, DBMS가 데이터 배치와 파티션 선택을 담당한다.

대표적인 분할 방식은 다음과 같다.

1. **범위 파티셔닝** — 날짜나 숫자의 연속 구간으로 나눈다. 월별 로그나 연도별 주문처럼 범위 조건으로 조회하고 기간 단위로 폐기하는 데이터에 적합하다.
2. **리스트 파티셔닝** — 지역 코드처럼 미리 정한 값의 목록에 따라 나눈다.
3. **해시 파티셔닝** — 파티션 키의 해시값을 이용해 데이터를 여러 파티션에 비교적 고르게 나눈다.
4. **복합 파티셔닝** — 범위와 해시처럼 둘 이상의 방식을 결합한다.

조회 조건이 파티션 키의 범위를 제한하면 옵티마이저는 관계없는 파티션을 실행 계획에서 제외할 수 있다. 이를 **파티션 프루닝(partition pruning)**이라고 한다. 보존 기간이 지난 데이터는 행별로 삭제하는 대신 해당 파티션을 분리하거나 통째로 제거할 수 있다.

## 사용 예시

다음 PostgreSQL 예시는 이벤트 로그를 월별 범위 파티션으로 나눈다.

```sql
CREATE TABLE event_log (
    id          bigint GENERATED ALWAYS AS IDENTITY,
    occurred_at timestamptz NOT NULL,
    payload     jsonb NOT NULL,
    PRIMARY KEY (id, occurred_at)
) PARTITION BY RANGE (occurred_at);

CREATE TABLE event_log_2026_01
PARTITION OF event_log
FOR VALUES FROM ('2026-01-01 00:00:00+00')
         TO ('2026-02-01 00:00:00+00');

CREATE TABLE event_log_2026_02
PARTITION OF event_log
FOR VALUES FROM ('2026-02-01 00:00:00+00')
         TO ('2026-03-01 00:00:00+00');

INSERT INTO event_log (occurred_at, payload)
VALUES
    ('2026-01-15 12:00:00+00', '{"event":"login"}'),
    ('2026-02-24 09:30:00+00', '{"event":"purchase"}');

EXPLAIN
SELECT *
FROM event_log
WHERE occurred_at >= '2026-02-01 00:00:00+00'
  AND occurred_at <  '2026-03-01 00:00:00+00';
```

마지막 질의는 파티션 키인 `occurred_at`을 2월 범위로 제한한다. DBMS는 1월 파티션을 제외하고 `event_log_2026_02`만 읽을 수 있다. 월별 보존 정책을 적용할 때는 오래된 파티션을 행 단위로 지우지 않고 파티션 단위로 제거할 수 있다.

## 왜 중요한가

큰 테이블에서는 인덱스와 데이터가 커지면서 디스크 I/O, 백업·복구, 유지보수 및 오래된 데이터 삭제 비용이 증가한다. 파티셔닝은 자주 조회하는 범위만 읽게 하고 데이터 수명 주기를 파티션 단위로 관리하게 해 이 비용을 줄인다.

특히 날짜 조건이 반복되는 로그·이력 테이블에서는 조회 패턴과 삭제 단위가 같은 시간 축을 공유한다. 이때 범위 파티셔닝은 조회 최적화와 보존 정책을 하나의 물리 구조로 함께 표현한다.

## 경계와 오해

- **파티셔닝 ≠ [[database-sharding]]** — 파티셔닝은 한 DB 인스턴스 내부의 저장 단위를 나누지만, 샤딩은 데이터를 여러 DB 인스턴스에 분산한다.
- **파티션 수 증가 ≠ 자동 성능 향상** — 질의가 파티션 키로 범위를 좁히지 못하면 여러 파티션을 모두 확인해야 한다. 파티션이 지나치게 많으면 메타데이터와 실행 계획 관리 비용도 증가한다.
- **파티셔닝 ≠ 단일 서버 한계 제거** — 모든 파티션은 여전히 같은 인스턴스의 CPU, 메모리와 디스크 자원을 사용한다.
- **파티션 키 ≠ 임의의 분류 컬럼** — 실제 조회 조건과 보존·삭제 단위에 맞지 않는 키는 프루닝과 관리 효율을 얻지 못한다.
- **파티션 생성은 일회성 작업이 아니다** — 시간 범위 파티션은 새 기간이 시작되기 전에 다음 파티션을 준비해야 한다. 범위를 벗어난 입력에 대비해 사전 생성 자동화나 기본 파티션을 검토해야 한다.
