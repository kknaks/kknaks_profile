# 메달리온 아키텍처

원천 데이터를 브론즈·실버·골드 레이어로 통과시키면서 데이터의 구조와 품질을 점진적으로 높이는 데이터 설계 패턴이다. 각 레이어는 원본 보존, 공통 의미 정립, 소비 목적별 최적화라는 서로 다른 책임을 맡는다. 레이크하우스뿐 아니라 실시간 애플리케이션 파이프라인에서도 이 책임과 의존 경계를 환경에 맞게 다시 정의해 적용할 수 있다.

## 정의

1. **브론즈 레이어** — 외부 소스 데이터를 원래 구조에 가깝게 적재하고 로드 시각, 프로세스 ID 같은 메타데이터를 더한다. 원본 이력과 리니지를 보존하여 감사와 재처리의 기반으로 삼는다. 실시간 처리 시스템에서는 제공 팀의 원본 이벤트를 수집하되 조회 소비자가 이 스키마를 직접 참조하지 못하게 하는 경계이기도 하다.
2. **실버 레이어** — 브론즈 데이터에 매칭, 병합, 표준화, 중복 제거를 적용한다. 주요 비즈니스 개체와 트랜잭션을 일관된 관점으로 제공하며 분석, 머신러닝, 애플리케이션 조회의 공통 입력이 된다. 최종 결과에 영향을 주는 변경인지 판별해 불필요한 후속 실행을 차단할 수도 있다.
3. **골드 레이어** — 구체적인 소비 목적에 맞춰 데이터를 집계하거나 조합하고 비정규화한다. 조인을 줄인 읽기 최적화 모델과 최종 데이터 품질·비즈니스 규칙을 적용한다. 반대로 쓰기 팬아웃이 지나치게 크다면 공통 데이터와 개별 데이터를 분리해 두고 조회 시 조합하는 선택도 가능하다.

데이터는 일반적으로 원천을 먼저 적재한 뒤 변환하는 ELT 흐름을 따른다. 수집 속도와 원본 보존을 우선하고, 공통 정리는 실버에서, 복잡한 비즈니스 규칙과 소비 목적별 변환은 골드로 이동할 때 적용한다.

레이어 이름만으로 아키텍처가 성립하지는 않는다. 각 레이어의 입력·출력 계약, 허용하거나 금지하는 변환, 품질 검사, 접근 통제, 재처리 방법을 함께 정의해야 한다. 예를 들어 브론즈에서는 비즈니스 가공을 금지하고 골드에서는 브론즈 DTO를 직접 참조하지 못하게 할 수 있다. 처음에는 컨벤션으로 적용할 수 있지만, 모듈과 인터페이스로 의존 방향을 강제하면 잘못된 참조를 컴파일 단계에서 차단할 수 있다.

## 왜 중요한가

원본 보존과 데이터 정제, 소비 목적별 모델링을 한 단계에서 모두 처리하면 변환 실패의 원인을 추적하거나 다른 용도로 데이터를 재사용하기 어렵다. 메달리온 아키텍처는 이 책임들을 분리해 브론즈에서는 재현성과 감사 가능성, 실버에서는 개체 식별과 표준화, 골드에서는 사용 목적에 맞는 의미와 조회 성능을 각각 검증하게 한다.

같은 실버 데이터를 여러 골드 데이터셋이 사용할 수 있으므로 공통 정제 로직의 중복을 줄이고, 원천 시스템을 다시 읽지 않고도 새로운 분석 모델을 만들거나 기존 파이프라인을 재처리할 수 있다. 조회 소비자가 실버의 안정된 내부 계약부터 사용하면 제공 팀의 원본 스키마 변경도 실버 변환에서 흡수할 수 있어 변경 전파와 팀 간 결합이 줄어든다.

실버에서 의미 있는 변경만 통과시키면 중복 이벤트나 최종 결과와 무관한 필드 변경이 전체 파이프라인을 재실행하는 일을 막는다. 또한 공통 데이터와 개별 데이터를 분리하면 하나의 원천 변경이 수많은 파생 레코드 쓰기로 증폭되는 팬아웃을 줄일 수 있다. 다만 쓰기 절감은 조회 조인과 읽기 부하 증가를 동반하므로 전체 비용을 함께 비교해야 한다.

## 경계와 오해

- **메달리온 아키텍처 ≠ 테이블에 브론즈·실버·골드라는 이름을 붙이는 것** — 레이어마다 책임과 품질 기준이 정의되고 데이터가 그 기준을 통과해야 한다.
- **브론즈 레이어 ≠ 검증과 보안이 없는 영구 저장소** — 원본 보존이 목적이어도 개인정보 보호, 접근 통제, 마스킹, 격리 같은 수집 단계의 조치는 필요할 수 있다.
- **ELT ≠ 모든 변환을 무조건 뒤로 미루는 것** — 데이터 민감도, 규제, 지연 시간과 품질 요구에 따라 적재 전후의 검증 범위를 정해야 한다.
- **메달리온 아키텍처 ≠ Databricks·Spark 전용 구조** — 특정 제품이나 정형 테이블의 구현 도구와 분리해 Spring 애플리케이션과 JSON 이벤트 같은 실시간 처리 환경에도 적용할 수 있다.
- **실버 ≠ 항상 3차 정규형, 골드 ≠ 항상 스타 스키마** — 정규화와 비정규화 방식은 대표적인 선택일 뿐이며 쓰기·읽기 특성과 소비 요구에 따라 달라진다.
- **실버 레코드 ≠ 모든 브론즈 레코드의 일대일 복사본** — 안정된 계약, 결합, 중복 제거, 의미 기반 변경 감지처럼 별도 가치가 있을 때 만들며 필요하면 여러 원천을 하나로 조합한다.
- **검증 ≠ null·형식 검사만 수행하는 것** — 후속 결과에 영향을 주는 변경인지 판단하는 것도 파이프라인 검증이다. 다만 변경 필드를 잘못 분류하면 필요한 갱신을 누락할 수 있으므로 계약 테스트가 필요하다.
- **레이어 수가 많을수록 좋은 것 ≠ 좋은 아키텍처** — 각 간접 계층에는 변환과 추적 비용이 따른다. 변경 격리, 품질 또는 관측성에 실질적인 이득을 주지 않는 계층은 만들지 않는다.
