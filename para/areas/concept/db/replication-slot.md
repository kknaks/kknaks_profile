# 복제 슬롯 (Replication Slot)

**「받는 쪽이 어디까지 가져갔는지」를 원본이 기억하게 만드는 표식.** 그 지점 이전의 로그만 지울 수 있게 되므로, 받는 쪽이 느려도 로그가 사라지지 않는다.

## 정의

로그를 흘려보내는 복제([[write-ahead-logging]] · [[change-data-capture]])에는 구조적 위험이 하나 있다 — **받는 쪽이 읽기 전에 원본이 로그를 지워 버리는 것.** 지워지면 그 구간은 영구히 비고, 체인이 끊긴 시점부터 복원이 불가능해진다.

슬롯은 그 구멍을 막는다.

```
받는 쪽: "여기까지 받았다"  ──▶  원본: restart_lsn 갱신
원본: restart_lsn 이전 로그만 삭제 가능
```

PostgreSQL 은 `pg_replication_slots` 의 `restart_lsn` 으로, MySQL 은 별도 슬롯 없이 **보존 기간**(`binlog_expire_logs_seconds`)으로 같은 문제를 다룬다 — 시간으로 재는지 지점으로 재는지의 차이다.

## 왜 중요한가

**보장과 위험이 같은 장치에서 나온다.**

| | 슬롯 없음 | 슬롯 있음 |
|---|---|---|
| 로그 구멍 | 생긴다 — 원본이 먼저 지움 | 안 생긴다 |
| 원본 디스크 | 안전 | **받는 쪽이 멈추면 무한히 참** |

받는 쪽 프로세스가 죽거나 네트워크가 끊기면 `restart_lsn` 이 전진하지 않고, 원본은 그 뒤의 로그를 전부 붙들고 있게 된다. **백업 장치가 운영 DB를 멈추는 경로가 여기 하나 있다.**

그래서 슬롯을 쓰면 감시가 따라붙어야 한다 — 밀린 양(`pg_current_wal_lsn()` 과 `restart_lsn` 의 차이)을 주기적으로 재고 임계치에서 알린다.

PostgreSQL 13+ 는 상한을 걸 수 있다.

```
max_slot_wal_keep_size = 50GB
```

넘으면 슬롯을 무효화하고 로그를 지운다 — **서비스는 살고 수집은 끊긴다.** 끊긴 슬롯은 베이스부터 다시 떠야 하므로, 이 값은 「운영 DB 보호」와 「수집 연속성」 중 무엇을 먼저 둘지의 선언이다.

## 경계와 오해

- **슬롯은 데이터를 보관하지 않는다** — 원본이 지우지 못하게 붙들 뿐이다. 실제 사본은 받는 쪽에 있어야 한다
- **`archive_command` 방식에는 슬롯이 없다** — 원본이 파일을 던지고 끝나므로 받는 쪽 장애가 원본에 전파되지 않는다. 대신 던진 파일이 도착했는지는 원본이 모른다. 슬롯은 그 안전성과 맞바꾼 보장이다
- **연결이 끊겨도 슬롯은 남는다** — 쓰지 않는 슬롯을 지우지 않으면 원본이 계속 로그를 쌓는다. 실험용으로 만든 슬롯이 잊히는 것이 흔한 사고다
- **MySQL 에는 같은 이름의 장치가 없다** — 보존 기간이 짧은데 받는 쪽이 느리면 그냥 구멍이 난다. 기본이 0인 관리형도 있어 설정하지 않으면 애초에 못 받는다
