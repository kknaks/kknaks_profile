# where 절의 연산자 (SQL Operator)

**`where` 조건 하나를 만들어 내는 기호들.** Day52 는 [[dql]] 의 셀렉션을 배운 직후 이 절로 넘어가 논리·사칙·비교·범위·패턴을 차례로 시험한다. 자바에서 이미 다 본 기호들인데 **같은 모양이 다른 규칙으로 동작하는 자리가 몇 개 있고**, 그 몇 개가 이 개념의 값이다 → [[operator]]

## 정의

자바 쪽과 나란히 놓으면 어디가 같고 어디가 갈리는지가 한눈에 보인다.

| 하는 일 | SQL | 자바 | 같은가 |
|---|---|---|---|
| 같다 | `=` | `==` | **기호가 다르다** |
| 다르다 | `!=` · `<>` | `!=` | `<>` 가 표준 |
| 크다·작다 | `>` `>=` `<` `<=` | 같음 | 같다 |
| 그리고 | `and` | `&&` | 낱말 vs 기호 |
| 또는 | `or` | `\|\|` | 낱말 vs 기호 |
| 부정 | `not` | `!` | 낱말 vs 기호 |
| 사칙 | `+` `-` `*` `/` `%` | 같음 | **`/` 의 결과가 다르다** |
| 범위 | `between a and b` | 없음 (`a <= x && x <= b`) | SQL 에만 있다 |
| 값이 없다 | `is null` | `== null` | → [[sql-null]] |

Day52 가 논리 연산자 셋에 붙인 정의가 정확하다 — OR 은 「두 조건 중에 참인 것이 있으면」, AND 는 「두 조건 모두 참일 때만」, NOT 은 「조건에 일치하지 않을 때만」 결과에 포함시킨다. **`where` 는 조건을 계산해 참인 행만 남기는 필터**이고, 연산자는 그 참·거짓을 만드는 부품이다.

`between` 은 **양끝을 포함**한다.

```sql
select 5 between 3 and 5;   -- 1 (참)
```

## 사용 예시

Day52 는 조건을 테이블에 걸어 보는 형태와, **테이블 없이 결과만 확인하는 형태**를 섞어 쓴다.

```sql
//or
select * from 테이브명 where 조건 or 조건;

//and
select * from 테이브명 where 조건 and 조건;

//not
select * from 테이브명 where not 컬럼명 = 값;
select * from 테이브명 where 컬럼명 != 값;
select * from 테이브명 where not 컬럼명 <> 값;
```

```sql
select (4 + 5), (4 - 5), (4 * 5), (4 / 5), (4 % 5);
select (4=5), (4!=5), (4>5), (4>=5), (4<5), (4<=5), (4<>5);
select 5 between 3 and 5;
```

**아래 세 줄이 이 절을 배우는 방법 자체다** — 테이블도 데이터도 없이 연산자만 서버에 계산시켜 결과를 눈으로 본다. 그리고 그 결과 화면이 이 개념의 두 가지 중요한 사실을 그대로 보여 준다: `4/5` 가 `0` 이 아니고, 비교의 결과가 `true`/`false` 가 아니다(아래) → [[dql]]

## 왜 중요한가

**`where` 한 줄이 「어느 행」을 정하므로, 연산자를 잘못 읽으면 [[dml]] 이 잘못된 행을 고친다.** 조회에서 틀리면 화면이 이상하고 끝이지만 `update`·`delete` 에서 틀리면 데이터가 바뀐다. 같은 조건 문법을 세 문장이 공유하는 것이 편리함이자 위험이다 → [[transaction]]

**결과가 boolean 이 아니라 숫자라는 것이 SQL 의 성격을 정한다.** `select (4=5)` 가 `0` 을, `(4<5)` 가 `1` 을 돌려준다. 그래서 `where 1` 이 전체 조회가 되고 `where 1=1` 을 조건 조립의 시작점으로 쓸 수 있다 — **참·거짓이 값이라 조건을 문자열로 이어 붙이는 방식이 성립한다.** 자바에서 `if (1)` 이 컴파일 오류인 것과 갈린다 → [[data-type]]

**그리고 조건의 모양이 성능을 정한다.** 같은 뜻의 조건도 컬럼을 함수로 감싸거나 패턴을 뒤에서 열면 인덱스를 쓰지 못한다. 「무엇을 원하는가」만 적는 것처럼 보이는 `where` 가 실은 **「어떻게 찾을 수 있는가」까지 지정하고 있다** → [[database-index]]

## 경계와 오해

- **`not 컬럼명 <> 값` 은 앞의 두 예제와 반대를 뜻한다 — 필기의 세 줄 중 하나가 다른 결과다** — Day52 는 NOT 을 「조건에 일치하지 않을 때만」이라 정의한 뒤 세 형태를 나란히 적었는데, `<>` 가 이미 「같지 않다」이므로 셋의 결과는 이렇게 갈린다.

  | 필기의 문장 | 실제 뜻 |
  |---|---|
  | `where not 컬럼명 = 값` | 값이 **아닌** 행 |
  | `where 컬럼명 != 값` | 값이 **아닌** 행 |
  | `where not 컬럼명 <> 값` | **이중 부정 — 값인 행** |

  「not 을 쓰는 세 가지 방법」으로 읽으면 세 번째에서 정확히 반대 결과를 얻는다. `!=` 와 `<>` 가 **같은 연산자의 두 표기**라는 것을 알면 바로 보이는데, 표기가 둘이라 「`!` 계열」과 「`<>` 계열」로 갈라 놓고 각각에 `not` 을 붙여 본 흔적으로 읽힌다.
- **`4 / 5` 가 `0` 이 아니라 `0.8000` 이다** — 자바에서 정수끼리의 `/` 는 정수 나눗셈이었지만, MySQL 의 `/` 는 **언제나 소수로 계산한다.** 정수 나눗셈을 원하면 `div` 를 따로 쓴다(`4 div 5` = `0`). 평균·비율을 자바에서 SQL 로 옮길 때 결과가 달라지는 자리이고, 반대 방향(SQL → 자바)에서는 **소수점이 조용히 잘린다** → [[operator]] · [[type-promotion]] · [[floating-point]]
- **비교의 결과가 `true`/`false` 가 아니라 `1`/`0` 이다** — Day52 의 `select (4=5), (4>5)` 화면이 그 증거다. MySQL 에 독립된 boolean 타입이 없고 `boolean` 은 `tinyint(1)` 의 별명이라, `true`·`false` 라고 써도 `1`·`0` 으로 저장된다. `where 컬럼명` 처럼 조건 자리에 컬럼을 그냥 두는 것도 문법적으로 성립한다(0 이 아니면 참) → [[sql-data-type]] · [[data-type]]
- **`=` 는 비교이고 대입이 아니다 — 그런데 `update ... set` 에서는 대입이다** — 같은 기호가 절에 따라 뜻이 바뀐다. `where age = 20` 은 「20 인가」이고 `set age = 20` 은 「20 으로 만들라」다. 자바에서 `==` 와 `=` 를 기호로 갈라 두어 `if (a = b)` 를 컴파일러가 막아 주던 보호가 **SQL 에는 없다** → [[dml]] · [[expression-vs-statement]]
- **`and` 가 `or` 보다 먼저 묶인다** — `where a or b and c` 는 `where a or (b and c)` 다. Day52 의 예제는 조건이 둘뿐이라 이 우선순위가 드러나지 않는데, **조건이 셋이 되는 순간 괄호를 안 쓰면 결과가 의도와 달라진다.** 「이름이 A 이거나 B 이고, 나이가 20」을 그대로 옮겨 적으면 A 는 나이 조건 없이 전부 걸린다 → [[operator]]
- **SQL 은 단축 평가를 보장하지 않는다** — 자바에서 `if (s != null && s.length() > 0)` 이 안전했던 것은 `&&` 가 앞이 거짓이면 뒤를 **평가하지 않는다**는 규칙 때문이다. SQL 의 `and` 에는 그런 약속이 없고 **옵티마이저가 조건 순서를 바꾼다.** 그래서 「앞 조건으로 막아 두었으니 뒤가 안전하다」는 형태(0 으로 나누기·형변환 실패를 앞 조건으로 막기)가 SQL 에서는 성립하지 않는다 → [[short-circuit-evaluation]]
- **`between` 을 날짜에 쓰면 양끝 포함이 함정이 된다** — Day52 의 `between '2022-11-1' and '2022-12-31'` 은 컬럼이 `datetime` 이면 **12월 31일 00:00:00 까지만** 잡아서 그날 낮의 데이터가 빠진다. 「끝까지 포함」이라는 것은 맞는데 그 「끝」이 자정이다. 안전한 형태는 `>= '2022-11-01' and < '2023-01-01'` 다 → [[sql-date-function]] · [[sql-data-type]]
- **사칙연산의 `%` 와 `like` 의 `%` 는 다른 것이다** — 같은 노트 안에서 두 절 떨어져 나온다. 연산자 절의 `%` 는 나머지(`4 % 5` = `4`), 패턴 절의 `%` 는 **길이 제한 없는 임의 문자**다. 조건 문자열을 조립할 때 둘이 같은 문장에 섞이면 어느 쪽인지 읽히지 않는다 → [[sql-like]]
- **`NULL` 이 섞이면 참·거짓이 아니라 셋이 된다** — `where 컬럼명 != 값` 은 값이 `NULL` 인 행을 **잡지 못한다.** 비교의 결과가 참도 거짓도 아닌 `NULL` 이 되고, `where` 는 참인 행만 남기기 때문이다. 그래서 조건을 뒤집어도 두 결과의 합이 전체가 되지 않는다 — Day52 가 `is null` 을 별도 항목으로 둔 이유다 → [[sql-null]]
- **`where` 에서 컬럼을 함수로 감싸면 인덱스가 죽는다** — `where year(regdt) = 2022` 는 정렬된 컬럼 값이 아니라 **계산한 결과**를 비교하므로 전체를 훑는다. 조건을 「컬럼 그대로 vs 상수」의 모양으로 유지하는 것이 인덱스를 쓰는 최소 조건이다 → [[database-index]]
- **필기 예제의 `테이브명` 은 `테이블명` 의 오기다** — 논리 연산자 절 네 곳에 있다. 그대로 실행하면 조건이 아니라 **테이블 이름에서** 막힌다(`Table ... doesn't exist`). 내용을 고치지 않는 원칙이라 본문은 그대로 두었다.
