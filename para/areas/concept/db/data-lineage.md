# 데이터 리니지 (Data Lineage)

데이터 리니지는 데이터가 어느 원천에서 나와 어떤 이동·변환을 거쳐 현재 결과에 사용되었는지 나타내는 계보다. 결과에서 입력으로 거슬러 올라가거나 원천 변경이 영향을 주는 파생 데이터를 찾는 근거가 된다.

## 정의

리니지는 데이터 사이의 생성·변환 의존 관계를 기록한다. 출처의 운영 판단 사례에서는 다음 경로를 연결한다.

1. **원천 기록** — ERP·MES·품질 시스템 등의 원래 데이터와 식별자.
2. **정제 과정** — 단위 통일, 코드 매핑, 중복 제거, 결측 처리 등 입력을 바꾸는 단계.
3. **판단 입력** — 정제 결과를 업무 객체와 속성에 연결한 데이터.
4. **소비 결과** — 해당 입력을 사용한 판단이나 보고서.

원천 위치만 적어 놓으면 변환 과정에서 무엇이 바뀌었는지 설명하기 어렵다. 판단을 재현하려면 리니지와 함께 당시 입력의 스냅샷 또는 복원 가능한 버전, 사용한 규칙과 평가 시각도 보존해야 한다.

### 판단 이력과의 연결

리니지는 ‘이 입력이 어떻게 만들어졌는가’를 설명하고, 판단 이력은 ‘이 입력과 기준으로 어떤 결정을 내렸는가’를 설명한다. 실제 업무 행동까지 추적하려면 승인자·실행 상태·최종 결과를 별도로 연결한다.

| 기록 | 답하는 질문 |
|---|---|
| 데이터 리니지 | 어떤 원천과 변환에서 이 값이 나왔는가? |
| 판단 당시 입력과 규칙 버전 | 당시 무엇을 보고 어떤 기준을 적용했는가? |
| 승인·실행 이력 | 누가 승인했고 실제로 무엇이 실행되었는가? |
| 후속 결과 | 그 행동 이후 어떤 결과가 발생했는가? |

이 기록을 함께 보면 실패 원인을 원천 데이터, 변환, 판단 기준, 승인 또는 실행 단계로 나누어 조사할 수 있다.

## 사용 예시

화장품 배치 `B-101`의 출하 판단이 품질 검사 `QC-101`을 사용했다고 하자. 최소한의 연결은 다음과 같다.

```text
품질 시스템의 QC-101
  → 불량률 단위·검사 시각 검증
  → B-101의 검사 속성
  → release-v1 기준으로 평가
  → READY_FOR_APPROVAL
  → 승인 및 출하 실행 이력
```

출처의 Python 예시는 `source_record='quality-system/QC-101'`로 원천 위치를 가리키고, `input_snapshot`과 `policy`로 당시 입력 및 판단 기준을 기록한다. 이는 추적을 위한 최소 정보다. 변환 이력과 영속 저장까지 구현된 완전한 리니지는 아니다.

출하 후 문제가 발견되면 검사값 자체가 틀렸는지, 불량률 단위를 잘못 변환했는지, 유효 기간이 지난 검사를 사용했는지, 승인 기준이 부적절했는지를 구분한다. 현재 검사값만 조회하면 이후 수정된 데이터가 나올 수 있으므로 당시 상태를 확인할 수 있어야 한다.

## 왜 중요한가

최종 값만 남으면 오류가 발생했을 때 어느 단계부터 다시 검토하거나 처리해야 하는지 알기 어렵다. 데이터의 생성 경로가 있으면 영향을 받은 결과를 찾고 수정 범위를 좁힐 수 있다.

운영 판단에서는 같은 결과라도 잘못된 데이터와 잘못된 정책에 대한 조치가 다르다. 리니지를 판단 이력에 연결하면 데이터 정정, 변환 수정, 기준 변경을 구분할 근거가 생긴다.

## 경계와 오해

- **데이터 리니지 ≠ 현실의 인과관계** — 데이터가 어떤 계산을 거쳤는지는 알 수 있어도 현실에서 무엇이 사건의 원인이었는지는 별도 검증이 필요하다.
- **원천 링크 ≠ 완전한 리니지** — 링크 하나로 중간 변환, 사용한 버전, 당시 입력을 모두 복원할 수는 없다.
- **리니지 ≠ 판단·승인 로그 전체** — 데이터 경로와 업무 결정의 기록은 역할이 다르며 서로 연결해야 한다.
- **리니지 존재 ≠ 데이터 정확성 보장** — 잘못된 값의 이동 경로도 정확하게 기록할 수 있다. 품질 검증은 별도로 필요하다.
- **관계 시각화 ≠ 추적 가능성** — 화면에 선을 그리는 것보다 실제 원천·변환·결과의 식별자와 이력이 연결되어 있는지가 중요하다.
