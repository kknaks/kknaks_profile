# 식별 관계와 비식별 관계

**부모의 기본키를 자식의 기본키에 넣을 것인가, 외래키로만 둘 것인가.** 같은 부모-자식 관계를 두 가지로 그릴 수 있고, 그 선택이 자식이 혼자 존재할 수 있는지를 정한다.

## 정의

| | 식별 관계 | 비식별 관계 |
|---|---|---|
| 부모 키 포함 여부 | 부모 키가 **자식의 기본키에 포함**된다 | 기본키에는 안 들어가고 **외래키로만** 있다 |
| 관계 강도 | 강한 종속 — 부모 없이는 자식이 존재할 수 없다 | 약한 종속 — 자식은 독립적으로 식별된다 |
| 키 구성 | 부모 키 + 자식 고유 속성 = 기본키 | 자식의 고유 속성만으로 기본키 |
| 사용 사례 | 주문과 주문 상세 | 부서와 직원 |

```sql
-- 식별 관계: 주문 상세는 어느 주문의 몇 번째인지로만 식별된다
create table order_item (
  order_no int,
  seq      int,
  primary key (order_no, seq),          -- 부모 키가 기본키의 일부
  foreign key (order_no) references orders(order_no)
);

-- 비식별 관계: 직원은 부서와 무관하게 자기 번호로 식별된다
create table employee (
  emp_no  int primary key,              -- 자기만의 키
  dept_no int,
  foreign key (dept_no) references department(dept_no)
);
```

## 왜 중요한가

**「이것은 혼자 존재할 수 있는가」라는 질문을 구조로 답하는 것이다.** 주문 상세는 주문이 없으면 의미가 없고, 직원은 부서가 없어도(또는 옮겨도) 여전히 그 직원이다. **그 판단이 키 구성에 남는다.**

**그리고 그 판단이 데이터를 지킨다.** 식별 관계에서는 부모 키가 기본키의 일부라 **부모 없는 자식이 애초에 만들어지지 않고**, 자식이 다른 부모로 옮겨 가는 것도 키를 바꾸는 일이라 사실상 막힌다 → [[foreign-key]] · [[primary-key]]

## 경계와 오해

- **식별 관계는 키가 계속 길어진다** — 손자 테이블은 부모의 복합키를 통째로 물려받고 자기 속성을 더한다. 3~4 단계만 내려가도 기본키가 컬럼 넷·다섯이 되고, **그것을 참조하는 쪽은 그만큼을 다 들고 가야 한다** → [[surrogate-key]]
- **그래서 실무는 대개 비식별 + 대리키로 기울어 있다** — 모든 테이블에 일련번호 기본키를 두고 관계는 외래키로만 두는 방식이다. 얻는 것은 **키의 단순함**이고 잃는 것은 **구조가 강제하던 제약**이라, 그 제약을 애플리케이션이 대신 지켜야 한다 → [[service-layer]]
- **비식별 관계라고 부모가 없어도 되는 것은 아니다** — 외래키에 `NOT NULL` 을 걸면 여전히 부모가 필수다. **식별/비식별은 「필수인가」가 아니라 「식별에 쓰이는가」**의 문제다 → [[sql-null]]
- **식별 관계는 조인을 늘린다** — 자식의 키가 부모 키를 포함하므로, 조회에서 그 컬럼을 이미 갖고 있어 조인을 줄이는 경우도 있다. **양쪽으로 작용하므로 성능을 이유로 고르기는 어렵다** → [[sql-join]]
- **ERD 에서 실선/점선으로 그린다** — IE 표기법에서 식별 관계는 실선, 비식별 관계는 점선이다. **그림의 선 종류가 키 설계를 담고 있다** → [[data-modeling]]
