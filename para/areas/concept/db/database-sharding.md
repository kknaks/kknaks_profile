# 데이터베이스 샤딩 (Database Sharding)

데이터를 여러 데이터베이스 인스턴스에 나눠 저장해 단일 서버의 저장 용량과 처리량 한계를 넘는 수평 확장 기법이다. 각 데이터 조각과 그것을 담당하는 인스턴스를 샤드라고 하며, 요청을 올바른 샤드로 보내는 라우팅이 설계의 핵심이다.

## 정의

샤딩은 **샤드 키**를 기준으로 데이터의 물리적 저장 위치를 결정한다. 사용자 ID, 테넌트 ID 또는 지역처럼 요청에서 안정적으로 얻을 수 있는 값이 주로 후보가 된다.

처리 흐름은 다음과 같다.

1. 주요 접근 패턴과 데이터 분포를 바탕으로 샤드 키를 정한다.
2. 범위, 해시 또는 별도의 디렉터리 매핑으로 키와 샤드의 관계를 정의한다.
3. 애플리케이션이나 미들웨어의 라우터가 요청의 샤드 키를 읽어 대상 DB를 선택한다.
4. 단일 샤드에서 읽기 또는 쓰기를 수행한다.
5. 용량이나 트래픽이 증가하면 샤드를 추가하고 데이터와 라우팅 정보를 함께 재배치한다.

샤드 키가 없는 전체 조회는 여러 샤드에 질의를 보내 결과를 합쳐야 한다. 교차 샤드 조인과 집계는 네트워크 왕복과 부분 실패를 다뤄야 하며, 여러 샤드에 걸친 원자적 변경에는 분산 트랜잭션 또는 다른 일관성 전략이 필요하다.

## 사용 예시

고객 데이터를 `customer_id`의 해시로 나눈다고 가정한다. 쓰기와 읽기 요청은 모두 같은 키를 이용해 고객이 속한 샤드를 찾으므로, 한 고객의 주문과 활동 이력을 같은 샤드에 배치하면 주요 질의를 단일 샤드 안에서 끝낼 수 있다.

글로벌 서비스에서는 지역을 기준으로 한국 데이터를 한국 샤드에, 미국 데이터를 미국 샤드에 둘 수도 있다. 이는 데이터 로컬리티를 높이지만 사용자의 지역 변경, 지역별 트래픽 불균형과 여러 지역을 아우르는 집계를 별도로 처리해야 한다.

샤드를 `hash(customer_id) % N`으로만 선택하면 샤드 수 `N`이 바뀔 때 많은 키의 목적지가 한꺼번에 달라진다. 운영 환경에서는 일관 해싱이나 별도의 샤드 매핑 테이블을 이용해 이동 범위를 통제할 수 있다.

## 왜 중요한가

단일 DB 서버는 CPU, 메모리, 디스크와 I/O 처리량을 계속 높일 수 없다. 샤딩은 데이터와 요청을 여러 서버에 분산해 서버를 추가하는 방식으로 저장 용량과 처리량을 확장하게 한다.

반면 샤딩은 데이터 위치를 애플리케이션 아키텍처의 관심사로 끌어올린다. 키 선택이 잘못되면 특정 샤드에 데이터나 요청이 몰리는 핫 샤드가 발생하고, 조인·트랜잭션·백업·복구·스키마 변경 같은 기존 DB 운영도 샤드 전체를 조율하는 작업으로 바뀐다. 따라서 샤딩의 가치는 확장 가능성뿐 아니라 이 복잡도를 감당할 필요가 있는지 판단하는 데 있다.

## 경계와 오해

- **샤딩 ≠ [[database-partitioning]]** — 샤딩은 여러 DB 인스턴스로 데이터를 물리적으로 분산하지만, 파티셔닝은 한 인스턴스 내부에서 테이블의 저장 단위를 나눈다.
- **샤딩 ≠ 복제** — 샤딩은 서로 다른 데이터를 나눠 가지며 용량과 쓰기 부하를 분산한다. 복제는 같은 데이터의 사본을 유지해 읽기 분산과 가용성을 얻는다.
- **샤드 수 증가 ≠ 균등한 확장** — 샤드 키의 값이나 요청 분포가 치우치면 한 샤드만 병목이 되는 핫 샤드가 생긴다.
- **단순 나머지 연산 ≠ 안전한 재분배** — `hash(key) % N`은 `N`이 바뀔 때 대량의 데이터 위치를 변경한다.
- **교차 샤드 질의 ≠ 일반 단일 DB 질의** — 조인·집계·트랜잭션이 여러 네트워크 요청과 부분 실패를 포함하므로 관련 데이터와 트랜잭션 경계를 가능한 한 같은 샤드에 배치해야 한다.
- **샤딩은 첫 번째 성능 처방이 아니다** — 인덱스와 질의 개선, 캐시, 읽기 복제본, 데이터 보존 정책과 스케일 업으로 단일 DB의 문제를 해결할 수 있는지 먼저 확인해야 한다.
