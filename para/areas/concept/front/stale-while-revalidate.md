# 받아 둔 화면을 먼저 보이고 뒤에서 갱신하기

탭을 오갈 때마다 스켈레톤이 번쩍이는 것은 대개 **응답이 느려서가 아니라 화면이 받아 둔 데이터를 버려서**다. 페이지가 언마운트되고 캐시가 없으면 응답이 0.1초여도 매번 「로딩」부터 다시 그린다. 다시 들어온 화면은 **마지막에 받은 값을 즉시 그리고, 같은 요청을 뒤에서 다시 보내 결과로 갈아 끼운다.** 스켈레톤은 받아 둔 것이 하나도 없는 첫 진입에만 뜬다.

## 정의

1. 화면별 키로 **마지막 응답**을 기억한다(모듈 수준 저장소 하나 + 화면 훅). 초깃값은 기억하지 않는다 — 받은 적 없는 빈 목록이 「받은 값」이 되면 안 된다
2. 재진입 = 기억한 값으로 시작 + 진입 요청은 그대로 → 같은 setter 로 교체. 쓰기 뒤 reload 도 같은 setter 라 기억이 함께 바뀐다
3. **주인(로그인 사용자)과 세대 토큰** — 로그아웃·사용자 전환 때 세대를 올리고, **요청을 시작한 세대 = 지금 세대**일 때만 기억한다. 아니면 A 의 늦은 응답이 B 의 기억에 들어간다
4. **기억한 권한으로는 명령을 열지 않는다** — 기억한 envelope 로 그린 화면의 명령 단추는 그 화면의 갱신 응답이 와야 풀린다. 풀리는 자리는 진입 effect 가 아니라 **그 화면의 어떤 다시 읽기든 성공한 지점**(아니면 갱신 한 번 실패로 영구 잠김)
5. 키가 바뀌는 화면(캘린더 구간·조직별·날짜별)은 접두사별 최근 N 개만 남긴다

## 경계와 오해

- 응답 속도 문제와 섞지 않는다 — 깜박임은 FE 구조, 느림은 서버(N+1·인증 재계산)다. 둘을 가르는 것은 Network 탭의 요청 시간이다
- 실시간 스트림 화면(회의 상세 등)은 대상이 아니다
- 라이브러리(react-query·SWR)가 이 다섯을 다 해 주지만, 들이면 API 계층 규율·테스트가 통째로 바뀐다 — 작은 저장소 하나로 충분했다
