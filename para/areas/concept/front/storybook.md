# Storybook

Storybook은 UI 컴포넌트를 애플리케이션의 페이지 흐름에서 분리해 개발하고, 상태별 예시를 탐색하며 개별적으로 확인하도록 돕는 도구다. 팀이 같은 컴포넌트와 입력 조건을 보며 구현과 디자인을 논의하는 작업 공간이 된다.

## 정의

Storybook의 관리 대상은 UI 컴포넌트와 특정 조건에서 렌더링한 예시인 **스토리(story)**다. 컴포넌트가 입력을 받아 화면을 만드는 구현이라면, 스토리는 그 구현에 어떤 입력과 환경을 제공해 관찰할지를 정한 사례다.

- **컴포넌트 탐색:** 버튼, 아바타, 댓글 등 이미 구현된 UI를 한곳에서 찾아 확인한다.
- **상태별 예시:** 기본 상태뿐 아니라 비활성 상태, 긴 문구, 빈 데이터 등 서로 다른 조건의 모습을 남긴다.
- **입력 조작:** 입력값을 바꾸면서 동일한 컴포넌트의 표시가 어떻게 달라지는지 관찰한다.
- **독립된 실행 환경:** 특정 페이지로 이동하거나 실제 사용자 흐름을 반복하지 않고 대상 컴포넌트를 확인한다. 테마나 로그인 정보처럼 필요한 외부 조건은 이 환경에서도 제공해야 한다.

컴포넌트를 독립적으로 렌더링할 수 있게 구성하면 확인과 테스트의 준비 비용을 줄일 수 있다. 다만 표시 환경을 마련하는 것과 동작의 정확성을 검증하는 것은 별도의 작업이다.

## 사용 예시

출처의 가디언 사례에서는 기사 화면에서 반복되는 아바타, 경기 정보, 댓글 등의 UI를 Storybook 목록에서 찾아본다. 경기 정보 컴포넌트는 리그명과 경기 상태 같은 입력을 조작할 수 있다. 리그명을 프리미어리그에서 라리가로 바꾸면 동일한 UI 구조 안의 표시 내용이 달라진다.

이 사례를 상태별 예시로 정리하면 다음과 같다.

| 입력 조건 | 확인할 내용 |
| --- | --- |
| 프리미어리그 · 예정 | 기본 정보와 예정 상태의 표시 |
| 라리가 · 진행 중 | 리그명 변경과 진행 상태의 표시 |
| 리그명 없음 | 빈 값의 대체 문구 |
| 긴 리그명 | 줄바꿈과 레이아웃 유지 |

앞의 리그명·경기 상태 조작은 영상의 사례이며, 빈 값과 긴 이름은 확정 교안에서 보충한 경계 조건이다.

교안의 독립 실행 HTML 예시는 `MatchCard({ league, status })`에 입력창과 선택 상자의 값을 전달한다. 이는 입력을 바꾸어 같은 UI를 확인하는 원리를 보여준다. Storybook API를 사용한 코드는 아니며, Storybook의 목록 탐색·스토리 관리·테스트 연동까지 구현하지는 않는다.

## 왜 중요한가

컴포넌트를 파일로 분리해도 팀이 그 존재와 지원 상태를 쉽게 알 수 있는 것은 아니다. 이름과 실제 모습을 함께 탐색할 수 있으면 기존 구현을 발견하고 재사용하기 쉬워져 비슷한 UI를 중복 구현하는 일을 줄인다.

대표 상태를 반복해서 확인할 수 있는 환경은 검증된 공통 구현을 유지하는 데 도움이 된다. 디자이너와 개발자도 같은 상태를 보며 변경 사항을 논의할 수 있어, 문구만으로 설명할 때 생기는 해석 차이를 줄인다.

## 경계와 오해

- **컴포넌트 분리만으로 재사용성이 확보되지는 않는다.** 특정 페이지의 전역 상태나 데이터 구조에 강하게 의존하면 독립적으로 확인하기 어렵다. 필요한 입력과 환경을 명시해야 한다.
- **렌더링 성공은 테스트 완료가 아니다.** 상호작용과 경계 조건의 검증이 필요하며, 실제 페이지의 레이아웃·데이터와 결합한 결과도 확인해야 한다.
- **Storybook 자체가 디자인 시스템 전체는 아니다.** 컴포넌트를 공유하는 공간은 제공하지만, 디자인 원칙과 사용 규칙까지 자동으로 정해 주지는 않는다.
- **공통 구현의 변경이 모든 제품에 즉시 반영되지는 않는다.** 사용하는 프로젝트의 버전 갱신과 배포가 필요할 수 있다.
- **웹과 모바일의 디자인 일관성이 코드의 동일성을 뜻하지는 않는다.** 디자인 원칙을 공유하더라도 플랫폼에 따라 구현은 달라질 수 있다.
