# 화면 흐름 맵

화면을 한 캔버스에 늘어놓고 **「어느 화면의 어느 버튼을 누르면 어느 화면으로 가는지」를 화살표로**, 그리고 그 버튼에 걸린 **정책 · 기획 메모를 화면 옆에** 붙인 지도다. 기획서를 화면 단위 · 버튼 단위로 펼쳐 본다.

## 정의

```text
[화면 A] ─(버튼 ③)→ [화면 B]
   │
   └ 메모 ③: 「…원문…」 (기획안 L412)
```

- **화면** — 실제 시안 수준으로 그린 화면. 회색 뼈대인 [[wireframe]] 과 다르다. 디자인을 입혀야 기획 검토자가 「이 화면이 맞다」를 판단할 수 있다
- **마커** — 화면 안 버튼 · 요소에 번호를 붙인다. 화살표와 메모가 이 번호에 걸린다
- **연결** — 출발 마커 → 도착 화면. 연결 없는 화면(고아)은 빠진 흐름이다
- **메모** — 정책 · 기획 메모 · 미정 질문을 나눠 둔다. 모두 **원천 문서의 줄**을 단다

## 데이터가 원본, 캔버스는 렌더 결과

화면 수십 개와 연결 · 메모 수백 개를 캔버스에서 손으로 관리하면, 고칠 때마다 여러 곳을 옮겨야 하고 검사도 할 수 없다. 그래서 원본을 데이터로 둔다.

| 원본 | 내용 |
|---|---|
| `screens.json` | 화면 id · 섹션 · 화면을 짜는 컴포넌트 |
| `edges.json` | 출발 화면 · 마커 → 도착 화면 · 종류 |
| `notes.json` | 화면 · 마커 · 종류(정책 · 메모 · 미정) · 원문 인용 · 출처 줄 |
| `layout.json` | 섹션 격자 위치 |

렌더러는 이 데이터를 읽어 캔버스를 다시 그린다. 노드 이름을 규약(`screen/<id>` · `edge/<from>→<to>` · `note/<id>` · `marker/<screen>/<no>`)으로 두면 아래 항목을 **기계로 셀 수 있다.**

- 고아 연결 0
- 출처 줄 없는 메모 0
- 원문과 다른 인용 0 → [[artifact-traceability]]
- 두 번 돌려도 노드 수가 같은지(멱등) → [[idempotency]]

멱등이면 섹션마다 따로 그리고 합칠 수 있다. 그래서 섹션별 병렬 작업이 된다.

## 경계와 오해

- **흐름 맵 ≠ 사이트맵** — 사이트맵은 메뉴 계층이다. 흐름 맵은 버튼 단위 전이와 그 규칙이다
- **캔버스를 직접 고치면 다음 렌더에 덮인다** — 공유 방에서 받은 의견은 데이터로 옮긴다. 캔버스는 보는 곳이다
- **배치는 데이터만큼만 좋다** — 섹션 격자로 놓으면 섹션을 넘는 연결이 긴 화살표로 얽힌다. 연결이 많은 화면끼리 가까이 두는 배치는 따로 풀 문제다
- **원천이 둘이면 먼저 정한다** — 기획안과 시안 결정이 다를 때 맵이 무엇을 시각화하는지(기획)에 따라 우선을 정하고, 다른 곳은 목록으로 남긴다
