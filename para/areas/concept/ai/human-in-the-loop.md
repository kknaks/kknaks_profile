# Human-in-the-loop (승인 대기와 재개)

**자동화를 다 하지 않고, 위험한 자리에서 멈춰 사람을 기다리는 것.** 멈췄다가 **다시 이어서** 갈 수 있어야 성립한다.

## 정의

```
지출 요청 ──▶ [금액 확인]
                ├ $500 미만 → 자동 승인 → 다음 단계
                └ $500 이상 → ⏸ 일시 정지(suspend)
                                    │
                          매니저 승인 ──▶ ▶ 재개(resume) → 완료
```

**기준 하나가 자동과 수동을 가른다.** 데모에서 $250 은 그대로 통과하고 $750 은 「Check Approval」 단계에서 멈춰 승인 뒤 이어졌다.

핵심은 **멈춤이 실패가 아니라는 것**이다 — 실행이 중단된 채 **기다리는 상태로 저장**되고, 승인이 오면 그 자리에서 다시 출발한다 → [[workflow-orchestration]]

사람의 답변을 이벤트로 받는 구현에서는 실행이 응답 이벤트를 기다리며 일시 정지되고, 일치하는 이벤트가 오면 그 데이터를 도구의 결과로 돌려받아 이어진다. 시작 요청과 응답에는 `ticketId` 같은 **상관관계 키**가 함께 있어야 여러 실행 중 어느 대기를 깨울지 구분할 수 있다. 대기에는 제한 시간을 두고, 만료되면 재요청·에스컬레이션·안전한 중단 중 하나로 전환한다.

기업 에이전트에서는 금액뿐 아니라 위험도, 외부 보고 여부, 안전 영향과 실행의 가역성을 기준으로 게이트를 둔다. 승인자는 에이전트가 사용한 데이터 출처, 적용 규칙, 결정과 예정된 실행을 확인할 수 있어야 하며, 승인자·시각·결과는 감사 기록으로 남아야 한다.

## 사용 예시

지원 에이전트가 복잡한 기술 문제를 만나 개발자에게 질문하는 흐름은 다음과 같다.

```
지원 티켓 생성(ticketId 포함)
  → 기술 지원 에이전트가 개발자 답변 요청
  → 실행을 저장하고 응답 이벤트 대기
  → Slack 등의 답변을 developer.response 이벤트로 변환
  → ticketId가 같은 대기를 찾아 재개
  → 답변을 도구 결과로 에이전트에 반환
```

이때 시작 이벤트와 응답 이벤트의 상관관계 키가 같아야 한다.

```json
{
  "name": "app/support.ticket.created",
  "data": { "ticketId": "ticket-123" }
}
```

```json
{
  "name": "developer.response",
  "data": {
    "ticketId": "ticket-123",
    "answer": "해당 고객 계정의 연결 로그를 먼저 확인하세요."
  }
}
```

## 왜 중요한가

**자동화의 범위를 「전부/전무」가 아니라 눈금으로 정하게 한다.** 위험이 낮은 대부분은 자동으로 흘리고, 드문 큰 건만 사람이 본다 — **사람의 시간을 어디에 쓸지**를 기준으로 표현한 것이다.

**그리고 그 기준이 곧 정책이다.** $500 이라는 숫자는 코드가 아니라 조직의 결정이고, 바뀌면 코드가 아니라 정책이 바뀐 것이다. 판단이 [[ai-agent]] 처럼 **비결정적인 주체**에게 맡겨질수록 이 게이트가 마지막 안전장치가 된다.

AI가 자료 수집·판단·실행을 연속으로 맡는 조직에서는 사람의 직무가 반복 처리자에서 예외 검토자와 의사결정자로 이동한다. 따라서 HITL은 단순한 승인 버튼이 아니라 자동화 이후의 책임과 직무를 배치하는 운영 구조다.

## 경계와 오해

- **사람이 병목이 된다** — 승인 대기가 쌓이면 처리량은 **승인자의 속도**로 수렴한다. 자동 승인 구간을 넉넉히 두는 이유가 그것이다
- **멈춘 상태를 어디에 두느냐가 진짜 문제다** — 프로세스 메모리에만 있으면 **재배포 한 번에 사라진다.** 며칠 걸릴 수 있는 승인을 견디려면 상태가 밖에 남아야 한다 → [[zero-downtime-deployment]] · [[distributed-session]]
- **응답을 실행과 정확히 연결해야 한다** — 상관관계 키가 없거나 값이 다르면 답변이 대기 중인 실행에 도달하지 않는다. 키의 충돌이나 임의 조작은 다른 실행을 잘못 재개할 수 있다
- **무기한 대기는 운영 정책이 아니다** — 제한 시간 안에 응답이 없을 때 재요청할지, 다른 사람에게 넘길지, 작업을 종료할지를 미리 정해야 한다
- **사람의 응답도 신뢰 경계 밖의 입력이다** — 외부 채널에서 들어온 답변은 권한과 형식을 검증한 뒤 에이전트나 후속 도구에 전달한다
- **판단 재료 없는 승인은 형식이 된다** — 무엇을 왜 승인하는지 보이지 않으면 전부 통과시킨다. **승인 화면이 곧 관측 화면**이어야 한다 → [[monitoring]]
- **모든 단계에 사람을 넣는 것은 HITL의 목적이 아니다** — 위험이 낮은 조회·초안 작성까지 일일이 승인하면 자동화의 처리량 이점이 사라진다. 위험 기반으로 게이트를 선택한다
- **기준을 우회하는 길이 없어야 한다** — 큰 건을 작게 쪼개면 통과하는 식이면 게이트가 무의미하다. 금액 임계값의 고전적인 허점이다
- **승인 이력이 남아야 한다** — 누가 언제 무엇을 통과시켰는지가 남지 않으면 사후에 책임도 원인도 못 짚는다 → [[application-event]]
- **되돌리기와는 다르다** — 트랜잭션의 롤백은 **한 뒤에 무르는 것**이고, 이 패턴은 **하기 전에 멈추는 것**이다. 이미 밖으로 나간 동작은 무를 수 없어서 앞에 세운다 → [[transaction]]
