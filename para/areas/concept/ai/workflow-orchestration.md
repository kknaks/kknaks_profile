# 워크플로우 오케스트레이션 (단계 체인)

**일련의 작업을 함수 호출이 아니라 「단계」로 선언하는 것.** 앞 단계의 결과가 다음 단계로 넘어가고, **그 이음매가 밖에서 보인다.**

## 정의

```
[함수 호출]   a() → b() → c()        흐름이 코드 안에만 있다
[워크플로우]  ┌──────┬──────┬──────┐
              │ 단계1 │ 단계2 │ 단계3 │  각 단계의 입력·출력·상태가 밖에 남는다
              └──────┴──────┴──────┘  ⏸ 멈췄다 이어갈 수 있다
```

VoltAgent 에서는 `createWorkflowChain` 으로 이 체인을 정의한다. **단계가 실행의 단위인 동시에 관측의 단위이고 중단점의 단위**라는 것이 핵심이다.

같은 코드를 그냥 함수로 이어 붙였다면 **어디까지 갔는지 물을 곳이 없다.**

## 왜 중요한가

**긴 작업은 중간에서 실패하고, 중간에서 기다린다.** 승인을 기다리거나(→ [[human-in-the-loop]]) 외부 응답이 늦거나 실패했을 때, **어느 단계였는지**를 아는 것과 모르는 것은 복구 비용이 다르다.

**그리고 흐름 자체가 데이터가 된다.** 타임라인에 단계별 입력·출력·비용이 남으므로, 디버깅이 「코드를 다시 읽는 일」이 아니라 **「기록을 보는 일」**이 된다 → [[monitoring]]

## 경계와 오해

- **체인은 순차 실행이다** — 단계를 이어 붙인다고 빨라지지 않는다. 겹쳐 돌릴 것은 **한 단계 안에서 병렬로** 처리해야 한다 → [[async-io]] · [[semaphore]]
- **단계를 잘게 쪼갤수록 공짜가 아니다** — 매 단계마다 상태를 저장하고 기록을 남기므로 **오버헤드가 붙는다.** 「멈출 수 있어야 하는 자리」와 「봐야 하는 자리」가 단계의 경계다
- **실패해도 자동으로 되돌아가지 않는다** — 3단계에서 실패했을 때 1·2단계가 이미 밖으로 낸 동작은 그대로 남는다. **되돌리는 단계를 직접 만들어야** 한다 → [[transaction]] 의 롤백과 다른 점이다
- **재시도는 부작용을 두 번 일으킬 수 있다** — 같은 단계를 다시 도는 것이 안전하려면 **여러 번 해도 결과가 같아야** 한다. 결제·발송처럼 그렇지 않은 단계는 따로 표시해 다뤄야 한다
- **오케스트레이션과 이벤트 기반은 다른 방향이다** — 한가운데서 순서를 쥐는 것과 각자 이벤트를 듣고 반응하는 것은 **책임의 위치가 반대**다. 흐름이 보이는 대신 중앙이 커진다 → [[message-broker]] · [[application-event]]
- **프레임워크에 갇힐 수 있다** — 단계 정의·중단·재개가 그 프레임워크의 방식이라, 옮길 때 흐름을 다시 짜게 된다
