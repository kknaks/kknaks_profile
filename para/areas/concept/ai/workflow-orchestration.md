# 워크플로우 오케스트레이션 (단계 체인)

**일련의 작업을 함수 호출이 아니라 「단계」로 선언하는 것.** 앞 단계의 결과가 다음 단계로 넘어가고, **그 이음매가 밖에서 보인다.**

## 정의

```
[함수 호출]   a() → b() → c()        흐름이 코드 안에만 있다
[워크플로우]  ┌──────┬──────┬──────┐
              │ 단계1 │ 단계2 │ 단계3 │  각 단계의 입력·출력·상태가 밖에 남는다
              └──────┴──────┴──────┘  ⏸ 멈췄다 이어갈 수 있다
```

VoltAgent 에서는 `createWorkflowChain` 으로 이 체인을 정의한다. Mastra에서는 각 단계의 입출력 스키마와 실행 로직을 `createStep()`으로 선언하고, `createWorkflow()`에 단계를 연결한 뒤 `.commit()`으로 실행 흐름을 확정한다. **단계가 실행의 단위인 동시에 타입 계약·관측·중단·복구의 단위**라는 것이 핵심이다.

같은 코드를 그냥 함수로 이어 붙였다면 **어디까지 갔는지 물을 곳이 없다.** 워크플로우 실행은 단계별 입력·출력과 상태를 남기며, 공유 상태가 필요하면 모든 단계의 입출력에 섞지 않고 별도의 상태 스키마로 관리할 수 있다.

실행 인터페이스는 최종 결과만 기다리는 방식과 진행 이벤트를 스트리밍하는 방식으로 나뉠 수 있다. Mastra의 실행 결과처럼 `success`·`failed`·`suspended`·`tripwire`·`paused` 상태를 구분하면, 호출자는 공통 실행 기록을 확인한 뒤 상태별 결과·오류·재개 데이터를 안전하게 처리할 수 있다.

중단 가능한 워크플로우는 특정 단계의 실행 상태를 스냅샷으로 영속화하고, 외부 입력이 도착하면 해당 단계와 상태를 복원해 계속 실행한다. 재개 입력과 중단 시 보존할 데이터에 스키마를 두면 프로세스 재시작과 배포를 넘어 입력 계약과 중단 당시의 맥락을 유지할 수 있다.

중단된 경로가 하나가 아닐 수 있으므로 실행 상태에는 중단된 단계나 중첩 워크플로우의 경로가 남아야 한다. 반복 실행의 특정 항목을 재개하려면 단계 경로뿐 아니라 반복 인덱스처럼 해당 실행을 식별하는 값도 필요하다.
단계를 선언으로 밀고 가면 **워크플로 자체가 데이터**가 된다. 실무 구현에서 관찰한 형태는 스테이지 그래프다 — 스테이지는 「재사용 조각(piece) 참조 + 파라미터」로, 전이는 「이 스테이지에서 이 신호가 오면 어디로」라는 엣지로 선언하고, 엔진 하나가 그 선언을 읽어 구동한다. 엣지 어휘는 유한 집합(on_trigger·on_approve·on_reject·on_decision(값)·on_event(이름)·on_all_done·on_timeout → go/loop/DONE/FAILED)이고 **값은 파라미터, 종류만 어휘**다 — 어휘가 느는 것은 전이의 의미 자체가 새로울 때뿐이다. 이렇게 하면 새 워크플로 추가가 오케스트레이터 코딩이 아니라 **선언 1개 작성 + 등록 1줄**이 되고, 2단계짜리와 8단계짜리(AI 산출 3회·게이트 3회·루프 포함)가 같은 어휘로 표현된다. 상태도 두 층으로 갈린다 — 게이트(승인 카드)의 FSM 은 고정이고, 워크플로 상태는 선언이 소유한다(새 상태 = 새 스테이지 선언, 코드 0).

전사 업무에서는 각 단계를 품질·생산·SCM·재무 같은 전문 [[ai-agent]]가 담당할 수 있다. 에이전트들은 표준화된 이벤트와 작업 상태를 주고받고, 오케스트레이터는 순서·분기·승인·시간 초과·재시도·보상 작업을 관리한다.

## 왜 중요한가

**긴 작업은 중간에서 실패하고, 중간에서 기다린다.** 승인을 기다리거나(→ [[human-in-the-loop]]) 외부 응답이 늦거나 실패했을 때, **어느 단계였는지**를 아는 것과 모르는 것은 복구 비용이 다르다. 중단된 실행을 저장한 자리에서 재개하거나 마지막 활성 단계부터 재시작할 수 있으면 처음부터 되풀이할 필요가 없다.

**그리고 흐름 자체가 데이터가 된다.** 타임라인에 단계별 입력·출력·비용이 남으므로, 디버깅이 「코드를 다시 읽는 일」이 아니라 **「기록을 보는 일」**이 된다 → [[monitoring]]. 진행 이벤트를 스트리밍하면 긴 실행이 끝나기 전에도 상태 변화를 관찰하거나 단계 완료에 반응할 수 있다.

상태를 외부 저장소에 지속하면 워크플로우의 수명이 애플리케이션 프로세스의 수명과 분리된다. 승인이나 콜백을 오래 기다리는 실행도 배포와 재시작 이후 저장된 `runId`로 복구할 수 있다.

ERP·MES·QMS처럼 서로 다른 시스템을 통과하는 업무는 개별 자동화만으로 끝까지 이어지지 않는다. 오케스트레이션은 품질 이상 탐지에서 생산 조정, 공급망 대응, 경영 보고까지 가치사슬을 하나의 추적 가능한 실행으로 묶는다. 이때 각 단계가 같은 기업 데이터를 해석하려면 [[data-fabric]]이 필요하다.

## 경계와 오해

- **체인은 순차 실행이다** — 단계를 이어 붙인다고 빨라지지 않는다. 겹쳐 돌릴 것은 **한 단계 안에서 병렬로** 처리해야 한다 → [[async-io]] · [[semaphore]]
- **단계를 잘게 쪼갤수록 공짜가 아니다** — 매 단계마다 상태를 저장하고 기록을 남기므로 **오버헤드가 붙는다.** 「멈출 수 있어야 하는 자리」와 「봐야 하는 자리」가 단계의 경계다
- **중단과 시간 대기는 같은 상태가 아니다** — 외부 입력을 기다리는 단계 중단은 재개 데이터와 대상 경로가 필요한 `suspended` 상태지만, 정해진 시각까지의 대기는 시간이 지나면 실행되는 워크플로우 수준의 `waiting` 상태다
- **중단 상태의 영속성은 저장소에 달려 있다** — 메모리에만 상태를 두면 프로세스 재시작과 배포를 넘는 재개를 보장할 수 없다
- **재개 대상을 생략할 수 있는 것은 중단 단계가 하나일 때뿐이다** — 여러 단계·중첩 워크플로우·반복 항목이 중단될 수 있으면 경로와 반복 인덱스를 명시해야 한다
- **실패해도 자동으로 되돌아가지 않는다** — 3단계에서 실패했을 때 1·2단계가 이미 밖으로 낸 동작은 그대로 남는다. **되돌리는 단계를 직접 만들어야** 한다 → [[transaction]] 의 롤백과 다른 점이다
- **재시작과 재시도는 부작용을 두 번 일으킬 수 있다** — 마지막 활성 단계부터 이어서 실행해도 그 단계가 외부 시스템에 일부 동작을 반영했을 수 있다. 같은 단계를 다시 도는 것이 안전하려면 **여러 번 해도 결과가 같아야** 한다. 발주·전표·설비 제어 단계는 요청 ID와 멱등성 키로 중복 실행을 막아야 한다
- **에이전트 협업은 자유로운 대화가 아니다** — 역할, 입력·출력 스키마, 상태 전이와 오류 계약을 정하지 않으면 책임과 복구 지점을 알 수 없다
- **공유 상태는 명시적 데이터 흐름을 대신하지 않는다** — 진행률·누적 결과·공통 설정처럼 여러 단계가 실제로 공유하는 값에 한정하지 않으면 단계 사이 의존성이 숨는다
- **스트리밍과 최종 결과 반환은 목적이 다르다** — 진행 관찰이나 단계별 반응이 필요하지 않다면 모든 이벤트를 소비하는 대신 최종 결과만 기다리는 실행이 단순하다
- **재사용 조각은 다음 단계를 몰라야 부품이다** — 단계 기계가 「완료했으니 다음은 X」까지 알면 그 순간 특정 워크플로에 박힌다. 조각은 신호만 반환하고 행선지는 선언의 엣지가 정해야, 전이 판정이 엣지표 한 곳에만 존재하고 조각이 어느 워크플로에나 꽂힌다. 실측 교훈: 조각을 라이브러리에 세워 두는 것만으로는 계약이 검증되지 않는다 — **두 번째 소비자가 붙기 전까지 그 조각은 미검증**이다
- **선언 밖 전이는 조용히 무시하지 말고 거부해야 한다** — 매칭되는 엣지가 없을 때 fallback 으로 흘리면 상태가 자유 문자열이던 시절과 같아진다. 명시 예외로 죽여야 선언이 곧 검증기가 된다
- **오케스트레이션과 이벤트 기반은 다른 방향이다** — 한가운데서 순서를 쥐는 것과 각자 이벤트를 듣고 반응하는 것은 **책임의 위치가 반대**다. 흐름이 보이는 대신 중앙이 커진다 → [[message-broker]] · [[application-event]]
- **프레임워크에 갇힐 수 있다** — 단계 정의·상태 저장·중단·재개·재시작이 그 프레임워크의 방식이라, 옮길 때 흐름과 복구 계약을 다시 짜게 된다
