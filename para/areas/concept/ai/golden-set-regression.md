# 골든셋 회귀 검증 (Golden-set Regression)

사람이 채점한 기준 사례 묶음(골든셋)을 고정해 두고, **무엇인가 바뀔 때마다 같은 묶음을 다시 돌려** 품질이 떨어졌는지 판정하는 것이다. AI 제품에서 「바뀌는 것」은 우리 코드만이 아니라 모델과 입력 분포까지 포함한다.

## 정의

골든셋은 [[llm-as-judge]] 절차의 2단계 산출물이다 — 루브릭으로 사람이 채점한 수십~수백 건. 이 묶음이 이후 모든 비교의 기준점이 된다.

돌려야 하는 시점이 셋이다.

| 바뀌는 것 | 왜 다시 돌리나 |
| --- | --- |
| 모델 버전 | 같은 프롬프트가 새 모델에서 다르게 동작한다 |
| 프롬프트 · 컨텍스트 구성 | 고친 것이 개선인지 판정할 다른 수단이 없다 |
| 검색 인덱스 · 임베딩 모델 | 근거가 달라지면 답이 달라진다 |

모델 교체의 절차는 **버전 고정(pin) → 골든셋 회귀 → 교체**다. 검증 없이 바꾸면 품질 변화를 확인할 방법이 없고, 제공사의 단종 일정이 우리 일정과 무관하게 정해지므로 이 절차는 미리 서 있어야 한다([[silent-model-degradation]]).

## 왜 중요한가

**평가·모니터링 자체가 인프라다.** 골든셋, 자동 채점, 프롬프트 버전 관리, 로그 수집은 제품 기능이 아니라서 미뤄지기 쉬운데, 없으면 모델이나 인프라 교체의 영향을 판단할 수 없다. 마일스톤에서 개선(4단계)보다 평가 체계(3단계)가 앞서는 이유다.

## 경계와 오해

- **골든셋 통과 ≠ 제품 정상** — 골든셋에 없는 입력은 안 보인다. 실패 사례를 계속 회수해 넣어야 한다.
- **회귀 검증 ≠ 단위 테스트** — 통과/실패가 아니라 점수의 이동을 본다. 확률 모델이라 완전 일치를 기대할 수 없다.
- **모델 교체 ≠ 코드 변경 없음** — 코드를 안 고쳐도 제품 동작이 바뀐다.
- **골든셋 고정 ≠ 영구 고정** — 입력 분포가 움직이면 기준 묶음도 갱신해야 한다.
