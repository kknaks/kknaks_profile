# 아키텍처 드리프트 방지

아키텍처 드리프트 방지는 개별 변경이 기능적으로 정상이어도 코드베이스 전체를 팀이 합의한 설계 방향에서 멀어지게 하는 현상을 막는 규율이다. AI 생성 코드가 기존 아키텍처 결정을 알지 못해 만드는 의미적 위반을 생성 전후에 통제한다.

## 정의

아키텍처 드리프트는 코드가 컴파일되고 테스트를 통과하더라도 시스템이 합의한 경계와 경로를 벗어날 때 발생한다. 이를 방지하려면 다음 연결이 유지되어야 한다.

1. 현재 유효한 아키텍처 결정을 ADR처럼 추적 가능한 형태로 기록한다.
2. 변경과 관련된 결정을 코드 생성 전에 찾아 에이전트의 문맥에 넣는다.
3. 생성된 코드가 결정을 위반하는지 CI에서 검사한다.
4. 경고나 차단을 일으킨 규칙과 코드 증거를 사람이 재현할 수 있게 남긴다.

예를 들어 고객 데이터 쓰기는 반드시 고객 서비스 API를 거쳐야 한다는 ADR이 있다면, 데이터베이스에 직접 쓰는 새 엔드포인트는 테스트 성공 여부와 무관하게 아키텍처 드리프트다. API에 있던 감사 로그 훅을 우회하기 때문이다.

## 왜 중요한가

AI 에이전트는 사람이 한 변경을 검토하는 속도보다 빠르게 여러 구현과 PR을 만들 수 있다. 기존 결정을 생성 문맥과 검증 경로에 연결하지 않으면 기능적으로 그럴듯한 위반이 반복해서 저장소에 들어오고, 뒤늦은 재작성·데이터 보정·감사 대응 비용으로 돌아온다.

아키텍처 드리프트 방지는 모델의 코드 작성 능력과 별개로 조직의 설계 기억을 보존한다. 더 강력한 모델도 전달받지 못한 결정을 따를 수 없으므로, 예방의 핵심은 모델 교체가 아니라 주변 시스템의 결정 전달과 집행이다.

## 경계와 오해

- **아키텍처 드리프트 ≠ 문법 오류** — 코드는 정상적으로 실행될 수 있으며 위반 대상은 팀이 합의한 의미적 경계다.
- **아키텍처 드리프트 방지 ≠ 코드 스타일 통일** — 포매터와 린터가 다루는 표기보다 서비스 경계, 데이터 접근 경로 같은 설계 결정을 다룬다.
- **두 번째 AI 리뷰 ≠ 드리프트 방지** — 생성 에이전트와 리뷰 모델이 같은 결정 기록을 보지 못하면 동일한 사각지대를 공유한다.
- **인간 리뷰 ≠ 유일한 집행 수단** — 리뷰어가 조직의 모든 결정을 기억한다는 가정은 코드 생성량이 커질수록 유지하기 어렵다.
