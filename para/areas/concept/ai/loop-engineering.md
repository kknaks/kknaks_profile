# 루프 엔지니어링 (Loop Engineering)

**사람이 에이전트의 매 실행을 직접 지시하는 대신, 목표를 달성할 때까지 작업 발견·계획·실행·검증을 반복하는 외부 제어 시스템을 설계하는 방식이다.** 핵심은 반복 자체가 아니라 성공 조건과 종료 조건을 기계가 판정할 수 있게 만드는 데 있다.

## 정의

루프 엔지니어링은 한 번의 [[ai-agent]] 실행을 감싸는 상위 제어 구조다. 프롬프트, 문맥, 도구와 실행 규칙이 단일 실행의 하네스를 이룬다면, 루프는 그 하네스를 반복 호출하면서 이전 결과를 다음 실행의 입력으로 전달한다.

기본 흐름은 다음과 같다.

1. **발견:** 테스트 실패, 이슈 큐, 모니터링 경보 등에서 수행할 작업을 찾는다.
2. **계획:** 변경 대상, 제약 조건과 검증 순서를 정한다.
3. **실행:** 격리된 작업 공간에서 에이전트가 결과물을 만든다.
4. **검증:** 테스트, 정적 분석, 명세 비교 또는 별도 리뷰 에이전트가 성공 여부를 판단한다.
5. **기록과 반복:** 결과와 실패 원인을 외부 메모리에 남기고, 성공하거나 한도에 도달할 때까지 다시 실행한다.

이 구조는 작업물을 만드는 **생성기**와 품질을 판정하는 **검증기**의 결합으로 볼 수 있다. 생성기는 모델이고, 검증기는 테스트·정적 분석·브라우저 검사·별도 리뷰 모델 등이 될 수 있다. 작성 모델의 완료 선언은 검증 결과가 아니므로 가능하면 생성자와 검증자를 분리한다.

안정적인 루프에는 다음 기반이 필요하다.

- 일정이나 이벤트로 실행을 시작하는 자동화
- 병렬 에이전트의 변경을 격리하는 브랜치와 Git worktree
- 프로젝트 규칙과 실행 절차를 재사용하는 스킬
- 이슈 추적기·데이터베이스 등 외부 시스템에 접근하는 커넥터
- 작성·조사·검증 역할을 나누는 하위 에이전트
- 실행 사이에 진행 상태와 학습을 보존하는 외부 메모리

## 사용 예시

다음은 테스트가 통과할 때까지 수정 에이전트를 최대 여섯 번 호출하는 폐쇄 루프다.

```bash
#!/usr/bin/env bash
set -euo pipefail

max_rounds=6
log_file="test-output.log"

for ((round = 1; round <= max_rounds; round++)); do
  if npm test >"$log_file" 2>&1; then
    echo "Verification passed."
    exit 0
  fi

  ./agent-fix \
    --input "$log_file" \
    --constraint "Do not change public APIs"
done

echo "Verification did not pass within ${max_rounds} rounds." >&2
exit 1
```

`./agent-fix`가 생성기이고 `npm test`가 검증기다. 테스트가 성공하면 루프를 끝내고, 계속 실패하면 정해진 횟수에서 중단한다. 실제 운영에서는 별도 worktree에서 변경하고 린트·타입 검사·보안 검사도 성공 조건에 포함하며, 반복마다 diff와 비용을 기록한다.

## 왜 중요한가

사람이 매 출력 뒤에 다음 프롬프트를 작성하면 사람이 곧 반복문의 제어 흐름이 된다. 루프로 목표, 제약과 판정 규칙을 외부화하면 사람은 개별 실행을 조작하는 운영자에서 반복 시스템을 설계하고 예외를 검토하는 역할로 이동한다.

반복 호출이 저렴해질수록 결과를 더 많이 생성하는 능력보다 **무엇이 좋은 결과인지 판정하는 능력**이 병목이 된다. “더 좋게 만들어라” 같은 목표는 방향을 제공하지 못하지만, 테스트 통과·공개 API 유지·접근성 점수처럼 관찰 가능한 조건은 반복을 실제 진전으로 바꾼다. 검증 규칙은 루프의 보상 함수 역할을 하며, 품질 하한과 종료 시점을 함께 결정한다.

자동화된 검증과 실행 증거가 있으면 테스트 복구, 정형 변환, 의존성 갱신 같은 작업을 예측 가능한 비용 안에서 반복할 수 있다. 반대로 검증할 수 없는 목표를 자동화하면 많은 토큰과 변경을 만들면서도 개선 여부를 알 수 없다.

## 경계와 오해

- **루프 엔지니어링 ≠ 단순 반복 프롬프트** — 이전 출력을 다시 모델에 넣는 것만으로는 부족하다. 성공 조건, 종료 조건, 상태 기록과 실패 시 처리 방식이 있어야 제어 가능한 루프가 된다.
- **자동 반복 ≠ 자기 개선 보장** — 약한 검증기는 서로 다른 결과만 계속 만들게 할 수 있다. 반복 횟수는 개선의 증거가 아니다.
- **에이전트의 완료 선언 ≠ 검증** — 완료는 주장이고, 테스트 로그·빌드 산출물·diff·브라우저 기록처럼 다시 확인할 수 있는 증거가 필요하다.
- **작성자 리뷰 ≠ 독립 검증** — 같은 모델과 문맥으로 자신의 결과를 평가하면 기존 판단을 정당화하기 쉽다. 결정적 검사를 우선하고 필요하면 다른 지침과 문맥을 가진 리뷰 에이전트를 둔다.
- **폐쇄 루프 ≠ 개방 루프** — 폐쇄 루프는 성공 조건을 미리 고정해 예측하기 쉽고, 개방 루프는 탐색 여지가 크지만 비용과 품질 편차도 크다. 탐색이 필요하면 테스트와 정책을 품질 하한으로 둔다.
- **높은 자율성 ≠ 더 나은 설계** — 상시 실행 에이전트는 장애 범위와 감독 비용도 키운다. 목적을 달성할 수 있는 가장 낮은 자율성부터 선택한다.
- **외부 메모리 ≠ 대화 문맥** — 대화는 실행 사이의 영구 상태가 아니다. 완료 항목, 실패 원인과 다음 작업은 저장소·이슈 보드·데이터베이스 등에 남긴다.
- **자동화 ≠ 인간 책임 제거** — 이해하지 못한 변경을 계속 승인하면 시스템 이해가 쇠퇴한다. 고위험 동작에는 [[human-in-the-loop]]을 두고 인간이 결과와 검증 근거를 계속 읽어야 한다.
