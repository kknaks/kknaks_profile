# 추론 지연 지표 (TTFT · TPOT)

LLM 응답의 지연을 **한 숫자로 재지 않고 둘로 쪼개는** 관점이다. 순차 생성이라 「첫 글자까지」와 「그 뒤 한 글자당」이 서로 다른 원인에서 나오기 때문이다.

## 정의

| 지표 | 뜻 |
| --- | --- |
| TTFT (time to first token) | 첫 글자가 나오기까지. 체감 속도를 좌우한다 |
| TPOT (time per output token) | 토큰 하나당 시간. 긴 답의 속도 |
| 전체 지연 시간 | 요청부터 완료까지 |
| 처리량 | 초당·분당 처리 요청 수 |
| 요청당 비용 | 입력·출력 토큰 × 단가 |
| 가용성 · 에러율 | 외부 API 장애 · 타임아웃 · 스키마 실패 |

대략 `전체 ≈ TTFT + TPOT × 출력 토큰 수`로 읽힌다. 그래서 개선의 처방이 갈린다 — TTFT 가 나쁘면 프롬프트 길이·검색 단계·모델 로딩을 보고, TPOT 가 나쁘면 모델 크기·서빙 구성을 본다. 둘을 합친 한 숫자만 보면 어느 쪽인지 모른다.

스트리밍은 TTFT 만 바꾸고 전체 시간은 그대로 둔다([[inference-optimization]]).

## 왜 중요한가

**기술 지표를 사업 지표와 연결하는 자리**다. 「지연이 2초에서 1초가 됐다」만으로는 투자 효과를 판단할 수 없고, 「1초가 되면 이탈이 몇 % 준다」까지 이어야 판단이 선다([[launch-criteria]]).

반응형과 선제형에서 요구가 완전히 다르다는 점도 여기서 갈린다. 사용자가 화면 앞에서 기다리는 반응형은 응답 속도가 곧 품질이고, 미리 만들어 두는 선제형은 배치로 느리게 돌려도 된다([[ai-role-taxonomy]]).

## 경계와 오해

- **전체 지연 하나 ≠ 충분한 측정** — 원인이 둘로 갈리므로 쪼개 재야 처방이 나온다.
- **TTFT 개선 ≠ 총 시간 단축** — 스트리밍은 체감만 바꾼다.
- **처리량 ↑ ≠ 지연 ↓** — 배칭은 둘을 맞바꾼다.
- **평균 ≠ 사용자 경험** — 꼬리 지연(p95·p99)이 체감을 만든다.
