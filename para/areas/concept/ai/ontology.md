# 온톨로지 (Ontology)

온톨로지는 특정 영역의 대상과 개념, 속성, 관계 및 제약을 명시적으로 표현하는 의미 모델이다. 업무 시스템에서는 여러 데이터가 무엇을 뜻하는지 공유하는 기반이 되며, 여기에 상태 변화·판단 규칙·실행 절차를 연결하면 운영 의사 결정을 지원할 수 있다.

## 정의

### 의미를 구성하는 요소

- **대상과 개념** — 배치·설비·검사처럼 업무에서 구별해야 하는 유형과 개별 대상을 정한다.
- **속성** — 불량률·검사 시각·설비 상태처럼 대상의 특징을 표현한다.
- **관계** — 배치가 어떤 설비에서 생산되고 어떤 검사를 받았는지 연결한다.
- **제약과 의미** — 어떤 검사가 해당 배치에 유효한지, ‘검사 완료’가 어떤 조건을 뜻하는지 명시한다.

이 구조를 만들려면 용어에 대한 합의가 필요하다. 영업팀이 말하는 ‘출하 가능’과 품질팀이 말하는 ‘출하 가능’이 다르면 단어가 같아도 동일한 상태로 취급할 수 없다. 현업은 의미와 예외를 설명하고, 기술 담당자는 구조로 표현하며, 권한 있는 업무 책임자는 충돌하는 정책을 조정한다.

### 운영으로 확장하는 세 계층

출처는 동적 온톨로지를 다음 세 계층으로 설명한다. 이는 해당 발표의 운영 설명 틀이며 모든 온톨로지가 갖춰야 하는 보편적인 제품 명세는 아니다.

| 계층 | 역할 | 출하 판단 예시 |
|---|---|---|
| 시멘틱 | 대상과 의미를 정의한다 | 배치·설비·검사와 관계를 정의한다 |
| 키네틱 | 현재 상태와 행동을 연결한다 | 검사 결과에 따라 승인 요청 또는 보류를 만든다 |
| 다이나믹 | 행동의 결과를 평가하고 기준을 개선한다 | 반품·재검사 결과로 기존 판단을 평가한다 |

운영 시스템으로 구현할 때는 의미 모델 외에도 데이터 연결, 시간 조건, 권한, 실행 기록, 변경 관리가 필요하다. 순간값과 기간 집계값, 사건 발생 시각과 수집 시각을 구분해야 같은 데이터를 일관되게 해석할 수 있다.

### 의사 결정에서 역으로 설계하기

1. 손실이나 위험이 큰 의사 결정과 책임자를 정한다.
2. 승인·보류·추가 검토처럼 가능한 행동을 구분한다.
3. 판단에 필요한 객체·관계·속성과 시간 조건을 찾는다.
4. 원천 시스템의 식별자·단위·결측 처리 기준을 맞춘다.
5. 판단 결과를 승인 및 실행 절차에 연결한다.
6. 결과와 당시 기준을 기록하고 변경안을 검증한다.

LLM은 인터뷰 내용을 구조화하거나 객체·관계 후보를 제안할 수 있다. 초안의 타당성은 현업 검토와 실제 사례 평가로 확인한다.

## 사용 예시

화장품 출하 판단에서는 `배치 → 검사`, `배치 → 설비`, `배치 → 원료 로트` 관계를 만든다. 검사 결과가 존재하는지, 해당 배치의 검사인지, 유효 기간 안에 있는지 확인한 뒤 불량률과 설비 상태를 평가한다.

출처의 학습용 코드에서 배치 `B-101`은 최근 검사와 예시 불량률 기준을 충족하므로 `READY_FOR_APPROVAL`이 된다. 검사 데이터가 없는 `B-102`는 `REVIEW`가 된다. 추천이 생성되어도 실제 출하는 실행되지 않으며, 품질 책임자의 승인과 실행 상태를 별도로 관리한다. 이는 의미 모델이 판단과 실행으로 이어지는 작은 예시이지 완전한 온톨로지 구현은 아니다.

가상의 식당 사례에서는 고객 방문·직원 배치·서빙·대기 시간·매출을 연결한다. ‘숙련 직원 부족이 대기 시간을 늘렸다’는 설명은 검증할 가설이다. 관계를 기록한 것만으로 직원 추가 배치의 매출 개선 효과가 입증되지는 않는다.

## 왜 중요한가

같은 용어를 다르게 쓰는 시스템을 연결하면 데이터가 모여도 판단이 충돌한다. 의미와 관계를 명시하면 서로 다른 시스템의 값을 어떤 업무 대상으로 해석해야 하는지 확인할 수 있다.

의사 결정에서 역으로 설계하면 수집 자체가 목적이 되는 일을 줄이고, 필요한데 없는 데이터와 합의되지 않은 기준을 드러낸다. 실행 결과까지 연결하면 실패가 데이터 오류인지 정책 오류인지 검토할 근거도 남는다.

## 경계와 오해

- **온톨로지 ≠ 그래프 DB** — 온톨로지는 의미를 표현하는 모델이고 그래프 DB는 저장·탐색 수단이다. 저장 기술만 도입해도 업무 정의와 실행 절차가 완성되는 것은 아니다.
- **온톨로지 ≠ 관계형 스키마의 이름 변경** — 테이블을 객체로 부르는 것만으로 업무 의미·제약·부서 간 합의가 생기지 않는다.
- **온톨로지 ≠ 결정론적 규칙 엔진** — 의미 모델과 판단 실행 방식은 구분해야 한다. 규칙을 연결하더라도 잘못된 기준은 잘못된 판단을 반복한다.
- **시간 순서와 관계 ≠ 인과관계의 증명** — 원인 후보를 좁힐 수 있지만 교란 요인 검토와 별도의 검증이 필요하다.
- **온톨로지 ≠ LLM의 필수 구성 요소 또는 환각 제거 장치** — LLM 없이도 의미 모델을 구축할 수 있고, LLM을 결합해도 출력의 정확성이 자동으로 보장되지는 않는다.
- **운영체제 비유 ≠ 모든 운영 기능의 내장** — 판단·권한·실행·피드백은 실제 시스템에서 구현하고 검증해야 한다.
