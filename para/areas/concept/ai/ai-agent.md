# AI 에이전트와 툴 (Tool)

**모델에게 말 대신 손을 쥐여 주는 것.** 텍스트를 만드는 데서 그치지 않고 **실제 동작을 부르는** 순간부터 에이전트가 된다.

## 정의

```
[모델만]      질문 ──▶ 모델 ──▶ 그럴듯한 문장
[에이전트]    질문 ──▶ 모델 ──▶ "날씨 툴을 불러야겠다"
                        ▲            │
                        └── 결과 ────┘  ──▶ 답변
```

**툴**은 모델이 부를 수 있게 등록해 둔 함수다 — 날씨 조회, DB 검색, 이메일 발송처럼 **텍스트 생성 밖의 일**을 여기서 한다.

부르는 주체가 코드가 아니라 **모델**이라는 점이 보통 함수 호출과 다르다. 언제 부를지, 무엇을 넣을지를 모델이 정한다.

기업 업무에서 에이전트는 목표를 받아 데이터를 조회하고 판단한 뒤 ERP·MES·QMS 같은 시스템을 조작하고 결과를 보고하는 **소프트웨어 업무 수행자**다. 조직이 이를 공식적인 수행자로 배치하려면 역할마다 입력·출력·권한·책임 범위를 제한하고, 품질·생산·SCM·재무 같은 전문 에이전트들이 [[workflow-orchestration]]을 통해 협업하게 해야 한다.

## 왜 중요한가

**툴이 없으면 아무것도 바뀌지 않는다.** 아무리 좋은 답을 만들어도 시스템 밖의 상태는 그대로다 — **경계를 넘는 지점이 툴 하나뿐**이라, 이 지점이 곧 권한의 경계이자 위험의 경계가 된다 → [[human-in-the-loop]]

**그리고 흐름이 코드에 안 적혀 있다.** 어느 툴이 언제 불렸는지는 **실행해 봐야** 알고, 같은 입력이 같은 순서를 보장하지도 않는다. 그래서 로그·트레이스가 부가 기능이 아니라 **기본 장비**가 된다 → [[monitoring]]

기업 에이전트의 성능은 모델만으로 결정되지 않는다. 여러 시스템의 데이터가 일관된 의미와 접근 규칙으로 제공되고 업무의 암묵지가 판단 기준과 예외 규칙으로 문서화되어야 한다 → [[data-fabric]]

## 경계와 오해

- **에이전트는 프레임워크가 아니다** — CLI 로 프로젝트를 만들어 주는 것과 에이전트가 무엇인지는 다른 층이다. 프레임워크는 **등록·호출·관측을 묶어 주는** 도구일 뿐이고, 갈아타도 개념은 그대로다
- **개인의 코파일럿 사용이 곧 조직의 에이전트 도입은 아니다** — 개인이 AI에 일을 다시 맡기는 구조에서는 업무 책임과 흐름이 여전히 사람에게 있다. 조직 도입은 업무 자체를 에이전트에게 할당하고 권한·산출물·검토자를 공식화한다
- **툴은 검증 없는 입구다** — 인자를 정하는 것이 모델이므로 **사용자 입력이 그대로 흘러 들어온 것과 같게** 다뤄야 한다. 툴 안에서 권한과 값을 다시 검사하는 것이 원칙이다 → [[sql-injection]] 과 같은 부류의 위험이다
- **비결정적이라 테스트가 다르다** — 같은 입력에 같은 출력이 안 나오므로 **단언으로 고정하기 어렵다.** 기록을 남겨 사후에 비교하는 쪽이 현실적이다
- **툴을 많이 붙일수록 고르기가 어려워진다** — 후보가 늘면 엉뚱한 것을 부르고, 설명이 모호하면 더 그렇다. **툴 설명이 곧 인터페이스 문서**다 → [[api-documentation]]
- **범용 에이전트 하나에 전사 권한을 몰아주지 않는다** — 역할별 전문 에이전트에 최소 권한을 주고, 되돌리기 어려운 실행은 [[human-in-the-loop]] 뒤에 둔다
- **비용이 호출 수에 붙는다** — 툴을 부르고 결과를 다시 넣는 왕복마다 토큰이 든다. 「몇 번 도는가」가 곧 요금이다
- **벤더 데모와 전사 운영은 검증 범위가 다르다** — 단일 에이전트의 성공 경로만으로 멀티에이전트 협업, 데이터 품질, 장애 복구와 사업 성과까지 입증되지는 않는다
