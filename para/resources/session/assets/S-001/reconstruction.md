```text
                                                                        ×10+
```

**발표자**

> 「저희는 공급망 데이터를 먼저 테이블을 **KPI 뷰로 만들었습니다.** 좀 더 상세히 말씀드리면
> 공급망 관련된 **디멘션이 많고 기존에 마트별로 기준이 다르기 때문에 일관된 기준을 가진 KPI

>
> 「그럼 이 KPI 뷰는 **판매 영역, 재고 영역** 이렇게 나뉠 수 있겠죠. 그러면 이 KPI에 **전월
> 대비 변화량, 변화율** 이런 값들을 붙이게 됩니다.」

여기서 첫 번째로 가린 대목이 나온다.

> 「좀 **상세 KPI 는 제가 못 보여드리(고) 나중에 부탁드리겠습니다. 저희 회사 정책상.**」

대신 예시 하나를 들었다.

> 「예를 들어서 재고에 **DOS** 라고 있어요. **Days of Supply** 라고 해서 재고 수준이 있습니다.
> **재고가 며칠 동안 버틸 수 있느냐**, 그 일수를 나타낸 지표입니다.」
>
> 「그럼 이 지표에, 이 재고에 있어서 **전월 대비 얼마나 변했어? 변화량, 변화율**, 그리고
> 거기 더해서 **이상 탐지를 위해서** 이 재고 DOS 가 **양호한지, 주의 수준인지, 경고
> 수준인지.** 예를 들면 **30% 밑이면 양호해.** 이런 식으로 저희가 기준을 정해서 붙여줬습니다.」

## 12 · CoCo 스킬로 KPI 인과관계 구성

![CoCo (Cortex Code) 스킬로 KPI 인과관계 구성 — 상단 ontology-stack-builder 의 P1~P7 단계(P3·P7 에 「✓ 사용자 승인」), 하단 5-Layer 스택 L1~L5 와 인과관계 Ontology 그래프](12-coco-ontology-stack-builder.webp)

**슬라이드**

```text
ontology-stack-builder
 P1 입력 수집 → P2 분석·제안 → P3 시각화·확인 → P4 배포
 → P5 Semantic View → P6 Cortex Agent → P7 E2E 검증
                    ✓ 사용자 승인 (P3)                ✓ 사용자 승인 (P7)

5-Layer 스택
 L1  물리 저장          NODE / EDGE
 L2  온톨로지 메타데이터   ONT_*
 L3  자동생성 추상 뷰     V_ONT_*     →  [인과관계 Ontology 그래프]
 L4  Semantic Model     의미 계층
 L5  Cortex Agent       대화형 활용
```

`P3` 와 `P7` 두 칸만 짙게 칠해져 있고 그 아래에 각각 「✓ 사용자 승인」이 붙어 있다.
`L3` 왼쪽에 화살표 표시가 있다.

**발표자**

> 「이렇게 준비된 KPI 를 가지고 **코코에게 던집니다.** 코코에게 그대로 주면 **온톨로지 스택
> 빌더라는 스킬**을 통해서 코코가 위와 같이 **7단계를 거치고 자동으로 5레이어의 스택을 만드는
> 온톨로지를 만들어주는데요.**」

여기서 「자동」에 단서를 달았다. **다만 말한 단계 번호가 슬라이드와 다르다.**

> 「지난번에도 자동이라고 말씀드렸지만 사실은 **세 번째 단계, 6번째 단계는 사용자가 확인하고
> 승인을 해줘야 합니다.**」

> ⚠️ **슬라이드에는 `P3` 와 `P7(E2E 검증)` 에 승인 표시가 붙어 있다.** `P6` 는 `Cortex Agent`
> 다. 말과 슬라이드가 어긋난 자리다.

그리고 더 중요한 것을 짚었다.

> 「**더 중요한 것은 첫 두 단계입니다.** 저 첫 번째 단계에 **어떤 데이터를 쓸지** — 저희 같은
> 경우는 공급망 데이터겠죠. 공급망 데이터를 저희가 멋지게 **KPI 로 만들어서 잘 제공해 줘야**
> 됩니다.」
>
> 「그리고 두 번째, 그 데이터 갖고 **무슨 분석을 하고 무슨 목표를 갖고 뭘 원하는지를 명확히
> 전달**해야 합니다. 저희는 **공급망 현업과 협의해서** 공급망에서 **어떤 시나리오들이
> 벌어지는지 듣고** 그 내용을 전달했습니다.」

## 13 · 인과관계 기반의 Ontology — Meta

![인과관계 기반의 Ontology — 왼쪽에 「인과관계 Meta」 블록만 있고 KPI 인과 세 줄이 나열된 상태](13-causal-ontology-meta.webp)

**슬라이드**

```text
인과관계 Meta
  KPI
   생산↑  ─(+)→  재고↑
   재고↑  ─(−)→  순매출↓
   재고↑  ─(+)→  부진재고↑
   ⋮
```

**발표자**

> 「여기서만 세 가지 항목이 있어요. **메타, 노드, 엣지.** 쉽죠? 메타, 노드, 엣지.」
>
> 「메타는 우선 **인과관계 메타**입니다. 예를 들어 **생산 KPI 가 올라간다. 그러면 재고 KPI 가

> 수 있습니다.**」
>
> 「예를 들어 **재고가 쌓인다는 KPI. 그러면 순매출은 떨어진다**는 이런 **네거티브 관계**도
> 메타로 정해놓습니다. 또한 재고가 쌓인다는 KPI, 그럼 **부진재고**라는 KPI 를 저희가 예를 들어
> 정했어요. 그럼 이게 올라온다는 관계도 정해놓습니다. 그리고 **이 관계의 가중치는 1, 뭐 0.8
> 이렇게 정할 수도 있겠죠.**」

```text
        KPI
```

>
> 「그러면 **상품 하나에 여러 KPI 가 붙을 수도 있고, 반대로 KPI 하나에는 여러 상품들이**
> 있겠죠.」

## 16 · SCI 공급망 KPI 인과관계 온톨로지 그래프

시맨틱 레이저→레이어 · 코어 텍스트 서치→Cortex Search · 버명 에이전트→범용 Agent ·

보이나 확인하지 못했다.

# 최종 정리 — 데이터에 의미와 판단 순서를 담은 두 가지 사례

이 발표는 AI 모델을 바꿔서 문제를 해결한 이야기가 아니다. 아모레퍼시픽은 먼저 **데이터가
회사의 용어를 이해하게 만들고**, 그다음에는 **업무 담당자가 원인을 판단하는 순서까지 데이터로
표현**했다. 그렇게 준비한 데이터를 Snowflake Agent와 사내 서비스에 연결했다.

## 사례 1 — 회사의 언어를 이해하는 실적 분석 Agent

### 문제 — 같은 질문도 사람마다 뜻이 달랐다

「지난 분기 북미에서 신제품이 얼마나 팔렸는가」라는 질문에는 이미 여러 해석이 들어 있다.
지난 분기가 회계 기준으로 언제인지, 북미에 어느 국가가 포함되는지, 출시 후 얼마까지를
신제품으로 볼지 정해야 한다. 이런 기준이 데이터에 없으면 AI는 질문을 이해하지 못하거나
사용자가 기대한 것과 다른 숫자를 답한다.

### 만든 개념 — AI Ready Data와 Semantic Layer

신제품, 북미, 분기처럼 회사에서 사용하는 용어의 정의와 테이블·컬럼의 관계를 관리하는
**Semantic Layer**를 만들었다. 발표에서 말한 **AI Ready Data**는 단순히 정제된 데이터가
아니라, AI가 업무의 의미와 맥락까지 해석할 수 있는 데이터에 가깝다.

### 적용과 아키텍처

도메인·용어와 데이터의 매핑을 메타 관리 시스템에서 관리하고, 실적·고객·재고 등 주제별
Semantic View를 만들었다. 표기 차이를 찾기 위한 Cortex Search와 엑셀 파일 생성 같은 Custom
Tool도 붙였다. 이 자산으로 실적 전문 에이전트인 **Sales Insight**를 만들었다.

| 계층 | 구성요소 | 역할 |
| --- | --- | --- |
| 비즈니스 정의와 거버넌스 | 도메인·용어 관리, 테이블·컬럼 매핑, Semantic View 매핑, 배포 이력 | 회사의 용어와 데이터가 뜻하는 바를 정의하고 변경을 관리한다 |
| 데이터 자산 | Semantic View, Cortex Search, Custom Tools | 실적을 조회하고, 표기 차이를 찾고, 엑셀과 같은 결과물을 만든다 |
| Agent | LLM, 실적 Semantic View, Tools | 질문을 해석하고 필요한 데이터와 도구를 선택해 답변한다 |
| 사용자 접점 | MS Teams, Snowflake Cowork, 사내 리포트 | 빠른 질의, 심층 분석, 기존 서비스 안의 요약을 제공한다 |

```mermaid
flowchart TB
    META["메타 관리 시스템<br/>도메인 · 용어 · 데이터 매핑 · 배포 이력"]

    subgraph ASSET[데이터 자산]
        SV["Semantic View<br/>실적 · 고객 · 재고"]
        SEARCH["Cortex Search<br/>표기 차이 검색"]
        TOOL["Custom Tools<br/>엑셀 등 파일 생성"]
    end

    AGENT["Snowflake Agent<br/>LLM + 실적 Semantic View + Tools"]

    subgraph CHANNEL[사용자 접점]
        TEAMS["MS Teams<br/>빠른 질의"]
        COWORK["Snowflake Cowork<br/>심층 분석"]
        REPORT["사내 리포트<br/>인사이트 브리프 · AI 서머리"]
    end

    META <--> SV
    META --> SEARCH
    META --> TOOL
    SV --> AGENT
    SEARCH --> AGENT
    TOOL --> AGENT
    AGENT -->|Agent API| TEAMS
    AGENT -->|MCP · Snowflake 내부 연동| COWORK
    SV -->|AI_COMPLETE 함수| REPORT
```

사용자는 **MS Teams**의 평소 쓰던 대화창에서 실적을 빠르게 질문하고, **Snowflake Cowork**에
목표값이 든 파일을 올려 실적과 비교하거나 분석 결과를 저장·재사용할 수 있다. 기존
대시보드에는 `AI_COMPLETE()`를 적용해 리포트의 요점을 먼저 보여주는 **인사이트 브리프**와
복잡한 화면을 문장으로 설명하는 **AI 서머리**를 만들었다.

Snowflake 안에 데이터와 에이전트의 중심을 두고 사용자 접점만 연결했지만, Teams에서 차트까지
보여주려면 Office Script, Power Automate, OneDrive 등을 포함한 8개 시스템의 연계가 필요했다.

### 결과

Sales Insight는 전사에 공개됐다. 발표자는 에이전트가 수십 초 안에 만든 결과가 기존에는
한두 시간에서 하루가 걸리던 리포트에 해당한다고 설명했다. Teams 안에서 바로 쓸 수 있어 별도
사용 교육 없이 접근할 수 있었고, **빠른 질의는 Teams, 심층 분석은 Cowork**라는 사용 방식도
구분했다.

## 사례 2 — 판단 순서를 데이터로 만든 공급망 Agent

### 문제 — KPI는 결과만 보여주고 판단은 사람에게 남았다

공급망 조직은 매일 생산·재고·판매 KPI를 정리하는 반복 업무를 하고 있었다. 리포트 생성을
자동화해도 「재고가 왜 늘었는가」, 「순매출이 왜 줄었는가」를 알아내는 일은 해결되지 않았다.
원인을 찾는 순서가 담당자마다 달랐고, 그 판단 과정도 데이터로 남지 않았기 때문이다.

### 만든 개념 — 인과관계 Ontology

계획 → 생산 → 재고 → 판매 → 유통으로 이어지는 공급망에서 KPI끼리 어떤 영향을 주고받는지를
**Ontology**로 표현했다. 발표자는 이를 **「판단 순서를 데이터가 갖게 한다」**고 설명했다.

| 요소 | 이 사례에서 뜻하는 것 | 예시 |
| --- | --- | --- |
| Meta | KPI 사이의 일반적인 인과관계 | 생산↑ → 재고↑, 재고↑ → 순매출↓ |
| Node | 특정 대상에 붙은 KPI와 상태 | 상품 A의 재고 증가 |
| Edge | 실제 노드 사이에 만들어진 관계 | 상품 A의 재고 증가 → 부진재고 증가 |

### 적용과 아키텍처

기준이 서로 달랐던 20개 이상의 원천 테이블을 10개 이상의 KPI View로 표준화했다. 각 KPI에는
전월 대비 변화량·변화율과 양호·주의·경고 같은 판정 기준을 붙였다. 이후 현업과 함께 실제로
발생하는 공급망 시나리오와 분석 목표를 정하고, CoCo의 `ontology-stack-builder`로 Meta·Node·
Edge와 Semantic Model, Agent까지 이어지는 스택을 구성했다.

```text
원천 테이블 → 표준 KPI View → Ontology(Meta · Node · Edge)
             ├→ 범용 Agent
             └→ Ontology Agent → 인과 그래프 · AI 원인 분석
```

「최근 3개월 순매출 평균」처럼 KPI View만으로 답할 수 있는 질문은 **범용 Agent**가 맡는다.
「특정 상품의 순매출이 왜 감소했는가」처럼 상품 단위 인과관계를 추적해야 하는 질문은 MCP를
통해 **Ontology Agent**로 연결한다.

대시보드에서는 위험 상태인 KPI 카드를 펼쳐 앞뒤의 인과관계를 보고, 더 깊은 원인을 따라가거나
에이전트에 추가 질문할 수 있게 했다. 사용자가 결과만 전달받는 것이 아니라 그래프와 원본
수치를 함께 보며 답변을 검수하도록 구성했다.

### 결과

특정 상품의 위험 KPI에서 출발해 생산·재고·판매를 거슬러 올라가는 인과 그래프와 공급망
대시보드를 구현했다. 기존의 결과 조회를 **원인 탐색과 다음 판단을 돕는 분석**으로 확장한
것이다.

다만 실제 KPI와 수치, AI의 원인 분석 답변은 비식별 처리되어 있다. 정확도, 사용률, 비용
절감액과 같은 정량 성과는 이 발표만으로 확인할 수 없다. 공급망 Ontology Agent도 완성된 전사
운영 성과가 아니라, 앞으로 통합 에이전트로 확장할 구현 사례로 소개됐다.

## 두 사례에서 가져갈 경험

1. **에이전트보다 먼저 용어를 합의한다.** 같은 질문을 같은 기준으로 해석할 수 있어야 한다.
2. **반복되는 업무 판단을 관계로 표현한다.** 긴 Instruction에 업무 규칙을 계속 추가하는 대신,
   추적할 관계를 데이터로 관리한다.
3. **좋은 원천 데이터와 명확한 분석 목표가 자동화보다 먼저다.** 어떤 데이터를 쓰고 무엇을
   판단할지는 현업과 함께 정해야 한다.
4. **범용 조회와 원인 분석을 분리한다.** 모든 질문을 무거운 구조로 처리하지 않고 필요한
   질문만 Ontology Agent로 보낸다.
5. **사용자 접점과 검증 방법까지 설계한다.** 익숙한 도구 안에서 제공하되, 기간·대상·지표를
   명확히 질문하고 답변의 필터와 수치를 다시 확인하도록 안내한다.

결국 두 사례가 보여준 것은 “AI에게 데이터를 연결했다”가 아니다. **조직이 공유하는 의미와
판단 방식을 먼저 데이터 구조로 만들었을 때, 에이전트가 실제 업무 흐름 안으로 들어올 수
있다**는 경험이다.
