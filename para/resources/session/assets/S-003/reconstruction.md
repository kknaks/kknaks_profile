> “전체적인 에이전트가 어떤 정의를 가지고 있고, 어떻게 동작하는지에 대한 표준 체계를 유지하게 되면” — 06:24–07:05, 블록 13

## 03–04 · 확장성을 높이는 연결 표준 도입 (07:11 ~ 09:15)

![MCP·Open API·A2A·AG-UI의 연결 지점](03-connection-standards-a.webp)

![같은 연결 표준 슬라이드를 다른 순간에 촬영한 사진](04-connection-standards-b.webp)

근거: STT 블록 15–18. 두 사진은 같은 구성을 보여준다. 촬영 구도와 발표자 위치가 다르며, 읽을 수 있는 범위에서 추가된 노드나 문구는 없다. 서로 다른 두 단계로 해석하지 않았다.

**슬라이드**

중앙의 표준 인터페이스가 연결 규칙을 표준화해 구성요소의 독립 교체를 지원한다.

| 연결 지점 | 화면 표기 | 제시한 효과 |
| --- | --- | --- |
| Tool ↔ Agent | MCP | 도구 교체 비용 감소 |
| Service ↔ Backend | Open API | 서비스 교체 유연성 |
| Agent ↔ Agent | A2A | 에이전트 간 연동 확장 |
| Agent ↔ UI | AG-UI | 에이전트와 일하는 방식 체계화 |

작은 주석에는 MCP의 리눅스 재단(AAIF) 이관 시점을 `'25.12`, A2A의 리눅스 재단 이관 시점을 `'25.6`으로 적었다. 이는 **발표 슬라이드의 표기**를 기록한 것이며 외부 연혁 검증은 하지 않았다.

**발표자**

기업이 제안한 프로토콜이 생태계 전반으로 확산되는 것을 예로 들며, 현재 사용할 수 있는 표준을 적용하고 새 표준도 살펴야 한다고 설명한다. 사내 백엔드 API도 AI가 사용할 수 있는 형태로 정리해야 하고, 사람과 에이전트의 상호작용까지 표준화 범위가 넓어진다고 말한다.

> “API를 AI가 사용할 수 있는 형태로 잘 정리하고 표준화하는 부분들이 필요하게 됩니다.” — 07:50–08:30, 블록 16

블록 15의 “MCP … 최근에 2.0 버전”은 두 모델의 음성 재전사에서도 “2.0 버전”으로 일치했다. 따라서 이 숫자를 단순한 원 STT 오인식으로 보기는 어렵다. 다만 사진에는 버전 표기가 없으며, 재전사의 일치가 프로토콜의 실제 공식 버전이나 발표 내용의 정확성을 검증하는 것은 아니다.

## 05 · 기업 AI 자산의 Marketplace (11:10 ~ 12:02)

![에이전트·도구·지식·모델의 등록과 검증 및 재사용 흐름](05-enterprise-ai-marketplace.webp)

근거: STT 블록 22–23.

**슬라이드**

내부 제작, 외부·구독형, 기존 시스템이라는 세 경로가 Marketplace로 들어온다. 자산은 Agent, Tool, Knowledge, Model로 나뉜다.

```text
내부 제작 / 외부·구독형 / 기존 시스템
  → Marketplace: Agent · Tool · Knowledge · Model
  → 등록 → 승인·검증 → 검색 → 재사용 → 평가
                           평가 결과는 앞선 흐름으로 환류
```

아래에는 Governance가 전체 흐름에 걸쳐 배치되어 있고 `권한·정책·감사`가 읽힌다. 발표자에게 가려진 앞부분의 문구는 복원하지 않았다.

**발표자**

흩어진 에이전트·도구·지식 자산을 모아 등록·배포·승인·검증하는 과정이 기업 내 확산의 기반이라고 설명한다. 재사용할 수 있는 저장소에 그치지 않고, 누가 사용할 수 있는지와 정책 준수 여부까지 관리해야 한다.

> “재사용이라는 측면에서의 마켓플레이스뿐만이 아닌, 기업에서의 적용할 기준을 관리하는 거버넌스의 영역으로도 이어질 수 있습니다.” — 11:45–12:02, 블록 23

![Task ID로 연결한 요청·판단·도구 결과·사람 승인과 FabriX Trace 예시](06-task-trace-human-approval.webp)

> “전체 과정들을 추적할 수 있고 분석할 수 있는 것이, 에이전트가 실행한 내용들을 이해하고 설명 가능하도록 하고” — 12:24–12:51, 블록 25

이 사례를 작은 예이지만 AX에서 반복되는 역할과 과정이라고 설명한다. 특정 복지 시스템의 운영 규모나 사용자 효과는 제시하지 않는다. STT의 “연계 테스트를 통해서 공격을 하게 되는”은 turbo 재전사에서도 “공격”, large-v3 재전사에서는 “공개”로 인식됐다. “공개”가 교정 후보이나 일치하지 않아 확정하지 않았고, 실제 배포 완료 등의 의미도 부여하지 않았다.

# 최종 정리 — 전환 과정에서 생긴 판단과 검증을 다음 운영의 자산으로 남긴다

앞부분의 플랫폼 설명은 뒤의 세 업무 사례를 읽는 기준이다. 코드 현대화는 평가 결과의 재사용, 복지 티켓 구매는 사람·에이전트·기존 시스템의 연결, 경비 처리는 판단과 정해진 실행의 분담을 보여준다. 마케팅 캠페인은 오케스트레이션의 설명용 화면이므로 별도의 실운영 사례로 세지 않았다.

## 사례 1 — 레거시 코드 변환을 분석·검증의 반복 과정으로 만든다

근거: 사진 12–13, STT 블록 42–46(21:01–23:37).

### 문제 — 코드를 바꾸기 전에 기존 업무 규칙을 이해하고 바뀐 결과를 검증해야 한다

레거시 코드와 문서에 들어 있는 구조·의존성·업무 규칙을 파악해야 새 코드로 옮길 수 있다. 많은 코드를 변환하더라도 테스트와 검수가 없으면 전환 결과를 신뢰하기 어렵다는 과제를 다룬다. 구체적인 실패율이나 작업 병목 수치는 공개하지 않았다.

### 만든 개념 — 한 번의 전환 결과가 다음 전환의 자산이 된다

발표가 세운 구조는 분석·이해, 변환·생성, 검증·보완을 반복하고 평가 결과를 축적하는 것이다. 이미 소프트웨어 개발에 쌓인 모듈화·재사용·테스트·변경 추적 기반 위에서 에이전트를 적용한다.

### 적용과 아키텍처

에이전트가 코드와 문서를 분석하고 코드·테스트를 생성한 뒤 테스트와 오류 보완을 반복한다. 사람은 승인하거나 보완을 지시한다. 검증에서 얻은 평가 결과는 다음 분석·변환에 사용하는 자산으로 돌아간다. 특정 모델, 저장소 구조, 자동 승인 기준은 발표만으로 확인할 수 없다.

### 결과

발표자는 관계사 적용에서 많은 레거시 코드를 자동 변환하고 테스트를 완수하는 과정을 확인했다고 설명했다. 공개 근거는 흐름도와 해당 발화다. 변환량·정확도·시간 절약을 측정한 자료는 없어 전환 생산성을 정량화하지 않는다.

## 사례 2 — 복지 업무를 승인 가능한 Agentic App으로 연결한다

근거: 사진 14, STT 블록 47–51(23:40–25:53).

### 문제 — 사용자 요청을 실행 가능한 조건으로 바꾸고 기존 시스템의 거래까지 연결해야 한다

“가족 나들이 티켓을 구매해 달라”는 요청에는 방문일·인원·금액·결제 방식 같은 확인 사항이 따른다. 이를 모아 사람에게 구매 내용을 보여주고 승인받은 뒤 기존 복지 시스템에 전달하는 과정이 필요하다.

### 만든 개념 — 사람의 확인과 시스템 실행을 포함해 업무 절차를 다시 설계한다

에이전트 앱을 만드는 일은 기획·현업·시스템 오너·API 개발자·에이전트 개발자가 단계별로 참여하는 업무 전환으로 설명된다. 기존 시스템은 AI가 사용할 수 있는 API로 연결하며, 필요한 경우 MCP도 사용한다.

### 적용과 아키텍처

직원의 자연어 요청을 에이전트가 이해하고 조건을 확인한다. 날씨와 구매 정보를 모아 사람이 금액·일정을 승인하게 한 뒤 복지 시스템과 연결하고 구매 결과를 반환한다. 개발 과정은 분석 → 설계 → API·에이전트 개발 → 연계 테스트로 나뉜다. 화면에 없는 인증 방식, 결제 취소·실패 처리, 거래 중복 방지 구조는 복원하지 않았다.

### 결과

구매 완료와 E-티켓 확인까지 이어지는 **예시 화면**이 제시됐다. 실제 운영 서비스의 이용자 수나 처리 성공률은 확인할 수 없다. 200,000원은 예시 거래 금액이며 비용 절감액이 아니다.

## 사례 3 — 경비 처리에서 Agent의 판단과 RPA의 실행을 조합한다

근거: 사진 15, STT 블록 52–53(25:56–27:16).

### 문제 — 기존 자동화가 다루기 어려운 예외와 변경 사항 때문에 사람의 검토가 남는다

사람이 영수증을 읽고 검토하던 업무에 RPA를 도입했지만, 예외 처리와 새로운 변경 사항은 기존 방식으로 다루기 어려웠다고 설명한다. 문제는 정해진 입력 절차뿐 아니라 경비 규정과 증빙을 해석하는 판단에 있다.

### 만든 개념 — 판단·실행·예외 검토의 담당을 나눈다

Agent가 증빙과 규정을 판단하고, RPA가 정해진 시스템 작업을 수행하며, 사람은 예외를 검토한다. 발표는 자동화의 기존 역할을 유지하면서 AI의 판단을 결합하는 방식을 제시한다.

### 적용과 아키텍처

카드 내역·영수증 → Agent의 증빙 인식·규정 판단·계정 분류·예외 판별로 진행한다. 예외는 사람이 검토하고, RPA는 경비시스템 입력·증빙 첨부·신청·결과 회신을 수행한다. 처리 결과와 함께 판단 근거·감사 추적을 남기는 구성이 제시된다. 예외 판별의 임계값이나 실제 규정 엔진의 내부 구현은 공개하지 않는다.

### 결과

발표자는 삼성SDS에서 **운영 중인 사례**라고 밝혔다. 시간 절약, 처리 상태와 판단 근거의 가시성, 정확도 향상을 설명했지만 수치와 측정 조건은 없다. 운영 여부는 발화로 확인되며 효과의 크기는 미확인이다.

## 세 사례에서 가져갈 경험

아래는 발표 사례를 바탕으로 작성자가 일반화한 적용 원칙이다. 발표자의 직접 인용이나 추가로 검증된 성과가 아니다.

1. **변환 결과와 평가 근거를 함께 남긴다.** 코드·에이전트만 저장하면 다음 전환에서 같은 판단을 반복할 수 있다. 무엇을 시도했고 어떤 검증에서 통과·실패했는지 재사용 가능한 형태로 남길 때 자산화가 성립한다. 다만 발표는 저장 스키마나 평가 기준까지 제시하지 않는다.
2. **사람의 책임을 업무 단계로 표현한다.** 코드 보완 지시, 구매 승인, 경비 예외 검토처럼 사람이 무엇을 판단하는지 먼저 구분한다. 적용하려는 업무의 책임자와 승인·예외 기준을 정해야 같은 구조를 옮길 수 있다.
3. **해석이 필요한 판단과 정해진 실행을 나눠 연결한다.** 경비 사례에서는 Agent와 RPA가 다른 일을 맡고, 티켓 사례에서는 API 개발자가 기존 시스템과의 접점을 만든다. 업무가 달라지면 판단·실행의 경계도 다시 확인해야 하며, 모든 단계를 같은 방식으로 자동화할 근거는 없다.
4. **운영 중의 추적·평가를 다음 변경에 연결한다.** 플랫폼은 Task ID, 평가, 거버넌스, 비용 관측을 함께 제시했다. 업무 결과와 실행 이력을 연결하고 평가할 기준이 있어야 운영에서 얻은 정보를 다음 개선에 쓸 수 있다. 이 발표에서 그 개선 폭을 수치로 입증하지는 않았다.
5. **표준 연결에도 데이터와 권한의 경계를 둔다.** 연결 가능한 도구·모델이 늘어나는 것과 회사 데이터의 사용이 허용되는 것은 별개다. 하이브리드 구성의 정책·데이터 경계 평가처럼, 사용할 자산과 실행 환경에 대한 기준을 갖춘 상태에서 표준 인터페이스를 적용한다.
