# 메달리온 아키텍처로 레이크하우스 데이터 품질을 단계적으로 높이는 법

> 출처: https://www.databricks.com/kr/blog/what-is-medallion-architecture · Databricks 직원 · 발행일 미상

## 요지

- 메달리온 아키텍처는 데이터를 브론즈, 실버, 골드 레이어로 구성해 구조와 품질을 점진적으로 개선하는 레이크하우스 설계 패턴이다.
- 브론즈는 원본과 이력을 보존하고, 실버는 데이터를 정리·통합해 엔터프라이즈 관점을 제공하며, 골드는 보고와 프로젝트별 활용에 맞게 집계·최적화한다.
- 데이터는 먼저 빠르게 적재한 뒤 후속 레이어에서 변환하는 ELT 흐름을 주로 따른다.
- Databricks는 Delta Live Tables, 스트리밍 테이블, 구체화된 보기를 이 패턴의 구현 수단으로 제시한다.
- 이 글은 게시 후 갱신되지 않은 보관 자료이므로, 제품 명칭과 구현 방법은 최신 문서와 교차 확인해야 한다.

## 내용

글은 메달리온 아키텍처를 레이크하우스 안의 데이터를 논리적으로 정리하는 설계 패턴으로 설명한다. 데이터가 브론즈에서 실버를 거쳐 골드로 이동할수록 구조와 품질이 증분적으로 개선되므로 멀티 홉 아키텍처라고도 부른다. 이는 글쓴이인 Databricks가 제시하는 설명이자 권장 패턴이다.

브론즈 레이어에는 외부 소스의 데이터를 원래 구조에 가깝게 적재하고, 로드 시각이나 프로세스 ID 같은 메타데이터를 덧붙인다. 글은 이 레이어의 역할로 빠른 변경 데이터 캡처, 원본 이력 보존, 데이터 리니지와 감사, 소스 시스템을 다시 읽지 않는 재처리를 든다.

실버 레이어에서는 브론즈 데이터에 매칭, 병합, 표준화, 중복 제거 등 적당한 수준의 정리를 적용한다. 고객, 매장, 거래 같은 주요 비즈니스 개체와 개념을 통합한 엔터프라이즈 뷰를 제공하며, 셀프서비스 분석과 고급 분석, 머신러닝의 공통 소스가 된다. 글은 이 레이어에 3차 정규형이나 데이터 볼트와 유사한, 쓰기 성능을 고려한 모델을 사용할 수 있다고 설명한다.

글은 레이크하우스 데이터 엔지니어링이 일반적으로 ETL보다 ELT를 따른다고 주장한다. 원천 데이터를 빠르게 수집하는 데 우선순위를 두고 실버까지는 변환을 제한하며, 복잡한 비즈니스 규칙과 프로젝트별 변환은 실버에서 골드로 이동할 때 적용한다는 관점이다.

골드 레이어는 보고와 구체적인 비즈니스 프로젝트에 바로 사용할 수 있도록 정리한 데이터로 구성한다. 조인을 줄이고 읽기에 최적화된 비정규화 모델을 사용하며, 최종 데이터 품질 규칙과 집계를 적용한다. 고객·제품·재고 분석, 고객 세분화, 추천, 마케팅 및 영업 분석 등이 대표적인 용도다. 모델링 방식으로는 Kimball식 스타 스키마나 Inmon식 데이터 마트가 제시된다.

Databricks는 레이크하우스가 데이터 레이크의 확장성과 데이터 웨어하우스의 관리·분석 특성을 결합해 원시 데이터와 준비된 데이터를 한 플랫폼에서 제공한다고 주장한다. 그 결과 기존 EDW와 여러 데이터 마트를 포함한 전사 데이터에 고급 분석과 머신러닝을 적용하고 데이터 사일로를 줄일 수 있다는 설명이다. 또한 메달리온 아키텍처는 데이터 메시와 양립하며, 업스트림 브론즈·실버 데이터를 여러 다운스트림 테이블이 사용하는 일대다 흐름을 구성할 수 있다고 본다.

제품 구현 측면에서는 Delta Live Tables로 브론즈·실버·골드 파이프라인을 만들고, 스트리밍 테이블과 구체화된 보기를 이용해 점진적으로 갱신되는 파이프라인을 구성할 수 있다고 소개한다. 다만 해당 글은 게시 이후 갱신되지 않은 보관 자료라고 명시되어 있으므로, 이 부분은 현재 Databricks 문서를 기준으로 검증할 필요가 있다.

## 배운 것

메달리온 아키텍처의 핵심은 단순히 테이블을 세 종류로 나누는 데 있지 않다. 원본 보존, 공통 의미 정립, 소비 목적별 최적화라는 서로 다른 책임을 분리하고 각 단계의 품질 기준을 명확히 하는 데 있다.

브론즈에서는 재현성과 감사 가능성, 실버에서는 개체 식별과 표준화, 골드에서는 사용 사례별 성능과 의미를 검증 기준으로 삼을 수 있다. 레이어 이름보다 각 레이어의 입력·출력 계약, 허용할 변환, 품질 검사, 재처리 방법을 문서화하는 것이 더 중요하다.

ELT가 항상 ETL보다 낫다는 주장에는 조건이 붙는다. 원시 데이터의 장기 보존은 비용, 개인정보 보호, 접근 통제 문제를 만들 수 있고, 실버에 변환을 지나치게 미루면 품질이 낮은 데이터가 넓게 소비될 수 있다. 데이터의 민감도와 지연 시간, 규제 요건에 따라 수집 단계에서도 검증·마스킹·격리가 필요하다.

또한 이 패턴은 Databricks 전용 개념이라기보다 플랫폼과 무관하게 적용할 수 있는 책임 분리 방식으로 이해하는 편이 유용하다. 다만 글이 Databricks 직원의 제품 블로그이며 보관 상태라는 점을 고려해, 제품 기능과 성능에 관한 설명은 독립적인 사실보다 공급자의 주장으로 읽고 최신 공식 문서에서 재확인해야 한다.
