# 용어 정의 — 병원 매출 온톨로지 (2단계 산출물)

> 상위 계획: [[hospital-revenue-ontology-plan]] · 원천: [[hospital-revenue-source-inventory]] · 2026-08-31

실버 레이어는 이 정의를 코드로 실행한 것이다. **여기 없는 해석으로 데이터를 가공하지
않는다.** ★ 표시는 회사 답변 대기 중인 가정 — 답이 오면 이 문서를 먼저 고치고 실버를
재실행한다.

## 1. 기본 단위

| 용어 | 정의 | 데이터 근거 |
| --- | --- | --- |
| 분석 대상 | 세라미크의원 강남 단일 지점 | Vegas `branch` NFC 정규화 = 「세라미크의원 강남」 · NEXUS `CERAMIQUE-GN-001` |
| 분석 기간 | 매출 측 2026-01-07 ~ 2026-08-30 · 리뷰 2025-07-05 ~ 2026-08-30 | 브론즈 반입분 |

| 영업일 | 내원 행이 1건 이상 있는 날 | 검증됨: 일요일 포함 매일 파일 생성. 분석 창 결측은 2026-02-17(설날) 하루뿐 — 예약 0 인 날은 파일이 없다. 1/1~6 은 연초 연휴 추정 |

## 2. 예약 결과

| 용어 | 정의 | 데이터 근거 |
| --- | --- | --- |
| 내원 | `visitStatus = '내원'` | 47,602행 (2026) |
| 취소 | `visitStatus = '취소'` — 사전에 예약을 무른 것 | 27,815행 |
| 노쇼 | `visitStatus = '부도'` — 통보 없이 안 온 것 | 2,799행 |
| **노쇼율** | 부도 ÷ (내원 + 부도) | **취소는 분모에서 뺀다** — 취소는 「안 온 것」이 아니라 「예약을 무른 것」. 섞으면 두 행동이 한 지표에 뭉개진다 |
| **취소율** | 취소 ÷ (내원 + 부도 + 취소) | 전체 예약 대비 |

## 3. 환자 구분

| 용어 | 정의 | 데이터 근거 |
| --- | --- | --- |
| 신환 | `visitCount = 1` 인 **내원** 행 | 검증됨(2026-08-31): 카운터는 실제 내원 시에만 +1 증가 (환자 9,511명 중 97.6% 정확히 연속). 불연속 2.4% 는 같은 날 중복 행 — 실버 중복 제거로 흡수 |
| 재진 | `visitCount ≥ 2` 인 내원 행 | 분석 창 최대 33회 — 관리 패키지 단골 수준. (275 는 2025 데이뷰 통합 파일의 값 — 우리 창에 없음) |
| **신규 이탈** | `visitCount = 0` 인 취소·부도 행 — **내원 이력 없는 사람이 첫 예약을 무르거나 안 온 것** | 1,409행 전부 취소(1,066)·부도(343), sales 전부 0. 유입 손실 지표 — 버리지 않고 별도 KPI 로 세운다 |
| 신환율 | 신환 ÷ 내원 | |

## 4. 매출

| 용어 | 정의 | 데이터 근거 |
| --- | --- | --- |
| 매출 (일별) | 해당일 내원 행의 `sales` 합 | **sales = 당일 결제액 — 확정** (데이터 검증 + 담당자 확인, 2026-08-31). ⚠️ 매출은 결제일 기준 현금흐름 — 내원(활동)과 시점이 어긋나므로 `내원↑→매출↑` 를 동시점 엣지로 그리지 않는다 |
| 수납 (일별) | 해당일 내원 행의 `receipt` 합 | |
| 미수 | sales − receipt | 월 차액 수만원 수준으로 확인됨 |
| **결제 발생 내원** | 내원이면서 `sales > 0` 인 행 | 내원의 약 11% — 나머지 89% 는 선결제 패키지의 회차 방문 |
| **객단가** | sales 합 ÷ 결제 발생 내원 수 | **분모는 결제 발생 내원.** 전체 내원으로 나누면 0원 행 89% 가 평균을 뭉갠다 |
| 결제 전환율 | 결제 발생 내원 ÷ 내원 | 회차 구조 확인 전까지 참고 지표 |

## 5. 유입 · 개입

| 용어 | 정의 | 데이터 근거 |
| --- | --- | --- |
| 리뷰 수 (일별) ★ | 플랫폼별로 분리해 `리뷰일` 기준 카운트 (분리는 정보 보존용) | 네이버 급증(2026-04·06·07)이 리뷰 이벤트인지 **회사 확인 대기** — 인과 해석(유기냐 내생이냐)은 답 전까지 판정하지 않는다 |
| 평점 | **강남언니 리뷰만의** 평균 평점 | 네이버는 평점이 없다 — 평점 KPI 에 네이버를 섞지 않는다 |
| 리뷰 감성 | 리뷰내용에서 추출한 긍/부정 (S-002 방식: AI 추출 · Rule 검증 · 예외만 사람) | 실버에서 생성. 수정 이력 보존 |
| 프로모션 진행중 ★ | 해당일이 `promotion_started_at ~ ended_at` 안 | 정본(v1/v2) **회사 확인 대기** — 답 전까지 합집합으로 계산하되 v1/v2 출처 컬럼을 분리해 어느 답이 와도 재계산 가능하게 |
| 계절 | 월 · 연휴 여부 (외생 노드) | 달력에서 생성 |

## 6. 답변이 오면 바뀌는 것 — 대기 항목과 영향 범위

| # | 질문 (인벤토리 §5) | 걸려 있는 용어 | 답 전까지의 가정 |
| --- | --- | --- | --- |
| 1 | ~~`sales` 인식 기준~~ → **확정: 당일 결제액** (데이터 검증 + 담당자 확인). 질문 아님 — 소진(회차 차감) 데이터가 있으면 발생주의 매출 축을 추가할 수 있다는 요청만 남음 | **매출** · 결제 발생 내원 · 객단가 | 확정. 환불은 음수 행이 아니라 과거 파일 덮어쓰기 |
| 2 | ~~`visitCount` 이상값~~ → 데이터로 해소. 0 = 내원 이력 없는 취소·부도(→ 신규 이탈 KPI), 275 는 우리 창에 없음(최대 33) | **신환** · 재진 · **신규 이탈** | 검증 완료 — 회사 질문 불필요 |
| 3 | ~~데이터 구멍~~ → 해소. 분석 창 결측은 설날(2026-02-17) 하루. 2025-09 는 창 밖 | 영업일 | 검증 완료 — 회사 질문 불필요 |
| 4 | **회사 확인 대기** — 네이버 리뷰 급증(2026-04·06·07)이 영수증 리뷰 이벤트인지 + 시기 목록 (데이터로는 네이버 단독 급증까지만 확인) | 리뷰 수 · 리뷰→신환 엣지 | 판정 보류. 플랫폼 분리로 어느 답이 와도 재계산 가능 |
| 5 | **회사 확인 대기** — v1/v2 정본 (데이터상 둘 다 활동 중: v1 최근 생성 2026-07-07 · v2 최근 수정 2026-08-31) | 프로모션 진행중 | 합집합 + v1/v2 출처 컬럼 분리 |
| 6 | **회사 확인 대기** — (B) 포맷 전환 시점 | (용어 아님 — 파서 대비) | A/B 둘 다 파싱 |

**규칙: 가정이 확정되거나 뒤집히면 이 문서를 먼저 고치고, 실버를 재실행한다.**
문서와 실버 코드가 어긋난 채로 골드를 만들지 않는다.
