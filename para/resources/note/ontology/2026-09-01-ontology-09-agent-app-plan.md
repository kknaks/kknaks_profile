# 온톨로지 실행 기록 09 — 데모 에이전트 앱 구축 계획

원칙 하나로 요약된다 — **앱은 기록 01~08 이 밟은 순서를 그대로 재현한다.**
브론즈(원본) → 실버(표준화) → 골드(KPI) → 온톨로지(관계) → 에이전트. note 의 기록
시리즈가 이 앱의 설계도이며, 각 계층 화면은 해당 기록을 근거로 단다. 결과(골드·그래프)만
보여주는 것이 아니라 **어느 계층이든 내려가서 원본까지 볼 수 있어야** 온톨로지 데모다.
이 구조가 서 있어야 다음 단계(수집 파이프라인)가 "브론즈에 새 데이터가 들어오면 같은
길을 자동으로 타는 것"으로 자연스럽게 이어진다.

## 1. 아키텍처 결정 (2026-09-01 합의)

| 결정 | 내용 | 근거 |
| --- | --- | --- |
| **DB = 메달리온 전 계층** | SQLite 에 `bronze_*`(vegas 예약 원장 78,216 · 리뷰 1,962 · nexus 14테이블 원형) + `silver_*` + `gold_*` + `ontology_*`(nodes·edges) 전부 적재 | 브론즈가 있어야 재처리·감사·드릴다운이 성립(메달리온 책임 분리). 파이프라인 단계에서 빌드가 파일이 아니라 DB 를 읽도록 지금부터 맞춘다 |
| 빌드의 DB 이식 | 기존 build 스크립트(reservations·catalog·reviews·gold)의 입출력을 DB 로 전환 — 변환 규칙·게이트는 그대로(명세는 기록 04·05 가 SoT) | 다음 단계 파이프라인 = 이 빌드의 자동 트리거일 뿐이 되게 |
| 웹 raw 업로드는 아직 없음 | 이번엔 로컬 원천 → 브론즈 적재 스크립트. 업로드 UI 는 파이프라인 단계에서 게이트와 함께 | 게이트 없는 적재 금지 |
| PII 표시 규칙 | 브론즈 조회 화면에서 `patientName`·`phone`·`birthday` 는 **마스킹 표시**(값은 DB 에 있되 뷰에서 가림). 에이전트의 브론즈 접근도 마스킹 뷰 경유 | 글로서리 PII 규칙의 화면판 |
| Agent 는 판단만 | 집계는 View, 관계는 edges 조회. 관계 지식을 프롬프트에 넣지 않는다 | S-001·S-002 |
| 코드 위치 | `app/ontology-agent/`. DB 파일·원천 데이터는 로컬(gitignore — PII 정책) | agents.md 루트 계약 |
| 갱신 주기 | 일 1회(원천이 일 배치). "실시간" 표방 금지 | 기록 02 실사 |

## 2. 화면 구성 — 구축 순서 그대로

```
[계층 탐색]                          [모니터링·분석]
① 브론즈 — 원본 테이블 조회(PII 마스킹)   ④ KPI 카드 (7일 빈도 상태)
   · vegas 일별 원장 · 리뷰 · nexus     ⑤ 원인 분석 그래프 (노드 상태색,
② 실버 — 표준화 테이블 + 변환 규칙 표시      엣지 판정별 구분, 미관측 ? 표시)
   · 이 컬럼이 어느 브론즈에서 어떤        ⑥ 예보 (엣지 기반 「다음 위험」)
     규칙(글로서리)으로 왔는지            ⑦ AI 채팅 — 답변이 밟은 엣지가
③ 골드 — KPI 테이블 + 계산식·게이트 이력      ⑤ 그래프에 하이라이트
```

각 계층 화면에 해당 기록 문서 링크를 단다(브론즈→기록 02, 실버→04, 골드→05,
그래프→07). **문서가 앱의 설명서이고 앱이 문서의 증명**이 되는 구조.

## 3. 구현 순서 (2026-09-02)

1. **브론즈 적재** — `load_bronze.py`: 원천 파일 → `bronze_*` 테이블 원형 적재.
   게이트: 행수 대사(vegas 78,216 · 리뷰 1,962 · nexus 테이블별 원본 행수 일치).
2. **실버·골드 빌드 DB 이식** — 기존 스크립트의 입출력을 DB 로. 게이트는 기록 04·05
   의 것을 그대로 재실행해 통과 확인(행수 대사·enum fail-fast·대조값). 온톨로지
   nodes/edges 도 적재(고아 0 검사).
3. **계층 탐색 뷰** — ①②③ 화면. 브론즈 PII 마스킹 뷰, 실버·골드에 변환 규칙·계산식
   툴팁(글로서리 인용).
4. **조회 도구** — Agent 용: `query_kpi`(골드 read-only) · `query_layer`(실버·브론즈
   마스킹 뷰 — 드릴다운 질문용) · `trace_ontology`(판정 구분 반환 — 기각 사유 포함) ·
   `get_definition`(글로서리).
5. **그래프 뷰 + 예보** — ⑤⑥. 노드 색 = 7일 빈도(알림 ≥3 / 관찰 ≥1 / 정상),
   예보 2규칙(취소율→예약, 강남언니→신환) 코드화.
6. **에이전트 루프** — 기록 08 스펙: 전제 검증 → 엣지 역추적 → 수치 역추적 가능 인용.
   응답 스키마 `used_edges` 필수(그래프 하이라이트 입력). 필요 시 브론즈까지 드릴다운
   ("그 취소들 원본 보여줘" → `query_layer`). LLM 경로는 착수 시 ADR-04 확인이 첫 작업.
7. **웹 통합** — FastAPI + 단일 페이지(또는 Streamlit — 착수 시 결정).
8. **회귀 테스트** — 기록 08 시나리오 2본 + 드릴다운 1본("8월 취소 원본 20건") 자동화.

## 4. 게이트

| # | 게이트 | 기준 |
| --- | --- | --- |
| 1 | 브론즈 대사 | 원천 파일 행수 = bronze 테이블 행수, 전 테이블 오차 0 |
| 2 | 빌드 재현 | DB 기반 재빌드 산출물 = 기존 CSV 산출물 (행수·매출 합 등 대조값 일치) |
| 3 | PII 마스킹 | 화면·에이전트 응답 어디에도 실명·전화·생년월일 원값 노출 0건 |
| 4 | 회귀 3본 | 기록 08 시나리오 2본(전제 교정 포함) + 드릴다운 1본 통과 |
| 5 | 근거 무결성 | 답변 수치 = DB 재조회 일치, used_edges ⊆ 확정 엣지, 하이라이트 = used_edges |

## 5. 범위 밖 (이번에 안 하는 것)

웹 raw 업로드와 수집 자동화(대행사 보고서·페이스북 — 파이프라인 단계), 알림 발송,
다지점 확장. 단, 이번 구조(브론즈 포함 DB + 빌드의 DB 이식)가 그 단계의 기반이 되도록
설계한다 — 파이프라인 단계에서 갈아엎는 것이 없어야 한다.
