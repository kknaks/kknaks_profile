# PARA

이 레포의 **세컨드 브레인**이다. 나는 어떤 사람이고, 무엇을 알고, 무엇을 했나가 여기 산다.

## 네 버킷

| 버킷 | 담는 것 | 문서 |
|---|---|---|
| `areas/` | **지속되는 것** — 나 자신과 내가 쌓은 개념 | [[areas/area\|area.md]] |
| `projects/` | **끝이 있는 일** — 지금 살아 있는 것 | |
| `resources/` | **밖에서 들어온 것** — 자료·출처·레퍼런스 | 아래 |
| `archive/` | **현역이 아닌 것** | |

## 가르는 축

**`areas/` ↔ `resources/` 는 「누가 썼나」다.** 내 머리에서 나온 정리는 `areas/`,
밖에서 들어온 자료(영상·글·공식문서)는 `resources/`.

**`areas/` ↔ `projects/` 는 「다른 데서도 쓰나」다.** 그 프로젝트에서만 의미 있는 판단은
프로젝트가 갖고, 어디서나 다시 쓰이는 것은 `areas/` 로 올린다.

**`projects/` ↔ `archive/` 는 「지금 하고 있나」다.** 아래를 본다.

`areas/` 가 축이다 — 프로젝트는 왔다 가지만 영역은 남는다. 프로젝트는 영역을 두껍게
만들려고 하는 것이다.

## `archive/` 는 버림이 아니라 상태다

현역이 아니면 여기로 내린다. **끝났든 손을 뗐든 마찬가지다.** 그래서 `projects/` 에는
지금 살아 있는 것만 남고 목록이 선명해진다.

**되돌릴 수 있다.** 다시 그 일을 맡게 되면 `projects/` 로 이관한다. 지우는 게 아니라
자리를 옮기는 것이다.

## `resources/` 는 매체로 나눈다

`areas/` 는 **주제**로 나누고 `resources/` 는 **매체**로 나눈다. 밖에서 들어오는 경로가 곧
매체고, 캡처하는 방식도 매체마다 다르기 때문이다(영상은 자막, 기사는 본문, 세션은 현장 노트).

| 디렉토리 | 담는 것 |
|---|---|
| `docs/` | 공식 문서·스펙·논문 — 가장 믿을 수 있고 가장 자주 참조한다 |
| `book/` | 책 |
| `youtube/` | 영상 |
| `article/` | 뉴스·언론 기사 |
| `blog/` | 개인·회사 블로그, 쓰레드, SNS |
| `session/` | 컨퍼런스·밋업·개발 세션 |

`article/` 과 `blog/` 를 나누는 이유는 **읽는 법과 믿는 정도가 다르기** 때문이다 — 기사는
사실 전달이고 블로그·쓰레드는 개인 경험과 주장이다.

회사 회의록은 여기 두지 않는다. 밖에서 들어온 자료가 아니라 내 일이라 `areas/personal/company/` 다.

## 소속은 디렉토리가 아니라 필드다

회사 일이냐 여름별컴퍼니 일이냐로 폴더를 나누지 않는다. 그러면 「내가 무슨 프로젝트를
했나」를 한 곳에서 못 본다. 프로젝트 frontmatter 가 갖는다.

```yaml
org: company | studio       # 누구 일인가
sot: here | external        # 기획·스펙의 원천이 여기냐 밖이냐
status: active | done
```

**`sot: external` 이면 여기 남는 것은 내 경험뿐이다.** 스펙·WP 를 복사하지 않는다 —
원천이 회사 레포라 복사하는 순간 어긋난다.

## 아직 정하지 않은 것

- **발행물의 자리** — 이력서·포트폴리오·잔디·공개 글처럼 밖으로 나가는 것. `para/` 안에
  둘지 DB 로 뺄지. 이 레포 리뉴얼을 시작한 질문(「DB 에 넣을 것과 md 로 관리할 것」)이 여기다.
- **미정제 생각(inbox)의 자리** — 네 버킷 어디에도 안 맞는다.
- **소유(사람/자동화)** — 버킷은 수명 축이라 누가 쓰는지가 안 드러난다. frontmatter 로
  둘지 승인 게이트로만 다룰지.
