# PARA

이 레포의 **세컨드 브레인**이다. 나는 어떤 사람이고, 무엇을 알고, 무엇을 했나가 여기 산다.

## 네 버킷

| 버킷 | 담는 것 | 문서 |
|---|---|---|
| `areas/` | **지속되는 것** — 나 자신과 내가 쌓은 개념 | [[areas/area\|area.md]] |
| `projects/` | **끝이 있는 일** — 지금 살아 있는 것 | |
| `resources/` | **밖에서 들어온 것** — 자료·출처·레퍼런스 | 아래 |
| `archive/` | **현역이 아닌 것** | |

## 가르는 축

**`areas/` ↔ `resources/` 는 「계속 자라나」다.** 새로 배울 때마다 두꺼워지는 것은
`areas/`, 한 번 쓰고 끝나는 것은 `resources/`.

**누가 썼는지는 기준이 아니다.** 내가 쓴 학습 필기도 2024-05-28 에 쓰고 다시 안 고치면
자료다. 한때 「내가 썼나 남이 썼나」로 가르려 했는데, 그러면 블로그 글이 「지속되는
관심」이 아닌데도 `areas/` 로 들어간다.

**`areas/` ↔ `projects/` 는 「다른 데서도 쓰나」다.** 그 프로젝트에서만 의미 있는 판단은
프로젝트가 갖고, 어디서나 다시 쓰이는 것은 `areas/` 로 올린다.

**`projects/` ↔ `archive/` 는 「지금 하고 있나」다.** 아래를 본다.

`areas/` 가 축이다 — 프로젝트는 왔다 가지만 영역은 남는다. 프로젝트는 영역을 두껍게
만들려고 하는 것이다.

## `archive/` 는 버림이 아니라 상태다

현역이 아니면 여기로 내린다. **끝났든 손을 뗐든 마찬가지다.** 그래서 `projects/` 에는
지금 살아 있는 것만 남고 목록이 선명해진다.

**되돌릴 수 있다.** 다시 그 일을 맡게 되면 `projects/` 로 이관한다. 지우는 게 아니라
자리를 옮기는 것이다.

**`projects/` 와 같은 모양으로 나눈다** — `archive/company/` · `archive/summer-star/`.
이관이 소속을 건너뛰지 않으므로 자리가 그대로 대응한다.

## `resources/` 는 출처로 나눈다

`areas/` 는 **주제**로 나누고 `resources/` 는 **어디서 왔나**로 나눈다. 들어오는 경로마다
다루는 방식이 다르기 때문이다(영상은 자막, 기사는 본문, 세션은 현장 노트).

| 디렉토리 | 담는 것 |
|---|---|
| `note/` | **내가 쓴 글** — 학습 필기·정리·블로그. 쓰고 나면 고치지 않는다 |
| `docs/` | 공식 문서·스펙·논문 — 가장 믿을 수 있고 가장 자주 참조한다 |
| `book/` | 책 |
| `youtube/` | 영상 |
| `article/` | 뉴스·언론 기사 |
| `blog/` | 개인·회사 블로그, 쓰레드, SNS |
| `session/` | 컨퍼런스·밋업·개발 세션 |

`article/` 과 `blog/` 를 나누는 이유는 **읽는 법과 믿는 정도가 다르기** 때문이다 — 기사는
사실 전달이고 블로그·쓰레드는 개인 경험과 주장이다.

**`note/` 가 `areas/concept/` 의 재료다.** 글을 쓰면서 알게 된 것이 개념 노트로 올라간다.
글은 그 자리에 남고 개념만 자란다.

회사 회의록은 여기 두지 않는다. 밖에서 들어온 자료가 아니라 내 일이라 `areas/personal/company/` 다.

## `projects/` 는 소속으로 나눈다

```
projects/company/       회사 일 — 스펙의 원천이 회사 레포에 있다
projects/summer-star/   여름별컴퍼니 — 기획부터 전부 여기 있다
```

나누는 이유는 이름이 겹쳐서가 아니라 **안에 들어가는 것이 다르기 때문**이다.
`sot: external` 이면 스펙 단계가 없고 경험만 남는다 — 한 폴더에 섞으면 「얘는 왜
`20-spec` 이 없지」가 매번 생긴다.

**공개 범위도 다르다.** 이 레포는 공개고 회사 문서에는 사내 정보가 섞일 수 있다.
폴더로 갈려 있으면 빼거나 막기가 쉽고, 섞여 있으면 파일 단위로 골라내야 한다.

`areas/personal/` 도 같은 축으로 `company/` · `summer-star/` 를 갖는다 — 두 층이 같은
이름을 쓰는 것이 일관된다.

**소속을 폴더로 나누는 것은 여기까지다.** `areas/concept/` 은 소속으로 나누지 않는다 —
개념은 어디서 배웠든 같은 개념이다.

## 그 밖의 축은 필드다

프로젝트 frontmatter 가 갖는다.

```yaml
sot: here | external        # 기획·스펙의 원천이 여기냐 밖이냐
status: active | done
```

`org` 는 필드로 두지 않는다 — 폴더가 이미 말한다.

**`sot: external` 이면 여기 남는 것은 내 경험뿐이다.** 스펙·WP 를 복사하지 않는다 —
원천이 회사 레포라 복사하는 순간 어긋난다.

## 아직 정하지 않은 것

- **발행물의 자리** — 이력서·포트폴리오·잔디·공개 글처럼 밖으로 나가는 것. `para/` 안에
  둘지 DB 로 뺄지. 이 레포 리뉴얼을 시작한 질문(「DB 에 넣을 것과 md 로 관리할 것」)이 여기다.
- **미정제 생각(inbox)의 자리** — 네 버킷 어디에도 안 맞는다.
- **소유(사람/자동화)** — 버킷은 수명 축이라 누가 쓰는지가 안 드러난다. frontmatter 로
  둘지 승인 게이트로만 다룰지.
