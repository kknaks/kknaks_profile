# para/

## 1. 개요

**정의**
- 이 레포의 세컨드 브레인. 내가 누구이고, 무엇을 알고, 무엇을 했나가 여기 산다.

**역할**
- 들어온 것이 **네 버킷 중 어디로 가는지** 가른다. 버킷 안에서 어디로 갈지는 각 문서가 갖는다.

**구조**

```text
para/
├── areas/        지속되는 것 — 나 자신과 내가 쌓은 개념
├── projects/     끝이 있는 일 — 지금 살아 있는 것
├── resources/    밖에서 들어온 것 — 자료 · 출처 · 레퍼런스
└── archive/      현역이 아닌 것
```

## 2. 어느 버킷인가

| 경계 | 선 |
| --- | --- |
| `areas` ↔ `resources` | **계속 자라나.** 새로 배울 때마다 두꺼워지면 `areas`, 한 번 쓰고 끝나면 `resources` |
| `areas` ↔ `projects` | **다른 데서도 쓰나.** 그 프로젝트에서만 의미 있으면 `projects`, 어디서나 다시 쓰이면 `areas` |
| `projects` ↔ `archive` | **지금 하고 있나.** 현역이 아니면 `archive` |

**누가 썼는지는 기준이 아니다.** 내가 쓴 학습 필기도 2024 년에 쓰고 다시 안 고치면 자료다.
「내가 썼나 남이 썼나」로 가르면 블로그 글이 지속되는 관심도 아닌데 `areas` 로 들어간다.

**`areas` 가 축이다.** 프로젝트는 왔다 가지만 영역은 남는다. 프로젝트는 영역을 두껍게
만들려고 하는 것이다.

**애매한 것이 나오면 예외를 추가하지 말고 위 기준을 고친다.**

## 4. projects/

**무엇**
- 끝이 있는 일. 지금 살아 있는 것만 여기 남는다.

**어디로** — [[project|projects/project.md]]

**하위** — 소속으로 나눈다.

| 디렉토리 | 담는 것 |
| --- | --- |
| `company/` | 회사 일. 기획과 스펙의 원천이 회사 레포에 있다 |
| `summer-star/` | 여름별컴퍼니. 기획부터 전부 여기 있다 |

이름이 겹쳐서가 아니라 **안에 들어가는 것이 다르기 때문**이다. `sot: external` 이면 스펙
단계가 없고 경험만 남는다 — 한 폴더에 섞으면 「얘는 왜 스펙이 없지」가 매번 생긴다.

**공개 범위도 다르다.** 이 레포는 공개고 회사 문서에는 사내 정보가 섞일 수 있다.
폴더로 갈려 있으면 빼거나 막기 쉽다.

**`sot: external` 이면 스펙을 복사하지 않는다.** 원천이 회사 레포라 복사하는 순간 어긋난다.
여기 남는 것은 내 경험뿐이다.

**필드**

```yaml
sot: here | external        # 기획 · 스펙의 원천이 여기냐 밖이냐
status: active | done
```

`org` 는 필드로 두지 않는다. 폴더가 이미 말한다.

## 6. archive/

**무엇**
- 버림이 아니라 **상태**다. 현역이 아니면 여기로 내린다. 끝났든 손을 뗐든 마찬가지다.

그래서 `projects/` 에는 지금 살아 있는 것만 남고 목록이 선명해진다.

**어디로** — [[archive|archive/archive.md]]

**되돌릴 수 있다.** 다시 그 일을 맡게 되면 `projects/` 로 이관한다. 지우는 게 아니라
자리를 옮기는 것이다.

**`projects/` 와 같은 모양으로 나눈다** — `company/` · `summer-star/`. 이관이 소속을
건너뛰지 않으므로 자리가 그대로 대응한다.

## 7. 미결

- **발행물의 자리** — 이력서 · 포트폴리오 · 공개 글처럼 밖으로 나가는 것.
  `para/` 안에 둘지 DB 로 뺄지.
- **미정제 생각(inbox)의 자리** — 네 버킷 어디에도 안 맞는다.
- **소유(사람 · 자동화)** — 버킷은 수명 축이라 누가 쓰는지가 안 드러난다.
  frontmatter 로 둘지 승인 게이트로만 다룰지.
