# 외부 연동 API 3차(charty 1차 상담) — 결정

> 기능 계약(경로 · 요청 · 응답 · 오류 표 · KOS 호출 수 · 시험)은 **SPEC-008 0.4.6 §4.3 · §6.4 · §6.10 ~ §6.18** 이 갖고, 작업 순서는 **WORK-014** 가 갖는다. 이 문서는 무엇을 정했는지만 적는다.
> 이미 배포된 여섯 경로와 공유하는 규칙(인증 · 제한 · 기록 · 오류 모양)은 **DEC-010** 이 정본이다. 여기서는 다시 정하지 않고 가리킨다.
> 결정 원천은 `orchestration/work/ext-api-charty1/_RESUME.md` §2 다 — **이 문서와 `_RESUME` 가 다르면 `_RESUME` 가 맞다.**

## Context

협업자 charty 가 1차 상담 화면에 쓸 데이터를 요청했다. linky 도 같은 API 를 쓴다. 구조는 **KOS → CC → 연동처** 다. CC 가 KOS 에서 값을 가져와 연동처에 준다.

이 제품은 프로토타입이다. 그래서 **연동처별 권한을 나누지 않고, 요청한 데이터를 준다.** 권한 설계와 「KOS = 저장소 / CC = 원본」 전환은 별도 고도화 작업에서 한다(이번 범위 밖).

조사로 확인한 사실(데모 테넌트 · 코드 `0a58aba`):

- 접수 목록에 필요한 칸(희망 상담사 · 관리실 · 접수 시각)은 지금 예약 사본 열에 이미 있다. 그래서 목록에 넣어도 KOS 호출이 늘지 않는다(조사 1차 §2).
- 「처음 상담 대기가 된 시각」은 공개 스펙에도, 받은 HAR 에도 없다. KOS 웹 JS 에 내부 `schedule/v1/queries/get-schedule-event-logs {scheduleId}` 가 있다. 실제 응답은 아직 보지 못했다(조사 3차 §1).
- 공개 시술권 조회는 「사용 중(`IN_USE`)」 장을 주지 않는다. 그래서 사용 중 장만 남은 묶음은 지금 lookup 에서 통째로 빠진다. 내부 `ticket/v1/queries/get-ticket-bundles` 는 그 장을 준다(조사 1차 §3-3).
- 고객 언어 · 오더 메모 쓰기 · 병원 정보 · 역할 이름은 내부 API 에만 있다(조사 1차 §1-2 · §4-1 · 2차 §1.2 · §2.2 · 3차 §2).
- 시술권 만료일은 KOS 에 칸이 없다. 예산 · 동행자 · 통역 필요 · 피부 진단도 KOS 와 CC 어디에도 없다(조사 1차 §3-4 · §3-6 · §3-7).

근거 칸 표기: **사용자 결정** = 사용자가 정한 것(2026-11-16 · `_RESUME` §2) / **코디 기본값** = 코디가 정해 통보한 값 / **조사 n차 §** = 사실 근거 / **검수 r1 Fn · Wn · DQn** = 문서 검수 r1 지적과 그 답(2026-11-16 · 사용자 「추천대로」).

없음. 사용자 결정 · 코디 기본값 · 조사 사실에서 나왔다.

## Decision

### 공통

| ID | 결정 | 근거 |
|---|---|---|
| D-01 | **아래 API 는 전부 연동처 공통이다.** linky · charty 가 같은 키 체계로 같은 경로를 부른다. 인증(`X-Api-Key`) · 키당 호출 제한 · `ext_call` 기록 · `Cache-Control: no-store` · Swagger tag 「외부 연동」 · 오류 모양은 DEC-010 을 그대로 쓴다(DEC-010 D-10 · D-23 ~ D-25 · D-34 · DEC-011 D-01 과 같음). 연동처별 권한 분기는 없다 | 사용자 결정 |
| D-02 | **DEC-011 D-03(예약 메모 · 상담 메모 · 의사 이름을 내지 않는다)과 DEC-010 의 「이름 + 이메일 둘 다 맞아야 고객을 연다」(D-11 · D-19 · D-21)를 이번에 더하는 경로에는 걸지 않는다.** 이미 배포된 여섯 경로의 계약은 그대로 두고 깨지 않는다. 사유: 프로토타입이고 사용자가 정했다. 따라서 ccc 정수 id(`customerId` · `reservationId`)로 고객 · 예약을 여는 경로가 생긴다. ccc id 는 차례로 붙는 정수라서 키를 가진 쪽은 차례로 넣어 볼 수 있다. 이 위험은 받아들인다(키를 가진 연동처만 · 호출 제한 · 기록 · 조사 1차 §3-2 함정) | 사용자 결정 |
| D-03 | 기존 lookup(`POST /api/ext/customers/lookup`)은 **필드 추가만** 한다. 이름이나 뜻이 바뀌는 칸은 없다. 다만 시술권 원천이 바뀌면서 「사용 중 장만 남은 묶음」이 새로 나온다. 이 행동 변화는 SPEC 변경 이력과 Swagger 에 적는다 | 사용자 결정(「기존 ext 6개 계약을 깨지 않는다」) |
| D-04 | **쓰기는 KOS 먼저.** 지금 직원 API 와 같은 순서로 한다: CC 사본에서 대상을 찾는다 → KOS 에 쓴다 → 성공하면 `event_log` 를 남긴다 → 사본을 고친다. CC 에 먼저 쌓았다가 나중에 보내지 않는다. KOS 가 실패하면 그 오류를 연동처에 그대로 낸다(`409 kos_rejected` · `502 kos_unavailable` · 실패 줄 `kos_rejected`) | 사용자 결정 · 코드 `service/reservations.py:710-721` `kos_write` |
| D-05 | 「차트 메모」는 **상담 메모**다. 이번 쓰기는 **오더 메모 · 상담 메모** 둘이다. 작업 단위 메모(간호 · 의사)와 고객 특이사항은 이번에 쓰지 않는다 | 사용자 결정(「오더 메모 상담 메모」) · 조사 1차 §4-2 |
| D-06 | **외주 직원 = KOS 계정**(역할 이름 「CS팀(콜센터)」)이다. CC 에 따로 저장하지 않는다. 직원 목록 하나에 모두 싣고, 역할 이름으로 구분한다 | 사용자 결정 · 조사 2차 §2.2 |
| D-07 | **빼는 것**: ① 예산 · 동행자 · 통역 필요 · 피부 진단 — KOS · CC 에 원천이 없다. **시술권 만료일 칸은 만들지 않는다**(KOS 에 없음). 발행일(`purchasedDate`)만 준다. ② 시술권 차감 — 이번 범위에서 정하지 않았다(차감 = KOS 시술 작업 생성). 연동처에는 「없음」으로 회신한다. (2026-11-16 고침 · 검수 r1 W14 · DQ6: 출처를 ① 과 ② 로 나눴다 — `_RESUME` §2 에 맞춤) | ① 사용자 결정(「원하는 데이터만」) · ② 코디 기본값 · 조사 1차 §3-4 · §3-6 · §3-7 |

### 이번 결정에 걸리지 않는 것 (열지 않음)

- **권한 · 원본 전환** — 연동처별 권한, 「KOS = 저장소 / CC = 원본」은 고도화 작업 몫이다(D-01 · D-04).
- **기존 여섯 경로의 D-03 · 이름+이메일 규칙** — 그대로다(D-02). 과거 시술(`/customers/visits`)은 계속 메모 · 의사를 내지 않는다.
- **열람 기록의 범위** — 고객 데이터를 여는 두 경로(D-18)만 남긴다. 헤더를 읽는 경로는 D-37. 직원 id 와 ccc 계정의 연결은 정하지 않는다(받은 값을 그대로 적는다).

## Consequences

- 연동처는 직원 계정 없이 그날 접수 목록 · 예약 상세 · 병원 · 직원을 읽고, 언어 · 오더 메모 · 상담 메모를 쓸 수 있다.
- **ext 에서 KOS 쓰기가 셋 늘어난다**(지금은 예약 생성 하나). 내부 API 의존도 늘어난다: 시술권 · 개인 정보 묶음 · 오더 메모 · 병원 정보 · 계정 · 운영 시간 · 휴무 · 이력. 내부 API 조건(시스템 계정 토큰 · 브라우저 UA)이 바뀌면 이 경로들이 `502` 로 멈춘다(SPEC-008 §6.18 표).
- lookup 응답에 사용 중 장만 남은 묶음이 새로 보인다. `totalCount` 는 뜻(상태 무관 장수)은 그대로이고, 사용 중 장이 세어지는 만큼 값이 커질 수 있다.
- 처음 상담 대기 시각을 아직 못 찾은 접수 뒤 일정은 사건(처음 봄 · 대기를 새로 봄 · 귀가 뒤 · 실패 재시도 ≤ 3)이 있을 때만 이력을 다시 부른다. 하루 이력 호출은 접수 뒤 일정 수 × 3 + 실패 재시도를 넘지 않고, 화면을 자주 불러도 늘지 않는다(D-38 · D-40). 대신 board 가 열리지 않은 사이에 지나간 대기는 귀가 뒤 1번이 받는다. 하루 대상은 접수 건수를 넘지 않는다(D-16 ③).
- ccc id 로 고객 · 예약을 여는 경로가 생긴다. 키만 있으면 차례 정수로 훑을 수 있다(D-02 수용). 대신 열람이 `event_log` 에 남는다(D-18). 다만 직원 id 는 신고값이라, 누가 열었는지는 연동처의 말을 믿는 수준이다.
