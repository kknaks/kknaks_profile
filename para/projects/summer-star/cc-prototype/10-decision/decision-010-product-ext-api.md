# 시술 · 상품 메뉴 저장 + 외부 연동 API — 결정

> 기능 계약(경로 · 요청 · 응답 · 오류 표)의 세부는 SPEC, 작업 순서는 WORK 가 갖는다. 이 문서는 무엇을 정했는지만 갖는다.
> 결정 원천은 `orchestration/work/api-swagger-docs/_RESUME.md` §2 — **이 문서와 `_RESUME` 가 다르면 `_RESUME` 가 맞다.**

## Context

외부 연동처(링키 · 차티)가 상담 중에 쓸 정보가 필요하다. 협업자 요청은 셋이다. 상품(시술) 가격, 기존 고객의 남은 시술권, 그리고 **고객 이름 + 이메일**로 예약하고 조회하는 것이다. 이메일 하나만으로 조회하면 정보가 샐 위험이 있어서 둘 다 필수로 한다. SNS 정보는 고객에게 요구하기 과해서 뺐다. 지금 back 의 고객 검색은 이름 · 전화 · 생년월일 · 차트번호뿐이고 직원 로그인 전용이라, 외부 연동용 API 와 보안을 따로 둔다.

KOS 사실(조사 1~4, 데모 테넌트):

- 메뉴는 `getProducts` 한 번에 상품 → 옵션(SINGLE · GROUP · CONSULTATION) → 구성 → 시술 · 진료항목 · 기기/약물까지 온다. 페이징은 없고 약 575KB · 0.3초다. 일정의 `optionId` 는 메뉴 옵션 id 와 같다(93/93).
- 고객이 산 것(수납 항목 · 시술권)은 **산 시점 값**을 들고 있다. 메뉴 가격을 바꿔도 이미 산 값은 그대로였고, 옵션 id 도 유지됐다(HAR).
- 메뉴 정가는 부가세 별도이고, 수납 가격은 그 값에 1.1을 곱한 값(부가세 포함)이다.
- 남은 시술권은 공개 `getTicketBundlesQuery` 가 사용 가능한 묶음만 준다. 고객 1명당 1호출, 약 40~60ms 다.
- 공개 API 의 고객 응답에는 email 칸이 없다. 이름만으로 검색하면 0건이다. 내부 `get-visitors` 목록은 email 을 같이 준다. 이름 검색은 부분 일치에 대소문자 무시이고, 공백은 그대로 비교한다.
- 데모 고객 494명 중 email 이 채워진 사람은 5명(1%)이다.

근거 칸 표기: **사용자 지시** = 사용자가 말하거나 고른 것 / **코디 기본값** = 코디 추천 · 사용자 승인. `R1-n` · `R2-n` · `R4-n` = 조사 1 §8 · 조사 2 §5 · 조사 4 §3 의 그 번호.

## 근거 개념

없음. 사용자 지시와 조사 리포트에서 나왔다.

## Decision

### 범위

| ID | 결정 | 근거 |
|---|---|---|
| D-01 | **자리 = `procedure/back`**. 화면(front · app)은 이번 범위가 아니다 | 코디 기본값 |
| D-02 | 이번에 만드는 것은 셋이다. ① KOS 메뉴를 우리 DB 에 저장, ② 외부 연동 API(메뉴 · 고객 조회 · 예약), ③ 외부 API 인증 | 사용자 지시 |

### 메뉴 저장

| ID | 결정 | 근거 |
|---|---|---|
| D-03 | **KOS 메뉴는 우리 DB 에 전부 넣는다.** 카테고리 · 상품 · 옵션 · 구성 · 시술 · 진료항목 · 기기 · 약물 · 타겟 국가, 그리고 각 객체의 모든 칸(다국어 `translsMap` · 가격 세부 · 상태 · deprecated 칸 포함)이다. 밖으로 내주는 칸은 D-27~D-31 이 정한다 | 사용자 지시(「우리 db 에는 일단 다 넣고」) |
| D-04 | 저장 모양 = 단계별 표(id · 상위 id · 이름 · 상태 · 가격 같은 조회에 쓰는 칸) + 각 행에 **KOS 원본 객체 JSON 을 통째로** 둔다. 표에 칸을 안 뽑은 값도 원본 JSON 으로 남게 하기 위해서다. 지금 back 의 SQLite · json 열 = 문자열 규약을 따른다 | 코디 기본값 · D-03 |
| D-05 | 원천 작업 = `getCategories` · `getProducts` · `getProductOptions` · `getProcedures` · `getMedicalServices` · `getMachines` · `getMedicines` · `getTargetCountries`. SINGLE 옵션의 진료항목은 `getProducts` 에 통째로 없어서(조사 1 §7-1) 붙일 id 가 없다. 그래서 `getProductOptions`(SINGLE 옵션 id 전부)로 진료항목 id 를 얻고, 본문은 `getMedicalServices` 행에 잇는다. 빈 검색어 `searchProductOptionSummaries` 는 부르지 않는다. (2026-11-11 고침: 처음엔 `getMedicalServices` 를 id 로 붙인다고 적었으나 옵션 쪽에 id 가 없어 `getProductOptions` 추가 — planner 질문 Q4) | 코디 기본값 · R1-2 · D-03 |
| D-06 | 동기화 = 지금 있는 **마스터 루프(`kos_poll_master_sec`, 1시간)에 얹는다**. 서버 시작 때 1회 받는다. Webhook 은 이번에 받지 않는다 | 코디 기본값 |
| D-07 | KOS 에서 사라진 행(삭제 · 숨김 · 닫힘)은 지우지 않고 「없음」 표시만 한다. 다시 나타나면 되살린다. 외부 API 의 메뉴 응답에는 지금 있는 것만 나간다 | 코디 기본값 · D-03 |
| D-08 | **메뉴 = 지금 기준, 고객이 산 것 = KOS 수납 · 시술권 값 그대로.** 고객이 산 것을 메뉴 값으로 덮지 않는다. 메뉴에 없는 옵션 id 를 가진 시술권도 시술권 쪽 값으로 그대로 보여 준다 | 사용자 지시 · 조사 2 · 3 · R2-1 · R2-4 |
| D-09 | 가격: 메뉴 정가는 **부가세 별도**로 저장 · 응답한다. 부가세 포함 금액은 계산(수납) 때 붙는다. 응답에서 어느 쪽 값인지 칸 이름 · 설명으로 밝힌다. 시술권 가격은 KOS 묶음 가격 그대로다(D-31). (2026-11-11 고침: 처음엔 「산 시점 가격 · 부가세 포함」 — D-31 고침에 맞춤) | 사용자 지시 |

### 외부 연동 API

| ID | 결정 | 근거 |
|---|---|---|
| D-10 | 외부 API 는 직원 API 와 **경로를 나눈다**(`/api/ext/…`). 직원 로그인 토큰으로는 부를 수 없고, 외부 키로는 직원 API 를 부를 수 없다 | 코디 기본값 · 사용자 지시(「외부 연동용 별도 api」) |
| D-11 | 엔드포인트는 셋이다. ① 메뉴 조회(우리 DB), ② **고객 조회(이름 + 이메일)** → 고객 + 남은 시술권, ③ **예약(이름 + 이메일 필수)**. 예약은 지금 예약 생성 로직을 다시 쓴다 | 사용자 지시 |
| D-12 | 남은 시술권 = `getTicketBundlesQuery`(사용 가능한 묶음만)를 조회 때마다 KOS 에서 읽는다. 우리 DB 에 복사하지 않는다. 다 쓴 · 취소된 시술권과 시술권 그룹 통계는 내주지 않는다 | 사용자 지시 · R2-2 · R2-7 |
| D-13 | 고객 조회 응답은 상담에 필요한 칸만 준다. 고객 id · 이름 · 신규 여부 · 남은 시술권 · 최근 방문 정도이고, 전화 · 생년월일 · 여권 같은 개인 칸은 빼 둔다(칸 목록은 D-31) | 코디 기본값 |
| D-14 | 「고객 없음」과 「고객은 있는데 남은 시술권 없음」은 응답에서 서로 다르게 보인다 | 코디 기본값 · R4-8 |

### 이름 + 이메일 조회

| ID | 결정 | 근거 |
|---|---|---|
| D-15 | 방식 = **KOS 내부 `get-visitors` 를 이름으로 검색한 뒤, 우리 쪽에서 이메일로 거른다**. 공개 API 로는 대신할 수 없어서(email 칸 없음) 내부 API 에 묶이는 것을 받아들인다. 지금 back 도 같은 내부 API 를 쓴다 | 사용자 지시 · R4-7 |
| D-16 | 이름 검색은 **한 페이지(최대 1000건)만** 받는다. `count` 가 1000 을 넘으면 거르지 않고 「없음」(D-21 과 같은 응답)으로 답한다. 받은 결과는 KOS 고객 id 로 중복을 지운 뒤 거른다. 지금 `search()` 의 20건으로는 21번째 이후 고객을 놓친다(데모 4명). (2026-11-11 고침: 처음엔 「`count` 끝까지 다 받는다」였으나, 페이지 사이 순서 밀림 · KOS 호출 증폭 때문에 한 페이지 + 상한으로 바꿈 — review-doc r1 W1 · W2 · Q-A, 사용자 승인) | 사용자 승인(Q-A) · R4-2(`countInPage` 5000 까지 받음) |
| D-17 | 이름은 앞뒤 공백만 지우고 보낸다. 띄어쓰기나 순서를 바꿔 다시 검색하지 않는다 | 코디 기본값 · R4-3 |
| D-18 | 이메일 비교 = 양쪽 모두 앞뒤 공백을 지우고 소문자로 바꾼 뒤 **정확히 같아야 한다**. KOS 에 email 이 없거나 빈 고객은 후보에서 빠진다 | 코디 기본값 · R4-4 |
| D-19 | KOS 검색은 부분 일치지만, **우리 쪽에서 이름이 정확히 같아야** 후보로 남긴다. 비교 = 양쪽 모두 공백을 전부 지우고 대소문자를 무시한 뒤 KOS 이름 또는 발음명(`phoneticName`)과 같음. 그다음 이메일로 거른다. 이름 한 글자 + 이메일로 사실상 이메일만으로 조회되는 것을 막는다. (2026-11-11 고침: 처음엔 「부분 일치 그대로」 — review-doc r1 Q-A, 사용자 승인) | 사용자 승인(Q-A) · Context(「둘 다 필수」) · R4-6 |
| D-20 | 거른 결과가 2명 이상이면 아무도 돌려주지 않고 「특정할 수 없음」으로 응답한다(데모 0쌍) | 코디 기본값 · R4-5 |
| D-21 | 틀린 입력과 없는 고객은 같은 「없음」 응답이다. 이름과 이메일 중 어느 쪽이 틀렸는지 알 수 없게 한다 | 코디 기본값 |
| D-22 | **email 이 비어 있는 기존 고객은 「없음」으로 둔다.** 보조 키(전화 · 생년월일)는 받지 않는다. 이름 + 이메일로 예약하면 KOS 고객에 email 이 저장돼서 다음부터는 찾힌다. 기존 고객이 처음 예약할 때 KOS 에 같은 고객이 두 번 생기는 것은 받아들이고, 데스크가 접수 때 정리한다 | 사용자 지시(추천안 A 채택) · R4-1 |

| ID | 결정 | 근거 |

| D-24 | 외부 API 호출마다 기록을 남긴다(연동처 · 엔드포인트 · 시각 · 결과 종류). 입력한 이름 · 이메일 원문은 기록하지 않는다 | 코디 기본값 |
| D-25 | 키별 호출 제한을 둔다(값은 D-34) | 코디 기본값 |
| D-26 | 외부 API 가 생기면 협업자에게 공유한 admin 계정은 **외부 키로 바꾸는 것을 권한다**. 언제 회수할지는 사용자가 정한다 | 코디 기본값 |

### 메뉴 응답 모양

| ID | 결정 | 근거 |
|---|---|---|
| D-27 | 외부 메뉴 응답 깊이 = 카테고리 → 상품 → 옵션 → (GROUP 이면) 구성 → 시술(id · 이름). 진료항목 · 기기 · 약물은 DB 에만 두고 응답에 넣지 않는다 | 코디 기본값 · R1-1 |
| D-28 | 옵션 갈래는 KOS 판별자 `type`(SINGLE · GROUP · CONSULTATION)을 그대로 둔다. CONSULTATION 은 가격 · 구성 없이 그대로 내보낸다(데모 0건) | 코디 기본값 · R1-3 |
| D-29 | 다국어는 KOS `translsMap` 을 그대로 내보낸다(언어를 고르지 않음). 기본 이름 칸도 같이 준다 | 코디 기본값 · R1-5 |
| D-30 | 가격 응답 = 정가 `amount`(부가세 별도) 하나를 「정가」로 준다. 공급가 · 부가세 · 면세 · 과세 유형 · 특별가 · 프로모션은 DB 에만 둔다. `TAXABLE` 의 세부 금액 해석은 응답에 쓰지 않으므로 이번 결정에 걸리지 않는다 | 사용자 지시(D-09) · R1-4 |

### 고객 조회 · 예약 계약

| ID | 결정 | 근거 |
|---|---|---|
| D-31 | 고객 조회 응답 칸 = 고객 id · 이름 · 신규 여부 · 최근 방문일 · 남은 시술권 목록. 시술권 한 줄 = 옵션 id · 옵션 이름 · 남은 장수 · 전체 장수 · 산 날 · **KOS 묶음 가격**(KOS `price` 그대로). 이 가격은 「고객이 낸 돈」이 아니다. 산 시점 값에서 출발하지만 세트를 쓰면 줄어들 수 있고, 부가세 포함 여부는 표기하지 않는다. 전화 · 생년월일 · 국적 · 여권 · 차트번호는 주지 않는다(D-13 을 구체화). ### 이번 결정에 걸리지 않는 것 (열지 않음)

- **운영 지점의 email 채움 비율**: D-22 는 비율과 관계없이 같다(없으면 「없음」, 예약으로 쌓임). 운영 키로는 조사하지 않는다.
- **이름 · 구성 · 횟수 수정 때도 산 값이 유지되나**: D-08 이 KOS 시술권 값을 그대로 쓰고 메뉴로 덮지 않으므로, 어느 쪽이든 우리 동작은 같다.

## Consequences

- 외부 연동처는 직원 계정 없이 메뉴 · 고객 · 남은 시술권을 볼 수 있다.
- 고객 조회 1건 = KOS 내부 이름 검색 1회 + 시술권 1회(D-16). 데모 실측은 107~235ms 다. (2026-11-11 고침: 처음엔 「1회 이상」)
- 이메일이 없는 기존 고객은 처음에는 찾을 수 없다. 예약을 거치며 email 이 쌓인다.
- 내부 API(시스템 계정 토큰 · 브라우저 UA) 조건이 바뀌면 이 조회도 같이 멈춘다.
