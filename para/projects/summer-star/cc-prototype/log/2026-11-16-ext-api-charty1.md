
# 작업 요약 — ext-api-charty1 (cc-prototype)

기간: `2026-11-16` ~ `2026-11-16`
결과: 머지 · 배포 완료 — 코드 #24 `969f44f` · infra #60 `88220d5` · 운영 읽기 경로 실호출 확인 · 외부 API 6 → 13

## 1. 무엇을 했나

차티(1차 상담 차팅 서비스)가 KOS 고객 데이터 중 상담 대기 화면 · 예약 상세 · 메모 쓰기 · 병원/직원 정보를 요청했다(11-12). 1차 외부 API(6개)로는 오늘 누가 상담을 기다리는지, 지금 메모가 무엇인지 알 수 없었다.
조사 3판(원천 21항목 · 병원/직원 · HAR 이력)으로 무엇이 KOS 어디에 있고 무엇이 아예 없는지(예산 · 동행자 · 통역 · 진단 · 시술권 만료일)를 가른 뒤, DEC-012 · SPEC-008 0.4.0 · WORK-014 를 세웠다. 프로토라 연동처별 권한 분기 없이 링키 · 차티 공통이다.
문서 검수 3판(r1 FAIL 3 → r2 FAIL 1 → r3 PASS)을 거쳐, 데모 KOS 실호출(KOS0)로 이력 모양을 확인하고 BE1 ~ BE6 을 한 워커가 구현했다(647 → 766 passed). 코드 검수 3판 뒤 로컬 실물 확인에서 버그 2건을 더 찾아 고치고, back 만 운영에 올렸다. 외부 API 는 13개다.

## 2. 적용한 기술·개념

- **「처음 상담 대기 시각」을 KOS 단계 변경 이력에서 꺼내기 — 찾은 값만 굳히고, 사건 때만 다시 부른다**
  - 왜 이걸 골랐나: CC 가 사본에서 상담 대기를 본 시각은 화면을 아무도 안 열면 영영 모르고(요청이 와야 도는 조회), KOS 웹에서만 지나간 대기는 못 본다. KOS 내부 `get-schedule-event-logs` 는 단계마다 기록을 남긴다. 실물에서 board 6건 중 4건이 「CC 판정 = 상담 안 거침」인데 이력에는 상담 대기가 있었다 — CC 판정을 문으로 썼으면 4건이 빠졌다
  - 무엇이 어려웠나: 저장 규칙이 세 번 틀렸다. ① 실패면 저장 안 함 → board 요청마다 N건 재호출(r1 F1) ② null 도 저장 → 재진입 · 이력 지연 · 대응 오류에서 영영 null(F3) ③ 「못 찾음 → 5분마다」 → 상담 안 거친 일정이 귀가까지 5분마다 불려 하루 약 1,250번(r2 N3 · DQ7). 결국 「일정마다 처음 봄 1 · 대기 새로 봄 1 · 귀가 뒤 1 · 실패만 5분 재시도 ≤ 3」으로 셈을 접수 건수의 작은 배수로 묶었다. 겹친 요청은 고르는 순간 먼저 적는 시도 예약(`BEGIN IMMEDIATE` · 안에 `await` 없음 · KOS 전 커밋)으로 막았다
  - 근거: `review-doc-r1.md` F1 · F3 · `review-doc-r2.md` N2 · N3 · DQ7 · DEC-012 D-16 · D-38 ~ D-41 · `procedure/back/app/service/ext.py` `_history` · 시험 T57(변이 확인)
  - 개념: [[job-lease]]
- **추측 대신 데모 실호출로 모양을 확정(KOS0)** — 이력은 KOS 웹 JS 로만 봤고 HAR 32개에 호출이 0건이었다
  - 왜 이걸 골랐나: 숫자 enum 대응표를 추측해 짓는 대신 WORK 첫 Phase 를 「조회만 · 쓰기 0」 실호출로 두고, 결과로 D-16 그대로 / D-17 대안을 판정하게 했다
  - 무엇이 어려웠나: 실물은 추측과 셋이 달랐다 — `eventType` 은 전체 이름(`protos.schedule.event.FlowStepChanged`), `flowStep` 은 숫자가 아니라 문자열, 원소 차례가 섞여 옴(12/40). 휴무 원소엔 이름 칸이 없었다(SPEC 예시의 `name` 을 뺌)
  - 근거: `kos0-report.md` · DEC-012 D-42 · D-43
  - 개념: [[empirical-limit-probing]] · [[public-vs-internal-api]]
- **내부 API(protobuf JSON)는 0 값을 뺀다 — 거르기 먼저, `value` 없음 = 0**
  - 왜 이걸 골랐나: 시술권 원천을 공개 → 내부로 바꾼 이유는 사용 중 묶음(공개는 빠뜨림)이다. 그런데 내부는 금액 0 묶음의 `price` 를 `{currency}` 만 준다. 내지도 않을 다 쓴 묶음의 모양 검사 때문에 lookup 전체가 502 였다
  - 무엇이 어려웠나: 가짜 KOS · 코드 검수 3판 · 시험 766개가 다 통과했다. 로컬 실물에서 **선불카드가 있는 고객**(데모 300명 중 이메일 7 · 카드 1)을 일부러 찾아 부르고서야 나왔다. 같은 고객의 공개 조회는 4묶음 모두 `value` 가 있어 원천 차이임을 확인했다
  - 근거: `be-fix-e2e1-instructions.md` · DEC-012 D-46 · 커밋 `1c3a340`
  - 개념: [[tolerant-reader]]
- **200 인데 안 바뀌는 쓰기를 400 으로 드러내기** — KOS 상담 메모는 `""` · `null` 을 받으면 200 을 주고 값을 그대로 둔다
  - 왜 이걸 골랐나: 「빈 값 = 비움」을 계약에 적어 두면 연동처는 지웠다고 믿는다. 비울 수 없는 쪽은 KOS 를 부르지 않고 400 으로 막았다(오더 메모는 `""` 로 비워져 그대로 둠)
  - 무엇이 어려웠나: 되돌리기 단계에서야 보였다(쓰기 → 되돌림 → 상세 재조회 비교). `" "` 은 공백으로 저장돼 비움 대용이 안 된다
  - 근거: `fix-e2e2-instructions.md` · DEC-012 D-47
  - 개념: [[no-silent-fallback]]
- **기존 계약을 깨지 않고 넓히기 — 헤더는 쓰는 경로에만, 상속은 끊는다**
  - 왜 이걸 골랐나: 열람 헤더 꼴 검사를 모든 경로에 걸면 기존 여섯 경로에 새 400 이 생긴다(r1 F2). lookup 요청 모델을 고치면 그 모델을 상속한 과거 시술 · 예약 내역까지 바뀐다(r2 N1 — 시험으로 안 잡힘). 헤더는 다섯 경로에만, `ExtCustomerRequest` 는 상속을 끊어 칸 · 검증 · Swagger 를 그대로 고정했다
  - 근거: `review-doc-r1.md` F2 · `review-doc-r2.md` N1 · DEC-012 D-37 · 시험 T71 ⓐ ⓑ ⓒ
  - 개념: [[minimal-api-surface]]

## 3. 막혔던 것 / 사고

- **처음 상담 대기 저장 규칙이 문서 검수 세 판을 먹었다** → 각 판의 고칠 방향을 코디가 「한 조건만」 보고 정했다(F1 은 호출 상한, F3 은 굳음, 그다음 셈). D-16 의 두 조건(한 번 정해짐 · 건수 비례 안 함)을 함께 놓고 셈(하루 호출 수)까지 적어 봤으면 r2 FAIL 을 피했다 → 규칙을 바꿀 때 「하루 호출 수」 식을 먼저 쓴다
- **시험 · 검수가 모두 초록인데 실물에서 502** → 가짜 응답을 KOS0 모양에 맞췄지만 KOS0 은 「카드 있는 고객 1명 · 묶음 25명」이었고 금액 0 묶음은 지나쳤다. 로컬 e2e 에서 대상 고객을 「가장 드문 모양」(카드 · 이메일 둘 다)으로 골라 찾았다 → 실물 확인은 흔한 고객이 아니라 드문 고객부터
- **오늘 예약 고객에 이메일이 없어 이름 + 이메일 경로를 확인할 수 없었다** → KOS 고객 목록 300명을 훑어 이메일 7명을 찾아 썼다. 값은 스크래치에서만 다뤘다
- **예약 직후 상세가 한 번 `reservation_gone`** → 다시 부르니 200 · 두 번째 예약은 0.4초에 200. KOS 반영 지연으로 보고 코드 재시도 없이 Swagger 안내만 넣었다
- **planner · researcher · reviewer_doc 터미널이 작업 중 죽었다** → planner 는 원 브리프 + 이번 지시 파일을 이어 붙인 spec 으로 새 터미널에 다시 발주했다. 지시를 파일로 둔 덕에 맥락 손실이 없었다
