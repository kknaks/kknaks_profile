## 1. 무엇을 했나

1차 cc PoC(현황판 · 직원 페이지 · 통역)를 10-16 지점 시연에 맞춰 넓혔다. 화면마다 따로이던 머리를 공통 헤더(현황판 | 예약관리 | 내 스케쥴)로 묶고, 폰에서는 도면 대신 1차 오른쪽 패널을 폭 전체로 보이게 했다.
Linky → cc → KOS 예약 흐름을 데모 버튼으로 흉내 내는 예약관리(요청 · KOS 등록 미리보기 · 스크린샷 · 변경 요청 · 수정 요청)를 시안부터 새로 만들었다.
배포본을 써 본 기획자 피드백 31개를 사용자와 하나씩 판단해(반영 9 · 안 함 다수) KOS 데이터가 있는 것만 넣었고, E2E 다섯 묶음을 거쳐 배포했다.

## 2. 적용한 기술·개념

- **기획 피드백을 「데이터가 있나」로 거른다** [[no-inference-from-free-text]] · [[seed-data]] — 기획자 목업의 칸마다 KOS 캡처(`getScheduleDetail` 177건)의 채움률을 세어 가능 · 부분 · 불가를 먼저 냈다
  - 왜 이걸 골랐나: 목업의 「오늘 받을 것(상담 · 온다 리프팅 희망)」 「주의사항」 「이후 진료 고객」은 화면으로는 그럴듯하지만 `requestedProcedures` 0/177 · 주의사항 전용 칸 없음 · `reservation.doctor` 0/177 — 메모 자유 글을 사람이 읽고 뽑은 값이었다. 1차의 「메모를 뽑아 쓰지 않는다」 원칙과 정면으로 부딪힌다
  - 반대로 `phoneticName` 140/177 · `phone` 142/177 · `categories`(VIP) 1/177 처럼 **KOS 에 있으면 시드를 고쳐서라도 넣는다**(사용자 「kos 기준으로 가능하면 우리 시드를 업데이트 해야지」)
  - 근거: `para/.../00-baseline/baseline-007-planner-feedback.md` 「데이터 확인 결과」 · DEC-004 D-24
- **쓸 수 있는 API 표면이 기능의 범위를 정한다** [[public-vs-internal-api]] — 접수 때 「추가 요청」 메모의 카테고리를 KOS 공개 OpenAPI(75개)에서 **쓰기 작업이 있는 메모**만으로 잡았다: 예약 메모(`changeReservationMemo`) · 상담 메모(`updateScheduleConsultationInfo`)
  - 왜: 오더 · 고객 · 시술(담당자) 메모는 읽을 수는 있어도 쓰는 공개 작업이 없다. 카테고리에 넣으면 「KOS 에 저장」이 거짓말이 된다 — 사용자 「일단 2개로 가자」
  - 덤: `searchVisitors` · `findVisitor` 가 있어 고객 검색은 실연동 때 KOS 전체 고객 대상으로 넓힐 수 있다
  - 근거: DEC-004 D-33 · BASE-007 D3 판단
- **경과 시간은 「지금 상태가 시작된 뒤」 — 상태와 시간을 같은 칸에** [[time-in-current-state]] — 도면 칸이 「3분 / 다음 단계 대기」 두 줄로 떨어져 있어 전체 체류 3분인지 그 상태 3분인지 읽히지 않았다
  - 알아낸 것: back 은 상태가 바뀔 때마다 `since = now`(`cc/back/app/domain/board.py` `commit`) — 값은 이미 「그 상태의 경과」였고, 문제는 표기였다
  - 최종: 1줄 현재 상태(`다음 단계 대기 중` / `포텐자 펌핑팁`) · 2줄 `<종류> N분 경과`(대기 · 상담 · 시술), 대기 30분↑ 빨강, 1분 미만 `대기 1분 미만`. 문구를 만드는 함수 하나를 9곳이 쓴다
  - 근거: SPEC-002 §5.5 · `e2e-feedback-batch-5.md`
- **시술권 차감은 「쓸 예정」과 「썼다」를 나눈다** [[consume-on-completion]] — 접수 때 자동 체크 + 사용 처리 → 직접 고르고 「오늘 사용 예정」 표시만, 차감은 시술 단계 완료 때
  - 왜: 시술 중간 취소 · 노쇼면 되돌려야 한다(기획자 덧붙임). 코드는 동선에 `ticketId` 만 붙어도 사용으로 셌다(접수 · 시술 추가 · 결제 완료) → 완료(done)만 센다
  - 같이 잡은 1차 버그: 보유 시술권 후보가 조건 없이 늘 떠서, 10회권 한 회차를 접수로 넣어도 같은 시술권이 「오늘 시술 후보」에 또 떴다 → 상담 종료 뒤에만 · 동선에 회차가 있으면 묶음째 제외
  - 근거: DEC-004 D-22 · D-32 · `fix2-be-report.md` §3 · §5
- **데모 버튼으로 외부 연동 자리를 대신한다** [[demo-stand-in-for-integration]] — Linky 연동이 아직 없으니 [링키 예약 요청 생성] · [링키 수정 요청 생성]을 주황 점선 「데모 전용」 상자에 따로 두고, KOS 등록 결과(스크린샷)는 등록 순간의 값을 `snapshot` 으로 남겨 HTML 카드로 그린다
  - 왜: 실제 흐름(본사 → 병원 → KOS)과 같은 상태 전이(확인중 → 확정 / 변경 요청 → 수정 확인중 → 수정 확정 · 이전 줄 변경됨)를 back 에 두면, 연동이 생길 때 버튼만 실제 수신으로 바꾸면 된다
  - 근거: SPEC-002 §3 · `wp4-be-report.md`
- **기존 디자인은 건드리지 않는다 · 예외는 범위로 적는다** [[design-system]] — D-21(1차 화면 · 시안 무변경) 위에 D-23(BASE-007 반영 항목만 예외)을 얹었다
  - 무엇이 어려웠나: 새 화면에서 medikit 에 없는 클래스(`bg-ms-gray-900` · `text-ms-gray-900`)를 써서 토스트가 흰 바탕 · 흰 글자가 됐다 → 새 파일의 클래스를 빌드 산출 CSS 와 전수 대조(MISS 0)를 워커 검증에 넣었다. 1차 서랍용 `zIndex: 41` 이 폰에서 헤더(30) 위로 올라와 햄버거를 덮은 것도 같은 결 — 1차 값을 새 맥락에서 그대로 쓴 것
  - 근거: `e2e-feedback-batch-1.md` #2 · #3 · `fix1` 보고

## 3. 막혔던 것 / 사고

- **사용자가 명시한 형식을 내 식으로 바꿨다** — 「현재 상태 / 경과 시간 두 줄」을 한 줄로 합쳐 제안 → 크게 질책. 화면 형식 지시는 문자 그대로 옮기고, 브리프에 「한 줄로 합치지 마라」를 박아 발주했다(메모리 `project_cc_prototype` 보강)
- **public 레포에 실명이 있었다** — 로그인 시연 카드의 prefer 이름 4개(1차부터)가 직원 실명. 시안 워커가 「가짜본 직원 목록에 없는 이름」으로 짚은 게 단서. PR 전 실명 대응표 grep 으로 확인 · 교체(이력은 남김 — 사용자 「괜찮아 이정도는」)
- **재시드가 안 될 뻔** — PVC 의 `cc.db` 만 지우면 entrypoint `seed ensure` 가 같은 폴더의 옛 `seed.json` 으로 다시 만든다(새 칸 없음). `cc.db` · `seed.json` 둘 다 지우고 재시작
- **코디 핸들이 세 번 바뀜**(adf432d6 → a8da76a5 → aa31d360) — 워커 보고의 `--from` 값으로 알아챘다. 발주 직전 `terminal list` 로 확인
- **사용자가 쓰는 로컬 서버를 초기화했다** — E2E 때마다 `/api/admin/reset` 을 쳤는데 사용자가 같은 3610 을 보고 있었다. 이후 「사용자 사용 중 — reset 금지」를 _RESUME 에 적고 지켰다
