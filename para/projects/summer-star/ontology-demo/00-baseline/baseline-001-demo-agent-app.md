# 데모 에이전트 앱 — 구축 순서를 그대로 재현하는 온톨로지 데모

피부과 의원 데이터를 메달리온(브론즈→실버→골드)과 온톨로지(nodes·edges)로 SQLite 한 DB 에
쌓고, 계층 탐색 · KPI 모니터링 · 원인 분석 그래프 · AI 채팅을 한 앱으로 낸다.
원천은 [[2026-09-01-ontology-09-agent-app-plan|기록 09]] 하나이며, 아래는 그 요약이다.

> 아직 결정하지 않은 날것의 입력이다. 정리보다 보존이 우선이다.

## Raw

원문: [[2026-09-01-ontology-09-agent-app-plan|기록 09 — 데모 에이전트 앱 구축 계획]]
(2026-09-01 작성, 구현 예정일 2026-09-02). 아래 수치·판단은 전부 그 문서의 것이다.

### 원칙

- **앱은 기록 01~08 이 밟은 순서를 그대로 재현한다** — 브론즈(원본) → 실버(표준화) →
  골드(KPI) → 온톨로지(관계) → 에이전트.
- 결과(골드·그래프)만 보여주는 것이 아니라 **어느 계층이든 내려가서 원본까지 볼 수 있어야**
  온톨로지 데모다.
- note 기록 시리즈가 이 앱의 설계도이고, 각 계층 화면은 해당 기록을 근거로 단다 —
  **문서가 앱의 설명서이고 앱이 문서의 증명**.
- 이 구조가 서 있어야 다음 단계(수집 파이프라인)가 「브론즈에 새 데이터가 들어오면 같은
  길을 자동으로 타는 것」으로 이어진다.

### 아키텍처 결정 7건 (기록 09 §1 — 2026-09-01 합의)

| # | 결정 | 요지 |
| --- | --- | --- |
| 1 | DB = 메달리온 전 계층 | SQLite 하나에 `bronze_*`(vegas 예약 원장 78,216 · 리뷰 1,962 · nexus 14테이블 원형) + `silver_*` + `gold_*` + `ontology_*`(nodes·edges) 전부 적재. 브론즈가 있어야 재처리·감사·드릴다운이 성립 |
| 2 | 빌드의 DB 이식 | 기존 build 스크립트(reservations·catalog·reviews·gold)의 입출력을 DB 로 전환. 변환 규칙·게이트는 그대로 — 명세의 SoT 는 기록 04·05 |
| 3 | 웹 raw 업로드는 아직 없음 | 이번엔 로컬 원천 → 브론즈 적재 스크립트. 업로드 UI 는 파이프라인 단계에서 게이트와 함께. 게이트 없는 적재 금지 |
| 4 | PII 표시 규칙 | 브론즈 조회 화면에서 `patientName`·`phone`·`birthday` 는 마스킹 표시(값은 DB 에 있되 뷰에서 가림). 에이전트의 브론즈 접근도 마스킹 뷰 경유 |
| 5 | Agent 는 판단만 | 집계는 View, 관계는 edges 조회. 관계 지식을 프롬프트에 넣지 않는다 (S-001·S-002) |
| 6 | 코드 위치 | `app/ontology-agent/`. DB 파일·원천 데이터는 로컬(gitignore — PII 정책) |
| 7 | 갱신 주기 | 일 1회(원천이 일 배치). 「실시간」 표방 금지 |

### 화면 구성 7종 (기록 09 §2)

계층 탐색과 모니터링·분석 두 갈래다.

| # | 화면 | 내용 | 근거 기록 |
| --- | --- | --- | --- |
| ① | 브론즈 | 원본 테이블 조회(PII 마스킹) — vegas 일별 원장 · 리뷰 · nexus | 기록 02 |
| ② | 실버 | 표준화 테이블 + 변환 규칙 표시 — 이 컬럼이 어느 브론즈에서 어떤 글로서리 규칙으로 왔는지 | 기록 04 |
| ③ | 골드 | KPI 테이블 + 계산식·게이트 이력 | 기록 05 |
| ④ | KPI 카드 | 7일 빈도 상태 | 기록 05 |
| ⑤ | 원인 분석 그래프 | 노드 상태색, 엣지 판정별 구분, 미관측 `?` 표시 | 기록 07 |
| ⑥ | 예보 | 엣지 기반 「다음 위험」 | 기록 07 |
| ⑦ | AI 채팅 | 답변이 밟은 엣지가 ⑤ 그래프에 하이라이트 | 기록 08 |

### 구현 순서 8단계 (기록 09 §3)

1. **브론즈 적재** — `load_bronze.py`: 원천 파일 → `bronze_*` 원형 적재. 게이트는 행수 대사.
2. **실버·골드 빌드 DB 이식** — 기록 04·05 게이트 재실행으로 통과 확인. 온톨로지 nodes/edges
   적재(고아 0 검사).
3. **계층 탐색 뷰** — ①②③. 브론즈 마스킹 뷰, 실버·골드에 변환 규칙·계산식 툴팁(글로서리 인용).
4. **조회 도구 4종** — `query_kpi`(골드 read-only) · `query_layer`(실버·브론즈 마스킹 뷰 —
   드릴다운) · `trace_ontology`(판정 구분 반환, 기각 사유 포함) · `get_definition`(글로서리).
5. **그래프 뷰 + 예보** — ⑤⑥. 노드 색 = 7일 빈도(알림 ≥3 / 관찰 ≥1 / 정상), 예보 2규칙
   (취소율→예약, 강남언니→신환) 코드화.
6. **에이전트 루프** — 기록 08 스펙(전제 검증 → 엣지 역추적 → 수치 역추적 가능 인용).
   응답 스키마 `used_edges` 필수. LLM 경로는 착수 시 ADR-04 확인이 첫 작업.
7. **웹 통합** — 기록 09 시점 기준 「FastAPI + 단일 페이지(또는 Streamlit)」 미결.
   이후 경과는 아래 「Possible Direction」 절 참조.
8. **회귀 테스트** — 기록 08 시나리오 2본 + 드릴다운 1본(「8월 취소 원본 20건」) 자동화.

### 게이트 5종 (기록 09 §4)

| # | 게이트 | 기준 |
| --- | --- | --- |
| 1 | 브론즈 대사 | 원천 파일 행수 = bronze 테이블 행수, 전 테이블 오차 0 |
| 2 | 빌드 재현 | DB 기반 재빌드 산출물 = 기존 CSV 산출물 (행수·매출 합 등 대조값 일치) |
| 3 | PII 마스킹 | 화면·에이전트 응답 어디에도 실명·전화·생년월일 원값 노출 0건 |
| 4 | 회귀 3본 | 기록 08 시나리오 2본(전제 교정 포함) + 드릴다운 1본 통과 |
| 5 | 근거 무결성 | 답변 수치 = DB 재조회 일치, `used_edges` ⊆ 확정 엣지, 하이라이트 = `used_edges` |

### 범위 밖 (기록 09 §5)

웹 raw 업로드와 수집 자동화(대행사 보고서·페이스북 — 파이프라인 단계), 알림 발송,
다지점 확장. 단, 이번 구조(브론즈 포함 DB + 빌드의 DB 이식)가 그 단계의 기반이 되도록
설계한다 — 파이프라인 단계에서 갈아엎는 것이 없어야 한다.

### 대조값 주석

- vegas 예약 원장 78,216 · 리뷰 1,962 는 기록 09 §1·§3 의 값 그대로다.
- 리뷰 1,962 의 내역은 기록 02 실사 기준 네이버 플레이스 1,448 + 강남언니 514,
  PK(`플랫폼리뷰ID`) 전건 유니크다.

## Context

- 온톨로지 실행 기록 01~08(`para/resources/note/ontology/`)이 완주됐다 — 데이터 실사부터
  실버·골드 빌드, 엣지 후보 EDA, [[2026-09-01-ontology-07-meta|기록 07]]의 Meta 전건 판정
  (채택 4 · 보류 1 · 기각 4 · 항등식 9 · 외생 노드 3종), [[2026-09-01-ontology-08-agent|기록 08]]의
  Agent 검증 데모(현황 질문 · 원인 질문 두 갈래, 게이트 3항목 통과)까지 끝났다.
- 그 위에서 [[2026-09-01-ontology-09-agent-app-plan|기록 09]]가 데모 앱 구축 계획을 세웠다 —
  검증까지 끝난 스택을 사람이 눌러 볼 수 있는 앱으로 내리는 계획이다.
- 이 baseline 은 그 note 기록을 제품 문서 파이프라인(00→10→20→30)으로 내리는 첫 단계다.
  기록 09 를 날것 입력 1건으로 등재해, 이후 decision·spec 이 이것을 근거로 갈라지게 한다.

## Why It Matters

- 다음 단계(수집 파이프라인)의 **기반**이다. 브론즈를 포함한 DB 와 빌드의 DB 이식이 지금
  서 있어야, 파이프라인 단계는 「브론즈에 새 데이터가 들어오면 같은 길을 자동으로 타는 것」이
  되고 갈아엎을 것이 없다.
- **문서가 앱의 설명서이고 앱이 문서의 증명**이 되는 구조를 세운다. 각 계층 화면이 해당
  기록을 근거로 달고 있어, 결과만 보이는 대시보드와 갈린다.
- 어느 계층이든 원본까지 드릴다운할 수 있어야 온톨로지 데모라는 것이 기록 09 의 판단이다 —
  재처리·감사·드릴다운은 브론즈가 있어야 성립한다.

## Possible Direction

- 기록 09 §3 의 구현 순서 8단계를 그대로 탄다 — 브론즈 적재 → 빌드 DB 이식 → 계층 탐색 뷰
  → 조회 도구 4종 → 그래프·예보 → 에이전트 루프 → 웹 통합 → 회귀 테스트.
- **웹 형태 — 기록 09 이후 경과 (2026-09-02).** §3 의 7단계 「FastAPI 단일 페이지(또는 Streamlit)」
  미결이 정식 프론트로 전환됐다: 기존 `app/front/`(Next.js) 통합 3페이지 — 채팅 · 모니터링 ·
  데이터. 백은 `app/ontology-agent/`(FastAPI). 이 전환 자체는 10-decision 에서 굳힌다.
- 디자인은 별도 세션에서 진행 중이다 — 이 baseline 의 범위 밖.
- 미결로 남은 것: 6단계의 LLM 경로(착수 시 ADR-04 확인이 첫 작업).
