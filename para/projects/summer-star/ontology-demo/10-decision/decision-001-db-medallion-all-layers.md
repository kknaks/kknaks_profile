# DB = 메달리온 전 계층 — 브론즈까지 한 DB 에 담고 빌드를 DB 로 이식한다

SQLite 한 DB 에 `bronze_*`(원형) · `silver_*` · `gold_*` · `ontology_*`(nodes·edges) 를 전부
적재한다. 기존 build 스크립트는 입출력만 파일에서 DB 로 갈아 끼우고, 변환 규칙과 게이트는
기록 04·05 의 것을 그대로 쓴다 — 이식이지 재설계가 아니다.

> baseline의 날것 입력을 spec으로 내리기 전에 적용 방향을 정하는 문서.
> 기능 계약 상세는 `20-spec/`, 실제 작업 순서는 `30-work/`에 둔다.

## Context

- 관련 baseline: [[baseline-001-demo-agent-app|BASE-001]]
- 지금까지의 산출물은 파일이다 — 기록 01~08 은 원천 파일을 읽어 실버·골드 CSV 와
  nodes/edges CSV 를 냈다. 앱은 그것을 읽어야 한다.
- 그런데 앱의 요구가 「어느 계층이든 내려가서 원본까지 볼 수 있어야 한다」이다(BASE-001 원칙).
  골드와 그래프만 저장하면 드릴다운의 끝이 없다.
- 다음 단계(수집 파이프라인)는 이 빌드를 자동으로 트리거하는 것이 되어야 한다. 그때 빌드가
  파일을 읽고 있으면 갈아엎어야 한다.
- 결정이 필요한 이유: **무엇을 DB 에 담을지**와 **빌드를 어떻게 옮길지**가 이후 모든 화면·도구의
  전제다. 조회 도구도, 계층 탐색 뷰도 이 위에 선다.

## Options

### 적재 범위

| Option | Description | Pros | Cons | Notes |
|---|---|---|---|---|
| A | 골드 + 온톨로지만 DB, 브론즈·실버는 파일 유지 | 적재량 최소 · 빌드 손 안 댐 | 드릴다운이 골드에서 끊긴다 · 재처리·감사 근거가 파일에 흩어짐 | 기각 |
| **B** | **브론즈·실버·골드·온톨로지 전 계층을 한 DB 에** | 어느 계층이든 같은 방식으로 조회 · 재처리·감사·드릴다운 성립 | 적재 스텝(브론즈 적재) 하나가 늘고 DB 가 커진다 | **채택** |
| C | 계층별로 DB 를 분리 | 계층 경계가 파일로 드러남 | 조인·드릴다운마다 커넥션이 갈림 · 데모 규모에 과잉 | 기각 |

### 빌드 전환 방식

| Option | Description | Pros | Cons | Notes |
|---|---|---|---|---|
| a | 빌드는 파일 그대로 두고, 산출 CSV 를 DB 로 밀어 넣는 적재기를 따로 | 빌드 무수정 | 파일이 여전히 중간 산물로 남는다 · 파이프라인 단계에서 또 옮겨야 함 | 기각 |
| **b** | **빌드 스크립트의 입출력을 DB 로 전환 — 변환 규칙·게이트는 기록 04·05 그대로** | 파이프라인 단계가 「같은 빌드의 자동 트리거」로 끝난다 | 기존 게이트를 DB 위에서 다시 통과시켜야 한다(검증 비용) | **채택** |
| c | 빌드를 DB 기준으로 재설계 | 이상적인 구조 | 검증이 끝난 변환 규칙을 다시 검증해야 한다 — 이번 범위 아님 | 기각 |

## Decision

- **채택**
  - SQLite 한 DB 에 `bronze_*`(vegas 예약 원장 · 리뷰 · nexus 원형) + `silver_*` + `gold_*` +
    `ontology_*`(nodes·edges) 를 전부 적재한다.
  - 기존 build 스크립트(reservations · catalog · reviews · gold)의 **입출력을 파일에서 DB 로
    전환**한다. 변환 규칙·게이트의 명세 SoT 는 기록 04·05 이고, 그것을 바꾸지 않는다.
  - 게이트는 DB 위에서 재실행해 통과를 확인한다 — 브론즈 행수 대사(오차 0), 빌드 재현
    (DB 기반 재빌드 산출물 = 기존 CSV 산출물), 온톨로지 고아 0.
- **기각**: 골드만 DB(A) · 계층별 DB 분리(C) · CSV 사후 적재(a) · 빌드 재설계(c).
- **보류**: 없음.

## Rationale

- **판단 기준**: 드릴다운이 원본까지 닿는가, 다음 단계에서 갈아엎을 것이 남는가, 검증이 끝난
  것을 다시 검증하게 만들지 않는가.
- **B 인 이유**: 브론즈가 있어야 재처리·감사·드릴다운이 성립한다. 메달리온의 계층 책임 분리가
  그것을 위해 있는 것이고, 브론즈를 빼면 남는 것은 대시보드지 온톨로지 데모가 아니다.
- **b 인 이유**: 다음 단계 수집 파이프라인이 「브론즈에 새 데이터가 들어오면 같은 길을 자동으로
  타는 것」이 되려면, 빌드가 지금부터 파일이 아니라 DB 를 읽어야 한다. 규칙까지 손대면 검증
  자산(기록 04·05 의 게이트 통과 기록)을 잃는다 — 그래서 이식으로 좁혔다.
- **리스크**
  - 게이트 재실행에서 DB 이식 자체가 만든 차이(타입 변환 · NULL 처리)가 나올 수 있다.
    빌드 재현 게이트(대조값 일치)가 그것을 잡는 자리다.
  - DB 파일이 커진다 — 원천·DB 는 로컬 보관(gitignore)이라 레포에는 영향이 없다.

## 근거 개념

- [[medallion-architecture]] — 브론즈·실버·골드의 **계층별 책임 분리**(원본 보존 / 공통 의미
  정립 / 소비 목적 최적화)가 이 결정의 골격이다. 「브론즈를 왜 버리면 안 되는가」의 답이
  그 개념에 있고, 이 결정은 그것을 한 SQLite 파일 안에 접두어로 구현한 것이다.
