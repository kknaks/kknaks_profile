# PII 경계 — 원값은 DB 에 보존하고 표시·응답에서 마스킹한다

`patientName` · `phone` · `birthday` · 리뷰 작성자명은 DB 에 원값으로 남기고, 화면 · API ·
에이전트 응답에서 마스킹한다. 에이전트의 브론즈 접근도 마스킹 뷰만 지난다. 게이트는
「어디에도 원값 노출 0건」이다.

> baseline의 날것 입력을 spec으로 내리기 전에 적용 방향을 정하는 문서.
> 기능 계약 상세는 `20-spec/`, 실제 작업 순서는 `30-work/`에 둔다.

## Context

- 관련 baseline: [[baseline-001-demo-agent-app|BASE-001]]
- [[decision-001-db-medallion-all-layers|DEC-001]] 로 브론즈 원형이 DB 에 들어온다 — 원본
  보존이 곧 PII 를 안고 간다는 뜻이다.
- 동시에 앱은 브론즈 조회 화면을 연다. 사람이 보는 표면과 에이전트가 읽는 표면 둘 다에서
  같은 데이터가 나간다.
- 글로서리에 PII 규칙이 이미 있고, 이 결정은 **그 규칙의 화면판**이다.
- 결정이 필요한 이유: 「보존」과 「노출 금지」가 한 데이터에 동시에 걸린다. 어느 지점에서
  가리는지를 정해야 화면·API·도구 계약이 전부 그 아래에서 정해진다.

## Options

| Option | Description | Pros | Cons | Notes |
|---|---|---|---|---|
| A | 수집 단계에서 PII 를 아예 적재하지 않는다(소거 후 브론즈) | 유출 경로가 원천 봉쇄 | 브론즈가 원형이 아니게 된다 — 행수 대사·재처리·감사가 무너진다(DEC-001 과 충돌) | 기각 |
| **B** | **원값은 DB 에 보존, 화면·API·에이전트 응답에서 마스킹 (뷰 경유)** | 원형 보존과 노출 금지를 동시에 만족 · 가리는 지점이 한 군데(뷰)로 모인다 | 뷰를 우회하는 경로가 생기면 새어 나간다 — 게이트가 그것을 잡는 자리 | **채택** |
| C | 배포용으로 PII 를 지운 DB 사본을 따로 만든다 | 배포 표면에 원값이 물리적으로 없다 | 사본 동기화 축이 늘고, 사본 위에서는 드릴다운·재처리가 반쪽이 된다. 내부 공유 데모(DEC-005)에는 과잉 | 기각 |

## Decision

- **채택**
  - PII 대상: `patientName` · `phone` · `birthday` · 리뷰 작성자명.
  - **DB 에는 원값을 보존**한다(브론즈 원형 유지 — DEC-001).
  - **화면 · API · 에이전트 응답에서 마스킹**해 내보낸다. 브론즈 조회 화면은 마스킹 표시가
    기본이고, 원값을 여는 토글을 두지 않는다.
  - **에이전트의 브론즈 접근은 마스킹 뷰 경유만** 허용한다 — 조회 도구가 원 테이블을
    직접 읽지 않는다.
  - 게이트: 화면·에이전트 응답 어디에도 실명·전화·생년월일 원값 **노출 0건**.
- **기각**: 수집 단계 소거(A) · 배포용 PII 소거 사본(C).
- **보류**: 없음.

### 전제 — 이 결정이 딛고 있는 것

이 데모는 **내부 공유용**이다([[decision-005-internal-demo-deploy|DEC-005]]). 그래서 배포용
PII 소거 사본을 만들지 않는다. **전제가 바뀌면(외부 공개로 전환) 이 결정을 재검토한다** —
그때 다시 보는 것은 C 안(소거 사본)과 마스킹의 강도다.

## Rationale

- **판단 기준**: 브론즈의 원형 보존을 깨지 않는가, 가리는 지점이 한 군데로 모이는가,
  에이전트라는 새 표면까지 같은 규칙이 닿는가.
- **B 인 이유**: 보존과 비노출은 저장 계층이 아니라 **표시 계층에서** 갈라야 둘 다 성립한다.
  뷰 하나를 경계로 세우면 사람과 에이전트가 같은 경계를 지난다 — 규칙이 두 벌이 되지 않는다.
- **에이전트를 뷰 뒤로 넣은 이유**: 프롬프트로 「이름은 말하지 마라」라고 지시하는 것은 경계가
  아니다. 도구가 마스킹된 것만 받으면 지시가 뚫려도 나갈 원값이 없다.
- **리스크**
  - 마스킹 뷰를 우회하는 조회 경로(신규 도구·디버그 엔드포인트)가 생기면 구멍이 된다.
    도구는 뷰만 본다는 것을 도구 계약(spec)에 못 박고, 게이트로 역검증한다.
  - 마스킹 규칙 자체(어느 자리까지 가릴지)는 spec 에서 형식을 정한다.

## 근거 개념

- [[pii-masking]] — 이 결정의 골격 그대로다. 「저장은 원값, 표면은 가림」으로 원본 보존과
  노출 금지의 상충을 가르는 것이 채택안(B)의 근거이고, **가리는 지점을 마스킹 뷰 한 군데로
  모은다**는 것이 사람과 에이전트를 같은 경계 뒤에 세운 이유다 — 소비자마다 각자 가리면
  규칙이 여러 벌이 되어 새 소비 경로가 생길 때마다 구멍이 된다. 「프롬프트 지시는 경계가
  아니다」도 이 개념의 항목이다.
- [[medallion-architecture]] — 「브론즈 = 검증과 보안이 없는 영구 저장소가 아니다」라는
  대목이 이 결정의 근거다. 원본 보존이 목적이어도 접근 통제·마스킹은 별개로 필요하다는
  것이 그 개념의 함정 항목이고, 이 결정은 그 조치를 뷰 계층으로 구현한 것이다.
