## 1. 무엇을 했나

업무 상세에 상위·하위는 있는데 선행·후행·프로젝트가 없었다. 낱개로 고치지 않고 세 층
(문서·서버·화면)을 각각 전수조사해 겹쳐 읽은 뒤 화면을 다시 설계했다. 셋의 이유가 달랐다 —
선행은 계약이 다 섰는데 상세 조회가 값을 버렸고, 후행은 같은 표를 반대로 읽으면 되는데 그 문이
없었고, 프로젝트는 서버가 열려 있는데 화면이 한 글자도 안 그렸다. 조사 → 결정 20건 → SPEC-007 →
WORK-007 7단계로 문서를 닫고 backend 셋·frontend 셋을 구현·검수했다. 사용자 실물 e2e 에서
나온 지적 일곱을 반영해 목록을 표에서 이어진 부품으로 바꿨다.

## 2. 적용한 기술·개념

- **한 줄을 양쪽에서 읽기 — 후행은 저장하지 않는다** — `task_predecessors` 한 행이
  「내 선행」과 「나를 기다리는 업무」 둘 다를 답한다.
  - 왜 이걸 골랐나: 사용자가 「선행으로 등록하면 저쪽 후행에 자동으로 뜨는 거 아니야?」라고 짚었다.
    맞는 말이었다 — 방향만 바꿔 읽으면 되니 새 표·새 컬럼·새 쓰기 경로가 하나도 필요 없다.
  - 무엇이 어려웠나: 읽는 방향이 바뀌니 인덱스가 반대쪽에 없었다. `task_id` 에만 있어서
    역방향 질의가 풀스캔이 된다. 그리고 권한이 비대칭이다 — 선행은 내가 골랐으니 읽을 수 있지만
    후행은 **남이 나를 고른 것**이라 내가 못 읽을 수 있다.
  - 근거: `be-report.md` §2 · `platform/persistence.py` · 코드 PR #4

- **못 읽는 것은 건수만 낸다** — 제목·담당자·기한을 빼고 「비공개 업무 N건」으로 접는다.
  - 왜 이걸 골랐나: 0건과 3건은 완전히 다른 정보다. 「내가 늦으면 누가 막히나」의 무게는
    제목을 몰라도 전해진다. 목록에서 통째로 지우면 그 무게가 사라진다.
  - 무엇이 어려웠나: 배열에 자리를 남기면 길이로 존재가 샌다. 자리도 id 도 없이 건수로만 접고,
    셈에는 포함하되 미완으로 세는 규칙을 선행·후행 양쪽에 같게 맞췄다.
  - 근거: `spec-007-task-detail.md` · `review-be-report.md`

- **검증을 복제하지 않고 재사용하기** — 상위 변경을 열면서 기존 `parent_for()` 를 그대로 불렀다.
  - 왜 이걸 골랐나: 읽기 권한·순환·끝난 업무·중심 업무 판정이 이미 생성 경로에 다 서 있었다.
    포크했으면 V-8 판정이 두 벌이 되고 한쪽만 고쳐지는 날이 온다.
  - 무엇이 어려웠나: `_is_central_task()` 는 **현재** 부모를 읽는데 새 게이트는 **이동 후** 값으로
    판정해야 해서 그것만 따로 계산했다. 재사용할 수 없는 자리를 가려낸 것이 핵심이었다.
  - 근거: `modules/work/application.py` · `be-report.md` §2

- **선행은 시작을, 하위는 완료를 막는다** — 같은 「막힘」을 두 축으로 가른다.
  - 왜 이걸 골랐나: 스펙이 `WORK_PREDECESSORS_UNFINISHED` 와 `WORK_CHILDREN_UNFINISHED` 를
    합치지 말라고 명시했다. 화면에서 한 낱말로 뭉개면 계약이 깨진다.
  - 무엇이 어려웠나: 프론트에 `blocking` 이 네 갈래로 섞여 있었다 — 선행 6건 · 하위 15건 ·
    캘린더 블록 4건 · 맨몸 16건. 낱말이 같다고 같은 것이 아니었다.
  - 근거: `fe-survey-report.md` §1 · `spec-007-task-detail.md`

- **CSS 스코프가 죽는 자리** — 규칙을 클래스로 가두면 그 클래스를 붙이는 것까지가 한 벌이다.
  - 왜 이걸 골랐나: 전역 이름 충돌을 막으려고 `.scax-td` 스코프를 줬다. 판단 자체는 옳았다.
  - 무엇이 어려웠나: **클래스를 아무 데도 안 붙였다.** 129줄이 전부 죽은 규칙이었는데 jsdom 이
    CSS 를 계산하지 않아 테스트 1082건이 초록이었다. 검수가 전수 grep 으로 잡았다.
    고친 뒤에도 「선택자 판이 0개를 세며 초록」이라 두 번째로 거짓이 났다.
  - 근거: `review-fe-report.md` FAIL-1 · `TaskDetailRelations.test.tsx`

- **폭이 안 늘어나는 이유는 체인에 있다** — `flex` 를 고쳐도 안 되면 그 아래를 봐야 한다.
  - 왜 이걸 골랐나: 세 판을 폭 하나에 썼다. `.rel__select` 만 보고 두 번 틀렸다.
  - 무엇이 어려웠나: `flex: 1 1 auto` 는 basis 를 `width` 에서 가져오는데 그 `width` 가
    내가 같은 판에서 넣은 `fit-content` 였다. 그걸 고친 뒤에도 안 됐는데, 진짜 원인은
    한 칸 더 아래 `span.popover-root` 의 `display: inline-flex` 였다.
    **폭은 체인 전체가 이어져야 닿는다. 한 칸만 봐서는 매번 다음 칸에서 끊긴다.**
  - 근거: `fe-report.md` §13~15 · `task-detail.css`

## 3. 막혔던 것 / 사고

- **CSS 129줄이 통째로 죽어 있었는데 테스트가 초록이었다** → jsdom 은 CSS 를 계산하지 않아
  「테스트 통과」가 「보인다」를 보장하지 못한다 → 검수가 소스 전수 grep 으로 잡았고,
  CSS 파일에서 선택자를 직접 읽어 마크업과 대조하는 판을 세웠다.
  그런데 그 판도 처음엔 vitest 의 CSS 스텁 때문에 **0개를 세며 초록**이었다 —
  워커가 스스로 「46/46 은 거짓이었다」고 정정하고 손으로 적은 목록과 대조하게 바꿨다.

- **`WorkModals.tsx` 에 원시 NUL 바이트 둘** → `join()` 구분자를 이스케이프 없이 실제 제어문자로
  적었다 → **grep 이 그 파일을 binary 로 보고 건너뛴다.** 워커·검수·코디 셋 다 그 파일에 대한
  grep 근거가 조용히 비어 있었다. 내가 「출력이 삼켜졌다」고만 보고 파이썬으로 우회했는데
  원인이 코드 안에 있었다. 검수가 잡았다.

- **셀렉터 폭을 세 판에 걸쳐 고쳤다** → 체인 중간 한 칸씩만 보고 추측으로 좁혔다 →
  마지막에 `.cell` 부터 `.select-trigger` 까지 일곱 칸을 전부 나열하고 각 단계의 CSS 원문을
  확인해서야 끊긴 고리(`popover-root`)가 나왔다. 그 사슬을 테스트로 고정했다.

- **사용자 말을 거꾸로 읽었다** → 「너비 왜 이래」를 「줄여라」로 읽고 내용 폭으로 줄였는데
  「칸을 채워라」였다 → 되돌리는 데 한 판을 더 썼다. 화면을 못 보는 상태에서 애매한 지적을
  추측으로 해석한 것이 원인이다.

- **로컬 스택이 메모리 부족으로 세 번 죽었다** → 병렬 vitest 가 워커 11개를 띄워 스택을
  밀어냈다 → 워커에게 `--no-file-parallelism` 만 쓰라고 지시하고, 사용자 e2e 중에는
  코디도 무거운 검증을 돌리지 않기로 했다.

- **코디 핸들이 세션 재연결로 바뀌었다** → 브리프에 박힌 옛 핸들로는 보고가 안 닿는다 →
  워커가 preamble 값으로 보내며 알려줬고, 브리프 17개의 핸들을 일괄 교정했다.

- **`make verify` 의 exit code 를 파이프로 가렸다** → `| tail -40` 을 붙여 `tail` 의 종료 코드를
  읽고 「통과」로 보고했는데 실제로는 `frontend-test` 가 실패해 있었다. 파이프 없이 다시 돌렸다.
