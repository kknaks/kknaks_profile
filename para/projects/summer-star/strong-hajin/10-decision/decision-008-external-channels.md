BASE-006 이 눕힌 요구·시안·시험·조사 위에서, 외부 채널 연동의 **1단계**를 정한다.

> 이 결정은 **무엇을 채택하고 무엇을 버리는가**까지다.
> **계약 조문(필드·상태값·오류·엔드포인트·저장 구조)은 다음 판 SPEC 의 몫**이고, **구현 계획·Phase 는
> `30-work/` 의 몫**이다. 테이블 이름·API 경로는 여기 적지 않는다.
>
> **결정의 유일한 근거는 원장** `orchestration/work/strong-hajin-inbox/_RESUME.md` §2 (2026-10-05~06) 다.
> 원장에 없는 결정을 이 문서가 만들지 않는다 — 원장이 열어 둔 것은 § Open Questions 로 간다.
> 원장 행과 결정의 대응은 **부록**이 센다.
>
> **accepted (2026-10-06).** 사용자가 결정 전체와 Open Questions 처리를 확인했다. OQ-801~810 은

## Context

- 관련 baseline: **BASE-006**. 그 계보로 BASE-001(업무 페이지 — 메일·그룹웨어를 원문 미결 C-2 로 둠)이 있다
- **업무의 생명주기와 「업무 > 수신함」의 계약을 바꾸지 않는다** — SPEC-001 U-12 · DEC-001 의 참고 읽음은 그대로다
- 이번 결정이 여는 것은 **외부 메시지가 들어와 쌓이는 길**(설정 연동 · 수집 · 메시지함 조회·읽음·답장)과
  **설정의 프로필 메뉴**다. **AX 가 메시지를 읽고 업무로 옮기는 일은 2단계**다(D-03)

시안-원은 「흩어진 메일·대화를 우리 DB 로 적재」하는 틀을 세 채널에 같은 모양으로 그렸다 —
IMAP 폼 · 봇 권한 · 이름 입력 · 수집 주기 · 참여자 동의 문구 (BASE-006 입력 2).
실물 시험과 조사가 그 틀을 채널마다 다시 세우게 했다.

| 무엇 | 시험·조사가 답한 것 | 근거 |
|---|---|---|
| 메일 | **Gmail API 동의 1회로 읽기+보내기**가 함께 열린다 | BASE-006 입력 4-1 |
| 슬랙 | **사용자 토큰**이면 관리자 승인 없이 채널·비공개·DM·그룹 DM 을 다 읽는다 — 봇은 남의 DM 을 못 읽는다 | BASE-006 입력 4-2 |
| 카톡 조회 | Mac 은 **키를 기기 값에서 유도**해 로컬 DB 를 읽는다 — 서버가 키를 들 필요가 없다 | BASE-006 입력 5-1 |
| 카톡 발송 | **UI 자동화 · 텍스트만 · 불안정** | BASE-006 입력 5-1 |
| 카톡 첨부 | **CDN URL 이 며칠 만에 만료**된다 — 클릭할 때 받는 길이 안 선다 | BASE-006 입력 5-2·5-3 |
| 카톡 동의 문구 | 로컬 DB 를 읽는 방식엔 상대에게 안내·동의를 받는 **기술적 단계가 없다** | BASE-006 입력 5-1 |

## Options

원장이 선택지를 놓고 고른 자리만 적는다.

### 메일을 어떻게 붙이나

- **M1 — IMAP + 앱 비밀번호.** 시안-원의 길. 같은 비밀번호로 SMTP 답장도 된다. 서버가 비밀번호를 들고 있어야 한다
- **M2 — Gmail API(OAuth).** 동의 1회로 읽기·보내기 권한을 함께 받는다. 클라우드 프로젝트에 클라이언트를 둬야 한다

원장 R-12 가 「Workspace 관리자 콘솔 접근 여부로 결정」이라고 미결로 두었고, 실물 시험(R-13)이 통과한 뒤
**M2 를 채택했다**(R-14 → D-09). 둘 자리는 「회사 GCP 프로젝트(①) — 이직·상용 때 정식 심사(③)로 이전」이다.

### 카톡 첨부를 어떻게 보이게 하나 (`kakao-attach-survey.md` §3)

- **(가) 서버가 CDN URL 로 중계** — 「저장 안 함」에 맞지만 사진 URL 이 ≈3일이면 끊긴다
- **(나) Rust 앱이 로컬 파일 중계** — Mac 로컬에 메시지 번호로 집을 저장소가 없다
- **(다) 수집하는 순간 받아 보관** — 확실하지만 「첨부 저장 안 함」 원칙의 예외가 된다

**(다)를 카톡에만 채택했다**(R-36 → D-30). 메일·슬랙은 원칙대로 중계다(D-29).

## Decision

### 채택

**쉰 건이다.** 원장 §2 의 서른아홉 행을 주제별로 묶은 마흔 건(D-01~D-40)에, 2026-10-06 사용자 결정으로
닫힌 Open Questions 열 건(D-41~D-50)을 더했다. 순서는
범위·단계(D-01~D-05) → 화면 역할(D-06~D-08) → 메일(D-09~D-10) → 슬랙(D-11~D-13) → 카톡(D-14~D-21) →
실시간·백필(D-22~D-23) → 저장·소유·삭제·첨부(D-24~D-31) → 답장(D-32) → 화면 모양(D-33~D-35) →
프로필 설정(D-36~D-37) → 과정(D-38~D-40) → OQ 처리(D-41~D-50) 이다.

## 시안과 달라진 점 — 한 줄씩

확정 시안이 정본이다. 화면 모양의 차이는 **시안을 기본값**으로 둔다.
범위·저장이 걸린 차이는 원장을 따르고, 시안 문구를 고칠지는 SPEC 이 받는다.

1. 원장 표기 「슬랙 - #채널명」 한 줄 ↔ 시안 카드는 **`슬랙` 배지 + 방 이름 두 줄**, 본문 머리는 「슬랙 · 채널」 (`design-change-1.md` §5) — **시안 기본값**
2. 원장 R-11 「스레드 답글은 같은 방 카드에 「답글」 표시」 ↔ 시안은 **부모 아래 「답글 N개」 줄 → 오른쪽 패널**(D-34) — **시안 기본값**
3. 시안 연결 해제·빼기 확인 창 문구 「**메시지함에서 사라진다**」 ↔ 원장은 **소프트 딜리트**(D-27) — 보이는 결과는 같고 되살리기는 시안에 없다 → **D-46**(다시 연결하면 되살림)
4. 시안은 슬랙이 끊기면 적재 상태 셋째 칸을 「**멈춤 — 연결 끊김**」으로 바꾼다 ↔ 원장은 「실시간」만 말한다 (`design-change-2.md` §5) — **시안 기본값**
5. 시안 메일 끊김 = **계정 하나**, 슬랙 끊김 = **워크스페이스 전체** (`design-change-2.md` §5) — 원장 언급 없음 · **시안 기본값**
6. 시안은 슬랙 **워크스페이스를 하나만** 그린다 — 원장 언급 없음 · **시안 기본값**
7. 시안은 메일 첨부 「한 번에 25MB까지」 · **넘는 파일이 있으면 보내기를 막는다** (`design-change-3.md` §5) — 원장 언급 없음 · **시안 기본값**
8. 시안은 슬랙 첨부 한도 문구가 없다 — 원장 언급 없음
9. 시안 프로필 머리 = **이름 · 소속 · 직책 · 직무**(명부 값) ↔ 원장 「이름·직무」 (`design-change-4.md` §5) — **시안 기본값**
10. 시안은 프로필 이미지·AX 캐릭터를 **고르면 바로 저장**한다 — 「프로필 저장」 단추 없음 (`design-change-4.md` §2.3) — **시안 기본값**

## 근거 개념

- [[webhook]] — 실시간 동기화(D-22)는 **상대가 사건을 알려 오는** 길이다. 슬랙 이벤트와 Gmail 푸시 신호가
  그 자리이고, 받는 쪽이 놓친 구간은 **재시작 때 마지막 시점 이후를 훑어** 메운다
- [[slack-bot]] — 봇 토큰과 사용자 토큰의 **권한 범위가 다르다.** 봇은 자기가 초대된 곳만 보고 남의 DM 을 못
  읽는다. 사람이 자기 DM 을 메시지함에 쌓으려면 그 사람의 토큰이어야 한다(D-11)
- [[polling]] — 카톡엔 알려 오는 쪽이 없다. Rust 앱이 로컬 DB 를 **물어서** 새 것을 찾는다(조사:
  `kakaocli` 고수위 폴링 · BASE-006 입력 5-1). 메일·슬랙과 카톡의 수집 방식이 갈리는 이유다(D-14 · D-22)

⚠ **소프트 딜리트(D-27) · OAuth 동의(D-09) 를 다루는 개념 노트는 `para/areas/concept/` 에 없다.**
이 발주의 allowed_paths 가 문서 넷으로 잘려 있어 여기서 만들지 않는다 — 작업 마감 때 개념 소화로 넘긴다.
