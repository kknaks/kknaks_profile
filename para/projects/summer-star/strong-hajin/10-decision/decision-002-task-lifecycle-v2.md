# 요청은 수락으로 담당을 확정하고, 업무는 재귀 하위를 갖는다 — W1 위에 v2 를 얹는다

2026-09-17 사용자가 승인한 정의·생명주기·작업계획서 v2 를, 이미 구현이 살아 있는 W1
(DEC-001 · SPEC-001 · SPEC-002 · WORK-001) 위에 **무엇을 뒤집고 무엇을 남기며** 얹을지 정한다.

> 이 결정은 **백엔드 외부 계약 + 확정 시안 기준의 UX 계약까지**다.
> WORK 계획과 코드는 스펙 검수 뒤 별도 발주다.
>
> **범위가 한 번 갱신됐다 (2026-09-17 오후).** 초판은 「백엔드 외부 계약까지 · 화면·문구·배치는
> 이번 결정 밖」이었다. 확정 시안이 내려오면서 사용자가 「이제 프론트까지 같이 작업 할 수 잇는거
> 같아서」로 승인했고, 코디네이터가 **WORK-002 를 BE v2 + 새 시안 FE 통합 계획**으로 받았다.
> **초판 문장은 지우지 않고 이 각주로 대체한다**(BASE-002 입력 2). **E2E 는 사용자 담당 그대로다.**

## Context

- 관련 baseline: **BASE-002**(v2 원문 사실 + 2026-09-17 현재 관측). BASE-001 은 그 아래 계보로 남는다.
  **2026-09-17 사용자가 `example.md`(사례집, 649줄)를 예시 원문으로 추가 지정했다.**
  전문을 읽어 BASE-002 § 원문이 확정한 것 — example.md(`E-1`~`E-13`)와
  § example.md 가 연 미정(`EU-1`~`EU-18`), § §10 전체 사례 10단계로 반영했다.
  이 문서는 절마다 **합의 / 미정 / 검토안**을 스스로 가르므로 **그 표기를 그대로 보존**한다 —
  검토안과 미정 분기를 정책으로 올리지 않는다(E-11). **순환 차단 1건이 작업계획서와
  어긋나며 작업계획서가 우선**이다(BASE-002 § 입력 3).
- 문제/기회: W1 이 「수락 없이 즉시 배정」을 계약으로 세우고 **미커밋 구현이 작업본에 살아 있다**
  (BASE-002 § 현재 관측 O-1). v2 는 그 자리에 수락 대기를 되돌리고, W1 이 범위 밖으로 둔
  **상하위 관계**를 1차로 끌어온다.
- 결정이 필요한 이유: 뒤집히는 것과 남는 것을 문서로 못 박지 않으면 두 방향으로 샌다 —
  W1 기록을 「v2 를 이미 지원한다」로 오독하거나(BASE-002 § 과거 관측과의 차이가 그 예다 —
  「기능이 존재한다」와 「요구대로 돈다」가 다르다),
  반대로 W1 이 세운 유효 보장(멱등 키 · 활성 담당 유일성 · 권한 재검사 · AX 사람 확인 ·
  실제 actor 기록)을 반전과 함께 통째로 걷어낸다.

## Options

| Option | Description | Pros | Cons | Notes |
|---|---|---|---|---|
| A | SPEC-001·002 를 그 자리에서 고쳐 v2 를 반영 | 문서가 하나로 모인다 | **과거 기록이 지워진다.** W1 이 왜 즉시 배정이었는지가 사라져 같은 논의가 반복된다 | 브리프 §1 이 금지 |
| B | **SPEC-003 을 새로 세우고 SPEC-001·002 에는 대체 안내만 단다** | 두 차수가 나란히 남는다. W1 구현의 근거가 보존된다 | 문서가 늘고 어느 절이 유효한지 독자가 한 번 더 확인해야 한다 | **채택** |
| C | v2 전체를 한 SPEC 으로 다시 쓰고 SPEC-001·002 를 `_archive/` 로 내린다 | 읽는 자리가 하나 | W1 구현이 살아 있는데 그 계약을 아카이브로 내리면 **지금 도는 코드의 계약 출처가 사라진다** | 기각 |

## Decision

### 채택

**D-1. 문서는 SPEC-003 신규 + 기존 두 스펙의 상단 안내다.**
SPEC-001·SPEC-002 의 본문과 버전 이력은 **한 줄도 지우지 않는다.** 머리에 「어느 절이
SPEC-003 으로 대체되었는지」와 SPEC-003 참조만 단다.

**D-2. 범위는 백엔드 외부 계약 + 확정 시안 기준의 UX 계약까지다 (2026-09-17 오후 갱신).**
API·MCP 가 내는 입력/응답/상태/허용 명령/오류/권한/동시성/멱등성/관계 조회가 SPEC-003 의 몫이고,
**확정 시안이 그리는 화면의 UX 계약**이 SPEC-003 §2 로 들어온다.

> **초판 D-2 를 보존한다** — 「범위는 백엔드 외부 계약까지다. UI 동작 원문은 **미래 프론트 요구로
> 보존**하되 이번 구현 책임은 그 화면이 필요로 하는 API 계약으로 분리한다」. 프론트가 범위에
> 들어오면서 **「미래 요구로 보존」이 「이번 판의 UX 계약」으로 바뀐 것**이고, API 계약이 화면
> 책임과 분리된다는 원칙은 그대로다.

**갱신 뒤에도 Out 인 것** — 컴포넌트 구현·DS 부품 신설·코드 경로·구현 phase·E2E.
SPEC 은 **무엇을 보여 주고 무엇을 할 수 있어야 하는가**까지 적고, 어떻게 만드는지는 `30-work/` 다.

**D-3. 요청 경로의 담당 확정 시점을 수락으로 되돌린다 — v2 우선.**
발송 시 Task 를 `open` 으로 만들고 상위에 연결하되, 담당은 **수락으로 확정**한다(V-9·V-10).
W1 의 「발송 즉시 활성 담당」은 **일반 요청 경로에서 물러난다.**

**이 되돌림은 경로가 아니라 행위에 걸린다.** `POST /api/tasks` 에 **타인** `assignee_id` 를 실은 생성은
W1 에서 이미 **수평 요청**이다 — `decide_task_creation()` 이 그 입력을 `horizontal` 로 갈라
`WORK_REQUEST_CREATE` 역량을 묻고 `WorkRequestApplication.create()` 를 부른다(BASE-002 O-26).
따라서 **입구를 없애거나 타인 지정을 거부할 필요가 없다.** 같은 행위이므로 같은 계약이 걸린다 —
그 갈래도 v2 에서 `open` Task + 수락 대기로 선다. **REST · MCP · AX 어느 입구로 들어와도 같다**(K-10).
관리자 배정(`managed`)은 이 입구로 들어오지 않으므로(O-26) 이 결정이 배정을 건드리지 않는다.

**D-4. 그러나 수락 대기를 수행 상태값으로 만들지 않는다.**
SPEC-001 이 세운 「기다림은 상태가 아니라 표시다」를 유지한다. Task 는 `open` 이고
수락 대기는 **파생 표시**로 드러난다. 이유는 둘이다 — (1) v2 §2.4 가 수락 후에도
「시작 전 상태를 유지한다」고 못 박으므로 수락 전후의 수행 상태가 **같아야 한다**.
(2) 생명주기 v2 §5.1 이 「제출·확인 단계의 정확한 상태값」을 미정으로 남겼으므로, 상태 enum 을
늘리는 쪽이 오히려 미정을 확정으로 굳힌다.

**D-5. 하위의 「완결」 판정을 상태 하나에서 상태 + 승인 둘로 넓힌다.**
v2 §2.6·§5.4 는 「요청한 하위 업무는 요청자가 승인해야 완료된 것으로 본다」이다. 현행은
**하위의 완결을 `state` 만으로 판정한다**(BASE-002 O-20). **그것이 이번에 닫는 자리다.**

> **정정 (2026-09-17 재검수 1차).** 초판 D-5 는 「요청받은 업무에서는 **하위 검사 자체를
> 건너뛴다**(O-19)」를 두 번째 근거로 들었다. **절반만 맞았다.**
> ① **승인 쪽 차단은 이미 있다** — `accept_delivery` 에 하위 완결 검사가 걸려 있다(O-34).
> ② 검사가 없는 자리는 **완료 보고 제출**이고(O-34), 그것은 v2 가 **미정으로 연 자리**다(OQ-203).
> ③ O-19 의 건너뛰는 가지는 요청 Task 에서 **도달하지 않는다**(O-19 정정 · O-33).
> **새로 닫는 것은 O-20 하나다.** 「승인에서 막는다」를 신규 구현으로 적지 않는다.

**D-6. 제안–동의의 「의미」를 공통으로 둔다. 저장 모양을 하나로 강제하지 않는다.**
담당 변경(V-18) · 수락 후 취소(V-19) · 수락 후 조건 변경(V-20)이 전부 「제안하고 상대가
응답할 때까지 **기존 상태 유지**」다. 셋을 각각 다른 뜻으로 만들면 「응답 전 기존 유지」가
세 번 따로 판정되고 한 곳만 어긋난다. 그래서 **공통으로 묶는 것은 규칙 넷**이다 —
(1) 제안만으로는 아무것도 바뀌지 않는다 (2) 제안 상태가 `대기 → 동의 / 동의하지 않음 / 철회` 넷이다
(3) 응답은 **지정된 응답자만** 부른다 (4) 제안·응답·적용이 **각각** 이력으로 남고 회차가 필수다.

**표면은 둘로 남는다 (제안).** 담당 변경은 W1 이 이미 세운 `task-assignments` 표면을 그대로 쓰고
(`accept`·`decline`·`cancel` 과 그 판단 항목이 이미 있다 — BASE-002 O-15), 취소·조건 변경은
`proposals` 로 받는다. **담당 변경을 `proposals` 의 `kind` 로 옮기지 않는다** — 옮기면 살아 있는
표면을 이유 없이 갈아엎게 되고, 그 자체가 정책이 아니라 저장 선택이다(P-12).
L-2 가 이것을 허용한다 — 「행위가 다르다는 이유로 전체 코드나 테이블을 따로 만들 필요는 없다」는
**합쳐도 된다**는 허가이고 **합쳐야 한다**는 요구가 아니다. 새 테이블을 세울지 기존 것을 넓힐지는
**구현자 몫**이다(M-10).

**D-7. 저장 깊이는 열고 표시 깊이만 둘로 둔다.**
`parent_task_id` 의 한 단계 제한(O-6)을 걷는다. 순환·자기 참조는 막는다. 상세 조회는
**저장 깊이와 무관하게 직속 하위만** 반환한다(L-11) — 표시 두 단계는 그 결과로 성립하고,
화면이 강제하는 규칙이 아니다.

**D-8. 생성 규칙은 담당자 기준으로 판정한다.**
같은 담당자의 직접 작업은 중심 업무 직속에만 둔다(V-8). 다른 사람이 수락한 요청 업무는
그 사람의 **새 중심 업무**가 되어 직속 하위와 요청을 갖는다(V-7). 따라서 **「부모가 없으면
중심 업무」로 판정하지 않는다** — 작업계획서 §4.2 가 같은 것을 지시한다.

**D-9. W1 이 세운 유효 보장은 전부 남긴다.**
멱등 키 필수와 그 유효 범위(행위자 + 명령 종류) · 활성 담당 최대 1 · 영수증 반환 전 **현재
권한 재검사** · AX 실행의 사람 확인 · 「출처는 실제로 명령을 부른 actor」. 되돌리는 것은
**응답 단계**뿐이고 이 다섯은 v2 가 건드리지 않았다. 새로 생기는 명령(수락·거절·철회·제안·
응답·재개)에도 같은 규칙을 건다.

**D-10. `accept()` 는 같은 Task 를 확정하는 명령으로 바뀐다.**
현행 `accept()` 는 **Task 를 새로 만든다**(O-3). v2 §2.4 는 「같은 Task 와 상위 연결을 유지」다.
새 Task 를 만드는 수락 경로는 v2 계약과 양립하지 않는다.

**D-11. 담당 변경 거절과 요청 최초 거절을 가른다.**
현행은 같은 `decide()` 를 지나며 **둘 다 Task 를 취소**한다(O-13). v2 는 최초 거절만 취소이고
(V-11), 담당 변경 거절은 **기존 담당 유지·Task 유지**다(V-18). 사건을 갈라 기록한다(L-12).

**D-12. 요청 관계를 읽기 권한의 세 번째 길로 연다.**
현행은 프로젝트 범위·조직 범위 둘뿐이다(O-21). 요청자가 **자신이 요청한 Task 의 하위 트리와
그 Task 들에 연결된 자료**를 읽는 길을 연다(V-21). 같은 판정이 Task 상세만이 아니라
**자료 본문·다운로드·검색·미리보기**에 함께 걸린다 — 한 곳만 열면 다른 곳에서 샌다.

**D-13. 기존 데이터는 전환하지 않는다.**
발송 즉시 active 로 선 기존 행을 **일괄 pending 으로 되돌리지 않고**, 수락 사실을 만들어내지
않는다(P-8). 상위가 없던 요청의 부모를 추정해 채우지 않는다(P-9). 거절로 취소된 재배정
업무를 임의 복원하지 않는다(P-10). 운영·사용자 DB 초기화는 마이그레이션 대안이 아니다(P-11).
**cutover 경계는 SPEC-003 이 계약으로 적고, 절차와 스크립트는 WORK 몫이다.**

**D-15. `example.md` 의 「하지 않는다」를 계약으로 싣는다.**
사례집이 합의로 적은 금지 다섯을 SPEC 이 명시적으로 갖는다 — 배정 실패의 **자동 요청 전환 없음**(E-2) ·
하위 관계가 편하다는 이유로 **요청을 배정으로 바꾸지 않음**(E-1) · **보완마다 자동 하위 Task 없음**(E-3) ·
기한 초과의 **자동 승인 없음**(E-4) · **참고 연결로 하위 관계를 대체하지 않음**(E-6).
금지를 적지 않으면 구현이 「편한 쪽」으로 흐른다.

**D-16. 사용자가 지정한 네 자리는 예시만으로 확정하지 않는다.**
**상위 없는 독립 요청의 허용 범위**(EU-3, example §3.1 이 「검토 사례」로 표시) ·
**담당 변경 후 기존 하위 구조의 처리**(EU-8) · **상위 관계 이동 정책**(EU-15) ·
**철회와 수락이 동시일 때의 최종 결정 순서와 상위 취소 후 수락 가능 여부**(EU-17).
이 넷은 **열린 채로** 두고, SPEC 은 그 자리에 「기존 동작을 보존한다」와 「모순된 상태를
만들지 않는다」까지만 쓴다. **우선순위 규칙을 예시에서 읽어 확정하지 않는다.**

**D-17. R·Q·D 를 스키마 근거로 쓰지 않는다.**
`example.md` §9·§10 의 예시 ID 와 단계별 확인표는 **실제 DB 조회 결과가 아니다**(E-8).
관계의 **의미**만 읽고 테이블·FK·상태 전이는 거기서 끌어내지 않는다.

**D-18. 기존 동작 보존과 신규 정책 확정을 가른다.**
SPEC 의 각 줄은 셋 중 하나다 — **(정책)** v2 가 확정한 것 · **(제안)** 그 정책의 기술 표현 ·
**기존 동작 보존** 원문이 말하지 않아 지금 코드를 그대로 두는 것. 세 번째를 **신규 확정으로
적지 않는다.** 본인 업무의 즉시 담당 확정(EU-1) · 상위 없는 요청 허용(EU-3) · 협의 경로 ·
거절 사유 필수가 그 자리다.

**D-14. 미정은 미정으로 둔다 — 그러나 착수를 막지 않는다.**
신규 배정 · 담당 없는 업무의 첫 지정 · 배정의 수정/취소/재개 · 체크리스트 강제 · 중간 검토 ·
공동 담당 · 복수 부모 · 상위 취소 전파 · 자동 수락은 **요청 정책으로 덮지 않는다**(P-13~P-16).
현행 동작을 회귀로 지키고, 바꿀 정책은 별도 합의 대상으로 표시한다.

### 기각

- **Option A · C** — 위 표.
- **수락 대기를 새 수행 상태값으로 만들기** — D-4.
- **요청과 배정을 위해 테이블·코드를 통째로 가르기** — L-2 가 명시적으로 불필요하다고 적는다.
- **`assigned` 행을 pending 으로 되돌리는 데이터 전환** — P-8 이 금지.
- **하위 완료로 상위를 자동 완료** — V-17 이 금지.
- **배정에 요청의 수락·거절 정책을 그대로 적용** — L-8 · P-13 이 금지.
- **배정 권한이 없을 때 사용자 의사 확인 없이 요청으로 자동 전환** — E-2 가 「정하지 않았다」.
- **하위 관계를 표현하기 편하다는 이유로 일반 요청을 배정으로 바꾸기** — E-1 이 금지.
- **보완마다 자동으로 하위 Task 만들기** — E-3 이 「정하지 않았다」.
- **기한 초과를 자동 승인으로 처리** — E-4 가 금지.
- **참고 연결을 하위 관계의 대체물로 쓰기** — E-6 이 금지.
- **재개를 「완료 이력을 지우고 새 업무로 만들기」로 구현** — E-5 가 금지.
- **R·Q·D 예시에서 테이블·FK·상태 전이를 끌어내기** — E-8 이 금지.

## Rationale

- **판단 기준**: (1) v2 원문이 답한 것은 v2 로 닫는다 (2) v2 가 「미정」이라 적은 것을 확정으로
  올리지 않는다 (3) v2 가 말하지 않은 W1 계약은 **건드리지 않는다** — 침묵은 폐기가 아니다
  (4) 업무 정책과 기술 선택을 가른다(P-12) (5) 과거 기록을 v2 지원으로 포장하지 않는다.
- **대안 대비 이유**: Option B 만이 「W1 구현이 살아 있는데 그 계약 출처를 지우지 않는다」와
  「v2 가 최신 방향이다」를 동시에 만족한다.
- **리스크**:
  - **C-1 은 enum 한 줄이 아니다.** 요청 응답·담당 상태·수신함·판단함·권한·알림이 함께 움직인다.
    표면 목록을 받아 시작하면 목록 밖에서 실패한다 — WORK 발주 때 같은 검색을 다시 돌린다.
  - **C-5 와 K-3 이 부딪칠 수 있다.** 담당 변경 대기 중 같은 Task 에 active 1 + pending 1 이
    공존한다. 「활성 담당 최대 1」은 **active 에만** 거는 제약이고 pending 을 세지 않는다.
    현행 `active_assignment_for()` 가 둘을 한 조회로 섞는다(O-11) — 여기서 조용히 어긋난다.
  - **C-7 을 열면 기존 요청 업무의 완료가 새로 막힐 수 있다.** 승인 쪽 하위 검사는 **이미 있고**
    (O-34), 새로 켜는 것은 **완결 판정을 `state` + 승인으로 넓히는 것**(O-20)이다. 정상 경로로 생긴
    기존 행은 **판단 행을 갖고 있어 매핑으로 읽히지만**(O-33), **실행 DB 의 예외 행까지 0건이라고
    단정하지 않는다**(U-6). **읽기 전용 점검이 먼저다**(P-4). **근거를 O-19 에서 O-33·O-34 로
    정정했다** (2026-09-17 재검수 1차).
  - **C-10 은 권한을 넓히는 변경이다.** 한 경로만 열고 자료·검색·미리보기를 빠뜨리면 「요청자가
    상세는 보는데 파일은 못 연다」가 되고, 반대로 넓게 열면 **무관한 자료가 샌다.**
  - **U-1(실행 DB 미확인)** 이 남아 있다. ORM 과 실행 스키마가 같다고 전제한 설계는 인덱스·FK
    단계에서 깨진다. `schema_sync` 는 **기존 테이블의 인덱스를 더하지 않는다**(O-24).

## 근거 개념

- [[human-in-the-loop]] — v2 의 뼈대가 이 개념이다. 자동으로 끝까지 가지 않고 **수락 대기 ·
  완료 승인 · 제안 응답 대기**에서 멈춰 사람을 기다리고, 멈춘 자리에서 **다시 이어서** 간다
  (재개 V-19, 보완 재보고 V-14). 「자동 수락·자동 완료 없음」(V-17 · L-7 · L-15)이 이 개념의
  같은 면이다.
- [[optimistic-lock]] — K-4 가 기대는 개념. 상태·값을 바꾸는 모든 명령이 회차를 싣고, 어긋나면
  지금 값으로 다시 읽는다. C-5 가 만드는 active/pending 공존과 C2 의 동시 실행이 전부 이 위에서
  판정된다.

> 새로 세울 개념은 두지 않는다. 이 결정의 나머지는 **사용자가 합의한 업무 정책**이고 일반화해
> 다시 쓸 판단이 아니다. 「기다림을 상태가 아니라 파생 표시로 둔다」(D-4)가 반복해서 쓰이면
> 그때 `para/areas/concept/` 로 올린다 — 지금은 사례가 이 제품 하나뿐이라 계보가 거짓이 된다.

> 같은 모양을 쓴다 **(제안)**」으로 적는다. 완료 확인과 달리 여기에는 **사람이 반드시 있다**

| **`POST /api/tasks` 에 타인 담당을 실은 생성** | **입구를 그대로 둔다.** 그 입력은 W1 에서 이미 **수평 요청**이고(O-26), v2 에서 같은 요청 계약(`open` Task + 수락 대기)을 받는다 | **기존 동작 보존 + D-3.** 입구를 없애거나 타인 지정을 거부하는 것은 **새 정책**이고 원문에 없다. 반대로 **서버가 배정을 요청으로 몰래 바꾸는 것도 하지 않는다**(E-2) — 이 갈래는 원래부터 요청이었다 |
| **회의 후속 승격의 본인 지정 요청** | **허용을 유지한다**(`allow_self_assignment`). v2 에서도 **같은 수락 대기**로 서고 본인이 **명시적으로 수락**한다. 자동 수락을 신설하지 않는다 | **기존 동작 보존**(O-30) + L-15·L-16 · M-7. 승격의 **출처는 회의**이고 **actor 는 누른 사람**이다 — 둘 다 그대로 둔다(K-6) |
| **일반 요청 표면의 본인 지정** | **서버가 열어 주지 않는다** — `allow_self_assignment` 를 켜는 호출부는 회의 승격 둘뿐이다 | **기존 동작 보존**(O-30 전수 grep). 새로 막는 것이 아니라 지금 그렇다 |
| **수락된 요청 Task 의 직접 취소** | **거부한다.** 취소는 제안–동의로만 반영된다 | **원문 확정**(정의 v2 §2.8 = V-19 · 생명주기 §6.1). 직접 취소를 남겨 두면 동의 경로가 선택지로 전락한다 |
| **수락 전 요청 Task 의 직접 취소 권한** | **현행 그대로**(담당자·요청자·관리자). v2 가 연 것은 요청자의 `withdraw` 이고, 다른 사람의 취소 권한을 **넓히지도 좁히지도 않는다** | **기존 동작 보존.** V-19 는 「수락 전에는 요청자가 철회한다」까지이고 타인의 취소를 논하지 않았다 — 침묵은 폐기가 아니다(Rationale 판단 기준 3) |
| 거절 사유 | **필수** (요청 거절 · 담당 변경 거절 모두) | 현행이 이미 필수(O-15). v2 는 미정으로 두었고 현행을 낮추지 않는다 |
| 협의(negotiating) | 기존 상태값과 경로를 **그대로 쓴다** | v2 §3.1 이 협의를 흐름으로만 정의했다 |
| 상위 없는 독립 요청 | **지금처럼 허용한다** | **기존 동작 보존.** example §3.1 이 「검토 사례 — 확인이 필요하다」이므로 **새로 막지도 새로 확정하지도 않는다**(EU-3 · M-11) |
| 상위 관계 **이동** | **명령을 만들지 않는다** | EU-15 · M-13. 없던 기능을 예시에서 만들어 내지 않는다 |
| 담당 변경 후 기존 하위 구조 | **그대로 둔다.** 소급 재배치 없음 | EU-8 · M-12 |
| 본인 업무의 완료 | 담당자가 직접 완료. 승인자를 지정했으면 SPEC-001 계약 그대로 | V-17 · K-7 |
| 지연 표시 | 표시만 바뀌고 **상태·기한은 그대로** | V-19 · P-1 |

## 시안 반영 — 분석 3종의 물음을 세 갈래로 가른다 (2026-09-17 오후)

확정 시안이 정본이고 분석 3종(BASE-002 입력 5)은 **그 시안을 읽은 보고서**다. 보고서가 남긴

**갈래 ① — 기존 계약에 이미 답이 있다. 표현만 고르면 된다.**
