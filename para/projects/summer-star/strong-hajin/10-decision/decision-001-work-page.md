# 업무 페이지를 원문 계약에 맞춰 세우고 #7 의 W1·W2 를 그 위에 반영한다

BASE-001 이 모은 **회사 원문이 이미 닫은 것**과 **현행 코드의 차이**를 어느 범위까지,
어떤 모양으로 스펙에 내릴지 정한다.

> 기능 계약 상세는 `20-spec/`, 실제 작업 순서는 `30-work/` 가 갖는다. 이 문서는 **무엇을
> 정했고 무엇이 아직 열려 있는지**만 갖는다. 열린 것을 추측으로 메우지 않고,
> **원문이 이미 답한 것을 미결로 올리지 않는다.**

## Context

- 관련 baseline: BASE-001
- 문제/기회: #7 이 요구하는 업무 계약과 `Strong_hajin` 현행 구현이 W1 전체와 W2 대부분에서
  어긋난다. 동시에 개발 주체가 회사 팀에서 **개인 1인**으로 바뀌었다.
- 결정이 필요한 이유: #7 은 다섯 slice(W1·W2·M1·X1·회귀)를 한 묶음으로 말한다. 1인이 한 번에
  갈 수 없다. 어디를 먼저 닫을지, 그리고 **무엇이 이미 닫혀 있는지**를 정하지 않으면
  원문이 답한 것을 다시 묻거나 폐기된 어휘를 계약에 남긴다.

**2026-09-19 추가 입력.** 사용자가 확정한 요구 둘이 들어왔다 — **참조(CC) 업무의 수신함
읽음 처리**와 **프로젝트 안에서 고르는 선행업무**다. 둘 다 회사 원문이 답하지 않은 자리이고
**이 제품에서 사용자가 직접 닫은 것**이므로, 원문 대조 없이 사용자 확정으로 쓴다(D-19·D-20).
현행 코드는 `/Users/kknaks/orca/workspaces/Strong_hajin/strong-hajin-work` 를 read-only 로 읽어
**차이만** 기록했다 — 코드가 계약이 되지 않는다(Option D 기각).

**2026-09-19 두 번째 입력.** 사용자가 **업무 만들기 창의 최종 프레임**을 확정했다 —
한 모달 안의 `업무 | 요청` 토글, 왼쪽 탭 넷, 갈래별 기본 정보, `업무 연결` 탭. D-21 이 받는다.
그 프레임이 **D-16 의 「이 창에 없다」 한 문장을 넘어서므로** D-21 이 그 조각만 정정한다 —
D-16 의 보존 규칙과 필수값 규칙은 그대로다.

**전제 하나를 정정한다.** 회사 원문은 `gh api …?ref=e9bfadbd…` 로 **읽힌다.** BASE-001 이
PLAN-001(339줄)·SCREENDEF-004(1,814줄)·PLAN-002(380줄)를 직접 받아 읽었다. 이 문서의
결정은 그 원문 대조 위에 선다.

## Options

| Option | Description | Pros | Cons | Notes |
|---|---|---|---|---|
| A | #7 전체(W1·W2·M1·X1)를 한 스펙 묶음으로 내린다 | 이슈와 1:1. 추적이 단순 | 1인이 검증할 수 없는 크기. M1·X1 의 외부 미결(D5·D6)이 스펙 본문에 섞인다 | 기각 |
| B | **W1·W2 와 업무 페이지를 스펙 둘로 내리고, M1·X1 은 원문 차수를 보존한 채 다음 slice 로 세운다** | 사용자 지시("업무 페이지를 먼저")와 같은 결. 원문이 대부분을 이미 닫아 두어 이번 스펙은 확정만으로 선다 | 이슈 하나가 여러 문서로 갈린다 | **채택** |
| C | 개인 프로젝트라는 이유로 조직·타인 요청·승인을 걷고 단일 사용자 모델로 줄인다 | 코드가 크게 준다 | 발주 브리프의 해석이 배제했고, 원문의 권한·승인 계약 전체를 버린다 | 기각 — **판단 소유는 코디네이터**(아래 D-2) |
| D | 코드 현행에 맞춰 SPEC 을 쓴다(현행 = 계약) | 문서와 코드가 즉시 일치 | #7 이 바꾸라고 한 것을 굳히고, 원문이 폐기한 어휘(막힘)를 되살린다 | 기각 |

## Decision

### 채택

**D-1. 범위는 W1·W2 와 업무 페이지까지.** 산출물은 SPEC 둘이다.

| 문서 | 담는 것 |
|---|---|
| SPEC-001 | W1 생성·타인 요청/배정, W2 수행·완료·기한·문의 발송, 업무 페이지의 축 셋·상세·생성·완료·기록·자료 |
| SPEC-002 | 답하면 끝나는 목록(판단함), 완료 승인 ActionItem, 종류 칩 둘, 회신 대기의 파생 표시 |

**D-2. 제품은 줄이지 않는다 — 판단 소유는 코디네이터다.**
개발 주체만 1인으로 바뀌고 조직 축·타인 요청·배정·승인·AX 실행 확인은 전부 남는다.
1인이라는 이유로 권한 검사를 끄지 않는다.

> 이 판단의 근거는 **발주 브리프 §1·§2 의 코디네이터 해석 문구**이고 사용자 발화 그대로가
> 아니다(BASE-001 § 입력 1). 사용자가 뒤집으면 Option C 의 기각 사유가 함께 바뀐다.

**D-3. 즉시 배정은 기존 생성 명령을 넓혀서 만든다** — BASE-001 Possible Direction 1 의 (b).
`POST /api/tasks` 가 수신자를 받는다. 이유는 둘이다.

1. #7 W1.4 가 요구하는 것이 "**한 번의** 명시적 생성 명령"이다. 본인 업무와 타인 배정이 같은
   명령의 인자 차이가 되면 우회로(본인 생성 → 재배정)가 필요 없다.
2. 기존 `POST /api/tasks/assign` 은 `task.assign` 을 요구한다. 구성원에게는 그 권한이 없다
   (BASE-001 § 현행 코드 관측 W1.5). (a) 안처럼 `assign` 의 의미만 바꾸면 #7 W1.5 와
   그 권한 게이트가 정면으로 부딪친다.

**멱등성은 근거가 아니다.** 현행 `POST /api/tasks` 는 멱등 키를 받지 않고 받으면 거부한다.
`causation_key` 재조회 경로는 있으나 그 키를 채우는 호출자는 AX 판단 경로뿐이고, 중복 활성
담당을 막는 unique 제약도 없다(BASE-001 § 현행 코드의 사실 정정). **재전송 안전성·동시 생성
안전성·활성 담당 유일성은 이번에 새로 세우는 계약이다** — 기존 경로 재사용으로 얻지 못한다.

**D-3b. 멱등 키는 논리적 생성 명령마다 필수다.** 키를 선택으로 두면 "같은 명령"의 식별 근거가
없어, 일부러 만든 두 건과 네트워크 재시도를 서버가 가를 수 없다 — 그 상태에서 「중복 업무 0」을
약속하면 지킬 수 없는 계약이 된다. 그래서 **키를 필수로 세우고**, 서버가 내용으로 두 명령을
합치는 길(내용 해시 + 시간창)은 **쓰지 않는다** — 그러면 의도적으로 같은 내용 두 건을 만드는
일이 막힌다.

- 키의 유효 범위는 **행위자 + 명령 종류**다(조직/tenant 경계가 있으면 포함). 전역이 아니다.
- 같은 키 + 다른 내용은 **충돌**, 다른 키 + 같은 내용은 **둘 다 생성**.
- 영수증을 돌려주기 전에 **현재 열람 권한을 다시 검사**하고, 잃었으면 존재를 숨긴다.
- 호출자(FE·REST·MCP·AX·회의 후속)는 **한 번의 생성 의도에 키 하나**를 만들어 재시도 동안
  그대로 다시 보낸다. 재시도마다 새 키가 되면 키가 있으나 마나다.
- 레포에 이미 같은 모양이 있다 — 회의실 예약이 `Idempotency-Key` 를 필수로 받고
  `(owner_id, request_key)` unique + payload 지문으로 충돌을 가른다. 새 계약은 그 모양을 따른다.

**키는 표면마다 호출자가 실어 보낸다. 서버가 대신 만들지 않는다.**

- REST: `Idempotency-Key` 헤더.
- **MCP: 생성 도구가 `idempotency_key` 를 명시적 인자로 받는다. 누락·빈 값은 거부다.**
  외부 호출자가 한 생성 의도에서 키를 만들어 재시도마다 그대로 다시 보내고, 다른 생성 의도에는
  새 키를 쓴다. **서버가 호출 시점에 임의 키를 만들어 채우는 fallback 을 두지 않는다** —
  그러면 응답을 잃은 호출자의 재시도가 새 업무가 되어 계약이 무너진다.
- **turn 식별자 하나로 키를 만들지 않는다.** 한 turn 안에서 같은 종류의 업무를 두 건 만들 수 있고,
  같은 turn·같은 operation 이라는 사실이 **같은 생성 의도라는 뜻이 아니다.**
  payload 는 키 재료가 아니라 **충돌 검사용 지문**이다.
- AX 실행이 이미 쓰는 `action.id` 는 **그 action 의 재실행 식별**로 그대로 보존한다.
- **고치는 범위는 W1 생성 경로뿐이다.** 여러 MCP mutation 이 함께 쓰는 공용 키 helper 를
  일괄로 바꾸지 않는다 — W1 전용 resolver 를 따로 두거나 적용 범위를 명시적으로 제한해,
  일일보고 초안·회의 예약 같은 **비 W1 mutation 의 기존 멱등 의미를 건드리지 않는다.**

기존 `POST /api/tasks/assign` 은 **관리자 직접 배정으로 남긴다**(`task.assign` scope 유지).
기존 업무의 담당자 변경은 계속 별개 명령이고 사유가 필수다(원문 DEC-003).

**D-3c. 신규 수평 요청의 출처 상태값은 `assigned`(즉시 배정됨)이다.**
수락 없이 업무가 서는 경로에서 요청 행을 `pending` 으로 두면 아무도 기다리지 않는데 「판단 대기」로
읽히고 수신함에 서며, `accepted` 로 두면 **사람이 하지 않은 수락을 기록**하는 것이 된다. 둘 다 못 쓴다.

- `assigned` 는 **수락·거절·조정 판단 없이 업무와 활성 담당이 생성됐다는 사실만** 말한다.
  가짜 accept 판단 회차·감사 로그를 남기지 않는다.
- 기존 다섯 값(`pending`·`negotiating`·`accepted`·`rejected`·`withdrawn`)의 뜻은 **바꾸지 않는다.**
  과거 행은 그대로 읽힌다.
- 이것은 **출처 상태**다 — 업무의 **수행 상태**(시작 전·진행 중·완료·취소, D-5)와 다른 축이고
  서로 섞지 않는다.
- 완료 승인 경로는 그대로다 — 업무가 `source_work_request_id` 로 그 요청을 가리키고,
  확인자를 거기서 찾는다.
- 이 값은 **외부 응답에 드러나므로** SPEC-001 Data Contract 가 노출 의미를 갖는다.

**D-4. 배정 거절 경로를 신설하지 않는다.** 원문이 확정 제외했다 — "요청·수락 게이트,
조건 협의·보완안 회차 … **거절 규칙이 새 예외를 만든다** … 확정 제외"(PLAN-001:127,
`X-61`·`X-84`). 잘못 온 배정의 출구는 **문의·요청과 담당자 [수정]**이다(RSK-001, :280).
이것은 사용자 미결이 아니다.

**신설 금지와 기존 삭제는 다른 말이다.** 이 결정은 **신규 생성 경로에 거절 명령을 열지 않는다**
는 뜻이고, 과거 행에 답하려고 이미 있는 명령을 지우라는 뜻이 아니다 — 과거 데이터는 D-17 이
전환을 면제한 영역이라 그대로 남고, 그 행을 읽고 답하는 기존 코드도 무단으로 지우지 않는다.

**D-5. 수행 상태는 넷이다 — 시작 전 · 진행 중 · 완료 · 취소.**
`completion_submitted` 와 **`blocked`(막힘) 둘 다** 목표 상태 모델에서 뺀다.

- `completion_submitted` → 완료 명령 성공 시 `done`. 승인 대기는 **파생 표시**다(#7 W2.3·W2.4).
- `blocked` → **원문이 폐기했다**(PLAN-001:107, `X-69`·`X-135` 폐기 2026-09-10 ·
  DEC-007 폐기 :297). 대체재는 둘이다 — 제품 안의 기다림은 **회신 대기**(문의를 보내면
  자동으로 붙고 답이 오면 자동으로 풀린다), 제품 밖의 기다림은 **상태 메모**.

현행 코드에 `blocked` 가 있다는 이유로 계약에 남기지 않는다. 코드 현황은 BASE-001 이 갖고,
어긋남은 work 가 옮기는 일이다.

**D-6. 파생 표시는 넷이다** — 회신 대기 · 승인 대기 · 승인됨 · 보완 요청(PLAN-001:105·:217).
표시는 상태를 바꾸지 않고, 상태는 **「나에게」 어떤 상태인가**를 낸다(`X-213`).

**D-7. 문의·회신 대기의 확정 계약을 이번에 내린다.**
#7 W2.8 이 확정한 것은 **발송 → 회신 대기 자동 부착 → 답변 시 자동 해소**와 **제품 밖 대기는
상태 메모**다. 원문도 같다(PLAN-001:107·:108·:206·:207). **D2 로 열려 있는 것은
「여러 미응답 문의가 있을 때의 해소·취소 판정」 하나**다.

미결 하나 때문에 그 미결이 걸린 기능 전체를 뒤로 미루지 않는다. **코드에 없다는 것은 구현
비용이지 범위 축소 사유가 아니다.**

**D-8. 승인 원장은 새로 만들지 않는다.** 기존 TaskDelivery Submission / `task.delivery`
ActionItem / ReviewDecision 을 그대로 쓴다. 제거 대상은 **생성 시 수행자 수락용 판단**뿐이다.

**D-9. 승인자는 0..1명이고 요청자와 고정 결합하지 않는다.** (최종 제품 계약이다 — **켜지는 시점은
W2**: 사람이 고른 승인자를 실제로 쓰는 것은 완료 승인 경로이므로, API 수용과 화면 노출을
그 경로와 **같은 단위로** 연다. 그 전에 입력만 받아 두면 고른 값이 무시되는 약속이 된다.)
담당자가 지정·변경·비움을 하고, **「완료 · 승인 대기」로 간 뒤에는 바꾸지 않는다** —
판정을 기다리는 중에 판정자를 바꾸면 그 판정이 누구 것인지 갈린다
(SCREENDEF-004 `SCR-102-E16` · §5.7 권한표). 생성 창은 승인자를 묻고([완료] 때 한 번 더 확인),
위임전결 순서 **자동 채움**은 그 순서의 값이 선 뒤다 — **원문에도 그 값이 없다**(OQ-C).

**D-10. `[완료 해제]` 를 두지 않고, 되돌리는 사람은 마지막 판정자다.**
원문이 확정했다 — "완료 판정은 [승인]·[보완 요청]이고 **완료를 되돌리는 사람은 마지막에
판정한 사람이다**"(PLAN-001 DEC-005 :295, `X-44`·`X-178`~`X-180`), "보완 요청을 받으면
「진행 중 · 보완 요청」으로 돌아오므로 [완료 해제]를 두지 않는다"(:105), "승인된 뒤에는
**확인자의 [보완 요청]만** 다시 연다"(:220 · SCREENDEF-004 §5.7 역할·상태표).
판정 자체는 되돌릴 수 없는 사실이고 다시 열려면 **새 판정을 단다**(PLAN-002:110·:223·:231).

**승인자가 0명인 Task 의 복구만 열려 있다.** 그 경우 「마지막 판정자」가 없다.
원문의 기본값은 SCREENDEF-004 §5.7 역할·상태표가 말한다 — 「담당자 · 완료 · 승인 대기
**또는 확인자 없는 완료**」 행의 상단 고정은 **없음**이고 오른쪽 끝에 [업무 취소]만 선다.
즉 원문은 **복구 경로 없음 · 취소만**이다. 이 한 조각에 사용자 질문이 나가 있으므로
**답이 오기 전까지 확정하지 않는다**(OQ-A). 답이 원문과 같으면 그대로 굳고, 다르면 여기만 바뀐다.

**D-11. 목록 축은 셋이고, 남의 업무 열람은 이 화면이 아니다.**
축 셋 — 내 업무 · 보낸 업무 · 완료 업무(PLAN-001:102 · `SCR-101-E07`).
현행의 네 번째 탭 `조직 업무` 는 **원문에서 팀 관리 화면(`SCR-108`)이 받는 일**이다
(PLAN-001:128 · DEC-004 :294). 업무 페이지의 축으로 두지 않는다.

> **기능을 없애는 결정이 아니다.** `work.read.all` 로 남의 업무를 읽는 현행 경로와 API 는
> 그대로 두고, **자리를 옮긴다**. 옮길 화면은 이번 slice 밖이므로 SPEC-001 은 "이 화면의
> 축이 아니다"까지만 계약하고 이관 대상으로 추적한다.

**D-12. 칩은 축마다 다르고 상태값으로 만들지 않는다.**
「이럴 때 이걸 본다」가 있을 때만 만든다(`X-216` · PLAN-001 DEC-009 :299).

| 축 | 칩 |
|---|---|
| 내 업무 | 전체 · 회신 대기 · 기한 지남 |
| 보낸 업무 | 전체 · 시작 전 · 기한 지남 |
| 완료 업무 | 전체 · 승인 대기 · **취소** |

「진행 중」 칩은 두지 않는다. **취소는 「완료 업무」 축이 받는다**(SCREENDEF-004 `SCR-101-E41`).

**D-13. 행 액션은 그 상태의 다음 한 걸음 하나다**(`X-146` · `SCR-101-E44`).
「시작 전」은 [시작], 「진행 중」은 [완료]. 답하면 끝나는 행은 [답변] 또는 [승인]·[보완 요청].
나머지 조작은 상세가 갖는다. **행에 전이 버튼을 여러 개 늘어놓지 않는다.**

**D-14. 종류 칩 둘의 경계를 정의한다.**
종류 칩은 **「내 업무」 축의 답하면 끝나는 행에만** 붙고 **문의 요청 · 승인 요청** 둘이다.
결정 요청은 문의 요청에 담는다. **직접 해야 끝나는 행과 일일보고는 칩이 없다**
(PLAN-001:102 · `SCR-101-E12`).

**AX 실행 확인은 이 둘에 넣지 않는다.** 원문에 AX 확인의 칩 귀속이 없고, 같은 줄이
「칩 없는 항목」을 허용한다. AX 확인이 서는 자리는 **AI 채팅의 카드 표면**이고 그 소유는
`PLAN-008` · `SCREENDEF-006` 이다(PLAN-001:146). 우리 코드에서 그 표면은 판단 항목의
`ax.<action_type>` kind 다(BASE-001 § 표면 전수 「AX」 행).

> **보존한다.** AX 실행 확인을 없애는 것이 아니라 **표시 표면을 가른다** — 판단 원장은
> 공유하고, 업무 목록의 종류 칩에는 들어가지 않는다. #7 W1.6 준수.

**D-15. 회의 후속업무 승격은 W1 과 같은 생성 계약을 쓴다.**
원문이 제외한 것은 **자동** 승격이고 "승격은 **사람의 명시적 행동**"이다(PLAN-001:130).
#7 M1.5 도 "W1과 동일한 명령·권한·멱등성 경로를 사용한다. 기존 WorkRequest 수락 경로를
**우회 adapter로 남기지 않는다**"고 못 박았다.

현행 승격은 이번에 바꾸는 **바로 그 두 생성 경로를 직접 호출한다**
(BASE-001 § 현행 코드 관측 W1/M1.5). 따라서 이것은 추적이 아니라 **영향**이다.
SPEC-001 이 승격의 생성 계약(같은 명령·같은 권한·같은 멱등성)을 갖고,
후보 선정·출처 회의·회의 화면은 회의 쪽이 갖는다.

**D-16. 체크리스트는 기존 API 를 보존하되 1차 UI 에 강제하지 않는다.**
원문은 체크리스트를 **2차 재검토**로 뒀다 — "업무 하나가 막대 하나다. 체크가 생기면 완료
판정이 흔들린다"(PLAN-001:132, `OQ-136` 종결). #7 X1 도 "현재 Checklist/Subtask/Project 가
있다는 이유로 1차 UI 에 강제하지 않는다"이고 동시에 "기존 데이터·API 를 즉시 삭제하지 않는다".

둘을 가른다 — **기존 API·저장 모델은 그대로 둔다(삭제 금지). 1차 업무 페이지의 생성 계약과
필수 검증에는 올리지 않는다.** 하위 업무·참고 업무·프로젝트 연결도 같은 취급이다.

**D-17. 기존 데이터 전환·호환은 범위 밖이다**(#7 D4).
migration·backfill·구 상태 adapter·전환표·dry-run·rollback 을 요구하지 않는다. 검증은 새
상태 모델의 seed·fixture 로 한다. **데이터 삭제나 DB reset 을 승인한 것은 아니다.**

**D-17b. 스키마는 migration 없이 모델 metadata 로 세우고, 새 DB 제약은 빈 격리 DB 에서 검증한다.**
코드 레포에 migration 프레임워크가 없다. 스키마를 만드는 자리는 `reset_demo` 하나이고,
기존 DB 를 맞추는 `sync-demo-schema` 는 표·열만 더할 뿐 **제약을 만들지 못한다**. 그래서

- 새 열과 활성 담당 유일성 제약은 **모델 metadata 에만** 더한다. migration 도구를 새로 들이지 않는다.
- **DB 수준 유일성은 이 작업 전용으로 만든 빈 격리 테스트 데이터베이스**에 목표 스키마를 세워
  검증한다. DB 제약을 application 검사로 낮추지 않는다.
- **기존 데이터베이스에 적용·전환하는 일은 이 실행 범위 밖**이고 별도 gated work 다.
  실제 사용자 데이터가 든 데이터베이스를 reset 하지 않는다.
- 되돌리기는 **코드·모델과 일회용 환경 교체**를 뜻한다. 존재하지 않는 migration downgrade 나
  기존 DB 의 데이터 무손실 보장을 발명하지 않는다.

**기존 pending 요청/배정 행의 처리는 사용자 미결이 아니다.** D4 가 면제한 영역이므로
BASE-001 § 잔여 추적 C-7 에 두고, work 가 "표시만 하고 손대지 않는다"로 처리한다.

**D-18. 고정 revision 이후의 회사 SPEC 변경은 되돌리지 않는다.**
`#719`·`#722`·`#725` 를 실제로 대조한 결과 **업무 계약 충돌은 0건**이고 다섯 변경 전부
보존 대상이다(BASE-001 § `#719`·`#722`·`#725` 본문 대조). 특히 회사 SPEC-002 규칙 10
(편집 가능 여부·필수값·후보·실행 command 를 **서버가 제공**)은 SPEC-002 의 봉투 원칙을
그대로 뒷받침한다.

**D-19. 참조(CC)로 들어온 참고 업무는 「읽음」으로 접고, CC 관계는 지우지 않는다.**

수신함의 참고 항목은 지금 **처리된 뒤에도 영원히 남는다**(코드 관측 — 수신함 조회가 CC 항목을
「처리된 것까지 포함해」 낸다). 그래서 참조자에게 수신함은 쌓이기만 하는 목록이고, 무엇이
새로 온 것인지가 화면에 없다. 사용자가 확정한 것은 **접는 방법**이다.

- 참조자가 `[읽음]` 을 누르거나 **참고 업무 카드를 열면** 읽음이 된다.
- 읽은 참고 항목은 **수신함 조회에서 사라진다.**
- 같은 업무는 **`참조 업무` 탭에서 계속 조회된다** — 읽음은 수신함이라는 **한 표면**에서만 접는다.
- 읽음 상태는 **사용자별**이다. 한 참조자가 읽어도 다른 참조자의 수신함에는 그대로 남는다.
- 수신함 뱃지는 **현재 사용자 기준 미읽음 참고 항목 수**를 낸다.
- 읽음 명령은 **멱등**이다. 두 번 눌러도 처음 읽은 시각이 그대로고 오류가 아니다.

**CC 관계를 삭제해서 숨기지 않는다.** 관계를 지우면 그 사람이 왜 이 업무를 알고 있었는지가
사라지고, `참조 업무` 탭에서도 함께 사라져 「읽은 것은 탭에 남는다」는 요구와 정면으로 부딪친다.
그래서 **별도의 읽음 영수증**을 둔다 — 관계는 그대로, 수신함 표면에서만 접힌다.

**이 절의 대상은 CC 참고 업무 하나다.** 업무 요청(담당자에게 온 것)의 수락·거절 흐름은
이 결정이 건드리지 않는다 — 수신함의 `work` 갈래는 지금처럼 `pending`·`negotiating` 만
서고, 읽음으로 접히지 않는다. 읽음이 수락을 대신하지 않는다.

**읽음 영수증의 모양은 레포에 이미 있는 것을 따른다.** 요청자가 자기 목록에서 항목을 빼는
`work_request_list_entries` 가 같은 문제를 이미 풀었다 — **행을 지우지 않고**, `(요청, 사람)`
한 쌍에 unique 를 걸고, **한 사람의 정리가 다른 사람의 목록을 바꾸지 않는다.** 새 표는 그
모양을 그대로 쓴다.

| 무엇 | 단일안 (이번 계약) |
|---|---|
| 표 | `work_request_read_receipts` |
| 열 | `id` · `work_request_id`(FK) · `member_id` · `read_at` |
| 유일성 | `uq_work_request_read_receipt (work_request_id, member_id)` — **DB 제약** |
| CC 관계 | `resource_relationships.relationship_kind = 'cc'` — **손대지 않는다** |

후보를 나열하지 않는다. 위 한 벌이 이번 계약이고, API·필터·오류는 SPEC-001 이 갖는다.

**읽음은 요청 행의 `version` 을 올리지 않는다.** 읽음은 그 사람에게만 있는 사실이라, 올리면
남이 쓰던 낙관적 잠금이 읽음 때문에 깨진다.

**MCP 에 읽음 명령을 내지 않는다.** 수신함 **조회**는 MCP·AX 가 같은 projection 을 쓰므로 필터가
함께 적용되지만, 읽음을 **누르는 것**은 사람이 본 사실이다 — 에이전트가 대신 눌러 주면
D-3c 가 거부한 것("사람이 하지 않은 수락을 기록하지 않는다")과 같은 종류의 거짓이 된다.

> **SPEC-003 과의 관계** — SPEC-003 §2.8(수신함)의 계약은 그대로다. 「유입 경로만으로 담당이
> 서지 않는다」도, 요청의 `pending` 수신함 등재도 바뀌지 않는다. SPEC-003 이 **계약을 만들지
> 않는다**고 둔 미정 **M-22**(수신함 카드의 아바타·수신 시각·출처·**미읽음**) 중 **「미읽음」
> 한 조각만** 이번에 닫힌다. 나머지 셋은 그대로 열려 있다. **DEC-002·SPEC-003 본문 갱신은
> 이번 범위 밖**이고 아래 § Open Questions 의 추적에 둔다.

**D-20. 선행업무(predecessor)는 상위(parent)·참고(reference)와 다른 세 번째 관계다.**

세 관계를 하나로 섞지 않는다. 현행 코드에 앞의 둘은 있고 **선행은 없다.**

| 관계 | 자리 | 뜻 | 시작을 막나 | 완료를 막나 |
|---|---|---|---|---|
| 상위 `parent` | `tasks.parent_task_id` | 이 업무가 **어느 업무의 일부**인가 | 아니다 | **그렇다** — 미완 하위가 최종 완료를 막는다(기존 `WORK_CHILDREN_UNFINISHED`) |
| 참고 `reference` | `task_references` | **맥락만** 준다 | **아니다** | 아니다 |
| 선행 `predecessor` | **신규** | 이것이 끝나야 **시작**한다 | **그렇다** | 아니다 |

- **참고 업무를 선행의 대체물로 쓰지 않는다.** 이미 SPEC-003 이 같은 말을 하위 관계에 대해
  했다(「참고 연결을 하위 관계의 대체물로 쓰지 않는다」). 선행도 같다 — 참고는 맥락이지 순서가 아니다.

**프로젝트가 선행 선택의 범위다.**

- 프로젝트를 고르면 **그 프로젝트에 속한 업무 중에서** 선행을 **여러 개** 고른다.
- 프로젝트가 안 골라졌으면 선행 선택은 **비활성**이고 화면이 프로젝트를 먼저 고르라고 안내한다.
- 후보 조회를 새로 만들지 않는다 — **프로젝트 상세 조회가 이미 그 프로젝트의 업무를 전부 낸다.**

**금지 셋** — 자기 자신 · 중복 관계 · 순환. 순환은 DB 가 못 보므로 **application 이 활성 선행만
따라 걸으며** 검사한다. 자기 자신과 중복은 **DB 제약**으로 막는다.

**기본 의존성은 finish-to-start 하나다.** 다른 종류(SS·FF·SF)를 이번에 열지 않는다.

- 고른 선행이 **모두 완료되지 않으면 후행의 시작 명령을 거부**한다.
- **취소된 선행은 막지 않는다** — 미완 하위 판정이 취소를 제외하는 기존 규칙과 같은 결이다.
- **게이트는 시작 시점 판정이다.** 시작한 뒤에 선행이 보완 요청으로 다시 열려도 후행을
  되돌리지 않는다. 사용자가 확정한 것은 「시작 명령을 거부한다」까지다.
- **`시작 전 → 완료` 직행도 같은 코드로 막는다.** 상세 상단의 `[완료]` 가 `open` 에서 바로
  `done` 으로 가는 길을 열어 두면(SPEC-001 §4 State/Lifecycle) 시작 게이트가 우회로를 갖는다.
  게이트를 세우기로 한 이상 그 우회로를 함께 닫는 것이 같은 결정의 일부다.

**거부 코드는 하나이고, 기존 상태 충돌 계약에 맞춘다.**

레포의 관례는 **오류 코드를 예외 클래스가 갖고 HTTP 상태는 entrypoint 가 매핑**하는 것이다.
「명령 자체는 말이 되는데 지금 그 업무의 상태가 받지 않는다」는 **409** 이고, 그 자리에 이미
`WORK_CHILDREN_UNFINISHED` 가 **무엇이 막는지 이름을 함께 내는** 모양으로 서 있다.

> **`WORK_PREDECESSORS_UNFINISHED` · 409 · `InvalidTaskTransition` 계열 · 막는 선행의 이름을 함께 낸다.**

기존 코드에 없는 코드지만 **Open Questions 로 올리지 않는다** — 자리와 모양이 기존 계약으로
정해지므로 이번 스펙이 **목표 계약으로 명시**한다(Option D 기각의 같은 논리).

**표·필드명은 현재 코드가 이미 고른 이름을 쓴다.** 공통 생성 payload 의 주석이 앞으로 올 값의
이름을 **`preceding_task_ids`** 로 적어 두었다("승인자(`approver_id`)와 선행 업무
(`preceding_task_ids`)도 없다: 후속 개발이고, 받지 않는 값을 미리 열어 두지 않는다").
그 이름을 그대로 쓴다.

| 무엇 | 단일안 (이번 계약) |
|---|---|
| payload·응답 필드 | `preceding_task_ids: UUID[]` |
| 표 | `task_predecessors` |
| 열 | `id` · `task_id`(FK) · `preceding_task_id`(FK) · `created_by` · `created_at` · `released_by` · `released_at` |
| 유일성 | 부분 unique `uq_task_predecessor_active (task_id, preceding_task_id) WHERE released_at IS NULL` |
| 자기 참조 금지 | `CHECK (task_id <> preceding_task_id)` |
| 순환 | application 검증 (DB 로 못 한다) |

- 해제는 **행을 지우지 않고 닫는다**(`released_at`). `task_references` 가 같은 이유로 같은
  모양을 쓴다 — "놓아준 것도 거기 있었다는 사실은 이력에 남는다".
- **전용 add/remove 엔드포인트를 따로 두지 않는다.** 선행은 화면이 프로젝트 안에서 **한 번에
  여러 개**를 고르는 **집합**이라, 생성·수정 payload 의 **배열 전체 교체**가 맞는 모양이다.
  (참고 업무는 한 건씩 붙였다 떼는 것이라 전용 명령을 갖는다 — 같은 모양일 이유가 없다.)
- 선행 변경은 그 업무의 **`version` 을 올리고 진행 기록에 남긴다** — 참고 업무 연결·해제가
  이미 그렇게 한다.
- **프로젝트를 바꿀 때 남은 선행이 있으면 거부한다.** 조용히 링크를 닫으면 사람이 세운 순서가
  본인도 모르게 사라진다. 하위 업무의 프로젝트가 상위를 따라 옮겨 가는 현행 동작에도 같은
  규칙이 걸린다.

**D-16 의 「프로젝트 연결」 조각만 1차 UI 로 올라온다.** D-16 은 체크리스트·하위 업무·참고
업무·프로젝트 연결 넷을 1차 생성 계약에서 뺐다. 선행 선택이 **프로젝트를 범위로 요구**하므로
그 넷 중 **프로젝트 연결 하나만** 생성·수정 창으로 올라온다. **체크리스트·하위 업무·참고
업무는 그대로 Out 이다** — D-16 의 나머지는 바뀌지 않는다.

**간트/타임라인은 데이터만 이번에 연다.** 프로젝트 상세 조회의 업무 줄이 `parent_task_id` ·
`start_date` · `due_date` 를 이미 내고 있으므로, 거기에 **`preceding_task_ids` 한 줄을 더해**
선행→후행 연결선을 그린다. **새 조회를 만들지 않는다.** 간트 화면이 어느 자리에 서는지는
아직 열려 있다(OQ-K) — SPEC-003 §2.10 이 「새 화면을 이 SPEC 이 만들지 않는다」로 둔 자리다.

**D-21. 업무 만들기 창의 최종 프레임 — 한 모달, 갈래 토글, 왼쪽 탭 넷.**

2026-09-19 에 사용자가 창의 최종 모양을 확정했다. **화면 결정이고, 이미 선 계약을 바꾸지 않는다** —
아래 「정정」 절이 바꾸는 것은 D-16 이 「창에 없다」고 적었던 **자리 결정 한 조각**뿐이다.

**골격** — 창 하나, 머리에 `업무 | 요청` 토글, 왼쪽에 세로 탭.

| 자리 | 확정 |
|---|---|
| 토글 | `업무` · `요청` 둘. 갈래를 바꿔도 **창은 하나**다 |
| 제목 | `업무` 고르면 **「새 업무 추가」**, `요청` 고르면 **「새 업무 요청」** |
| 필수 탭 | `기본 정보` 하나 |
| 선택 탭 | `체크리스트` · **`업무 연결`** · `자료` 셋 |

**기본 정보 — 갈래로 갈린다.**

| 줄 | 업무 | 요청 |
|---|---|---|
| 제목 | `업무 제목` | `요청할 업무 제목` |
| 날짜 | `시작일` \| `마감일` | `시작일` \| `희망 기한` |
| 담당자 | **없다** — 화면이 묻지 않고 **서버가 현재 사용자를 담당자로 기록**한다 | `담당자` **한 명** |
| 내용 | `업무 내용` | `요청 내용` |
| 사람 | `참조자`(여러 명) \| `결재자`(한 명) | `참조자`(여러 명) \| `결재자`(한 명) |

- **업무 갈래에 담당자 칸을 두지 않는다.** 남에게 보내는 길은 `요청` 갈래다 — 두 갈래가 같은 일을
  두 방법으로 하게 두지 않는다. 서버가 담당자를 현재 사용자로 기록하는 것이 계약이다.
- **요청 갈래에도 시작일이 선다.** 현행 화면은 「서버가 받지 않는다」며 그 칸을 접고 있으나
  **사실이 아니다** — 요청 생성 입력이 이미 시작일을 받는다. 화면이 낡았다.

**업무 연결 탭 — 넷 중 셋만 선다.**

| 줄 | 확정 |
|---|---|
| `상위 업무` | **단일 선택** |
| `프로젝트` | **단일 선택** |
| `선행 업무` | **고른 프로젝트의 업무 중 복수 선택.** 프로젝트가 없으면 **비활성** (D-20) |
| ~~`참고 업무`~~ | **UI 에서 내린다** |

**참고 업무 연결 UI 를 내리는 것은 계약 삭제가 아니다.** 입력 필드·저장 모델·기존 명령은
그대로 남는다(D-16 의 보존 규칙). 내리는 이유는 **창 안에서 두 개념이 섞여 읽히기 때문**이다 —
참조자(CC)는 **사람**이고 참고 업무는 **업무**인데, 둘 다 「참조」라는 낱말을 쓰고 한 판에 나란히
서 있었다. 참고 업무를 다는 자리는 **업무 상세**다.

**결재자는 화면 라벨이고, 계약상 이름은 승인자(`approver_id`) 그대로다.**
D-9 가 세운 「0..1명 · 담당자가 지정·변경·비움 · `승인 대기` 뒤 고정」은 **바뀌지 않는다.**
바뀌는 것은 **켜지는 시점**이다 — D-9 는 「W2 와 같은 단위로 연다」고 했고 WORK-001 은 열만
만들어 두었다. **이번 프레임이 그 값을 창에서 받아 저장·조회까지 연다.**

> **요청 갈래의 결재자는 확정 계약이 아니다.** SPEC-003 이
> 「요청 Task 의 확인자는 요청자로 고정」을 세워 두었고, 확정 프레임은 요청 창에도 결재자 칸을
> 둔다. **두 사실이 어떻게 정합하는지는 정해지지 않았다** — 아래 OQ-M 으로 남긴다.
> **업무 갈래의 결재자만 이번에 확정 계약이다.**

**정정 — D-16 의 「1차 UI 강제」 조각.**

D-16 은 체크리스트·하위 업무·참고 업무·프로젝트 연결 넷을 「1차 UI 에 강제하지 않는다」로 두었고
SPEC-001 U-6 은 그것을 **「이 창에 없다」**로 적었다. 확정 프레임이 그 문장을 넘어선다.

| D-16 의 넷 | 확정 프레임 |
|---|---|
| 체크리스트 | **선택 탭으로 창에 선다.** 필수가 아니다 |
| 하위 업무(= 상위 업무 고르기) | **`업무 연결` 탭에 선다.** 단일 선택 |
| 프로젝트 연결 | **`업무 연결` 탭에 선다** (D-20 이 이미 올렸다) |
| 참고 업무 | **창에서 내린다.** 계약·데이터는 보존 |

- **D-16 의 보존 규칙은 그대로다** — 기존 API·저장 모델을 삭제하지 않는다.
- **「필수 검증에 올리지 않는다」도 그대로다** — 넷 중 무엇도 생성의 필수값이 아니다.
  바뀐 것은 **자리**뿐이다: 선택 탭에 서는 것과 창에 아예 없는 것은 다르다.
- 이 정정은 **D-16 을 지우지 않는다.** 위 표가 D-16 의 그 한 문장을 대체한다.

**자료 탭은 현행 두 단계를 그대로 쓴다.** 업무가 서야 자료가 매달릴 자리가 생기므로,
창에서는 고르기까지이고 실제 첨부는 생성 성공 직후다. 붙일 수 없는 갈래에서 고른 파일을
**조용히 버리지 않는다**(현행 동작 보존).

**참조자는 두 갈래 모두에서 저장된다.** 현행 화면은 업무 갈래에서 「함께 저장되지 않습니다」라고
말하지만 **사실이 아니다** — 업무 생성 입력이 이미 참조자를 받아 저장한다. 화면 문구가 낡았다.

### 기각

- Option C — 1인 전용 축소. 조직·타인 요청·승인을 걷지 않는다.
- Option D — 코드를 정본으로 삼기. SPEC 이 정본이고 어긋남은 work 가 옮긴다.
- 배정 거절 경로 신설(D-4) · 새 승인 원장(D-8) · ActionItem/Submission 체계 제거 ·
  AX 실행 확인 제거 · 체크리스트 API 삭제. 전부 원문 또는 #7 이 제외했다.
- **읽음을 CC 관계 삭제로 구현하기**(D-19) — 관계를 지우면 `참조 업무` 탭에서도 사라져
  「읽은 것은 탭에 남는다」와 부딪친다.
- **참고 업무(`reference`)를 선행 관계로 겸용하기**(D-20) — 참고는 맥락이고 순서가 아니다.
- **선행 의존 종류를 넷(FS·SS·FF·SF)으로 열기**(D-20) — 사용자가 확정한 것은 finish-to-start 하나다.
- **읽음을 MCP 도구로 내기**(D-19) — 사람이 보지 않은 읽음을 기록하게 된다.
- **업무 갈래에 담당자 칸 두기**(D-21) — 남에게 보내는 길은 요청 갈래다. 같은 일을 두 방법으로 하지 않는다.
- **참고 업무 연결 UI 를 창에 남기기**(D-21) — 사람(참조자)과 업무(참고)가 한 판에서 「참조」로 섞여 읽힌다.
- **참고 업무의 입력 필드·저장 모델 삭제**(D-21) — UI 를 내리는 것과 계약을 지우는 것은 다른 말이다.
- **요청 갈래 결재자를 이번에 확정 계약으로 굳히기**(D-21) — SPEC-003 의 확인자 고정과 정합이 미정이다(OQ-M).

## Rationale

- **판단 기준**: (1) 원문이 답한 것은 원문으로 닫는다 (2) 사용자가 확정한 것만 확정으로 쓴다
  (3) 기존 부품을 재사용하되 없는 것을 있다고 쓰지 않는다 (4) 1인이 한 번에 검증할 수 있는
  크기로 자르되 **원문 차수를 내리지 않는다** (5) 미결은 미결로 남긴다.
- **대안 대비 이유**: Option A 는 외부 미결(D5·D6)을 스펙 본문으로 끌고 들어온다. Option B 는
  그 미결이 M1·X1 에 몰려 있다는 사실을 이용해 이번 스펙을 확정만으로 닫는다.
- **리스크**:
  - `completion_submitted` 와 `blocked` 를 함께 걷는 것은 enum 두 줄이 아니다. 전이표·라벨·
    칸반 칼럼·정렬 키·프론트 타입·contract 테스트가 함께 움직인다. WP 를 발주할 때
    BASE-001 § 표면 전수를 그대로 믿지 말고 같은 검색을 다시 돌린다.
  - 수락 gate 제거는 판단 목록에서 두 kind 를 걷는 일이다. 대상을 잘못 잡으면 완료 승인까지
    사라진다. SPEC-002 가 kind 별 존치/제거를 표로 못 박는다.
  - 문의·회신 대기는 코드에 하나도 없다. W2 slice 의 실제 작업량 대부분이 여기 있다.
  - 구성원이 `work_request.decide` 를 갖지 않아 수평 요청이 지금 받는 쪽에서 막혀 있다.
    즉시 배정으로 가면 이 gate 는 사라지지만 기존 pending 행은 D-17 에 따라 남는다.
  - **읽음 필터는 「사라지는」 조회다.** 필터를 `work` 갈래나 요청 목록 조회에 잘못 걸면
    받은 업무 요청이나 `참조 업무` 탭이 통째로 비는 것으로 보인다. 필터가 닿는 **입구를 전부
    세고** 시작한다 — 화면·REST·MCP 가 같은 projection 을 쓴다.
  - **선행 게이트는 우회로를 갖기 쉽다.** 시작 명령만 막으면 `시작 전 → 완료` 직행이 뚫려 있고,
    생성 payload 만 막으면 수정 경로가 뚫린다. 전이 판정이 한 자리에 모여 있는지 먼저 확인한다.
  - **선행과 하위는 둘 다 「막는」 관계라 섞이기 쉽다.** 하위는 완료를, 선행은 시작을 막는다.
    거부 코드가 하나로 합쳐지면 사람이 무엇을 먼저 해야 하는지 알 수 없다.

- W2 — 수행 상태 넷 / 파생 표시 넷 / 승인자 0..1 / 완료 시 `done` / 승인 대기 파생 /
  승인·보완·재완료 회차 / 마지막 판정자의 되돌리기 / `[완료 해제]` 제거 /
  담당·취소·기한 변경의 직접 명령 / 계획(박제)·실제 기한 두 값 /
  **문의 발송 → 회신 대기 자동 부착 → 답변 시 자동 해소** / 상태 메모
- 업무 페이지 — 축 셋, 축별 칩, 행 액션 하나, 생성 창, 상세(내용 → 값 → 자료 → 진행 기록)

- 참고 업무를 **상세에서 다는 자리**의 재설계 — UI 를 창에서 내릴 뿐 상세는 그대로다
- 남의 업무 열람 화면(`SCR-108`) 자체 — 자리 이관만 추적(D-11)
- 코드 구현. 이번 발주는 스펙까지다

### D-19 참조 수신함 읽음

| | BE | FE |
|---|---|---|
| 데이터 | `work_request_read_receipts` 표와 `(work_request_id, member_id)` unique 를 **모델 metadata 로** 세운다(D-17b). migration 도구를 들이지 않고, 제약은 **빈 격리 DB** 에서 검증한다 | — |
| 명령 | 읽음 명령 하나. **멱등** — 두 번째 호출은 처음 `read_at` 을 그대로 돌려준다. 요청 행의 `version` 을 올리지 않는다 | `[읽음]` 버튼과 **카드 열기**가 같은 명령 하나를 부른다. 연타 중 버튼 비활성 |
| 권한 | **그 요청의 CC 참조자만.** 아니면 403. 없거나 못 읽으면 기존 404 와 같은 말 | 권한 없는 사람에게 버튼을 **그리지 않는다** |
| 조회 | 수신함의 `reference` 갈래에 **미읽음 필터**. `work` 갈래는 손대지 않는다. 요청 목록 조회(= `참조 업무` 탭의 원천)에는 **필터를 걸지 않는다** | 탭은 그대로 요청 목록에서 읽는다. 수신함만 접힌다 |
| 뱃지 | — | 필터가 걸린 수신함 건수를 그대로 쓴다(OQ-H) |
| 표면 | MCP `work_request_inbox` 가 같은 projection 을 쓰므로 필터가 함께 간다. **도구 설명의 「처리된 것까지 포함해」 문구를 함께 고친다.** 읽음 명령은 MCP 에 내지 않는다 | — |
| 회귀 | 한 참조자의 읽음이 **다른 참조자의 수신함을 바꾸지 않는다**. 동시 두 번 호출이 행 하나를 만든다 | 읽은 항목이 수신함에서 빠지고 `참조 업무` 탭에는 남는다 |

### D-20 프로젝트 선행업무

| | BE | FE |
|---|---|---|
| 데이터 | `task_predecessors` · 부분 unique · 자기참조 CHECK. 순환은 **활성 행만 따라 걷는** application 검증 | — |
| payload | 공통 생성 payload 와 수정 payload 에 `preceding_task_ids`. **배열 전체 교체**, 생략하면 안 건드린다 | 프로젝트를 고른 뒤에만 선행 선택이 열린다. 안 골랐으면 **비활성 + 프로젝트를 먼저 고르라는 안내** |
| 검증 | 프로젝트 미선택 · 프로젝트 불일치 · 자기 자신 · 중복 · 순환 각각의 거절 | 서버가 막기 전에 **고를 수 없게** 한다 — 후보가 그 프로젝트 업무뿐이고 자기 자신이 빠진다 |
| 후보 | **새 조회를 만들지 않는다** — 프로젝트 상세 조회가 이미 그 프로젝트 업무를 낸다 | 그 목록을 후보로 쓴다 |
| 게이트 | 시작 명령과 **`시작 전 → 완료` 직행**을 같은 코드로 막는다. 취소된 선행은 막지 않는다. 막는 선행의 **이름을 함께 낸다** | 거절을 **그 버튼 옆**에 내고 막는 선행 이름을 보여 준다. 조건이 뻔하면 버튼을 비활성으로 둔다 |
| 프로젝트 변경 | 남은 선행이 있으면 **거부**. 하위가 상위를 따라 옮기는 경로에도 같은 규칙 | 거절 문구를 프로젝트 필드 옆에 |
| 간트 | 프로젝트 상세 조회의 업무 줄에 `preceding_task_ids` 를 더한다 | 그 배열로 선행→후행 **연결선**을 그린다. 화면 자리는 OQ-K |
| 동시성 | 선행 변경은 `expected_version` 을 요구하고 `version` 을 올린다. 순환 검사와 저장이 **한 덩어리**다 | 어긋나면 지금 값으로 다시 읽되 **쓰던 입력은 남긴다** |
| 표면 | 화면·REST·MCP·AX 가 **같은 계약**을 쓴다. 생성 도구의 인자에도 같은 배열이 선다 | — |

### D-21 업무 만들기 창의 최종 프레임

| | BE | FE |
|---|---|---|
| 결재자 | 업무 생성·수정 payload 가 `approver_id` 를 **받아 저장**하고 조회 투영이 낸다. 검증은 D-9 그대로(0..1 · 재직 중 · 담당자 본인 불가 · `승인 대기` 뒤 고정). **요청 갈래는 OQ-M 이 닫히기 전까지 저장 계약을 열지 않는다** | 결재자 칸의 「아직 저장되지 않습니다」 안내를 **걷고** 실제로 보낸다. 요청 갈래의 칸은 OQ-M 답까지 안내 문구를 유지 |
| 담당자 | 업무 갈래는 담당자 인자 없이 와도 **현재 사용자를 담당자로 기록**한다(현행 동작 확인) | 업무 갈래에 담당자 칸을 **세우지 않는다**. 요청 갈래만 한 명 고른다 |
| 참조자 | 이미 두 갈래 모두 저장한다 — **바꿀 것이 없다.** 저장되는지 회귀로 못 박는다 | 「내 업무로 만들면 함께 저장되지 않습니다」 **낡은 문구를 고친다** |
| 시작일 | 요청 생성이 이미 시작일을 받는다 — **바꿀 것이 없다** | 요청 갈래에 `시작일` 칸을 **세우고 보낸다**(현행은 접혀 있고 보내지 않는다) |
| 탭 | — | 선택 탭 이름을 **`업무 연결`** 로. `참고 업무` fieldset 을 **창에서 내린다**(상세의 자리는 그대로) |
| 선행 | D-20 의 BE 몫 | 「아직 저장되지 않습니다」 안내를 걷고 실제로 보낸다. 프로젝트 미선택 시 비활성 유지 |
| 회귀 | 업무 갈래에 담당자를 보내지 않아도 본인이 담당이 된다 · 결재자가 저장되고 조회에서 읽힌다 | 갈래 토글로 제목·필드가 갈린다 · 참고 업무 UI 가 없다 · 고른 값이 조용히 버려지지 않는다 |
