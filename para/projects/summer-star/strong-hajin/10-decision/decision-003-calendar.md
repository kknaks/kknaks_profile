# 캘린더에 시간 축을 얹는다 — 배정은 업무에 종속이고, 숨기기는 읽기로 · 지우기는 쓰기로 가른다

BASE-003 의 시안과 사용자 원문을, 조사가 드러낸 실제 코드 지형 위에 어떻게 앉힐지 정한다.

> 이 결정은 **저장 구조 + 외부 계약 + UX 계약**까지다.
> WORK 계획과 코드는 스펙 검수 뒤 별도 발주다. E2E 는 사용자 담당 그대로다.
>
> **⚠ 전제가 한 번 정정됐다 (2026-09-20 오후, 사용자).** 초판은 시안을 「정본 — 깎지 마라」로
> 통째로 받았다. 사용자가 그 범위를 갈랐다:
>
> > "시안은 디자인 레이아웃만 보고 기능이 이런게 있다는거지 / 실제 기능 / 모달 항목 등은
> > 우리가 가지고 잇는걸로 하는거야"
>
> | 무엇 | 정본 |
> |---|---|
> | 레이아웃 · 배치 · 시각 언어 | **시안** |
> | 기능 · 모달 항목 · 데이터 · 상태 어휘 | **우리 것** — 기존 코드 · SPEC-001/002/003 · 이 문서 |
>
> **그리고 디자이너가 없다.** 시안에 있고 우리에게 없는 부품은 **우리가 만든다.**
> 「디자이너 몫」으로 미룬 항목은 전부 우리 범위로 들어온다.
>
> **초판 문장은 지우지 않는다.** 이 정정이 바꾼 자리마다 그 자리에 표시한다.

## Context

- 관련 baseline: **BASE-003**. 그 아래 계보로 BASE-002(업무 생명주기 v2)가 있다.
- 업무의 생명주기 자체는 **건드리지 않는다** — SPEC-003 이 세운 6종 상태와 전이표는 그대로다.
- 이번 결정이 여는 것은 업무 **위에 얹히는 시간 축** 하나다.

조사가 전제 둘을 뒤집었고(BASE-003 「조사가 뒤집은 전제 둘」), 그 결과 **이 결정의 중심
질문이 바뀌었다.** 「배정을 어디에 저장할까」가 아니라 **「배정이 사라지는 두 가지 이유를
같은 메커니즘으로 다룰 것인가」** 다.

## Options

배정이 화면에서 사라지는 이유가 둘이다.

| | 이유 | 성격 |
|---|---|---|
| 가 | 업무 기간이 바뀌어 **밖으로 나갔다** | 되돌려도 복구 안 함(사용자 확정) → **기록이 필요하다** |
| 나 | 업무가 **끝났다**(`done`·`cancelled`) | 업무를 따라갈 뿐 → 배정 자체의 사실은 안 바뀐다 |

- **O1 — 둘 다 쓰기.** 상태가 바뀔 때마다 배정 행을 닫는다. 일관되지만 닫을 자리가 다섯이고
  그중 셋이 영속 계층이다(BASE-003). 새 취소 경로가 생기면 또 빠뜨린다.
- **O2 — 둘 다 읽기.** 조회에서 전부 거른다. 한 자리로 끝나지만 **「가」를 표현할 수 없다** —
  기간이 되돌아오면 배정이 저절로 살아난다. 사용자가 명시적으로 막은 동작이다.
- **O3 — 갈라서 건다.** 「가」는 쓰기(소프트 딜리트), 「나」는 읽기(조회 필터).

## Decision

### 채택

#### A. 저장 — `task_schedules` 한 표

```
task_schedules
  id            PK
  task_id       FK → tasks.id     (NOT NULL)
  on_date       Date              배정된 날
  starts_at     Time              시작 시각
  ends_at       Time              종료 시각
  released_at   DateTime | null   소프트 딜리트 — 비어 있으면 살아 있다
  released_reason  String | null  왜 닫혔나
  created_at · updated_at

  부분 unique  (task_id, on_date) WHERE released_at IS NULL
```

- **범용 `schedules` 표를 만들지 않는다.** 시안의 `CAL_SCHEDULE` 은 저장 단위가 아니라
  읽기 합본이다(BASE-003 Context). 회의는 `meetings` 가 그대로 갖는다.
- **`meetings` 에 `task_id` 를 뚫지 않는다.** `meeting_agendas`·`meeting_lines`·
  `meeting_attendees`·`meeting_transcripts`·`meeting_recording_files` 가 전부 `meetings` 에
  FK 를 건다. 뚫으면 그 표 다섯에 「업무인 회의」라는 빈 가지가 생긴다.
- **제목·담당자를 담지 않는다.** 조인으로 끌어온다. 복사하면 업무 제목이 바뀔 때
  캘린더가 조용히 낡는다.
- **시각 타입은 `Date` + `Time` + `Time`** 이다(BE Q9 가). 업무 기간이 `Date` 축이라
  「기간 밖」 판정이 단순한 날짜 비교로 끝난다. 자정을 넘는 배정은 불가능한데,
  업무 시간 배분에 그런 것이 없다.
- **모양의 선례가 이미 있다** — `task_predecessors`·`task_references` 의
  `released_at` + 부분 unique 와 같은 자리의 같은 뜻이다(BASE-003).

#### B. 사라지는 두 이유를 **갈라서** 건다 — **O3 채택**

> **사용자 결정 (2026-09-20)**: D5 를 **읽기**로 건다.

| 이유 | 메커니즘 | 자리 |
|---|---|---|
| 기간 밖으로 나갔다 | **쓰기** — `released_at` 을 찍는다 (`released_reason = out_of_range`) | 날짜가 바뀌는 세 자리 |
| 업무가 끝났다 | **읽기** — 캘린더 조회가 `tasks.state` 를 조인해 거른다 | 조회 한 자리 |

**왜 갈랐나.** 둘은 같아 보이지만 **되돌릴 수 있는가**가 다르다.

- 기간 밖은 **되돌려도 복구하지 않는다**(사용자 확정). 복구 안 함을 표현하려면
  행에 흔적이 남아야 한다 → 쓰기일 수밖에 없다.
- 업무가 끝난 것은 **업무를 따라갈 뿐**이다. `done → in_progress` 로 다시 열리면
  배정도 자연히 다시 보이는 게 맞다. 읽기면 공짜로 그렇게 된다.

**대가를 안다.** 「왜 안 보이나」의 답이 둘이 된다. 그래서 spec 이 이 둘을 **같은 절에
나란히** 적어야 한다. 그 대신 O1 의 구멍 다섯(그중 셋이 영속 계층, 하나가 정상 완료 경로)을
피한다 — 새 취소 경로가 생겨도 캘린더가 조용히 틀리지 않는다.

#### C. D5 의 「done」 은 **내부 `DONE` 만**

> **사용자 결정 (2026-09-20)**: 내부 `DONE` 만.

`COMPLETION_SUBMITTED`(완료 보고를 냈고 승인 대기)는 **아직 안 끝난 것으로 보고 배정을
살려 둔다.** 앞서 정한 D4(「미완으로 취급해 캘린더에 계속 낸다」)와 일관된다.

외부 `done`(= `DONE` + `COMPLETION_SUBMITTED`)으로 잡으면 `request_delivery_changes` 가
되돌리는 경우가 생기는데, 그때 **보완 요청 한 번에 사람이 짠 시간표가 영구히 사라진다.**
읽기 필터라 실제로 사라지진 않지만, 판정 기준이 왔다 갔다 하는 것 자체가 화면을 못 믿게 만든다.

#### D. 가시성 — **내 것만**

> **사용자 결정 (2026-09-20)**: 내 업무 + 내 회의.

- 업무: `my_work`(활성 담당만)
- 회의: `board`(참석·공유)

"이번 주에 **내가 맡은** 업무 중에 시간을 배분하고 싶은거야" 라는 원문과 정확히 맞는다.
조직 축을 골랐다면 타인의 배정이 내 캘린더에 서고, 그러면 「담당자는 조인으로」(A)가
표시 요구로 번진다 — 시안에는 그 자리가 없다.

#### E. 상호작용 — R1~R9 를 그대로 계약으로 올린다

BASE-003 의 R1~R9 를 계약으로 받는다.

**근거는 시안이 아니라 사용자 원문이다** (2026-09-20 정정). BASE-003 「입력 2」의 인용 넷이
R1·R2·R3 을 말로 확정했고, 시안 코드는 그것을 **확인해 준 것**이다. 전제가 갈린 뒤에도
R1~R9 가 그대로 서는 이유가 이것이다 — 기능이 시안에서 온 것이 아니다.

#### F. 회의는 캘린더에서 **읽기 전용**

- 좌측 레일에서 끌 수 없다 (시안 `draggable: false`).
- 시간 격자에서도 **늘릴 수 없다.** 시안 `week.jsx:231-232` 가 회의 블록에도 세로 손잡이를
  붙이지만, 회의에는 참석자·회의실 예약이 딸려 있어 캘린더에서 조용히 시각을 바꾸면 안 된다.
  회의 시각은 회의 화면에서 바꾼다.
  - **2026-09-20 정정 전에는 이것을 「시안의 빠뜨림으로 판정한다」고 적었고, 시안 작성자
    확인이 필요한 자리로 남겼다.** 전제가 갈린 뒤에는 확인할 일이 아니다 — 기능은 우리가
    정하므로 이것은 판정이 아니라 **결정**이다.

#### G. 날짜는 **ISO** 로 간다

시안 전체가 `day: number`(달 안의 일 번호)로 돈다. 이것은 목데이터의 한계지 계약이 아니다.
코드는 ISO 이므로 **달 경계를 넘는 이동·조정을 허용한다.** 시안 안에서 그 동작이 표현되지
않았을 뿐, 막을 이유가 없다.

#### H. 회의 목록은 기존 라우트에 **기간 파라미터를 더한다**

`GET /api/meetings` 에 `from`/`to` 를 더한다. 새 라우트를 내면 inventory 에 행이 늘고
count 둘이 움직이는데, 기존 라우트 수정은 `http_signature` 한 줄이다(BASE-003 비용 절).

#### I. 금지는 **말로** 한다

시안은 조용하다(`canDrop` 이 거짓이면 `preventDefault` 를 안 불러 브라우저가 거절, 문구 없음).
저장소의 같은 자리는 문구로 말한다 — 칸반 `WorkViews.tsx:520-522` `onInvalidMove`.
**저장소 선례를 따른다.** 접근성에서 조용한 거절은 원인을 못 알려 준다.

#### J. 나머지 실무 판정

| 질문 | 결정 | 근거 |
|---|---|---|
| D1 검증을 한 자리에 걸까 | **세 자리에 명시적으로** — `update`(`application.py:518-520`) · `transition`(`:1443`) · `_apply_proposal`(`:1679`) | 공통 지점 `repository.touch()` 는 날짜와 무관한 변경에도 아홉 번 불린다. 「날짜가 바뀌었나」를 스스로 판정해야 하고 틀리면 조용히 안 돈다 |
| 기간을 전부 지운 업무의 배정 | **전부 닫는다** (`released_reason = task_dates_cleared`) | 기간이 없으면 배정할 수 없다는 R1·R2 와 일관 |
| `released_by` 를 둘까 | **두지 않는다.** nullable 도 안 만든다 | 닫기는 시스템 판정이라 member id 가 없다. 왜는 `released_reason` 이 말한다 |
| `released_reason` 값 | `out_of_range` · `task_dates_cleared` 둘 | B 에서 「업무가 끝났다」가 읽기로 갔으므로 `task_closed` 사유는 생기지 않는다 |
| 하루 한 칸이 계약인가 | **계약이다** (부분 unique 로 박는다) | 사용자 원문의 「월 오전 / 화 오후 / 수 오전」이 그 모양 |
| 30분 눈금을 CHECK 로 박을까 | **박지 않는다.** 화면 편의로 둔다 | 나중에 15분으로 바꾸고 싶을 때 DB 마이그레이션이 필요해진다 |
| `local-stack` preflight 표지 | **넣는다** (`Makefile:170` + `test_local_stack_targets.py:28-40` 동시 수정) | 안 넣으면 스키마가 뒤처진 로컬에서 통과하고 런타임에 터진다 |
| 부분 unique 를 어떻게 증명할까 | `tests/integration/postgres/` 선례를 따른다 | "선언했다" 가 아니라 "선다" 를 증명한다 — `information_schema`·`pg_index` 에 묻고 잘못된 행이 거절되는 것을 남긴다 |
| 캘린더가 상태를 색으로 말할까 | **말하지 않는다** — 유형 둘(업무/회의)로만 칠한다 | 시안 `calendar.css:45-47`. 상태는 좌측 카드·상세에서 읽는다 |
| 프론트에 `completion_submitted` 를 들일까 | **들이지 않는다** | `viewModels.ts:111-120` 이 「들이면 "승인 전 done" 을 상태값으로 판단하는 코드가 다시 생긴다」는 이유로 일부러 뺐다. C 의 판정은 **백엔드 조회**에서 하므로 프론트 어휘를 바꿀 이유가 없다 |
| 오른쪽 레일 | **비운다** — `railLeft` 만 | 시안 `calendar.v1.jsx:293` |
| `GutterList` 이름 충돌 | **새것에 다른 이름을 준다** | 기존 `ds/GutterList.tsx` 의 소비처를 세지 않았다. 개명은 이번 범위 밖 |
| 「오늘」의 출처 | `seoulToday()` | 시안의 `CAL_TODAY` 하드코딩은 목데이터용 |
| 「업무 만들기」 모달 | **기존 모달을 그대로 쓴다.** 시안 `TaskCreateModal` 의 필드 구성을 따라가지 않는다 | 2026-09-20 정정 — 모달 항목은 우리 것이 정본이다. 업무 생성 계약은 SPEC-001·SPEC-003 이 이미 갖고 있고, 시안의 목 모달이 그것을 이길 이유가 없다 |
| 시안에 있고 DS 에 없는 부품 | **우리가 만든다.** FE 범위 | 2026-09-20 정정 — 디자이너가 없다. 초판은 「디자이너 몫」으로 미뤘다 |
| 새 라우트를 운영 대장에 등록할까 | **등록한다.** 라우트마다 `docs/unified-operations-inventory.json` 에 행 하나 + `http_count` 갱신 | `test_operation_inventory.py:202` 가 `http_count == len(actual)` 를 assert 한다. 안 넣으면 무조건 깨진다 — 선택지가 아니다 |

## Rationale

가장 크게 흔들린 지점은 **「한 자리에 걸면 된다」는 직관이 틀렸다**는 것이다.
코디네이터가 대화 중 D5 를 「`transition_task` 하나에 걸면 된다」로 깔고 갔는데,
조사가 상태 변경 경로 아홉 중 여덟이 그 함수를 안 지난다는 것을 파일:줄로 보였다.

그 사실을 받고 나니 선택지가 달라졌다. **구멍 다섯을 막으려 애쓰는 대신, 막을 필요가 없는
자리로 문제를 옮겼다** — 업무가 끝났는지는 조회 시점에 `tasks.state` 를 보면 알 수 있고,
그건 언제나 최신이다. 반면 「기간 밖으로 나갔다」는 조회 시점에 알 수 없다. 기간이
되돌아오면 밖이 아니게 되기 때문이다. 그래서 그것만 기록한다.

**둘을 억지로 같은 메커니즘으로 묶지 않은 것이 이 결정의 핵심이다.** 일관성은 좋지만,
성격이 다른 둘을 같게 다루면 한쪽이 반드시 망가진다.
