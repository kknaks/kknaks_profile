### 2.1 알림 목록 화면 (D-14 · D-17 · D-31 · 시안 1 §2)

- **들어오는 길**: 사이드바 「알림」(`bell`) — 모든 화면에서. 알림 화면에서는 그 줄이 활성. ~~앱 상태 `surface = "alerts"`~~ → *(v0.2.0 · W-10)* 앱 상태 **`surface = "notifications"`** — 사이드바 항목 id 도 지금 코드의 **`notifications`**(`F/App.tsx:456`) 하나로 쓴다(지금 `onSelect` 가 `setSurface(id)` 라 둘이 같아야 한다 · `App.tsx:445`). **시안 `nav.js` 의 `alert` = 코드 `notifications`**(이름만 다르다). `ProductSurface` 에 `"notifications"` 를 더한다 — 새 화면 · 라우터 없음, 지금 `surface` 모델 그대로 · FE D-3
- **틀**(시안 그대로): 머리 = 제목 「알림」 · 「안 읽음 N」(빨간 숫자 Badge) · [모두 읽음](**전체** 안 읽은 것이 없으면 비활성 — 필터와 무관 · D-40) / 필터 SegmentedControl `전체 · 업무 · 메시지 · 회의` — 테마 탭에 안 읽은 수(「업무 2」) / 레일 없는 한 단(읽기 폭 880px) / 날짜 구분 `오늘 · 어제 · 이번 주 · 이전`(KST 기준 · 구분마다 라운드 상자)
- **한 줄**(시안 그대로): 왼쪽 테마 표식(업무 accent `square-check` · 메시지 info `inbox` · 회의 progress `persons` · **실패·끊김은 danger `circle-exclamation`**) · 문장 「누가 · 무엇을 · 어디에」(사람 이름 · ‘대상 이름’ 굵게) · 보조 한 줄(있을 때만) · 아래 줄 = 테마 이름 → **관계 꼬리표** → 상대 시각 → 가는 곳(「메시지함 · 슬랙 ›」) · 오른쪽 안 읽음 빨간 점 + 안 읽은 줄 옅은 accent 배경
- **문장·보조 줄·가는 곳 글자는 화면이 만든다** — 서버는 종류(`kind`) · 값(사람 · 대상 이름 · 바뀐 값 · 건수)만 준다(§4.5). 문구 정본은 §4.2 의 「문장 모양」 열이고 `F/lib/labels.ts` 에 둔다. **OS 알림 글자도 같은 함수가 만든다**(§2.5)
- **누르면** — ① 그 줄 읽음(`POST …/{id}/read`) ② **대상(`target`)을 고른 상태로 연다**(D-31): 업무 = 업무 화면 + 그 업무 상세 / 업무 요청 = 업무 화면 + 그 요청 / 메시지 = 메시지함 + 그 메일 · 그 방(그 메시지로 스크롤 · 잠깐 강조 — SPEC-008 §2.9 ④ 와 같은 모양) / 회의 = 회의 화면 + 그 회의 / 연동 끊김 = 설정 + 그 연동 탭.
  `target` 이 `null` 이면(이제 열 수 없는 자원 — 빠진 회의 · 지워진 업무 등, §4.5-4) **읽음만** 하고 그 자리에 「열 수 없는 항목입니다」 토스트(공통 토스트 · `F/App.tsx:137-150`)

### 2.5 OS 시스템 알림 (D-06 ~ D-09 · D-21 · D-22 · D-31)

- **언제 띄우나**: 앱 셸 안에서(`hasShell()` 참 · `F/lib/shell.ts:64-72`) 사건 채널로 **`notification.upserted` 가 «새 줄»(`created: true`)로 오면** 그 알림 하나를 OS 알림 하나로 띄운다 — **단 아래 셋은 띄우지 않거나 묶는다(D-39 · 목록 · 점은 그대로)**. ~~목록에 쌓이는 것은 전부 뜬다 · 창이 앞에 있어도 띄운다(「앱이 켜져 있을 때」 — D-06)~~(v0.1.0)
  1. **보고 있으면 생략** — 앱 창이 앞에 있고(문서 `visibilityState = "visible"` 이면서 `document.hasFocus()`) **지금 화면이 그 알림의 대상**이면 띄우지 않는다. 「대상을 보고 있음」 = `target` 과 지금 화면 · 포커스가 같다: 업무 = 업무 화면에서 그 업무(또는 그 요청) 상세가 열려 있음 · 메일 = 메시지함에서 그 메일이 열려 있음 · 방 = 메시지함에서 그 방이 열려 있음 · 회의 = 회의 화면에서 그 회의가 열려 있음 · 연동 = 설정의 그 연동 탭. **알림 목록 화면을 보고 있는 것은 「대상을 보고 있음」 이 아니다**(OQ-1111)
  2. **합친 슬랙 채널 줄은 처음 생길 때만** — `created: false`(합쳐져 늘어남)는 OS 알림 없음(~~OQ-1103~~ 닫힘)
  3. **몰리면 묶는다** — 띄울 OS 알림이 **10초 창 안에 3건을 넘으면**, 넷째부터는 띄우지 않고 그 창이 끝날 때 **「새 알림 N건」 하나**(N = 띄우지 않은 수 · 누르면 알림 목록 화면)를 띄운다. 창은 첫 알림을 띄운 때부터 10초. **근거**: 사람 한 명의 연속 행동(요청 + 댓글 + 기한 변경)은 3건 안에 든다 — 그만큼은 낱낱이 보는 편이 낫다 · 숨은 · 최소화 웹뷰가 스로틀에서 풀리며 쌓인 사건을 쏟는 것(검수 §10 ⑥)과 재연결 직후 실시간 몰림은 수 초 안에 온다 · macOS 배너가 한 건에 약 5초 머무니 10초에 넷 이상이면 겹쳐 읽을 수 없다. 값은 **웹 상수**(실측 뒤 조정 — WORK-013 WP4)
- **이어 받기로 온 줄은 띄우지 않는다** — 재연결 때 `Last-Event-ID` 뒤로 다시 받은 줄(§4.1-4)은 목록 · 점만 고친다(끊긴 사이 쌓인 것을 한꺼번에 울리지 않는다) — 사건에 `replayed: true` 가 실린다
- **글자**: 제목 = 테마 이름 + 꼬리표(「업무 · 담당」) · 본문 = 목록 줄의 문장(§2.1 과 같은 함수) · 보조 줄은 싣지 않는다. 앱 이름·아이콘은 OS 가 번들에서 그린다
- **누르면**: OS 가 셸을 깨운다 → 셸이 창을 앞으로 → 셸이 웹에 **알림 클릭 사건**(`notification_id` · `target`)을 보낸다(SPEC-006 v0.7.0) → 웹이 §2.1 「누르면」 과 같은 일(읽음 + 대상 고른 상태로) · 「새 알림 N건」(묶음 — `notification_id: null`)을 누르면 **읽음 없이** 알림 목록 화면만 연다(`target = {surface: "notifications"}` · R-W5)

## 3. User Scenario

- **S-1. 업무 요청** — 팀원 A 가 나에게 업무를 요청한다 → 앱 사이드바 「알림」 에 점 · OS 알림 「업무 · 담당 — 팀원 A님이 ‘견적서 정리’ 업무를 요청했습니다」 → 누르면 앱이 앞으로 오고 업무 화면에 그 업무가 열린다 · 점이 꺼진다
- **S-2. 내가 한 일** — 내가 팀원 A 에게 업무를 요청한다 → 나에게는 알림이 없다(원칙 ①) · 팀원 A 에게만
- **S-3. 슬랙 채널** — 고른 채널에 새 메시지가 셋 온다 → 알림 목록에 「#pilot-launch 에 새 메시지가 3건 왔습니다」 한 줄 · 그 사이 나를 멘션한 메시지는 **따로 한 줄**
- **S-4. 끄기** — 설정에서 메시지 테마의 「슬랙」 을 끈다 → 이후 슬랙 메시지는 목록에도 OS 에도 없다 · 다시 켜도 끈 동안의 것은 생기지 않는다
- **S-5. 회의에서 빠짐** — 주최자가 나를 회의에서 뺀다 → 「회의 · 참석자 — ‘디자인 리뷰’ 에서 빠졌습니다」 · 누르면 「열 수 없는 항목입니다」(이제 그 회의를 못 본다)
- **S-6. 끊겼다 붙음** — 노트북을 덮었다 연다 → 사건 채널이 다시 붙으며 그 사이 알림을 목록에 받는다 · OS 알림은 몰아 울리지 않는다 · 메시지함은 다시 읽는다
- **S-6b. 배포 재시작** — 서버가 재시작되는 동안 연결이 502 로 끊긴다 → 화면이 세션을 확인(로그인 유지) → 몇 초 뒤 새 연결 + 마지막 id 로 이어 받기 · 로그인 화면으로 튕기지 않는다
- **S-9. 보고 있으면 조용히** — 메시지함에서 그 DM 방을 열어 둔 채 새 DM 이 온다 → 목록 · 점에는 서지만 OS 알림은 뜨지 않는다 · 방을 읽은 상태라 알림 줄도 읽음(D-37)
- **S-7. 회의록** — 회의를 끝낸다 → 몇 분 뒤 「회의 · 소유자 — ‘주간 기획 회의’ 회의록 정리가 끝났습니다」 · 참석자에게도
- **S-8. 연동 끊김** — 메일 토큰이 만료된다 → 「메시지 · 내 연동 — 메일 연동 … 의 연결이 끊겼습니다」(붉은 표식) → 누르면 설정 메일 연동 탭

#### 4.1-3 사건 id · 이어 받기 (D-12)

1. **id 가 있는 사건은 `notification.upserted` 하나**다. id = 그 알림의 **사건 순번**(서버 전역에서 커지는 정수 — 알림이 서거나 합쳐질 때마다 새 순번을 받는다 · 저장 위치는 WORK-013 Schema). 회원마다 띄엄띄엄이어도 된다 — **커지기만** 하면 된다
2. 다시 붙을 때 마지막 순번이 오는 길은 둘이다 — ① 브라우저가 네트워크 오류 뒤 **스스로** 다시 붙으면 **`Last-Event-ID` 머리**(EventSource 자동) ② **화면이 새 연결을 만들면**(§4.1-6 — 비-200 뒤) 새 `EventSource` 엔 그 머리가 없으므로 **쿼리 `?last_event_id=`**. **둘 다 있으면 머리가 우선**. 서버는 그 회원의 알림 가운데 아래 3-1 의 범위를 순번 순으로 `notification.upserted`(`replayed: true`)로 보내고, 이어서 **`resync`** 를 보낸다
   - **3-1 겹침 창(W-2 · 순번 ≠ 커밋 순서)** — 순번은 `nextval` 때 정해지고 보이는 순서는 커밋 순서라, 작은 순번이 더 늦게 커밋될 수 있다. 그래서 이어 받기 = **순번 > 마지막 순번** 인 것 **+ 순번 ≤ 마지막 순번이지만 `updated_at` 이 「마지막 순번 알림의 `updated_at` − 60초」 이후인 것**. *(v0.2.1 · R-W1)* **기준 줄을 못 찾으면**(마지막 순번이 합쳐지며 새 순번을 받아 그 순번의 행이 없을 때) **「그 순번 이하 가운데 가장 큰 순번 줄」의 `updated_at` − 60초**를 기준으로 · **그것도 없으면**(그 회원의 그 순번 이하 줄이 하나도 없음) 이어 받기 없이 `resync(reconnected)` 만 — 화면이 다시 읽는다. 화면은 **이미 받은 (알림 id · 순번) 쌍을 기억해 거른다**(그 세션 동안) — 겹침 창으로 다시 온 것은 끼우지도 OS 알림도 하지 않는다. **60초 넘게 열린 트랜잭션에서 선 알림**은 겹침 창에도 빠질 수 있다 — 그 줄은 `resync` 뒤 목록 다시 읽기가 메우고 **잃는 것은 그 줄의 OS 알림뿐**이다(알림을 만드는 트랜잭션은 요청 · 워커 한 단위라 60초를 넘지 않는 것이 기대값)
3. **상한 200건** — 그보다 많으면 이어 받기를 보내지 않고 `resync`(`reason: "replay_overflow"`)만 보낸다 — 화면이 목록을 처음부터 다시 읽는다
4. **메시지함 사건 넷 · `notification.read` 는 저장하지 않는 신호**라 다시 주지 않는다 — 놓친 것은 **`resync` 를 받은 화면이 API 로 다시 읽어** 메운다(지금 규칙 「재연결 때 API 로 다시 읽는다」 `user_event_hub.py:11` 그대로)
5. 첫 연결(머리 · 쿼리 모두 없음)에는 이어 받기도 `resync` 도 없다 — 서버는 첫 연결과 「순번 없이 다시 붙은 연결」 을 가르지 못한다. **그래서 다시 읽기는 화면이 맡는다**: 앱 세션의 첫 `ready` 는 처음부터 `GET` 으로 읽고, **둘째 이후 `ready` 는 `resync` 와 같이 다시 읽는다**(§4.1-2 · v0.2.1 R-F1 — 지금 WS 의 「다시 붙을 때마다 `onReconnect`」 와 같다). **한 연결에서 다시 읽기는 한 번만**(v0.2.2 · R3-W2) — 다시 붙을 때 화면이 **마지막 순번을 실었으면**(머리 또는 쿼리) 서버가 그 연결에 이어 받기 → `resync` 를 보내므로 **`ready` 에서는 다시 읽지 않고 `resync` 에서 한 번** 다시 읽는다(순서: 이어 받기 → `resync` → 다시 읽기). **순번 없이 다시 붙었으면**(`resync` 가 오지 않는다) **둘째 이후 `ready` 에서 한 번** 다시 읽는다. 같은 연결에 `resync`(`replay_overflow` · `dropped`)가 또 오면 그때는 따른다. 화면은 앱을 다시 열 때(창 새로 만듦) 마지막 순번을 들고 있지 않으므로 그때는 늘 첫 연결이다
6. 이어 받기와 실시간 사이 **빈틈이 없어야 한다** — 서버는 구독을 먼저 걸고(LISTEN 큐에 넣기 시작) 그다음 DB 에서 이어 받기를 읽어 보내며, 그사이 큐에 들어온 같은 순번은 **한 번만** 보낸다(순번으로 거른다)

  2. `readyState === CLOSED` 이면 **비-200 을 받아 브라우저가 포기한 것**이다(401 · 403 · 502 · 503 · Cloudflare 52x 를 가릴 수 없다) → 그 인스턴스를 버리고 **세션 확인 API `GET /api/auth/me`**(`B/entrypoints/http.py:736` · 화면 `getSession` `F/lib/api.ts:826`)를 부른다
     - **`401` → 세션 상실** — App 의 세션 상실 처리(`F/App.tsx:522-526` 회의 스트림 4401 과 같은 길)로. 다시 붙지 않는다 · **로그인 화면으로 가는 것은 이때뿐**

     - 세션 확인 자체도 같은 백오프로 다시 한다(그 API 도 502 일 수 있다)
  3. 브라우저 자체 재연결이 오래 이어지면(`CONNECTING` 이 30초 넘게) 화면이 버리고 2 로 간다

### 4.3 생성 규칙 (D-22 · D-23 · D-25 · D-28 · D-30 · D-33 · D-34)

1. **원칙 ① 행위자 거름** — 사건의 행위자가 받는 사람이면 만들지 않는다. 행위자 = 그 명령을 부른 회원(AX 실행이면 그 Action 을 확정한 사람). 메시지는 **`from_me = true`** 인 줄(§4.3-6)
2. **원칙 ② 항목 거름 · 설정 거름(D-22)** — 위 표에 항목이 없는 행은 만들지 않는다. 항목이 있으면 **받는 사람의 설정**(§4.4)을 읽어 **전체 · 그 테마 · 그 항목** 중 하나라도 꺼져 있으면 **만들지 않는다**(목록에도 OS 에도 없다). 끈 동안의 사건은 나중에 켜도 생기지 않는다. 설정이 없는 회원은 기본값(§4.4)
3. **관계가 둘 이상이면 하나(D-23)** — 한 사람이 한 사건에 여러 관계로 걸리면 **알림은 한 줄**, 꼬리표는 **담당 > 요청자 > 배정자 > 참조** 순의 첫 것. 그 꼬리표의 행이 정하는 `kind` · 항목을 쓴다(꼬리표가 달라도 같은 사건의 `kind` 는 표에서 정해진다). 업무 밖(메시지 · 회의)은 한 사건에 한 관계만 나온다 — 회의 소유자/참석자 겹침은 OQ-1104
4. **슬랙 채널 합침(D-25)** — X06(채널 일반 메시지)만 합친다. 받는 사람 · 그 방마다 **「합칠 줄」** = 그 방의 `message.slack`·`channel` 알림 가운데 **안 읽은 것**(`read_at` 없음)이면서 **그 줄이 선 뒤 그 방을 읽지 않은 것**(그 방 읽음 지점이 그 줄의 첫 메시지 시각보다 앞)이다. 있으면 **그 줄을 고친다** — `count` +1 · 보낸 사람 목록 · 마지막 시각 · **새 사건 순번**(§4.1-3) — 그 줄은 목록 맨 위로 온다. 없으면 새 줄. **X04(DM · 그룹 DM) · X05(멘션)은 합치지 않는다** — 메시지마다 한 줄 · *(v0.2.0 · D-37)* 메시지함에서 그 방을 읽으면 그 방의 합친 줄도 **읽음이 된다**(§4.5-3) — 그래서 「합칠 줄」 은 사실상 「그 방의 안 읽은 채널 줄」 하나다. OS 알림은 그 줄이 **처음 설 때만**(§2.5 · D-39)
5. **원칙 ③ 과 예외(D-33)** — 관계가 없는 사람에게는 만들지 않는다. **예외 하나 — 회의에서 빠진 참석자(M06)**: 빠지는 순간의 관계(참석자)로 판단해 만든다
6. **판정 재료**(D-05 · D-34) — **저장 칸은 `from_me` 하나**, 나머지는 **저장할 때 raw 에서 한 번 푼다**:

   | 재료 | 어디서 | 저장 | 근거 |
   |---|---|---|---|
   | **「내가 보낸 줄」 `from_me`** | 슬랙 = **`raw.user` == 그 연동의 `account_meta.user_id`**(이름으로 덮인 `author` 가 아니다 — 운영 4,041건 100% 덮임) · 메일 = **From 주소 == 그 연동의 계정 주소(`account_key`)**(대소문자 무시 · addr-spec · **DEC-010 D-41** — 검수 W-4) · 카톡 = **수집기가 올리는 `from_me`**(SPEC-009 v0.6.0 · SPEC-008 v0.7.0 §4.6) | **메시지 줄의 칸**(nullable bool — `null` = 모름) | 알림(원칙 ①) **과 안 읽음 수 · 메시지함 점**(SPEC-008 v0.7.0) 두 곳이 **줄마다 매번** 쓴다 — 매번 raw 를 풀면 안 읽음 셈 SQL 이 raw JSON 을 연동별로 비교해야 한다. 그래서 칸으로 |
   | 메일 「To/CC 중 나」 | 저장 때 raw 헤더(`To` · `Cc`)를 풀어 그 연동 계정 주소가 어디 있는지 | **칸 없음** — 알림의 꼬리표(`to`·`mail-cc`·`mail-other`)로만 남는다 | 쓰는 곳이 알림 생성 한 번뿐. 메일 본문 화면은 지금처럼 열 때 헤더를 푼다(INB:576-578) |
   | 슬랙 「나를 멘션」 | 저장 때 `raw.text` 에 `<@{그 연동의 account_meta.user_id}>` 가 있는지(팬아웃이라 연동마다 다르다) | **칸 없음** — 꼬리표 `mention` 으로만 | 쓰는 곳이 알림 생성 한 번뿐. `@here`·`@channel`·사용자 그룹 멘션은 **멘션이 아니다**(일반 채널 메시지 — X06) — DEC 에 문장이 없어 OQ-1105 |

   - `from_me = null`(옛 줄 · 카톡 수집기가 아직 표지를 올리지 않는 판)은 **「내가 보낸 줄 아님」 으로 다룬다** — 알림을 만들고 안 읽음에 센다. 옛 줄은 §4.7 백필이 채운다
7. **지금 생성 1곳 흡수(D-30)** — `WT:2116` 의 `emit`(요청 발송 · 수락) 자리는 **이 생성기를 부르는 자리**가 된다 — 받는 사람 셈·종류·설정 거름이 W01 · W05 규칙을 따른다(지금은 수락 알림만 요청자 · 설정 없음). 생성 멱등(같은 받는 사람 · 같은 원천이면 다시 만들지 않음 — `uq_notification_recipient_source`)은 **그대로** 둔다 — 원천 = 그 사건의 원장·감사 행(합친 줄은 처음 원천)
8. **트랜잭션** — 알림 행은 **사건을 쓴 트랜잭션 안에서** 만들고 같은 트랜잭션에서 NOTIFY 한다(§4.1-4) — 사건이 롤백되면 알림도 없다
9. **업무 수신함과 알림은 둘 다 · 읽음은 따로(D-30)** — 업무 요청 발송은 수신함 `work` 카드와 알림 W01 에 둘 다 선다. 한쪽 읽음이 다른 쪽을 접지 않는다(수신함 읽음 API · 알림 읽음 API 는 서로 부르지 않는다)
10. **보관(D-26)** — 지우는 규칙이 없다. 행은 계속 남는다

   | *(v0.2.1 · R-W5)* 묶음 OS 알림 「새 알림 N건」 | `{surface: "notifications"}` — 알림 목록 화면 · 고를 것 없음(서버 알림 항목에는 쓰이지 않고 화면이 묶음 OS 알림에만 단다) |

   화면은 지금의 포커스 상태(`focusTaskId` · `focusWorkRequestId` · `focusMeetingId` · `inboxFocus` — `F/App.tsx:87-121`)로 연다 — AX 서랍 `onOpenResource`(`F/App.tsx:694-754`)와 **같은 함수**를 쓴다
4. **읽기 인가(지금 규칙을 바꾼다)** — 지금은 행마다 원래 자원을 다시 읽어 **읽을 수 없으면 줄이 빠진다**(`B/modules/notifications.py:73-83`). 이 판은 **줄은 남기고 `target` 만 `null`** 로 한다 — 회의에서 빠진 사람(M06 · D-33) · 취소된 회의 · 철회된 요청처럼 **알림을 받는 이유가 곧 그 자원을 못 보게 된 일**인 경우가 있어서다. 그래서 **`subject.title` · `actor` · `data` 는 만들 때 저장한 값**을 보인다(지금은 자원의 지금 값을 다시 읽는다). 받는 사람 확인(남의 알림 404)은 그대로
5. 메시지 알림의 인가 = 그 메시지 · 방 · 연동이 **지금도 그 회원 것**이고 지워지지 않았으면 `target` 을 준다(SPEC-008 §5 권한)

#### 4.5-3 메시지함 읽음 → 메시지 알림 읽음 (D-37)

메시지함의 읽음 API 가 성공하면 **같은 트랜잭션에서** 그 메시지의 알림 줄(`message.mail` · `message.slack` · `message.kakao` — 받는 사람 = 그 회원)을 읽음으로 하고 `notification.read`(`notification_ids`)를 낸다.

| 메시지함 읽음(SPEC-008 §4.4) | 함께 읽는 알림 줄 |
|---|---|
| `POST /api/inbox/mail/{message_id}/read` | 그 메일의 `message.mail` 줄 |
| `POST /api/inbox/rooms/{room_id}/read` `{up_to_ts}` | 그 방의 `message.slack` · `message.kakao` 줄 가운데 **메시지 시각 ≤ `up_to_ts`** 인 것 · 그 방의 합친 채널 줄(마지막 메시지 시각 ≤ `up_to_ts` 이면) |
| `POST /api/inbox/read-all?source` | 그 출처(없으면 전부)의 메시지 알림 줄 전부 |

- **연동 끊김 · 방 접근 잃음 줄(`message.integration_lost`)은 메시지가 아니라 함께 읽지 않는다**
- **반대 방향은 없다** — 알림 줄을 읽어도 메시지는 읽음이 되지 않는다(D-37 이 정하지 않았다 · 누르면 메시지함이 그 메시지를 연다 — 그때 메시지함의 지금 읽음 규칙이 돈다)
- 업무 수신함 읽음과 업무 알림은 **그대로 따로**(D-30)

### 4.7 기존 카톡 백필 (D-35) — **일회성 수동 마이그레이션으로 정한다**

**택일: ① 일회성 수동 마이그레이션.** ② 수집기 재전송은 **지금 계약으로는 표지를 채울 수 없다** — 근거(코드를 읽었다):

- 서버 카톡 업로드는 **이미 있는 `logId` 를 건너뛴다** — `B/modules/external_channels/kakao_ingest.py` `ingest_messages`: `existing = self._repository.existing_message_keys(...)` 뒤 `if log_id in existing: continue`(`:201-208` — 같은 묶음 안 중복도 `setdefault` 로 버림). 같은 줄을 다시 올려도 **raw · 칸이 바뀌지 않는다**
- 수집기는 handshake 의 **`last_logId` 뒤만** 올린다(SPEC-008 §4.6 · SPEC-009 §3.2) — 다시 올리려면 반영 지점을 되돌려야 한다
- 그래서 ② 는 **업로드 계약 변경(이미 있는 줄 갱신) + 반영 지점 되감기 + 수집기 판 배포**가 모두 필요하다 — 116건 · 방 3개를 위해 계약을 바꾸지 않는다

**① 의 계약**

- 운영 DB 에 **한 번** 실행하는 수동 SQL(`backend/migrations/manual/` 방식 — 운영은 사람이 `psql` 로 적용)
- 인자 = **카톡 연동 id** · **사용자 본인의 카톡 표시 이름** — **둘 다 실행 인자**(`psql -v` 변수)로 준다. **이름을 SQL 파일 · 코드 · 문서 · 커밋에 쓰지 않는다**
- 동작: 그 연동의 카톡 메시지 가운데 `from_me` 가 `null` 인 줄에 — `author` = 인자 이름이면 `true`, `author` 가 다른 이름이면 `false`, `author` 가 없으면(시스템 줄) `false`
- ~~**먼저 세고 적용한다** — 적용 전 `SELECT` 로 `true` 가 될 줄 수를 보이고 운영 확인 값(본인 14건 · 방 3개 · 전체 116건)과 맞을 때만 적용~~ *(v0.2.0 · W-3 — 같은 날에도 114 → 116 으로 늘었다 · 「같음」 으로 걸면 깨진다)*
- **두 걸음 — 세고 · 사람이 보고 · 적용** — ① **셈 모드**(`-v apply=0`, 기본): 바꾸지 않고 출력만 — `true` 가 될 줄 수 · 그 줄의 방 수 · 그 연동 카톡 줄 전체 수 · `author` 이름 종류 수 · **인자 이름과 같은 `author` 가 그 연동의 «본인» 하나뿐인지**(다른 사람이 같은 표시 이름이면 멈춘다). 참고값 = 2026-10-08 운영 본인 14건 · 방 3개 · 전체 116건(`prod-check-1.md`) — 늘어 있는 것이 정상이다 ② **코디가 출력을 보고 맞다고 판단하면** 적용 모드(`-v apply=1`)로 같은 SQL 을 다시 — 한 트랜잭션 · `from_me IS NULL` 인 줄만 바꾼다(다시 돌려도 안전)
- **`from_me` 가 `null` 인 줄의 규칙(백필 전 · 새 수집기 dmg 전)** — **「내 것 아님」 으로 본다**: 알림을 만들고(원칙 ① 이 걸리지 않는다) 안 읽음에 센다. 그래서 그 사이 **내가 보낸 카톡 줄이 나에게 알림으로 올 수 있다**. 줄이는 순서 = **새 수집기 dmg 를 먼저 깔고 → 백필**(WORK-013 반영 순서) · 백필 뒤에 표지 없는 줄이 남으면(옛 수집기가 더 올렸으면) 같은 SQL 을 한 번 더 — `null` 줄만 채운다
- 이름이 바뀐 적이 있으면(카톡 표시 이름 변경) 그 기간 줄은 `false` 가 된다 — 지금 운영 분포(이름 종류 10 · 본인 이름 하나)로는 없다. 이후 줄은 수집기 표지가 정본
- 같은 SQL 에 **슬랙 기존 줄의 `from_me`**(`raw.user` == 연동 `account_meta.user_id` — 이름 인자 없이 계산된다)와 **메일 기존 줄**(From 이 계정 주소 — raw 헤더에서)을 함께 채운다 — 메일 헤더를 SQL 로 풀기 어려우면 메일은 `null`(= 아님) 로 둔다(받은편지함만 받으므로 내가 보낸 메일은 드물다 · SYNC:646)

### Validation

- SSE: `Last-Event-ID` 가 정수가 아니면 없는 것으로 본다(첫 연결처럼) · 회원의 가장 큰 순번보다 크면 이어 받기 없이 `resync`
- 알림 목록 `limit` 1~100 · `cursor` 는 서버가 준 값만(모양 검사 실패 = `422`)

- 카톡 업로드 `from_me`: bool 또는 없음(없으면 `null`)

## 5. Implementation Rules

### 서버

- **알림 생성기 하나** — 사건 × 관계(§4.2) · 규칙(§4.3) · 설정 읽기 · 행 쓰기 · NOTIFY 를 한 모듈이 맡는다. 사건 자리는 **「무슨 일이 일어났고 관련자가 누구인가」 만 넘긴다**(사건 자리마다 규칙을 따로 짜지 않는다). `WT:2116` 의 `emit` 도 이것을 부른다(D-30)
- 사건 자리 전부(W · X · M 의 「알림」 행)가 같은 트랜잭션에서 생성기를 부른다 — 자리 전수는 WORK-013 Code Surface
- **SSE 엔드포인트** = API 프로세스의 async 응답(StreamingResponse 계열) — 지금 `user_event_hub` 의 구독 큐를 그대로 쓴다. 이어 받기는 구독을 건 **뒤** DB 에서 읽는다(§4.1-3-6)
- WebSocket `/api/inbox/stream` 서버 라우트는 **화면이 더 쓰지 않는다**. 라우트 제거는 운영 반영 1회 뒤(되돌림 여지 — WORK-013 Rollback)
- 메시지 저장(`save_messages` · `kakao_ingest`)이 **저장할 때 `from_me` 를 채운다**(§4.3-6). 안 읽음 셈(`B/platform/external_channels_inbox_store.py:197-199`)은 `from_me is not true` 로(SPEC-008 v0.7.0)
- 읽기 인가 변경(§4.5-2-4) — 저장한 제목 · 행위자 · 값을 보이고 `target` 만 인가로 가른다. 지금 `_authorized_view`(`B/modules/notifications.py:73-83`)와 정의만 있는 `_authorized_notification_view`(`BA:2473-2492` · 호출 0)를 **하나로** 정리한다

- **앱 전역 사건 채널 하나**(EventSource) — `App` 이 소유하고, 화면은 사건 이름으로 구독(지금 `createInboxEventHub` 의 구독 모양을 전역으로 · `F/features/inbox/inboxStream.ts:72-88`)
