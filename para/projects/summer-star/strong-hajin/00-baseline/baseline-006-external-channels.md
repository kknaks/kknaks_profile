# 외부 채널(메일·슬랙·카톡) — 들어온 요구, 원래 시안이 그린 것, 실물 시험과 카톡 조사가 보여 준 것

메일·슬랙·카카오톡에 흩어진 대화를 Strong Hajin 안으로 가져오자는 요구가 들어왔다.
이 문서는 그 요구와 함께 **원래 시안(설정·수신함)이 그린 것**, **지금 제품에 서 있는 「업무 > 수신함」**,
**메일·슬랙 실물 시험 결과**, **카톡 조사 셋**, **시안을 여섯 번 고친 기록**을 눕힌다.

**판단하지 않는다.** 무엇을 채택하는지는 DEC-008 이 가른다.

### 입력 1 — 사용자 요구 (2026-10-05 ~ 06)

원장 §2 의 행 가운데 **사용자가 낸 요구의 원문 요지**다. 어떤 것이 채택·대체되었는지는 DEC-008
부록 대응표가 센다.

| 주제 | 사용자가 말한 것 (요지) |
|---|---|
| 일의 순서 | 시안 → 정책 확정 → 구현. 채널은 슬랙 → 메일(회사 Google Workspace) → 카카오톡 순 |
| 카톡을 가져오는 길 | Tauri 데스크톱 앱(Rust)이 개인 Mac 의 카톡 **로컬 DB** 를 읽어 가져온다 |
| 채널의 단위 | 메일 = 건 · 슬랙(채널)·카톡(대화방) = 흐름 |
| 메시지가 오면 | 도착 = 이벤트 → AX 가 읽고 내 프로젝트·업무를 탐색 → **업무 업데이트 / 업무 생성 / 패스** |
| 화면 둘 | 시안 `Inbox.html` = 수집한 메시지를 **조회**하는 자리. AX 의 생성·업데이트 제안을 사람이 판단하는 자리는 기존 **업무 > 수신함** |
| 단계 | 1단계 = 메일·슬랙·카톡이 쌓인다(설정 연동 화면 + 수집 + 조회·읽음). 2단계 = AX 판단 |
| 슬랙 | 보고 싶은 채널·대화방(DM·그룹 DM)을 설정에서 저장 → 이벤트가 생길 때마다 실시간 반영 |
| 메일 | 사용자 1회 등록으로 읽기와 답장을 모두 덮는다 |
| 저장과 노출 | 메일/슬랙 수신 → 우리 DB 저장 → 앱에서 **개인별 노출** |
| 과거 | 최초 1회 연동 때 과거 내용을 최대한 |
| 본문 모양 | 메일은 메일답게, 슬랙은 **진짜 슬랙 대화방처럼** |
| 답장 | 메일 답장·전체 답장 · 슬랙 메시지·스레드 답글 · 첨부 보내기 |
| 카톡 범위 | Mac 에서만. Rust 앱이 백그라운드 실행 · **카카오톡이 켜져 있는지 확인** |
| 설정의 계정 메뉴 | 「계정 설정」 → 「프로필 설정」 — 프로필 이미지 · AX 캐릭터 · 비밀번호 변경. 이름·직무는 조직 명부 값 |
| 피드백 | 메시지함 본문은 폭 전체 · 슬랙 스레드는 오른쪽 패널 (`design-feedback-batch-1.md`) |

### 입력 2 — 원래 시안이 그린 것 **(시안-원)**

설정 `Settings.html` · 수신함 `Inbox.html` 두 장. 관측 원장은 `design-survey.md` §2~§4.

#### 2-1. 설정 — 세 연동이 같은 틀

- 메뉴 두 묶음: **연동**(`메일 연동`·`슬랙 연동`·`카카오톡 연동`) · **계정**(`계정 설정`·`알림 설정`) (`design-survey.md:64-66`)
- 세 연동이 같은 순서로 선다 — 「적재 상태 3셀 → 대상 목록(받아오기·삭제) → 추가」.
  시안 주석: 「연동의 목적이 흩어진 메일·대화를 **우리 DB 로 적재**하는 것」 (`design-survey.md:68`)
- 적재 상태 3셀 = `마지막 수집` · `DB 적재 건수` · `수집 주기`(15분·1시간·6시간·수동) (`design-survey.md:74-75`)

| 연동 | 시안-원이 그린 연결 방식 | 대상 고르기 | 눈에 띄는 문구 |
|---|---|---|---|
| 메일 | **IMAP + 비밀번호/앱 비밀번호** 폼 하나. 목데이터엔 「Gmail · OAuth 연결됨」 행이 있으나 OAuth 단추·흐름은 없다 | 계정 단위 · `가져올 범위`(30일·**90일 기본**·1년·전체) | 「가져올 범위는 처음 연결할 때 한 번」 · 「비밀번호는 암호화해 보관」 (`design-survey.md:85-92`) |
| 슬랙 | 워크스페이스 카드가 「연결됨」 한 상태만 — **연결 단계 없음** · 봇 권한 `channels:history`·`groups:history` | **채널 이름을 손으로 입력** | 「봇이 초대된 채널만 추가할 수 있다」 (`design-survey.md:96-106`) |
| 카톡 | **기기·계정 연결 카드 없음** | **대화방 이름을 손으로 입력** · 메타 「단체방」 | 「참여자에게 수집 사실이 공지된다」 · 「대화방을 추가하면 참여자에게 안내가 전송되고, 동의 이후 대화부터 적재된다」 (`design-survey.md:110-119`) |

- 계정 설정 = 프로필(아바타 변경·삭제, `이름`·`직무` 입력, 「프로필 저장」) · 비밀번호(현재/새/확인) (`design-survey.md:123`)
- 알림 설정 = 받는 경로(앱·메일·슬랙 DM) · 묶음 `업무`·`회의 · 연동`(「연동 수집 실패」 포함) (`design-survey.md:124-126`)

#### 2-2. 수신함 — 카드와 행동

- 내비의 **독립 화면** `./Inbox.html`, 이름은 「수신함」. 출처 전환 `전체·메일·슬랙·카톡` (`design-survey.md:134-143`)
- 메일 = **단건 카드**, 슬랙·카톡 = **대화방 하나가 카드 하나**(마지막으로 읽은 뒤 쌓인 메시지를 묶음) (`design-survey.md:149`)
- 메일 카드에만 **`업무`/`참고` 배지**, 값(`candidate`)을 누가 정하는지 시안에 없다 (`design-survey.md:155`·`:210`)
- 카드·본문의 행동: `+`/`내 업무로` · `답장` · `원문 확인하기` · `확인완료` · `대화 보기` · `대화방 열기` ·
  `모두 읽음으로`. **결과가 그려진 것은 「누르면 읽음」과 「모두 읽음으로」뿐**이다 — `내 업무로` 는 빈 함수,
  `답장`·`대화방 열기`·`확인완료` 는 핸들러 없음 (`design-survey.md:185-197`)
- 시안 수신함엔 **AX 자리 · 로딩·오류 상태가 없다** (`design-survey.md:194`·`:197`)

#### 2-3. 시안-원이 남긴 질문

`design-survey.md` §7 이 질문 **39** 개를 세웠다 — 공통 C-1~C-16 · 슬랙 S-1~S-7 · 메일 M-1~M-8 ·
카톡 K-1~K-8. 각 질문이 어떻게 받아졌는지는 DEC-008 이 센다.

### 입력 3 — 지금 서 있는 「업무 > 수신함」 **(문서)**

`design-survey.md` §5 가 시안 수신함과 기존 수신함을 나란히 놓았다.

| 무엇 | 기존 「업무 > 수신함」 | 시안-원 「수신함」 |
|---|---|---|
| 자리 | 업무 화면의 **좌 레일** (`design-survey.md:225`) | 내비의 **독립 화면** |
| 담는 것 | **업무 요청**(내가 답할 것) + **참고**(CC) — `spec-001-work-management.md` U-12 | **외부에서 수집한 것만** — 메일·대화방 |
| 필터 축 | 기획 = 종류 칩 · 코드 = 상태 축(판단 대기·조정 필요) (`design-survey.md:243`) | **출처** |
| 읽은 뒤 | 참고 카드는 **읽으면 수신함에서 사라진다** (SPEC-001 U-12 · DEC-001) | **읽어도 남는다** |
| 이름 | 「수신함」 | 「수신함」 — **같은 이름** (`design-survey.md:233`) |

- SPEC-001 은 「수신함·메일·그룹웨어 → **다음 slice**」로 밀어 두었다 (`spec-001-work-management.md:172`).
  BASE-001 은 메일·그룹웨어 **API·권한·회신 성공 판정**을 원문 미결 C-2 로, **원문 보존·파기 기간**을 C-9 로 둔다
  (`baseline-001-work-page.md:337`·`:344`)
- 업무의 「출처」 행은 기획상 **AX 제안·요청·직접 배정** 셋뿐이다 — 외부 메시지에서 온 업무의 출처 자리는
  없다 (`design-survey.md:254`)

### 입력 4 — 메일·슬랙 실물 시험 **(시험)** (2026-10-06)

#### 4-1. Gmail API

| 항목 | 관측 |
|---|---|
| 붙인 자리 | **회사 GCP 프로젝트**에 데스크톱 클라이언트 하나 |
| 동의 | **1회**로 `gmail.readonly` + `gmail.send` **동시 부여** |
| 토큰 | refresh token 받음 |
| 읽기 | 받은편지함 **5통** 읽음 |
| 남은 물음 | 운영 연동을 어느 GCP 프로젝트에 둘지(회사/개인 · 이직 · 상용) — 원장이 미결로 적었다 |

#### 4-2. 슬랙 사용자 토큰

| 항목 | 관측 |
|---|---|
| 앱 | 회사 워크스페이스에 **새 앱** 하나 |
| 권한 | **User Token Scopes 10개**(`admin.teams:write` 제외) |
| 설치 | **관리자 승인 없이** 설치됨 |
| 방 목록 | 채널 **52** · 비공개 **4** · 그룹 DM **35** · DM **53** |
| 읽기 | 채널·DM 메시지 읽기 ✓ |
| 그룹 DM 이름 | `mpdm-…` 꼴 — 참여자 이름으로 풀어야 사람이 읽는다 |
| 봇 | DM 목록에 봇이 섞여 있다. 실측: **DM 66 중 봇 26** · **채널 56 중 39 에 봇 메시지** |

- 시안-원의 슬랙은 **봇 권한**(`channels:history`·`groups:history`)으로 그렸다 — **봇은 남의 DM 을 읽지 못한다**
  (원장 2026-10-05 슬랙 기본값 행의 근거)
- 슬랙 파일 보내기엔 `files:write` 사용자 권한이 **더 필요하다** — 시험 10개 권한에 들어 있는지는 원장이 적지 않았다

### 입력 5 — 카톡 조사 셋 **(조사)**

#### 5-1. 조회와 발송 (`kakao-survey.md`)

| 축 | 관측 |
|---|---|
| **조회** | **된다.** Mac 은 복호 키를 **기기 값에서 오프라인으로 유도**한다 — 카톡이 꺼져 있어도, 메모리를 안 건드려도 로컬 DB 를 읽는다 (`kakao-survey.md` §1). Windows 판(`mykakao`)이 막혔던 벽(오프라인 키 파생 실패)이 Mac 엔 없다 |
| 키 | 사용자가 키를 넣지 않는다 — 기기 값에서 언제든 다시 유도된다 (`kakao-survey.md` §2 표 「키 입력 필요?」) |
| **발송** | **API 가 아니라 UI 자동화**(macOS 접근성). 카톡 실행 + 로그인 + 접근성 권한 필요 · **텍스트만** · 발송 멈춤(hang) 이슈 열림 · 오발송 소지 (`kakao-survey.md` §3) |
| 실시간 | `kakaocli` 는 **폴링**(고수위 logId, 기본 2초). Windows 판은 파일 변경 감지 (`kakao-survey.md` §2) |
| 과거 범위 | **이 Mac 에서 연 채팅만** 로컬에 있다 — 더 불러오는 길은 유료 기능에 막힌다 (`kakao-survey.md` §2) |
| 방 목록 | 읽힌다 — 1:1·단체·오픈채팅 구분 가능 (`kakao-survey.md` §5 K-3·K-4) |
| 동의 문구 | 로컬 DB 를 조용히 읽는 방식이라 상대에게 안내·동의를 받는 단계가 **기술적으로 없다** (`kakao-survey.md` §5 K-2) |
| 안정성 | 비공식 도구 · 카톡 버전 업데이트로 키·userId 탐지·실행 경로가 깨진 이력 · 마지막 커밋 2026-03-31 (`kakao-survey.md` §6) |
| 붙이는 그림 | 선택지 A 사이드카 / B Rust 포팅 / C 하이브리드 — **결정하지 않았다** (`kakao-survey.md` §4) |
| 새 질문 | K-9 첨부 · K-10 키 보관 위치 · K-11 발송 안정성 · K-12 여러 Mac (`kakao-survey.md` §5) |

#### 5-2. 첨부 (`kakao-attach-survey.md`)

- 첨부 **구분**은 메시지 행 안에서 된다 (`type` + 첨부 JSON)
- Mac 에는 메시지 번호로 집을 수 있는 **로컬 첨부 저장소가 안 보인다** — 시스템 URL 캐시는 불투명하고 OS 가 비운다
- 실체는 **시간제한 CDN URL** 에 묶여 있다 → 메일·슬랙처럼 「저장하지 않고 클릭할 때 받기」가 **카톡엔 그대로
  안 통한다** — 공식 재조회 API 가 없고 URL 이 만료되면 끝이다 (`kakao-attach-survey.md` §1)
- 길 셋 비교 — (가) 서버가 CDN URL 로 중계 · (나) Rust 앱이 로컬 파일 중계 · (다) 수집 시점에 받아 보관.
  **결정하지 않았다** (`kakao-attach-survey.md` §3)

#### 5-3. DB 필드 (`kakao-db-fields.md`, 본인 DB 사본 · 읽기 전용 · 사용자 승인)

| 항목 | 관측 |

| 중복 키 | 메시지 번호 단독은 유일하지 않다 · **(방, 메시지 번호)** 조합은 전수 유일 (`kakao-db-fields.md` §6) |
| 로컬 파일 경로 칸 | 사용자가 **손으로 저장한 파일만** 가리킨다(사진 30 · 파일 43) — 자동 캐시가 아니다 (`kakao-db-fields.md` §7) |

## 이 문서가 답하지 않은 것

1. 무엇을 1단계에 넣고 무엇을 미루는가
2. 메일 연결 방식(IMAP / Gmail API)과 연동을 둘 클라우드 프로젝트
3. 슬랙 토큰 종류 · 고를 수 있는 방의 종류 · 봇 메시지 처리
4. 실시간인가 주기인가, 과거를 얼마나 가져오는가
5. 연동·방·메시지의 소유와 공유, 삭제의 성격
6. 첨부를 우리 쪽에 저장하는가 — 메일·슬랙과 카톡이 같은가
7. 답장의 범위와 채널별 차이
8. 카톡의 범위 — 조회·발송, 방 종류, 키의 자리, 동의 문구
9. 설정의 계정·알림 메뉴의 운명
10. 시안-원 질문 39 와 시안 변경 판들이 남긴 미결 각각의 처분

→ 전부 DEC-008 이 받는다.

## 조사 한계

- **이 문서는 코드를 읽지 않았다.** 코드 관측은 `design-survey.md` §5 의 인용을 그대로 옮긴 것이다.
- **실물 시험은 시험 스크립트 한 번씩**이다 — 실시간 수신(슬랙 이벤트 · Gmail 푸시 신호)·보내기·첨부 받기는
  시험하지 않았다. Gmail 은 읽기 5통, 슬랙은 목록·읽기까지다.
- **카톡 CDN 은 접속하지 않았다.** 만료 수치는 URL 의 `expires` 와 보낸 시각의 차이로 셈한 것이고,
  실제로 끊기는 시점은 미검증이다 (`kakao-db-fields.md` §3).
- **카톡 DB 확인은 한 사용자·한 기기·카톡 26.1.1 하나**다. 다른 버전·한국어 설치판·여러 Mac 은 보지 않았다.
- **시안은 목데이터**다 — 실시간 갱신·OAuth 동의 화면·보내기 성공/실패는 흉내다 (각 판 §4).
- 원격 시안의 `_ds_bundle.css` 뒤 73KB 는 비교하지 못했다 (`design-survey.md:29`).
