## Why It Matters

이슈가 "구현하지 않았다"고 말한 것과 "코드에 이미 있다"와 "원문이 이미 닫았다"가 섞여 있다.
셋을 가르지 않으면 있는 것을 다시 만들거나, 원문이 답한 것을 사용자에게 다시 묻거나,
폐기된 어휘를 계약에 남긴다. 특히 네 곳이 갈린다.

1. **수락 gate 는 한 종류가 아니다.** 배정 수락, 요청 수락, 완료 승인이 각각 다른 원장·다른
   명령이다. 어느 것을 걷는지 kind 단위로 갈라 두지 않으면 완료 승인까지 사라진다.
2. **`completion_submitted` 는 상태 하나가 아니라 경로다.** 전이표·화면·라벨·테스트가 함께 물린다.
3. **「막힘」은 원문에서 폐기됐다.** 대체재는 회신 대기 + 상태 메모다. 대체재를 미루고 원본만
   남기면 원문과 반대 방향의 계약이 된다.
4. **회의 후속 승격은 「회의 쪽 흐름」이 아니다.** 이번에 바꾸는 바로 그 두 생성 경로를 호출한다.

## 현행 코드의 사실 정정 — 멱등성과 유일성

DEC-001 D-3 과 SPEC 인수조건이 여기 기댄다. **기존 경로 재사용만으로는 서지 않는다.**

| 주장 | 사실 | 근거 |
|---|---|---|
| `POST /api/tasks` 가 이미 멱등하다 | **아니다.** 핸들러가 `causation_key` 를 넘기지 않는다 | `entrypoints/http.py:1251-1265` — `title/description/start_date/due_date/checklist/reference_task_ids/parent_task_id/project_id` 뿐 |
| 요청 본문에 멱등 키를 실으면 된다 | **거부된다.** `TaskCreationFields.model_config = ConfigDict(extra='forbid')` | `modules/work/task_creation.py:12-13` |
| `causation_key` 재조회가 REST 를 덮는다 | **아니다.** 그 키를 채우는 호출자는 AX 판단 경로뿐이다 | `platform/actions.py:705,816,838` (`causation_key=str(action.id)`) ↔ `work_tasks.py:326-328` |
| 중복 활성 담당이 막혀 있다 | **아니다.** 인덱스 하나뿐이고 unique 제약이 아니다 | `platform/persistence.py:1531` `Index("ix_task_assignments_assignee_status", …)` |
| 회의 후속 승격은 중복이 안 난다 | 승격 **기록** 층에서만 막는다. 생성 명령 자체의 멱등 키와 다른 층이다 | `modules/meetings/followups.py:21-27` |

따라서 REST 재전송은 지금 중복 Task 를 만든다. 목표 계약은 **신규 계약**이다.

## 용어 충돌 — 계약 이름과 현행 필드

SPEC 이 쓰는 계약 어휘를 현행 필드에 1:1 로 매핑하면 뜻이 뒤집힌다. 매핑은 work 가 정한다.

| 현행 필드 | 값 | 뜻 |
|---|---|---|
| `tasks.origin_kind` | `direct` | **본인 생성** (`work_tasks.py:344`) |
| 〃 | `request_effect` · `meeting` · `assignment` · `project_plan` | 요청 수락 · 회의 후속 · 관리자 배정 · 프로젝트 계획 (`:1235,1683,1538`) |
| `task_assignments.assignment_kind` | `self` · `request_effect` · `direct` | 본인 · 요청 수락 · **관리자 배정** (`persistence.py:1527`) |

같은 낱말 `direct` 가 두 필드에서 반대를 가리킨다. SPEC 은 이 낱말을 쓰지 않고
사람이 읽는 값(본인 생성 · 수평 요청 · 관리자 배정 · 회의 후속)으로만 계약한다.

## Possible Direction

결정이 아니다. 갈림길만 적는다. DEC-001 이 고른다.

1. **즉시 배정 명령의 자리** — (a) `POST /api/tasks/assign` 의 의미를 바꾼다 (b) `POST /api/tasks`
   에 수신자 인자를 더한다 (c) 새 명령을 판다. (b) 가 "한 번의 명시적 생성 명령"(W1.4)에 가장
   가깝고, (a) 는 `task.assign` 권한 게이트가 W1.5 와 부딪친다.
2. **`completion_submitted` 와 `blocked` 를 어떻게 걷나** — 둘 다 전이표·라벨·칸반 칼럼·정렬 키·
   프론트 타입·contract 테스트가 함께 움직인다. 승인 대기는 `delivery_view` 파생으로,
   막힘은 회신 대기 + 상태 메모로 간다.
3. **멱등성과 유일성을 어디서 세우나** — 요청 본문의 멱등 키 필드 추가(`extra='forbid'` 확장),
   활성 담당의 유일성 보장, 그리고 재전송이 같은 결과를 돌려주는 계약. 셋 다 신규다.
4. **회의 후속 승격을 어느 문서가 갖나** — 생성 계약은 SPEC-001, 승격의 후보·출처는 회의 쪽.
   원문은 경로를 `PLAN-004` 소유로 두되 **자동** 승격만 제외했다(PLAN-001:130).
