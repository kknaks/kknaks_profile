# 업무 구조·생명주기 v2 — 사용자 승인 원문과 현재 작업본 관측

2026-09-17 사용자가 승인한 업무 정의·생명주기 v2 원문과, 그 방향을 받는 **현재 작업본**의
관측을 한자리에 모은다.

> 아직 결정하지 않은 입력이다. **무엇이 원문 사실이고, 지금 코드가 무엇인지**만 남긴다.
> 무엇을 바꿀지는 DEC-002, 계약은 SPEC-003 이 갖는다. SPEC 은 코드 경로를 싣지 않고
> 이 문서의 절을 이름으로 가리킨다.
> **원문 사실과 현재 관측을 절로 갈랐다.** 섞어 읽지 않는다.

## Raw

### 입력 1 — 사용자 승인 원문 세 건 (2026-09-17)

| 문서 | 경로 | 역할 |
|---|---|---|
| 정의 v2 | `reference/2026-09-10-sc-meeting/정의_v2.md` | 업무의 정의·구조·세 행위·완료 규칙 |
| 생명주기 v2 | `reference/2026-09-10-sc-meeting/생명주기_v2.md` | 생성부터 완료 확인까지의 흐름·합의/미정 구분 |
| 작업계획서 v2 | `reference/2026-09-10-sc-meeting/작업계획서_v2.md` | 구현 계획·인수 시나리오 A1~C2·검증 명령·데이터 호환 |

세 문서가 **최신 사용자 승인 방향**이다. 기존 `definition.md`·`lifecycle.md` 는 참고 기록이며
구현 명세가 아니라고 원문이 직접 밝힌다(생명주기 v2 머리말 · 작업계획서 §1).

### 입력 2 — 이번 발주의 범위 (2026-09-17 사용자)

**초기 승인 (2026-09-17 오전) — 기록으로 보존한다.**

- 프론트 **전면 디자인 개편이 예정**되어 있어 **v2 스펙 + 백엔드만 먼저** 진행한다.
- **이번 발주는 스펙 단계까지다.** WORK 계획과 코드 구현은 스펙 검수 뒤 별도 발주다.
- 프론트/UI/E2E/디자인 싱크는 이번 범위 밖이다.

**갱신 승인 (2026-09-17 오후) — 위 세 줄 중 셋째를 대체한다.**

사용자: 「아니 이제 프론트까지 같이 작업 할 수 잇는거 같아서」. 확정 시안이 내려왔기 때문이다
(입력 5). 코디네이터가 **WORK-002 를 BE v2 + 새 시안 FE 통합 계획**으로 받고, 검수 뒤
**BE/FE 분담 구현**으로 진행하는 것으로 수락했다.

- **프론트가 범위 안이다.** 화면 요구는 「미래 요구로 보존」이 아니라 **이번 판의 UX 계약**이다.
- **다만 이번 문서 단계는 여전히 스펙까지다.** WORK-002 는 다음 단계이고 이번에 쓰지 않는다.
- **E2E(브라우저 확인)는 사용자 담당 그대로다.** 이 줄은 갱신되지 않았다.
- 코드·디자인 파일 수정은 이번 범위 밖이다(문서만).

### 입력 3 — `example.md` — 사용자가 추가 지정한 네 번째 원문 (사례집)

**2026-09-17 사용자가 `reference/2026-09-10-sc-meeting/example.md` 를 예시 원문으로 명시 지정했다.**
세 원문도 모두 이 문서를 참조한다(생명주기 v2 머리말 · §8 마지막 줄, 작업계획서 §1).
**전문(649줄)을 읽어 아래 § 원문이 확정한 것 — example.md 와 § example.md 가 연 미정에 반영했다.**

**관측 이력을 그대로 남긴다** — 이 문서를 쓰기 시작한 2026-09-17 오후 시점에는
`reference/2026-09-10-sc-meeting/example.md` 가 **없었고**, 레포 전체(`_archive/` 포함)에도
같은 이름의 파일이 0건이었다. **작업 도중(파일 타임스탬프 13:57) 생겼다** — 다른 세션이
만든 것으로 보인다. 아래는 **생긴 뒤의 내용을 읽은 결과**다.

- 649줄의 **사례집**이다. 머리말이 스스로 "현재 구현 명세가 아니며, 아래에 나오는 검토안은
  사용자와 합의한 정책이 아니다" 라고 밝히고, **합의 / 미정 / 검토안**을 절마다 구분해 적는다.
- 마지막 줄이 "**이 사례집의 미정 분기나 검토안을 구현 정책으로 사용하지 않는다**" 이다.
- 따라서 이 문서는 **보조 자료**다. 정의·생명주기·작업계획서 세 건이 위이고 여기가 아래다.
- 확인한 「합의」 표시 내용은 **세 원문과 어긋나지 않는다** — 발송 시 Task 생성(§9.1) ·
  거절 시 cancelled·재요청은 새 Task(§9.2) · 직접 작업은 중심 업무 직속까지(§5.4) ·
  취소 제외 미완료 하위로 상위 완료 차단(§6.4) · 체크리스트와 하위 Task 구분(§6.5) ·
  요청자의 하위·연결 자료 조회(§5.5)가 전부 같다.
- §9.2 가 "**수락 시 Task 를 처음 생성하는 이전 검토안은 채택하지 않았다**" 라고 적어,
  발송 시 생성이 확정임을 한 번 더 못 박는다.

**어긋나는 자리 1건 — 보고한다.**

| 항목 | `example.md` | 작업계획서 v2 | 처분 |
|---|---|---|---|
| 순환 관계·자기 참조 차단 | **§7.8 「미정: 이동 허용 여부와 순환 방지 규칙」** | **§4.5 「순환 관계·자기 자신 연결을 막고」 — 구현 항목으로 확정** | **작업계획서 우선.** 사례집은 보조이고 스스로 「미정 분기를 정책으로 쓰지 말라」고 적는다 |

`example.md` 가 별도로 여는 미정(세 원문에도 이미 열려 있는 것) — 복수 담당·Task 당 담당자 수(§7.6) ·
여러 상위 업무(§7.7) · 상위 관계 이동 권한(§7.8) · 담당 변경 후 기존 하위 구조의 처리(§5.4).
전부 DEC-002 M-6 과 같은 자리다.

**사례 원장** — 생명주기 v2 §8 표와 `example.md` §9·§10 이 같은 9단계를 말한다. SPEC-003 은
**생명주기 v2 §8 을 원장으로** 쓰고 `example.md` 는 보조로만 읽는다.

### 입력 4 — 같은 디렉토리의 다른 자료

`reference/2026-09-10-sc-meeting/` 에는 `plan-004-meeting-note.md`(25KB) ·
`screen-005-meeting-note.md`(164KB) · `[공유용] TheSC AX.fig` · `task.md` 가 함께 있다.
`task.md` 는 **정리 이전의 날것 메모**이고 첫 줄이 "위로는 정리본이 올라옴"이다 —
업무의 정의를 「조직에서 일하는 최소 단위」로 적고 「신규/연관/하위」 세 성격을 나눈다.
**정의 v2 가 이 메모를 대체한다**(업무를 만드는 세 행위 = 본인 생성·요청·배정). 충돌로
다루지 않고 **선행 메모**로 둔다. 나머지 셋은 회의·화면 자료이고 이번 백엔드 범위 밖이다.

| 문서 | 경로 | 역할 |
|---|---|---|
| 발주서 | `reference/2026-09-10-sc-meeting/design-change-2026-09-17/00-발주서.md` | 분석 3종의 지시·전수조사 요구 |
| 01 | 같은 디렉토리 `01-현재화면-대-시안.md` | 현재 화면 → 확정 시안 차이 (탭·표·칩·레일·모달·내비) |
| 02 | 같은 디렉토리 `02-DS-gaps.md` | 시안이 쓰는데 우리 DS 에 없는 부품·토큰·글리프 |

**이 셋의 위치를 분명히 해 둔다.**

- **확정 시안(`.design-sync/screens/`, 코드 레포)이 디자인의 정본**이고, 위 셋은 **그 시안을 읽은
  분석 보고서**다. 보고서의 주장을 그대로 정책으로 올리지 않는다.

  **최신 SPEC-003 대조가 아니다.** 스스로 「판정하지 않는다 · 차이만 적었다 ·
  시안이 그리지 않은 것이 정책 부정은 아니다」라고 적는다(`03` 머리말).
- 따라서 `03` 의 OQ 를 **그대로 사용자 질문으로 복사하지 않는다.** 최신 계약으로 이미 답이 있는지,
  표현·매핑의 기술 선택인지, 진짜 새 제품 정책인지를 먼저 가른다 — DEC-002 § 시안 반영이 그 원장이다.
- `01`·`02` 는 **화면·디자인 시스템 차이**이고 백엔드 계약과 직접 닿지 않는다. SPEC 이 쓰는 것은
  그중 **API 데이터가 필요한 자리**뿐이다.

## Context

### 이 입력이 서는 자리

`BASE-001 → DEC-001 → SPEC-001·SPEC-002 → WORK-001` 계보가 이미 있고, WORK-001(W1)의
**구현이 미커밋 상태로 작업본에 살아 있다**(§ 현재 관측). v2 는 그 W1 이 확정한 것 가운데
**요청·수락·담당 변경**을 정면으로 되돌리고, W1 이 범위 밖으로 둔 **상하위 관계**를 1차로
끌어온다. 그래서 이 문서는 BASE-001 을 대체하지 않고 **그 위에 덧쓰는 두 번째 입력**이다.

### 관측 기준점

- 문서 레포: `toy_pr2/kknaks_profile`, 워크트리 `kknaks_profile/strong_hajin`,
  브랜치 `kknaksss/strong_hajin`, 최근 커밋 `6906c47`.
- 코드 레포: `/Users/kknaks/orca/workspaces/Strong_hajin/strong-hajin-work`,
  **HEAD `8973791`**, 브랜치 `kknaksss/strong-hajin-work`.
  **읽기 전용으로만 열었다.** 이번 작업에서 코드·DB·테스트를 건드리지 않았다.
- 작업본에 **W1 미커밋 변경이 살아 있다** — 2026-09-17 `git status` 기준 `backend/src` 18개 ·
  `backend/tests` 다수 · `README.md` 등이 `M`(수정) 상태다. 아래 관측은 **그 미커밋 상태**를 읽은 것이고
  `origin/main` 의 상태가 아니다.

### 실행하지 않은 것 — 사실 그대로

| 항목 | 상태 |
|---|---|
| PostgreSQL 실제 스키마(컬럼·FK·인덱스) 확인 | **하지 않았다.** DB 접속이 이번 금지 범위 |
| 테스트 실행(`make test-unit` · `test-contract` · `test-postgres`) | **하지 않았다** |
| 프론트·브라우저 확인 | **하지 않았다.** 이번 범위 밖 |
| 코드 수정 | **하지 않았다** |

따라서 아래 관측은 전부 **ORM·애플리케이션 코드를 읽은 결과**이고, 실행 DB가 그와 같다고
전제하지 않는다.

### 과거 관측과 지금 관측의 구분

작업계획서 v2 §3 의 표는 **그 문서를 쓰던 대화 시점의 관측**이다. 아래 § 현재 관측은
2026-09-17 에 같은 자리를 다시 읽은 것이다. 두 관측이 어긋난 자리는 § 과거 관측과의 차이에 적는다.

### 47 / 1297 을 통과 근거로 쓰지 않는다

작업계획서 §3 마지막 줄이 「이전 선택 계약 테스트 47개 통과는 현 구현의 회귀 기준이다.
새 정책의 인수 기준을 통과한 결과로 사용하지 않는다」고 직접 못 박는다. 이 문서도 같다 —
**과거에 통과한 어떤 수치도 v2 통과의 근거가 아니다.** 이번에 실행한 검증은 0건이다.

## Why It Matters

W1 은 「수락 없이 즉시 배정」을 계약으로 세웠고 그 구현이 작업본에 있다. v2 는 그 자리에
**수락 대기**를 되돌려 놓는다. 이것은 enum 한 줄이 아니라 요청·담당·판단함·수신함·권한이
함께 움직이는 반전이다. 무엇이 뒤집히고 무엇이 그대로인지를 문서로 못 박지 않으면,
구현이 W1 기록을 「v2 를 이미 지원한다」로 오독하거나, 반대로 W1 이 세운 유효 보장
(멱등 키 · 활성 담당 유일성 · 권한 재검사)을 함께 걷어낸다.

## 원문이 확정한 것 — 정의 v2

문장은 요약하고 **절 번호로 가리킨다.** 원문을 이 문서로 복사하지 않는다.

| ID | 확정 사실 | 원문 |
|---|---|---|
| V-1 | 업무 = 담당자·기대 결과·완료 기준을 정하고 작업·요청·진행 상태를 관리하는 단위. 하위 작업 없이도 존재한다 | 정의 v2 머리말 |
| V-2 | 업무를 만드는 행위는 **셋** — 본인 업무 생성 · 업무 요청 · 업무 분배(배정). 담당자 유무로 구분하지 않는다 | §1.1~§1.4 |
| V-3 | 유입 경로(메일·슬랙·AI 채팅)와 세 행위의 구분은 **별개**다 | §1.4 |
| V-4 | **하위 작업도 Task 로 관리한다** | §2.1 |
| V-5 | 체크리스트는 완료 기준, 하위 Task 는 그 기준을 충족할 일. 둘을 구분한다 | §2.1 · §4.4 |
| V-6 | 화면은 중심 업무와 **직속 하위까지 두 단계**. 화면 범위로 **생성 깊이를 제한하지 않는다** | §2.2 |
| V-7 | 다른 사람이 수락한 업무는 그 사람의 **새 중심 업무**가 되어 직속 하위와 요청을 가질 수 있다 | §2.2 |
| V-8 | 직접 수행 작업은 중심 업무 **바로 아래**에 둔다. 같은 담당자가 직접 작업 아래에 직접 작업을 중첩하지 않는다 | §2.2 |
| V-9 | **요청 발송 시 Task 를 `open` 으로 생성**하고 상위에 연결하며 수락 대기로 표시한다 | §2.4 |
| V-10 | **수락하면 같은 Task 와 상위 연결을 유지**하고 담당을 확정하며 **시작 전 상태를 유지**한다 | §2.4 |

## example.md §10 — 전체 사례의 10단계

**계약 검증 사례의 원장**이다. 생명주기 v2 §8 표(9단계)와 같은 흐름이고 여기가 한 단계 더 잘게 나눈다.
**이 표는 업무 관계의 예시이고 실제 DB 조회 결과가 아니다(E-8).**

| 단계 | 사건 | 유지할 관계·기록 | example 이 미정으로 둔 것 |
|---|---|---|---|
| 1 | 보고서 등록 | Task R — 내가 수행할 중심 업무 | 본인 업무의 담당 확정 처리 (EU-1) |
| 2 | 디자인 요청 발송 | 요청 Q + Task D, `Q → D`, `D → R`. 수락 대기 | 담당 기록의 생성 시점과 상태 |
| 3-A | 디자이너 수락 | 같은 Q·D. 담당 확정, **시작 전 `open` 유지**, 상위 연결 유지 | 수락 기록의 상세 저장 |
| 3-B | 디자이너 거절 | Q 거절 기록, **D `cancelled`**, 상위 관계·로그 유지 | 거절 사유의 필수 여부 |
| 3-C | 재요청 | **새 요청 Q2 + 새 Task D2**, `D2 → R`. 거절된 D 재사용 없음 | 재요청 이력의 연결 방식 · 취소 항목 삭제 방식 |
| 4 | 디자인 시작 | D 의 `open → in_progress`. **변경 시각이 시작 시각** | 시작 기록의 저장 방식 |
| 5 | 직접 작업 추가 | 조사 Task L · 시안 Task S 가 **각각 D 아래** — 디자이너의 직속 하위 | 하위 간 선후행 (EU-2) |
| 6 | 1차 완료 보고 | D 의 결과 제출 기록. **별도 검토 요청·Task 없이** 요청자가 확인 | 제출의 필수 입력·상태값 (EU-9) |
| 7 | 보완 | D 의 확인 결과로 보완 의견 기록. 디자이너가 **같은 업무를 수정** | 보완 시 상태·회차 (EU-10) |
| 8 | 2차 완료 보고 | **같은 D 의 다음 제출 회차.** 새 요청·Task 를 만들지 않음 | 회차·결과 버전의 저장 |
| 9 | 승인 | D 의 완료 확인 기록. **D 의 하위가 완료되어야 D 완료 가능.** 역승인 없음 | 확인 권한의 위임·대리 (EU-9) |
| 10 | 보고서 표시·완료 | `D → R` 관계로 상태·결과 확인. **미완료 하위가 있으면 R 완료 불가** | 그 밖의 완료 기준 · 제출부터 막을지 |

재요청 이후에는 표의 D 를 **새로 수락한 D2 로 읽는다**(§10.2 마지막 줄).
**완료 보고 회차의 저장 테이블이나 상태 전이를 이 표만으로 확정하지 않는다**(E-8).

## 불확실한 것 — 추측으로 메우지 않는다

| # | 무엇 | 왜 열려 있나 |
|---|---|---|
| U-1 | 실행 PostgreSQL 의 컬럼·FK·인덱스가 ORM 과 같은지 | DB 접속이 이번 금지 범위. **ORM = 실행 DB 를 전제하지 않는다** |
| U-2 | `assigned` 요청 출처 상태가 실제로 어느 행에 실리는지 | O-4. 요청 생명주기 모듈에서 찾지 못했다 |
| ~~U-3~~ | 「타인 생성의 parent 입력 거부」의 실제 위치 | **닫혔다 (2026-09-17 재확인)** — `creation_commands.py:157-173` 의 `_refuse_unsupported_horizontal_fields` 다(O-27). `parent_for()` 의 한 단계 제한과는 **다른 검사**다 |
| U-4 | 미커밋 W1 변경이 앞으로 어떻게 바뀔지 | 다른 세션이 계속 건드리고 있다. **착수 시 `git status` 와 표면 검색을 다시 돌린다** |
| U-5 | 자료 본문·다운로드·검색·미리보기 경로의 권한 판정 자리 전수 | 이번 읽기는 `modules/work/application.py` 중심이었다. `material_*` 계열 전수는 세지 않았다 |
| U-6 | **실행 DB 에 「승인 판단 행 없이 `done` 인 요청 하위」가 실제로 있는지** | O-33 은 **코드 경로**의 사실이다. 그것만으로 **DB 0건을 단정하지 않는다** — `source_work_request_id` 가 없던 시절의 유산 행·직접 SQL·과거 마이그레이션이 남았을 수 있다. **읽기 전용 SELECT 한 번으로 세어진다**(착수 전 점검, `30-work/`). **0건이 아니면 그때 사용자에게 올린다** |
| U-7 | **시안이 요구하는 화면 데이터 중 계약이 없는 것**(별표 `starred` · 수신함 카드의 아바타·수신 시각·출처·미읽음 수 · 근무 시간 · 캘린더의 회의 일정) | 분석 3종(입력 5)이 「대응 필드가 없다」로 적었고 이번에 코드에서 **반증을 찾지 못했다**. **무엇을 새로 만들지는 제품 결정**이고 SPEC-003 §2 가 그 경계를 적는다 |

**U-5 는 착수 전에 반드시 닫는다.** 계약이 닿는 표면을 목록으로 받으면 목록 밖에서 실패한다 —
BASE-001 § 계약이 닿는 표면과 같은 검색을 다시 돌려야 한다.

## Possible Direction

아직 결정이 아니다. DEC-002 가 고른다.

1. **W1 의 유효 보장을 남기고 응답 단계만 되돌린다** — 멱등 키 · 활성 담당 유일성 · 권한 재검사 ·
   AX 사람 확인 · 실제 actor 기록을 그대로 두고, 요청 경로의 담당 확정 시점만 수락으로 옮긴다.
2. **수락 대기를 수행 상태값으로 만들지 않는다** — SPEC-001 이 세운 「기다림은 상태가 아니라 표시」
   원칙을 유지하면 `open` 하나로 V-9·V-10 을 동시에 만족한다.
3. **하위의 「완결」 판정을 상태 하나에서 상태+승인 둘로 넓힌다** — O-19·O-20 이 v2 와 어긋나는
   실제 지점이다.
4. **제안–동의 한 쌍을 공통 모양으로 둔다** — 담당 변경 · 수락 후 취소 · 수락 후 조건 변경이
   전부 「제안하고 상대가 응답할 때까지 기존 상태 유지」다(V-18·V-19·V-20).
