# 알림 — 사용자가 바란 것, 지금 코드에 있는 알림 한 곳과 실시간 길, 확정 시안 둘

사용자가 strong-hajin 에 **알림**을 만들자고 했다(2026-10-07). BE·FE 조사 → 시안 둘(알림 목록 · 설정 알림) → 사용자 결정까지 끝났다.
이 문서는 **사용자가 바란 것 · 조사가 확인한 지금 코드의 동작 · 확정 시안이 그린 것**을 눕힌다.

**판단하지 않는다.** 무엇을 채택하고 무엇을 범위에서 빼는지, 사건마다 누구에게 알리는지는 DEC-010 이 가른다.
재개 노트 §2 의 결정 문장은 DEC-010 으로 옮기고, 여기에는 그 결정이 기대는 **요구와 관찰**만 둔다.

## 2. 지금 있는 알림 — 한 곳, 화면은 쓰지 않는다

### 2.1 서버 (BE §1)

- 표 `notifications` 하나. 마이그레이션 파일 없이 ORM `create_all` 로 선다 (BE A-1)
- 칸 = 수신자 · 원천 종류·id · 종류(`kind`) · 자원(종류·id·버전·제목) · 행위자 · 요약(300자) · 만든 시각 · 읽은 시각.
  (수신자, 원천) 이 유일하다 — 같은 원천이면 다시 만들지 않는다 (BE A-1)
- **만드는 자리는 단 1곳**(WT:2116) — 업무 요청 감사 훅 안 (BE A-2)

  | 사건 | 종류 | 받는 사람 |
  |---|---|---|
  | 업무 요청 발송 | `work_request.received` | 받는 사람(담당) |
  | 업무 요청 수락 | `work_request.accepted` | 요청자 |

  CC · 결재자 · 회의 승격자는 받지 않는다. 요청 감사 사건 11종 가운데 2종만 알림이 된다
- 읽을 때 행마다 **원래 자원을 다시 인가**한다 — 회의·업무 요청이 아니면 목록에서 조용히 빠진다 (BE A-1).
  회의 갈래는 응답 모양이 어긋나지만 meeting 행을 쓰는 자리가 없어 닿지 않는다(관찰 1)
- 읽기 API = 목록(배열 전체 · 페이지·안읽음 수·전체 읽음 없음) + 단건 읽음 (BE A-3)
- **「알림의 자리」 표시 2곳** — 의도적으로 부르지 않는다: 상위·프로젝트 이동(APP:741) · 선행 해제(APP:1581). 「부르지 않는다」 를 시험이 지킨다 (BE A-2)
- 코드 레포 문서의 경계: 「완료 알림함/푸시 … 추가하지 않는다」 · 「알림은 추가하지 않는다」(`docs/unified-operations.md`) · 회의 공유는 알림을 내지 않는다(`tool_catalog.py:446`) (BE A-2)
- 코드 레포 `docs/domain-model.md` 는 알림을 「`activity_events` 위의 파생 projection, 대상자는 `resource_relationships` 에서 파생」 으로 **결정됨·아직 구현하지 않음**이라 적었다. 지금 구현(감사 훅에서 행을 직접 씀)은 그 모양이 아니다 (BE A-4)

### 2.2 화면 (FE §1)

- `getNotifications` · `markNotificationRead` 와 `Notification` 타입은 **정의만 있고 부르는 곳이 0** (FE A-1)
- 타입의 `kind` 는 `meeting.shared` 도 적는다 — 서버엔 그 종류를 만드는 자리가 없다 (FE A-1 · BE A-1)
- 앱 안의 짧은 알림은 전역 토스트 한 통뿐이다 (FE A-4)

### 2.3 업무 수신함 · 메시지함과의 관계 (BE A-4 · FE A-3)

| 표면 | 원천 | 읽음 |
|---|---|---|
| 업무 > 수신함(InboxRail) | 업무 요청 + CC 관계 | `work` = 수락·거절로 접힘 · `reference` = 읽음 표 |
| 알림 | `notifications` | `read_at` |
| 메시지함 | 외부 메시지 표 | 사용자별 읽음 상태 |
| 판단함 | ActionItem·DecisionItem | 별개 |

- **업무 요청 발송**은 수신함 `work` 카드와 알림 행에 **둘 다** 선다. 읽음은 따로 움직인다
- **CC 참고**는 수신함에만, **수락**은 알림에만 있다

**관련자를 정할 재료의 빈 곳 (BE §2)**

- **업무** — 관련자 필드는 다 있다: 요청자 · 담당 · 승격자 · 결재자 · CC · 배정자 · 제안자. 댓글은 **업무 요청 스레드에만** 있고 업무 단독 댓글은 없다. 댓글 독자에 결재자는 들지 않는다. **@멘션 파싱은 없다** (BE B-1)
- **메일** — 「To/CC 중 나」 칸이 없다. 열 때 raw 헤더에서 푼다. INBOX 라벨만 받는다 (BE B-2)
- **슬랙** — 「나를 멘션」 · 「내가 보낸 것」 칸이 없다. 판정 재료(raw 본문 · 내 슬랙 id)는 있다. 방 종류 = `channel|private|dm|group_dm` (BE B-3)
  - **관찰 3** — 이름 조회에 성공하면 `author` 가 표시 이름으로 덮여, 미읽음 수의 「내 줄 빼기」 가 이름 조회가 실패한 줄에서만 맞는다. 슬랙 id 는 raw 에 남는다. 실행으로 확인하지 않았다
  - **운영 확인 (코디 2026-10-08 · `prod-check-1.md`)** 슬랙 메시지 4,041건 전부(100%) `author` 가 이름으로 덮였다 — 「내 줄 빼기」 는 한 줄도 못 뺀다. 판정 재료는 `raw.user`. 카톡 114건의 raw 키는 일곱(`type · author · seq_in_log · at · attachments · logId · text`)뿐이고 「내가 보낸」 표지는 0건이다
  - **운영 확인 — 카톡 보낸 사람 분포 (코디 2026-10-08 · `prod-check-1.md`)** 카톡 연동 1개 · 메시지 116건 — `author` 가 사용자 본인 카톡 이름인 줄 14건(방 3) · 그 밖 99건(방 2) · `author` 없음 3건(시스템 줄). 수집기가 표지를 올려도 기존 행엔 표지가 없다
- **카톡** — 「내가 보낸 것」 칸이 없다. 수집기가 보낸 여분 키는 raw 에 남는다. 방 종류 = `direct|group` (BE B-4)
- **연동 끊김** (BE B-6)
  - 메일·슬랙은 상태 `disconnected` + 사유로 전이한다. 사유는 API 응답에 나가지 않는다
  - **카톡은 상태를 바꾸지 않는다** — 수집기 보고가 90초 없으면 꺼짐으로 본다. 방은 `paused`
  - 방 단위 `access_lost` 가 따로 있다
  - **기록되지 않는 실패** — 슬랙 앱 토큰 거절 · Gmail Pub/Sub 거절은 로그만 남는다
- **시각 기반** — **스케줄러가 없다.** 기한·시작일을 훑는 루프도 없다. 일일 보고는 사용자가 요청할 때만 잡을 넣는다 (BE B-7)

| 경로 | 방식 | 단위 | 원천 | 사건 |
|---|---|---|---|---|
| `/api/inbox/stream` | WebSocket | **회원별** | Postgres `LISTEN/NOTIFY` 채널 하나 | 메시지함·연동 **4종**(`inbox.message_arrived` · `inbox.reply_result` · `integration.changed` · `inbox.message_updated`) — 본문 없이 무엇이 바뀌었는지만 |
| `/api/meetings/{id}/stream` | WebSocket | 회의별 | API 프로세스 메모리 방 | 전사 · AI 배치 · 메모 · 안건 |

- **SSE 는 코드에 없다**(서버 `text/event-stream` 0 · 화면 `EventSource` 0)
- 회원별 채널은 사람별로 거른다 · `integration.changed` 는 1초 1회로 묶는다 · 큐 200칸, 넘치면 오래된 것을 버린다 · 하트비트 없음
- **알림·업무 사건은 이 채널에 실리지 않는다** — 업무 코드에 게시 호출 0. 채널 docstring 은 「2단계(AX 판단·알림)도 쓸 사용자 사건 채널」 이라 적었다
- 그 밖(AX 대화 · 일일 보고 · 알림)은 전부 폴링 또는 REST 다

### 4.2 게시 프로세스 (BE C-2)

- 게시는 같은 트랜잭션에서 `pg_notify` — 커밋될 때 전달된다. API 프로세스마다 듣는 스레드 하나
- **게시하는 프로세스는 API · external_worker 둘뿐.** conversation · material · **meeting** · report 워커는 게시하지 않는다 — 회의록 합성 완료·실패는 지금 어떤 스트림에도 닿지 않는다
- 회의 WS 는 프로세스 사이 길이 없다(메모리 방)

### 4.3 끊겼다 붙을 때 — 커서 없음 (BE C-3 · FE B-3)

- 두 WS 모두 **커서·last-event-id·since 가 없다.** NOTIFY 는 저장되지 않는 신호라 끊긴 사이 사건은 잃는다
- 화면은 재연결 때 API 로 다시 읽는다 — 메시지함은 목록 다시 읽기, 설정은 연동 다시 읽기
- 알림 목록 API 에도 `since`·커서가 없다
- 화면 재연결은 2s → 30s 상한 백오프. **닫힘 코드를 가르지 않아** 인증 실패여도 계속 다시 붙는다(회의 스트림은 4401 을 가른다)

### 4.4 화면이 연결을 여는 자리 (FE B-1)

- **전역 연결이 없다.** 메시지함 화면과 설정 화면이 **화면마다 따로** 연다. 화면을 옮기면 닫힌다
- 그래서 홈·업무·캘린더 등 다른 화면에 있을 때 열린 사용자 사건 연결은 **0개**다

## 이 문서가 답하지 않은 것

1. 알림을 어디까지 만드나 — 사건 묶음 · 받는 경로 · 시각 기반 사건
2. 사건마다 **어떤 관계의 사람에게 · 어느 설정 항목으로** 알리나, 관계가 둘 이상이면 무엇을 보이나
3. 실시간 채널을 어떻게 바꾸나 — 방식 · 범위 · 끊긴 사이 사건 · 게시 프로세스
4. 셸이 OS 알림을 어디까지 맡나 — SPEC-006 §2.5 의 칸 가운데 무엇을 여나
5. 사이드바 표시 · 설정 저장 · 끄면 목록에도 안 쌓이나 · 보관
6. 지금 있는 알림(1곳) · 업무 수신함 · 메시지함과 새 알림 목록의 관계
7. DEC-008 · DEC-005 · SPEC-006 의 어느 결정을 뒤집거나 채우나
8. 위 어긋남 ①~⑯ 각각의 처분

→ 전부 DEC-010 이 받는다.

## 조사 한계

- **이 문서는 코드를 직접 읽지 않았다.** 코드 관측은 BE·FE 리포트를 옮긴 것이다
- 리포트 둘은 **읽기만** 했다 — 테스트·서버·앱·브라우저·cargo 를 돌리지 않았다
- BE 관찰 1(회의 갈래 응답 모양) · 관찰 3(슬랙 내 줄 판정)은 실행으로 확인하지 않았다
- 지연 실행 잡(예약 시각) 칸이 있는지 — 스케줄러 없이 시각 기반 사건을 만들 재료가 있는지 — 는 보지 않았다(BE §9)
- 운영 DB·로그·프로세스 구성은 보지 않았다(BE §8)
- OS 알림 · 숨은 웹뷰 · 창 수명은 실측하지 않았다(§9)
