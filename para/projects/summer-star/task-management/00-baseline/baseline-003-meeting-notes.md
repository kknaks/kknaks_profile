# 회의록

실시간 받아쓰기·화자 분리(Soniox) 위에서 **사람과 AI가 각자 회의록을 쓰고, 종료 후 통합**하는 영역. 2026-09-03 사용자 논의로 생성·회의 중·종료 전 구간 확정.

> 아직 결정하지 않은 날것의 입력이다. 정리보다 보존이 우선이다.

## Raw

2026-09-03 사용자 논의에서 나온 그대로:

- 회의 중 흐름: 회의 시작 → 웹소켓 연결 → 사람은 안건/액션 직접 입력 · 음성은 백엔드로 전송 → 백엔드가 Soniox 웹소켓으로 중계 → 트랜스크립트·화자 분리 결과 수신 → 프론트 렌더 → 배치 요약 → 회의 종료 → 최종 요약(마지막 배치) → 음성 원본 서버 저장.
- 배치 요약: 회의 시작 시 컨텍스트 전달(웜스타트, 결과는 무시) → 대화 쌓임 → 백엔드가 사람 입력 + 트랜스크립트를 워커(open-kknaks)로 → codex 요약 → 백엔드 → 프론트. **매 배치마다 새 세션이 아니라 한 세션 유지.** 첫 시작 시 업무+프로젝트+미리 생성된 안건을 DB에서 찾아 전달해 콜드 스타트를 피한다.
- **"회의를 2명이서 참가하는 컨셉이지 — AI, 사람."** 사람이 모든 걸 다 칠 수 없고 AI가 모든 걸 정확히 요약할 수도 없으니, 둘 다 일하고 종합하는 게 최선. AI는 발화 구간 근거 타임스탬프도 찍어준다. **AI 제안은 필요 없다 — 회의 중 AI는 AI 탭만 채우면 된다.**
- AI 탭도 회의록과 같은 구조(안건 > 결정/논의/액션/업무). 사람이 적은 안건이 DB에 있으니 컨텍스트로 같이 전달되고, AI는 그걸 보고 채운다. 안건이 없거나 해당 안건이 아니라고 판단하면 새로 만든다.
- 최종: "회의 종료되면 스피너 돌면서 회의록 생성중입니다." **회의록 탭 = 통합 정리본(사람은 회의 끝나고 이것만 볼 거라고 확신해), AI 탭 = 로그성 기록(마지막 배치 결과).** 즉 AI 요약(마지막 배치) → 통합본(회의록 생성) 순.
- 반복 회의는 이번 버전 제외. 녹음은 v1은 내 마이크만.
- 알림은 Tauri로 주고 싶은데 "일단 기능 구현하고 알림 테이블 새로 만들고" — 회의록 v1 범위 밖.
- 실무 경고: "DB에 없는 목록을 줄 때가 있는데 이거 막아야 해. 없는 업무인데 업데이트하라고 주면 DB에 집어넣다 터지더라. 그리고 JSON 형식 준수 안 하면 결과 자체를 업데이트 못 해."
- **"우리가 설계한 거 이외에 터지는 에러는 터지게 둬야 해. fallback 하면 어디서 터지는지 내가 모르니까."**

## Context

디자인(`12-meeting-notes.md` + `회의록.dc.html` 보드 13종, P-33~P-46)이 화면·줄 구조·드로어 3종까지 정의돼 있다. STT 엔진은 Soniox로 조사 완료(`orchestration/work/docs-v1/soniox-study.md`) — 실시간 화자 분리 지원, 익명 라벨(화자 1/2)이 디자인의 「참석자 이름 표기 없음」 원칙과 일치. 유형·프로젝트는 인증·설정(DEC-001), 업무 생성·갱신은 내 업무(DEC-002)가 제공한다.

## Why It Matters

- **회의록이 업무의 두 번째 입구다.** 액션 줄 → 업무 생성, 업무 줄 → 업무 갱신. 회의에서 나온 일이 기록에서 끊기지 않고 업무로 이어진다.
- **사람·AI 2트랙이 이 영역의 설계 축이다.** 어느 한쪽만으로는 회의록이 완성되지 않는다는 판단에서 나왔고, 데이터 모델·화면·배치 파이프라인이 전부 여기서 갈린다.
- **실시간 STT가 제품에서 기술 난도가 가장 높은 지점**이다. 웹소켓 2단 중계·배치 세션 유지·화자 분리 정확도·실패 처리가 얽힌다.

## Possible Direction

확정 사항을 DEC-003 으로 내린다. 디자인 정정 4건(유형 enum·상태값·2트랙 데이터 모델·AI 탭 렌더 구조)과 미설계 화면은 OQ. spec 전에 WKWebView 마이크 스파이크가 필요하다.
