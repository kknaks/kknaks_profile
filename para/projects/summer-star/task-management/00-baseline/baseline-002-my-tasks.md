# 내 업무

업무의 생성·상세·상태 전이·리스트/칸반. 제품의 원자 도메인 — 다른 모든 영역이 업무를 참조한다. 2026-09-03 사용자 논의로 미결 전부(Q-04~12) 확정.

> 아직 결정하지 않은 날것의 입력이다. 정리보다 보존이 우선이다.

## Raw

2026-09-03 사용자 논의에서 나온 그대로:

- 계층: "내 계정 밑에 내 프로젝트 밑에 업무, 프로젝트 무관 업무" vs "기본 프로젝트를 만들어 전부 밑에 엮을까" 논의 → **업무당 프로젝트 0..1개(N:1), 무소속 허용(null), M:N 없음**. 「프로젝트 없음」은 표시 계층의 가상 그룹.
- "유형은 필수지. 업무인지 미팅인지는 필수야."
- 완료: "결과자료가 있거나 완료결과 내용을 작성하거나 둘 중 하나는 있어야 업무를 어떻게 끝냈는지 기록이 되지."
- 일정 없는 업무: 정렬 맨 아래 · D-day 미표시 · 월 소속은 생성일 기준 (제안 수락).
- 리스트 상태 셀 직접 변경 허용, 칸반 드래그 앤 드롭 지원. 완료 전이는 판정 — "사전에 완료자료 올릴 수 있으니까 완료 판정이 맞으면 드래그 앤 드롭, 없으면 토스트로 결과지나 결과 입력하라고 하자."
- "취소는 업무 취소고, 잘못 만든 거는 소프트 딜리트지."

## Context

디자인이 가장 두꺼운 영역이다 — md 01~08 + 업무 화면 정의서(보드 14종, P-18~P-31). 데이터 모델(02)·상태 전이(05)·뷰(07)·반응형(08)이 이미 정의돼 있고, 원본 미결(10-open-questions §2~4, Q-04~13)이 이 영역에 몰려 있었다. 유형·프로젝트는 인증·설정(BASE-001/DEC-001)이 제공한다.

## Why It Matters

- **원자 도메인.** 회의록의 task/action 줄, 캘린더 표시·생성, 메시지의 업무 등록, 홈 집계가 전부 업무를 참조한다 — 여기 정책이 서야 뒤가 선다.
- **1280 반응형이 유일하게 그려진 영역**(P-28~31) — 반응형 규약이 여기서 확정된다.
- 원본 미결 10건(Q-04~13) 중 9건이 이번 논의로 닫혔다. 남은 건 미설계 화면(Q-13)뿐.

## Possible Direction

확정 사항을 DEC-002(정책 8절)로 내린다. 완료 게이트가 디자인 전제(05-status §완료 4 "결과자료가 비어 있어도 완료를 막지 않는다")를 뒤집으므로 디자인 정정 대상. spec 은 Phase 2 게이트 뒤.
