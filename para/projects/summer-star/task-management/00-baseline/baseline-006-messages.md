# 메시지함

외부 채널(메일·카카오톡·슬랙)에서 들어온 메시지를 모아 업무 후보로 넘기는 화면. **v1 은 목록 화면까지만, 기능은 v2.**

> 아직 결정하지 않은 날것의 입력이다. 정리보다 보존이 우선이다.

## Raw

2026-09-03 사용자 확정 그대로:

> "메시지함은 목록만 만들고 v2로 갈 거야. v1도 지금 너무 비대해."

## Context

디자인(`15-messages.md` + `메시지함.dc.html` 화면 2종, P-71·P-72)은 필터(채널·처리 상태) + 목록 + 원문·업무 등록 패널까지 그려져 있고, dc.html 에는 md 문서에 없는 **AI 업무 추출 패널 · 답장 컴포저 · 연결된 기록**까지 있다(분석 Q-35).

그런데 이 영역은 **수신 경로가 통째로 v2에 걸려 있다.** 메시지가 들어오려면 연동 관리(메일·카카오톡·슬랙)가 살아 있어야 하는데, DEC-001 에서 연동 관리를 목 UI 로 확정했다. 즉 v1 에서는 **받을 메시지가 없다.**

## Why It Matters

- **v1 범위를 지키기 위한 결정이다.** 인증·설정, 내 업무, 회의록, 문서함, 캘린더까지 이미 크다. 수신이 안 되는 영역에 구현을 넣을 이유가 없다.
- **자리는 남겨 둔다.** 사이드바 메뉴와 목록 화면이 있어야 제품의 형태가 온전하고, v2 에서 연동이 열리면 그 위에 얹으면 된다.
- Q-35(dc.html 의 AI 추출·답장 컴포저가 v1 인가)는 **자동으로 닫힌다** — 전부 v2.

## Possible Direction

v1 은 사이드바 메뉴 + 목록 화면(빈 상태)만. 나머지는 「v2에서 제공됩니다」 안내. DEC-006 은 이 경계와 v2 로 넘긴 목록을 기록하는 것이 주 역할이다.

## 기능명세

| # | 기능 | 설명 | v1 범위 | 근거 |
|---|---|---|---|---|
| 1 | 목록 화면 | 좌측 필터 카드(채널·처리 상태) + 목록 + 우측 빈 상태 | **UI 만** — 데이터 없음(빈 상태) | P-71 · 확정 |
| 2 | 메시지 수신 | 메일·카카오톡·슬랙 연동으로 메시지 적재 | **v2** — 연동이 목(DEC-001) | 확정 |
| 3 | 메시지 상세·원문 | 선택 시 원문 표시 | **v2** | P-72 |
| 4 | 읽음 처리 | 열 때만 읽음 기록, 첫 진입 자동 선택 금지 | **v2** | 15-messages §읽음 처리 |
| 5 | 업무로 등록 | 메시지 → 업무 생성 | **v2** | 확정 |
| 6 | 일정으로 추가 | 메시지 → 캘린더 일정 | **v2** | 메시지함.dc.html |
| 7 | AI 업무 추출 · 답장 컴포저 · 연결된 기록 | dc.html 에만 있던 것 | **v2** | 확정 (Q-35 해소) |

## 인바운드 / 아웃바운드

| 방향 | 상대 | 무엇 | 비고 |
|---|---|---|---|
| In | 인증·설정 | 연동 관리(채널 연결 상태) | **v2** — 목 UI |
| Out | 내 업무 | 메시지 → 업무 등록 | **v2** |
| Out | 캘린더 | 메시지 → 일정 추가 | **v2** |
| Out | 홈 | 미확인 메시지 집계 | **v2** (홈 제외 중) |
