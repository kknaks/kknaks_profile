# 캘린더

업무와 회의를 **시간축으로 다시 보여주는 뷰**. 데이터를 새로 만들지 않고, 생성·상세는 기존 드로어를 재사용한다. 2026-09-03 사용자 논의로 드래그 규격·일정 테이블 분리·겹침 차단 확정.

> 아직 결정하지 않은 날것의 입력이다. 정리보다 보존이 우선이다.

## Raw

2026-09-03 사용자 논의에서 나온 그대로:

- 일정 이동은 드래그로 하되 뷰마다 다르다:
  - **월** — 일자별 이동 / 기간 좌우 드래그로 기간 변경 (시간 변경 불가)
  - **주** — 일자별 이동(같은 시간으로) / 종일 좌우 드래그(기간 변경) / 종일에서 시간대로 드롭 시 **해당 지점부터 1시간 기본 생성** / 시간 테이블 항목의 일자 이동 / 위아래 드래그로 시간 늘리고 줄이기
  - **일** — 드래그 앤 드롭(시간대 이동) / 위아래 드래그로 길이 조절
- "업무 테이블에 시간도 표시해줘야 하나, FK로 연결해서 시간은 별도 관리를 할까?" → **별도 일정 테이블로 분리.**
- "일정 생성되는데 기존 기간이랑 겹치면 겹치는 게 있다고 토스트도 필요할 듯" → 경고가 아니라 **차단**. "아니 막아야지!" 단 **시간 있는 일정끼리만.**
- 드래그 중 겹치는 자리는 애초에 못 놓게 한다 — "다시 종일에서 끌어서 같은 자리에 넣을 수 있어?" → 못 넣는다.
- **드래그 고스트는 목적지 크기로** — "7일 기간 태스크에서 드래그하는 순간 하루짜리 크기로 바뀌어야지. 7일 너비를 하루에 넣는다는 느낌이 되면 안 되잖아."
- 회의 상세 드로어는 "기능상 거기(회의록)에 두고 캘린더에서 사용한다."
- 유형은 동적 생성 — 4색 고정 폐기.

## Context

디자인(`13-calendar.md` + `캘린더.dc.html` 화면 9종, P-47~P-55)이 월·주·일 그리드 규격, 일정 표시 규칙 5종, 유형 필터, 생성·상세 흐름까지 정의돼 있다. 데이터는 내 업무(BASE-002)와 회의록(BASE-003)에서 오고, 유형·프로젝트는 인증·설정(BASE-001)에서 온다. **캘린더 전용 생성 폼은 만들지 않는다**는 것이 디자인의 원칙.

## Why It Matters

- **시간축이 있는 유일한 영역이다.** 업무·회의가 언제 몰려 있는지는 여기서만 보인다.
- **일정 테이블 분리가 이 영역이 만든 구조 결정이다** — 캘린더가 업무·회의를 한 번에 읽고, 겹침 검사를 한 곳에서 하고, v2 외부 캘린더가 붙을 자리가 여기서 생긴다.
- **재사용이 원칙**이라 신규 화면 수 대비 구현이 싸다. 드로어는 전부 남의 것을 쓰고, 새로 만드는 건 그리드 3종뿐이다.

## Possible Direction

확정 사항을 DEC-005 로 내린다. 디자인 정정 2건(유형 4색 고정 폐기, 업무 startDate/endDate → 일정 테이블 이관)과 미설계(드래그 규격 시각 표현)는 OQ.
