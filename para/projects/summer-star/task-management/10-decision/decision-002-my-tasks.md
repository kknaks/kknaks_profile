# 내 업무 정책

BASE-002 의 영역 정책. 원본 미결 Q-04~12 를 2026-09-03 사용자 논의로 전부 닫았다.

> 근거 표기: `P/C/S/F/Q-xx` = 분석 리포트(`orchestration/work/docs-v1/docs-v1-design-report.md`), 「확정」 = 2026-09-03 사용자 논의, 파일명 = `00-design/`.

## 1. 범위

- In: 생성·상세(드로어/페이지)·인라인 편집·상태 전이·완료 게이트·취소·리스트/칸반·할일/메모/참고자료/결과자료/로그·연관업무·소프트 딜리트·반응형 3규격
- Out: 메시지 → 업무 등록, 홈 집계(v2 — 각 영역이 닫힘), **업무 목록 검색**(v1 제외 — 문서함 검색이 v2 인 것과 같은 결. 업무가 쌓이면 v2 에서 검색과 함께 설계한다)

|---|---|

**2026-09-06 업무의 시간 지정 제거** (사용자 확정)

| 항목 | 결정 |
|---|---|
| 「시간 지정」 토글 | **없앤다** |
| `due_start_time` · `due_end_time` | **컬럼 제거.** ERD T-1-b CHECK 도 함께 제거 |
| `schedule` 파생 | 「시간 일정」 경우가 **사라진다** — **업무는 항상 종일/기간**이다 |

근거 — **시안 어디에도 업무에 시간을 받는 UI 가 없다.**
새 업무 드로어(`업무 화면 정의서.dc.html` 570~594)도, 캘린더 「개인 업무 생성」(`캘린더.dc.html` 585~999)도
제목·유형·프로젝트·**일정**·설명·할일뿐이다. **시간이 있는 것은 회의뿐**이고 회의 일시는 `meeting.start_at`·`end_at` 이 소유한다.
칸반 카드의 「08.27 09:30」·「08.28 17:00」도 전부 **미팅·회의 유형** 카드다.

UI 없이 컬럼만 남기면 죽은 컬럼이 된다 — 배경·목표와 같은 처리다.
**캘린더 시간 그리드에는 회의만 뜬다.**

**2026-09-06 배경 · 목표 → 설명 하나** (사용자 확정)

| 항목 | 결정 |
|---|---|
| `background`(배경) · `goal`(목표) | **제거한다** |
| **`description`(설명)** | **신설.** `TEXT NULL` · 4000자 이하 |
| `completion_result`(완료 결과) | **그대로 둔다** — 성격이 다르다. 완료 게이트가 이걸 본다(ERD T-5) |
| 기존 데이터 | **이관하지 않는다. 날린다**(사용자 확정 — 배포 전) |

근거 — 「이 태스크에 대한 **설명 하나**면 된다」. 「왜 하는가」와 「무엇이 되면 끝인가」를 **나눠 받을 필요가 없다.**
개인 도구라 남에게 설명할 상대가 없고, 두 칸을 다 채우게 하면 대부분 한쪽이 빈다.

**화면 파급** — 생성·상세 드로어의 배경/목표 2단 그리드가 **설명 한 칸**이 된다.

**2026-09-06 칸반 드래그는 「상태 변경 UI」다 — 순서를 저장하지 않는다** (사용자 확정)

| 항목 | 결정 |
|---|---|
| 드래그의 뜻 | **상태 변경**이다. 「어느 컬럼에 놓았나」가 전부다 |
| 컬럼 안 위치 | **약속하지 않는다.** 「이 카드 뒤에」를 지원하지 않는다 |
| 삽입 가이드선 | **두지 않는다** — 위치를 약속하지 않으므로 |
| `order_index` · `task_day_order` | **만들지 않는다** |
| 컬럼 안 정렬 | 정렬 드롭다운(기한순 등)을 그대로 따른다 |

> **근거 — 업무는 서로 순서 관계가 없다.** 각자 상태를 가질 뿐이고, 상태는 **독립적인 값**이다.
> 「A 다음에 B」라는 사실이 도메인에 존재하지 않으므로 저장할 것도 없다.
>
> 이 결정이 딸려오던 질문들을 **한꺼번에 없앤다** — 「새로 만든 업무는 어느 순서에?」 ·
> 「손으로 옮겼는데 기한순이 걸려 있으면 뭐가 이기나?」 · 「오늘 순서와 내일 순서가 같아야 하나?」.
> 전부 **순서를 저장하기로 했을 때만 생기는 질문**이었다.
>
> **화면이 보여줄 것은 「어느 컬럼에 놓이는가」뿐이다** — 드롭 대상 컬럼 하이라이트가 그 역할을 한다(SPEC-004 U-4).
> 필요해지면 나중에 얹을 수 있다. 지금 안 한다고 버리는 설계가 없다.

**2026-09-06 칸반 카드 하단 행** (사용자 확정 · 시안 285~310줄 + 상태별 규칙 신설)

시안 카드 하단은 **좌: 일정 / 우: 상태별 값** 한 줄이다(12px `#757575`, `justify-between`).
지금 코드에는 **하단 행이 아예 없다.**

| 자리 | 무엇 |
|---|---|
| **좌측** | 계획 기간 `MM.DD – MM.DD`. 한쪽만 있으면 그것만. 시간이 있으면 `MM.DD HH:mm`(시안 「08.27 09:30」) |
| **우측** | 아래 상태별 표 |

| 상태 | 우측 | 색 |
|---|---|---|
| **시작전 · 진행중** | **`D-n`** — 완료예정일(`due_date`)까지 카운트. 오늘 `D-0`, 지났으면 **`D+n`** | `D-0` `#7181F8` · `D+n` **`#E2685B`** · 그 외 `#757575` |
| **완료** | **계획 대비 차이** — `due_date` ↔ `completed_at`. 「정시」 / 「**N일 늦음**」 / 「**N일 빠름**」 | 정시 `#757575` · 늦음 **`#E2685B`** · 빠름 `#7181F8` |
| **취소** | 취소 사유(시안 「일정 연기」·「중복 업무」) | `#9EA2AE` |
| **`due_date` 없음** | **「미정」** — 어느 상태든 | `#9EA2AE` |

> **문구·색은 코디가 정했다**(2026-09-06). 시안에 「차이 표시」의 구체 문구가 없다.
> 「정시 / N일 늦음 / N일 빠름 / 미정」 네 가지이고, **늦음만 지연색**을 쓴다 —
> 완료한 일을 붉게 칠하는 것이 아니라 **계획을 넘긴 사실**을 표시하는 것이다.
> 시작전·진행중의 `D+n`(지연)과 같은 축이라 색을 맞춘다.

**2026-09-06 뷰 토글 활성색 — A-16 번복** (사용자 확정 · 시안 지목)

| 항목 | 결정 |
|---|---|
| **뷰 전환(리스트\|칸반) 활성** | **`#1E1E1E` 배경 + 흰 글씨 13/700 으로 되돌린다.** 시안 원본(`업무 화면 정의서.dc.html` 63~66줄 · 261~264줄)이 그렇다 |

~~A-16(「뷰 전환 선택을 `#F4F5FF`+`#4B52A8` 로」)~~ → **번복.**
A-16 의 근거는 「같은 화면의 유형 탭 밑줄도 Ink 라 [10] RULES 『검정은 위치, 화면당 하나』를 어긴다」였다.
**그러나 시안은 실제로 둘 다 Ink 를 쓴다** — 유형 탭은 **밑줄**(`border-bottom 2px #1E1E1E`), 뷰 토글은 **배경**(`background:#1E1E1E`).
표현 방식이 달라 서로 경쟁하지 않는다. **시안이 정본이고, 규칙 해석으로 시안을 고치지 않는다.**

> 이 건은 **코디가 규칙 문장을 근거로 시안을 뒤집은 자리**다. 필터 칩·「오늘」 버튼과 같은 종류다 —
> 시안에 없는 것을 더하거나, 시안에 있는 것을 규칙으로 지웠다. **이후 정정은 시안을 먼저 열고 판단한다.**

**2026-09-06 일정 필드 4개 확정 — A-4 번복** (사용자 확정)

> **정정 A-4(「`startDate`/`endDate` → `due_date` 하나」)를 번복한다.** 업무는 **계획 기간**을 갖는다.

| 필드 | 뜻 | 누가 채우나 |
|---|---|---|
| `start_date` | **계획 시작** (선택) | 사용자 |
| `due_date` | **계획 종료 = 기한** (선택) | 사용자 |
| `started_at` | **실적 시작** — `진행중` 전이 시각 | 시스템 |
| `completed_at` | **실적 종료** — `완료` 전이 시각 | 시스템 |

**「기한」을 계획 종료와 따로 두지 않는다.** 개인 워크스페이스라 요청자·담당자가 없고([10] RULES 「사람 표기 없음」)
**「내 계획 종료」와 「외부 약속 마감」이 갈릴 상대가 없다.** 필드를 늘리면 매번 채워야 하고 안 채우면 죽는다.
**지연 판정은 `due_date` 기준**이다.

**실적 2개는 상태 전이 로그(리비전 0003)에서 파생 가능하지만 컬럼으로 승격한다** — 「오늘 완료 처리하면 오늘 완료에
간다」 규칙이 조회·정렬에서 매번 쓰이므로 매번 로그를 되짚지 않는다.

> **v2 예약 — 메시지에서 온 「요청 기한」** (2026-09-06 판단, 지금 만들지 않는다)
>
> 메일·카톡 연동이 붙으면 「9/10까지 해주세요」가 들어온다. **그건 계획 종료의 초기값으로 채우고 사용자가 고칠 수 있게 한다.**
> 별도 필드를 지금 만들지 않는 이유 —
> ① **v1 에 받을 메시지가 없다**(DEC-006) → 내내 비어 있는 죽은 필드가 된다
> ② 요청 기한은 날짜 하나가 아니라 **출처가 있는 약속**이다(누가·어느 메시지에서). 날짜만 떼어 두면 맥락이 없어 v2 에서 어차피 다시 설계한다
> ③ 대부분은 초기값을 그대로 쓴다. 갈리는 빈도는 써 봐야 안다
>
> 갈리는 것이 실제 문제가 되면 그때 `requested_due_date` 를 **메시지 도메인과 함께** 추가한다. nullable 컬럼이라 나중 비용이 작다.

**2026-09-06 조회 단위 전환 — 월 → 일** (사용자 확정 · 이 영역의 기본 전제가 바뀐다)

> **「내 업무」는 오늘 업무다.** 들어가면 오늘 기준으로 뜬다. 월 단위가 아니다.

| 항목 | 결정 |
|---|---|
| **기본 진입 범위** | **오늘 하루**. 이전 「이번 달」을 대체한다 |
| 기간 스테퍼 | `‹` `›` 가 **하루씩** 이동(고른 범위 길이만큼 — 아래 날짜 범위 결정과 같은 규칙). 라벨은 「2026년 9월 6일」 |

**오늘 화면에 뜨는 것 — 4종** (범위를 넓히면 「오늘」 자리에 그 범위가 들어간다)

| # | 무엇 | 조건 |
|---|---|---|
| 1 | **기간이 오늘에 걸치는 업무** | `start_date ≤ 오늘 ≤ due_date`. 시작이 없으면 `due_date = 오늘`, 종료가 없으면 `start_date ≤ 오늘` |
| 2 | **기한 없는 업무** | `due_date IS NULL` 이고 **미완료** → 범위와 무관하게 **매일**. 안 뜨면 영영 안 보이고 **기한을 정할 계기가 생기지 않는다**(사용자 근거) |
| 3 | **지연 업무** | `due_date < 오늘` 이고 **미완료** → **매일**. 어제 기한이던 업무가 사라지면 **가장 봐야 할 것이 안 보인다** |
| 4 | **오늘 완료·취소한 업무** | `completed_at`(또는 취소 전이 시각)이 오늘 → **기한이 지났든 오늘이 아니든 오늘 완료 칸에 간다**(사용자 확정) |

~~기한 없는 업무는 생성일 기준 달에 속한다~~ (BASE-002 규칙 폐기 — 위 2번이 대체)
**완료·취소는 `due_date` 가 아니라 실적 시각으로 거른다.** 과거 완료분을 끌어오면 「오늘 화면」이 아니게 된다.

**파급** — 칸반 G-3(그 달 전체·상한 500)은 「고른 범위 전체」로 읽는다. 페이지 요약·`formatMonth` 계열이 전부 기간 범위를 받아야 한다.
**서버 변경이 필요하다** — 지금 `from`·`to` 는 기한 범위로만 거른다. 「기한 없음」·「지연」을 오늘에 얹으려면 조회 규칙이 달라진다. 백엔드 발주 대상.

**2026-09-06 SPEC 오적용 교정** (시안에 없는 UI 를 spec 이 만들어 낸 것 — 사용자 확정)

| 항목 | 결정 |
|---|---|
| **활성 필터 칩 「필터 n ✕」** | **두지 않는다.** 내 업무 시안에 없다(`업무 화면 정의서.dc.html` 「필터」 0건). 출처는 디자인 시스템 [11] CALENDAR 의 「Type Filter · 범례 겸 필터」이고, **유형 분포 카드가 별도 패널이라 화면 위에서 무엇이 걸렸는지 안 보이는 캘린더 사정**이다. 내 업무는 유형 탭이 바로 아래에서 선택 상태를 밑줄+굵기로 보여주므로 **같은 정보를 두 번 말하게 된다.** SPEC-004 U-12 에서 삭제 |
| **「오늘」 버튼** | **두지 않는다.** 시안 헤더에 없다. 필터 칩과 같은 종류(코디가 spec 에서 더한 것) |
| **헤더는 뷰와 무관하게 하나다** | **정본 = `업무 화면 정의서.dc.html` 리스트 헤더(24~88줄).** breadcrumb / 좌측 `내 업무 + ‹ 2026년 8월 ›`(붙어 있다) / 우측 `[리스트\|칸반] · 정렬·종료일 · 상태 전체 · + 새 업무` / 그 아래 유형 탭. **뷰 토글은 그 아래 본문만 바꾼다** — 헤더는 움직이지도 사라지지도 않는다 |
| ~~칸반 헤더 필터 = 프로젝트~~ | **번복**(위 2026-09-05 결정 대체). 정렬·상태 필터를 **리스트·칸반 공통**으로 둔다. 프로젝트 필터는 만들지 않는다 |

> **번복 근거** — 사용자가 시안 헤더 이미지를 정본으로 지목하며 「보여 주는 게 칸반이냐 리스트냐일 뿐,
> 필터·정렬·유형은 이 이미지 기준으로 통일하라」고 확정했다(2026-09-06).
>
> **알려진 결과** — 칸반은 컬럼 축이 상태라 상태 필터를 걸면 해당 컬럼 하나만 남는다.
> 기능상 문제는 없고, 사용자가 이 동작을 알고 통일을 선택했다.
>
> 이전 A-17 의 근거(「칸반에 유형 필터는 중복」)는 **유형 축에 대한 것**이었고 지금도 유효하다 —
> 칸반 헤더에 **유형 드롭다운을 두지 않는다**(유형은 탭이 갖는다). 바뀐 것은 「대신 프로젝트를 둔다」뿐이다.

> **이 두 건이 같은 원인에서 나왔다** — 코디가 시안을 열지 않고 다른 영역의 패턴을 옮겨 적었고,
> 정한 것은 구현으로 내려보내지 않았다. 이후 spec 은 **시안에 그 UI 가 실제로 있는지 먼저 확인**한다.
