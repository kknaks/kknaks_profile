## 1. 무엇을 했나

회의록 영역이 「AI 가 사람 노트를 읽고 미러 안건을 만들고, 종료 시 통합 단계로 합치는」 옛 설계 위에 있었고, 실물로 돌리면 실패 경로가 많고 AI 요약의 톤이 사람 노트를 따라갔다. 사용자가 앱을 직접 돌리며 적은 `Meeting flow.md`(결정 71건)를 정본으로 삼아 DEC-003 → SPEC-006/007/008 → WORK-009~015 → 아키텍처를 다시 세우고, WP 7개를 하나씩 발주·검증·검수·커밋했다(밤샘 6개 + 아침 1개). 아침에 실물 회의 8건으로 배치·최종 회의록이 실제로 나오는 것을 확인했고, 그 과정에서 스키마 400 · 팝오버 스크롤 · 라벨 정렬 · MF-71(중간 배치는 AI 혼자)을 추가로 닫았다. 두 레포 PR 을 머지하고 마감했다.

## 2. 적용한 기술·개념

- **OpenAI 구조화 출력(strict JSON schema)의 규격** [[strict-json-schema-output]] — codex `output_schema` 로 회의록 한 벌을 받는 데 썼다.
  - 왜 이걸 골랐나: 모델 출력을 서버가 재검증하는 대신 스키마로 먼저 강제해 폐기율을 낮추려고. 단 strict 는 모든 object 에 `additionalProperties:false` + 전 키 `required` 를 요구한다.
  - 무엇이 어려웠나: `payload` 자리를 `{"type":["object","null"]}` 로만 두자 400 `invalid_json_schema` 로 codex 가 exit 1 · 빈 출력. 밤새 대역(fake) 게이트웨이만 돌아 테스트·검수가 못 잡았고, 아침 실물 회의에서 16회 연속 실패로 드러났다. 워커 컨테이너의 codex 세션 파일(`task_complete.error`)에서 원인을 읽었다.
  - 근거: `app/back/ai_schemas/meeting_notes.json` · `e2e-01-real-summit-evidence.md` · 커밋 `dd9d861`
- **MCP 도구 + 회의별 단명 토큰(auth_session 행 · 원문 컬럼)** [[resource-scoped-token]] — AI 가 우리 데이터를 읽는 유일한 길.
  - 왜 이걸 골랐나: 프롬프트에 스냅샷을 실으면 낡는다(MF-50). 토큰은 refresh 처럼 해시가 아니라 원문을 두었다 — 매 제출이 원문을 헤더에 실어야 하고, 단명·회의 범위·폐기=행 삭제라 노출 위험이 다르다(MF-69). 회의 토큰으로 열리는 표면은 allowlist 여섯뿐.
  - 무엇이 어려웠나: `/finalize` 재시도가 ② 종결 폐기와 부딪혀 토큰 없이 죽었다(워커 실측) — 같은 발급 함수로 재발급하되 회의당 하나 유지로 풀었다. 검수 FAIL 1 = 회의 토큰으로 목록 API 가 열리던 것.
  - 근거: `app/back/api/deps.py` `_MEETING_TOKEN_SURFACES` · `work009-review-report.md` · A-13
- **단계별 도구 잠금(enabled_tools)으로 「AI 가 무엇을 보나」를 설정으로 고정** [[tool-allowlist-by-phase]] — MF-71.
  - 왜 이걸 골랐나: 프롬프트로 「사람 안건을 보지 마라」고 해도 모델이 어길 수 있다. `-c` 가 resume 에도 살아 매 제출마다 도구 셋/일곱이 다시 걸린다.
  - 무엇이 어려웠나: 실물 회의 9 에서 AI 요약이 사람 노트의 키워드 톤을 그대로 따라갔다 — 원인은 미러 안건 설계였고, 「두 사람이 각자 쓰고 최종에 합친다」는 처음 개념으로 되돌렸다. 회의 12 에서 AI 안건이 독립적으로 갈리는 것을 확인.
  - 근거: `app/back/integrations/agent.py` `_TOOLS_BY_PHASE` · SPEC-007 v0.0.3 §4 도구 표 · 커밋 `1ca243e`
