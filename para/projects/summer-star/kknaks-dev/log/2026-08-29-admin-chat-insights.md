## 1. 무엇을 했나

전날 라이브된 채용담당자 채팅의 대화 데이터를 owner 가 볼 창구가 없었다. 시안을 먼저
만들어 owner 확정을 받고(위젯 3종 + 목록/상세), SPEC-017 에 U-8 과 admin API 3종의

로컬 실데이터(전날 e2e 대화 12건)로 확인 후 머지·배포.

## 2. 적용한 기술·개념

- **JSONB 스칼라 `'null'` 함정** — 파이썬 `None` 을 JSONB 컬럼에 넣으면 SQL NULL 이 아니라 JSONB `'null'`(스칼라)로 저장된다. 그 위에서 `jsonb_array_elements` 는 「cannot extract elements from a scalar」로 터지고, **LATERAL 이 WHERE 보다 먼저 평가돼 WHERE 필터로는 못 막는다**
  - 왜 실전 값인가: 재시도 경로(retry)가 `sources: None` 초기화를 실제로 남긴다 — 빈 픽스처로는 안 보이는 조합
  - 어떻게 풀었나: join 안 `jsonb_typeof='array'` CASE 가드. 테스트가 실패를 먼저 재현하고 잠갔다
  - 근거: `app/back/repository/chat_repo.py` · PR #25
- **소유권 축의 파일 분리** — 소유 세션을 검사하는 공개 서비스와 검사하지 않는 어드민 서비스를 한 클래스에 섞으면 「세션 None 이면 전부 보임」류 우회 인자가 공개 API 로 새는 축이 생긴다 → `admin_service.py` 별도 파일
  - 근거: `app/back/service/chat/admin_service.py` 머리 주석
- **목록 정렬의 페이지 안정성** — 활동순(lastMessageAt DESC)은 새 메시지가 올 때마다 페이지 경계가 흔들린다 → 생성순 + id 역순(결정적). 시안은 두 해석이 같은 순서라 판별 불가였고 워커가 판단 근거를 남겨 보고했다
- **집계는 요청 시 계산** — 대화 수십 건 규모에 사전 집계 테이블은 관리 축만 는다. daily 30일 빈 날 0 채움은 SQL 이 아니라 파이썬에서(단순함 우선)
- **읽기 전용 재사용** — 어드민 상세는 방문자 스레드 렌더 3컴포넌트를 그대로 쓰되 폴링·컴포저·재시도를 안 붙였다. `onRetry` 를 optional 로 바꾸는 한 줄이 재사용의 전부 — 복사 없이 회귀 0
