# 작업 요약 — consult-layer1 (consult-analysis)

기간: `2026-11-16` ~ `2026-11-17`
결과: 1층 적재 · 2층 판정 · LLM 라벨 · 집계 · 보고서까지 끝냄(PR #144) · 차트는 비공개 Artifact · 2층 reviewer 검수는 사용자 정리 지시로 생략

## 1. 무엇을 했나

피부과 클리닉 상담 DM(Meta 「내 정보 다운로드」 · 인스타그램 511방 + 페이스북 메신저 1,405방)을 보고 「예약까지 가는 대화는 어떤 대화인가 · 언어마다 무엇이 다른가」를 숫자로 내야 했다.
원본 JSON 을 판단 없이 SQLite 5개 테이블로 펼치는 1층(대조 274/274)과, 그 위에 언어 · 예약 단계 · 국적 · 문의 주제를 붙이는 2층을 나눴다. 2층은 규칙으로 먼저 판정하고(언어 · 단계), 규칙이 못 하는 주제 · 시술만 로컬 `claude -p`(haiku)로 1,883방에 라벨을 붙였다.
결과는 건수 · 비율만 `stats-001.json` 과 보고서로 냈다. 성공(고객이 채운 예약표 회신)은 93방 · 4.9%, 예약표 발송 뒤 회신은 39.2%(IG 62.5% · FB 30.6%)다. 성공 93방 가운데 91방이 번체 중국어 방이다. 영어 · 한국어 방은 성공이 0이고, 첫 응답 중앙값이 278분 · 403분으로 늦다.
레포가 PUBLIC 이라 원본 · DB · 확인용 CSV 는 gitignore 로 두고, 문서 · 스크립트 · 보고서에는 건수와 구조만 담았다.

## 2. 적용한 기술·개념

- **판단 없는 1층 · 판정은 2층 — 판정마다 주체 · 근거 · 버전** [[medallion-architecture]] [[data-lineage]]
  - 왜 이걸 골랐나: 「예약 성공」 정의와 LLM 프롬프트가 몇 번 바뀔 걸 처음부터 알았다. 1층에 언어 · 단계를 넣으면 정의가 바뀔 때마다 적재를 다시 해야 한다. 1층은 원본 키 43개를 전부 처분하고(모르는 키는 G-1 로 멈춤) 행마다 `source_file` + 순번을 둔다. 2층 행에는 `judge` · `version` · `evidence_message_id` 를 둔다
  - 무엇이 어려웠나: 코디가 원본을 처음 잴 때 페이스북 메신저 1,405방 · 21,612건을 「대화 없음」으로 빠뜨렸다. 범위를 두 채널로 넓히면서 방 키를 (`channel`, `thread_path`)로 바꾸고, 우리 계정은 「그 채널 모든 방에 공통인 이름」 규칙으로 구했다
  - 근거: SPEC-001 0.2.1 §3 · §4.3 · §5.4 · `scripts/load_layer1.py` · `verify_layer1.py`(적재 코드를 import 하지 않고 원본을 다시 센다) · BASE-001 정정

- **Meta 내보내기의 이중 인코딩 — `encode('latin1').decode('utf8')`** [[character-encoding]]
  - 왜 이걸 골랐나: 내보낸 JSON 이 UTF-8 바이트 하나하나를 `\u00XX` 문자로 적어 한자 · 이모지가 깨진다. latin1 로 바이트를 되찾아 UTF-8 로 다시 읽으면 원래 글자가 나온다
  - 무엇이 어려웠나: 이미 정상인 글자에 같은 변환을 하면 오류가 난다. 그래서 읽기 실패를 조용히 넘기지 않고 G-13(원본 읽기 실패에서 멈춤)으로 막았다
  - 근거: `scripts/load_layer1.py:92` · SPEC-001 §5.1 · reviewer W-2

- **번체 · 간체 판정은 OpenCC 로 글자를 센다 · 가를 글자가 없으면 `zh`** [[chinese-script-conversion]]
  - 왜 이걸 골랐나: 대만 · 홍콩 손님이 대부분이라 번체 · 간체 구분이 곧 손님 구성이다. 짧은 메시지는 번간이 같은 글자뿐이라 억지로 번체에 넣지 않고 `zh`(미상, 38방)로 남겼다(D-17)
  - 근거: `scripts/judge_layer2.py:166` · DEC-002 D-17 · `requirements-layer2.txt`

- **LLM 입력에 결과 라벨을 정하는 메시지가 섞이면 특징이 부풀어 오른다** [[target-leakage]]
  - 왜 이걸 골랐나: 성공 = 예약표 회신인데, 그 예약표에는 통역 · 날짜 · 연락처 칸이 있다. 이 메시지를 LLM 에 그대로 넣었더니 성공 방마다 `interpreter` · `schedule` 주제가 붙었다. 「통역을 물은 방의 성공률」이 57.1% 로 나왔지만, 예약표 메시지를 뺀 `llm-0.3.0` 으로 다시 돌리니 33.8% 였다
  - 무엇이 어려웠나: 숫자만 보면 그럴듯해서 보고서에 들어갈 뻔했다. 라벨마다 붙여 둔 근거 메시지 id 로 「성공 방 주제의 근거가 예약표 메시지인가」를 셌더니 통역 89 · 일정 93 · 위치 75 · 부작용 36 전부가 예약표 메시지였다. 같은 문제가 이모지에도 있었다. 예약표 양식 기호 ★ · 📝 가 이모지로 세여 성공 방 이모지 사용이 94.6% 로 나왔고, 빼니 50.5% 였다(SPEC 0.2.2)
  - 근거: SPEC-002 0.2.2 · 0.3.0 변경 이력 · DEC-002 D-23 · `scripts/label_layer2_llm.py:87` · `check_llm_form_evidence.py` · 재실행 $0.72 · 실패 0 · 오염 점검 0

- **분모를 늘 같이 내고 작은 분모는 표시 · 상관은 원인이 아니다** [[conversion-rate]]
  - 왜 이걸 골랐나: 언어 · 시술 칸이 작은 곳이 많다(일본어 3방). 모든 비율을 `{n, d, pct, small}` 로 내고 `d < 10` 이면 `small` 로 표시했다. 보고서의 수 611개는 전부 JSON 에 있는지 기계로 대조한다
  - 무엇이 어려웠나: 「통역 · 부작용을 물은 방이 성공률이 높다」는 방문을 이미 생각하는 손님이 그런 걸 묻는다는 뜻일 수 있다. 보고서와 차트에 「원인으로 읽지 말 것」을 함께 적었다
  - 근거: `scripts/stats_layer2.py:36` · `check_report_numbers.py` · 보고서 ②한계 · ⑥

- **사람 확인은 규칙이 못 정한 것만 · 50건 안쪽** [[human-in-the-loop]]
  - 왜 이걸 골랐나: 단계 판정은 규칙으로 먼저 하고, 예약표 칸 수가 애매한 15건만 큐로 올렸다. 코디가 판정안을 내고 사용자가 승인했다(3 · 4 · 7 → 회신 · 성공 93)
  - 근거: SPEC-002 §2.4 · DEC-002 D-19

- **공개 레포에는 집계만 · 고객 본문은 LLM API 로만 나간다** [[pii-masking]]
  - 왜 이걸 골랐나: 원본에는 여권 이름 · 생일 · 전화번호가 든 예약표 회신이 있다. 시험 자료는 지어낸 문장으로 쓰고, 워커마다 고객 이름 전체를 메모리에 올려 산출물과 대조해 일치 0 을 확인했다. LLM 라벨링은 방 본문을 Anthropic API 로 보낸다는 점을 사용자에게 알리고 규칙만 쓰는 대안도 냈다. 사용자는 haiku 로 진행하라고 했다
  - 근거: DEC-001 · WORK-002 수용 기준 3 · `.gitignore`

## 3. 막혔던 것 / 사고

- **원본을 덜 쟀다** — 코디가 BASE-001 에서 페이스북 메신저를 「대화 없음」으로 적었다. planner 가 SPEC 0.1.0 을 쓰는 동안 드러났고, BASE 를 고친 뒤 SPEC 0.2.0 에서 범위를 두 채널로 넓혔다. 내보내기 폴더는 하위 폴더까지 전부 센 뒤에 범위를 정한다
- **예약표가 특징으로 새어 들어갔다(이모지 → 주제, 두 번)** — 첫 차트를 낸 뒤에 이모지에서 먼저 발견했고, 같은 꼴을 주제에서 다시 찾았다. LLM 라벨 전체를 다시 돌렸다($0.72 · 30분). 처음 라벨링할 때 「결과를 정하는 메시지는 입력에서 뺀다」를 넣었어야 했다
- **남은 작은 오염** — 성공 방의 고객 메시지 수 · 턴 수에는 예약표 회신이 들어 있다(24 → 22 · 28 → 27). 방 언어도 약 5방이 바뀔 수 있다. 보고서 한계에 적었다
- **차트 화면 확인 못 함** — Artifact 페이지 검사 결과가 끝내 오지 않았다. 사용자가 직접 확인해야 한다
