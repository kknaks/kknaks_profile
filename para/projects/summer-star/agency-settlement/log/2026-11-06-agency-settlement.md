# 작업 요약 — agency-settlement (agency-settlement)

기간: `2026-10-29` ~ `2026-11-06`
결과: 로컬 PoC 완성 · 머지(문서 kknaks/kknaks_profile#114 · 코드 kknaksss/agency-settlement#1) · 운영 데이터 = 로컬 PG · 서버 배포 · 스케줄 켜기는 다음

## 1. 무엇을 했나

병원(운영 명동점)이 에이전시 · 유입 채널별로 수수료를 정산하려는데, 「누가 데려온 손님이 최종적으로 무엇을 얼마 냈나」를 볼 화면이 없었다.
운영 KOS 를 조회만 해서 결제 · 품목 · 수납 요약 · 일정을 이어 붙이고, 손님마다 **최종 결제 품목과 실결제**만 보이는 월별 리스트 → 유입 채널 결산 표 → 상품 단위 수수료율(달별 스냅샷) → PDF 거래 명세서(zip) 까지 만들었다.
처음 cc-prototype 의 기능 폴더로 시작했다가 별도 프로젝트로 옮겼고, 저장은 메모리 → SQLite → PostgreSQL 로, 화면은 시안 v1 → v3 로 바뀌었다. 끝에 운영 기준을 11월부터로 두고 매일 21시 스케줄 · 상품 일별 스냅샷 · 수동 연결 구조로 착지했다.

## 2. 적용한 기술·개념

- **KOS 품목에 없는 상품 id 를 같은 수납 안에서 짝지어 얻기** [[entity-resolution]] — 결제 품목 통계엔 상품 id 가 없다
  - 왜 이걸 골랐나: 처음엔 이름 키로 갔다(planner OQ-138). 사용자 「상품 id 로 매핑하는 게 아니야?」 → 같은 수납의 수납 요약(⑤) `items[].optionConfiguration.id` 와 옵션 이름으로 짝지으면 수집본 671/671 하나로 정해짐 → 옵션 id → 상품 목록(⑦) `options[].id` → 상품 id
  - 무엇이 어려웠나: 9월 품목 1,002 줄이 이어지지 않았다. 처음엔 「이름이 지금 목록과 같다」고 잘못 보고 백엔드에 고침을 두 번 냈다 — PG 를 직접 조회해 보니 **그 상품 자체가 KOS 에서 삭제**(공개 API 는 삭제된 상품을 안 줌 · 옵션 상세에 상품 id 칸 없음). 해법은 과거가 아니라 앞으로 — 상품 목록을 **매일 스냅샷으로 쌓고 지우지 않기**(D-25) · 남은 것은 사람이 연결(D-27)
  - 근거: `be4-add-product-id.md` · `be4-fix-1-instructions.md` · DEC-001 D-20 · D-25 · D-27 · 코드 `8089f72` · `788f73f`

- **증분 수집에서 시각으로 자르지 않기 — 「목록은 다시, 비싼 조회만 새 것」** [[idempotency]] — 「마지막 이후만」을 문자 그대로 구현하면 돈이 빠진다
  - 왜 이걸 골랐나: KOS 결제 목록엔 만든 시각이 없어(마지막 상태 변경 시각뿐) 같은 수단 · 같은 금액 새 결제가 「이미 받은 것」으로 버려졌다(doc r3 F-2). 그래서 결제 목록(① — 한 달 한 페이지)은 매번 달 전체를 받고, 묶음 키(수납 · 상태 · 수단 · 금액 · 통화) 수 비교로 새 행만 골라 품목 · 수납 · 이름 조회만 새 것에 한다
  - 무엇이 어려웠나: 결과는 사용자 말(「확정 달은 다시 부르지 마 · 이번 달은 마지막 이후만」)과 같지만 구현 해석이 달라 사용자에게 통보가 필요했다
  - 근거: SPEC-001 §4.5 · OQ-123 · `review-doc-r3-report.md` F-2 · LIVE: 확정 달 KOS 0 · 이번 달 증분 1 ~ 2 호출

- **「달을 모두 더하면 KOS 최종 금액」을 불변식으로 두기** [[as-of-visibility]] — 결제가 달을 넘는 꼴(앞 달 결제의 이 달 취소 · 확정 달 품목의 재결제 · 부분 취소 뒤 재승인)
  - 왜 이걸 골랐나: 화면 · 에이전시 합 · 엑셀/PDF 가 같은 숫자여도 그 숫자가 최종 금액과 다를 수 있었다(doc r6 F-1 · code r3 F-1). 판정을 함수 하나(`settle()`)에 두고, 품목 달을 받은 시각보다 늦은 취소만 음수로 더하는 「반영 판정」을 넣었다
  - 무엇이 어려웠나: 시험은 같은 숫자끼리 비교해서 초록이었다 — 리뷰어가 가짜 KOS 로 「9월 500,000 → 10월 취소 · 300,000 재승인」을 재현해서야 드러남. 시험에 「두 달 합 = KOS 최종」을 넣었다
  - 근거: SPEC §6.9 · `review-doc-r6-report.md` · `review-code-r3-report.md` · 시험 #61 ~ #66

- **화면은 「최종 결제」만 — 결제 흐름 줄을 그리지 않기** [[no-inference-from-free-text]] — 사용자 「최종 얼마를 병원에 냈는지가 중요 · 취소된 건 필요 없잖아」
  - 왜 이걸 골랐나: 승인 · 취소를 줄로 그리던 2판은 「결제 → 취소 → 재결제」 수납에서 머리가 승인 합(두 배)으로 보이고 취소 줄만 보여 0원처럼 읽혔다. 머리 = 실결제 · 품목 = 최종 결제된 것만 · 취소 · 환불은 숫자로만(D-18)
  - 무엇이 어려웠나: 0원 품목을 「앞 품목의 구성품」으로 들여 그렸는데 KOS 엔 그 연결이 없었다(가짜 데이터로 그린 시안을 믿음). ⑤ `priceAdjustments` 로 보니 0원 190 줄 = 할인 서비스 147 · 원래 0원 14 · 환불 30 · 묶음 구성은 별도 줄이 아니라 GROUP 옵션의 `compositions` 안
  - 근거: `feedback-2026-11-02-b.md` 1 · 3 · 5 · DEC-001 D-18

- **로컬 PostgreSQL 로 옮기기 — 옮긴 뒤 숫자 대조 · 한 번만 다시 받기** [[database-migration]] [[database-lock]]
  - 왜 이걸 골랐나: 사용자가 서버 배포를 전제로 PG 를 정했다. SQLite → PG 한 번짜리 명령(읽기 전용 · 빈 PG 만 · 행 수/합 대조) → 앱으로 9 · 10 · 11월 같은 숫자 확인 → 상품 id 를 위해 세 달만 KOS 전체 다시 받기(사용자 허락)
  - 무엇이 어려웠나: 운영 PG 컨테이너가 워크트리 안 init 스크립트를 마운트해서 마감 스크립트가 막혔다 → 볼륨은 두고 컨테이너만 main 체크아웃 기준으로 다시 띄움. advisory lock + 연결 풀은 같은 달 요청이 몰리면 1분 멈춤 → 짧은 기다림 + 바로 503
  - 근거: SPEC §4.4 · `review-code-r4-report.md` W-3 · 코드 `8089f72`

## 3. 막혔던 것 / 사고

- **프로젝트를 잘못 놓음** — 「cc-prototype 처럼」을 「cc-prototype 안에」로 들었다 → 사용자 「다른 프로젝트인데 cc 같은 거랬지」 → 문서 · config · roles 를 새 프로젝트로 옮기고 번호를 다시 매김(DEC-009 → DEC-001). 기계 치환으로 한글이 깨진 줄이 하나 생겨 planner 가 찾음
- **결정 줄이 _RESUME 에 안 들어감** — 넣을 자리를 찾는 앵커 문구가 앞서 바뀌어 6줄이 조용히 빠졌고, planner 질문으로 알았다 → 앵커 대신 「§2 표 마지막 줄 뒤」로 넣음
- **워커 핸들이 세 번 바뀜** — 보낸 지시가 사라졌는데 전송 결과를 안 봐서 몰랐다 → 보낼 때마다 `"ok"` 확인 · 워커 화면 확인
- **사용자 브라우저가 옛 front JS** — dev 서버 청크가 캐시되어 「그달 결제 0 · NaN줄」이 두 번 보임 → 3800 을 production build 로(해시 청크)
- **「데이터로 구분할 방법 없다」고 단정** — 사용자 「왜 없다는 거야」 뒤 ⑤ 를 보니 구분됨. 단정 전에 원천을 먼저 본다
- **public 레포에 실제 값** — 작업 기록 · 지시서에 실제 금액 · 수납 id · 에이전시 이름이 몇 번 들어감(검수자가 두 번 찾음) → 기호로 가리고, 조사 리포트는 gitignore · main 로컬에만
- **9 · 10월은 연결 불가** — 삭제된 상품은 공개 API 로 상품 id 를 못 얻음 → 테스트 데이터로 두고 11월부터 운영(D-28)
