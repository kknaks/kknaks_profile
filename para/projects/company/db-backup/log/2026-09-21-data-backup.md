# 2026-09-21 — 사내 DB 백업 방식 선정과 인프라 조사

기간: 2026-09-20 ~ 2026-09-21
결과: 아키텍처 초안·인프라 조사 리포트를 main 에 머지 (PR #50). 실측 4건 미결

## 무엇을 했나

사내 8개 서비스(서비스당 약 120GB, 총 약 960GB)의 운영 DB를 맥스튜디오 백업 서버로
모으는 방식을 정했다. 시니어는 덤프를 제안했고, 전송 시간이 문제라는 판단에서 대안을 설계했다.

**베이스 백업 1회 + 바이너리 로그 상시 스트리밍**으로 착지했고, 수집 방식을 엔진 단위
단일(`pg_receivewal` / `mysqlbinlog`)로 확정했다. 배포 대상인 맥스튜디오 k8s 인프라는
조사 워커를 발주해 사실을 확보하고, 그 결과로 통신 구간·배치 제약을 문서에 반영했다.

## 배운 것

**축을 잘못 잡으면 설계가 갈라진다.** 「덤프 vs CDC」로 시작했지만 실제 축은
**베이스를 물리로 뜰 수 있는가**였다. WAL은 블록 단위 물리 로그라 논리 덤프 위에 못 얹고
(`pg_control` 불일치로 기동 거부), MySQL binlog는 ROW 이벤트라 `mysqldump` 베이스 위에
얹힌다. 이 비대칭이 엔진별 베이스 방식을 갈랐다. → [[write-ahead-logging]]

**수집 방법 선택이 아키텍처 분기를 만들었다.** 처음엔 `archive_command` 를 전제해서
「관리형 RDB는 셸을 못 써 → 논리 복제로 분기」라는 결론을 내고 호스팅 3형태별로 경로를
쪼갰다. `pg_receivewal` 은 파일시스템이 아니라 네트워크로 붙는 클라이언트라 관리형에서도
되고, 이걸 수집 방식으로 잡으니 환경 차이가 통째로 사라졌다. **제약이라고 믿은 것이 내가
고른 도구의 부작용이었다.**

**운영 인력 수가 설계를 정한다.** 논리 복제는 DDL이 전파되지 않아 서비스팀이 마이그레이션
할 때마다 백업 쪽이 따라가야 한다. 8개 서비스 × 1명 운영에서는 이게 가장 큰 비용이라,
5분짜리 사전 확인 하나를 피하려고 영구적인 운영 부담을 떠안는 거래는 성립하지 않았다.
→ [[replication-slot]]

**검증을 별도 작업으로 두지 않는 구조.** 백업은 조용히 썩고 복원 시도 시점은 이미 장애
상황이다. 재생 인스턴스가 매일 로그를 적용하며 살아 있으면 그 자체가 매일 도는 복원
검증이 된다. → [[point-in-time-recovery]]

**CDC와 WAL 아카이빙은 같은 로그를 읽지만 다른 기술이다.** CDC는 로그를 디코딩해
변경 이벤트 스트림을 만들고(이종 타겟 가능), WAL 아카이빙은 디코딩 없이 원본을 보관한다
(같은 엔진에서 재생). 제안할 때 「CDC」라고 부르면 Debezium+Kafka 운영 부담을 떠올리게
되므로, 같은 일을 하면서도 용어 선택이 통과 확률을 바꾼다. → [[change-data-capture]]

## 막혔던 것

- **스코프를 반복해서 넘었다.** 「§3.1까지 써라」에 §3.4·§4까지 썼고, 논의에 없던 목적을
  넣었고, 확정된 안을 다시 꺼냈다. §3 전체 삭제·문서 전면 재작성으로 교정됐다.
  같은 지적이 한 세션에 네 번 나왔다
- **실측 없이 낙관했다.** 크기를 모른 채 「덤프로 감당된다」고 말했다가 8×120GB를 듣고
  뒤집었다. 확인 항목을 먼저 닫았어야 했다
- **제약을 과장했다.** 「x86_64 베이스는 arm64에서 재생 불가」로 단정했으나, 양쪽 모두
  64bit 리틀엔디안·`MAXALIGN 8`·`BLCKSZ 8192` 라 `pg_control` 검사를 통과할 여지가 있다.
  확실한 제약은 메이저 버전 불일치뿐이다
- **스쿼시 머지 후 아카이브 검사가 막혔다.** 원본 커밋이 main 히스토리에 없어
  「미머지 의심」으로 중단 → 내용 동일성 확인 후 `git reset --hard origin/main` 으로 정렬
