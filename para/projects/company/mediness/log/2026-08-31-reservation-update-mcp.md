
# 작업 요약 — reservation-update-mcp (mediness)

기간: `2026-08-31` ~ `2026-08-31`
결과: spec PR #670 · code PR #139 머지, dev 배포 감시 중. main 릴리스는 #667·#138 에 편승

## 1. 무엇을 했나

prod 실사용 2건이 발단. ① MCP(에이전트)로 잡은 완료 예약을 «시간 변경» 요청하자 에이전트가 「승인난 회의는 변경이 안 된다」고 답했다 — back REST 는 있는데 MCP 손만 없었다(`reservation_revise` docstring 에 기록된 과거 사고의 재발). ② 15:08 「오늘 오후 3시」 예약이 말없이 다음날로 잡혔다 — 시각 해석 규칙의 무조건 미래 제약. SPEC-151 §6.2b 등재·§7.10 신설 → WP-128 → 코드 착지(`reservation_update_request` 툴 + `TIME_RESOLUTION_RULE` 재작성 + 되묻기 1턴)로 직렬 파이프라인.

## 2. 적용한 기술·개념

- **원장 실측으로 원인 확정** — 「왜 다음날로 잡혔나」를 코드 추정이 아니라 prod `triggers`(발화 원문)·`actions`(payload date)·`action_events`(승인 시각) 대조로 확정. 발화가 15:08, 요청 시각 15:00 — 8분 차이가 원인이었다
  - 왜: 첫 가설(본인 예약만 지목 가능)이 사용자 정정("둘 다 김태우")으로 무너짐 — 추정으로 두 번 틀리기 전에 원장으로
  - 근거: prod triggers/actions 쿼리 · actions `918e4411`
- **「REST 는 있고 MCP 손만 없다」 패턴 인식** — cancel 툴(`reservation_cancel_request`)은 있는데 update 만 없었다. 같은 레포의 revise docstring 이 동일 사고를 이미 기록하고 있었음 → 신설이 아니라 «빠진 형제 채우기» 로 스코프 축소
- **프롬프트 규칙의 «침묵 조정» 해부** — 규칙이 빈 게 아니라 **무조건 제약 + 처방 하나** 구조라, 커버 안 되는 케이스(명시 날짜+지난 시각)에서 모델이 유일한 처방(내일)을 전용한 것. 수정은 «문장 추가» 가 아니라 «제약 문장 삭제·재작성»('must start in the future' + 무한정 'from now' 둘 다) — 하나만 지우면 나머지가 같은 일을 계속한다
  - 근거: `provider.py:26-30` · SPEC-151 §7.10 · 검수 W-1/W-2
- **되묻기의 결정 자리와 출구 분리** — 되묻기를 감사 프롬프트에 얹으면 구조적으로 동작 안 함(워크플로 고른 턴은 감사에 미도달). `CatalogTurn.clarification` = 접수 해석 축에서 워크플로 선택 **전에** 갈리게 배선
- **«그 시점 실측이 정본» 카운트 규율의 실전** — 타 세션이 툴 1개 제거(61→60)한 뒤 우리 +1 이 겹쳐, rebase 충돌에서 62 가 아니라 **60+1=61** 로 재계산. 표 숫자를 옮겨 적지 않는 규율이 정확히 이 상황을 위해 있었다
