# 작업 요약 — task-slack-notify (mediness)

기간: `2026-09-02` ~ `2026-09-02`
결과: 스펙(SPEC-120)·코드(WP-132)·env 전부 머지, prod 배포·테스트 발송까지 완료. 크론 첫 실발송은 09-03 09:00.

## 1. 무엇을 했나

태스크 축의 슬랙 통로 두 개를 세웠다. ① 배정 DM 전면화 — 요청(수동·채팅)에만 가던 DM 을 「담당자 존재 ∧ 생성 행위자 ≠ 담당자」 전부(워크플로 배정 포함)로 넓히되, 판정을 태스크 생성 seam 한 곳으로 수렴시켰다. ② 매일 09:00 KST 데일리 리포트 — 전날 개인별 생성/진행/완료 + 열린 태스크 마감 유무를 #009--업무일지 채널 본문 1건 + 개인별 스레드 댓글로 발송(C레벨 제외·멘션 없음). 같은 날 실사용 발견분 셋을 함께 처리했다: 슬랙 미매핑 5명 백필, MCP 댓글 툴 카탈로그 enable, 채팅 «내 업무» 전체 754건 조회 문제.

## 2. 적용한 기술·개념

- **발송 판정의 생성 seam 수렴** — 입구 6곳(웹·채팅·WBS·의사결정·인시던트·워크플로 수동)이 전부 지나는 `create_task_with_cc` 한 곳에서 DM 여부를 판정
  - 왜 이걸 골랐나: 입구마다 훅을 걸면 입구가 늘 때마다 표가 늘고, 빠진 입구는 실기동 반려로만 드러난다(WP-129 의 교훈 — [[contract-surface-enumeration]])
  - 무엇이 어려웠나: P0 전수에서 **기존 알림 종⑤가 입구 ④⑥에서 이미 생성 DM 을 쏘고 있음**이 드러남 — 스펙 §2.2 가 「기존 발송 = 요청 DM 2곳」만 세서 이중 발송 충돌. 워커의 결정 게이트로 올라와 A안(종⑤ 생성 발화 2곳 제거·재배정 존치) 확정
  - 근거: mediness-app#145 · request_axis.should_notify_assignment · SPEC-120 §2.2 각주
- **행위자 판정 전용 인자** — 원장에 사람을 안 적는 입구([+태스크])가 「누가 눌렀나」를 `actor_member_id` 판정 인자로만 넘김
  - 왜: `created_by` 에 적으면 같은 사실이 두 자리(원장 이원화). 판정에만 쓰고 저장하지 않는다
  - 근거: factory.py docstring · #145
- **파생 view 의 구조적 멱등** — 리포트·DM 모두 발송 원장 없음(행 1건 = 발송 1회, 크론 중복은 수용)
  - 왜: dedup 저장소는 새 원장이고, 리포트는 파생이라 중복이 원장을 오염시키지 않는다
- **채널 ID 계약 + 빈값 no-op** — 채널은 이름이 아니라 ID 로, env 미설정 = job 건너뜀
  - 왜: 이름은 바뀌고 ID 는 불변. 빈값 no-op 이 dev→실채널 오발송을 구조적으로 차단
  - 근거: config.py slack_task_daily_report_channel_id · k8s_infra_mac#3(prod 만 설정)

## 3. 막혔던 것 / 사고

- **구지윤 요청 DM 미발송** → prod 조회로 `users.slack_id` NULL 확인 → 원인은 판정이 아니라 **6월 말 시드 이후 합류자 5명 미매핑**. 슬랙 `users.list` 로 5명 ID 확보(이메일 조회는 봇 scope 부재), NULL-only 멱등 UPDATE 백필 + 시드 정본 동기화
- **MCP 댓글 툴이 에이전트에 안 보임** → 서버엔 있는데(tools 62) `tools/list` 필터에서 소실 → **카탈로그 `enabled=false` 기본값**(관리자 큐레이션 게이트)을 켜는 걸 배포 때 빠뜨림. prod·dev·로컬 3곳 enable — 「MCP 툴 추가 = 카탈로그 enable 까지 한 세트」
- **«내 업무»에 조직 전체 754건(240만 자)** → 버그가 아니라 8-12 확정(「관리자는 채팅에서 전체 조회」)이 원인 — 자격 보유자 9명에게 실사용 부담으로 드러나 사용자가 뒤집음(내 것만)
