# 작업 요약 — sc-design-system (sc-ax)

기간: `2026-09-07` ~ `2026-09-08`
결과: 코드 PR(ax-workspace #2) · 문서 PR(kknaks_profile #41) 제출. 읽기 화면까지 완료, 소속·직책 변경 command 는 다음 작업으로 넘김.

## 1. 무엇을 했나

sc-ax 에 코드레포가 처음 붙었다. 프론트는 `:root` 토큰만 디자인 v2 와 같고 그 아래 규칙·컴포넌트·
레이아웃은 따로 놀았고(조사 갭 40건), 조직 화면은 트리+권한 폼 골격뿐이었다. 디자인 시스템을
1~3차로 맞추고, SC 실제 조직도 169행을 dataset 계약으로 로컬에 넣고, 확정 디자인(Claude Design
「SCAX」 조직 화면 템플릿)대로 3분할 화면을 세운 뒤, 화면이 요구하는 읽기 API 4개를 열었다.
변경 command(소속·직책)는 BE 에 아예 없어 화면에도 그리지 않고 다음 작업으로 남겼다.

## 2. 적용한 기술·개념

- **토큰 층과 규칙 층의 분리** ([[design-token]]) — `:root` 토큰 41개는 v2 와 일치했지만 그 아래
  규칙이 새고 있었다(금지 간격 57회·행간 오버라이드 9곳·정의 없는 변수 16곳)
  - 왜 이걸 골랐나: 토큰을 다시 만드는 대신 「토큰 아래 규칙만」 고치는 1차와, 프리미티브·레이아웃을
    올리는 2·3차로 나눴다. 한 번에 하면 검증이 섞인다
  - 무엇이 어려웠나: 조사 리포트의 「금지 간격」 판정이 v2 가 지정한 버튼 패딩 14·18 을 오탐했다 —
    워커가 디자인 원문으로 되짚어 4건을 바로잡았다. 리포트도 디자인 앞에서는 2차 자료다
  - 근거: `fe-survey-report.md` A 표 · 커밋 `7e6fc53`
- **소비처 없는 프리미티브는 만들지 않는다** — Radio·Toggle·Search·Status Dropdown·Popover(1차) 를
  자리가 없어 보류했고 Popover 는 툴바 필터 칩이라는 소비처가 생긴 2차-b 에서 만들었다
  - 왜 이걸 골랐나: v2 자체가 「안 쓰는 토큰은 오답 선택지」라 못박는다. 죽은 컴포넌트는 다음 사람이
    규격을 믿고 쓰다 어긋난다
  - 무엇이 어려웠나: 브리프가 「상태 변경 `<select>`」를 전제했는데 앱에 그런 select 가 없었다 —
    워커 질문으로 드러났고, 코디가 게이트(`--radius-popover` 사용 1회)를 면제했다
  - 근거: 2차-a 워커 질문 · `_RESUME` §2 09-07
- **뷰포트 기준 오버레이 배치** ([[viewport-aware-overlay]]) — 팝오버가 60vh 만 보고 트리거 위치를
  안 봐서 아래쪽 트리거에서 최대 114px 화면 밖으로 나갔다. 「스크롤이 안 된다」는 보고의 실체
  - 왜 이걸 골랐나: 팝오버 한 곳에서 트리거 아래·위 남은 자리를 재서 넓은 쪽으로 열고
    `clamp(160, 남은 자리, 420)` 을 주는 게, 소비처마다 높이를 박는 것보다 낫다
  - 무엇이 어려웠나: 늦게 도착한 내용(이력)의 높이 변화를 팝오버가 모른다 — FE 가 resize 이벤트로
    우회했고 제대로는 ResizeObserver(잔여)
  - 근거: `popover-scroll-fix-report.md` · 커밋 `010a594`
- **부분 자격 응답은 필드를 비운다** ([[field-level-visibility]]) — 6축 통합 조회에서 전화·생년월일·
  권한·회수분은 본인 또는 `organization.manage` 보유자에게만 값, 아니면 null/빈 배열
  - 왜 이걸 골랐나: 화면이 한 요청으로 그리려면 자격 없는 필드에서 403 을 던질 수 없다. 반면 이력·
    변경 기록은 「현재값보다 더 아는 것」이라 403 으로 갈랐다
  - 무엇이 어려웠나: 「phone 이 null 이면 자격 없음」이라는 프론트 휴리스틱이 무너졌다 — SC 는
    전화가 없어 전원 null 이다. 서버와 같은 술어를 프론트에도 두는 것으로 대체
  - 근거: `test_organization_member_axes.py` · 2단계 워커 보고 · 커밋 `5f8b608`·`663319c`
- **데이터는 리포 밖, 계약은 리포 안** — SC CSV 를 dataset 표 6개로 변환해 `make dataset-import`
  로 넣었다. sc-org 가 만든 mediness 모델 기반 시드는 버리고 판정 규칙(겸임 병합·동명이인·slug 표)만
  재활용
  - 왜 이걸 골랐나: mediness 모델은 GiST EXCLUDE(btree_gist)를 요구하는데 이 제품은 「확장 없는
    PostgreSQL」이 설계 제약이다. 게다가 조직 원장이 이미 있다
  - 무엇이 어려웠나: 사번이 어디에도 없어 `members.key` 를 임시 사번으로 썼다. 로그인 계정과
    이메일이 한 테이블(`member_credentials`)이라 「테스트 계정」을 덮어쓰면 실제 계정이 사라진다는
    것을 늦게 알았다(§3)
  - 근거: `reference/2026-09-04-SC-org_data/README.md` · 커밋 `929872f`~`83c0197`
- **BE 에 없는 기능은 그리지 않는다** — 소속·직책 「변경」, 행 메뉴, 변경 기록 테이블(1단계)을 뺐다
  - 왜 이걸 골랐나: SPEC-005 §5. 버튼을 먼저 그리면 command 가 화면에 끌려 나온다
  - 근거: `org-screen-survey-report.md` BE 표 · 1단계 브리프 §3

## 3. 막혔던 것 / 사고

- **리뷰에서 잡힌 8건** — 높음 3: 후보 API 로 개인정보 유출(명부 응답 모델을 후보 API 가 돌려씀), 상세 응답 경합으로 권한 부여 대상 불일치(요청 세대 없음), 변경 기록이 타 회사까지(unit_id 생략 시 필터 소실). 공통점은 「한 조회·한 모델을 다른 입구가 재사용」과 「비동기 응답의 순서 가정」. 회귀 테스트 11개로 고정. 리뷰어의 재현 서술이 그대로 테스트가 됐다 — 리뷰 요청 때 재현 가능한 형태를 요구할 가치가 있다

- **가짜 계정을 세 번 끼워 넣었다** — 「위하고 메일로 로그인」이라는 지시를 「logins 안 만듦」→
  「데모 도메인 테스트 150개」→「3개」→「실제 메일 보유자를 가짜로 대체」로 비껴갔다. 사용자 질책 후
  전원 회사 도메인으로 되돌리고 나열 규칙을 env 로 열었다. 데이터 결정은 사용자 말을 그대로 옮긴다
  (코디 메모리 feedback_no_fake_accounts 로 기억)
- **조사를 서브에이전트로 돌렸다가 반려** — 워커 발주로 다시. 워커 산출물만 work/ 에 남는다
- **코디 handle 이 세션 재연결로 두 번 바뀌었다** — 워커 보고가 옛 handle 로 가면 코디가 안 깨어난다.
  바뀔 때마다 워커에게 새 handle 을 꽂고 `_RESUME` 을 덮어썼다
- **같은 워크트리를 디자인 싱크 세션이 쓰고 있었다** — 미커밋 부품(Drawer·ConfirmModal·DatePicker)이
  쌓였고, 조직 화면이 그 위에 올라가야 해서 코디가 검증 후 커밋했다. 한 워크트리에 코디 둘은 위험
- **브리프 전제 오류** — 「상태 변경 select 존재」「phone null = 자격 없음」「1106·1107 로그인 401」
  (워커가 주소를 잘못 침) — 워커 질문·보고로 잡혔다. 전제는 브리프 쓰기 전에 grep 으로 센다
