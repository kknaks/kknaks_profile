# 작업 요약 — day-cc-mig (day)

기간: `2026-11-20` ~ `2026-11-22`
결과: 1단계(테이블 보충)까지 끝. CENTURION_DAY #265(dev 머지 · 배포 · dev 실제 업데이트) · mediness #954 · Delivery #264. ext 이관 · 고도화(2단계)는 다음 작업으로 넘겼다(사용자). prod 는 사용자가 따로 버전 관리하며 올린다.

## 1. 무엇을 했나

목표는 cc-prototype 에서 시험한 ext 외부 연동 API(13 경로)를 DAY 로 옮겨 고도화하는 것이었다. 조사를 세 번 했다. 먼저 ext 가 넘기는 값과 그 값이 DAY DB 에 있는지를 봤다. 그다음 KOS 응답 키 전체를 DAY 칸과 맞췄다(HAR 67 + 새 HAR 7). 조사해 보니 DAY 에 빈 칸이 많았다. 사용자는 순서를 **「테이블 먼저 다 채우고, 기능은 그다음」** 으로 정했다. 이유는 테이블을 지금 다 만들어 두면 나중에 기능을 붙일 때 마이그레이션이 준다는 것이었다.

- KOS 응답 키 2,155개를 HAR 로 전수 대조했다. DAY 에 없거나 시점이 다른 키는 고유 632개였다.
- SPEC-000 에 §4A 「KOS 키 보충」을 새로 썼다. 630개를 반영했다(mediness #954).
- migration 0012: 새 표 12개, 지금 있는 23표에 nullable 칸 180개, 새 DAY enum 9개를 더했다. 지금 칸 변경은 0이다.
- 이미 도는 동기화 회차가 새 칸을 채운다. 기준 정보 회차에는 병원 설정 단계(정보 · 운영 시간 · 휴무 · 예약 규칙)를 더했다. 화면 · 입력 기능은 만들지 않았다.
- 이미 있는 행은 `runtime.backfill --stage kos_keys` 로 채웠다.
  - 로컬 DEMO: 드라이런 0 → 실제 6,126 → 재실행 0.
  - dev 실제: 일정 4,880 · 구매 7,020 · 시술권 9,119행을 쓰고 중간에 끊겼다. 이어 받은 뒤 재실행은 6단계 모두 쓴 행 0이었다.

## 2. 적용한 기술·개념

- **외부 응답 키를 전부 칸으로 — 스키마를 미리 넓혀 마이그레이션을 줄인다** → [[online-schema-change]] · [[data-modeling]] — 사용자 규칙 「DAY 테이블은 외부 CRM 보다 크다」(11-03)를 이번에 키 단위로 지켰다.
  - 왜: 기능을 붙일 때마다 칸을 더하면 상용 DB 에 마이그레이션이 계속 쌓인다. KOS 를 뗄 때 「필요할 때 외부를 읽는다」로 비워 둔 칸은 볼 곳이 없어진다.
  - 판단이 갈린 것: 「일부러 안 둠」 54행(병원 전화 · 주소 · 고객 isNew · 카드 total 등)은 「다 저장」 원칙으로 뒤집었다. 다만 DAY 가 계산할 수 있는 값(「계산으로 대체」 160)은 그대로 칸을 두지 않았다. 질의마다 답이 바뀌는 응답(예약 칸 · 칸 점유)은 표로 두지 않고 계산한다.
  - 근거: `research-kos-keys-report.md` K3-2 · `research-kos-keys-3-report.md` N7 · SPEC-000 §4A.10
- **HAR 로 응답 키 전수 대조 — 경로식 펼치기 · 합집합 · 판정** → [[public-vs-internal-api]] — 응답 JSON 을 `data[].reservation.counselor.name` 처럼 경로식으로 펼쳤다. 여러 HAR 의 합집합을 내고, 키마다 저장됨 / 칸 있음·미동기화 / 칸 없음 / 시점 다름 / 일부러 안 둠 / 계산으로 대체 중 하나로 판정했다.
  - 한계 ①: **HAR 은 데모에 값이 있어야 키가 보인다.** 휴무 · 예약 정책 · 병원 언어는 세 번 캡처해도 빈 배열이었다. 특별 휴무 · 그룹 휴무는 KOS 웹에 입력하는 곳 자체가 없었다(사용자). 그래서 cc 코드가 읽던 모양 `{id, startDateTime, endDateTime}` 으로 표를 두고 첫 실값에서 확인한다(OQ-4A-2).
  - 한계 ②: **공개 API 는 웹 HAR 에 안 찍힌다.** 칸 정원 · 예약 수(`get-reservation-slots-by-groups`)를 대신할 내부 경로가 없었다. 그래서 정원 + 점유 계산으로 갔다.
  - 기본 휴무는 따로 저장되는 데이터가 아니었다. 화면이 운영 시간표의 요일 `enabled:false` 로 칠하는 값이었다(사용자 스크린샷 + `병원휴무.har`).
  - 근거: 2차 · 3차 리포트 부록 A(스크립트) · `reference/2026-11-20-day-cc-mig/2026-11-20-kos-payment-screen.png(기본 체크아웃 · 개인정보 · 커밋 안 함)`
- **같은 이름 · 다른 시점 — 칸을 시점으로 나눈다** → [[data-modeling]] — cc ext 의 `counselor` 는 **예약 때 지정한 희망 상담사** 였다. 사용자가 기대한 값은 상담 차트의 상담사였다. DAY 는 두 값을 다른 칸(`visit.requested_counselor_id` · `consultation.counselor_id`)에 둔다. 이번 보충에서도 일정의 단일 상담 정보(상담사 · 원장 · 메모)를 상담 기록과 다른 칸으로 뒀다. 산 시점 메뉴 스냅샷도 지금 메뉴와 다른 칸이다.
  - 근거: `research-cc-ext-report.md` A2-1 「뜻 불일치 후보」 8 · SPEC-000 §4A.3
- **모르는 외부 값 — 행은 받고 그 칸만 비우고 경고 한 번** → [[tolerant-reader]] · [[no-silent-fallback]] — 상태 · 종류는 DAY enum(「enum 은 DAY 말」)으로 두되, 목록 밖 KOS 값이 와도 행을 버리지 않는다.
  - 왜: 기존 매퍼는 목록 밖 결제 수단을 만나면 **그 거래 행째** 뺐다(`MappingError`). 그래서 KOS 에 있는 `CARD` 결제가 동기화에서 조용히 빠지는 구멍이 있었다. 이번 2차 조사에서 HAR 로 처음 발견했다.
  - 실물: 로컬 DEMO 첫 회차에서 목록 밖 값 9줄이 나왔다(`URGENT` · `CANCELED` · `ONCE_PER_RESERVATION` · 예약 규칙 이력 5종). 행은 저장되고 칸만 null 이었다. 백필 · 업데이트까지 다 돌려 본 뒤 **한 번에** 0012 에 값을 추가했다(사용자 「결과 보고 한 번에」).
  - 경고는 프로세스당 한 번만 남긴다. 처음엔 회차마다 찍혀 값 하나에 하루 8,640줄이 될 뻔했다(검수 W2).
  - 남은 예외: `payment_type` 은 지금 NOT NULL 칸이라 칸만 비울 수 없다. 모르는 결제 수단(앱 결제 · 간편결제)은 여전히 거래를 뺀다(OQ-4A-1 · 데모에서 결제 승인 불가).
  - 근거: `be-1-report.md` A4 · 고침 1 · `review-code-1-report.md` W2
- **10초 회차의 N+1 과 동시 쓰기 — 묶음 SELECT · 같은 잠금 안 반영 · query-count 테스트** → [[n-plus-one]] · [[database-lock]] — 새 칸 보충이 부모 행마다 SELECT 를 냈다. 반영 상한도 30초로 10초 주기보다 길었다. 다음 일정 회차와 같은 방문 · 작업 행을 다른 잠금으로 동시에 쓸 수 있었다(검수 W1).
  - 고친 것: 표마다 `in_` 묶음 SELECT, 그 회차와 같은 잠금 안에서 반영, 상한 8초, 방문 1건 vs 7건 문 수가 같다는 query-count 테스트.
  - 결과: dev DEMO 회차 6초 · 4초.
  - 근거: `review-code-1-report.md` W1 · `be-1-report.md` 고침 2
- **변경 감지 칸이 매 회차 왕복 — 쓰기 증폭** → [[external-id-mapping-table]] — 지금 반영의 연결(`Refs.link`)은 `external_updated_at` 을 매번 None 으로 덮었고, 새 보충이 KOS 수정 시각으로 다시 썼다. 값은 회차 끝에 맞았지만 직원 83 · 상담 3 · 고객 8 행이 10초마다 UPDATE 됐다(DEMO 실물에서 발견).
  - 첫 고침은 `Refs.link` 를 「None = 유지」로 바꿨다. 그런데 그러면 구매 · 카드 · 메뉴의 「바뀜」 판정까지 뜻이 바뀐다(검수 W5). 그래서 원래 뜻으로 되돌리고, 직원 · 상담 · 고객 호출 자리에서만 옵션으로 유지했다.
  - 교훈: **공용 함수 한 줄의 뜻 변경은 모든 호출자에게 퍼진다.**
- **수동 업데이트 — 페이싱 · 멱등 · 이어 받기 · 진행 키 분리** → [[paced-backfill]] · [[idempotency]] — customer-erd 백필(`runtime.backfill`)에 `--stage kos_keys` 를 더했다. KOS 1초 1회, 드라이런 DB 쓰기 0, `--resume`, 자기 세션만 해제.
  - 진행 위치를 지난 백필과 같은 키에 두면 서로 덮는다(검수 W7). 그래서 stage 별로 나눴다.
  - 실물: dev 실행 중 **다른 세션이 dev 에 #266 을 머지해 배포가 돌았다.** 컨테이너가 바뀌면 `docker exec` 실행이 끊긴다. 마이그레이션 0013 · 0014 와 겹칠 위험도 있었다. 그래서 사용자 지시로 업데이트를 멈췄다(SIGINT). 그 배포가 취소된 뒤 `--resume` 이 남은 카드 단계만 34호출로 마쳤다.
  - 근거: dev VM `~/kos-keys-20261120-*.log` · `review-code-1-report.md` W7

## 3. 막혔던 것 / 사고

- **범위를 계속 넓히고 말을 길게 해 사용자를 크게 화나게 했다.**
  - 수납 리다이렉트 → 수납 URL 재캡처 · 결제 설정 저장, 문진 → 문진 HAR, 예약 현황 화면을 차례로 범위에 끌어왔다. 사용자는 「지금 수납이 왜 필요한 거야」 · 「ext 랑 테이블 보충만 하는 거 아니야」라고 짚었다.
  - 「데이터 다 채우는 게 먼저」를 decision · SPEC · 백필 · 새 표 7개의 긴 계획과 발주 질문으로 되돌려 줬다. 사용자는 욕설과 함께 「지금 필요한 기능들만 하고 테이블만 일단 만들자니까」라고 했다.
  - 「테이블은 다 채우고」를 「ext 13개가 쓰는 테이블만」으로 잘못 줄였다가 다시 고쳤다.
  - → **범위는 사용자가 말한 낱말 그대로 · 짧게.** 기억(do-only-what-asked)에 재발로 적었다.
- **3차 조사에서 HAR 재캡처를 여러 번 요청했다.** 휴무는 입력하는 곳이 KOS 웹에 없어 세 번 받아도 값이 비었다. 「그 HAR 이 어떤 테이블에 필요한가」를 먼저 따졌다면 요청이 휴무 둘로 줄었을 것이다. 사용자가 「지금 어떤 테이블에 저 HAR 이 필요한 거야」라고 묻고 나서야 줄였다.
- **로컬 실물이 KOS 기기 제한(동시 로그인 5)에 막혔다.** 테스트 계정 세션 5개가 모두 다른 표시라 워커가 멈췄다. 사용자 「테스트 계정 줬잖아」 → 오래된 2개를 해제하고 진행했다. 테스트 계정은 우리 것이라 해제해도 된다는 걸 미리 브리프에 넣었어야 했다.
- **디스크 100%(남은 174MB)** 로 코디와 워커가 함께 멈췄다(ENOSPC). 이번 작업 산출물은 1MB 미만이었다. 사용자가 정리해 26GB 를 확보했다.
- **다른 세션의 dev 배포와 겹침** — 위 §2 마지막. dev 는 여러 작업이 같이 머지하는 곳이라, 수동 업데이트 같은 긴 실행은 배포 Actions 를 먼저 확인하고 돌려야 한다.
- **문서 검수 FAIL 2** — 뒤집은 결정(`visit.reservation_group_id`)이 본문 4곳 중 1곳만 고쳐졌다. 상태 칸을 KOS 문자열 `varchar` 로 둬 「enum 은 DAY 말」과 부딪혔다. 고침 1 → 재검수 PASS.
- **mediness #954 머지가 main 보다 뒤처져 막혔다.** 이 레포는 auto-merge 가 꺼져 있다. rebase → CI 대기 → 수동 머지로 처리했다.
