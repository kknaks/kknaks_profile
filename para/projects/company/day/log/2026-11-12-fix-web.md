## 1. 무엇을 했나

prod 첫 배포 뒤 사용자가 /board 를 직접 보며 피드백 11건을 줬다 — 왼쪽 받은함이 탭 3개 + 아코디언 6칸이라 「무엇을 봐야 하나」가 흐렸다.
받은함을 「확인 필요 n」 · 「수락 대기 n」 두 목록으로 줄이고, 확인 필요 상황을 4가지(대기 · 마취 · 호출 · 귀가대기)로 줄였다(수락 뒤 미시작은 서버에서 뺌).
로컬 E2E 에서 오더 메모에 「누가 상담했나」를 요청받아, 이미 동기화돼 있던 상담 기록의 상담사를 판 스냅샷에 실어 메모 제목 줄 배지로 띄웠다. 앱은 심사 중이라 한 줄도 고치지 않았다.

## 2. 적용한 기술·개념

- **공개 API 에서 값을 빼도 깔린 클라이언트가 안 깨지는지 — 파서가 값 목록을 검사하는지로 판정** — 수락 뒤 미시작(`needs[].why = accept`)을 서버에서 뺄지 웹에서만 거를지 → [[tolerant-reader]] · [[contract-surface-enumeration]]
  - 왜 이걸 골랐나: 사용자는 처음 「심사 중이니 프론트에서만」을 골랐다. 조사로 앱 파서(`Need.parse` · `Limits.parse`)가 why 를 문자열 그대로 받고 모르는 칸을 null 로 두는 걸 확인 → 서버에서 빼도 크래시 없고 앱 화면에서도 같이 사라질 뿐이라 웹 · 앱 정의를 하나로 두는 쪽(서버)으로 바꿨다. 값 이름을 바꾸거나(`inbox.section`) 칸 모양을 바꾸는 건 깨지므로 그쪽은 손대지 않았다.
  - 무엇이 어려웠나: 「웹 전용 목록(`rules.inbox()` startable · waiting)」과 「앱도 쓰는 카드별 `inbox.section`」이 같은 이름이라 지우면 안 되는 쪽을 섞기 쉬웠다 — 조사 리포트가 두 층을 나눠 줘서 웹 쪽만 지웠다.
  - 근거: `research-1-report.md` §2 · §10 · §11 · `be-1-report.md` 앱 호환 근거 · CENTURION_DAY#250
- **화면 높이로 「펼치기」 판정** — 오더 메모 접힘 판정이 줄바꿈 수(`split('\n') > 5`)라 줄바꿈 없는 긴 한 줄은 잘린 채 버튼이 없었다 → [[measured-overflow-toggle]]
  - 왜 이걸 골랐나: 글자를 10 → 12 → 14px 로 키우면서 한 줄이 접힐 확률이 커졌다(리뷰 W2). 서버는 늘 버튼을 숨겨 두고 day.js 가 `scrollHeight > clientHeight` 로 켠다 — 다시 그릴 때(swap 뒤)도 같이 잰다.
  - 근거: `review-code-3-report.md` W2 · `fe-4-report.md`
- **동기화로 이미 들어온 값을 먼저 찾는다** — 「KOS 에서 상담사를 불러오나」는 새 호출이 아니라 `consultation.counselor_id` 를 판 조회에 한 번 더 읽는 일이었다. 사용자 HAR 로 이름이 같은 값인지 대조했다.
  - 무엇이 어려웠나: 「여러 명이면 여러 명」을 처음엔 한 상담의 상담사 배열로 읽어 migration 까지 꺼냈다 — KOS 는 상담 하나에 상담사 한 명만 저장한다(사용자) → 방문의 상담 여러 건 = 여러 명으로 지금 구조 그대로.
  - 근거: `research-2-report.md` §1 · §2 · `be-2-report.md`
- **조회에 쓰는 FK 는 인덱스까지** — `consultation.visit_id` 에 FK 만 있고 인덱스가 없어 판(SSE 로 자주 다시 읽힘)마다 상담 표 전체를 훑는 자리 → 부분 인덱스 `WHERE deleted_at IS NULL`(migration 0009) + 인덱스를 타는지 가드 테스트. 표가 작아 CONCURRENTLY 는 불필요(리뷰 4). → [[database-index]]
  - 근거: `review-code-3-report.md` W1 · `be-3-report.md` · `review-code-4-report.md`
