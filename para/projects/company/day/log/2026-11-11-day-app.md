## 1. 무엇을 했나

DAY 직원 앱(Flutter · iOS 먼저)을 cc-prototype 앱 디자인을 그대로 두고 DAY 서버 계약 · 색으로 다시 붙였다. 시술 현황
(목록 카드 · 룸 상세 · 호출 · 직무별 수락 · 통역 드로어) → 데모 계정 로그인 환경 연결(D1) → 직원 채팅(SPEC-004 · 서버
API · 기기 등록 · 첨부 · APNs) → 원장 호출 알림 · 알림 목록 · 개인 설정(SPEC-005)을 스펙 → Delivery #235(v7 · v8) →
코드 → 독립 리뷰 순서로 쌓았다. 이 앱 세션은 시술 현황 작업(day-procedure-board-2)과 별도로 돌다가, 사용자 결정으로
코드 PR(#237 → #238)과 스펙 PR(#920 → #921)을 하나로 합쳐 머지했다.

## 2. 적용한 기술·개념

- **원본 디자인 유지 · 서버 계약만 바꾸기** — 프로토타입 앱 화면 골격(카드 네 줄 · 통역 드로어 · 하단 4탭 · 상단 종)은 그대로, 색과 데이터는 DAY
  - 왜 이걸 골랐나: 첫 구현이 「DAY 스펙대로」 레이아웃을 새로 짜서 원본과 달라졌고, 사용자가 화면을 하나씩 비교하며 교정했다. 디자인 수정에 업무 · 권한 · 서버 계약 변경을 끼워 넣지 않는다는 선을 결정 표에 박았다
  - 무엇이 어려웠나: 교정 지시가 카드 상태마다(시술 대기 · 마취 · 호출 · 진행 · 완료) 이어져, 기록 단계와 코드 반영 단계를 섞지 않도록 「아직 반영 안 함」을 결정마다 적었다
  - 근거: day-app `_RESUME.md` §2 UI 교정 합의 · 카드 와이어
- **직무별 수락 동선** — 원장 로그인 = 본인으로 바로 수락 · 간호사 = 원장 골라 대리 수락(`doctorStaffId`)
  - 왜 이걸 골랐나: 앱은 개인 로그인이라 웹(공용 단말 · 원장 선택 필수)과 달리 로그인한 사람이 누군지 안다. 서버 수락 권한은 그대로 두고 진입만 가른다
  - 근거: SPEC-003 · day-app `_RESUME.md` §2 (2026-11-10)
- **데모 계정 → dev 환경 연결(서버 쪽)** — 정식 빌드 하나에서 심사 · 데모 계정은 dev, 실제 직원은 prod 로. 로그인 응답 `api_base_url`
  - 왜 이걸 골랐나: 앱을 환경마다 따로 빌드하거나 외부 env · JSON 설정을 배포하는 대신 서버가 계정으로 정한다(사용자)
  - 근거: SPEC-001 · CENTURION_DAY 6c6b9d13
- **선택 비밀은 없으면 꺼짐(fail-closed) · 배포는 성공** [[secret-store]] · [[apns-direct-push]] — 채팅 첨부(Blob) · APNs 키가 Key Vault 에 없으면 app.env 에 안 넣고 기능만 꺼짐
  - 왜 이걸 골랐나: Apple 키 · Team ID 가 사용자 몫이라 코드는 먼저 가고 키는 나중에 연결한다. 키가 없다고 배포가 깨지면 다른 기능도 못 나간다
  - 근거: `scripts/deploy/day_vm.py` OPTIONAL_SECRETS · `deploy/config/dev.env`
- **같은 칸 · 다른 뜻을 머지 때 맞추기** [[server-rendered-fragments]] — 앱 스펙의 version(「서버 시각 · 이하 버림」) · 재호출(「대상 고르는 창」)이 시술 현황 스펙과 달랐다
  - 무엇이 어려웠나: 두 세션이 같은 서버 계약을 각자 소비하며 따로 정해, 합친 뒤 문서 리뷰에서야 드러났다(재호출 400). 앱 코드는 재호출만 맞추고(f1e67a2c) version 소비는 다음 작업
  - 근거: day-procedure-board-2 `review-doc-merge921-report.md` · 개정 ⑮ · SPEC-003 개정 ⑦
