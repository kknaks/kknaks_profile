## 1. 무엇을 했나

시술 현황의 차트 모달은 줄마다 자동 저장이었다. 사용자가 「명시적 저장이 중요」하다고 해서 두 가지를 바꿨다.

- **차트**: 탭을 「간호관리차트 | 의사차트 | 시술전후사진」으로 나눴다. 차트 탭마다 [저장]과 「최근 저장」을 두고, 저장하지 않고 닫으면 확인 창을 띄운다. 저장하기 전에 KOS 의 지금 값을 확인한다. 다른 줄이 하나라도 있으면 탭 전체를 저장하지 않고, 그 칸에 「KOS 글 + 내 글」을 이어 붙여 보여 준다.
- **시술전후사진**: DAY 저장소(Azure Blob `beforeAfter/`)와 새 테이블 `visit_photo` 에 저장하고, 로그인한 직원 토큰으로 KOS 에도 등록한다. 여러 장 올리기, 「KOS 미반영」 [다시 시도], 삭제 확인을 넣었다. 사진 탭이 열려 있는 동안 그 방문만 10초마다 KOS 사진을 가져오고, KOS 에서 지운 사진을 DAY 에 반영한다.

여기에 두 가지가 더 붙었다. KOS 시스템 계정 토큰을 Redis 에 하나 두고 API · 워커가 같이 쓰게 했고, 웹 헤더에 로그인한 사람을 표시했다.

착지까지 스펙 8커밋, 문서 검수 5회, 코드 검수 4회, 사용자 e2e 3회가 걸렸다.

## 2. 적용한 기술·개념

- **저장 충돌 = 연 때 값과 외부 지금 값의 대조 · 하나라도 다르면 전부 거절 · 이어 붙여 되돌려 줌** → [[optimistic-lock]]
  - 처음 planner 기본값은 「걸린 줄만 빼고 나머지 저장」(기획 4-2 예외 1)이었다. 사용자가 말한 기준은 「트랜잭션처럼 묶는다」였고, 이 표현을 두 가지로 읽을 수 있었다. 검수가 이 갈림을 잡았다.
  - 사용자 결정(C17): 저장 전에 KOS 를 확인하고, 하나라도 다르면 탭 전체를 저장하지 않는다. 그 칸은 KOS 글 + 줄바꿈 + 내 글로 채운다.
    - 이 방식은 DAY 사본의 `baseLogId` 만으로는 부족했다. KOS 를 사람이 직접 고친 것이 아직 동기화되지 않았을 수 있기 때문이다.
    - 그래서 열 때 받은 `base`(글 · 집도의)를 요청에 되돌려 받는다.
  - 코드 검수가 「다시 저장해도 또 걸리는」 틈 셋을 찾았다.
    - ① 409 직후 동기화가 KOS 이력을 쌓는 경우 → 동기화 이력은 글만 비교해서 같으면 통과(C18)
    - ② 응답이 유실된 뒤 같은 저장을 다시 보내는 경우 → 같은 직원 · 같은 글이면 이미 저장된 것으로 본다(C19)
    - ③ CRLF 줄바꿈이 섞인 경우 → 정규화(C20)
  - 근거: DAY-SPEC-002 규칙 31 · `policies/board_chart_tabs.py` · `review-code-1-report.md` · `review-code-2-report.md`
- **멱등: 응답을 잃은 재시도를 「이미 저장됨」으로 읽기** → [[idempotency]]
  - 자동 저장 시절의 ACK 복구 테스트를 지우면서 「명시적 저장이니 그 경로가 없어졌다」고 판단했는데, 틀렸다. 커밋 뒤 응답이 유실되는 경로는 남아 있었고, 검수가 이를 잡았다(W2).
  - 마지막 이력이 같은 직원 · `source=day` · 같은 글 · 같은 담당자면, 그 줄은 건너뛰고 200 으로 응답한다.
- **외부 원천과 DAY 원장 둘 다에 쓰는 파일 — 순서 · 실패 · 정리** → [[object-storage]] · [[external-write-queue]]
  - 처음 결정(C14)은 「KOS 에만 올리고 DAY 에는 저장 안 함」이었다. 사용자가 「데이에 저장하고 kos 에도」로 뒤집었다(C22). DAY 가 결국 원장이라는 데이터 규칙과도 맞는다.
  - 올리는 순서는 저장소 → DAY 행 커밋 → (transaction 밖에서) KOS 7단계 → `external_ref` 이다. KOS 가 실패해도 DAY 행은 남기고 「KOS 미반영」 + [다시 시도]를 보인다.
    - 사진은 방문 단위 `external_outbox` 에 태우지 않았다. KOS 가 준 id 를 받아야 하고, 직원 토큰으로 써야 하기 때문이다(공지 저장 선례).
  - KOS 웹이 PNG 로 올리는 것을 HAR 에서 보고, 형식을 JPEG · PNG 둘 다로 했다(C24). JPEG 만 받았으면 가져오기에서 KOS 사진이 빠졌다.
  - 저장소 폴더 이름: 코드에는 `before-after` 로 예약돼 있었는데, 인프라가 만든 실제 폴더는 `beforeAfter` 였다. 사용자가 Azure 화면을 보여 줘서 알았다.
- **외부 삭제를 내 원장에 반영할 때의 안전장치** → [[input-space-enumeration]]
  - 「KOS 목록에 없으면 지움」(C31)은 목록 조회가 실패하면 막혔다. 그런데 **성공했지만 비었거나 모자란 목록**은 막지 못했다(검수 4 W1). 권한 없음 · 예약 병합 · 매핑 실패 한 건만 있어도 그 방문의 사진이 10초마다 사라질 수 있었다.
  - C34: 매핑 실패가 하나라도 있거나, 목록이 비었는데 반영된 행이 있으면 그 회차는 판정하지 않는다.
- **10초 폴링이 사용자가 만지는 칸을 갈아 끼우면 입력이 죽는다** → [[polling]]
  - 사진 탭 동기화(C30)를 「조각 전체 innerHTML 교체」로 넣었다. 그러자 파일 고르기 창이 열린 사이에 파일 칸이 바뀌어, 고른 파일의 change 가 떨어져 나간 옛 칸에서 일어났다. 업로드가 조용히 안 됐다.
    - 로그에 POST 0건 · GET 10초마다로 원인을 바로 찾았다. 사용자 e2e(F2)와 검수(W2)가 같은 것을 동시에 잡았다.
  - 고친 방식: 목록만 다시 그린다. 고르는 중 · 보내는 중에는 건너뛴다. 숨겨진 탭에서는 멈춘다(`document.hidden`). 삭제 직후에 온 응답은 지운 사진을 다시 그리지 않는다.
  - 같은 날 예약 현황(day-reservation)에서 이미 배운 것(사람이 손대는 칸은 폴링이 덮지 않는다)을 이번 브리프에 넣지 않았다.
- **외부 시스템 세션은 프로세스가 아니라 병원 단위 하나로 — 공유 저장소의 토큰** → [[shared-session-storage]] · [[distributed-lock]]
  - 증상: 차트를 저장할 때마다 KOS 시스템 계정이 sign-in 했다.
    - 원인 ①: 저장 전 KOS 읽기가 캐시 어댑터(`adapter_for`)가 아니라 `build_adapter`(새 클라이언트)를 썼다. KOS 는 IP 가 아니라 sign-in 마다 세션을 세므로 5기기 한도에 계속 걸렸다.
    - 원인 ②: ①을 고치자, API 와 워커가 각자 세션을 갖고 5기기 한도에서 서로의 「가장 오래된 같은 표시 세션」을 해제했다. 그래서 번갈아 재로그인했다(로그 08:47:29 · 08:49:59).
  - C35: 토큰을 Redis 에 병원마다 하나 두고(암호화 · TTL), 만료나 401 이면 잠금을 잡은 한 프로세스만 다시 받는다.
    - 실물 확인: 저장 12번 → sign-in 1번(① 뒤), 재시작 뒤 API · 워커 sign-in 0번(②).
    - rebase 에서 #274 가 넣은 KOS 조회 워커 경로도 같은 공유 토큰을 쓰게 했다. 구조 규칙(ARCH001 · emr 밖 import 금지) 때문에 저장소 구현은 `bootstrap/kos_tokens.py` 로 옮겼다.
- **서버 앞단 본문 상한은 앱 테스트가 못 본다** → [[contract-surface-enumeration]]
  - 여러 장 올리기(C28)를 하면서 서버의 전체 본문 상한을 없앴다. 그런데 dev · prod 앞의 Caddy 가 `request_body max_size 6MiB` 였다. 5MB 사진 두 장부터 413 이 나고, 그 413 에는 `X-Day-Error` 가 없어 화면에 아무것도 안 뜬다.
  - 로컬 `start.sh` 는 Caddy 를 거치지 않고 테스트는 ASGI 직접 호출이라, 코드 검수 4가 Caddyfile 을 읽어서야 잡았다.
  - C33: 사진 올리기 경로만 100MiB 로 올렸다. 상한 초과는 토스트로 알린다.
- **dev 가 앞서 나가 migration 번호를 밀었다** → [[database-migration]]
  - dev #274 가 `0024_customer_memo` 를 넣어 우리 `0024_visit_photo` 를 `0025` 로 밀었다(down = `0024_customer_memo`).
  - 로컬 DB 는 옛 번호에 서 있었다. 그래서 `visit_photo` · enum 둘을 지우고 `alembic_version` 을 0023 으로 되돌린 뒤 다시 올렸다.

## 3. 막혔던 것 / 사고

- **「저장은 자동 → 명시」를 듣고 사진까지 저장 흐름에 섞었다.**
  - Blob 임시 보관 · 트랜잭션 묶음을 제안했다가, 사용자 「사진은 올리고 삭제만」으로 바로잡혔다.
  - 그 뒤 「Blob 안 씀」으로 정리했는데, 사용자의 「블롭 어떻게 쓰는지 알지?」가 사실은 「DAY 에 저장」이라는 뜻이었다. 결정이 C14 → C22 로 뒤집혔다.
  - 사용자 말의 뜻을 한 번 더 확인했어야 했다.
- **차트 내용이 KOS 로 가지 않는다고 잘못 말했다.** 스펙을 열어 보니 차트 글은 이미 outbox 로 KOS 메모에 가고 있었다. 확인하기 전에 단정했다.
- **Delivery 발행이 막혔다.** harness 가 baseline = fetch 한 origin/main 을 요구하는데, 대상 SPEC-002 는 이미 main 에 stable 이었다. 그래서 「최초 스펙 pending」 길을 쓸 수 없었다. 사용자는 「PR 나중에 머지 · 바로 구현」 → 「이슈 없이 마감」을 택했다.
- **orca 가 `run-create` 없이는 발주를 받지 않게 바뀌어 있었다**(`run_required`). run 을 만들고 진행했다.
- **로컬 스택 기동에서 세 번 걸렸다.**
  - ① 정본 `local.env` 가 KOS 값을 한 파일에 담고 있었는데, 새 실행기는 `local.env` · `kos-demo.env` 를 나눠서 받는다. 그래서 둘로 나눴다.
  - ② 포트 TIME_WAIT 로 bind 가 실패했다 → bind 시험 루프로 기다렸다.
  - ③ 샌드박스 안에서는 bind 가 막힌다 → 샌드박스 밖에서 실행했다.
- **로컬에 「방 배정」 줄이 보였다.** 새 로컬 DB 의 연결 설정에 `room_assign_etc_task_id` 가 없었다(정본 env 에 값이 없음). 코드 문제가 아니었다. `kos-demo.env` 에 넣고 seed-demo 를 다시 돌렸다.
- **e2e 를 중간에 요청했다가 「최종 e2e 해야지」 질책을 받았다.** 사진 서버가 없는 상태에서 「사진 탭 확인」을 목록에 넣었다.
- **프론트가 구조 테스트(architecture)를 돌리지 않아 `innerHTML` 금지를 놓쳤다.** 코디의 전체 시험에서 잡혔다.
- **[바로 시작] 뒤 KOS 집도의가 「시스템」인 것을 사용자가 버그로 봤다.** 집도의 없는 시술은 시스템 계정을 쓰는 것이 기존 규칙(F-3)이다. 정상 흐름은 의사 호출 → 수락이다. 그대로 두기로 했다(C32).
