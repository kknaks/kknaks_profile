# 모놀리식 · 마이크로서비스 아키텍처

**하나의 애플리케이션에 모든 기능을 담을 것인가, 작은 서비스 여럿으로 쪼개 연결할 것인가.** 배포 단위를 몇 개로 둘 것인가의 선택이다.

## 정의

| | 모놀리식 | 마이크로서비스 |
|---|---|---|
| 구조 | 하나의 큰 목적에 **여러 기능이 통합** | 개별 기능을 하는 **작은 서비스를 연결** |
| 설계 | 용이하다 | 시스템 복잡도가 증가한다 |
| 개발 | 단순하다 | 서비스 간 통신·데이터 일관성을 다뤄야 한다 |
| 유지보수 | **어렵다** | **용이하다** |

**배포가 갈리는 것이 실질적 차이**다 — 모놀리식은 한 줄을 고쳐도 전체를 다시 올리고, 마이크로서비스는 바뀐 서비스만 올린다.

## 왜 중요한가

**이 실습이 지나온 길이 모놀리식이다.** 컨트롤러·서비스·DAO 를 층으로 나눴지만 **한 애플리케이션 안**이고, 배포도 하나다 → [[mvc-pattern]] · [[service-layer]]

층으로 나누는 것과 **프로세스로 나누는 것**은 다른 결정이다. 층은 같은 메모리 안에서 메서드를 부르지만, 서비스로 나누면 **네트워크 너머의 호출**이 된다 — 느리고, 실패하고, 트랜잭션이 안 걸린다 → [[remote-procedure-call]] · [[transaction]]

**그래서 「유지보수가 용이하다」는 대가를 치른 결과다.** 필기가 「시스템의 복잡도는 증가하지만」이라고 앞에 단 것이 그 대가이고, 그 복잡도를 감당할 도구가 있어야 성립한다 → [[container]]

## 경계와 오해

- **마이크로서비스가 더 나은 아키텍처가 아니다** — 팀과 서비스가 작을 때는 모놀리식이 거의 모든 면에서 낫다. **쪼개는 이유는 기술이 아니라 조직과 배포 주기**인 경우가 많다
- **「유지보수가 어렵다/용이하다」가 뒤집힐 수 있다** — 서비스가 열 개면 장애 추적·버전 호환·배포 순서가 새 일이 된다. **한 곳의 복잡함이 여러 곳의 복잡함으로 옮겨 가는 것**이지 사라지지 않는다 → [[coupling]]
- **층 분리 ≠ 서비스 분리** — 이 실습의 컨트롤러/서비스/DAO 는 **한 프로세스 안의 층**이다. 그것을 잘해 두면 나중에 쪼개기 쉬워지지만, **이미 쪼개진 것은 아니다** → [[cohesion]]
- **데이터를 나누는 것이 가장 어렵다** — 서비스마다 DB 를 두면 조인이 사라지고 **한 트랜잭션으로 묶을 수 없다.** 「전부 성공하거나 전부 되돌린다」가 성립하지 않는 세계로 넘어가는 것이라, 보정 절차를 따로 설계해야 한다 → [[transaction]] · [[declarative-transaction]]
- **모놀리식도 잘 설계할 수 있다** — 안에서 경계를 잘 지킨 모놀리식은 쪼갤 때 쉽고, 그러지 않은 것을 쪼개면 **분산된 엉킴**이 된다 → [[solid-principles]]
