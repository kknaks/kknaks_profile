# 정규화 (Normalization)

데이터 중복을 제거하기 위해 테이블을 논리적 단위로 분리하는 관계형 데이터베이스 설계 원칙이다.

## 정의

- 동일한 데이터가 여러 테이블에 반복 저장되면 갱신 시 불일치가 생긴다.
- 정규화는 중복 데이터를 별도 테이블로 분리하고 외래 키(참조)로 연결해 이 문제를 해소한다.
- 결과적으로 데이터 정확도와 일관성이 높아진다.
- 반면 조회 시 조인(JOIN)이 필요해 입출력 문법이 복잡해지고 쿼리 성능이 낮아질 수 있다.

### 나누는 신호는 「중복」 하나가 아니다

Day54 가 손으로 겪은 것은 데이터 중복이 아니라 **컬럼의 반복**이다. 「하나에 여러 개가 딸린다」를 컬럼을 여러 개 두어 담으면 세 가지가 함께 온다.

| 신호 | Day54 의 표현 | 무엇이 문제인가 |
|---|---|---|
| 컬럼이 번호를 달고 반복된다 (`filepath1`~`filepath5`) | 「최대 5개 까지만 올릴수 있다」 | **개수 상한이 스키마에 박힌다** — 늘리려면 `alter table` |
| 대부분의 칸이 빈다 | 「5개가 안되는 게시글도 무조건 5개 파일 경로를 차지」 | 행마다 `NULL` 이 쌓이고, 「몇 개인가」를 세려면 컬럼을 하나씩 확인해야 한다 |
| **한 컬럼에 값 여러 개를 이어 담는다** (`"1,3,7"`) | Day55 가 제거한 형태 | 상한은 없지만 **검색·제약·조인을 전부 잃는다** (아래) |
| 같은 값이 여러 행에 반복된다 | (Day54 에는 없음) | 갱신 불일치 — 위의 「동일한 데이터가 반복 저장」 |

앞의 세 줄이 **제1정규형**이 말하는 것이고 마지막 줄이 **제2·제3정규형**이 말하는 것이다. 「정규화 = 중복 제거」로만 알아 두면 Day54 의 사례가 왜 정규화인지 설명되지 않는다 — `filepath1`~`filepath5` 에는 **중복된 데이터가 하나도 없다.**

세 번째 줄이 **하루 뒤 Day55 에서 실제로 지워지는 형태**다. 실습 프로젝트는 프로젝트의 팀원 목록을 컬럼 하나에 **콤마로 이어 붙여** 담고 있었다.

```java
String memberNoList = project.getMembers().stream()
          .map(user -> String.valueOf(user.getNo()))
          .collect(Collectors.joining(","));
```

**첫 번째 줄(반복 컬럼)과 반대 방향의 잘못**이다. `filepath1`~`filepath5` 는 개수 상한을 스키마에 박은 대가로 각 값이 여전히 **한 칸에 하나**였는데, 콤마 문자열은 상한을 없앤 대가로 **한 칸에 여럿**을 넣는다. 제1정규형이 요구하는 「값이 더 쪼개지지 않는다」를 어기는 쪽은 후자이고, 그래서 **DB 가 그 안을 볼 수 없다** — 아래 「경계와 오해」가 그 목록이다.

## 사용 예시

Day54 가 게시판 첨부파일로 그 과정을 그대로 밟는다. 처음은 한 테이블에 경로 칸을 다섯 개 박아 둔 것이다.

```sql
create table test1(
  no int primary key auto_increment,
  title varchar(255) not null,
  content text,
  rdt datetime default now(),
  filepath1 varchar(255),
  filepath2 varchar(255),
  filepath3 varchar(255),
  filepath4 varchar(255),
  filepath5 varchar(255)
);
```

「하나에 여러 개」를 **컬럼의 개수**로 담은 형태다. 이것을 「하나에 여러 개」를 **행의 개수**로 담는 형태로 옮긴다.

```sql
/* 게시판 테이블 */
create table test1(
  no int not null primary key auto_increment,
  title varchar(255) not null,
  content text,
  rdt datetime not null default now()
);

/* 첨부 파일 테이블 */
create table test2(
  fno int not null primary key auto_increment,
  filepath varchar(255) not null,
  bno int not null /* 게시글 번호 */
);
```

**이 자리에서 Day54 가 남긴 한 줄이 정규화의 대가를 말한다** — 「데이터 무결성 에러(파일관리시스템과 게시글의 연결성이 없다.)」. 테이블을 나누면 **나눈 것을 다시 잇는 장치가 필요해지고**, 그것이 [[foreign-key]] 다. 정규화와 외래키가 같은 회차에서 함께 나오는 것이 우연이 아니다.

다대다는 한 걸음 더 간다 — Day54 의 프로젝트·회원 예에서 두 테이블을 직접 이을 방법이 없으므로 **중간 테이블(`myapp_members`)** 을 하나 더 만들고 그 테이블이 양쪽으로 외래키를 갖는다.

### Day55 — 나누는 값이 코드에서 청구된다

Day54 가 SQL 로만 밟은 과정을 Day55 가 **자바 코드까지** 가져간다. 팀원 목록을 담던 컬럼을 지우고 중간 테이블 `myapp_project_members` 를 만든 뒤, 필기가 고친 자리는 **DAO 세 곳과 Command 네 곳**이다.

| 지운 것 | 대신 온 것 |
|---|---|
| `insert` 의 `Collectors.joining(",")` — 팀원 번호를 문자열로 조립 | `insertMembers(projectNo, members)` — 팀원마다 행 하나 |
| `findBy` 의 `members.split(",")` + 번호마다 `userDao.findBy()` | `getMembers(projectNo)` — 조인 한 문장 → [[sql-join]] |
| `update` 의 같은 조립 코드 | `deleteMembers` + `insertMembers` |

**나누는 결정 하나가 스키마 세 줄과 자바 메서드 셋으로 갈라진다.** 「조회 시 조인이 필요해 입출력 문법이 복잡해진다」고 위에 적어 둔 대가가 여기서는 문법이 아니라 **메서드 개수**로 나타나고, 등록 하나가 문장 둘이 되면서 그 둘을 잇는 값(부모 키)과 그 둘을 묶는 경계(트랜잭션)까지 함께 필요해진다 → [[generated-keys]] · [[transaction]]

## 왜 중요한가

중복 없이 한 곳에만 저장된 데이터는 수정 시 한 곳만 바꾸면 전파가 끝난다. 금융 거래처럼 정확도가 생명인 도메인에서 중복 데이터는 조용한 불일치로 이어져 치명적 버그가 된다.

**그리고 「몇 개까지」라는 제한이 스키마에서 데이터로 내려온다.** Day54 의 첫 설계에서 「첨부파일 6개」는 **컬럼을 더하는 배포**였고, 컬럼을 읽는 자바 코드도 같이 고쳐야 했다. 나눈 뒤에는 같은 요구가 **행을 하나 더 넣는 것**이 된다 — 구조 변경이 값 변경으로 내려오는 것이 정규화의 가장 실감되는 이득이다 → [[ddl]] · [[dml]]

## 경계와 오해

- **정규화 ≠ 성능 최적화** — 정규화는 정확성을 위한 설계다. 조인 비용으로 성능이 낮아질 수 있어, 성능이 우선이면 의도적으로 비정규화(denormalization)를 선택한다.
- **정규화는 관계형 DB에 특유** — 도큐먼트 DB·컬럼 패밀리 DB는 의도적으로 중복을 허용하며 정규화를 하지 않는다. 이 선택 덕분에 분산 처리가 쉬워진다.
- **「컬럼이 반복된다」 ≠ 「데이터가 중복된다」** — 둘 다 정규화가 답이지만 증상이 다르다. Day54 의 `filepath1`~`filepath5` 는 **같은 값이 두 번 저장된 곳이 한 군데도 없다** — 갱신 불일치가 생기지 않으므로 「중복 제거」라는 정의로는 왜 고쳐야 하는지 설명되지 않는다. 문제는 **개수가 정의에 박혔다는 것**이고, 그것이 제1정규형이 요구하는 「반복 그룹을 두지 않는다」다. 정규화를 중복 하나로만 기억하면 이 모양을 그냥 두게 된다.
- **Day54 가 든 세 번째 문제는 테이블을 나눠도 해결되지 않는다** — 「파일 입출력으로 인한 속도 저하」인데, **파일은 여전히 파일시스템에 있고** 나뉜 것은 경로를 적는 자리뿐이다. 오히려 조회가 두 테이블에 걸치므로 DB 쪽 일은 늘어난다. 필기가 이 항목을 다른 둘과 나란히 적어 「테이블을 가르면 셋 다 풀린다」로 읽히지만, **풀리는 것은 앞의 둘**이다. 파일 입출력 비용은 저장 위치(파일시스템 vs BLOB 컬럼 vs 오브젝트 스토리지)를 고르는 다른 문제다 → [[io-stream]] · [[sql-data-type]]
- **빈 칸이 많은 것과 `NULL` 이 허용되는 것은 다른 문제다** — Day54 의 「5개가 안되는 게시글도 무조건 5개 파일 경로를 차지」는 저장 공간 이야기로 읽히지만(`varchar` 는 `NULL` 이면 거의 자리를 안 쓴다) 실제 대가는 **질의**다. 「첨부가 있는 게시글」을 찾으려면 `filepath1 is not null or filepath2 is not null or ...` 이고, 「첨부 개수」를 세려면 다섯 컬럼을 하나씩 확인해야 한다. 나눈 뒤에는 둘 다 한 줄이다 → [[sql-null]] · [[aggregate-function]]
- **「컬럼 하나에 콤마로 이어 담기」는 컬럼이 하나여서 정규화 위반으로 보이지 않는다** — `filepath1`~`filepath5` 는 눈에 보이는 반복이지만 `members varchar(255)` 는 평범한 컬럼 하나다. 그런데 잃는 것이 더 많다. ① **조건으로 찾을 수 없다** — 「3번 회원이 속한 프로젝트」를 `like '%3%'` 로 찾으면 13번·23번·30번이 함께 걸리고, `like '%,3,%'` 로 고쳐도 맨 앞과 맨 끝이 빠진다. ② **외래키를 걸 수 없다** — 값이 번호 하나가 아니므로 참조 검사가 성립하지 않고, 그래서 **탈퇴한 회원의 번호가 문자열 안에 영구히 남는다**(고아 참조인데 DB 는 모른다). ③ **개수를 셀 수 없다** — 팀원 수는 콤마를 세어야 하고 그것은 SQL 의 일이 아니다. ④ **한 명을 빼려면 문자열 전체를 다시 쓴다** — 읽고 쪼개고 지우고 다시 이어 붙여 `update` 하므로, 두 사람이 동시에 팀원을 추가하면 나중 것이 앞의 것을 덮는다. **상한을 없앴다고 문제가 없어진 것이 아니라 문제가 DB 밖으로 나간 것**이고, 나간 곳에는 검사해 줄 사람이 없다 → [[foreign-key]] · [[sql-like]] · [[aggregate-function]] · [[transaction]]
- **필기가 그 컬럼을 두 이름으로 부른다** — Day55 의 본문은 「myapp_projects에서 **userNo**를 제거하고」인데 같은 노트의 자바 코드는 `rs.getString("**members**")` 로 읽는다. 지우는 대상이 하나인지 둘인지 필기만으로는 알 수 없고, 이름이 갈린 것은 **팀원 번호를 담던 컬럼을 부르는 말이 굳지 않았다**는 흔적이다. 「무엇을 지웠는가」가 뒤에 남지 않으면 이 변경은 되짚을 수 없다 → [[ddl]]
- **중간 테이블은 정규화의 산물이 아니라 관계형 모델의 필연이다** — 다대다에 중간 테이블을 두는 것은 「중복을 없애려고」가 아니라 **컬럼 하나에 값 여러 개를 담을 문법이 아예 없기 때문**이다. 비정규화를 고르더라도 다대다에는 중간 테이블이 남는다 — 정규화 단계와 함께 배우기 때문에 같은 종류로 묶이는 자리다 → [[foreign-key]] · [[array]]
- **나누는 것에는 끝이 있다** — 「더 나누면 더 정확해진다」로 가면 테이블 수십 개에 조인이 열 겹이 되고, 어떤 화면도 쿼리 하나로 그릴 수 없게 된다. 나누는 기준은 「나눌 수 있는가」가 아니라 **「이 둘이 서로 다른 속도로 변하는가·따로 존재할 수 있는가」**다. 첨부파일은 게시글보다 늘고 줄고 게시글 없이 존재할 이유가 없으므로 갈라도 되는 쪽이었다.

- [[2024-08-12-Day54]] — 게시판 첨부파일을 `filepath1`~`filepath5` 한 테이블에서 게시글·첨부 두 테이블로 가르며 **정규화를 손으로 밟은 회차**다. 「최대 5개까지만」·「5개가 안 되는 게시글도 5개 경로를 차지」·「파일 입출력으로 인한 속도 저하」 세 문제를 스스로 적었고, 가른 뒤 「데이터 무결성 에러(파일관리시스템과 게시글의 연결성이 없다.)」로 **외래키가 필요한 이유까지 이어 갔다.** 다대다에서는 중간 테이블(`myapp_members`)을 세워 양쪽으로 외래키를 두는 형태를 그림으로 남겼다. 「정규화」라는 낱말은 나오지 않고, 세 문제 중 「파일 입출력으로 인한 속도 저하」는 테이블 분리로 해결되지 않는다
