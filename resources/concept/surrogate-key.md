# 데이터가 자기 필드로 갖는 식별 번호 (시퀀스 번호)

「몇 번째에 있는가」가 아니라 **「몇 번인가」를 데이터 자신이 필드로 들고 있는 것.** 배열 중간을 지워도 남은 것들의 번호가 흔들리지 않는다.

## 정의

필드가 **두 개** 필요하다. 지금까지 몇 개를 발급했는지 세는 카운터와, 그중 자기가 받은 번호를 담는 자리다.

```java
public class User {
  private static int seqNo;                     // 클래스당 하나 — 발급기
  private int no;                               // 인스턴스마다 하나 — 받은 번호

  public static int getSeqNo() {
    return ++seqNo;                             // 올리고, 올린 값을 준다
  }

  public int getNo()          { return no; }
  public void setNo(int no)   { this.no = no; }
}
```

발급기가 클래스 멤버여야 한다는 것이 핵심이다 — 인스턴스마다 하나씩 있으면 전부 1번이 된다 → [[static-member]]

```java
User user = new User();
user.setNo(User.getSeqNo());                    // 인스턴스를 만든 뒤 번호를 받아 넣는다
```

그러면 같은 숫자가 세 가지 뜻으로 갈린다.

| | 배열 인덱스 | 목록 번호 (`i + 1`) | 식별 번호 (`no`) |
|---|---|---|---|
| 어디서 나오나 | 배열의 칸 | 인덱스 + 1, 출력할 때 계산 | 인스턴스 필드, 등록할 때 저장 |
| 중간을 삭제하면 | 뒤가 당겨진다 | 남은 것들의 번호가 바뀐다 | **그대로다** |
| 번호로 찾는 법 | — | `users[no - 1]` (계산) | 훑으며 비교 (탐색) |
| 지운 번호 | 다음 등록이 그 칸을 쓴다 | 즉시 다시 쓰인다 | **다시 나오지 않는다** |

앞의 둘은 **배열이 아는 것**이고 마지막 하나는 **데이터가 아는 것**이다. 그 차이가 삭제할 때 드러난다 → [[one-based-numbering]]

## 사용 예시

전날까지의 코드에서 **번호를 다루는 자리가 전부 바뀐다.** 세 곳이 같은 이유로 움직였다.

```java
// 목록 — 위치를 세어 보여 주던 것을, 데이터에게 물어본다
for (int i = 0; i < userLength; i++) {
  User user = users[i];
  System.out.printf("%d %s %s\n", user.getNo(), user.getName(), user.getEmail());
}                                     // (i + 1) → user.getNo()

// 조회 — 범위를 검사하고 계산하던 것을, 훑어서 찾는다
public static User findByNo(int userNo) {
  for (int i = 0; i < userLength; i++) {
    User user = users[i];
    if (user.getNo() == userNo) {
      return user;
    }
  }
  return null;
}                                     // if (범위) + users[userNo - 1] → for 문 탐색

// 삭제 — 번호로 당기던 것을, 인덱스를 되찾아 당긴다
int index = indexOf(user);
for (int i = index + 1; i < userLength; i++) {
  users[i - 1] = users[i];
}
users[--userLength] = null;           // for (i = userNo; ...) → for (i = index + 1; ...)
```

**전날의 삭제 루프가 `userNo` 로 시작할 수 있었던 것은 번호와 인덱스가 `-1` 하나로 이어져 있었기 때문**이다. 번호가 위치와 무관해지자 그 연결이 끊겨서, 인덱스를 **다시 찾아오는 메서드**가 새로 필요해졌다 → [[linear-search]] · [[array-element-removal]]

그리고 유효성 검증이 사라진 것이 아니라 **자리를 옮겼다.** 「1 ~ 개수 사이인가」를 묻던 `if` 가 없어지고, 대신 `findByNo` 가 `null` 을 돌려주는지 보는 검사가 조회·변경·삭제 세 곳에 들어갔다.

```java
User user = findByNo(userNo);
if (user == null) {
  System.out.println("없는 회원입니다.");
  return;
}
```

**검사할 것이 「범위」에서 「존재」로 바뀐 것**이고, 이쪽이 실제로 묻고 싶었던 질문이다. 전날 세 메서드가 `>=` 와 `>` 로 갈려 마지막 하나에 손댈 수 없던 종류의 실수가, 이 형태에서는 **애초에 쓸 자리가 없다.**

## 왜 중요한가

**삭제가 남의 번호를 바꾸지 않는다.** 전날까지는 3번을 지우면 4번이 3번이 됐고, 그래서 목록을 보고 두 개를 연달아 지우면 두 번째로 엉뚱한 것이 사라졌다. 번호가 데이터 안에 있으면 지운 뒤에도 나머지가 그대로여서, **화면에서 읽은 번호를 나중에 써도 된다.** 번호가 그때그때의 위치 표시에서 **약속**으로 바뀐 것이다.

**대신 조회가 계산에서 탐색으로 바뀐다.** `users[userNo - 1]` 은 한 번에 닿았는데 이제는 앞에서부터 비교해야 한다. **안정성을 얻고 비용을 냈다** — 이 교환이 이 변경의 전부이고, 10건짜리 CLI 라 비용이 안 보인다. 나중에 인덱스·해시·DB 를 배우는 동기가 여기서 생긴다 → [[linear-search]] · [[search-index]]

**그리고 데이터가 저장소 밖에서도 자기를 말할 수 있게 된다.** 「3번째 칸에 있는 것」은 그 배열을 들고 있어야 하는 말이고, 「3번 회원」은 배열 없이도 성립한다. 파일이나 DB 에 적어 두는 것도, 다른 화면에서 다시 찾는 것도 이 번호로 한다 — 관계형 DB 의 기본키가 정확히 이 자리에 오는 것이며, Day19 의 `seqNo` 는 그것을 손으로 만들어 본 것이다. **그 예고가 7주 뒤 Day51 에서 문법으로 도착한다** — 「artificial key(인공키; 대리키)」라는 이름과 `auto_increment` 라는 발급기가 함께 온다 → [[db-normalization]] · [[primary-key]]

## 경계와 오해

- **식별 번호 ≠ 목록 번호 ≠ 인덱스** — 세 개가 다 「숫자 하나」로 보이고 값도 처음에는 겹친다(회원 셋을 등록하면 1·2·3 이 세 체계에서 다 같다). **삭제를 한 번 하는 순간에만 갈린다.** 그래서 지우기 전까지는 어느 것을 쓰고 있었는지 코드만 보고 알 수 없다 → [[one-based-numbering]]
- **`getSeqNo()` 는 getter 가 아니다** — 부를 때마다 다른 값을 주고, 부른 것 자체가 카운터를 올린다. 이름이 getter 처럼 생겨서 「그냥 읽는 것」으로 읽히지만 **번호를 발급하는 명령**이다. 필기 자신이 「클래스 분리하기」 절에서 `getNextSeqNo()` 로 바꿔 부른 것이 그 인식이다 → [[read-side-effect]]
- **번호는 유일하지만 연속이 아니다** — 카운터는 삭제해도 되돌지 않으므로 2번을 지우면 목록이 1·3·4 가 된다. 「번호가 빠졌다」로 보이지만 **그게 목적**이다. 빈 번호를 메우려고 카운터를 되돌리면 지운 번호가 다시 나와 옛 번호와 새 번호가 겹친다.
- **「고유 번호」가 전역 유일은 아니다** — `seqNo` 가 `User`·`Board`·`Project` 에 **각각** 있으므로 1번 회원과 1번 게시글이 동시에 존재한다. 유일한 범위는 **클래스 하나**다. 필기의 「회원, 프로젝트, 게시글에 대한 고유 번호」를 전역으로 읽으면 어긋난다 → [[static-member]]
- **번호를 밖에서 넣는다** — `user.setNo(User.getSeqNo())` 를 부르는 것은 `addUser` 다. 그 한 줄을 빠뜨린 등록은 `no` 가 `0` 인 회원을 만들고, `0` 은 아무 번호와도 맞지 않아 **조회·변경·삭제가 전부 「없는 회원입니다」로 답한다.** 생성자에서 발급했다면 잊을 수 있는 단계가 아예 없었다 → [[constructor]] · [[default-initialization]]
- **번호가 열려 있다** — `setNo` 가 `public` 이므로 밖에서 아무 번호나 다시 넣을 수 있고, 그러면 같은 번호를 가진 회원이 둘 생겨 `findByNo` 가 앞의 것만 돌려준다. 식별자는 한 번 정해지면 안 바뀌어야 하는 값인데 여느 필드와 같은 setter 를 받았다 → [[encapsulation]]
- **번호도 휘발한다 — 4주 뒤에 파일로 남지만 카운터는 따로 손봐야 한다** — Day19 시점의 저장소는 `static` 배열이므로 프로그램을 끄면 데이터와 카운터가 함께 사라지고 다음 실행은 다시 1번부터다. **Day38 이 회원 정보를 파일에 적으면서 그 한계가 풀린다.** 그런데 `no` 필드를 저장해도 **`seqNo` 는 따라오지 않는다** — 발급기는 `static` 이라 어느 인스턴스의 필드도 아니고, 직렬화는 인스턴스의 필드만 훑는다. 그래서 로드 마지막에 한 줄이 따로 있다.

  ```java
        maxUserNum = Math.max(maxUserNum, user.getNo());
        /* ... 루프 끝 ... */
        User.initSeqNo(maxUserNum);
  ```

  **이 줄이 없으면 다음 등록이 1번을 다시 발급한다** — 파일에서 읽어 온 1번 회원과 새 1번 회원이 함께 존재하고, `findByNo(1)` 이 앞의 것만 돌려주므로 뒤에 등록한 회원은 조회·변경·삭제가 전부 「없는 회원입니다」로 답한다. **「번호를 저장했다」와 「번호 체계를 복원했다」가 다른 일**이라는 것이 이 한 줄에 들어 있다 → [[static-member]] · [[serialization]]
- **카운터를 「세는 것」과 「저장하는 것」이 다르고, 세면 지운 번호가 되살아난다** — `initSeqNo` 에 넘기는 값은 **남아 있는 회원의 최댓값**이다. 5번까지 발급한 뒤 5번 회원을 지우고 저장하면 파일의 최댓값이 4가 되고, 다음 실행에서 카운터가 4로 복원되어 **새 회원이 5번을 다시 받는다.** 위의 「번호는 유일하지만 연속이 아니다」가 **그게 목적**이라고 적은 성질이 **파일 왕복을 한 번 거치면 깨진다** — 지운 번호가 다시 나오고, 그 번호를 적어 둔 다른 기록이 있다면 엉뚱한 회원을 가리킨다. 카운터 자체를 파일에 적었다면 유지됐다. **예외도 경고도 없고, 지운 뒤 재시작해야만 드러난다** → [[serialization]]
- **7주 뒤 Day51 의 `auto_increment` 가 이 필드 둘을 대신한다 — 그리고 위의 카운터 버그를 DB 도 갖고 있었다** — Day51 의 「자동 증가」 절 세 줄이 이 노트의 성질과 그대로 겹친다. 「숫자 타입의 PK 컬럼 또는 Unique 컬럼」은 발급 대상이 식별자여야 한다는 것이고, 「삭제를 통해 중간에 비어있는 번호는 다시 채우지 않는다」는 위의 「유일하지만 연속이 아니다」이며, **「한 테이블 당 하나만 지정 가능하다」는 발급기가 `static` 이라 클래스당 하나였던 것과 같은 제약**이다. 놀라운 것은 세 번째 줄 다음이다 — **MySQL 8.0 이전의 InnoDB 는 자동 증가 카운터를 메모리에만 두고 재시작할 때 `MAX(컬럼) + 1` 로 다시 계산했다.** 즉 마지막 번호의 행을 지우고 재시작하면 그 번호가 다시 발급되어, 바로 위 항목에 적은 Day38 의 `initSeqNo(maxUserNum)` 버그와 **원인·증상이 같다.** MySQL 8.0 이 그 값을 디스크에 남기도록 바꾸어 고쳤고 해법도 같다 — **세지 말고 저장한다** → [[primary-key]] · [[ddl]]
- **대리키(surrogate key) ≠ 대체키(alternate key)** — 이 노트가 `대체키` 를 별칭으로 들고 있어 `[[대체키]]` 가 여기로 풀리지만, **DB 용어의 alternate key 는 다른 것**이다. alternate key 는 **기본키가 되지 못한 후보키**, 즉 원래 있던 컬럼이고, surrogate key 는 **쓸 만한 후보키가 없어서 새로 만든 컬럼**이다. Day51 이 둘을 같은 절에 나란히 적어 두었고 우리말 번역이 「대체」와 「대리」로 한 글자만 달라서, 이 노트를 찾을 때는 그 구별을 함께 기억해야 한다 → [[primary-key]]
- **필기 「데이터 클래스에 seqNo 적용」 절의 예시는 `static` 이 아니다** — `public int getSeqNo()` 로 적혀 있어 인스턴스를 통해서만 부를 수 있고 `User.getSeqNo()` 형태가 성립하지 않는다. 같은 노트의 `User` 클래스에서는 `public static int getSeqNo()` 로 고쳐졌다.
- **필기 안에서 발급 메서드 이름이 갈렸다** — 「Command 클래스 파일 수정」 절은 `User.getSeqNo()`, 「클래스 분리하기」 절은 `User.getNextSeqNo()` 다. 뒤쪽 이름은 정의된 적이 없으므로 그대로는 컴파일되지 않는다. 이름이 더 정확해지는 쪽으로 움직였는데 **정의를 같이 고치지 않아 두 절이 어긋났다.**
- **필기 「데이터 클래스에 seqNo 적용」 절의 예시 클래스 이름이 `Object` 다** — `java.lang.Object` 와 같은 이름이라 그 파일 안에서는 진짜 `Object` 를 가리킬 수 없게 된다(같은 패키지에 두면 자동 import 를 덮는다). 「데이터 클래스 일반」을 뜻하려고 고른 이름인데, 자바에서 가장 쓰면 안 되는 이름을 골랐다 → [[class]]
- **필기 「데이터 클래스에 seqNo 적용」 절 예시의 `setNo`·`getNo` 는 반환 타입이 없다** — `public setNo(int no)` · `public getNo()` 로 적혀 있다. 자바에서 타입을 생략할 수 있는 것은 생성자뿐이다. `User` 클래스 쪽에는 `void`·`int` 가 붙어 있다.
- **`Board`·`Project` 라고 이름 붙은 코드 블록이 둘 다 `public class User` 다** — 「Board class. Project class 도 동일하다」고 적고 `User` 코드를 세 번 붙인 흔적이다. 셋이 **각자의 `seqNo` 를 갖는다**는 것이 이 절의 요점인데, 복사된 코드만 보면 그것이 드러나지 않는다. 세 블록 모두 끝에 닫는 중괄호가 하나 더 있는 것도 같은 복사에서 왔다.

## 출처

- [[2024-06-20-Day19]] — 「배열 중간에 인스턴스를 삭제하여도 고유번호 유지」를 목표로 `private static int seqNo` 와 `private int no` 를 데이터 클래스에 넣고, `user.setNo(User.getSeqNo())` 로 등록할 때 번호를 발급했다. 그 결과 목록의 `i + 1` 이 `getNo()` 로, 조회의 범위 검사가 `findByNo` 탐색으로, 삭제의 루프 시작값이 `indexOf` 로 바뀌는 것까지 한 회차에 이어졌다
- [[2024-07-18-Day38]] — **이 번호가 처음 파일에 적힌다.** `User.getBytes()` 가 `no` 를 4바이트 고정으로 맨 앞에 쓰고 `valueOf` 가 `setNo` 로 되돌리므로 「번호가 안정적인 범위는 한 번의 실행 안」이 풀린다. 그런데 발급기 `seqNo` 는 `static` 이라 직렬화에 따라오지 않아, `loadUser` 가 읽으면서 `Math.max` 로 최댓값을 모아 `User.initSeqNo(maxUserNum)` 로 카운터를 복원한다 — **필드 복원과 번호 체계 복원이 다른 일**임을 보여 주는 한 줄이다. 다만 그 값이 **남아 있는 회원의 최댓값**이라 마지막 회원을 지우고 재시작하면 그 번호가 다시 발급되고, Day19 가 이 번호 체계의 성질로 적은 「지운 번호는 다시 나오지 않는다」가 파일 왕복 한 번에 깨진다
- [[2024-08-06-Day51]] — **이 번호에 DB 의 이름이 붙는다.** 「artificial key : (인공키; surrogate key(대리키))」를 「Primary key 로 사용하기에 적절한 컬럼을 찾을 수 없는 경우 새로운 구분자를 Key 로 column 에 추가한다」로 정의하고, 게시글(제목·내용·작성자·등록일·조회수)에 게시글 번호를 더하는 것을 예로 들었다 — Day19 가 손으로 만든 `seqNo` 가 그것이다. 발급기 쪽도 문법이 되어 「숫자 타입의 PK 또는 Unique 컬럼은 값을 1씩 자동 증가」·「삭제로 비어 있는 번호는 다시 채우지 않는다」·「한 테이블 당 하나만 지정 가능」 세 줄로 정리되고, `alter table ... modify column 컬럼명 int not null auto_increment` 로 나중에 붙이는 형태까지 나온다. 같은 절이 alternate key(대체키)를 인공키 바로 위에 나란히 적어 두어, 이 노트의 별칭과 겹치는 자리도 여기서 생긴다
