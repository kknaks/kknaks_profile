# 인터페이스 분리 원칙 (ISP)

**약속을 「누가 쓸 것인가」 기준으로 자르는 것.** 필기의 두 줄이 「특정 클라이언트를 위한 인터페이스 여러 개가 범용 인터페이스 하나보다 낫다 / 클라이언트가 자신이 사용하지 않는 메서드에 의존하지 않도록 인터페이스를 분리해야 한다」다. **자르는 기준이 구현하는 쪽이 아니라 부르는 쪽**이라는 것이 이 원칙의 전부다.

## 정의

「의존하지 않도록」의 의미가 두 방향이다.

| 누가 | 쓰지 않는 메서드가 있으면 |
|---|---|
| **부르는 쪽**(클라이언트) | 안 쓰는 메서드가 바뀌어도 다시 컴파일·다시 확인해야 한다 |
| **구현하는 쪽** | 쓸모없는 메서드를 억지로 채워야 한다(빈 몸통·`UnsupportedOperationException`) |

원칙의 문장은 앞쪽만 말하지만 이 회차의 예제는 **뒤쪽으로 걸린다** — 「Switch로 제어안해도 되는 코드도 강제로 사용해야한다」.

분리한 뒤에는 클래스 하나가 **여러 약속을 동시에 지킬 수 있다.** `implements` 가 여러 개 붙는다는 성질이 이 원칙을 실행 가능하게 만드는 문법이고, 그래서 ISP 는 인터페이스에 대한 원칙이지 상속에 대한 원칙이 아니다 → [[interface]] · [[multiple-inheritance]]

## 사용 예시

램프/스위치 예제의 3단계가 위반이고 4단계가 그 수정이다.

**3단계** — 램프뿐 아니라 선풍기까지 한 스위치로 제어하려고 **더 높은 상위 클래스**를 만들었다.

* 「더 높은 수준의 상위클래스로 상속받으면 Switch로 제어가능」
* 「상속의 클래스가 복잡해진다.」
* 「Switch로 제어안해도 되는 코드도 강제로 사용해야한다.」
* 「**Interface Segregation Principle을 충족시키지 못한다.**」

한 타입에 램프의 밝기 조절과 선풍기의 풍량 조절이 함께 올라가면, **스위치는 켜고 끄는 것만 필요한데 그 전부를 아는 타입으로 받는다.**

**4단계** — 「Switch클래스에서 사용할 Interface를 생성한다 / 제품군(Lamp, Fan)별 세부기능 가진 자식클래스를 생성하고 인터페이스를 구현한다」.

```text
3단계:  Switch ──▶ Appliance (on/off + 밝기 + 풍량 + …)
                      ▲            ▲
                    Lamp          Fan

4단계:  Switch ──▶ Switchable (on/off 뿐)
                      ▲            ▲
                    Lamp          Fan      ← 세부 기능은 각자 갖는다
```

**바뀐 것은 클래스가 아니라 「스위치가 아는 타입의 크기」다.** 램프는 여전히 밝기 조절을 갖고 있고, 스위치만 그것을 모르게 되었다 → [[dependency-inversion-principle]]

## 왜 중요한가

**안 쓰는 메서드도 의존이다.** 큰 인터페이스를 받으면 그 안의 아무 메서드 하나가 바뀔 때 부르는 쪽이 다시 컴파일되고 다시 확인 대상이 된다. **부르지도 않는 것 때문에 영향을 받는 것**이고, 이것이 「사용하지 않는 메서드에 의존하지 않도록」의 실제 내용이다 → [[coupling]]

**그리고 구현하는 쪽에 거짓말을 강요하지 않는다.** 약속이 크면 그것을 지킬 수 없는 클래스가 빈 몸통이나 예외로 자리를 메운다. 그러면 그 타입으로 받은 코드가 「이 메서드는 있다」를 믿고 부르는데 실제로는 아무 일도 일어나지 않고, **컴파일은 되고 동작만 틀리는** 상태가 된다 — 나흘 앞 회차에서 `MergeSort` 가 `sort` 를 재정의하지 않은 채 부모의 빈 몸통을 실행시킨 것과 같은 종류의 실패다 → [[abstract-class]] · [[polymorphism]]

**작게 자른 약속은 관계없는 클래스끼리도 묶는다.** `Switchable` 이 `on()`·`off()` 두 개뿐이면 램프도 선풍기도 문도 그것을 지킬 수 있다. 큰 인터페이스는 그 반대로, **한 제품군의 사정이 이름 안에 들어와** 다른 것이 들어오지 못하게 만든다.

## 경계와 오해

- **ISP ≠ SRP** — 「하나만 하게 쪼갠다」가 닮았지만 쪼개는 대상과 기준이 다르다. SRP 는 **클래스**를 「변경 이유」로 쪼개고, ISP 는 **인터페이스**를 「클라이언트」로 쪼갠다. 그래서 ISP 를 지키면 **한 클래스가 여러 인터페이스를 구현**하게 되지 클래스가 늘지 않는다 — 오히려 SRP 와 반대 방향으로 움직이는 자리가 있다 → [[solid-principles]] · [[cohesion]]
- **필기가 두 번 「ICP」로 적었다** — 4단계 제목이 「ICP(Interface Segregation Principle) 전환」이고 5단계 첫 줄이 「ICP를 충족하는 인터페이스를 생성한다」다. 풀어 쓴 이름은 맞으므로 머리글자 오기이며, **바른 것은 ISP** 다. `I` 다음이 `C` 가 아닌 이유가 원칙의 내용이기도 하다 — Segregation(분리)이 이 원칙이 하는 일이고 Cohesion·Composition 은 다른 개념이다.
- **인터페이스 개수가 늘어난다는 것이 대가다** — 클라이언트가 넷이면 인터페이스도 넷일 수 있고, 그러면 한 클래스의 선언부가 `implements A, B, C, D` 로 길어진다. 「그 클래스가 무슨 약속을 지키나」가 한눈에 안 들어오는 상태와 「부르는 쪽이 안 쓰는 것을 안다」 사이의 저울이며, **작을수록 좋다는 규칙이 아니다** → [[interface]]
- **같은 노트가 ISP 를 배우고 나서 곧바로 위반한다** — 뒤쪽 절에서 메뉴 경로를 추적하기 위해 `Command` 인터페이스를 이렇게 바꾼다.

  ```java
  public interface Command {
    void execute(Stack menuPath);
  }
  ```

  **`HelpCommand` 는 `menuPath` 를 쓰지 않는다.**

  ```java
  public class HelpCommand implements Command {
    public void execute(Stack menuPath) {
        System.out.println("도움말입니다!");
    }
  }
  ```

  `HistoryCommand` 도 같고, 그쪽은 매개변수 이름을 `menuTitle` 로 잘못 붙여 두었다. 서브메뉴가 없는 명령에게 **필요 없는 인자가 시그니처로 강제된 것**이고, 정확히 「자신이 사용하지 않는 메서드(인자)에 의존한다」다. 그리고 이 한 줄을 바꾸느라 **구현 클래스 전부와 `AbstractCommand`·`App` 을 같이 고쳤다** — 큰 약속을 고칠 때 파급이 어디까지 가는지를 같은 노트가 실물로 보여 준다 → [[open-closed-principle]] · [[template-method-pattern]]
- **`Stack extends LinkedList` 도 같은 위반이다** — 스택을 연결 리스트를 상속해 만들면 `add`·`remove(int)`·`get(int)`·`indexOf` 가 전부 함께 딸려 온다. 스택을 쓰는 쪽에는 `push`·`pop`·`isEmpty` 만 있어야 하는데 목록의 아무 자리나 만질 수 있게 열려 있다. **인터페이스를 안 만들고 상속으로 자료구조를 만들면 ISP 를 지킬 방법이 없다** — 물려받는 것을 골라서 받을 수 없기 때문이다 → [[stack]] · [[inheritance]]
- **분리한 인터페이스를 클라이언트가 소유하는 것이 자연스럽다** — 4단계의 인터페이스 이름을 필기가 「Switch클래스에서 사용할 Interface」로 적었다. 이름을 램프 쪽 사정으로 정하면(`LampFunctions`) 다시 커지고, 쓰는 쪽 사정으로 정하면(`Switchable`) 작게 유지된다. **ISP 는 「무엇을 자를까」가 아니라 「누구 이름으로 자를까」의 문제**이며, 그래서 DIP 의 「고수준이 인터페이스를 소유한다」와 같은 자리에서 만난다 → [[dependency-inversion-principle]]
- **원칙을 지켰는지가 인터페이스 크기로 판정되지 않는다** — 메서드 여섯 개짜리 인터페이스도 그 여섯 개를 다 쓰는 클라이언트만 있으면 위반이 아니다. 13일 앞선 회차의 `List` 가 그 예에 가깝다 — `add`·`remove`·`get`·`toArray`·`indexOf`·`size` 여섯 개는 목록을 쓰는 쪽이 대개 다 쓴다. **세는 것은 메서드가 아니라 「안 쓰는 메서드를 가진 클라이언트」다** → [[interface]]
