# 와일드카드 타입 (`<?>` · `? extends` · `? super`)

**타입 인자 자리에 「무엇이든」·「이것 아래」·「이것 위」를 적는 문법.** 있어야 하는 이유는 하나다 — **제네릭은 상속을 타고 넘어가지 않는다.** `String` 이 `Object` 의 하위 타입인데도 `Box<String>` 은 `Box<Object>` 의 하위 타입이 아니고, 그 벽 때문에 「어떤 상자든 받는 코드」를 쓸 수 없다. 와일드카드가 그 벽에 문을 낸다 → [[generics]]

## 정의

Day40 은 이 성질을 상속 계층 하나로 보여 준다.

```java
  static class A {}
  static class B1 extends A {}
  static class B2 extends A {}
  static class C extends B1 {}

  static class Box<T> {
    void set(T obj) {}
  }
```

| 선언 | 대입할 수 있는 것 | 필기의 표현 |
|---|---|---|
| `Box<B1>` | `new Box<B1>()` **하나뿐** | 「B1만 가능」 |
| `Box<? extends B1>` | `new Box<B1>()` · `new Box<C>()` | 「B1 아래는 다 가능」 |
| `Box<? super B1>` | `new Box<B1>()` · `new Box<A>()` · `new Box<Object>()` | 「B1 위는 다 가능」 |
| `Box<?>` | 전부 | 「모든 타입에 대한 객체를 생성할 수 있으나…」 |

**`extends`·`super` 는 자기 자신을 포함한다** — 「아래」·「위」라는 말이 자기 제외로 읽히기 쉬운 자리다.

그리고 필기가 멈춘 곳에 나머지 절반이 있다. **무엇을 대입할 수 있는지가 정해지면 무엇을 부를 수 있는지도 같이 정해진다.**

| 선언 | `set(...)` 호출 | `get()` 의 반환 타입 |
|---|---|---|
| `Box<B1>` | `set(B1)` · `set(C)` | `B1` |
| `Box<? extends B1>` | **불가능** (`null` 만) | `B1` |
| `Box<? super B1>` | `set(B1)` · `set(C)` | `Object` |
| `Box<?>` | **불가능** (`null` 만) | `Object` |

읽는 규칙이 **PECS** 다 — *Producer Extends, Consumer Super*. **꺼내 쓰려면 `extends`, 넣으려면 `super`.** 이유는 대칭이다.

- `Box<? extends B1>` 은 실제로 `Box<C>` 일 수 있다 → `set(new B1())` 을 허용하면 `C` 상자에 `B1` 이 들어간다 → 그래서 **막는다.** 대신 꺼내면 최소한 `B1` 이다.
- `Box<? super B1>` 은 실제로 `Box<Object>` 일 수 있다 → `set(new B1())` 은 **언제나 안전하다**(`B1` 은 `Object` 이기도 하다). 대신 꺼낸 것이 무엇인지는 `Object` 까지만 보장된다.

## 사용 예시

필기의 `<?>` 절이 두 규칙을 한 화면에 놓는다 — **대입은 전부 되고 `add` 는 전부 막힌다.**

```java
    // 레퍼런스를 선언할 때 제네릭 타입을 <?> 로 선언하면
    // 객체 생성시 어떤 제네릭 타입을 지정하더라도 상관없다.
    ArrayList<?> list2;
    list2 = new ArrayList<Member>(); // OK

    //=> add() 메서드의 파라미터 타입은 ? 가 된다.
    list2.add(new String()); // 컴파일 오류!
    list2.add(new Integer(100)); // 컴파일 오류!
    list2.add(new java.util.Date()); // 컴파일 오류!
    list2.add(new Member("홍길동", 20)); // 컴파일 오류!
```

**「무엇인지 모른다」는 것이 「아무것도 넣을 수 없다」로 이어진다.** 무엇을 넣어야 맞는지 컴파일러가 확정할 수 없으면 답은 거부다 → [[raw-type]]

그리고 같은 필기가 **`<?>` 가 실제로 쓰이는 자리**를 앞 章에서 이미 지나갔다.

```text
Save 코드수정하기
  1. Gson을 새로 인스턴스한다.
  2. toJson(List<?>)을 호출한다.
```

**넘기는 쪽에서 `List<Board>`·`List<User>`·`List<Project>` 를 전부 받아야 하니 `List<?>` 다.** 꺼내서 문자열로 만들기만 하므로(Producer) 넣을 필요가 없고, 그래서 `<?>` 로 충분하다 → [[json]]

## 왜 중요한가

**「어떤 목록이든 받는 메서드」를 타입 안전하게 쓸 수 있다.** 와일드카드가 없다면 선택은 둘뿐이다 — 타입마다 메서드를 복사하거나, `List` 로 받아(raw) 검사를 전부 포기하거나. 세 번째 길이 이 문법이다 → [[raw-type]]

**호출부에 무엇을 허용할지 시그니처 한 줄로 정해진다.** `void print(List<? extends Number>)` 는 「읽기만 한다」를 타입으로 선언한 것이고, 안에서 `add` 를 부르면 **구현자가 컴파일 오류를 본다.** 주석으로 「이 리스트를 수정하지 마세요」라고 쓰는 것과 문법으로 막는 것의 차이다 → [[interface]] · [[immutability]]

**제네릭이 상속과 다르게 동작하는 이유를 알게 된다.** `Box<String>` 을 `Box<Object>` 로 못 쓰는 것을 「자바의 불편함」으로 넘기면 와일드카드가 왜 있는지 끝까지 모른다. 그 제약이 **배열이 겪는 실행 시점 실패를 컴파일 시점으로 옮겨 놓은 결과**라는 것이 아래 첫 항목이다 → [[polymorphism]]

## 경계와 오해

- **`Box<String>` ≠ `Box<Object>` — 허용했다면 무엇이 깨지는지가 답이다** — `Box<Object> b = box;` 를 허용하면 `b.set(new Integer(1))` 이 통과하고, **`Box<String>` 안에 `Integer` 가 들어간다.** 꺼내는 쪽은 `String` 을 기대하므로 `ClassCastException` 이 실행 중에 난다. 즉 제네릭의 이 「불편함」은 **바로 그 사고를 막는 값**이다. 배열은 반대로 `Object[] arr = new String[10];` 을 허용하고, 대신 `arr[0] = 1;` 에서 **실행 시점에** `ArrayStoreException` 을 던진다 — **같은 문제에 대해 배열은 실행 시점 실패를, 제네릭은 컴파일 거부를 골랐다** → [[array]] · [[type-erasure]]
- **「와일드카드는 파라미터 타입으로 사용할 수 없다」는 오해다 — 같은 필기가 다음 장에서 스스로 반증한다** — 필기의 문장은 「레퍼런스를 와이드카드(?)로 선언되면 … 파라미터 타입으로는 사용 할 수 없다」인데, 실제로 막히는 것은 **`add(?)` 의 인수 자리에 값을 넘기는 것**이다. **메서드 매개변수를 `List<?>` 로 선언하는 것은 표준 관용구**이고 — 같은 필기가 앞 章에서 「`toJson(List<?>)` 을 호출한다」로 적었다 — 「어떤 원소 타입이든 받아 읽기만 한다」를 뜻한다. **「선언에 못 쓴다」와 「값을 못 넘긴다」를 가르지 않으면 `<?>` 를 아예 쓸 수 없는 문법으로 오해하게 된다.**
- **`<?>` 에는 `null` 은 넣을 수 있다** — `list2.add(null)` 만 통과한다. `null` 은 모든 참조 타입에 맞기 때문이다. 실용성은 없지만 **「전부 막힌다」가 아니라 「타입을 확정할 수 없는 것이 막힌다」**라는 규칙을 확인하는 자리다 → [[object-reference]]
- **`<?>` ≠ raw type — 정반대로 위험하다** — `ArrayList list`(raw)는 `add` 가 **전부 통과**하고 `ArrayList<?> list` 는 **전부 거부**한다. 필기가 두 절을 나란히 놓았는데 「둘 다 타입을 안 적은 것」으로 뭉치면 정확히 거꾸로 이해한다. **raw 는 검사를 포기한 것이고 `<?>` 는 모른다는 것을 타입으로 적은 것** → [[raw-type]]
- **`? extends` 는 타입 파라미터 자리에 못 쓴다 — 필기의 「T = ? extends B1 일때」는 표기가 어긋났다** — `?` 는 **타입 인자 자리**(`Box<? extends B1> box`)에만 쓰고, 선언 자리에는 `class Box<T extends A>` 나 `<T extends A> void m(...)` 처럼 **이름 있는 파라미터에 상한**을 준다. 필기는 둘을 「T의 상속옵션」이라는 한 이름으로 부르는데, 실제로는 **누가 정하는가**가 다르다 — 상한은 **클래스·메서드를 만드는 쪽**이 정하고, 와일드카드는 **쓰는 쪽이 참조를 선언하며** 정한다.
- **`new Box<?>()` 는 만들 수 없다** — 와일드카드는 **참조를 선언할 때만** 쓴다. 무엇을 만들지 정하지 않고 만들 수는 없기 때문이고, 그래서 필기의 예시가 전부 「선언은 `?`, 생성은 구체 타입」의 형태다 → [[instance]]
- **`Box<? extends B1>` 에서 꺼낸 것을 다시 넣을 수도 없다** — `B1 b = box.get(); box.set(b);` 조차 거부된다. 안쪽이 `Box<C>` 일 수 있으므로 `B1` 을 넣는 것이 안전하지 않다. **같은 상자에서 꺼낸 것이니 괜찮다는 직관이 타입 시스템에는 없다** — 컴파일러가 아는 것은 선언뿐이다.
- **와일드카드 두 개는 서로 같다는 보장이 없다** — `void copy(List<?> a, List<?> b)` 의 두 `?` 는 별개다. 「둘이 같은 타입」을 요구하려면 이름 있는 타입 파라미터(`<T> void copy(List<T> a, List<T> b)`)여야 한다. Day40 의 `loadJson(List<E> list, ..., Class<E> elementType)` 이 `E` 를 쓴 이유가 정확히 이것이다 → [[generics]]
- **상한이 있으면 소거도 그 상한으로 된다** — `<T extends B1>` 의 `T` 는 실행 시점에 `Object` 가 아니라 `B1` 으로 지워진다. 그래서 상한을 주면 **캐스팅 없이 `B1` 의 메서드를 부를 수 있다** — 와일드카드·상한이 문법 장식이 아니라 컴파일 결과를 바꾸는 자리다 → [[type-erasure]]
- **필기의 `Box<Member> box3` 는 그 코드 조각에 `Member` 클래스가 없다** — 앞뒤 예시에서 쓰던 클래스를 가져온 것이고, 그 조각만 떼어 컴파일하면 오류다. 내용의 오류는 아니다.
