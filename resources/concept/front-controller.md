# 프론트 컨트롤러 (Front Controller)

**모든 요청을 하나의 진입점이 먼저 받고, 거기서 알맞은 처리기로 나눠 주는 배치.** 요청마다 서블릿을 하나씩 두던 것을 뒤집는다.

## 정의

특징이 넷이고 서로 물려 있다.

1. **단일 진입점** — 클라이언트의 모든 요청이 한 곳을 통과한다
2. **공통 처리 로직** — 인증·권한 검증·로깅처럼 **모든 요청에 공통인 일**을 여기서 먼저 한다
3. **처리기 분배** — 요청을 분석해 알맞은 컨트롤러로 넘긴다
4. **유지보수성** — 공통 코드가 한 곳이라 중복이 줄고, 새 요청 유형이 늘어도 고칠 자리가 좁다

**1 이 있어야 2 가 성립한다.** 진입점이 여럿이면 「모든 요청에 대해」라는 말 자체가 성립하지 않는다 — 새로 만든 서블릿에 인증 코드를 빠뜨리면 그 하나만 뚫린다.

얻는 것과 내는 것.

| 얻는 것 | 내는 것 |
|---|---|
| 요청 처리가 일관된다 | 초기 설정이 복잡하다 |
| 사전 처리(인증·권한)를 쉽게 끼운다 | 모든 요청이 한 곳을 지나 **병목 가능성** |
| 중복 코드가 줄어든다 | |

자바 웹에서는 [[servlet]] 하나가 이 역할을 맡고, 스프링에서는 `DispatcherServlet` 이 그 자리다.

## 사용 예시

앞 회차들의 배치와 비교하면 차이가 분명하다.

```
Day63~74 — 요청마다 서블릿 하나
  /board/list   → BoardListServlet
  /board/add    → BoardAddServlet
  /user/list    → UserListServlet
```

```
Day75 — 진입점 하나
  /app/*  →  FrontController
               ├ 공통 처리(인증·인코딩·로깅)
               └ 경로를 보고 분배 → BoardListHandler / UserListHandler / ...
```

앞의 배치에서는 인증을 넣으려면 **서블릿을 전부 열어야** 하고, 뒤의 배치에서는 진입점 한 곳만 고친다.

## 왜 중요한가

**「모든 요청」이라는 말을 코드로 보증할 수 있게 된다.** 인증·인코딩·로깅은 하나라도 빠지면 의미가 없는 종류의 일인데, 진입점이 흩어져 있으면 그 보증을 사람의 주의력에 맡기게 된다 → [[servlet-filter]]

그리고 **URL 과 클래스의 결합이 끊어진다.** `@WebServlet("/board/list")` 로 매핑하면 주소를 바꿀 때 클래스를 열어야 하지만, 진입점이 경로를 읽어 분배하면 그 대응표가 한 곳에 모인다 — 나중에 그 표가 설정이 되고, 애노테이션이 되고, 결국 스프링의 요청 매핑이 된다 → [[dispatch-table]] · [[annotation]]

이 회차의 [[service-layer]] 분리와 방향이 같다. **역할이 뒤섞인 서블릿에서 하나씩 떼어 내는 것**이고, 프론트 컨트롤러는 그중 「흐름 제어」를 떼어 낸 결과다 → [[mvc-pattern]]

## 경계와 오해

- **필기의 「이 역할을 `Request Dispatcher` 라고도 한다」는 이름이 겹쳐 오해를 만든다** — 여기서 말하는 것은 **요청을 알맞은 처리기로 분배하는 역할**이고, 자바의 `RequestDispatcher` 는 **다른 서블릿/JSP 로 실행을 넘기는 API** 다. 프론트 컨트롤러가 분배할 때 그 API 를 **쓸 수는 있지만**, 역할 이름과 클래스 이름이 같은 것이 아니다 → [[request-dispatcher]]
- **「병목 가능성」은 대체로 성립하지 않는다** — 진입점이 하나라는 것은 **클래스가 하나**라는 뜻이지 **쓰레드가 하나**라는 뜻이 아니다. 서블릿은 요청마다 쓰레드에서 동시에 도므로 코드를 지나는 것 자체는 병목이 아니다. **다만 그 클래스에 상태를 두면** 모든 요청이 같은 필드를 만져 진짜 병목(그리고 버그)이 된다 → [[thread]] · [[servlet-lifecycle]]
- **프론트 컨트롤러 ≠ MVC** — [[mvc-pattern]] 은 역할을 셋으로 가르는 것이고, 이것은 **컨트롤러로 들어오는 문을 하나로 만드는 것**이다. MVC2 를 쓰면서 컨트롤러 서블릿을 여러 개 둘 수도 있다. 필기가 「주로 MVC 에서 사용된다」고 적은 관계가 그것이다
- **분배 대상이 여전히 필요하다** — 진입점 하나로 모든 처리를 하면 그 클래스가 거대해진다. 프론트 컨트롤러는 **받아서 넘기는** 것까지이고, 실제 처리는 요청별 처리기가 갖는다. 「서블릿 여러 개」가 「if-else 여러 개」로 옮겨 갔을 뿐이면 얻은 것이 없다 → [[cohesion]] · [[dispatch-table]]
- **공통 처리를 넣는 자리가 여기만 있는 것은 아니다** — 서블릿 필터도 모든 요청을 가로챈다. 필터는 컨테이너가 제공하는 장치이고 프론트 컨트롤러는 애플리케이션이 만든 것이라, **인코딩처럼 컨테이너 수준의 일은 필터가 더 맞다** → [[servlet-filter]]
- **「작은 수정만 하면 된다」가 열려 있음을 뜻하지는 않는다** — 새 요청 유형마다 진입점을 고쳐야 한다면 그 클래스는 **확장할 때마다 열리는** 자리다. 분배를 표나 규칙으로 바꿔야 고치지 않고 늘릴 수 있다 → [[open-closed-principle]]
