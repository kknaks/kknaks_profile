# TCP (Transmission Control Protocol)

**바이트를 보낸 순서대로, 빠짐없이 상대에게 넘겨 주는 전송 프로토콜.** Day46 의 정의가 「Transmission Control Protocol은 연결형 프로토콜로 상대방이 연결된 상태에서 데이터를 송수신한다」다. [[socket]] 으로 쓰던 통로의 **아래 층에 이름이 붙는 자리**다.

## 정의

Day46 은 프로토콜을 두 층으로 가른다. 「IP주소로 프로그램들이 통신할 때는 약속된 데이터 전송 규약을 사용한다」 — 이 규약이 **전송용 프로토콜**이고 TCP 와 UDP 둘이 있다.

| 층 | 정하는 것 | 누가 주나 |
|---|---|---|
| 전송 프로토콜 (TCP·UDP) | 바이트가 **어떻게** 건너가는가 — 순서·손실·연결 | 라이브러리·OS 가 이미 만들어 준다 |
| 애플리케이션 프로토콜 | **무엇을** 보내는가 — 누가 먼저, 어디까지가 한 메시지 | 사람이 정해야 한다 → [[network-protocol]] |

TCP 가 주는 것은 셋이다.

1. **연결** — 「클라이언트가 연결을 요처하고 서버가 연결을 수락하면」 그 뒤로 상대를 매번 지정하지 않는다. 주소는 연결을 만들 때 한 번만 쓴다.
2. **순서** — 보낸 순서와 읽히는 순서가 같다.
3. **빠짐없음** — 중간에 사라진 것은 다시 보내진다.

Day46 은 이 셋의 근거를 「통신 회선이 고정되고」·「고정된 회선을 사용하기 때문에」로 적었다. **셋이 성립하는 것은 맞고 이유는 틀렸다** — 아래 「경계와 오해」의 첫 두 항목이다.

## 사용 예시

TCP 를 고르는 자리는 따로 없다. **어느 클래스를 쓰는가가 곧 프로토콜 선택**이다.

```java
// 서버 — 받을 자리를 만들고 기다린다
ServerSocket serverSocket = new ServerSocket("Port번호");
Socket socket = serverSocket.accept();

// 클라이언트 — 찾아가 붙는다
Socket socket = new Socket("IP","Port");
```

`ServerSocket`·`Socket` 이 TCP 전용이고, UDP 는 `DatagramSocket`·`DatagramPacket` 이라는 **다른 클래스 짝**이다. 그래서 TCP 를 UDP 로 바꾸는 일이 설정 한 줄이 아니라 **코드를 다시 쓰는 일**이 된다 — 보내는 단위가 스트림에서 패킷으로 바뀌고, `accept()` 처럼 연결을 받는 단계가 아예 없어진다.

Day46 의 두 줄은 문자열 자리가 잘못돼 있어 그대로는 컴파일되지 않는다 → [[socket-binding]]

## 왜 중요한가

**「데이터가 깨져서 오면 어쩌나」를 코드에서 지운다.** 순서·재전송을 TCP 가 맡으므로 애플리케이션은 순서 번호를 붙이거나 빠진 것을 확인하지 않는다. 지금까지 파일에 쓰던 코드가 소켓에서 그대로 통한 이유의 절반이 이것이다 → [[io-stream]]

**대신 남는 문제가 무엇인지도 정해진다.** TCP 가 순서와 손실을 가져가고 나면 애플리케이션에 남는 것은 **경계와 순서**뿐이다 — 어디까지가 한 메시지이고 누가 먼저 말하는가. 「TCP 를 쓰면 통신이 끝난 것」으로 읽으면 이 남은 절반이 안 보인다 → [[network-protocol]] · [[length-prefix-framing]]

**연결이 상태라는 것이 비용이 된다.** 연결마다 양쪽 OS 가 버퍼와 상태를 들고 있어야 하므로, 접속이 많아지면 그 자체가 자원이다. 끊긴 뒤에도 자리가 잠깐 남는 것(`TIME_WAIT`)도 이 상태 때문이다 → [[port-number]]

## 경계와 오해

- **TCP 연결 ≠ 고정된 회선** — Day46 이 「통신 회선이 고정되고 이 회선을 통해 데이터를 송수신한다」로 적은 것은 **회선 교환(전화)의 그림**이다. TCP 는 그 위에서 도는 것이 아니라 **패킷을 낱개로 던지는 IP 위에** 얹혀 있고, 같은 연결의 패킷들이 서로 다른 경로로 갈 수 있다. 고정된 것은 회선이 아니라 **양쪽이 들고 있는 상태**(어디까지 보냈고 어디까지 받았나)다. 「연결」이라는 낱말이 물리적인 선을 떠올리게 해서 생기는 오해이고, **회선이 없다는 것을 알아야** 다음 두 항목이 설명된다.
- **「손실이 발생하지 않는다」는 결과이고 회선 때문이 아니다** — Day46 의 「고정된 회선을 사용하기 때문에 데이터가 순서대로 전달되며 손실이 발생하지 않는다」는 **인과가 뒤집혀 있다.** 실제로는 패킷이 사라지고 순서가 뒤바뀌고 중복해서 도착한다. TCP 는 순서 번호와 확인 응답(ACK)으로 그것을 **찾아내 다시 보내고 줄을 세워** 위층에 넘긴다. 즉 손실이 **일어나지 않는** 것이 아니라 **보이지 않는** 것이다. 이 차이가 실무에서 드러나는 자리가 **속도**다 — 손실이 많은 구간에서 TCP 는 에러 없이 그냥 **느려진다.** 「에러가 없으니 네트워크는 정상」이라는 판단이 여기서 어긋난다.
- **빠짐없이 도착한다 ≠ 끊기지 않는다** — 다시 보내도 안 되면 TCP 는 포기하고 연결을 끊는다. 그때 애플리케이션이 보는 것은 「데이터 일부 유실」이 아니라 **`IOException`** 이다. 그래서 TCP 위의 코드는 「반만 왔을 때」를 처리할 필요가 없고 **「연결이 죽었을 때」를 처리해야 한다** → [[exception-handling]]
- **연결 수립은 `accept()` 가 아니다** — Day46 의 「서버가 연결을 수락하면」이 `accept()` 처럼 읽히는데, 3-way handshake 는 **OS 커널이 프로그램을 깨우지 않고 먼저 끝낸다.** 완성된 연결은 큐에 들어가 있고 `accept()` 는 **거기서 하나 꺼내는 일**이다. 그래서 서버가 딴 일을 하고 있어도 클라이언트 쪽은 「접속 성공」으로 보인다 — 붙었는데 아무 응답이 없는 상태가 이렇게 생긴다. Day45 가 대기열크기를 「최대 접속수」로 잘못 배운 자리가 정확히 이 큐다 → [[socket]] · [[queue]]
- **TCP ≠ 메시지 단위 전달** — 스트림이라 「한 번 `write()` = 한 번 `read()`」가 성립하지 않는다. 두 번 쓴 것이 붙어서 한 번에 읽히거나(합쳐짐), 한 번 쓴 것이 두 번에 나뉘어 읽힌다. **순서를 보장한다는 말이 경계를 보장한다는 뜻으로 읽히는 것**이 가장 비싼 오해이고, 테스트에서는 짧은 메시지라 붙지 않아 통과했다가 길어지면 깨진다 → [[length-prefix-framing]] · [[network-protocol]]
- **`write()` 성공 ≠ 상대가 받았음** — 쓰기는 내 OS 버퍼에 넣는 것으로 끝난다. 그 뒤 상대에게 가는 것은 TCP 가 알아서 하므로, **`write()` 가 예외 없이 끝난 다음에 연결이 죽어도 아무도 알려 주지 않는다.** 「보냈으니 처리됐다」로 쓰면 상대가 못 받은 요청이 성공으로 기록된다 — 응답을 받아야 확인되는 것이지 `write()` 로 확인되지 않는다.
- **TCP ≠ UDP 의 상위 버전** — Day46 은 「TCP와 UDP가 있다」로만 적고 UDP 를 다루지 않는데, 둘은 좋고 나쁨이 아니라 **버릴 것을 고르는 선택**이다. UDP 는 연결도 재전송도 없어서 늦게 온 데이터를 기다리지 않는다 — 화상 통화·게임에서 **지난 화면을 다시 보내는 것이 무의미**하기 때문에 쓴다. 「신뢰성」을 성능과 맞바꾸는 축이 아니라 **「늦은 정확함」과 「이른 부정확함」 중 무엇이 쓸모 있나**의 축이다.
- **TCP 를 쓴 것은 프로토콜을 정한 것이 아니다** — 낱말이 같아서 「TCP 프로토콜을 쓴다」로 끝내기 쉽지만, TCP 는 **바이트를 나르는 방법**만 정하고 그 바이트가 무슨 뜻인지는 아무것도 정하지 않는다. HTTP·MySQL 프로토콜이 모두 TCP 위에 있으면서 서로 말이 안 통하는 이유다 → [[network-protocol]]
- **포트 번호 공간이 TCP 와 UDP 로 따로다** — 같은 8888 을 TCP 와 UDP 가 동시에 쓸 수 있다. 「포트가 이미 쓰이고 있다」를 볼 때 어느 프로토콜인지 함께 봐야 하는 근거가 이것이다 → [[port-number]]

## 출처

- [[2024-10-23-chapter6-transport]] — **「연결형」이라는 한 낱말이 절차와 헤더로 펼쳐진다.** 3방향 핸드셰이크가 SYN → SYN+ACK → ACK 세 걸음이고 **번호에 1을 더해 되돌려 주는 것**으로 서로를 확인한다는 것, 헤더에 **일련번호·확인응답번호·윈도우 크기·코드비트**가 있고 각각이 순서·수신 확인·전송량·패킷 성격을 맡는다는 것이 나온다. 1500바이트를 500씩 세 번 보내며 일련번호가 `1 → 501 → 1001` 로 가는 예가 「순서대로 빠짐없이」의 실제 구현을 보인다. UDP 는 **헤더 필드가 넷뿐**(포트 둘·길이·검사합)이라는 대비로 「무엇을 포기하면 무엇이 없어지는가」를 드러낸다 → [[transport-layer]]
- [[2024-07-30-Day46]] — 「이 규약을 전송용 프로토콜 이라 부르며, TCP와 UDP가 있다」로 전송 층에 이름을 주고, 「Transmission Control Protocol은 연결형 프로토콜로 상대방이 연결된 상태에서 데이터를 송수신한다」로 TCP 를 정의한 뒤 `ServerSocket`·`Socket` 코드로 넘어간다. 다만 **근거로 적은 「통신 회선이 고정되고」·「고정된 회선을 사용하기 때문에 …손실이 발생하지 않는다」는 회선 교환의 그림이고 TCP 의 실제 동작이 아니다**(순서 번호와 재전송이 손실을 감추는 것이다). UDP 는 이름만 나오고 비교가 없어, 「무엇을 버려서 무엇을 얻나」는 이 회차에 없다
