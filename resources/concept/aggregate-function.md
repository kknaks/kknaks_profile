# 집계 함수 (Aggregate Function) — count 를 중심으로

**여러 행을 하나의 값으로 접는 함수.** Day54 는 `count()` 하나만 다루는데, 소제목이 「**null 아닌** 데이터 갯수 세기」다 — **접는 과정에서 `NULL` 을 빼고 센다**는 것이 이 부류 전체를 관통하는 성질이고, 필기가 그것을 첫 문장에서 짚었다. [[sql-date-function]] 같은 함수는 행 하나를 받아 값 하나를 주지만, 이쪽은 **행 여러 개를 받아 값 하나**를 준다 → [[dql]]

## 정의

```sql
select count(컬럼명) 별명 from 테이블명;
```

`select` 목록에 함수가 들어가지만 **결과의 행 수가 달라진다** — 표 전체가 **한 행**으로 접힌다. 이것이 [[dql]] 의 프로젝션(열을 고르는 것)과 다른 층인 이유다.

`NULL` 을 어떻게 다루는지가 이 부류의 규칙이고, **`count` 만 두 얼굴을 갖는다.**

| 쓰는 형태 | 세는 것 | `NULL` 인 행 |
|---|---|---|
| `count(*)` | **행의 개수** | 센다 |
| `count(컬럼명)` | 그 컬럼에 **값이 있는** 행의 개수 | **빼고 센다** ← Day54 가 적은 것 |
| `count(distinct 컬럼명)` | 그 컬럼의 **서로 다른 값**의 개수 | 빼고 센다 |

나머지는 전부 「값이 있는 것만」으로 한 가지다.

| 함수 | 하는 일 | 빈 결과에서는 |
|---|---|---|
| `sum(컬럼)` | 합 | `NULL` |
| `avg(컬럼)` | 평균 = `sum / count(컬럼)` | `NULL` |
| `min(컬럼)` · `max(컬럼)` | 최소·최대 | `NULL` |
| `count(...)` | 개수 | **`0`** |

**마지막 줄만 다르다** — 셀 것이 없으면 「0개」라는 답이 성립하지만, 없는 값들의 합이나 평균에는 답이 없다. 「합계가 0으로 나올 것」을 기대하고 화면에 그대로 찍으면 빈 테이블에서 `0` 이 아니라 아무것도 안 나온다 → [[sql-null]]

그리고 Day54 의 예제가 `count(컬럼명)` **뒤에 `as` 없이 별칭**을 붙였다. 함수를 쓰면 기본 열 이름이 `count(컬럼명)` 이라는 식 전체가 되므로, 애플리케이션이 이름으로 값을 꺼내려면 별칭이 사실상 필수다 → [[dql]]

## 사용 예시

Day54 의 한 줄이 전부다.

```sql
select count(컬럼명) 별명 from 테이블명;
```

이 한 줄과 `count(*)` 를 나란히 놓으면 필기가 적은 「null 아닌」이 눈에 보인다. 전화번호가 없는 회원이 셋 있는 표에서는 이렇게 갈린다.

```sql
select count(*) 전체, count(tel) 연락처있음 from member;
-- 전체: 100, 연락처있음: 97
```

## 왜 중요한가

**세는 일이 코드에서 문장으로 옮겨 온다.** 자바로 만든 목록에서 「등록된 게시글이 몇 개인가」는 배열을 처음부터 끝까지 돌며 카운터를 올리는 일이었고, 그러려면 **모든 행을 애플리케이션까지 실어 와야** 했다. `count()` 는 그 일을 서버에서 하고 **숫자 하나만 돌려준다** — 100만 행을 세기 위해 100만 행을 네트워크로 보내지 않는다 → [[linear-search]] · [[array]]

**「없는 값」의 처리 방침이 함수에 박혀 있어서 내가 정하지 않아도 결정된다.** 자바에서 평균을 구하려면 `null` 인 항목을 건너뛸지 `0` 으로 셀지 코드가 정해야 했다. SQL 의 집계 함수는 **언제나 건너뛰는 쪽**으로 고정되어 있고, 그래서 `avg` 의 분모는 `count(*)` 가 아니라 `count(컬럼)` 이다. **모르는 값을 0점으로 세는 평균과 아예 빼고 내는 평균은 다른 숫자**이며, 그 선택이 함수 이름 안에 이미 들어 있다 → [[sql-null]]

**그리고 「행 하나 = 결과 한 줄」이라는 감각이 여기서 깨진다.** 지금까지 조회 결과의 행은 테이블의 행이었지만, 집계 이후로는 **결과의 한 행이 여러 행에서 계산된 것**이다. 이 구분을 잡아 두지 않으면 집계와 일반 컬럼을 같은 `select` 에 섞어 쓰다 막히고(아래 참조), 그 오류 메시지가 무엇을 말하는지 읽히지 않는다.

## 경계와 오해

- **`count(*)` ≠ `count(컬럼명)`** — Day54 의 소제목이 「null 아닌 데이터 갯수 세기」이므로 필기는 이것을 알고 있는데, **알아야 할 것은 「그럼 전부 세는 것은 무엇인가」**다. `*` 는 [[dql]] 에서 「모든 컬럼」이라는 뜻이었는데 `count(*)` 에서는 컬럼과 아무 상관이 없고 **행 자체를 센다.** 「회원 수」를 `count(tel)` 로 세면 연락처가 없는 회원이 빠진 숫자가 나오고, **오류가 아니라 그냥 작은 숫자**라서 눈치채기 어렵다. 회원 수를 세려면 `count(*)` 이고 「연락처가 있는 회원 수」를 셀 때만 컬럼을 적는다.
- **`count(*)` 가 「가장 무거운 것」이 아니다** — `*` 라서 모든 컬럼을 읽는다고 오해하기 쉬운데, MySQL 은 `count(*)` 에서 컬럼 값을 꺼내지 않고 가장 작은 인덱스를 훑는다. 오히려 **`count(컬럼명)` 이 그 컬럼의 `NULL` 여부를 확인해야 해서** 그 컬럼에 인덱스가 없으면 더 비쌀 수 있다. 「`*` 는 나쁘다」는 `select *` 에서 참인 이야기이고 `count(*)` 로 그대로 옮겨지지 않는다 → [[database-index]]
- **그렇다고 `count(*)` 가 공짜는 아니다** — MyISAM 은 행 수를 따로 갖고 있어 즉시 답하지만, **InnoDB 는 세어야 한다**(트랜잭션마다 보이는 행이 다르므로 하나의 정답이 없다). 큰 테이블의 `select count(*)` 가 수 초 걸리는 것이 여기서 온다. 「개수를 구하는 것쯤은 빠르다」는 InnoDB 에서 성립하지 않고, 그래서 게시판 총 개수를 따로 저장해 두는 설계가 나온다 → [[transaction]] · [[caching]]
- **집계 함수는 `where` 에 쓸 수 없다** — `where count(*) > 5` 는 `Invalid use of group function` 이다. `where` 는 **행을 하나씩 보며 고르는 자리**이고 그 시점에는 아직 집계가 계산되지 않았기 때문이며, 집계 결과로 거르는 것은 `having` 이 맡는다. [[dql]] 에 적어 둔 「`as` 별칭을 `where` 에서 못 쓴다」와 **같은 원인**(절의 평가 순서)이고, 그래서 `where`·`having` 의 구분은 취향이 아니라 순서의 결과다.
- **집계와 일반 컬럼을 섞으면 막힌다** — `select name, count(*) from member` 는 MySQL 5.7.5 부터 기본으로 켜진 `ONLY_FULL_GROUP_BY` 때문에 오류다. 접힌 한 행에 「이름」을 넣으려면 100개 중 어느 것인지 정해지지 않기 때문이다. **옛 MySQL 은 이것을 통과시키고 아무 이름 하나를 골라 줬고**, 그 시절 코드를 옮겨 오면 이 자리에서 처음 실패한다 — 「전에는 됐는데」의 원인이 서버 설정이라는 점이 [[sql-null]] 의 엄격 모드와 같은 축이다.
- **`sum` 은 자바처럼 넘치지 않는다** — 자바에서 `int` 를 계속 더하면 조용히 음수가 되지만, MySQL 의 `sum()` 은 정수 컬럼을 받아도 결과 타입을 `DECIMAL` 로 넓혀 돌려주므로 `int` 범위를 넘어도 값이 맞다. 「자바에서 겪은 오버플로가 SQL 에도 있겠지」로 방어 코드를 넣을 자리가 아니고, 반대로 **그 값을 자바의 `int` 로 받는 순간 넘친다** — 위험은 SQL 이 아니라 경계에 있다 → [[overflow]] · [[type-casting]]
- **`avg` 도 잘라 버리지 않는다** — 자바의 `10 / 4` 는 `2` 지만 MySQL 의 `avg` 는 `2.5000` 이다. 정수 컬럼의 평균을 정수로 기대하고 화면 형식을 짜면 소수점 네 자리가 그대로 찍힌다. 「나눗셈은 타입이 정한다」는 자바의 규칙이 SQL 에는 없다 → [[floating-point]] · [[format-string]]
- **`min`·`max` 는 문자열·날짜에도 걸린다** — 숫자 전용이 아니라 **정렬 규칙이 있는 모든 타입**에서 동작하며, 문자열이면 collation 이, 날짜면 시간 순서가 기준이다. 그래서 `max(name)` 은 오류가 아니라 「사전순 마지막 이름」이고, 의미 없는 값이 오류 없이 나온다 → [[string-comparison]] · [[sql-date-function]]
- **`union all` 로 합친 결과에 씌우면 이중 계산이 된다** — 두 결과에 같은 행이 있으면 `union all` 은 그대로 두 행으로 두고, 그 위의 `count`·`sum` 은 그것을 두 번 센다. 오류가 나지 않고 **숫자만 커진다** → [[sql-set-operation]]
- **집계 함수 ≠ [[ddl]] 이 말한 「함수」** — Day51 이 DB 객체 목록에 적은 「함수(function)」는 **내가 `create function` 으로 만드는 것**이고, `count`·`sum` 은 서버에 내장된 것이라 만들 대상이 아니다. 같은 낱말이 「DDL 로 만드는 객체」와 「이미 있는 문법 요소」 둘을 가리킨다.

## 함께 보는 개념

- [[dql]] — 집계가 얹히는 `select` 문. 별칭·`*`·절의 평가 순서가 여기 있다
- [[sql-null]] — 집계가 빼고 세는 값. `avg` 의 분모를 정한다
- [[database-index]] — `count` 가 실제로 무엇을 훑는지 정하는 것
- [[sql-set-operation]] — 합친 결과에 집계를 씌울 때 이중 계산이 되는 자리
- [[sql-date-function]] — 행 하나를 받는 함수. 이쪽은 여러 행을 받는다
- [[overflow]] · [[type-casting]] — `sum` 의 결과를 자바로 옮길 때 넘치는 자리
- [[floating-point]] — `avg` 가 정수를 자르지 않는 것
- [[transaction]] · [[caching]] — InnoDB 에서 `count(*)` 가 비싼 이유와 그 대응
- [[linear-search]] · [[array]] — 같은 일을 자바에서 하던 방법
- [[ddl]] — 같은 「함수」라는 낱말이 다른 것을 가리키는 자리
