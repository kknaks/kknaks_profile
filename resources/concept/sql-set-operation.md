# SQL 집합 연산 (union · union all · 차집합 · 교집합)

**조회 결과 두 개를 위아래로 합치거나 서로 빼서 하나의 결과로 만드는 것.** Day54 가 이 절을 「집합관계」라 불렀다. [[dql]] 의 `select` 는 결과를 **가로·세로로 자르는** 문장이었는데(프로젝션·셀렉션), 집합 연산은 **결과 두 개를 통째로 다루는** 층이라 축이 하나 더 붙는다 — 자르는 것이 아니라 **쌓는 것**이다.

## 정의

| 연산 | 하는 일 | MySQL | Day54 가 쓴 방법 |
|---|---|---|---|
| 합집합 (중복 유지) | 두 결과를 그냥 이어 붙인다 | `union all` | `union all` |
| 합집합 (중복 제거) | 이어 붙인 뒤 같은 행을 하나로 접는다 | `union` | `union` |
| 교집합 | 양쪽에 다 있는 것만 | `intersect` (8.0.31+) | `where 컬럼 in (서브쿼리)` |
| 차집합 | 왼쪽에만 있는 것 | `except` (8.0.31+) | `where 컬럼 not in (서브쿼리)` |

**`union` 과 `union all` 의 차이는 「중복 제거를 하는가」 하나뿐**이고, 그 하나가 비용을 가른다 — 중복을 제거하려면 전체를 정렬하거나 해시로 모아야 하므로 `union` 이 `union all` 보다 늘 비싸다. **중복이 없다는 것을 아는 자리에서 `union` 을 쓰는 것은 그냥 낭비**다 → [[hash-based-collection]]

성립 조건은 두 가지다.

- **컬럼 개수가 같아야 한다.** 다르면 `The used SELECT statements have a different number of columns` 다.
- **대응은 이름이 아니라 위치로 한다.** 왼쪽 첫 컬럼과 오른쪽 첫 컬럼이 짝이 되고, 타입이 다르면 둘을 담을 수 있는 타입으로 넓혀진다. [[dml]] 의 `insert ... select` 가 이름이 아니라 타입·순서로 대응하던 것과 **같은 규칙**이다 → [[sql-data-type]] · [[type-promotion]]

그리고 **결과의 컬럼 이름은 첫 번째 `select` 가 정한다.** 두 번째 쪽에 `as` 로 다른 별칭을 붙여도 무시되므로, 별칭은 첫 줄에 적어야 한다 → [[dql]]

## 사용 예시

Day54 의 네 예제다. 위 둘이 문법으로 지원되는 것, 아래 둘이 서브쿼리로 흉내 낸 것이다.

```sql
select distinct 컬럼명 from 테이블명
union all 
select distinct 컬럼명 from 테이블명
```

```sql
select distinct 컬럼명 from 테이블명
union 
select distinct 컬럼명 from 테이블명
```

```sql
select distinct 컬럼명 from 테이블명
where 컬럼명 not in (select distinct 컬럼명 from 테이블명2);
```

```sql
select distinct 컬럼명 from 테이블명
where 컬럼명 in (select distinct 컬럼명 from 테이블명2);
```

**네 예제 모두 양쪽에 `distinct` 가 붙어 있고, 그것이 위 두 예제의 뜻을 절반 지운다** — 아래 「경계와 오해」의 첫 항목이 그 이야기다.

## 왜 중요한가

**「한 테이블에서 꺼낸 것」과 「여러 곳에서 모은 것」의 경계가 무너진다.** 지금까지 조회의 결과는 언제나 어떤 테이블 하나의 부분집합이었다. `union` 이후로는 **결과가 그 자체로 값의 집합**이고, 어디서 왔는지가 결과의 모양에 남지 않는다 — 그래서 「올해 주문」과 「작년 주문」이 다른 테이블에 있어도 화면 하나로 보일 수 있다.

**그리고 결과를 다시 입력으로 쓰는 감각이 여기서 생긴다.** Day54 의 차집합·교집합 예제는 `select` 안에 `select` 를 넣었다. **조회의 결과가 조건이 될 수 있다**는 것이고, 이것이 조인·뷰·서브쿼리로 이어지는 문의 첫 형태다 → [[dql]]

**대신 「값을 세로로 합치는 것」과 「테이블을 가로로 잇는 것」을 처음부터 갈라 놓아야 한다.** 정규화로 테이블을 나눈 뒤 다시 붙이는 일은 대개 **가로**(조인)이고, 집합 연산은 **세로**다. 둘을 섞으면 「테이블을 나눴으니 `union` 으로 합치면 된다」가 되어 게시글과 첨부파일을 `union` 으로 붙이려는 시도가 나온다 → [[db-normalization]] · [[foreign-key]]

## 경계와 오해

- **Day54 의 `union all` 예제는 「중복 포함」이 되지 않는다 — 양쪽에 `distinct` 가 붙어 있다** — 주석이 「중복 포함하여 데이터 합치기」인데 각 `select` 가 이미 자기 쪽 중복을 지우고 들어오므로, **남는 중복은 「양쪽에 다 있는 값」뿐**이다. 한쪽에 같은 값이 세 번 있어도 하나로 접힌 뒤 합쳐진다. `union all` 로 무엇을 보려던 것인지가 예제에서 사라진 셈이고, 그 자리에 들어갈 형태는 **양쪽 다 `distinct` 없는** `select 컬럼명 from t1 union all select 컬럼명 from t2` 다. 반대로 `union` 예제의 `distinct` 는 **뜻은 안 바뀌고 일만 늘린다**(`union` 이 어차피 전체를 중복 제거한다) — 같은 한 낱말이 한쪽에서는 의미를 지우고 다른 쪽에서는 비용만 더한다.
- **「MySQL 은 차집합·교집합을 지원하지 않는다」는 이 필기를 쓴 시점에 이미 사실이 아니었다** — MySQL 은 **8.0.31**(2022년 10월)에서 `INTERSECT` 와 `EXCEPT` 를 추가했고, Day54 는 **2024년 8월**이다. 오래된 교재·블로그에서 옮겨 온 문장으로 보인다. 「지원하지 않는다」는 **MySQL 8.0.30 이하와 MariaDB 이전 버전**에 대해 참이므로 시점을 붙여 읽어야 한다.

  ```sql
  select 컬럼명 from 테이블명
  except
  select 컬럼명 from 테이블명2;
  ```
- **`not in` 서브쿼리는 결과에 `NULL` 이 하나라도 있으면 아무 행도 돌려주지 않는다** — Day54 의 차집합 우회에 있는 **실제 버그**다. `x not in (1, 2, NULL)` 은 `x != 1 and x != 2 and x != NULL` 이고 마지막 항이 언제나 `NULL`(참이 아님)이라, **`x` 가 무엇이든 전체가 참이 되지 못한다.** 즉 참조 테이블의 그 컬럼이 nullable 이고 `NULL` 행이 하나만 있으면 **차집합이 조용히 0행**이 되고, 오류가 아니므로 「겹치는 게 전부였구나」로 읽힌다. **`in` 쪽은 이 함정이 없다** — 맞는 값이 있으면 참이 되므로 교집합 예제는 정상 동작한다. **같은 문법의 부정형만 무너지는 비대칭**이고, `NULL` 이 값이 아니라 「모른다」이기 때문에 「모르는 것과 다르다」를 단정할 수 없는 것이 원인이다 → [[sql-null]] · [[sql-operator]]
- **그래서 `not in` 은 차집합의 안전한 대체가 아니다** — 위 함정 말고도 **컬럼이 하나일 때만 쓸 수 있다.** `EXCEPT` 는 **행 전체**를 비교하고 중복까지 제거하는데 `not in` 은 **컬럼 하나**를 비교하고 바깥 `select` 의 나머지 컬럼을 그대로 남긴다. 두 컬럼으로 차집합을 하려면 `not in` 으로는 표현되지 않고, `EXCEPT` 가 없던 시절의 정석은 `left join ... where 오른쪽.컬럼 is null` 이었다 — **`NULL` 함정도 없고 컬럼 여러 개도 된다.**
- **`in`/`not in` 서브쿼리는 집합 연산이 아니다** — 결과의 모양이 다르다. 집합 연산은 **두 결과를 나란히 세워 행을 만드는 것**이라 컬럼 개수가 같아야 하지만, `in` 은 **한쪽을 조건으로 쓰는 것**(셀렉션)이라 바깥 `select` 의 컬럼을 자유롭게 고를 수 있다. Day54 가 넷을 「집합관계」 한 절에 묶었기 때문에 같은 층으로 보이는데, **위 둘은 결과를 합치는 연산이고 아래 둘은 `where` 조건**이다 → [[dql]]
- **`union` 의 중복 제거는 `NULL` 을 같은 값으로 본다** — `where 컬럼 = null` 이 한 행도 못 잡는 것과 정반대다. `distinct`·`union`·`group by` 는 **`NULL` 끼리 같다고 보고 하나로 접고**, 비교 연산자는 `NULL` 끼리 비교하면 참을 주지 않는다. 「`NULL` 은 자기 자신과도 같지 않다」로 외우면 `union` 결과에 `NULL` 이 한 줄만 나오는 것이 설명되지 않는다. 참고로 `unique` 제약은 또 다르게 취급해서 **`NULL` 을 여러 행이 가질 수 있다** — 같은 `NULL` 이 문맥마다 세 갈래로 다뤄진다 → [[sql-null]] · [[unique-key]]
- **`order by` 는 마지막에 한 번만, 그리고 전체에 걸린다** — 중간 `select` 뒤에 붙이면 문법 오류이거나 무시되고, 끝에 붙인 것은 합쳐진 결과 전부에 적용된다. 「각 부분을 정렬한 순서로 위아래로 쌓는다」는 되지 않는다 — 그러려면 각 `select` 를 괄호로 싸고 정렬용 컬럼을 하나 더 만들어 그것으로 정렬해야 한다. **`union all` 의 결과 순서 자체도 보장되지 않는다** — 위에 적은 쪽이 먼저 나오는 것은 구현이 그렇게 하는 것이지 문장이 요구한 것이 아니다 → [[dql]]
- **`union all` 은 그냥 이어 붙이므로 「같은 것」이 두 번 세어진다** — 두 결과에 같은 행이 있으면 그대로 두 행이고, 그 위에 `count()` 를 씌우면 실제 값의 개수보다 크다. 「합계를 구하려고 두 테이블을 `union all` 로 합쳤다」가 조용히 이중 계산이 되는 자리이며, 오류가 나지 않아 숫자만 어긋난다 → [[aggregate-function]]
- **SQL 의 「집합」은 수학의 집합과 다르다** — 수학의 집합은 중복이 없고 순서가 없지만 SQL 의 테이블·결과는 **중복이 있고**(그래서 `union all` 이 성립한다) 실무에서는 순서를 신경 쓴다. 정확히는 집합이 아니라 **멀티셋(bag)** 이고, `union` 은 그것을 집합으로 만드는 연산이다. 자바의 `Set` 이 애초에 중복을 담지 못하는 것과 갈리는 지점이다 → [[hash-based-collection]]
- **`select` 목록에 `distinct` 를 쓰는 것은 문제를 감추는 데 쓰이기 쉽다** — 조인이나 합치기를 잘못해서 행이 불어난 결과에 `distinct` 를 붙이면 화면은 맞아 보인다. **원인은 그대로 있고 비용만 늘어난 상태**이며, 컬럼을 하나 더 꺼내는 순간(그 컬럼 값이 다르면) 중복이 다시 드러난다. Day54 의 네 예제가 전부 `distinct` 로 시작하는 것이 그 습관의 시작점이 될 수 있는 자리다.
- **필기의 집합 연산 예제에는 `;` 이 없다** — 위 두 예제(`union all`·`union`)의 끝에 세미콜론이 없어 `mysql` 클라이언트에 그대로 붙이면 실행되지 않고 `->` 프롬프트로 계속 기다린다. [[ddl]] 노트에 적어 둔 것과 같은 자리이고, 아래 두 예제에는 붙어 있어 **같은 절 안에서 갈린다**.
