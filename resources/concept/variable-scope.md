# 변수의 유효범위 (Variable Scope)

**같은 이름의 변수가 여러 층에 있을 때 컴파일러는 가장 가까운 층의 것을 고른다.** 이름이 겹치는 것은 오류가 아니고, 안쪽 이름이 바깥 이름을 **가린다**(가려진 쪽은 사라지지 않고 층을 지정하면 여전히 닿는다). 그래서 「어느 `v1` 인가」는 실행 중의 값이 아니라 **그 코드가 어느 층에 쓰여 있는가**가 정한다.

## 정의

이 회차가 순서를 한 줄로 적었다 — 「컴파일러가 변수를 찾을 때 순서: 로컬 변수 -> 인스턴스 변수 -> 바깥 객체의 인스턴스 변수」.

| 표기 | 찾는 곳 | 못 찾으면 |
|---|---|---|
| `v1` | 가장 가까운 층부터 위로 | 컴파일 오류 |
| `this.v1` | **자기 인스턴스**의 필드 | 컴파일 오류 (위로 올라가지 않는다) |
| `바깥클래스명.this.v1` | **바깥 인스턴스**의 필드 | 컴파일 오류 |

지정하지 않은 이름만 층을 타고 올라간다. `this.` 나 `B3.this.` 를 쓰는 순간 **탐색이 그 한 층에 고정된다** → [[this-reference]]

층은 세 개가 아니라 안쪽에서 밖으로 이어지는 사슬이다.

1. 그 블록의 로컬 변수 · 매개변수
2. 그 클래스의 멤버 — **자기가 선언한 것과 상속받은 것**
3. 바깥 클래스의 멤버 (그 위의 바깥까지 계속)

`static` 문맥에는 2·3 중 인스턴스 층이 없다. 그래서 정적 중첩 클래스에서는 바깥의 `static` 멤버까지만 이름으로 닿고, 인스턴스 멤버는 이름이 있어도 **가리킬 대상이 없어서** 못 쓴다 → [[static-member]] · [[nested-class]]

## 사용 예시

이 회차는 이름 `v1` **셋**을 한 호출 안에 겹쳐 두고 다섯 줄을 찍는다.

```java
class B3 {
    // 인스턴스 멤버
    int v1 = 10;
    int v3 = 90;
    class X {
        int v1 = 20;
        int v2 = 80;

        void test() {
            int v1 = 1000;
            System.out.printf("v1 = %d\n", v1);                 // 로컬 변수
            System.out.printf("this.v1 = %d\n", this.v1);       // 인스턴스 변수
            System.out.printf("B3.this.v1 = %d\n", B3.this.v1); // 바깥 객체의 인스턴스 변수
            System.out.printf("v1 = %d\n", v2);                 // 인스턴스 변수
            System.out.printf("v1 = %d\n", v3);                 // 바깥 객체의 인스턴스 변수
        }
    }
}

public class NonStaticNestedAcessMember2 {
    public static void main(String[] args) {
        B3 outer = new B3();
        outer.v1 = 11;
        B3.X x1 = outer.new X();
        x1.test();
    }
}
```

찍히는 것은 이렇다.

```text
v1 = 1000
this.v1 = 20
B3.this.v1 = 11
v1 = 80
v1 = 90
```

**`main` 의 `outer.v1 = 11` 이 이 예시의 장치다.** 필드 초기값이 `10` 인데 `11` 이 찍히므로, `B3.this.v1` 이 「`B3` 이라는 클래스에 적힌 값」이 아니라 **그 인스턴스의 현재 값**을 읽는다는 것이 확인된다. 클래스 이름을 앞에 쓰지만 정하는 것은 **어느 인스턴스인가**뿐이다 → [[instance]]

그리고 **뒤 두 줄은 지정자를 하나도 쓰지 않았는데 서로 다른 층에서 왔다.** `v2` 는 `X` 에만 있으니 2층에서 멈추고, `v3` 는 `X` 에 없으니 3층까지 올라간다. **같은 모양의 코드가 어디를 읽는지는 「그 이름이 안쪽에 있는가」가 정한다** — 그것이 이 예시의 결론이다.

로컬 클래스도 같은 규칙을 받는다. 이 회차가 로컬 클래스를 「특정 메서드 안에서만 사용되는 클래스」로 정의하고 지정자를 못 붙이는 이유를 「**로컬 변수처럼**」이라고 적었다.

```java
public class NonStaticNestedClass {
    static void m1(){
        // private class A1 {}
        class A2 {}
        // protected class A3 {}
        // public class A4 {}
    }
}
```

**이름의 유효범위가 그 블록이라면 「누가 볼 수 있나」를 말할 대상이 없다.** 지정자가 문법적으로 막히는 것이 규칙의 결과가 아니라 **스코프의 결과**다 → [[access-modifier]] · [[nested-class]]

## 왜 중요한가

**이름이 겹쳐도 컴파일 오류가 아니라는 것이 이 개념의 전부다.** 오류가 났다면 배울 것이 없다. `v1` 이 셋인 코드가 조용히 컴파일되고 각 줄이 다른 값을 읽으므로, **어느 것을 읽는지 아는 것이 코드를 읽는 능력에 포함된다.**

**안쪽에 이름을 하나 더하면 멀리 있는 코드가 조용히 다른 값을 읽는다.** `X` 에 `v3` 필드를 나중에 추가하면 `test()` 의 마지막 줄은 손대지 않았는데도 `90` 대신 새 필드를 읽는다. 컴파일도 되고 경고도 없다 — **수정한 자리와 깨지는 자리가 다른** 종류의 사고이고, 그래서 바깥 것을 쓸 때 `바깥클래스명.this.` 를 명시하는 것이 방어가 된다.

**`this.` 를 생략하는 관례가 안전한 범위가 여기서 정해진다.** 층이 하나뿐인 톱레벨 클래스에서는 생략해도 읽는 곳이 하나다. 중첩이 생기는 순간 생략된 이름이 두 층 중 어느 쪽인지 **선언을 찾아봐야** 알 수 있게 되고, 이 회차의 필기가 「중첩 클래스 안에 해당 필드나 메서드가 없다면 바깥클래스명.this 생략 가능」이라고 적은 편의가 곧 그 비용이다 → [[this-reference]]

**스코프가 좁으면 이름을 아껴 쓸 수 있다.** `X` 가 `v1` 을 다시 쓸 수 있는 것은 그것이 실수가 아니라 성질이다 — 클래스마다 자기 이름 공간을 갖는 것이 [[class]] 를 쪼개는 값의 일부다.

## 경계와 오해

- **스코프 가리기 ≠ 필드 은닉** — 결과가 같아 보이고 「섀도잉」이라는 말도 겹치는데, **무엇이 고르는가가 다르다.** 필드 은닉은 **상속** 축이고 고르는 것은 **레퍼런스의 선언 타입**이다(`((Parent) obj).x`). 스코프 가리기는 **중첩·블록** 축이고 고르는 것은 **그 코드가 쓰여 있는 자리**다. 그래서 은닉은 같은 인스턴스를 두 이름으로 물으면 답이 갈리고, 가리기는 **한 자리에서 층을 지정해** 골라 읽는다 → [[field-hiding]]
- **`this.v1` 은 「내 것부터 찾아라」가 아니라 「내 것만 찾아라」다** — `X` 에 그 필드가 없으면 `this.v3` 는 컴파일 오류다(생략한 `v3` 는 잘 된다). 「`this.` 는 붙여도 되고 안 붙여도 되는 것」으로 외우면 이 자리가 설명되지 않는다. 붙이지 않은 이름만 사슬을 타고, `this.` 는 사슬을 끊는다 → [[this-reference]]
- **상속이 중첩보다 먼저다 — 필기의 3단 순서에 이 층이 빠져 있다** — 정확한 순서는 「로컬 → **그 클래스가 상속받은 것까지 포함한** 멤버 → 바깥 클래스의 멤버」다. `X` 가 어떤 부모를 상속하고 그 부모에 `v3` 가 있으면, `test()` 의 `v3` 는 `B3.v3` 가 **아니라** 물려받은 쪽을 읽는다. 이 코드에서 `X` 가 아무것도 상속하지 않아 드러나지 않았을 뿐이고, 「안쪽 → 바깥쪽」 두 방향만 있는 것으로 기억하면 상속이 끼어드는 자리에서 어긋난다 → [[inheritance]] · [[field-hiding]]
- **스코프 ≠ 수명** — 이름을 쓸 수 있는 범위와 값이 살아 있는 기간은 다른 축이다. 로컬 클래스의 이름은 메서드 안에서만 유효하지만 그 **인스턴스**는 밖으로 반환되어 계속 살 수 있다(Day32 의 `iterator()` 가 그 모양이다). 이 어긋남이 로컬 클래스가 쓰는 지역변수를 사실상 `final` 로 묶는 이유다 — 이름이 사라진 뒤에도 객체가 그 값을 들고 있어야 하니 컴파일러가 **복사해 넣는다** → [[call-by-value]] · [[garbage-collection]]
- **필기의 printf 라벨 둘이 틀렸다 — 하필 스코프를 보여 주는 자리다** — 넷째·다섯째 줄이 `v2`·`v3` 를 넘기면서 서식 문자열은 `"v1 = %d\n"` 이다. 출력이 `v1 = 80` · `v1 = 90` 으로 나오므로, **다섯 줄 중 세 줄이 `v1` 을 찍는 것처럼 보이고 그 값이 1000·20·11 도 아니다.** 이 예시의 목적이 「같은 이름이 층마다 다른 값」인데 라벨이 그 목적을 정확히 망가뜨린다. 값을 옮기는 코드가 아니라 **찍는 라벨**이 틀린 것이라 실행에는 아무 문제가 없다는 점이 이 종류의 실수를 오래 남게 한다 → [[format-string]]
- **가려진 것은 없어지지 않는다** — `int v1 = 1000` 이 있어도 `this.v1`·`B3.this.v1` 은 그대로 읽힌다. 「덮어썼다」가 아니라 **「이름으로 부를 순서가 뒤로 갔다」**다. 값이 지워진다고 읽으면 셋이 동시에 찍히는 것이 설명되지 않는다 → [[variable]]
- **`static` 중첩 클래스에는 3층이 없다** — 같은 노트의 `B2.X.test()` 가 `v1 = 200`(바깥의 `static`)은 쓰고 `v2 = 100`(바깥의 인스턴스 필드)은 컴파일 오류인 것이 그것이다. **이름은 보이는데 대상이 없다** — 스코프 문제가 아니라 대상 문제이므로, 층을 명시해도(`B2.v2`) 풀리지 않는다 → [[static-member]]
- **매개변수도 로컬 층이다** — 생성자의 `this.name = name` 에서 `this.` 를 빼면 매개변수가 필드를 가려 `name = name` 이 되고, **컴파일되고 실행되면서 아무 일도 하지 않는다.** 중첩 클래스가 없어도 같은 규칙이 이미 작동하고 있었던 자리다 → [[constructor]] · [[parameter-and-argument]]
- **루프 변수의 스코프도 같은 규칙이다** — 21일 앞선 회차의 `for (int i = ...)` 가 헤더에서 선언했을 때만 좁은 것은 특수 규칙이 아니라 **선언이 그 블록에 있기 때문**이다 → [[for-loop]]
