# 부동소수점 (Floating Point, IEEE 754)

실수를 **부호 + 지수 + 가수** 세 조각으로 나눠 저장하는 방식. Java 의 `float`·`double` 이 이것이고, 규격은 IEEE 754 를 따른다.

## 정의

세 조각이 각각 다른 방법으로 저장된다.

| 조각 | 저장 방법 |
|---|---|
| 부호 | 비트 1개 |
| 지수부 | **K-excess** (bias 를 더해 기준을 옮긴다) |
| 가수부 | **sign-magnitude** → [[twos-complement]] |

**K-excess** 는 음수 지수를 담기 위해 값에 bias 를 더해 기준을 옮기는 것이다. 8비트 기준으로 bias = 2^(8-1) − 1 = 127 이므로, 지수 13 은 13 + 127 = 140 = `0b1000 1100` 으로 저장된다.

변환은 세 단계다.

1. 값을 2진수로 변환
2. **정규화** — `1.xxx * 2^n` 꼴로 만든다
3. 가수부는 sign-magnitude, 지수부는 K-excess 로 변환

정규화하면 정수부가 **항상 1** 이 되므로, 그 1 은 저장하지 않는다(생략해도 복원할 수 있다).

## 사용 예시

`12.375` 를 32비트로 저장하는 과정이다.

```plaintext
1) 2진수 변환      12.375 → 1100.011
   정수부 12       → 0b0000 1100
   소수부 0.375    → 0.375 * 2 = 0.75 … 0
                     0.75  * 2 = 1.5  … 1
                     0.5   * 2 = 1.0  … 1     → 0b011

2) 정규화          1.100011 * 2^3
                   (정수부 1 은 항상 1이므로 저장하지 않는다)

3) 지수부          3 + 127 = 130 → 1000 0010
   가수부          100011 (뒤는 0으로 채운다)

결과   0b 0100 0001 0100 0110 0000 0000 0000 0000
       0x 4146 0000
```

소수부를 구할 때 **2를 곱해 정수 부분을 떼는 것을 반복**한다. `0.375` 는 세 번에 끝났지만, 끝나지 않는 값도 있다.

### 유효자릿수 — 범위를 자릿수로 말하는 이유

2진수로 변환되기 때문에 "소수점 이상 얼마, 이하 얼마"로 범위를 정의할 수 없다. 대신 **유효자릿수**(소수점을 뺀 전체 자릿수)로 대략 말한다.

| | 크기 | 유효자릿수 | 이름 |
|---|---|---|---|
| `float` | 4 byte | 약 7자리 | 단정도 (single-precision) |
| `double` | 8 byte | 약 15~16자리 | 배정도 (double-precision) |

**배정도라는 이름이 "두 배 정밀하게 저장한다"에서 왔다.** 자릿수를 넘으면 값이 잘려 저장된다.

```java
System.out.println(999.9999f);           // 7자리 — 거의 정상
System.out.println(987654321.1234567f);  // 16자리 — 잘린다
```

그래서 **자릿수가 다른 값을 더할 때 위험하다.** `12345.67 + 12.34567` 은 전체 자릿수가 10자리가 되어 `float` 로는 정확한 계산이 어렵다.

## 왜 중요한가

**소수 계산이 정확하지 않은 이유가 이 구조에 있다.** 2진 소수로 딱 끝나지 않는 값(`0.1` 같은 것)은 가수부 비트 수만큼만 담기고 나머지가 잘린다.

```java
System.out.println(7 * 0.1);   // 0.7000000000000001
```

**CPU·OS·컴파일러·[[jvm]] 의 문제가 아니다.** IEEE 754 의 방법 자체에 내재된 것이라 환경을 바꿔도 같다. 그래서 `0.1 + 0.2 != 0.3` 이 되고, 돈 계산에 `double` 을 쓰면 안 되는 이유가 된다.

### 그래서 `==` 로 비교하면 안 된다

```java
double d1 = 987.6543;
double d2 = 1.111111;

System.out.println((d1 + d2) == 988.765411);   // false
System.out.println(d1 + d2);                   // 988.7654110000001
```

기대한 값과 다른 것이 아니라 **극한의 미세 소수점이 붙은 것**이다. 게다가 같은 수를 다른 경로로 계산하면 붙는 값이 달라진다.

```java
double x = 234.765411, y = 754.0;
System.out.println((x + y) == 988.765411);     // true   ← 이쪽은 딱 떨어졌다
System.out.println((d1 + d2) == (x + y));      // false  ← 같은 수인데 다르다
```

**JVM 이 알아서 처리해 주지 않는다.** 개발자가 오차 허용 범위(EPSILON)를 두고 비교해야 한다.

```java
double EPSILON = 0.00001;
System.out.println(Math.abs((d1 + d2) - (x + y)) < EPSILON);   // true
```

### 연산 결과 타입이 정밀도를 정한다

`float + float` 의 결과는 `float` 다 → [[type-promotion]]. **담을 변수를 키워도 이미 늦는다.**

```java
float f1 = 987.6543f, f2 = 1.111111f;

double r2 = f1 + f2;
System.out.println(r2);
// 기대값: 988.765411
// 결과값: 988.765380859375
```

`double` 변수에 담기 **전에** 이미 `float` 로 계산되면서 값이 왜곡됐다. 그래서 결론은 **처음부터 `double` 을 쓰는 것**이다 — 큰 타입으로 바꾼 다음 연산하는 것보다도 낫다. [[overflow]] 가 정수에서 같은 모양으로 나타나는 문제다.

지수와 가수를 나눠 담기 때문에 **아주 크거나 아주 작은 수를 같은 비트 수로 담을 수 있다**는 것이 이 방식의 값이다. 정밀도를 내주고 범위를 얻은 것이다.

## 경계와 오해

- **부동소수점 오차는 버그가 아니다** — 규격대로 동작한 결과다. 고칠 방법은 방식을 바꾸는 것(정수로 다루거나 10진 소수 타입을 쓰는 것)이고, 반올림으로 덮는 것은 미루는 것이다.
- **가수부에 2의 보수를 쓰지 않는다** — 음수를 다루는 데 2의 보수가 표준인데, 부동소수점의 가수부는 sign-magnitude 다. 방식마다 쓰는 자리가 다르다.
- **정규화된 1 은 저장되지 않지만 존재한다** — 비트를 세어 보면 가수부가 하나 짧아 보이는데, 생략된 1 이 실제 정밀도에 포함된다.
- **`float` 과 `double` 은 조각 크기만 다르다** — 구조는 같고 지수부·가수부에 주는 비트 수가 다르다.
- **유효자릿수는 정확한 경계가 아니다** — "약 7자리"·"약 15~16자리"이고, 값에 따라 달라진다. 옛 필기도 본문에서는 `double` 을 16자리로, 결론에서는 15자리로 적었다 — 딱 떨어지는 수가 없어서 생기는 흔들림이다. **경계를 외우는 것보다 "자릿수가 늘면 잘린다"를 기억하는 쪽이 맞다.**
- **해결책은 정밀도를 포기하는 것이 아니다** — 옛 필기의 결론은 "필요한 만큼 소수점 이하 자릿수를 잘라 쓰라"였다. 표시할 때는 맞는 방법이지만, **누적 계산에서는 자르는 것이 오차를 미루는 것**이다. 돈처럼 정확해야 하는 값은 정수(최소 단위)로 다루거나 10진 소수 타입을 쓴다.
