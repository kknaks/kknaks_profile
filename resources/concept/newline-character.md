# 줄바꿈 문자 (LF / CRLF)

줄이 끝났다는 것을 나타내는 제어 문자. **OS 마다 쓰는 것이 다르다.**

## 정의

| OS | 방식 | 바이트 |
|---|---|---|
| Linux · Unix · macOS | LF (Line Feed) | `0x0A` |
| Windows | CRLF (Carriage Return + Line Feed) | `0x0D 0x0A` |

Windows 는 **두 바이트**를 쓴다. 이름이 타이프라이터에서 왔다 — 종이를 한 줄 올리는 동작(LF)과 활자를 맨 왼쪽으로 되돌리는 동작(CR)이 원래 따로였다.

과거에는 OS 간에 개행 호환이 안 되어 파일을 옮기면 줄이 깨졌지만, 지금은 대부분의 도구가 양쪽을 처리한다.

## 왜 중요한가

**보이지 않는 차이라서 진단이 늦다.** 줄바꿈은 화면에 나타나지 않으므로, 파일이 달라졌는데 눈으로는 같아 보이는 상황이 생긴다. 협업에서 "고친 것이 없는데 전체 파일이 변경으로 잡힌다"는 일이 대표적이다 — 누군가의 편집기가 개행을 바꿔 저장한 것이다.

문자열을 다룰 때도 걸린다. 한 줄을 읽어 길이를 세면 개행이 1이냐 2냐에 따라 값이 달라지고, 줄 끝을 `\n` 만으로 자르면 CRLF 파일에서는 `\r` 이 남는다.

## 경계와 오해

- **개행은 한 문자가 아닐 수 있다** — CRLF 는 문자 둘이다. "줄바꿈 하나"를 문자 하나로 가정한 코드가 Windows 파일에서 어긋난다.
- **지금 호환된다는 것이 같아졌다는 뜻은 아니다** — 도구가 알아서 처리해 주는 것이고 파일 안의 바이트는 여전히 다르다.
- **줄바꿈이 데이터 형식의 일부가 되면 이 차이가 형식을 깨는 자리가 된다** — Day39 의 CSV 저장은 `out.write(user.toCsvString() + "\n")` 로 **줄바꿈을 코드에 직접 박는다.** `System.lineSeparator()` 는 Windows 에서 `\r\n` 이므로 이 파일은 실행 OS 와 무관하게 늘 LF 다. 읽는 쪽 `Scanner` 가 LF·CRLF 를 모두 줄 구분으로 보기 때문에 **이 프로그램 안에서 왕복은 성립하지만**, 그 파일이 프로그램 밖으로 나가면(엑셀·다른 도구·다른 언어) 한 줄로 보이거나 마지막 필드에 `\r` 이 붙어 들어온다. **「줄」을 레코드 경계로 쓰기로 한 순간 「줄이 무엇인가」가 형식의 일부가 된다** → [[csv]] · [[character-stream]]
- **[[platform-dependency]] 의 한 갈래다** — CPU·OS 별 실행파일 문제와 층은 다르지만 뿌리는 같다. OS 마다 기본값이 다르고, 그 차이가 파일을 넘길 때 드러난다.
