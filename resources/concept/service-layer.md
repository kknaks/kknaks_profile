# 서비스 계층 (Service Layer)

**업무 로직과 트랜잭션 제어를 담는 층.** 컨트롤러(서블릿)에서 「무엇을 할 것인가」를 떼어 내, 컨트롤러에는 「화면을 어떻게 보일 것인가」만 남긴다.

## 정의

이 회차의 출발점은 서블릿 하나가 두 가지를 겸하고 있다는 관찰이다.

- **DAO 제어** — 어떤 데이터를 어떤 순서로 읽고 쓸 것인가 → [[dao-pattern]]
- **JSP 제어** — 어떤 화면을 어떻게 보일 것인가 → [[jsp]]

「서블릿의 주요 기능은 JSP 제어」라고 보면, 나머지 하나가 **떼어 낼 것**이다.

```
[전]  Servlet ──┬─→ DAO
                └─→ JSP

[후]  Servlet ──┬─→ Service ──→ DAO
                └─→ JSP
```

서비스가 갖는 것이 둘이다.

1. **로직** — 여러 DAO 호출을 순서대로 엮어 하나의 업무를 이룬다
2. **트랜잭션 제어** — 그 여러 번의 쓰기를 **전부 성공하거나 전부 되돌리는** 단위로 묶는다 → [[transaction]]

## 왜 중요한가

**트랜잭션의 경계가 있어야 할 자리이기 때문이다.** 「게시글을 지우면 첨부파일도 지운다」는 두 번의 DELETE 인데, 하나만 성공하면 데이터가 깨진다. 이 경계를 DAO 에 두면 DAO 하나가 한 트랜잭션이라 여러 DAO 를 묶을 수 없고, 서블릿에 두면 **화면마다 커밋·롤백 코드가 복사된다.** 둘 다 아닌 자리가 필요하고 그것이 서비스다.

**그리고 화면이 없어도 되는 코드가 생긴다.** 서블릿에 로직이 있으면 그 로직을 부르려면 HTTP 요청이 있어야 한다 — 테스트도, 배치 작업도, 다른 화면도 그 코드를 재사용할 수 없다. 서비스로 내려온 로직은 **그냥 자바 메서드**다 → [[coupling]]

**「Servlet 이 바뀌면 전체를 바꿔야 한다」**는 필기의 문제 진술이 이 지점이다. 화면 기술이 바뀌는 것(JSP → 다른 것)과 업무 규칙이 바뀌는 것은 **서로 다른 이유로 일어나는 변경**인데, 한 클래스에 있으면 항상 같이 열어야 한다 → [[cohesion]] · [[solid-principles]]

## 경계와 오해

- **서비스가 「DAO 를 부르는 껍데기」면 층이 하나 늘었을 뿐이다** — `service.list()` 가 `dao.list()` 를 그대로 부르기만 하면 얻은 것이 없다. 이 층이 값을 갖는 것은 **여러 호출을 엮을 때**와 **트랜잭션을 그을 때**다. 단순 조회에서는 얇은 것이 자연스럽고, 그것이 잘못은 아니다
- **서비스는 HTTP 를 몰라야 한다** — `HttpServletRequest` 를 서비스에 넘기면 화면 기술이 다시 딸려 들어와 분리한 이유가 사라진다. 넘길 것은 값이나 도메인 객체다 → [[servlet]]
- **서비스 ≠ 모델 전부** — [[mvc-pattern]] 의 모델은 데이터와 업무 로직을 아우르는 말이고, 서비스는 그 안에서 **로직 쪽**을 맡는 층이다. 데이터 접근은 여전히 DAO 다
- **트랜잭션 제어를 서비스로 옮겨도 자동으로 되지는 않는다** — 이 시점의 코드는 커밋·롤백을 손으로 쓴다. 그 반복을 걷어내는 것이 나중의 일이고, [[dynamic-proxy]] 로 감싸는 방식을 앞 회차에서 이미 봤다
- **필기에 실습코드가 없다** — 「4. 실습코드」 절이 제목만 있고 비어 있어, **분리의 이유는 남았지만 분리한 모양은 남지 않았다.** 실제 코드는 뒤 회차에서 봐야 한다
