# 클래스 (Class)

클래스는 두 가지 일을 한다 — **메서드를 이름 있는 묶음으로 분류**하고, **새 데이터 타입을 정의**한다. 이 필기의 첫 문장이 그 둘을 나란히 적어 뒀고, 실습도 그 두 용도를 따로 만난다.

## 정의

| 용도 | 얻는 것 | 이 필기의 예 |
|---|---|---|
| 메서드 분류 | 기능을 소속이 있는 묶음으로 갈라 둔다 | `Calculator` 의 `plus`·`minus`·… |
| 데이터 타입 정의 | 기본 자료형으로 표현할 수 없는 값 한 덩어리를 **한 이름**으로 다룬다 (User-defined Data Type) | `Score`(`name`·`kor`·`eng`·`math`·`sum`·`aver`) |

클래스 안에 들어가는 것은 **필드**(데이터) · **메서드**(기능) · **생성자**(초기화)다. 그리고 선언한 클래스 이름이 **그대로 타입 이름**이 된다.

```java
public class Score {     // 이 줄로 타입 이름 하나가 생긴다
  String name;           // 필드
  int kor;

  void compute() { }     // 메서드
}

Score s1 = new Score();  // 타입으로 쓴다 → [[instance]]
```

기본 타입은 여덟 개로 닫혀 있고 그 밖은 전부 참조 타입이다. 그러므로 클래스를 만드는 것은 **참조 타입을 하나 늘리는 일**이다 → [[data-type]]

## 사용 예시

이 필기의 실습은 낱개 변수로 학생 셋을 처리하던 코드에서 시작한다.

```java
String name;
int kor, eng, math, sum;
float aver;

name = "홍길동"; kor = 100; eng = 90; math = 85;
sum = kor + eng + math;
aver = (float) sum / 3;
System.out.printf("%s: %d, %d, %d, %d, %.1f\n", name, kor, eng, math, sum, aver);

name = "임꺽정"; kor = 90; eng = 80; math = 75;    // 같은 변수를 덮어쓴다
...
```

여섯 변수를 묶어 타입으로 만들면 이렇게 바뀐다.

```java
public class Score {
  String name;
  int kor;
  int eng;
  int math;
  int sum;
  float aver;
}
```

```java
Score s1 = new Score();
s1.name = "홍길동";
s1.kor = 100;
...

Score s2 = new Score();     // 홍길동이 사라지지 않는다
s2.name = "임꺽정";
```

**변수 이름이 없어진 것이 아니라 소속이 생겼다.** `kor` 는 이제 「어떤 `Score` 의 `kor`」이고, 앞 코드에서 지금 누구의 점수인지를 **코드 순서로만** 알 수 있었던 것이 타입으로 드러난다.

## 왜 중요한가

**가장 먼저 달라지는 것은 재사용도 가독성도 아니라 「셋을 동시에 들고 있을 수 있는가」다.** 낱개 변수 버전은 다음 학생을 담을 때 같은 변수를 덮어쓰므로 앞 학생의 값이 사라진다. 그래서 출력이 대입 사이에 끼어 있어야 했다 — **저장할 수 없어서 바로 출력한 것**이다. 타입이 생기면 값이 살아 있으므로 모아 두고 나중에 처리할 수 있고, 여러 개를 다뤄야 하면 배열에 담으면 된다 → [[array]]

두 번째는 **메서드에 넘길 수 있는 덩어리가 된다**는 것이다. 낱개 변수 여섯 개로 합계와 평균을 계산하는 메서드를 만들려면 여섯 개를 넘기고 결과 두 개를 되받아야 하는데, 기본 타입은 호출한 쪽으로 값을 돌려보낼 방법이 `return` 하나뿐이라 두 개를 돌려줄 수 없다. `compute(Score s)` 는 그 문제가 아예 없다 — 넘어간 것이 주소라서 고친 것이 부른 쪽에 보인다 → [[call-by-value]]

세 번째는 **이름 붙일 자리가 하나로 모인다**는 것이다. 「학생」이라는 개념이 코드에 없던 상태에서 `Score` 라는 단어가 생기고, 그 뒤로 그 개념에 딸린 기능과 제약을 어디에 둘지가 정해진다 → [[encapsulation]]

## 경계와 오해

- **클래스 ≠ 인스턴스** — 클래스는 「무엇이 담기고 무엇을 할 수 있는가」의 선언이고, 실행 중에 메모리를 갖는 것은 `new` 가 만든 인스턴스다. 클래스는 한 벌, 인스턴스는 여럿이다. `Score` 를 고치면 `s1`·`s2`·`s3` 이 전부 바뀌는 것이 그 관계다 → [[instance]]
- **사용자 정의 데이터 타입 ≠ 새 기본 타입** — 기본 타입 여덟 개는 늘지 않는다. 클래스로 만든 타입은 **참조 타입**이라 변수에 담기는 것이 값이 아니라 주소다. 그래서 `s1 == s2` 가 내용 비교가 아니고, 매개변수로 넘긴 쪽에서 내용을 고치면 부른 쪽에 보인다. 「내가 만든 타입도 `int` 처럼 쓰면 된다」로 읽으면 이 둘이 다 어긋난다 → [[object-reference]] · [[string-comparison]]
- **필드를 나열한 것만으로는 「메서드 분류」쪽 값이 생기지 않는다** — 이 필기의 `Score` 는 처음에 필드만 있었고 계산은 여전히 `Test02` 의 `static void compute(Score s)` 로 밖에 있었다. **데이터를 묶는 것과 그 데이터를 다루는 기능을 같이 옮기는 것은 다른 단계**이고, 3.3 에서 `compute()` 를 `Score` 안으로 옮긴 것이 두 번째 단계다 → [[this-reference]]
- **`static` 으로만 채운 클래스는 타입 역할을 하지 않는다** — `App`·`Test01`·`Test02` 는 인스턴스를 만들 일이 없고 메서드 묶음으로만 쓰인다. 같은 `class` 문법으로 성격이 다른 두 가지를 만드는 셈이라, "클래스는 객체의 설계도"라는 설명만으로는 `main` 이 든 클래스가 무엇인지 설명되지 않는다 → [[static-member]] · [[main-method]]
- **두 용도는 결국 다른 패키지로 갈라진다** — 다음 회차의 실습이 그것을 코드 구조로 만든다. 타입 노릇을 하는 `User`·`Project` 는 `vo` 로, 메서드 묶음인 `Prompt`·`UserCommand` 는 `util`·`command` 로 갔다. 「클래스는 두 가지 일을 한다」가 설명이 아니라 **폴더 이름**이 된 것이다 → [[package]]
- **필드가 다른 클래스 타입이면 관계도 클래스가 표현한다** — `Project` 가 `User[] users` 를 갖는 순간 「프로젝트에 팀원이 있다」가 타입으로 적힌다. 그리고 그 관계에 딸린 판단(중복 팀원인가)이 어느 클래스에 살아야 하는지가 곧바로 문제가 된다 → [[cohesion]]
- **클래스 ≠ 소스 파일** — 한 파일에 클래스를 여럿 둘 수 있고 파일명과 같아야 하는 것은 `public` 클래스뿐이다. 컴파일하면 클래스마다 `.class` 가 따로 나온다 → [[java-compilation-unit]] · [[class-file-format]]
- **`vo(dto)` 는 한 이름이 아니다** — 필기가 패키지 이름을 `vo(dto)` 로 적어 둘을 붙여 뒀다. VO 는 담긴 값이 같으면 같은 것으로 취급하는 객체, DTO 는 계층 사이로 데이터를 옮기는 것이 목적인 객체다. 게다가 이 `Score` 는 `compute()` 라는 계산 기능을 가지므로 어느 쪽으로도 딱 떨어지지 않는다. **패키지 이름은 그 안의 클래스가 어떤 규약을 따르는지 선언하는 자리**라서, 두 이름을 겹쳐 두면 나중에 어느 규약으로 읽어야 하는지가 흐려진다 → [[package]]
