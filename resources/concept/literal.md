# 리터럴 (Literal)

코드에 값을 직접 적은 것. **적는 방식이 그 값의 [[data-type]] 을 정한다** — 같은 `100` 도 표기에 따라 다른 크기의 정수가 된다.

## 정의

정수 리터럴은 기본이 4바이트다. 8바이트로 쓰려면 접미사 `L` 을 붙인다.

| 표기 | 크기 |
|---|---|
| `100` | 4 byte (`int`) |
| `100L` | 8 byte (`long`) |

`l`(소문자)도 되지만 **대문자를 쓴다** — 소문자 `l` 은 숫자 `1` 과 헷갈린다.

4바이트 범위를 넘는 값을 접미사 없이 쓰면 **컴파일 오류**다. 값이 커서가 아니라, 그 표기가 4바이트를 뜻하기 때문이다.

```java
System.out.println(2147483647);    // 4바이트 최대값 — 된다
// System.out.println(2147483648); // 컴파일 오류
System.out.println(2147483648L);   // L 을 붙이면 된다
```

### 비트 수와 정수 범위

크기가 범위를 정하는 계산은 이렇다.

| 비트 | 음수 없음 | 음수 있음 |
|---|---|---|
| 2 | 0 ~ 3 | −2 ~ 1 |
| 4 | 0 ~ 15 | −8 ~ 7 |
| 8 | 0 ~ 255 | −128 ~ 127 |
| 16 | 0 ~ 65,535 | −32,768 ~ 32,767 |
| 32 | 0 ~ 4,294,967,295 | −2,147,483,648 ~ 2,147,483,647 |

음수가 있으면 한 비트를 부호에 쓰므로 양쪽이 절반씩이고, 0 이 양수 쪽에 들어가 음수가 하나 더 넓다 → [[twos-complement]]

## 왜 중요한가

**리터럴 표기가 타입을 결정하므로, 계산 결과도 표기가 정한다.** 4바이트끼리 곱해 4바이트를 넘으면 결과가 잘리는데, 담을 변수가 `long` 이어도 마찬가지다 — 계산이 이미 4바이트로 끝난 뒤에 옮겨 담기 때문이다. 큰 수를 다룰 때 리터럴에 `L` 을 붙여야 하는 이유가 이것이다.

컴파일 오류로 미리 막힌다는 점도 값이다. 범위를 넘는 리터럴은 실행 전에 걸리므로, 실행 중에 조용히 잘리는 것과 달리 알아차릴 수 있다.

## 경계와 오해

- **`100` 과 `100L` 은 다른 값이다** — 같은 수를 뜻하지만 크기가 다른 정수다. 담기는 비트 수가 다르므로 같은 것으로 보면 안 된다.
- **변수 타입이 리터럴 타입을 바꾸지 않는다** — `long x = 2147483648;` 은 오류다. 대입받을 자리가 8바이트여도 오른쪽 리터럴은 여전히 4바이트로 해석된다.
- **접미사가 필요한 쪽과 그렇지 않은 쪽이 있다** — 정수는 큰 쪽(`long`)에 접미사를 붙이지만, 실수는 작은 쪽(`float`)에 `f` 를 붙인다. 각 계열의 기본값이 `int`·`double` 이기 때문이다.
