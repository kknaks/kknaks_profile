# 분산 환경의 세션 (외부 세션 저장소)

**서버가 여러 대가 되는 순간 「서버 메모리에 담아 둔 세션」이 깨진다.** 두 번째 요청이 다른 서버로 가면 그 서버는 그 사용자를 모른다.

## 정의

```
[한 대일 때]      요청 ─▶ 서버 A (세션: 로그인함)     ✔

[여러 대일 때]    요청1 ─▶ 파드 A (세션 생성)
                  요청2 ─▶ 파드 B (그런 세션 없음)   ✘  ← 로그아웃된 것처럼 보인다
```

**로드밸런서가 라운드로빈으로 나누기 때문**이다 — 쿠버네티스 서비스도 파드들에 요청을 돌아가며 보낸다 → [[kubernetes]] · [[reverse-proxy]]

답이 셋이고, 이 회차는 두 번째를 골랐다.

| 방법 | 어떻게 | 대가 |
|---|---|---|
| **스티키 세션** | 같은 사용자를 **늘 같은 서버로** 보낸다 | 그 서버가 죽으면 세션도 죽는다. 부하가 고르지 않다 |
| **외부 저장소** | 세션을 **Redis 같은 곳에 모아 둔다** | 저장소가 하나 더 늘고, 그것이 단일 실패 지점 |
| **무상태(토큰)** | 세션을 **아예 안 쓴다** → [[jwt]] | 발급한 것을 취소하기 어렵다 |

## 왜 중요한가

**「서버를 늘리면 처리량이 는다」가 성립하려면 상태가 서버에 없어야 한다.** 세션·파일·캐시가 각 서버 안에 있으면, 늘리는 순간 **각자 다른 것을 보게 된다** → [[distributed-processing]]

이 실습이 그 조각을 하나씩 밖으로 내보낸 흐름이 보인다.

| 상태 | 어디로 옮겼나 |
|---|---|
| 업로드 파일 | 오브젝트 스토리지 → [[object-storage]] |
| 세션 | **외부 세션 저장소** |
| 데이터 | 처음부터 DB → [[data-source]] |

**남는 것이 없어야 컨테이너를 마음대로 늘리고 줄일 수 있다** → [[container]] · [[kubernetes-workload]]

## 경계와 오해

- **세션 저장소를 둔다고 세션이 공짜가 되지는 않는다** — 요청마다 그 저장소를 왕복하므로 **네트워크 한 번이 더 붙는다.** 토큰 방식이 그것마저 없애는 대신 다른 것을 포기한다 → [[jwt]]
- **세션 저장소가 새 단일 실패 지점이다** — 그것이 죽으면 **모든 서버가 동시에** 사용자를 잃는다
- **세션 정보는 노출되면 안 된다** — 필기가 Redis 포트를 **기본적으로 막아 둔다**고 적은 이유다. 세션 저장소가 열려 있으면 남의 로그인을 그대로 가져갈 수 있다 → [[spring-security]]
- **스티키 세션은 「임시 방편」으로 자주 쓰인다** — 코드를 안 고쳐도 되므로 편하지만, **배포할 때마다 파드가 바뀌면 그때 세션이 날아간다.** 무중단 배포와 상성이 나쁘다 → [[zero-downtime-deployment]]
- **저장소를 바꾸는 것은 설정 문제에 가깝다** — 스프링에서는 세션 저장소를 Redis 로 바꾸는 것이 의존성과 속성 몇 줄이다. **어려운 것은 「무엇이 상태인가」를 알아내는 쪽**이다 → [[spring-boot]]
- **세션과 캐시를 같은 저장소에 두는 것은 다른 결정이다** — 캐시는 잃어도 다시 만들면 되지만 **세션은 잃으면 사용자가 로그아웃된다.** 수명과 중요도가 다르다 → [[caching]]
