# 조회가 데이터를 바꿀 때 (읽기의 부수효과)

「읽기」로 이름 붙인 연산이 **실제로는 데이터를 고치는** 상태. 조회수가 그 첫 예다 — 게시글을 열어 보기만 했는데 저장된 값이 하나 늘어난다.

## 정의

읽기만 하는 연산은 **몇 번 불러도 결과와 데이터가 같다.** 부수효과가 붙으면 그 성질이 사라진다.

| | 부르기 전과 후 | 두 번 불렀을 때 |
|---|---|---|
| 부수효과 없는 조회 | 데이터 그대로 | 같은 결과 |
| 부수효과 있는 조회 | 데이터가 바뀐다 | 다른 결과 |

```java
Board board = boards[boardNo - 1];
board.setViewCount(board.getViewCount() + 1);   // 읽으러 왔는데 쓴다
```

이 한 줄은 세 단계다 — **읽고 · 더하고 · 다시 쓴다** → [[increment-operator]]

## 사용 예시

같은 데이터를 다루는 두 화면이 서로 다르게 행동한다.

```java
private static void listBoard() {                 // 목록 — 조회수를 보여만 준다
  for (int i = 0; i < boardLength; i++) {
    Board board = boards[i];
    System.out.printf("%d %s %tY-%3$tm-%3$td %d", (i + 1), board.getTitle(),
        board.getCreatedDate(), board.getViewCount());
  }
}

private static void viewBoard() {                 // 조회 — 보여 주면서 올린다
  ...
  Board board = boards[boardNo - 1];
  board.setViewCount(board.getViewCount() + 1);
  ...
  System.out.printf("조회수: %d", board.getViewCount());
}
```

**목록에서 스무 번 봐도 조회수는 안 오르고, 조회로 한 번 들어가면 오른다.** 그래서 이 숫자의 뜻은 「본 횟수」가 아니라 **「조회 화면을 띄운 횟수」**다. 세는 코드가 어디 있는지가 곧 그 숫자의 정의다.

그리고 이 필기는 **변경에서도 올린다.**

```java
private static void updateBoard() {
  ...
  Board board = boards[boardNo - 1];
  board.setViewCount(board.getViewCount() + 1);          // 고치러 왔는데 조회수가 오른다
  board.setTitle(Prompt.input("제목(%s)?", board.getTitle()));
  board.setContent(Prompt.input("내용(%s", board.getContent()));
}
```

필기가 그렇게 정해 두었다 — 「글 변경은 제목과 내용을 변경하고 조회수를 하나 증가 시킨다」. 그러면 작성자가 오타를 세 번 고칠 때마다 조회수가 셋 오른다. **부수효과가 한 연산에서 옆 연산으로 번지면 숫자의 뜻이 미끄러진다.**

`viewBoard` 는 올린 뒤에 찍는다는 것도 화면에 그대로 드러난다.

```java
board.setViewCount(board.getViewCount() + 1);
...
System.out.printf("조회수: %d", board.getViewCount());   // 처음 열어도 1 이 보인다
```

### 다음 회차의 `getSeqNo()` 는 부수효과가 전부다

조회수는 「보여 주는 일에 세는 일이 딸려 온 것」이었다. 그 다음 회차에는 **부르는 것 자체가 목적인 부수효과**가 나온다.

```java
public static int getSeqNo() {
  return ++seqNo;                       // 올리고, 올린 값을 준다
}
```

이름은 getter 인데 **두 번 부르면 다른 값이 오고, 부른 흔적이 남는다.** 조회수와 방향이 반대다 — 조회수는 값을 보여 주려고 부르면서 세는 것이 딸려 왔고, 이쪽은 **번호를 하나 소비하려고** 부르는데 값을 돌려받는 것이 딸려 온다 → [[surrogate-key]]

| | `getViewCount()` | `getSeqNo()` |
|---|---|---|
| 두 번 부르면 | 같은 값 | **다른 값** |
| 부수효과의 위치 | 부르는 쪽(`setViewCount(...+1)`) | **메서드 안** |
| 부수효과가 | 딸려 온 것 | **목적** |
| 안 부르면 | 조회수가 안 오른다 | 번호가 발급되지 않는다 |

그래서 이 메서드는 **부르고 결과를 버리면 안 된다.** `User.getSeqNo();` 한 줄만 실행해도 번호 하나가 사라지고, 그 다음 회원이 받는 번호에 구멍이 생긴다. 「읽기니까 아무 데서나 불러도 된다」가 성립하지 않는 자리다.

필기 자신이 이것을 알아차렸다 — 「데이터 클래스에 seqNo 적용」 절에서는 「시퀀스넘버를 접근하는 **getter** 메서드」로 적고 「Command 클래스 파일 수정」 절에서 `User.getSeqNo()` 로 부르는데, 「클래스 분리하기」 절의 최종 코드는 **`User.getNextSeqNo()`** 다. `get` 에 `Next` 가 붙는 순간 「다음 것을 받아 온다」로 읽히고, 두 번 부르면 다른 값이 온다는 것이 이름에 들어간다. **이름이 정확해지는 방향으로 움직였는데 정의를 같이 고치지 않아 두 절이 어긋나 있다** → [[method]]

## 왜 중요한가

**「읽기는 안전하다」는 가정이 깨진다.** 읽기만 하는 연산은 마음대로 다시 불러도 되고, 그래서 실패했을 때 재시도할 수 있고 결과를 캐시에 둘 수 있고 읽기 전용 복제본으로 보낼 수 있다. 조회가 쓰기를 하면 **그 셋이 전부 막힌다** — 재시도가 조회수를 두 번 올리고, 캐시에 태우면 조회수가 안 오르고, 읽기 전용 쪽에서는 실패한다 → [[caching]]

**세는 자리를 옮기면 숫자의 뜻이 바뀐다.** 목록에 넣으면 노출 횟수가 되고, 조회에 넣으면 열어 본 횟수가 되고, 화면을 그리기 전에 넣으면 「띄우려 한 횟수」가 된다. 조회수처럼 사소해 보이는 값도 **정의가 코드의 위치에 들어 있다.**

**그리고 늘리는 코드가 밖에 있으면 규칙이 흩어진다.** 이 필기는 `viewBoard` 와 `updateBoard` 두 곳에서 `setViewCount(getViewCount() + 1)` 를 쓴다. `Board` 에 `increaseViewCount()` 가 있었다면 「조회수를 어떻게 올리나」가 한 곳에 있고, 「작성자 자기 글은 세지 않는다」 같은 규칙이 생겨도 고칠 자리가 하나다 → [[cohesion]] · [[encapsulation]]

## 경계와 오해

- **부수효과 ≠ 버그** — 조회수 증가는 의도한 동작이다. 문제는 이름(「조회」)과 실제 동작(쓰기)이 갈리는 것이고, 그 사실을 **아는 상태로 두는 것**이 이 개념이 하는 일이다. 「없애야 한다」가 아니라 「어디에 있는지 세어 둔다」다.
- **조회의 부수효과 ≠ 변경의 부수효과** — 이 필기의 `updateBoard` 도 조회수를 올린다. 변경은 이미 쓰기 연산이므로 문제가 안 될 것 같지만, 올라가는 값이 **다른 뜻을 가진 숫자**라는 것이 문제다. 조회수는 「읽힌 횟수」로 읽히는데 여기서는 손댄 횟수가 섞인다.
- **읽고 더해 쓰기는 원자적이지 않다** — 두 사람이 같은 글을 동시에 조회하면 둘 다 `5` 를 읽고 둘 다 `6` 을 쓴다. 하나가 사라진다(lost update). CLI 단일 실행에서는 절대 드러나지 않고 **웹으로 옮기는 순간 그대로 나타난다.** `+ 1` 이라는 모양이 「한 동작」처럼 보이는 것이 원인이다 → [[increment-operator]]
- **부수효과와 출력의 순서가 화면을 바꾼다** — 이 코드는 올린 뒤에 찍으므로 처음 열어도 조회수가 `1` 이다. 순서를 바꾸면 `0` 이 보인다. 어느 쪽이 맞는지는 규칙이 정하는 것이지 코드가 정해 주지 않는다.
- **부수효과에는 되돌릴 자리가 없다** — 조회수를 올린 뒤 출력이 실패해도 숫자는 이미 올라 있다. 「보여 주기」와 「세기」가 한 메서드에 붙어 있어 둘의 성공·실패를 따로 다룰 수 없다 → [[exception-handling]]
- **여기서는 늘어난 값이 저장되지 않는다** — 조회수는 `private static Board[]` 안의 인스턴스에만 남으므로 **프로그램을 끝내면 0으로 돌아간다.** 부수효과의 무게는 그 값이 어디까지 살아남는지에 달려 있고, 파일이나 DB 로 가면 같은 코드가 훨씬 무거워진다 → [[static-member]]
- **모든 파생값 갱신이 부수효과는 아니다** — Day16 의 `setKor` 가 `compute()` 를 불러 합계를 다시 맞추는 것은 **쓰기 연산 안에서 자기 값을 정리하는 일**이다. 부수효과가 문제가 되는 자리는 **읽기라고 이름 붙인 곳**이다 → [[encapsulation]]
- **`get` 접두사가 「읽기」를 보장하지 않는다** — `getSeqNo()` 는 부를 때마다 값을 바꾼다. 자바에서 `get` 은 관례일 뿐 문법이 강제하는 것이 없으므로, **이름으로 안전을 판단하면 이 자리에서 틀린다.** 판단 기준은 이름이 아니라 「두 번 불러도 같은가」다 → [[method]]
- **`getSeqNo()` 의 부수효과는 없앨 수 있는 것이 아니다** — 조회수는 `viewBoard` 밖으로 뺄 수 있지만, 번호 발급은 **올리는 것과 값을 받는 것이 하나여야** 한다. 나눠서 「읽고 · 올린다」로 쓰면 두 사람이 같은 번호를 받는다. 부수효과를 **한 덩어리로 묶는 것이 오히려 정답인 경우**이고, 그래서 이 자리는 고칠 대상이 아니라 이름을 정확히 할 대상이다.
- **읽고 더해 쓰기가 아니라 한 식이다** — `++seqNo` 는 `setViewCount(getViewCount() + 1)` 과 하는 일이 같아 보이지만 **필드 안에서 끝난다.** 그래도 원자적이지는 않다 — 증감 연산자 하나도 바이트코드에서는 읽고·더하고·쓰는 세 단계라, 스레드 둘이면 같은 번호가 두 번 나온다 → [[increment-operator]] · [[bytecode]]
- **`++seqNo` 와 `seqNo++` 의 차이가 번호 체계를 바꾼다** — 전위는 올린 값을 주므로 첫 번호가 `1` 이고, 후위로 쓰면 첫 번호가 `0` 이다. 부수효과와 반환값의 순서가 **화면에 보이는 첫 번호**를 정하는 것이고, 조회수를 올린 뒤에 찍어서 처음 열어도 `1` 이 보이던 것과 같은 종류의 선택이다 → [[increment-operator]] · [[one-based-numbering]]
