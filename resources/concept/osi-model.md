# OSI 7계층과 캡슐화

**통신을 층으로 나누고, 내려가며 헤더를 붙이고 올라가며 벗기는 구조.** 각 층은 **자기 헤더만 보고** 자기 일을 한다.

## 정의

```
송신자                                        수신자
7 응용    HTTP 요청 만들기                     7 응용    데이터를 프로그램에
6 표현                                         6 표현
5 세션                                         5 세션
4 전송    + TCP 헤더(포트)  = 세그먼트          4 전송    포트 보고 헤더 벗김
3 네트워크 + IP 헤더        = 패킷              3 네트워크 IP 맞으면 헤더 벗김
2 데이터링크 + MAC 헤더     = 프레임             2 데이터링크 MAC 맞으면 헤더 벗김
1 물리    전기신호로 변환                       1 물리    전기신호를 프레임으로
          │                                            ▲
          └──────── 스위치 · 라우터 ────────────────────┘
```

**내려갈 때마다 이름이 바뀐다** — 데이터 → 세그먼트 → 패킷 → 프레임 → 전기신호. **감싸는 것(캡슐화)**이고, 받는 쪽은 **거꾸로 벗긴다.**

### 구간마다 무엇이 바뀌나

`https://www.google.com` 을 열 때 실제로 일어나는 일에서 두 주소의 성격이 갈린다.

| | 출발지·목적지 IP | 출발지·목적지 MAC |
|---|---|---|
| 내 컴퓨터 → 스위치 | 나 → 구글 | 나 → **내 라우터** |
| 라우터 → 라우터 | 나 → 구글 | 앞 라우터 → 다음 라우터 |
| 라우터 → 수신자 | 나 → 구글 | 그 라우터 → **구글 서버** |

**IP 는 끝까지 그대로, MAC 은 구간마다 바뀐다** — 「최종 목적지」와 「다음에 넘길 상대」를 각각 다른 층이 들고 있기 때문이다 → [[ip-address]] · [[mac-address]]

그래서 **다른 망으로 보낼 때 프레임의 목적지 MAC 은 상대가 아니라 내 라우터**다. 상대의 MAC 은 알 수도 없다(브로드캐스트가 라우터를 못 넘으므로) → [[network-layer]]

### 장비가 어느 층까지 보나

| 장비 | 보는 것 |
|---|---|
| 허브·리피터 | 전기신호만 → [[physical-layer]] |
| **스위치** | 프레임의 **MAC** → [[data-link-layer]] |
| **라우터** | 패킷의 **IP** → [[network-layer]] |

**라우터는 이더넷 헤더를 떼어 내고 IP 를 본 뒤 새 헤더를 붙여 보낸다** — 그래서 MAC 이 바뀐다.

## 왜 중요한가

**층을 나눈 덕에 한 층만 바꿔도 나머지가 그대로다.** 유선을 무선으로 바꿔도 위층은 모르고, HTTP 를 다른 프로토콜로 바꿔도 아래층은 그대로다 → [[wireless-lan]] · [[network-protocol]]

**그리고 문제를 찾을 때 층으로 좁힐 수 있다.** 「핑은 되는데 접속이 안 된다」는 3계층은 되고 4계층 위가 안 된다는 뜻이다 — **어느 층까지 됐는지**가 곧 진단이다 → [[port-number]] · [[socket-binding]]

**계층은 이 레포의 다른 개념들이 왜 그렇게 생겼는지도 설명한다.** 소켓이 바이트만 주는 것, 프로토콜을 따로 정해야 하는 것, 프레임 크기 때문에 나눠 보내야 하는 것이 전부 이 구조의 결과다 → [[socket]] · [[length-prefix-framing]]

## 경계와 오해

- **7계층을 다 쓰는 것이 아니다** — 실제 인터넷은 TCP/IP 4계층 모델로 돌고, 5·6계층은 응용계층에 녹아 있다. **OSI 는 설명을 위한 모델**이라는 것을 알고 봐야 한다
- **계층이 순서를 뜻하지는 않는다** — HTTP 요청 전에 DNS 질의(7계층)가 이미 끝나 있어야 한다. **위아래는 포함 관계이지 시간 순서가 아니다** → [[domain-name-system]]
- **헤더가 붙는 만큼 실제 데이터 비율이 준다** — 작은 데이터를 자주 보내면 **헤더가 본문보다 클 수도** 있다. 폴링이 비싼 이유 중 하나다 → [[polling]]
- **「캡슐화」가 객체지향의 그것과 이름만 같다** — 여기서는 **감싸서 아래층에 넘긴다**는 뜻이다 → [[encapsulation]]
- **라우터가 헤더를 「뜯어본다」는 것은 매 홉의 비용이다** — 지날 때마다 헤더를 벗기고 붙이므로, **홉이 많을수록 느려진다** → [[remote-procedure-call]]

## 출처

- [[2024-12-06-chapter8-apply]] — **앞의 여섯 장을 하나의 요청으로 꿰는 장**이다. `https://www.google.com` 을 여는 예로 송신자가 7 → 1 로 내려가며 **HTTP 요청 → TCP 헤더(세그먼트) → IP 헤더(패킷) → MAC 헤더(프레임) → 전기신호**로 감싸는 과정을 계층마다 한 절씩 적었고, 수신자 쪽은 1 → 7 로 **헤더를 하나씩 벗기며** 확인하는 과정을 적었다. 가장 값진 것은 「장비 관점에서의 데이터 흐름」이다 — **「다른 네트워크 간의 통신의 경우 송신자의 컴퓨터는 송신자가 속한 라우터 MAC 주소로 기입」**하고, 라우터가 「수신자의 MAC 주소 부분이 자신의 MAC 주소와 같으면 이더넷 헤더를 떼어내고」 IP 를 본 뒤 **새 MAC 으로 바꿔** 보낸다는 것을 단계마다 그림과 함께 남겼다. **IP 는 그대로이고 MAC 만 구간마다 바뀐다**는 이 책의 핵심이 여기서 완성된다. 다만 본문이 「응용계층」 제목에서 끊긴다 → [[ip-address]] · [[mac-address]]
