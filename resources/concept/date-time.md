# 시각을 값으로 담기 (java.util.Date)

시각을 「2024-06-19」 같은 **문자열이 아니라 시각 전용 타입**으로 담는 것. 값은 한 번 담고 보여 줄 때 형식을 입힌다 — **저장과 표시를 가르는 것**이 이 개념의 몸통이다.

## 정의

`java.util.Date` 는 클래스이므로 [[data-type]] 상 참조 타입이고, `java.lang` 이 아니라서 `import` 가 필요하다 → [[package]]

```java
import java.util.Date;

private Date createdDate;                   // 필드의 타입이 된다
board.setCreatedDate(new Date());           // 인수 없는 생성자 = 「지금」
```

- **`new Date()` 는 그 객체를 만든 순간의 시각을 담는다.** 인수를 받지 않는 생성자가 시스템 시계를 읽는다 → [[constructor]]
- 안에 든 것은 연·월·일이 아니라 **1970-01-01 00:00:00 UTC 부터 흐른 밀리초 하나**다. 사람이 읽는 모양은 출력할 때 만들어진다 → [[format-string]]

```java
System.out.printf("작성시간: %tY-%1$tm-%1$td %1$tH:%1$tM:%1$tS", board.getCreatedDate());
```

## 사용 예시

게시글의 네 필드 중 **작성날짜만 사용자에게 묻지 않는다.**

```java
private static void addBoard() {
  Board board = new Board();
  board.setTitle(Prompt.input("제목?"));      // 묻는다
  board.setContent(Prompt.input("내용?"));    // 묻는다
  board.setCreatedDate(new Date());          // 묻지 않는다 — 프로그램이 정한다
  boards[boardLength++] = board;
}
```

그리고 같은 값이 화면마다 다른 형식으로 나온다.

| 화면 | 서식 | 보이는 것 |
|---|---|---|
| 목록 | `%tY-%3$tm-%3$td` | `2024-06-19` |
| 조회 | `%tY-%1$tm-%1$td %1$tH:%1$tM:%1$tS` | `2024-06-19 14:07:52` |

**저장된 것은 하나고 형식이 둘이다.** 목록에 날짜만 보이는 것은 값에 시·분·초가 없어서가 아니라 그 자리표를 안 썼기 때문이다.

같은 프로그램 안에 **다른 선택도 남아 있다.** 앞 회차의 `Project` 는 기간을 문자열로 받았다.

```java
// Project — 사용자가 입력한 문자열을 그대로 담는다
private String startDate;
private String endDate;

// Board — 시각 타입으로 담는다
private Date createdDate;
```

`Project` 쪽은 사람이 입력하는 값이고 `Board` 쪽은 프로그램이 만드는 값이라서 이렇게 갈렸다. **입력이 문자열로 들어온다는 사실이 저장까지 문자열이어야 할 이유는 아니다** — 두 방식이 나란히 있는 이 코드가 그 차이를 보여 주는 표본이다.

### 시각을 읽는 것에서 날짜를 계산하는 것으로

**열엿새 뒤 팀 프로젝트는 시각을 담는 데서 끝나지 않고 날짜를 옮기고 되돌아간다.** 「일과 종료 시 저장된 ToDoList 객체를 ArrayList에 추가」한 뒤 「새로운 ToDoList 객체생성 및 날짜 조정」을 하고, 조회 쪽은 「당일 날짜 값을 가지고 그 주 첫째날을 계산」해 「일주일 날짜, 당일 달성률, 누적 달성률」을 한 화면에 모은다 → [[gamification]]

**`new Date()` 로는 둘 다 안 된다.** 하나는 시각에 하루를 더하는 일이고, 다른 하나는 시각에서 요일을 꺼내 그만큼 되돌아가는 일이다. `java.util.Date` 에서 그 두 가지를 하는 메서드(`getDay`·`setDate`)는 deprecated 이므로, **이 자리가 `Calendar`(현행으로는 `java.time` 의 `LocalDate`)가 필요해지는 첫 지점**이다. 시각을 값으로 담는 것과 날짜를 연산하는 것은 같은 타입이 맡는 일이 아니다.

### 한 달 뒤 — 표시 형식이던 것이 저장 형식이 된다

Day18 에서 형식은 **화면의 문제**였다. 목록과 조회가 같은 값을 다르게 찍었고, 틀리면 눈에 보였다. Day40 이 이 값을 파일로 내보내면서 형식의 성격이 바뀐다.

```text
json파일에 데이터 타입이 "createdDate":"Jul 22, 2024, 5:13:25 PM"으로 출력이 된다.
```

**JSON 에는 날짜 타입이 없어서 시각이 문자열로 나간다.** 안에 든 것이 밀리초 하나인 값을 파일에 적으려면 표기를 골라야 하고, 그 선택이 **저장 형식**이 된다 → [[json]]

```java
new GsonBuilder().setDateFormat("yyyy-MM-dd HH:mm:ss").create()
```

여기 쓰는 패턴은 `%t` 서식과 **다른 형식 언어**(`SimpleDateFormat`)다.

| 패턴 | 뜻 |
|---|---|
| `yyyy` | 연 (4자리) |
| `MM` | **월** |
| `dd` | 일 |
| `HH` | 시 (24시간) |
| `mm` | **분** |
| `ss` | 초 |

**「저장과 표시를 가른다」의 대가가 여기서 나온다.** 값이 하나이므로 형식은 여러 개일 수 있는데, 그중 **파일로 나가는 형식은 되읽는 쪽과 반드시 같아야 한다** — 화면 형식이 틀리면 이상하게 보이고 끝이지만, 저장 형식이 어긋나면 **값이 변한다**(아래 첫 항목).

## 왜 중요한가

**문자열로 담으면 비교와 정렬이 사전순이 된다.** `"2024-6-9"` 와 `"2024-06-19"` 는 사람에게는 순서가 분명한데 문자열로는 앞이 뒤로 간다. 시각 타입은 안에 든 것이 숫자 하나라서 크기 비교가 곧 시간 순서다 → [[string-comparison]]

**들어올 수 있는 값의 범위가 달라진다.** `String startDate` 에는 `"어제"`·`"2024/6/19"`·빈 문자열이 다 들어간다. 타입이 `Date` 면 시각이 아닌 것은 **애초에 대입되지 않는다.** 검사 코드를 쓰지 않고 얻는 보장이다.

**그리고 형식이 저장에 섞이지 않는다.** 문자열로 담아 두면 그 문자열의 모양이 곧 저장 형식이 되어, 화면을 바꾸려면 저장된 값의 형식을 바꿔야 한다. 시각 타입은 표시 형식을 화면 쪽에 남겨 두므로 **목록과 조회가 다른 모양으로 찍는 일이 저장을 건드리지 않고** 된다.

## 경계와 오해

- **`mm` ≠ `MM` — 그리고 `%t` 서식에서는 규칙이 정확히 반대다** — `SimpleDateFormat` 에서 **월은 `MM`, 분은 `mm`** 이다. 그런데 Day18 부터 써 온 `%t` 서식은 **월이 `%tm`(소문자), 분이 `%tM`(대문자)** 다 — 같은 두 글자가 두 언어에서 뒤집혀 있다. Day40 의 `saveJson` 이 `"yyyy-mm-dd HH:mm:ss"` 로 적힌 것이 그 습관에서 나온 것으로 보이고, **결과는 조용한 데이터 손상**이다: 2024-07-22 17:13:25 이 월 자리에 분을 넣어 `"2024-13-22 17:13:25"` 로 저장되고, `loadJson` 은 `MM` 으로 읽어 **13월** 로 해석하며, `SimpleDateFormat` 은 기본이 lenient 라 예외 대신 **다음 해 1월** 로 넘긴다. **왕복마다 연도가 1년씩 밀리고 월은 1월에 고정된다** → [[json]] · [[format-string]]
- **파싱이 관대한 것이 형식 검사를 대신하지 않는다** — `SimpleDateFormat` 은 기본 `lenient = true` 라 13월·32일·25시를 **예외 없이 자리올림**해서 받아들인다. 「파싱에 성공했다」가 「형식이 맞았다」가 아니고, 엄격하게 받으려면 `setLenient(false)` 를 켜야 한다. **틀린 값이 예외로 드러나지 않는 종류의 입력** → [[exception-handling]]
- **`HH` ≠ `hh`** — `HH` 는 0~23, `hh` 는 1~12 다. `hh` 로 저장하면 오전·오후 표시(`a`)를 함께 적지 않는 한 **오후 5시와 오전 5시가 같은 문자열**이 되어 되읽을 때 12시간이 사라진다. Gson 의 기본 출력 `5:13:25 PM` 이 12시간 표기여서 더 헷갈리는 자리다.
- **`"yyyy-MM-dd HH:mm:ss"` 에는 타임존이 없다** — `Date` 가 담는 것은 UTC 기준 밀리초인데, 이 형식으로 적는 순간 **어느 지역의 시각인지가 파일에서 사라진다.** 같은 파일을 다른 타임존에서 읽으면 그 지역 기준으로 해석되어 **다른 순간**이 되고, 서버가 UTC 인 곳에 배포하면 9시간이 어긋난다. ISO 8601(`yyyy-MM-dd'T'HH:mm:ssXXX`)이 오프셋을 함께 적는 이유이고, 저장 형식으로는 그쪽이 표준이다 → [[platform-dependency]]
- **`Date` ≠ 날짜** — 이름이 `Date` 지만 담는 것은 시각이다. `%tH:%tM:%tS` 가 값에서 나오는 것이 그 증거다. 「날짜만 담긴다」로 읽으면 같은 날 쓴 두 글의 작성일이 왜 다른 값인지 설명되지 않는다.
- **`new Date()` 는 「오늘」이 아니라 「지금」이다** — 이 필기의 "날짜는 당일 날짜를 받아온다" 는 절반만 맞다. 시·분·초·밀리초까지 들어가므로 1초 뒤에 등록한 글은 다른 값을 갖는다. 목록에서 날짜만 보이니 같아 보이는 것이다.
- **`java.util.Date` 는 지금 새로 쓸 타입이 아니다** — Java 8 부터 `java.time` 의 `LocalDateTime`·`LocalDate`·`Instant` 가 이 자리를 대체했고, `Date` 의 `getYear()`·`getMonth()` 등은 deprecated 다. 2024년의 실습이 배운 것이 **현행 권장과 다른 자리**이므로, 여기서 익힌 것은 「시각을 타입으로 담는다」는 판단이고 클래스 이름 쪽은 아니다.
- **`java.util.Date` ≠ `java.sql.Date`** — 이름이 같아서 IDE 의 `import` 자동 완성이 다른 쪽을 고를 수 있다. `java.sql.Date` 는 시·분·초를 버리는 쪽이라 **`%tH` 가 0으로 찍히기 시작한다.** 컴파일도 되고 예외도 없다 → [[package]]
- **`Date` 는 가변 객체다** — `getCreatedDate()` 가 돌려주는 것은 주소이고, 받은 쪽이 `setTime()` 으로 그 값을 바꾸면 `private` 필드가 밖에서 바뀐다. `Project.getUsers()` 가 배열을 통째로 내주던 구멍과 **같은 구멍의 다른 타입**이다 → [[encapsulation]] · [[object-reference]]
- **작성 시각은 등록 때 한 번 정해지는 값이다** — 이 필기의 `updateBoard` 가 작성날짜를 건드리지 않는 것은 맞는 선택이다. 다만 `setCreatedDate` 가 열려 있어 그 규칙이 문법으로 막혀 있지는 않다. 「고쳐도 작성일은 그대로」는 코드가 지키는 것이 아니라 안 부르는 것으로 지켜지고 있다.
- **채우지 않으면 `null` 이다** — 참조 타입이므로 등록에서 `setCreatedDate` 를 빼먹으면 `0` 이 아니라 `null` 이 남는다. `int viewCount` 가 `0` 으로 시작해 그냥 쓸 수 있는 것과 갈린다 → [[default-initialization]]
- **시각을 읽는 것 ≠ 날짜를 상태로 들고 있는 것** — 이 필기의 `new Date()` 는 필요할 때 시스템 시계를 한 번 읽는다. 열엿새 뒤 프로젝트는 「당일 날짜」를 프로그램이 들고 있다가 「일과종료」 명령에서 스스로 조정하므로, **프로그램이 아는 날짜와 시계의 날짜가 어긋날 수 있다** — 하루에 「일과종료」를 두 번 누르면 이틀이 지나고, 사흘 동안 안 켜면 하루만 지난다. 시계를 읽는 구조에는 없던 일이고, 날짜를 상태로 들면 **켤 때마다 시계와 맞추는 일**이 따로 필요해진다 → [[command-loop]]
- **「그 주 첫째날」은 계산 문제가 아니라 정의 문제로 시작한다** — 주의 시작이 일요일인지 월요일인지 정하지 않으면 같은 날이 다른 주에 들어가고, 주간 화면의 달성률이 사람마다 다르게 나온다. `java.util.Calendar` 의 `DAY_OF_WEEK` 는 **일요일이 `1`** 이고, `Calendar.getInstance()` 가 정하는 `firstDayOfWeek` 는 **로케일에 따라 달라진다.** 그래서 한국 환경에서 맞던 계산이 다른 로케일에서 하루 밀리는데, 예외도 오류도 없이 **잘못된 주가 조용히 나온다.**
- **날짜를 뺄셈으로 되돌리면 월·연 경계에서 깨진다** — 첫째날을 「일(日) 필드 − 요일 번호」로 구하면 매달 1~6일에 0이나 음수가 나온다. 날짜에는 **자리내림**이 있으므로 필드를 직접 고치지 말고 `Calendar.add(Calendar.DATE, -n)`(현행으로는 `LocalDate.minusDays(n)`)에 맡겨야 한다. 같은 이유로 「하루 더하기」도 `날짜 + 1` 이 아니다.
