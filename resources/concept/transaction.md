# 트랜잭션과 autocommit (commit · rollback)

**여러 문장을 「전부 되거나 전부 안 되는」 한 덩어리로 묶는 것, 그리고 그 덩어리의 경계를 누가 정하는지의 설정.** Day52 는 [[dml]] 세 문장을 배운 직후 이 절로 넘어간다 — `update`·`delete` 를 배운 다음에 나올 수밖에 없는 절이다. 시작점은 한 줄이다: **「mysql은 autocommit의 기본 값이 true이다」.**

## 정의

`autocommit` 은 **문장 하나가 곧 트랜잭션 하나인가**를 정하는 스위치다. Day52 는 `false` 쪽만 자세히 적었으므로 두 쪽을 나란히 세운다.

| | `autocommit = true` (MySQL 기본) | `autocommit = false` |
|---|---|---|
| 트랜잭션의 범위 | **문장 하나** | `commit`/`rollback` 까지의 **문장 여럿** |
| 확정 시점 | 문장이 성공한 순간 | `commit` 을 실행한 순간 |
| 되돌리기 | **없다** (문장이 이미 끝났다) | `rollback` 으로 시작 시점까지 |
| 남이 내 변경을 보는 시점 | 문장 직후 | `commit` 이후 |
| 내가 남의 변경을 보는 시점 | 문장마다 최신 | **트랜잭션이 끝날 때까지 안 보인다** (아래) |
| 잠금이 풀리는 시점 | 문장 직후 | `commit`/`rollback` 시 |

**「되돌릴 수 있는가」와 「남이 언제 보는가」가 같은 스위치에 묶여 있다.** 되돌릴 여지를 남기려면 아직 확정하지 않아야 하고, 확정하지 않은 것은 남에게 보일 수 없기 때문이다.

### 수동 커밋으로 바꾸기

```sql
set autocommit = false;
```

그다음 Day52 의 두 줄이 규칙이다 — 「삽입/변경/삭제한 데이터를 서버에 올리려면 **commit** 을 수행」하고 「취소하려면 **rollback** 을 수행」한다. 조회에는 이 둘이 필요 없다 → [[dql]]

### Day52 가 창을 두 개 열고 확인한 것

`autocommit` 이 `false` 인 쪽에서 필기가 적은 세 줄이 트랜잭션의 성질을 셋 다 짚고 있다.

| Day52 의 문장 | 무엇을 본 것인가 |
|---|---|
| 「조회 시 마지막으로 커밋한 테이블과 임시저장소에 저장된 내용이 출력된다」 | **내 트랜잭션 안에서는 내 변경이 보인다** |
| 「커밋이후에 다른 서버에서 변경한 내용은 조회가 불가능하다」 | **내가 보는 데이터에 시점이 있다** (스냅샷) |
| 「다른 서버는 수동commit서버의 수정내용을 commit 전 까지는 확인 할 수 없다」 | **확정되지 않은 변경은 남에게 보이지 않는다** (dirty read 없음) |

세 번째는 정확하고, 앞의 두 줄은 관찰은 맞지만 설명이 어긋난다 — 아래 「경계와 오해」의 처음 세 항목이 그것이다.

## 사용 예시

Day52 의 실험을 문장 순서로 세우면 이렇게 된다.

```sql
set autocommit = false;

insert into test1(no, name) values(10, 'aaa');
select * from test1;      -- 내 창에서는 10번 행이 보인다

rollback;                 -- 취소
select * from test1;      -- 10번 행이 없다

insert into test1(no, name) values(11, 'bbb');
commit;                   -- 확정 — 이제 다른 창에서도 보인다
```

**`rollback` 과 `commit` 사이에 있는 동안 같은 `select` 가 두 창에서 다른 답을 준다.** 이것이 「데이터가 하나」라는 감각이 처음 흔들리는 자리이고, 자바에서 변수 하나를 두 곳에서 읽으면 늘 같은 값이던 것과 갈린다 → [[client-server-model]]

## 왜 중요한가

**「절반만 실행된 상태」를 만들지 않을 수 있다.** 계좌에서 빼고 다른 계좌에 넣는 두 `update` 사이에서 연결이 끊기면, 자동 커밋에서는 **돈이 사라진 상태**가 남는다. 두 문장을 한 트랜잭션으로 묶으면 그 중간 상태가 저장되지 않는다 — 이것이 원자성(atomicity)이고, **DB 를 파일 저장과 가르는 첫 성질**이다 → [[serialization]]

**`where` 를 빼먹은 `update` 를 구제할 수 있는지가 이 설정 하나에 달려 있다.** Day52 가 `update`·`delete` 를 배운 직후 이 절로 온 것이 그래서 필연이다. 기본값이 `true` 이므로, **아무 설정도 하지 않은 상태에서 전체 행을 날린 것은 되돌릴 방법이 없다** — 백업에서 복구하는 일이 된다 → [[dml]]

**그리고 「내가 보는 데이터」에 시점이 생긴다.** 조회가 지금 이 순간의 테이블이 아니라 **내 트랜잭션이 잡은 시점**을 보므로, 한 트랜잭션 안에서 같은 조회를 두 번 하면 남이 무엇을 하든 같은 답이 온다. 화면 하나를 만들며 조회를 다섯 번 해도 서로 어긋나지 않는 것이 이 성질에 얹혀 있다.

## 경계와 오해

- **DB 의 `commit` ≠ git 의 `commit`** — 이름이 같고 「확정한다」는 느낌도 같아서 그대로 겹쳐 읽게 되는데, 세 가지가 다르다. ① git 의 `commit` 은 **로컬에 버전을 남기는 것**이고 남에게 보이려면 `push` 가 더 필요하지만, DB 의 `commit` 은 **그 순간 모든 세션에 보인다.** ② git 은 `commit` 뒤에도 되돌릴 수 있지만(`reset`·`revert`) DB 는 **`commit` 전까지만** `rollback` 이다. ③ git 은 `add` 로 담을 것을 고르는데 DB 에는 고르는 단계가 없다 — 트랜잭션 안의 변경 **전부**가 함께 확정되거나 함께 취소된다 → [[git]] · [[staging-area]]
- **「임시저장소에 저장된다」는 실물과 다르다** — 커밋하지 않은 변경은 어딘가에서 대기하다가 `commit` 때 옮겨지는 것이 아니라, **이미 실제 데이터 페이지에 반영**되어 있고 대신 **되돌릴 재료(undo log)** 가 따로 적힌다. 그래서 두 가지가 필기의 모델로는 설명되지 않는다: `commit` 이 거의 즉시 끝나는데 **큰 `rollback` 은 오래 걸린다**(되돌리는 일이 실제 작업이다), 그리고 커밋 안 한 변경도 **디스크에 이미 쓰여 있을 수 있다.** 「대기실」이 아니라 「되돌릴 기록을 남기고 먼저 반영한다」가 정확한 그림이다. 필기가 `staging area` 를 「임시저장소」로 부르는 [[git]] 을 먼저 배웠기 때문에 그 감각이 옮겨 온 것으로 보인다 → [[staging-area]]
- **「다른 서버」가 아니라 「다른 세션」이다** — 필기는 창을 두 개 열어 실험하고 그것을 「다른 서버」라 적었다. 서버는 하나이고 **접속(세션·커넥션)이 둘**이다. `autocommit` 은 **세션 변수**라서 한 창에서 끄면 그 창에서만 꺼지고, 옆 창은 여전히 자동 커밋이다. 하루 전 Day51 이 `'study'@'%'` 를 「원격에서만 접속」이라 읽은 것과 **같은 축의 혼동**이다 — 접속이 어디서 왔는지와 서버가 몇 대인지를 가르지 않은 것이다 → [[database-user]] · [[client-server-model]] · [[socket]]
- **「커밋 이후에 다른 서버에서 변경한 내용은 조회가 불가능하다」의 이유는 커밋 순서가 아니다** — InnoDB 의 기본 격리 수준이 **REPEATABLE READ** 라서, 트랜잭션이 처음 조회한 시점의 **스냅샷**을 끝까지 계속 본다. 남이 커밋해도 내 트랜잭션은 과거를 보고 있으므로 화면이 바뀌지 않고, 내가 `commit` 이나 `rollback` 을 하면 다음 조회부터 새 스냅샷이라 그때 보인다. **「조회가 불가능하다」가 아니라 「내가 아직 과거를 보고 있다」**이고, `set transaction isolation level read committed` 로 바꾸면 같은 실험에서 남의 커밋이 **바로 보인다.** 즉 필기가 본 현상은 MySQL 의 기본 설정이 정한 것이지 트랜잭션의 정의가 아니다.
- **`autocommit` 을 끄는 것이 곧 트랜잭션을 여는 것이다** — 별도의 `begin` 없이 **다음 문장부터** 트랜잭션이 시작되고, 그래서 `commit`·`rollback` 을 잊으면 **그 트랜잭션이 계속 열려 있다.** 잠금과 undo 가 쌓이고, 남의 `update` 가 그 행에서 기다리다 `Lock wait timeout exceeded` 로 실패한다. 「수동 커밋으로 바꿔 두면 안전하다」의 대가가 이것이고, 그래서 실무는 세션 전체를 끄는 대신 **필요한 구간만 `start transaction` ~ `commit`** 으로 감싼다.
- **`select` 도 트랜잭션 안에 있다** — 「조회에는 commit 이 필요 없다」는 「조회가 트랜잭션 밖에 있다」가 아니다. 수동 커밋 상태에서 처음 실행한 `select` 가 **스냅샷의 시점을 잡아 버리므로**, 조회만 하고 며칠 열어 둔 세션도 남의 갱신을 붙들어 놓는다. 위 항목의 실제 원인이 대개 이것이다 → [[dql]]
- **DDL 은 `rollback` 되지 않는다** — `create`·`alter`·`drop`·`truncate` 는 **암시적 커밋**을 일으켜, 트랜잭션 안에서 실행해도 그 앞의 [[dml]] 까지 함께 확정된다. 「감싸 두었으니 되돌릴 수 있다」가 스키마 변경 앞에서 깨진다 → [[ddl]]
- **`rollback` 이 되돌리지 않는 것이 있다** — 자동 증가 카운터(`auto_increment`)는 되돌아가지 않아서, 롤백한 `insert` 가 써 버린 번호는 **영구히 빈다.** 「번호가 1부터 연속일 것」을 가정한 화면이나 통계가 여기서 깨진다. 되돌아가는 것은 **행의 값**이고, 카운터·파일·이미 보낸 메일은 트랜잭션의 대상이 아니다 → [[surrogate-key]]
- **`commit` 은 「저장」 버튼이 아니다** — 자동 커밋 상태에서도 `insert` 는 이미 저장된 것이다. `commit` 이 하는 일은 저장이 아니라 **경계 선언**(여기까지를 한 덩어리로 확정한다)이고, 그래서 자동 커밋에서는 칠 일이 없다. 편집기의 저장 감각으로 읽으면 「커밋을 안 했으니 아직 안 들어갔다」를 자동 커밋 상태에서도 기대하게 된다.
- **트랜잭션은 「동시에 하나만」이 아니다** — 묶는 것은 순서가 아니라 **원자성과 격리**다. 두 세션의 트랜잭션은 동시에 진행되며, 같은 행을 만질 때만 뒤에 온 쪽이 기다린다. 「트랜잭션을 쓰면 줄을 서니 느리다」로 읽으면 필요한 곳에서도 안 쓰게 된다.
- **한 문장은 자동 커밋에서도 원자적이다** — `insert` 하나로 100행을 넣다가 하나가 제약을 어기면 **전부 들어가지 않는다.** 「autocommit=true 면 원자성이 없다」가 아니라 **원자성의 단위가 문장 하나**인 것이다 → [[dml]]
