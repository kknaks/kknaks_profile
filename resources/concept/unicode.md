# 유니코드 (Unicode)와 UTF

**유니코드는 전세계 문자에 번호를 부여한 국제 표준**이고, **UTF-8·UTF-16 은 그 번호를 바이트로 담는 방법**이다. 둘은 다른 층이다.

## 정의

유니코드는 문자마다 번호(코드포인트)를 정한다. 32비트를 할당했지만 실제로 쓰이는 범위는 21비트다.

그 번호를 파일이나 메모리에 담을 때 방식이 갈린다.

| | 영어 | 한글 | 성격 |
|---|---|---|---|
| **UTF-16** | 2 byte | 2 byte | 고정 폭에 가깝다. **Java 가 문자를 다룰 때 쓰는 방식** |
| **UTF-8** | **1 byte** | **3 byte** | 가변 폭. 서구권에서 기존 1바이트 문자를 2바이트로 늘려야 하는 문제를 피하려고 UTF-16 을 변형한 것 |

UTF-8 이 널리 쓰이게 된 이유가 이 표에 있다. 영어가 1바이트로 유지되므로 **ASCII 로 쓰인 기존 파일이 그대로 UTF-8 파일이 된다.** 대신 한글은 3바이트를 쓴다.

### 번호와 바이트를 옮겨 적으면 이렇게 된다

일곱 주 뒤 회차가 같은 글자들을 두 층에 나란히 적어 놓는다 — **왼쪽이 메모리의 번호, 오른쪽이 파일의 바이트**다.

```java
    // JVM(UCS2)    File(UTF-8)
    // 00 41    ==> 41
    // 00 42    ==> 42
    // 00 30    ==> 30
    // ac 00    ==> ea b0 80
    // ac 01    ==> ea b0 81
    // ac 04    ==> ea b0 84
    // b6 18    ==> eb 98 98
    // b6 25    ==> eb 98 a5
```

값이 전부 맞다 — `가`=U+AC00, `각`=U+AC01, `간`=U+AC04, `똘`=U+B618, `똥`=U+B625 이고 각각의 UTF-8 세 바이트도 정확하다. **이 표가 이 노트의 첫 문장을 그대로 보여 준다** — 왼쪽은 「유니코드가 이 글자에 준 번호」이고 오른쪽은 「그 번호를 UTF-8 규칙으로 담은 것」이라, 둘은 다른 것이 아니라 **같은 번호의 두 표기**다.

바뀌는 폭도 보인다 — 알파벳·숫자는 2바이트에서 1바이트로 **줄고**, 한글은 2바이트에서 3바이트로 **늘어난다.** 「UTF-8 이 항상 작다」가 아니라 **어느 문자가 많은가에 따라 갈린다**는 것이 여덟 줄 안에 다 있다 → [[character-encoding]]

다만 왼쪽 칸의 이름이 어긋난다. 필기는 그것을 「UCS2(UTF16BE, 2바이트)」라 부르는데, **셋 다 정확한 이름이 아니다**(아래 「경계와 오해」).

## 왜 중요한가

**"UTF-8 로 저장했는데 자바에서 길이가 다르게 나온다"의 답이 이 구분이다.** 파일은 UTF-8, Java 의 `char` 는 UTF-16 이므로 같은 한글 한 글자가 파일에서는 3바이트, 메모리에서는 2바이트다. 바이트 수와 글자 수를 같은 것으로 보면 계속 어긋난다.

그리고 국제 표준이라는 점이 실질적이다. [[character-encoding]] 의 옛 방식들은 나라마다 갈라져 있어서 같은 바이트가 지역에 따라 다른 글자였는데, 유니코드는 번호를 하나로 고정해 그 문제를 끝냈다.

## 경계와 오해

- **유니코드 ≠ UTF-16** — 옛 필기에 "Unicode(UTF-16)"이라 적어 둔 대로 묶어서 부르기 쉽지만, 유니코드는 **번호를 정하는 표준**이고 UTF-16 은 **그 번호를 담는 여러 방법 중 하나**다. UTF-8 로 저장한 파일도 똑같이 유니코드다.
- **UTF-8 이 유니코드보다 나중이다** — UTF-8 은 유니코드를 대체한 것이 아니라 유니코드를 담는 방식으로 나중에 나온 것이다.
- **한글이 항상 2바이트인 것이 아니다** — 방식마다 다르다(UTF-8 3바이트, UTF-16 2바이트, MS949 2바이트). "한글은 2바이트"는 어느 방식인지를 빼놓은 말이다.
- **21비트를 다 쓰면 UTF-16 도 2바이트로 안 된다** — 이모지 같은 것은 UTF-16 에서 2바이트 두 개를 쓴다. 그래서 UTF-16 도 완전한 고정 폭이 아니다.
- **UCS-2 ≠ UTF-16 — 그리고 Java 는 2005년부터 UCS-2 가 아니다** — Day41 이 「JVM은 문자 데이터를 다룰 때 UCS2(UTF16BE, 2바이트) 유니코드를 사용한다」로 적은 것이 이 자리다. 둘은 **다른 것이고, 갈리는 것이 바로 위 항목**이다. UCS-2 는 **모든 문자가 정확히 2바이트인 고정 폭** 방식이고 그래서 U+FFFF 를 넘는 문자를 아예 표현할 수 없다. UTF-16 은 그 한계를 풀려고 **서로게이트 쌍**(두 개의 `char` 로 한 글자)을 도입한 것이라 가변 폭이다. Java 는 1.0~1.4 에서 실제로 UCS-2 였고, **Java 5 에서 `String`·`char` 의 의미가 UTF-16 으로 바뀌었다**(그때 `codePointAt`·`codePoints` 같은 API 가 생겼다). 즉 「JVM 은 UCS2 를 쓴다」는 **20년 전에는 맞았던 문장**이고 지금은 아니다 — 이모지가 `char` 두 개인 것이 그 증거다. 「UCS2 라서 2바이트 고정」으로 외우면 `"👍".length()` 가 `2` 인 이유를 설명할 수 없다 → [[jvm]] · [[data-type]]
- **그리고 「UTF16BE」는 메모리에 붙일 수 있는 이름이 아니다** — BE/LE 는 **값을 바이트 열로 늘어놓을 때** 정해지는 규칙이고, 메모리의 `char` 는 16비트 값 하나로 다뤄지므로 물을 수 있는 질문이 아니다. 필기의 표에서 왼쪽 칸을 `ac 00` 처럼 **두 바이트로 적은 것이 그 착각을 만든 표기**이고, 실제로 정확한 이름은 「UTF-16 코드 단위 U+AC00」이다. `str.getBytes("UTF-16BE")` 처럼 **파일로 내보낼 때**에야 BE 가 뜻을 갖는다 → [[endianness]]
- **`char` 하나가 글자 하나가 아니다 — 그리고 이 사실이 Java API 곳곳에 새어 나온다** — 위 두 항목의 실질적인 결과다. `length()` 는 글자 수가 아니라 `char` 개수이고, `charAt(i)` 는 서로게이트 쌍의 반쪽을 돌려줄 수 있고, `substring` 은 한 글자 중간에서 자를 수 있다. 글자 단위로 세려면 `codePointCount`·`codePoints()` 를 쓴다. 그리고 결합 문자·이모지 조합(가족 이모지)까지 가면 **코드포인트 하나도 「사람이 보는 글자 하나」가 아니다** — 세는 단위가 바이트 · `char` · 코드포인트 · 그래핌 클러스터로 네 층이다 → [[character-stream]] · [[string-comparison]]
- **파일이 UTF-8 이어도 메모리는 UTF-16 이다 — 그래서 문자집합을 지정할 필요가 없어지는 자리가 있다** — Day41 의 주석이 그것을 정확히 적었다 — 「char 배열에 담을 때 (…) 코드 값으로 변환한다. 그래서 String 객체를 만들 때 문자집합을 지정할 필요가 없다」. **결론이 맞다** — `char[]` 은 이미 유니코드 번호를 담고 있으므로 `new String(char[])` 에는 규칙을 넘길 자리가 없다. 인코딩을 지정해야 하는 것은 `byte[]` 에서 만들 때뿐이고, **그 변환을 이미 `FileReader` 가 해 버린 것**이다 → [[character-encoding]] · [[character-stream]]
