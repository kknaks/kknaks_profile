# 오버플로우 (Overflow)

연산 결과가 그 타입이 담을 수 있는 범위를 넘는 것. **오류가 아니라 값이 조용히 바뀐다** — 넘친 비트가 버려져 엉뚱한 수가 남는다.

## 정의

`int` 최대값 둘을 더하면 음수가 된다.

```java
int x = Integer.MAX_VALUE;   // 0x7fffffff = 약 +21억
int y = Integer.MAX_VALUE;

int r1 = x + y;              // 0x7fffffff + 0x7fffffff = 0xfffffffe = -2
System.out.println(r1);      // -2
```

최상위 비트로 자리 올림이 넘어가 부호 비트가 1 이 되고, [[twos-complement]] 로 읽으면 `-2` 다.

**결과를 더 큰 타입에 담아도 소용없다.**

```java
long r2 = x + y;             // 여전히 -2
```

`int + int` 의 결과 타입이 `int` 이므로 → [[type-promotion]] — **덧셈이 이미 4바이트로 끝난 뒤에** 8바이트 변수로 옮겨진다. 레지스터에서 이미 오버플로우가 발생했고 `r2` 는 그 `-2` 를 전달받는다.

## 왜 중요한가

**컴파일도 되고 실행도 되고 예외도 안 난다.** 그래서 값이 틀린 것을 알아차릴 방법이 결과를 확인하는 것뿐이다. 범위를 넘는 [[literal]] 은 컴파일 단계에서 막히는데, **연산 결과의 오버플로우는 아무도 막아 주지 않는다** — 이 비대칭이 함정이다.

고치는 방법은 **연산 전에** 타입을 키우는 것이다. 담을 변수를 키우는 것이 아니라 피연산자를 키워야 한다.

```java
long r3 = (long) x + y;      // 연산 자체가 long 으로 수행된다
```

## 경계와 오해

- **큰 변수에 담는 것으로 해결되지 않는다** — 가장 흔한 오해다. 대입은 연산이 끝난 다음 일이다. 시간 순서를 놓치면 왜 안 되는지 설명할 수 없다.
- **오버플로우 ≠ 예외** — Java 는 정수 오버플로우에 예외를 던지지 않는다. 나눗셈의 0 처리와 달리 조용하다.
- **부동소수점은 다르게 어긋난다** — `float`·`double` 은 범위를 넘으면 무한대가 되고, 그보다 흔한 문제는 정밀도가 잘리는 것이다 → [[floating-point]]
- **음수 쪽으로도 넘친다** — 최소값에서 1 을 빼면 최대값이 된다(언더플로우). 같은 원리의 반대 방향이다.
