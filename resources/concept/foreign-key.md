# 외래키 (Foreign Key) — 그리고 참조 무결성

**한 테이블의 컬럼이 다른 테이블의 행을 가리키도록 강제하는 제약.** Day54 의 첫 줄이 「한 테이블의 필드가 다른 테이블의 기본 키를 참조하는 키」다. 지금까지의 제약([[primary-key]]·[[unique-key]]·[[sql-null]])은 **한 테이블 안에서 값을 검사**했는데, 이것이 처음으로 **두 테이블 사이를 검사**한다 — 그래서 「테이블이 여러 개」라는 사실이 설계 문제가 되는 첫 자리다.

## 정의

외래키가 강제하는 것은 하나가 아니라 **두 방향의 검사**다. Day54 의 「외부키 적용하기」 절이 그 둘을 정확히 두 줄로 적었다.

| 방향 | Day54 의 문장 | 언제 걸리는가 |
|---|---|---|
| 자식 → 부모 | 「다른 데이터를 참조하는 경우 해당 데이터의 존재 유무를 검사하도록 강제한다」 | 자식 행을 `insert`·`update` 할 때 |
| 부모 → 자식 | 「데이터를 삭제하는 경우 다른 테이터에 의해 참조되는지 여부를 검사하도록 강제한다」 | 부모 행을 `delete`·`update` 할 때 |

이 두 검사가 유지하는 상태가 **참조 무결성(referential integrity)** 이다 — **가리키는 값이 언제나 실재하는 행을 가리킨다.** 「데이터가 사라지지 않는다」가 아니라 **「가리킴이 유효하다」**가 이 말의 뜻이고, 그 구별이 Day54 가 어긋난 자리다(아래 「경계와 오해」 첫 항목).

### 적용 — 문법

```sql
alter table 테이블명
    add constraint 제약조건이름 foreign key (컬럼명) references 테이블명(컬럼명);
```

`add constraint` 로 붙는다는 점에서 [[primary-key]]·[[unique-key]] 와 같은 계열이고, [[ddl]] 의 `alter table` 세 갈래 중 `add` 쪽이다. `create table` 안의 컬럼 목록 뒤에 적어 처음부터 걸 수도 있다.

### 부모가 사라질 때 무엇을 하나 — `ON DELETE` · `ON UPDATE`

Day54 는 「외래 키의 주요 특징」 4번에 **「ON DELETE / ON UPDATE 동작」이라는 이름만 적고 본문을 비웠다.** 그 자리에 들어가는 것은 네 가지 선택이고, **고르지 않으면 첫 줄이 된다.**

| 옵션 | 부모를 지우려 하면 | 쓰는 자리 |
|---|---|---|
| `RESTRICT` (**생략 시 기본**) | **삭제가 거절된다** — 자식을 먼저 정리해야 한다 | 실수로 통째로 날아가는 것을 막고 싶을 때 |
| `NO ACTION` | InnoDB 에서는 `RESTRICT` 와 같다 | (표준에서는 검사 시점이 다르지만 MySQL 은 동일) |
| `CASCADE` | 자식 행도 **함께 지워진다** | 부모 없이 존재할 이유가 없는 것 (게시글의 첨부파일) |
| `SET NULL` | 자식의 그 컬럼이 `NULL` 이 된다 | 「작성자 탈퇴 후에도 글은 남는다」 |

```sql
alter table test2
   add constraint test2_bno_fk foreign key (bno) references test1(no)
   on delete cascade on update cascade;
```

**`SET NULL` 은 그 컬럼이 `not null` 이면 걸 수 없고**, `SET DEFAULT` 는 문법은 통과하지만 InnoDB 가 실제로 지원하지 않는다. 그리고 **기본값이 `RESTRICT` 라는 것이 중요하다** — 아무것도 적지 않으면 「회원 삭제」가 그 회원의 글이 하나라도 있는 순간 실패하기 시작한다.

### 관계의 모양이 테이블 개수를 정한다

Day54 는 관계를 두 가지로 나눠 그렸다.

| 관계 | 어떻게 담는가 | Day54 의 예 |
|---|---|---|
| 1 : N | **N 쪽 테이블에 외래키 컬럼 하나** | 게시글 하나에 첨부파일 여럿 (`test2.bno`) |
| N : M | **중간 테이블을 하나 더 만들고 그 테이블이 양쪽으로 외래키 두 개** | 프로젝트와 회원 (`myapp_members`) |

중간 테이블의 기본키는 대개 **두 외래키를 묶은 복합키**다 — 그러면 같은 회원을 같은 프로젝트에 두 번 넣는 것까지 함께 막힌다. [[primary-key]] 에서 「복합키가 정당한 곳은 관계 자체를 담는 테이블」이라 적어 둔 자리가 **여기**다 → [[db-normalization]]

## 사용 예시

Day54 는 게시판 첨부파일을 **세 번 고쳐 가며** 외래키에 도착한다. 처음은 한 테이블에 파일 경로를 다섯 칸 박아 둔 것이다.

```sql
create table test1(
  no int primary key auto_increment,
  title varchar(255) not null,
  content text,
  rdt datetime default now(),
  filepath1 varchar(255),
  filepath2 varchar(255),
  filepath3 varchar(255),
  filepath4 varchar(255),
  filepath5 varchar(255)
);
```

Day54 가 적은 문제 셋이 「첨부파일을 최대 5개까지만」·「5개가 안 되는 게시글도 5개 경로를 차지」·「파일 입출력으로 인한 속도 저하」다. 그래서 테이블을 둘로 가른다.

```sql
/* 게시판 테이블 */
create table test1(
  no int not null primary key auto_increment,
  title varchar(255) not null,
  content text,
  rdt datetime not null default now()
);

/* 첨부 파일 테이블 */
create table test2(
  fno int not null primary key auto_increment, /* 첨부파일 고유번호 */
  filepath varchar(255) not null, /* 파일시스템에 저장된 첨부파일의 경로 */
  bno int not null /* 게시글 번호 */
);
```

**여기서 Day54 가 스스로 남긴 한 줄이 이 개념의 필요를 만든다** — 「데이터 무결성 에러(파일관리시스템과 게시글의 연결성이 없다.)」. `bno` 는 그냥 `int` 이고, 주석에만 「게시글 번호」라 적혀 있다. **주석은 서버가 읽지 않는다** — `insert into test2 values(1,'/a.png',999)` 는 999번 게시글이 없어도 통과한다.

```sql
alter table test2
   add constraint test2_bno_fk foreign key (bno) references test1(no);
```

이 한 줄이 붙은 뒤에야 `bno` 의 「게시글 번호」가 주석에서 **규칙**이 된다.

## 왜 중요한가

**「없는 것을 가리키는 데이터」를 애플리케이션 코드 없이 막는다.** 자바로 첨부파일을 저장할 때는 게시글이 있는지 먼저 조회해 확인해야 했고, 확인을 잊거나 확인과 저장 사이에 게시글이 지워지면 그대로 들어갔다. 외래키는 그 검사를 **데이터가 사는 곳 옆으로** 옮겨서, 어느 프로그램이 접속해도·손으로 `insert` 를 쳐도 같은 규칙을 받게 한다 → [[encapsulation]] · [[ddl]]

**첨부파일 개수가 스키마에서 데이터로 내려온다.** `filepath1`~`filepath5` 구조에서 「6개를 올리고 싶다」는 요구는 **`alter table` 로 컬럼을 더하는 배포**였고, 그러면 그 컬럼을 읽는 자바 코드도 함께 고쳐야 했다. 테이블을 가르면 같은 요구가 **행을 하나 더 넣는 것**이 된다 — 구조 변경이 필요했던 일이 값 변경으로 내려오는 것이 정규화의 실질적인 이득이다 → [[db-normalization]] · [[dml]]

**그리고 `delete` 가 처음으로 설계 판단이 된다.** 지금까지 [[dml]] 의 `delete` 는 그 행 하나의 일이었다. 참조가 생기는 순간 **「이것을 지우면 무엇이 함께 지워지나」**를 정해야 하고, 그 답을 코드가 아니라 스키마에 적는 것이 `ON DELETE` 절이다. 정하지 않으면 기본값 `RESTRICT` 가 골라져서, 서비스가 자란 뒤 「회원 삭제」가 조용히 실패하기 시작한다 → [[transaction]]

## 경계와 오해

- **「User 삭제 → Project 의 member 도 삭제된다 → 참조무결성 위반」은 뒤집혀 있다** — Day54 가 참조 무결성 절에 든 유일한 예인데, **함께 삭제되는 것은 위반이 아니라 무결성을 지키는 동작**(`ON DELETE CASCADE`)이다. 위반은 반대쪽이다: User 가 사라졌는데 member 행에 그 `user_id` 가 **그대로 남아 없는 행을 가리키는 상태**(고아 행·dangling reference). 필기는 「데이터가 사라진다」를 손실로 읽어 위반이라 적었지만, 참조 무결성이 말하는 것은 **손실 여부가 아니라 가리킴의 유효성**이다. 외래키가 없을 때 생기는 것이 정확히 그 고아 행이고, 걸어 두면 삭제가 거절되거나(`RESTRICT`) 함께 정리된다(`CASCADE`) — **두 결말 다 무결성은 지켜진다.** 다만 `CASCADE` 에 진짜 위험이 있는 것은 맞다: 회원 하나를 지우면 그 회원의 글과 그 글의 첨부까지 연쇄로 사라지고, `rollback` 하지 않으면 되돌릴 수 없다 → [[transaction]]
- **외래키 ≠ 기본키의 사본** — Day54 의 정의는 「다른 테이블의 **기본 키**를 참조」이지만, MySQL 이 요구하는 것은 「참조 대상 컬럼이 **인덱스의 맨 앞**에 있을 것」이라서 `unique` 컬럼도 참조할 수 있다. 반대로 **인덱스가 없는 컬럼은 참조할 수 없고**, 그러면 `alter table` 이 `errno: 150` 으로 거절된다 — 「기본키만」으로 외우면 이 오류의 원인을 못 찾고, 「아무 컬럼이나」로 읽으면 오류를 만난다 → [[primary-key]] · [[unique-key]] · [[database-index]]
- **외래「키」는 값의 유일성을 주지 않는다** — [[primary-key]]·[[unique-key]] 는 중복을 막는 제약이고 셋 다 「키」라 불리는데, 외래키 컬럼은 **같은 값이 여러 행에 있어야 정상**이다(1:N 의 N 쪽 — 게시글 하나에 첨부가 다섯이면 `bno` 가 다섯 번 같다). 「키니까 유일하겠지」로 읽으면 관계의 방향이 뒤집힌다. **키 계열의 다른 둘은 「값을 제한」하고 외래키는 「값의 출처를 제한」한다.**
- **`bno int not null` 은 아무것도 막지 못한다** — Day54 의 두 번째 설계가 그 상태이고 필기가 스스로 「데이터 무결성 에러」라 적었다. **타입이 맞는다는 것과 그 번호의 게시글이 있다는 것은 다른 이야기**이며, `not null` 은 「값이 있다」만 요구한다. 주석에 「게시글 번호」라고 써 두는 것도 서버에게는 아무 뜻이 없다 — 규칙을 사람이 읽는 곳에 두는 것과 서버가 검사하는 곳에 두는 것의 차이가 이 자리다.
- **그런데 그 `not null` 은 우연히 중요하다** — 외래키 컬럼이 `NULL` 이면 **참조 검사를 건너뛴다**(`NULL` 은 「가리키지 않음」이라 위반이 아니다). `bno` 에 `not null` 이 없으면 **주인 없는 첨부파일**이 정당하게 들어온다. Day54 는 `not null` 을 적어 두었지만 그 이유는 적지 않았다 → [[sql-null]]
- **나중에 걸 때는 이미 든 데이터가 전부 통과해야 한다** — `alter table ... add constraint` 는 기존 행을 검사하므로, 고아 행이 하나라도 있으면 `Cannot add or update a child row: a foreign key constraint fails` 로 **제약 추가 자체가 실패한다.** [[ddl]] 의 `modify column`·`add constraint unique` 와 같은 성질이고, 그래서 **외래키는 데이터가 쌓인 뒤에 붙이기 가장 어려운 제약**이다. Day54 가 빈 테이블에서 실습했기 때문에 이 벽이 드러나지 않았다.
- **제약 이름은 데이터베이스 전체에서 유일해야 한다** — Day54 가 `test2_bno_fk` 처럼 테이블명을 접두사로 붙인 것이 관례가 아니라 필요다. `unique` 제약 이름은 테이블 안에서만 유일하면 되는데(Day51 의 `test1_uk`) 외래키 이름은 **스키마 단위**라, 테이블 둘에 `bno_fk` 를 각각 걸면 두 번째가 거절된다. **같은 `constraint` 문법이 제약 종류에 따라 이름의 유효 범위를 달리 갖는다** → [[database-schema]]
- **「1대다/다대다를 직접적으로 연결하면」은 두 경우를 한 줄에 묶었다** — 1:N 은 **직접 연결이 정상**이다(N 쪽에 외래키 컬럼 하나). 반면 N:M 은 「막을 수 없다」가 아니라 **직접 연결할 문법이 아예 없다** — 컬럼 하나에 값 여러 개를 담을 수 없기 때문이고, 그래서 중간 테이블이 선택이 아니라 유일한 방법이다. 한 줄로 읽으면 「1:N 도 중간 테이블을 만들어야 한다」가 되어 테이블이 두 배가 된다 → [[array]]
- **MySQL 에서만 외래키 컬럼에 인덱스가 저절로 생긴다** — InnoDB 는 외래키를 걸면 그 컬럼에 인덱스를 자동으로 만든다(부모 삭제 시 자식을 찾아야 하므로). 이것은 **표준이 요구하는 것이 아니어서** PostgreSQL 등은 만들어 주지 않는다. 「외래키를 걸면 조인이 빨라진다」는 제품에 딸린 이야기이지 외래키의 성질이 아니다 → [[database-index]]
- **외래키는 무료가 아니다** — 자식 행을 넣을 때 **부모 행에 잠금**을 잡는다(그 사이 부모가 사라지면 안 되므로). 참조가 몰리는 부모(카테고리·상태 코드 같은 소수 행)가 있으면 그 행에서 대기가 생기고, 이것이 대규모 서비스가 외래키를 빼고 애플리케이션에서 검사하는 쪽을 고르는 이유다. **「제약을 걸면 안전하고 공짜」가 아니라 「정합성과 쓰기 처리량의 교환」**이다 → [[transaction]] · [[little-law]]
- **외래키는 조인의 조건이 아니다** — 외래키를 걸어 두면 두 테이블이 「연결된 것」처럼 보이지만, 조회할 때 두 테이블을 함께 읽으려면 여전히 조건을 매번 적어 줘야 한다(`test1.no = test2.bno`). 외래키가 하는 일은 **쓸 때 검사**이고 **읽을 때 자동으로 이어 주지는 않는다** — [[db-normalization]] 이 적어 둔 「조회 시 조인이 필요해 문법이 복잡해진다」의 대가가 그것이다.
- **참조 무결성 ≠ 데이터 무결성 전체** — Day54 는 「데이터의 무결성」과 「참조 무결성」을 섞어 쓴다. 참조 무결성은 **테이블 사이의 가리킴**만 다루고, 「나이가 음수가 아니다」(도메인 무결성)·「행이 서로 구분된다」(개체 무결성)는 다른 제약이 맡는다. 외래키를 걸었다고 데이터가 「올바른」 것이 되지는 않는다 → [[primary-key]] · [[sql-data-type]]

## 함께 보는 개념

- [[primary-key]] — 외래키가 가리키는 쪽. 「바뀌면 안 되는 값」인 이유가 여기서 드러난다
- [[unique-key]] — 기본키가 아니어도 참조 대상이 될 수 있는 제약
- [[sql-null]] — 외래키 컬럼이 `NULL` 이면 검사를 건너뛰는 자리
- [[ddl]] — 이 제약을 붙이는 `alter table ... add constraint`
- [[dml]] — 이 제약이 실제로 막는 세 문장
- [[db-normalization]] — 테이블을 가르고 외래키로 다시 잇는 설계 원칙
- [[database-index]] — 외래키가 (MySQL 에서) 자동으로 만드는 것
- [[transaction]] — 연쇄 삭제와 부모 행 잠금이 걸리는 경계
- [[database-schema]] — 제약 이름의 유효 범위가 되는 단위
- [[surrogate-key]] — 참조당할 값으로 인공키를 고르는 이유
- [[crud]] — 등록·삭제가 두 테이블에 걸치기 시작하는 자리
- [[encapsulation]] — 검사 규칙을 데이터 옆으로 옮기는 것의 같은 축

## 출처

- [[2024-08-12-Day54]] — 「한 테이블의 필드가 다른 테이블의 기본 키를 참조하는 키」로 정의하고 특징 넷(참조 무결성·연결 관계·제약 조건·`ON DELETE`/`ON UPDATE`)을 나열한 뒤, 게시판 첨부파일을 `filepath1`~`filepath5` → 두 테이블 분리 → `alter table ... add constraint test2_bno_fk foreign key (bno) references test1(no)` 로 **세 단계에 걸쳐 고쳐 가며** 도착한다. 「존재 유무를 검사」·「참조되는지 여부를 검사」로 **두 방향의 검사를 정확히 갈라 적었고**, 두 번째 설계에서 스스로 「데이터 무결성 에러(파일관리시스템과 게시글의 연결성이 없다.)」라 적어 제약의 필요를 만들어 냈다. 1:N 과 N:M(중간 테이블 `myapp_members`)을 그림으로 나눈 것도 이 회차다. 다만 특징 4번 `ON DELETE`/`ON UPDATE` 는 **이름만 적고 본문이 비어 있고**, 참조 무결성의 유일한 예(「User 정보가 삭제되면 Project 의 meeber 도 삭제된다 → 참조무결성 위반」)는 위반과 `CASCADE` 동작을 뒤집어 읽었다. 「1대다/다대다의 관계를 직접적으로 연결하면」은 직접 연결이 정상인 1:N 과 문법 자체가 없는 N:M 을 한 줄에 묶었다
