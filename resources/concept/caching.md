# 캐싱 (Caching)

자주 조회되는 데이터를 고속 저장소에 복사해 두고, 원본 저장소 대신 거기서 꺼내 응답 속도를 높이는 성능 최적화 패턴이다.

## 정의

- 원본 데이터는 메인 DB(디스크 기반)에 보관한다.
- 자주 읽히는 데이터를 RAM 같은 고속 저장소(캐시)에 복사해 둔다.
- 요청이 오면 메인 DB 대신 캐시에서 꺼내 반환한다 — RAM이 디스크보다 수십~수백 배 빠르기 때문이다.
- Redis가 대표적인 인메모리 캐시 구현체다.

### 캐시에는 언제나 「범위」가 있다

**「어디에 복사해 두는가」보다 「누가 그 복사본을 보는가」가 캐시의 성질을 정한다.** Day62 가 걸린 자리가 그것이다 — MyBatis 의 1차 캐시(로컬 캐시)는 **`SqlSession` 하나의 범위**이고, 기본으로 켜져 있다 → [[sql-session]] · [[mybatis]]

| 범위 | 누가 보나 | 비워지는 시점 |
|---|---|---|
| 문장 하나 (`localCacheScope=STATEMENT`) | 그 호출만 | 문장이 끝날 때 |
| **`SqlSession` (기본)** | **그 세션을 쓰는 모두** | 변경 문장 실행 · `commit` · `rollback` · `close` |
| 매퍼 네임스페이스 (`<cache/>` — 2차 캐시) | **세션을 넘어 전부** | 그 매퍼의 변경이 커밋될 때 |

**Day62 의 「하나의 SqlSession을 생성하여 하나의 캐시를 공유한다」는 가운데 줄이 접속 전체로 넓어진 상태**를 말한다. 캐시를 잘못 설정한 것이 아니라 **캐시가 딸린 객체를 여럿이 공유한 것**이고, 그래서 답이 캐시 설정이 아니라 세션을 나누는 것이 된다 → [[thread]] · [[thread-local]]

## 사용 예시

Day62 의 프록시가 **캐시 조회의 최소 형태**다 — 있으면 그대로, 없으면 만들어 넣고 돌려준다.

```java
SqlSession sqlSession = sqlSessionThreadLocal.get();   // 조회
if (sqlSession == null) {
  sqlSession = original.openSession(autoCommit);       // 미스 — 원본에 물어본다
}
sqlSessionThreadLocal.set(sqlSession);                 // 채워 둔다
return sqlSession;
```

**키가 사람이 준 값이 아니라 부른 쪽 쓰레드**이고, 캐시하는 대상이 데이터가 아니라 **비싼 객체**다(연결을 품은 세션). 그래서 여기서는 「빨라진다」가 아니라 **「같은 것을 받는다」가 목적**이며, 그 성질이 [[transaction]] 경계를 만든다. 다만 **버리는 코드가 없다** — 아래 「무효화가 없는 캐시」 → [[thread-local]] · [[proxy-pattern]]

## 왜 중요한가

같은 데이터를 반복해서 디스크 기반 DB에서 조회하면 I/O 비용이 누적된다. 캐싱은 이 병목을 제거한다. 읽기 비중이 높은 서비스일수록 효과가 크고, 사용자 체감 응답 속도가 크게 달라진다.

**그리고 캐시의 범위를 모르면 「왜 방금 바꾼 값이 안 보이나」에 답할 수 없다.** Day62 의 서버는 세션 하나가 접속 내내 살아 있어서, 다른 사용자가 등록한 글이 **목록을 다시 조회해도 나타나지 않는다** — 같은 세션·같은 문장·같은 파라미터이므로 1차 캐시가 답하기 때문이다. 눈에 보이는 증상(화면이 갱신되지 않는다)과 원인(캐시의 범위가 너무 넓다)이 멀리 떨어져 있고, **성능을 위해 켜 둔 장치가 정합성 문제로 나타나는** 형태다 → [[sql-session]] · [[dql]]

## 경계와 오해

- **캐시 ≠ 메인 DB** — 캐시는 복사본이다. 메인 DB와 동기화가 필요하며, 캐시가 날아가도 메인 DB에 원본이 남아 있어야 한다. 캐시를 단일 저장소로 쓰면 데이터 유실 위험이 있다.
- **인메모리 캐시는 기본적으로 휘발성** — Redis는 서버 재시작 시 데이터를 잃을 수 있다. 영속성이 필요하면 별도 설정(AOF·RDB 스냅샷)이 필요하다.
- **쓰기 빈도가 높으면 효과 반감** — 데이터가 자주 바뀌면 캐시 무효화(cache invalidation) 관리가 복잡해지고 stale data 문제가 생긴다.
- **캐시가 커밋될 때 DB 로 올라가는 것이 아니다** — Day62 의 「하나의 클라이언트에서 커밋을 하면 전체 캐시가 데이터베이스에 업데이트된다」가 그 그림인데, 방향이 반대다. **변경 문장은 이미 DB 로 갔고**(그 세션의 트랜잭션 안에 있다) `commit` 은 그것을 확정할 뿐이며, 커밋은 캐시를 올려보내는 것이 아니라 **비운다.** 필기가 본 현상(한 사람의 커밋이 남의 작업까지 확정한다)은 맞지만 원인은 캐시가 아니라 **커밋 경계를 공유한 것**이다. [[transaction]] 노트가 지적한 「임시저장소에 저장된다」와 **같은 모양의 오해**이고, 두 번 다 「어딘가에 모아 두었다가 나중에 옮긴다」는 그림이 실제 구조를 대신하고 있다 → [[transaction]] · [[sql-session]]
- **캐시 ≠ 격리 — 「각자 캐시를 가지니 서로 영향이 없다」는 결론은 맞고 이유는 다르다** — Day62 의 「각자 고유의 캐시를 가지기 때문에 다른 클라이언트의 작업이 현재 클라이언트의 작업에 영향을 미치지 않는다」에서, 실제로 작업을 갈라 주는 것은 캐시가 아니라 **세션마다 따로 있는 트랜잭션 경계**다. 캐시를 문장 범위로 줄여도(`localCacheScope=STATEMENT`) 세션을 공유하는 문제는 그대로 남고, 반대로 2차 캐시(`<cache/>`)를 켜면 **세션을 나눠도 결과가 다시 공유된다.** 캐시는 **읽기를 아끼는 장치**이고 격리는 트랜잭션이 하는 일이라, 둘을 한 이유로 묶으면 「캐시를 껐으니 안전하다」·「세션을 나눴으니 캐시도 안전하다」 두 방향으로 다 틀린다 → [[transaction]] · [[thread]]
- **무효화가 없는 캐시는 캐시가 아니라 누출이다** — Day62 의 프록시는 채우는 코드만 있고 **버리는 코드가 없다.** 일반적인 캐시는 크기 상한이나 만료로 스스로 줄어들지만, 이것은 키가 쓰레드라서 **그 쓰레드가 사는 동안 값이 산다** — 담긴 것이 연결을 붙들고 있는 세션이므로 대가가 메모리가 아니라 **커넥션 풀**로 온다. 「무효화 관리가 복잡해진다」의 가장 단순한 실패가 **무효화를 아예 안 쓴 것**이고, 그때 캐시의 이득(같은 것을 받는다)과 손해(놓지 않는다)가 같은 코드에서 나온다 → [[thread-local]] · [[connection-lifetime-mismatch]]

- [[2024-08-23-Day62]] — 이 개념이 **성능 장치가 아니라 정합성 문제로** 처음 나오는 자리다. 멀티쓰레드 서버가 `SqlSession` 하나를 공유하던 상태를 「하나의 SqlSession을 생성하여 하나의 캐시를 공유한다」·「하나의 클라이언트에서 커밋을 하면 전체 캐시가 데이터베이스에 업데이트된다」로 적고, 세션을 쓰레드마다 나눈 뒤 「각자 고유의 캐시를 가지기 때문에 다른 클라이언트의 작업이 현재 클라이언트의 작업에 영향을 미치지 않는다」로 닫는다 — 여기서 말하는 캐시는 MyBatis 의 **1차 캐시(세션 범위, 기본 켜짐)**이고, 필기는 그 이름도 범위도 설정도 다루지 않는다. 그리고 같은 절의 프록시 코드가 **캐시 조회의 최소 형태**(get → 미스면 원본 → set → 반환)인데 무효화·만료·상한이 없어 값이 쓰레드가 사는 동안 남는다. 「커밋하면 캐시가 DB 에 업데이트된다」는 실제 구조와 방향이 반대이며(변경은 이미 DB 에 있고 커밋은 캐시를 비운다), 세션을 나눈 것이 격리를 만든 이유가 캐시가 아니라 트랜잭션 경계라는 구별도 없다
