# 템플릿 엔진 (Template Engine)

**틀(템플릿)과 데이터를 합쳐 문서를 만들어 주는 도구.** 틀은 HTML 처럼 생긴 파일이고, 정해진 문법 자리에 데이터가 꽂힌다.

## 정의

하는 일이 셋이다.

- **데이터 바인딩** — 데이터와 템플릿을 결합해 최종 문서를 만든다
- **논리적 제어** — 템플릿 안에서 조건문·반복문을 쓸 수 있다
- **코드와 표현의 분리** — 자바 코드 파일과 화면 파일이 갈린다

[[jsp]] 가 이 갈래의 한 구현이다. 다른 것으로 Thymeleaf·Mustache·Handlebars 가 있고, **문법만 다르고 하는 일은 같다.**

얻는 것과 내는 것.

| 얻는 것 | 내는 것 |
|---|---|
| 반복되는 HTML 구조를 틀로 정의해 **재사용** | 엔진마다 문법이 달라 **배우는 비용** |
| HTML 과 비슷한 구조라 **읽기 쉽다** | 서버·클라이언트에 **처리 로직이 하나 더 붙는다** |
| 동적 페이지를 빨리 만든다 | |

## 왜 중요한가

**화면을 문자열로 조립하지 않게 된다.** Day63~66 의 서블릿이 `out.println("<tr>")` 을 줄마다 쓴 것과 비교하면, 틀 파일 쪽은 태그가 태그로 보이고 편집기·브라우저가 그것을 이해한다. **틀린 태그를 실행 전에 발견할 수 있다**는 것이 실질적 차이다.

그리고 **누가 고치나가 갈린다.** 화면만 고치는 사람이 자바 파일을 열지 않아도 되므로, [[mvc-pattern]] 의 분리가 파일 단위로 실현된다.

## 경계와 오해

- **템플릿 엔진이 분리를 보장하지 않는다** — 「코드와 프레젠테이션을 분리하여 유지보수가 용이하다」는 **가능해진다**는 뜻이고, 템플릿에 조건·반복을 마음껏 쓸 수 있으므로 업무 로직을 그 안에 넣는 것도 막지 않는다. 필기의 `view.jsp` 가 판정 메서드를 선언해 쓰는 것이 그 예다. **문법이 주는 것은 자리이고 분리는 규율이다** → [[jsp]] · [[mvc-pattern]]
- **「논리적 제어」의 범위를 정해야 한다** — 반복·조건까지가 표시의 일이고, 「누가 팀원인가」·「권한이 있는가」는 아니다. 이 선을 안 그으면 템플릿이 두 번째 소스 코드가 되고, **그쪽은 컴파일러가 검사해 주지 않는다.**
- **서버 측과 클라이언트 측 엔진이 다른 문제를 푼다** — 이 회차의 JSP 는 서버에서 완성된 HTML 을 만들어 보낸다. 브라우저에서 합치는 방식(클라이언트 측 템플릿)은 첫 화면이 비어 있고 데이터를 따로 받아 온다 — **검색 엔진이 보는 것과 사용자가 보는 것이 갈리는 지점**이다.
- **데이터를 태그 사이에 그대로 꽂으면 값이 태그가 된다** — 제목에 `<script>` 가 들어 있으면 그것이 실행된다. 필기의 `<%=board.getTitle()%>` 이 정확히 그 형태이고, 이스케이프 이야기는 나오지 않는다. 값이 SQL 문장으로 읽히던 문제와 **같은 모양이 화면 쪽에서 반복되는 것**이다 → [[sql-injection]] · [[output-escaping]]
- **「러닝 커브」가 단점 목록의 첫 줄일 이유는 없다** — 문법은 몇 개뿐이고, 실제 비용은 **이름 계약이 컴파일 시점에 검사되지 않는다**는 쪽이다.
- **템플릿 엔진 ≠ 인터프리터** — 갈래 안에서 다시 갈린다. [[jsp]] 는 틀을 **자바 소스로 번역해 컴파일**하고, 다른 엔진들은 틀을 매 요청 읽어 해석한다. Day73 이 「Python이나 PHP 처럼 직접 그 스크립트가 인터프리팅이 아니다」로 짚은 자리다. 이 차이가 **오류가 언제 드러나는가**와 **첫 요청이 왜 느린가**를 정한다 → [[interpreter]] · [[compilation]]

## 출처

- [[2024-09-11-Day74]] — Day67 이 특징으로만 적었던 **「논리적 제어」에 실제 문법이 붙는 회차**다. `<c:if>`·`<c:choose>`·`<c:forEach>` 가 조건과 반복을 태그로 만들어, 자바 블록과 HTML 태그가 서로 교차해 열리고 닫히던 모양을 없앤다 — **틀 안의 제어가 HTML 과 같은 중첩 규칙을 따르게 되는 자리**다. 동시에 Day67 이 남긴 이스케이프 문제에 답이 하나 나온다: `c:out` 의 `escapeXml` 이 기본 `true` 다. 다만 「논리적 제어를 어디까지 허용할 것인가」라는 이 노트의 질문은 필기가 다루지 않고, 태그가 늘어날수록 그 선이 흐려진다는 것도 적혀 있지 않다

- [[2024-08-30-Day67]] — 「템플릿 엔진 (Template Engine)」 절이 정의와 주요 특징 셋(데이터 바인딩·논리적 제어·유지보수성), 장점 셋, 단점 둘을 정리한다. JSP 를 그 갈래의 하나로 두고 뷰 구현 후보에 Thymeleaf 를 나란히 적은 것이 정확하다. 다만 「분리하여 유지보수가 용이하다」가 도구의 성질처럼 적혀 있어, 같은 노트의 JSP 파일들이 로직을 담고 있는 것과 어긋난다. 값을 태그 사이에 그대로 꽂을 때의 위험(이스케이프)과 서버 측·클라이언트 측 엔진의 차이는 다루지 않았다
- [[2024-09-10-Day73]] — 「JSP의 구동원리」에서 **「JSP 파일을 분석해서 JSP Engine이 class파일을 생성하는 template 기술이다」**라는 한 문장이 이 갈래 안의 갈림을 만든다. Day67 은 템플릿 엔진을 「틀과 데이터를 합치는 도구」로만 두었는데, 여기서 **합치는 방식이 번역인가 해석인가**가 갈리고 그 선택이 오류 시점·첫 요청 비용으로 이어진다. 엔진 비교나 다른 구현은 다루지 않고 JSP 한 갈래만 안쪽에서 본다
