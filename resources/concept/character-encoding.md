# 문자 인코딩 (Character Encoding)

글자를 바이트로 바꾸는 규칙. 같은 바이트를 다른 규칙으로 읽으면 다른 글자가 나오므로, 쓴 쪽과 읽는 쪽이 같은 규칙을 써야 한다.

## 정의

규칙이 여러 개인 것은 **담을 문자를 늘려 오는 과정에서 하나씩 덧붙었기 때문**이다.

| 방식 | 담는 것 | 한계 |
|---|---|---|
| **ASCII** | 알파벳. 7비트로 128자 | 영어만 |
| **ISO-8859-1** | ASCII + 라틴 계열 문자 | 여전히 서구권만 (`~4` 버전까지 있다) |
| **EUC-KR** | 한글 완성형 2350자 | 한글 음절은 11,172자다. `똡`·`똣` 같은 일부가 담기지 않는다 |
| **조합형** | 초성·중성·종성을 조합. 2byte = 한글 1bit + 각 5bit | **국제 표준이 아니다.** 16비트의 절반을 한글이 쓰면 다른 나라 문자가 들어갈 자리가 없다 |
| **MS949 (CP949)** | EUC-KR + 알파로 11,172자 전부 | EUC-KR 기반 2byte. **국제 표준이 아니다** |
| **유니코드 / UTF-8** | 전세계 문자 | → [[unicode]] |

앞의 것들이 **각자 자기 나라 문자만 담으려 한 결과** 같은 바이트가 지역에 따라 다른 글자가 되었고, 그것을 끝낸 것이 유니코드다.

### 기본값이 어긋날 때

규칙이 여러 개 남아 있으니 **도구마다 기본값이 다르다**는 문제가 생긴다.

| 주체 | 기본 인코딩 |
|---|---|
| `javac` (컴파일러) | UTF-8 |
| Windows | MS949 |

Windows 에서 소스를 저장하면 MS949 로 저장되는데 `javac` 는 UTF-8 로 읽으려 하니, 한글이 든 소스를 컴파일할 때 문자 집합 오류가 난다. 규칙을 명시해 맞춰 주면 해결된다.

## 사용 예시

컴파일할 때 소스가 어떤 인코딩인지 `-encoding` 으로 알려준다.

```bash
$ javac -encoding UTF-8 Hello.java
```

**읽는 쪽과 쓰는 쪽을 따로 지정해야 하는 경우도 있다.** [[javadoc]] 은 소스를 읽어 HTML 을 만드므로 옵션이 둘로 갈린다.

```plaintext
-encoding [소스 파일의 문자집합]        # 읽을 때
-charset  [생성될 HTML 파일의 문자집합]  # 쓸 때
```

입력과 출력의 인코딩이 같을 이유가 없기 때문이다. 한쪽만 맞추면 다른 쪽에서 깨진다.

### 명령줄 옵션이 아니라 코드 안에서 지정하는 자리

**바이트 배열에서 문자열을 만들 때는 규칙을 인자로 넘긴다.** 세 주 뒤 회차의 예제가 같은 글자(`가각`)를 세 방식으로 적어 놓고 각각 읽는다.

```java
byte[] bytes =
    {(byte) 0xb0, (byte) 0xa1, (byte) 0xb0, (byte) 0xa2, 0x30, 0x31, 0x32, 0x41, 0x42, 0x43};
String s5 = new String(bytes, "euc-kr");            // 가각012ABC

byte[] bytes2 =
    {(byte) 0xac, (byte) 0x00, (byte) 0xac, (byte) 0x01, 0x00, 0x61, 0x00, 0x62, 0x00, 0x63};
String s6 = new String(bytes2, "utf-16");           // 가각abc

byte[] bytes3 = {(byte) 0xea, (byte) 0xb0, (byte) 0x80, (byte) 0xea, (byte) 0xb0, (byte) 0x81,
    0x61, 0x62, 0x63};
String s7 = new String(bytes3, "utf-8");            // 가각abc
```

**같은 `가` 가 세 규칙에서 다른 바이트다.**

| 규칙 | `가` | `각` | 알파벳 한 글자 |
|---|---|---|---|
| EUC-KR | `B0 A1` | `B0 A2` | 1바이트 |
| UTF-16 | `AC 00` | `AC 01` | **2바이트** (`00 61`) |
| UTF-8 | `EA B0 80` | `EA B0 81` | 1바이트 |

**UTF-16 의 `AC00` 이 유니코드가 `가` 에 부여한 번호 그 자체**이고, UTF-8 의 `EA B0 80` 은 같은 번호를 세 바이트에 나눠 담은 것이다. 즉 뒤의 둘은 **같은 번호의 다른 표기**이고 EUC-KR 은 아예 다른 번호 체계다 → [[unicode]]

그리고 알파벳 쪽에서 갈리는 것이 UTF-8 이 널리 쓰이는 이유를 보여 준다 — UTF-16 은 `a` 에도 2바이트를 쓰고 UTF-8 은 1바이트로 끝낸다.

### 세 주 뒤, 반대 방향으로 — 그리고 규칙을 문자열이 아니라 타입으로 넘긴다

Day22 는 바이트를 **읽는** 쪽에서 규칙을 정했다. Day38 은 **쓰는** 쪽에서 정한다.

```java
      byte[] bytes = name.getBytes(StandardCharsets.UTF_8);
```

그리고 되읽을 때 같은 규칙을 다시 넘긴다.

```java
      user.setName(new String(buffer, 0, len, StandardCharsets.UTF_8));
```

**Day22 의 `new String(bytes, "utf-8")` 과 두 곳이 다르다.**

| | Day22 | Day38 |
|---|---|---|
| 규칙을 지정하는 방식 | 문자열 `"utf-8"` | 상수 `StandardCharsets.UTF_8` |
| 읽는 범위 | 배열 전체 | `(buffer, 0, len)` — **앞에서 `len` 바이트만** |

앞의 차이는 아래 「경계와 오해」가 답하는 자리이고, 뒤의 차이는 **버퍼를 재사용하기 때문**이다 — `buffer` 는 `new byte[10000]` 하나를 네 필드가 돌려 쓰므로 앞 필드의 꼬리가 남아 있고, 읽은 길이만큼만 잘라야 한다 → [[byte-array-stream]]

### 닷새 뒤 — 같은 글자를 다섯 규칙으로 한 화면에 늘어놓는다

Day22 는 세 규칙을 각각 다른 바이트 배열로 적어 두었고, Day41 은 **문자열 하나에서 다섯 배열을 꺼낸다.**

```java
    String str = new String("AB가각");
    
    byte[] bytes_default = str.getBytes();            //41 42 ea b0 80 ea b0 81 
    byte[] bytes_UTF_8 = str.getBytes("UTF-8");       //41 42 ea b0 80 ea b0 81 
    byte[] bytes_MS949 = str.getBytes("MS949");       //41 42 b0 a1 b0 a2 
    byte[] bytes_UTF_16BE= str.getBytes("UTF-16BE");  //00 41 00 42 ac 00 ac 01 
    byte[] bytes_UTF_16LE = str.getBytes("UTF-16LE"); //41 00 42 00 00 ac 01 ac 
```

**방향이 Day22 의 반대다.** Day22 는 「이 바이트를 이 규칙으로 읽으면 이 글자」였고 여기는 「이 글자를 이 규칙으로 쓰면 이 바이트」다. 그리고 **다섯 줄의 길이가 다르다** — 8·8·6·8·8. 같은 네 글자인데 규칙에 따라 6바이트가 되기도 8바이트가 되기도 한다는 것이 한눈에 보인다.

| 규칙 | `A` | `가` | 전체 |
|---|---|---|---|
| UTF-8 | `41` (1바이트) | `EA B0 80` (3바이트) | 8바이트 |
| MS949 | `41` (1바이트) | `B0 A1` (2바이트) | 6바이트 |
| UTF-16BE | `00 41` (2바이트) | `AC 00` (2바이트) | 8바이트 |
| UTF-16LE | `41 00` | `00 AC` | 8바이트 |

**마지막 두 줄은 규칙이 아니라 순서만 다르다** — 같은 바이트가 두 개씩 뒤집혀 있다. 「인코딩」 안에 축이 하나 더 있다는 것이 이 자리에서 처음 드러나고, 그것은 별개 개념이다 → [[endianness]]

첫 줄 `bytes_default` 는 **인자를 주지 않은 경우**인데 결과가 UTF-8 줄과 같다. 필기가 그것을 「문자열 인코딩은 UCS2 -> UTF-8이다.(단, 윈도우는 UCS2 -> MS949)」로 적었다 — **기본값은 규칙이 아니라 환경이라는 것**을 알고 있는 문장이고, 이 노트의 「기본값이 어긋날 때」와 같은 자리다. 다만 그 기본값이 언제부터 무엇인지는 갈리는 지점이 있다(아래 「경계와 오해」) → [[platform-dependency]]

### 두 주 뒤 — 규칙을 코드가 아니라 데이터베이스에 붙인다

Day51 은 같은 결정을 **저장소를 만들 때** 한 번 한다.

```sql
CREATE DATABASE studydb /* 인코딩 방식*/
DEFAULT CHARACTER SET utf8 /* 정렬 및 비교 방식*/
DEFAULT COLLATE utf8_general_ci;
```

`DEFAULT` 가 붙은 것이 이 형태의 성격이다 — **한 번 적으면 그 안에 만들어지는 테이블·컬럼이 물려받는다.** 자바에서는 변환이 일어나는 지점마다 인자를 넘겨야 했는데(그래서 한 군데를 빠뜨리면 그 자리만 기본값이 됐다), 여기서는 **바깥에 한 번 적고 안쪽이 상속한다** → [[database-schema]]

그리고 **축이 하나 늘어난다.** 필기의 주석 두 개가 「인코딩 방식」과 「정렬 및 비교 방식」으로 갈려 있는데, 뒤가 **collation** 이다 — 같은 바이트를 어떤 순서로 세우고 **무엇을 같은 값으로 볼지**를 정한다. `utf8_general_ci` 의 `_ci` 는 대소문자를 구분하지 않는다는 뜻이라 `'Kim'` 과 `'kim'` 이 같은 값이 되고, 그 판정이 `order by` 뿐 아니라 **중복 거절**까지 바꾼다 → [[unique-key]] · [[string-comparison]]

### 세 주 뒤 — 규칙을 HTTP 응답에 붙이고, 처음으로 못 담은 글자가 사라진다

Day64 는 같은 결정을 **브라우저로 나가는 응답**에 대고 한다. 필기가 골격을 정확히 적었다.

```java
ServletResponse.setContentType("MIME타입;문자집합")
```

실제로 넘긴 값이 `"text/html;charset=UTF-8"` 이고, **한 문자열이 두 축을 정한다** — 이 바이트를 무엇으로 볼지(MIME 타입)와 어떤 글자 규칙인지(문자집합) → [[request-response]] · [[servlet]]

**그리고 이 회차에서 처음으로 「고칠 수 없는 깨짐」이 나온다.** 필기가 두 자리를 나눠 적었는데 **성질이 반대다.**

| 어디서 깨지나 | Day64 의 설명 | 바이트가 남아 있나 |
|---|---|---|
| **서버(서블릿)** — 인코딩을 지정하지 않고 내보냈다 | 「한글은 없는 문자로 적용되어 ?로 출력된다」 | **없다** — `?` 로 대체돼 나갔다 |
| **브라우저** — 읽는 규칙이 다르다 | 「브라우저상에는 뷁?뷁?으로 표시 된다」 | **있다** — 규칙만 틀렸다 |

**아래쪽은 읽는 규칙을 바꾸면 살아나고 위쪽은 무엇을 해도 안 돌아온다.** 이 노트의 「왜 중요한가」가 「깨진 글자는 대개 데이터가 손상된 것이 아니라 읽는 규칙이 틀린 것이다」로 적어 둔 문장의 **예외가 여기서 처음 나온다** — 담을 자리가 없는 문자를 인코딩하면 **대체 문자로 바꿔서 내보내고**(자바의 기본 대체 문자가 `?` 다) 원본은 그 자리에서 없어진다. 즉 **읽는 쪽 사고는 복구되고 쓰는 쪽 사고는 복구되지 않는다** → [[unicode]] · [[io-stream]]

그리고 규칙을 **어디에 적는가**가 정적·동적으로 갈린다 — 필기의 「인코딩설정 방법」이 그것이다.

| | 규칙을 정하는 것 |
|---|---|
| 서블릿이 만든 HTML | `res.setContentType(...)` → **응답 헤더** |
| 파일로 있는 HTML | 문서 안의 `<meta charset=...>` → [[static-and-dynamic-content]] |

**Day51 의 `DEFAULT CHARACTER SET` 과 같은 일이면서 방향이 반대다** — 저장소에서는 바깥에 한 번 적고 안쪽이 물려받았고, 여기서는 **응답마다** 적어야 한다. 서블릿이 열 개면 열 곳이고, 그것이 이 일을 필터로 옮기는 이유다 → [[servlet-filter]]

## 왜 중요한가

**깨진 글자는 대개 데이터가 손상된 것이 아니라 읽는 규칙이 틀린 것이다.** 이 구분을 하면 고칠 자리가 달라진다 — 파일을 다시 만들 게 아니라 읽는 쪽 설정을 맞추면 되는 경우가 많다.

그리고 이 문제는 **경계를 넘을 때마다** 다시 나온다. 소스와 컴파일러 사이뿐 아니라 브라우저와 서버 사이, 서버와 DB 사이, 파일과 프로그램 사이에서 같은 형태로 반복된다. 층마다 기본값이 다르다는 것이 원인이라 한 번 겪으면 다음에 어디를 볼지 알게 된다.

## 경계와 오해

- **MySQL 의 `utf8` ≠ UTF-8** — 이름이 같아서 「지정했으니 됐다」로 읽히는데, MySQL 의 `utf8` 은 **한 글자에 최대 3바이트만** 쓰는 반쪽 구현(`utf8mb3`)이라 4바이트가 필요한 문자(이모지·일부 한자)를 넣으면 `Incorrect string value` 로 거절한다. 진짜 UTF-8 은 `utf8mb4` 다. **Day51 안에 그 증거가 이미 있다** — 「`varchar` 는 UTF-8 로 지정된 경우 n 이 최대 21844」라는 숫자가 행 상한 65535바이트를 **3으로** 나눈 값이다. 이 노트의 「이름에 UTF 가 붙었다고 UTF-8 인 것이 아니다」(`writeUTF` 항목)와 **같은 함정이 다른 제품에서 반복된 것**이다 → [[unicode]] · [[sql-data-type]]
- **collation ≠ 인코딩** — Day51 이 두 줄을 나란히 적어 하나로 보이지만 축이 다르다. 인코딩은 **글자 → 바이트** 규칙이고 collation 은 **바이트 ↔ 바이트 비교·정렬** 규칙이다. 같은 `utf8` 에도 `utf8_general_ci`·`utf8_bin` 이 붙을 수 있고, 인코딩이 맞는데 정렬이 이상하거나 대소문자가 구분되지 않는 증상은 전부 이쪽이다. **인코딩이 틀리면 글자가 깨져 바로 보이고, collation 이 다르면 결과가 조용히 달라진다** → [[database-schema]] · [[string-comparison]]
- **인코딩 ≠ 폰트** — 글자가 이상하게 보일 때 원인이 갈린다. 인코딩이 틀리면 **다른 글자**가 나오고(`한글` → `ÇÑ±Û`), 폰트가 없으면 자리는 맞고 **모양만** 안 나온다(`□□`).
- **UTF-8 이 기본값인 것은 도구마다 다르다** — "요즘은 다 UTF-8"이 아니라, 각 도구가 자기 기본값을 갖는다. OS 기본값이 다른 것이 [[platform-dependency]] 가 문자 층에서 나타나는 모습이다.
- **완성형 ≠ 조합형** — EUC-KR·MS949 는 완성된 글자에 번호를 붙인 **완성형**이고, 조합형은 초성·중성·종성을 조합해 만든다. 완성형은 목록에 없는 음절을 담을 수 없고(`똡`), 조합형은 표준이 되지 못했다.
- **문자 인코딩과 줄바꿈은 다른 축이다** — 둘 다 "OS 마다 기본값이 다르다"에 걸리지만 별개 문제다 → [[newline-character]]
- **파일 자체에 인코딩이 적혀 있지 않다** — 텍스트 파일은 바이트 나열일 뿐이라, 무슨 규칙으로 저장했는지 파일이 알려주지 않는다. 그래서 읽는 쪽이 추측하거나 지정받아야 한다.
- **「한글이 깨진다. 이유?」의 답은 「지정하지 않으면 기본값을 쓴다」다** — 필기가 `new String(bytes)` 에 물음표로 남긴 자리다. 인자를 안 주면 **실행 환경의 기본 인코딩**으로 읽는데, EUC-KR 바이트인 `B0 A1` 은 UTF-8 규칙에 맞는 조합이 아니라 해석에 실패한다. **바이트가 손상된 것이 아니고 규칙이 틀린 것**이라 `"euc-kr"` 를 넘긴 다음 줄에서 그대로 살아난다. 이 노트의 「기본값이 어긋날 때」가 `javac` 에서 코드 안으로 내려온 것이고, **어긋남이 컴파일이 아니라 실행 결과로 나타나는** 것만 다르다 → [[platform-dependency]]
- **인코딩을 문자열로 넘기면 오타가 컴파일에서 안 걸린다 — 세 주 뒤에 그 답이 나온다** — `"euc-kr"`·`"utf-8"` 은 그냥 문자열이라 `"utf8x"` 라고 써도 컴파일된다. 실행 시점에 예외가 나고, 이름의 대소문자·하이픈 표기가 여러 개 통하는 것도 헷갈리는 자리다. **Day38 은 `StandardCharsets.UTF_8` 상수를 넘긴다** — `Charset` 타입이므로 오타가 **컴파일에서** 걸리고, 이름 표기가 여럿인 문제도 사라지며, 문자열 판을 쓸 때 붙던 `UnsupportedEncodingException`(체크 예외)도 없어진다. **같은 인자 자리에 타입을 세우는 것으로 세 문제가 함께 해결된 것**이고, 문자열 판이 아직 남아 있는 것은 상수가 Java 7 에 와서야 생겼기 때문이다 → [[exception-handling]] · [[literal]] · [[data-type]]
- **문자 수 ≠ 바이트 수 — 그리고 이 차이가 형식을 무너뜨릴 수 있는 자리가 있다** — Day38 은 문자열을 파일에 담을 때 길이를 먼저 적는데, 그 길이가 `name.getBytes(UTF_8).length` 이고 `name.length()` 가 아니다. 「이건학」은 앞이 9, 뒤가 3 이다. `length()` 를 적었다면 **3바이트만 읽어 「이」 하나로 복원되고 남은 6바이트가 다음 필드의 길이 자리로 밀려** 뒤가 전부 무너진다. **UTF-8 이 가변 길이인 것이 길이를 적어야 하는 이유이면서 그 길이를 잘못 셀 수 있는 이유**이고, 두 값이 알파벳 이름에서는 같아서 영어로 시험하면 드러나지 않는다 → [[length-prefix-framing]] · [[string-comparison]]
- **파일에 인코딩이 적혀 있지 않은 문제가 바이너리 형식에서도 그대로다** — 위의 「파일 자체에 인코딩이 적혀 있지 않다」와 같은 자리다. Day38 의 `user.data` 는 UTF-8 로 쓴 바이트를 담고 있지만 그 사실이 파일에 없고, **`getBytes` 와 `valueOf` 두 메서드가 같은 상수를 쓴다는 것에만 있다.** 한쪽만 다른 인코딩으로 고치면 컴파일도 되고 실행도 되며 저장된 파일만 못 읽게 된다 → [[serialization]] · [[binary-io]]
- **하루 뒤 규칙이 코드에서 사라진다 — 지정할 자리가 없어졌기 때문이다** — Day39 는 `writeUTF`/`readUTF` 와 `FileReader`/`FileWriter` 를 쓰는데 **어디에도 인코딩 인자가 없다.** 규칙이 없어진 것이 아니라 **누가 정하는지가 옮겨 간 것**이고, 두 경우가 정반대다. `writeUTF` 는 규칙을 **규격으로 못 박아** 인자를 받지 않고(그래서 왕복이 늘 성립한다), `FileReader` 는 규칙을 **환경 기본값에 맡겨** 인자를 받지 않는다(그래서 왕복이 환경에 따라 깨진다). **인자가 없는 두 API 가 정반대의 이유로 그런 것**이고, 「지정하지 않아도 되는 것」과 「지정할 수 있었는데 안 한 것」을 가르지 않으면 Day38 이 `StandardCharsets.UTF_8` 로 얻은 것이 조용히 반납된다 → [[character-stream]] · [[data-io-stream]] · [[platform-dependency]]
- **`writeUTF` 의 UTF 는 표준 UTF-8 이 아니다** — 수정(modified) UTF-8 이라 두 곳이 다르다. `U+0000` 을 1바이트 `00` 대신 2바이트로 적고, 보조 평면 문자(이모지)를 4바이트 하나가 아니라 **서로게이트 쌍을 각각 3바이트씩 6바이트**로 적는다. Java 안에서 `readUTF` 로 되읽는 한 문제가 없지만, 그 바이트를 다른 언어의 UTF-8 디코더에 넘기면 깨진다. **이름에 UTF 가 붙었다고 UTF-8 인 것이 아니고**, 「파일 자체에 인코딩이 적혀 있지 않다」가 이 경우에는 「적혀 있지 않은데 표준과 미묘하게 다르다」로 한 겹 더해진다 → [[unicode]] · [[data-io-stream]]
- **`char[]` 로 만들 때는 인코딩이 없다** — `new String(chars)` 는 규칙을 안 받는다. `char` 는 이미 유니코드 번호를 담고 있어 변환할 것이 없기 때문이다. **인코딩은 `byte` 와 글자 사이에서만 문제가 되고 `char` 와 글자 사이에서는 아니다** → [[unicode]] · [[data-type]]
- **닷새 뒤 문자열 판이 다시 돌아온다 — 그리고 같은 노트에 타입 판도 함께 있다** — Day38 이 `StandardCharsets.UTF_8` 로 얻은 것(오타가 컴파일에서 걸린다·체크 예외가 없어진다)이 Day41 의 `str.getBytes("UTF-8")` 에서 반납된다. 그런데 같은 노트의 문자 스트림 절은 `Charset.forName("MS949")` 로 **`Charset` 객체를 만들어 넘긴다.** 세 형태가 한 필기 안에 있고 성질이 셋 다 다르다 — `getBytes(String)` 은 **체크 예외**(`UnsupportedEncodingException`)를 던져 `throws` 를 강제하고, `Charset.forName(String)` 은 **비체크 예외**(`UnsupportedCharsetException`)를 던지며 이름 검증이 한 번에 끝나고, `StandardCharsets.UTF_8` 은 **이름을 아예 쓰지 않아** 검증할 것이 없다. **문자열을 어디까지 끌고 가는가로 세 형태가 갈리는 것**이고, 이름을 문자열로 쓸 수밖에 없는 경우(MS949 처럼 `StandardCharsets` 에 상수가 없는 것)에는 `Charset.forName` 이 그 중간 답이다 → [[exception-handling]] · [[literal]]
- **「윈도우는 UCS2 -> MS949」는 JDK 18 부터 성립하지 않는다** — 필기가 기본값을 환경의 문제로 본 것은 맞지만, JDK 18 이 기본 문자집합을 **OS 와 무관하게 UTF-8 로 고정**했다. 그래서 같은 코드가 같은 Windows 에서 JDK 17 과 JDK 18 에 다른 바이트를 만든다 — 갈리는 축이 「어느 OS 인가」에서 **「어느 JDK 인가」로 하나 늘었다.** 「기본값에 맡기지 않는다」가 답인 것은 그대로이고, 이유가 하나 더 붙은 것이다. 필기의 예제에서 `getBytes()` 가 UTF-8 결과를 낸 것도 **작성자의 환경이 그랬다**는 기록일 뿐 규칙이 아니다 → [[platform-dependency]] · [[jdk]]
- **「서블릿은 기본적으로 UTF-16BE 인코딩을 사용한다」 — 두 사실이 섞였다. 서블릿 응답의 기본 문자집합은 ISO-8859-1 이다** — Day64 필기의 두 줄이 「UTF-16BE 를 쓰다가 ISO-8859-1 로 변환한다」로 읽히는데, 실제로는 **한 단계뿐이다.** 자바 `String` 이 메모리에서 UTF-16 인 것(그래서 Day41 이 `getBytes("UTF-16BE")` 를 볼 수 있었던 것)은 **인코딩 선택이 아니라 언어의 내부 표현**이고, 그것을 바이트로 내보낼 때 쓰는 규칙의 **기본값이 ISO-8859-1** 이다. 「UTF-16BE 를 쓴다」로 읽으면 응답이 2바이트 문자로 나가는 그림이 되는데 그런 일은 없다. **결론(한글이 `?` 가 된다)은 맞고 경로가 한 겹 어긋난 것**이라 코드로는 드러나지 않는다 — `setContentType` 을 부르면 어느 쪽 이해로도 고쳐진다 → [[unicode]] · [[data-type]]
- **「ISO-8859-1(아스키코드)」도 다르다 — 그리고 이 차이가 「왜 `?` 인가」의 답을 바꾼다** — ISO-8859-1 은 ASCII(7비트 128자)의 **8비트 확장**이고 상위 128칸에 라틴 문자가 채워져 있다. 이 노트의 정의 표에 이미 두 줄로 갈라 적혀 있다. 「아스키코드」로 읽으면 한글이 못 담기는 이유가 **「7비트라서」**가 되는데, 실제 이유는 **256칸이 전부 채워져 있고 그중 한글이 없어서**다. 「비트 수를 늘리면 된다」와 「다른 표를 써야 한다」의 차이이고, 뒤쪽이 유니코드가 존재하는 이유다 → [[unicode]]
- **필기가 적은 「뷁?뷁?」은 조합이 하나 더 있는 경우다 — 요지는 그대로다** — UTF-8 로 보낸 바이트를 ISO-8859-1 로 읽으면 3바이트가 라틴 문자 세 개로 흩어져 보이고(`ê°`), 「뷁」처럼 **한글 완성형 글자가 나오는 것은 MS949·EUC-KR 계열로 읽었을 때**의 모양에 가깝다. 어느 조합이든 이 절이 말하려는 것은 같다 — **바이트는 온전하고 읽는 규칙만 틀렸다.** 그래서 이 자리의 값은 어떤 글자가 보이는지가 아니라 **바로 위 항목(서버 쪽 `?`)과 복구 가능성이 반대**라는 대비다 → [[platform-dependency]]
- **`setContentType` 은 `getWriter()` 보다 먼저여야 한다 — 순서를 바꾸면 오류 없이 무시된다** — `getWriter()` 가 불리는 순간 그 응답의 문자 인코딩이 확정되므로, 뒤에 온 `setContentType` 은 **조용히 버려진다.** Day64 의 코드는 순서가 맞는데 **왜 그 순서인지가 주석에 없어서** 줄을 옮기면 깨진다는 것을 알 수 없다. [[tomcat]] 노트의 「`setPort` 와 `getConnector` 의 순서가 뜻을 갖는다」와 같은 형태의 함정이고, **이번에는 요청마다 걸린다** → [[request-response]] · [[io-stream]]
- **「HTML에 메타데이터를 입력하지 않아도 자동으로 메타데이터에 인코딩 설정이 된다」 — 결론은 맞고 기전이 다르다** — 컨테이너가 HTML 안에 `<meta>` 를 끼워 넣어 주는 것이 아니라 **`Content-Type` 응답 헤더**를 보내고, 브라우저는 **헤더를 문서 안의 `<meta>` 보다 우선**한다. 그래서 동적 HTML 은 `<meta>` 가 없어도 되고 파일로 있는 정적 HTML 은 헤더에 문자집합이 없을 수 있어 `<meta>` 가 필요하다. 「메타데이터에 설정된다」로 알고 있으면 **헤더와 `<meta>` 가 다른 값일 때 어느 쪽이 이기는지**를 모른다 — 헤더가 이긴다. Day64 의 코드는 둘을 **다 넣었다**(`setContentType` 과 `<meta charset='UTF-8'>`) → [[static-and-dynamic-content]]
- **요청 쪽 인코딩은 이 회차에 없다 — 「UTF-8 로 설정했다」가 절반만 한 것이 되는 자리다** — `setContentType` 은 **나가는 것**만 정한다. 브라우저가 보낸 파라미터를 한글로 읽으려면 `request.setCharacterEncoding("UTF-8")` 을 **파라미터를 처음 읽기 전에** 불러야 하고, 그 시점 제약 때문에 서블릿마다 첫 줄에 넣게 된다. Day64 의 서블릿이 요청 객체를 아예 쓰지 않아 이 절반이 드러나지 않았다 → [[request-response]] · [[servlet-filter]]
- **`new String(byte[], 시작, 끝, 인코더)` — 세 번째 인자는 「끝」이 아니라 「길이」다 — Day41 필기의 오류다** — 생성자의 시그니처는 `String(byte[] bytes, int offset, int length, Charset)` 이고 **읽을 개수**를 받는다. 필기가 골격을 「시작, 끝」으로 적었는데, 바로 다음 예제가 `new String(buf, 0, count, 인코더정보)` 로 **offset 이 0** 이라 「끝」과 「길이」가 같은 값이 되어 **틀린 이해로도 맞는 코드가 나온다.** offset 을 0 이 아니게 주는 순간 갈린다 — 「10번부터 20번까지」를 뜻하고 `(buf, 10, 20, cs)` 라 쓰면 실제로는 10~29번을 읽고, 배열이 짧으면 `IndexOutOfBoundsException`, 길면 **뒤쪽 열 바이트가 조용히 붙어 나온다.** 같은 노트의 `read(buf, offset, len)` 설명은 「[offset,offset+count)」로 정확히 적혀 있어 **한 노트 안에서 같은 형태의 인자를 한 번은 맞게, 한 번은 틀리게 읽었다** → [[array]] · [[parameter-and-argument]]

- [[2024-06-25-Day22]] — `new String(byte[], "euc-kr")`·`"utf-16"`·`"utf-8"` 로 **코드 안에서** 인코딩을 지정하는 것을 배웠다. 같은 글자 `가각` 을 세 규칙의 바이트로 나란히 적어 놓아 EUC-KR 의 `B0A1`·UTF-16 의 `AC00`·UTF-8 의 `EAB080` 이 대비되고, 지정하지 않은 `new String(bytes)` 에 「한글이 깨진다. 이유?」를 남겨 두었다 — 기본 인코딩으로 읽었기 때문이고 물음은 필기에서 답 없이 끝난다
- [[2024-07-18-Day38]] — 파일 저장 실습에서 **쓰는 쪽**의 인코딩을 처음 지정한다 — `name.getBytes(StandardCharsets.UTF_8)` 로 문자열을 바이트로 만들고 `new String(buffer, 0, len, StandardCharsets.UTF_8)` 로 되돌린다. **규칙을 문자열이 아니라 `Charset` 상수로 넘기는 형태**이고, Day22 의 `"utf-8"` 문자열 판이 갖던 오타·표기 문제와 체크 예외가 여기서 사라진다. 그리고 길이 접두사에 적는 값이 `getBytes(UTF_8).length` 라서 **UTF-8 의 가변 길이가 형식의 일부가 된다** — 문자 수를 적었다면 한글 이름부터 파일이 무너지는데, 필기는 이 구분을 따로 적지 않았다
- [[2024-07-19-Day39]] — 같은 저장·로딩을 표준 도구로 다시 짜면서 **인코딩 인자가 코드에서 사라진다.** `writeUTF`/`readUTF` 는 규칙을 규격으로 갖고 있어 인자를 받지 않지만 그 규칙이 **표준 UTF-8 이 아니라 수정 UTF-8** 이고, `new FileReader("user.csv")`·`new FileWriter("user.csv")` 는 규칙을 **환경 기본값에 맡긴다** — Day38 이 `StandardCharsets.UTF_8` 로 코드에 박아 두었던 것이 여기서 없어져 **같은 코드가 OS·JDK 버전에 따라 다른 파일을 만든다.** 필기는 두 경우 모두 인코딩을 언급하지 않았다
- [[2024-07-23-Day41]] — `"AB가각"` 하나에서 `getBytes()`·`"UTF-8"`·`"MS949"`·`"UTF-16BE"`·`"UTF-16LE"` 다섯 배열을 꺼내고 결과를 주석으로 나란히 적어 **같은 네 글자가 규칙에 따라 6~8바이트로 갈리는 것**을 한 화면에 놓는다(Day22 의 「이 바이트를 이 규칙으로 읽으면」의 반대 방향이다). 마지막 두 줄이 규칙이 아니라 **순서만 다르다**는 것이 여기서 처음 나오고, 그것은 인코딩과 별개의 축이다. 인코딩을 지정하는 형태 셋이 한 노트에 섞여 있다 — `getBytes("UTF-8")`(문자열·체크 예외) · `Charset.forName("MS949")`(객체·비체크 예외) · 인자 없는 기본값 — 이고, Day38 이 `StandardCharsets` 상수로 얻었던 것이 문자열 판에서 다시 반납된다. 기본값을 「UCS2 -> UTF-8, 단 윈도우는 MS949」로 적어 **환경의 문제라는 것은 정확히 봤지만** JDK 18 부터 OS 와 무관하게 UTF-8 로 고정된 것은 반영되지 않았고, `new String(byte[], 시작, 끝, 인코더)` 로 골격을 적어 **세 번째 인자를 「끝」으로 읽었다** — 예제의 offset 이 0 이라 그 오해가 화면에서 드러나지 않는다
- [[2024-08-06-Day51]] — 규칙을 **저장소에 붙이는** 형태가 처음 나온다. `CREATE DATABASE studydb DEFAULT CHARACTER SET utf8 DEFAULT COLLATE utf8_general_ci` 를 「인코딩 방식」·「정렬 및 비교 방식」 두 주석으로 갈라 적어 **비교·정렬 규칙(collation)이 인코딩과 별개의 축**임을 알고 있고, `DEFAULT` 라 테이블·컬럼이 물려받는다. 컬럼 타입 절의 「`varchar` 는 ISO-8859-n 이면 최대 65535, UTF-8 이면 최대 21844」는 **문자집합이 컬럼의 최대 길이를 정한다**는 것을 보여 주는데, 그 21844 라는 값 자체가 MySQL 의 `utf8` 이 3바이트 구현이라는 뜻이다 — 필기는 그것을 UTF-8 이라 적었다
- [[2024-08-27-Day64]] — 규칙을 **HTTP 응답**에 붙이는 형태가 처음 나온다. 「문자열 출력시 글자 깨짐」 절이 원인을 두 자리로 나눠 적고(서블릿 쪽·브라우저 쪽) 골격을 `ServletResponse.setContentType("MIME타입;문자집합")` 으로 남겼으며, 서블릿 코드가 `res.setContentType("text/html;charset=UTF-8")` → `getWriter()` 순서로 실제로 그것을 한다. 「인코딩설정 방법」 절이 **동적 HTML 은 `setContentType`, 정적 HTML 은 `<meta>`** 로 갈라 적어 규칙을 적을 자리가 콘텐츠 종류에 따라 다르다는 것을 보여 준다. 이 회차가 이 개념에 더하는 가장 큰 것은 **복구 가능성의 대비**다 — 서버가 못 담는 글자를 `?` 로 바꿔 내보낸 것은 되돌릴 수 없고(「한글은 없는 문자로 적용되어 ?로 출력된다」), 브라우저가 규칙을 잘못 잡은 것은 규칙만 바꾸면 살아난다(「브라우저상에는 뷁?뷁?으로 표시 된다」). 다만 「서블릿은 기본적으로 UTF-16BE 인코딩을 사용한다」는 자바 `String` 의 내부 표현과 응답 기본 문자집합(**ISO-8859-1**)을 섞은 것이고, 「ISO-8859-1(아스키코드)」도 정확하지 않다(ASCII 의 8비트 확장이고, 한글이 못 담기는 이유는 비트 수가 아니라 표에 없어서다). 「자동으로 메타데이터에 인코딩 설정이 된다」는 결론은 맞지만 실제로는 **응답 헤더**가 나가고 브라우저가 그것을 `<meta>` 보다 우선하는 것이며, `setContentType` 을 `getWriter()` 앞에 두어야 하는 이유와 **요청 쪽 인코딩**(`setCharacterEncoding`)은 다루지 않았다
