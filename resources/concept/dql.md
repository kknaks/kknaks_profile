# DQL (Data Query Language) — select

**데이터를 바꾸지 않고 꺼내 오는 문장.** Day52 의 한 줄이 「데이터 조회를 다루는 SQL문법」이고 문장은 하나(`select`)다. 그 하나 안에 **고르는 축이 두 개**로 갈려 있고, Day52 가 그 둘에 이름을 붙인다 — 컬럼을 고르는 것이 **프로젝션**, 행을 고르는 것이 **셀렉션**이다.

**5일 뒤 Day54 가 축을 두 개 더 붙인다** — 행을 **어떤 순서로** 줄 것인가(`order by`)와 같은 값을 **몇 번** 줄 것인가(`distinct`)다. 자를 대상이 아니라 **결과를 내놓는 방식**을 정하는 조각이라 앞의 둘과 층이 다르다.

## 정의

`select` 한 문장은 세 조각이고, 각 조각이 결과의 다른 축을 자른다.

| 조각 | 이름 | 자르는 축 | 없으면 |
|---|---|---|---|
| `select 컬럼목록` | 프로젝션 (projection) | **열** | `*` 로 전부 |
| `from 테이블명` | — | 어느 테이블인가 | 테이블 없는 조회 (아래) |
| `where 조건` | 셀렉션 (selection) | **행** | 모든 행 |

**두 낱말이 반대 방향을 가리킨다.** Day52 가 각각 「특정 칼럼의 값만 조회하는 것을 프로젝션이라고 한다」·「조건을 지정해서 결과를 선택하는 것을 셀렉션이라고 한다」로 적었다.

```sql
select * from 테이블명;                                  -- 열 전부 · 행 전부
select 컬럼명, 컬럼명 from 테이블명;                       -- 프로젝션
select * from 테이블명 where 조건;                        -- 셀렉션
```

### 결과의 컬럼은 만들어 낼 수 있다

조회 결과의 열이 테이블의 컬럼과 1:1 일 필요가 없다. 값을 이어 붙인 것도 한 열이 된다.

```sql
select 컬럼명, concat(컬럼명,컬럼명) from 테이블명;
```

그리고 그 열의 **이름을 정하는 것**이 `as` 다. Day52 가 「as는 생략가능하다」고 적었다.

```sql
select 컬럼명 as 별명, concat(컬럼명,컬럼명) as 별명 from 테이블명;
select 컬럼명 별명, concat(컬럼명,컬럼명) 별명 from 테이블명;
```

**`as` 는 보기 좋게 하는 장치가 아니라 결과의 스키마를 정하는 일이다** — `concat(name, tel)` 의 기본 열 이름은 그 식 전체이므로, 애플리케이션이 이름으로 값을 꺼내려면 별칭이 있어야 한다.

Day54 가 여기에 한 줄을 더한다 — 「별명에 공백을 삽입하려면 `''` 으로 묶어서 표기한다」.

```sql
select 컬럼명 '별  명' from 테이블명;
```

### 순서와 중복 — Day54 가 더한 두 조각

Day54 가 「select column」·「Order by」 두 절로 붙인 것이 **행의 중복**과 **행의 순서**다. 둘 다 이미 고른 행들을 대상으로 하므로 `where` 뒤에 온다.

| 조각 | 정하는 것 | 생략하면 | 반대쪽 키워드 |
|---|---|---|---|
| `select all` / `select distinct` | 같은 결과 행을 **몇 번 줄 것인가** | `all` — 중복을 그대로 준다 | `all` 이 기본값 |
| `order by 컬럼 asc` / `desc` | 행을 **어떤 순서로** 줄 것인가 | **순서를 요구하지 않음** | `asc` 가 기본값 |

```sql
select all 컬럼명 from 테이블명;      -- all 은 생략 가능하다
select distinct 컬럼명 from 테이블명;

select 컬럼명 from 테이블명 order by 정렬할_컬럼명 asc;   -- asc 는 생략 가능하다
select 컬럼명 from 테이블명 order by 정렬할_컬럼명 desc;
```

**두 키워드 다 「생략 가능한 쪽」이 기본값**이라, 필기가 `all`·`asc` 를 적어 둔 것은 문법을 쓰기 위해서가 아니라 **반대쪽이 있다는 것을 드러내기 위해서**다. `all` 을 알기 전에는 `distinct` 가 「추가 기능」으로 보이지만, 실제로는 **둘 중 하나를 고르는 자리이고 안 고르면 `all` 이 골라진다.**

## 사용 예시

Day52 는 조회를 다섯 단계로 넓혀 간다 — 전부 → 고른 열 → 만든 열 → 이름 붙인 열 → 고른 행.

```sql
select * from 테이블명;

select 컬럼명, concat(컬럼명,컬럼명) from 테이블명;

select 컬럼명 as 별명, concat(컬럼명,컬럼명) as 별명 from 테이블명;

select * from 테이블명 where 조건;
```

그리고 **테이블 없이도 `select` 가 성립한다.** 같은 노트의 연산자 절과 날짜 절이 실제로 그렇게 쓴다.

```sql
select (4 + 5), (4 - 5), (4 * 5), (4 / 5), (4 % 5);
select now();
select 5 between 3 and 5;
```

**`from` 이 없는 `select` 는 서버에게 식을 계산시키는 것**이고, 그래서 테이블을 만들지 않고도 문법을 시험할 수 있다. Day52 가 연산자와 날짜 함수를 배우는 방식이 전부 이 형태다 → [[sql-operator]] · [[sql-date-function]]

Day54 는 별칭 예제를 **혼자 두지 않고 `order by` 와 함께** 적어서, 한 문장 안에 조각이 늘어나는 모양을 보여 준다.

```sql
select 컬럼명 as 별명, 컬럼명 as 별명 from 테이블명 order by 정렬할_컬럼명;
select 컬럼명 별명, 컬럼명 별명 ..... from 테이블명 order by 정렬할_컬럼명;
```

`select` → `from` → `order by` 가 **적는 순서**이고, 서버가 평가하는 순서는 `from` → `where` → `select` → `order by` 다 — 그 어긋남이 아래 「경계와 오해」의 별칭 항목들을 만든다.

## 왜 중요한가

**「어느 행을 볼 것인가」가 코드에서 문장으로 옮겨 온다.** 자바로 만든 목록·조회는 배열을 처음부터 끝까지 돌며 조건을 `if` 로 걸렀고, 조건이 바뀌면 메서드를 고쳐야 했다. `where` 는 같은 일을 **문자열 한 줄**로 하고, 훑는 방법(전체 스캔인가 인덱스인가)은 서버가 정한다 — 내가 정하는 것은 **무엇을 원하는가**뿐이다 → [[linear-search]] · [[database-index]]

**`select *` 와 컬럼 지정의 차이가 나중에 계약이 된다.** `*` 는 「지금 이 테이블에 있는 모든 컬럼」이라서, `alter table ... add column` 한 번으로 **결과의 모양이 바뀐다.** 열의 개수·순서를 믿고 읽는 코드는 그때 조용히 어긋나고, 필요 없는 큰 컬럼(`text`)까지 네트워크로 실려 온다. 컬럼을 적어 두는 것은 **결과의 모양을 내가 고정하는 일**이다 → [[ddl]] · [[sql-data-type]]

**그리고 조회가 값을 만들어 낼 수 있다는 것이 화면 코드를 줄인다.** 이름과 연락처를 붙여 보여 주는 일을 `concat` 이 하면 자바 쪽 `printf` 가 짧아진다. 반대로 **표시 형식을 SQL 에 넣으면 그 쿼리는 그 화면 전용이 된다** — 저장·조회·표시 중 어디까지를 DB 에 맡길지의 첫 선택이 이 자리다 → [[format-string]]

## 경계와 오해

- **프로젝션 ≠ 셀렉션 — 그런데 SQL 의 키워드는 `select` 다** — 두 낱말이 Day52 의 같은 절에 나란히 있고 뜻은 수직·수평으로 반대다(프로젝션은 **열**, 셀렉션은 **행**). 헷갈리는 원인은 문법 쪽에 있다: 영어 `select`(고르다)가 정작 **프로젝션 자리**의 키워드이고, **셀렉션은 `where`** 가 맡는다. 「select 니까 셀렉션」으로 읽으면 두 이름이 뒤집힌다. 관계대수에서 온 용어이며 각각 π(프로젝션)·σ(셀렉션)다.
- **「특정 칼럼 데이터 조회하기」의 예제 코드는 다음 절과 똑같다** — Day52 의 그 자리에 붙은 코드는 `select 컬럼명, concat(컬럼명,컬럼명) from 테이블명;` 으로 바로 다음 「특정 칼럼 병합하여 조회」와 한 글자도 다르지 않다. 붙여넣기 사고이고, **그 자리에 들어갈 형태는 `select 컬럼명, 컬럼명 from 테이블명;`** 다 — 프로젝션의 최소형에는 `concat` 이 필요 없다. 본문은 그대로 두었으므로 「프로젝션 = 컬럼을 이어 붙이는 것」으로 읽히지 않게 이 노트가 그 답을 갖는다.
- **`as` 를 생략할 수 있다는 것이 콤마 하나를 침묵하게 만든다** — `select name, tel from t` 에서 콤마를 빠뜨리면 `select name tel from t` 가 되는데, 이것은 **오류가 아니라 `name` 컬럼 하나를 `tel` 이라는 이름으로** 돌려주는 정당한 문장이다. 결과에 `tel` 이라는 열이 있으니 애플리케이션도 눈치채지 못하고, **연락처 자리에 이름이 찍힌다.** 「생략 가능」의 대가가 여기 있다.
- **`as` 로 붙인 별칭은 `where` 에서 쓸 수 없다** — `select age as 나이 from t where 나이 > 20` 은 `Unknown column '나이' in 'where clause'` 다. `where` 가 먼저 평가되고 별칭은 그 뒤에 붙기 때문이다. 반대로 `having`·`order by` 에서는 쓸 수 있어서 **규칙이 절마다 다르다.** Day52 가 별칭을 배운 바로 다음 절에서 `where` 를 배우므로 부딪히기 쉬운 자리이고, **Day54 의 별칭 예제는 전부 `order by` 를 함께 달고 있어** 되는 쪽만 보게 된다 — 같은 이름이 한 절에서는 통하고 다른 절에서는 없는 컬럼이 되는 이유가 **평가 순서**라는 것을 알아 두지 않으면 오류 메시지가 읽히지 않는다.
- **별칭의 `''` 는 MySQL 방언이고, 위치가 한 칸 어긋나면 값이 된다** — Day54 의 「별명에 공백을 삽입하려면 `''` 으로 묶어서 표기한다」는 MySQL 에서 참이지만 표준은 겹따옴표(`"별  명"`)이고, Oracle·PostgreSQL 에서 `'별  명'` 을 별칭 자리에 쓰면 문법 오류다. 더 걸리는 것은 **같은 표기가 자리에 따라 다른 것이 된다**는 점이다 — `select 컬럼명 '별  명' from t` 는 별칭이지만 `select '별  명' from t` 는 **모든 행에 그 글자를 채워 넣는 문자열 리터럴 컬럼**이다. 컬럼명 하나를 지우거나 콤마를 하나 더하면 별칭이 값으로 바뀌고, 두 경우 다 오류가 아니다 → [[literal]]
- **`select all` 의 `all` 은 「모든 컬럼」이 아니다** — Day54 의 「컬럼 가져오기」 절이 `select all 컬럼명 from 테이블명` 으로 시작하고 바로 아래에 `select 컬럼명` 이 있어서, `all` 이 `*` 의 다른 표기처럼 읽힌다. **`all` 은 컬럼이 아니라 중복에 대한 지시**이고 `distinct` 의 반대다(`select all 컬럼명` = `select 컬럼명`, `select * ` 와는 아무 관계가 없다). 두 낱말이 같은 절의 위아래에 놓여 있어 겹쳐 읽기 가장 쉬운 자리다.
- **`distinct` 는 컬럼 하나에 걸리는 것이 아니라 `select` 목록 전체에 걸린다** — Day54 의 예제가 컬럼 하나뿐이라 드러나지 않는다. `select distinct name, tel from t` 는 「이름의 중복을 없애고 연락처도 보여 준다」가 아니라 **`(name, tel)` 조합이 같은 행만 접는다** — 이름이 같고 연락처가 다르면 둘 다 남는다. `select distinct(name), tel from t` 로 괄호를 씌워도 결과는 똑같다(괄호가 함수처럼 보이지만 그냥 식을 감싼 것이다). **「컬럼을 하나 더 꺼냈더니 중복이 다시 나타났다」의 원인이 전부 이것**이고, 조회가 원하는 답을 못 줄 때 `distinct` 를 덧붙이는 습관이 여기서 조용히 실패한다 → [[sql-set-operation]]
- **`distinct` 는 `NULL` 끼리를 같은 값으로 본다** — `where 컬럼 = null` 이 한 행도 못 잡는 것과 정반대로, `distinct` 는 `NULL` 이 든 행 여럿을 **한 줄로 접는다.** 「`NULL` 은 자기 자신과도 같지 않다」로만 외우면 이 결과가 설명되지 않는다 → [[sql-null]] · [[sql-set-operation]]
- **`order by` 를 컬럼 번호로 쓸 수 있고, 그것이 조용히 어긋난다** — `order by 2` 는 「`select` 목록의 두 번째 열로 정렬」이라는 뜻으로 동작한다. 짧아서 쓰게 되는데, 뒤에 누가 `select` 목록에 컬럼을 하나 끼워 넣으면 **정렬 기준이 말없이 다른 컬럼으로 옮겨간다.** 오류도 경고도 없다.
- **`order by` 에서 `NULL` 은 「가장 작은 값」이 아니라 규약이다** — MySQL 오름차순에서 `NULL` 이 맨 앞에 오고, Oracle 은 기본이 맨 뒤다. Day54 가 `asc`/`desc` 만 다루므로 이 자리가 비어 있다 → [[sql-null]]
- **`concat` 은 인수 하나가 `NULL` 이면 결과 전체가 `NULL` 이다** — 이름과 연락처를 붙일 때 연락처가 없는 행은 빈 문자열이 아니라 **아무것도 없는 값**이 된다. 자바의 `"a" + null` 이 `"anull"` 이 되던 것과 정반대다. 빠진 값을 건너뛰고 이어 붙이려면 `concat_ws` 나 `ifnull` 이 필요하다 → [[sql-null]] · [[string-comparison]]
- **`select *` 의 `*` 는 「모든 행」이 아니라 「모든 컬럼」이다** — `where` 를 안 썼을 때 행이 전부 나오는 것은 `*` 때문이 아니라 셀렉션이 없기 때문이다. 「전체 조회」라는 말로 둘을 함께 부르면 `select * from t where no=1` 이 왜 한 행인지 설명되지 않는다.
- **`order by` 가 없는 `select` 의 결과 순서는 보장되지 않는다** — Day52 에는 `order by` 가 아예 없고 결과 화면이 등록 순서로 보인다. InnoDB 가 기본키 순서로 데이터를 보관하기 때문에 대개 그렇게 나오는 것이지 **문장이 요구한 것이 아니다.** 인덱스를 쓰거나 실행 계획이 바뀌면 순서가 달라지고, 「보이는 순서」에 기대던 화면이 그때 깨진다. **5일 뒤 Day54 가 `order by` 를 배우면서 이 자리가 채워진다** — 순서가 필요하면 요구해야 하고, 요구하지 않은 순서는 우연이다. Day52 의 화면을 「등록순으로 나온다」로 읽어 두었다가 Day54 이후에도 `order by` 를 안 붙이는 것이 이 회차가 남기는 위험이다 → [[primary-key]] · [[database-index]]
- **조회는 데이터를 바꾸지 않지만 무료도 아니다** — `select` 는 값을 고치지 않아서 되돌릴 일이 없지만, 큰 테이블을 훑는 조회는 서버 자원을 쓰고 다른 문장을 기다리게 만든다. 「읽기만 하니 안전하다」와 「부담이 없다」는 다른 이야기다 → [[transaction]]
- **`select` 는 화면이 아니라 값의 집합을 돌려준다** — `mysql` 클라이언트가 표로 그려 주기 때문에 결과가 곧 화면처럼 보이지만, 서버가 준 것은 열 이름과 행들이다. 자바에서 목록과 조회가 **같은 데이터로 다른 형식을 찍던 구분**이 그대로 남아 있다 → [[crud]] · [[format-string]]

## 출처

- [[2024-10-21-Day98]] — 두 달 뒤. **`limit` 이 「결과를 줄여 보는 것」에서 「화면을 나누는 장치」가 된다.** `limit 시작행, 개수` 의 두 인자 형태와 **시작 행이 0부터**라는 것(`limit 4,4` → 5번째부터 4개)이 명시되고, 그 두 값이 `(pageNo-1)*pageSize` 와 `pageSize` 로 계산돼 들어온다. 함께 있는 `order by` 가 장식이 아니라 **필수 조건**이라는 것은 적히지 않았다 → [[pagination]]
- [[2024-08-07-Day52]] — 「데이터 조회를 다루는 SQL문법」으로 DQL 을 정의하고 `select *` → 특정 컬럼 → `concat` 병합 → `as` 별칭 → `where` 순으로 넓혀 갔다. **프로젝션(열)과 셀렉션(행)이라는 두 이름이 이 회차에서 나온다.** 「as는 생략가능하다」도 여기서 적혔다. 「특정 칼럼 데이터 조회하기」의 예제 코드는 바로 다음 「병합하여 조회」와 동일해서 프로젝션의 최소형이 빠져 있고, 연산자·날짜 절의 `select (4+5)`·`select now()` 는 `from` 없는 조회의 실제 예다
- [[2024-08-12-Day54]] — 5일 뒤 「SQL 기본문법(추가)」로 돌아와 **결과를 내놓는 방식**을 더한다 — `select all`/`select distinct`(중복), `order by ... asc`/`desc`(순서), 그리고 별칭에 공백을 넣는 `'별  명'` 표기다. `all`·`asc` 를 **생략 가능한 기본값으로 명시해 적은 것**이 이 회차의 값이고, 그래서 `distinct` 가 추가 기능이 아니라 두 선택 중 하나임이 드러난다. 별칭 예제 전부에 `order by` 를 함께 달아 두었다. 다만 `distinct` 예제가 컬럼 하나뿐이라 **`select` 목록 전체에 걸린다는 성질**이 드러나지 않고, `all` 이 `select *` 바로 위아래에 놓여 「모든 컬럼」으로 읽힐 여지가 있다. `order by` 의 `NULL` 위치·컬럼 번호 정렬·다중 컬럼 정렬은 다루지 않았고, 별칭의 `''` 가 MySQL 방언이라는 것도 적히지 않았다
