# 재귀 호출 (Recursion)

메서드가 **자기 자신을 다시 호출**하는 것. 호출이 끝나기 전에 같은 메서드가 또 불리므로, [[jvm-stack]] 에 같은 모양의 프레임이 층층이 쌓인다.

## 정의

호출이 끝나기 전에 자신을 부르는 것이므로, **되돌아 나올 조건이 코드 안에 있어야** 한다.

```java
static int f(int n) {
    if (n <= 1) return 1;      // 종료 조건 — 여기서 더 이상 자신을 부르지 않는다
    return n * f(n - 1);       // 자기 자신을 호출
}
```

두 부분이 한 벌이다.

| 부분 | 하는 일 | 없으면 |
|---|---|---|
| 종료 조건 | 더 부르지 않고 값을 돌려준다 | 프레임이 계속 쌓여 `StackOverflowError` |
| 재귀 단계 | 문제를 한 단계 줄여 자신을 부른다 | 같은 문제를 그대로 넘겨 역시 끝나지 않는다 |

이 필기는 재귀를 이렇게 정리했다.

```text
메서드를 중복해서 호출 할 수 있으며, 이를 재귀함수라고 한다.
재귀함수의 깊이가 깊어지면 stack 메모리를 초과하여 stack overflow를 발생시킨다.
```

뒤 문장은 정확하지만 앞 문장은 재귀의 정의가 아니다 → 「경계와 오해」

## 왜 중요한가

**반복문과 달리 재귀는 깊이가 곧 메모리다.** `for` 는 몇 번을 돌든 프레임이 하나지만, 재귀는 한 단계마다 프레임 하나를 쓴다. 같은 일을 하는 두 코드가 성능이 아니라 **죽는 방식**에서 갈리는 것이다 → [[for-loop]] · [[while-loop]]

두 번째는 **종료 조건이 스타일이 아니라 정확성**이라는 것이다. 조건문 하나를 빼먹으면 결과가 틀리는 정도가 아니라 프로그램이 죽는다. 그리고 그 실패가 **입력에 따라서만** 드러나기도 한다 — 얕은 입력에서는 잘 돌던 코드가 깊은 입력에서 처음 터진다.

세 번째는 **한계선이 내 코드 밖에 있다**는 것이다. 몇 층까지 쌓을 수 있는지는 스택 크기가 정하므로, 재귀로 풀 수 있는 문제의 크기가 실행 환경에 걸린다. 데이터 크기를 모르는 입력을 재귀로 훑는 코드는 그 자체로 위험을 안고 있다.

## 경계와 오해

- **재귀 ≠ 메서드를 여러 번 호출하는 것** — 이 필기는 "메서드를 중복해서 호출 할 수 있으며, 이를 재귀함수라고 한다"로 배웠다. 같은 메서드를 반복문에서 100 번 부르는 것은 재귀가 아니다(프레임이 하나씩 생기고 바로 사라진다). 재귀는 **자기 호출이 끝나기 전에 자신이 다시 불리는 것**이고, 그래서 프레임이 **동시에** 쌓여 있다. 「중복 호출」로 외우면 왜 반복문에서는 stack overflow 가 안 나는지 설명할 수 없다 → [[jvm-stack]]
- **간접 재귀도 재귀다** — `a()` 가 `b()` 를 부르고 `b()` 가 다시 `a()` 를 부르는 것도 같은 결과를 낸다. 자기 이름이 코드에 보이지 않아도 순환이면 재귀이고, 그래서 눈에 띄지 않는 무한 재귀는 대개 이 모양이다.
- **무한 재귀 ≠ 무한 루프** — `while(true)` 는 자원을 더 쓰지 않고 영원히 돌지만, 무한 재귀는 스택을 소진하고 **죽는다.** 증상이 「멈춤」과 「종료」로 갈리므로 진단하는 방법도 다르다 → [[while-loop]]
- **깊이 한계가 문제의 원인은 아니다** — 이 필기는 "깊이가 깊어지면" 이라 적었는데, 실무에서 터지는 대부분은 깊이 설계가 아니라 **종료 조건이 안 걸린 것**이다. 스택 크기를 늘리는 것은 원인이 정말 깊이일 때만 답이다.
- **Java 에는 꼬리 재귀 최적화가 없다** — 재귀 호출이 메서드의 마지막 문장이어도 프레임이 줄지 않는다. 함수형 언어에서 재귀를 자유롭게 쓰는 것을 보고 Java 에 그대로 가져오면 깊이 한계에 걸린다.
- **`StackOverflowError` 를 `catch` 해서 넘기는 것은 해결이 아니다** — 잡아도 스택은 이미 한계까지 갔던 상태이고, 원인은 호출 구조에 있다 → [[exception-handling]]
