# LIKE 와 패턴 검색

**문자열을 「정확히 같은가」가 아니라 「이런 모양인가」로 비교하는 연산자.** Day52 의 한 줄이 「문자열을 비교할 때 사용한다」이고, 모양을 적는 문자가 둘이다 — `%` 는 「0개 이상의 문자」, `_` 는 「`_` 갯수당 1자리 글자」다. **검색 기능이 처음으로 SQL 한 줄이 되는 자리**다.

## 정의

패턴 문자 둘의 차이는 **길이를 정하는가**다.

| 패턴 문자 | 대응하는 것 | 길이 |
|---|---|---|
| `%` | 아무 문자든 | **0개 이상** (없어도 된다) |
| `_` | 아무 문자든 | 정확히 **1개** — 두 개 쓰면 2글자 |

```sql
컬럼명 like '패턴'
```

Day52 가 적은 세 가지 모양이 실제로 쓰는 형태 전부다.

| 패턴 | 뜻 | 예 — `'값'` 을 찾을 때 |
|---|---|---|
| `'값%'` | 값으로 **시작**하는 모든 문자열 | 앞이 고정 |
| `'%값%'` | 값이 **포함된** 모든 문자열 | 앞뒤가 열림 |
| `'값_'` | 값으로 시작하고 뒤에 **1글자** | 길이까지 고정 |

**`'값%'` 과 `'%값%'` 은 문법으로는 한 글자 차이지만 서버가 하는 일이 완전히 다르다**(아래 「왜 중요한가」).

## 사용 예시

Day52 의 세 줄이다. **그대로는 실행되지 않는다** — `where` 와 컬럼 이름이 빠져 있다(아래 「경계와 오해」의 첫 항목).

```sql
//'값%' : 값으로 시작하는 모든 문자열 
select * from 테이블명 like '값%';

// '%값%' : 값이 포한된 모든 문자열
select * from 테이블명 like '%값%';

// '값_' : 값으로 시작하고 뒤에 1개의 문자가 붙은 문자열
select * from 테이블명 like '값_';
```

성립하는 형태는 `like` 를 **조건 자리**에 두는 것이다.

```sql
select * from 테이블명 where 컬럼명 like '값%';
```

## 왜 중요한가

**「검색」이라 부르던 기능이 여기서 처음 한 줄이 된다.** 자바에서는 배열을 처음부터 끝까지 돌며 `contains`·`startsWith` 로 비교하고 걸린 것을 따로 모으는 코드였다. `like` 는 같은 일을 조건 하나로 적고, 어떻게 훑을지는 서버가 정한다 → [[linear-search]] · [[string-comparison]]

**패턴의 모양이 인덱스를 쓸 수 있는지를 정한다.** 이것이 `like` 를 배울 때 함께 알아야 하는 유일한 성능 사실이다.

| 패턴 | 인덱스 | 이유 |
|---|---|---|
| `'값%'` | **쓸 수 있다** | 정렬된 값 중 「값」으로 시작하는 구간만 보면 된다 |
| `'%값%'` | 못 쓴다 | 시작이 정해지지 않아 정렬이 아무 도움이 안 된다 |
| `'%값'` | 못 쓴다 | 같은 이유 (뒤에서 맞추는 정렬은 없다) |

전화번호부가 성-이름 순으로 정렬돼 있을 때 「김으로 시작하는 사람」은 바로 펼치지만 「이름에 '수' 가 든 사람」은 전부 읽어야 하는 것과 같다. **가장 자주 쓰고 싶은 `'%값%'` 이 정확히 인덱스를 못 쓰는 모양**이라, 검색 기능이 데이터가 늘면서 느려지는 대표 경로가 여기다 → [[database-index]]

**그리고 그래서 별도의 장치가 필요해진다.** 부분 문자열 검색을 진짜로 빠르게 하려면 문장을 단어로 쪼개 어디에 있는지 적어 두는 구조(전문 인덱스·검색엔진)가 필요하다. 하루 전 Day51 이 `name` 컬럼에 `fulltext index` 를 걸어 두었는데, **`like` 는 그 인덱스를 쓰지 못한다** — 전문 인덱스는 `MATCH ... AGAINST` 전용이다 → [[search-index]]

## 경계와 오해

- **필기의 `like` 예제 셋은 그대로 실행되지 않는다 — `where` 와 컬럼이 빠졌다** — `select * from 테이블명 like '값%';` 는 `like` 가 **무엇과** 비교하는지가 없고 `where` 도 없어서 파싱 단계에서 거절된다(`You have an error in your SQL syntax`). 올바른 형태는 `select * from 테이블명 where 컬럼명 like '값%';` 다. 바로 앞 절들이 조건을 `where 조건` 이라는 자리표로만 적어 왔기 때문에, `like` 를 배울 때 **그것도 「조건」의 한 종류라는 연결이 빠진 것**으로 읽힌다. `like` 는 독립된 절이 아니라 [[sql-operator]] 와 같은 자리에 들어가는 연산자다.
- **`like` 의 `%` ≠ 나머지 연산자 `%`** — 같은 노트의 몇 줄 위에서 `4 % 5` 를 배웠다. 하나는 산술 연산자이고 하나는 **문자열 안의 자리표**다. 문자로 적혀 있으니 구분은 「따옴표 안인가」다 → [[sql-operator]]
- **자바 제네릭의 와일드카드와 이름만 같다** — 「와일드카드」라는 말은 이 레포에서 [[wildcard-type]](`List<?>`)이 이미 별칭으로 갖고 있어서 `[[와일드카드]]` 라고 쓰면 그쪽으로 풀린다. 하나는 **타입 자리에 무엇이 와도 되는가**이고 이쪽은 **문자 자리에 무엇이 와도 되는가**다. 같은 비유에서 온 다른 개념이다.
- **`like` 는 기본적으로 대소문자를 구분하지 않는다** — 문자열 비교 규칙은 컬럼의 collation 이 정하고 MySQL 의 기본이 `_ci`(case insensitive) 라서, `like 'abc%'` 가 `ABC` 로 시작하는 행도 잡는다. 편의처럼 보이지만 **해시·토큰·비밀번호처럼 대소문자가 다른 값을 다른 값으로 취급해야 하는 컬럼에서는 결함**이 된다(`=` 비교도 같다). 구분해야 하면 컬럼을 `_bin`·`_cs` collation 으로 두거나 `binary` 를 붙인다 → [[string-comparison]] · [[database-schema]]
- **`_` 는 「한 글자」이고 한 바이트가 아니다** — UTF-8 에서 한글 한 자는 3바이트지만 `_` 하나로 잡힌다. 패턴은 바이트가 아니라 문자 단위로 센다 → [[character-encoding]] · [[unicode]]
- **패턴 문자를 값으로 찾을 수 없다** — 「50%」가 든 행을 찾으려고 `like '50%'` 를 쓰면 `50` 으로 시작하는 모든 행이 나온다. `%`·`_` 자체를 찾으려면 `escape` 를 지정하거나 `\%` 로 적어야 한다. **사용자가 입력한 검색어를 그대로 패턴에 넣으면 이 문제가 그대로 들어온다** — 검색창에 `%` 를 넣으면 전체가 나오는 것이 그 결과다.
- **`like '값%'` ≠ `= '값'`** — 「시작한다」와 「같다」가 다르다. `'값%'` 는 `%` 가 0개 문자에도 대응하므로 **정확히 `'값'` 인 행도 포함**한다. 반대로 `like '값'`(패턴 문자 없음)은 `= '값'` 과 같은 결과이고, 이때는 굳이 `like` 를 쓸 이유가 없다.
- **`like` ≠ 정규식** — MySQL 에는 정규식 연산자(`regexp`·`rlike`)가 따로 있다. `%`·`_` 는 정규식의 `.*`·`.` 에 대응하지만 **문법이 섞이지 않는다** — `like '^값'` 은 `^` 를 글자 그대로 찾는다. 정규식을 아는 상태로 오면 이 자리에서 조용히 0행을 받는다.
- **`NULL` 은 어떤 패턴에도 걸리지 않는다** — `where 컬럼명 like '%'` 조차 값이 `NULL` 인 행을 잡지 못한다. 「전부 다」를 뜻하는 패턴에도 안 걸리므로, 「검색어가 비어 있으면 `%` 를 넣어 전체 조회」로 구현하면 **값이 없는 행만 빠진 전체**가 된다 → [[sql-null]]
