# 서블릿 필터 (Servlet Filter)

**요청이 서블릿에 닿기 전과 응답이 나가기 전에 끼어드는 부품 — 모든 서블릿에 공통으로 들어갈 코드를 서블릿 밖으로 빼는 자리.** Day64 의 정의가 그대로다 — 「클라이언트의 요청이 서블릿에 도달하기 전이나 응답이 클라이언트에 전달되기 전에 특정 작업을 수행할 수 있게 해주는 컴포넌트이다」 → [[servlet]] · [[web-component]]

## 정의

Day64 는 성질 한 줄과 역할 넷을 적는다 — 「요청과 응답을 변환하거나 로깅, 인증, 인코딩 처리와 같은 전처리/후처리 작업을 담당한다」.

| Day64 의 역할 | 요청 쪽인가 응답 쪽인가 | 무엇을 대신하나 |
|---|---|---|
| 「**요청/응답 변환**: 요청 객체나 응답 객체의 내용을 수정하거나 데이터 가공」 | 양쪽 | 서블릿마다 적던 손질 → [[request-response]] |
| 「**인증 및 권한 확인**: 사용자 인증이나 접근 권한 확인」 | 요청 — **막을 수 있다** | 서블릿 첫 줄마다 있던 로그인 검사 |
| 「**로깅 및 감사**: 요청 정보나 처리 시간 등의 기록」 | 양쪽 (시간을 재려면 앞뒤가 다 필요하다) | 흩어진 로그 호출 |
| 「**데이터 압축 및 인코딩**: 응답 데이터를 압축하거나 인코딩 처리」 | 응답 | 서블릿 안의 `setContentType` → [[character-encoding]] |

### 「전처리/후처리」가 한 메서드에서 일어난다 — 필기에 없는 자리

Day64 는 필터가 앞뒤에 선다고만 적고 **그 앞뒤가 어떻게 한 클래스에 담기는지**는 적지 않는다. 규격의 모양은 이렇다.

| 위치 | 무엇을 하나 |
|---|---|
| `doFilter` 시작 ~ 다음 줄까지 | **전처리** — 요청을 보고 고치고, 통과시킬지 정한다 |
| `chain.doFilter(req, res)` | **위임** — 다음 필터나 서블릿에 넘긴다 |
| 그 호출이 돌아온 뒤 | **후처리** — 응답에 대해 할 일 |

**즉 「앞」과 「뒤」가 다른 메서드가 아니라 한 호출의 이전·이후다.** 그래서 성질 둘이 곧바로 나온다 — ① `chain.doFilter` 를 **부르지 않으면** 요청이 서블릿에 도달하지 않는다(그것이 「인증 및 권한 확인」이 성립하는 방식이다), ② 필터가 여럿이면 **감싸는 순서대로 들어가고 반대로 나온다.** 이 두 성질이 [[proxy-pattern]]·[[decorator-pattern]] 의 위임과 글자까지 같은 모양이다.

## 왜 중요한가

**Day64 의 실습에 이미 필터로 갈 코드가 들어 있다.** 서블릿 안에 손으로 적은 이 한 줄이다.

```java
res.setContentType("text/html;charset=UTF-8");
```

서블릿이 하나일 때는 문제가 없지만, 회원·게시판·프로젝트 화면이 생기면 **같은 줄이 서블릿마다** 들어간다. 그리고 한 곳에서 빠뜨리면 그 화면만 한글이 깨지는데, 그것이 **빠뜨렸다는 신호 없이** 나타난다. 「모든 요청에 공통이면 필터」라는 배치 규칙이 여기서 값을 만든다 → [[character-encoding]] · [[web-component]] · [[cohesion]]

**서블릿 코드가 자기 일만 하게 된다.** 목록을 그리는 서블릿에 로그인 검사·인코딩 설정·로깅이 앞에 붙어 있으면, **그 서블릿을 읽어도 무엇이 그 화면의 일인지 안 보인다.** 필터로 빼면 서블릿에 남는 것이 그 화면의 일뿐이고, 공통 규칙은 URL 패턴 하나로 「어디에 적용되는지」가 선언된다 → [[servlet-lifecycle]]

**그리고 내 서블릿을 고치지 않고 규칙을 얹을 수 있다.** 남이 만든 서블릿·라이브러리에도 붙는다 — 그것이 이 규격이 필터를 컨테이너 층에 둔 이유이고, 뒤에 스프링에서 같은 자리에 여러 이름의 장치가 서는 것도 같은 필요 때문이다 → [[open-closed-principle]] · [[servlet-container]]

### 엿새 뒤 — 세 메서드와 사슬이 필기로 온다

Day64 는 정의와 역할 넷만 있었고, `doFilter`·`FilterChain` 은 이 노트가 추론으로 채웠다.
Day68 이 그것을 **필기 자신의 문장으로** 적는다.

| 메서드 | 언제 | 하는 일 |
|---|---|---|
| `init(FilterConfig config)` | 처음 생성될 때 **한 번** | 초기 설정. `FilterConfig` 로 초기화 매개변수를 얻는다 |
| `doFilter(req, res, chain)` | **요청마다** | 실제 필터링. 요청·응답을 조작하고 `chain` 으로 다음에 넘긴다 |
| `destroy()` | 더 필요 없거나 컨테이너 종료 시 | 자원 해제 |

**[[servlet-lifecycle]] 과 같은 모양이다** — 한 번·매번·한 번. 다른 것은 가운데 메서드가
`chain` 을 하나 더 받는다는 점이고, 그것이 이 컴포넌트의 성격 전부다.

> 「`FilterChain` 을 호출하여, 다음 Filter 가 있는지 확인하고, 없으면 Servlet 의 Service 를 실행한다.」
> 「컨테이너는 요청에 적용될 모든 필터를 순서대로 연결하여 하나의 `FilterChain` 객체를 생성한다.」

**사슬을 만드는 것은 내가 아니라 컨테이너다.** 나는 「다음으로 넘긴다」만 부르고, 그 다음이
필터인지 서블릿인지는 모른다 — [[decorator-pattern]] 이 겹을 쌓던 것과 같은 모양이고,
갈리는 것은 **겹을 쌓는 주체가 설정 파일**이라는 점이다 → [[web-xml]]

그리고 필기가 필터로 할 일을 앞뒤로 갈라 적었다 — **앞은 풀고 뒤는 싸는 대칭**이다.

| 서블릿 실행 전 | 서블릿 실행 후 |
|---|---|
| 암호화된 파라미터 **해제** | 보낼 데이터 **암호화** |
| 압축된 데이터 **해제** | 보낼 데이터 **압축** |
| 권한 검사 · 로그인 사용자 검사 · 로그 남기기 | |

**Day65~66 이 서블릿마다 흩어 놓은 로그인 확인이 갈 자리가 여기다** → [[http-session]]

## 경계와 오해

- **필터 ≠ 서블릿 — 응답을 만드는 것이 일이 아니다** — 필터도 응답을 쓸 수 있지만(인증 실패에 오류 페이지) **그것이 역할이 아니라 예외**다. 갈리는 기준은 「이 URL 의 답을 내가 만드나」이고, 필터의 정상 경로는 **답을 만들지 않고 넘기는 것**이다. 필기의 「요청과 응답을 변환하거나」를 「응답을 만든다」로 읽으면 서블릿과 구별할 이유가 없어진다 → [[servlet]]
- **필터 ≠ 리스너 — 요청 흐름 위에 있는가로 갈린다** — 리스너는 **통보만** 받아서 이벤트를 취소하거나 요청을 막을 수 없고, 필터는 **길 위에 서 있어서** `chain.doFilter` 를 안 부르면 그대로 끝난다. 그래서 「인증」은 필터의 일이고 「앱이 뜰 때 초기화」는 리스너의 일이다. Day64 가 리스너의 역할에 「요청 로깅 및 감사」를 적었는데 **요청 정보를 기록하는 일은 대개 이쪽**이다 → [[servlet-listener]]
- **「요청 객체나 응답 객체의 내용을 수정한다」가 그대로는 되지 않는다 — 감싸서 넘긴다** — `ServletRequest` 는 컨테이너가 준 객체이고 파라미터를 바꿔 넣는 메서드가 없다. 실제로 하는 일은 **같은 인터페이스를 구현한 래퍼**(`HttpServletRequestWrapper`)로 감싸서 `chain.doFilter` 에 **원본 대신 래퍼를 넘기는** 것이다. 즉 이 자리가 [[decorator-pattern]] 이 실제로 쓰이는 첫 자리이고, 「수정」이라는 낱말은 결과를 말한 것이지 방법이 아니다. 방법을 모르면 **원본을 고치려다 방법이 없어 막힌다** → [[request-response]] · [[immutability]]
- **후처리에서 헤더를 고치려 하면 이미 늦었을 수 있다** — HTTP 는 헤더가 본문보다 먼저 나가므로, 서블릿이 출력을 시작해 응답이 **커밋된 뒤**에는 `setContentType`·상태 코드·리다이렉트가 조용히 무시된다. Day64 의 서블릿은 `getWriter()` 로 HTML 을 쭉 쓰므로, 그 뒤 필터의 후처리에서 인코딩을 고치는 것은 **효과가 없다.** 그래서 「응답 인코딩을 필터로 처리한다」는 반드시 **전처리에서** 해야 하고(요청이 서블릿에 닿기 전에 `setContentType`·`setCharacterEncoding` 을 걸어 둔다), 「압축」처럼 본문 자체를 바꾸려면 **응답도 래퍼로 감싸** 서블릿의 출력을 가로채야 한다. **「전처리/후처리 둘 다 할 수 있다」가 「무엇이든 뒤에 고칠 수 있다」는 뜻이 아니다** → [[character-encoding]] · [[io-stream]]
- **필터는 서블릿과 1:1 이 아니다 — URL 패턴에 붙는다** — 그래서 「어느 서블릿에 걸리는지」가 필터 쪽 선언에만 있고 서블릿 코드에는 흔적이 없다. 얻는 것은 서블릿을 안 고친다는 것이고, 대가는 **서블릿만 읽어서는 그 요청에 무슨 일이 먼저 일어나는지 알 수 없다**는 것이다. [[proxy-pattern]] 노트의 「지금 내가 쥔 것이 무엇인가가 코드에서 사라진다」와 같은 종류의 대가다 → [[web-application-deployment]]
- **인증을 필터로 옮기면 서블릿이 「누구인지」를 인자로 받지 못한다** — 필터가 통과시킨 사실은 서블릿 쪽 코드에 나타나지 않으므로, 사용자 정보를 넘기려면 **요청 속성이나 세션**을 거쳐야 한다. Day61 이 `prompt.setAttribute("loginUser", loginUser)` 로 상태를 연결에 붙였던 자리가 웹에서는 이 통로가 되고, 「검사한 곳」과 「쓰는 곳」이 문자열 키로만 이어진다 → [[servlet-context]] · [[client-server-model]]
- **이 회차에 필터 코드가 없다 — 정의와 역할 목록뿐이다** — 그래서 `Filter` 인터페이스의 메서드(`init`·`doFilter`·`destroy`), `FilterChain`, `@WebFilter` 의 URL 패턴, 필터 순서가 전부 비어 있다. 위의 「전처리/후처리가 한 메서드에서」 표가 그 빈 자리를 채운 것이고, **필기만으로는 필터를 쓸 수 없다** — 「앞뒤에 선다」까지가 이 회차의 범위다 → [[servlet-lifecycle]]

- [[2024-08-27-Day64]] — 「필터」 절(「필터의 정의」·「필터의 역할」)이 이 개념이다. 「클라이언트의 요청이 서블릿에 도달하기 전이나 응답이 클라이언트에 전달되기 전에 특정 작업을 수행할 수 있게 해주는 컴포넌트」·「요청과 응답을 변환하거나 로깅, 인증, 인코딩 처리와 같은 전처리/후처리 작업을 담당한다」로 정의하고 역할을 넷(요청/응답 변환 · 인증 및 권한 확인 · 로깅 및 감사 · 데이터 압축 및 인코딩) 적었다. **코드가 없다** — `Filter` 인터페이스의 메서드도 `FilterChain` 도 `@WebFilter` 도 나오지 않아서, 전처리·위임·후처리가 `doFilter` 한 메서드의 앞·중간·뒤라는 것, `chain.doFilter` 를 부르지 않으면 요청이 막힌다는 것, 요청·응답을 「수정」하려면 래퍼로 감싸 넘겨야 한다는 것, 응답이 커밋된 뒤에는 후처리에서 헤더를 고칠 수 없다는 것이 모두 비어 있다. 같은 노트가 서블릿 안에 `res.setContentType("text/html;charset=UTF-8")` 을 손으로 적어 두었는데, 그것이 이 절에서 정의한 「인코딩 처리」의 자리이면서 아직 옮겨지지 않은 코드다
