# 컬럼 타입 (SQL Data Type)

**컬럼 하나가 어떤 값을 얼마만큼 담을 수 있는지 정하는 것.** 자바의 [[data-type]] 이 변수가 잡을 메모리의 크기와 해석을 정했던 것과 같은 일을 하는데, **여기서는 그 선언이 프로그램이 아니라 서버에 남고 그 뒤로 들어오는 모든 값이 그 선언에 걸러진다.**

## 정의

Day51 이 적은 타입을 성격으로 묶으면 네 무리다.

| 무리 | 타입 | Day51 이 적은 것 |
|---|---|---|
| 정수 | `tinyint`(1) · `smallint`(2) · `mediumint`(3) · `int`(4) · `bigint`(8) | 괄호 안이 바이트 크기 |
| 실수 | `float` / `numeric` = `decimal` | 「부동소수점」 / 「전체 자릿수와 소수점 이하 자릿수를 정밀하게」 |
| 문자 | `char(n)` · `varchar(n)` · `text`·`mediumtext`·`longtext` | 고정 / 가변 / 긴 텍스트 |
| 날짜·시간 | `date` · `time` · `datetime` | 년월일 / 시분초 / 둘 다 |

정수는 **크기만 다르고 성격이 같다** — 담을 범위가 바이트 수로 정해지므로 자바의 `byte`·`short`·`int`·`long` 과 그대로 대응한다(`int` 가 4바이트인 것까지 같다) → [[data-type]] · [[overflow]]

### 실수 둘의 차이가 「정밀」의 뜻이다

```sql
numeric(n, e)      -- 전체 n 자릿수 중 소수점 아래가 e 자릿수
numeric(10, 2)     -- 12345678.12
numeric            -- numeric(10, 0) 과 같다
```

Day51 은 `numeric` 을 「정밀하게 지정할 수 있다」로 적었다. **자릿수를 적는 것보다 중요한 것은 저장 방식이다** — `decimal` 은 10진수를 그대로 담아 `0.1` 이 정확히 `0.1` 이지만, `float` 는 2진 근사라 `0.1` 이 딱 담기지 않는다. 자바에서 `0.1 + 0.2 != 0.3` 이었던 그 문제가 컬럼 타입 선택으로 되돌아온 것이고, 그래서 **돈은 `decimal`** 이다 → [[floating-point]]

### 문자 둘의 차이는 「길이를 어디에 적는가」다

| | `char(n)` | `varchar(n)` |
|---|---|---|
| 크기 | 고정 — 한 글자만 넣어도 n 자리를 쓴다 | 가변 — 넣은 만큼 + **길이 접두사 1~2바이트** |
| n 의 한계 | 0 ~ 255 | 행 전체가 65535바이트를 못 넘는 범위 안 |
| 어울리는 것 | 길이가 늘 같은 값 (우편번호·성별코드·해시) | 길이가 들쭉날쭉한 값 (이름·주소) |

**`varchar` 가 앞에 길이를 적어 두는 형태**는 Day38 에서 문자열을 파일에 쓸 때 「길이를 먼저 쓰고 내용을 쓰는」 것과 같은 장치다 → [[length-prefix-framing]]

Day51 이 「`varchar` 는 UTF-8 이면 n 이 최대 21844」로 적은 숫자는 **그 두 사실의 곱**이다 — 행의 상한 65535바이트를 MySQL `utf8` 의 글자당 3바이트로 나누고(≈21845) 길이 접두사 2바이트를 뺀 값이다. **문자집합을 `utf8mb4` 로 바꾸면 이 숫자가 16383 으로 줄어든다** → [[character-encoding]] · [[database-schema]]

### 날짜는 세 개로 갈려 있다

`date`(년월일) · `time`(시분초) · `datetime`(둘 다). Day51 이 덧붙인 「오라클의 `date` 는 시간 정보도 저장한다」가 중요한 한 줄이다 — **같은 이름의 타입이 제품마다 다른 것을 담는다.**

## 사용 예시

Day51 의 실험 테이블이 타입을 고르는 실제 모양이다.

```sql
create table test1(
no int not null,
name varchar(20) default 'noname',
age int default 20
);
```

`no` 는 번호라서 `int`, `name` 은 길이가 사람마다 다르니 `varchar(20)`, `age` 는 작은 정수다. **`varchar(20)` 의 20 은 「예상 최대」이지 예약이 아니다** — 넉넉히 잡아도 실제 저장은 넣은 글자 수만큼이라 손해가 없고, 대신 **넘치는 값은 잘리거나 거절된다.**

```sql
create table test1(
  no int,
  name varchar(20),
  age int,
  kor int,
  eng int,
  math int,
  constraint primary key(no),
  constraint test1_uk unique (name, age)
  );
```

## 왜 중요한가

**타입이 「들어올 수 없는 값」을 정한다.** 자바에서는 `String age` 로 선언해도 컴파일이 되고 `"스무살"` 이 들어갔지만, `age int` 컬럼은 그 값을 받지 않는다. **잘못된 값이 저장되는 것을 막는 첫 방어선이 타입이고, 그것을 문자로 다 받으면(`varchar` 로 전부 선언) 그 방어선을 스스로 없애는 것**이다 → [[number-parsing]]

**크기 선택이 나중에 사고가 된다.** `int` 는 21억까지(부호 없으면 42억)이고, 이 값이 자동 증가 컬럼에 붙으면 **행이 21억 개를 넘는 순간 더 이상 등록되지 않는다** — 데이터를 지워도 카운터는 되돌지 않으니 「행 수」가 아니라 「지금까지 발급한 번호」가 기준이다. 유명한 서비스 장애가 이 한 글자(`int` → `bigint`)에서 났다 → [[overflow]] · [[surrogate-key]]

**그리고 정렬·비교의 뜻이 타입에서 나온다.** `'10'` 과 `'9'` 를 문자로 담으면 `'10' < '9'` 이고 숫자로 담으면 그 반대다. 날짜를 `varchar` 로 담으면 `order by` 가 「2024-1-5」와 「2024-11-5」를 문자 순서로 늘어놓는다 → [[string-comparison]] · [[date-time]]

## 경계와 오해

- **`DATETIME` 컬럼 타입과 애플리케이션의 시각 값은 다른 층이다** — 여기서 정하는 것은 **DB 가 무엇을 저장하는가**이고, 그 값을 코드에서 어떤 타입으로 받을지는 따로다 → [[date-time]]
- **`char` 가 빠르고 `varchar` 가 느린 것이 아니다 — Day51 의 「검색 시 느리다」는 근거가 어긋났다** — 필기는 「`char` 는 메모리 크기가 고정되어 검색이 빠르고, `varchar` 는 위치를 계산해야 해서 느리다」고 적었다. 위치 계산이 필요하다는 것은 **한 행 안에서 다음 컬럼이 어디서 시작하는지**의 이야기이고, 그 비용은 나노초 단위다. **`where name = 'aaa'` 의 실제 속도를 정하는 것은 타입이 아니라 인덱스가 있는지**다 — 인덱스가 없으면 `char` 든 `varchar` 든 전체를 훑는다. 두 타입의 실제 차이는 (1) 저장 공간(짧은 값이 많으면 `varchar` 가 작다) (2) **뒤 공백 처리**(`char` 는 저장할 때 공백을 채우고 읽을 때 잘라 낸다) (3) 고정 폭이라 갱신 시 행이 옮겨질 일이 없다는 점이다 → [[database-index]] · [[linear-search]]
- **`varchar(n)` 의 n 은 글자 수, 한계는 바이트** — Day51 이 「최대 n개의 문자」와 「0 ~ 65535 바이트」를 같은 절에 적어 둔 것이 헷갈리는 지점인데 둘 다 맞다. **선언은 글자 수로 하고 한계는 바이트로 걸린다** — 그래서 같은 `varchar(21844)` 가 문자집합에 따라 되기도 하고 안 되기도 한다. 게다가 65535 는 컬럼 하나가 아니라 **행 전체**의 한도라, `varchar` 컬럼을 여러 개 두면 각각이 작아도 합쳐서 걸린다 → [[character-encoding]]
- **`numeric` = `decimal` 은 같은 것의 두 이름** — Day51 의 `numeric = decimal` 은 정확하다. MySQL 에서 `numeric` 은 `decimal` 의 별명일 뿐이고, **자릿수를 적었다고 정확해지는 것이 아니라 10진 저장이라 정확한 것**이다. 반대로 `float(10,2)` 처럼 적으면 자릿수는 지정되지만 오차는 남는다 → [[floating-point]]
- **`text` ≠ 긴 `varchar`** — 같은 문자 저장이지만 셋이 다르다. `text` 계열은 **기본값을 가질 수 없고**(`default` 를 붙이면 오류다 → [[sql-null]]), 인덱스를 걸 때 앞 몇 글자까지만 지정해야 하며, 값이 행 밖의 별도 페이지에 저장되어 조회할 때 한 번 더 따라가야 한다. 「길면 `text`」가 아니라 **「기본값·인덱스·정렬이 필요하면 `varchar`」**가 고르는 기준이다.
- **`date` ≠ `datetime`, 그리고 제품마다 다르다** — Day51 이 적은 대로 Oracle 의 `DATE` 는 시간까지 담는다. MySQL 의 `date` 로 옮기면 **시각이 조용히 잘려 나가고**(00:00:00 이 된다) 그 뒤로 「같은 날 안의 순서」를 복원할 방법이 없다. 마이그레이션에서 손실이 나는 대표적인 자리다 → [[date-time]]
- **타입은 시간대를 담지 않는다** — `datetime` 은 「2024-08-06 14:00」이라는 **글자에 해당하는 값**이고 어느 지역의 14시인지는 저장하지 않는다. 서버를 다른 나라로 옮기면 같은 값이 다른 시각이 되는데 **타입만 보면 그것이 드러나지 않는다**(그 문제를 다루는 별도 타입이 `timestamp` 다) → [[date-time]]
- **`int` 의 괄호는 크기가 아니다** — MySQL 에서 `int(11)` 처럼 쓸 수 있어 「11자리까지」로 읽히지만, 저장 크기는 **언제나 4바이트**이고 괄호 안은 표시 폭 힌트일 뿐이다(지금은 폐기 예정). 크기를 바꾸려면 `bigint` 처럼 **타입을 바꿔야** 한다. `varchar(20)` 의 괄호와 뜻이 다르다는 것이 이 타입군에서 가장 자주 어긋나는 지점이다.
