# 웹 서버 (Web Server)

**브라우저의 요청을 받아 이미 파일로 있는 것을 그대로 내보내는 프로그램.** Day63 의 정의가 그것이다 — 「클라이언트(브라우저)에서 요청한 정적 콘텐츠(HTML, CSS, 이미지, JavaScript 파일 등)를 제공하는 서버이다」. **하는 일이 좁은 것이 이 프로그램의 성질**이고, 그래서 좁은 만큼 앞에 세울 수 있다 → [[static-and-dynamic-content]] · [[client-server-model]]

## 정의

Day63 이 기능을 셋 적었다. **셋이 같은 층의 일이 아니다.**

| Day63 의 기능 | 실제로 하는 일 | 무엇이 필요한가 |
|---|---|---|
| **정적 콘텐츠 제공** | 「HTML, 이미지, CSS, JavaScript 파일과 같은 정적 리소스를 클라이언트에 전달」 | 디스크와 네트워크 |
| **HTTP 요청 처리** | 「들어오는 HTTP 요청을 받아 그에 따른 응답을 반환」 | 요청 줄을 읽고 응답을 조립하는 것 |
| **로드 밸런싱** | 「여러 서버 간의 트래픽을 분배 … 높은 트래픽을 효율적으로 처리」 | **자기가 답하지 않고 남에게 넘기는 것** |

**앞의 둘은 「내가 답한다」이고 세 번째는 「남에게 넘긴다」다.** 그래서 세 번째는 정적 콘텐츠를 다루는 능력에서 나오는 것이 아니라 **이 프로그램이 서 있는 자리**에서 나온다 — 브라우저가 가장 먼저 닿는 곳이라 넘길 결정을 여기서 할 수 있다. 같은 자리의 성질이 WAS 로 동적 요청을 넘기는 일이기도 하다 → [[web-application-server]]

대표적인 구현으로 Day63 은 **Apache HTTP Server · Nginx · Microsoft IIS** 를 든다.

### 요청 하나가 어디까지 가는가

Day63 의 구조 절이 흐름을 다섯 칸으로 적었고, 이 프로그램은 **두 번째 칸**이다.

| 칸 | Day63 이 적은 일 |
|---|---|
| Web Browser | 「HTTP 프로토콜을 통해 서버로 요청을 보내고 결과를 받는다」 |
| **Web Server** | 「HTTP 요청을 받아 처리한다 … 동적 요청은 WAS로 전달한다」 |
| WAS | 동적 요청을 받아 비즈니스 로직 계층으로 넘긴다 |
| Java Application | 「비즈니스 로직은 Java Application에 의해 처리된다」 |
| (되돌아오는 길) | 「WAS를 통해 다시 웹 서버로 전달되며, 최종적으로 … 웹 브라우저로 반환」 |

**갈림길이 두 번째 칸에 있다** — 정적이면 여기서 끝나고 동적이면 뒤로 넘어간다. 즉 이 프로그램의 판단 하나가 **요청 하나의 비용을 정한다** → [[static-and-dynamic-content]] · [[little-law]]

## 왜 중요한가

**뒤에 있는 것을 가릴 수 있다.** 브라우저가 닿는 곳이 여기 하나이므로, 뒤에 WAS 가 몇 대인지·어떤 언어로 짜였는지·포트가 몇 번인지가 밖에서 보이지 않는다. Day61 의 클라이언트가 서버 주소와 포트를 **사람에게 물어야** 했던 것과 갈리는 자리다 — 그때는 클라이언트가 상대의 위치를 알아야 했다 → [[port-number]] · [[domain-name-system]]

**그리고 요청 대부분이 여기서 끝난다.** 화면 하나는 HTML 한 장과 이미지·CSS·JS 수십 개다. 그 수십 개가 [[thread]] 를 잡고 DB 연결을 빌리는 층까지 들어가지 않고 여기서 답해지면, 뒤쪽 자원은 **정말로 코드를 실행해야 하는 요청에만** 쓰인다. Day63 이 「tomcat mini web sever는 개발용으로는 적합하나, 성능이 제한된다 / web server는 NginX와 같은 외부 서버를 혼용해서 사용한다」로 적은 것의 내용이 이것이다 → [[universal-scalability-law]]

## 경계와 오해

- **웹 서버 ≠ 서버 컴퓨터** — 「서버」라는 낱말이 장비를 가리키기도 해서, 웹 서버를 「웹을 서비스하는 기계」로 읽게 된다. **웹 서버는 프로그램**이고 한 기계에 웹 서버와 WAS 와 DBMS 가 함께 돌 수 있다. [[client-server-model]] 노트의 「클라이언트/서버 ≠ 컴퓨터 두 대」와 같은 축의 혼동이다.
- **웹 서버 ≠ WAS** — Day63 의 표가 이 구분에 일곱 줄을 썼는데, 실제로 갈리는 것은 **한 줄**이다: 응답이 파일로 이미 있는가, 코드를 실행해 만들어야 하는가. 나머지 여섯 줄(주요 기능·복잡성·대표 예…)은 그 한 줄의 결과다 → [[web-application-server]] · [[static-and-dynamic-content]]
- **「웹 서버가 없으면 동적 요청을 못 받는다」가 아니다 — 그런데 필기는 그렇게 읽히게 적혀 있다** — Day63 의 구조 절은 「HTTP 요청이 웹 서버로 전달되고, WAS로 전달된다」로 **웹 서버를 반드시 지나는 관문처럼** 세운다. 그런데 같은 노트의 Tomcat 구조 절을 보면 톰캣 안에 「Mini Web Server」가 이미 있고, 실습에서 브라우저는 **8888 번 톰캣에 직접 붙는다.** 즉 **이 회차의 실제 구성에는 외부 웹 서버가 없다.** 그림의 다섯 칸은 「반드시 이렇게 생긴다」가 아니라 **규모가 커졌을 때 나누는 자리**이고, 필기가 그 조건을 적지 않았다 → [[tomcat]]
- **「로드 밸런싱」을 웹 서버의 기능 목록에 넣으면 층이 섞인다** — 트래픽을 분배하는 것은 **자기가 답하지 않고 대신 물어봐 주는 일**이라, 정적 파일을 내보내는 일과 성질이 다르다. 같은 자리에서 하는 일이라 같은 프로그램이 맡는 것이고, 그래서 「Nginx 를 쓴다」가 정적 파일 제공을 뜻할 때도 있고 뒤로 넘기는 것만 뜻할 때도 있다. **하나의 소프트웨어가 두 역할을 겸한다는 것**이 이 목록이 감추는 사실이다 → [[web-application-server]]
- **정적 콘텐츠를 내보내는 것도 「아무 코드도 안 도는 것」은 아니다** — 경로를 실제 파일로 바꾸고, 없으면 404 를 만들고, 형식을 알려 주고, 압축·범위 요청·캐시 헤더를 붙인다. 「그냥 파일을 준다」로 외우면 **경로 하나가 파일 시스템의 어디로 풀리는지**가 보안 문제라는 것이 안 보인다 — 올려 둔 백업 파일이나 설정 파일이 URL 로 그대로 내려가는 사고가 여기서 난다 → [[filesystem-path]] · [[web-application-deployment]]
- **웹 서버가 HTTP 를 「처리한다」는 것과 HTTP 를 「정한다」는 것은 다르다** — Day63 은 웹 서버를 HTTP 로 정의하지만 HTTP 자체가 무엇인지는 이 회차에 나오지 않는다. 그래서 이 노트가 소유하는 것은 **「그 규칙을 지키는 프로그램이 이런 일을 한다」까지**이고, 규칙 자체(요청 줄·메서드·헤더·상태 코드)는 뒤에 배울 자리로 남는다. Day61 이 자기 프로토콜을 손으로 정했던 것과 갈리는 것은 **이 규칙은 이미 있고 내가 정하지 않는다**는 것뿐이다 → [[network-protocol]]

## 출처

- [[2025-01-13-Day10]] — **이 층이 실제로 앞단에 서는 자리**를 본다. Nginx Proxy Manager 컨테이너가 80·443 을 받아 도메인을 매칭하고 SSL 을 끝낸 뒤 안쪽 애플리케이션 포트로 넘긴다. 필기가 웹 서버의 기능을 **정적 콘텐츠 제공 · 로드 밸런싱 · HTTP 요청 처리** 셋으로 정리했는데, 이 배치에서 실제로 쓰이는 것은 뒤의 둘이다 → [[reverse-proxy]]
- [[2024-08-26-Day63]] — 「웹 서버(Web Server)」 절이 정의와 기능 셋을 적었다. 정의는 「클라이언트(브라우저)에서 요청한 정적 콘텐츠(HTML, CSS, 이미지, JavaScript 파일 등)를 제공하는 서버」·「주로 HTTP 프로토콜을 사용하여 클라이언트와 통신하고, 클라이언트의 요청을 처리하여 정적 파일을 전달하는 역할」이고, 기능은 정적 콘텐츠 제공·로드 밸런싱·HTTP 요청 처리 셋이다. 대표 예로 Apache HTTP Server·Nginx·Microsoft IIS 를 들고, WAS 와의 비교 표에서 「단순: 정적 파일을 전달하는 데 중점」·「직접적인 응용 프로그램 처리 기능 없음」으로 갈랐으며, 구조 절에서 요청이 브라우저 → 웹 서버 → WAS → Java Application 으로 흐르고 응답이 그 역순으로 돌아온다고 적었다. 다만 **기능 셋이 같은 층의 일이 아니라는 것**(앞의 둘은 답하는 일, 로드 밸런싱은 넘기는 일)과 **외부 웹 서버가 없어도 되는 구성**(같은 노트의 톰캣이 Mini Web Server 를 이미 갖고 있고 실습은 브라우저가 8888 로 직접 붙는다)은 다루지 않아서, 다섯 칸 그림이 「반드시 이렇게 생긴다」로 읽히는 상태로 남는다. HTTP 자체의 규칙도 이 회차에는 나오지 않고 「HTTP 프로토콜을 사용한다」는 문장으로만 스친다
