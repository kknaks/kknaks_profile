# 성능 테스트 (부하 · 스트레스)

**얼마나 견디는지를 재 보는 것.** 목적이 둘로 갈리고, **무엇을 재는지도 그에 따라 다르다.**

## 정의

| | 부하 테스트 | 스트레스 테스트 |
|---|---|---|
| 목적 | **정상 작동 상태에서의 성능 확인** | **장애 지점(Breaking Point) 찾기** |
| 부하 | 예상 최대 사용자까지 **점진적으로** | 처리할 수 있는 것보다 **의도적으로 더** |
| 측정 대상 | 응답시간 · 처리량 · 자원 사용률 | 안정성 · 오류 처리 능력 · **복구 능력** |

**「잘 도는지」와 「어디서 무너지고 어떻게 무너지는지」는 다른 질문**이다.

### 읽어야 할 세 숫자

| 이름 | 무엇 |
|---|---|
| **VU**(Virtual User) | 지금 요청을 보내고 있는 가상 사용자 수 — **동시성** |
| **Throughput** | 초당 처리하는 요청 수 (TPS) — **처리량** |
| **Latency** | 요청을 보낸 뒤 응답까지의 시간 — **응답시간** |

**셋은 독립이 아니다** — 동시성이 오르면 처리량이 오르다가 어느 지점부터 **응답시간만 늘고 처리량은 안 는다.** 그 꺾이는 자리가 한계다 → [[little-law]] · [[universal-scalability-law]]

### K6 스크립트의 뼈대

```javascript
export const options = {
  stages: [                                  // 부하를 어떻게 올릴 것인가
    { duration: '1m', target: 20 },          // 1분에 걸쳐 20명까지
    { duration: '2m', target: 20 },          // 2분 유지
    { duration: '1m', target: 50 },          // 1분에 걸쳐 50명까지
  ],
  thresholds: {                              // 합격 기준 (SLO)
    http_req_duration: ['p(95)<200'],        // 95% 가 200ms 이내
    http_req_failed:   ['rate<0.01'],        // 오류율 1% 미만
  },
};

export default function () {
  http.get('http://localhost:8090/api/v1/posts');
  sleep(Math.random() * 3 + 1);              // 사람처럼 1~4초 쉰다
}
```

**`thresholds` 가 있다는 것이 이 도구의 성격**이다 — 결과를 보고 사람이 판단하는 것이 아니라 **통과/실패가 나온다.** 그래서 파이프라인에 넣을 수 있다 → [[ci-cd]]

## 왜 중요한가

**「빠른가」를 숫자 하나로 말할 수 없다는 것을 배우는 자리다.** 평균 응답시간은 느린 소수를 감추므로 **`p(95)`·`p(99)` 같은 백분위**로 본다 — 「95%의 사용자는 200ms 안에 받는다」가 실제로 의미 있는 약속이다.

**그리고 부하를 만들어 봐야 병목이 어디인지 알 수 있다.** 지금까지 배운 것들 — 커넥션 풀 크기, N+1 질의, OSIV, 세션 저장소 — 이 **전부 부하가 걸려야 드러나는 문제**였다 → [[connection-pool-sizing-formula]] · [[n-plus-one]] · [[osiv]]

**`sleep` 을 넣는 이유도 중요하다.** 쉬지 않고 때리면 실제 사용자 패턴이 아니라 **도구의 한계를 재게 된다.**

## 경계와 오해

- **평균만 보면 안 된다** — 평균 200ms 여도 상위 1% 가 5초면 **그 사용자들에게는 망가진 서비스**다. 백분위를 보는 습관이 이 도구의 핵심 학습이다
- **테스트 대상보다 테스트 도구가 먼저 막힐 수 있다** — 부하를 만드는 쪽의 CPU·네트워크가 한계면 **측정한 것은 서버가 아니라 내 노트북**이다
- **로컬에서 잰 숫자는 운영의 숫자가 아니다** — 네트워크 지연·다른 사용자·데이터 양이 전부 다르다. **경향을 보는 것**이지 절대값을 믿는 것이 아니다
- **부하를 올리는 모양(`stages`)이 결과를 바꾼다** — 갑자기 올리는 것과 서서히 올리는 것은 **캐시·커넥션 풀이 데워지는 정도**가 달라 다른 결과가 나온다 → [[caching]]
- **한 번 재고 끝내면 의미가 없다** — 성능은 코드가 바뀌면 변한다. **기준선을 두고 반복해서 비교**해야 회귀를 잡는다 → [[ci-cd]]
- **스트레스 테스트는 「복구」까지 봐야 한다** — 무너지는 것보다 **부하가 빠진 뒤 정상으로 돌아오는가**가 더 중요할 때가 많다

## 출처

- [[2025-02-10-Day25]] — 「성능테스트」 절이 **부하와 스트레스를 목적으로 갈랐다** — 「시스템의 성능 저하지점을 찾는 것이 아닌, **정상 작동 상태에서의 성능을 확인**」 대 「시스템의 **장애지점(Breaking Point)** 을 찾는 것이 목적」, 그리고 각각의 측정 대상까지 나눠 적었다. K6 스크립트는 **커스텀 메트릭(`Counter`·`Rate`·`Trend`)·`stages`·`thresholds`·`handleSummary`** 를 한 파일에 담은 전문이 실려 있고, 임계값에 `p(95)<200`·`rate<0.01` 처럼 **백분위와 비율로 기준을 적는** 모양이 나온다. 기본 메트릭 표 둘(일반 8개·HTTP 9개)이 특히 값지다 — `http_req_duration` 이 **sending + waiting + receiving 의 합**이라는 것까지 적혀 있어 어디서 시간이 드는지를 나눠 볼 수 있다. 대시보드 항목 표 아래의 **Throughput·Latency 정의**(「1초에 1000개 처리 가능 → 1000TPS」·「평균 응답시간 2.5초 → 평균 Latency 2.5초」)도 이 회차가 남긴 어휘다
