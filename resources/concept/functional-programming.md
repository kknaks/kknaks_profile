# 함수형 프로그래밍 (Functional Programming)

**처리할 데이터를 가진 쪽에 「어떻게 처리할지」를 넘겨 주는 방식.** Day36 의 정의가 그 방향을 그대로 적었다 — 「함수를 정의하고 이 함수를 데이터 처리부로 보내 데이터를 처리하는 기법」. 데이터를 가진 쪽이 처리 방법을 고르는 것이 아니라, **부르는 쪽이 방법을 들고 온다.**

## 정의

필기가 네 줄로 정리했고 순서에 논리가 있다.

1. 함수를 정의하고 이 함수를 **데이터 처리부**로 보내 데이터를 처리한다
2. 데이터 처리부는 **데이터만** 가지고 있으며 처리 방법이 따로 정해지지 않는다
3. 같은 데이터가 주어져도 **처리하는 함수에 따라 결과가 달라진다**
4. 그래서 **「데이터 처리의 다형성」**이라고도 볼 수 있다

무엇이 어디에 있는지가 뒤집힌다.

| | 데이터를 가진 쪽 | 방법을 정하는 쪽 |
|---|---|---|
| 절차적 · 명령형 | 데이터 + 처리 방법 | 같은 쪽 |
| 함수형 | 데이터만 | **부르는 쪽이 넘긴다** |

자바가 이 방식을 위해 8부터 넣은 문법이 람다식이고, 넘겨받을 그릇이 함수형 인터페이스다 → [[lambda-expression]] · [[functional-interface]]

## 사용 예시

Day36 의 `Factory` 가 「이자를 계산하는 방법」 자체를 만들어 돌려준다.

```java
interface InterestCalculator {
  double compute(int money);
}

static InterestCalculator create6(double rate) {
  return money -> money * (1 + rate);
}
```

```java
InterestCalculator c6 = Factory.create6(0.025);
System.out.println(c6.compute(10000000));
```

**`compute(10000000)` 을 부르는 자리에는 이율도 계산식도 없다.** 금액만 있고, 어떻게 계산할지는 이미 넘겨받아 들고 있다 — 위 정의의 2번이 코드로 나타난 모양이다. 이율을 바꾸려면 `create6(0.05)` 로 **다른 방법을 만들어 넘기면 되고**, 금액을 받아 처리하는 쪽은 한 글자도 바뀌지 않는다.

Day36 이 여섯 개(`c1`~`c6`)를 만들어 같은 `10000000` 에 대해 여섯 번 `compute` 를 부르는 것이 이 장의 마지막 코드다. **여섯이 만들어진 방법은 로컬 클래스 · 익명 클래스 · 람다로 다 다르고 결과는 같다** — 「같은 데이터, 다른 함수」의 대칭으로 「다른 문법, 같은 함수」를 보인 것이다. 다만 그 `Test` 는 실제로는 컴파일되지 않는다 → [[nested-class]]

## 왜 중요한가

**「무엇을 할지」가 코드의 위치에서 값으로 내려온다.** 하루 전 회차가 `switch` 를 지우고 트리의 잎마다 다른 커맨드 객체를 매단 것이 이미 같은 방향이었다 — 실행할 것이 값이 되면 담아 두거나 바꿔 끼울 수 있다. 함수형 프로그래밍은 그것을 **패턴이 아니라 문법으로** 하게 만든다 → [[command-pattern]] · [[dispatch-table]]

**같은 데이터에 대해 처리를 갈아 끼우는 코드가 짧아진다.** 이 구조를 클래스로 하면 방법 하나당 파일 하나가 필요하다(열사흘 전의 정렬 실습이 `BubbleSort`·`QuickSort` 로 그렇게 했다). 방법이 한 번만 쓰인다면 그 파일은 읽는 사람에게 아무것도 알려 주지 않는다 — **재사용되지 않는 이름을 만들지 않게 되는 것**이 실제로 얻는 것이다 → [[anonymous-class]] · [[parameterization]]

**데이터를 가진 쪽을 다시 쓰지 않게 된다.** 처리 방법이 밖에서 오면 데이터 처리부는 방법이 늘어도 열리지 않는다. 「기능을 더하는 일이 기존 코드를 고치는 일이 아니게 된다」의 함수 버전이다 → [[open-closed-principle]]

## 경계와 오해

- **「데이터 처리의 다형성」 ≠ 상속 다형성** — 이미 배운 [[polymorphism]] 은 업캐스팅과 메서드 재정의로 성립하고, 무엇이 실행될지를 정하는 것은 **인스턴스의 실제 타입**이다. 여기서 갈리는 축은 **어느 함수를 넘겼는가**다. 구현으로 보면 여전히 인터페이스 타입 + 구현 객체이니 다형성의 한 쓰임이 맞지만, **고르는 주체가 「인스턴스를 만든 쪽」에서 「인스턴스를 넘기는 쪽」으로 옮겨 간다.** 필기의 낱말은 정확한데, 그것을 상속 다형성과 같은 것으로 읽으면 「부모 클래스가 어디 있나」를 찾게 된다 — 그런 것은 없다.
- **람다를 쓰는 것과 함수형 프로그래밍을 하는 것은 다르다** — 함수형이 말하는 핵심(부작용 없는 순수 함수, 불변 데이터, 값으로서의 함수) 중 자바 람다가 보장하는 것은 하나도 없다. Day36 의 람다들은 대부분 `System.out.println` 을 부르므로 **하는 일이 부작용 그 자체**이고, 반환값도 없다(`void play()`·`void introduce(String)`). **문법을 쓴 것과 방식을 따른 것을 가르지 않으면 「람다로 바꿨으니 함수형이다」가 된다** → [[immutability]]
- **자바에는 함수가 없다 — 객체가 있다** — 「함수를 데이터 처리부로 보낸다」는 문장을 그대로 믿으면 자바에 함수 타입이 있다고 오해한다. 넘어가는 것은 함수형 인터페이스의 인스턴스이고, 타입 자리에는 언제나 인터페이스 이름이 적힌다(`InterestCalculator c6 = …`). 그래서 같은 `(int) -> double` 모양이어도 **인터페이스가 다르면 서로 대입되지 않는다** → [[functional-interface]] · [[object-reference]]
- **「데이터 처리부」는 이 필기의 낱말이다** — 표준 용어로는 함수를 인자로 받는 쪽을 고차 함수(higher-order function)라 부르고, 그렇게 동작을 인자로 올리는 설계를 동작 파라미터화라 한다. **낱말은 편의지만, 다른 자료를 볼 때 「데이터 처리부」로 검색하면 아무것도 나오지 않는다.**
- **구조가 새로 생긴 것이 아니라 값이 싸진 것이다** — 「동작을 인터페이스로 받아 넘긴다」는 인터페이스를 배운 자리에서 이미 나왔고, 하루 전 회차의 커맨드 패턴이 그 완성형이다. 함수형 프로그래밍이 자바에 들어와 바뀐 것은 **그 구조를 쓰는 데 드는 코드 양**이다. 「새 패러다임」으로만 읽으면 이미 아는 것과 이어지지 않는다 → [[interface]] · [[command-pattern]]
- **처리 방법이 밖에서 오면 검증할 곳도 밖으로 나간다** — 데이터 처리부는 넘겨받은 함수가 무엇을 하는지 모르므로, 잘못된 계산식이 와도 막을 방법이 없다. `money -> money * (1 + rate)` 에 음수 이율이 들어오는 것을 `compute` 쪽에서는 확인할 수 없다. **유연함과 검증 지점이 반대 방향으로 당긴다** → [[encapsulation]]
