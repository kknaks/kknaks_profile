# 싱글톤 패턴 (Singleton Pattern)

**인스턴스를 하나만 존재하게 만드는 방법.** 생성자를 닫아 밖에서 `new` 를 못 하게 하고, 대신 클래스 메서드 하나를 유일한 입구로 두어 이미 만들어 둔 것을 돌려준다.

## 정의

세 조각이 맞물려야 성립한다. 하나라도 빠지면 「하나뿐」이 깨진다.

```java
public class Car {
  private Car() {}                     // 1. 밖에서 new 를 막는다

  private static Car instance;         // 2. 만들어 둔 하나를 클래스가 들고 있는다

  public static Car getInstance() {    // 3. 유일한 입구
    if (instance == null) {
      instance = new Car();            // 처음 불렸을 때만 만든다
    }
    return instance;
  }
}
```

- **생성자가 `private`** — `new Car()` 는 클래스 안에서만 된다 → [[constructor]] · [[access-modifier]]
- **필드가 `static`** — 저장소가 클래스당 하나여야 「그 하나」를 가리킬 수 있다. 인스턴스 필드였다면 인스턴스마다 자기 것을 갖게 되어 셀 수 없다 → [[static-member]]
- **메서드가 `static`** — 인스턴스를 얻으려는 시점에 인스턴스가 아직 없으므로, 클래스 이름으로 불려야 한다

`if (instance == null)` 이 성립하는 이유는 **`static` 필드가 선언만으로 `null` 로 초기화되기 때문**이다. 첫 호출 때만 `new` 가 돌고 그 다음부터는 통과한다 — 필기가 「인스턴스의 고유성 여부를 확인」이라 적은 줄이 이것이다 → [[default-initialization]]

## 사용 예시

필기가 쓴 코드는 이렇다. 주석이 세 조각의 역할을 그대로 붙여 두었다.

```java
public class Car{
	//생성자를 접근제한
    private Car();

    //하나의 값(전역변수)만을 가지는 인스턴스 선언
    private static Car instance;

    //인스턴스의 고유성 여부를 확인
    public static Car getInstance(){
    	if(instance == null){
        	//private은 같은 class내에서 접근 가능
        	instance = new Car();
        }
    //고유한 인스턴스 생성
    return instance;
    }
}
```

**「private은 같은 class내에서 접근 가능」이라는 주석이 이 패턴의 전부다.** `private` 생성자를 만들어 놓고 그 다음 줄에서 `new Car()` 를 부를 수 있는 것이 모순처럼 보이는데, `private` 은 **인스턴스 단위가 아니라 클래스 단위**라서 성립한다. 같은 파일 안이면 자기 생성자를 부를 수 있다 → [[access-modifier]]

부르는 쪽에서는 `new` 가 사라진다.

```java
Car car = Car.getInstance();     // new Car() 는 컴파일이 막힌다
```

## 왜 중요한가

**「몇 개 존재하는가」를 부르는 쪽이 정하지 못하게 된다.** 생성자가 열려 있으면 개수는 호출부의 사정이고, `new` 를 두 번 쓴 사람을 막을 방법이 없다. 설정값·연결 풀·로그 기록처럼 **둘이 되면 값이 갈라지는 것**은 「하나만 쓰기로 하자」는 약속으로 지킬 수 없다 — 약속을 지키지 않은 코드가 컴파일되기 때문이다. 싱글톤은 그 약속을 **컴파일러가 지키는 규칙**으로 바꾼다.

**그리고 그 결정이 클래스 안으로 들어온다.** `getInstance()` 안에 무엇이 들어 있는지는 밖에서 안 보이므로, 나중에 「처음 불릴 때 만들기」를 「클래스가 로드될 때 미리 만들기」로 바꿔도 호출부는 한 줄도 안 바뀐다. 캡슐화가 필드에서 하던 일을 **생성 자체에** 한 것이다 → [[encapsulation]]

## 경계와 오해

- **`private Car();` 는 컴파일되지 않는다** — 필기의 코드가 몸통 없이 세미콜론으로 끝난다. 몸통 없는 선언은 **추상 메서드의 문법**인데 생성자는 `abstract` 가 될 수 없다. `private Car() {}` 로 빈 몸통을 붙여야 하고, 「접근을 막는 것이 목적이라 안이 비어 있다」는 것과 「선언만 한다」는 것은 다른 이야기다 → [[abstract-class]] · [[constructor]]
- **싱글톤 ≠ 전부 `static` 인 클래스** — 필기 자신이 두 주 전 실습에서 `UserList` 를 필드·메서드 전부 `static` 으로 만들어 「프로그램 전체에 한 벌」을 이미 얻었다. 결과는 비슷해 보이지만 **한쪽은 인스턴스가 없고 한쪽은 하나 있다.** 갈리는 것은 인스턴스로 존재하는가이고, 그래서 싱글톤만 인터페이스를 구현하고 매개변수로 넘어갈 수 있다 — 전부 `static` 인 클래스는 다형성에 참여하지 못한다 → [[static-member]] · [[interface]] · [[polymorphism]]
- **「하나의 값(전역변수)」는 필기가 두 번째로 같은 말을 한 자리다** — 하나뿐이라는 점은 전역변수와 같지만, 이름이 `private` 이라 밖에서 부를 수 없고 접근 경로가 `getInstance()` 하나로 좁혀진다. 다만 **공유 상태라는 문제는 그대로 남는다** — 어디서든 꺼낼 수 있으므로 누가 그 상태를 바꿨는지 추적할 수 없다. 「전역변수가 아니다」는 문법 이야기이고, 「전역변수와 같은 문제를 갖는다」는 설계 이야기다 → [[static-member]]
- **`getInstance()` 는 getter 가 아니다** — `get` 이 붙었지만 값을 읽어 주는 것이 아니라 **없으면 만든다.** 처음 부른 사람과 두 번째로 부른 사람에게 일어나는 일이 다르고, 부르는 것 자체가 상태를 바꾼다. 필기가 두 주 전 `getSeqNo()` 에서 만난 것과 같은 종류의 이름이다 → [[read-side-effect]]
- **이 `null` 검사는 스레드가 둘이면 깨진다** — 두 스레드가 `instance == null` 을 **동시에** 통과하면 `new Car()` 가 두 번 돌아 인스턴스가 둘 생기고, 늦게 끝난 쪽이 필드를 덮어써서 **먼저 받아 간 쪽만 다른 객체를 들고 있게 된다.** 「고유성 여부를 확인」한다는 그 한 줄이 확인해 주는 것은 **단일 스레드에서만** 참이다. 이것이 이 패턴의 교과서적 함정이고, 필기 시점에는 아직 스레드를 배우지 않아 문제로 보이지 않는다.
- **생성자를 닫으면 상속도 같이 막힌다** — 자식이 `super()` 를 부를 수 없으므로 `extends Car` 자체가 성립하지 않는다. 「인스턴스를 하나로」와 「자식을 만들어 갈아 끼우기」는 **같이 가질 수 없고**, 그래서 싱글톤으로 만든 클래스는 테스트에서 가짜로 바꿔 끼우기도 어렵다 → [[inheritance]] · [[abstract-class]]
- **하나뿐인 것이 언제나 이득은 아니다** — 상태를 들고 있는 싱글톤은 프로그램이 도는 동안 초기화되지 않으므로, 앞에서 바꾼 값이 뒤의 동작에 남는다. 「목록이 둘 필요해지는 날」의 문제를 `static` 저장소와 똑같이 갖는다 — 싱글톤은 그 문제를 해결한 것이 아니라 **하나로 두기로 명시한 것**이다 → [[static-member]] · [[cohesion]]
- **패턴 이름이 문법이 아니다** — `singleton` 이라는 키워드는 없다. 세 조각을 손으로 맞춰 두는 관용이고, 하나라도 빠지면 컴파일은 되면서 「하나뿐」만 조용히 깨진다. 생성자를 `private` 으로 닫는 것을 잊으면 `getInstance()` 는 그대로 있는데 `new` 도 되는 클래스가 된다.
