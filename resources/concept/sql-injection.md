# SQL 삽입 공격 (SQL Injection)

**값으로 들어온 문자열이 SQL 문장의 일부로 파싱되어, 프로그램이 의도하지 않은 문장이 실행되는 것.** Day57 의 정의가 정확하다 — 「입력 문자열에 SQL 명령을 삽입하여 프로그램의 의도와 다르게 데이터를 조작하는 행위」. 원인은 입력이 나쁜 것이 아니라 **문장을 문자열 이어 붙이기로 만든 것**이고, 그래서 답도 검사가 아니라 [[prepared-statement]] 다 → [[jdbc]]

## 정의

Day57 이 「1.3 Statment의 문제점」에 든 예가 이것이다. **필기는 완성된 두 문장만 나란히 적었고, 그 사이에 있어야 할 「무엇을 입력했는가」가 비어 있다.**

```java
// 1. 여러개 삽입
// 원래 쿼리문
stmt.executeUpdate("insert into x_board(title, contents) " +
        "values('" + title + "','" + contents + "')");
// 공격 쿼리문
stmt.executeUpdate("insert into x_board(title, contents) " +
        "values('aaaa','bbbb'), ('haha', 'hoho'), ('hehe','puhul')");
```

빈 자리를 채우면 이렇게 된다.

| 조각 | 값 |
|---|---|
| `title` 입력값 | `aaaa` |
| `contents` 입력값 | `bbbb'), ('haha', 'hoho'), ('hehe','puhul` |
| 조립된 문장 | `insert into x_board(title, contents) values('aaaa','bbbb'), ('haha', 'hoho'), ('hehe','puhul')` |

**공격 문자열이 하는 일은 세 걸음**이다.

1. `'` 로 자기 값의 따옴표를 **닫는다**
2. `)` 로 값 묶음을 닫고 `, (...), (...)` 로 **행을 더 붙인다**
3. 마지막 따옴표와 괄호는 **원래 템플릿에 이미 있으므로 열어 둔 채 끝낸다** — 그래서 문법이 딱 맞는다

즉 공격자가 쓰는 것은 SQL 전체가 아니라 **템플릿의 남은 부분에 이어 붙을 조각**이고, 그러려면 뒤에 무엇이 오는지 짐작해야 한다. 그 짐작을 쉽게 해 주는 것이 오류 메시지다(아래).

### 필기가 이름만 적고 넘어간 쪽 — 「정보 탈취」

Day57 의 다음 줄이 「단순 데이터 조작 뿐만아니라 SQL select문법을 이용해서 사용자의 정보를 탈취 할 수도 있다」인데 **예가 없다.** 그 자리에 들어가는 것은 갈래 셋이고, 셋 다 「값 자리에서 문법을 여는」 같은 동작이다.

| 갈래 | 취약한 문장 | 넣는 값 | 결과 |
|---|---|---|---|
| **인증 우회** | `where id='" + id + "' and pw='" + pw + "'` | id 에 `admin' -- ` | `--` 뒤가 주석이 되어 **비밀번호 조건이 사라진다** |
| **조건 무력화** | 같은 문장 | pw 에 `' or '1'='1` | 조건이 항상 참 — **아무 비밀번호로나 통과** |
| **정보 탈취** | `where title like '" + kw + "'` | kw 에 `x' union select user_id, password from myapp_users -- ` | 게시글 목록 자리에 **회원 표의 내용이 실려 나온다** |

세 번째가 필기가 말한 「select문법을 이용해서」다. **컬럼 개수와 타입만 맞추면 아무 표나 붙일 수 있고**, 화면은 그것을 게시글로 알고 그려 준다 → [[sql-set-operation]] · [[dql]]

## 사용 예시

Day57 의 취약한 형태가 그날 처음 나온 것이 아니다. 사흘 전 Day55 의 실습 DAO 가 이미 그 형태였다.

```java
String sql = String.format(
    "insert into myapp_project_members(user_id, project_id) values(%d,%d)",
    projectNo, user.getNo());
stmt.executeUpdate(sql);
```

여기 들어가는 것은 `int` 둘이라 **당장은 사고가 나지 않는다** — 숫자는 따옴표를 닫을 수 없기 때문이다. 그래서 「문자열 조립도 되긴 된다」는 감각이 남고, 같은 코드에 제목·설명 같은 **사용자가 쓴 글자**가 들어가는 순간 열린다. Day57 이 이 형태를 [[prepared-statement]] 로 바꾼 것이 §2.1 이고, 그 바꿈이 곧 이 취약점을 닫는 일이다 → [[format-string]] · [[literal]]

### 나흘 뒤 Day59 — 프레임워크가 두 표기로 나눠 준다

MyBatis 는 값을 넣는 문법을 **둘** 준다. 한 글자 차이이고, 그 한 글자가 이 개념의 안쪽과 바깥쪽이다 → [[mybatis]]

| 표기 | 하는 일 | 이 개념에서 |
|---|---|---|
| `#{name}` | `?` 로 바뀌어 [[prepared-statement]] 가 된다 | **닫혀 있다** |
| `${name}` | 그 자리에 **문자열을 붙인다** | **Day57 이전으로 돌아간다** |

**Day59 의 필기가 `#{}` 를 후자로 설명한다** — 「xml에 작성된 `#{property}`을 `getPorperty()`으로 변환을 한다」·「`user.getProperty()`를 하여 sql구문을 완성한다」·「완성된 sql구문을 sql서버에 전송한다」. 그 서술이 정확히 「1.3 Statment의 문제점」이 말한 「쿼리문을 완성해서 보내는 문법」이므로, **필기의 설명을 그대로 믿으면 「MyBatis 를 써도 열려 있다」거나 「`${}` 를 써도 마찬가지다」라는 결론이 나온다.** 실제로 `#{}` 는 `?` 가 되어 닫혀 있고, `${}` 는 열려 있다 — **두 표기의 갈림이 설명에 없기 때문에 어느 쪽을 써야 하는지가 이 회차의 필기에서 판단할 수 없다.**

그리고 위험이 **또 한 번 옮겨간다.** [[sql-session]] 노트가 Day58 에 대해 「인젝션 위험은 줄지 않고 옮겨간다 — 문자열 조립을 하는 자리는 호출부로 옮겨졌을 뿐이다」라고 적었는데, Day59 에서는 그 자리가 **매퍼 XML** 이다. 문장이 자바 밖으로 나간 만큼 **리뷰에서 눈에 덜 띄는 파일**로 옮겨간 셈이다 → [[xml]]

## 왜 중요한가

**방금 배운 문장 조립 형태가 그대로 취약점이다.** `Statement` 로 SQL 을 보내는 법을 배우면 값을 넣는 방법은 문자열 결합밖에 없고, 그 코드가 도는 것을 확인한 순간 배움이 끝난 것처럼 보인다. Day57 이 「1.1 SQL문 보내기」 바로 다음 절을 「1.3 Statment의 문제점」으로 둔 것은 그래서 필연이다 — **동작하는 코드와 안전한 코드가 다르다는 것을 처음 만나는 자리**다.

**입력을 믿는 코드와 믿지 않는 코드의 경계가 여기서 생긴다.** 지금까지 `Prompt.input()` 으로 받은 문자열은 그냥 값이었다. 그 값이 **문장으로 해석되는 곳으로 흘러가면** 성격이 바뀌고, 같은 문제가 SQL 밖에서도 같은 모양으로 나타난다 — 명령줄 조립, 파일 경로 조립, 로그에 그대로 찍는 것. 「데이터를 코드가 되게 하지 마라」가 이 개념이 남기는 규율이다 → [[standard-input]] · [[filesystem-path]] · [[cli]]

**그리고 피해가 조회에서도 생긴다.** 「읽기만 하는 화면은 안전하다」는 감각이 여기서 깨진다. `select` 하나로 회원 표를 통째로 뽑을 수 있으므로, **쓰기 권한이 없어도 유출은 일어난다** → [[database-user]]

## 경계와 오해

- **막는 것은 「특수문자를 걸러내는 일」이 아니다** — 가장 흔한 대응이 `'` 를 지우거나 두 번으로 바꾸는 것인데, 이 방법은 **빠뜨린 자리에서 그대로 열린다**: ① 숫자 자리(`where no = " + no`)는 따옴표가 아예 없어서 `1 or 1=1` 로 충분하고, ② 정렬·컬럼 이름 자리에는 따옴표가 없고, ③ 문자셋에 따라 `'` 를 만드는 다른 바이트열이 있다. [[prepared-statement]] 가 이기는 이유는 더 촘촘히 걸러서가 아니라 **값이 문법으로 해석되는 경로 자체를 없애서**다. 「필터 목록을 잘 만들자」로 방향을 잡으면 목록에 없는 것이 늘 남는다 → [[character-encoding]]
- **입력 검증은 방어가 아니라 보조다** — 길이 제한·형식 검사(숫자만·이메일 형태)는 있어야 하지만, 그것이 있어도 자유 입력(제목·본문·검색어)은 남는다. 검증의 목적은 **데이터를 바르게 유지하는 것**이고 인젝션 방어는 문장을 만드는 방식이 맡는다 — 두 목적을 겹쳐 두면 「검증했으니 조립해도 된다」가 된다 → [[number-parsing]]
- **`?` 로 감쌀 수 없는 자리가 남고, 거기가 유일한 위험 지점이다** — 테이블·컬럼 이름과 `order by` 방향은 값이 아니라 식별자라서 바인딩되지 않는다. 정렬 컬럼을 사용자가 고르는 화면에서는 **허용 목록(화이트리스트)에 있는 이름만 문자열에 넣는 것**이 답이고, 「사용자가 준 컬럼 이름을 검사해서 쓴다」가 아니라 「내가 가진 이름 중에서 고른다」로 방향이 뒤집혀야 한다 → [[prepared-statement]]
- **MySQL + JDBC 에서는 `;` 로 문장을 덧붙이는 고전 공격이 기본적으로 안 통한다 — 그래서 Day57 의 예가 다중 행 `insert` 다** — Connector/J 는 `allowMultiQueries=false` 가 기본이라 `'; drop table x_board; --` 는 문법 오류로 끝난다. 대신 **한 문장 안에서 할 수 있는 것**은 전부 열려 있고, 그것이 필기가 든 `values(...),(...),(...)` 다 — 문장이 하나이므로 아무 설정도 우회하지 않는다. 「멀티쿼리를 막았으니 인젝션은 막혔다」가 가장 위험한 오해이고, `union select` 로 표를 뽑는 것도 문장 하나다.
- **`insert` 도 정보를 「읽어」 낼 수 있다** — 필기가 예로 든 것이 등록이라 피해가 「이상한 글 세 개」로 작게 보인다. 그러나 `values('a', (select password from myapp_users where user_id=1))` 처럼 **값 자리에 서브쿼리**를 넣으면 남의 비밀번호가 내 게시글 본문으로 저장되고, 그다음은 그냥 화면에서 읽는다. **쓰기 취약점과 읽기 취약점이 갈리지 않는다** → [[dml]] · [[dql]]
- **예외 메시지를 그대로 보여 주면 공격의 절반을 대신 알려 준다** — 조립이 깨졌을 때 나오는 `SQLException` 에는 **문장 원문과 컬럼·테이블 이름**이 들어 있다. Day57 §2.2 의 `e.printStackTrace()` 는 콘솔 프로그램이라 문제가 없지만, 같은 습관이 웹으로 가면 화면에 스키마가 찍힌다. 공격자가 값을 하나씩 바꿔 가며 오류 메시지를 읽는 것이 실제 순서이고(**오류 기반 인젝션**), 그래서 「사용자에게는 일반 메시지, 로그에는 자세히」가 규율이 된다 → [[exception-handling]]
- **오류가 안 나도 취약할 수 있다** — 메시지를 숨기면 대신 **참/거짓만 보고** 값을 한 글자씩 알아내는 방법(블라인드 인젝션)이 쓰인다. `and substring(password,1,1)='a'` 를 넣고 목록이 나오는지 아닌지를 본다. **증상이 없다는 것이 안전의 증거가 되지 않는다** → [[sql-like]]
- **「관리자만 쓰는 화면」·「내부 CLI」라서 괜찮다가 아니다** — Day57 의 실습은 콘솔 프로그램이라 입력하는 사람이 나뿐이다. 그런데 인젝션은 악의 없이도 사고를 낸다 — 이름에 `'` 가 하나 있으면(오도철·D'Angelo) **평범한 등록이 문법 오류로 실패**한다. 즉 이 문법을 고치는 첫 번째 이유는 공격이 아니라 **정상 데이터가 깨지는 것**이고, 그쪽이 훨씬 자주 일어난다 → [[literal]]
- **프레임워크를 쓰는 것이 막지 않는다 — 표기를 고르는 것이 막는다 (Day59 기준으로 확인된다)** — JPA·MyBatis 는 문자열을 이어 붙이는 API 를 **함께** 준다(네이티브 쿼리, MyBatis 의 `${}`). 값 바인딩 `#{}` 와 문자열 치환 `${}` 가 한 글자 차이이고 **둘 다 컴파일도 검사도 받지 않으므로**, 어느 쪽을 썼는지는 사람이 읽어서만 안다. Day59 의 필기가 `#{}` 만 쓰고 `${}` 를 언급하지 않은 채 **그 동작을 문자열 완성으로 서술했으므로**, 그 상태에서는 두 표기의 차이를 알 근거가 없다 — 「프레임워크가 알아서 한다」가 아니라 **「내가 어느 표기를 썼나」가 유일한 답**이고, 그것을 확인하는 방법은 매퍼 XML 을 눈으로 훑는 것이다 → [[mybatis]]
- **`${}` 를 써야 하는 자리가 실제로 있고, 그 자리가 위험이 모이는 곳이다** — `?` 가 설 수 없는 식별자 자리(테이블명·`order by` 컬럼)는 `#{}` 로 쓸 수 없어 `${}` 가 유일한 길이다. 즉 프레임워크가 위험을 없앤 것이 아니라 **위험한 자리를 문법으로 표시해 준 것**이고, 남는 일은 위의 「허용 목록에서 고른다」와 같다 — **표기가 갈렸으므로 코드 검색으로 그 자리를 전부 찾을 수 있게 된 것**이 프레임워크가 실제로 더해 준 값이다.
- **SQL 인젝션 ≠ 잘못된 SQL** — 문법이 깨져 예외가 나는 것은 **증상**이고, 진짜 위험한 것은 **문법이 맞아서 조용히 실행되는 문장**이다. Day57 의 예도 오류가 없다 — 글이 셋 들어가고 프로그램은 성공했다고 말한다. 「오류가 났으니 막힌 것」과 「오류가 없으니 정상」이 둘 다 틀린 읽기다.
- **입력을 저장할 때가 아니라 조립할 때가 문제다** — `'` 를 지워서 **저장**하는 대응은 원인을 고치지 않고 데이터를 손상시킨다(`D'Angelo` 가 `DAngelo` 로 남는다). 문자열은 원래 값 그대로 저장되어야 하고, 위험은 **그것을 다시 문장에 끼워 넣는 순간**에만 생긴다. 그래서 저장된 값에서 다시 SQL 을 조립하는 코드는 사용자 입력과 똑같이 위험하다(**2차 인젝션**) — 「내 DB 에서 읽은 값이니 안전하다」가 성립하지 않는다 → [[immutability]]

MyBatis 의 매퍼 XML 에서 값을 넣는 문법 `#{property}` 가 나오는데, **필기가 그 동작을 「getter 를 불러 sql구문을 완성한다」·「완성된 sql구문을 sql서버에 전송한다」로 적었다** — 그것은 이 개념이 문제로 지목한 「쿼리문을 완성해서 보내는 문법」의 서술이고, MyBatis 의 다른 표기 `${}` 쪽의 동작이다. 실제로 `#{}` 는 `?` 로 바뀌어 닫혀 있으나, **두 표기가 갈린다는 사실이 필기에 없어서 그 상태로는 어느 쪽을 써야 하는지 판단할 근거가 없다.** 그리고 문자열을 조립할 수 있는 자리가 이번에는 자바 코드가 아니라 **매퍼 XML** 로 옮겨가므로, Day58 에서 「호출부로 옮겨갔다」고 적은 이동이 한 번 더 일어난다 — 문장이 자바 밖으로 나간 만큼 리뷰에서 덜 보이는 파일이 된다 → [[mybatis]] · [[prepared-statement]]
