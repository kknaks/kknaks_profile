# 서블릿 (Servlet)

**HTTP 요청 하나를 받아 HTTP 응답 하나를 만드는 일을 맡은 자바 클래스.** Day63 의 정의가 그대로다 — 「자바로 작성된 서버 측 컴포넌트로, 클라이언트의 HTTP 요청을 처리하고, 그 결과로 HTTP 응답을 생성하는 역할을 한다」. **내가 짜는 것이 프로그램이 아니라 「불려 갈 클래스」로 바뀌는 것**이 이 규격의 실질이다 → [[servlet-container]] · [[java-ee]]

## 정의

Day63 이 이 낱말에 붙인 것이 셋이다.

| Day63 의 문장 | 무엇을 정하는가 |
|---|---|
| 「자바로 작성된 서버 측 컴포넌트」 | 언어와 자리 — 클라이언트가 아니라 서버에서 돈다 |
| 「HTTP 요청을 처리하고, 그 결과로 HTTP 응답을 생성」 | **입력과 출력이 고정된다** — 요청 하나, 응답 하나 |
| 「동적인 웹 콘텐츠를 생성하는 데 사용되며, 자바의 클래스로 구현된다」 | 만드는 것이 파일이 아니라 그때의 결과다 → [[static-and-dynamic-content]] |

그리고 **넷째가 밖에 있다** — 「서블릿의 생명 주기(생성, 초기화, 서비스 요청 처리, 종료)는 서블릿 컨테이너에 의해 제어된다」. 즉 이 클래스는 **자기가 언제 만들어지고 언제 불릴지를 모른다.** Day63 이 그것을 한 줄로 못 박았다 — 「서블릿 컨테이너가 없다면, 서블릿은 독립적으로 동작할 수 없다」 → [[servlet-container]]

Day63 에 서블릿 코드는 나오지 않는다. 이 회차가 정하는 것은 **그 클래스가 놓일 자리**까지이고(`/WEB-INF/classes`), 실제로 무엇을 상속하고 어떤 메서드를 채우는지는 다음 회차로 남는다 → [[web-application-deployment]]

### 하루 뒤 Day64 — 「무엇을 상속하나」의 답이 「상속하지 않는다」다

Day64 가 그 빈 칸을 채운다. 그리고 **답이 상속이 아니었다.**

```java
@WebServlet("/user/list")
public class UserListServlet implements Servlet { … }
```

`Servlet` **인터페이스를 직접 구현**하고 메서드 다섯을 손으로 채운다 — 추상 클래스(`GenericServlet`)는 같은 노트의 마지막 절에 개념으로만 나오고 코드로는 쓰이지 않는다. 즉 이 필기는 **규격의 밑바닥을 한 번 손으로 짚고 나서** 편의 클래스로 올라가는 순서를 잡았다 → [[servlet-lifecycle]] · [[generic-servlet]] · [[interface]]

Day63 에서 비어 있던 다섯 자리 중 넷이 여기서 채워진다.

| Day63 에 없던 것 | Day64 가 채운 것 |
|---|---|
| 무엇을 상속·구현하나 | `implements Servlet` — 메서드 다섯 → [[servlet-lifecycle]] |
| 요청·응답 객체가 무엇인가 | `ServletRequest`·`ServletResponse` → [[request-response]] |
| URL 과 클래스가 어떻게 이어지나 | `@WebServlet("/user/list")` → [[annotation]] |
| 의존을 어디서 받나 | `init()` 에서 `ServletContext` 속성을 꺼낸다 → [[servlet-context]] |
| **인스턴스가 하나라는 것** | **여전히 없다** — 아래 「경계와 오해」 |

그리고 Day64 는 서블릿을 웹 컴포넌트 셋 중 하나로 다시 세운다 — 리스너·필터와 나란히 놓고 **셋 다 컨테이너가 만들어 부른다**는 공통점 아래 묶는다 → [[web-component]] · [[servlet-listener]] · [[servlet-filter]]

## 왜 중요한가

**Day45 부터 세 온 코드 절반이 없어진다.** 지금까지 서버를 만드는 일은 `ServerSocket` 을 열고, `accept()` 를 루프로 돌리고, 접속마다 쓰레드를 붙이고, 무엇을 주고받을지 약속을 정하고, 끝을 알리는 신호를 만드는 일이었다. 서블릿을 쓰면 **그 다섯 가지를 하나도 쓰지 않는다** — 요청은 객체로 주어지고 응답은 객체에 쓰면 된다 → [[socket]] · [[network-protocol]] · [[thread]]

**대신 그 다섯 가지를 내가 정하지 못한다.** [[network-protocol]] 노트가 Day61 에 대해 「사람이 정한 셋 중 둘이 맞고 하나가 틀렸다」고 적은 그 자리가 사라지는데, 사라지는 방식이 **답을 얻는 것이 아니라 질문이 남의 것이 되는 것**이다. 종료 신호를 어떻게 표시할지 고민할 필요가 없어지는 대신, HTTP 가 그것을 어떻게 표시하는지 배워야 한다.

**그리고 내 클래스를 「부르는 쪽」이 프레임워크가 된다.** 실습의 Command 인터페이스가 정확히 같은 모양이었다 — 나는 `execute` 를 채우고, 부르는 것은 메뉴 루프였다. 서블릿은 그 관계가 **프로세스 경계를 넘어** 성립하는 형태이고, 내 코드에 `main` 이 없어지는 첫 자리다 → [[command-pattern]] · [[template-method-pattern]] · [[main-method]]

## 경계와 오해

- **서블릿 ≠ 실행되는 프로그램** — `main` 이 없고 내가 `new` 하지도 않는다. 「자바 클래스로 구현된다」를 「자바 프로그램이다」로 읽으면 **흐름을 내가 갖고 있다고 착각**하게 된다. 실제로는 컨테이너가 클래스를 찾아 만들고, 요청이 올 때 메서드를 부르고, 앱을 내릴 때 정리한다 — 제어가 반대 방향이다 → [[servlet-container]] · [[dependency-injection]]
- **서블릿 하나가 요청 하나가 아니다 — 인스턴스는 보통 **한 개**이고 모든 요청이 그것을 공유한다** — Day63 은 「멀티스레딩」을 컨테이너의 기능으로만 적고 이 사실을 적지 않았는데, 두 문장을 합치면 결론이 하나다: **여러 쓰레드가 같은 객체의 같은 메서드에 동시에 들어온다.** 그래서 서블릿의 **인스턴스 필드에 요청별 값을 담으면** 남의 값을 보게 된다 — Day61 의 서버가 `SqlSession` 하나를 모든 접속이 공유해서 커밋 경계가 섞였던 것과 **같은 형태의 사고**이고, 이번에는 공유되는 것이 내가 무심코 만든 필드다. Day62 가 그 답으로 쓴 도구(값을 쓰레드마다 나누기)가 이 층에서 다시 필요해진다 → [[thread]] · [[thread-local]] · [[singleton-pattern]]
- **서블릿 ≠ 동적 콘텐츠만** — 응답에 파일 내용을 실어 보내도 되고 이미지를 만들어 내보내도 된다. **「동적 콘텐츠를 생성하는 데 사용된다」는 용도이고 제약이 아니다** → [[static-and-dynamic-content]]
- **「컴포넌트」는 클래스라는 뜻이 아니라 「명세가 정한 규칙을 지키는 부품」이라는 뜻이다** — 같은 노트의 JavaEE 표에서 EJB 도 「분산 컴포넌트」로 불린다. 규칙을 지키면 **누가 만든 서버에도 얹을 수 있다**는 것이 이 낱말이 약속하는 것이고, 그래서 서블릿을 쓰는 값의 절반은 톰캣이 아니라 명세에서 온다 → [[java-ee]] · [[interface]]
- **「Servlet/JSP」로 붙어 나오지만 이 회차는 서블릿만 다룬다** — Day63 의 JavaEE 표는 둘을 한 칸(「WebApplication 제작기술」)에 넣고 버전 표에서도 나란히 두는데, 정의와 설명이 붙은 것은 서블릿뿐이다. 둘의 관계는 이 필기에 없다.
- **필기의 Tomcat 구조 절은 서블릿과 내 애플리케이션을 다른 층에 놓는다** — 「Web Container(Servlet Container) : Servlet을 구축하는 환경이다 … Java App : Servlet을 수행하며 동적자원을 관리한다」인데, **서블릿을 「수행」하는 것은 컨테이너**이고 Java App 은 **곧 그 서블릿들**이다. 같은 노트의 다른 절이 맞게 적혀 있어서(「서블릿은 서블릿 컨테이너 안에서 실행됩니다」) 한 노트 안에 두 그림이 있는 상태다 → [[servlet-container]] · [[tomcat]]
- **하루 뒤 Day64 가 「웹 서버 내에서 실행되며」로 되돌려 적는다 — 전날 갈라 놓은 두 낱말이 다시 붙었다** — Day64 의 서블릿 정의는 「웹 서버 내에서 실행되며 클라이언트의 요청을 받아…」인데, **Day63 은 「서블릿은 서블릿 컨테이너 안에서 실행됩니다」로 적고 웹 서버와 컨테이너를 표로 갈라 두었다.** 서블릿을 실행하는 것은 컨테이너이고 웹 서버는 정적 자원을 답하는 부분이므로 Day64 의 표현이 한 겹 뭉개진 것이다. 톰캣이 그 둘을 한 제품에 갖고 있어서 **일상적으로는 구별이 필요 없고**, 필요해지는 자리는 앞단에 Nginx 를 두는 구성이다 — 그때 「웹 서버 안에서 돈다」로 알고 있으면 서블릿을 앞단에서 찾게 된다 → [[web-server]] · [[servlet-container]] · [[tomcat]]
- **「서블릿 ≠ 실행되는 프로그램」이 Day64 에서 실물 사고가 된다 — 생성자를 만든 순간 클래스가 뜨지 않는다** — 위 첫 항목이 개념 설명이었는데, Day64 의 `UserListServlet` 에 `public UserListServlet(UserDao userDao)` 가 남아 있다. 컨테이너는 인수 없는 생성자로 만들므로 이 클래스는 **인스턴스화 자체가 실패하고 그 URL 만 500** 이다. 컴파일도 되고 서버도 정상 기동하며 다른 화면은 잘 돈다. **「내가 `new` 하지 않는다」를 몰라서가 아니라 옛 습관의 코드가 남아서** 생긴 것이고, 그 생성자는 `init()` 이 같은 일을 하므로 필요조차 없다 → [[servlet-lifecycle]] · [[constructor]] · [[dependency-injection]]
- **Day64 의 「`GET`, `POST`, `PUT`, `DELETE` 등의 HTTP 메서드를 지원한다」는 이 회차 코드에 대해 참이 아니다** — `Servlet` 인터페이스에는 `doGet`·`doPost` 가 없고 `service` 하나만 있다. 요청 방식을 보고 갈라 주는 것은 `HttpServlet` 이 하는 일이므로, **`implements Servlet` 으로 만든 이 서블릿은 GET·POST·DELETE 어느 것으로 와도 같은 목록을 돌려준다.** 「서블릿이 HTTP 메서드를 지원한다」는 규격 전체에 대한 말이고 **내가 방금 구현한 것에 대한 말이 아니다** → [[servlet-lifecycle]] · [[generic-servlet]]
- **인스턴스가 하나라는 사실이 하루 뒤에도 적히지 않았다 — 그런데 Day64 의 코드는 우연히 안전하다** — Day64 도 「멀티스레드 처리 … 각 요청은 개별 스레드에서 처리되며」까지만 적고 인스턴스 수를 말하지 않는다. 그 코드가 안전한 이유는 규칙을 알고 지킨 것이 아니라 **담은 것이 마침 안전한 종류**여서다 — `config`·`userDao` 는 `init` 에서 한 번 담고 읽기만 하고, 요청마다 다른 `PrintWriter out` 은 지역 변수다. **두 종류의 필드가 문법으로 구별되지 않으므로** 다음에 요청 값을 필드에 담는 날 같은 코드 모양이 결함이 된다 → [[servlet-lifecycle]] · [[thread]] · [[variable-scope]]
- **Day64 가 역할에 든 「비즈니스 로직 처리」를 같은 노트의 코드는 하지 않는다** — 「데이터베이스 조회, 파일 처리 등과 같은 비즈니스 로직을 수행한다」로 적혀 있지만 `UserListServlet` 은 `userDao.list()` 를 부를 뿐이고 SQL 도 트랜잭션도 만지지 않는다. **역할 목록은 「서블릿에서 할 수 있는 일」이고 코드는 「해야 하는 일만」인 상태**이며, 뒤쪽이 Day56~62 에서 세운 DAO 층의 결과다. 목록을 그대로 읽고 서블릿에 조회를 직접 쓰면 그 층이 무너진다 → [[dao-pattern]] · [[cohesion]]
- **요청 객체를 필드에 보관하면 그 요청이 끝난 뒤에도 붙들고 있게 된다** — 위의 「인스턴스가 하나」와 같은 뿌리인데 증상이 다르다. 컨테이너는 요청·응답 객체를 **재사용하거나 되돌려 놓을 수 있으므로**, 응답을 다 보낸 뒤에 그 객체를 만지면 무엇을 만지는지 보장되지 않는다. 「객체를 받았으니 내 것」이 성립하지 않는 첫 자리다 → [[object-reference]] · [[garbage-collection]]

## 출처

- [[2024-08-26-Day63]] — 「서블릿 컨테이너와 서블릿」 절의 「서블릿(Servlet)」 항목이 이 개념이다. 「자바로 작성된 서버 측 컴포넌트로, 클라이언트의 HTTP 요청을 처리하고, 그 결과로 HTTP 응답을 생성하는 역할을 한다」·「동적인 웹 콘텐츠를 생성하는 데 사용되며, 자바의 클래스로 구현된다」로 정의하고, 관계 항목에서 「서블릿은 서블릿 컨테이너 안에서 실행됩니다」·「서블릿의 생명 주기(생성, 초기화, 서비스 요청 처리, 종료)는 서블릿 컨테이너에 의해 제어된다」·「서블릿 컨테이너가 없다면, 서블릿은 독립적으로 동작할 수 없다」로 **흐름의 주인이 내가 아니라는 것**을 못 박았다. JavaEE 표에서는 「Servlet/JSP : WebApplication 제작기술」로 묶여 나오고 버전 표에 Servlet 2.5~4.0 이 적혀 있다. 다만 **서블릿 코드가 이 회차에 없다** — 무엇을 상속하고 어떤 메서드를 채우는지, 요청·응답 객체가 무엇인지, URL 과 클래스가 어떻게 이어지는지는 나오지 않고, 놓일 자리(`/WEB-INF/classes`)만 톰캣 부팅 코드에서 확인된다. **인스턴스가 하나이고 모든 요청이 그것을 공유한다는 사실**도 적히지 않아서, 같은 노트가 컨테이너의 기능으로 든 「멀티스레딩」과 합쳤을 때 나오는 결론(인스턴스 필드에 요청별 값을 담으면 남의 값이 보인다)이 비어 있다. 같은 노트의 Tomcat 구조 절이 「Java App : Servlet을 수행하며」로 적은 것은 이 절의 설명과 어긋난다
- [[2024-08-27-Day64]] — 하루 뒤. **서블릿 코드가 처음 나오는 회차**다. 「Web Component의 종류 > 서블릿」 절이 정의를 「웹 애플리케이션을 만들 때 서버 측에서 동작하는 자바 코드」·「HTTP 요청을 처리하고 동적인 웹 콘텐츠를 생성하는 역할한다」로 다시 적고 역할을 넷(HTTP 요청 처리 · 동적 콘텐츠 생성 · 비즈니스 로직 처리 · 요청/응답 관리) 들었으며, 뒤쪽 절에서 `@WebServlet("/user/list")` + `implements Servlet` 으로 회원 목록 서블릿을 만든다. Day63 이 「다음 회차로 남는다」고 적어 둔 것들이 여기서 채워지는데 **답이 상속이 아니라 인터페이스 직접 구현**이고(`GenericServlet` 은 같은 노트 마지막 절에 개념으로만 나온다), 요청·응답 객체(`ServletRequest`/`ServletResponse`)·URL 매핑(`@WebServlet`)·의존을 받는 자리(`init` 에서 `ServletContext` 속성 조회)가 함께 나온다. 다만 **정의를 「웹 서버 내에서 실행되며」로 적어** 전날 갈라 둔 웹 서버와 컨테이너를 다시 붙였고, 역할 목록의 「`GET`, `POST`, `PUT`, `DELETE` 등을 지원한다」·「비즈니스 로직 처리」는 같은 노트의 코드에서 성립하지 않는다(`Servlet` 인터페이스에는 `doGet`·`doPost` 가 없고, 서블릿은 DAO 에 위임한다). **인스턴스가 하나라는 사실은 이 회차에도 없고**, 코드에 남은 `public UserListServlet(UserDao userDao)` 생성자 때문에 컨테이너가 이 클래스를 인스턴스화할 수 없어 해당 URL 이 500 이 된다 — 「서블릿은 내가 `new` 하지 않는다」가 코드로 지켜지지 않은 자리다(→ [[servlet-lifecycle]])
