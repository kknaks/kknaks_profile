# 검색 인덱스 (Search Index)

빠른 검색을 가능하게 하는 색인 구조로, 원본 데이터와 별도로 저장·관리된다.

## 정의

- 책의 목차나 색인처럼, 검색 키워드가 어떤 문서에 있는지를 미리 정리해 둔 구조다.
- 원본 DB에서 데이터를 꺼내 검색 인덱스 저장소(Elasticsearch 등)에 입력하면, 인덱스를 자동 생성·보관한다.
- 검색 요청이 오면 원본 DB 대신 인덱스를 통해 결과를 빠르게 반환한다.
- 부가 기능: 실시간 검색어 추천, 오타 교정, 연관 검색어 제공.

**이 구조는 별도 제품에만 있는 것이 아니다.** Day51 이 MySQL 의 `fulltext index` 로 처음 만나는 것이 같은 것 — 문장을 단어로 쪼개 「어느 단어가 어느 행에 있는지」를 적어 두는 역인덱스이고, 다만 **원본 테이블 옆에 산다.** 그래서 이 개념의 경계는 「어느 제품인가」가 아니라 **「원본과 별개의 파생 구조인가」**로 잡아야 한다 → [[database-index]]

```sql
fulltext index test1_name_idx (name)     -- MySQL 안에 만드는 역인덱스
```

## 왜 중요한가

일반 DB에서 텍스트 전체 검색은 데이터를 전부 순회(full scan)해야 해서 느리다. 인덱스를 별도로 유지하면 검색 속도가 크게 빨라진다. 검색이 핵심 기능인 서비스에서 인덱스 없이 DB 직접 조회로 버티는 것은 규모가 커질수록 불가능에 가깝다.

## 경계와 오해

- **인덱스 저장소 ≠ 메인 DB — 다만 「메인 DB 안에는 없다」는 뜻은 아니다** — Elasticsearch 같은 인덱스 전용 DB는 검색 보조 저장소이고, 원본 데이터는 메인 DB에 두고 인덱스는 검색 성능을 위한 파생 구조다. **그런데 MySQL 의 `fulltext index` 도 역인덱스이므로 이 문장을 「역인덱스는 밖에 있다」로 읽으면 어긋난다**(Day51). 둘을 실제로 가르는 것은 위치가 아니라 **갱신 시점**이다 — DB 안의 전문 인덱스는 같은 트랜잭션에서 함께 갱신되어 원본과 어긋날 수 없고, 별도 제품의 인덱스는 원본을 따라 밀어 넣어야 해서 **시차와 불일치가 생긴다.** 별도 제품을 고르는 이유도 성능만이 아니라 **검색 부하를 원본 DB에서 떼어 내는 것**이다.
- **검색 인덱스 ≠ DB 인덱스** — 이 노트가 `인덱스`·`index` 별칭을 갖고 있어 `[[인덱스]]` 는 여기로 풀리지만, 관계형 DB에서 `where`·`order by` 를 빠르게 하는 B-tree 인덱스는 [[database-index]] 쪽이다. **역인덱스는 「이 단어가 든 문서」를 찾고 B-tree 인덱스는 「이 값인 행」을 찾는다** — 전자는 전문 검색용 문법(`MATCH ... AGAINST`)으로만 쓰이고, `where name = 'aaa'` 에는 쓰이지 않는다.
- **인덱스는 쓰기 비용이 있다** — 원본 데이터가 바뀌면 인덱스도 갱신해야 한다. 쓰기가 매우 빈번한 데이터는 인덱스 갱신 비용이 부담이 된다.
- **일반 DB 기능과 다르다** — Elasticsearch도 일반 DB로 사용할 수 있지만, 그것이 주 용도가 아니다.
