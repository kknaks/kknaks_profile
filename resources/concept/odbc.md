# ODBC (Open Database Connectivity)

**어느 DB 를 쓰든 애플리케이션이 부르는 함수는 같게 하고, 그 함수와 실제 DB 사이를 드라이버가 잇게 만든 표준 API.** Day53 의 첫 세 줄이 이 표준이 왜 있는지를 그대로 적는다 — 판매사마다 API 를 따로 만들었고(Native API), 「Oracle, MSSQL, MySQL 상호 호환이 불가능」했고, 그래서 「ODBC로 통일」했다.

Day51~Day52 는 `mysql` 클라이언트 창에서 SQL 을 쳤다. **여기서부터는 프로그램이 DB 에 접속하는 이야기**이고, 그 첫 질문이 「무엇을 향해 함수를 부르나」다.

## 정의

`ODBC` 는 DB 에 접속·질의하는 **함수의 규격**이다. 구현이 아니다. 그래서 Day53 이 적은 세 줄이 순서대로 규격·효과·대가다.

| Day53 의 줄 | 무엇을 말하는가 |
|---|---|
| 「API규칙을 정의 하여 각 판매사별로 규칙을 통일」 | **규격** — 함수 이름과 호출 형태를 표준이 정한다 |
| 「명령어를 동일하게 적용가능」 | **효과** — 애플리케이션 코드가 DB 종류를 몰라도 된다 |
| 「각 Driver을 설치 해야한다」 | **대가** — 규격은 실행되지 않는다. DB 마다 구현체가 따로 필요하다 |

호출이 DB 까지 가는 경로는 층이 넷이다.

```text
애플리케이션  →  ODBC API  →  (DB 별) ODBC Driver  →  판매사 Native API  →  DB
   내 코드      표준 함수         설치하는 구현체         원래의 벤더 API
```

**Native API 가 사라진 것이 아니라 드라이버 안으로 들어갔다.** 통일된 것은 내가 부르는 자리이고, 판매사별 차이는 그 아래 층이 계속 떠안는다.

### Native API 만 있던 세계

| | Native API | ODBC |
|---|---|---|
| 부르는 함수 | DB 마다 다르다 | 표준 하나 |
| DB 를 바꿀 때 | 호출 코드를 **다시 쓴다** | 드라이버와 접속 정보를 바꾼다 |
| 설치할 것 | 그 DB 의 라이브러리 | 그 DB 의 ODBC 드라이버 |
| 두 DB 를 함께 쓸 때 | API 두 벌을 익힌다 | 드라이버 두 개를 등록한다 |

## 왜 중요한가

**「DB 를 바꾸면 무엇을 고쳐야 하는가」의 답이 여기서 정해진다.** Native API 시절의 답은 「DB 를 만지는 코드 전부」였다. 표준이 생긴 뒤의 답은 「드라이버와 접속 문자열」이다. 코드량이 줄어든 것이 아니라 **바뀌는 것이 코드 밖으로 나갔다.**

**그리고 이것이 「인터페이스와 구현을 가른다」의 첫 실물 사례다.** Day23 이후 배운 [[interface]] 는 내가 만든 클래스 두 개를 갈라놓는 이야기였는데, 여기서는 **규격을 정한 쪽과 구현한 쪽이 아예 다른 회사**다. 규격이 코드가 아니라 문서로 존재하고, 구현체는 나중에 설치되는 파일로 온다 — 인터페이스가 조직의 경계를 넘는 계약이 될 수 있다는 것을 이 층이 보여준다 → [[dependency-inversion-principle]] · [[polymorphism]]

**대가도 함께 배워야 한다.** 표준은 「설치할 것이 없어진다」가 아니라 **「무엇을 설치할지가 표준 밖으로 밀려난다」**다. Day53 이 굳이 「각 Driver을 설치 해야한다」를 적어 둔 것이 그 대가이고, 접속이 안 될 때 의심할 자리가 SQL 이 아니라 **드라이버 등록**으로 옮겨간다.

## 경계와 오해

- **ODBC ≠ SQL 이 같아진다** — 통일된 것은 **API**(접속·질의·결과 읽기 함수)이고, 그 함수에 실어 보내는 **SQL 문자열은 그대로 갈린다.** 바로 앞 회차가 배운 것이 이 반례다: Day52 의 `date_format` 은 MySQL 것이고 Oracle 에서는 `to_char` 이며, 행 수를 제한하는 것도 MySQL 은 `limit`, Oracle 은 `rownum`, SQL Server 는 `top` 이다. 「명령어를 동일하게 적용가능」은 **함수 호출을 두고 한 말**이지 SQL 을 두고 한 말이 아니다 → [[sql-date-function]] · [[sql-data-type]] · [[dql]]
- **표준 ≠ 구현** — 「ODBC 를 설치한다」는 말이 성립하지 않는다. 설치하는 것은 **그 DB 의 ODBC 드라이버**이고, ODBC 자체는 규격 문서다. 이 구분이 없으면 「표준을 깔았는데 왜 MySQL 에 못 붙나」에서 막힌다. Day53 이 규격 줄과 설치 줄을 나란히 적어 둔 이유가 여기 있다.
- **ODBC 드라이버 ≠ 장치 드라이버** — 같은 「드라이버」라는 말이지만, OS 가 하드웨어를 제어하려고 쓰는 것([[web-application]] 이 System S/W 로 분류한 그것)과 달리 여기서는 **표준 API 호출을 특정 DB 의 통신으로 번역하는 라이브러리**다. 공통점은 「위에서 정한 규격을 아래의 특정 제품에 맞춰 구현한 것」이라는 자리뿐이다.
- **「통일」이 「어디서나 같다」는 아니다** — ODBC 는 Microsoft 가 낸 **C 함수 규격**이고, 드라이버를 찾아 주는 드라이버 매니저가 OS 마다 다르다(Windows 는 OS 에 들어 있지만 macOS·Linux 는 `unixODBC` 같은 것을 따로 깐다). DB 판매사 차이는 흡수하지만 **OS 차이는 흡수하지 않는다** — 흡수하는 축이 하나뿐이라는 것이 다음 절의 [[jdbc]] 가 따로 필요한 이유가 된다 → [[platform-dependency]]
- **필기의 「ODBS」는 오기다** — Day53 은 네 자리에서 `ODBS` 로 적었다(`ODBS API규칙`·`ODBS Driver`·`ODBS의 기능`·`ODBS-JDBC Bridge Driver`). Open Database **Connectivity** 이므로 `ODBC` 다. 본문은 그대로 두었지만, 이 오기로는 검색해도 아무것도 안 나오고 `ODBS`(Open Database Server 등)라는 다른 말과 부딪힌다.
- **DB 를 바꿀 수 있다 ≠ 바꿔도 똑같이 돈다** — API 가 같아도 성능·잠금·기본 격리 수준·자동 증가 방식이 제품마다 다르다. Day52 가 본 「커밋 전에는 안 보인다」는 InnoDB 의 기본값이었고, 다른 제품으로 옮기면 같은 코드가 다른 시점에 다른 것을 본다 → [[transaction]]
