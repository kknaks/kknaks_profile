# 스테이지 사이 세션을 이어받는다 — 체인 하나가 한 대화다

게이트 스테이지가 앞 스테이지의 **AI 세션을 물고** 시작한다. 지금은 재생성·재시도 안에서만 이어받고 스테이지가 넘어가면 새 세션이라, 매 스테이지가 규칙과 양식을 다시 읽고 앞 단계 결과를 payload 로 다시 받는다.

## Context

- 관련 baseline: [[baseline-003-inbox-approval-pipeline|KDEV-BL-003]]
- [[decision-011-approval-gate-chain|KDEV-DEC-011]] D4 가 「재생성은 세션 resume 으로 이어서 실행한다」를 정했고 [[spec-009-gate-feedback|KDEV-SPEC-009]] S-5 가 그 순서(버전 → 실행 → stateless)를 규정했다. **둘 다 게이트 하나 안쪽만 본다.**
- 실측이 그 대가를 처음 보여 줬다([[2026-08-13-knowledge-pipeline-stage-timing]]). 항목 #3880 의 다섯 스테이지 합이 약 13분이고, 매 스테이지가 `rules/knowledge-note-pipeline.md` 와 양식 파일을 다시 읽는다.
- **비용만의 문제가 아니다.** 지금 `concept` 는 `source_note` 를 payload 로만 알고 `derived` 는 그 둘을 요약본으로만 안다. 세션을 물면 「방금 내가 쓴 자료 노트」를 그대로 딛는다.
- 재료는 이미 있다. `AITask.session_ref` 와 `GateRevision.session_ref` 가 스테이지마다 저장되고 있고, 실행기 옵션(`resume`)도 이미 배선돼 있다. **저장은 하는데 스테이지를 넘길 때 안 읽을 뿐이다.**

## 근거 개념

- [[cold-start]] — 지금 구조가 정확히 이것이다. 스테이지마다 준비 상태 없이 시작해 규칙·양식·원문을 다시 들인다. 「준비 비용은 일의 크기와 무관하다」가 스테이지를 잘게 쪼갠 이 파이프라인에서 그대로 나타난다. 이 개념이 **웜으로 바꿀 때 무엇을 함께 정해야 하는지**(무엇을 물려받고 무엇을 버리나, 잃었을 때 어디로 떨어지나)도 같이 말해 준다
- [[stateless-protocol]] — 지금 스테이지 경계는 사실상 무상태다. 각 실행이 필요한 것을 payload 에 담아 독립적으로 처리된다. 그 성질이 준 것(재시작 내성 · 수확 멱등성)을 D4 의 폴백이 그대로 지킨다 — **웜을 얹되 무상태 경로를 없애지 않는다**

## Options

### 어디까지 이어받나

| Option | Description | Pros | Cons | Notes |
|---|---|---|---|---|
| A | 지금처럼 게이트 안쪽만 | 변경 없음 | 스테이지마다 콜드. 뒤 스테이지가 앞 산출물을 요약으로만 안다 | 기각 |
| **B** | **게이트 사이를 잇는다** (route → source_note → concept → derived) | 사람이 그린 그림 그대로. 뒤 스테이지가 앞의 산출물을 자기 것으로 딛는다 | 잘못된 전제까지 물려받을 수 있다 → D2 가 받는다 | **채택** |
| C | auto 스테이지(`summarize`)까지 잇는다 | 원문을 읽은 세션이 그대로 내려온다 — 가장 크다 | auto 는 게이트와 계약이 다르고(리비전이 없다) 검증 축이 하나 더 는다 | **보류** — OQ-1 |

### 재시도가 무는 세션

| Option | Description | Pros | Cons | Notes |
|---|---|---|---|---|
| a | 항상 새 세션 | 오염된 세션을 반복하지 않는다 | 형식 하나 틀렸는데 처음부터 다시 읽는다. #3880 의 309초가 이것 | 기각 |
| **b** | **형식·검증 실패만 이어받고 사유를 준다** | 「그 자리에서 고쳐라」가 된다. 실행 실패는 물 세션 자체가 없다 | 실패 시에도 세션을 저장해야 한다 | **채택** |
| c | 사유 불문하고 늘 이어받는다 | 단순 | timeout 뒤 같은 상태를 다시 태울 수 있다 | 기각 |

## Decision

### D1. 이어받기 순서에 **앞 스테이지**를 더한다

```text
1  이 게이트의 최신 버전 세션          (지금과 같다 — 재생성)
2  이 게이트의 최신 실행 세션          (지금과 같다 — 재시도, D3 이 확장한다)
3  앞 게이트의 세션 — 정의 역순, 가장 가까운 것부터   ← 새로 더한다
4  없으면 stateless                    (지금과 같다 — D4)
```

3단의 후보는 **파이프라인 정의의 게이트 스테이지**를 역순으로 훑어 찾는다. `AITask.kind` 로 찾지 않는다 — 그 축은 게이트가 살아 있는지를 모른다(D2).

### D2. `cancelled` 게이트의 세션은 잇지 않는다

route 재오픈([[decision-011-approval-gate-chain|KDEV-DEC-011]] D5)으로 무효화된 게이트의 세션은 **틀린 목적지 위에서 쓴 것**이다. 그것을 물고 새 목적지의 노트를 쓰면 재오픈이 한 일이 반쯤 취소된다.

대신 **살아 있는 route 세션을 문다.** 재오픈된 route 세션에는 원래 판단, 「이 목적지가 아님」 피드백, 수정된 판단이 순서대로 들어 있다 — 뒤 스테이지가 알아야 할 것이 정확히 그것이다.

이 조항은 지금 코드의 결함도 함께 닫는다. `AITask.kind` 폴백이 취소 여부를 보지 않아, 재오픈 뒤 새로 열린 `source_note` 게이트가 **취소된 옛 게이트의 세션**을 물 수 있었다.

### D3. 실패한 실행의 세션도 저장하고, 형식 실패의 재시도는 그것을 문다

지금은 `_fail` 이 `session_ref` 를 저장하지 않는다. 그래서 **형식이 틀려서 실패한 실행**의 세션 — 재시도가 가장 물고 싶은 바로 그것 — 이 버려진다.

- 파싱·검증 실패는 실행이 **성공한 뒤** 나는 것이라 세션이 손에 있다. 저장한다.
- 재시도 입력에 **직전 실패 사유**를 넣는다(`previous_error`). 사람 피드백과 섞지 않는다 — 출처가 다르다.
- 실행 실패(timeout · 작업 소실 · 빈 결과)는 물 세션이 애초에 없어 자연히 새 세션이 된다. **사유 목록으로 분기하지 않는다** — 「세션이 저장돼 있는가」가 곧 그 판정이다.

### D4. 세션이 없거나 만료되면 stateless 로 만든다 — 실패시키지 않는다

[[spec-009-gate-feedback|KDEV-SPEC-009]] S-5 를 그대로 유지한다. payload 에 원문·요약·앞 단계 결과가 다 들어 있어 만들 수는 있다. 품질이 떨어질 뿐 막히지 않는다.

**웜을 전제로만 도는 경로를 만들지 않는다**는 뜻이다. 세션 저장소가 사라지는 날 파이프라인이 통째로 멈추면 안 된다.

> **구현이 이 조항을 절반만 지킨다 (2026-08-14 실측, item #3881).**
>
> 폴백이 도는 것은 **DB 에 `session_ref` 가 없을 때**뿐이다. ref 는 있는데 **실행기 쪽에서 세션이 사라진 경우**는 제출이 성공하고 *실행*이
> `No conversation found with session ID: …` 로 실패한다 — 게이트가 `failed` 가 되고, 재시도는 같은 죽은 세션을 다시 문다.
>
> 세션은 `kknaks-worker` 컨테이너의 `/tmp` 에 살고 **볼륨이 없다.** 즉 **배포할 때마다 전부 사라진다.**
> 승계 전에는 게이트 하나 안쪽에만 영향이 있었지만, 이제 뒤 스테이지가 전부 앞 세션에 의존하므로
> **배포 한 번이 진행 중인 항목을 전부 막는다.** 이 결정이 키운 구멍이다.
>
> 받는 방법은 「죽은 세션을 만나면 stateless 로 한 번 다시 돈다」이고, 그 판정은 실행 실패 메시지에서 나온다.
> OQ-4 로 추적한다.

### D5. 이어받을 때는 원문(`source_excerpt`)을 다시 보내지 않는다

[[spec-009-gate-feedback|KDEV-SPEC-009]] S-1 5항이 「세션을 이어받으면 원문·지침을 다시 보내지 않아도 된다」고 적었는데 **코드는 매번 전량을 다시 보내고 있었다.** 실행기가 프롬프트 뒤에 payload 전문을 붙이기 때문이다.

- 세션을 물면 `source_excerpt`(상한 40,000자)를 payload 에서 뺀다.
- **요약은 항상 남긴다.** 짧고, 뒤 스테이지의 판단 축이며, 세션이 압축됐을 때 마지막 방어선이다.
- 뺐다는 사실을 payload 에 남긴다(`resumed_session: true`) — 에이전트가 「원문은 위에 있다」를 알아야 한다.

### 기각

- 게이트 안쪽만 잇는 현행(A), 재시도에서 사유 불문 이어받기(c), 항상 새 세션(a).
- 스테이지 경계마다 세션을 새로 만들고 앞 산출물을 더 두껍게 요약해 넘기는 안 — 요약을 두껍게 할수록 payload 가 커져 원래 문제로 돌아온다.

### 보류

- `summarize`(auto) → `route` 승계(옵션 C). OQ-1.
- 세션 만료를 감지해 미리 다시 데우는 것(warm-up). 만료가 실제로 관측되기 전에는 만들지 않는다.

## Rationale

- **판단 기준**: 이미 저장하고 있는 것을 읽기만 하면 되는가, 잘못 물려받았을 때 빠져나갈 길이 있는가, 물려받을 게 없을 때 그대로 도는가.
- **B 인 이유**: owner 가 그린 그림이 「route 로 목적지가 정해지면 그걸 문 채로 자료노트 → 개념 → 교안」이다. 그리고 이 승계는 **품질 축이 더 크다.** `concept` 가 자료 노트를 payload 의 문자열이 아니라 자기가 방금 쓴 문서로 알고, `derived` 가 그 둘을 요약본이 아니라 원본으로 안다. 시간은 그 부산물이다.
- **b 인 이유**: #3880 에서 형식 오류 하나가 95초 + 309초를 태웠다. 그 재시도는 「같은 자료를 처음부터 다시 읽는 일」이었는데, 실제로 필요한 것은 「방금 낸 출력의 3행 840열을 고치는 일」이었다.
- **D2 를 명시적으로 쓰는 이유**: 재오픈은 「앞의 판단이 틀렸다」는 선언이다. 그 선언 뒤에 틀린 판단의 세션이 조용히 살아 있으면, 사람은 되돌렸다고 믿는데 시스템은 안 되돌린 상태가 된다.
- **리스크**:
  - **오염 전파.** 앞 스테이지에서 어긋난 이해가 뒤까지 간다. 지금은 스테이지마다 새로 시작해 그 사슬이 끊겼다. 받는 장치는 게이트 자체다 — 사람이 매 스테이지에서 보고 승인하며, 피드백 재생성은 그 게이트의 세션을 물어 그 자리에서 고친다.
  - **세션 압축.** 긴 체인에서 앞부분이 압축돼 원문 세부가 사라질 수 있다. D5 가 원문을 빼므로 이 위험이 커진다. 요약을 항상 남기는 것과 게이트 검토가 방어선이고, 실제로 관측되면 D5 를 자료 길이 조건부로 좁힌다(OQ-2).
  - **측정 없이 좋아졌다고 말할 수 없다.** 표본이 1건이라(#3880) 개선 판정에는 같은 성격의 자료로 다시 재야 한다.
