# Knowledge Note Pipeline

## 목적

지식 노트 파이프라인의 목적은 노트를 늘리는 것이 아니라, **자료가 재사용 가능한 개념이 되고 그 개념이 제품으로 내려가는 경로**를 고정하는 것이다.

이 문서는 사람과 AI가 지식 노트를 쓸 때 따르는 작성 규칙이다. `rules/product-doc-pipeline.md`의 지식노트 대칭이다.

| | 규칙 | 템플릿 | 검증기 |
|---|---|---|---|
| 제품 문서 | `rules/product-doc-pipeline.md` | `templates/product/` | `.agent/scripts/product_doc_pipeline.py` |
| **지식 노트** | **이 문서** | `templates/knowledge/` | `app/back/core/graph.py` (L1~L6) |

계약의 SSOT는 spec이다 — 이 문서는 *쓸 때 따르는 규칙*, spec은 *검증기가 검사하는 계약*이다.

- 디렉토리: [[spec-001-directory-structure|KDEV-SPEC-001]]
- 스키마·층·엣지: [[spec-002-graph-schema|KDEV-SPEC-002]]
- 생명주기: [[spec-003-knowledge-workflow|KDEV-SPEC-003]]
- 검증: [[spec-004-graph-validation|KDEV-SPEC-004]]

## 4층 모델

지식은 **출처 → 개념 → 판단 → 실행** 방향으로 자란다.

| 층 | 답하는 질문 | 경로 | `type` | 단위 | 수명 |
|---|---|---|---|---|---|
| 출처 기록 | "이 자료가 뭐라고 했나" | `reference/` (flat) | `reference` | 자료 하나 | 생성 후 고정 |
| 원자 개념 | "이 개념은 뭔가" | `permanent/concept/` | `concept` | 개념 하나 | 출처 합류로 **성장** |
| 종합 판단 | "내 판단·전략은 뭔가" | `permanent/` 루트 | `permanent` | 영역 하나 | 개념 유입마다 갱신 |
| 실행 | "그래서 뭘 만드나" | `products/{제품}/` | `baseline`·`decision`·`spec`·`work`… | 프로젝트 문서 | 제품 파이프라인 |

층 밖:

| 경로 | `type` | 성격 |
|---|---|---|
| `inbox/` | `idea` | 미정제 보류함. 노드이되 층 없음, `up:` 대상이 될 수 없다 |
| `permanent/archive/` | (원 타입 유지) | 층이 아니라 **상태**. `permanent`·`concept` 공용 |
| `persona/contents/` · `algorithms/` | `content`·`algorithm` | 그래프 밖 (KDEV-DEC-008) |

### 왜 나누나

자료와 개념은 **1:1이 아니다.** 영상 하나에서 개념이 여럿 나오고, 개념 하나가 영상 여럿에 걸쳐 나온다. 층을 합치면 자료 기준으로는 개념이 흩어지고, 개념 기준으로는 "그 자료가 뭐라 했는지"가 사라진다.

수명도 다르다. `reference`는 박제(그 영상이 한 말은 변하지 않는다), `concept`는 성장, `permanent`는 개념이 늘 때마다 갱신.

## 핵심 규율

### SoT 위임 — 개념 상세는 한 곳에만

개념의 상세 설명은 **concept 노트 한 곳**이 소유한다.

- `reference`는 개념을 재서술하지 않고 **요지 + `[[concept]]` 링크**로 위임한다.
- `permanent`도 개념을 재서술하지 않고 **엮은 판단만** 소유한다.

"재서술하지 않는다"는 **상세 설명 섹션을 복사하지 않는다**는 뜻이다. 판단 문장 안에 개념 요지가 인용되는 것은 허용하며 필연적이다("성숙도 2단계이므로 확산에 집중" 같은 문장에는 개념 요지가 스며든다).

### 개념 성장 — 두 번째 출처는 보충이다

같은 개념에 두 번째 출처가 오면 **새 파일을 만들지 말고 기존 concept를 보충**한다. `up:`과 본문 `[[]]`에 새 출처를 더한다.

이게 없으면 `stt.md`와 `speech-to-text.md`가 갈라져 SoT가 둘이 된다. **`aliases`가 그 갈라짐을 막는 1차 장치**다.

### 개념의 입도 — 독립 재사용 가능성

**다른 자료·다른 맥락에서 이 개념만 따로 등장할 수 있으면 별개 개념**이다. 아니면 상위 개념의 구성 요소로 본문에 둔다.

보조 신호:

- **`aliases`를 붙일 수 있는가.** 이름이 여러 개 있다는 건 독립된 것으로 불린다는 뜻이다.
- **"X는 ~이다" 한 문장 정의가 써지는가.** 안 써지면 대개 구성 요소다.

예 — 한 영상에서 개념 후보가 셋 나왔다면:

| 후보 | 판정 | 근거 |
|---|---|---|
| 구조와 내용의 분리 | 분리 | API 설계 등 다른 맥락에서도 독립 등장 |
| 결정적 뼈대 우선 | 분리 | 컴파일러·파서 맥락에서도 독립 등장 |
| "그래프=위치, 위키=내용" | 분리 안 함 | 위 첫 개념의 **구성 요소**. 단독으로 등장하지 않는다 |

> **잠정 규칙이다.** 표본이 아직 없다(concept 0건). **concept 10건 도달** 또는 **같은 개념이 두 파일로 갈라진 첫 사례**(입도가 너무 잘다는 신호) 중 먼저 오는 시점에 재검토한다.

### `up:`은 상류만 가리킨다

`up:`은 "이 노트는 저것을 기반으로 한다"는 계보다. 같거나 낮은 층만 가리킬 수 있다.

| 노트 | `up:` 대상 |
|---|---|
| `concept` | `reference` (자신이 나온 출처) |
| `permanent` | `concept` (판단을 구성하는 개념) |
| 제품 문서 | `concept` · `permanent` (결정의 근거) |
| `idea` | **금지** (휘발이라 상류를 가질 수 없다) |

**비교 대상은 `up:`이 아니다.** "내가 만든 것과 대조해보면…" 같은 참조는 본문 `[[]]`(assoc)로만 둔다. 기반이 아닌 것을 `up:`에 넣으면 계보가 거짓이 된다.

### 오버레이 — `up:`은 본문 링크의 부분집합

`up:`에 넣은 stem은 **본문 `[[]]`에도 있어야 한다**. 본문이 엣지의 단일 소스이고 `up:`은 그중 계보인 것을 마킹하는 오버레이이기 때문이다(KDEV-DEC-004).

## 층별 필수 필드

| type | 필수 | 근거 |
|---|---|---|
| 공통 | `type` · `id`(=파일명 stem) · `title` | 노드 식별 |
| `reference` | + `date` | flat — 하위 디렉토리·group 없음 |
| `concept` | + **`aliases`** · **`up`** | 개념 중복 방지 / 출처 없는 개념은 성립 안 함 |
| `permanent` | + **`up`** | 개념을 엮지 않은 종합은 성립 안 함 |
| `idea` | (`up` 금지) | 휘발 |

`layer`는 **적지 않는다.** `type`에서 도출되며 빌더가 `_graph.json`에 담는다. 같은 사실을 두 곳에 두면 어긋난다.

## 파일명과 식별자

- 노드 식별자 = **파일명 stem**. 전역 유일.
- frontmatter `id`는 stem과 같아야 한다(지식 노트 한정 — 제품 문서는 `{PRODUCT}-{TYPE}-{NNN}` 형식을 쓴다).
- `reference`는 `{YYYY-MM-DD}-{slug}` 형태를 쓴다. **flat이다** — `concept`와 같은 이유로 하위 디렉토리를 두지 않는다(분류는 폴더가 아니라 링크 그래프가 한다).
- `concept`는 날짜를 붙이지 않는다 — 개념은 특정 시점에 묶이지 않는다.

## 검증

작성 후 아래가 자동으로 검사된다([[spec-004-graph-validation|KDEV-SPEC-004]]).

| 규칙 | 검사 |
|---|---|
| L1 | 본문 `[[]]`·`up:` 타겟이 실존 |
| L2 | 필수 필드 · type 허용값 · stem/alias 전역 유일 |
| L3 | `up:`의 stem이 본문 `[[]]`에도 존재 |
| L4 | `up:` 방향(상류만) · `idea` up 금지 |
| L5 | orphan — **층마다 의미가 다르다** (아래) |
| L6 | 활성 노트가 `archived`를 `up` 의존 |

L5는 층별로 판정이 다르다.

- `reference` orphan → **위반이 아니다.** "아직 개념으로 정리되지 않은 자료" = 미소화 큐
- `concept` orphan → 성립하지 않음
- `permanent` orphan → 개념을 엮지 않았다는 경고
- 제품 문서 · `idea` → 검사 제외

실행 지점: pre-commit · 발행 전(Apply Executor) · 부팅 · 런타임 reload.

## 자동 유입과의 관계

승인 파이프라인([[spec-008-gate-chain|KDEV-SPEC-008]])이 만드는 노트도 **같은 규칙을 받는다.** AI가 초안을 내고 사람이 게이트에서 승인하지만, 형식·계보·필수 필드는 동일하게 검증된다.

### 규칙은 프롬프트가 아니라 레포에 있다

AI 에이전트는 레포를 읽을 수 있는 상태로 실행된다(worker 가 repo 를 마운트하고 cwd 가 레포 루트다). 따라서 **형식 규칙을 프롬프트에 복사해 넣지 않는다.**

```text
프롬프트   →  "무엇을 만들라" + 입력 자료
레포 문서  →  "어떻게 생겼는가"  ← 이 문서와 templates/knowledge/
```

진입 경로는 `CLAUDE.md → agent.md → 이 문서 → templates/knowledge/`다. 규칙이 바뀌면 **이 문서 하나만** 고치면 사람과 AI가 같은 것을 본다. 프롬프트나 skill 에 복사해 두면 그 순간 SoT 가 둘이 되고, 한쪽만 고쳐지는 날 조용히 어긋난다.

`templates/knowledge/`의 템플릿은 사람용 참고자료가 아니라 **형식의 SoT**다. 템플릿이 검증을 통과하지 못하면 AI 산출물도 통과하지 못한다.

손으로 직접 쓰는 경로는 계속 유효하다. 게이트는 자동 유입에 대한 장치다.

### 미소화 큐는 부채가 아니다

개념으로 올라가지 않은 `reference`는 검증에서 **미소화 큐**로 집계된다. 이것은 위반이 아니라 **파이프라인의 입력 백로그**다.

- **손으로 일괄 정제하지 않는다.** 큐에서 하나 골라 파이프라인에 태우는 것이 정상 경로다.
- **큐 크기를 경보로 쓰지 않는다.** 줄지 않아도 문제가 아니다 — 읽은 자료가 전부 개념이 되어야 할 이유는 없다.
- 자료 성격에 따라 뽑을 것이 다르다. 학습 노트는 개념이 바로 나오지만, 문제 풀이 기록은 문제가 아니라 **패턴**을 뽑아야 한다.

## 한 곳 원칙

- 같은 사실은 한 곳에만 둔다 — 개념 상세는 concept, 자료 요지는 reference, 판단은 permanent.
- `layer`처럼 도출 가능한 값은 저장하지 않는다.
- 규칙은 이 문서, 검증 계약은 spec. 서로 복사하지 않는다.
